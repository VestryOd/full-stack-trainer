# Replication, Transactions, and Consistency

## Реплика-сет — минимальная продакшен-конфигурация

Одиночный `mongod` в продакшене не используется: без реплик нет ни отказоустойчивости, ни транзакций (они требуют реплика-сет). Стандартная конфигурация — три узла: один primary и две secondary.

```txt
Реплика-сет: одна точка записи, несколько копий данных

┌─────────────────────────────────────────────┐
│ приложение (драйвер знает всех членов сета) │
└─────────────────────────────────────────────┘
                      │  все записи — только на primary
                      ▼
   ┌─────────────────────────────────────┐
   │ PRIMARY                             │
   │ применяет запись и пишет её в oplog │
   │ (local.oplog.rs — capped-коллекция) │
   └─────────────────────────────────────┘
                      │  secondaries тянут oplog и применяют операции
                      ▼
┌─────────────────┐    ┌────────────────────┐
│ SECONDARY       │    │ SECONDARY          │
│ копия данных,   │    │ кандидат в primary │
│ может отставать │    │ при выборах        │
└─────────────────┘    └────────────────────┘

primary недоступен → выборы (несколько секунд) → новый primary из большинства
размер oplog задаёт окно, за которое отставший узел ещё может догнать
```

```txt
Как это работает:
  - ВСЕ записи идут только на primary. Secondary принимает чтения,
    но не записи
  - primary записывает каждую применённую операцию в oplog —
    capped-коллекцию local.oplog.rs
  - операции в oplog идемпотентны: {$inc: {views: 1}} превращается
    в {$set: {views: 43}}, поэтому повторное применение безопасно
  - secondaries непрерывно тянут oplog и применяют операции у себя
  - размер oplog определяет окно восстановления: узел, отставший
    больше чем на это окно, не сможет догнать инкрементально и
    потребует полной синхронизации (initial sync)
```

Выборы (elections) и автоматический failover достаточно понимать на уровне механики, без протокола:

```txt
  - члены сета обмениваются heartbeat каждые 2 секунды
  - если primary не отвечает ~10 секунд, secondaries инициируют
    выборы: новым primary становится узел, за который проголосовало
    БОЛЬШИНСТВО членов сета
  - «большинство» — причина, по которой узлов делают нечётное
    число: в сете из 3 узлов кластер выживает потерю одного;
    в сете из 2 — потеря любого лишает большинства, и записи
    прекращаются
  - на время выборов (обычно секунды) записи невозможны. Драйвер это
    переживает сам: retryable writes включены по умолчанию, и
    одиночная запись будет повторена автоматически
  - специальные роли: arbiter голосует, но не хранит данные (обычно
    признак экономии, которая позже мешает: majority-запись такому
    сету труднее подтвердить); hidden/delayed члены — для бэкапов
    и аналитики
```

## Read preference: откуда читать

```js
// в строке подключения
mongodb+srv://host/db?readPreference=secondaryPreferred

// или для конкретного запроса
db.posts.find(f).readPref("secondaryPreferred")
```

```txt
primary             — только primary (по умолчанию)
primaryPreferred    — primary, при его отсутствии — secondary
secondary           — только secondary
secondaryPreferred  — secondary, если их нет — primary
nearest             — узел с минимальной сетевой задержкой
```

Чтение с secondary выглядит бесплатным способом «разгрузить базу», и именно поэтому это одна из самых частых ошибок:

```txt
1. Ломается read-your-own-write. Пользователь сохранил профиль
   (запись на primary) и сразу открыл страницу (чтение с secondary,
   которая ещё не применила операцию) → он видит СТАРЫЕ данные и
   считает, что сохранение не сработало.

2. Репликационный лаг непредсказуем. В норме это миллисекунды, но
   при пиковой записи, долгой индексной сборке или медленном диске
   secondary отстаёт на секунды и минуты. Ограничить можно только
   выбор узла: maxStalenessSeconds: 90 (драйвер не будет читать
   с узлов, отставших сильнее).

3. Масштабирования записи не происходит. Каждая secondary применяет
   ТУ ЖЕ запись, что и primary: добавление реплик не увеличивает
   пропускную способность на запись. Реплики масштабируют только
   чтение — и то ценой устаревших данных.

Когда чтение с secondary уместно:
  - отчёты и аналитика (данные за прошлый день не устареют)
  - тяжёлые агрегации, которые не должны конкурировать с
    продуктовой нагрузкой (см. [Aggregation Pipeline])
  - гео-распределённое чтение через nearest/тэги
  - экспорт данных, бэкап-джобы
```

Если нужны и разгрузка primary, и гарантия «увижу свою запись», решение — causally consistent session: драйвер передаёт логическое время операции, и чтение ждёт, пока узел его догонит.

```js
const session = client.startSession();   // causalConsistency: true по умолчанию
await posts.updateOne({ _id }, { $set: { title } }, { session });
const fresh = await posts.findOne({ _id }, { session });  // увидит запись
```

## Write concern: что значит «запись подтверждена»

```txt
                     Что на самом деле значит «запись подтверждена»
┌────────────────────────┬───────────────────────────────┬─────────────────────────────┐
│ настройка              │ подтверждение получено, когда │ чем рискуете                │
├────────────────────────┼───────────────────────────────┼─────────────────────────────┤
│ w: 0                   │ драйвер отправил пакет        │ запись могла не примениться │
├────────────────────────┼───────────────────────────────┼─────────────────────────────┤
│ w: 1                   │ применил primary              │ откат при failover          │
├────────────────────────┼───────────────────────────────┼─────────────────────────────┤
│ w: 1, j: true          │ primary записал в журнал      │ откат при failover          │
├────────────────────────┼───────────────────────────────┼─────────────────────────────┤
│ w: "majority"          │ применило большинство узлов   │ выше задержка               │
├────────────────────────┼───────────────────────────────┼─────────────────────────────┤
│ w: "majority", j: true │ большинство записало в журнал │ самая высокая задержка      │
└────────────────────────┴───────────────────────────────┴─────────────────────────────┘
              начиная с MongoDB 5.0 значение по умолчанию — w: "majority"
         wtimeout ограничивает ожидание, но НЕ отменяет уже применённую запись
```

```js
await db.collection("orders").insertOne(doc, {
  writeConcern: { w: "majority", j: true, wtimeout: 5000 }
});
```

```txt
Разбор параметров:
  w  — сколько узлов должны подтвердить операцию.
       1 — только primary; "majority" — большинство членов сета;
       0 — не ждать подтверждения вообще (fire-and-forget)
  j  — ждать, пока операция попадёт в журнал (на диск), а не
       останется только в памяти. Защищает от потери при внезапном
       выключении узла
  wtimeout — сколько ждать подтверждения. По истечении драйвер
       получает ошибку, но операция МОЖЕТ БЫТЬ УЖЕ ПРИМЕНЕНА:
       wtimeout отменяет ожидание, а не запись
```

Ключевой сценарий, который объясняет разницу между `w: 1` и `w: "majority"`:

```txt
  1. клиент пишет с w: 1 → primary применил, подтвердил клиенту
  2. secondaries ещё не получили эту операцию из oplog
  3. primary падает
  4. выборы: новый primary выбран из тех, кто НЕ видел операцию
  5. старый узел возвращается и обнаруживает у себя операцию,
     которой нет в истории нового primary → он ОТКАТЫВАЕТ её
     (rollback), складывая в файл на диске

Итог: клиент получил «успех», а данных в базе нет. Именно от этого
защищает w: "majority": подтверждение приходит, когда операцию
видело большинство, а значит любой будущий primary её содержит.

Поэтому начиная с MongoDB 5.0 write concern по умолчанию —
w: "majority". На старых кластерах и в старых приложениях
по умолчанию был w: 1, и это надо проверять.
```

## Read concern: какие данные считать существующими

```txt
local         — вернуть последние данные узла, даже если они ещё не
                подтверждены большинством (то есть могут быть
                откачены). Значение по умолчанию для чтений
                с primary
available     — как local, но на шардированном кластере не ждёт
                консистентности с config servers (быстро, но может
                вернуть «сиротские» документы)
majority      — вернуть только те данные, которые подтверждены
                большинством и потому НЕ будут откачены
linearizable  — самая строгая для одного документа: гарантирует, что
                чтение видит все успешные записи, завершившиеся до
                него; дорого, требует primary и w: "majority"
snapshot      — чтение согласованного снапшота; используется
                в транзакциях
```

Реальные гарантии определяет комбинация трёх настроек, и это именно тот вопрос, который отделяет «читал документацию» от «эксплуатировал»:

```txt
w: "majority" + readConcern: "majority" + readPreference: primary
  → строго: подтверждённые данные не откатятся, чтения их видят

w: 1 + readConcern: "local"
  → быстро, но подтверждённая запись может исчезнуть при failover

w: "majority" + readPreference: secondaryPreferred, без сессии
  → запись надёжна, но своё же изменение можно не увидеть сразу

w: "majority" + causally consistent session + secondary
  → надёжно и read-your-own-write работает, ценой ожидания
    догона узла
```

Формулировка для интервью: write concern отвечает на вопрос «когда считать запись состоявшейся», read concern — «какие данные считать существующими», read preference — «у кого спрашивать». Три независимые ручки, и «консистентность» без указания всех трёх — пустое слово.

## Multi-document транзакции

Транзакции появились в 4.0 для реплика-сетов и в 4.2 для шардированных кластеров. Утверждение «в MongoDB нет транзакций» — устаревшее.

```js
const session = client.startSession();
try {
  await session.withTransaction(async () => {
    // Внутри транзакции ОБЯЗАТЕЛЬНО передавать session в каждую операцию
    const post = await posts.findOneAndUpdate(
      { _id: postId },
      { $inc: { "stats.comments": 1 } },
      { session, returnDocument: "after" }
    );
    if (!post) throw new Error("post not found");   // throw → abort

    await comments.insertOne(
      { postId, body, author, createdAt: new Date() },
      { session }
    );
  }, {
    readConcern:  { level: "snapshot" },
    writeConcern: { w: "majority" }
  });
} finally {
  await session.endSession();
}
```

```txt
Что важно про API:
  - withTransaction сам делает ретраи на TransientTransactionError
    (конфликт записи, смена primary) и на
    UnknownTransactionCommitResult. Писать retry-цикл руками не надо
  - операция БЕЗ { session } внутри блока выполняется ВНЕ транзакции.
    Это самая частая ошибка: половина операций откатывается,
    половина остаётся
  - callback может вызваться повторно, поэтому он должен быть
    идемпотентным: никаких «отправить письмо» и «списать с внешнего
    API» внутри
  - throw внутри callback → abort всей транзакции
```

```txt
Цена транзакций:
  - изоляция снапшота: параллельная запись в те же документы даёт
    WriteConflict, и транзакция ретраится — под конкуренцией это
    заметная потеря пропускной способности
  - лимит времени: 60 секунд по умолчанию
    (transactionLifetimeLimitSeconds). Длинная транзакция будет
    прервана сервером
  - удерживаемые изменения занимают WiredTiger-кэш до коммита
  - в шардированном кластере транзакция становится распределённой
    (двухфазный коммит между шардами) — на порядок дороже
  - долгая транзакция удерживает снапшот и мешает уборке старых
    версий
```

Когда транзакция действительно нужна:

```txt
  - инвариант охватывает несколько ДОКУМЕНТОВ, и рассинхронизация
    недопустима: списать со счёта A и зачислить на счёт B
  - создать сущность и связанную с ней запись в другой коллекции,
    где «половина» — это порча данных: заказ + резерв склада
  - удалить агрегат вместе с его дочерними документами так, чтобы
    не осталось висячих ссылок, когда это критично

Когда транзакция НЕ нужна, а её всё равно пишут:
  - изменение одного документа — он уже атомарен, даже если меняется
    десять полей и массив (см. [CRUD and Query Operators])
  - инкремент счётчика — это $inc
  - «прочитать, проверить, записать» — это findOneAndUpdate
    с условием в фильтре
  - обновление денормализованных копий, где допустима eventual
    consistency (Extended Reference, Subset — см. [Schema Design:
    Embedding vs Referencing])
```

Отсюда главная мысль раздела: транзакции в MongoDB — не замена проектированию схемы. Если агрегат спроектирован так, что инвариант живёт внутри одного документа, транзакция не нужна вообще. Если транзакции требуются на каждый второй запрос — это сигнал, что схема реляционная и стоит пересмотреть либо схему, либо выбор БД (см. [Document Model and Use Cases]).

## Sharding — обзорно

Реплика-сет решает отказоустойчивость, но не объём: все данные лежат на каждом узле, и все записи идут через один primary. Когда данные или поток записи перестают влезать в один узел, коллекцию шардируют — распределяют по нескольким реплика-сетам.

```txt
Компоненты шардированного кластера:
  shard          — реплика-сет, хранящий подмножество данных
  config servers — реплика-сет с метаданными: какой диапазон
                   ключей на каком шарде
  mongos         — роутер, к которому подключается приложение;
                   он знает распределение и направляет запросы
```

Ключевое решение — **shard key**: поле (или комбинация полей), по которому данные распределяются. Оно определяет производительность кластера, и менять его дорого (`reshardCollection` появился в 5.0, но это тяжёлая операция).

```txt
 TARGETED: фильтр содержит shard key      SCATTER-GATHER: shard key отсутствует
┌────────────────────────────────────┐    ┌────────────────────────────────┐
│ find({ tenantId: "acme", _id: x }) │    │ find({ status: "published" })  │
│                                    │    │                                │
│ mongos → шард 2                    │    │ mongos → все шарды → слияние   │
│                                    │    │                                │
│ шард 1  ·  [шард 2]  ·  шард 3     │    │ [шард 1] · [шард 2] · [шард 3] │
└────────────────────────────────────┘    └────────────────────────────────┘
     запрос уходит на ОДИН шард;            каждый шард выполняет запрос,
  масштабируется линейно с их числом      mongos сливает; сортировка — тоже на нём
```

```js
sh.shardCollection("blog.posts", { tenantId: 1, _id: 1 })   // ranged
sh.shardCollection("blog.events", { _id: "hashed" })        // hashed
```

```txt
ranged (по диапазонам значений)
  + запросы по диапазону ключа уходят на один-два шарда
  + данные одного tenant/пользователя лежат рядом
  - монотонно возрастающий ключ (ObjectId, timestamp) отправляет
    ВСЕ вставки на один шард — это hot shard, классическая ошибка

hashed (по хешу значения)
  + вставки распределяются равномерно даже по монотонному полю
  - диапазонные запросы становятся scatter-gather: соседние
    значения лежат на разных шардах
```

Последствия плохого выбора shard key — то, что спрашивают на senior-интервью:

```txt
hot shard          — ключ монотонный при ranged-распределении:
                     весь поток записи идёт в один шард, остальные
                     простаивают

jumbo chunks       — низкая кардинальность ключа (country, status):
                     все документы с одним значением обязаны лежать
                     вместе, чанк вырастает и не может быть разделён,
                     балансировка ломается

scatter-gather     — фильтр без shard key: mongos рассылает запрос
                     на ВСЕ шарды и сливает результаты. Латентность
                     определяется самым медленным шардом, а
                     добавление шардов делает такие запросы хуже,
                     а не лучше

ограничения        — уникальный индекс возможен только по shard key
                     (или его префиксу); shard key нельзя изменить
                     в документе (кроме случаев с 4.2+ и ценой);
                     сортировка без shard key выполняется на mongos
```

Практический критерий выбора: ключ должен быть (1) высокой кардинальности, (2) равномерно распределять запись, (3) присутствовать в большинстве запросов чтения. Составной ключ вида `{ tenantId: 1, _id: 1 }` часто удовлетворяет всем трём: tenant-изоляция даёт targeted-запросы, `_id` внутри — кардинальность.

И честная оговорка: шардинг — это ответ на проблему объёма, а не на проблему медленных запросов. Медленный запрос на шардированном кластере становится медленным на N шардах. Сначала индексы и схема (см. [Indexes and Query Performance]), потом шардинг.

## Как отвечать на вопрос про гарантии

```txt
Вопрос «какие гарантии консистентности даёт MongoDB» не имеет
однозначного ответа — и это правильный ответ. Каркас:

1. Один документ атомарен всегда — это базовая гарантия, из которой
   строится всё остальное.

2. Долговечность записи задаётся write concern. По умолчанию
   (5.0+) w: "majority": подтверждённая запись не будет откачена.

3. Видимость данных задаётся read concern и read preference.
   Чтение с primary + local — свежо, но данные теоретически могут
   быть откачены; majority — только подтверждённое; чтение
   с secondary — eventual consistency.

4. Между документами и коллекциями атомарности нет, пока нет
   транзакции. Транзакции есть, они дают snapshot-изоляцию, но их
   цена — конфликты и ретраи, поэтому правильная схема их избегает.

5. Причинная согласованность («увижу свою запись») достигается
   сессиями, а не выбором узла.
```

## Типичные ошибки на интервью

- **«В MongoDB нет транзакций»** — есть с 4.0 (реплика-сет) и 4.2 (шардированный кластер). Правильная формулировка: транзакции есть, дают snapshot-изоляцию, но стоят дорого, и хорошая схема делает их редкими.

- **«Чтение с secondary разгружает базу без последствий»** — это eventual consistency: пользователь может не увидеть свою же запись. Плюс лаг непредсказуем. Ограничивается `maxStalenessSeconds`, лечится causally consistent сессией.

- **«Реплики масштабируют запись»** — каждая secondary применяет те же операции, что primary. Реплики дают отказоустойчивость и масштабирование чтения; запись масштабирует только шардинг.

- **«Запись прошла — значит она в базе»** — при `w: 1` подтверждённая запись может быть откачена при failover. Гарантию даёт `w: "majority"`, которое с 5.0 стоит по умолчанию (но не на старых кластерах).

- **«`wtimeout` отменяет запись»** — он отменяет только ожидание подтверждения. Операция может быть уже применена, поэтому получить ошибку `wtimeout` и повторить запись — путь к дублям, если операция не идемпотентна.

- **«Транзакция нужна, чтобы обновить два поля одного документа»** — одна операция над одним документом атомарна сама по себе, включая массивы и вложенные объекты.

- **«Внутри `withTransaction` всё автоматически в транзакции»** — только операции, которым передана `session`. Забытая `session` тихо работает вне транзакции.

- **«Транзакцию можно держать сколько нужно»** — 60 секунд по умолчанию, дальше сервер её прервёт; и всё это время изменения занимают кэш и удерживают снапшот.

- **«ObjectId — хороший shard key»** — он монотонный: при ranged-распределении весь поток вставок идёт в один шард (hot shard). Нужен `hashed` или составной ключ с tenant-полем впереди.

- **«Шардинг ускорит медленные запросы»** — запрос без shard key превращается в scatter-gather по всем шардам, и добавление шардов делает его хуже. Сначала индексы и схема, потом шардинг.
