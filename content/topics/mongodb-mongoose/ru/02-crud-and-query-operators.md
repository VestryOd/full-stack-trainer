# CRUD и операторы запросов

## Фильтр — это документ, а не строка запроса

CRUD — это четыре базовые операции над данными: create, read, update, delete, то есть создание, чтение, обновление и удаление. Текстового языка запросов для них в MongoDB нет. И фильтр, и обновление, и проекция — это документы BSON. BSON — двоичная типизированная форма JSON, в которой MongoDB хранит и передаёт данные.

Отсюда следует то, что часто удивляет после SQL — текстового языка запросов к реляционным базам. Запрос здесь собирается как обычный объект, а значит его легко строить динамически. Так же легко собрать в него пользовательский ввод: клиент прислал `{ $ne: null }` там, где ждали строку, и получился фильтр, а не значение. Поэтому вход обязан проходить валидацию.

```js
// Полный набор операций записи и чтения. Единственное различие в форме
// вызова — множественное число: One работает с первым подошедшим документом.
db.posts.insertOne({ title: "Индексы", authorId: userId })
db.posts.insertMany([{ ... }, { ... }])

db.posts.find({ authorId: userId })          // курсор
db.posts.findOne({ slug: "mongodb-indexes" }) // документ или null

db.posts.updateOne({ _id: id }, { $set: { title: "Новый" } })
db.posts.updateMany({ authorId: userId }, { $set: { archived: true } })
db.posts.replaceOne({ _id: id }, { title: "Новый", authorId: userId })

db.posts.deleteOne({ _id: id })
db.posts.deleteMany({ archived: true })

// Отдельное семейство: атомарно изменить и вернуть документ
db.posts.findOneAndUpdate({ _id: id }, { $inc: { "stats.views": 1 } })
db.posts.findOneAndDelete({ _id: id })
db.posts.findOneAndReplace({ _id: id }, { ... })
```

```txt
Что возвращают операции записи:
  insertOne   → { acknowledged, insertedId }
  updateOne   → { matchedCount, modifiedCount, upsertedId }
  deleteOne   → { acknowledged, deletedCount }

matchedCount ≠ modifiedCount: документ найден, но $set записал то же
значение → matched 1, modified 0. Поэтому проверять надо именно то,
что нужно: «документа не было» — это matchedCount === 0, а не
modifiedCount === 0.
```

## Операторы выборки

Фильтр собирается из операторов, и их пять семейств: равенство, сравнение, проверка наличия поля и типа, логические операторы и регулярные выражения.

```js
// Равенство — оператор не нужен: {field: value} это неявный $eq
db.posts.find({ status: "published" })

// Сравнение
db.posts.find({ "stats.views": { $gte: 100, $lt: 1000 } })  // и то, и то
db.posts.find({ status: { $in: ["published", "featured"] } })
db.posts.find({ status: { $nin: ["draft"] } })
db.posts.find({ status: { $ne: "draft" } })

// Наличие поля и тип — прямое следствие отсутствия жёсткой схемы
db.posts.find({ coverUrl: { $exists: false } })   // поля нет вообще
db.posts.find({ coverUrl: null })                 // поля нет или он null
db.posts.find({ publishedAt: { $type: "string" } })  // ищем «сломанные»
                                                     // документы

// Логические операторы
db.posts.find({ $or: [{ status: "published" }, { authorId: userId }] })
db.posts.find({ $and: [{ tags: "mongo" }, { tags: "perf" }] })  // см. $all
db.posts.find({ tags: { $not: { $size: 0 } } })

// Регулярные выражения
db.posts.find({ slug: { $regex: "^mongodb-", $options: "i" } })
db.posts.find({ slug: /^mongodb-/ })   // то же самое короче
```

Два места, где легко ошибиться:

```txt
{ coverUrl: null } ≠ { coverUrl: { $exists: false } }
  null находит и документы без поля, и документы с полем = null —
  оба случая. Если нужно строго «поля нет»: { $exists: false }.
  Если нужно строго «есть и null»: { coverUrl: { $type: "null" } }.

$regex использует индекс только при якоре в начале и только без
регистронезависимости. То есть /^mongodb-/ индекс возьмёт, а
/^mongodb-/i и /indexes/ — нет; про это статья 04 про индексы. Поиск
«содержит подстроку» на большой коллекции через $regex заканчивается
COLLSCAN — так называется план полного сканирования коллекции, когда
сервер читает каждый документ. Для такого поиска нужен текстовый
индекс или Atlas Search.
```

## Массивы: точечная нотация против $elemMatch

Массив в фильтре ведёт себя не так, как ожидает человек с опытом SQL. Условие на поле массива считается выполненным, если ему соответствует **хотя бы один** элемент. И каждое условие проверяется независимо от остальных.

```js
// Массив скаляров: фильтр по значению находит элемент, а не весь массив
db.posts.find({ tags: "mongodb" })              // есть такой тег
db.posts.find({ tags: ["mongodb", "perf"] })    // массив равен ровно
                                                // этому, с тем же порядком
db.posts.find({ tags: { $all: ["mongodb", "perf"] } })  // содержит оба
db.posts.find({ tags: { $size: 3 } })           // ровно 3 элемента
db.posts.find({ "tags.0": "mongodb" })          // первый элемент
```

С массивом объектов начинается классическая ловушка интервью:

```txt
        Точечная нотация проверяет условия по отдельности
┌──────────────────────────────────────────────────────────────────┐
│ документ в коллекции posts:                                      │
│ { _id: 1, ratings: [ { userId: "a", score: 5 },                  │
│                      { userId: "b", score: 2 } ] }               │
├──────────────────────────────────────────────────────────────────┤
│ { "ratings.score": { $gte: 4 } }                                 │
│   → совпадение: хотя бы один элемент имеет score >= 4            │
├──────────────────────────────────────────────────────────────────┤
│ { "ratings.userId": "b", "ratings.score": { $gte: 4 } }          │
│   → совпадение есть, и это ловушка: условия выполнены            │
│     разными элементами — userId вторым, score первым             │
├──────────────────────────────────────────────────────────────────┤
│ { ratings: { $elemMatch: { userId: "b", score: { $gte: 4 } } } } │
│   → совпадения нет: нужен один элемент, проходящий оба           │
│     условия (именно это обычно и имеют в виду)                   │
└──────────────────────────────────────────────────────────────────┘
 правило: два и более условия на один элемент — всегда $elemMatch
```

У практического правила две половины. Одно условие на массив — это точечная нотация. Два и больше условий, которые должны выполниться на **одном** элементе, требуют `$elemMatch`. Тот же оператор нужен и когда условие одно, но составное:

```js
// Диапазон на одном элементе: без $elemMatch это «есть элемент >= 4
// И есть элемент <= 5», возможно разные
db.posts.find({ ratings: { $elemMatch: { score: { $gte: 4, $lte: 5 } } } })
```

## Операторы обновления

Второй аргумент `updateOne` — не новый документ, а набор инструкций. Поле, которого нет в инструкциях, остаётся как было.

```js
// Скалярные поля
{ $set:    { title: "Новый", "stats.views": 0 } }  // точечная нотация
                                                   // создаёт вложенность
{ $unset:  { coverUrl: "" } }        // удалить поле (значение игнорируется)
{ $inc:    { "stats.views": 1, "stats.likes": -1 } }  // атомарный инкремент
{ $mul:    { price: 1.2 } }
{ $min:    { lowestPrice: 42 } }     // записать, только если меньше текущего
{ $max:    { peakViews: 1200 } }
{ $rename: { body: "content" } }
{ $currentDate: { updatedAt: true } }
{ $setOnInsert: { createdAt: new Date() } }   // только при upsert-вставке

// Массивы
{ $push:     { tags: "mongodb" } }
{ $push:     { comments: { $each: [c1, c2], $sort: { createdAt: -1 },
                           $slice: 20 } } }   // добавить, отсортировать,
                                              // оставить 20 — в одном шаге
{ $addToSet: { tags: "mongodb" } }   // добавить, если ещё нет
{ $pull:     { tags: "legacy" } }    // удалить по условию
{ $pull:     { comments: { authorId: bannedId } } }
{ $pop:      { tags: 1 } }           // 1 — последний, -1 — первый
```

Комбинация `$push` + `$slice` + `$sort` — рабочий приём против неограниченного роста массива. Документ хранит только последние N элементов. В статье 03 про проектирование схемы это называется паттерном Subset.

Для обновления элемента внутри массива есть три позиционных оператора:

```js
// $ — первый элемент, подошедший под фильтр запроса
db.posts.updateOne(
  { _id: postId, "comments._id": commentId },
  { $set: { "comments.$.body": "отредактировано" } }
)
// требование: поле массива обязано присутствовать в фильтре, иначе
// ошибка «The positional operator did not find the match»

// $[] — все элементы массива
db.posts.updateMany({}, { $set: { "comments.$[].moderated": false } })

// $[ident] — все элементы, подошедшие под arrayFilters
db.posts.updateOne(
  { _id: postId },
  { $set: { "comments.$[c].hidden": true } },
  { arrayFilters: [{ "c.score": { $lt: -5 } }] }
)
```

`$` меняет только первый совпавший элемент: если под фильтр подходят три, обновится один. Это ещё одна причина держать `_id` у вложенных объектов — точное совпадение вместо «первый похожий».

## updateOne против replaceOne

`updateOne` меняет те поля, которые вы назвали. `replaceOne` подменяет документ целиком на переданный, и всё, что вы не передали, пропадает.

```js
// updateOne — частичное обновление: остальные поля не тронуты
db.posts.updateOne({ _id: id }, { $set: { title: "Новый" } })

// replaceOne — документ целиком заменяется на переданный (кроме _id)
db.posts.replaceOne({ _id: id }, { title: "Новый" })
// → authorId, tags, stats, createdAt из документа удалены
```

```txt
Классический баг: обработчик PUT /posts/:id, который пишет
req.body через replaceOne. Update без операторов делает то же
самое: драйверы трактуют документ без операторов как замену.
Клиент прислал { title }, а из документа исчезли authorId и
createdAt. Дальше страница поста ломается на отсутствующем
авторе, а причину ищут в чтении, не в записи.

Правило: семантика PUT в REST (representational state transfer —
обычный стиль HTTP-интерфейсов) это не replaceOne. Даже для PUT
надёжнее $set по явному белому списку полей, чем замена
документа телом запроса.
```

## upsert и гонка при вставке

`upsert: true` означает: если фильтр ничего не нашёл — вставить документ. Новый документ собирается из полей-равенств фильтра плюс инструкций обновления.

```js
db.postStats.updateOne(
  { postId: postId, day: "2026-08-13" },        // равенства → попадут в
                                                // новый документ
  {
    $inc: { views: 1 },                          // 1 при вставке
    $setOnInsert: { createdAt: new Date() }      // только при вставке
  },
  { upsert: true }
)
// вставит { postId, day, views: 1, createdAt } или увеличит счётчик у
// существующего — одним обращением, без «сначала find, потом решаем»
```

Важно, что в новый документ попадают только равенства. Фильтр `{ views: { $gt: 5 } }` в документ ничего не добавит, потому что операторы сравнения при вставке игнорируются.

```txt
Гонка (race condition). Без уникального индекса upsert
не атомарен как «проверил и вставил»:

  A: не нашёл { postId, day } → решает вставить
  B: не нашёл { postId, day } → решает вставить
  → в коллекции два документа на одну пару (postId, day)

Уникальный индекс — единственная реальная защита:
  db.postStats.createIndex({ postId: 1, day: 1 }, { unique: true })

С ним второй upsert получит ошибку duplicate key с кодом E11000.
Это ожидаемый исход, а не авария. Сервер сам повторяет операцию
для одиночного upsert, а в прикладном коде остаётся приём
«поймать E11000 → повторить один раз». Как превратить E11000
в ошибку API, показано в статье 08.
```

## Проекции: читать только то, что нужно

Проекция — это третий документ в вызове, и он перечисляет, какие поля вернутся.

```js
// Включение: _id возвращается всегда, если не выключить явно
db.posts.find({ authorId: userId }, { title: 1, slug: 1, _id: 0 })

// Исключение: всё, кроме перечисленного
db.users.find({}, { passwordHash: 0, tokens: 0 })

// Смешивать включение и исключение нельзя (кроме _id):
db.posts.find({}, { title: 1, body: 0 })   // → ошибка

// Проекции по массивам
db.posts.find({}, { comments: { $slice: 5 } })        // первые 5
db.posts.find({}, { comments: { $slice: -5 } })       // последние 5
db.posts.find({ "comments.authorId": userId },
              { "comments.$": 1 })                     // первый совпавший
db.posts.find({}, { comments: { $elemMatch: { score: { $gt: 10 } } } })
```

Проекция — это не только меньше трафика. Если все нужные поля есть в индексе, запрос может быть выполнен без обращения к документам вообще. Это покрывающий запрос (covered query), и разобран он в статье 04 про индексы.

Обратное тоже верно. Привычка тянуть документ целиком в Mongoose стоит, кроме трафика, ещё и превращения сырых документов в объекты модели. Про это статья 08, раздел про `lean()`.

## Курсоры и порции документов

`find` не возвращает данные — он возвращает курсор. Документы приходят порциями, их называют батчами: первый батч вместе с ответом на запрос, следующие — по `getMore`.

```txt
find → сервер готовит курсор, отдаёт первый батч (101 документ или
       ~16 МБ, что наступит раньше)
       ↓
драйвер отдаёт документы приложению по одному
       ↓
батч закончился → getMore → следующий батч (по умолчанию до 16 МБ)
       ↓
курсор исчерпан → закрыт автоматически

Курсор без обращений живёт 10 минут, потом сервер его закрывает.
«cursor id not found» в логах — обычно медленная обработка батча
в приложении или забытый незакрытый курсор.
```

```js
// Node.js driver: итерация без загрузки всей выборки в память
const cursor = db.collection("posts").find({ status: "published" });
for await (const post of cursor) {
  await handle(post);         // документы приходят батчами, память ровная
}

// toArray() материализует всю выборку в массив. На большой коллекции
// это нехватка памяти и убитый процесс (OOM, out of memory).
// Допустимо только после явного limit.
const page = await db.collection("posts").find(f).limit(20).toArray();

// batchSize управляет размером батча — полезно, когда обработка
// одного документа долгая (иначе курсор простаивает и «стареет»)
db.collection("posts").find(f).batchSize(50);
```

Пагинация через `skip` выглядит удобно и деградирует линейно: `skip(100000)` заставляет сервер пройти и выбросить 100 000 документов. Для «бесконечной прокрутки» правильный инструмент — пагинация по ключу (keyset) по `_id` или по паре (`sort`-поле, `_id`). Сортировка по `_id` и так почти совпадает с сортировкой по времени создания, как показано в статье 01.

```js
// вместо .skip(pageSize * n).limit(pageSize)
db.posts.find({ _id: { $lt: lastSeenId } }).sort({ _id: -1 }).limit(20)
```

## Атомарность на уровне одного документа — фундаментальная гарантия

Любая операция записи над **одним** документом атомарна: либо применены все её изменения, либо ни одно. Это верно для нескольких полей, вложенных объектов и элементов массива сразу, и транзакции для этого не нужно.

```js
// Один атомарный шаг: три поля и элемент массива изменяются вместе.
// Никакой читатель не увидит состояние «комментарий добавлен, но
// счётчик ещё старый».
db.posts.updateOne(
  { _id: postId },
  {
    $push: { comments: { _id: new ObjectId(), body, authorId } },
    $inc:  { "stats.comments": 1 },
    $currentDate: { updatedAt: true }
  }
)
```

Границы гарантии надо называть точно:

```txt
Атомарно:        одна операция над одним документом
Не атомарно:     updateMany по 100 документам — это 100 отдельных
                 атомарных операций; читатель между ними увидит
                 половину обновлённых
Не атомарно:     две операции подряд в коде приложения
                 (даже над одним документом)
Для остального:  транзакции на несколько документов, про них
                 статья 06 про репликацию и транзакции
```

Отсюда главное практическое следствие. Схема «прочитал — изменил — записал» (read-modify-write) в коде приложения — это гонка, а `findOneAndUpdate` — нет.

```txt
Потерянное обновление: прочитал — изменил — записал
┌─────┬─────────────────────┬─────────────────────┐
│ шаг │ процесс A           │ процесс B           │
├─────┼─────────────────────┼─────────────────────┤
│ 1   │ find: views = 100   │                     │
├─────┼─────────────────────┼─────────────────────┤
│ 2   │                     │ find: views = 100   │
├─────┼─────────────────────┼─────────────────────┤
│ 3   │ update: views = 101 │                     │
├─────┼─────────────────────┼─────────────────────┤
│ 4   │                     │ update: views = 101 │
└─────┴─────────────────────┴─────────────────────┘
два увеличения счётчика, результат 101 вместо 102 — одно потеряно
findOneAndUpdate({ _id }, { $inc: { views: 1 } }) — один шаг: 102
```

`findOneAndUpdate` делает всё это атомарно. Сервер находит документ, применяет обновление и возвращает его версию до или после изменения. Именно поэтому он так часто закрывает задачи, для которых в SQL взяли бы транзакцию с `SELECT FOR UPDATE`.

```js
// 1. Атомарный счётчик с возвратом нового значения
const post = await db.collection("posts").findOneAndUpdate(
  { _id: postId },
  { $inc: { "stats.views": 1 } },
  { returnDocument: "after" }    // "before" — старая версия, по умолчанию
);

// 2. Compare-and-set: условие внутри фильтра, а не в коде.
//    Если статус успел измениться — документ не найден, и это ответ.
const claimed = await db.collection("jobs").findOneAndUpdate(
  { _id: jobId, status: "pending" },              // условие-предпосылка
  { $set: { status: "running", startedAt: new Date() } },
  { returnDocument: "after" }
);
if (!claimed) throw new ConflictError("задача уже взята");

// 3. Очередь задач без внешнего брокера: рабочие процессы конкурируют,
//    но задачу получит ровно один — сервер сериализует записи
const job = await db.collection("jobs").findOneAndUpdate(
  { status: "pending", runAt: { $lte: new Date() } },
  { $set: { status: "running", workerId } },
  { sort: { runAt: 1 }, returnDocument: "after" }
);

// 4. Инвариант «не уйти в минус» — тоже в фильтре
const ok = await db.collection("accounts").findOneAndUpdate(
  { _id: accountId, balance: { $gte: amount } },
  { $inc: { balance: -amount } }
);
if (!ok) throw new InsufficientFundsError();
```

Общий приём: перенести проверку из кода в фильтр запроса. Тогда решение «применять или нет» принимает сервер в момент записи, а не приложение по устаревшей копии документа. Оптимистическая блокировка — тот же приём с полем версии; в Mongoose это поле `__v`, и про него статья 08.

Массовые операции с разной формой закрывает `bulkWrite`, и его флаг `ordered` стоит понимать:

```js
await db.collection("posts").bulkWrite([
  { insertOne: { document: { title: "A" } } },
  { updateOne: { filter: { _id: id }, update: { $set: { views: 0 } } } },
  { deleteOne: { filter: { archived: true } } }
], { ordered: false });
// ordered: true (по умолчанию) — по порядку, остановка на первой ошибке
// ordered: false — параллельно на сервере, ошибки собираются и
//                  возвращаются все сразу; быстрее, но порядок не
//                  гарантирован. Атомарности всей пачки нет ни в одном
//                  режиме — атомарен каждый элемент по отдельности.
```

## Типичные ошибки на интервью

- **«В MongoDB нет атомарности»** — атомарность есть, и она фундаментальна. Любая операция над **одним** документом атомарна, включая изменение нескольких полей и массивов. Неверно другое утверждение: что атомарен `updateMany` или две операции подряд.

- **«`{ "ratings.userId": "b", "ratings.score": { $gte: 4 } }` найдёт элемент с обоими условиями»** — условия проверяются независимо, и выполнить их могут разные элементы массива. Нужен `$elemMatch`.

- **«`updateOne` без операторов обновит переданные поля»** — документ без операторов трактуется как замена, и недостающие поля исчезнут. Осознанная замена — это `replaceOne`.

- **«`upsert` защищает от дублей»** — без уникального индекса два параллельных upsert вставят два документа. Защищает индекс, а upsert лишь избавляет от «сначала find, потом insert».

- **«`matchedCount === 0` и `modifiedCount === 0` — одно и то же»** — `$set` того же значения даёт `matched: 1, modified: 0`. «Не найдено» проверяется по `matchedCount`.

- **«`{ field: null }` находит документы без поля»** — находит и без поля, и с `null`. Строгое «поля нет» — это `$exists: false`.

- **«Сначала прочитаю документ, потом посчитаю новое значение и запишу»** — классическое потерянное обновление. Правильно: `$inc`/`$push` в одной операции либо `findOneAndUpdate` с условием в фильтре.

- **«`toArray()` — обычный способ получить результат»** — на большой выборке это загрузка всей коллекции в память процесса. Штатный способ — итерация по курсору; `toArray()` — после `limit`.

- **«`skip`/`limit` — нормальная пагинация»** — `skip` линейно дорожает с номером страницы. Для лент нужна пагинация по ключу: по `_id` или по паре (`sort`-поле, `_id`).
