# Document Model and Use Cases

## Документ вместо строки: единица хранения в MongoDB

В реляционной БД сущность разложена по таблицам, и запрос собирает её обратно джойнами. В MongoDB единица хранения — документ: самодостаточная структура с вложенными объектами и массивами, которую можно записать и прочитать одним обращением.

```js
// коллекция posts — один документ содержит всё, что нужно для страницы поста
{
  _id: ObjectId("66b0f2c14a1e2d0012ab34cd"),
  title: "Индексы в MongoDB",
  slug: "mongodb-indexes",
  author: { _id: ObjectId("66a1..."), name: "Максим", avatar: "/a/12.png" },
  tags: ["mongodb", "performance"],
  stats: { views: 1204, comments: 8 },
  publishedAt: ISODate("2026-07-14T09:12:00Z")
}
```

Тот же пост в PostgreSQL — это `posts` + `users` + `post_tags` + `tags` и три-четыре джойна на чтение. Разница не в «лучше/хуже», а в том, где выполняется сборка сущности: в БД при чтении (SQL) или при записи, один раз (документ).

Коллекция — это контейнер документов, аналог таблицы, но без объявленной структуры. Базовые понятия:

```txt
database    → набор коллекций (аналог schema/database в PostgreSQL)
collection  → набор документов (аналог таблицы, но без DDL)
document    → BSON-объект, максимум 16 МБ (аналог строки)
field       → ключ внутри документа (аналог столбца, но у каждого
              документа свой набор)
```

## BSON — это не JSON: типы, которых в JSON нет

На проводе и на диске MongoDB использует BSON (Binary JSON) — бинарный формат, где у каждого поля есть явный тип и длина. Из этого следуют два практических свойства: движок может пропускать поля, не разбирая их целиком, и типы не теряются при round-trip.

```txt
Типы BSON, которых нет в JSON:
  ObjectId     — 12-байтный идентификатор, значение _id по умолчанию
  Date         — int64, миллисекунды с epoch, ВСЕГДА UTC
  Decimal128   — десятичное число с точной арифметикой (деньги)
  Int32/Int64  — целые фиксированной ширины (в JSON просто "number")
  Double       — IEEE 754, поведение как у number в JS
  Binary       — байты + subtype (например, UUID)
  Regex        — регулярное выражение как значение поля
  Timestamp    — ВНУТРЕННИЙ тип для oplog, не для прикладных дат
```

Три ловушки, которые вырастают из разницы BSON и JSON:

```js
// 1. Числа. В JS все числа — double. Драйвер по умолчанию пишет Double;
//    целое больше 2^53 теряет точность ещё в JS, до записи в базу.
db.posts.insertOne({ views: 9007199254740993 })  // ← уже не то число
db.posts.insertOne({ views: Long("9007199254740993") })  // явный Int64

// 2. Деньги. Double накапливает ошибку округления — как и Float в SQL
//    (см. топик PostgreSQL про numeric/decimal).
db.orders.insertOne({ total: 19.99 })                     // Double — плохо
db.orders.insertOne({ total: Decimal128("19.99") })       // точно
// альтернатива без Decimal128: хранить копейки как Int32/Int64

// 3. Даты. Строка "2026-07-14" — это НЕ Date: по ней не работают
//    диапазонные запросы как по времени, сравнение идёт лексикографически.
db.posts.insertOne({ publishedAt: "2026-07-14" })         // строка
db.posts.insertOne({ publishedAt: new Date("2026-07-14") })  // BSON Date
```

Когда документ уходит наружу через HTTP, BSON сериализуется в Extended JSON — в relaxed-режиме `ObjectId` становится строкой, `Date` — ISO-строкой. Поэтому API возвращает `"_id": "66b0f2c1..."`, а не объект, и обратный маппинг (строка → ObjectId) — задача слоя приложения. `new ObjectId(req.params.id)` на невалидной строке бросает исключение — это первое место, где нужна валидация входа.

## _id и устройство ObjectId

У каждого документа есть `_id`: обязательный, уникальный внутри коллекции, неизменяемый после вставки. Под него автоматически создан уникальный индекс `_id_`, который нельзя удалить. Если `_id` не задан явно, драйвер (не сервер) генерирует `ObjectId`.

```txt
                      ObjectId — 12 байт, а не случайный UUID
┌───────┬─────────────────────────────┬───────────────────────────────────────────┐
│ байты │ что внутри                  │ практическое следствие                    │
├───────┼─────────────────────────────┼───────────────────────────────────────────┤
│ 0-3   │ unix-время в секундах, UTC  │ сортировка по _id ≈ по времени создания   │
├───────┼─────────────────────────────┼───────────────────────────────────────────┤
│ 4-8   │ случайное значение процесса │ два процесса не сгенерируют одинаковый id │
├───────┼─────────────────────────────┼───────────────────────────────────────────┤
│ 9-11  │ счётчик внутри процесса     │ порядок внутри одной секунды сохраняется  │
└───────┴─────────────────────────────┴───────────────────────────────────────────┘
             гранулярность времени — 1 секунда: внутри секунды порядок
                       между разными процессами не определён
```

Практические следствия устройства ObjectId:

```js
// Время создания достаётся из самого _id — отдельное поле createdAt
// не обязательно (но обычно всё равно полезно: его можно бэкфиллить,
// а _id — нет).
ObjectId("66b0f2c14a1e2d0012ab34cd").getTimestamp()  // ISODate(...)

// Сортировка по _id ≈ сортировка по времени создания → бесплатная
// keyset-пагинация «свежие сначала» по уже существующему индексу _id_.
db.posts.find({ _id: { $lt: lastSeenId } }).sort({ _id: -1 }).limit(20)

// Диапазон по времени можно выразить через _id, собрав его из timestamp.
db.posts.find({ _id: { $gte: ObjectId.createFromTime(1750000000) } })
```

Чего ObjectId не гарантирует: строгого глобального порядка (между процессами в пределах одной секунды порядок произволен) и секретности — из значения видно время создания, а соседние документы одного процесса имеют близкие id. Для публичных ссылок, где это важно, используют отдельное непредсказуемое поле, а не `_id`.

Свой `_id` задавать можно и иногда стоит: естественный ключ (`_id: "mongodb-indexes"` для slug, `_id: userId` в коллекции профилей 1:1) убирает лишний индекс и делает связь «одна запись — один ключ» явной. Цена — тот же trade-off локальности индекса, что у UUID в B-tree (см. топик PostgreSQL): монотонный ObjectId вставляется в правый край дерева, случайный ключ — в произвольное место.

## «Schemaless» не значит «без схемы»

Коллекция примет любой документ: без обязательных полей, с полем другого типа, с новым вложенным объектом. DDL нет, `ALTER TABLE` нет, добавление поля — это просто новый `$set`.

```txt
          MongoDB: схема живёт в коде                   PostgreSQL: схема живёт в БД
┌─────────────────────────────────────────────┐    ┌────────────────────────────────────┐
│ коллекция posts                             │    │ таблица posts                      │
│                                             │    │                                    │
│ { title, authorId, tags }                   │    │ title      text   NOT NULL         │
│ { title, authorId }          ← нет tags     │    │ author_id  bigint REFERENCES users │
│ { title, author: {...} }     ← другая форма │    │ tags       text[] DEFAULT ARRAY[]  │
└─────────────────────────────────────────────┘    └────────────────────────────────────┘
   БД примет всё; проверять форму обязан код            БД отвергнет неверную форму,
   (Mongoose-схема или $jsonSchema-валидатор)          но изменение формы = миграция
```

Схема не исчезает — она переезжает из БД в код. Это перенос ответственности, а не бесплатная гибкость:

```txt
Что становится задачей приложения:
  - каждое чтение должно выдерживать документы старой формы
    (поля нет / поле другого типа / вложенность изменилась)
  - «миграция» превращается в ленивый апгрейд при чтении
    или в отдельный batch-скрипт — но не в один DDL
  - аналитика и BI спотыкаются о разнородные документы
  - новый разработчик узнаёт форму данных из кода, а не из \d posts

Что взамен:
  - добавить поле = задеплоить код, без миграции и блокировок
  - разнородные сущности (товары с разным набором атрибутов)
    живут в одной коллекции без EAV и без 40 nullable-столбцов
  - версия документа может отличаться от версии соседа — это
    иногда именно то, что нужно (события, снапшоты, аудит)
```

Дисциплину можно вернуть на уровень БД — валидатором схемы. Это не аналог полноценного DDL, но защищает от заведомо мусорных документов, в том числе от записей, сделанных мимо приложения (из shell, из скрипта миграции):

```js
db.createCollection("posts", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["title", "authorId", "createdAt"],
      properties: {
        title:     { bsonType: "string", minLength: 1, maxLength: 200 },
        authorId:  { bsonType: "objectId" },
        createdAt: { bsonType: "date" },
        tags:      { bsonType: "array", items: { bsonType: "string" } }
      }
    }
  },
  validationLevel: "moderate",   // strict — все записи; moderate — только
                                 // валидные ранее документы
  validationAction: "error"      // error — отклонить; warn — только в лог
})
```

`validationLevel: "moderate"` — рабочий режим для существующей коллекции с историческими документами: новые и уже валидные записи проверяются, «старьё» продолжает обновляться. Второй, более распространённый в Node-проектах путь — держать схему в Mongoose (см. [Mongoose: Schemas, Models, and Validation]), помня, что это проверка на стороне приложения: `mongosh` и любой другой клиент её обойдут.

## Когда MongoDB — хороший выбор, а когда нет

```txt
┌──────────────────────┬──────────────────────────────────────┬────────────────────────────────┐
│ сигнал в требованиях │ скорее MongoDB                       │ скорее PostgreSQL              │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ форма данных         │ агрегат читается целиком             │ связи и запросы по любой оси   │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ схема                │ поля различаются от записи к записи  │ поля известны и стабильны      │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ запись               │ очень много вставок, шардинг впереди │ умеренная, важнее целостность  │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ транзакции           │ меняется один документ               │ меняются 3-5 таблиц сразу      │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ аналитика            │ заранее известные отчёты             │ произвольные JOIN и BI-запросы │
├──────────────────────┼──────────────────────────────────────┼────────────────────────────────┤
│ целостность          │ контролирует приложение              │ нужны FK и ON DELETE           │
└──────────────────────┴──────────────────────────────────────┴────────────────────────────────┘
```

Где MongoDB действительно на своём месте:

```txt
- Агрегат читается и пишется целиком: заказ с позициями, пост с
  превью автора и тегами, профиль с настройками. Один round-trip
  вместо джойна — и никакого «собери сущность из пяти таблиц».
- Форма данных переменная: каталог, где у телевизора и у книги
  почти не пересекающиеся атрибуты; интеграции с внешними API,
  где приходит произвольный payload.
- Поток записи: события, логи, телеметрия, IoT — плюс TTL-индексы
  для автоудаления (см. [Indexes and Query Performance]) и
  паттерн Bucket (см. [Schema Design: Embedding vs Referencing]).
- Горизонтальное масштабирование заложено в продукт: шардинг —
  штатная функция, а не внешнее решение (см. [Replication,
  Transactions, and Consistency]).
- Ранняя стадия продукта: форма данных меняется каждую неделю,
  и цена изменения схемы важнее строгости.
```

Где MongoDB будет мешать:

```txt
- Операция по определению затрагивает несколько сущностей:
  перевод денег, списание склада + создание заказа + начисление
  бонусов. Транзакции есть, но это исключение, а не норма —
  реляционная модель тут дешевле.
- Ссылочная целостность обязательна: FK, ON DELETE CASCADE,
  «не может быть комментария без поста» на уровне БД. В MongoDB
  этого нет вообще — только код приложения.
- Произвольная аналитика: отчёты «в любом разрезе», ad-hoc JOIN,
  BI-инструменты. $lookup умеет джойн, но это не JOIN
  планировщика (см. [Aggregation Pipeline]).
- Уникальность или инварианты через несколько коллекций:
  уникальный индекс работает внутри одной коллекции.
- Сильная реляционная модель уже есть и работает: миграция ради
  миграции даёт денормализацию, дубли и код синхронизации.
```

И честная оговорка, которую senior обязан произнести сам: `jsonb` в PostgreSQL закрывает значительную часть «нам нужна гибкая схема» — с GIN-индексами по документу и полноценными транзакциями рядом (см. топик PostgreSQL, [PostgreSQL Fundamentals]). Поэтому аргумент «в Mongo можно хранить JSON» сам по себе выбор не обосновывает.

## Каркас ответа «почему Mongo, а не Postgres»

Слабые ответы, которые интервьюер слышит чаще всего: «Mongo быстрее», «в Mongo нет схемы, удобнее разрабатывать», «Mongo лучше масштабируется». Первое — без указания нагрузки бессмысленно, второе описывает недостаток как преимущество, третье верно только для конкретного профиля запросов.

Взрослый ответ строится по четырём осям — и заканчивается признанием границы применимости:

```txt
1. Форма данных и паттерн доступа
   «Основной запрос — карточка заказа целиком: позиции, адрес,
   статус. Это один агрегат, который читается и пишется как
   единое целое, поэтому он лежит одним документом — вместо
   джойна по четырём таблицам на каждый запрос.»

2. Требования к консистентности
   «Все инварианты заказа — внутри одного документа, поэтому
   атомарности документа достаточно; распределённые транзакции
   не нужны. Если бы требовалось списывать склад и создавать
   заказ атомарно — это аргумент за реляционную БД.»

3. Масштаб и профиль нагрузки
   «Пишем ~5k событий/с, читаем по ключу и по времени. Готовы
   к шардингу по tenantId. Аналитика — фиксированный набор
   отчётов, считаем агрегациями на secondary.»

4. Операционный контекст
   «Команда уже держит Atlas, есть бэкапы и мониторинг;
   вводить второе хранилище ради одного сервиса дороже.»

5. Граница применимости (то, что и отличает senior)
   «Если появится биллинг с многосущностными транзакциями или
   потребуется ad-hoc аналитика — это уедет в PostgreSQL, и
   MongoDB останется для событий и каталога.»
```

Тот же каркас работает в обратную сторону. На вопрос «почему Postgres, а не Mongo» плохой ответ — «Mongo несерьёзная база»; хороший — «данные сильно связанные, запросы приходят по любой оси, нужны FK и транзакции; гибкие атрибуты закрыли `jsonb`-колонкой».

## Типичные ошибки на интервью

- **«BSON — это просто JSON в бинарном виде»** — BSON типизирован: `Date`, `ObjectId`, `Decimal128`, `Int32/Int64` в JSON не выражаются. Именно поэтому наружу документ уходит как Extended JSON, где `_id` становится строкой.

- **«ObjectId — случайный идентификатор вроде UUID»** — первые 4 байта это unix-время, поэтому сортировка по `_id` почти совпадает с сортировкой по времени создания, а из значения можно достать дату. Обратная сторона: `_id` не годится там, где нужна непредсказуемость.

- **«MongoDB — schemaless, схемы нет»** — схема есть всегда, вопрос только в том, где она проверяется: в БД (`$jsonSchema`), в приложении (Mongoose) или нигде — тогда в рантайме, ценой багов на разнородных документах.

- **«Mongo быстрее, потому что NoSQL»** — скорость определяется соответствием схемы паттерну доступа и индексами. Плохо спроектированная схема с `$lookup` на каждый запрос будет медленнее нормализованной таблицы с индексами.

- **«В Mongo нет транзакций»** — устаревшее утверждение: multi-document транзакции есть с версии 4.0 (реплика-сет) и 4.2 (шардированный кластер). Верная формулировка: транзакции есть, но правильная схема делает их редко нужными, и они не бесплатны.

- **«Деньги храним как обычное число»** — `Double` даёт ту же ошибку округления, что и `Float` в SQL. Нужен `Decimal128` или целые копейки.

- **«Mongo подходит, потому что данные будут меняться»** — изменчивость формы данных не отменяет анализа паттерна доступа и требований к консистентности; и в PostgreSQL есть `jsonb`. Без этого анализа ответ звучит как выбор по привычке.
