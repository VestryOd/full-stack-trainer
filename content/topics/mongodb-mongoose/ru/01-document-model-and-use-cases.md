# Документная модель и когда её выбирать

## Документ вместо строки: единица хранения в MongoDB

MongoDB хранит данные документами. Документ — самодостаточная структура с вложенными объектами и массивами внутри. Его можно записать и прочитать одним обращением: один запрос к серверу, один ответ обратно.

```js
// коллекция posts — один документ содержит всё, что нужно для страницы поста
{
  _id: ObjectId("66b0f2c14a1e2d0012ab34cd"),
  title: "Индексы в MongoDB",
  slug: "mongodb-indexes",
  author: { _id: ObjectId("66a1..."), name: "Максим", avatar: "/a/12.png" },
  tags: ["mongodb", "performance"],
  stats: { views: 1204, comments: 8 },
  publishedAt: ISODate("2026-07-14T09:12:00Z")
}
```

Тот же пост в PostgreSQL — это `posts` + `users` + `post_tags` + `tags` и три-четыре джойна на каждое чтение. Разница не в «лучше или хуже». Разница в том, *где* собирается сущность. SQL (язык запросов к реляционной базе данных) собирает её в базе при каждом чтении. Документ собран один раз — при записи.

Коллекция — это контейнер документов, аналог таблицы, но без объявленной структуры. Базовые понятия:

```txt
database    → набор коллекций
              (аналог schema или database в PostgreSQL)
collection  → набор документов (таблица без объявленной формы)
document    → BSON-объект (двоичный JSON), максимум 16 МБ
              (аналог строки)
field       → ключ внутри документа (аналог столбца, но у
              каждого документа свой набор ключей)
```

## BSON — это не JSON: типы, которых в JSON нет

На проводе и на диске MongoDB использует BSON (Binary JSON, двоичный JSON). Это двоичный формат, где у каждого поля есть явный тип и длина. Отсюда два практических свойства. Движок может пропустить поле, не разбирая его целиком. И типы не теряются при обмене: что записали, то и прочитали.

```txt
Типы BSON, которых нет в JSON:
  ObjectId     — 12-байтный идентификатор, значение _id по умолчанию
  Date         — int64, миллисекунды с начала эпохи, всегда в
                 UTC (всемирное координированное время, нулевой
                 часовой пояс)
  Decimal128   — десятичное число с точной арифметикой (деньги)
  Int32/Int64  — целые фиксированной ширины (в JSON просто "number")
  Double       — IEEE 754, поведение как у number в JS
  Binary       — байты + subtype (например, UUID)
  Regex        — регулярное выражение как значение поля
  Timestamp    — внутренний тип для oplog, журнала репликации
                 MongoDB; для прикладных дат он не годится
```

Из разницы между BSON и JSON вырастают три ловушки:

```js
// 1. Числа. В JS все числа — double. Драйвер по умолчанию пишет Double;
//    целое больше 2^53 теряет точность ещё в JS, до записи в базу.
db.posts.insertOne({ views: 9007199254740993 })  // ← уже не то число
db.posts.insertOne({ views: Long("9007199254740993") })  // явный Int64

// 2. Деньги. Double накапливает ошибку округления — как и Float в SQL
//    (см. топик PostgreSQL про numeric/decimal).
db.orders.insertOne({ total: 19.99 })                     // Double — плохо
db.orders.insertOne({ total: Decimal128("19.99") })       // точно
// альтернатива без Decimal128: хранить копейки как Int32/Int64

// 3. Даты. Строка "2026-07-14" — это не Date: диапазонные запросы по
//    ней сравнивают текст побуквенно, а не время.
db.posts.insertOne({ publishedAt: "2026-07-14" })         // строка
db.posts.insertOne({ publishedAt: new Date("2026-07-14") })  // BSON Date
```

Когда документ уходит наружу через HTTP, BSON сериализуется в Extended JSON. В режиме relaxed `ObjectId` становится обычной строкой. `Date` становится текстовой датой в формате ISO 8601. ISO — это международная организация по стандартизации, а 8601 — номер её стандарта на запись даты и времени: `"2026-07-14T09:12:00Z"`.

Поэтому API возвращает `"_id": "66b0f2c1..."`, а не объект. Обратное преобразование, строка → `ObjectId`, — задача слоя приложения. На невалидной строке `new ObjectId(req.params.id)` бросает исключение, и это первое место, где нужна валидация входа.

## _id и устройство ObjectId

У каждого документа есть `_id`: обязательный, уникальный внутри коллекции, неизменяемый после вставки. Под него автоматически создан уникальный индекс `_id_`, и удалить его нельзя. Если `_id` не задан явно, `ObjectId` генерирует драйвер — драйвер, а не сервер.

`ObjectId` — это не UUID (universally unique identifier, универсальный уникальный идентификатор), то есть не 128-битный случайный ключ. Его 12 байт имеют фиксированную структуру, и первые четыре из них — метка времени в UTC (всемирное координированное время):

| байты | что внутри | что это даёт |
|---|---|---|
| 0-3 | unix-время в секундах, UTC | сортировка по `_id` ≈ по времени создания |
| 4-8 | случайное значение процесса | два процесса не дадут одинаковый id |
| 9-11 | счётчик внутри процесса | порядок внутри одной секунды сохранён |

Гранулярность времени — одна секунда. Внутри одной секунды порядок между разными процессами не определён.

Что это устройство даёт на практике:

```js
// Время создания достаётся из самого _id, отдельное поле createdAt
// не обязательно. Но обычно оно всё равно полезно: createdAt можно
// проставить старым документам задним числом, а _id — нельзя.
ObjectId("66b0f2c14a1e2d0012ab34cd").getTimestamp()  // ISODate(...)

// Сортировка по _id ≈ сортировка по времени создания → бесплатная
// keyset-пагинация «свежие сначала» по уже существующему индексу _id_.
db.posts.find({ _id: { $lt: lastSeenId } }).sort({ _id: -1 }).limit(20)

// Диапазон по времени можно выразить через _id, собрав его из timestamp.
db.posts.find({ _id: { $gte: ObjectId.createFromTime(1750000000) } })
```

Две вещи `ObjectId` не гарантирует. Первая — строгий глобальный порядок: внутри одной секунды порядок между процессами произволен. Вторая — секретность: из значения видно время создания, а соседние документы одного процесса получают близкие id. Там, где нужна непредсказуемость (например, в публичной ссылке), берут отдельное случайное поле, а не `_id`.

Свой `_id` задавать можно и иногда стоит. Естественный ключ убирает лишний индекс и делает связь «одна запись — один ключ» явной. Два примера: `_id: "mongodb-indexes"` для slug (это адрес поста в ссылке) и `_id: userId` в коллекции профилей 1:1.

Цена — локальность индекса, тот же компромисс, что у случайного первичного ключа в PostgreSQL. Монотонный `ObjectId` всегда попадает в правый край B-дерева, и в кэше нужно держать только этот край. Случайный ключ попадает куда угодно, поэтому горячим должно быть всё дерево. В топике PostgreSQL это разобрано в статье 04, про индексы и внутреннее устройство.

## «Schemaless» не значит «без схемы»

Коллекция примет любой документ: без обязательных полей, с полем другого типа, с новым вложенным объектом. Здесь нет DDL — data definition language, той половины SQL, где живут `CREATE TABLE` и `ALTER TABLE`. Добавить поле — это просто ещё один `$set`.

```txt
          MongoDB: схема живёт в коде
┌─────────────────────────────────────────────┐
│ коллекция posts                             │
│                                             │
│ { title, authorId, tags }                   │
│ { title, authorId }          ← нет tags     │
│ { title, author: {...} }     ← другая форма │
└─────────────────────────────────────────────┘
   БД примет всё; проверять форму обязан код
   (Mongoose-схема или $jsonSchema-валидатор)

     PostgreSQL: схема живёт в БД
┌────────────────────────────────────┐
│ таблица posts                      │
│                                    │
│ title      text   NOT NULL         │
│ author_id  bigint REFERENCES users │
│ tags       text[] DEFAULT ARRAY[]  │
└────────────────────────────────────┘
     БД отвергнет неверную форму,
    но изменение формы = миграция
```

Схема не исчезает. Она переезжает из базы данных (БД) в код. Это перенос ответственности, а не бесплатная гибкость:

```txt
Что становится задачей приложения:
  - каждое чтение должно выдерживать документы старой формы
    (поля нет / поле другого типа / вложенность изменилась)
  - «миграция» превращается в ленивое обновление при чтении
    или в отдельный пакетный скрипт — но не в один DDL
  - аналитика и инструменты бизнес-аналитики (BI) не
    справляются с документами разной формы
  - новый разработчик узнаёт форму данных из кода, а не из
    \d posts

Что взамен:
  - добавить поле = задеплоить код, без миграции и блокировок
  - разнородные сущности (товары с разным набором атрибутов)
    живут в одной коллекции: не нужна ни таблица
    «сущность — атрибут — значение» (EAV), ни 40 столбцов,
    допускающих NULL
  - версия документа может отличаться от версии соседа, и
    иногда это именно то, что нужно (события, снимки, аудит)
```

Дисциплину можно вернуть на уровень базы — валидатором схемы. Это не замена полноценному DDL, но от заведомо мусорных документов он защищает. В том числе от записей, сделанных мимо приложения — из `mongosh` или из скрипта миграции:

```js
db.createCollection("posts", {
  validator: {
    $jsonSchema: {
      bsonType: "object",
      required: ["title", "authorId", "createdAt"],
      properties: {
        title:     { bsonType: "string", minLength: 1, maxLength: 200 },
        authorId:  { bsonType: "objectId" },
        createdAt: { bsonType: "date" },
        tags:      { bsonType: "array", items: { bsonType: "string" } }
      }
    }
  },
  validationLevel: "moderate",   // strict — все записи; moderate — только
                                 // валидные ранее документы
  validationAction: "error"      // error — отклонить; warn — только в лог
})
```

`validationLevel: "moderate"` — рабочий режим для коллекции, в которой уже лежат исторические документы. Новые и ранее валидные записи проверяются, а «старьё» продолжает обновляться.

Второй путь, более распространённый в Node-проектах, — держать схему в Mongoose. Про это статья 07. Помните, что это проверка на стороне приложения: `mongosh` и любой другой клиент её обойдут.

## Когда MongoDB — хороший выбор, а когда нет

Решают шесть сигналов в требованиях, и ни один из них не звучит как «какая база нам больше нравится»:

| сигнал в требованиях | скорее MongoDB | скорее PostgreSQL |
|---|---|---|
| форма данных | агрегат читается целиком | связи и запросы по любой оси |
| схема | поля различаются от записи к записи | поля известны и стабильны |
| запись | очень много вставок, впереди шардинг | умеренная, важнее целостность |
| транзакции | меняется один документ | меняются 3-5 таблиц сразу |
| аналитика | заранее известные отчёты | произвольные отчёты и джойны |
| целостность | контролирует приложение | нужны внешние ключи и `ON DELETE` |

Где MongoDB действительно на своём месте:

```txt
- Агрегат читается и пишется целиком: заказ с позициями, пост с
  превью автора и тегами, профиль с настройками. Одно обращение
  вместо джойна — и никакого «собери сущность из пяти таблиц».
- Форма данных переменная: каталог, где у телевизора и у книги
  почти не пересекающиеся атрибуты; интеграции с внешними API,
  откуда приходит произвольное тело ответа.
- Поток записи: события, логи, телеметрия, данные с датчиков
  «интернета вещей» (IoT). Плюс TTL-индексы (time to live,
  «время жизни»), которые удаляют документы по сроку — про них
  статья 04 про индексы — и паттерн Bucket, который делает их
  дешёвыми: статья 03 про проектирование схемы.
- Горизонтальное масштабирование заложено в продукт: шардинг —
  штатная функция, а не внешняя пристройка. Про репликацию и
  шардинг — статья 06.
- Ранняя стадия продукта: форма данных меняется каждую неделю,
  и цена изменения схемы важнее строгости.
```

Где MongoDB будет мешать:

```txt
- Операция по определению затрагивает несколько сущностей:
  перевод денег, списание склада + создание заказа + начисление
  бонусов. Транзакции есть, но это исключение, а не норма —
  реляционная модель тут дешевле.
- Ссылочная целостность обязательна: внешние ключи, ON DELETE
  CASCADE, «не может быть комментария без поста» на уровне базы.
  В MongoDB этого нет вообще — только код приложения.
- Произвольная аналитика: отчёты «в любом разрезе», джойны на
  ходу, инструменты бизнес-аналитики. Оператор $lookup умеет
  соединять коллекции, но это не джойн, выбранный
  планировщиком. Про это статья 05 про конвейер агрегации.
- Уникальность или инварианты через несколько коллекций:
  уникальный индекс работает внутри одной коллекции.
- Сильная реляционная модель уже есть и работает. Миграция ради
  миграции даёт денормализацию, дубли и код синхронизации —
  и больше ничего.
```

И честная оговорка, которую senior обязан произнести сам: `jsonb` в PostgreSQL закрывает значительную часть запроса «нам нужна гибкая схема». PostgreSQL индексирует содержимое `jsonb` через GIN — generalized inverted index, обобщённый обратный индекс, — а полноценные транзакции лежат рядом. Про это статья 01 топика PostgreSQL. Поэтому аргумент «в Mongo можно хранить JSON» сам по себе выбор не обосновывает.

## Каркас ответа «почему Mongo, а не Postgres»

Слабых ответов, которые интервьюер слышит чаще всего, три: «Mongo быстрее», «в Mongo нет схемы, удобнее разрабатывать», «Mongo лучше масштабируется». Первый бессмыслен без указания нагрузки. Второй описывает недостаток как преимущество. Третий верен только для конкретного профиля запросов.

Сильный ответ строится по четырём осям и заканчивается признанием границы применимости:

```txt
1. Форма данных и паттерн доступа
   «Основной запрос — карточка заказа целиком: позиции, адрес,
   статус. Это один агрегат, который читается и пишется как
   единое целое, поэтому он лежит одним документом — вместо
   джойна по четырём таблицам на каждый запрос.»

2. Требования к консистентности
   «Все инварианты заказа — внутри одного документа, поэтому
   атомарности документа достаточно. Распределённые транзакции
   не нужны. Если бы требовалось списывать склад и создавать
   заказ атомарно, это был бы аргумент за реляционную базу.»

3. Масштаб и профиль нагрузки
   «Пишем около 5k событий в секунду, читаем по ключу и по
   времени. Готовы к шардингу по tenantId. Аналитика — это
   фиксированный набор отчётов, считаем агрегациями на
   secondary.»

4. Операционный контекст
   «Команда уже держит Atlas, есть резервные копии и мониторинг.
   Вводить второе хранилище ради одного сервиса дороже.»

5. Граница применимости — то, что и отличает senior
   «Если появится биллинг с многосущностными транзакциями или
   потребуется аналитика в любом разрезе, эта часть уедет в
   PostgreSQL. MongoDB останется для событий и каталога.»
```

Тот же каркас работает в обратную сторону. На вопрос «почему Postgres, а не Mongo» плохой ответ — «Mongo несерьёзная база». Хороший называет данные: «связей много, запросы приходят по любой оси, нужны внешние ключи и транзакции. Гибкие атрибуты закрыли колонкой `jsonb`».

## Типичные ошибки на интервью

- **«BSON — это просто JSON в двоичном виде»** — BSON типизирован. `Date`, `ObjectId`, `Decimal128`, `Int32/Int64` в JSON не выражаются. Именно поэтому наружу документ уходит как Extended JSON, где `_id` становится строкой.

- **«ObjectId — случайный идентификатор вроде UUID»** — первые 4 байта это unix-время. Поэтому сортировка по `_id` почти совпадает с сортировкой по времени создания, а из значения можно достать дату. Цена: `_id` не годится там, где нужна непредсказуемость.

- **«MongoDB — schemaless, схемы нет»** — схема есть всегда. Вопрос только в том, где она проверяется: в базе через `$jsonSchema`, в приложении через Mongoose или нигде. «Нигде» значит в рантайме — багами на документах другой формы.

- **«Mongo быстрее, потому что NoSQL»** — NoSQL это лишь ярлык «не реляционная база», а ярлык не бывает характеристикой скорости. Скорость определяется соответствием схемы паттерну доступа и индексами. Плохо спроектированная схема с `$lookup` на каждый запрос проиграет нормализованной таблице с индексами.

- **«В Mongo нет транзакций»** — устаревшее утверждение. Транзакции на несколько документов есть с версии 4.0 для реплика-сета и 4.2 для шардированного кластера. Верная формулировка: транзакции есть, правильная схема делает их редко нужными, и они не бесплатны.

- **«Деньги храним как обычное число»** — `Double` даёт ту же ошибку округления, что и `Float` в SQL. Нужен `Decimal128` или целые копейки.

- **«Mongo подходит, потому что данные будут меняться»** — изменчивость формы данных не отменяет анализа паттерна доступа и требований к консистентности. И в PostgreSQL есть `jsonb`. Без этого анализа ответ звучит как выбор по привычке.
