# Запросы Mongoose, populate и ловушки

## Query — объект, а не промис

`Model.find()` возвращает не промис, а объект `Query`, который можно достраивать. Запрос уходит на сервер только при `await` или `.exec()`.

```typescript
// Цепочка строится лениво — запрос ещё не выполнен
const query = PostModel.find({ status: 'published' })
  .where('stats.views').gte(100)
  .select('title slug author stats.views')
  .sort({ publishedAt: -1 })
  .limit(20)
  .lean();

const posts = await query.exec();   // вот здесь идёт обращение к базе
```

```typescript
// Практическая польза: динамический фильтр без склейки объектов
function buildPostsQuery(f: PostFilter) {
  const q = PostModel.find({ status: 'published' });
  if (f.tag)     q.where({ tags: f.tag });
  if (f.author)  q.where({ 'author._id': f.author });
  if (f.since)   q.where('publishedAt').gte(f.since);
  return q.sort({ publishedAt: -1 }).limit(f.limit ?? 20);
}
```

```txt
Две вещи про Query:

1. await и .exec() делают одно и то же, но exec() возвращает
   настоящий промис и даёт более полезный стектрейс при ошибке.
   В коде, где важна диагностика, .exec() предпочтительнее.

2. Один Query нельзя выполнить дважды: повторный await того же
   объекта бросит "Query was already executed". Это ловит
   реальный баг — попытку переиспользовать «шаблон запроса»
   как переменную. Шаблон должен быть функцией, а не объектом.
```

## populate — это **не** $lookup, а дополнительные запросы

`populate` подставляет в поле-ссылку сам связанный документ. Выглядит это как соединение таблиц, но соединением не является. Склейка происходит в вашем процессе Node, после того как Mongoose вторым запросом достал связанные документы.

```txt
   populate — это отдельные запросы, а не $lookup на сервере
┌──────────────────────────────────────────────────────────────┐
│ PostModel.find().limit(20).populate("author._id")            │
│   запрос 1: db.posts.find(...).limit(20)                     │
├──────────────────────────────────────────────────────────────┤
│ Mongoose собирает все authorId из 20 документов              │
│   запрос 2: db.users.find({ _id: { $in: [ ...20 id... ] } }) │
├──────────────────────────────────────────────────────────────┤
│ склейка в памяти процесса Node:                              │
│   post.author._id = соответствующий документ user            │
└──────────────────────────────────────────────────────────────┘
20 постов = 2 запроса, а не 21 — но это всё равно два round-trip
 вложенный populate добавляет ещё один запрос на КАЖДЫЙ уровень
```

```typescript
// Схема со ссылкой
const commentSchema = new Schema<Comment>({
  postId: { type: Schema.Types.ObjectId, ref: 'Post', required: true },
  author: { type: Schema.Types.ObjectId, ref: 'User', required: true },
  body:   { type: String, required: true },
});

// populate с опциями
const comments = await CommentModel.find({ postId })
  .populate({
    path: 'author',
    select: 'name avatar',        // тянуть только нужные поля
    match: { banned: { $ne: true } },   // ← читайте ловушку ниже
  })
  .limit(50)
  .lean();
```

Ключевой факт: `populate` — не серверное соединение, а **дополнительные запросы**, результат которых Mongoose склеивает в памяти процесса. Из этого вытекают четыре практических следствия.

```txt
1. Один populate по списку — это ОДИН дополнительный запрос,
   а не N. Mongoose собирает все id и делает $in. Расхожее
   «populate = N+1» неверно в базовом случае — и именно поэтому
   на интервью стоит объяснять механику, а не повторять мем.

2. N+1-подобные эффекты появляются в конкретных случаях. N+1 — это
   когда один запрос за списком из N элементов тянет за собой ещё
   по одному запросу на каждый элемент: N+1 обращений к базе вместо
   двух. Случаи такие:
   - вложенный populate: populate({ path: 'comments',
     populate: { path: 'author' } }) — это запрос на КАЖДЫЙ
     уровень вложенности
   - populate внутри цикла по документам (populate на каждом
     объекте отдельно) — вот это настоящий N+1
   - populate с perDocumentLimit: чтобы дать «по 3 комментария
     НА КАЖДЫЙ пост», Mongoose обязан выполнить отдельный запрос
     на каждый родительский документ
   - populate в резолверах GraphQL без батчинга

3. options: { limit: 3 } в populate — это ОБЩИЙ лимит на весь
   $in-запрос, а не «по 3 на документ». Классический сюрприз:
   у первого поста три комментария, у остальных ноль.
   «По 3 на каждый» — это perDocumentLimit, и он дорогой.

4. match фильтрует СВЯЗАННЫЕ документы, но не убирает родителя:
   если автор забанен, пост вернётся с author: null. Фильтровать
   родителя по свойству связанного документа populate не умеет
   вообще — для этого нужен $lookup + $match или денормализованное
   поле в родителе.
```

```typescript
// Virtual populate: связь «сверху вниз» без массива id в родителе
postSchema.virtual('comments', {
  ref: 'Comment',
  localField: '_id',
  foreignField: 'postId',
  justOne: false,
});

// Только количество, без загрузки документов
postSchema.virtual('commentCount', {
  ref: 'Comment',
  localField: '_id',
  foreignField: 'postId',
  count: true,
});

const post = await PostModel.findById(id).populate('comments');
```

Virtual populate удобен и опасен одновременно. `foreignField` обязан быть проиндексирован, иначе каждый такой populate — это `COLLSCAN` по дочерней коллекции. `COLLSCAN` — название стадии в плане запроса, которое означает «индекс не использован, прочитана вся коллекция». Индексам и производительности запросов посвящена отдельная статья.

И `count: true` считает каждый раз заново. Для горячего экрана нужен хранимый счётчик: это паттерн Computed из статьи про проектирование схемы.

```txt
         Три способа получить связанные данные
┌─────────────────────────────────────────────────────┐
│ populate                                            │
│                                                     │
│ где выполняется       Node + N запросов             │
│ round-trips           2 и больше                    │
│ фильтр по связанным   match, но родитель остаётся   │
│ цена                  сеть и память Node            │
│ когда уместно         админки, редкие экраны        │
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ $lookup                                             │
│                                                     │
│ где выполняется       на сервере                    │
│ round-trips           1                             │
│ фильтр по связанным   полноценно в пайплайне        │
│ цена                  вложенный цикл                │
│ когда уместно         отчёты и агрегации            │
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ пересмотр схемы                                     │
│                                                     │
│ где выполняется       нигде: данные уже в документе │
│ round-trips           1                             │
│ фильтр по связанным   обычный find                  │
│ цена                  дубли надо синхронизировать   │
│ когда уместно         горячий путь чтения           │
└─────────────────────────────────────────────────────┘
      если populate стоит в самом частом запросе —
            вопрос не к populate, а к схеме
```

Отдельно про целостность: `populate` вернёт `null`, если связанный документ удалён. Внешних ключей и каскадов в MongoDB нет. Внешний ключ (FK, foreign key) — это ограничение реляционной базы, которое заставляет саму базу отказать в ссылке на несуществующую строку.

Поэтому «висячие» ссылки — нормальное состояние базы, и код обязан его переживать. Проверка `if (!post.author) ...` — не паранойя, а обязательная ветка.

## lean(): за что платит гидрация

Без `lean()` Mongoose превращает каждый документ ответа в полноценный `Document`: сеттеры, геттеры, отслеживание изменений, virtuals, методы, встроенная валидация. Для списка из 500 объектов это заметная работа впустую, если объекты нужны только для JSON.

```typescript
// Гидрированный документ: есть save(), virtuals, методы
const post = await PostModel.findById(id);
post.title = 'new';
await post.save();

// lean: обычный объект, в разы дешевле по памяти и процессорному времени
const posts = await PostModel.find({ status: 'published' })
  .select('title slug author')
  .lean<Pick<Post, '_id' | 'title' | 'slug' | 'author'>[]>()
  .exec();
// posts[0].save  → undefined: это НЕ документ
```

```txt
Что теряется вместе с гидрацией:
  - save(), методы документа, markModified
  - virtuals (если нужны — lean({ virtuals: true }) в новых версиях
    или считать в коде)
  - геттеры/сеттеры схемы: значение приходит как оно лежит в базе
  - применение defaults к полям, отсутствующим в документе

Что НЕ теряется:
  - populate работает с lean()
  - проекции, сортировки, индексы — всё то же самое

Правило: любой запрос «только почитать и отдать» — с lean().
Запрос «изменить и сохранить» — без. Смешивать в одном
репозитории удобнее всего через отдельные методы: findForRead()
и findForUpdate().
```

Про типизацию: `lean()` меняет тип результата, и путать его с `HydratedDocument` нельзя. Дженерик у `lean<T>()` — самый простой способ описать реальную форму, особенно с `select`.

А `_id` в такой форме остаётся `Types.ObjectId`, пока вы явно не сериализуете его в строку на границе API. Про эту границу — статья про схемы, модели и валидацию в Mongoose.

## findOneAndUpdate: поведение, которое надо знать

```typescript
const post = await PostModel.findOneAndUpdate(
  { _id: id, status: 'draft' },                 // условие-предпосылка
  { $set: { status: 'published', publishedAt: new Date() } },
  {
    returnDocument: 'after',   // 'before' — по умолчанию!
    runValidators: true,       // иначе валидация НЕ выполняется
    upsert: false,
    projection: { title: 1, status: 1 },
  },
);
if (!post) throw new ConflictError('пост не найден или уже опубликован');
```

```txt
Что важно помнить:

  - returnDocument по умолчанию 'before'. Это значит: вернётся
    состояние документа ДО изменения, а не после. Старый алиас
    new: true делает то же, что returnDocument: 'after' — в новом
    коде используйте returnDocument
  - runValidators нужен явно, и даже с ним required для отсутствующих
    в апдейте полей не проверяется (об этом статья про схемы, модели
    и валидацию в Mongoose)
  - document middleware (pre/post 'save') НЕ вызывается — это
    query-операция
  - null означает «ничего не подошло под фильтр». Это часть API,
    а не ошибка: именно так реализуется compare-and-set
    (об этом статья про CRUD и операторы запросов)
  - upsert + setDefaultsOnInsert: дефолты схемы применяются при
    вставке (в актуальных версиях Mongoose это поведение
    по умолчанию), но проверять это стоит на своей версии
```

```txt
Как выбирать между findOneAndUpdate и save():

  findOneAndUpdate — когда важна АТОМАРНОСТЬ и условие можно
  выразить фильтром: счётчики, смена статуса, «занять задачу»,
  проверка баланса. Один round-trip, гонки нет.

  save() — когда важны ХУКИ И ВАЛИДАЦИЯ документа целиком:
  хеширование пароля, инварианты между полями, аудит через
  post('save'). Цена: чтение + запись, между которыми чужая
  запись может вклиниться.

  Смешанный вариант, который часто и нужен: писать через
  findOneAndUpdate, а инварианты держать явными функциями
  домена, не полагаясь на магию схемы.
```

## versionKey `__v` и оптимистичная блокировка

`__v` — поле версии, которое Mongoose добавляет в каждый документ, и оно гораздо слабее, чем обещает название «оптимистичная блокировка». Оно защищает позиции в массиве, а не произвольные изменения полей.

```txt
Что такое __v: поле версии, которое Mongoose добавляет в документ.
Оно НЕ инкрементируется на каждом save() — только когда операция
может конфликтовать по позициям в массиве (например, $push/$pull
меняют индексы элементов).

Механика: при save() Mongoose добавляет __v в фильтр обновления.
Если документ успел измениться, обновление не находит цели и
Mongoose бросает VersionError.

Чем это НЕ является: полноценной оптимистичной блокировкой на
любые изменения. Поле title можно перезаписать поверх чужой
правки без всякой ошибки.
```

```typescript
// Явная оптимистичная блокировка на уровне схемы (Mongoose 5.10+)
const postSchema = new Schema<Post>({ ... }, {
  optimisticConcurrency: true,   // __v проверяется на КАЖДОМ save()
});

// Или своими руками, без Mongoose-магии — версия в фильтре
const res = await PostModel.updateOne(
  { _id: id, version: expectedVersion },
  { $set: { ...changes }, $inc: { version: 1 } },
);
if (res.matchedCount === 0) throw new ConflictError('документ изменён');
```

Второй вариант — тот же приём «условие в фильтре», что и в статье про CRUD (create, read, update, delete — создание, чтение, обновление, удаление) и операторы запросов. Он работает и без Mongoose, виден в коде и не зависит от версии библиотеки.

## Подключение: пул, буферизация и serverless

Mongoose держит пул открытых соединений внутри процесса и переиспользует их, поэтому `connect()` вызывают при старте приложения и больше нигде. Настройки ниже — те, что реально меняют поведение под нагрузкой.

```typescript
await mongoose.connect(process.env.MONGO_URL!, {
  maxPoolSize: 20,                 // размер пула соединений
  minPoolSize: 2,
  serverSelectionTimeoutMS: 5000,  // сколько ждать подходящий узел
  socketTimeoutMS: 45000,
});

mongoose.connection.on('error', (err) => logger.error({ err }, 'mongo error'));
mongoose.connection.on('disconnected', () => logger.warn('mongo disconnected'));
```

```txt
Пул соединений живёт в процессе и переиспользуется: connect()
вызывается ОДИН раз при старте приложения, а не в обработчике
запроса. Второй connect() к тому же URI Mongoose переиспользует,
но код, который «подключается на каждый запрос», обычно означает
утечку соединений где-то рядом.

Размер пула: слишком маленький — запросы стоят в очереди
(видно как рост латентности при неизменной нагрузке на базу);
слишком большой при N инстансах — упор в лимит соединений
кластера (в Atlas он зависит от тарифа).
```

Буферизация команд — механизм, который чаще маскирует проблему, чем помогает:

```txt
Пока соединение не установлено, Mongoose НЕ бросает ошибку сразу:
он БУФЕРИЗУЕТ операции (bufferCommands: true по умолчанию) и ждёт
до bufferTimeoutMS (10 секунд). Симптом в проде: запросы «висят»
десять секунд и падают с

  MongooseError: Operation `posts.find()` buffering timed out
  after 10000ms

Опасность в том, что реальная причина — недоступный кластер,
неверный URI, адрес, не добавленный в список разрешённых, —
превращается в непонятный таймаут через 10 секунд после старта.
Что делать:

  - проверка живости приложения (healthcheck) смотрит на
    mongoose.connection.readyState === 1
  - не отдавать трафик, пока соединение не установлено
  - в критичных сервисах: bufferCommands: false — тогда операция
    без соединения падает СРАЗУ и с внятной ошибкой
  - логировать события соединения, а не только ошибки запросов
```

```typescript
// Serverless / Next.js: соединение кэшируется между инвокациями
// в globalThis, иначе каждый hot-reload или cold start создаёт
// новый пул
const globalForMongoose = globalThis as unknown as {
  mongooseConn?: Promise<typeof mongoose>;
};

export function getConnection() {
  if (!globalForMongoose.mongooseConn) {
    globalForMongoose.mongooseConn = mongoose.connect(process.env.MONGO_URL!, {
      maxPoolSize: 5,          // в serverless пул держат маленьким:
                               // инстансов много, лимит кластера один
    });
  }
  return globalForMongoose.mongooseConn;
}
```

## autoIndex: почему в проде его отключают

`autoIndex` заставляет Mongoose создавать при старте приложения каждый индекс, объявленный в схемах. В разработке это удобно, в проде — нет. Сборка индексов переезжает в момент деплоя, а правка схемы меняет индексы на проде без ревью.

```typescript
await mongoose.connect(url, {
  autoIndex: false,      // не создавать индексы автоматически
  autoCreate: false,     // и не создавать коллекции
});
```

```txt
По умолчанию autoIndex: true — при старте приложения Mongoose
вызывает createIndex для КАЖДОГО индекса, объявленного в схемах.
В разработке это удобно. В проде — три проблемы:

1. Сборка индекса на большой коллекции — это заметная нагрузка,
   которая случится в момент деплоя, то есть в самый неудачный
   момент (об этом статья про индексы и производительность
   запросов).

2. При N инстансах сервиса N параллельных попыток создать один
   индекс: сервер обработает это, но лишняя работа и странные
   логи гарантированы.

3. Изменения индексов происходят неявно: кто-то поправил схему —
   индекс появился на проде без ревью и без плана.

Правильный процесс: autoIndex отключён, индексы применяются
осознанно — миграционным скриптом в пайплайне деплоя.
```

```typescript
// Осознанная синхронизация индексов — отдельный шаг деплоя
await PostModel.syncIndexes();
// ВНИМАНИЕ: syncIndexes УДАЛЯЕТ индексы, которых нет в схеме.
// Индекс, созданный вручную для отчёта, исчезнет. Для аудита
// используйте:
const diff = await PostModel.diffIndexes();   // что будет создано/удалено
```

Отдельная ловушка связывает эту тему со статьёй про схемы, модели и валидацию в Mongoose: `unique: true` в схеме — это объявление индекса. При `autoIndex: false` и без миграции индекс не создан. А значит **никакой уникальности нет**, хотя код выглядит так, будто есть. Уникальные индексы обязаны быть в миграции.

## Обработка ошибок: маппинг в ответ API

Mongoose и драйвер бросают шесть ошибок, которые имеют значение, и у каждой есть свой правильный HTTP-код. Большинство из них — ожидаемый исход, а не сбой. Поэтому отвечать на все 500-м значит превратить нормальный контракт API в вызов дежурного.

```txt
     Ошибки Mongoose/драйвера → ответ API
┌───────────────────────────────────────────┐
│ ValidationError                           │
│                                           │
│ причина   схема отвергла значения         │
│ ответ     400 + список полей              │
└───────────────────────────────────────────┘
┌───────────────────────────────────────────┐
│ CastError                                 │
│                                           │
│ причина   невалидный вход: битый ObjectId │
│ ответ     400                             │
└───────────────────────────────────────────┘
┌───────────────────────────────────────────┐
│ E11000 (code 11000)                       │
│                                           │
│ причина   нарушен уникальный индекс       │
│ ответ     409 + имя поля                  │
```

```typescript
import mongoose from 'mongoose';

interface ApiError { status: number; code: string; details?: unknown }

export function mapMongoError(e: unknown): ApiError {
  // Нарушение уникального индекса: поле достаём из ошибки драйвера
  if (typeof e === 'object' && e !== null && (e as any).code === 11000) {
    const key = Object.keys((e as any).keyPattern ?? {})[0] ?? 'field';
    return { status: 409, code: 'DUPLICATE', details: { field: key } };
  }

  if (e instanceof mongoose.Error.ValidationError) {
    return {
      status: 400,
      code: 'VALIDATION',
      details: Object.entries(e.errors).map(([path, err]) => ({
        path,
        message: err.message,
      })),
    };
  }

  if (e instanceof mongoose.Error.CastError) {
    return { status: 400, code: 'BAD_INPUT', details: { path: e.path } };
  }

  if (e instanceof mongoose.Error.VersionError) {
    return { status: 409, code: 'CONFLICT' };
  }

  if (e instanceof mongoose.Error.MongooseServerSelectionError) {
    return { status: 503, code: 'DB_UNAVAILABLE' };
  }

  return { status: 500, code: 'INTERNAL' };
}
```

## Типичные ошибки на интервью

- **«`populate` — это `$lookup` в Mongoose»** — это отдельные запросы плюс склейка в памяти Node. Один populate по списку = один дополнительный запрос через `$in`; `$lookup` выполняется на сервере.

- **«`populate` всегда даёт N+1»** — в базовом случае нет. N+1 — это когда один запрос за списком из N элементов тянет за собой ещё по одному запросу на каждый элемент. Появляется при вложенном populate, populate в цикле по документам и при `perDocumentLimit`. На интервью ценно объяснить, где именно возникает лишний запрос.

- **«`options: { limit: 3 }` в populate даст по 3 связанных документа на каждый родитель»** — это общий лимит на весь `$in`-запрос: первый родитель получит три, остальные ноль. «По 3 на каждого» — `perDocumentLimit`, и он выполняет запрос на каждый документ.

- **«`match` в populate отфильтрует родителей»** — не отфильтрует: родитель вернётся с `null` в связанном поле. Фильтрация родителя по свойству связанного документа — это `$lookup` + `$match` или денормализованное поле.

- **«`lean()` — это микрооптимизация»** — на списках это разница в разы по процессорному времени и памяти, потому что отменяется гидрация каждого документа. Любой путь «только чтение» должен быть `lean()`.

- **«`findOneAndUpdate` возвращает обновлённый документ»** — по умолчанию `returnDocument: 'before'`, то есть состояние **до** изменения. `'after'` указывается явно.

- **«`__v` — это оптимистичная блокировка»** — `__v` инкрементируется не на каждом `save()`, и обычная перезапись поля конфликта не вызовет. Настоящая блокировка — `optimisticConcurrency: true` или своё поле версии в фильтре.

- **«Запрос просто медленный»** (когда он падает через 10 секунд с `buffering timed out`) — это не медленный запрос, а отсутствие соединения. Команда лежала в буфере Mongoose. Диагностика — `readyState`, события соединения и проверка живости.

- **«`autoIndex` можно оставить включённым, это же удобно»** — в проде это сборка индексов в момент деплоя, гонки между инстансами и неявные изменения. Индексы применяются миграцией; `syncIndexes()` при этом **удаляет** всё, чего нет в схеме.

- **«`unique: true` в схеме гарантирует уникальность»** — только если индекс реально создан. С `autoIndex: false` и без миграции гарантии нет вообще.

- **«Ошибки Mongo — это 500»** — `E11000` это 409, `ValidationError` и `CastError` — 400, недоступность кластера — 503. Причём `E11000` приходит от драйвера и не проверяется через `instanceof mongoose.Error`.
