Отдельно про манеру ответа. Вопросы про MongoDB чаще других провоцируют лозунги: «Mongo быстрее», «схемы нет», «populate — это N+1». Запись `N+1` означает вот что: один запрос за списком из N элементов тянет за собой ещё по одному запросу на каждый элемент. Итого N+1 обращений к базе там, где хватило бы двух. Сильный ответ всегда содержит механику и границу применимости, а не оценку.

## Группа 1: документная модель и выбор базы данных

**1. Чем BSON отличается от JSON, и что даёт устройство ObjectId?**

BSON (binary JSON — бинарный JSON) — это бинарный типизированный формат: у каждого поля есть явный тип и длина. Отсюда два следствия. Движок может пропустить поле, не разбирая его целиком, а типы не теряются при записи и обратном чтении.

В JSON нет `Date`, `ObjectId`, `Decimal128` и `Int32/Int64`. Отсюда два практических следствия, которые стоит назвать самому:

- Деньги хранят в `Decimal128` или целыми копейками. В `Double` накапливается та же ошибка округления, что у `Float` в SQL (structured query language — язык запросов к реляционным базам).
- Дату хранят как BSON `Date`, а не строкой. Иначе диапазонные запросы сравнивают значения лексикографически, и `"2026-1-9"` окажется раньше `"2026-10-01"`.

```js
db.orders.insertOne({
  total: NumberDecimal("19.99"),   // не 19.99 — без двоичного округления
  createdAt: new Date(),           // не "2026-08-13" — настоящая Date
});
```

`ObjectId` — это 12 байт, и первые 4 из них хранят unix-время в секундах:

```txt
ObjectId("66b0f2c1a4e3f21c8d9b1234")  — 12 байт, 24 hex-символа

  66b0f2c1    4 байта   unix-время в секундах
  a4e3f21c8d  5 байт    случайные, свои на процесс
  9b1234      3 байта   счётчик, свой на процесс
```

Такая раскладка даёт три вещи бесплатно. Сортировка по `_id` почти совпадает с сортировкой по времени создания. Дату можно достать из значения через `getTimestamp()`. И keyset-пагинация «свежие сначала» работает по индексу `_id`, который существует всегда.

Обратная сторона: `ObjectId` предсказуем и раскрывает время создания. Для публичных ссылок, где это важно, нужно отдельное непредсказуемое поле.

На границе API BSON сериализуется в Extended JSON, и `_id` становится строкой. Обратный маппинг «строка → ObjectId» — то самое место, где валидация входа обязательна. Полностью это разобрано в статье про документную модель.

**2. MongoDB называют schemaless. Что это значит на самом деле?**

Это значит, что схема не проверяется базой, а не что её нет. Коллекция примет документ любой формы, и никакого DDL (data definition language — язык описания данных) не существует: ни `CREATE TABLE`, ни `ALTER TABLE`.

Но форма данных всё равно есть. Она просто переехала из базы в код приложения.

Это перенос ответственности, и у него есть цена:

- Каждое чтение обязано выдерживать документы старой формы.
- «Миграция» превращается в ленивый апгрейд при чтении или в скрипт, который проходит коллекцию пачками.
- Аналитика спотыкается о разнородные документы.
- Новый разработчик узнаёт форму из кода, а не из `\d posts`.

Что вы получаете взамен:

- Добавление поля — это деплой кода, без миграции и без блокировок.
- Разнородные сущности живут в одной коллекции: без 40 nullable-столбцов и без EAV (entity-attribute-value). EAV — это реляционный приём, когда гибкую схему подделывают строками вида «имя поля / значение поля».

Часть дисциплины можно вернуть в базу валидатором `$jsonSchema`. Важно, что он ловит и записи, сделанные мимо приложения — из консоли, из скрипта.

```js
db.createCollection("posts", {
  validator: { $jsonSchema: {
    bsonType: "object",
    required: ["title", "status"],
    properties: { status: { enum: ["draft", "published"] } },
  } },
  validationLevel: "moderate",   // старые плохие документы не отвергаются
});
```

В Node-проектах схему обычно держат в Mongoose, помня, что это проверка только на стороне приложения. Об этом статья про документную модель и статья про схемы Mongoose.

**3. Почему вы выбрали MongoDB, а не PostgreSQL?**

Ответ строится по четырём осям и заканчивается границей применимости.

1. **Форма данных и паттерн доступа.** «Основной запрос — карточка заказа целиком. Она читается и пишется как один агрегат, поэтому лежит одним документом вместо джойна по четырём таблицам».
2. **Требования к консистентности.** «Все инварианты заказа внутри одного документа, значит достаточно атомарности документа. Если бы нужно было атомарно списывать склад и создавать заказ, это был бы аргумент за реляционную базу».
3. **Масштаб и профиль нагрузки.** Сколько пишем, как читаем, готовы ли к шардингу.
4. **Операционный контекст.** Что команда уже умеет эксплуатировать.

Дальше — финал, который отличает senior: «если появится биллинг с многосущностными транзакциями или ad-hoc аналитика, эта часть уедет в PostgreSQL».

Отдельно стоит произнести честную оговорку, не дожидаясь вопроса. В PostgreSQL тип `jsonb` закрывает значительную часть «нам нужна гибкая схема», причём с полноценными транзакциями рядом. Поэтому «в Mongo можно хранить JSON» само по себе выбор не обосновывает.

Это сравнение разобрано и в статье про документную модель, и в топике PostgreSQL.

## Группа 2: проектирование схемы

**4. Embedding или referencing — по каким критериям выбираете?**

Критериев четыре, и порядок важен.

1. **Кардинальность в терминах «сколько может стать»** — а не «сколько сейчас». One-to-few (3–10 тегов) вкладываем. One-to-many (комментарии) выносим со ссылкой. One-to-squillions (просмотры) храним отдельно с бакетированием.
2. **Паттерн доступа.** Если дочерние данные нужны всегда при чтении родителя — вкладываем. Если нужен независимый доступ («все комментарии пользователя», модерация), своя пагинация и своя сортировка — отдельная коллекция.
3. **Частота изменений.** Дублируем то, что меняется редко и читается почти всегда: имя и аватар автора. Не дублируем то, что меняется часто или критично: email, права.
4. **Границы роста.** Может ли пользователь наращивать этот набор элементов без предела? Если да, вложение — это отложенная авария.

```txt
сколько дочерних        что делать
──────────────────────  ──────────────────────────────
one-to-few (3-10)       вкладываем массивом
one-to-many (сотни)     своя коллекция + ссылка
one-to-squillions       своя коллекция + бакетирование
предела нет вообще      своя коллекция, без исключений
```

И начинать надо не с сущностей. Начинать надо со списка топ-5 запросов с их частотами. Без него любой ответ про вложение — это угадывание. Правило, к которому всё сводится: что читается вместе, то хранится вместе. Этому посвящена вся статья про проектирование схемы.

**5. Конкретный кейс: комментарии к посту — вкладывать или ссылка?**

Ссылка плюс Subset — и обоснование важнее ответа. У комментариев нет верхней границы. У 99% постов их будет 20, но у одного вирусного — 50 000, и схема должна выдержать именно этот случай.

Полное вложение упирается в лимит документа 16 МБ (мегабайт), но ломается задолго до него — по трём причинам:

1. `WiredTiger`, движок хранения MongoDB, не правит документ на месте. Каждый `$push` переписывает документ целиком.
2. Документ целиком читается в память и уходит по сети, даже когда нужен один комментарий.
3. Индекс по массиву — это multikey-индекс: одна запись индекса на каждый элемент массива. Индекс распухает вместе с документом.

Поэтому комментарии живут своей коллекцией со ссылкой `postId`, и по этому полю нужен индекс. Так получается нормальная пагинация, сортировка и независимая модерация.

При этом страница поста показывает первые три комментария в 95% просмотров. Их держим в самом посте, массивом фиксированной длины:

```js
await posts.updateOne({ _id: postId }, {
  $push: {
    previewComments: {
      $each: [{ author, body, createdAt: new Date() }],
      $sort: { createdAt: -1 },
      $slice: 3,                 // оставить только три свежих
    },
  },
});
```

Цена: записи стало две, и они не атомарны. Поэтому сначала пишем в `comments`, потому что это источник истины, и только потом обновляем preview. Тогда при сбое теряется кэш, а не данные. Глубже об этом — статья про проектирование схемы и статья про CRUD (create, read, update, delete — создание, чтение, обновление, удаление).

**6. Какие паттерны проектирования применяете и какова их цена?**

Четыре паттерна, и у каждого называем не только выгоду, но и цену.

**Extended Reference.** В пост кладём не `authorId`, а `author: { _id, name, avatar }` — ровно те поля, которые рисуются. Это убирает второй запрос на каждой странице и в каждом элементе ленты. Цена: дубли надо обновлять. Нужно сказать, каким механизмом — фоновая задача, change streams — или что это осознанный снапшот «имя на момент публикации».

**Subset.** Горячее подмножество лежит внутри документа, с обязательным `$slice`. Без `$slice` паттерн превращается в анти-паттерн, потому что массив растёт без предела.

**Bucket.** Документ не на событие, а на корзину (`postId` плюс час), с `upsert` и `$inc`:

```js
await views.updateOne(
  { postId, hour: "2026-08-13T14" },
  { $inc: { count: 1 } },
  { upsert: true },        // нужен уникальный индекс по { postId, hour }
);
```

Миллионы крошечных документов превращаются в 24 на пост в сутки, и отчёт за неделю читает 168 документов вместо 70 миллионов. Уникальный индекс по ключу корзины обязателен: иначе гонка upsert создаст две корзины на один час.

**Computed.** Счётчик комментариев храним готовым и меняем атомарным `$inc`, вместо `countDocuments()` на каждом чтении ленты. Обязательное дополнение — фоновый пересчёт из источника истины, потому что счётчик рано или поздно разъедется.

**7. Что плохого в полностью нормализованной схеме в MongoDB и в чём опасность обратного — массивной денормализации?**

Полная нормализация в Mongo даёт худший из двух миров. Ломается сразу три вещи:

- Джойны формально есть, но `$lookup` выполняется как вложенный запрос на каждый входной документ. Ни hash join, ни выбора порядка соединения планировщиком нет, а `populate` в Mongoose — это вообще отдельные запросы.
- Целостности всё равно нет: ни FK, ни `ON DELETE CASCADE`, ни межколлекционных проверок. FK — это внешний ключ, то есть ограничение реляционной базы, которое запрещает ссылку на несуществующую строку.
- Транзакции становятся нужны на каждый шаг, и стоят они дороже, чем в реляционной базе.

То есть получается реляционная схема без реляционных гарантий и без реляционного оптимизатора. Если данные действительно требуют нормализации по всем осям, правильный вывод — взять PostgreSQL.

Обратная крайность — копировать полный документ автора в каждый пост и каждый комментарий. Тогда смена email превращается в `updateMany` по миллионам документов без транзакции вокруг. Падение посередине оставляет систему в двух состояниях. А запрос на удаление данных по GDPR (General Data Protection Regulation — европейский регламент о защите данных) превращается в поиск копий по всем коллекциям.

Вопрос интервьюера всегда один и тот же. Кто и когда обновляет дубли? И что будет при сбое посередине? Хороший ответ называет конкретный механизм или честно говорит: «это снапшот, мы его не обновляем». Это продолжают статья про проектирование схемы и статья про агрегацию.

## Группа 3: запросы, обновления и атомарность

**8. Что именно гарантирует атомарность на уровне документа, и когда всё же нужна транзакция?**

Любая операция записи над **одним** документом атомарна: либо применились все её изменения, либо ни одно. Это верно сразу для нескольких полей, вложенных объектов и элементов массива.

```js
// Ни один читатель не увидит это «наполовину»
await posts.updateOne({ _id: postId }, {
  $push: { previewComments: comment },
  $inc:  { "stats.comments": 1 },
  $set:  { updatedAt: new Date() },
});
```

Границы надо называть точно, потому что именно их и уточняют дальше:

- `updateMany` по 100 документам — это 100 отдельных атомарных операций. Между ними видно половину обновлённых.
- Две операции подряд в коде приложения тоже не атомарны, даже над одним документом.

Транзакция нужна, когда инвариант охватывает несколько документов и рассинхронизация недопустима. Три примера: перевод между счетами, заказ плюс резерв склада, удаление агрегата вместе с дочерними документами.

Транзакции есть с 4.0 для реплика-сетов и с 4.2 для шардированных кластеров, так что утверждение «в MongoDB нет транзакций» устарело. Но правильно спроектированный агрегат делает их редкими. Если транзакция нужна на каждый второй запрос, это сигнал, что схема реляционная. Дальше эту тему ведут статья про CRUD и статья про репликацию.

---

**9. Как вернуть «оценки 4 и выше от конкретного пользователя»? В чём подвох с массивами?**

Подвох в том, что условия на поле массива, записанные через точечную нотацию, проверяются **независимо** друг от друга.

```js
// НЕВЕРНО: userId "b" может быть у одного элемента, а score 5 — у другого
await reviews.find({ "ratings.userId": "b", "ratings.score": { $gte: 4 } });

// ВЕРНО: оба условия должны выполниться на ОДНОМ элементе
await reviews.find({
  ratings: { $elemMatch: { userId: "b", score: { $gte: 4 } } },
});
```

То же касается диапазона на одном элементе. Без `$elemMatch` условие `{ score: { $gte: 4, $lte: 5 } }` означает «есть элемент не меньше 4 и есть элемент не больше 5» — возможно, разные элементы.

Практическое правило короткое. Одно условие по полю массива — точечной нотации достаточно. Два и больше условий, которые обязаны совпасть на одном элементе — всегда `$elemMatch`.

Для выборки самих элементов есть проекции `$slice`, `comments.$` и `$elemMatch`. Но если такие выборки нужны регулярно, с пагинацией и сортировкой, это признак, что данные должны лежать отдельной коллекцией. Обе стороны разобраны в статье про CRUD и операторы запросов.

**10. `updateOne` против `replaceOne`, и почему `upsert` не защищает от дублей?**

Оператор `updateOne` обновляет перечисленные поля и не трогает остальные. А `replaceOne` заменяет документ целиком, кроме `_id`. Отсюда классический баг:

```js
// Классический баг PUT: клиент прислал только { title }
await posts.replaceOne({ _id: id }, req.body);
// → authorId и createdAt из документа ИСЧЕЗЛИ

// Надёжнее: $set по явному белому списку полей
const allowed = pick(req.body, ["title", "body", "tags"]);
await posts.updateOne({ _id: id }, { $set: allowed });
```

Обновление без операторов драйверы тоже трактуют как замену, так что тот же баг прячется и там. И семантика `PUT` в REST (representational state transfer — обычный стиль HTTP-API) не равна `replaceOne`. Когда `authorId` и `createdAt` пропадают, причину потом ищут в чтении, а не в записи.

Про `upsert`: он избавляет от лишнего обращения «сначала find, потом решаем», но это **не** атомарное «проверил и вставил». Два параллельных upsert, ни один из которых ничего не нашёл, вставят два документа. Защищает только уникальный индекс: с ним второй upsert получит `E11000`, и это ожидаемый исход, который обрабатывается как «повторить один раз».

Ещё нюанс про вставляемый документ. В него попадают только равенства фильтра, а операторы сравнения при вставке игнорируются. Поля «только при вставке» задаются через `$setOnInsert`.

**11. Как реализовать «занять задачу» или «списать со счёта, не уходя в минус» без транзакции?**

Через `findOneAndUpdate` с условием в **фильтре**. Это атомарный read-modify-write на сервере: аналог `SELECT FOR UPDATE` плюс update, в одном шаге.

```js
// Занять задачу. null означает «уже занята» — это и есть ответ,
// а не ошибка.
const job = await jobs.findOneAndUpdate(
  { _id, status: "pending" },
  { $set: { status: "running", workerId } },
  { returnDocument: "after" },
);

// Списать, не уходя в минус: проверку делает сервер в момент записи.
const acc = await accounts.findOneAndUpdate(
  { _id, balance: { $gte: amount } },
  { $inc: { balance: -amount } },
);
```

Альтернатива «прочитать, посчитать в Node, записать обратно» — это классический lost update, потерянное обновление. Два процесса читают `views = 100`, оба пишут 101, и один инкремент пропал.

Тот же приём работает как оптимистичная блокировка: версия документа в фильтре плюс `$inc` версии в обновлении. Тогда `matchedCount === 0` означает конфликт.

Общий принцип в одну фразу: перенести проверку из кода приложения в фильтр запроса. На нём строятся и статья про CRUD, и статья про запросы Mongoose.

## Группа 4: индексы и производительность

**12. Что такое правило ESR и почему порядок именно такой?**

ESR расшифровывается как Equality, Sort, Range — равенство, сортировка, диапазон. Это правило порядка полей в составном индексе.

- **Equality первыми.** Точное равенство фиксирует префикс ключа и сужает скан до непрерывного участка индекса.
- **Sort сразу после равенств.** Внутри зафиксированного префикса ключи уже отсортированы по следующему полю индекса. Если это поле совпадает с `sort`, сервер отдаёт документы в готовом порядке, и стадии `SORT` в плане нет. И `limit` становится дешёвым: 20 документов берутся с начала скана, а не после сортировки всей выборки.
- **Range последними.** Диапазон читает непрерывный участок ключей, и внутри этого участка порядок по следующему полю уже не является общим порядком. Поэтому любое sort-поле **после** range-поля не спасает от сортировки в памяти.

```js
// Запрос
db.posts.find({ status, "author._id": a, publishedAt: { $gte: d } })
        .sort({ views: -1 });

// Правильно — сначала E, потом S, потом R
{ status: 1, "author._id": 1, views: -1, publishedAt: 1 }

// «Интуитивно» и неверно — диапазон стоит раньше sort-поля,
// поэтому в плане появится SORT с лимитом памяти 100 МБ
{ status: 1, publishedAt: 1, views: -1 }
```

И отдельно — prefix rule, правило префикса: индекс `{a, b, c}` обслуживает `(a)`, `(a,b)` и `(a,b,c)`, но не `(b)`. Оба правила разобраны в статье про индексы.

**13. Как вы читаете `explain()` и какие числа смотрите?**

Запускаю `explain("executionStats")`. В отличие от режима по умолчанию `queryPlanner`, он реально выполняет запрос и даёт фактические числа, а не оценки. Дальше смотрю четыре из них:

```txt
nReturned            сколько документов вернулось
totalKeysExamined    сколько записей индекса прочитано
totalDocsExamined    сколько документов поднято из хранилища
executionTimeMillis  сколько это заняло по часам
```

Ориентир здорового запроса — `nReturned ≈ totalKeysExamined ≈ totalDocsExamined`. Любой разрыв на порядок — это работа, выполненная впустую.

Дальше стадии, и у каждой фиксированный смысл:

- `COLLSCAN` — скан коллекции: индекс не использован, прочитана вся коллекция.
- `SORT` — сортировка в памяти, то есть индекс не покрывает `sort`.
- `docsExamined` намного больше `nReturned` — индекс недостаточно селективен либо порядок полей неверный.
- `totalDocsExamined: 0` при `nReturned > 0` — covered query, ответ собран из одного индекса. Это и есть цель.

Важная деталь чтения: дерево в `winningPlan` печатается от корня к листьям. Это обратно потоку данных, поэтому начинать удобнее с самой глубокой стадии.

И то, что «`IXSCAN` есть» — не вывод. `IXSCAN` — это скан индекса, а индекс, просматривающий миллион ключей ради 20 документов, всё равно медленный запрос. Сам медленный запрос ищу профайлером, `setProfilingLevel(1, { slowms: 100 })`, а не догадками.

**14. Назовите ситуации, когда индекс есть, но не используется.**

Их восемь, и на практике они всплывают примерно в таком порядке:

- **Нарушен ESR.** Range-поле стоит раньше sort-поля, и вместо экономии появляется `SORT` по всей выборке.
- **`$regex` без якоря в начале или с флагом `i`.** Шаблон `/^mongodb-/` даёт скан диапазона; `/^mongodb-/i` и `/indexes/` уже нет.
- **`$ne` и `$nin`.** Они означают «всё, кроме», поэтому селективность близка к 100% и почти весь индекс читается всё равно. Переформулируется в `$in` по разрешённым значениям.
- **Вычисление над полем вместо самого поля.** Выражение `$expr` с `$year: "$publishedAt"` индекс по `publishedAt` не задействует. Нужен диапазон по границам года. А `$where` не использует индексы вовсе.
- **Несовпадение типов BSON.** Значения `"42"` и `42` — разные. Классика тут: `id` приходит строкой из query-строки, а в базе лежит `ObjectId`.
- **Несовпадение collation** между индексом и запросом.
- **`$or`, где хотя бы одной ветке не хватает индекса.** Деградирует весь `$or`, а не только эта ветка.
- **Низкая селективность.** При `{ archived: false }`, когда 99% документов — `false`, планировщик обоснованно выберет `COLLSCAN`.

**15. Расскажите про multikey, unique и TTL — какие там ловушки?**

Три вида индекса и три разные ловушки.

**Multikey** возникает автоматически, когда индексируемое поле — массив: создаётся запись индекса на каждый **элемент**. Поэтому размер индекса пропорционален суммарному числу элементов. Миллион документов по 20 тегов — это 20 миллионов записей.

Отсюда два ограничения. В одном составном индексе может быть только один массивный путь, иначе получите «cannot index parallel arrays». И covered query по multikey-полю невозможна, потому что массив нельзя восстановить из отдельных записей.

**Unique** несёт ловушку, которая ломает продакшен: отсутствующее поле индексируется как `null`, а `null == null`. Поэтому **два** документа, у которых поля `email` нет вообще, дают `E11000`.

```js
// Решение: индексировать только документы, где поле есть
db.users.createIndex(
  { email: 1 },
  { unique: true, partialFilterExpression: { email: { $exists: true } } },
);
// sparse: true тоже работает, но partial гибче и рекомендуется
```

**TTL** расшифровывается как time-to-live, «время жизни»: сервер сам удаляет документ, когда его поле с датой стало старше заданного срока. Знать надо четыре вещи.

Удаление делает фоновый процесс, просыпающийся раз в 60 секунд, поэтому это не точный дедлайн. Истечение сессии всё равно проверяется условием в запросе. Поле обязано быть типа `Date`, и на составной индекс TTL не ставится. И удаляет только primary; на secondary изменение приходит через oplog, журнал применённых записей.

## Группа 5: агрегация

**16. Почему `$lookup` — это не бесплатное соединение, и что с этим делать?**

Стадия `$lookup` выполняется как вложенный цикл: для **каждого** документа, пришедшего в стадию, делается поиск в целевой коллекции. Нет ни hash join, ни merge join, ни выбора порядка соединения планировщиком. Это принципиальное отличие от `JOIN` в PostgreSQL.

Отсюда напрямую три следствия:

- Индекс по `foreignField` обязателен. Без него каждый из N поисков сканирует целевую коллекцию целиком.
- Результат всегда массив, поэтому чтобы получить объект, нужен `$unwind` — плюс решение, что делать с документами без совпадений.
- Форма с `let` и `pipeline` — это correlated subquery, коррелированный подзапрос, тоже выполняемый на каждый входной документ.

```js
db.posts.aggregate([
  { $match: { status: "published" } },   // СНАЧАЛА сужаем вход
  { $sort:  { publishedAt: -1 } },
  { $limit: 20 },
  { $lookup: { from: "users", localField: "author._id",
               foreignField: "_id", as: "author" } },
  { $unwind: "$author" },
]);
```

Но главный вывод относится к схеме, а не к агрегации. Если `$lookup` стоит в основном пути чтения, схема спроектирована реляционно. Extended Reference убирает стадию целиком, а не оптимизирует её: `author: { _id, name, avatar }` прямо в посте. Сама стадия остаётся законным инструментом для отчётов, админок и редких запросов. Обе половины разобраны в статье про агрегацию и статье про проектирование схемы.

**17. Как оптимизировать пайплайн, и где вообще стоит считать — в базе или в Node?**

Главное правило — «фильтруй раньше». Индексы в агрегации работают только на стадиях **до** первой стадии, меняющей поток документов, поэтому `$match` и `$sort` должны быть в начале.

Кое-что оптимизатор делает сам:

- Протаскивает `$match` через `$project` и `$addFields`.
- Сливает `$sort` плюс `$limit` в top-k sort, сортировку с отбором лучших.
- Склеивает подряд идущие `$limit` и `$skip`.

Но двух вещей он не сделает. Он не протащит `$match` через `$group`, потому что это фильтр по вычисленному полю — аналог `HAVING`, и индекса там нет. И он не догадается, что `$lookup` стоило сделать после `$limit`.

Дальше надо помнить про лимиты:

- Блокирующие стадии (`$group`, `$sort` без индекса, `$facet`) ограничены 100 МБ. Опция `allowDiskUse` снимает падение, но не медленную работу. Она нужна, чтобы пережить пик, а не как постоянный режим.
- Документ результата ограничен 16 МБ. Поэтому `$group` с `$push` по большой коллекции упадёт независимо от `allowDiskUse`.

Где считать — в базе, когда:

- объём на входе много больше результата (2M комментариев дают 10 строк отчёта);
- работа сводится к индексам и группировке;
- результат материализуется через `$merge`.

В Node, когда:

- данных уже мало;
- логика содержит вызовы внешних сервисов и правила, меняющиеся с продуктом;
- её нужно покрыть тестами.

Ориентир: агрегация хорошо считает данные, приложение хорошо выражает бизнес-правила. Пайплайн на 12 стадий из `$cond` и `$switch` — это программа на неудобном языке без отладчика.

## Группа 6: репликация, консистентность, транзакции, шардинг

**18. Что значит «запись подтверждена»? Разберите write concern и read concern.**

Write concern отвечает на один вопрос: когда считать запись состоявшейся. Назвать стоит четыре настройки.

```txt
w: 1            применил primary
w: "majority"   применило большинство членов сета
j: true         операция попала в журнал на диске
w: 0            не ждём вообще ничего
```

Разница между `w: 1` и `majority` конкретна. Пройдите по сбою шаг за шагом:

1. Клиент пишет с `w: 1`. Primary применяет запись и подтверждает.
2. Secondaries ещё не скопировали операцию из oplog — журнала применённых записей, который они повторяют у себя.
3. Primary падает.
4. Выборы делают новым primary узел из тех, кто операции не видел.
5. Старый узел возвращается, находит у себя операцию, которой нет в истории нового primary, и откатывает её.

Итог: клиент получил «успех», а данных в базе нет. Именно поэтому с MongoDB 5.0 значение по умолчанию — `w: "majority"`. На старых кластерах и в старом коде было `w: 1`, и это надо проверять.

Read concern отвечает на другой вопрос — какие данные считать существующими:

- `local` вернёт свежие данные узла, которые теоретически могут быть откачены.
- `majority` вернёт только подтверждённое большинством.
- `snapshot` используется внутри транзакций.

И третья независимая настройка — read preference: у кого спрашивать. Реальные гарантии определяет комбинация всех трёх, и «консистентность» без указания всех трёх — пустое слово.

Отдельно: `wtimeout` отменяет ожидание, а не запись. Поэтому слепой повтор после `wtimeout` даёт дубли, если операция не идемпотентна. Полная матрица — в статье про репликацию.

**19. Чем опасно чтение с secondary, и как получить read-your-own-write?**

Чтение с secondary даёт итоговую согласованность (eventual consistency): копия догоняет чуть позже. Проблем тут три, и они разные.

1. **Ломается read-your-own-write.** Пользователь сохранил профиль, то есть записал на primary. И сразу открыл страницу, которая читает с secondary, ещё не применившей операцию. Он видит старые данные и считает, что сохранение не сработало.
2. **Репликационный лаг непредсказуем.** В норме миллисекунды, но при пиковой записи, долгой сборке индекса или медленном диске — секунды и минуты. Ограничить можно только выбор узла, через `maxStalenessSeconds`.
3. **Реплики не масштабируют запись.** Каждая secondary применяет те же операции, что primary, поэтому добавление реплик увеличивает только пропускную способность чтения, и то ценой устаревших данных. Запись масштабирует шардинг.

Уместные случаи для secondary: отчёты, тяжёлые агрегации, которые не должны конкурировать с продуктовой нагрузкой, гео-локальные чтения через `nearest`, резервное копирование.

А если нужны и разгрузка primary, и гарантия «увижу свою запись» — это сессия с причинной согласованностью. Драйвер передаёт логическое время операции, и чтение ждёт, пока узел его догонит. То есть решается сессией, а не выбором узла.

**20. Как выглядит транзакция в MongoDB, чего она стоит и где чаще всего ошибаются?**

API — это `session.withTransaction(async () => { ... })`. Он сам делает ретраи на `TransientTransactionError` (конфликт записи, смена primary) и на `UnknownTransactionCommitResult`, а `throw` внутри колбэка означает abort.

```js
await session.withTransaction(async () => {
  // Каждая операция ОБЯЗАНА ��олучить { session }
  await posts.updateOne({ _id }, { $inc: { "stats.comments": 1 } },
                        { session });
  await comments.insertOne({ postId: _id, body }, { session });
});
```

Основной ущерб приносят две ошибки:

1. **Забыть `{ session }`** у операции внутри блока. Такая операция выполняется **вне** транзакции, и в итоге половина изменений откатывается, а половина остаётся.
2. **Неидемпотентный колбэк.** Он может быть вызван повторно, поэтому «отправить письмо» или «списать через внешний API» внутри него делать нельзя.

Цена состоит из четырёх частей. Изоляция снапшота означает `WriteConflict` и ретраи под конкуренцией. Есть лимит времени, по умолчанию 60 секунд. Удерживаемые изменения занимают кэш WiredTiger до коммита. А в шардированном кластере это распределённая транзакция с двухфазным коммитом, на порядок дороже.

И главное: транзакция не заменяет проектирование схемы. Инкремент счётчика — это `$inc`. «Прочитать, проверить, записать» — это `findOneAndUpdate` с условием в фильтре. Обновление денормализованных копий обычно допускает итоговую согласованность.

**21. Как выбирают shard key и к чему приводит плохой выбор?**

Ключ должен удовлетворять трём требованиям: высокая кардинальность, равномерное распределение записи, присутствие в большинстве запросов чтения. Составной ключ вида `{ tenantId: 1, _id: 1 }` часто закрывает все три — разделение по арендаторам даёт targeted-запросы, а `_id` внутри даёт кардинальность.

Плохой выбор даёт четыре узнаваемых симптома:

- **Hot shard, горячий шард.** Монотонный ключ (`ObjectId`, timestamp) при ranged-распределении отправляет весь поток вставок в один шард, остальные простаивают. Лечится `hashed` или составным ключом.
- **Jumbo chunks, распухшие чанки.** Низкая кардинальность (`country`, `status`) означает, что все документы с одним значением обязаны лежать вместе. Чанк вырастает за лимит разделения, и балансировка ломается.
- **Scatter-gather, рассылка всем.** Фильтр без shard key заставляет `mongos` рассылать запрос на все шарды и сливать результаты. Латентность определяется самым медленным шардом, а добавление шардов делает такие запросы хуже, а не лучше.
- **Ограничения.** Уникальный индекс возможен только по shard key или его префиксу, а сортировка без shard key выполняется на `mongos`.

Ключ менять можно — `reshardCollection` появился в 5.0 — но это тяжёлая операция.

И честная оговорка: шардинг отвечает на проблему объёма, а не медленных запросов. Медленный запрос на шардированном кластере становится медленным на N шардах. Перечитать тут стоит статью про репликацию и статью про индексы.

## Группа 7: Mongoose

**22. Что Mongoose добавляет к драйверу и какой ценой?**

Mongoose — это слой над официальным драйвером. Он возвращает в код то, чего MongoDB не требует:

- схему как единую точку правды о форме документа;
- приведение типов и валидацию;
- middleware, virtuals, methods и statics;
- `populate` и цепочечный query builder.

Цена делится на три части:

1. **Гидрация.** Результат запроса — это не документ базы, а обёртка `Document` с геттерами, отслеживанием изменений и валидацией. Это стоит памяти и процессорного времени на каждый объект, и лечится это `lean()`.
2. **Скрытая магия.** Часть механизмов работает не там, где ожидаешь. Это не мелочь, а источник реальных багов — валидация и `pre('save')` на update-операциях, о чём следующий вопрос.
3. **Ещё один слой при отладке.** Между вашим вызовом и запросом к серверу есть трансформация, которую надо уметь смотреть, через `mongoose.set('debug', true)`.

Где Mongoose не нужен: скрипты миграций, тяжёлые агрегации, узкие сервисы на несколько запросов. Там прямой драйвер честнее.

И главное, что стоит произнести вслух: Mongoose не убирает необходимость понимать документную модель, индексы и атомарность. Плохая схема останется плохой. Его часто называют ORM (object-relational mapper — отображение объектов на реляционные таблицы), и название подходит лишь приблизительно, потому что MongoDB не реляционная.

---

**23. Хук `pre('save')` хеширует пароль, но в базе оказался открытый пароль. Что произошло?**

Пароль менялся через `findOneAndUpdate` или `updateOne`, а `pre('save')` — это document middleware. Оно привязано к жизненному циклу **документа**: загрузили, изменили, сохранили.

```js
// Схема хеширует в pre('save')
userSchema.pre('save', async function () { /* bcrypt.hash */ });

// Но код смены пароля прошёл мимо
await UserModel.findOneAndUpdate(
  { _id: userId },
  { $set: { passwordHash: newPassword } },   // ← пароль в открытом виде
);
// pre('save') не вызывается: документ вообще не загружался
```

Операции `findOneAndUpdate`, `updateOne`, `updateMany` и `bulkWrite` документ не загружают. Они отправляют серверу описание изменений, поэтому не существует документа, чей `save()` можно было бы перехватить.

У второй половины проблемы ровно та же природа. Валидация схемы по умолчанию не выполняется на update-операциях: для неё нужен `runValidators: true`. И даже тогда `required` не проверяется для полей, отсутствующих в обновлении, а `this` внутри кастомного валидатора — это `Query`, а не документ.

Три способа лечения, по возрастанию честности:

1. **Весь домен пишет через `doc.save()`.** Тогда хуки и валидация работают всегда. Цена — лишнее чтение и потеря атомарного read-modify-write.
2. **Продублировать хук на `pre('findOneAndUpdate')`,** работая с `this.getUpdate()` и `this.set()`. Работает для обоих путей, но логика дублируется, и остаётся третий путь — `bulkWrite`.
3. **Убрать хеширование из схемы** и делать его в сервисе — единственном месте, где меняется пароль. Часто самый честный вариант: меньше магии, и поведение видно в коде.

---

**24. `populate` против `$lookup` против пересмотра схемы. И зачем `lean()`?**

Метод `populate` — это не `$lookup`, а **дополнительные запросы**, результат которых Mongoose склеивает в памяти процесса Node. Важная поправка к расхожему мему: базовый populate по списку из 20 документов — это **один** дополнительный запрос через `$in`, а не 21.

Настоящие эффекты N+1 появляются в четырёх конкретных случаях:

- вложенный populate — запрос на каждый уровень вложенности;
- populate в цикле по документам;
- `perDocumentLimit` — запрос на каждый родительский документ;
- резолверы GraphQL без батчинга.

Две ловушки ловят почти всех. Первая: `options: { limit: 3 }` — это общий лимит на весь `$in`-запрос, а не «по 3 на документ». Первый родитель получит три, остальные ноль. Вторая: `match` фильтрует связанные документы, но не убирает родителя. Родитель вернётся с `null` в этом поле.

```txt
         Три способа получить связанные данные
┌─────────────────────────────────────────────────────┐
│ populate                                            │
│                                                     │
│ где выполняется       Node + N запросов             │
│ round-trips           2 и больше                    │
│ фильтр по связанным   match, но родитель остаётся   │
│ когда уместно         админки, редкие экраны        │
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ $lookup                                             │
│                                                     │
│ где выполняется       на сервере                    │
│ round-trips           1                             │
│ фильтр по связанным   полноценно в пайплайне        │
│ когда уместно         отчёты и агрегации            │
└─────────────────────────────────────────────────────┘
┌─────────────────────────────────────────────────────┐
│ пересмотр схемы                                     │
│                                                     │
│ где выполняется       нигде: данные уже в документе │
│ round-trips           1                             │
│ фильтр по связанным   обычный find                  │
│ когда уместно         горячий путь чтения           │
└─────────────────────────────────────────────────────┘
```

Поэтому если связанные данные нужны в **самом** частом запросе, правильный ответ — пересмотреть схему через Extended Reference. Тогда лишних обращений нет вообще.

А `lean()` — про другое. Он отдаёт обычный объект вместо `Document`, отменяя гидрацию, и на списках это разница в разы по процессорному времени и памяти. Правило: любой путь «только чтение» — с `lean()`, «изменить и сохранить» — без.

**25. Что нужно сделать с Mongoose-приложением перед продом?**

Четыре вещи.

**1. Отключить `autoIndex`.** По умолчанию Mongoose при старте вызывает `createIndex` для каждого индекса каждой схемы. У этого три цены:

- индексы собираются в момент деплоя, то есть в самый неудачный момент;
- при N инстансах сервиса получается N параллельных попыток создать один индекс;
- индекс попадает на прод всякий раз, когда кто-то правит схему, — без ревью.

Вместо этого индексы применяются миграционным шагом в пайплайне деплоя.

```js
mongoose.connect(url, { autoIndex: false });

// Шаг деплоя, запускаемый осознанно:
await PostModel.diffIndexes();   // сначала аудит: что изменится
await PostModel.syncIndexes();   // ВНИМАНИЕ: удалит индексы не из схемы
```

**2. Положить уникальные индексы в миграцию.** Это следует из первого пункта и есть его менее очевидная половина. Опция `unique: true` в схеме — это объявление индекса, а не валидатор. Поэтому при `autoIndex: false` и без миграции никакой уникальности нет вообще — хотя код выглядит так, будто есть.

**3. Понимать буферизацию команд.** До установления соединения Mongoose не бросает ошибку. Он буферизует операции до `bufferTimeoutMS`, то есть 10 секунд. В проде это выглядит как «запрос висит 10 секунд». А реальная причина — недоступный кластер или адрес, не добавленный в список разрешённых. Лечится тремя вещами:

- проверка живости по `mongoose.connection.readyState`;
- отказ принимать трафик, пока соединение не установлено;
- `bufferCommands: false` в критичных сервисах, чтобы операция без соединения падала сразу.

**4. Разложить ошибки по ответам.** Ошибка `E11000` — это 409, и приходит она от драйвера, поэтому проверяется по `e.code`, а не через `instanceof mongoose.Error`. `ValidationError` и `CastError` — это 400. Недоступность кластера — 503. Без этого маппинга всё превращается в 500 и бесполезный алерт, а `e.message` драйвера ещё и утекает значение ключа в ответ API. Полная таблица — в статье про запросы Mongoose.
