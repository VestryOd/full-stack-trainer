# Indexes and Query Performance

## Индекс — отдельная B-tree-структура по полям документа

Без индекса `find({ slug: "mongodb-indexes" })` — это COLLSCAN: сервер читает каждый документ коллекции и проверяет условие. Индекс — отдельная структура (B-tree, как в PostgreSQL), которая хранит отсортированные значения ключа и ссылку на место документа в файле данных.

```js
db.posts.createIndex({ slug: 1 })                       // 1 — по возрастанию
db.posts.createIndex({ slug: 1 }, { name: "slug_uniq", unique: true })
db.posts.getIndexes()                                   // все индексы
db.posts.dropIndex("slug_1")
db.posts.stats().indexSizes                             // размер каждого
```

```txt
Что нужно помнить про устройство:
  - индекс _id_ создаётся автоматически и не удаляется
  - в индекс попадают ВСЕ документы коллекции; документ без поля
    индексируется со значением null (кроме sparse/partial-индексов)
  - индекс по вложенному полю задаётся точечной нотацией:
      { "author._id": 1 }  — индекс по полю внутри объекта
      { author: 1 }        — индекс по объекту ЦЕЛИКОМ; работает
                             только для запросов на полное равенство
                             объекта с тем же порядком ключей
  - индексы живут в том же WiredTiger-кэше, что и данные, и
    конкурируют с ними за память
```

## Single field: направление не имеет значения

```js
db.posts.createIndex({ publishedAt: 1 })
// обслуживает и sort({ publishedAt: 1 }), и sort({ publishedAt: -1 }):
// B-tree сканируется в обе стороны
```

Направление начинает иметь значение только в составном индексе при сортировке по нескольким полям — об этом ниже.

## Compound-индекс и правило ESR

Составной индекс хранит ключи, отсортированные сначала по первому полю, внутри него — по второму, и так далее. Из этого вытекают два практических правила.

Первое — **prefix rule**: индекс `{a: 1, b: 1, c: 1}` обслуживает запросы по `(a)`, `(a, b)`, `(a, b, c)`, но не по `(b)` и не по `(b, c)`. Без фиксации левых полей нельзя «прыгнуть» в нужную часть дерева.

Второе — **ESR: Equality → Sort → Range**. Это главный практический инструмент проектирования составного индекса.

```txt
      ESR: как разложить запрос в порядок полей индекса
┌───────────────────────────────────────────────────────────┐
│ запрос:                                                   │
│ db.posts.find({ status: "published",                      │
│                 "author._id": authorId,                   │
│                 publishedAt: { $gte: monthAgo } })        │
│         .sort({ views: -1 })                              │
├───────────────────────────────────────────────────────────┤
│ E (equality)  status, author._id   — точные значения      │
│ S (sort)      views: -1            — порядок выдачи       │
│ R (range)     publishedAt: $gte    — диапазон             │
├───────────────────────────────────────────────────────────┤
│ индекс:                                                   │
│ { status: 1, "author._id": 1, views: -1, publishedAt: 1 } │
│   → IXSCAN без стадии SORT и без лишних FETCH             │
└───────────────────────────────────────────────────────────┘
поменять S и R местами — и появится SORT в памяти на всей выборке
```

Почему именно такой порядок:

```txt
E — Equality первыми.
    Точное равенство фиксирует префикс ключа, то есть сужает скан до
    непрерывного участка индекса. Каждое equality-поле впереди
    уменьшает количество просмотренных ключей.

S — Sort сразу после equality.
    Внутри зафиксированного префикса ключи УЖЕ отсортированы по
    следующему полю индекса. Если это поле совпадает с sort, сервер
    отдаёт документы в готовом порядке — стадии SORT в плане нет.
    Это же делает limit дешёвым: 20 документов берутся с начала
    скана, а не после сортировки всей выборки.

R — Range последними.
    Диапазон ($gt, $lt, $in по многим значениям, $regex с префиксом)
    читает НЕПРЕРЫВНЫЙ участок ключей. Внутри этого участка порядок
    по следующему полю уже не является общим порядком — поэтому
    любое sort-поле ПОСЛЕ range-поля не спасает от сортировки
    в памяти.
```

```js
// Тот же запрос с «интуитивным» индексом (range перед sort)
db.posts.createIndex({ status: 1, publishedAt: 1, views: -1 })
db.posts.find({ status: "published", publishedAt: { $gte: monthAgo } })
        .sort({ views: -1 }).limit(20).explain("executionStats")
// → в плане есть SORT: сервер собрал ВСЕ подходящие документы за
//   месяц, отсортировал их в памяти и только потом взял 20

// Индекс по ESR
db.posts.createIndex({ status: 1, views: -1, publishedAt: 1 })
// → SORT нет: скан идёт в нужном порядке, limit обрывает его рано
```

Направление полей в составном индексе важно, когда сортировка идёт по нескольким полям в разных направлениях:

```txt
sort({ publishedAt: -1, title: 1 }) обслуживается индексом
  { publishedAt: -1, title: 1 }   — прямое совпадение
  { publishedAt: 1, title: -1 }   — ПОЛНЫЙ реверс (скан в обратную
                                    сторону) тоже подходит
  { publishedAt: -1, title: -1 }  — НЕ подходит: нужна сортировка
                                    в памяти
```

## Multikey: индексы по массивам

Если индексируемое поле — массив, индекс становится multikey: для документа создаётся отдельная запись индекса на КАЖДЫЙ элемент массива. Специального синтаксиса нет — MongoDB определяет это сама.

```js
db.posts.createIndex({ tags: 1 })       // multikey, если tags — массив
db.posts.find({ tags: "mongodb" })      // IXSCAN по одной записи индекса

// Индекс по полю внутри массива объектов — тоже multikey
db.posts.createIndex({ "recentComments.author._id": 1 })
```

```txt
Ограничения multikey, которые спрашивают на интервью:
  - в одном составном индексе может быть только ОДИН массивный путь.
    { tags: 1, ratings: 1 } при двух массивах → ошибка записи
    "cannot index parallel arrays"
  - covered query по multikey-полю невозможна: сервер не может
    восстановить исходный массив из отдельных записей индекса,
    поэтому документ всё равно читается (FETCH)
  - размер индекса пропорционален суммарному числу элементов, а не
    числу документов: 1M документов по 20 тегов = 20M записей
  - $elemMatch с несколькими условиями использует индекс, но
    отсеивание «оба условия на одном элементе» происходит уже
    на FETCH (см. [CRUD and Query Operators])
```

Это ещё один аргумент против неограниченно растущих массивов из [Schema Design: Embedding vs Referencing]: они бьют не только по размеру документа, но и по размеру индекса.

## Unique, partial, TTL

```js
// unique — уникальность в пределах коллекции
db.users.createIndex({ email: 1 }, { unique: true })
// на массиве проверяются ЭЛЕМЕНТЫ: два документа не могут иметь
// общий элемент в уникальном multikey-поле
```

```txt
Ловушка unique, которая ломает продакшен: отсутствующее поле
индексируется как null, а null == null. Значит ДВА документа без
поля email нарушают уникальность:

  db.users.insertOne({ name: "a" })            // ок, email = null
  db.users.insertOne({ name: "b" })            // E11000 duplicate key

Правильное решение — partial-индекс: «уникальность только среди тех,
у кого поле есть»:

  db.users.createIndex(
    { email: 1 },
    { unique: true, partialFilterExpression: { email: { $exists: true } } }
  )

sparse: true решает ту же задачу и остаётся рабочим, но
partialFilterExpression гибче и рекомендуется как основной способ.
```

```js
// partial — индексируем подмножество документов
db.posts.createIndex(
  { publishedAt: -1 },
  { partialFilterExpression: { status: "published" } }
);
// индекс в разы меньше (черновики в него не попадают) → лучше
// умещается в кэш. Условие: запрос ДОЛЖЕН содержать
// { status: "published" } (или более строгое), иначе планировщик
// не имеет права использовать этот индекс

// TTL — автоматическое удаление по времени
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
// удалит документ, когда expiresAt окажется в прошлом
db.eventLog.createIndex({ createdAt: 1 }, { expireAfterSeconds: 604800 });
// удалит через 7 дней после createdAt
```

```txt
Что важно про TTL:
  - удаляет ФОНОВЫЙ процесс, просыпающийся раз в 60 секунд:
    удаление не мгновенное, документ может «жить» лишнюю минуту и
    дольше под нагрузкой. Логика приложения не должна на TTL
    полагаться как на точный дедлайн (сессию всё равно проверяем
    по expiresAt в запросе)
  - поле должно быть Date (или массив дат — тогда берётся минимальная)
  - TTL нельзя поставить на составной индекс
  - удаляет только primary; на secondary изменения приходят через
    oplog (см. [Replication, Transactions, and Consistency])
```

## Text-индекс и честная оговорка про Atlas Search

```js
db.posts.createIndex({ title: "text", body: "text" },
                     { weights: { title: 10, body: 1 },
                       default_language: "russian" });

db.posts.find({ $text: { $search: "индексы mongodb" } },
              { score: { $meta: "textScore" } })
        .sort({ score: { $meta: "textScore" } });
```

```txt
Возможности и границы встроенного text-индекса:
  + стемминг и стоп-слова для основных языков, веса полей,
    исключение слов через "-слово", фразы в кавычках
  + работает в обычном self-hosted кластере, без внешних сервисов
  - НА КОЛЛЕКЦИЮ МОЖЕТ БЫТЬ ТОЛЬКО ОДИН text-индекс
  - нет опечаток (fuzzy), автодополнения, синонимов, релевантности
    уровня поисковика, фасетов
  - $text нельзя комбинировать с некоторыми стадиями и сортировками
    так свободно, как обычный индекс

Честный ответ на интервью: для настоящего поиска в 2026 году в
экосистеме MongoDB используют Atlas Search (Lucene внутри) —
он даёт fuzzy, autocomplete, фасеты и подсветку. Встроенный
text-индекс — это «поиск по заголовкам, чтобы не тащить Elasticsearch»,
и его ограничение «один на коллекцию» надо называть сразу.
```

Ещё два типа стоит знать по названию: **wildcard** `{ "attributes.$**": 1 }` — когда набор полей заранее неизвестен (те самые разнородные атрибуты каталога), и **hashed** — для шардинга по хешу ключа (см. [Replication, Transactions, and Consistency]).

## explain(): как читать план

```js
db.posts.find({ status: "published" }).sort({ views: -1 }).limit(20)
        .explain("executionStats")
```

```txt
Три режима:
  queryPlanner       — только выбранный план, запрос НЕ выполняется
                       (по умолчанию)
  executionStats     — план + фактические числа: выполняется
  allPlansExecution  — то же плюс статистика отвергнутых планов
```

```txt
без индекса             индекс + документы              covered query
┌──────────┐            ┌────────┐                  ┌────────────────────┐
│ COLLSCAN │            │ IXSCAN │                  │ IXSCAN             │
│   ↓      │            │   ↓    │                  │   ↓                │
│ SORT     │            │ FETCH  │                  │ PROJECTION_COVERED │
│   ↓      │            │   ↓    │                  │   ↓                │
│ LIMIT    │            │ LIMIT  │                  │ LIMIT              │
└──────────┘            └────────┘                  └────────────────────┘
читает все документы,   по индексу находит ключи,   документы не читаются
сортирует в памяти      потом читает документы      вообще: docsExamined = 0
```

Дерево в `winningPlan` печатается от корня к листьям, то есть в обратном порядке относительно потока данных: сначала виден `LIMIT`, внутри него `FETCH`, внутри — `IXSCAN`. Читать удобнее с самой глубокой стадии — она и есть источник документов.

```txt
Четыре числа из executionStats, которые решают всё:
  nReturned          — сколько документов вернул запрос
  totalKeysExamined  — сколько ключей индекса просмотрено
  totalDocsExamined  — сколько документов прочитано из коллекции
  executionTimeMillis — время выполнения

Здоровый запрос: nReturned ≈ totalKeysExamined ≈ totalDocsExamined.
Любой разрыв на порядок — это работа, которая была выполнена впустую.
```

```txt
                Чтение executionStats: признак → диагноз → что делать
┌───────────────────────────┬─────────────────────────┬─────────────────────────────┐
│ что видно                 │ что это значит          │ что делать                  │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ stage: COLLSCAN           │ индекс не используется  │ создать индекс по ESR       │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ stage: SORT               │ сортировка в памяти     │ добавить sort-поле в индекс │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ docsExamined >> nReturned │ индекс плохо селективен │ уточнить порядок полей      │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ keysExamined >> nReturned │ скан широкого диапазона │ вынести equality вперёд     │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ docsExamined = 0          │ covered query           │ ничего, это цель            │
├───────────────────────────┼─────────────────────────┼─────────────────────────────┤
│ rejectedPlans пусто       │ план один               │ проверить, что он ожидаемый │
└───────────────────────────┴─────────────────────────┴─────────────────────────────┘
         ориентир здорового запроса: nReturned ≈ docsExamined ≈ keysExamined
```

Про стадию `SORT` стоит сказать отдельно: она означает сортировку в памяти, и у неё есть лимит 100 МБ. При превышении запрос падает с «Sort exceeded memory limit» — либо нужен `allowDiskUse` (доступен и для `find` с 4.4), либо, что правильнее, индекс по ESR, который убирает стадию вообще.

```js
// Проверка, использовался ли ожидаемый индекс
const e = db.posts.find(filter).sort(s).explain("executionStats");
e.executionStats.executionStages.stage      // "LIMIT" / "FETCH" / "SORT"...
e.queryPlanner.winningPlan.inputStage.indexName
e.queryPlanner.rejectedPlans.length         // были ли альтернативы
```

Планировщик выбирает план не по формуле, а эмпирически: при первом запуске формы запроса он прогоняет кандидатов на небольшом объёме работы, выбирает лучший и кладёт его в plan cache. Отсюда практическое следствие — план может «внезапно измениться»: кэш сбрасывается при перестройке индексов, рестарте, значительном изменении объёма данных. Поэтому индекс проектируют так, чтобы он был выигрышным по ESR, а не надеются на удачный выбор планировщика.

## Covered queries

Если все поля, нужные запросу (и в фильтре, и в проекции, и в сортировке), присутствуют в индексе, сервер отвечает, не читая документы вообще.

```js
db.posts.createIndex({ status: 1, publishedAt: -1, title: 1 });

db.posts.find({ status: "published" }, { _id: 0, title: 1, publishedAt: 1 })
        .sort({ publishedAt: -1 });
// → totalDocsExamined: 0, стадия PROJECTION_COVERED
```

```txt
Условия covered query:
  1. все поля фильтра/сортировки/проекции — в индексе
  2. проекция исключает _id ({ _id: 0 }), если _id не входит в индекс
  3. индексируемое поле НЕ multikey (массив восстановить нельзя)
  4. поля не должны быть в поддокументах, для которых требуется
     проверка формы

Признак в explain: totalDocsExamined = 0 при nReturned > 0.
Практический смысл: covered query — цель для горячих
«списочных» запросов (лента, автодополнение), где проекция
маленькая и предсказуемая.
```

## Когда индекс НЕ используется

```txt
1. Нарушен ESR: range-поле стоит раньше sort-поля
   → IXSCAN есть, но появляется SORT в памяти на всей выборке.

2. $regex без якоря в начале или с флагом i
   /^mongodb-/  → префикс известен → IXSCAN по диапазону
   /^mongodb-/i → регистронезависимость ломает порядок → скан индекса
   /indexes/    → подстрока в середине → скан индекса или COLLSCAN

3. $ne / $nin — по смыслу «всё, кроме»: селективность близка к 100%,
   поэтому даже при использовании индекса читается почти весь его
   объём. Практически всегда переформулируется в $in по разрешённым
   значениям.

4. Вычисление над полем вместо самого поля
   { $expr: { $gt: [ { $year: "$publishedAt" }, 2025 ] } } — индекс
   по publishedAt не применяется; нужен диапазон по самому полю
   ($gte/$lt на границы года). $where — не использует индексы вовсе
   и выполняет JS на сервере (не применять).

5. Несовпадение типов BSON: "42" и 42 — разные значения индекса.
   Классика: id пришёл из query-строки строкой, а в базе ObjectId →
   запрос честно ничего не находит.

6. Collation не совпадает: индекс, созданный с одной коллацией, не
   обслуживает запрос с другой.

7. $or — каждой ветке нужен СВОЙ индекс. Если у одной ветки индекса
   нет, весь $or деградирует до COLLSCAN (в плане это SUBPLAN/OR).

8. Низкая селективность: { archived: false } при 99% false —
   планировщик обоснованно выберет COLLSCAN, потому что чтение
   документов по индексу вразброс дороже последовательного чтения.

9. Индекс не влезает в память: он используется, но каждое обращение
   к его страницам — это дисковое чтение, и выигрыш падает.
```

## Цена индексов на запись

```txt
Каждый insert/update/delete обновляет ВСЕ затронутые индексы:
  - insert → одна запись в каждый индекс (в multikey — по одной
    на каждый элемент массива)
  - update поля, входящего в индекс → удаление старого ключа +
    вставка нового
  - update поля, НЕ входящего ни в один индекс → индексы не трогаются
  - delete → удаление ключей из всех индексов

Практические следствия:
  - 10 индексов на коллекцию с интенсивной записью — это x10 работы
    на каждую вставку
  - индексы должны умещаться в WiredTiger-кэш (по умолчанию ~50%
    RAM минус 1 ГБ) вместе с рабочим набором данных; иначе индекс
    перестаёт быть быстрым
  - «индекс на всякий случай» — это постоянный налог на запись
    без выгоды на чтении
```

```js
// Найти неиспользуемые индексы: статистика обращений с рестарта
db.posts.aggregate([{ $indexStats: {} }])
// → { name, accesses: { ops: 0, since } } — ops: 0 на живом трафике
//   за длительный период это кандидат на удаление

// Безопасное удаление: сначала скрыть от планировщика, убедиться,
// что ничего не замедлилось, и только потом удалять
db.posts.hideIndex("status_1_views_-1")
db.posts.unhideIndex("status_1_views_-1")   // если стало хуже
db.posts.dropIndex("status_1_views_-1")
```

Про сборку индексов в проде: начиная с 4.2 `createIndex` использует гибридную сборку и не держит коллекцию заблокированной всё время построения, но нагрузку на диск и CPU создаёт заметную. На больших продакшен-кластерах индексы традиционно собирают rolling-способом — по одному узлу реплика-сета за раз. В приложениях на Mongoose важно отдельно отключить автоматическое создание индексов (`autoIndex: false`) и управлять ими осознанно — см. [Mongoose Queries, populate, and Pitfalls].

## Типичные ошибки на интервью

- **«Порядок полей в составном индексе не важен»** — важен принципиально: prefix rule и ESR. `{status, views, publishedAt}` и `{status, publishedAt, views}` — это индексы с разным поведением на одном и том же запросе; второй добавит стадию SORT.

- **«Правило ESR — это Equality, Sort, Range… а sort вообще при чём?»** — sort-поле должно быть в индексе, иначе сортировка идёт в памяти с лимитом 100 МБ, а `limit` перестаёт быть дешёвым: сортировать приходится всю выборку.

- **«`{ tags: 1 }` — обычный индекс»** — если `tags` массив, это multikey: запись на каждый элемент, невозможность covered query и запрет на второй массив в том же составном индексе.

- **«`unique: true` — и всё, дублей не будет»** — документы без поля индексируются как `null`, поэтому второй такой документ упадёт с E11000. Нужен `partialFilterExpression: { field: { $exists: true } }`.

- **«TTL-индекс удаляет документ точно в срок»** — фоновый процесс просыпается раз в минуту, под нагрузкой задержка больше. Истечение сессии проверяется в запросе, а не доверяется TTL.

- **«Индекс всегда ускоряет запрос»** — при низкой селективности планировщик выберет COLLSCAN, и это правильное решение. А на записи каждый индекс — постоянные накладные расходы.

- **«explain показывает, что используется индекс — значит всё хорошо»** — надо смотреть числа: `keysExamined` и `docsExamined` против `nReturned`, и отсутствие стадии SORT. IXSCAN, просматривающий миллион ключей ради 20 документов, — это медленный запрос с индексом.

- **«Covered query — это когда есть индекс»** — это когда документы не читаются вообще: `totalDocsExamined: 0`. Требуется, чтобы все поля были в индексе, `_id` исключён из проекции, а поле не было multikey.

- **«`$regex` работает по индексу»** — только с якорем `^` и без флага `i`. Поиск подстроки — это скан; для настоящего поиска нужен text-индекс (один на коллекцию) или Atlas Search.

- **«Больше индексов — быстрее»** — быстрее до момента, когда индексы перестают влезать в кэш и когда запись начинает стоить в разы дороже. Неиспользуемые индексы находятся через `$indexStats` и удаляются (сначала `hideIndex`).
