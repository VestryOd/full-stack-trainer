# Индексы и производительность запросов

## Индекс — отдельная B-tree-структура по полям документа

Без индекса `find({ slug: "mongodb-indexes" })` — это COLLSCAN. Так называется план полного сканирования коллекции: сервер читает каждый документ и проверяет условие. Индекс — отдельная структура, B-дерево, точно как в PostgreSQL. Он хранит отсортированные значения ключа и ссылку на место документа в файле данных.

Когда подходящий индекс есть, план становится IXSCAN — сканированием индекса. Сервер идёт по отсортированным ключам и не трогает документы, которые ему не нужны.

```js
db.posts.createIndex({ slug: 1 })                       // 1 — по возрастанию
db.posts.createIndex({ slug: 1 }, { name: "slug_uniq", unique: true })
db.posts.getIndexes()                                   // все индексы
db.posts.dropIndex("slug_1")
db.posts.stats().indexSizes                             // размер каждого
```

```txt
Что нужно помнить про устройство:
  - индекс _id_ создаётся автоматически и не удаляется
  - в индекс попадают все документы коллекции; документ без поля
    индексируется со значением null (кроме sparse/partial-индексов)
  - индекс по вложенному полю задаётся точечной нотацией:
      { "author._id": 1 }  — индекс по полю внутри объекта
      { author: 1 }        — индекс по объекту целиком; работает
                             только для запросов на полное
                             равенство объекта с тем же порядком
                             ключей
  - индексы живут в том же кэше WiredTiger, что и данные, и
    конкурируют с ними за память
```

## Индекс по одному полю: направление не имеет значения

Индекс по одному полю работает в обе стороны сортировки, потому что B-дерево можно сканировать в любом направлении.

```js
db.posts.createIndex({ publishedAt: 1 })
// обслуживает и sort({ publishedAt: 1 }), и sort({ publishedAt: -1 }):
// B-tree сканируется в обе стороны
```

Направление начинает иметь значение только в составном индексе, при сортировке по нескольким полям — об этом ниже.

## Составной индекс и правило ESR

ESR расшифровывается как Equality → Sort → Range, то есть «равенство, сортировка, диапазон». Это порядок, в котором надо перечислять поля составного индекса.

Сначала — одно свойство структуры. Составной индекс хранит ключи, отсортированные по первому полю, внутри него — по второму, и так далее. Из этого вытекают два практических правила.

Первое — **правило префикса** (prefix rule). Индекс `{a: 1, b: 1, c: 1}` обслуживает запросы по `(a)`, `(a, b)` и `(a, b, c)`. Запросы по `(b)` и `(b, c)` он не обслуживает. Без фиксации левых полей нельзя «прыгнуть» в нужную часть дерева.

```txt
индекс { status: 1, views: -1, publishedAt: 1 } обслуживает
  { status }                                    → да
  { status, views }                             → да
  { status, views, publishedAt }                → да
  { views }                                     → нет, status
                                                  не зафиксирован
  { views, publishedAt }                        → нет
```

Второе правило — сам **ESR**. Это главный практический инструмент проектирования составного индекса.

```txt
      ESR: как разложить запрос в порядок полей индекса
┌───────────────────────────────────────────────────────────┐
│ запрос:                                                   │
│ db.posts.find({ status: "published",                      │
│                 "author._id": authorId,                   │
│                 publishedAt: { $gte: monthAgo } })        │
│         .sort({ views: -1 })                              │
├───────────────────────────────────────────────────────────┤
│ E (equality)  status, author._id   — точные значения      │
│ S (sort)      views: -1            — порядок выдачи       │
│ R (range)     publishedAt: $gte    — диапазон             │
├───────────────────────────────────────────────────────────┤
│ индекс:                                                   │
│ { status: 1, "author._id": 1, views: -1, publishedAt: 1 } │
│   → IXSCAN без стадии SORT и без лишних FETCH             │
└───────────────────────────────────────────────────────────┘
поменять S и R местами — и появится SORT в памяти на всей выборке
```

Почему именно такой порядок:

```txt
E — Equality первыми.
    Точное равенство фиксирует префикс ключа, то есть сужает скан
    до непрерывного участка индекса. Каждое equality-поле впереди
    уменьшает количество просмотренных ключей.

S — Sort сразу после equality.
    Внутри зафиксированного префикса ключи уже отсортированы по
    следующему полю индекса. Если это поле совпадает с sort,
    сервер отдаёт документы в готовом порядке, и стадии SORT
    в плане нет. Это же делает limit дешёвым: 20 документов
    берутся с начала скана, а не после сортировки всей выборки.

R — Range последними.
    Диапазон ($gt, $lt, $in по многим значениям, $regex
    с префиксом) читает непрерывный участок ключей. Внутри этого
    участка порядок по следующему полю — уже не общий порядок.
    Поэтому sort-поле, стоящее после range-поля, не спасает
    от сортировки в памяти.
```

```js
// Тот же запрос с «интуитивным» индексом (range перед sort)
db.posts.createIndex({ status: 1, publishedAt: 1, views: -1 })
db.posts.find({ status: "published", publishedAt: { $gte: monthAgo } })
        .sort({ views: -1 }).limit(20).explain("executionStats")
// → в плане есть SORT: сервер собрал все подходящие документы за
//   месяц, отсортировал их в памяти и только потом взял 20

// Индекс по ESR
db.posts.createIndex({ status: 1, views: -1, publishedAt: 1 })
// → SORT нет: скан идёт в нужном порядке, limit обрывает его рано
```

Направление полей в составном индексе важно, когда сортировка идёт по нескольким полям в разных направлениях:

```txt
sort({ publishedAt: -1, title: 1 }) обслуживается индексом
  { publishedAt: -1, title: 1 }   — прямое совпадение
  { publishedAt: 1, title: -1 }   — полный реверс, скан
                                    в обратную сторону; тоже
                                    подходит
  { publishedAt: -1, title: -1 }  — не подходит: нужна
                                    сортировка в памяти
```

## Multikey: индексы по массивам

Если индексируемое поле — массив, индекс становится multikey. На каждый элемент массива в документе создаётся отдельная запись индекса. Специального синтаксиса нет — MongoDB определяет это сама.

```js
db.posts.createIndex({ tags: 1 })       // multikey, если tags — массив
db.posts.find({ tags: "mongodb" })      // IXSCAN по одной записи индекса

// Индекс по полю внутри массива объектов — тоже multikey
db.posts.createIndex({ "recentComments.author._id": 1 })
```

```txt
Ограничения multikey, которые спрашивают на интервью:
  - в одном составном индексе может быть только один массивный
    путь. { tags: 1, ratings: 1 } при двух массивах → ошибка
    записи "cannot index parallel arrays"
  - покрывающий запрос по multikey-полю невозможен: сервер не
    может восстановить исходный массив из отдельных записей
    индекса, поэтому документ всё равно читается (FETCH)
  - размер индекса пропорционален суммарному числу элементов,
    а не числу документов: 1M документов по 20 тегов = 20M записей
  - $elemMatch с несколькими условиями использует индекс, но
    отсеивание «оба условия на одном элементе» происходит уже
    на FETCH (см. статью 02 про операторы запросов)
```

Это ещё один аргумент против неограниченно растущих массивов из статьи 03 про проектирование схемы: они бьют не только по размеру документа, но и по размеру индекса.

## Unique, partial и TTL: три индекса, которые делают не только поиск

Эти три вида индекса решают задачи, не связанные с ускорением чтения. Индекс `unique` запрещает дубли. Индекс `partial` покрывает только часть документов, поэтому он меньше и лучше умещается в кэш. TTL, от time to live — «время жизни», удаляет документы по истечении срока.

```js
// unique — уникальность в пределах коллекции
db.users.createIndex({ email: 1 }, { unique: true })
// на массиве проверяются элементы: два документа не могут иметь
// общий элемент в уникальном multikey-поле
```

```txt
Ловушка unique, которая ломает продакшен: отсутствующее поле
индексируется как null, а null == null. Значит два документа
без поля email нарушают уникальность:

  db.users.insertOne({ name: "a" })     // ок, email = null
  db.users.insertOne({ name: "b" })     // E11000 duplicate key

Правильное решение — partial-индекс, то есть «уникальность
только среди тех, у кого поле есть»:

  db.users.createIndex(
    { email: 1 },
    { unique: true,
      partialFilterExpression: { email: { $exists: true } } }
  )

sparse: true решает ту же задачу и остаётся рабочим, но
partialFilterExpression гибче и рекомендуется как основной способ.
```

```js
// partial — индексируем подмножество документов
db.posts.createIndex(
  { publishedAt: -1 },
  { partialFilterExpression: { status: "published" } }
);
// индекс в разы меньше (черновики в него не попадают) → лучше
// умещается в кэш. Условие: запрос должен содержать
// { status: "published" } (или более строгое), иначе планировщик
// не имеет права использовать этот индекс

// TTL — автоматическое удаление по времени
db.sessions.createIndex({ expiresAt: 1 }, { expireAfterSeconds: 0 });
// удалит документ, когда expiresAt окажется в прошлом
db.eventLog.createIndex({ createdAt: 1 }, { expireAfterSeconds: 604800 });
// удалит через 7 дней после createdAt
```

```txt
Что важно про TTL:
  - удаляет фоновый процесс, который просыпается раз в 60 секунд.
    Удаление не мгновенное: под нагрузкой документ может «жить»
    лишнюю минуту и дольше. Логика приложения не должна полагаться
    на TTL как на точный дедлайн — срок сессии всё равно
    проверяется по expiresAt в запросе.
  - поле должно быть Date или массивом дат, тогда берётся
    минимальная дата
  - TTL нельзя поставить на составной индекс
  - удаляет только primary; на secondary изменения приходят через
    oplog, журнал операций, который они повторяют (статья 06)
```

## Text-индекс и честная оговорка про Atlas Search

В MongoDB есть встроенный полнотекстовый индекс. Для поиска по заголовкам его хватает, но поисковой системой он не работает.

```js
db.posts.createIndex({ title: "text", body: "text" },
                     { weights: { title: 10, body: 1 },
                       default_language: "russian" });

db.posts.find({ $text: { $search: "индексы mongodb" } },
              { score: { $meta: "textScore" } })
        .sort({ score: { $meta: "textScore" } });
```

```txt
Возможности и границы встроенного text-индекса:
  + стемминг и стоп-слова для основных языков, веса полей,
    исключение слов через "-слово", фразы в кавычках
  + работает в обычном самостоятельно развёрнутом кластере,
    без внешних сервисов
  - на коллекцию может быть только **один** text-индекс
  - нет устойчивости к опечаткам (fuzzy), автодополнения,
    синонимов, релевантности уровня поисковика, фасетов
  - $text нельзя комбинировать с некоторыми стадиями
    и сортировками так свободно, как обычный индекс

Честный ответ на интервью: для настоящего поиска в 2026 году
в экосистеме MongoDB используют Atlas Search, внутри которого
работает Lucene. Он даёт устойчивость к опечаткам,
автодополнение, фасеты и подсветку. Встроенный text-индекс —
это «поиск по заголовкам, чтобы не тащить Elasticsearch»,
и его ограничение «один на коллекцию» надо называть сразу.
```

Ещё два типа стоит знать по названию. Индекс **wildcard**, `{ "attributes.$**": 1 }`, нужен, когда набор полей заранее неизвестен. Обычный случай — те самые разнородные атрибуты каталога. Индекс **hashed** нужен для шардинга по хешу ключа, про это статья 06.

## explain(): как читать план

`explain()` — это способ узнать, что сервер сделал на самом деле, вместо того чтобы догадываться.

```js
db.posts.find({ status: "published" }).sort({ views: -1 }).limit(20)
        .explain("executionStats")
```

```txt
Три режима:
  queryPlanner       — только выбранный план, запрос не выполняется
                       (по умолчанию)
  executionStats     — план плюс фактические числа: запрос
                       выполняется
  allPlansExecution  — то же плюс статистика отвергнутых планов
```

Три формы плана покрывают почти всё, что вы встретите:

```txt
без индекса
┌──────────┐
│ COLLSCAN │
│   ↓      │
│ SORT     │
│   ↓      │
│ LIMIT    │
└──────────┘
читает все документы,
сортирует в памяти

индекс + документы
┌────────┐
│ IXSCAN │
│   ↓    │
│ FETCH  │
│   ↓    │
│ LIMIT  │
└────────┘
по индексу находит ключи,
потом читает документы

  покрывающий запрос
┌────────────────────┐
│ IXSCAN             │
│   ↓                │
│ PROJECTION_COVERED │
│   ↓                │
│ LIMIT              │
└────────────────────┘
документы не читаются
вообще: docsExamined = 0
```

Дерево в `winningPlan` печатается от корня к листьям. Это обратный порядок относительно потока данных: сначала виден `LIMIT`, внутри него `FETCH`, внутри — `IXSCAN`. Читать удобнее с самой глубокой стадии, потому что она и есть источник документов.

```txt
Четыре числа из executionStats, которые решают всё:
  nReturned           — сколько документов вернул запрос
  totalKeysExamined   — сколько ключей индекса просмотрено
  totalDocsExamined   — сколько документов прочитано из коллекции
  executionTimeMillis — время выполнения

Здоровый запрос: nReturned ≈ totalKeysExamined ≈ totalDocsExamined.
Любой разрыв на порядок — это работа, сделанная впустую.
```

Чтение `executionStats` — это сопоставление признака с действием:

| что видно | что это значит | что делать |
|---|---|---|
| `stage: COLLSCAN` | индекс не используется | создать индекс по ESR |
| `stage: SORT` | сортировка в памяти | добавить sort-поле в индекс |
| `docsExamined >> nReturned` | индекс плохо селективен | уточнить порядок полей |
| `keysExamined >> nReturned` | скан широкого диапазона | вынести equality вперёд |
| `docsExamined = 0` | покрывающий запрос | ничего, это цель |
| `rejectedPlans` пусто | план один | проверить, что он ожидаемый |

Про стадию `SORT` стоит сказать отдельно: она означает сортировку в памяти, и у неё есть лимит в 100 мегабайт (МБ). При превышении запрос падает с ошибкой «Sort exceeded memory limit». Дальше либо нужен `allowDiskUse`, доступный и для `find` с версии 4.4, либо — что правильнее — индекс по ESR, который убирает стадию вообще.

```js
// Проверка, использовался ли ожидаемый индекс
const e = db.posts.find(filter).sort(s).explain("executionStats");
e.executionStats.executionStages.stage      // "LIMIT" / "FETCH" / "SORT"...
e.queryPlanner.winningPlan.inputStage.indexName
e.queryPlanner.rejectedPlans.length         // были ли альтернативы
```

Планировщик выбирает план не по формуле. Он измеряет. При первом запуске формы запроса он прогоняет каждого кандидата на небольшом объёме работы. Дальше он сравнивает, сколько каждому пришлось просмотреть, оставляет победителя и кладёт его в кэш планов.

Отсюда практическое следствие: план может «внезапно измениться». Кэш сбрасывается при перестройке индексов, при рестарте и при значительном изменении объёма данных. Поэтому индекс проектируют так, чтобы он был выигрышным по ESR, а не надеются на удачный выбор планировщика.

## Покрывающие запросы

Если все нужные запросу поля есть в индексе, сервер отвечает, не читая документы вообще. Речь про поля фильтра, проекции и сортировки.

```js
db.posts.createIndex({ status: 1, publishedAt: -1, title: 1 });

db.posts.find({ status: "published" }, { _id: 0, title: 1, publishedAt: 1 })
        .sort({ publishedAt: -1 });
// → totalDocsExamined: 0, стадия PROJECTION_COVERED
```

```txt
Условия покрывающего запроса:
  1. все поля фильтра, сортировки и проекции — в индексе
  2. проекция исключает _id ({ _id: 0 }), если _id не входит
     в индекс
  3. индексируемое поле не multikey (массив восстановить нельзя)
  4. поля не должны быть в поддокументах, для которых требуется
     проверка формы

Признак в explain: totalDocsExamined = 0 при nReturned > 0.
Практический смысл: покрывающий запрос — цель для горячих
«списочных» запросов (лента, автодополнение), где проекция
маленькая и предсказуемая.
```

## Когда индекс не используется

Девять случаев, и каждый из них встречается в реальном коде:

```txt
1. Нарушен ESR: range-поле стоит раньше sort-поля
   → IXSCAN есть, но появляется SORT в памяти на всей выборке.

2. $regex без якоря в начале или с флагом i
   /^mongodb-/  → префикс известен → IXSCAN по диапазону
   /^mongodb-/i → регистронезависимость ломает порядок → скан
                  индекса
   /indexes/    → подстрока в середине → скан индекса или
                  COLLSCAN

3. $ne / $nin — по смыслу «всё, кроме». Селективность близка
   к 100%, поэтому даже при использовании индекса читается почти
   весь его объём. Практически всегда переформулируется в $in
   по разрешённым значениям.

4. Вычисление над полем вместо самого поля.
   { $expr: { $gt: [ { $year: "$publishedAt" }, 2025 ] } } —
   индекс по publishedAt не применяется; нужен диапазон по самому
   полю ($gte/$lt на границы года). $where не использует индексы
   вовсе и выполняет JS на сервере (не применять).

5. Несовпадение типов BSON: "42" и 42 — разные значения индекса.
   Классика: id пришёл из строки запроса строкой, а в базе лежит
   ObjectId → запрос честно ничего не находит.

6. Collation не совпадает: индекс, созданный с одним правилом
   сравнения строк, не обслуживает запрос с другим.

7. $or — каждой ветке нужен свой индекс. Если у одной ветки
   индекса нет, весь $or деградирует до COLLSCAN (в плане это
   SUBPLAN/OR).

8. Низкая селективность: { archived: false } при 99% false.
   Планировщик обоснованно выберет COLLSCAN, потому что чтение
   документов по индексу вразброс дороже последовательного
   чтения.

9. Индекс не влезает в память: он используется, но каждое
   обращение к его страницам — это дисковое чтение, и выигрыш
   падает.
```

## Цена индексов на запись

За индекс платят на каждой записи, и счёт пропорционален числу индексов у коллекции.

```txt
Каждый insert/update/delete обновляет все затронутые индексы:
  - insert → одна запись в каждый индекс (в multikey — по одной
    на каждый элемент массива)
  - update поля, входящего в индекс → удаление старого ключа
    и вставка нового
  - update поля, не входящего ни в один индекс → индексы
    не трогаются
  - delete → удаление ключей из всех индексов

Практические следствия:
  - 10 индексов на коллекцию с интенсивной записью — это в десять
    раз больше работы на каждую вставку
  - индексы должны умещаться в кэш WiredTiger (по умолчанию около
    50% памяти минус 1 ГБ) вместе с рабочим набором данных; иначе
    индекс перестаёт быть быстрым
  - «индекс на всякий случай» — это постоянный налог на запись
    без выгоды на чтении
```

```js
// Найти неиспользуемые индексы: статистика обращений с рестарта
db.posts.aggregate([{ $indexStats: {} }])
// → { name, accesses: { ops: 0, since } } — ops: 0 на живом трафике
//   за длительный период это кандидат на удаление

// Безопасное удаление: сначала скрыть от планировщика, убедиться,
// что ничего не замедлилось, и только потом удалять
db.posts.hideIndex("status_1_views_-1")
db.posts.unhideIndex("status_1_views_-1")   // если стало хуже
db.posts.dropIndex("status_1_views_-1")
```

Про сборку индексов в продакшене. Начиная с 4.2 `createIndex` использует гибридную сборку и не держит коллекцию заблокированной всё время построения. Но нагрузку на диск и процессор создаёт заметную.

На больших продакшен-кластерах индексы традиционно собирают по одному узлу реплика-сета за раз — это называется сборкой по кругу. В приложениях на Mongoose автоматическое создание индексов надо отдельно отключить через `autoIndex: false` и управлять ими осознанно. Про это статья 08.

## Порядок работы с медленным запросом

Шесть шагов. Первый — тот, который пропускают, а его пропуск означает оптимизацию не того запроса.

```txt
1. Найти медленный запрос, а не угадать его: профайлер
   db.setProfilingLevel(1, { slowms: 100 })
   db.system.profile.find().sort({ ts: -1 })
   (в Atlas — Performance Advisor и вкладка Profiler)

2. explain("executionStats") и четыре числа: nReturned против
   keysExamined и docsExamined.

3. Разложить запрос по ESR и спроектировать индекс — включая
   sort-поле.

4. Проверить, можно ли сделать запрос покрывающим: маленькая
   проекция плюс { _id: 0 }.

5. Перепроверить explain на тех же данных: пропала ли стадия
   SORT, сошлись ли числа.

6. Убедиться, что не создан дубль: индекс { a: 1 } не нужен,
   если есть { a: 1, b: 1 } — префикс уже обслуживает запросы
   по a.
```

## Типичные ошибки на интервью

- **«Порядок полей в составном индексе не важен»** — важен принципиально, через правило префикса и ESR. На одном и том же запросе `{status, views, publishedAt}` и `{status, publishedAt, views}` ведут себя по-разному. Второй добавит стадию `SORT`.

- **«Правило ESR — это Equality, Sort, Range… а sort вообще при чём?»** — sort-поле должно быть в индексе. Иначе сортировка идёт в памяти, с лимитом 100 МБ. И `limit` перестаёт быть дешёвым, потому что сортировать приходится всю выборку.

- **«`{ tags: 1 }` — обычный индекс»** — если `tags` массив, это multikey. Значит: запись на каждый элемент, невозможность покрывающего запроса и запрет на второй массив в том же составном индексе.

- **«`unique: true` — и всё, дублей не будет»** — документы без поля индексируются как `null`. Поэтому второй такой документ упадёт с ошибкой дубликата ключа, `E11000`. Нужен `partialFilterExpression: { field: { $exists: true } }`.

- **«TTL-индекс удаляет документ точно в срок»** — фоновый процесс просыпается раз в минуту, а под нагрузкой задержка больше. Истечение сессии проверяется в запросе, а не доверяется TTL.

- **«Индекс всегда ускоряет запрос»** — при низкой селективности планировщик выберет COLLSCAN, и это правильное решение. А на записи каждый индекс — постоянные накладные расходы.

- **«explain показывает, что используется индекс — значит всё хорошо»** — надо смотреть числа: `keysExamined` и `docsExamined` против `nReturned`, и отсутствие стадии `SORT`. IXSCAN, просматривающий миллион ключей ради 20 документов, — это медленный запрос с индексом.

- **«Покрывающий запрос — это когда есть индекс»** — это когда документы не читаются вообще: `totalDocsExamined: 0`. Требуется, чтобы все поля были в индексе, `_id` был исключён из проекции, а поле не было multikey.

- **«`$regex` работает по индексу»** — только с якорем `^` и без флага `i`. Поиск подстроки — это скан; для настоящего поиска нужен text-индекс (один на коллекцию) или Atlas Search.

- **«Больше индексов — быстрее»** — быстрее до момента, когда индексы перестают влезать в кэш и когда запись начинает стоить в разы дороже. Неиспользуемые индексы находятся через `$indexStats` и удаляются — сначала `hideIndex`.
