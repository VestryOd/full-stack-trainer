# Конвейер агрегации

## Конвейер стадий, а не запрос

`find` умеет фильтровать, проецировать и сортировать. Всё остальное делает агрегация: группировки, вычисляемые поля, соединения, статистику. Конвейер (pipeline) — это массив стадий. Каждая стадия получает поток документов, что-то с ним делает и передаёт дальше. Документы на выходе стадии не обязаны совпадать по форме с документами на входе.

Дальше в статье встречаются два имени плана, потому что агрегация планируется как любой другой запрос. COLLSCAN — это полное сканирование коллекции: сервер читает каждый документ. IXSCAN — сканирование индекса: сервер идёт по отсортированным ключам.

```txt
Конвейер: каждая стадия получает поток и отдаёт поток
┌───────────────────────────────────────────┐
│ коллекция comments                        │
│ 2 000 000 документов                      │
└───────────────────────────────────────────┘
                      │  180 000
                      ▼
┌───────────────────────────────────────────┐
│ $match: { createdAt: { $gte: monthAgo } } │
│ использует индекс — стадия первая         │
└───────────────────────────────────────────┘
                      │  4 200
                      ▼
┌───────────────────────────────────────────┐
│ $group: по author._id                     │
│ сумма и количество на автора              │
└───────────────────────────────────────────┘
                      │  4 200
                      ▼
┌───────────────────────────────────────────┐
│ $sort: { total: -1 }  +  $limit: 10       │
│ top-k: сортируются только группы          │
└───────────────────────────────────────────┘
                      │  10
                      ▼
┌───────────────────────────────────────────┐
│ курсор с результатом                      │
│ 10 документов                             │
└───────────────────────────────────────────┘
числа на стрелках — сколько документов уходит в следующую стадию
```

```js
// Топ-10 авторов по числу комментариев за месяц
db.comments.aggregate([
  { $match: { createdAt: { $gte: monthAgo } } },
  { $group: { _id: "$author._id",
              name:  { $first: "$author.name" },
              total: { $sum: 1 } } },
  { $sort:  { total: -1 } },
  { $limit: 10 }
]);
```

```txt
Что важно про сам механизм:
  - aggregate возвращает курсор, как и find: результат читается
    порциями (см. статью 02 про CRUD и операторы запросов)
  - ссылка на поле внутри стадии — это строка со знаком доллара:
    "$author.name". Без доллара это литерал
  - стадии можно повторять: два $match, три $addFields —
    нормально
  - порядок стадий определяет и результат, и производительность
```

## Основные стадии

Примерно десяток стадий закрывает почти любой реальный конвейер. Вот они, по строке на каждую:

```js
// $match — фильтр. Синтаксис тот же, что у find
{ $match: { status: "published", "stats.views": { $gte: 100 } } }

// $project — оставить/переименовать/вычислить поля (форма меняется)
{ $project: { _id: 0, title: 1, author: "$author.name",
              short: { $substrCP: ["$body", 0, 200] } } }

// $addFields / $set — добавить поля, не убирая остальные
{ $addFields: { commentsPerView: { $divide: ["$stats.comments",
                                            "$stats.views"] } } }

// $group — группировка с аккумуляторами
{ $group: { _id: "$author._id", posts: { $sum: 1 } } }

// $sort / $limit / $skip
{ $sort: { publishedAt: -1 } }, { $limit: 20 }

// $unwind — развернуть массив в отдельные документы
{ $unwind: "$tags" }

// $lookup — «соединение» с другой коллекцией
{ $lookup: { from: "users", localField: "author._id",
             foreignField: "_id", as: "authorDoc" } }

// $facet — несколько независимых подконвейеров на одном входе
{ $facet: { items: [ ... ], total: [ { $count: "n" } ] } }

// $count / $sortByCount — частые сокращения
{ $count: "total" }
{ $sortByCount: "$tags" }        // = $group по значению + $sort по count

// $replaceRoot / $replaceWith — сделать вложенный объект корнем
{ $replaceWith: "$author" }

// $out / $merge — записать результат в коллекцию
{ $merge: { into: "authorStats", on: "_id", whenMatched: "replace" } }
```

## $group и аккумуляторы

`_id` в `$group` — это ключ группировки, а не идентификатор. Он может быть полем, составным объектом или `null` — тогда получается одна группа на всю выборку.

```js
db.comments.aggregate([
  { $group: {
      // составной ключ: автор + месяц
      _id: { author: "$author._id",
             month: { $dateTrunc: { date: "$createdAt", unit: "month" } } },
      count:    { $sum: 1 },
      avgScore: { $avg: "$score" },
      best:     { $max: "$score" },
      // $first/$last имеют смысл только после $sort
      firstBody: { $first: "$body" },
      // $push собирает массив — осторожно: это путь к 16 МБ
      ids:      { $push: "$_id" },
      unique:   { $addToSet: "$postId" }
  } }
]);

// Одна группа на всю коллекцию
{ $group: { _id: null, total: { $sum: 1 }, views: { $sum: "$stats.views" } } }
```

```txt
Ловушка $push: он собирает всё в массив внутри одного документа
результата, а документ ограничен 16 МБ. Группировка с $push
по большой коллекции падает с BSONObjectTooLarge. Если нужен
список — ограничивайте его: $slice после $push или $limit
до группировки. Либо не группируйте вовсе.
```

## Принцип «фильтруй раньше»

Индексы в агрегации работают только на стадиях, которые идут до первой стадии, меняющей поток документов. Практически это означает: `$match` и `$sort` должны стоять в начале конвейера.

```txt
   ПЛОХО: фильтр после разворота
┌─────────────────────────────────┐
│ $unwind: "$tags"                │
│ $lookup: from: "users"          │
│ $match: { status: "published" } │
│ $sort:  { publishedAt: -1 }     │
└─────────────────────────────────┘
индекс не используется: перед $match
 уже прошли стадии, меняющие форму;
$lookup выполнен для черновиков тоже

ХОРОШО: фильтр и сортировка первыми
┌─────────────────────────────────┐
│ $match: { status: "published" } │
│ $sort:  { publishedAt: -1 }     │
│ $limit: 20                      │
│ $lookup: from: "users"          │
│ $unwind: "$tags"                │
└─────────────────────────────────┘
    $match + $sort берут индекс
  { status: 1, publishedAt: -1 };
 $lookup работает по 20 документам
```

Оптимизатор кое-что переставляет сам, и знать его границы полезно:

```txt
Что оптимизатор умеет:
  - протащить $match вперёд через $project/$addFields/$unwind,
    если условие ссылается на поля, которые эти стадии не меняли
  - слить $sort + $limit в сортировку top-k: сортировщик держит
    в памяти только N лучших, а не всю выборку
  - слить подряд идущие $limit, $skip, $match
  - убрать поля, которые дальше не используются
    (projection pushdown)

Чего оптимизатор не умеет:
  - протащить $match через $group, если фильтр идёт
    по вычисленному полю. В { $group: ... },
    { $match: { total: { $gt: 10 } } } фильтр выполняется после
    группировки, по всем группам. Это нормально и неизбежно —
    аналог HAVING в SQL, языке запросов к реляционным базам.
    Важно лишь понимать, что индекса тут нет.
  - угадать, что $lookup стоило выполнить после $limit — порядок
    задаёте вы
```

Проверять надо так же, как для `find` — через explain. Как читать план, разобрано в статье 04 про индексы.

```js
db.posts.explain("executionStats").aggregate([ ... ]);
// в выводе: stages[0].$cursor.queryPlanner.winningPlan — что стало
// с первой стадией: IXSCAN или COLLSCAN, была ли она слита с $sort
```

## $lookup — почему это не бесплатное соединение

`$lookup` выглядит как соединение, а ведёт себя как цикл. Он выполняется по одному разу на каждый документ, дошедший до стадии.

```txt
       $lookup — вложенный цикл, а не hash join
┌────────────────────────────────────────────────────┐
│ на входе стадии: 500 постов                        │
├────────────────────────────────────────────────────┤
│ для каждого поста выполняется поиск в users:       │
│   { _id: <authorId поста> }                        │
│   → 500 отдельных обращений к коллекции users      │
│   → с индексом по _id это 500 быстрых IXSCAN       │
│   → без индекса по foreignField — 500 COLLSCAN     │
├────────────────────────────────────────────────────┤
│ на выходе: те же 500 постов + поле author: [ ... ] │
└────────────────────────────────────────────────────┘
планировщик не выбирает порядок соединения и не строит хеш-таблицу
Extended Reference в схеме убирает эту стадию целиком
```

```js
// Базовая форма: соединение по равенству, результат — массив совпадений
db.posts.aggregate([
  { $match: { status: "published" } },
  { $sort:  { publishedAt: -1 } },
  { $limit: 20 },                        // ← сначала сузить вход!
  { $lookup: { from: "users",
               localField: "author._id",
               foreignField: "_id",
               as: "authorDoc" } },
  { $unwind: "$authorDoc" }              // массив из 1 элемента → объект
]);

// Форма с подконвейером: фильтрация и проекция внутри lookup
db.posts.aggregate([
  { $lookup: {
      from: "comments",
      let: { pid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$postId", "$$pid"] } } },
        { $sort: { createdAt: -1 } },
        { $limit: 3 },
        { $project: { body: 1, "author.name": 1 } }
      ],
      as: "recentComments"
  } }
]);
```

```txt
Что нужно понимать про механику:
  - $lookup — вложенный цикл: он выполняется для каждого
    документа, пришедшего в стадию. Нет hash join, нет merge
    join, нет выбора порядка соединения планировщиком. Это
    принципиальное отличие от джойна в PostgreSQL — см. статью 06
    топика PostgreSQL, про планировщик запросов.
  - индекс по foreignField обязателен: без него каждый из N
    поисков сканирует целевую коллекцию целиком
  - результат всегда массив; чтобы получить объект, нужен
    $unwind, и тогда придётся решить, что делать с документами
    без совпадений
  - в форме с подконвейером условие соединения пишется через
    $expr и $$переменную. Это связанный подзапрос, и он тоже
    выполняется на каждый входной документ.
  - $lookup + $unwind по многозначной связи умножает количество
    документов в конвейере

Отсюда правило: сузить вход до $lookup через $match, $sort
и $limit. И не ставить $lookup в горячий путь чтения.
```

Главный вывод этого раздела относится не к агрегации, а к схеме. Если основной запрос требует `$lookup`, скорее всего схема спроектирована реляционно.

Extended Reference — `author: { _id, name, avatar }` прямо в посте — убирает стадию целиком, а не оптимизирует её. Про это статья 03 про проектирование схемы. `$lookup` остаётся законным инструментом для отчётов, админок и редких запросов. Это как раз те случаи, где второй запрос дороже соединения на сервере.

## $unwind и взрыв кардинальности

`$unwind` превращает один документ с массивом из N элементов в N документов. Это мощно и опасно ровно по одной причине: количество документов в конвейере умножается.

```js
// Сколько постов в каждом теге
db.posts.aggregate([
  { $match: { status: "published" } },   // 50 000 постов
  { $unwind: "$tags" },                  // → 250 000 документов (5 тегов)
  { $group: { _id: "$tags", posts: { $sum: 1 } } },
  { $sort: { posts: -1 } }
]);
```

```txt
Два обязательных параметра, о которых забывают:

  { $unwind: { path: "$tags",
               preserveNullAndEmptyArrays: true } }

  По умолчанию документ, у которого массива нет или он пуст,
  выпадает из конвейера. Это самый частый баг с $unwind:
  «в отчёте пропали посты без тегов» — и его не видно, пока
  кто-то не сверит итоги.

  { $unwind: { path: "$tags", includeArrayIndex: "tagIndex" } }
  — сохранить позицию элемента, если она нужна.
```

```txt
Признак того, что $unwind не нужен: сразу после него идёт
$group, который собирает документ обратно ($first по всем полям
плюс $push по развёрнутому). Часто вместо этого достаточно:
  - $filter / $map / $reduce — выражения над массивом без
    разворота
  - $size — длина массива
  - $reduce для суммы по массиву
  - $match с $elemMatch — если нужен только фильтр
Пример: { $addFields: { hot: { $size: { $filter: {
  input: "$ratings", cond: { $gte: ["$$this.score", 4] } } } } } }
```

## Лимиты памяти и allowDiskUse

Часть стадий не умеет работать потоком. Они обязаны собрать данные, прежде чем отдать первый документ. Именно эти стадии и упираются в лимит памяти — 100 МБ (мегабайт) на стадию.

```txt
Блокирующие стадии — те, что обязаны собрать данные, прежде чем
отдать первый документ: $group, $sort (без индекса), $bucket,
$setWindowFields, $facet.

Лимит на такую стадию — 100 МБ оперативной памяти.
При превышении: "Exceeded memory limit for $group ... pass
allowDiskUse:true".

  db.comments.aggregate(pipeline, { allowDiskUse: true })

allowDiskUse разрешает выгрузку на диск. Запрос перестаёт
падать, но становится ощутимо медленнее, поэтому это аварийная
мера, а не штатный режим. Правильные ходы: сузить $match, дать
$sort индекс, уменьшить кардинальность группировки, считать
инкрементально через $merge.

Отдельный лимит: каждый документ результата, как любой документ
BSON, ограничен 16 МБ. Вот почему $group с $push по большой
коллекции падает даже с allowDiskUse.
```

## $facet — несколько подсчётов за один проход

Типичная задача списка с фильтрами: нужны сама страница, общее число найденных и счётчики по фасетам. Это три запроса — или один `$facet`.

```js
db.posts.aggregate([
  { $match: { status: "published", tags: "mongodb" } },   // ← индекс тут
  { $facet: {
      items: [
        { $sort: { publishedAt: -1 } },
        { $limit: 20 },
        { $project: { title: 1, slug: 1, author: 1 } }
      ],
      total: [ { $count: "count" } ],
      byTag: [
        { $unwind: "$tags" },
        { $sortByCount: "$tags" },
        { $limit: 10 }
      ]
  } }
]);
// результат — один документ: { items: [...], total: [{count}], byTag: [...] }
```

```txt
Что важно про $facet:
  - индекс используется только стадиями до $facet; внутри ветвей
    работа идёт с уже полученным потоком документов
  - каждая ветвь обрабатывает весь входной поток независимо.
    Экономия в том, что коллекция читается один раз, а не три.
  - результат — один документ, значит на него действует лимит
    16 МБ
  - $facet блокирующий: первый документ отдаётся, когда посчитаны
    все ветви
```

## Агрегация в базе или обработка в Node

Границу определяет соотношение объёма входных данных и объёма результата.

```txt
Считать в базе, когда:
  - объём данных на входе много больше результата (2M
    комментариев → 10 строк отчёта): по сети уходит результат,
    а не данные
  - работа сводится к $match/$sort по индексам и группировке
  - нужна сортировка с limit по всей коллекции (top-k)
  - результат материализуется в коллекцию через $merge/$out
  - выборка не влезает в память процесса Node

Считать в Node, когда:
  - объём уже маленький: получили 20 документов, и городить
    конвейер ради формата ответа не надо
  - логика содержит вызовы внешних сервисов, обращения к кэшу,
    правила, которые меняются вместе с продуктом
  - логику нужно покрыть юнит-тестами и читать через год
  - выражения агрегации начинают выглядеть как программа:
    $cond/$switch/$reduce на десять уровней вложенности
```

Практический ориентир: агрегация хорошо считает **данные**, приложение хорошо выражает **бизнес-правила**. Конвейер на 12 стадий с ветвлениями — это программа, написанная на неудобном языке без отладчика. Его стоит разделить: тяжёлую фильтрацию и группировку оставить в базе, форматирование и правила — в коде.

И обратная ошибка, которая встречается чаще: вытащить 200 000 документов в Node и посчитать сумму циклом. Это трафик, память процесса и нагрузка на сборщик мусора вместо одной стадии `$group`.

## Материализованные представления через $merge

Когда отчёт тяжёлый, а свежесть в пределах часа устраивает, агрегацию считают по расписанию и складывают в отдельную коллекцию.

```js
// раз в час: пересчитать статистику авторов
db.comments.aggregate([
  { $match: { createdAt: { $gte: hourAgo } } },
  { $group: { _id: "$author._id", newComments: { $sum: 1 } } },
  { $merge: {
      into: "authorStats",
      on: "_id",
      whenMatched: [ { $set: { comments: { $add: ["$comments",
                                                 "$$new.newComments"] } } } ],
      whenNotMatched: "insert"
  } }
]);
// дальше API читает authorStats обычным find — быстро и предсказуемо
```

```txt
$merge против $out:
  $out    — полностью заменяет целевую коллекцию результатом
  $merge  — вставляет, обновляет или сливает по ключу; умеет
            инкрементальный пересчёт и работает с существующими
            данными и индексами целевой коллекции
```

## Связь с другими темами

- **02 — CRUD и операторы запросов.** CRUD — это create, read, update, delete: создание, чтение, обновление и удаление. `$match` использует тот же язык фильтров; курсоры и порции результата.
- **03 — Проектирование схемы: вложение или ссылка.** Почему правильная схема убирает `$lookup`; поля Computed вместо агрегации на каждом чтении.
- **04 — Индексы и производительность запросов.** Индекс работает только на первых стадиях; explain для конвейера; индекс по `foreignField` для `$lookup`.
- **06 — Репликация, транзакции и консистентность.** Тяжёлые агрегации на secondary и чем это опасно.
- **08 — Запросы Mongoose, populate и ловушки.** `populate` против `$lookup`: N+1 запросов против одной стадии.
- **Топик PostgreSQL, статья 06 «Планировщик запросов и EXPLAIN ANALYZE».** Как выглядит настоящий планировщик соединений, с которым сравнивают `$lookup`.

## Типичные ошибки на интервью

- **«$lookup — это джойн, только в MongoDB»** — это вложенный цикл, выполняемый для каждого входного документа, без hash join и без выбора порядка соединения. Он требует индекс по `foreignField` и не годится для горячего пути чтения.

- **«Порядок стадий не важен, оптимизатор разберётся»** — оптимизатор переставит `$match` через `$project`/`$addFields`. Но он не протащит его через `$group` и не догадается, что `$lookup` стоило сделать после `$limit`. Индекс работает только на стадиях до первой, меняющей поток.

- **«$unwind просто разворачивает массив»** — он ещё и умножает количество документов в конвейере. И по умолчанию **выбрасывает** документы без массива. Нужен `preserveNullAndEmptyArrays: true`, если пустые важны.

- **«Агрегация не использует индексы»** — использует, но только на первых стадиях: `$match` и `$sort` до любой стадии, меняющей форму документов. Именно поэтому «фильтруй раньше» — не стиль, а требование.

- **«allowDiskUse решает проблему с памятью»** — он снимает падение, но не медленную работу. Настоящее решение — индекс под `$sort`, более узкий `$match` или инкрементальный пересчёт через `$merge`.

- **«Соберу всё через $group + $push»** — документ результата ограничен 16 МБ. `$push` по большой коллекции упрётся в этот лимит независимо от `allowDiskUse`.

- **«$facet выполняет ветви параллельно, поэтому это быстро»** — выгода не в параллельности, а в том, что входной поток читается один раз. Внутри ветвей индексов уже нет, и стадия блокирующая.

- **«Раз есть агрегация, счётчики можно считать на лету»** — на горячем чтении это лишняя работа на каждый запрос. Обычный пример — лента. Счётчик держат готовым (`$inc` при записи, паттерн Computed), а агрегацию оставляют для пересчёта и отчётов.

- **«Всю логику лучше держать в конвейере — так меньше кода в приложении»** — конвейер на 12 стадий с `$cond`/`$switch` не покрывается юнит-тестами. Прочитать его через год тоже не выйдет. В базе — фильтрация и группировка объёмов, в приложении — бизнес-правила.
