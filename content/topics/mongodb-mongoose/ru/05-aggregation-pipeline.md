# Aggregation Pipeline

## Конвейер стадий, а не запрос

`find` умеет фильтровать, проецировать и сортировать. Всё остальное — группировки, вычисляемые поля, соединения, статистика — делает агрегация. Пайплайн это массив стадий: каждая получает поток документов, что-то с ним делает и передаёт дальше. Документы на выходе стадии не обязаны совпадать по форме с документами на входе.

```txt
Пайплайн: каждая стадия получает поток и отдаёт поток
┌───────────────────────────────────────────┐
│ коллекция comments                        │
│ 2 000 000 документов                      │
└───────────────────────────────────────────┘
                      │  180 000
                      ▼
┌───────────────────────────────────────────┐
│ $match: { createdAt: { $gte: monthAgo } } │
│ использует индекс — стадия первая         │
└───────────────────────────────────────────┘
                      │  4 200
                      ▼
┌───────────────────────────────────────────┐
│ $group: по author._id                     │
│ сумма и количество на автора              │
└───────────────────────────────────────────┘
                      │  4 200
                      ▼
┌───────────────────────────────────────────┐
│ $sort: { total: -1 }  +  $limit: 10       │
│ top-k: сортируются только группы          │
└───────────────────────────────────────────┘
                      │  10
                      ▼
┌───────────────────────────────────────────┐
│ курсор с результатом                      │
│ 10 документов                             │
└───────────────────────────────────────────┘
числа на стрелках — сколько документов уходит в следующую стадию
```

```js
// Топ-10 авторов по числу комментариев за месяц
db.comments.aggregate([
  { $match: { createdAt: { $gte: monthAgo } } },
  { $group: { _id: "$author._id",
              name:  { $first: "$author.name" },
              total: { $sum: 1 } } },
  { $sort:  { total: -1 } },
  { $limit: 10 }
]);
```

```txt
Что важно про сам механизм:
  - aggregate возвращает КУРСОР, как и find: результат читается
    батчами (см. [CRUD and Query Operators])
  - ссылка на поле внутри стадии — это строка со знаком доллара:
    "$author.name". Без доллара это литерал
  - стадии можно повторять: два $match, три $addFields — нормально
  - порядок стадий определяет и результат, и производительность
```

## Основные стадии

```js
// $match — фильтр. Синтаксис тот же, что у find
{ $match: { status: "published", "stats.views": { $gte: 100 } } }

// $project — оставить/переименовать/вычислить поля (форма меняется)
{ $project: { _id: 0, title: 1, author: "$author.name",
              short: { $substrCP: ["$body", 0, 200] } } }

// $addFields / $set — добавить поля, НЕ убирая остальные
{ $addFields: { commentsPerView: { $divide: ["$stats.comments",
                                            "$stats.views"] } } }

// $group — группировка с аккумуляторами
{ $group: { _id: "$author._id", posts: { $sum: 1 } } }

// $sort / $limit / $skip
{ $sort: { publishedAt: -1 } }, { $limit: 20 }

// $unwind — развернуть массив в отдельные документы
{ $unwind: "$tags" }

// $lookup — «соединение» с другой коллекцией
{ $lookup: { from: "users", localField: "author._id",
             foreignField: "_id", as: "authorDoc" } }

// $facet — несколько независимых подпайплайнов на одном входе
{ $facet: { items: [ ... ], total: [ { $count: "n" } ] } }

// $count / $sortByCount — частые сокращения
{ $count: "total" }
{ $sortByCount: "$tags" }        // = $group по значению + $sort по count

// $replaceRoot / $replaceWith — сделать вложенный объект корнем
{ $replaceWith: "$author" }

// $out / $merge — записать результат в коллекцию
{ $merge: { into: "authorStats", on: "_id", whenMatched: "replace" } }
```

## $group и аккумуляторы

`_id` в `$group` — это ключ группировки, а не идентификатор. Он может быть полем, составным объектом или `null` (одна группа на всю выборку).

```js
db.comments.aggregate([
  { $group: {
      // составной ключ: автор + месяц
      _id: { author: "$author._id",
             month: { $dateTrunc: { date: "$createdAt", unit: "month" } } },
      count:    { $sum: 1 },
      avgScore: { $avg: "$score" },
      best:     { $max: "$score" },
      // $first/$last имеют смысл только после $sort
      firstBody: { $first: "$body" },
      // $push собирает массив — осторожно: это путь к 16 МБ
      ids:      { $push: "$_id" },
      unique:   { $addToSet: "$postId" }
  } }
]);

// Одна группа на всю коллекцию
{ $group: { _id: null, total: { $sum: 1 }, views: { $sum: "$stats.views" } } }
```

```txt
Ловушка $push: он собирает ВСЁ в массив внутри одного документа
результата, а документ ограничен 16 МБ. Группировка с $push по
большой коллекции падает с BSONObjectTooLarge. Если нужен список —
ограничивайте его ($slice после $push, $limit до группировки) или
не группируйте вовсе.
```

## Принцип «фильтруй раньше»

Индексы в агрегации работают только на стадиях, которые идут ДО первой стадии, меняющей поток документов. Практически это означает: `$match` и `$sort` должны стоять в начале пайплайна.

```txt
   ПЛОХО: фильтр после разворота        ХОРОШО: фильтр и сортировка первыми
┌─────────────────────────────────┐     ┌─────────────────────────────────┐
│ $unwind: "$tags"                │     │ $match: { status: "published" } │
│ $lookup: from: "users"          │     │ $sort:  { publishedAt: -1 }     │
│ $match: { status: "published" } │     │ $limit: 20                      │
│ $sort:  { publishedAt: -1 }     │     │ $lookup: from: "users"          │
└─────────────────────────────────┘     │ $unwind: "$tags"                │
индекс не используется: перед $match    └─────────────────────────────────┘
 уже прошли стадии, меняющие форму;         $match + $sort берут индекс
$lookup выполнен для черновиков тоже      { status: 1, publishedAt: -1 };
                                         $lookup работает по 20 документам
```

Оптимизатор кое-что переставляет сам, и знать его границы полезно:

```txt
Что оптимизатор умеет:
  - протащить $match вперёд через $project/$addFields/$unwind, если
    условие ссылается на поля, которые эти стадии не меняли
  - слить $sort + $limit в top-k sort: сортировщик держит в памяти
    только N лучших, а не всю выборку
  - слить подряд идущие $limit, $skip, $match
  - убрать поля, которые дальше не используются (projection pushdown)

Чего оптимизатор НЕ умеет:
  - протащить $match через $group, если фильтр по вычисленному полю:
    { $group: ... }, { $match: { total: { $gt: 10 } } } — фильтр
    выполняется ПОСЛЕ группировки, по всем группам. Это нормально
    и неизбежно (аналог HAVING в SQL); важно лишь понимать, что
    индекса тут нет
  - угадать, что $lookup стоило выполнить после $limit — порядок
    задаёте вы
```

Проверять надо так же, как для `find` — через explain (см. [Indexes and Query Performance]):

```js
db.posts.explain("executionStats").aggregate([ ... ]);
// в выводе: stages[0].$cursor.queryPlanner.winningPlan — что стало
// с первой стадией: IXSCAN или COLLSCAN, была ли она слита с $sort
```

## $lookup — почему это не бесплатный JOIN

```txt
       $lookup — вложенный цикл, а не hash join
┌────────────────────────────────────────────────────┐
│ на входе стадии: 500 постов                        │
├────────────────────────────────────────────────────┤
│ для КАЖДОГО поста выполняется поиск в users:       │
│   { _id: <authorId поста> }                        │
│   → 500 отдельных обращений к коллекции users      │
│   → с индексом по _id это 500 быстрых IXSCAN       │
│   → без индекса по foreignField — 500 COLLSCAN     │
├────────────────────────────────────────────────────┤
│ на выходе: те же 500 постов + поле author: [ ... ] │
└────────────────────────────────────────────────────┘
планировщик не выбирает порядок соединения и не строит хеш-таблицу
Extended Reference в схеме убирает эту стадию целиком
```

```js
// Базовая форма: equality join, результат — МАССИВ совпадений
db.posts.aggregate([
  { $match: { status: "published" } },
  { $sort:  { publishedAt: -1 } },
  { $limit: 20 },                        // ← сначала сузить вход!
  { $lookup: { from: "users",
               localField: "author._id",
               foreignField: "_id",
               as: "authorDoc" } },
  { $unwind: "$authorDoc" }              // массив из 1 элемента → объект
]);

// Форма с подпайплайном: фильтрация и проекция внутри lookup
db.posts.aggregate([
  { $lookup: {
      from: "comments",
      let: { pid: "$_id" },
      pipeline: [
        { $match: { $expr: { $eq: ["$postId", "$$pid"] } } },
        { $sort: { createdAt: -1 } },
        { $limit: 3 },
        { $project: { body: 1, "author.name": 1 } }
      ],
      as: "recentComments"
  } }
]);
```

```txt
Что нужно понимать про механику:
  - $lookup — вложенный цикл: он выполняется для КАЖДОГО документа,
    пришедшего в стадию. Нет hash join, нет merge join, нет выбора
    порядка соединения планировщиком — это принципиальное отличие
    от JOIN в PostgreSQL (см. топик PostgreSQL, [Query Planner
    and EXPLAIN])
  - индекс по foreignField обязателен: без него каждый из N поисков
    сканирует целевую коллекцию целиком
  - результат ВСЕГДА массив; чтобы получить объект, нужен $unwind
    (и тогда решайте, что делать с документами без совпадений)
  - в форме с pipeline условие соединения пишется через $expr и
    $$переменную — это correlated subquery, и она тоже выполняется
    на каждый входной документ
  - $lookup + $unwind по многозначной связи умножает количество
    документов в пайплайне

Отсюда правило: сузить вход ДО $lookup ($match, $sort, $limit) и
не ставить $lookup в горячий путь чтения.
```

Главный вывод этого раздела относится не к агрегации, а к схеме: если основной запрос требует `$lookup`, скорее всего схема спроектирована реляционно. Extended Reference (`author: { _id, name, avatar }` прямо в посте) убирает стадию целиком, а не оптимизирует её — см. [Schema Design: Embedding vs Referencing]. `$lookup` остаётся законным инструментом для отчётов, админок и редких запросов, где второй запрос дороже, чем соединение на сервере.

## $unwind и взрыв кардинальности

`$unwind` превращает один документ с массивом из N элементов в N документов. Это мощно и опасно ровно по одной причине: количество документов в пайплайне умножается.

```js
// Сколько постов в каждом теге
db.posts.aggregate([
  { $match: { status: "published" } },   // 50 000 постов
  { $unwind: "$tags" },                  // → 250 000 документов (5 тегов)
  { $group: { _id: "$tags", posts: { $sum: 1 } } },
  { $sort: { posts: -1 } }
]);
```

```txt
Два обязательных параметра, о которых забывают:

  { $unwind: { path: "$tags",
               preserveNullAndEmptyArrays: true } }

  По умолчанию документ, у которого массива НЕТ или он пуст,
  ВЫПАДАЕТ из пайплайна. Это самый частый баг с $unwind: «в отчёте
  пропали посты без тегов» — и его не видно, пока кто-то не сверит
  итоги.

  { $unwind: { path: "$tags", includeArrayIndex: "tagIndex" } }
  — сохранить позицию элемента, если она нужна.
```

```txt
Признак того, что $unwind не нужен: сразу после него идёт $group,
который собирает документ обратно ($first по всем полям + $push по
развёрнутому). Часто вместо этого достаточно:
  - $filter / $map / $reduce — выражения над массивом БЕЗ разворота
  - $size — длина массива
  - $reduce для суммы по массиву
  - $match с $elemMatch — если нужен только фильтр
Пример: { $addFields: { hot: { $size: { $filter: {
  input: "$ratings", cond: { $gte: ["$$this.score", 4] } } } } } }
```

## Лимиты памяти и allowDiskUse

```txt
Блокирующие стадии — те, что обязаны собрать данные, прежде чем
отдать первый документ: $group, $sort (без индекса), $bucket,
$setWindowFields, $facet.

Лимит на такую стадию — 100 МБ оперативной памяти.
При превышении: "Exceeded memory limit for $group ... pass
allowDiskUse:true".

  db.comments.aggregate(pipeline, { allowDiskUse: true })

allowDiskUse разрешает выгрузку на диск: запрос не падает, но
становится ощутимо медленнее. Это спасательный круг, а не режим
работы. Правильные ходы: сузить $match, дать $sort индекс,
уменьшить кардинальность группировки, считать инкрементально
через $merge.

Отдельный лимит: каждый документ РЕЗУЛЬТАТА, как любой документ
BSON, ограничен 16 МБ — вот почему $group с $push по большой
коллекции падает даже с allowDiskUse.
```

## $facet — несколько подсчётов за один проход

Типичная задача списка с фильтрами: нужны сама страница, общее число найденных и счётчики по фасетам. Это три запроса — или один `$facet`.

```js
db.posts.aggregate([
  { $match: { status: "published", tags: "mongodb" } },   // ← индекс тут
  { $facet: {
      items: [
        { $sort: { publishedAt: -1 } },
        { $limit: 20 },
        { $project: { title: 1, slug: 1, author: 1 } }
      ],
      total: [ { $count: "count" } ],
      byTag: [
        { $unwind: "$tags" },
        { $sortByCount: "$tags" },
        { $limit: 10 }
      ]
  } }
]);
// результат — ОДИН документ: { items: [...], total: [{count}], byTag: [...] }
```

```txt
Что важно про $facet:
  - индекс используется только стадиями ДО $facet; внутри ветвей
    работа идёт с уже полученным потоком документов
  - каждая ветвь обрабатывает ВЕСЬ входной поток независимо —
    экономия в том, что коллекция читается один раз, а не три
  - результат — один документ, значит на него действует лимит 16 МБ
  - $facet блокирующий: первый документ отдаётся, когда посчитаны
    все ветви
```

## Агрегация в БД или обработка в Node

```txt
Считать в базе, когда:
  - объём данных на входе много больше результата (2M комментариев
    → 10 строк отчёта): по сети уходит результат, а не данные
  - работа сводится к $match/$sort по индексам и группировке
  - нужна сортировка с limit по всей коллекции (top-k)
  - результат материализуется в коллекцию через $merge/$out
  - выборка не влезает в память процесса Node

Считать в Node, когда:
  - объём уже маленький (получили 20 документов — не надо
    городить пайплайн ради формата ответа)
  - логика содержит вызовы внешних сервисов, обращения к кэшу,
    правила, которые меняются с продуктом
  - логику нужно покрыть юнит-тестами и читать через год
  - выражения агрегации начинают выглядеть как программа:
    $cond/$switch/$reduce на десять уровней вложенности
```

Практический ориентир: агрегация хорошо считает **данные**, приложение хорошо выражает **бизнес-правила**. Пайплайн на 12 стадий с ветвлениями — это программа, написанная на неудобном языке без отладчика; её стоит разделить: тяжёлую фильтрацию и группировку оставить в БД, форматирование и правила — в коде.

И обратная ошибка, которая встречается чаще: вытащить 200 000 документов в Node и посчитать сумму циклом. Это трафик, память процесса и GC вместо одной стадии `$group`.

## Материализованные представления через $merge

Когда отчёт тяжёлый, а свежесть в пределах часа устраивает, агрегацию считают по расписанию и складывают в отдельную коллекцию.

```js
// раз в час: пересчитать статистику авторов
db.comments.aggregate([
  { $match: { createdAt: { $gte: hourAgo } } },
  { $group: { _id: "$author._id", newComments: { $sum: 1 } } },
  { $merge: {
      into: "authorStats",
      on: "_id",
      whenMatched: [ { $set: { comments: { $add: ["$comments",
                                                 "$$new.newComments"] } } } ],
      whenNotMatched: "insert"
  } }
]);
// дальше API читает authorStats обычным find — быстро и предсказуемо
```

```txt
$merge против $out:
  $out    — ПОЛНОСТЬЮ заменяет целевую коллекцию результатом
  $merge  — вставляет/обновляет/сливает по ключу; умеет
            инкрементальный пересчёт, работает с существующими
            данными и индексами целевой коллекции
```

## Типичные ошибки на интервью

- **«$lookup — это JOIN, только в MongoDB»** — это вложенный цикл, выполняемый для каждого входного документа, без hash join и без выбора порядка соединения. Он требует индекс по `foreignField` и не годится для горячего пути чтения.

- **«Порядок стадий не важен, оптимизатор разберётся»** — оптимизатор переставит `$match` через `$project`/`$addFields`, но не протащит его через `$group` и не догадается, что `$lookup` стоило сделать после `$limit`. Индекс работает только на стадиях до первой, меняющей поток.

- **«$unwind просто разворачивает массив»** — он ещё и умножает количество документов в пайплайне, и по умолчанию ВЫБРАСЫВАЕТ документы без массива. Нужен `preserveNullAndEmptyArrays: true`, если пустые важны.

- **«Агрегация не использует индексы»** — использует, но только на первых стадиях (`$match`, `$sort` до любой стадии, меняющей форму документов). Именно поэтому «фильтруй раньше» — не стиль, а требование.

- **«allowDiskUse решает проблему с памятью»** — снимает падение, но не медленную работу. Настоящее решение — индекс под `$sort`, более узкий `$match` или инкрементальный пересчёт через `$merge`.

- **«Соберу всё через $group + $push»** — документ результата ограничен 16 МБ, и `$push` по большой коллекции упрётся в него независимо от `allowDiskUse`.

- **«$facet выполняет ветви параллельно, поэтому это быстро»** — выгода не в параллельности, а в том, что входной поток читается один раз. Внутри ветвей индексов уже нет, и стадия блокирующая.

- **«Раз есть агрегация, счётчики можно считать на лету»** — на горячем чтении (лента) это лишняя работа на каждый запрос. Счётчик держат готовым (`$inc` при записи, паттерн Computed), а агрегацию оставляют для пересчёта и отчётов.

- **«Всю логику лучше держать в пайплайне — так меньше кода в приложении»** — пайплайн на 12 стадий с `$cond`/`$switch` не тестируется юнит-тестами и не читается через год. В БД — фильтрация и группировка объёмов, в приложении — бизнес-правила.
