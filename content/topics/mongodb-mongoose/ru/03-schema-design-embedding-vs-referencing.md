# Schema Design: Embedding vs Referencing

## Схема проектируется от запросов, а не от сущностей

В реляционном проектировании порядок такой: выделить сущности, нормализовать до 3NF, а потом оптимизировать то, что оказалось медленным. В MongoDB этот порядок перевёрнут: сначала пишется список запросов, которые приложение будет выполнять чаще всего, и только потом решается, как разложить данные. Нормальных форм в документной модели нет — есть соответствие схемы паттерну доступа.

```txt
Что нужно выписать ДО первой коллекции (на примере блога):

  1. страница поста          — пост + автор (имя, аватар) + первые
                               3 комментария                    ~1000/мин
  2. лента постов            — 20 постов: заголовок, автор, число
                               комментариев, теги                ~500/мин
  3. все комментарии поста   — постранично, по 50               ~50/мин
  4. профиль автора          — автор + его последние 10 постов    ~20/мин
  5. модерация комментария   — один комментарий по _id            ~5/мин

Из этого списка видно главное: запросы 1 и 2 — 95% нагрузки, и оба
хотят имя автора и число комментариев вместе с постом. Всё остальное
проектирование — следствие этого факта.
```

Правило, к которому сводится вся тема, формулируется одной фразой: **что читается вместе — хранится вместе**. Дальше идут ограничения, которые не позволяют довести это правило до абсурда.

## Два способа связать данные

```txt
EMBEDDING: комментарии внутри поста              REFERENCING: две коллекции
┌──────────────────────────────────┐      ┌──────────────────────────────┐
│ коллекция posts                  │      │ коллекция posts              │
│                                  │      │                              │
│ { _id: 1,                        │      │ { _id: 1, title: "Индексы" } │
│   title: "Индексы",              │      └──────────────────────────────┘
│   comments: [                    │
│     { _id: 11, body: "..." },    │      ┌─────────────────────────────────────┐
│     { _id: 12, body: "..." } ] } │      │ коллекция comments                  │
└──────────────────────────────────┘      │                                     │
  одно чтение отдаёт всю страницу;        │ { _id: 11, postId: 1, body: "..." } │
одна запись меняет пост и комментарий     │ { _id: 12, postId: 1, body: "..." } │
атомарно; но массив растёт без границы    └─────────────────────────────────────┘
                                               рост не ограничен документом,
                                              комментарии живут своей жизнью;
                                              но два запроса и нет атомарности
```

Embedding — вложить дочерние данные в родительский документ. Referencing — хранить `_id` (или наоборот, `parentId` в дочернем) и делать второй запрос.

```txt
Что даёт embedding:
  + одно чтение отдаёт всё; никаких джойнов и второй сетевой задержки
  + одна запись меняет родителя и вложенное АТОМАРНО
    (см. [CRUD and Query Operators])
  + данные лежат физически рядом — одно обращение к диску/кэшу
  - документ растёт; лимит 16 МБ и переписывание документа на запись
  - к вложенным нельзя обратиться независимо: нет своей коллекции,
    нет отдельной пагинации по ним, сложнее «дай все комментарии
    пользователя по всем постам»
  - обновление одного вложенного элемента переписывает документ целиком

Что даёт referencing:
  + рост не ограничен размером родителя
  + дочерние сущности живут своей жизнью: собственные индексы,
    сортировка, пагинация, удаление
  + один и тот же дочерний документ может быть связан со многими
  - минимум два запроса (или $lookup — см. [Aggregation Pipeline])
  - нет атомарности между коллекциями без транзакции
  - целостность на совести приложения: «висячие» ссылки MongoDB
    не запрещает — FK и ON DELETE CASCADE тут нет
```

## Четыре критерия выбора

### 1. Кардинальность

```txt
                       Кардинальность — первый фильтр решения
┌───────────────────┬─────────────────────────────┬────────────────────────────────┐
│ связь             │ пример в блоге              │ решение                        │
├───────────────────┼─────────────────────────────┼────────────────────────────────┤
│ one-to-few        │ у поста 3-10 тегов          │ вкладывать массивом            │
├───────────────────┼─────────────────────────────┼────────────────────────────────┤
│ one-to-few        │ у пользователя 2 адреса     │ вкладывать массивом            │
├───────────────────┼─────────────────────────────┼────────────────────────────────┤
│ one-to-many       │ у поста 50-500 комментариев │ ссылка + Subset в посте        │
├───────────────────┼─────────────────────────────┼────────────────────────────────┤
│ one-to-squillions │ у поста миллионы просмотров │ ссылка из дочернего, Bucket    │
├───────────────────┼─────────────────────────────┼────────────────────────────────┤
│ many-to-many      │ посты и теги как сущности   │ массив id на «главной» стороне │
└───────────────────┴─────────────────────────────┴────────────────────────────────┘
                  граница few/many — не число, а ответ на вопрос:
                 может ли пользователь наращивать это без предела?
```

Формулировка «one-to-few / one-to-many / one-to-squillions» полезна тем, что переводит вопрос из «сколько сейчас» в «сколько может стать». Три-десять тегов у поста — это few и навсегда few. Комментарии — many: у 99% постов их будет 20, но у одного вирусного будет 50 000, и схема должна выдержать именно этот случай.

### 2. Паттерн доступа: читается вместе или по отдельности

```txt
Вопросы, которые дают ответ:
  - Нужны ли дочерние данные ВСЕГДА, когда читается родитель?
    Всегда → embedding. Иногда → referencing (не платить за то,
    что не читаешь).
  - Нужен ли доступ к дочерним БЕЗ родителя? «Все комментарии
    пользователя», «модерация свежих комментариев по всей системе»
    → отдельная коллекция.
  - Нужна ли пагинация/сортировка по дочерним? Внутри массива это
    делается только в агрегации ($slice, $unwind + $sort) — дорого
    и неудобно → отдельная коллекция.
```

### 3. Частота изменений и стоимость дублей

Вкладывая или дублируя, вы делаете копию. Копия — это обязательство её обновлять. Поэтому дублируют то, что меняется редко, и не дублируют то, что меняется часто.

```txt
Имя и аватар автора       → меняются раз в год    → дублировать можно
Число комментариев поста  → меняется каждый час   → хранить как счётчик
                                                    у поста (Computed),
                                                    но не дублировать
                                                    в 500 местах
Email, права, статус бана → меняются и критичны   → только ссылка
```

### 4. Границы роста

```txt
Ключевой вопрос: может ли пользователь (или внешняя система)
наращивать эту коллекцию элементов без предела?

  теги поста       — задаёт автор, редактор ограничивает 10 → граница есть
  лайки            — ставит любой из миллиона юзеров        → границы НЕТ
  комментарии      — пишет любой                            → границы НЕТ
  адреса доставки  — пользователь, реалистично 1-5          → граница есть

Массив без верхней границы во вложении — это отложенная авария,
а не «пока работает».
```

## Сквозной пример: схема блога

```js
// users — сущность со своей жизнью, ссылаются многие
{
  _id: ObjectId("64a1"),
  email: "max@test.com",          // меняется, критично → НЕ дублируем
  name: "Максим",                 // меняется редко → дублируем
  avatar: "/a/12.png",            // меняется редко → дублируем
  passwordHash: "...",
  createdAt: ISODate("...")
}

// posts — центральный агрегат: то, что нужно для страницы и ленты
{
  _id: ObjectId("66b0"),
  slug: "mongodb-indexes",
  title: "Индексы в MongoDB",
  body: "...",

  // Extended Reference: id + минимум полей для отображения
  author: { _id: ObjectId("64a1"), name: "Максим", avatar: "/a/12.png" },

  // one-to-few, границы есть, всегда читаются вместе → embedding
  tags: ["mongodb", "performance"],

  // Computed: считается при записи, читается на каждой странице
  stats: { comments: 128, views: 9421, likes: 42 },

  // Subset: только то, что показывает страница поста «выше сгиба»
  recentComments: [
    { _id: ObjectId("77c1"), body: "спасибо!",
      author: { _id: ObjectId("64b2"), name: "Аня" },
      createdAt: ISODate("...") }
  ],

  publishedAt: ISODate("...")
}

// comments — one-to-many без границы → своя коллекция, ссылка на пост
{
  _id: ObjectId("77c1"),
  postId: ObjectId("66b0"),       // ссылка ИЗ дочернего в родителя
  author: { _id: ObjectId("64b2"), name: "Аня" },
  body: "спасибо!",
  score: 3,
  createdAt: ISODate("...")
}
```

Что даёт такая схема на основных запросах:

```js
// 1. Страница поста — ОДИН запрос вместо джойна по трём таблицам:
//    пост, автор для отображения и первые комментарии уже внутри
const post = await db.collection("posts").findOne({ slug });

// 2. Лента — ОДИН запрос, всё нужное в проекции
const feed = await db.collection("posts")
  .find({ status: "published" })
  .project({ title: 1, slug: 1, author: 1, tags: 1, "stats.comments": 1 })
  .sort({ publishedAt: -1 })
  .limit(20)
  .toArray();

// 3. Все комментарии поста — отдельный запрос с настоящей пагинацией
const comments = await db.collection("comments")
  .find({ postId: post._id })
  .sort({ createdAt: -1 })
  .limit(50)
  .toArray();
```

Ключевое наблюдение: 95% нагрузки (запросы 1 и 2) обслуживается одним обращением к одной коллекции. Остальные 5% платят вторым запросом — и это правильный компромисс, а не недоработка.

## Практические паттерны проектирования

```txt
┌────────────────────┬────────────────────────────────────┬────────────────────────────┐
│ паттерн            │ какую боль лечит                   │ цена                       │
├────────────────────┼────────────────────────────────────┼────────────────────────────┤
│ Extended Reference │ лишний запрос за именем автора     │ дубли надо обновлять       │
├────────────────────┼────────────────────────────────────┼────────────────────────────┤
│ Subset             │ документ раздут, а нужно 3 записи  │ две записи вместо одной    │
├────────────────────┼────────────────────────────────────┼────────────────────────────┤
│ Bucket             │ миллионы крошечных документов      │ сложнее точечные правки    │
├────────────────────┼────────────────────────────────────┼────────────────────────────┤
│ Computed           │ агрегат считается на каждом чтении │ значение может разъехаться │
└────────────────────┴────────────────────────────────────┴────────────────────────────┘
```

### Extended Reference — дублируем несколько полей, а не весь документ

Проблема: чистая ссылка `authorId` заставляет делать второй запрос ради имени и аватара — на каждой странице и в каждом элементе ленты. Полное вложение автора в пост — перебор: у пользователя есть email, хеш пароля, настройки, и всё это не нужно.

```js
// решение: положить в пост ровно те поля автора, которые рисуются
author: { _id: ObjectId("64a1"), name: "Максим", avatar: "/a/12.png" }
```

```txt
Критерий применимости: дублируются только поля, которые
  (а) нужны почти в каждом чтении родителя,
  (б) меняются существенно реже, чем читаются.

План синхронизации обязателен — и у него есть два варианта:

  1. Копия должна догонять источник:
     смена имени → фоновое обновление всех документов, где оно
     закопировано (updateMany по author._id + индекс на это поле).
     Между этими двумя записями система рассинхронизирована —
     это осознанная eventual consistency, а не баг.

  2. Копия — это СНАПШОТ на момент события, и обновлять её не нужно:
     имя автора «на момент публикации», цена товара «на момент
     заказа», адрес доставки «как было в заказе». Здесь дублирование
     не техническая оптимизация, а требование предметной области.

Разделение этих двух случаев — то, что отличает продуманную схему
от случайной денормализации.
```

```js
// Вариант 1 в коде: обновление профиля обновляет и копии
await users.updateOne({ _id: userId }, { $set: { name: newName } });
await posts.updateMany(
  { "author._id": userId },
  { $set: { "author.name": newName } }
);
await comments.updateMany(
  { "author._id": userId },
  { $set: { "author.name": newName } }
);
// нужен индекс на { "author._id": 1 } в обеих коллекциях, иначе это
// COLLSCAN (см. [Indexes and Query Performance])
```

### Subset — держим горячее подмножество в документе

Проблема: комментариев может быть 50 000, вкладывать их нельзя. Но страница поста показывает первые три — и ради них делается второй запрос на 95% просмотров.

```js
// решение: массив ФИКСИРОВАННОЙ длины в посте + полная коллекция
db.posts.updateOne(
  { _id: postId },
  {
    $push: {
      recentComments: {
        $each: [newComment],
        $sort: { createdAt: -1 },
        $slice: 3                  // ← верхняя граница массива
      }
    },
    $inc: { "stats.comments": 1 }
  }
);
await db.collection("comments").insertOne(newComment);  // полная копия
```

```txt
Что важно понимать про Subset:
  - $slice в $push — это и есть механизм, который делает рост
    ОГРАНИЧЕННЫМ; без него Subset превращается в анти-паттерн
  - записи стало две (в посты и в comments) и они НЕ атомарны:
    возможен пост с обновлённым preview и без записи в comments
    при падении между операциями
  - допустимость этой рассинхронизации — продуктовое решение:
    для preview и счётчика обычно допустимо (перезаполнится при
    следующем комментарии или фоновым пересчётом), для денег — нет,
    и тогда нужна транзакция (см. [Replication, Transactions,
    and Consistency])
  - «правильный» порядок: сначала insert в comments (источник
    истины), потом обновление preview — так теряется только кэш,
    а не данные
```

### Bucket — группируем поток в документы-корзины

```txt
     Bucket: документ на корзину, а не на событие
┌───────────────────────────────────────────────────┐
│ наивно — документ на каждый просмотр:             │
│ { postId: 1, at: ISODate("...T10:00:03Z") }       │
│ { postId: 1, at: ISODate("...T10:00:07Z") }       │
│   → 10M документов в сутки, 10M записей в индексе │
├───────────────────────────────────────────────────┤
│ Bucket — документ на (postId, час):               │
│ { postId: 1, hour: ISODate("...T10:00Z"),         │
│   count: 8421, uniqueUsers: 3190 }                │
│   → 24 документа в сутки на пост, upsert + $inc   │
└───────────────────────────────────────────────────┘
 отчёт за неделю: 168 документов вместо 70 миллионов
```

Проблема: документ на каждое событие даёт миллионы крошечных документов. Каждый — это накладные расходы на хранение, запись в индекс и, главное, миллионы документов, которые придётся просканировать для отчёта.

```js
// Просмотры: не документ на просмотр, а корзина на (postId, час)
await db.collection("postViews").updateOne(
  { postId, hour: startOfHour },
  {
    $inc: { count: 1 },
    $setOnInsert: { createdAt: new Date() }
  },
  { upsert: true }
);
// уникальный индекс { postId: 1, hour: 1 } обязателен — иначе гонка
// upsert создаст две корзины (см. [CRUD and Query Operators])

// Отчёт за неделю по посту: 168 документов вместо 70 миллионов
db.postViews.find({ postId, hour: { $gte: weekAgo } }).sort({ hour: 1 })
```

```txt
Bucket применяется, когда:
  - поток событий однородный и очень плотный (метрики, IoT, лог
    действий, показы)
  - читается ДИАПАЗОНОМ, а не по одному событию
  - точечная правка отдельного события не нужна

Цена: изменить или удалить одно событие внутри корзины сложно;
гранулярность (час/день) фиксируется на этапе проектирования и
меняется только пересчётом. Для чистых временных рядов рассмотрите
time series collections — MongoDB 5.0+ делает бакетирование сам.
```

### Computed — считаем при записи, а не при чтении

Проблема: `stats.comments` можно получить `countDocuments({ postId })` — но тогда лента из 20 постов делает 20 подсчётов, каждый из которых сканирует индекс по всем комментариям поста.

```js
// решение: держать готовое значение и обновлять его в том же
// атомарном шаге, что и сам факт
db.posts.updateOne({ _id: postId }, { $inc: { "stats.comments": 1 } });

// то же для среднего рейтинга — храним сумму и количество, чтобы
// не пересчитывать по всем оценкам
db.posts.updateOne(
  { _id: postId },
  { $inc: { "rating.sum": score, "rating.count": 1 } }
);
// среднее считается на чтении из двух чисел, без обхода оценок
```

```txt
Когда применять: читается на порядок чаще, чем изменяется
(счётчики, суммы, средние, «последняя активность»).

Обязательное дополнение — способ восстановления. Счётчик рано или
поздно разъедется: упавший процесс, ручное удаление документа,
баг в новой ветке. Нужна фоновая задача пересчёта из источника
истины, которую можно запустить руками:

  const real = await comments.countDocuments({ postId });
  await posts.updateOne({ _id: postId },
                        { $set: { "stats.comments": real } });

Схема с Computed без такой задачи — это схема, у которой нет
способа вернуться к правде.
```

## Анти-паттерны

### Неограниченно растущий массив

```txt
{ _id: postId, comments: [ ... 40 000 элементов ... ] }

Почему это ломается ЗАДОЛГО до лимита 16 МБ:
  - WiredTiger не правит документ на месте: обновление массива
    переписывает документ целиком → чем он больше, тем дороже
    КАЖДЫЙ $push
  - документ целиком читается в память и целиком уходит по сети,
    даже если нужен один элемент (проекция $slice спасает трафик,
    но не чтение с диска)
  - multikey-индекс по массиву получает запись НА КАЖДЫЙ элемент
    документа → индекс распухает (см. [Indexes and Query
    Performance])
  - обновление элемента в конце массива требует прохода по массиву
  - в реплика-сете каждое такое обновление — большая запись в oplog

Признак анти-паттерна формулируется без цифр: элементы добавляются
действиями пользователей, и верхней границы нет.

Лечение: referencing (своя коллекция) или Subset с $slice.
```

### Лимит 16 МБ

```txt
16 МБ — жёсткий лимит на РАЗМЕР ОДНОГО ДОКУМЕНТА в BSON, включая
все вложенные объекты и массивы. Ошибка на записи:
  BSONObjectTooLarge / "object to insert too large"

Где лимит встречается ещё:
  - результат агрегации, если она собирает один документ через
    $group/$push (см. [Aggregation Pipeline]) — обходится через
    курсор или $out/$merge
  - ответ на запрос в целом ограничен ~16 МБ на батч (курсор
    отдаёт следующие батчи через getMore)

Практический смысл: 16 МБ — это не «цель, к которой можно расти»,
а знак, что схема выбрана неверно. Документы в здоровой схеме —
это килобайты. Файлы и медиа в документах не хранят: в MongoDB
для этого GridFS, но правильный ответ обычно S3 и ссылка в
документе.
```

### Массивная денормализация без плана синхронизации

```txt
Симптом: в posts и comments лежит ПОЛНАЯ копия автора — email,
роли, настройки, счётчики.

Что происходит дальше:
  - пользователь меняет email → updateMany по миллионам документов,
    минуты работы и всплеск нагрузки на запись
  - обновление упало на середине → часть документов с новым email,
    часть со старым, и НИКАКОЙ транзакции вокруг этого нет
  - удаление пользователя по GDPR превращается в поиск копий по
    всем коллекциям
  - размер каждого поста вырос в разы ради полей, которые не
    рисуются

Вопрос, который задаёт интервьюер: «кто и когда обновляет дубли,
и что будет, если обновление упадёт посередине?» Хороший ответ
называет конкретный механизм:
  - фоновая задача/очередь с ретраями и идемпотентностью
  - change streams: слушаем изменения users и обновляем копии
  - транзакция — если рассинхронизация недопустима (и тогда
    честно: она дороже)
  - осознанное «дубли не обновляем, это снапшот»

Отсутствие ответа = денормализация была случайной.
```

### Схема «как в SQL»: полная нормализация в MongoDB

```txt
Симптом: users, posts, comments, tags, post_tags, post_stats —
всё по отдельности, в документах только идентификаторы, каждая
страница собирается тремя-четырьмя $lookup или пятью populate.

Почему это худший из миров:
  - джойны есть, но они хуже реляционных: $lookup выполняется как
    вложенный запрос на каждый входной документ, без hash join и
    выбора порядка соединения планировщиком (см. [Aggregation
    Pipeline]); populate в Mongoose — это вообще N+1 отдельных
    запросов (см. [Mongoose Queries, populate, and Pitfalls])
  - целостности всё равно нет: FK, ON DELETE CASCADE и
    межколлекционных CHECK не существует
  - транзакции нужны на каждый шаг, а они здесь дороже, чем в
    реляционной БД
  - гибкость документа не используется: получилась реляционная
    схема без реляционных гарантий и без реляционного оптимизатора

Что делать: либо пересобрать схему вокруг агрегатов (и тогда
$lookup становится не нужен), либо признать, что данные
реляционные, и взять PostgreSQL — см. [Document Model and
Use Cases]. Промежуточное состояние — самое дорогое.
```

## Процедура проектирования: как отвечать у доски

```txt
1. Выписать топ-5 запросов приложения и их частоту.
   Без этого шага любой ответ про embedding — угадывание.

2. Для каждой связи определить кардинальность в терминах
   few / many / squillions — и отдельно: есть ли верхняя граница.

3. Решить embed или reference по критериям: читается вместе?
   нужен независимый доступ? как часто меняется?

4. Проверить границы: сколько будет весить документ на худшем
   реальном примере (вирусный пост, крупный tenant).

5. Для каждого дубля назвать план синхронизации ИЛИ явно сказать,
   что это снапшот.

6. Проверить, какие индексы нужны получившимся запросам
   (см. [Indexes and Query Performance]) — схема без индексов
   под её же запросы недоделана.

7. Назвать, что изменится, если требование изменится: «если
   понадобится независимая пагинация комментариев — они уже в
   отдельной коллекции; если понадобится история имён автора —
   Extended Reference станет снапшотом».
```

И главное, что стоит произнести вслух: правильного ответа «вкладывать или ссылаться» в вакууме нет. Есть ответ для конкретного набора запросов, объёмов и требований к консистентности. Кандидат, который говорит «комментарии всегда вкладываем» или «всегда ссылка», отвечает хуже того, кто называет критерий и применяет его к условию.

## Типичные ошибки на интервью

- **«Комментарии всегда вкладываем в пост — это же документная БД»** — комментарии не имеют верхней границы: один вирусный пост упирается в лимит 16 МБ, а задолго до этого — в переписывание документа на каждый `$push`. Правильный ответ: ссылка + Subset для preview.

- **«Embedding — это всегда быстрее»** — быстрее на чтении родителя целиком. На обновлении одного вложенного элемента большого документа — медленнее, потому что переписывается весь документ, и на выборках, где вложенное не нужно, — дороже по трафику.

- **«Referencing — это как в SQL, значит правильно»** — нормализованная схема в MongoDB даёт реляционную форму без реляционных гарантий: `$lookup` вместо планировщика, populate вместо JOIN, отсутствие FK. Это худший из двух миров.

- **«Дублирование данных — это плохо»** — в документной модели дублирование это инструмент. Плохо — дублирование без ответа на вопрос «кто и когда обновляет копии, и что будет при сбое посередине».

- **«Лимит 16 МБ — это много, нам не грозит»** — граница обнаруживается не в среднем, а на худшем реальном документе: самый популярный пост, самый крупный клиент. И проблемы с производительностью начинаются на сотнях килобайт, а не на 16 МБ.

- **«Extended Reference — это то же самое, что вложить весь документ»** — смысл именно в том, чтобы копировать 2-3 поля для отображения, а не весь профиль. Копируется то, что редко меняется и почти всегда читается.

- **«Счётчик комментариев можно считать `countDocuments()` на чтении»** — на ленте из 20 постов это 20 подсчётов. Счётчик хранится и обновляется атомарным `$inc`; отдельно нужен способ пересчёта из источника истины.

- **«$lookup решает проблему связей, так что можно нормализовать»** — `$lookup` выполняется на каждый входной документ и не является планируемым JOIN. Он допустим для редких запросов и отчётов, но не для основного пути чтения.

- **«Я бы посмотрел, как сделано в похожем проекте»** — на этом вопросе интервьюер проверяет умение вывести схему из требований. Ответ должен начинаться со списка запросов, а не с шаблона.
