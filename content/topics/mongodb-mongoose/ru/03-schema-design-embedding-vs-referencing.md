# Проектирование схемы: вложение или ссылка

## Схема проектируется от запросов, а не от сущностей

В MongoDB схему выводят из запросов. Сначала выписывают список запросов, которые приложение будет выполнять чаще всего. И только потом решают, как разложить данные.

В реляционном проектировании порядок обратный: выделить сущности, нормализовать до 3NF, а потом оптимизировать то, что оказалось медленным. 3NF — это третья нормальная форма, набор правил, который выносит повторяющиеся столбцы в отдельные таблицы. Нормальных форм в документной модели нет вообще. Вместо них — соответствие схемы паттерну доступа.

```txt
Что нужно выписать до первой коллекции (на примере блога):

  1. страница поста   ~1000/мин
     пост + автор (имя, аватар) + первые 3 комментария
  2. лента постов     ~500/мин
     20 постов: заголовок, автор, число комментариев, теги
  3. все комментарии поста   ~50/мин
     постранично, по 50
  4. профиль автора   ~20/мин
     автор + его последние 10 постов
  5. модерация комментария   ~5/мин
     один комментарий по _id

Из этого списка видно главное: запросы 1 и 2 — 95% нагрузки, и оба
хотят имя автора и число комментариев вместе с постом. Всё остальное
проектирование — следствие этого факта.
```

Правило, к которому сводится вся тема, формулируется одной фразой: **что читается вместе — хранится вместе**. Дальше идут ограничения, которые не дают довести это правило до абсурда.

## Два способа связать данные

Способов ровно два. Вложение (embedding) — положить дочерние данные внутрь родительского документа. Ссылка (referencing) — хранить `_id` (или наоборот, `parentId` в дочернем документе) и делать второй запрос.

```txt
EMBEDDING: комментарии внутри поста
┌──────────────────────────────────┐
│ коллекция posts                  │
│                                  │
│ { _id: 1,                        │
│   title: "Индексы",              │
│   comments: [                    │
│     { _id: 11, body: "..." },    │
│     { _id: 12, body: "..." } ] } │
└──────────────────────────────────┘
  одно чтение отдаёт всю страницу;
одна запись меняет пост и комментарий
атомарно; но массив растёт без границы

       REFERENCING: две коллекции
┌──────────────────────────────┐
│ коллекция posts              │
│                              │
│ { _id: 1, title: "Индексы" } │
└──────────────────────────────┘

┌─────────────────────────────────────┐
│ коллекция comments                  │
│                                     │
│ { _id: 11, postId: 1, body: "..." } │
│ { _id: 12, postId: 1, body: "..." } │
└─────────────────────────────────────┘
     рост не ограничен документом,
    комментарии живут своей жизнью;
    но два запроса и нет атомарности
```

```txt
Что даёт вложение:
  + одно чтение отдаёт всё; никаких джойнов и второй сетевой
    задержки
  + одна запись меняет родителя и вложенное атомарно
    (про атомарность документа — статья 02)
  + данные лежат физически рядом — одно обращение к диску и кэшу
  - документ растёт; лимит 16 МБ и переписывание документа
    на каждую запись
  - к вложенным данным нельзя обратиться независимо: нет своей
    коллекции, нет отдельной пагинации по ним, и запрос «дай все
    комментарии пользователя по всем постам» усложняется
  - обновление одного вложенного элемента переписывает документ
    целиком

Что даёт ссылка:
  + рост не ограничен размером родителя
  + дочерние сущности живут своей жизнью: собственные индексы,
    сортировка, пагинация, удаление
  + один и тот же дочерний документ может быть связан со многими
  - минимум два запроса или $lookup — см. статью 05 про конвейер
    агрегации
  - нет атомарности между коллекциями без транзакции
  - целостность на совести приложения: «висячие» ссылки MongoDB
    не запрещает. Внешних ключей и ON DELETE CASCADE здесь нет.
```

## Четыре критерия выбора

### 1. Кардинальность

Кардинальность — это сколько дочерних записей может быть у одного родителя, и это первый фильтр решения:

| связь | пример в блоге | решение |
|---|---|---|
| one-to-few | у поста 3-10 тегов | вкладывать массивом |
| one-to-few | у пользователя 2 адреса | вкладывать массивом |
| one-to-many | у поста 50-500 комментариев | ссылка + Subset в посте |
| one-to-squillions | у поста миллионы просмотров | ссылка из дочернего, Bucket |
| many-to-many | посты и теги как сущности | массив id на «главной» стороне |

Граница между few и many — не число. Это ответ на один вопрос: может ли пользователь наращивать это без предела?

Формулировка «one-to-few / one-to-many / one-to-squillions» полезна тем, что переводит вопрос из «сколько сейчас» в «сколько может стать». Три-десять тегов у поста — это few и навсегда few. Комментарии — many. У 99% постов их будет 20, у одного вирусного — 50 000, и схема должна выдержать именно этот случай.

### 2. Паттерн доступа: читается вместе или по отдельности

Решают три вопроса, и каждый сразу указывает на ответ:

```txt
  - Нужны ли дочерние данные всегда, когда читается родитель?
    Всегда → вложение. Иногда → ссылка (не платить за то, что
    не читаешь).
  - Нужен ли доступ к дочерним данным без родителя? «Все
    комментарии пользователя», «модерация свежих комментариев
    по всей системе» → отдельная коллекция.
  - Нужна ли пагинация или сортировка по дочерним данным?
    Внутри массива это делается только в конвейере агрегации
    ($slice, $unwind + $sort) — дорого и неудобно → отдельная
    коллекция.
```

### 3. Частота изменений и стоимость дублей

Вкладывая или дублируя, вы делаете копию. Копия — это обязательство её обновлять. Поэтому дублируют то, что меняется редко, и не дублируют то, что меняется часто.

- **Имя и аватар автора** — меняются раз в год, дублировать можно.
- **Число комментариев поста** — меняется каждый час. Хранить как счётчик у поста (паттерн Computed ниже), но не дублировать в 500 местах.
- **Email, права, статус бана** — меняются и критичны. Только ссылка.

### 4. Границы роста

Последний критерий — один вопрос: может ли пользователь или внешняя система наращивать этот набор элементов без предела?

```txt
  теги поста      — задаёт автор, редактор ставит предел 10 → есть
  лайки           — ставит любой из миллиона пользователей  → нет
  комментарии     — пишет любой                             → нет
  адреса доставки — пользователь, реалистично 1-5           → есть

  («есть» и «нет» в правой колонке — про верхнюю границу роста)
```

Массив без верхней границы во вложении — это отложенная авария, а не «пока работает».

## Сквозной пример: схема блога

Из критериев выше блог складывается в три коллекции: `users`, `posts` и `comments`.

```js
// users — сущность со своей жизнью, ссылаются многие
{
  _id: ObjectId("64a1"),
  email: "max@test.com",          // меняется, критично → не дублируем
  name: "Максим",                 // меняется редко → дублируем
  avatar: "/a/12.png",            // меняется редко → дублируем
  passwordHash: "...",
  createdAt: ISODate("...")
}

// posts — центральный агрегат: то, что нужно для страницы и ленты
{
  _id: ObjectId("66b0"),
  slug: "mongodb-indexes",
  title: "Индексы в MongoDB",
  body: "...",

  // Extended Reference: id + минимум полей для отображения
  author: { _id: ObjectId("64a1"), name: "Максим", avatar: "/a/12.png" },

  // one-to-few, границы есть, всегда читаются вместе → вложение
  tags: ["mongodb", "performance"],

  // Computed: считается при записи, читается на каждой странице
  stats: { comments: 128, views: 9421, likes: 42 },

  // Subset: только то, что показывает первый экран страницы поста
  recentComments: [
    { _id: ObjectId("77c1"), body: "спасибо!",
      author: { _id: ObjectId("64b2"), name: "Аня" },
      createdAt: ISODate("...") }
  ],

  publishedAt: ISODate("...")
}

// comments — one-to-many без границы → своя коллекция, ссылка на пост
{
  _id: ObjectId("77c1"),
  postId: ObjectId("66b0"),       // ссылка идёт из дочернего в родителя
  author: { _id: ObjectId("64b2"), name: "Аня" },
  body: "спасибо!",
  score: 3,
  createdAt: ISODate("...")
}
```

Что даёт такая схема на основных запросах:

```js
// 1. Страница поста — один запрос вместо джойна по трём таблицам:
//    пост, автор для отображения и первые комментарии уже внутри
const post = await db.collection("posts").findOne({ slug });

// 2. Лента — один запрос, всё нужное в проекции
const feed = await db.collection("posts")
  .find({ status: "published" })
  .project({ title: 1, slug: 1, author: 1, tags: 1, "stats.comments": 1 })
  .sort({ publishedAt: -1 })
  .limit(20)
  .toArray();

// 3. Все комментарии поста — отдельный запрос с настоящей пагинацией
const comments = await db.collection("comments")
  .find({ postId: post._id })
  .sort({ createdAt: -1 })
  .limit(50)
  .toArray();
```

Ключевое наблюдение: 95% нагрузки (запросы 1 и 2) обслуживается одним обращением к одной коллекции. Остальные 5% платят вторым запросом, и это правильный компромисс, а не недоработка.

## Практические паттерны проектирования

Четыре паттерна закрывают почти всё, что нужно документной схеме, и у каждого есть цена:

| паттерн | какую боль лечит | цена |
|---|---|---|
| Extended Reference | лишний запрос за именем автора | дубли надо обновлять |
| Subset | документ раздут, а нужно 3 записи | две записи вместо одной |
| Bucket | миллионы крошечных документов | сложнее точечные правки |
| Computed | агрегат считается на каждом чтении | значение может разъехаться |

### Extended Reference — дублируем несколько полей, а не весь документ

Проблема: чистая ссылка `authorId` заставляет делать второй запрос ради имени и аватара — на каждой странице и в каждом элементе ленты. Вложить автора целиком — перебор: у пользователя есть email, хеш пароля и настройки, и всё это здесь не нужно.

```js
// решение: положить в пост ровно те поля автора, которые рисуются
author: { _id: ObjectId("64a1"), name: "Максим", avatar: "/a/12.png" }
```

```txt
Критерий применимости: дублируются только поля, которые
  (а) нужны почти в каждом чтении родителя,
  (б) меняются существенно реже, чем читаются.

План синхронизации обязателен, и у него два варианта:

  1. Копия должна догонять источник.
     Смена имени запускает фоновое обновление всех документов,
     где оно закопировано: updateMany по author._id плюс индекс
     на это поле. Между этими двумя записями система
     рассинхронизирована. Это осознанная согласованность
     в конечном счёте (eventual consistency): копии становятся
     верными чуть позже, а не мгновенно. Это не баг.

  2. Копия — это снимок на момент события, и обновлять её не
     нужно: имя автора «на момент публикации», цена товара
     «на момент заказа», адрес доставки «как было в заказе».
     Здесь дублирование не техническая оптимизация,
     а требование предметной области.

Разделение этих двух случаев — то, что отличает продуманную схему
от случайной денормализации.
```

```js
// Вариант 1 в коде: обновление профиля обновляет и копии
await users.updateOne({ _id: userId }, { $set: { name: newName } });
await posts.updateMany(
  { "author._id": userId },
  { $set: { "author.name": newName } }
);
await comments.updateMany(
  { "author._id": userId },
  { $set: { "author.name": newName } }
);
// нужен индекс на { "author._id": 1 } в обеих коллекциях, иначе это
// COLLSCAN — полный проход по всем документам (см. статью 04)
```

### Subset — держим горячее подмножество в документе

Проблема: комментариев может быть 50 000, вкладывать их нельзя. Но страница поста показывает первые три, и ради них делается второй запрос на 95% просмотров.

```js
// решение: массив фиксированной длины в посте + полная коллекция
db.posts.updateOne(
  { _id: postId },
  {
    $push: {
      recentComments: {
        $each: [newComment],
        $sort: { createdAt: -1 },
        $slice: 3                  // ← верхняя граница массива
      }
    },
    $inc: { "stats.comments": 1 }
  }
);
await db.collection("comments").insertOne(newComment);  // полная копия
```

```txt
Что важно понимать про Subset:
  - $slice внутри $push — это и есть механизм, который ограничивает
    рост; без него Subset превращается в анти-паттерн
  - записи стало две, в posts и в comments, и они не атомарны:
    при падении между операциями останется пост с обновлённым
    превью и без записи в comments
  - допустима ли эта рассинхронизация — продуктовое решение.
    Для превью и счётчика обычно допустима: следующий комментарий
    или фоновый пересчёт всё поправят. Для денег — нет, и тогда
    нужна транзакция, см. статью 06.
  - «правильный» порядок такой: сначала insert в comments
    (источник истины), потом обновление превью. Так теряется
    только кэш, а не данные.
```

### Bucket — группируем поток в документы-корзины

Проблема: документ на каждое событие даёт миллионы крошечных документов. Каждый — это накладные расходы на хранение и запись в индекс. И, главное, отчёту приходится сканировать миллионы документов.

```txt
     Bucket: документ на корзину, а не на событие
┌───────────────────────────────────────────────────┐
│ наивно — документ на каждый просмотр:             │
│ { postId: 1, at: ISODate("...T10:00:03Z") }       │
│ { postId: 1, at: ISODate("...T10:00:07Z") }       │
│   → 10M документов в сутки, 10M записей в индексе │
├───────────────────────────────────────────────────┤
│ Bucket — документ на (postId, час):               │
│ { postId: 1, hour: ISODate("...T10:00Z"),         │
│   count: 8421, uniqueUsers: 3190 }                │
│   → 24 документа в сутки на пост, upsert + $inc   │
└───────────────────────────────────────────────────┘
 отчёт за неделю: 168 документов вместо 70 миллионов
```

```js
// Просмотры: не документ на просмотр, а корзина на (postId, час)
await db.collection("postViews").updateOne(
  { postId, hour: startOfHour },
  {
    $inc: { count: 1 },
    $setOnInsert: { createdAt: new Date() }
  },
  { upsert: true }
);
// уникальный индекс { postId: 1, hour: 1 } обязателен — иначе гонка
// upsert создаст две корзины (см. статью 02 про upsert)

// Отчёт за неделю по посту: 168 документов вместо 70 миллионов
db.postViews.find({ postId, hour: { $gte: weekAgo } }).sort({ hour: 1 })
```

```txt
Bucket применяется, когда:
  - поток событий однородный и очень плотный: метрики, лог
    действий, показы, показания датчиков «интернета вещей»
    (IoT — подключённые к сети устройства и сенсоры)
  - читается диапазоном, а не по одному событию
  - точечная правка отдельного события не нужна

Цена: изменить или удалить одно событие внутри корзины сложно.
Гранулярность (час или день) фиксируется на этапе проектирования
и меняется только пересчётом. Для чистых временных рядов
рассмотрите time series collections — MongoDB 5.0+ делает
разбиение на корзины сам.
```

### Computed — считаем при записи, а не при чтении

Проблема: `stats.comments` можно получить через `countDocuments({ postId })`. Но тогда лента из 20 постов делает 20 подсчётов, и каждый сканирует индекс по всем комментариям поста.

```js
// решение: держать готовое значение и обновлять его в том же
// атомарном шаге, что и сам факт
db.posts.updateOne({ _id: postId }, { $inc: { "stats.comments": 1 } });

// то же для среднего рейтинга — храним сумму и количество, чтобы
// не пересчитывать по всем оценкам
db.posts.updateOne(
  { _id: postId },
  { $inc: { "rating.sum": score, "rating.count": 1 } }
);
// среднее считается на чтении из двух чисел, без обхода оценок
```

```txt
Когда применять: значение читается на порядок чаще, чем меняется —
счётчики, суммы, средние, «последняя активность».

Обязательное дополнение — способ восстановления. Счётчик рано или
поздно разъедется: упавший процесс, ручное удаление документа,
баг в новой ветке. Нужна фоновая задача, которая пересчитывает
значение из источника истины и запускается ещё и руками:

  const real = await comments.countDocuments({ postId });
  await posts.updateOne({ _id: postId },
                        { $set: { "stats.comments": real } });

Схема с Computed без такой задачи — это схема, у которой нет
способа вернуться к правде.
```

## Анти-паттерны

### Неограниченно растущий массив

Массив, который только растёт, — самый частый дефект схемы в MongoDB. Он ломается задолго до лимита 16 МБ, и причин тому пять.

```txt
{ _id: postId, comments: [ ... 40 000 элементов ... ] }

  - WiredTiger, движок хранения MongoDB, не правит документ на
    месте. Обновление массива переписывает документ целиком,
    поэтому чем он больше, тем дороже каждый отдельный $push.
  - документ целиком читается в память и целиком уходит по сети,
    даже если нужен один элемент (проекция $slice спасает трафик,
    но не чтение с диска)
  - индекс по массиву — это multikey-индекс: он хранит по записи
    на каждый элемент документа, поэтому распухает вместе
    с массивом (см. статью 04)
  - обновление элемента в конце массива требует прохода по нему
  - в реплика-сете каждое такое обновление — большая запись
    в oplog, журнал операций, который повторяют вторичные узлы

Признак анти-паттерна формулируется без цифр: элементы добавляются
действиями пользователей, и верхней границы нет.

Лечение: ссылка (своя коллекция) или Subset с $slice.
```

### Лимит 16 МБ

16 МБ — жёсткий лимит на размер одного документа. Его часто считают целью, до которой можно расти, тогда как это предупреждающий знак.

```txt
Лимит считается по одному документу в BSON — двоичной
типизированной форме, в которой MongoDB хранит данные, — включая
все вложенные объекты и массивы. Ошибка на записи:
  BSONObjectTooLarge / "object to insert too large"

Где лимит встречается ещё:
  - результат агрегации, если она собирает один документ через
    $group/$push (см. статью 05) — обходится курсором или через
    $out/$merge
  - ответ на запрос ограничен ~16 МБ на батч (следующие батчи
    курсор отдаёт через getMore)

Практический смысл: 16 МБ — это не «цель, к которой можно
расти», а знак, что схема выбрана неверно. Документы в здоровой
схеме — это килобайты. Файлы и медиа в документах не хранят:
в MongoDB для этого есть GridFS, но правильный ответ обычно —
объектное хранилище вроде S3 и ссылка в документе.
```

### Массивная денормализация без плана синхронизации

Симптом виден сразу: в `posts` и `comments` лежит полная копия автора — email, роли, настройки, счётчики.

```txt
Что происходит дальше:
  - пользователь меняет email → updateMany по миллионам
    документов, минуты работы и всплеск нагрузки на запись
  - обновление упало на середине → часть документов с новым
    email, часть со старым, и никакой транзакции вокруг этого нет
  - удаление данных по требованию GDPR (General Data Protection
    Regulation — европейский закон о защите персональных данных)
    превращается в поиск копий по всем коллекциям
  - размер каждого поста вырос в разы ради полей, которые
    не рисуются

Вопрос, который задаёт интервьюер: «кто и когда обновляет дубли,
и что будет, если обновление упадёт посередине?» Хороший ответ
называет конкретный механизм:
  - фоновая задача или очередь, с повторами и идемпотентностью
  - change streams: слушаем изменения users и обновляем копии
  - транзакция, если рассинхронизация недопустима — и тогда
    честно сказать, что она дороже
  - осознанное «дубли не обновляем, это снимок»

Отсутствие ответа значит, что денормализация была случайной.
```

### Схема «как в SQL»: полная нормализация в MongoDB

Полностью нормализованная схема в MongoDB даёт реляционную форму без реляционных гарантий. SQL — язык запросов к реляционным базам, и это то самое место, где копирование его привычек стоит дороже всего.

```txt
Симптом: users, posts, comments, tags, post_tags, post_stats —
всё по отдельности, в документах только идентификаторы, каждая
страница собирается тремя-четырьмя $lookup или пятью вызовами
populate.

Почему это худший из миров:
  - джойны есть, но они хуже реляционных. $lookup выполняется как
    вложенный запрос на каждый входной документ, без hash join и
    без выбора порядка соединения планировщиком (см. статью 05).
    А populate в Mongoose — это буквально N+1 отдельных запросов:
    один за списком из N родителей и ещё по одному на каждого
    родителя (см. статью 08).
  - целостности всё равно нет: внешних ключей, ON DELETE CASCADE
    и межколлекционных CHECK не существует
  - транзакции нужны на каждый шаг, а они здесь дороже, чем
    в реляционной базе
  - гибкость документа не используется: получилась реляционная
    схема без реляционных гарантий и без реляционного
    оптимизатора

Что делать: либо пересобрать схему вокруг агрегатов, и тогда
$lookup становится не нужен, либо признать, что данные
реляционные, и взять PostgreSQL — см. статью 01. Промежуточное
состояние — самое дорогое.
```

## Процедура проектирования: как отвечать у доски

Семь шагов, именно в таком порядке. Пропуск первого превращает все остальные в угадывание.

```txt
1. Выписать топ-5 запросов приложения и их частоту.
   Без этого шага любой ответ про вложение — угадывание.

2. Для каждой связи определить кардинальность в терминах
   few / many / squillions — и отдельно: есть ли верхняя граница.

3. Решить, вкладывать или ссылаться, по критериям: читается
   вместе? нужен независимый доступ? как часто меняется?

4. Проверить границы: сколько будет весить документ на худшем
   реальном примере (вирусный пост, крупнейший клиент).

5. Для каждого дубля назвать план синхронизации либо явно
   сказать, что это снимок.

6. Проверить, какие индексы нужны получившимся запросам
   (см. статью 04) — схема без индексов под её же запросы
   недоделана.

7. Назвать, что изменится, если изменится требование: «если
   понадобится независимая пагинация комментариев — они уже
   в отдельной коллекции; если понадобится история имён автора —
   Extended Reference станет снимком».
```

И главное, что стоит произнести вслух: правильного ответа «вкладывать или ссылаться» в вакууме нет. Есть ответ для конкретного набора запросов, объёмов и требований к консистентности. «Комментарии всегда вкладываем» и «всегда ссылка» — оба хуже, чем назвать критерий и применить его к условию.

## Связь с другими темами

- **01 — Документная модель и когда её выбирать.** Лимит 16 МБ и атомарность документа как причина проектировать агрегатами.
- **02 — CRUD и операторы запросов.** CRUD — это create, read, update, delete: создание, чтение, обновление и удаление. `$push`/`$slice` для Subset, `upsert` + `$inc` для Bucket, атомарный `$inc` для Computed.
- **04 — Индексы и производительность запросов.** Индексы под получившиеся запросы, multikey-индексы по вложенным массивам, индекс на `"author._id"` для синхронизации дублей.
- **05 — Конвейер агрегации.** `$lookup` как цена ссылок и почему вложение его убирает.
- **06 — Репликация, транзакции и консистентность.** Когда рассинхронизацию дублей допускать нельзя: транзакция и её цена.
- **08 — Запросы Mongoose, populate и ловушки.** `populate` как самый частый способ случайно получить N+1 на нормализованной схеме.

## Типичные ошибки на интервью

- **«Комментарии всегда вкладываем в пост — это же документная база»** — у комментариев нет верхней границы. Один вирусный пост упирается в лимит 16 МБ, а задолго до этого — в переписывание документа на каждый `$push`. Правильный ответ: ссылка плюс Subset для превью.

- **«Вложение — это всегда быстрее»** — быстрее на чтении родителя целиком. Медленнее на обновлении одного вложенного элемента большого документа, потому что переписывается весь документ. И дороже по трафику на выборках, где вложенное не нужно.

- **«Ссылки — это как в SQL, значит правильно»** — нормализованная схема в MongoDB даёт реляционную форму без реляционных гарантий: `$lookup` вместо планировщика, `populate` вместо джойна, никаких внешних ключей. Это худший из двух миров.

- **«Дублирование данных — это плохо»** — в документной модели дублирование это инструмент. Плохо — дублирование без ответа на вопрос «кто и когда обновляет копии, и что будет при сбое посередине».

- **«Лимит 16 МБ — это много, нам не грозит»** — граница обнаруживается не на среднем документе, а на худшем реальном: самый популярный пост, самый крупный клиент. И проблемы с производительностью начинаются на сотнях килобайт.

- **«Extended Reference — это то же самое, что вложить весь документ»** — смысл именно в том, чтобы копировать 2-3 поля для отображения, а не весь профиль. Копируется то, что редко меняется и почти всегда читается.

- **«Счётчик комментариев можно считать `countDocuments()` на чтении»** — на ленте из 20 постов это 20 подсчётов. Счётчик хранится и обновляется атомарным `$inc`. Отдельно нужен способ пересчёта из источника истины.

- **«$lookup решает проблему связей, так что можно нормализовать»** — `$lookup` выполняется на каждый входной документ, и планируемым джойном он не работает. Он допустим для редких запросов и отчётов, но не для основного пути чтения.

- **«Я бы посмотрел, как сделано в похожем проекте»** — на этом вопросе интервьюер проверяет умение вывести схему из требований. Ответ должен начинаться со списка запросов, а не с шаблона.
