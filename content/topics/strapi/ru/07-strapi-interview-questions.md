# Strapi Interview Questions

## Группа 1: Архитектура и концепция

**Q: Что такое Strapi и чем он отличается от WordPress?**

Strapi — это open-source headless CMS (content management system, система управления контентом) на Node.js, а точнее на Koa.js. «Headless» значит, что у неё нет слоя представления: встроенного фронтенда для конечных пользователей просто нет.

Контраст — WordPress. В нём и бэкенд на PHP (hypertext preprocessor), и фронтенд на шаблонах, и эти две части жёстко связаны. Strapi даёт редакторам Admin Panel, а всем остальным — API, который можно вызывать. У этого API две формы, REST (representational state transfer) и GraphQL, и обращаться к нему может любой клиент: React, Next.js, мобильное приложение.

Из этого разделения вырастает весь порядок работы. Вы описываете Content Types, а Strapi генерирует из них интерфейс администратора, схему базы данных и эндпоинты, чтобы создавать, читать, обновлять и удалять записи (CRUD). Он же заводит записи ролевой модели доступа (RBAC), которые решают, какой роли что можно вызывать.

**Q: Что происходит под капотом когда создаёшь Content Type в Strapi?**

Создание Content Type записывает один файл, а всё остальное в Strapi реагирует уже на него. Это `schema.json` в папке `src/api/<name>/content-types/<name>/`, и он — единственный источник правды о форме ваших данных. База данных не меняется до перезапуска сервера, поэтому порядок шагов ниже важен.

1. Strapi записывает `schema.json` в `src/api/<name>/content-types/<name>/`.
2. При следующем запуске Strapi читает эту схему и выполняет автоматическую миграцию. Таблица создаётся или обновляется в PostgreSQL, MySQL или SQLite, а каждая связь получает отдельную таблицу-связку.
3. Регистрируются сгенерированные маршруты: `GET`, `POST`, `PUT` и `DELETE` на `/api/<plural-name>`.
4. Собираются core router, controller и service — их строят фабрики `createCoreRouter`, `createCoreController` и `createCoreService`.
5. Admin Panel обновляется, и новый тип сразу виден редакторам.
6. Новые маршруты появляются в настройках, в ролях плагина Users & Permissions. Там вы отмечаете галочками действия, которые хотите выдать ролям Public и Authenticated.

Инструмент, который пишет `schema.json` за вас, — Content-Type Builder — доступен только в среде разработки. В production схема живёт как обычный код: вы правите `schema.json` руками, коммитите и деплоите.

**Q: Strapi использует Express или что-то другое?**

Koa.js. Ключевые отличия от Express: единый `ctx` объект вместо `req/res`, нативный async/await без обёрток, onion-model middleware (вместо next() линейного). Strapi добавляет поверх Koa: router, Plugin system, Document Service, Admin Panel (embedded React app).

## Группа 2: Content Types и Data Modeling

**Q: В чём разница между Collection Type, Single Type и Component?**

Разница в том, сколько записей хранит каждый из них и получает ли он собственный API. Collection Type хранит много записей одной формы. Single Type хранит ровно одну запись — так делают главную страницу или подвал сайта. Component — переиспользуемый блок полей, у которого нет ни записей, ни своего API: он живёт только внутри Content Type.

| | Collection Type | Single Type | Component |
|---|---|---|---|
| Записей | много | ровно одна | своих нет |
| Примеры | Articles, Products, Authors | Homepage, Footer, общие настройки для поисковиков | блок адреса, пункт «вопрос — ответ» |
| Чтение | `GET /api/articles` — список, `GET /api/articles/:documentId` — одна запись | `GET /api/homepage` возвращает объект, а не массив | своего эндпоинта нет |
| Запись | `POST` создаёт, `PUT` и `DELETE` работают по `documentId` | `PUT /api/homepage` создаёт или обновляет, `DELETE` удаляет | своего эндпоинта нет |

На двух деталях спотыкаются чаще всего. У Single Type вообще нет `POST`: `PUT /api/homepage` создаёт запись в первый раз и обновляет её при всех следующих вызовах. А вот `DELETE` у него есть — документация перечисляет его рядом с `GET` и `PUT`.

Component не может существовать сам по себе. Его схема лежит в `src/components/<категория>/`, а до API он доходит только как поле того Content Type, который его включает. Пометьте это поле `repeatable: true`, и оно станет массивом компонентов одного типа.

**Q: Что такое Dynamic Zone и когда её использовать?**

Dynamic Zone — массив компонентов разных типов. Позволяет редактору собирать страницу из блоков в любом порядке. Каждый элемент содержит `__component` поле для идентификации типа.

```javascript
// schema.json:
"sections": {
  "type": "dynamiczone",
  "components": ["sections.hero", "sections.faq", "sections.cta"]
}

// API response:
"sections": [
  { "__component": "sections.hero", "title": "Welcome" },
  { "__component": "sections.faq", "items": [...] }
]

// Использовать когда:
// ✓ Marketing/Landing pages с гибкой структурой
// ✓ Page Builder для редакторов
// ✓ Разные страницы имеют разный набор блоков
// ✗ Когда структура фиксированная — Component проще
```

**Q: Чем Draft & Publish важен для production?**

Draft & Publish позволяет редакторам работать с контентом без немедленной публикации. `publishedAt === null` → Draft (не видно через публичный API). `publishedAt !== null` → Published. Public API по умолчанию возвращает **только** Published записи. Draft видны только в Admin Panel или через Admin API token. Важно для контент-команд: редактор готовит материал, старший редактор утверждает и публикует.

## Группа 3: Кастомизация — Routes, Controllers, Services

**Q: Как добавить кастомный endpoint в Strapi?**

Кастомный эндпоинт — это три небольших куска в трёх файлах. Route объявляет URL, метод контроллера обрабатывает запрос, а метод сервиса делает саму работу. Route пишут в собственном файле в `src/api/<name>/routes/`, отдельно от сгенерированного core route. Строка `handler` связывает куски между собой: `'article.popular'` означает метод `popular` контроллера `article`.

Две настройки в конфиге маршрута стоит знать до того, как читать код. Маршруты по умолчанию требуют аутентификации, поэтому публичным этот эндпоинт делает именно `config: { auth: false }`. Фабрики `createCoreController` и `createCoreService` сохраняют пять сгенерированных действий: `find`, `findOne`, `create`, `update` и `delete`. Ваш собственный метод встаёт рядом с ними и ничего не заменяет.

```typescript
// 1. Создать route в отдельном файле (не в core route):
// src/api/article/routes/custom-article.ts
export default {
  routes: [{
    method: 'GET',
    path: '/articles/popular',
    handler: 'article.popular',
    config: { auth: false }, // публичный
  }],
};

// 2. Добавить метод в Controller:
// src/api/article/controllers/article.ts
export default factories.createCoreController('api::article.article', ({ strapi }) => ({
  async popular(ctx) {
    const articles = await strapi.service('api::article.article').findPopular();
    return this.transformResponse(articles);
  },
}));

// 3. Добавить метод в Service:
export default factories.createCoreService('api::article.article', ({ strapi }) => ({
  async findPopular() {
    return strapi.documents('api::article.article').findMany({
      filters: { publishedAt: { $notNull: true } },
      sort: { views: 'desc' },
      pagination: { limit: 10 },
    });
  },
}));
```

**Q: Зачем sanitizeOutput и почему его нельзя пропустить?**

`sanitizeOutput` убирает из ответа поля на которые у текущего пользователя нет прав (согласно RBAC). Без него кастомный контроллер может вернуть чувствительные данные (email, password hash, internal fields) публичному endpoint. Стандартные CRUD методы делают это автоматически. В кастомных методах нужно вызывать явно: `await this.sanitizeOutput(entity, ctx)` перед `this.transformResponse()`.

**Q: Document Service vs Query Engine — когда что использовать?**

Document Service используйте почти всегда, а Query Engine берите, только когда точно понимаете зачем. Документация формулирует это прямо: в большинстве случаев Query Engine брать не надо, нужен Document Service.

Document Service — верхний слой, и он понимает собственные структуры Strapi: компоненты, динамические зоны, черновые и опубликованные версии, локали. Query Engine лежит под ним и работает напрямую со строками базы, поэтому ни о чём из этого он не знает.

| | Document Service | Query Engine |
|---|---|---|
| Вызов | `strapi.documents('api::article.article')` | `strapi.db.query('api::article.article')` |
| Работает с | структурами контента Strapi | строками базы и соединениями таблиц |
| Draft & Publish | понимает и фильтрует сам | игнорирует |
| Локали | понимает | игнорирует |
| Компоненты, динамические зоны | понимает | не знает о них |
| Подтягивание связей | вложенные связи поддержаны | вручную |
| Идентификатор | `documentId` | числовой `id` |
| Когда брать | обычное чтение и запись, примерно 90% кода | сложные кастомные запросы и агрегация |

Чего не делает ни один из них — не убирает поля, которые вызывающему видеть не положено. Document Service это слой доступа к данным, он не знает, кто спрашивает, и вернёт приватные поля. Встроенные маршруты REST и GraphQL вычищают ответ сами. Кастомный контроллер, который зовёт Document Service напрямую, обязан сделать это руками.

## Группа 4: Безопасность — Policies, Middleware, RBAC

**Q: Чем Policy отличается от Middleware в Strapi?**

Policy решает, пропустить запрос или нет. Middleware меняет то, как выглядит запрос или ответ. В этом вся разница, и из неё понятно, почему документация называет policy шагом проверки, который ничего не меняет.

Policy может закрыть маршрут, но переписывать запрос — не её работа. Middleware оборачивает всю остальную цепочку и может действовать и до неё, и после, потому что сама решает, когда вызвать `await next()`.

| | Policy | Middleware |
|---|---|---|
| Назначение | пропустить запрос или отклонить | обработать и преобразовать запрос или ответ |
| Сигнатура | `(policyContext, config, { strapi })` | `(context, next)` |
| Пропускает дальше | возвращая `true` либо не возвращая ничего | вызывая `await next()` |
| Останавливает | возвращая `false` | вернув управление, не вызвав `next()` |
| Область действия | вешается на маршрут через `config.policies` | глобальная на весь сервер либо один маршрут |
| Видит обработчик | да, и пользователя в `ctx.state.user` | нет |

Порядок важен при отладке. Первыми отрабатывают глобальные middleware — ещё до того, как запрос сопоставлен с маршрутом. Только потом Strapi доходит до policies и middleware самого маршрута, а за ними до контроллера. На обратном пути ответ проходит через middleware маршрута и глобальные middleware.

Если вы знаете NestJS, то policy — это его Guard. Если знаете Koa или Express, то middleware в Strapi — та же идея, с луковичной формой, которую Koa даёт и так.

**Q: Какие есть типы авторизации в Strapi?**

Их три, и каждый рассчитан на своего клиента: конечные пользователи, машины и люди, которые работают в Admin Panel. Выбор не того типа — обычная причина того, что токен внезапно перестаёт работать.

1. **JWT (JSON Web Token) для конечных пользователей.** Это плагин Users & Permissions. Пользователь логинится запросом `POST /api/auth/local` и получает в ответ поля `jwt` и `user`. Дальше токен едет в заголовке `Authorization: Bearer <jwt>`, а что пользователю разрешено, определяет его роль — Public или Authenticated.
2. **API Token для машинных клиентов.** Создаётся в Admin Panel в разделе Settings и не привязан ни к какому аккаунту. Токен бывает Read-only, Full access или Custom. Custom выдаётся на конкретный тип контента и конкретное действие, а Read-only умеет вызывать только `find` и `findOne`. Срок жизни выбирается из четырёх вариантов: 7, 30, 90 дней или без ограничения. Едет он в том же заголовке `Authorization: Bearer`.
3. **Admin Session для пользователей Admin Panel.** Администратор входит по почте и паролю и получает сессию. Дальше его доступом управляет отдельный слой ролевой модели со своими подробными правами. Этот слой решает, кому можно править тип контента, а не кому можно читать `/api/articles`.

Между первыми двумя выбирайте по тому, у кого лежит секрет. JWT принадлежит человеку и выдаётся при логине, а сервер, который рендерит страницу, залогиниться ни за кого не может. API Token принадлежит вашему развёрнутому приложению — поэтому он и подходит для серверного запроса из Next.js или для сборочного конвейера.

## Группа 5: Lifecycle Hooks и автоматизация

**Q: Когда использовать Lifecycle Hook вместо Service?**

Lifecycle hook берут, когда что-то должно происходить при каждой записи в модель — каким бы кодом эта запись ни была сделана. Service берут, когда это кусок бизнес-логики, который кто-то вызывает осознанно.

Хук живёт в файле `src/api/<name>/content-types/<name>/lifecycles.ts`. Срабатывает он на парных событиях модели: `beforeCreate` и `afterCreate`, `beforeUpdate` и `afterUpdate`, `beforeDelete` и `afterDelete`. Есть и события чтения — например, `beforeFindMany`.

Хороший повод взять lifecycle hook:

- Автоматически заполнить поле перед сохранением — например, slug или permalink.
- Аудит: писать строку в лог на каждую операцию с моделью.
- Сбрасывать кеш при изменении записи.
- Валидация на уровне данных, например проверка зависимостей в `beforeDelete`.

А что вместо этого стоит положить в сервис:

- Бизнес-логика, которую хочется читать, переиспользовать и тестировать отдельно.
- Агрегация, расчёты и правила.
- Общение с внешними системами.
- Всё, что должны уметь вызвать контроллер, cron job или другой сервис.

За обоими списками стоит одно правило — видимость. Хук не виден с места вызова, поэтому сложная логика, спрятанная в нём, плохо читается и плохо тестируется. А вызов внешнего API из хука превращает каждое сохранение в побочный эффект, которого никто не просил.

Держать хуки тонкими стоит и по второй причине. Они работают на собственном слое данных Strapi, и код, который идёт мимо этого слоя, их не запускает. Обычный способ незаметно потерять хуки — обратиться к построителю запросов knex напрямую.

**Q: Как избежать дублирования Cron Job при horizontal scaling?**

Каждый инстанс поднимает всё приложение целиком, вместе с его cron job. При трёх инстансах за балансировщиком ночная задача отработает три раза. Решение всегда одной формы: либо дать инстансам общий предмет, за который они конкурируют, либо вообще унести задачу от них.

Три способа получить ровно один запуск:

- **Распределённая блокировка в Redis.** Перед выполнением задачи инстанс берёт блокировку с TTL (time to live — срок, после которого она снимается сама). Работу делает только тот инстанс, который блокировку получил, а срок не даёт упавшему инстансу держать её вечно.
- **Отдельный воркер.** Унести cron из веб-инстансов в собственный процесс или в запускаемую по расписанию функцию, работающую в единственном экземпляре.
- **Очередь задач.** Положить задачу в очередь вроде BullMQ и держать на ней ровно один воркер.

**Q: Что такое bootstrap в src/index.ts и зачем он нужен?**

`bootstrap` — это функция, которую Strapi вызывает один раз при каждом старте сервера. Она отрабатывает после того, как приложение полностью настроилось, и до того, как серверная часть начнёт слушать порт. В этом моменте весь смысл. К нему у вас уже есть полный объект `strapi`, поэтому можно ходить в базу, подписываться на события и регистрировать cron job.

Рядом `src/index.ts` экспортирует вторую функцию, `register`, и подменять одну другой нельзя. Функция `register` — самое первое, что происходит при старте приложения Strapi, ещё до всякой настройки. Там пока нет ничего: ни базы, ни маршрутов, ни политик.

| | `register` | `bootstrap` |
|---|---|---|
| Когда работает | первым, до всякой настройки | после настройки, до старта сервера |
| Что доступно | почти ничего | полный объект `strapi` |
| Для чего | кастомные поля, провайдеры, расширения плагинов | заполнение данными, подписки, cron job |

Пример ниже создаёт категорию по умолчанию при первом запуске. Это работа ровно для `bootstrap`: она лезет в базу, а значит, в `register` жить не может.

```typescript
// bootstrap вызывается один раз при старте Strapi после загрузки плагинов
export default {
  async bootstrap({ strapi }) {
    // Подписаться на события
    strapi.eventHub.on('entry.create', handler);

    // Seed данные при первом запуске
    const count = await strapi.documents('api::category.category').count({});
    if (count === 0) {
      await strapi.documents('api::category.category').create({
        data: { name: 'General' },
      });
    }

    // Зарегистрировать Cron Jobs
    // Настроить внешние connections
  },

  register({ strapi }) {
    // Вызывается ДО bootstrap, ДО загрузки плагинов
    // Регистрировать кастомные providers, поля, расширения
  },
};
```

## Группа 6: Интеграция и production

**Q: Как правильно соединить Next.js с Strapi?**

На сервере используйте API Token, а не JWT пользователя. Серверу не за кого логиниться. Токен, созданный в Admin Panel, принадлежит развёрнутому приложению, а не человеку. Держите его в переменной окружения, читайте только в серверном коде и отправляйте в заголовке `Authorization: Bearer`.

Все вызовы стоит завернуть в один типизированный помощник, а не раскидывать `fetch` по приложению. Помощник ниже собирает адрес из `STRAPI_URL`, добавляет токен и бросает ошибку, когда ответ неуспешен. Сломанные данные до компонента не доходят.

Вторая половина примера — про то, как остаться быстрым и не отдавать устаревшее. ISR (incremental static regeneration — инкрементальная статическая регенерация) отдаёт каждому посетителю заранее отрисованную страницу. Когда странице становится больше `revalidate` секунд — в примере это час — следующий запрос всё равно получит копию из кеша. Next.js пересобирает страницу в фоне и дальше отдаёт уже свежую.

Если ждать час нельзя, добавьте ревалидацию по требованию. Webhook из Strapi дёргает маршрут вашего приложения Next.js в момент публикации, и этот маршрут сбрасывает кеш нужного пути.

```typescript
// Серверная сторона Next.js — использовать API Token (не JWT):
// - API Token не истекает при перезапуске сервера
// - Не нужна сессия пользователя на сервере

// next.config.js: env.STRAPI_API_TOKEN (Full-access или Custom)

// lib/strapi.ts:
async function fetchStrapi<T>(endpoint: string, options?: RequestInit): Promise<T> {
  const res = await fetch(`${process.env.STRAPI_URL}/api/${endpoint}`, {
    headers: {
      'Authorization': `Bearer ${process.env.STRAPI_API_TOKEN}`,
      'Content-Type': 'application/json',
    },
    ...options,
  });

  if (!res.ok) throw new Error(`Strapi error: ${res.status}`);
  return res.json();
}

// ISR (Incremental Static Regeneration) + Webhook для инвалидации:
// Strapi Webhook → POST /api/revalidate → next.revalidatePath()
export async function getStaticProps() {
  const data = await fetchStrapi('articles?populate=*');
  return { props: { articles: data.data }, revalidate: 3600 };
}
```

**Q: Что нужно для production деплоя Strapi?**

Каждый пункт ниже следует из одного факта: Strapi — это долгоживущий сервер на Node.js, у которого есть состояние. Ему нужна база, которую можно разделить между инстансами, место для загруженных файлов вне диска самого контейнера и процесс, который не умирает между запросами.

- **База данных.** Strapi поддерживает SQLite 3, MySQL 8.0+, MariaDB 10.3+ и PostgreSQL 14.0+. Для production берите PostgreSQL. База SQLite — это один файл на локальном диске инстанса. Два инстанса не могут делить этот файл, а на эфемерном хостинге его сотрёт очередной деплой.
- **Загрузка файлов.** Провайдер по умолчанию хранит файлы локально на сервере, и проблема здесь ровно та же. Переключитесь на официального провайдера поверх объектного хранилища: Amazon S3 (Simple Storage Service) или Cloudinary.
- **Переменные окружения.** Сгенерированный `.env` описывает `APP_KEYS`, `API_TOKEN_SALT`, `ADMIN_JWT_SECRET`, `TRANSFER_TOKEN_SALT` и `JWT_SECRET`, плюс группу `DATABASE_*`. `APP_KEYS` — это список через запятую, и в сгенерированном файле в нём четыре значения. Добавьте то, что нужно вашему хранилищу: ключ доступа, секрет и имя бакета.
- **Хостинг.** Руководства Strapi по деплою покрывают Strapi Cloud, AWS (Amazon Web Services), Azure, DigitalOcean App Platform и Heroku. Там же советуют pm2, чтобы процесс не падал. Платформа вокруг короткоживущих serverless-функций для Strapi не той формы — поэтому на Vercel живёт фронтенд на Next.js, а не бэкенд на Strapi.
- **Admin Panel и схема.** Content-Type Builder доступен только в среде разработки. В production тип контента меняют правкой `schema.json`: закоммитить и задеплоить, как любой другой код.
- **CORS (cross-origin resource sharing — доступ к ресурсу с другого источника).** Настраивается в `config/middlewares.ts`, в записи `strapi::cors`. Параметр `origin` по умолчанию равен `*`. В production поставьте туда список тех источников фронтенда, которые вы действительно обслуживаете.

**Q: Strapi v4 vs v5 — главные различия?**

Разница, с которой вы сталкиваетесь каждый день, — форма ответа. Пятая версия убрала обёртку `attributes`, и поля записи лежат прямо на ней. Глубже лежит идентификатор: у каждого документа в v5 есть постоянный строковый `documentId` рядом с числовым `id`, и маршруты REST адресуют документы именно по `documentId`.

Вместе с этим сменился и вызываемый API. Entity Service из v4, то есть `strapi.entityService`, уступил место Document Service — `strapi.documents(...)`. В том же релизе переработали Draft & Publish, и у Document Service появились методы `publish`, `unpublish` и `discardDraft`.

Блок ниже держит обе формы рядом. Половину про v4 читайте как историю, а не как то, что стоит копировать в новый проект.

```txt
Strapi v4 (старый):
  Entity Service API: strapi.entityService.findMany(...)
  Ответ: { data: [{ id, attributes: { title, ... } }] }

Strapi v5 (новый, 2024):
  Document Service API: strapi.documents('api::...').findMany(...)
  Ответ: { data: [{ id, documentId, title, ... }] }
  ↑ нет вложенного attributes, в отличие от v4
  documentId: строковый ID (вместо числового id в v4)
  Draft & Publish улучшен: версионирование

Критично при интеграции:
  v4: data.attributes.title
  v5: data.title  ← прямой доступ
```
