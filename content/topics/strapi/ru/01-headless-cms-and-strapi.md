# Headless CMS и Strapi

## Что такое Headless CMS

CMS (content management system) — это система управления контентом: приложение, в котором редакторы создают и публикуют материалы сайта, не трогая код. Традиционные системы вроде WordPress и Drupal объединяют backend и frontend в одном приложении.

Контент хранится в базе данных, а страницы собираются на сервере из шаблонов на PHP (языке, на котором написаны оба движка). Frontend поэтому жёстко привязан к конкретной CMS.

Headless CMS убирает "голову" — presentation layer, слой отображения. Остаётся только управление контентом и API. Frontend (React, Next.js, мобильное приложение) сам решает, как отображать данные.

```txt
Traditional CMS:                Headless CMS (Strapi):
──────────────────              ──────────────────────────────────
Editor                          Editor
  ↓                               ↓
WordPress/Drupal                Strapi Admin
  ↓                               ↓
PHP Templates                   REST API / GraphQL
  ↓                               ↓
HTML → Browser                  React / Next.js / Mobile / TV App
                                (каждый клиент рендерит сам)
```

## Что такое Strapi

Strapi — это open-source headless CMS на Node.js, где за HTTP-слой отвечает Koa.js. Вы описываете модели данных, которые в Strapi называются Content Types, и по этому описанию Strapi собирает работающее приложение. Два из собранных кусков — это два API над одними и теми же данными: REST (representational state transfer) и GraphQL. Ничего из списка ниже писать руками не нужно:

- REST API и GraphQL API
- Admin Panel для управления контентом
- RBAC (role-based access control, доступ по ролям)
- Media upload во внешнее хранилище: Amazon Simple Storage Service (S3) или Cloudinary
- Webhooks

Всё это выдаёт стек из пяти частей:

- **Node.js вместе с Koa.js** — HTTP-сервер, который принимает запросы.
- **`@strapi/database`** — ORM (object-relational mapper), слой, который превращает вызовы методов в запросы к базе. Работает с SQLite, PostgreSQL и MySQL.
- **Admin Panel на React** — frontend, встроенный в тот же процесс; именно в него заходят редакторы.
- **Content-Type Builder** — GUI (graphical user interface), графический редактор схем. Доступен только в режиме разработки.
- **Plugin system** — точка расширения: i18n (internationalization, интернационализация), GraphQL, email и другое.

## REST API из коробки

Как только вы сохранили Content Type, Strapi строит для него полный набор HTTP-эндпоинтов, и роутинг писать не нужно вообще. Тип с именем Article получает пять эндпоинтов по адресу `/api/articles`: список, одна запись, создание, обновление, удаление. Эндпоинты на чтение принимают параметры запроса, которые заменяют код, написанный руками:

- `filters` сужает выборку до записей, подходящих под условие.
- `sort` задаёт порядок.
- `pagination` режет результат на страницы.
- `populate` подтягивает в ответ связанные записи, например автора статьи.

У любого ответа два ключа верхнего уровня. Ключ `data` несёт записи, а `meta` — счётчики пагинации. У каждой записи виден числовой `id`, строковый `documentId` и её собственные поля прямо на ней. Strapi v5 отдаёт поля плоско, а версия 4 заворачивала их в объект `attributes`.

```typescript
// После создания Content Type "Article" Strapi генерирует:
// GET    /api/articles                — список статей
// GET    /api/articles/:id            — одна статья
// POST   /api/articles                — создать
// PUT    /api/articles/:id            — обновить
// DELETE /api/articles/:id            — удалить

// Запрос с фильтрацией, сортировкой, пагинацией, populate:
// GET /api/articles?
//   filters[category][name][$eq]=Tech&
//   sort[0]=publishedAt:desc&
//   pagination[page]=1&
//   pagination[pageSize]=10&
//   populate[author][fields][0]=name&
//   populate[author][fields][1]=avatar

// Ответ (Strapi v5: без обёртки "attributes", documentId рядом с id):
{
  "data": [
    {
      "id": 1,
      "documentId": "hgv1vny5cebq2l3czil1rpb3",
      "title": "Getting Started with Strapi",
      "publishedAt": "2024-01-15T10:00:00.000Z",
      "author": {
        "id": 5,
        "documentId": "znrlzntu9ei5onjvwfaalu2v",
        "name": "Alice",
        "avatar": "..."
      }
    }
  ],
  "meta": {
    "pagination": { "page": 1, "pageSize": 10, "total": 42, "pageCount": 5 }
  }
}
```

## Strapi vs традиционный NestJS/Express

Strapi и написанный руками сервис на NestJS или Express отвечают на разные вопросы, поэтому сравнение идёт про цену, а не про качество. Strapi отдаёт вам работающий API и интерфейс редактора за минуты, но взамен вы остаётесь внутри того, что позволяют плагины. Ручной сервис стоит часов или дней до первого ответа эндпоинта, зато в нём не зафиксировано ничего.

Читайте таблицу ниже как список разменов. Каждая строка называет то, что одна сторона даёт даром, а вторая берёт за это плату.

| Критерий | Strapi | NestJS/Express |
|---|---|---|
| Время до первого API | Минуты, в Content-Type Builder | Часы или дни ручного кода |
| Кастомизация | Ограничена плагинами | Полная свобода |
| Бизнес-логика | Через хуки и кастомные routes | Нет ограничений |
| Масштабируемость | Средняя, это монолит | Высокая, вплоть до микросервисов |
| Admin Panel | Встроена | Нужно строить |
| RBAC | Встроен | Нужно строить |
| Подходит для | Контентные сайты, маркетинг, каталоги | Любая сложная логика |
| Не подходит для | High-load, сложный домен | Простой контентный сайт (overkill) |

## Когда выбирать Strapi

Решение сводится к одному вопросу: где в вашем проекте тяжёлая часть — в контенте или в правилах? Strapi подходит там, где редакторы каждый день меняют тексты и картинки, а сервер в основном отдаёт эти записи обратно. Он перестаёт быть верным инструментом, когда ценность лежит в логике: расчёт цены, взаиморасчёты, маршруты согласования.

Такому коду нужно жить там, где Strapi им не владеет, и запихивание его в хуки портит обе половины. Два списка ниже покрывают большинство реальных случаев.

**Strapi — хороший выбор для:**

- Маркетинговых и корпоративных сайтов.
- Блогов и новостных порталов.
- Каталогов интернет-магазина — именно данных о товарах, а не платёжной логики.
- Бэкенда мобильного приложения с простыми операциями создания, чтения, обновления и удаления.
- MVP (minimum viable product), то есть минимально жизнеспособного продукта, где API нужен быстро.
- Команд, в которых есть редакторы без опыта разработки.

**Strapi — плохой выбор для:**

- Сложной бизнес-логики: трейдинг, банковские операции, ERP (enterprise resource planning) — системы управления ресурсами предприятия.
- Высокой нагрузки. Выше примерно 10k запросов в секунду Strapi горизонтально масштабируется тяжело.
- Микросервисов, потому что Strapi — монолит.
- Проектов, которым нужен полный контроль над схемой базы данных.
- Нестандартной авторизации.

## Типичные ошибки на интервью

- **"Strapi заменяет NestJS"** — нет. Strapi — CMS для управления контентом. NestJS — фреймворк для создания любых Node.js приложений. Strapi использует Koa внутри и не является альтернативой NestJS/Express для сложной бизнес-логики.

- **"Headless CMS не имеет admin panel"** — нет. "Headless" означает что нет публичного frontend (presentation layer). Admin Panel для редакторов — есть. Strapi включает полноценный интерфейс администратора, написанный на React. "Headless" = нет шаблонизации для конечных пользователей.

- **"Strapi работает только с REST"** — нет. Strapi поддерживает GraphQL через официальный плагин `@strapi/plugin-graphql`. После установки плагина автоматически генерируются queries, mutations и subscriptions для всех Content Types.

- **"Content Types в Strapi можно создавать в production"** — нет. Content-Type Builder доступен только в development mode. В production изменения схемы делаются через код (schema files в `src/api/`) и деплоятся как обычный код. Это принципиально важно для стабильности production.

- **"Strapi v4 и v5 — одно и то же"** — нет. Strapi v5 (2024) — крупный breaking change: новый Document Service API вместо Entity Service, новый query engine, улучшенная типизация. API ответы имеют другую структуру (убраны вложенные `attributes`). Важно уточнять версию в разговоре об API структуре.
