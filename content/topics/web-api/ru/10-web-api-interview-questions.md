# Web API: вопросы для интервью

## Как пользоваться этой шпаргалкой

Каждый ответ ниже — сжатая версия того, что подробно разобрано в
статьях этой темы. Часть вопросов пересекается по теме с банком
Browser / JS Runtime, но задана под другим углом: там разбирают
устройство возможности, здесь — то, что о ней чаще всего спрашивают
на собеседовании и куда разговор идёт дальше.

## Группа 1: модель платформы и условия доступа

**1. Почему у Web API нет `import`, а есть `window` и `navigator`?**

Потому что это не библиотека, которую ставят, а часть уже запущенной
среды. Браузер создаёт `window` и `navigator` для каждой вкладки сам,
и оба объекта существуют до того, как выполнилась хоть одна строка
вашего кода.

```ts
console.log(typeof navigator.clipboard); // 'object' — уже готов
```

**2. Какие условия может требовать одна и та же возможность
одновременно?**

Источник (origin), безопасный контекст и жест пользователя
складываются, а не выбираются по одному. Точная геолокация, например,
требует сразу двух: безопасного контекста и отдельного разрешения.

| возможность | что требует |
|---|---|
| `Service Worker` | только безопасный контекст |
| запись в буфер обмена | только жест |
| точная геолокация | безопасный контекст и разрешение |

**3. Как проверить, доступна ли возможность, не завязываясь на
конкретный браузер?**

Спросить у объекта напрямую — `'clipboard' in navigator` — вместо
разбора строки `User-Agent`. Проверка по имени браузера устаревает в
момент, когда любой из движков меняет поведение, а факт наличия
объекта — нет.

## Типичные уточняющие вопросы (группа 1)

```txt
«Что если возможность есть в navigator, но не работает?» →
скорее всего не выполнено одно из условий: контекст,
источник или жест — сам факт наличия объекта этого не проверяет

«Почему Promise, а не готовое значение?» → за вызовом
почти всегда диалог для человека или обращение к ОС,
и оба не отвечают мгновенно
```

## Группа 2: наблюдатели

**4. В каком порядке сработают колбэк `MutationObserver` и колбэк из
`setTimeout(0)`, если оба запланированы в одном синхронном блоке?**

`MutationObserver` — раньше: он выполняется как микрозадача сразу
после текущего кода, а `setTimeout` ждёт следующего макротаска.

```txt
sync-end → microtask → mutationobserver → setTimeout0 → rAF
снято тем же стендом на Chromium 153 через Playwright
```

`ResizeObserver` и `IntersectionObserver` идут ещё позже — они
привязаны не к микрозадачам, а к шагу рендеринга, ближе к кадру.

**5. Почему забытый наблюдатель — это утечка, а не просто лишний
код?**

Наблюдатель держит ссылку на элемент до вызова `disconnect()` или
`unobserve()`, и эта ссылка не даёт элементу освободиться, даже если
он давно удалён из разметки страницы. Симптом на практике — колбэк
продолжает стрелять для списка, которого в интерфейсе уже нет.

## Типичные уточняющие вопросы (группа 2)

```txt
«Чем четыре наблюдателя отличаются по задаче?» →
видимость, размер, разметка, технические замеры —
у каждого своя, путать их — частая ошибка

«MutationObserver вызывается на каждое изменение?» →
нет, изменения копятся и приходят одним пакетом записей
```

## Группа 3: фоновые потоки и сервис-воркер

**6. Чем `Worker` отличается от `Service Worker` по времени жизни?**

`Worker` умирает вместе со страницей, которая его создала. `Service
Worker` живёт по правилам источника (origin) и продолжает
существовать, даже когда вкладок не осталось вовсе.

**7. Что произойдёт с `ArrayBuffer` на отправляющей стороне после
`postMessage(data, [buf])`?**

Он опустеет: `buf.byteLength` станет `0`, потому что данные не
скопированы, а переданы — память перешла в другой поток целиком.

```ts
worker.postMessage({ buf }, [buf]);
console.log(buf.byteLength); // 0 — проверено тем же стендом
```

Без списка передачи вторым аргументом сработал бы обычный
`structuredClone`, и исходный буфер остался бы нетронутым.

**8. Сервис-воркер в состоянии `activated`, но
`navigator.serviceWorker.controller` — `null`. Это баг?**

Нет, часть спецификации: страница, вызвавшая `register()`, не
получает нового контроллера, пока не перезагрузится сама. Первая
регистрация активирует сервис-воркер, но не подменяет поведение сети
у уже открытой вкладки посреди её работы.

## Типичные уточняющие вопросы (группа 3)

```txt
«Что видно изнутри Worker и Service Worker?» → self, fetch,
IndexedDB — да; window, document, localStorage — нет ни в одном

«Как заставить сервис-воркер взять контроль сразу?» →
skipWaiting() в install и clients.claim() в activate
```

## Группа 4: хранилища и связь между вкладками

**9. Почему `localStorage` — плохой выбор для автосохранения на
каждое нажатие клавиши?**

Потому что он синхронный: `setItem` не возвращает управление, пока
не запишет на диск, и при частом вызове эта задержка накапливается.
`IndexedDB` устроена иначе — `open()` сразу отдаёт объект запроса, а
не блокирует код в ожидании данных.

**10. Вкладка A вызвала `localStorage.setItem`. Какие вкладки получат
событие `storage`?**

Все вкладки того же источника, кроме самой вкладки A — событие не
приходит инициатору изменения. Точно так же ведёт себя
`BroadcastChannel`: отправитель никогда не слышит собственное
сообщение.

```ts
notesChannel.postMessage({ type: 'note-updated' });
// в этой же вкладке notesChannel.onmessage не вызовется
```

**11. Почему `BroadcastChannel` и `localStorage` не годятся для
мьютекса между вкладками?**

Потому что это каналы сообщений, а не арбитр: между проверкой флага
«свободно» и его установкой есть окно, в которое могут одновременно
попасть две вкладки. `Web Locks` устраняет это окно — блокировку даёт
браузер, а не самодельный протокол поверх сообщений.

## Типичные уточняющие вопросы (группа 4)

```txt
«Какое хранилище видит сервис-воркер?» → IndexedDB и
Cache Storage — да, localStorage и sessionStorage — нет

«Что вернёт navigator.storage.estimate()?» → приблизительные

```

## Группа 5: файлы, буфер обмена, потоки

**12. Чем ручка File System Access отличается от объекта `File` из
`<input>`?**

`File` из `<input>` одноразовый: без нового диалога тот же файл не
прочитать. Ручка `FileSystemFileHandle` переживает сессию — её можно
сохранить и запросить разрешение заново в следующий раз, не показывая
пользователю диалог выбора повторно.

**13. Почему чтение буфера обмена и запись в него подчиняются разным
правилам?**

Запись расценивается как менее рискованная: обычно хватает жеста
человека. Чтение может раскрыть чужие данные, случайно оказавшиеся в
буфере, поэтому оно дополнительно требует разрешения `clipboard-read`,
а не одного лишь клика.

**14. Что произойдёт с уже обработанными данными, если оборвать
`pipeTo` сигналом посередине конвейера?**

Они останутся как есть: источник получит `cancel()` с причиной
отмены, но всё, что уже дошло до `WritableStream`, никуда не
денется. Отмена останавливает то, что не успело, а не откатывает то,
что уже случилось.

```ts
await readable.pipeTo(writable, { signal });
// после abort('cancelled') — уже записанные чанки остаются записанными
```

## Типичные уточняющие вопросы (группа 5)

```txt
«Что такое обратное давление (backpressure)?» → взаимное
ожидание шагов конвейера: быстрый источник не обгоняет
медленного потребителя

«Зачем URL.revokeObjectURL, если сборщик мусора и так
есть?» → сборщик не знает про blob-адрес сам по себе,
без явного revoke файл остаётся в памяти
```

## Группа 6: жизненный цикл и разрешения

**15. Почему `unload` — плохое место для финального сохранения
данных?**

Он не гарантирует срабатывание — мобильный браузер может закрыть
вкладку, не дождавшись его, — а сама подписка на `unload` отключает
кэш обратного перехода (bfcache) для страницы. `visibilitychange` на
переход в `hidden` работает надёжнее и не портит bfcache.

**16. Чем состояние `prompt` у `navigator.permissions.query`
отличается от `'default'` у `Notification.requestPermission()`?**

Ничем по смыслу — оба означают «разрешение ещё не спрашивали». Это
два разных API для одной и той же возможности, и они называют одно и
то же состояние разными строками — источник частой путаницы в коде,
который сравнивает состояние напрямую.

**17. Что означает `pageshow` с `persisted: true`?**

Страница поднята из bfcache, а не загружена заново: скрипты не
перезапускались, и JavaScript-состояние осталось таким же, каким было
в момент ухода. Данные при этом могут устареть — сервер мог обновить
их, пока страница лежала в кэше, поэтому такой момент — повод
перепроверить их, а не просто обрадоваться быстрой загрузке.

## Типичные уточняющие вопросы (группа 6)

```txt
«Что отличает frozen от hidden?» → hidden — это видимость,
frozen — Chromium ставит фоновую вкладку на паузу для
экономии процессора, и другие браузеры делают это иначе

«Разрешение denied — как его вернуть?» → только через
настройки сайта в браузере, повторный запрос из кода
диалог не откроет
```
