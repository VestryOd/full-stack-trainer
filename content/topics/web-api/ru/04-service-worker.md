# Сервис-воркер — сетевой посредник, который живёт отдельно от страницы

Сервис-воркер, по-английски `Service Worker`, — это код, который
браузер ставит между страницей и сетью и который переживает закрытие
вкладки. В отличие от фонового потока из предыдущей статьи, он не
принадлежит одной странице: один сервис-воркер обслуживает все
вкладки в своей области действия и продолжает существовать, когда
вкладок не осталось вовсе.

## Сервис-воркер стоит между страницей и сетью, а не в её потоке

`Worker` умирает вместе со страницей, которая его создала, а
сервис-воркер живёт по правилам источника (origin), а не одной
вкладки.

| | `Worker` | `Service Worker` |
|---|---|---|
| кто создаёт | одна страница | регистрация на весь источник (origin) |
| с кем говорит | только со своей страницей | со всеми вкладками своей области действия |
| время жизни | закрылась вкладка — исчез | браузер может остановить и разбудить снова |
| видит сеть | нет | перехватывает запросы через событие `fetch` |

Событие `fetch` — то, чего нет ни у одного другого потока в этой
теме. Сервис-воркер может ответить на запрос из кеша, изменить его
или отправить в сеть как есть, и страница даже не узнает, что запрос
прошёл через посредника.

## Жизненный цикл проходит через состояния по порядку

Прежде чем начать перехватывать запросы, сервис-воркер проходит
несколько состояний подряд, и пропустить их нельзя.

```txt
             Пять состояний одного сервис-воркера
┌───────────────────────────────────────────────────┐
│ installing: выполняется обработчик install        │
└───────────────────────────────────────────────────┘
                          │
                          ▼
┌───────────────────────────────────────────────────┐
│ installed / waiting: ждёт закрытия старых вкладок │
└───────────────────────────────────────────────────┘
                          │  skipWaiting() пропускает ожидание
                          ▼
┌───────────────────────────────────────────────────┐
│ activating: выполняется обработчик activate       │
└───────────────────────────────────────────────────┘
                          │
                          ▼
┌───────────────────────────────────────────────────┐
│ activated: перехватывает запросы новых вкладок    │
└───────────────────────────────────────────────────┘
waiting возникает, только если есть старый активный сервис-воркер
```

```ts
// sw.js — минимальный сервис-воркер: сам по себе ничего не кеширует
self.addEventListener('install', (event) => {
  console.log('installing');
});

self.addEventListener('activate', (event) => {
  console.log('activating');
});
```

Состояние `waiting` — не пауза по умолчанию, а защита: браузер не
подставит новую версию под вкладки, которые ещё держат открытой
старую. Полный разбор `skipWaiting()`, `clients.claim()` и
версионирования кеша при деплое — тема Browser / JS Runtime, банк
вопросов про жизненный цикл сервис-воркера и деплой без простоя.

## Область действия решает, какие запросы увидит сервис-воркер

Область действия, по-английски `scope`, — это префикс пути, за
пределы которого сервис-воркер не видит ни одного запроса. По умолчанию она
равна папке, где лежит файл сервис-воркера.

```ts
// Регистрация из корня — сервис-воркер обслуживает ленту заметок целиком
await navigator.serviceWorker.register('/sw.js');
console.log((await navigator.serviceWorker.ready).scope);
// http://localhost:3000/
```

Попытка расширить область действия за пределы папки со скриптом
проваливается прямо на регистрации.

```txt
SecurityError: Failed to register a ServiceWorker for scope
('http://localhost:8934/') with script
('http://localhost:8934/scoped/sw2.js'): The path of the provided
scope ('/') is not under the max scope allowed ('/scoped/'). Adjust
the scope, move the Service Worker script, or use the
Service-Worker-Allowed HTTP header to allow the scope.
```

Сообщение снято тем же стендом на Playwright. Шире область действия
можно сделать только заголовком ответа `Service-Worker-Allowed` со
стороны сервера — переносом файла ограничение не обойти, если сервер
не отдаёт сервис-воркер из корня.

## Только что зарегистрированный сервис-воркер ещё не перехватывает запросы

Первая регистрация активирует сервис-воркер, но страница, с которой пришёл
вызов `register`, продолжает ходить в сеть напрямую до перезагрузки.

```ts
await navigator.serviceWorker.register('/sw.js');
await navigator.serviceWorker.ready;

console.log(!!navigator.serviceWorker.controller);
// false — даже после активации: сервис-воркер станет controller
// только для страниц, загруженных ПОСЛЕ регистрации
```

Это не баг и не гонка, а часть спецификации: страница, которая
привела к появлению сервис-воркера, не должна внезапно поменять поведение
сети посреди своей же работы. Офлайн-режим ленты заметок начнёт
работать только со второго открытия страницы, если не звать
`clients.claim()` в `activate`.

## Отладка живёт в DevTools, а не в консоли сервис-воркера

У сервис-воркера нет собственной вкладки, поэтому `console.log`
внутри него не появляется в обычной консоли страницы — он попадает в
консоль сервис-воркера в панели `Application` инструментов разработчика.

- **Галочка `Update on reload`.** Заставляет браузер ставить новую
  версию сервис-воркера при каждой перезагрузке, минуя обычные правила
  проверки на 24 часа.
- **Кнопка `Unregister`.** Снимает регистрацию совсем — полезно,
  когда старая версия сервис-воркера мешает проверить актуальную.
- **Флажок `Offline`.** Отключает сеть для вкладки, не трогая
  реальное соединение, — так проверяют офлайн-ветку без выключения
  Wi-Fi.

## Типичные ошибки

- **Ждать, что сервис-воркер заработает сразу после регистрации.**
  Симптом: офлайн-режим не срабатывает на первом открытии страницы,
  хотя `register()` отработал без ошибок.
- **Расширять область действия переносом файла сервис-воркера.** Симптом:
  регистрация падает с `SecurityError`, хотя путь к файлу выглядит
  правильным.
- **Держать открытой вкладку с DevTools и не глядеть в `Application`.**
  Симптом: логи из `install` и `activate` кажутся пропавшими, хотя
  сервис-воркер их печатает — просто не в ту консоль.
- **Путать `Service Worker` с обычным `Worker`.** Симптом: код ждёт,
  что сервис-воркер умрёт вместе со вкладкой, а он продолжает отвечать на
  запросы из другой вкладки того же источника.
