# Страница не всегда жива, а разрешение — не всегда получено

Вкладка с лентой заметок не переключается только между «открыта» и
«закрыта»: браузер скрывает её, замораживает в фоне и может держать
живой в специальном кэше даже после ухода на другой сайт. Разрешения
устроены так же не бинарно — у них три состояния, а не два, и
получить его можно только через явное действие человека, а не
проверкой кода.

## Страница проходит через состояния, которые вы не запрашивали

Свернуть вкладку, переключиться на другую или заблокировать экран
телефона — для браузера это разные, различимые в коде события.

```txt
Состояния страницы, которые вы не запрашивали
┌───────────────────────────────────────────────────┐
│ visible: вкладка на экране, всё как обычно        │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ hidden: document.visibilityState стал hidden      │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ frozen: браузер поставил фоновую вкладку на паузу │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ terminated, или страница жива в bfcache           │
└───────────────────────────────────────────────────┘
со шага hidden страница может вернуться в visible в любой момент
```

```ts
// Проверка текущего состояния в любой момент, без подписки
console.log(document.visibilityState); // 'visible' или 'hidden'
```

Состояние `frozen` — способ Chromium экономить процессор: у фоновой
вкладки останавливают таймеры и сетевые запросы, а `resume` сообщает,
что вкладку разморозили. Другие браузеры реализуют паузу фоновых
вкладок иначе, поэтому таймеры и опрос сервера стоит останавливать
уже на `hidden`, не дожидаясь `frozen`.

## `unload` не годится — вместо него `pagehide` или скрытие вкладки

Событие `unload` не гарантирует, что успеет сработать: мобильный
браузер может закрыть вкладку, не дожидаясь его, а сам факт подписки
на `unload` отключает браузеру кэш обратного перехода для этой
страницы.

```ts
// Так сохраняли черновик раньше — ненадёжно и вдобавок платит
// отключением bfcache для всей страницы
window.addEventListener('unload', () => saveDraftSync());
```

```ts
// Надёжная замена: сохраняем черновик, как только вкладку скрыли,
// а не ждём закрытия — на скрытии код гарантированно ещё жив
document.addEventListener('visibilitychange', () => {
  if (document.visibilityState === 'hidden') saveDraft(currentDraft);
});
```

`visibilitychange` на переходе в `hidden` срабатывает раньше, чем
браузер решит выгрузить страницу насовсем, и работает одинаково на
телефоне и на десктопе. Событие `pagehide` подходит для той же цели:
оно приходит при уходе со страницы независимо от того, попадёт ли
она в bfcache.

## Кэш обратного перехода хранит страницу живой, а не перезагружает её

Кэш обратного перехода, по-английски bfcache (back-forward cache), —
это снимок всей вкладки в памяти: скрипты не перезапускаются, а
JavaScript-состояние остаётся точно таким, каким было в момент ухода.

```ts
// pageshow сообщает, откуда пришла страница
window.addEventListener('pageshow', (e) => {
  if (e.persisted) {
    // страница поднята из bfcache: перепроверьте свежесть данных,
    // а не полагайтесь на то, что видели секунду назад
    revalidateNotesList();
  }
});
```

Обработчик `unload` — одна из причин, по которой страница не попадает
в bfcache вовсе: браузер не готов держать в памяти вкладку, которая
подписалась на событие, гарантированно ломающее такой снимок.
Открытые соединения вроде `IndexedDB`-транзакции в процессе записи —
другая частая причина отказа.

Поведение bfcache тяжело воспроизвести через автоматизированное
управление браузером: сами инструменты автоматизации нередко
отключают его. Проверяйте его в настоящем браузере руками, а не
только в тестах.

## Отдать главный поток можно простоем, а не своим таймером

`requestIdleCallback` планирует работу на момент, когда браузер сам
сочтёт себя свободным, — в отличие от `setTimeout`, который просто
ждёт назначенное время.

```ts
// Доразбор архива заметок из прошлой статьи: доедаем остаток
// между кадрами, а не одним блоком, который подвесит интерфейс
function processRemaining(deadline: IdleDeadline) {
  while (deadline.timeRemaining() > 0 && queue.length) {
    saveNote(queue.pop()!);
  }
  if (queue.length) requestIdleCallback(processRemaining);
}
requestIdleCallback(processRemaining);
```

Здесь `requestIdleCallback` — только способ не занимать главный поток
целиком, а не полноценный планировщик анимации. Как выбирать между
`requestAnimationFrame`, `requestIdleCallback` и другими способами
распределить работу по кадрам — тема Browser Animation.

## У разрешения три состояния, и проверить их можно не спрашивая

`navigator.permissions.query` сообщает текущее состояние, не
показывая пользователю никакого диалога — в отличие от вызова самой
возможности, который состояние заодно и меняет.

| состояние | что показывать |
|---|---|
| `granted` | функция уже включена, кнопки «Разрешить» не нужно |
| `prompt` | кнопка «Включить напоминания», которая запросит разрешение |
| `denied` | ссылка на настройки браузера — повторный запрос кода уже не откроет диалог |

```ts
// Свежая установка: у геолокации, уведомлений, камеры и чтения
// буфера обмена одно и то же начальное состояние
const s = await navigator.permissions.query({ name: 'notifications' });
console.log(s.state); // 'prompt' — снято тем же стендом, что и в первой статье темы
```

Заметный источник путаницы — `Notification.requestPermission()`
возвращает строку `'default'` для того же состояния, которое
`navigator.permissions.query` называет `'prompt'`. Это два разных API
для одной и той же возможности, и у них разные имена для «ещё не
спрашивали».

```ts
// Напоминания в ленте заметок: проверяем состояние, прежде
// чем показывать пользователю кнопку включения
async function reminderButtonState() {
  const s = await navigator.permissions.query({ name: 'notifications' });
  if (s.state === 'granted') return 'enabled';
  if (s.state === 'denied') return 'blocked'; // показать ссылку на настройки
  return 'ask'; // показать кнопку, которая вызовет requestPermission
}
```

После отказа браузер обычно не откроет диалог повторно ни на один
следующий вызов `requestPermission` — состояние `denied` меняют
только в настройках сайта, вручную.

## Событие и то, что стоит сделать в ответ

| событие или состояние | что делать |
|---|---|
| `visibilitychange` → `hidden` | сохранить черновик, остановить опрос сервера |
| `pagehide` | тот же финальный сброс, что и на `hidden`, на случай ухода со страницы |
| `freeze` | поставить на паузу таймеры и открытые соединения |
| `pageshow` с `persisted: true` | перепроверить данные, а не доверять снимку из bfcache |
| разрешение `denied` | показать путь в настройки, а не повторный диалог |

## Типичные ошибки

- **Сохранять данные только на `unload`.** Симптом: часть правок
  теряется на телефоне, где вкладку закрывают без единого события.
- **Держать таймеры активными после `hidden`.** Симптом: батарея
  телефона садится быстрее, чем должна, из-за вкладки в фоне.
- **Доверять данным со страницы, поднятой из bfcache.** Симптом:
  список заметок показывает то, что было час назад, хотя данные на
  сервере успели поменяться.
- **Вызывать `requestPermission()` повторно после отказа.** Симптом:
  кнопка нажимается, а диалог больше не появляется — и код думает,
  что запрос завис.
