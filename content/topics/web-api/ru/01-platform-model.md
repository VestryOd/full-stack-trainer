# Что браузер даёт приложению и на каких условиях

Браузер даёт приложению доступ к камере, буферу обмена, фоновым потокам
и десяткам похожих возможностей — но не как к обычной библиотеке,
которую ставят через пакетный менеджер. Эти возможности уже встроены
в браузер, и открываются они только тем, кто выполнил его условия. Эта
тема разбирает такие возможности платформы: откуда они берутся, что их
ограничивает и как проверить, что нужная возможность вообще доступна.

## Возможности приходят готовыми объектами, а не импортами кода

Когда вам нужен доступ к буферу обмена, вы не пишете `npm install
clipboard` — вы обращаетесь к готовому объекту `navigator.clipboard`,
который браузер уже создал для этой страницы. Так устроена вся
платформа: возможности лежат в двух глобальных объектах и никуда не
импортируются.

Объект `window` — это сама вкладка: её размер, адрес, таймеры,
открытие новых окон. Объект `navigator` — это браузер и устройство,
на котором он работает: сеть, батарея, буфер обмена, геолокация.
Страница внутри вкладки — тоже готовый объект: объектная модель
документа (DOM), доступная через `window.document`.

```ts
// Бейдж «офлайн» у ленты заметок — используем то, что уже лежит
// в navigator, без единого импорта
function updateOfflineBadge() {
  const badge = document.querySelector('#offline-badge')!;
  badge.hidden = navigator.onLine; // true — сеть есть, бейдж прячем
}

window.addEventListener('online', updateOfflineBadge);
window.addEventListener('offline', updateOfflineBadge);
updateOfflineBadge();
```

Ни `navigator.onLine`, ни события `online`/`offline` не нужно нигде
подключать. Они существуют в любой вкладке с самого её открытия, а
код выше просто подписывается на то, что уже готово.

## Три условия ограничивают любую возможность платформы

Возможность может быть доступна объекту `navigator`, но всё равно
отказать в работе, если не выполнено одно из трёх условий платформы.

```txt
От самого открытого уровня к самому закрытому
┌────────────────────────────────────────────┐
│ Всегда: window, navigator, DOM             │
├────────────────────────────────────────────┤
│ + безопасный контекст (HTTPS)              │
│ Service Worker, Web Locks, Clipboard API   │
├────────────────────────────────────────────┤
│ + жест пользователя                        │
│ полноэкранный режим, запись в буфер обмена │
├────────────────────────────────────────────┤
│ + разрешение пользователя                  │
│ уведомления, камера, точная геолокация     │
└────────────────────────────────────────────┘
каждый уровень добавляет своё условие к предыдущему
```

Условия складываются, а не выбираются: возможность может требовать
сразу двух из них. Точная геолокация, например, требует и безопасного
контекста, и отдельного разрешения пользователя.

| условие | что проверяет браузер | пример возможности |
|---|---|---|
| источник (origin) | схема, домен и порт страницы совпадают с тем, кто просит доступ | cookies, `postMessage` |
| безопасный контекст | страница открыта по HTTPS (защищённой версии HTTP) или на localhost | Service Worker, Web Locks |
| жест пользователя | вызов идёт прямо из обработчика клика или нажатия клавиши | полноэкранный режим, запись в буфер обмена |

Источник страницы называют origin: он остаётся тем же самым для
`https://notes.app` и `https://notes.app/archive`, но меняется для
`https://api.notes.app`, хотя это тот же продукт. Безопасный контекст
и жест пользователя устроены проще — оба либо есть, либо нет, и
браузер проверяет их сам перед тем, как отдать возможность.

## Почти любой вызов возможности — это обещание, а не готовый результат

Большинство методов `navigator` возвращают не значение, а обещание —
`Promise`, который сходится позже, когда браузер закончит спрашивать
устройство или пользователя.

```ts
// Напоминание о заметке — только если пользователь разрешит
// уведомления; permission не будет готов раньше, чем ответит человек
async function enableReminders(): Promise<boolean> {
  const permission = await Notification.requestPermission();
  return permission === 'granted'; // 'granted' | 'denied' | 'default'
}
```

Причина в том, что за многими вызовами стоит либо диалог для
пользователя, либо обращение к операционной системе, либо и то, и
другое сразу. Ни то, ни другое не отвечает мгновенно, поэтому
`Promise` — не стилистический выбор автора платформы, а следствие
самой задачи.

## Доступность возможности проверяют напрямую, а не по имени браузера

Правильная проверка спрашивает у объекта, есть ли в нём то, что вам
нужно, а не выясняет марку и версию браузера.

```ts
// Кнопка «Скопировать ссылку» у заметки — есть не в каждом браузере
function canCopyLink(): boolean {
  return 'clipboard' in navigator
    && typeof navigator.clipboard.writeText === 'function';
}

async function copyNoteLink(noteId: string) {
  if (!canCopyLink()) {
    return showFallbackPrompt(noteId); // ссылка текстом для ручного копирования
  }
  await navigator.clipboard.writeText(`https://notes.app/n/${noteId}`);
}
```

Проверка по имени браузера устаревает в момент, когда любой из трёх
движков меняет своё поведение, а список имён приходится держать в
голове и обновлять вручную. Проверка `'clipboard' in navigator`
переживает любое такое изменение сама, потому что спрашивает не имя,
а факт.

## Типичные ошибки

- **Проверять браузер по строке `User-Agent`.** Симптом: код работает
  в одном браузере и ломается в другом, хотя нужная возможность там
  тоже есть — просто её искали не под тем именем.
- **Забыть про безопасный контекст на тестовом стенде.** Симптом: всё
  работает на localhost и молча перестаёт работать там, где страницу
  открыли по обычному HTTP.
- **Вызывать возможность с жестом слишком поздно.** Симптом: клик
  обработан, но внутри обработчика успел пройти `await`, и браузер
  больше не засчитывает вызов как результат действия человека.
- **Не проверять, чем разрешился `Promise` возможности.** Симптом:
  код продолжает работу так, будто разрешение получено, хотя
  пользователь его отклонил.
