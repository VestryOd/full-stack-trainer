# Как вкладки одного приложения договариваются между собой

Каждая вкладка — это отдельный процесс выполнения кода со своими
переменными, и открытие второй вкладки того же приложения не
создаёт между ними ничего общего само по себе. Правка заметки в
одной вкладке не появится в другой, пока обе не начнут слушать один
и тот же канал связи. В браузере таких каналов четыре, и у каждого
свой охват и своя цена.

## У вкладок одного источника есть общий диск, но не общая память

Переменная, объявленная в одной вкладке, не существует в другой —
`window` каждой вкладки живёт в своём процессе выполнения.

```ts
// Вкладка A
let openNoteId = 42; // существует только здесь

// Вкладка B того же приложения
console.log(typeof openNoteId); // 'undefined' — это другой window
```

При этом обе вкладки одного источника (origin) читают один и тот же
`localStorage`, одну и ту же `IndexedDB` и одни и те же cookies — это
общий диск, а не общая память. Чтобы вкладка узнала об изменении
сразу, а не при следующем открытии, нужен отдельный канал уведомлений.

## Четыре канала связи, и у каждого свой охват

Прежде чем выбирать канал, полезно понять, кто вообще его услышит.

| канал | кто услышит | остаётся после закрытия вкладки |
|---|---|---|
| `BroadcastChannel` | вкладки того же источника с тем же именем канала | нет, только пока открыты |
| событие `storage` | все вкладки источника, кроме той, что сделала запись | нет |
| `SharedWorker` | вкладки, подключившиеся к тому же файлу фонового потока | нет, поток закрывается без вкладок |
| Web Locks | никто — это не канал сообщений, а очередь доступа | нет |

Web Locks не передаёт данные между вкладками вовсе: он решает, чья
очередь действовать, а не что при этом сказать другим. Устройство
`SharedWorker` — один процесс, к которому подключаются через порты —
разобрано в статье [Тяжёлая работа уходит с главного
потока](./03-workers.md), и здесь не повторяется.

## `BroadcastChannel` не доставляет сообщение самому отправителю

Два экземпляра `BroadcastChannel` с одним именем в разных вкладках
слышат друг друга, а отправитель — нет, даже если подписан на тот
же канал.

```ts
// Вкладка A: правит заметку и сообщает об этом остальным
const notesChannel = new BroadcastChannel('notes-sync');
notesChannel.onmessage = () => console.log('услышал сам себя');
notesChannel.postMessage({ type: 'note-updated', id: 1 });
// 'услышал сам себя' не печатается — проверено на двух вкладках
// в одном профиле Chromium через Playwright
```

```ts
// Вкладка B: получает то же сообщение и обновляет список
const notesChannel = new BroadcastChannel('notes-sync');
notesChannel.onmessage = (e) => {
  if (e.data.type === 'note-updated') refreshNoteInList(e.data.id);
};
```

Если вкладке-отправителю тоже нужно отреагировать, реакцию вызывают
напрямую в момент изменения, а не ждут собственного сообщения из
канала — оно никогда не придёт.

## Событие `storage` слышат все вкладки, кроме той, что его вызвала

`window.addEventListener('storage', …)` работает без создания
отдельного канала — событие приходит само при любой записи в
`localStorage`.

```ts
// Вкладка B видит правку черновика, сделанную во вкладке A
window.addEventListener('storage', (e) => {
  if (e.key === 'draft-42') applyDraftUpdate(e.newValue);
});
```

Событие срабатывает во всех вкладках источника, кроме той, где
вызвали `setItem` — это проверено тем же стендом и совпадает с
поведением `BroadcastChannel`. В отличие от него, `storage` реагирует
на любой ключ `localStorage`, так что фильтровать по `e.key`
обязательно, а не по желанию.

## Один лидер выбирается через Web Locks, а его находки — через `BroadcastChannel`

Задача «пусть сервер опрашивает только одна вкладка» решается не
самодельным протоколом, а комбинацией двух возможностей: Web Locks
выбирает, кто сейчас главный, `BroadcastChannel` рассказывает
остальным, что он нашёл.

```txt
Кто станет лидером и как об этом узнают остальные
┌───────────────────────────────────────────────────┐
│ Вкладки A, B, C просят navigator.locks.request    │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ Вкладка A получает блокировку первой — лидер      │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ Лидер опрашивает сервер, находит новые заметки    │
└───────────────────────────────────────────────────┘
                           │
                           ▼
┌───────────────────────────────────────────────────┐
│ BroadcastChannel сообщает B и C: список изменился │
└───────────────────────────────────────────────────┘
лидер меняется сам: он держит блокировку, пока открыта вкладка
```

```ts
// Лидер: держит блокировку, пока вкладка открыта, и рассылает находки
const syncChannel = new BroadcastChannel('notes-leader-sync');

navigator.locks.request('poll-leader', async () => {
  while (true) {
    const fresh = await fetchNewNotes();
    if (fresh.length) syncChannel.postMessage({ notes: fresh });
    await sleep(30_000);
  }
});

// Все вкладки, включая лидера: применяют то, что нашёл лидер
syncChannel.onmessage = (e) => mergeNotes(e.data.notes);
```

Механику самой блокировки — почему `BroadcastChannel` и `localStorage`
не годятся для взаимного исключения, что происходит при крахе
вкладки-держателя и как выставить таймаут через `AbortSignal` —
подробно разбирает банк Browser / JS Runtime. Здесь не повторяется
ничего из этого разбора, только то, чего в нём нет: как сказать
остальным вкладкам, что нашёл лидер.

## Типичные ошибки

- **Ждать собственное сообщение из `BroadcastChannel`.** Симптом:
  код во вкладке-отправителе не реагирует на своё же изменение,
  хотя обработчик подписан на канал правильно.
- **Не фильтровать событие `storage` по ключу.** Симптом: вкладка
  перерисовывает список заметок из-за того, что где-то поменялся
  никак не связанный флаг бокового меню.
- **Писать свой мьютекс на `localStorage`-флаге.** Симптом: изредка
  обе вкладки одновременно проходят проверку «свободно» и обе
  считают себя лидером.
- **Держать блокировку `navigator.locks` без учёта закрытия
  вкладки.** Симптом: код предполагает, что лидер меняется по
  таймеру, а на деле он меняется в момент, когда старый лидер
  закрылся.
