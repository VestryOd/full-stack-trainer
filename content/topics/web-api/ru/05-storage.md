# Хранилища браузера: у каждого своя работа

В браузере несколько разных хранилищ, и они не взаимозаменяемы: одно
читается мгновенно, но блокирует код, пока читает; другое асинхронно
и выдерживает мегабайты; третье видно только сервис-воркеру. Выбор
неправильного хранилища для черновика заметки — частая причина
подвисаний интерфейса и потерянных данных, которых можно было
избежать.

## У каждого хранилища свои правила: скорость, объём и видимость

Прежде чем выбирать хранилище, полезно свести их правила в одну
таблицу.

| хранилище | синхронное | переживает перезагрузку | видно сервис-воркеру |
|---|---|---|---|
| `localStorage` | да | да | нет |
| `sessionStorage` | да | нет, только вкладка | нет |
| `IndexedDB` | нет | да | да |
| Cache Storage | нет | да | да |

Разница между `localStorage` и `sessionStorage`, а также место
cookies в этом списке подробно разбирает Browser / JS Runtime — там
это сравнение уже есть, и повторять его здесь незачем. Эта таблица
добавляет то, чего в том сравнении нет: `IndexedDB` и Cache Storage
рядом с Web Storage, и то, что из них видит сервис-воркер.

## `localStorage` блокирует главный поток, потому что читает диск сразу

`localStorage.getItem` возвращает значение в той же строке, где его
вызвали, — значит, браузер обязан дождаться чтения с диска прямо
сейчас, а не когда-нибудь потом.

```ts
const t0 = performance.now();
localStorage.setItem('draft', body);
const saved = localStorage.getItem('draft');
console.log(performance.now() - t0); // 0.8 — на одном ключе почти незаметно
```

Одна операция стоит меньше миллисекунды, но и заметки — не один
ключ: автосохранение черновика на каждое нажатие клавиши уже
умножает эту стоимость на скорость печати. `IndexedDB` устроена
иначе — `indexedDB.open()` сразу возвращает объект запроса, а не
данные, и результат приходит позже через событие.

```ts
const isRequest = indexedDB.open('notes') instanceof IDBRequest;
console.log(isRequest); // true — открытие не блокирует код ни на миллисекунду
```

Хранить токен доступа в `localStorage` — отдельный вопрос
безопасности, а не скорости: он разобран в банке Browser / JS
Runtime, вместе с тем, что реально снижает риск кражи через XSS
(межсайтовый скриптинг).

## Квота — это оценка, а не точное число

Метод `navigator.storage.estimate()` возвращает не жёсткий лимит, а
приблизительную оценку свободного места.

```ts
const { quota, usage } = await navigator.storage.estimate();
console.log(quota, usage);
```

```txt
Запуск 1, этот же стенд:  quota 3 221 225 472  usage 0
Запуск 2, тот же стенд:   quota 4 294 967 296  usage 0
```

Оба числа сняты одним и тем же Chromium 153 на одном и том же
компьютере в разные дни. Квота зависит от свободного места на диске
и правил браузера, поэтому её нельзя зашивать в код числом — только
запрашивать заново.

```ts
// После записи ~1 МБ в IndexedDB usage вырос, но не ровно на 1 000 000 байт:
// оценка округляется, и это ожидаемо, а не баг вашего кода
const before = await navigator.storage.estimate();
await saveDraftBlob(bigDraft);
const after = await navigator.storage.estimate();
console.log(after.usage - before.usage); // около 1 МБ, не ровно
```

## Постоянное хранилище защищает данные от вытеснения, но не обещает его

Когда на устройстве кончается место, браузер вправе вытеснить данные
источника (origin), которым давно не пользовались, — это называют
вытеснением.

```txt
Два режима хранения: обычный и защищённый
┌────────────────────────────────────────────────┐
│ Best-effort — режим по умолчанию               │
│ место кончилось — браузер вытесняет данные     │
├────────────────────────────────────────────────┤
│ Persistent — после navigator.storage.persist() │
│ браузер обычно не трогает данные               │
└────────────────────────────────────────────────┘
решение браузер принимает сам — это эвристика, не гарантия
```

```ts
console.log(await navigator.storage.persisted()); // false
console.log(await navigator.storage.persist());   // false на этом стенде
console.log(await navigator.storage.persisted()); // false
```

На стенде без реальной истории посещений браузер отказал в
постоянном режиме — так и должно быть: решение опирается на
эвристику вовлечённости пользователя, а не на сам факт вызова.
Постоянный режим снижает риск вытеснения, но не убирает его совсем —
пользователь может очистить данные сайта вручную в любой момент.

## Что выбрать для черновика заметки

Сквозной пример темы — лента заметок, и черновик новой заметки нужно
сохранять на каждое изменение, не блокируя ввод текста.

| сценарий | подходящее хранилище |
|---|---|
| Один флаг: свернута ли боковая панель | `localStorage` — маленькое значение, читают редко |
| Текст черновика заметки, сохраняют на каждый ввод | `IndexedDB` — асинхронно, не блокирует печать |
| Вложение к заметке, снятое с камеры | `IndexedDB` — умеет хранить `Blob` целиком |
| Заполненная наполовину форма входа | `sessionStorage` — не должна пережить закрытие вкладки |
| Офлайн-копия отданных сервером ответов | Cache Storage — её читает сервис-воркер |

```ts
// Автосохранение черновика: IndexedDB не блокирует поле ввода
noteBody.addEventListener('input', async (e) => {
  const text = (e.target as HTMLTextAreaElement).value;
  await saveDraft({ id: currentNoteId, text, savedAt: Date.now() });
});
```

## Типичные ошибки

- **Сохранять черновик заметки в `localStorage` на каждый ввод.**
  Симптом: печать подтормаживает на длинных заметках, хотя код
  выглядит простым и коротким.
- **Хардкодить квоту числом из одного замера.** Симптом: код
  перестаёт проходить проверку места на другом устройстве или даже
  на том же через месяц.
- **Считать, что `persist()` — это разрешение вроде уведомлений.**
  Симптом: код ждёт диалог с кнопками «Разрешить»/«Запретить», а
  браузер решает молча и без вопроса к человеку.
- **Забыть, что `localStorage` не виден сервис-воркеру.** Симптом:
  код в `fetch`-обработчике пытается прочитать `localStorage` и
  падает, потому что такого объекта в этой области просто нет.
