# Тяжёлая работа уходит с главного потока

Главный поток браузера — это один и тот же поток выполнения для
вашего кода, пересчёта стилей, раскладки страницы и отрисовки кадра.
Если синхронный код в нём работает долго, всё остальное — клики,
скролл, анимации — ждёт своей очереди. Фоновый поток, по-английски
`Worker`, даёт коду свой собственный поток выполнения, у которого нет
доступа к странице и который общается с ней только сообщениями.

## Главный поток занят вёрсткой и вашим кодом одновременно

Поиск по тексту — частый источник долгой синхронной работы, потому
что растёт вместе с числом заметок.

```ts
// Поиск прямо в обработчике инпута: с ростом ленты
// каждое нажатие клавиши подвешивает интерфейс на дольше
searchInput.addEventListener('input', (e) => {
  const query = (e.target as HTMLInputElement).value;
  const matches = notes.filter((n) => n.body.includes(query));
  renderResults(matches); // на 5000 заметок это уже заметная пауза
});
```

Пока `filter` перебирает пять тысяч заметок, браузер не может
обработать следующий клик и не может отрисовать кадр. Один и тот же
поток выполнения обслуживает и ваш код, и интерфейс страницы.

## Фоновый поток — своя область выполнения, а не облегчённая страница

`Worker` запускает код в отдельном потоке со своим окружением, и
это окружение — не копия страницы с урезанными правами.

| есть в фоновом потоке | нет в фоновом потоке |
|---|---|
| `self`, `fetch`, `importScripts` | `window`, `document` |
| `navigator`, `setTimeout` | доступ к элементам страницы |
| `IndexedDB`, `caches`, `crypto.subtle` | `localStorage`, `sessionStorage` |

Список снят тем же стендом на Playwright 1.63.0, Chromium 153.0.8010.12,
18 сентября 2026 года. Хранилища `localStorage` и `sessionStorage`
недоступны фоновому потоку по спецификации в любом браузере — это не
особенность одного движка.

```ts
// main.ts — печатает в поиск, тяжёлую часть делает фоновый поток
const searchWorker = new Worker('search-worker.js');
searchWorker.postMessage({ notes }); // один раз отдаём весь список

searchInput.addEventListener('input', (e) => {
  const query = (e.target as HTMLInputElement).value;
  searchWorker.postMessage({ query });
});
searchWorker.onmessage = (e) => renderResults(e.data.matches);
```

Главный поток теперь занят только текстовым полем и отрисовкой
результата. Сам перебор пяти тысяч заметок ушёл туда, где долгая
работа никому не мешает.

## Между потоками данные либо копируются, либо передаются

У `postMessage` есть два разных способа доставить данные, и выбирают
его вторым аргументом.

```txt
Два пути от главного потока к воркеру
┌────────────────────────────────────────────────┐
│ Главный поток вызывает postMessage(data)       │
└────────────────────────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────┐
│ Без transfer: данные клонирует structuredClone │
└────────────────────────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────┐
│ С transfer: buf меняет владельца, копии нет    │
└────────────────────────────────────────────────┘
                         │
                         ▼
┌────────────────────────────────────────────────┐
│ Воркер получает данные в self.onmessage        │
└────────────────────────────────────────────────┘
      выбор — за вторым аргументом postMessage
```

По умолчанию `postMessage` копирует данные тем же алгоритмом
структурного клонирования, что использует `IndexedDB`. Он клонирует
`Map`, `Set`, `Date`, `Error` и большинство встроенных типов, но
бросает ошибку на функциях, узлах документа (DOM) и `Symbol` — это
проверено тем же стендом. Если вторым аргументом передать список
передаваемых объектов, копирования не будет вовсе.

```ts
// search-worker.js — получает и заметки, и запрос через одно сообщение
let notes: Note[] = [];

self.onmessage = (e) => {
  if (e.data.notes) notes = e.data.notes;
  if (e.data.query !== undefined) {
    const matches = notes.filter((n) => n.body.includes(e.data.query));
    self.postMessage({ matches });
  }
};
```

```ts
// Передача владения буфером вместо копии: после этой строки
// buf.byteLength на главном потоке становится 0
worker.postMessage({ buf }, [buf]);
console.log(buf.byteLength); // 0 — данные теперь у воркера
```

Передаваемый объект — это `ArrayBuffer`, `MessagePort` или похожий
тип, который можно перевести из одного потока в другой без
копирования памяти. За это отправитель расплачивается: после
передачи исходный буфер пуст, и читать из него больше нельзя.

## SharedWorker даёт одну область на несколько вкладок

`SharedWorker` — это тот же фоновый поток, но к нему может
подключиться больше одной вкладки сразу через отдельный `MessagePort`
на каждую.

```ts
// Все вкладки ленты заметок подключаются к одному SharedWorker —
// например, чтобы держать один WebSocket на всех, а не по одному на вкладку
const shared = new SharedWorker('sync-worker.js');
shared.port.start();
shared.port.postMessage({ type: 'subscribe' });
shared.port.onmessage = (e) => applyRemoteChange(e.data);
```

На момент написания `WebKit` (движок Safari) не поддерживает
`SharedWorker` — актуальный статус проверяйте в таблицах поддержки
браузеров, а не по этому тексту. Пока это так, `SharedWorker`
годится для прогрессивного улучшения, но не как единственный способ
что-то сделать.

## Worklets — ещё один вид потока, но не для переписки

Worklets — это лёгкие потоки выполнения для конкретных подсистем
браузера: например, `PaintWorklet` для собственных функций отрисовки
в CSS. У них нет `postMessage` для общения со страницей, и код в них
пишут ради узкой задачи рендеринга, а не ради вычислений. В этой
теме worklets дальше не разбираются — они ближе к рендерингу, чем к
фоновым вычислениям.

## Типичные ошибки

- **Создавать `Worker` на каждый поисковый запрос.** Симптом: список
  процессов растёт, а старые фоновые потоки продолжают висеть в
  памяти. Воркер создают один раз и переиспользуют.
- **Ждать доступа к `document` внутри воркера.** Симптом: код падает
  на первой же строке, где воркер пытается прочитать элемент
  страницы, — такого объекта там нет.
- **Читать `buf` на главном потоке сразу после передачи.**
  Симптом: `byteLength` неожиданно равен нулю, потому что данные уже
  переехали в фоновый поток.
- **Полагаться на `SharedWorker` без проверки поддержки.** Симптом:
  код молча ничего не делает в одном браузере и работает в другом.
