# Microtasks, Macrotasks и process.nextTick

## Почему это любимая тема интервьюеров — и в чём реальная глубина вопроса

Реальная глубина этой темы — один вопрос: **между чем именно происходит переключение очередей и как часто?** Ответьте на него, и вы сможете объяснить целый класс продакшен-багов. Типичный звучит так: "почему один долгий запрос замедляет **все** остальные, хотя я использую async/await везде?"

Поверхностный уровень другой. Это "выучить порядок: nextTick → microtasks → macrotasks" плюс предсказывать вывод `console.log` в коротких примерах. Это необходимо, но это не то, что отличает senior-ответ.

## Три очереди — и когда каждая из них опустошается

```txt
process.nextTick queue  — опустошается полностью после
                           завершения любой текущей операции:
                           после синхронного кода скрипта,
                           после каждого microtask, после
                           каждого callback фазы Event Loop

Microtask queue          — опустошается полностью, включая
(Promise.then,             новые микротаски, добавленные во
queueMicrotask)             время выполнения текущих. Это
                           происходит после завершения текущей
                           операции и после опустошения
                           очереди nextTick

Macrotask queue           — Event Loop переходит к следующему
(setTimeout, setImmediate,  macrotask только когда обе очереди
I/O callbacks)               выше полностью пусты
```

Ключевая деталь, которую опускает большинство объяснений: это не происходит **один раз**, "после синхронного блока скрипта". Это происходит **после каждого callback**, где бы он ни выполнялся. Это может быть один из множества I/O callbacks в poll-фазе или один `setTimeout` среди десяти запланированных.

Каждый отдельный callback, который выполнил Event Loop, заканчивается полным опустошением очередей nextTick и microtask. Только после этого Event Loop берёт следующую задачу.

```txt
Poll-фаза, 3 готовых callback от I/O:

  callback1() {
    promise.then(microtaskA)  // запланирован
  }
  → выполнить microtaskA (очередь опустошается)
  callback2() { ... }
  → очередь опустошается
  callback3() { ... }
  → очередь опустошается

  Только теперь Event Loop переходит к фазе check
```

## async/await — это .then() в синтаксическом сахаре, и это важно для подсчёта "тиков"

```ts
// Эти два фрагмента эквивалентны по количеству microtask-тиков
async function a() {
  await Promise.resolve();
  console.log('after await');
}

function b() {
  Promise.resolve().then(() => console.log('after then'));
}
```

```ts
// ❌ Каждый await внутри цепочки добавляет минимум один
// microtask-тик — для цепочки из 100 вызовов await даже
// над уже готовыми значениями (без реального I/O)
// понадобится 100 проходов через microtask queue
async function chainedAwaits() {
  let result = 0;
  for (let i = 0; i < 100; i++) {
    result = await Promise.resolve(result + 1); // тик на каждой итерации
  }
  return result;
}
```

Практическое значение: микротаски могут заставить готовые таймеры ждать. Допустим, к выполнению готовы 100 вызовов `setTimeout(fn, 0)`, и при этом где-то в цепочке промисов работает функция `chainedAwaits` выше. Все 100 таймеров будут ждать, пока microtask queue не опустеет полностью.

При достаточно длинных цепочках промисов эта задержка становится заметной, хотя обычно она меньше миллисекунды. Большинство приложений её не замечают. Но приложения с очень высокой частотой событий — трейдинг, realtime-аналитика — замечают. Там разница между "await на каждой итерации" и "await раз в N итераций" измерима.

## process.nextTick starvation — не теоретический сценарий, а реальный класс багов

```ts
// ❌ Классический пример starvation — Event Loop никогда
// не дойдёт до I/O, таймеров или вообще чего-либо ещё.
// Сервер перестанет отвечать на запросы, но не "упадёт" —
// просто будет бесконечно крутиться в nextTick queue
function loop() {
  process.nextTick(loop);
}
loop();
```

Но реалистичный вариант этого бага выглядит куда менее очевидно:

```ts
// ❌ Рекурсивная обработка очереди сообщений через nextTick —
// выглядит как "эффективная" немедленная обработка, но если
// сообщения поступают быстрее, чем обрабатываются, очередь
// nextTick никогда не опустеет, и HTTP-сервер того же процесса
// перестанет отвечать на запросы
function processQueue() {
  if (messages.length > 0) {
    handleMessage(messages.shift());
    process.nextTick(processQueue);  // "продолжить как можно скорее"
  }
}
```

```ts
// ✅ setImmediate возвращает управление Event Loop —
// между итерациями обрабатываются I/O и таймеры
function processQueue() {
  if (messages.length > 0) {
    handleMessage(messages.shift());
    setImmediate(processQueue);
  }
}
```

Разница принципиальна. При `process.nextTick` callback попадает в очередь, которая **полностью опустошается до перехода к следующей фазе Event Loop**. А `setImmediate` — это macrotask: он ждёт своей фазы, `check`. Поэтому между итерациями успевает выполниться фаза `poll`, в которой обрабатывается входящий трафик.

## Полная карта приоритетов — с привязкой к фазам Event Loop

```txt
Call Stack (синхронный код) — выполняется первым, всегда
    ↓
process.nextTick queue — опустошается полностью
    ↓
Microtask queue (Promise, queueMicrotask) — опустошается полностью
    ↓
═══════════ конец "текущей операции" ═══════════
    ↓
timers (setTimeout/setInterval, готовые по времени)
    ↓ (nextTick + microtasks опустошаются после каждого callback)
pending callbacks
    ↓ (nextTick + microtasks опустошаются после каждого callback)
poll (I/O callbacks — основная фаза)
    ↓ (nextTick + microtasks опустошаются после каждого callback)
check (setImmediate)
    ↓ (nextTick + microtasks опустошаются после каждого callback)
close callbacks
    ↓
[следующий проход цикла → снова timers]
```

## Разбор классического примера — с объяснением механизма, а не просто ответа

```ts
console.log('1');

process.nextTick(() => console.log('2'));

Promise.resolve().then(() => console.log('3'));

setTimeout(() => console.log('4'), 0);

console.log('5');

// Вывод: 1, 5, 2, 3, 4
```

```txt
Шаг 1: выполняется синхронный код скрипта (Call Stack)
       → печатает "1", регистрирует nextTick-callback,
         регистрирует microtask, регистрирует timer,
         печатает "5"

Шаг 2: синхронный код скрипта завершён → опустошается
       очередь nextTick → печатает "2"

Шаг 3: очередь nextTick пуста → опустошается microtask queue
       → печатает "3"

Шаг 4: обе очереди пусты → Event Loop переходит к фазе timers
       → timer готов → печатает "4"
```

Запоминание конкретного вывода "1 5 2 3 4" перестаёт помогать, как только пример меняется. Интервьюеру достаточно вложить ещё один `setTimeout` внутрь первого или поставить `.then()` внутрь `nextTick`.

Разобрать **любой** вариант этого вопроса позволяет одно правило. После любой операции сначала полностью опустошается nextTick, потом полностью microtasks, и только потом идёт следующий macrotask.

## Практическое применение: когда выбирать что

```txt
process.nextTick — для:
  - гарантии, что callback выполнится до любого I/O,
    но после завершения текущей синхронной операции
    (например, эмит события сразу после конструктора,
    чтобы подписчики успели подписаться: классический
    паттерн в EventEmitter-based API)
  - редко нужен в обычном бизнес-коде

queueMicrotask / await — для:
  - стандартного асинхронного кода, цепочек промисов

setImmediate — для:
  - "выполнить как можно скорее, но после текущей I/O-фазы" —
    например, разбивка тяжёлой синхронной работы на чанки
    (см. The Event Loop)

setTimeout(fn, 0) — для:
  - похоже на setImmediate, но проходит через фазу timers,
    которая идёт первой в следующем проходе цикла; разница
    между setImmediate и setTimeout(0) обычно незначительна,
    кроме случаев внутри I/O callback (см. The Event Loop)
```

## Типичные ошибки на интервью

- **Заучивание конкретных примеров вместо механизма.** Любое изменение примера ломает заученный ответ: вложенный `.then`, `nextTick` внутри `nextTick`, несколько вызовов `setTimeout`. Объяснять надо через "очереди опустошаются после каждой операции", а не через таблицу запомненных выводов.

- **Не знать, что microtask queue опустошается после каждого callback**, а не один раз "после скрипта". Это объясняет частую неожиданность. Промис, запланированный во время обработки одного I/O callback, выполнится раньше следующего I/O callback, даже если готовы оба.

- **Не видеть starvation как реальную угрозу.** Рекурсию через `process.nextTick` воспринимают как "экзотический крайний случай". В реальном коде рекурсивная обработка очередей через nextTick — нередкая практика, хоть и ошибочная.

- **Не понимать, что async/await — это .then() в сахаре.** Следствие: вы не сможете объяснить, почему длинная цепочка вызовов await добавляет microtask-тики, даже когда ожидаемые значения уже доступны синхронно.

- **Путать setImmediate и setTimeout(fn, 0) как "то же самое".** Одно — отдельная фаза, `check`; другое — фаза timers. Разница проявляется именно при вызове внутри I/O callback (см. [Event Loop](./03-event-loop.md)).
