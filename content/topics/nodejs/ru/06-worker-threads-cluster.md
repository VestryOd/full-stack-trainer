# Worker Threads и Cluster

## Три способа использовать больше одного ядра — и это разные задачи

Все три нужны по одной причине. Один процесс Node выполняет ваш JavaScript на одном ядре CPU (central processing unit — центральный процессор). Заменять их друг другом нельзя: каждый закрывает свою задачу.

```txt
Thread Pool (libuv)  — не выполняет ваш JS вообще. Решает
                        проблему "у операции X нет
                        асинхронного API операционной
                        системы" (см. [libuv and the
                        Thread Pool])

Worker Threads        — выполняет ваш JS-код в отдельном
                        потоке, со своим экземпляром V8 и
                        своим Event Loop. Решает проблему
                        "тяжёлое вычисление блокирует
                        главный поток"

Cluster / несколько
процессов              — несколько полностью независимых
                        процессов Node, делящих один порт.
                        Решает проблему "один процесс
                        использует одно ядро CPU"
```

Частая ошибка — воспринимать их как взаимозаменяемые "способы параллелизма". Это решения для **разных** проблем, и зрелая архитектура обычно совмещает два из них:

- Cluster или несколько контейнеров — чтобы утилизировать все ядра под HTTP-трафик.
- Worker Threads внутри **каждого** из этих процессов — чтобы конкретные тяжёлые операции не блокировали именно этот процесс.

## Worker Threads: не просто "новый поток", а новый экземпляр V8

V8 — это движок JavaScript внутри Node, и каждый Worker получает собственный его экземпляр.

```txt
Каждый Worker имеет:
  - свой экземпляр V8 (свой heap, свой сборщик мусора —
    независимый от главного потока, см. Memory and
    Garbage Collection)
  - свой Event Loop (свою очередь microtasks/macrotasks)
  - свой global scope

Не делится с главным потоком:
  - обычные переменные и объекты (передаются через
    структурное клонирование — это копирование, а не
    ссылка)

Может делиться, но только явно:
  - SharedArrayBuffer + Atomics — единственный способ
    реальной общей памяти между потоками
```

```ts
// main.ts
import { Worker } from 'node:worker_threads';

const worker = new Worker('./hash-worker.js', {
  workerData: { password: 'user-input', cost: 100_000 },
});

worker.on('message', (hash) => console.log('Hash:', hash));
worker.on('error', (err) => console.error('Worker crashed:', err));
```

```ts
// hash-worker.js
import { parentPort, workerData } from 'node:worker_threads';
import crypto from 'node:crypto';

const hash = crypto.pbkdf2Sync(workerData.password, 'salt', workerData.cost, 64, 'sha512');
parentPort.postMessage(hash.toString('hex'));
```

### Senior-нюанс №1: создание воркера — это не бесплатно

```txt
Создание воркера требует:
  - инициализации нового экземпляра V8 (десятки миллисекунд)
  - выделения памяти под отдельный heap

❌ Создавать воркер на каждый запрос — накладные расходы на
   инициализацию могут превысить выигрыш от параллелизма
   для коротких задач:

  app.post('/hash', (req, res) => {
    const worker = new Worker('./hash-worker.js', {
      workerData: req.body,
    });
    worker.on('message', (h) => res.json({ hash: h }));
  });

✅ Worker Pool — фиксированный набор воркеров, которые
   переиспользуются между запросами. Этот паттерн
   реализуют библиотеки piscina и workerpool: в реальных
   проектах их берут вместо своей реализации.

  const pool = new Piscina({ filename: './hash-worker.js' });
  app.post('/hash', async (req, res) => {
    const hash = await pool.run(req.body); // воркер из пула
    res.json({ hash });
  });
```

### Senior-нюанс №2: передача данных — копирование, если не Transferable/SharedArrayBuffer

```ts
// ❌ Передача большого Buffer/массива через postMessage —
// структурное клонирование копирует данные (память x2 на
// время передачи, и время на сериализацию больших объёмов)
worker.postMessage({ buffer: largeBuffer }); // largeBuffer копируется

// ✅ Transferable objects — передача "владения" ArrayBuffer
// без копирования (после передачи исходный буфер становится
// недоступен в отправляющем потоке)
worker.postMessage({ buffer: largeArrayBuffer }, [largeArrayBuffer]);

// ✅ SharedArrayBuffer + Atomics — оба потока видят одну и
// ту же память; нужна явная синхронизация (Atomics.wait/
// notify), как в "настоящем" многопоточном программировании
// со всеми соответствующими рисками гонок
const shared = new SharedArrayBuffer(1024);
worker.postMessage({ shared });
```

`SharedArrayBuffer` — редкий случай в Node, где появляются настоящие гонки данных (data race), привычные для языков с разделяемой памятью (C++/Java). Большинству задач достаточно передать входные данные и получить результат. Для этого хватает Transferable ArrayBuffer, и его проще обосновать на интервью.

## Cluster: несколько процессов, общий порт

```ts
import cluster from 'node:cluster';
import os from 'node:os';

if (cluster.isPrimary) {
  const numCPUs = os.availableParallelism(); // учитывает лимиты cgroup, в отличие от os.cpus().length
  for (let i = 0; i < numCPUs; i++) cluster.fork();

  cluster.on('exit', (worker) => {
    console.log(`Worker ${worker.process.pid} died, restarting`);
    cluster.fork(); // graceful restart упавшего воркера
  });
} else {
  startHttpServer(); // каждый worker-процесс — отдельный HTTP-сервер
}
```

### Как несколько процессов слушают один порт

```txt
Primary-процесс создаёт серверный сокет и передаёт файловый
дескриптор каждому worker-процессу. На современных
операционных системах он может вместо этого использовать
SO_REUSEPORT: тогда входящие соединения распределяет между
процессами само ядро.

Стратегия распределения по умолчанию (Linux, "round-robin"
в модуле cluster):
  Primary принимает соединение → передаёт его одному из
  worker-процессов по round-robin

  (на Windows и при SO_REUSEPORT операционная система
  балансирует сама, без участия Primary)
```

### Senior-нюанс: Cluster и stateful-соединения (WebSocket)

```txt
Проблема: round-robin распределяет между процессами новые
соединения, но каждый WebSocket-клиент "застревает" на том
процессе, который принял соединение. Если этот процесс
хранит в памяти presence (кто сейчас онлайн) или другое
состояние — другие процессы об этом не знают.

Это тот же вопрос "connection pinning" / "sticky session",
что разобран для балансировщиков нагрузки в WebSockets and
Realtime Systems и Scalability and Load Balancing.
Cluster просто переносит ту же проблему с уровня "несколько
серверов" на уровень "несколько процессов на одном
сервере". Решение тоже то же: Redis Pub/Sub для обмена
между процессами и presence в Redis, а не в памяти.
```

## Cluster vs контейнеры — действительно ли Cluster "устарел"

```txt
Старая модель (один bare-metal сервер):
  1 сервер, 8 ядер → 1 процесс Node использует 1 ядро →
  Cluster с 8 worker-процессами утилизирует все 8

Современная модель (Kubernetes, он же k8s, или Amazon ECS):
  Деплой настроен на N "реплик" (подов/контейнеров),
  каждая — отдельный процесс Node. Оркестратор сам
  распределяет реплики между ядрами/нодами кластера,
  Load Balancer/Service распределяет трафик между репликами.
```

Из этого можно сделать неверный вывод "Cluster больше не нужен никогда" — но это не совсем так:

```txt
Нюанс: пусть контейнеру выделено 4 виртуальных ядра
(4 vCPU), а внутри запущен один процесс Node. Этот процесс
всё равно использует только 1 ядро для выполнения JS,
потому что event loop однопоточный. Остальные 3 виртуальных
ядра контейнера простаивают для CPU-bound части нагрузки
(хотя Thread Pool и Worker Threads используют их частично).

Вариант А: 1 контейнер = 1 процесс Node, реплик больше
  (4 реплики по 1 vCPU вместо 1 реплики на 4 vCPU) —
  чаще предпочтительно в Kubernetes: проще health checks,
  проще rolling updates, метрики на уровне реплики

Вариант Б: 1 контейнер = Cluster с несколькими
  worker-процессами (например, через PM2 — это менеджер
  процессов для Node — в режиме cluster). Иногда так делают,
  когда оркестрация на уровне реплик ограничена или дорога
  (накладные расходы на sidecar в каждой реплике)
```

Сильный ответ — не "Cluster устарел" и не "Cluster всегда нужен". Обозначьте компромисс (trade-off) явно:

- **За Cluster:** внутри контейнера он даёт более тонкую утилизацию CPU этой одной реплики.
- **Против Cluster:** сложнее наблюдаемость — логи и метрики идут теперь от нескольких процессов в одном контейнере.
- **Против Cluster:** сложнее graceful shutdown — по `SIGTERM` нужно корректно остановить **все** worker-процессы (см. [Основы Node.js](./01-nodejs-fundamentals.md)).

## Итоговая таблица решений

```txt
Задача                          → Решение
─────────────────────────────────────────────────────
fs/crypto/zlib операция, для    → Thread Pool (встроено,
которой нет async API ОС           просто await/.promises)

Тяжёлое вычисление (обработка    → Worker Threads (через
изображений, свой хэшинг,          worker pool — piscina)
парсинг больших документов)

Утилизация всех ядер CPU         → несколько процессов:
сервера/контейнера для               Cluster или несколько
HTTP-трафика                          реплик контейнера
                                         (в k8s предпочтительно)

Координация состояния между      → Redis (Pub/Sub, presence)
процессами/репликами                 — не в памяти, см.
                                         [WebSockets and
                                         Realtime Systems]
```

## Типичные ошибки на интервью

- **"Worker Threads решают ту же проблему, что Thread Pool"** — это разные вещи. Worker Threads выполняют **ваш** JS в отдельном потоке. Thread Pool делегирует в фоновые потоки libuv операции, у которых нет асинхронного API операционной системы.

- **Создавать воркер на каждый запрос** — не упоминать накладные расходы на инициализацию экземпляра V8. Стандартное решение — паттерн worker pool (piscina/workerpool).

- **Не знать, что передача данных в воркер по умолчанию — копирование** — путать обычный `postMessage` с Transferable objects и `SharedArrayBuffer`. Заодно теряется стоимость структурного клонирования для больших объёмов данных.

- **"Cluster полностью устарел из-за Docker"** — один процесс Node внутри многоядерного контейнера всё равно использует одно ядро для event loop. Cluster и несколько реплик решают это на разных уровнях и с разными компромиссами.

- **Не связывать Cluster с проблемой sticky session** — для WebSocket и других stateful-соединений Cluster создаёт ту же проблему connection pinning, что несколько серверов за балансировщиком нагрузки. И решается она так же — через Redis.
