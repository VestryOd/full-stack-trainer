# Память, Heap, Stack и сборка мусора

## Почему это вторая по частоте причина продакшен-инцидентов (после Event Loop lag)

Утечка памяти в Node редко выглядит как явная ошибка. Приложение продолжает отвечать на запросы, но резидентная память процесса (RSS, resident set size) медленно растёт часами или днями.

В итоге оркестратор — например, Kubernetes (k8s) — убивает контейнер за перерасход памяти (OOM, out of memory) и перезапускает его. Между перезапусками всё "работает", поэтому проблему часто замечают только когда частота перезапусков становится подозрительной.

## Stack vs Heap — быстро, но с акцентом на то, что путают

```txt
Stack:
  - кадры вызовов функций, примитивы, ссылки на объекты
  - размер фиксирован при старте (--stack-size), переполнение
    → "Maximum call stack size exceeded" (RangeError)
  - не управляется сборщиком мусора — память автоматически
    освобождается при выходе из функции

Heap:
  - объекты, массивы, функции, замыкания (closures)
  - управляется сборщиком мусора V8
  - именно здесь происходят утечки памяти
```

Частая путаница: "примитив, объявленный внутри функции, хранится в Heap, потому что переменные — это объекты". Это не так. Сам примитив (`number`, `boolean`, короткая `string`) лежит на Stack. В Heap размещаются объекты, массивы и функции, а переменная на Stack хранит **ссылку** на них.

## Структура V8 Heap — детальнее, чем "Young + Old Generation"

```txt
V8 Heap состоит из нескольких пространств (spaces):

  New Space (Young Generation)
    - маленький (обычно несколько MB), для новых объектов
    - очищается алгоритмом Scavenge (копирующий сборщик) —
      быстро и часто (десятки/сотни раз в секунду
      под нагрузкой)

  Old Space (Old Generation)
    - объекты, "выжившие" после 2 циклов Scavenge
      в New Space, перемещаются сюда (promotion)
    - очищается Mark-Sweep-Compact — реже, но дороже

  Large Object Space
    - объекты больше определённого порога (например,
      крупные Buffer/массивы) — минуют New Space,
      сразу попадают сюда (не перемещаются — слишком дорого)

  Code Space, Map Space
    - скомпилированный код (JIT — компиляция на ходу,
      just-in-time), Hidden Classes/Shapes
      (см. [V8 and the Runtime])
```

### Scavenge: почему очистка молодого поколения такая быстрая

```txt
Scavenge — копирующий сборщик (вариант алгоритма Чейни,
Cheney's algorithm):

  New Space делится на 2 половины: "from-space" и "to-space"

  1. живые объекты копируются из from-space в to-space
  2. всё from-space целиком считается мусором и просто
     "забывается" (никакого обхода мёртвых объектов!)
  3. половины меняются местами

Поэтому стоимость Scavenge пропорциональна количеству
живых объектов, а не общему объёму мусора — большинство
объектов в New Space умирают быстро (req/res, временные
массивы), поэтому "живых" мало → Scavenge почти всегда
очень быстрый (доли миллисекунды).
```

### Mark-Sweep-Compact: почему очистка старого поколения медленнее

```txt
1. Mark: обход от Root Objects (global, активные кадры
   вызовов, замыкания) — помечает достижимые объекты
2. Sweep: непомеченные объекты освобождаются
3. Compact: живые объекты дефрагментируются (перемещаются
   вместе), чтобы избежать "дырявой" памяти

Old Space обычно много больше New Space — обход графа
объектов занимает значительно больше времени.
```

### Современный V8: почему "Stop The World" — больше не вся правда

```txt
Старый V8 (до ~2018): Major GC = полная пауза JS-выполнения
на десятки-сотни миллисекунд при большом heap.

Современный V8:
  - Incremental Marking — фаза Mark разбивается на маленькие
    шаги, чередующиеся с выполнением JS (проект Orinoco)
  - Concurrent Marking — часть Mark выполняется в фоновых
    потоках (см. [libuv and the Thread Pool] — это другие
    потоки, не Thread Pool, а собственные потоки сборщика
    мусора V8)
  - Parallel Compaction — фаза Compact использует несколько
    потоков одновременно

Итог: полные паузы стали короче (единицы миллисекунд для
большинства приложений), но не исчезли полностью — финальная
синхронизация Mark и сама фаза Sweep всё ещё требуют
короткой паузы основного потока.
```

Для интервью важно не "сборщик мусора (GC, garbage collector) останавливает мир, и это плохо". Скажите это в три шага:

- Современный GC **снижает** влияние на latency, но не убирает его.
- При достаточно большом heap (гигабайты живых объектов) паузы всё равно заметны на p99 и p999 latency — то есть на самом медленном 1% и 0.1% запросов.
- Поэтому несколько процессов с меньшим heap каждый выигрывают у одного процесса с огромным heap. Это аргумент в пользу горизонтального масштабирования, см. [Worker Threads and Cluster].

## process.memoryUsage() — что означает каждое поле

```ts
console.log(process.memoryUsage());
// {
//   rss: 85000000,
//   heapTotal: 50000000,
//   heapUsed: 35000000,
//   external: 12000000,
//   arrayBuffers: 8000000
// }
```

```txt
rss (Resident Set Size)
  — вся память процесса в физической памяти: V8 heap +
    Buffer + нативные модули + сам исполняемый код Node.
    Это число сравнивает оркестратор (k8s) с memory limit
    контейнера для OOM Kill.

heapTotal
  — сколько памяти V8 выделил под heap (может расти не
    плавно, а скачками — V8 резервирует память блоками)

heapUsed
  — сколько из heapTotal реально занято живыми объектами.
    Основной индикатор для отслеживания утечек на JS-стороне

external
  — память, управляемая C++, но связанная с JS-объектами —
    в первую очередь содержимое Buffer/TypedArray.
    Не входит в heapUsed!

arrayBuffers
  — подмножество external, конкретно ArrayBuffer/Buffer
```

### Senior-нюанс: утечка через `external`, а не через `heapUsed`

```ts
// ❌ heapUsed может оставаться стабильным, пока external растёт
const buffers: Buffer[] = [];

app.post('/upload', (req, res) => {
  buffers.push(req.body); // удерживаем Buffer навсегда
  res.send('ok');
});
```

```txt
Данные Buffer хранятся вне обычного V8 heap (в "external"
памяти), но ссылка на объект Buffer — обычный JS-объект
в heap. Если мониторить только heapUsed (как часто советуют
"быстрые" гайды) — рост RSS из-за удерживаемых объектов
Buffer останется незамеченным. RSS и external — обязательные
метрики при диагностике утечек, связанных с файлами или
сетевыми данными.
```

## Утечки памяти: три классических паттерна — и почему сборщик мусора здесь не помогает

```ts
// ❌ Паттерн 1: неограниченно растущая коллекция,
// достижимая из глобального scope (Root Object)
const requestLog: RequestInfo[] = [];
app.use((req, res, next) => {
  requestLog.push({ url: req.url, timestamp: Date.now() }); // никогда не очищается
  next();
});
```

```ts
// ❌ Паттерн 2: EventEmitter listeners, добавляемые
// на каждый запрос/соединение, но не удаляемые
function handleConnection(socket: Socket) {
  const onBroadcast = (msg: string) => socket.send(msg);
  broadcaster.on('message', onBroadcast); // подписка...

  socket.on('close', () => {
    // ❌ забыли: broadcaster.off('message', onBroadcast)
    // broadcaster (живёт долго) теперь держит ссылку на
    // onBroadcast → onBroadcast держит socket (через замыкание)
    // → socket никогда не будет собран сборщиком мусора,
    // даже после закрытия соединения
  });
}
```

```ts
// ❌ Паттерн 3: замыкание удерживает большой объект,
// который нужен был только во время инициализации
function createHandler() {
  const hugeConfigCache = loadHugeConfig(); // 200 MB, нужен один раз

  return (req: Request) => {
    // hugeConfigCache используется не здесь, но замыкание
    // всё равно держит на него ссылку, потому что JS не
    // делает "частичный захват" — захватывается вся
    // переменная из охватывающего scope
    return processRequest(req);
  };
}
```

```txt
Во всех трёх случаях GC работает корректно. Он не удаляет
объект, потому что объект достижим из Root: из global, из
долгоживущего EventEmitter, из замыкания. "Утечка" — это не
баг GC, а баг графа ссылок в вашем коде.

На собеседовании это стоит проговорить прямо: GC в V8 не
"теряет" память. Он честно сохраняет всё, что вы
продолжаете считать нужным — в том числе по ошибке.
```

### WeakMap / WeakRef — когда они реально решают проблему

```ts
// ✅ WeakMap — ключ не удерживает объект живым
const metadataCache = new WeakMap<object, Metadata>();

function attachMetadata(obj: object, meta: Metadata) {
  metadataCache.set(obj, meta);
  // когда obj больше нигде не используется (даже если
  // metadataCache всё ещё существует) — GC может удалить
  // и obj, и связанную запись в WeakMap
}
```

```txt
WeakMap/WeakRef подходят для кэшей, привязанных к жизненному
циклу объекта. Примеры: метаданные для узлов DOM в браузере
(DOM — объектная модель документа) или для request-объектов
в Node. В Node это редкий случай: request живёт недолго, и
обычного Map с явной очисткой по событию 'close' чаще
достаточно.

Не подходят для кэшей со временем жизни (TTL, time to live).
У WeakMap нет TTL: объект живёт, пока на него есть хоть одна
сильная ссылка где-то ещё.
```

## Диагностика в production

```ts
// Базовый мониторинг — экспортировать как метрику
setInterval(() => {
  const mem = process.memoryUsage();
  metrics.gauge('nodejs.heap_used', mem.heapUsed);
  metrics.gauge('nodejs.rss', mem.rss);
  metrics.gauge('nodejs.external', mem.external);
}, 10_000);
```

```txt
Признак утечки: heapUsed (или external/rss) растёт монотонно
после каждого полного цикла GC. Локально график всё так же
поднимается и падает (выделение → GC → сброс), но нижняя
точка после каждого сброса выше предыдущей.

Признак "это просто нормальное поведение": heapUsed растёт
до некоего плато и стабилизируется — V8 просто увеличил
heapTotal под рабочий набор данных (кэши, пулы соединений)
и больше не растёт.
```

```bash
# Heap snapshot — чтобы найти конкретный виновный объект
node --inspect server.js
# Chrome DevTools → Memory → Heap Snapshot,
# сравнить два снапшота с разницей в N минут → вид "Comparison"
# показывает объекты, появившиеся между снапшотами и не
# освобождённые
```

```txt
Осторожно: снятие heap snapshot — это операция Stop The World
и временный рост памяти (V8 должен материализовать полное
описание графа объектов). Снимать snapshot на живом
production-инстансе под нагрузкой — риск кратковременного
полного зависания процесса. Обычно это делают на одной
реплике, временно выведенной из балансировки, или через heap
profiler из clinic.js, у которого накладные расходы меньше.
```

## `--max-old-space-size` и контейнеры — частый источник "необъяснимых" OOM

```txt
По умолчанию V8 устанавливает лимит Old Space на основе
общей памяти системы, а не лимита, выданного контейнеру
control-группой Linux (cgroup). На машине с 64 GB памяти,
но с контейнером с лимитом 512 MB, V8 может попытаться
выделить heap, превышающий лимит контейнера. Тогда
оркестратор убьёт процесс по OOM до того, как сам V8
решит, что нужен GC.

✅ Явно ограничить heap V8 ниже лимита контейнера:
  node --max-old-space-size=400 server.js
  # оставляя ~25% запас под external/Buffer/нативные модули,
  # которые не учитываются в --max-old-space-size
```

```txt
Современные версии Node (≥18) частично решают эту проблему
автоматически (V8 умеет читать лимиты cgroup), но явная
настройка остаётся best practice. External-память (Buffer)
не ограничивается --max-old-space-size вообще, поэтому
контейнер всё равно может упасть по OOM из-за накопления
буферов даже при "безопасном" heap.
```

## Типичные ошибки на интервью

- **"GC останавливает приложение полностью на каждом цикле"** — без уточнения про Incremental/Concurrent/Parallel GC в современном V8. Они резко снижают влияние на latency, хотя и не убирают его полностью.

- **Мониторить только `heapUsed`** — так пропускаются утечки через `external`/`arrayBuffers` (удерживаемые объекты Buffer). В heapUsed они не отражаются, но напрямую влияют на RSS и риск OOM Kill.

- **"Объект утёк — это баг сборщика мусора"** — GC работает корректно по определению достижимости (reachability). Утечка — это ошибка в графе ссылок кода: забытый listener, растущий глобальный массив, замыкание с лишним захватом.

- **Не знать про `--max-old-space-size` и контейнерные лимиты памяти** — оркестратор может убить процесс по OOM, пока V8 "думает", что GC ещё не нужен. Без этого флага объяснить такое не получится.

- **Предлагать WeakMap как универсальное решение для кэшей** — кэш, привязанный к жизненному циклу объекта, WeakMap закрывает. Кэш со временем жизни (TTL) — нет: без внешних сильных ссылок понятия времени жизни просто нет.
