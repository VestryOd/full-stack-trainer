# libuv и Thread Pool

## "Node однопоточный" — где проходит точная граница

Утверждение "Node однопоточный" верно для одной конкретной вещи — выполнения вашего JS-кода в V8. Но процесс Node содержит:

```txt
1 поток — выполняет JS (V8) + Event Loop libuv
N потоков — Thread Pool libuv (по умолчанию 4)
M потоков — фоновые потоки V8 для сборки мусора (GC),
            см. [Memory and Garbage Collection]
```

Сетевые операции (`http`, `net`, `tcp`) **не используют Thread Pool вообще** — это критически важная деталь, которую путают чаще всего. Они опираются на нативные асинхронные механизмы операционной системы (ОС):

```txt
Linux:   epoll
macOS:   kqueue
Windows: IOCP (I/O Completion Ports)
```

Эти механизмы позволяют **одному** потоку отслеживать тысячи файловых дескрипторов (сокетов). Поток получает уведомление, когда конкретный сокет готов к чтению или записи, и отдельный поток на соединение не нужен.

Поэтому Node может держать 10 000+ открытых WebSocket-соединений, не имея 10 000 потоков. Для сети поток вообще не нужен, пока данные не готовы.

## Почему файловая система — другая история

Логичный вопрос: "если для сети есть epoll, почему `fs.readFile` использует Thread Pool, а не такой же механизм?"

```txt
Ответ: на большинстве платформ (особенно Linux) надёжного
неблокирующего API для операций с файлами на уровне ОС
не существует — в отличие от сокетов.

epoll отлично работает для сокетов, но при попытке
использовать его для обычных файлов на Linux он либо
не поддерживается, либо ведёт себя непредсказуемо
(всегда сообщает "готово").

Решение libuv: выполнить блокирующий системный вызов
(read(), open(), stat()) в отдельном потоке Thread Pool —
и когда вызов завершится (поток блокируется, но это
не главный поток!), результат передаётся обратно
в Event Loop через тот же механизм уведомлений.
```

Это объясняет, почему **операции с файлами имитируют асинхронность через потоки**, а сетевые операции — **действительно асинхронны на уровне ОС**. Для пользовательского кода разница незаметна: и там и там callback или Promise. Но если вы хотите понять, что реально потребляет ресурс Thread Pool, различие именно это.

## Полная карта: что использует Thread Pool

```txt
Используют Thread Pool:
  fs.*           (кроме fs.FSWatcher — наблюдение за файлами
                  использует platform-specific уведомления)
  crypto.pbkdf2, crypto.scrypt, crypto.randomBytes (async),
  crypto.generateKeyPair (async)
  zlib.* (gzip/gunzip/brotli — async-версии)
  dns.lookup()   — использует getaddrinfo() системы

Не используют Thread Pool (нативный async ОС):
  net, http, https, tcp, udp — epoll/kqueue/IOCP
  dns.resolve*() — использует c-ares, собственную асинхронную
                   реализацию разрешения имён DNS (DNS —
                   система доменных имён, переводит имя хоста
                   в адрес). Не системную getaddrinfo()
                   и не Thread Pool
```

### Senior-нюанс: `dns.lookup` vs `dns.resolve` — частая ловушка

```ts
// dns.lookup использует getaddrinfo() ОС → Thread Pool
// (тот же пул, что и fs/crypto/zlib!)
dns.lookup('example.com', callback);

// dns.resolve4/resolve6/resolveCname использует c-ares →
// не Thread Pool, отдельный механизм
dns.resolve4('example.com', callback);
```

Некоторые приложения разрешают много имён через `dns.lookup`. Часто это происходит неявно: `http.get` с доменным именем по умолчанию разрешает его через `lookup`. Если это идёт одновременно с тяжёлыми операциями `crypto` или `fs`, они **конкурируют за один и тот же Thread Pool**.

Эту связь мало кто проговаривает. "Медленные исходящие HTTP-запросы к внешним API" и "медленное чтение файлов" могут оказаться двумя симптомами одной причины — насыщенного Thread Pool.

## Конкретный пример "невидимого" узкого места

```ts
// ❌ На каждый запрос — bcrypt (CPU-heavy, через Thread Pool).
// CPU = central processing unit, процессор.
// Плюс чтение файла (тоже Thread Pool)
app.post('/register', async (req, res) => {
  const hash = await bcrypt.hash(req.body.password, 12); // Thread Pool
  const template = await fs.promises.readFile('welcome.html'); // Thread Pool
  // ...
});
```

```txt
При UV_THREADPOOL_SIZE=4 (по умолчанию) и 10 одновременных
регистраций:

  - 4 запроса начинают bcrypt.hash сразу → они занимают
    все 4 потока пула
  - fs.readFile этих же запросов ждёт своей очереди,
    хотя само чтение файла занимает доли миллисекунды
  - оставшиеся 6 запросов на bcrypt.hash ждут полностью

  Наблюдаемый симптом: "API стал медленным", "CPU
  не на пределе" — bcrypt быстрый, но пул
  узкий. Задержки растут нелинейно с количеством
  одновременных запросов.
```

### Решение и его границы

```bash
# Увеличение пула — снимает остроту, но не решает корневую причину
UV_THREADPOOL_SIZE=16 node app.js
```

```txt
Важно: UV_THREADPOOL_SIZE должен быть установлен до того,
как Node поставит в очередь первую задачу для пула —
то есть до любого require или вызова, который инициирует
Thread Pool (часто — до первого вызова fs или crypto).
Установка значения "по ходу выполнения" через
process.env в коде уже может не сработать, если
к этому моменту пул уже инициализирован.

Но: больше потоков = больше памяти на стеки + больше
переключений контекста на CPU с ограниченным числом ядер.
"Просто увеличить до 128" — не решение, это перенос
проблемы и потенциально новая (CPU contention).

Реальное решение для CPU-heavy операций (bcrypt, pbkdf2
с большим cost factor) — Worker Threads (см.
[Worker Threads and Cluster]), где вычисление получает
собственный выделенный поток, а не делит общий пул
с файловыми операциями всего приложения.
```

## Как диагностировать насыщение Thread Pool в production

```txt
Косвенные признаки:
  - загрузка CPU не на пределе, но p99 задержки растёт.
    p99 — это значение, ниже которого остаются 99% запросов
  - задержки растут не линейно с RPS (requests per second,
    запросов в секунду), а скачком после определённого
    уровня параллелизма
  - операции, которые "по логике" не связаны (DNS, fs,
    bcrypt), деградируют одновременно

Прямая диагностика:
  - инструменты APM (application performance monitoring —
    мониторинг производительности приложения), например
    Datadog или New Relic, показывают "thread pool queue
    time" отдельно от "execution time"
  - можно явно измерить через обёртку, засекая время
    между вызовом fs.readFile и началом выполнения callback
    относительно времени постановки в очередь
```

## Связь с другими темами

```txt
[The Event Loop]            — Thread Pool — это только один
                               из источников событий для poll-фазы;
                               сеть приходит в poll напрямую через
                               epoll/kqueue, без Thread Pool
[Worker Threads and Cluster] — правильное решение для CPU-heavy
                               задач, которое не делит ресурс
                               с fs/crypto/zlib/dns.lookup
[Memory and Garbage
 Collection]                  — ещё один источник фоновых потоков
                               в процессе (потоки V8 для GC)
```

## Типичные ошибки на интервью

- **"Node однопоточный" без уточнений**. Не упомянуть ни Thread Pool, ни фоновые потоки V8 для сборки мусора (GC). И не сказать, что "однопоточность" относится конкретно к выполнению JS.

- **Считать, что любая async-операция в Node использует Thread Pool**. Сетевые операции идут через epoll, kqueue или IOCP (I/O completion ports) — асинхронные механизмы ОС, без Thread Pool. А файловые операции, crypto и zlib пул используют.

- **Не знать про разницу `dns.lookup` vs `dns.resolve*`**. Разрешение имён через `lookup` конкурирует с fs и crypto за один и тот же пул. Разрешение через `resolve*` — нет.

- **"Просто увеличить UV_THREADPOOL_SIZE" как универсальное решение**. Это снимает только симптом, и у него есть своя цена: больше памяти на стеки потоков, больше переключений контекста. Замену Worker Threads для действительно тяжёлых вычислений это не даёт.

- **Не уметь диагностировать насыщение пула**. Ситуацию "CPU (процессор) в норме, но задержки растут" воспринимают как нерешаемую загадку. А это классический симптом конкуренции за Thread Pool.
