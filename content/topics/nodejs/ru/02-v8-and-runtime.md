# V8 и runtime Node.js

## V8 — это конвейер, а не "один компилятор"

V8 не компилирует код целиком заранее и не интерпретирует его строка за строкой бесконечно. Это многоступенчатый конвейер. Конвейер **постепенно повышает качество компиляции для горячего кода** и откатывается назад, если его предположения об этом коде оказались неверными.

```txt
Source code
    ↓
Parser → AST (Abstract Syntax Tree)
    ↓
Ignition (baseline interpreter) → Bytecode
    ↓ (если функция вызывается часто — "горячая")
TurboFan (optimizing JIT compiler, JIT = just-in-time)
    → оптимизированный машинный код
    ↑ ↓
    └── Deoptimization (если предположения нарушены —
        откат на bytecode, см. ниже)
```

Главный практический вывод из этой схемы: V8 оптимизирует код **по факту наблюдаемого поведения**, а не по статическому анализу типов. TypeScript, например, работает наоборот — он разбирает типы на этапе компиляции.

Значит, один и тот же код может выполняться с разной скоростью в зависимости от того, какие данные через него проходили ранее. Именно поэтому "тёплый старт" (warm-up) — реальное явление, и его важно учитывать при нагрузочном тестировании Node-сервисов.

## Ignition и TurboFan: baseline vs optimized

```txt
Ignition:
  - запускает функцию сразу, без задержки на компиляцию
  - генерирует компактный bytecode
  - собирает feedback (профиль типов аргументов, форм объектов)

TurboFan:
  - срабатывает, когда V8 видит, что функция "горячая"
    (вызывается много раз с одинаковым "профилем")
  - использует feedback от Ignition, чтобы сгенерировать
    машинный код, специализированный под те типы,
    которые он наблюдал
  - результат — код, который быстрее интерпретируемого
    в разы, но верен только для этого профиля типов
```

```ts
function add(a: number, b: number) {
  return a + b;
}

// Если add вызывается тысячи раз и всегда с числами —
// TurboFan сгенерирует машинный код, который ожидает
// именно числа (например, представление SMI без боксинга;
// SMI = small integer, маленькое целое)
for (let i = 0; i < 100_000; i++) add(i, i + 1);

// Внезапный вызов с другим типом — TurboFan-код больше
// не валиден для этого случая → deoptimization
add('5', '10'); // V8 откатывается на Ignition bytecode
                // для этого call site (минимум — для него)
```

## Deoptimization — обратная сторона JIT, о которой часто молчат

Деоптимизация — это не "ошибка", а штатный механизм V8. JIT здесь означает just-in-time: V8 компилирует уже во время работы программы, опираясь на предположения о коде, который он видел.

Иногда оптимизированный код встречает ситуацию, для которой он не был специализирован: другой тип аргумента, изменённая форма объекта, удалённое свойство. Тогда V8 **откатывается** на bytecode-исполнение для этого участка и теряет все преимущества TurboFan на этом пути.

```ts
// ❌ Полиморфная функция — вызывается с разными "формами" объектов
function getArea(shape) {
  return shape.width * shape.height;  // у Circle нет height!
}

getArea({ width: 10, height: 5 });          // Rectangle-like shape
getArea({ width: 10, radius: 5 });          // другая "форма" → polymorphic call site
```

Senior-нюанс: один-два полиморфных типа на точку вызова (call site) — это нормально. С небольшим числом форм V8 справляется неплохо.

Проблема начинается при **megamorphic** call sites — когда через одну и ту же функцию проходит много разных форм объектов. Тогда V8 перестаёт пытаться специализировать код и падает на самый медленный общий путь.

Значит, на горячем пути форма объектов, проходящих через функцию, реально влияет на производительность. Горячий путь здесь — это парсинг тысяч записей в цикле или обработчики middleware, которые вызываются на каждый запрос.

## Hidden Classes (Shapes) и почему форма объекта важна

V8 не хранит объекты как hash-map "имя свойства → значение" — это было бы слишком медленно для доступа к свойствам. Вместо этого каждый объект связан с **Hidden Class**; внутри движка её называют "Map" или "Shape". Hidden Class описывает раскладку свойств в памяти — примерно так же, как компилятор C++ знает смещения (offset) полей структуры.

```ts
// Оба объекта создаются с одинаковым порядком и набором свойств
const user1 = { name: 'Alice', age: 30 };
const user2 = { name: 'Bob', age: 25 };
// → user1 и user2 делят одну и ту же Hidden Class
// → функции, работающие с такими объектами, могут быть
//   мономорфными и быстрыми

// ❌ Изменение формы объекта после создания —
// создаёт новую Hidden Class для этого конкретного объекта
const user3 = { name: 'Carol', age: 28 };
user3.address = 'London';  // новая Hidden Class, отличная от user1/user2

// ❌ Удаление свойства — тоже создаёт новую (и часто
// "медленную", dictionary-mode) Hidden Class
delete user3.age;
```

```txt
Практическое следствие — конструкторы и фабрики должны
всегда инициализировать все поля объекта, даже если
значение пока неизвестно:

  ❌ class User {
       constructor(name) {
         this.name = name;
         // address добавляется позже, в другом методе
       }
     }

  ✅ class User {
       constructor(name, address = null) {
         this.name = name;
         this.address = address;  // поле есть с самого начала,
                                   // даже если значение null
       }
     }
```

Это не "микрооптимизация для энтузиастов". Возьмите код, который создаёт тысячи объектов одной формы в горячем пути — например, маппинг строк из базы данных (БД) в DTO. DTO (data transfer object) — это простой объект, единственная задача которого переносить данные между слоями.

Здесь одинаковая форма объектов решает вполне конкретную вещь: останется ли V8 в "быстром" режиме или перейдёт на dictionary-режим хранения свойств.

## Inline Caches — кеш "где искать свойство"

Inline Cache (IC) — механизм, дополняющий Hidden Classes. Возьмите любое место в коде, где происходит доступ к свойству, например `obj.name`. V8 запоминает Hidden Class объекта и смещение свойства **прямо в этом месте кода**.

```txt
function getName(obj) {
  return obj.name;  // ← здесь V8 создаёт Inline Cache
}

Первый вызов getName(user1):
  - V8 видит Hidden Class объекта user1
  - запоминает: "для этой Hidden Class, name находится по offset 0"
  - IC становится monomorphic (1 запомненная форма)

Повторные вызовы с объектами той же Hidden Class:
  - V8 сразу читает offset 0, без поиска свойства — очень быстро

Вызов с объектом другой Hidden Class:
  - IC становится polymorphic (запоминает 2-4 формы)
  - при превышении лимита форм → megamorphic, IC перестаёт
    помогать, используется generic lookup
```

Hidden Classes и Inline Caches — две стороны одной идеи. JS динамичен: любое свойство можно добавить или удалить когда угодно. V8 пытается превратить это в статические, предсказуемые структуры — похожие на структуры скомпилированных языков. Работает это только пока код действительно ведёт себя предсказуемо.

## Heap: где V8 хранит объекты, и почему это важно для GC

Данные лежат в двух областях: stack и heap. От того, куда попал объект внутри heap, зависит, как с ним будет работать GC (garbage collector, сборщик мусора — часть V8, которая освобождает неиспользуемую память).

```txt
Stack:
  - примитивы, ссылки, кадры вызовов функций (frames)
  - управляется автоматически при входе/выходе из функции

Heap — разделён на "поколения" (generational hypothesis:
большинство объектов умирают быстро):

  New Space (Young Generation):
    - новые объекты создаются здесь
    - небольшой размер → сборка мусора здесь (Scavenger) —
      частая, но быстрая (большинство объектов уже мертвы)

  Old Space (Old Generation):
    - объекты, "переживающие" несколько циклов Scavenger,
      перемещаются ("promotion") сюда
    - сборка здесь (Mark-Compact/Mark-Sweep) — реже,
      но дороже (полный обход графа объектов)
```

Алгоритмы сборки мусора, практические паттерны утечек памяти и heap snapshot разобраны полностью в [Память, Heap, Stack и сборка мусора](./08-memory-garbage-collection.md). Здесь важно зафиксировать более узкую связь.

Умрёт ли объект, созданный в New Space, быстро — или "повысится" в Old Space, напрямую завязано на Hidden Classes и форму объектов. Поэтому переиспользование объектов одной формы в горячих циклах делает сразу две вещи. Оно ускоряет доступ к свойствам и снижает давление на GC.

## Runtime = V8 + Node APIs + libuv

```txt
V8 умеет:           V8 не умеет (и это нормально —
  - выполнять JS       не его ответственность):
  - управлять heap      - читать файлы
  - делать JIT/деопт     - открывать сокеты
  - GC                   - работать с таймерами ОС
                           (операционной системы)
                         - разрешать доменные имена (DNS)
```

Node заполняет этот пробел:

```txt
fs, net, http, crypto, timers, dgram, ...
    ↓ (C++ bindings)
libuv — предоставляет event loop и thread pool
    ↓
системные вызовы ОС: epoll (Linux), kqueue (macOS),
IOCP (I/O completion ports, Windows), читать файл, ...
```

Одна строка кода проходит через все три слоя. Когда вы пишете `await fs.promises.readFile(...)`:

1. V8 выполняет ваш async-код и управляет Promise.
2. Node API оборачивает вызов в формат, понятный libuv.
3. libuv решает, как физически выполнить операцию — через thread pool или через асинхронный API операционной системы (ОС).

Сами слои разобраны в [Event Loop](./03-event-loop.md) и [libuv and the Thread Pool]. Часть про Promise — в [Microtasks, Macrotasks и process.nextTick](./04-microtasks-macrotasks-nexttick.md).

## Практический вывод: когда V8-детали реально имеют значение

```txt
Имеет значение:
  - горячие пути с тысячами/миллионами итераций (парсинг,
    маппинг данных, вычисления в цикле)
  - библиотеки и фреймворки, через которые проходит весь
    трафик: маппинг строк в объекты в ORM (object-relational
    mapper), валидаторы, сериализаторы
  - выбор структур данных для часто мутируемых объектов
    с непредсказуемой формой (Map вместо обычного объекта,
    если ключи динамические)

Почти никогда не имеет значения:
  - бизнес-логика уровня "обработать один HTTP-запрос" —
    разница в наносекундах на доступ к свойству объекта
    исчезает на фоне миллисекунд I/O (запрос к БД, к сети)
  - микрооптимизации, ухудшающие читаемость кода ради
    мономорфности точки вызова, которая вызывается 10 раз
    за всё время жизни процесса
```

Эта калибровка сознательная, и её стоит проговорить на интервью. Знание Hidden Classes и IC показывает, что вы понимаете движок. Применять это знание как безусловное правило — другое дело.

Возьмите правило "всегда инициализируй все поля в конструкторе, даже неиспользуемые". В коде, который не лежит на горячем пути, это попытка оптимизировать там, где оптимизировать нечего. На senior-собеседовании это тоже сигнал — и отрицательный.

## Типичные ошибки на интервью

- **"V8 интерпретирует JS"** — без упоминания Ignition (baseline bytecode) и TurboFan (оптимизирующий JIT). Современный V8 — это многоступенчатый конвейер, а не чистый интерпретатор.

- **Hidden Classes как "просто факт из Википедии"** — без связи с конкретным следствием. А следствие такое: непоследовательная инициализация полей или добавление и удаление свойств на ходу создают новые Hidden Classes и могут деоптимизировать горячие функции.

- **Не знать о деоптимизации** — воспринимать JIT как "один раз скомпилировалось и всегда быстро", не понимая, что V8 может откатиться на bytecode, если предположения о типах нарушены.

- **Путать V8 и Node** — приписывать V8 возможности fs/net/http, которые на самом деле предоставляются Node через libuv и C++ биндинги.

- **Применять микрооптимизации не там, где они нужны** — переусложнять обычный бизнес-код "ради V8", когда реальное узкое место — I/O, а не доступ к свойствам объекта.
