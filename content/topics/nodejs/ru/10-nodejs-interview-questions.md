## Группа 1: Runtime, V8, npm

**1. Что такое Node.js?**
Node.js — это **runtime**: среда выполнения, которая объединяет V8 (движок JavaScript от Google) с libuv и набором встроенных API. Это не "язык программирования" и не "фреймворк". См. [Основы Node.js](./01-nodejs-fundamentals.md).

- V8 выполняет ваш JS.
- libuv даёт event loop, thread pool и асинхронный I/O.
- Встроенные Node API (`fs`, `http`, `crypto` и т.д.) в браузере недоступны.

**2. Чем Node отличается от браузера, если оба используют V8?**
Различается **набор доступных API**, а JS в обоих случаях выполняет один и тот же V8. Браузер даёт DOM (объектная модель документа), `window` и `fetch` через свои Web API. Node даёт `fs`, `process` и `net` через libuv. Это два разных "хоста" вокруг одного движка.

**3. Что делает V8 помимо "выполнения JS"?**
Он прогоняет код через целый конвейер компиляции. Кроме этого он держит Hidden Classes и Inline Caches для быстрого доступа к свойствам плюс поколенческий GC (сборщик мусора). См. [V8 и runtime Node.js](./02-v8-and-runtime.md).

```txt
Parser → AST (abstract syntax tree, синтаксическое дерево)
       → Ignition   интерпретатор байткода — быстрый старт
       → TurboFan   JIT-компилятор (just-in-time), который
                     оптимизирует горячий код
       → Deopt      возможен при изменении формы объектов
```

**4. Что такое Hidden Class и зачем он нужен?**
V8 присваивает скрытый класс каждой "форме" объекта, то есть каждому набору ключей в определённом порядке. Это позволяет JIT-компилятору (just-in-time) генерировать оптимизированный код доступа к свойствам по фиксированному смещению, как в статически типизированных языках.

Добавьте или удалите свойства в разном порядке у объектов одного "логического типа" — и получите разные Hidden Classes. Inline Cache тогда становится polymorphic, затем megamorphic, и код деоптимизируется.

## Группа 2: Event Loop, микротаски, process.nextTick

**5. Что такое Event Loop простыми словами?**
Это **механизм с фазами**, а не "очередь задач". Фазы идут так: timers → pending callbacks → idle, prepare → poll → check → close callbacks. На каждой итерации он выбирает готовые callback-функции и выполняет их. Между **каждой** такой функцией он полностью опустошает очередь `process.nextTick` и очередь микротасков. См. [Event Loop](./03-event-loop.md).

**6. Перечислите фазы Event Loop и что происходит в каждой.**
Фазы ниже идут в фиксированном порядке. В фазе `poll` процесс может заблокироваться и ждать на механизме готовности операционной системы (ОС). Это epoll в Linux, kqueue в macOS, IOCP (input/output completion ports) в Windows.

```txt
timers            → готовые setTimeout/setInterval
pending callbacks → некоторые системные операции
poll              → основная фаза: I/O callbacks; здесь же
                     блокируется, если делать больше нечего
check             → setImmediate
close callbacks   → события 'close'
```

**7. Чем microtask queue отличается от macrotask queue, и когда происходит переключение?**
Очередь микротасков (`Promise.then`, `queueMicrotask`, async/await) опустошается **полностью** после завершения **любой** операции. Это касается и каждого отдельного callback внутри фазы poll, а не только одного раза "после скрипта".

Макротаски (timers, `setImmediate`, I/O) ждут следующей фазы цикла. См. [Microtasks, Macrotasks и process.nextTick](./04-microtasks-macrotasks-nexttick.md).

**8. Почему `Promise.then` выполняется раньше `setTimeout(fn, 0)`?**
Потому что очередь микротасков имеет приоритет над **любой** фазой Event Loop. Event Loop не переходит к следующей задаче, включая таймеры, пока эта очередь не опустеет полностью.

**9. Что такое `process.nextTick` и чем он отличается от microtask queue?**
Это отдельная очередь с **ещё более высоким** приоритетом, чем очередь микротасков. Она опустошается первой. Всё, что добавлено в неё **во время** опустошения, тоже будет обработано до перехода к микротаскам.

```txt
Приоритет, от высшего:
  1. очередь process.nextTick — опустошается полностью
  2. очередь микротасков      — опустошается полностью
  3. следующая фаза Event Loop (timers, poll, check, ...)
```

**10. Почему `process.nextTick` может быть опасен?**
Рекурсивный вызов `process.nextTick` внутри себя создаёт starvation (голодание). Event Loop **никогда** не доходит до I/O и таймеров, поэтому процесс перестаёт отвечать на запросы — но не "падает". Реалистичный пример: рекурсивная обработка очереди сообщений через `nextTick` вместо `setImmediate`.

**11. Чем `setImmediate` отличается от `setTimeout(fn, 0)`?**
На верхнем уровне порядок **не гарантирован**: он зависит от точности таймера операционной системы. **Внутри** I/O callback `setImmediate` **всегда** выполнится раньше `setTimeout(fn, 0)`. Фаза `check` идёт сразу после `poll`, а `timers` — только на следующей итерации цикла.

## Группа 3: libuv, Thread Pool, Worker Threads, Cluster

**12. Node однопоточный или многопоточный?**
И то и другое — смотря про что говорить. Ваш JS-код выполняется в **одном** потоке (V8 плюс Event Loop). Но процесс Node содержит ещё N потоков Thread Pool в libuv (по умолчанию 4) и M фоновых потоков GC в V8. См. [libuv and the Thread Pool] и [Память, Heap, Stack и сборка мусора](./08-memory-garbage-collection.md).

**13. Какие операции используют Thread Pool, а какие — нет?**
Только узкий набор операций:

```txt
Используют Thread Pool:
  fs.*
  crypto.pbkdf2 / scrypt / randomBytes  (async-формы)
  zlib.*                                (async-формы)
  dns.lookup                            (через getaddrinfo)

Не используют:
  net / http / tcp  → epoll, kqueue, IOCP: нативные
                       асинхронные интерфейсы ОС
  dns.resolve*      → через c-ares, отдельный механизм
```

**14. Почему `fs.readFile` не блокирует Event Loop?**
Сам системный вызов `read()` **блокирующий**. Но Node выполняет его на **отдельном** потоке Thread Pool, а не на главном JS-потоке. Когда вызов завершается, результат приходит через тот же механизм уведомлений, что и сетевые события.

**15. Когда нужны Worker Threads, и почему не Thread Pool?**
Thread Pool **не выполняет** ваш JS. Он обслуживает только встроенные блокирующие операции операционной системы. Поэтому CPU-bound код на JS требует Worker Thread с собственным экземпляром V8.

CPU-bound значит, что работа загружает центральный процессор (CPU), а не ждёт I/O: обработка изображений, свой хэшинг, парсинг больших документов. Worker Thread — единственный способ убрать такую работу с главного потока. См. [Worker Threads и Cluster](./06-worker-threads-cluster.md).

**16. Чем Worker Threads отличаются от Cluster?**
Несколько потоков в одном процессе против нескольких полностью независимых процессов:

```txt
                 Worker Threads      Cluster
──────────────────────────────────────────────────────────
Единица          потоки внутри       полностью независимые
                  одного процесса     процессы
V8/Event Loop    свой на поток       свой на процесс
Общая память     да, через           нет
                  SharedArrayBuffer
Общий порт       —                   да, через round-robin
                                      или SO_REUSEPORT
```

**17. "Cluster устарел из-за Docker" — согласны?**
Не совсем. Если контейнеру выделено 4 виртуальных ядра (4 vCPU), а внутри запущен **один** процесс Node, JS event loop всё равно использует только 1 ядро. Это решают двумя способами: больше реплик контейнера либо Cluster внутри контейнера. В Kubernetes (k8s) чаще предпочитают реплики. Компромиссы у этих вариантов разные — по наблюдаемости и по graceful shutdown.

## Группа 4: Streams, Backpressure, Buffer

**18. Что такое Stream и почему он "лучше" readFile?**
Главное свойство — **автоматическая** синхронизация скорости producer и consumer, то есть backpressure, а не просто "обработка по частям". `readFile` грузит весь файл в память. Stream держит в буфере не больше `highWaterMark` — по умолчанию 64KB начиная с Node.js 22, до этого 16KB. См. [Streams и Backpressure](./07-streams-and-backpressure.md).

**19. Четыре типа streams и где они применяются?**
Четыре типа, по направлению потока данных:

```txt
Readable   — источник              (fs.createReadStream)
Writable   — получатель            (fs.createWriteStream)
Duplex     — оба направления сразу (TCP-сокет; TCP — это
              transmission control protocol, транспортный
              протокол)
Transform  — Duplex плюс преобразование данных (gzip,
              парсеры)
```

**20. Что реально происходит при backpressure?**
`writeStream.write(chunk)` возвращает `false`, когда внутренний буфер превысил `highWaterMark`. Данные при этом всё равно записываются в буфер. `false` — это только сигнал: "притормози producer". Если его игнорировать, буфер растёт неограниченно. `.pipe()` реагирует на этот сигнал и на событие `'drain'` автоматически, через `pause()` и `resume()`.

**21. Чем `pipeline()` лучше `.pipe()`?**
При ошибке в середине цепочки `.pipe()` не освобождает ресурсы: оставшиеся потоки и файловые дескрипторы остаются открытыми. Функция `pipeline()` вызывает `destroy()` на **всех** потоках цепочки, если любой из них упал. Плюс она поддерживает async/await.

**22. Что такое Buffer и почему он "не считается" в heapUsed?**
`Buffer` — это представление бинарных данных, физически размещённое **вне** обычного V8 heap, в "external"-памяти. Поэтому отслеживание утечек только по `heapUsed` пропустит рост из-за удерживаемых объектов Buffer. Смотреть нужно ещё и на `rss` (resident set size) и `external`.

## Группа 5: Память и сборка мусора

**23. Stack vs Heap — в чём разница?**
На Stack лежат кадры вызовов, примитивы и **ссылки**. Он не управляется GC: память освобождается автоматически при выходе из функции. В Heap лежат объекты, массивы, функции и замыкания, и он управляется GC. Утечки происходят только в Heap. См. [Память, Heap, Stack и сборка мусора](./08-memory-garbage-collection.md).

**24. Как GC решает, что удалить?**
По достижимости от Root Objects: global, активные кадры вызовов, замыкания. Всё, что недостижимо, считается мусором.

```txt
Mark     → помечает все объекты, достижимые от корня
Sweep    → освобождает непомеченные объекты
Compact  → дефрагментирует Old Space, сдвигая живые
            объекты вместе
```

**25. Что такое поколенческий GC, и почему он эффективен?**
New Space — молодое поколение — очищается алгоритмом Scavenge. Scavenge копирующий, и его стоимость пропорциональна **количеству живых** объектов, а не объёму мусора. Большинство объектов умирают быстро, поэтому Scavenge почти всегда быстрый.

Объекты, выжившие после 2 циклов, перемещаются в Old Space, который очищается более дорогим Mark-Sweep-Compact.

**26. GC всегда останавливает приложение полностью?**
Уже нет. Современный V8 использует Incremental, Concurrent и Parallel Marking и Compaction на фоновых потоках, и это резко сокращает паузы. Но финальная синхронизация и Sweep всё ещё требуют короткой паузы главного потока. При большом heap эта пауза видна на p99 latency — самом медленном 1% запросов.

**27. Назовите 3 классических паттерна утечки памяти в Node.**
Все три — ошибки в графе ссылок, а не в GC:

```txt
1. Глобальный массив или кэш, который никогда не очищается:
   растёт по setInterval или на каждый запрос.
2. Не удалённые listeners у EventEmitter. Хуже всего, когда
   listener захватывает в замыкание короткоживущий объект
   (socket), а сам emitter живёт долго.
3. Замыкание, удерживающее большой объект, который был
   нужен только при инициализации.
```

**28. Почему `process.memoryUsage().heapUsed` не показывает всю утечку?**
`heapUsed` — это только V8 heap. `external` и `arrayBuffers` — содержимое `Buffer` и `TypedArray` — отдельная категория. В `heapUsed` они не входят, но влияют на `rss` и на риск OOM Kill (OOM — out of memory, нехватка памяти).

**29. Контейнер падает по OOM, хотя V8 "думает", что памяти достаточно — почему?**
По умолчанию V8 ставит лимит Old Space по памяти **всей машины**, а не по лимиту контейнера в cgroup. Cgroup — это control-группа Linux, которая ограничивает ресурсы контейнера. Поэтому задайте `--max-old-space-size` явно и оставьте запас под `external`-память, которую этот флаг не ограничивает.

## Группа 6: Модули — CommonJS vs ES Modules

**30. Главное отличие CommonJS от ESM — это не только синтаксис. В чём ещё?**
ESM (ES Modules — ES означает ECMAScript) отличается от CommonJS тем, как модуль загружается и что даёт импорт. В CommonJS `require()` — синхронный вызов функции, а экспорт — **копия** значения на момент вызова.

В ESM загрузка идёт в 3 фазы: Construction → Instantiation → Evaluation. Импорт там — это **live binding**, живая связь с "ячейкой" в исходном модуле. См. [CommonJS vs ES Modules](./09-commonjs-vs-esm.md).

**31. Как circular dependency ведёт себя в CommonJS vs ESM?**
Оба варианта её переживают, но результат разный:

```txt
CommonJS → модуль получает частично заполненный
            module.exports: только то, что экспортировано
            до строки require(), вызвавшей цикл

ESM      → функции работают лучше благодаря hoisting и
            live bindings. Но let/const с вычисляемым
            значением могут оказаться в temporal dead zone
            (TDZ) при доступе во время цикла
```

**32. Может ли CommonJS импортировать чистый ESM-пакет напрямую через `require()`?**
Нет. `require()` синхронный, а ESM требует асинхронной загрузки. Единственный путь — динамический `import()`, он асинхронный. Обратное направление работает: когда ESM импортирует CommonJS (CJS), `module.exports` становится `default`.

**33. Что такое "dual package hazard"?**
Если библиотека поставляет и CJS-, и ESM-сборку, одна часть приложения может импортировать её через `require()`, а другая — через `import()`. Node тогда загружает **два** отдельных модуля с **двумя** экземплярами внутреннего состояния. Если библиотека использует Singleton, приложение получает два не связанных между собой Singleton.

## Самый частый "итоговый" senior-вопрос

**Почему Node способен обрабатывать тысячи соединений одновременно с одним JS-потоком?**

Слабый ответ: "Event Loop и неблокирующий I/O".

Сильный ответ раскладывает это на конкретные механизмы:

- Сетевые операции обрабатываются через epoll, kqueue или IOCP. **Один** поток может отслеживать тысячи файловых дескрипторов, без отдельного потока на каждое соединение (см. [libuv and the Thread Pool]).
- Для операций без асинхронного API ОС — файлы, часть crypto — есть Thread Pool, ограниченный пул фоновых потоков.
- Event Loop с фазами гарантирует, что готовые callback-функции обрабатываются по очереди. Они не блокируют друг друга дольше, чем длится синхронная часть каждой из них (run-to-completion, см. [Event Loop](./03-event-loop.md)).
- Ограничение модели: если один callback **долго** выполняется синхронно (CPU-bound), **все** остальные соединения ждут. Поэтому для CPU-bound работы нужны Worker Threads, а для утилизации нескольких ядер под I/O-bound трафик — Cluster или несколько реплик.

## Типичные ошибки на интервью

- **Заучивание ответов без понимания механизма** — любая модификация вопроса ("а что если добавить ещё один await/listener/процесс?") ломает заученный ответ.

- **Игнорирование уточняющих вопросов** — каждый из 33 вопросов выше — это входная точка в более глубокий разговор. Неготовность к "а почему?" — главный признак поверхностной подготовки.

- **Путать "что использует Thread Pool" с "что асинхронно"** — почти всё в Node асинхронно. Но Thread Pool используется лишь для узкого набора операций: `fs`, `crypto`, `zlib`, `dns.lookup`.

- **Не связывать темы между собой** — например, не видеть связь между Memory/GC и Cluster. Несколько процессов с меньшим heap снижают влияние пауз GC. Другая упущенная связь — Streams и Event Loop: события потоков идут через тот же цикл.
