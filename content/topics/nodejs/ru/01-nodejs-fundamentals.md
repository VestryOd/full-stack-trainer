# Основы Node.js

## Node.js — это runtime, а не язык и не фреймворк

```txt
JavaScript — язык (спецификация ECMAScript: синтаксис, типы,
  Promise, async/await, ...)

Node.js — runtime: программа на C++, которая встраивает движок
  V8 и добавляет к нему API, которых в спецификации языка нет
  (fs, net, process, Buffer, ...)

Express/Nest/Fastify — фреймворки над Node.js
```

Путаница "Node = V8" — частая, и её стоит разобрать. V8 выполняет JS-код и управляет памятью: это heap и сборщик мусора (GC, garbage collector — часть движка, которая освобождает неиспользуемую память). И то и другое разобрано в [Memory and Garbage Collection].

Но V8 **не знает**, что такое файл или сокет TCP. TCP (Transmission Control Protocol) — это протокол с установлением соединения, на котором работает почти весь сетевой обмен.

Эти возможности предоставляет сам Node через C++ биндинги к libuv и другим библиотекам. Когда вы вызываете `fs.readFile(...)`, JS-код в V8 вызывает C++ функцию. Эта функция делегирует операцию libuv (см. [libuv and the Thread Pool]).

```txt
┌─────────────────────────────────────────┐
│             Node.js Process             │
│                                         │
│ ┌────────────┐   ┌────────────────────┐ │
│ │ V8         │←──│ Node.js APIs       │ │
│ │ (выполняет │   │ (fs, net, http,    │ │
│ │ JS, heap,  │   │ crypto, Buffer...) │ │
│ │ GC)        │   └─────────┬──────────┘ │
│ └────────────┘             ▼            │
│                     ┌──────────────┐    │
│                     │ libuv        │    │
│                     │ (Event Loop, │    │
│                     │ Thread Pool) │    │
│                     └──────────────┘    │
└─────────────────────────────────────────┘
```

Эта диаграмма — каркас для всего раздела. У каждого блока своя статья:

- V8 → [V8 and the Runtime], [Memory and Garbage Collection]
- Event Loop → [The Event Loop], [Microtasks, Macrotasks, and process.nextTick]
- Thread Pool → [libuv and the Thread Pool]
- Несколько процессов и потоков → [Worker Threads and Cluster]

## Почему "один поток" — это осознанный архитектурный выбор, а не ограничение

Когда Node появился в 2009 году, доминирующая модель серверов была "поток (или процесс) на каждое соединение" (Apache prefork/threaded). Проблема такой модели — цена потока. Поток дорого стоит: память на стек плюс переключение контекста. И большую часть времени поток, обслуживающий сетевой запрос, **ничего не делает**. Он просто ждёт ответа от базы данных (БД), диска или другого сервиса.

```txt
Традиционная модель (1 поток = 1 запрос):
  10,000 одновременных соединений → 10,000 потоков,
  каждый в основном в состоянии "жду I/O"
  → память и переключения контекста становятся узким
  местом задолго до того, как CPU (central processing
  unit, процессор) реально загружен

Node-модель (1 поток выполняет JS, I/O делегируется):
  10,000 соединений → 1 основной поток обрабатывает события
  по мере готовности I/O-операций
  → память на стеки не тратится, переключений контекста нет
```

Ключевой нюанс, который часто упускают: "single-threaded" относится **только к выполнению вашего JS-кода**. Сам процесс Node — многопоточный.

Внутри работает Thread Pool libuv: по умолчанию 4 потока, см. [libuv and the Thread Pool]. Пул берёт на себя операции, у которых нет асинхронного системного API — часть файловой системы, некоторые криптографические функции и DNS. DNS — это система доменных имён, которая переводит имя хоста в адрес IP (Internet Protocol). Плюс к пулу V8 держит свои фоновые потоки для сборки мусора.

Значит, "один поток" описывает модель программирования: в вашем коде нет гонок данных между двумя кусками JS. Про физическое число потоков операционной системы (ОС) в процессе это ничего не говорит.

## I/O-bound vs CPU-bound — где граница на самом деле проходит

Граница проходит по тому, на что уходит время. I/O-bound работа ждёт: диск, сеть, базу данных. CPU-bound работа считает и занимает процессор (CPU, central processing unit).

```txt
I/O-bound (Node — отличный выбор):
  - HTTP/REST API, GraphQL
    (REST = ресурсы адресуются через URL, действия над
     ними задаются методами HTTP)
  - WebSocket / realtime
  - Reverse proxy / API Gateway
  - Streaming (видео, файлы — см. [Streams and Backpressure])
  - BFF (Backend for Frontend) — много параллельных запросов
    к другим сервисам, минимум собственных вычислений

CPU-bound (Node работает хуже "из коробки"):
  - Обработка изображений/видео
  - Сложные вычисления (например, шифрование больших объёмов,
    парсинг огромных документов синхронно)
  - Machine Learning inference
```

Но "Node плохо подходит для CPU-bound" — упрощение, которое стоит уточнить на интервью. Проблема не в том, что Node "не может" делать вычисления. Проблема в том, что **любая синхронная CPU-операция блокирует единственный поток, выполняющий event loop**. Пока она выполняется, Node не может обработать **ни одно** другое событие — включая входящие HTTP-запросы от других пользователей.

```ts
// ❌ Блокирует event loop на время выполнения —
// все остальные запросы к серверу "зависают" на это время
app.get('/hash', (req, res) => {
  const hash = crypto.pbkdf2Sync(req.query.password, 'salt', 100_000, 64, 'sha512');
  res.json({ hash: hash.toString('hex') });
});

// ✅ Выносим CPU-bound работу в Worker Thread —
// event loop основного потока остаётся свободным
// (полный разбор — в [Worker Threads and Cluster])
app.get('/hash', async (req, res) => {
  const hash = await runInWorker('hash', req.query.password);
  res.json({ hash: hash.toString('hex') });
});
```

К этой идее возвращаются многие темы раздела. "Node плохо подходит для CPU-bound" — не абсолютная истина, а следствие архитектуры с одним JS-потоком. И у этого следствия есть конкретные решения: Worker Threads, Cluster, выгрузка работы в отдельный сервис.

## EventEmitter — основа, на которой построен весь Node

Большая часть встроенных API Node (HTTP-сервер, потоки, процессы) — это `EventEmitter` под капотом.

```ts
import { EventEmitter } from 'node:events';

const emitter = new EventEmitter();

emitter.on('userCreated', (user) => {
  console.log('Welcome email queued for', user.email);
});

emitter.emit('userCreated', { email: 'alice@example.com' });
```

### Senior-нюанс №1: событие `'error'` — особый случай

```ts
// ❌ Если на EventEmitter (или Stream, Socket, ...) нет обработчика
// 'error', а событие 'error' эмитится — Node выбрасывает исключение
// и (по умолчанию) завершает процесс, даже если try/catch обернёт
// код вокруг emitter
const socket = net.connect(...);
socket.emit('error', new Error('ECONNRESET')); // → process crash

// ✅ Всегда подписывайтесь на 'error' у тех EventEmitter, которые
// могут его эмитить (сокеты, потоки, дочерние процессы)
socket.on('error', (err) => {
  logger.error('Socket error', err);
});
```

Это не абстрактная рекомендация "на всякий случай". Такое поведение среди всех событий Node есть только у `'error'`. И оно регулярно ловит даже опытных разработчиков при работе с сетевыми сокетами или дочерними процессами.

### Senior-нюанс №2: утечки памяти через накопление обработчиков

```ts
// ❌ На каждый HTTP-запрос подписываемся на общий emitter,
// но никогда не отписываемся — обработчики накапливаются,
// Node выведет предупреждение "MaxListenersExceededWarning"
// после 10 обработчиков по умолчанию, и это сигнал реальной
// утечки памяти (каждый обработчик держит замыкание с req/res)
app.get('/subscribe', (req, res) => {
  eventBus.on('update', (data) => res.write(JSON.stringify(data)));
});

// ✅ Снимаем обработчик при закрытии соединения
app.get('/subscribe', (req, res) => {
  const handler = (data: unknown) => res.write(JSON.stringify(data));
  eventBus.on('update', handler);
  req.on('close', () => eventBus.off('update', handler));
});
```

`MaxListenersExceededWarning` часто воспринимают как "просто предупреждение, можно игнорировать". На практике это почти всегда индикатор утечки, и причин обычно две:

- отписки нет;
- emitter создан не там, где должен быть — новый `EventEmitter` на каждый запрос вместо одного общего.

## process — интерфейс к окружению, в котором живёт приложение

```ts
process.env.NODE_ENV     // переменные окружения — конфигурация (см. 12-factor app)
process.argv             // аргументы командной строки
process.pid               // id процесса (PID) — для логов/мониторинга
process.exitCode          // код завершения: 0 = успех, != 0 = ошибка.
                          // Его читают CI (continuous integration —
                          // автоматическая сборка и проверка) и
                          // оркестратор контейнеров.
```

### Senior-нюанс: graceful shutdown через сигналы

```ts
// ❌ Процесс убивается мгновенно (docker stop, k8s rolling update) —
// активные запросы и соединения с БД прерываются на середине
process.on('SIGTERM', () => process.exit(0));

// ✅ Graceful shutdown: перестаём принимать новые соединения,
// даём текущим запросам завершиться, закрываем пул соединений к БД
process.on('SIGTERM', async () => {
  server.close(() => {           // перестать принимать новые соединения
    db.pool.end().then(() => {   // закрыть соединения с БД
      process.exit(0);
    });
  });

  // safety net: если что-то зависло — принудительно выйти через 10 сек
  setTimeout(() => process.exit(1), 10_000);
});
```

Это напрямую связано с тем, как оркестратор раскатывает деплои. Kubernetes и ECS (Elastic Container Service — сервис запуска контейнеров в Amazon Web Services) посылают `SIGTERM` **до** того, как контейнер будет убит. `SIGKILL` приходит позже, после grace period — обычно через 30 секунд.

Приложение, которое не обрабатывает `SIGTERM`, при каждом деплое обрывает активные запросы пользователей. Это частая причина "странных ошибок только во время деплоя", и интервьюеры любят проверять её у backend-кандидатов.

## npm-экосистема: масштаб как преимущество и как риск

```txt
Преимущество:
  практически любая задача (парсинг, валидация, работа с БД,
  криптография) уже решена и опубликована в npm

Риск (supply chain):
  типичный проект на Node имеет сотни транзитивных
  зависимостей — вы доверяете коду, который не писали
  и, скорее всего, не читали, от десятков разных авторов
```

Senior-нюансы, которые стоит знать:

```txt
- package-lock.json / yarn.lock / pnpm-lock.yaml — фиксируют
  точные версии всего дерева зависимостей. Без lock-файла
  "npm install" в CI и на машине разработчика может установить
  разные patch-версии транзитивных пакетов — источник
  "у меня работает, а в проде не работает"

- Semver (^1.2.3 vs ~1.2.3 vs 1.2.3) — "^" разрешает minor/patch
  обновления автоматически; для production-кода многие команды
  предпочитают точные версии + Dependabot/Renovate с review,
  а не "молчаливые" автообновления

- npm audit / Snyk и т.п. — поиск известных уязвимостей
  в зависимостях. Это не "на усмотрение аккуратных команд",
  а часть стандартного CI-пайплайна для серьёзного
  backend-проекта

- postinstall-скрипты — пакет может выполнять произвольный код
  при установке; это реальный вектор атаки (известны случаи
  компрометации популярных пакетов с майнингом/кражей токенов
  через postinstall)
```

## Типичные ошибки на интервью

- **"Node = V8"** — не различать движок (выполнение JS, память, GC) и runtime (предоставляет fs/net/process через C++ биндинги и libuv).

- **"Node однопоточный, точка"** — без уточнения, что однопоточность касается выполнения JS-кода, а сам процесс использует Thread Pool и потоки V8 для GC.

- **"Node не подходит для CPU-задач"** без объяснения **механизма**: блокируется единственный поток, который выполняет event loop. И без упоминания решений — Worker Threads или вынос в отдельный сервис.

- **Не подписываться на `'error'` у EventEmitter/Stream/Socket** — и не знать, что необработанный `'error'` приводит к падению процесса, в отличие от любого другого события.

- **Игнорировать `SIGTERM`** — не понимать связь между сигналами процесса и graceful shutdown при деплоях в контейнеризированной среде.

- **Недооценивать риски supply chain** — рассматривать npm-зависимости как "бесплатный и безопасный" код без упоминания lock-файлов, semver-стратегии и аудита уязвимостей.
