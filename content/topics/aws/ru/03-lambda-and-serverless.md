# Lambda и Serverless

## Что такое AWS Lambda и модель Serverless

Lambda — функция как сервис (FaaS): вы загружаете код, а AWS (Amazon Web Services) обеспечивает инфраструктуру, масштабирование и мониторинг. «Serverless» не означает отсутствие серверов — они существуют, но разработчик ими не управляет.

Разницу проще всего увидеть как два списка дел.

**Традиционный EC2 (Elastic Compute Cloud)**

- Поднять виртуальную машину.
- Настроить операционную систему и среду выполнения.
- Задеплоить приложение.
- Настроить автомасштабирование.
- Патчить операционную систему.
- Платить 24/7 за время работы.

**Lambda**

- Загрузить код.
- Настроить триггер и объём памяти.
- Всё остальное делает AWS.

**Модель оплаты Lambda**

- $0.20 за 1 млн вызовов.
- $0.0000166667 за гигабайт-секунду.
- Free Tier: 1 млн вызовов в месяц плюс 400k гигабайт-секунд, навсегда.

Возьмите 100k вызовов в месяц при 128 мегабайтах (MB) памяти и 200 мс на вызов. Стоимость выйдет около $0.00, потому что укладывается во Free Tier. А EC2 `t3.micro` стоит около $8 в месяц даже без нагрузки.

## Execution Model — жизненный цикл функции Lambda

Каждый вызов — это либо холодный старт, либо тёплый, и разница между ними в четырёх шагах против одного.

**Холодный старт — новая среда исполнения**

1. Скачать пакет развёртывания: zip-архив или образ контейнера.
2. Запустить песочницу среды выполнения для Node.js, Python или Java.
3. Выполнить код инициализации вне обработчика: импорты, подключения к базе.
4. Вызвать `handler(event, context)`.

**Тёплый старт — существующая среда исполнения**

1. Вызвать `handler(event, context)`. Это весь список.

После вызова контейнер «заморожен» примерно на 5-15 минут. Следующий вызов будет тёплым стартом, если контейнер ещё жив, и холодным, если уже нет.

Параллелизм считается по вызовам: каждый **одновременный** вызов получает отдельную среду исполнения. 100 одновременных запросов — это 100 контейнеров или 100 холодных стартов, если они первые. Конкурентность Lambda наращивает сама, до лимита аккаунта, а он по умолчанию равен 1000.

## Cold Start — причины, измерение, оптимизация

Холодный старт — это время, которое Lambda тратит на постройку свежей среды исполнения до запуска вашего обработчика. Складывается оно из трёх вещей: времени инициализации среды выполнения, размера пакета и кода инициализации.

Как это выглядит по стекам:

- Тяжёлый — Java Spring или NestJS: 2-5 секунд.
- Средний — Node.js с TypeORM и множеством импортов: 500-1500 мс.
- Лёгкий — бинарник на Go или Rust: 50-100 мс.

**1. Минимизируйте размер бандла.** Возьмите esbuild или tsup вместо webpack. Пусть tree shaking выбросит всё, что вы не импортируете, и никогда не тяните весь SDK (software development kit), когда хватает одного клиента.

```typescript
// ПЛОХО: в бандл попадает весь SDK
import AWS from 'aws-sdk';

// ХОРОШО: только тот клиент, который вы реально вызываете
import { S3Client } from '@aws-sdk/client-s3';
```

**2. Ленивая инициализация.** Пул подключений, созданный на уровне модуля, пересоздаётся при каждом холодном старте — нужен он этому вызову или нет. Создавайте его при первом обращении, и тёплые старты будут его переиспользовать.

```typescript
// ПЛОХО: подключение создаётся сразу при каждом cold start
const db = createPool({ ... }); // вне handler → всегда при cold start

// ХОРОШО: создать при первом вызове, переиспользовать при warm
let dbPool: Pool | null = null;
export async function handler(event: APIGatewayEvent) {
  if (!dbPool) dbPool = await createPool({ ... });
  // ...
}
```

**3. Provisioned Concurrency.** Lambda заранее прогревает N сред исполнения, и N одновременных вызовов не увидят холодного старта вообще. За эти прогретые среды вы платите постоянно, поэтому приём окупается на чувствительных к задержке API с предсказуемым трафиком.

**4. Lambda SnapStart, только для Java.** Восстанавливает снимок уже инициализированной среды примерно за 200 мс. Для Node.js и Python недоступно.

## Типичный Lambda Handler с TypeScript

Обработчик ниже читает одну запись из DynamoDB. В нём две привычки, важные для любой Lambda. Клиенты создаются вне обработчика, поэтому тёплые старты их переиспользуют. Каждая ветка ошибки возвращает код статуса, а не бросает исключение.

```typescript
import { APIGatewayProxyEvent, APIGatewayProxyResult, Context } from 'aws-lambda';
import { DynamoDBClient } from '@aws-sdk/client-dynamodb';
import { DynamoDBDocumentClient, GetCommand } from '@aws-sdk/lib-dynamodb';

// Инициализация вне handler → переиспользуется при warm start
const ddbClient = new DynamoDBClient({ region: process.env.AWS_REGION });
const docClient = DynamoDBDocumentClient.from(ddbClient);

export async function handler(
  event: APIGatewayProxyEvent,
  context: Context
): Promise<APIGatewayProxyResult> {
  // context.getRemainingTimeInMillis() → осталось мс до timeout

  const userId = event.pathParameters?.userId;
  if (!userId) {
    return { statusCode: 400, body: JSON.stringify({ error: 'userId required' }) };
  }

  try {
    const result = await docClient.send(new GetCommand({
      TableName: process.env.TABLE_NAME!,
      Key: { pk: `USER#${userId}` },
    }));

    if (!result.Item) {
      return { statusCode: 404, body: JSON.stringify({ error: 'Not found' }) };
    }

    return {
      statusCode: 200,
      headers: { 'Content-Type': 'application/json' },
      body: JSON.stringify(result.Item),
    };
  } catch (err) {
    console.error('DynamoDB error:', err); // → CloudWatch Logs автоматически
    return { statusCode: 500, body: JSON.stringify({ error: 'Internal error' }) };
  }
}
```

## Triggers — чем запускается Lambda

Триггеры делятся на три группы, и от группы зависит, что произойдёт при ошибке вызова.

**Синхронные — Lambda ждёт и возвращает ответ**

- API Gateway или Function URL — HTTP-запрос и ответ на него.
- ALB (Application Load Balancer) — Lambda работает как бэкенд.
- CloudFront Functions — обработка на границе сети.

**Асинхронные — Lambda получает событие, ответа никто не ждёт**

- S3 (Simple Storage Service): «файл загружен» запускает Lambda, например чтобы уменьшить картинку.
- SNS (Simple Notification Service): «пришло сообщение» запускает Lambda.
- EventBridge: правило по расписанию (cron) запускает Lambda.
- При ошибке Lambda повторяет вызов 2 раза с задержкой, а потом отправляет событие в очередь недоставленных, Dead Letter Queue (DLQ).

**Потоковые — Lambda сама опрашивает источник**

- SQS (Simple Queue Service): Lambda забирает пачку сообщений, размер пачки 1-10000.
- Kinesis: Lambda забирает записи, а при ошибке делит пачку пополам.
- DynamoDB Streams: Lambda реагирует на изменения в таблице.

## Concurrency и Limits

Каждое число ниже — жёсткая граница, и продакшен упирается в них раньше, чем принято думать.

- Одновременных выполнений на аккаунт: 1000 по умолчанию, лимит можно поднять.
- Пиковый прирост: 500-3000 в секунду, зависит от региона.
- Таймаут: максимум 15 минут, то есть 900 секунд.
- Память: от 128 MB до 10240 MB. Доля процессора растёт вместе с запрошенной памятью.
- Пакет развёртывания: 50 MB в виде zip-архива или 10 гигабайт в виде образа контейнера.
- Хранилище `/tmp`: от 512 MB до 10240 MB, эфемерное и живёт только в рамках одного вызова.
- Синхронная полезная нагрузка (payload): 6 MB на запрос плюс 6 MB на ответ.
- Асинхронная полезная нагрузка: 256 килобайт.

**Reserved Concurrency** резервирует N конкурентности за одной функцией. Это гарантирует, что минимум N ей всегда доступны, и одновременно ограничивает её сверху этим же N. Всё, что выше потолка, отбрасывает throttling (ограничение скорости), и вызов приходится повторять — обычно через SQS.

Throttling — это и есть то, как выглядит превышение конкурентности: HTTP 429 для синхронных вызовов и повтор для асинхронных.

## Lambda + VPC — доступ к RDS/ElastiCache

Lambda, помещённая внутрь VPC (Virtual Private Cloud), достаёт до инстанса RDS (Relational Database Service) в приватной подсети. Плата за это — более медленный холодный старт, и сниппет отмечает и цену, и способ её снизить.

```typescript
// Lambda в VPC для доступа к RDS в private subnet
const lambdaFn = new lambda.Function(this, 'ApiHandler', {
  runtime: lambda.Runtime.NODEJS_20_X,
  handler: 'index.handler',
  code: lambda.Code.fromAsset('dist'),
  vpc,
  vpcSubnets: { subnetType: ec2.SubnetType.PRIVATE_WITH_EGRESS },
  securityGroups: [lambdaSecurityGroup],
  // Важно: Lambda в VPC → cold start +100-600ms (ENI provisioning)
  // Mitigation: использовать RDS Proxy (connection pooling)
});

// RDS Proxy: решает проблему "1000 Lambda * DB connection = pool exhaustion"
// Lambda → RDS Proxy (pooling) → RDS (реальных connections гораздо меньше)
```

**Важно**: Lambda в VPC по умолчанию не имеет доступа в интернет. Чтобы достучаться до API AWS вроде S3 или DynamoDB, нужно одно из двух. NAT Gateway (network address translation) обходится дорого; VPC Endpoints дешевле.

## Когда Lambda, когда ECS/EC2

В общем виде не выигрывает никто. Lambda выигрывает, когда трафик нерегулярный, а единица работы короткая. ECS (Elastic Container Service) на Fargate выигрывает, когда процесс обязан жить постоянно.

**Lambda**

- ✓ Нерегулярный трафик — нет трафика, нет и оплаты.
- ✓ Обработка событий из S3, SQS, SNS.
- ✓ Простой HTTP API с API Gateway.
- ✓ Фоновые задания и запуски по расписанию (cron).
- ✓ Обработка файлов, например генерация миниатюр.
- ✗ Постоянные соединения WebSocket.
- ✗ Задачи длиннее 15 минут.
- ✗ Задачи, упирающиеся в процессор, вроде кодирования видео.
- ✗ Сервисы с состоянием.

**ECS / Fargate**

- ✓ Предсказуемый трафик большого объёма.
- ✓ Серверы WebSocket.
- ✓ Сервисы с состоянием.
- ✓ Сложные монолиты на NestJS.
- ✓ Задачи без ограничения по времени.
- ✓ Холодного старта нет — процесс работает всегда.
- ✗ Вы платите даже при нулевом трафике.

## Типичные ошибки на интервью

- **«Lambda stateless — нельзя ничего хранить между вызовами»** — среда исполнения переиспользуется при тёплом старте. Переменные вне обработчика, например подключения к базе и кэш, сохраняются между вызовами **одного и того же контейнера**. Но рассчитывать, что конкретное состояние доживёт до следующего вызова, нельзя: контейнер может оказаться другим.

- **«Cold start можно устранить через Provisioned Concurrency»** — уменьшить до нуля для N одновременных вызовов можно, но постоянно «прогретые» среды стоят денег. Для большинства API дешевле другое: оптимизировать бандл, отложить инициализацию и смириться с холодным стартом в 200-500 мс.

- **«Lambda в VPC такая же быстрая, как без VPC»** — нет. Lambda в VPC добавляет примерно 100-600 мс к холодному старту, потому что ей нужно поднять ENI (elastic network interface). AWS это улучшил через Hyperplane ENI, но накладные расходы никуда не делись. Где можно, берите DynamoDB вместо RDS: ей VPC не нужна.

- **«Lambda масштабируется бесконечно»** — на аккаунте есть лимит одновременных выполнений, по умолчанию 1000. На пике создаётся 500-3000 новых контейнеров в секунду. При превышении включается throttling и приходит 429. Лимит поднимается запросом в AWS Support.

- **«Таймаут Lambda — 5 минут»** — максимум 15 минут, то есть 900 секунд. По умолчанию 3 секунды. Таймаут под задачу нужно выставлять явно.
