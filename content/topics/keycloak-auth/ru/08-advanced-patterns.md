# Продвинутые паттерны — за пределами простого логина

## Когда "просто настроить логин" перестаёт быть достаточным

Эта статья — про сценарии auth, которые senior-инженеру приходится проектировать, а не просто настраивать.

Статьи 01-07 покрывают то, что нужно для корректного и безопасного стандартного флоу: логин, токены, защита backend и frontend. Сценарии ниже встречаются реже, но систематически всплывают в senior-роли. Вопрос перестаёт быть "как сделать логин" и становится "как спроектировать auth для конкретной непростой бизнес-ситуации":

- Повышенные требования к безопасности для отдельных действий.
- Объединение личностей из разных источников.
- Мультитенантный SaaS (software as a service).
- Нестандартные claims.
- Миграция с legacy-системы.
- Эксплуатационная зрелость самого Keycloak.

## Step-up аутентификация — второй фактор точечно, а не глобально

Проблема, которую решает step-up: требовать MFA (multi-factor authentication, многофакторную аутентификацию) или WebAuthn для **всех** действий в приложении — это трение в UX (user experience, опыт пользователя) на каждом логине. Эта цена платится даже там, где ставки низкие: например, чтобы посмотреть список заказов.

Требовать второй фактор **только** для чувствительных действий — правильный баланс: перевод денег, смена пароля, изменение email. Keycloak поддерживает это как первоклассный сценарий, через **Authentication Flows** (статья 02) в сочетании с **параметром `acr` (Authentication Context Class Reference)**.

```txt
Механизм:
  1. Обычный логин проходит стандартный browser flow (пароль,
     возможно "запомнить меня") → выдаётся access token
     с claim "acr": "1", низкий уровень доверия
     к аутентификации

  2. Перед чувствительным действием приложение инициирует новый
     authorization request с параметром:
       &acr_values=2  (запрос повышенного уровня аутентификации)
     или Keycloak-специфичным:
       &kc_action=CONFIGURE_TOTP  (форсировать конкретное действие)

  3. Keycloak видит, что текущая сессия аутентифицирована с acr=1,
     а запрошен acr=2 → форсирует дополнительный шаг (WebAuthn
     или одноразовый код) поверх уже существующей сессии, без
     полного релогина

  4. Новый access token содержит "acr": "2" — и приложение
     проверяет этот claim перед тем, как разрешить чувствительное
     действие, а не полагается на "пользователь как-то прошёл
     через step-up на клиенте"
```

```typescript
// NestJS: Guard, проверяющий уровень аутентификации перед чувствительным действием
import { Reflector } from '@nestjs/core';

@Injectable()
export class StepUpGuard implements CanActivate {
  constructor(private reflector: Reflector) {} // читает метаданные @RequireAcr

  canActivate(context: ExecutionContext): boolean {
    const { user } = context.switchToHttp().getRequest();
    const requiredAcr = this.reflector.get<string>('acr', context.getHandler());

    if (requiredAcr && user.acr !== requiredAcr) {
      throw new ForbiddenException({
        error: 'step_up_required',
        required_acr: requiredAcr,
        // Frontend должен инициировать НОВЫЙ authorization request
        // с acr_values=<requiredAcr>, а не просто показать ошибку
      });
    }
    return true;
  }
}

@Post('transfer-funds')
@RequireAcr('2') // требует step-up для этого конкретного эндпоинта
async transferFunds(@Body() dto: TransferDto) { /* ... */ }
```

Ключевой архитектурный момент: **проверка claim `acr` должна происходить на Resource Server, то есть на бэкенде, а не только в UI (user interface, пользовательском интерфейсе) фронтенда**.

Частая ошибка выглядит так. Фронтенд показывает модалку с WebAuthn перед вызовом чувствительного эндпоинта, а бэкенд реальный `acr` в токене не проверяет. Атакующий, у которого уже есть валидный access token с `acr: 1` — обычный логин, без step-up, — просто вызывает API напрямую. UI-проверка обходится целиком.

## Account Linking — объединение личностей из нескольких провайдеров (Identity Provider)

Сценарий: пользователь изначально зарегистрировался локально, по email и паролю. Позже он хочет привязать вход через Google для удобства. Оба способа входа должны вести к **одному и тому же** аккаунту, а не создавать дубликат пользователя.

```txt
Без явного linking (проблема):
  Пользователь регистрируется локально: user@example.com / пароль
  Позже логинится через "Sign in with Google" тем же email —
  Keycloak (через Identity Brokering, статья 02) по умолчанию МОЖЕТ
  создать ВТОРОЙ, отдельный аккаунт, даже если email совпадает —
  результат: два непересекающихся "пользователя" в системе,
  с разной историей заказов/настроек/прав.

С Account Linking:
  Первый вход:  локальный логин user@example.com/пароль
  Пользователь заходит в "Настройки аккаунта" → "Привязать
  аккаунты" → "Привязать Google" → редирект на Google → после
  успешной аутентификации Keycloak связывает google-sub с уже
  существующим локальным аккаунтом (Federated Identity Link),
  а не создаёт новый

  После linking и локальный пароль, и "Sign in with Google"
  ведут к одному и тому же пользователю Keycloak, с одной
  историей ролей, групп и данных
```

```txt
Автоматический account linking по email — соблазнительная,
но опасная конфигурация "по умолчанию":

  Keycloak можно настроить на автоматическое связывание аккаунтов
  по совпадению email, без явного подтверждения пользователем
  ("First Login Flow" с включённым "Automatically link"). Это
  удобно, но создаёт реальную уязвимость. Допустим, внешний
  IdP — например, малоизвестный корпоративный провайдер,
  добавленный через Identity Brokering, — верифицирует email
  не так строго, как ваш основной realm. Атакующий регистрируется
  у этого внешнего IdP с чужим email, если тот IdP разрешает
  это без верификации. Дальше он логинится через него в ваше
  приложение и автоматически "наследует" локальный аккаунт
  жертвы с тем же email.

  Безопасная практика: явное действие пользователя — кнопка
  "Привязать" в уже аутентифицированной сессии — вместо
  автоматического связывания по email при первом логине через
  новый IdP. Особенно это важно для IdP, чья политика верификации
  email вам не полностью известна и вами не контролируется.
```

## Мультитенантность — Realm-per-tenant vs Shared Realm

Это один из самых частых архитектурных вопросов при построении B2B (business-to-business) SaaS на Keycloak. Универсально правильного ответа здесь нет — только осознанный компромисс.

```txt
Realm-per-tenant:
  Каждый клиент компании (арендатор SaaS) получает собственный
  realm Keycloak: acme-corp, globex-inc, initech-llc...

  ✓ Полная изоляция "из коробки" — своя политика паролей, своя
    тема логина (важно для white-label SaaS: клиент видит свой
    брендинг на странице логина, а не общий), свои Identity
    Providers и User Federation (клиент может подключить свой
    Active Directory без риска для других клиентов)
  ✓ Проще выполнить требование "данные тенанта физически
    изолированы" для клиентов, чувствительных к compliance
  ✗ Операционные накладные расходы растут линейно с числом
    тенантов: конфигурацию realm-as-code (статья 02) надо
    применять к N realm, мониторинг и алертинг — агрегировать
    по N realm, а апгрейд Keycloak тестировать против N
    конфигураций
  ✗ Практический потолок: тысячи realm на одном инстансе
    Keycloak начинают создавать реальную операционную нагрузку
    (админ-консоль, синхронизация конфигурации, время старта)

Shared Realm с group/organization-based изоляцией:
  Один realm на всех тенантов, изоляция — через Groups (статья 02):
  /tenants/acme-corp, /tenants/globex-inc, с атрибутом tenantId
  и Protocol Mapper, кладущим tenant_id в токен (статья 02)

  ✓ Операционная нагрузка не растёт линейно с числом тенантов —
    один realm обслуживает тысячи организаций
  ✓ Проще делить общую инфраструктуру (единая тема для всех,
    кроме случаев white-label) и общие Identity Providers
  ✗ Изоляция идёт на уровне приложения, а не Keycloak: Resource
    Server обязан сам фильтровать данные по tenant_id из токена
    на каждом запросе. Ошибка в этой проверке — утечка данных
    между тенантами, и это уже не проблема Keycloak, а баг
    вашего кода
  ✗ Кастомизация на тенанта (своя тема логина, свой Identity
    Provider) сложнее. Keycloak Organizations — относительно
    новая фича, доступная начиная с определённых версий —
    частично закрывает этот разрыв, но полной изоляции
    realm-per-tenant не даёт
```

Практическая рекомендация, зависящая от контекста. **Realm-per-tenant оправдан для B2B enterprise SaaS с небольшим числом крупных клиентов** — десятки или сотни. Каждому из них нужна кастомизация и жёсткая изоляция, и часто это прямое требование compliance.

**Shared realm с группами оправдан для B2C (business-to-consumer) или self-serve B2B с тысячами мелких тенантов.** На таком масштабе операционная нагрузка realm-per-tenant стала бы неподъёмной, а требования к изоляции там и так менее строгие.

Гибридный вариант, Keycloak Organizations, стоит рассматривать отдельно — под конкретную версию Keycloak и конкретные требования. Это относительно новая область, где лучшие практики продолжают формироваться.

## Расширение claims через Protocol Mapper SPI — когда встроенных мапперов не хватает

Статья 02 показала встроенные Protocol Mapper (User Attribute, Role). Иногда claim нужно вычислить по нетривиальной бизнес-логике: агрегация данных из внешней базы данных, вызов другого сервиса, сложная трансформация. Декларативным маппером "из коробки" это не выразить.

```txt
Keycloak SPI (Service Provider Interface) — общий механизм
расширяемости Keycloak: Java-интерфейсы, которые можно
реализовать самостоятельно и упаковать как JAR-плагин,
разворачиваемый в providers/ директорию Keycloak.

Protocol Mapper SPI — конкретный SPI для кастомной claim-логики:
  реализуете интерфейс ProtocolMapper (Java), внутри которого
  можете выполнить произвольный код (сходить в свою БД, вызвать
  внутренний сервис, применить сложную бизнес-логику) для
  вычисления значения claim при выдаче токена.
```

```java
// Концептуальный набросок (не полный туториал — цель показать идею)
public class SubscriptionTierMapper extends AbstractOIDCProtocolMapper
    implements OIDCAccessTokenMapper {

  @Override
  protected void setClaim(IDToken token, ProtocolMapperModel mappingModel,
                          UserSessionModel userSession, KeycloakSession session,
                          ClientSessionContext clientSessionCtx) {
    String userId = userSession.getUser().getId();
    // Кастомная логика: например, запрос к billing-сервису
    String tier = billingServiceClient.getSubscriptionTier(userId);
    token.getOtherClaims().put("subscription_tier", tier);
  }
}
```

```txt
Когда это оправдано:
  - Claim требует данных, которых физически нет в Keycloak
    (атрибуты пользователя, роли, группы) — например, "текущий
    тариф подписки", который меняется в биллинг-системе,
    независимой от Keycloak
  - Вычисление claim требует логики, недоступной в декларативных
    мапперах (агрегация, условная логика сложнее простого
    маппинга атрибута)

Когда НЕ оправдано (стоит остановиться на встроенных мапперах):
  - Данные уже есть как атрибут пользователя/роль/группа — тогда
    встроенный Protocol Mapper (статья 02) решает задачу без
    единой строчки Java-кода и без необходимости деплоить,
    версионировать и поддерживать кастомный плагин

Операционная цена кастомного SPI:
  Каждый кастомный provider — дополнительный код, который нужно
  тестировать и держать совместимым с версией Keycloak: контракты
  SPI могут меняться между мажорными версиями. Его же приходится
  учитывать при каждом апгрейде самого Keycloak. Это реальный
  инженерный актив с постоянной ценой поддержки, а не просто
  конфигурация.
```

## Миграция с самописной auth-системы на Keycloak — strangler pattern применительно к auth

Реалистичный senior-сценарий: существующее приложение с legacy-аутентификацией на JWT (JSON Web Token). У него собственная таблица `users`, свой bcrypt-хэш и свой код выдачи токенов. Перевести его на Keycloak нужно **без** одномоментного flag day для всех пользователей сразу: такой риск для бизнеса неприемлем.

```txt
Классический strangler fig pattern, применённый к auth:

Фаза 1 — Keycloak рядом, но не в проде:
  Развернуть Keycloak, настроить realm, НЕ переключать реальный
  трафик. Валидировать конфигурацию на staging.

Фаза 2 — User Federation через Custom User Storage SPI (мост):
  Написать Custom User Storage Provider (тот же механизм SPI, что
  выше), который делает Keycloak "прозрачным фасадом" над
  существующей таблицей users legacy-системы. На логине Keycloak
  проверяет пароль, ходя в старую базу и применяя старый
  хэш-алгоритм (bcrypt, scrypt — что использовалось раньше),
  вместо того чтобы мигрировать все пароли сразу. Пользователи
  логинятся через Keycloak, даже не зная, что что-то изменилось:
  их пароль всё ещё живёт в старой таблице.

Фаза 3 — Постепенная миграция паролей "на лету":
  При успешном логине через Custom User Storage Provider Keycloak
  импортирует пользователя в свою внутреннюю базу, уже с новым,
  Keycloak-нативным хэшем пароля. Дальше для этого пользователя
  логины идут напрямую через Keycloak, а не через мост
  к legacy-таблице. Со временем, по мере логинов реальных
  пользователей, доля мигрированных растёт органически. Никакого
  форс-мажорного flag day, и не нужно заранее знать все пароли
  в открытом виде — что невозможно, раз они захэшированы.

Фаза 4 — Переключение клиентов (backend/frontend):
  Постепенно, сервис за сервисом, backend переходит с валидации
  собственных legacy-JWT на валидацию Keycloak-токенов через
  JWKS (статья 03/04). Делать это можно поэтапно, если
  у Resource Server временно есть два пути валидации сразу
  (legacy JWT secret и Keycloak JWKS) — явно помеченные
  и убираемые по готовности.

Фаза 5 — Демонтаж моста:
  Когда доля немигрированных пользователей становится
  пренебрежимо малой (или после явной кампании "залогиньтесь
  один раз, чтобы завершить миграцию" для неактивных аккаунтов) —
  Custom User Storage Provider и legacy-таблица выводятся из
  эксплуатации.
```

Ключевая идея strangler-подхода здесь та же, что и в любом другом домене. **Это не одномоментная замена системы. Старую систему постепенно "обёртывают" новым фасадом, а данные мигрируют органически, через реальное использование.**

Альтернатива — единоразовый batch-скрипт. Ему потребовался бы доступ к паролям в виде, недоступном по определению: пароли захэшированы необратимо.

## HA и кластеризация — операционная зрелость, а не разбор инфраструктуры

Keycloak в проде — это stateful-сервис, и HA (high availability, высокая доступность) для него реальное требование. Недооценка этого — частая причина инцидентов "Keycloak упал — весь продакшен встал". Аутентификация по определению единая точка отказа для всей системы.

```txt
Почему нужна реальная БД (не embedded H2):
  Realm-конфигурация, пользователи, сессии (в зависимости от
  конфигурации кэша) — персистентные данные, требующие настоящей
  production-grade БД (PostgreSQL — наиболее распространённый
  выбор) с бэкапами, репликацией, мониторингом — так же, как
  для любого другого критичного сервиса, а не как для "просто
  ещё одного микросервиса, который можно пересоздать из ничего".

Почему нужна кластеризация (несколько инстансов Keycloak):
  Один инстанс Keycloak — единая точка отказа для аутентификации
  ВСЕЙ системы: если он падает, никто не может залогиниться и,
  что критичнее, если используется token introspection (статья 03),
  никто не может делать API-запросы вообще, пока Keycloak не
  поднимется. Production-развёртывание — минимум 2+ реплики
  Keycloak за балансировщиком нагрузки, с общей БД и
  (в зависимости от версии) распределённым кэшем сессий
  (Infinispan в кластерном режиме) для консистентности
  server-side сессий между инстансами.

Практический вывод для инженера, не обязательно DevOps-специалиста:
  Планируя архитектуру, закладывайте Keycloak как компонент,
  требующий ТОЙ ЖЕ операционной серьёзности, что и основная БД
  продукта — HA-развёртывание, мониторинг latency и error rate
  на auth-эндпоинтах, alerting на рост p99 login-запросов —
  а не как "поставили один под в k8s и забыли".
```

## Итоговая связь понятий

```txt
[Step-up + acr]              →  точечное требование второго
                                фактора, проверяемое на бэкенде
                                через claim, а не только в UI

[Account Linking]            →  явное действие пользователя
                                безопаснее автоматического
                                связывания по email, особенно
                                для внешних IdP с неизвестной
                                политикой верификации

[Realm-per-tenant vs
 Shared Realm]               →  изоляция и кастомизация против
                                операционных расходов, растущих
                                с числом тенантов — решение
                                зависит от масштаба и требований
                                compliance

[Protocol Mapper SPI]        →  оправдан, когда claim требует
                                данных или логики за пределами
                                Keycloak, и стоит реальной
                                постоянной поддержки

[Strangler pattern
 для миграции]               →  Custom User Storage Provider как
                                мост к legacy-паролям, а миграция
                                органическая, через реальные
                                логины, а не batch-скриптом

[HA/кластеризация]           →  Keycloak — критичный, stateful
                                компонент, требующий той же
                                операционной серьёзности, что
                                и основная база данных продукта
```

Когда вообще стоит выбирать self-hosted Keycloak вместо managed-альтернатив вроде Auth0, Okta и Cognito — или вместо самописного решения?

## Типичные ошибки на интервью

- **"Step-up-аутентификация — это просто показать модалку с OTP перед чувствительным действием на фронтенде"** — недостаточно. Модалка на фронтенде — это только запрос OTP (one-time password, одноразовый код). Без проверки claim `acr` на бэкенде атакующий с обычным, не step-up токеном вызовет защищённый эндпоинт напрямую.

- **"Account linking по email должен быть автоматическим — это удобнее для пользователя"** — риск. Автоматическое связывание по email без явного подтверждения пользователем создаёт уязвимость. Она открывается, как только внешний Identity Provider (IdP) верифицирует email не так строго, как ваш основной realm. Через такой слабо верифицированный внешний IdP атакующий может "унаследовать" чужой локальный аккаунт.

- **"Realm-per-tenant — всегда лучший выбор для мультитенантного SaaS, потому что даёт полную изоляцию"** — не универсально верно. Операционная нагрузка растёт линейно с числом тенантов. Для self-serve B2C или B2B с тысячами мелких клиентов shared realm с group-based изоляцией — более реалистичный выбор. Изоляция данных при этом ложится на приложение, а не на Keycloak, и это его цена.

- **"Миграцию с legacy auth-системы на Keycloak нужно делать одномоментно, иначе будут два источника правды"** — нет. Flag day здесь и невозможен, и не нужен. Strangler-подход через Custom User Storage Provider позволяет мигрировать пароли органически, по мере реальных логинов. Вся пользовательская база разом ничем не рискует, и доступ к паролям в открытом виде никому не нужен.

- **"Keycloak — это просто ещё один stateless-микросервис, который можно скейлить как любой другой"** — неверно. Keycloak — stateful-сервис с реальными требованиями к базе данных, бэкапам и распределённому кэшу сессий при кластеризации. Недооценка этого — частая причина инцидентов на проде, где падение auth-слоя останавливает всю систему целиком.
