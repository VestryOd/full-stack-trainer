# Продвинутые паттерны — за пределами простого логина

## Когда "просто настроить логин" перестаёт быть достаточным

Статьи 01-07 покрывают то, что нужно для корректного и безопасного стандартного флоу: логин, токены, защита backend/frontend. Эта статья — про сценарии, которые встречаются реже, но систематически всплывают в senior-роли: не "как сделать логин", а "как спроектировать auth для конкретной непростой бизнес-ситуации" — повышенные требования к безопасности для отдельных действий, объединение личностей из разных источников, мультитенантный SaaS, нестандартные claims, миграция с legacy-системы, и эксплуатационная зрелость самого Keycloak.

## Step-up аутентификация — второй фактор точечно, а не глобально

Проблема, которую решает step-up: требовать MFA/WebAuthn ДЛЯ ВСЕХ действий в приложении — это UX-трение на каждом логине, даже там, где ставки низкие (посмотреть список заказов). Требовать его ТОЛЬКО для чувствительных действий (перевод денег, смена пароля, изменение email) — правильный баланс, и Keycloak поддерживает это как первоклассный сценарий через **Authentication Flows** (статья 02) в сочетании с **параметром `acr` (Authentication Context Class Reference)**.

```txt
Механизм:
  1. Обычный логин проходит стандартный browser flow (пароль,
     возможно "запомнить меня") → выдаётся access token с
     claim'ом "acr": "1" (низкий уровень доверия к аутентификации)

  2. Приложение, ПЕРЕД чувствительным действием, инициирует НОВЫЙ
     authorization request с параметром:
       &acr_values=2  (запрос повышенного уровня аутентификации)
     или Keycloak-специфичным:
       &kc_action=CONFIGURE_TOTP  (форсировать конкретное действие)

  3. Keycloak видит, что текущая сессия аутентифицирована с acr=1,
     а запрошен acr=2 → форсирует ДОПОЛНИТЕЛЬНЫЙ шаг (WebAuthn/OTP)
     ПОВЕРХ уже существующей сессии, без полного релогина

  4. Новый access token содержит "acr": "2" — приложение
     ПРОВЕРЯЕТ ЭТОТ CLAIM перед тем, как разрешить чувствительное
     действие, а не просто полагается на "пользователь как-то
     прошёл через степ-ап на клиенте"
```

```typescript
// NestJS: Guard, проверяющий уровень аутентификации перед чувствительным действием
@Injectable()
export class StepUpGuard implements CanActivate {
  canActivate(context: ExecutionContext): boolean {
    const { user } = context.switchToHttp().getRequest();
    const requiredAcr = this.reflector.get<string>('acr', context.getHandler());

    if (requiredAcr && user.acr !== requiredAcr) {
      throw new ForbiddenException({
        error: 'step_up_required',
        required_acr: requiredAcr,
        // Frontend должен инициировать НОВЫЙ authorization request
        // с acr_values=<requiredAcr>, а не просто показать ошибку
      });
    }
    return true;
  }
}

@Post('transfer-funds')
@RequireAcr('2') // требует step-up для этого конкретного эндпоинта
async transferFunds(@Body() dto: TransferDto) { /* ... */ }
```

Ключевой архитектурный момент: **проверка `acr` claim'а ДОЛЖНА происходить на Resource Server'е (backend), а не только в UI фронтенда**. Частая ошибка — заставить фронтенд показать модалку с WebAuthn перед вызовом чувствительного эндпоинта, но не проверять реальный `acr` в токене на бэкенде — тогда атакующий, у которого уже есть валидный access token с `acr: 1` (обычный логин, без step-up), может вызвать API напрямую, минуя UI-проверку.

## Account Linking — объединение личностей из нескольких Identity Provider'ов

Сценарий: пользователь изначально зарегистрировался локально (email+пароль), позже хочет привязать вход через Google для удобства — оба способа входа должны вести к ОДНОМУ И ТОМУ ЖЕ аккаунту, а не создавать дубликат пользователя.

```txt
Без явного linking (проблема):
  Пользователь регистрируется локально: user@example.com / пароль
  Позже логинится через "Sign in with Google" тем же email —
  Keycloak (через Identity Brokering, статья 02) по умолчанию МОЖЕТ
  создать ВТОРОЙ, отдельный аккаунт, даже если email совпадает —
  результат: два непересекающихся "пользователя" в системе,
  с разной историей заказов/настроек/прав.

С Account Linking:
  Первый вход:  локальный логин user@example.com/пароль
  Пользователь заходит в "Настройки аккаунта" → "Привязать аккаунты" →
  "Привязать Google" → редирект на Google → после успешной
  аутентификации Keycloak СВЯЗЫВАЕТ google-sub с УЖЕ СУЩЕСТВУЮЩИМ
  локальным аккаунтом (Federated Identity Link) вместо создания нового

  После linking: и локальный пароль, И "Sign in with Google" ведут
  к ОДНОМУ И ТОМУ ЖЕ Keycloak-пользователю, с одной и той же историей
  ролей/групп/данных
```

```txt
Автоматический account linking по email — соблазнительная, но опасная
конфигурация "по умолчанию":

  Keycloak МОЖЕТ быть настроен на автоматическое связывание аккаунтов
  по совпадению email БЕЗ явного подтверждения пользователем ("First
  Login Flow" с включённым "Automatically link"). Это удобно, но
  создаёт РЕАЛЬНУЮ уязвимость: если внешний IdP (например, малоизвестный
  корпоративный провайдер, добавленный через Identity Brokering)
  НЕ верифицирует email так же строго, как ваш основной realm —
  атакующий может зарегистрироваться у ЭТОГО внешнего IdP с ЧУЖИМ
  email (если тот IdP это разрешает без верификации), залогиниться
  через него в ваше приложение, и автоматически "унаследовать"
  локальный аккаунт жертвы с тем же email.

  Безопасная практика: явное действие пользователя (кнопка "Привязать"
  в уже аутентифицированной сессии) вместо автоматического связывания
  по email при первом логине через новый IdP — особенно для IdP,
  чья политика верификации email вам не полностью известна и не
  контролируется вами напрямую.
```

## Мультитенантность — Realm-per-tenant vs Shared Realm

Это один из самых частых архитектурных вопросов при построении B2B SaaS на Keycloak, и здесь нет универсально правильного ответа — только осознанный trade-off.

```txt
Realm-per-tenant:
  Каждый клиент компании (арендатор SaaS) получает СОБСТВЕННЫЙ Keycloak
  realm: acme-corp, globex-inc, initech-llc...

  ✓ Полная изоляция "из коробки" — своя политика паролей, своя
    тема логина (важно для white-label SaaS — клиент видит СВОЙ
    брендинг на странице логина, а не общий), свои Identity
    Providers/User Federation (клиент может подключить СВОЙ
    Active Directory без риска для других клиентов)
  ✓ Проще выполнить требование "данные тенанта физически
    изолированы" для compliance-чувствительных клиентов
  ✗ Операционные накладные расходы РАСТУТ линейно с числом
    тенантов: realm-as-code (статья 02) конфигурация должна
    применяться к N realm'ам, мониторинг/алертинг должен агрегировать
    по N realm'ам, upgrade Keycloak тестируется против N конфигураций
  ✗ Практический потолок: тысячи realm'ов на одном инстансе
    Keycloak начинают создавать реальную операционную нагрузку
    (админ-консоль, синхронизация конфигурации, время старта)

Shared Realm с group/organization-based изоляцией:
  Один realm на ВСЕХ тенантов, изоляция — через Groups (статья 02):
  /tenants/acme-corp, /tenants/globex-inc, с атрибутом tenantId
  и Protocol Mapper, кладущим tenant_id в токен (статья 02)

  ✓ Операционная нагрузка НЕ растёт линейно с числом тенантов —
    один realm обслуживает тысячи организаций
  ✓ Проще шарить общую инфраструктуру (единая тема для всех, кроме
    случаев white-label) и общие Identity Providers
  ✗ Изоляция — на уровне ПРИЛОЖЕНИЯ, не Keycloak: Resource Server
    ОБЯЗАН сам фильтровать данные по tenant_id из токена на КАЖДОМ
    запросе — ошибка в этой проверке = утечка данных между тенантами,
    и это уже не Keycloak-проблема, а баг вашего кода
  ✗ Кастомизация на тенанта (своя тема логина, свой Identity
    Provider) сложнее — Keycloak Organizations (относительно
    новая фича, доступная начиная с определённых версий) частично
    закрывает этот разрыв, но не даёт полной изоляции realm-per-tenant
```

Практическая рекомендация, зависящая от контекста: **realm-per-tenant — оправдан для B2B enterprise SaaS с небольшим числом (десятки-сотни) крупных клиентов, каждому из которых нужна кастомизация и жёсткая изоляция (часто — прямое compliance-требование). Shared realm с группами — оправдан для B2C или self-serve B2B с тысячами мелких тенантов**, где операционная нагрузка realm-per-tenant стала бы неподъёмной, а требования к изоляции менее строгие. Гибридный вариант (Keycloak Organizations) стоит рассматривать отдельно под конкретную версию Keycloak и конкретные требования — это относительно новая область, где лучшие практики продолжают формироваться.

## Расширение claims через Protocol Mapper SPI — когда встроенных мапперов не хватает

Статья 02 показала встроенные Protocol Mapper'ы (User Attribute, Role). Иногда claim нужно вычислить по нетривиальной бизнес-логике: агрегация данных из внешней БД, вызов другого сервиса, сложная трансформация — то, что не выражается декларативным маппером "из коробки".

```txt
Keycloak SPI (Service Provider Interface) — общий механизм
расширяемости Keycloak: Java-интерфейсы, которые можно
реализовать самостоятельно и упаковать как JAR-плагин,
разворачиваемый в providers/ директорию Keycloak.

Protocol Mapper SPI — конкретный SPI для кастомной claim-логики:
  реализуете интерфейс ProtocolMapper (Java), внутри которого
  можете выполнить произвольный код (сходить в свою БД, вызвать
  внутренний сервис, применить сложную бизнес-логику) для
  вычисления значения claim'а при выдаче токена.
```

```java
// Концептуальный набросок (не полный туториал — цель показать идею)
public class SubscriptionTierMapper extends AbstractOIDCProtocolMapper
    implements OIDCAccessTokenMapper {

  @Override
  protected void setClaim(IDToken token, ProtocolMapperModel mappingModel,
                          UserSessionModel userSession, KeycloakSession session,
                          ClientSessionContext clientSessionCtx) {
    String userId = userSession.getUser().getId();
    // Кастомная логика: например, запрос к billing-сервису
    String tier = billingServiceClient.getSubscriptionTier(userId);
    token.getOtherClaims().put("subscription_tier", tier);
  }
}
```

```txt
Когда это оправдано:
  - Claim требует данных, которых физически нет в Keycloak
    (атрибуты пользователя, роли, группы) — например, "текущий
    тариф подписки", который меняется в биллинг-системе,
    независимой от Keycloak
  - Вычисление claim'а требует логики, недоступной в декларативных
    мапперах (агрегация, условная логика сложнее простого
    маппинга атрибута)

Когда НЕ оправдано (стоит остановиться на встроенных мапперах):
  - Данные уже есть как атрибут пользователя/роль/группа — тогда
    встроенный Protocol Mapper (статья 02) решает задачу без
    единой строчки Java-кода и без необходимости деплоить,
    версионировать и поддерживать кастомный плагин

Операционная цена кастомного SPI:
  Каждый кастомный provider — дополнительный код, который нужно
  тестировать, версионировать СОВМЕСТИМО с версией Keycloak
  (SPI-контракты могут меняться между мажорными версиями), и
  учитывать при апгрейде самого Keycloak. Это реальный
  инженерный актив с ongoing maintenance cost, а не просто
  конфигурация.
```

## Миграция с самописной auth-системы на Keycloak — strangler pattern применительно к auth

Реалистичный senior-сценарий: существующее приложение с legacy JWT-аутентификацией (собственная таблица `users`, свой bcrypt-хэш, свой JWT-issuing код), которое нужно перевести на Keycloak БЕЗ одномоментного flag day для всех пользователей сразу (риск для бизнеса неприемлем).

```txt
Классический strangler fig pattern, применённый к auth:

Фаза 1 — Keycloak рядом, но не в проде:
  Развернуть Keycloak, настроить realm, НЕ переключать реальный
  трафик. Валидировать конфигурацию на staging.

Фаза 2 — User Federation через Custom User Storage SPI (мост):
  Написать Custom User Storage Provider (тот же механизм SPI, что
  выше), который делает Keycloak "прозрачным фасадом" НАД
  СУЩЕСТВУЮЩЕЙ таблицей users legacy-системы: Keycloak на логине
  проверяет пароль, ХОДЯ В СТАРУЮ БД И ПРИМЕНЯЯ СТАРЫЙ ХЭШ-АЛГОРИТМ
  (bcrypt/scrypt/что использовалось раньше), вместо миграции всех
  паролей одномоментно. Пользователи логинятся ЧЕРЕЗ Keycloak,
  даже не зная, что что-то изменилось — их пароль всё ещё живёт
  в старой таблице.

Фаза 3 — Постепенная миграция паролей "на лету":
  При УСПЕШНОМ логине через Custom User Storage Provider — Keycloak
  импортирует пользователя в СВОЮ внутреннюю БД (с новым,
  Keycloak-нативным хэшем пароля), и для ЭТОГО пользователя
  дальнейшие логины идут уже напрямую через Keycloak, а не через
  мост к legacy-таблице. Со временем (по мере логинов реальных
  пользователей) доля "мигрированных" пользователей растёт органически,
  без форс-мажорного flag day и без необходимости заранее знать
  все пароли в открытом виде (что невозможно, если они захэшированы).

Фаза 4 — Переключение клиентов (backend/frontend):
  Постепенно, сервис за сервисом, backend переходит с валидации
  собственных legacy-JWT на валидацию Keycloak-токенов через JWKS
  (статья 03/04) — можно делать поэтапно, если у Resource Server'а
  временно есть ДВА пути валидации одновременно (legacy JWT secret
  + Keycloak JWKS), явно помеченные и убираемые по готовности.

Фаза 5 — Демонтаж моста:
  Когда доля немигрированных пользователей становится
  пренебрежимо малой (или после явной кампании "залогиньтесь
  один раз, чтобы завершить миграцию" для неактивных аккаунтов) —
  Custom User Storage Provider и legacy-таблица выводятся из
  эксплуатации.
```

Ключевая идея strangler-подхода здесь та же, что и в любом другом домене: **не одномоментная замена системы, а постепенное "обёртывание" старой системы новым фасадом, с миграцией данных, происходящей органически через реальное использование**, а не единоразовым batch-скриптом, требующим доступа к паролям в виде, недоступном по определению (пароли захэшированы необратимо).

## HA и кластеризация — операционная зрелость, не глубокий DevOps-разбор

Keycloak в проде — это stateful-сервис с реальными требованиями к отказоустойчивости, и недооценка этого — частая причина инцидентов "Keycloak упал — весь продакшен встал", потому что аутентификация — синглтон-точка отказа для всей системы по определению.

```txt
Почему нужна реальная БД (не embedded H2):
  Realm-конфигурация, пользователи, сессии (в зависимости от
  конфигурации кэша) — персистентные данные, требующие настоящей
  production-grade БД (PostgreSQL — наиболее распространённый
  выбор) с бэкапами, репликацией, мониторингом — так же, как
  для любого другого критичного сервиса, а не как для "просто
  ещё одного микросервиса, который можно пересоздать из ничего".

Почему нужна кластеризация (несколько инстансов Keycloak):
  Один инстанс Keycloak — единая точка отказа для аутентификации
  ВСЕЙ системы: если он падает, никто не может залогиниться и,
  что критичнее, если используется token introspection (статья 03),
  никто не может делать API-запросы вообще, пока Keycloak не
  поднимется. Production-развёртывание — минимум 2+ реплики
  Keycloak за балансировщиком нагрузки, с общей БД и
  (в зависимости от версии) распределённым кэшем сессий
  (Infinispan в кластерном режиме) для консистентности
  server-side сессий между инстансами.

Практический вывод для инженера, не обязательно DevOps-специалиста:
  Планируя архитектуру, закладывайте Keycloak как компонент,
  требующий ТОЙ ЖЕ операционной серьёзности, что и основная БД
  продукта — HA-развёртывание, мониторинг latency и error rate
  на auth-эндпоинтах, alerting на рост p99 login-запросов —
  а не как "поставили один под в k8s и забыли".
```

## Итоговая связь понятий

```txt
[Step-up + acr]                  →  точечное требование второго
                                   фактора, проверяемое НА BACKEND'Е
                                   через claim, а не только в UI

[Account Linking]                 →  явное действие пользователя
                                   безопаснее автоматического
                                   связывания по email — особенно
                                   для внешних IdP с неизвестной
                                   политикой верификации

[Realm-per-tenant vs Shared
 Realm]                            →  изоляция и кастомизация vs
                                   операционные накладные расходы,
                                   растущие с числом тенантов —
                                   решение зависит от масштаба и
                                   compliance-требований

[Protocol Mapper SPI]             →  оправдан, когда claim требует
                                   данных/логики за пределами
                                   Keycloak — с реальной ongoing
                                   maintenance-ценой

[Strangler pattern для миграции]  →  Custom User Storage Provider
                                   как мост к legacy-паролям,
                                   органическая миграция через
                                   реальные логины, а не batch-скрипт

[HA/кластеризация]                →  Keycloak — критичный, stateful
                                   компонент, требующий той же
                                   операционной серьёзности, что и
                                   основная БД продукта
```

Следующая статья — [Keycloak vs Alternatives] — переходит от "как использовать Keycloak на полную" к вопросу более высокого уровня: когда вообще стоит выбирать Keycloak (self-hosted) вместо managed-альтернатив (Auth0, Okta, Cognito) или даже вместо самописного решения.

## Типичные ошибки на интервью

- **"Step-up-аутентификация — это просто показать модалку с OTP перед чувствительным действием на фронтенде"** — недостаточно: без проверки `acr` claim'а на backend'е атакующий с обычным (не step-up) токеном может вызвать защищённый эндпоинт напрямую, минуя UI-проверку полностью.

- **"Account linking по email должен быть автоматическим — это удобнее для пользователя"** — риск: автоматическое связывание по email без явного подтверждения пользователем создаёт уязвимость, если внешний Identity Provider не верифицирует email так же строго, как ваш основной realm — атакующий может "унаследовать" чужой локальный аккаунт через слабо верифицированный внешний IdP.

- **"Realm-per-tenant — всегда лучший выбор для мультитенантного SaaS, потому что даёт полную изоляцию"** — не универсально верно: операционная нагрузка растёт линейно с числом тенантов, и для self-serve B2C/B2B с тысячами мелких клиентов shared realm с group-based изоляцией — более реалистичный выбор, несмотря на то что изоляция данных при этом ложится на приложение, а не на Keycloak.

- **"Миграцию с legacy auth-системы на Keycloak нужно делать одномоментно, иначе будут два источника правды"** — упускает практическую невозможность (и ненужность) flag day: strangler-подход через Custom User Storage Provider позволяет мигрировать пароли органически, по мере реальных логинов, без риска для всей пользовательской базы разом и без необходимости иметь доступ к паролям в открытом виде.

- **"Keycloak — это просто ещё один stateless-микросервис, который можно скейлить как любой другой"** — неверно: Keycloak — stateful-сервис с реальными требованиями к БД, бэкапам и распределённому кэшу сессий при кластеризации; недооценка этого — частая причина production-инцидентов, где падение auth-слоя останавливает всю систему целиком.
