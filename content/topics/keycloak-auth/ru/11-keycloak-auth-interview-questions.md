# Keycloak / OAuth2 / OIDC — вопросы для интервью (Middle → Senior)

## Group 1: Протокольный фундамент

**В чём реальная разница между OAuth2 и OIDC?**

OAuth2 — протокол **авторизации**, а OIDC (OpenID Connect) — слой **идентичности** поверх него. OAuth2 выдаёт access token и отвечает на вопрос "что разрешено предъявителю токена". Стандартного способа узнать, **кто** такой пользователь, он не даёт.

OIDC использует те же механизмы — те же эндпоинты, те же grant types — и добавляет три вещи:

- **ID Token** — JWT (JSON Web Token) с claims об идентичности: `sub`, `email`, `name`.
- **UserInfo endpoint** — получить актуальный профиль по access token.
- **Discovery document** — `/.well-known/openid-configuration`.

Путать их — ошибка не терминологическая, а архитектурная. Использовать access token как доказательство идентичности — это антипаттерн "OAuth as authentication". Именно ради того, чтобы закрыть эту дыру, OIDC и появился в 2014 году.

---

**Назовите четыре роли OAuth2 и объясните, почему backend-сервис может быть одновременно двумя из них.**

Четыре роли:

- **Resource Owner** — пользователь.
- **Client** — приложение, запрашивающее доступ.
- **Authorization Server** — Keycloak: аутентифицирует пользователя и выдаёт токены.
- **Resource Server** — API, владеющее защищёнными данными.

NestJS-бэкенд в связке "React SPA + API" — это Resource Server по отношению к SPA (single-page application, одностраничное приложение). Тот же бэкенд становится Client в момент, когда вызывает **другой** внутренний сервис от своего имени. Пользователя в этом вызове нет — работает Client Credentials Grant.

Путаница "кто есть кто" в конкретной архитектуре — источник неправильных решений о том, кто обновляет токены и где они хранятся.

---

**Что такое front-channel и back-channel, и почему это разделение важно?**

Front-channel — данные идут через браузер пользователя: редиректы, query-параметры, URL fragment. Этот путь виден в истории браузера, в заголовке `Referer` и в логах прокси. Back-channel — прямое серверное соединение, минуя браузер, невидимое пользователю.

Правило: секреты и токены передаются по back-channel везде, где это возможно.

Именно поэтому Authorization Code Grant безопаснее Implicit Grant. Authorization Code отдаёт через front-channel только одноразовый code, а на токены его меняют по back-channel. Implicit кладёт сам токен прямо в URL fragment — то есть во front-channel.

## Group 2: Grant Types

**Почему Implicit Grant считается устаревшим — дайте конкретный технический ответ, а не "он старый".**

Три конкретные причины:

1. Токен передаётся через URL fragment — это front-channel. Он оказывается в истории браузера, в заголовке `Referer` при переходе по внешней ссылке и в логах прокси.
2. Токен выдаётся сразу на редиректе, без дополнительной проверки клиента. У Authorization Code иначе: back-channel обмен code→token позволяет проверить `code_verifier` из PKCE (Proof Key for Code Exchange) или client secret.
3. Refresh token не выдаётся вообще — через front-channel это тоже было бы небезопасно. Поэтому продление сессии зависело от хрупкого iframe-механизма с `prompt=none`.

---

**Почему ROPC (Resource Owner Password Credentials) не подходит для современных приложений?**

Клиент физически собирает пароль пользователя в своей форме. Это прямо противоречит цели OAuth2 — не раскрывать пароль третьей стороне.

Отсюда две практические потери:

- **MFA и step-up становятся трудными.** MFA — это многофакторная аутентификация. Authorization Server не видит и не контролирует форму логина, поэтому MFA пришлось бы переизобретать внутри клиента.
- **SSO становится невозможен.** SSO — это единый вход, один логин на несколько приложений. С ROPC пользователь логинится заново в каждом клиенте отдельно.

Keycloak по умолчанию отключает Direct Access Grants для новых клиентов.

---

**Когда стоит использовать Client Credentials Grant, и что принципиально отличает его от логина пользователя?**

Когда за токеном обращается сервис от своего собственного имени, без пользователя. Типичный случай — внутренний RPC (remote procedure call, удалённый вызов процедуры) между микросервисами.

Принципиальное отличие: front-channel шага нет вообще — ни браузера, ни редиректа. Весь обмен — один back-channel `POST` на `/token` с `client_id` и `client_secret`.

В выданном токене нет `sub`, указывающего на реального пользователя, и ID Token не выдаётся. Идентифицировать здесь некого.

## Group 3: Токены и валидация

**Объясните разницу между access token, ID token и refresh token — куда каждый отправляется и кто его использует.**

У каждого из трёх ровно один адресат:

- **Access token** — для Resource Server. Отправляется в заголовке `Authorization: Bearer` на каждый API-запрос. Содержит scope и roles: "что разрешено".
- **ID Token** — только для клиентского приложения, чтобы показать информацию о пользователе. Отправлять его в другое API вместо access token нельзя. Содержит identity claims: "кто это". По требованию OIDC это всегда JWT.
- **Refresh token** — **только** для Authorization Server. Отправляется только на эндпоинт `/token`, чтобы получить новый access token. Клиент его не парсит и напрямую не использует.

---

**Как Resource Server проверяет подпись JWT, не обращаясь к Keycloak на каждый запрос?**

Через JWKS — это JSON Web Key Set. Keycloak публикует свои публичные ключи на `/protocol/openid-connect/certs`. Resource Server скачивает их один раз и кэширует. Дальше он проверяет подпись локально, обычной криптографией, без сетевого запроса.

В header каждого JWT есть `kid` (Key ID) — он говорит, каким из ключей набора подписан токен. Это и позволяет Keycloak ротировать ключи без даунтайма: во время ротации в JWKS одновременно лежат старый и новый ключ.

```typescript
secretOrKeyProvider: passportJwtSecret({
  jwksUri: `${issuer}/protocol/openid-connect/certs`,
  cache: true,
  rateLimit: true,
}),
```

---

**В чём trade-off между локальной JWT-валидацией и Token Introspection?**

Локальная валидация быстрая — доли миллисекунды, без сети. Её цена: Resource Server узнаёт об отзыве токена только по истечении TTL (time to live, время жизни), то есть отзыв не мгновенный.

Introspection (`POST /token/introspect`) делает отзыв видимым сразу. Её цена: сетевой round-trip на каждый запрос и Keycloak как зависимость каждого API-вызова, а не только логина.

Практика: локальная валидация по умолчанию, с коротким TTL access token в 5-15 минут. Introspection — точечно, для высокочувствительных операций вроде переводов денег и admin-действий.

---

**Почему нельзя хардкодить публичный ключ Keycloak в конфиге приложения?**

Три причины:

1. Любая ротация ключей на стороне Keycloak сломает валидацию у всех клиентов с захардкоженным ключом — до ручного передеплоя.
2. При компрометации ключа самый быстрый ответ — сгенерировать новый в Keycloak. Хардкод исключает этот путь.
3. Библиотеки вроде `jwks-rsa` уже решают кэширование и обновление по `kid`. Изобретать своё не нужно.

## Group 4: Keycloak-специфика

**В чём разница между realm role и client role, и как выбрать, какую использовать?**

Realm role существует на уровне всего realm и имеет смысл сразу во всех клиентах (`realm_access.roles`). Client role существует в контексте одного клиента и для остальных смысла не имеет (`resource_access.<client>.roles`).

Правило выбора:

- Право имеет смысл "вообще для пользователя" → realm role.
- Право специфично для одного сервиса, например "может ли пользователь удалять инвойсы в billing-service" → client role этого сервиса.

Если заводить всё как realm roles "для простоты", `realm_access.roles` со временем превращается в свалку, где непонятно, к какому сервису что относится.

---

**Чем принципиально отличаются Identity Brokering и User Federation?**

**Identity Brokering** — Keycloak делегирует **аутентификацию** внешнему IdP (identity provider, внешний провайдер идентичности): Google, другому Keycloak. Пользователь редиректится на внешний провайдер и логинится там. Keycloak получает токен или assertion и создаёт локальную "тень"-учётку, привязанную к внешнему `sub`. Пароль Keycloak не видит вообще.

**User Federation** — Keycloak сам проверяет пароль, но данные и сам bind-запрос идут во внешнее хранилище. Обычно это LDAP (Lightweight Directory Access Protocol) или Active Directory.

Мнемоника: brokering — это "ещё одна кнопка на экране логина", выбор, который пользователь видит. Federation — это "невидимый бэкенд" за стандартной формой логина.

---

**Что такое Protocol Mapper, и когда нужен кастомный SPI-маппер вместо встроенного?**

Protocol Mapper — это правило внутри Client Scope, а кастомный маппер — это Java-плагин на SPI (Service Provider Interface) Keycloak. Маппер превращает данные — атрибут пользователя, роль, статичное значение — в конкретный claim токена.

Встроенных мапперов достаточно, когда данные уже существуют как атрибут, роль или группа пользователя.

Кастомный Protocol Mapper SPI нужен в двух случаях:

- Claim требует данных, которых физически нет в Keycloak — например, "текущий тариф подписки" из внешнего billing-сервиса.
- Логика сложнее декларативного маппинга.

В обоих случаях есть реальная постоянная цена сопровождения: расширение придётся версионировать под версию Keycloak.

## Group 5: NestJS Resource Server

**Почему аутентификация и авторизация в NestJS должны быть двумя разными Guard-классами, а не одним?**

`AuthGuard('jwt')` отвечает на "кто это": валидирует токен и извлекает payload. `RolesGuard` отвечает на "что ему разрешено": сравнивает роли из payload с метаданными декоратора.

Разделение позволяет переиспользовать `RolesGuard` для **других** способов аутентификации — например, для API-ключа внутренних сервисов — без дублирования логики проверки ролей. Слитный Guard пришлось бы копировать целиком, как только появится второй способ аутентификации.

---

**Когда простой role-based проверки недостаточно, и что даёт Keycloak Authorization Services в этом случае?**

Простой проверки ролей не хватает, когда правило зависит от **конкретного** экземпляра ресурса. Обычный случай — ownership: "только свои документы". Второй случай — контекст: время или атрибуты за пределами ролей.

Authorization Services вводит модель Resource + Scope + Policy + Permission. Resource Server выступает как Policy Enforcement Point. Он спрашивает Keycloak — Policy Decision Point — через тикет UMA (User-Managed Access): "может ли этот пользователь применить scope `edit` к ресурсу `Invoice:42`?"

Цена — сетевой round-trip и когнитивная нагрузка модели. Для простого "мои записи против чужих" обычно достаточно проверить `resource.ownerId === user.sub` прямо в коде, не разворачивая полноценный UMA.

---

**Кто должен обновлять access token — клиент или Resource Server, и что должен вернуть API при истёкшем токене?**

Всегда клиент — именно он держит refresh token. Исключение — архитектура BFF (Backend-for-Frontend), где обновление токена вынесено в отдельную, явно спроектированную роль.

Resource Server физически не имеет refresh token пользователя и не должен пытаться его получить. Это сломало бы stateless-модель API, превратив её в скрытый auth-клиент.

Правильная реакция на истёкший или невалидный токен — 401 со структурированным телом ошибки, например `{"error": "token_expired"}`. Что делать дальше — обновлять токен или отправлять на релогин — решает клиент.

---

**Какой архитектурный выбор безопаснее в микросервисах: каждый сервис валидирует JWT сам, или API Gateway валидирует один раз?**

Каждый сервис валидирует сам — это более безопасный дефолт. Особенно в окружениях Kubernetes, где сетевая изоляция не гарантирована: соседний под в том же namespace может достучаться до сервиса напрямую.

Вариант с Gateway оправдан только внутри осознанной zero-trust архитектуры. Она предполагает mTLS — взаимный Transport Layer Security, когда сертификат предъявляют обе стороны — между Gateway и сервисами. "Экономия одного JWKS-запроса" сама по себе не аргумент: валидация по JWKS и так дешёвая локальная операция.

## Group 6: React SPA, хранение токенов, BFF

**Почему Authorization Code + PKCE — единственный правильный флоу для SPA?**

React SPA — это public client. Весь код исполняется в браузере пользователя, и любой "секрет" в JS-бандле доступен через DevTools.

PKCE не требует `client_secret` вообще. Защиту от перехвата authorization code даёт `code_verifier`, и никакого секрета для этого не нужно. Перехваченный `code` бесполезен без оригинального `code_verifier`, который никогда не покидал память легитимного клиента.

---

**В чём заключается проблема `silent-check-sso` в Safari, и как её диагностировать?**

Сначала механизм. Невидимый iframe грузит страницу Keycloak с `prompt=none`. Если у пользователя есть активная сессия, Keycloak тихо отдаёт authorization code через `postMessage`.

Для этого нужно отправить cookie сессии Keycloak в контексте iframe, встроенного в чужой для Keycloak домен — классический сценарий third-party cookie. Safari ITP (Intelligent Tracking Prevention) блокирует third-party cookies по умолчанию. Поэтому `silent-check-sso` молча "не находит" реально активную сессию. Приложение показывает экран логина пользователю, который формально уже залогинен.

**Как диагностировать:**

- Воспроизвести именно в Safari, а не в Chrome с дефолтными настройками.
- Посмотреть сетевые запросы iframe: cookie сессии Keycloak физически не уходит с запросом.

**Как смягчить:**

- Использовать `login-required` вместо `check-sso`, если анонимного контента в приложении нет.
- Перейти на паттерн BFF, который убирает проблему архитектурно.

**Второстепенные гипотезы, которые стоит проверить и исключить:**

- Слишком короткий TTL access token в сочетании с багом в логике `updateToken()` и retry на фронтенде.
- Истёкший из-за неактивности SSO Session Idle timeout.

---

**Сравните хранение токена в памяти, в localStorage и в httpOnly cookie.**

Три варианта — три разные поверхности атаки:

- **В памяти** — недоступен XSS (cross-site scripting, межсайтовый скриптинг), но теряется при обновлении страницы, поэтому нужен silent refresh.
- **localStorage** — доступен **любому** JS, включая внедрённый через XSS. Это единственный вариант, который ничего не даёт взамен, — потому индустрия и считает его недопустимым для токенов.
- **httpOnly cookie** — недоступен XSS, но браузер отправляет его автоматически на каждый запрос к домену, включая инициированные вредоносной страницей. Это CSRF (Cross-Site Request Forgery), поэтому обязательны `SameSite`, `Secure` и точный CORS (Cross-Origin Resource Sharing).

Это выбор не между "безопасно" и "небезопасно", а выбор того, какой вектор атаки вы принимаете как риск.

---

**Объясните паттерн BFF и когда он оправдан по сравнению с public client в браузере.**

BFF убирает проблему архитектурно: браузер никогда не видит access, refresh и ID token — только first-party session cookie самого приложения.

BFF — это confidential client. Обмен Authorization Code + PKCE он делает сам, на сервере. Токены он хранит в Redis или базе данных по session id и проксирует API-запросы, прикрепляя к ним реальный токен.

**Плюсы:**

- XSS физически не может украсть токен — читать нечего.
- Проблема third-party cookie исчезает архитектурно.

**Минусы:**

- Лишний сетевой хоп.
- Ещё один компонент, который надо держать на сервере.
- Сам BFF становится критичной целью атаки.

Оправдан для fintech, healthcare и enterprise-приложений с высокими ставками на безопасность. Для MVP (minimum viable product) классический public client остаётся адекватным и быстрее в реализации.

## Group 7: Атаки и защита

**Почему PKCE важен даже для confidential-клиентов, у которых уже есть client_secret?**

`client_secret` защищает от того, что **кто-то другой** выдаст себя за клиент на шаге обмена code→token. От другого сценария он не защищает.

Атакующий, перехвативший `code`, предназначенный именно этому клиенту, может попробовать обменять его первым. Он использует **тот же** confidential client и обгоняет легитимного пользователя.

PKCE закрывает именно этот сценарий, независимо от типа клиента. Поэтому современный OAuth 2.0 Security BCP (Best Current Practice) рекомендует его для всех клиентов.

---

**В чём разница между `state` и `nonce`, и почему нужны оба?**

`state` защищает сам redirect-обмен от CSRF и replay. Клиент генерирует случайное значение до редиректа, сохраняет его локально и сверяет на callback. Это предотвращает Login CSRF — привязку сессии жертвы к аккаунту атакующего.

`nonce` защищает от повторного использования содержимое ID Token. Keycloak встраивает его **в сам токен** как claim, а клиент сверяет при получении. Это предотвращает повторное предъявление старого, ещё не истёкшего ID Token.

Мнемоника: `state` — это транспорт, `nonce` — это содержимое. Друг друга они не заменяют.

---

**Опишите механику JWT algorithm confusion атаки и как от неё защититься.**

Вариантов атаки два.

**Атака "alg: none".** Атакующий меняет header токена на `{"alg": "none"}` и убирает подпись. Уязвимая библиотека, доверяющая значению `alg` из самого токена, "проверяет" пустую подпись и принимает токен.

**Атака RS256/HS256 confusion.** RS256 — это подпись через RSA (асимметричный алгоритм: подписывают приватным ключом, проверяют публичным). HS256 — это подпись одним общим секретом через HMAC (hash-based message authentication code).

Атакующий меняет header на `{"alg": "HS256"}` и подписывает токен через HMAC, используя как секрет **публичный** RSA-ключ Keycloak. Этот ключ открыто доступен через JWKS. Если библиотека не требует строго ожидаемый алгоритм, а подстраивается под заявленное в токене, — проверка пройдёт.

Защита в обоих случаях одна. Список допустимых алгоритмов **всегда** захардкожен в конфиге Resource Server (`algorithms: ['RS256']`). Из значения внутри токена он не выводится никогда.

---

**Почему refresh token rotation — это механизм обнаружения атаки, а не просто гигиена?**

Каждый обмен refresh token на новую пару отзывает старый. Это превращает кражу токена в событие, которое можно заметить.

Допустим, токен украли через XSS до того, как им воспользовался легитимный клиент. Возможны два порядка:

- **Атакующий использует токен первым.** Легитимное приложение потом пробует использовать свой — уже отозванный — токен и получает ошибку. Эта ошибка и есть сигнал компрометации.
- **Легитимный клиент использует токен первым.** Атакующий позже предъявляет уже отозванный токен, и Keycloak видит попытку повторного использования.

Правильная реакция — отозвать **всю** цепочку токенов этой сессии, а не просто отклонить один запрос. Достоверно определить, какая копия токена "правильная", невозможно.

## Group 8: Архитектура и сценарии

**В чём trade-off между realm-per-tenant и shared realm с группами для мультитенантного SaaS?**

Для мультитенантного SaaS — software as a service — компромисс лежит между изоляцией и операционной нагрузкой.

**Realm-per-tenant** даёт полную изоляцию из коробки: своя политика паролей, своя тема, свои Identity Providers. Цена — операционная нагрузка, растущая линейно с числом тенантов. Realm-as-code конфигурация, мониторинг и апгрейды умножаются на число realm.

**Shared realm с группами** (`/tenants/acme-corp` плюс claim `tenant_id` через Protocol Mapper) так не растёт. Взамен изоляция данных ложится на приложение: Resource Server **обязан** фильтровать по `tenant_id` на каждом запросе. Ошибка здесь — это утечка данных между тенантами, и это уже не проблема Keycloak.

Практика: realm-per-tenant — для enterprise B2B (business-to-business) с десятками-сотнями крупных клиентов и жёсткими compliance-требованиями. Shared realm — для self-serve с тысячами мелких тенантов.

**Сценарий: пользователи на Safari время от времени внезапно "разлогиниваются", хотя ничего похожего на logout не делали. Как вы будете диагностировать проблему?**

Первая гипотеза — вообще не logout, а сбой **проверки** сессии.

Если приложение использует `onLoad: 'check-sso'` в `keycloak-js`, то `silent-check-sso` полагается на iframe, встроенный с домена приложения и читающий cookie сессии Keycloak. Это сценарий third-party cookie, и Safari ITP блокирует его по умолчанию.

**Как проверить.** Воспроизвести именно в Safari при активной сессии Keycloak в соседней вкладке. Вызов `check-sso` не найдёт сессию, хотя она реально жива, и приложение покажет неаутентифицированное состояние.

Если гипотеза подтвердилась, есть три варианта решения:

1. Принять как есть и обеспечить нормальный UX (user experience, пользовательский опыт) для этого случая — видимая кнопка "Войти", а не белый экран.
2. Перейти на `login-required`, если анонимного контента в приложении нет.
3. Архитектурно перейти на паттерн BFF, где идентификация идёт через first-party cookie самого приложения. Проблема third-party cookie тогда исчезает полностью.

**Второстепенные гипотезы, которые тоже стоит проверить и исключить:**

- Слишком короткий TTL access token в сочетании с багом в логике `updateToken()` и retry на фронтенде.
- SSO Session Idle timeout, истёкший из-за реального периода неактивности.

**Спроектируйте auth-архитектуру для нового мультитенантного SaaS на Keycloak — какие решения вы примете и почему?**

Пять решений держат эту архитектуру: мультитенантность, хранение токенов, авторизация, эксплуатация и логаут.

**1. Мультитенантность.** Немного крупных enterprise-клиентов → realm-per-tenant. Каждому из них нужен свой Identity Provider, свой брендинг логина и своя история с compliance, и это оправдывает растущую операционную нагрузку.

Self-serve модель с большим числом мелких тенантов → один shared realm, изоляция группами и claim `tenant_id` в токене. Тогда Resource Server фильтрует по `tenant_id` на **каждом** запросе.

**2. Хранение токенов.** Начинать сразу с паттерна BFF, а не с public client в браузере. У B2B SaaS с корпоративными клиентами реальные требования к безопасности. BFF убирает целый класс проблем архитектурно: XSS-атаке нечего красть, а хрупкость third-party cookie у `silent-check-sso` просто не возникает.

**3. Авторизация.** Realm- и client-роли для статичных правил. Keycloak Authorization Services — только там, где реально нужна авторизация по владению или по контексту, а не по умолчанию.

**4. Эксплуатация.** Keycloak с самого начала разворачивается как HA-кластер (high availability, высокая доступность) с настоящей базой данных PostgreSQL. Realm держим как код — `keycloak-config-cli` или Terraform — чтобы окружения воспроизводились, а не собирались кликами в консоли.

**5. Логаут.** Back-channel logout, а не front-channel. Тогда распространение logout по нескольким клиентам одной SSO-сессии не зависит от состояния браузера пользователя.
