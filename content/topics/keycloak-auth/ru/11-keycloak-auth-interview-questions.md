# Keycloak / OAuth2 / OIDC — вопросы для интервью (Middle → Senior)

## Group 1: Протокольный фундамент

**В чём реальная разница между OAuth2 и OIDC?**

OAuth2 — протокол АВТОРИЗАЦИИ: он отвечает на вопрос "что разрешено предъявителю токена", выдавая access token, но не даёт стандартизированного способа узнать, КТО такой пользователь. OIDC — тонкий слой ИДЕНТИЧНОСТИ, построенный поверх OAuth2 теми же механизмами (те же эндпоинты, те же grant types), добавляющий три конкретные вещи: ID Token (JWT с claims об идентичности — `sub`, `email`, `name`), UserInfo endpoint (получить актуальный профиль по access token'у) и discovery document (`/.well-known/openid-configuration`). Путать их — не терминологическая, а архитектурная ошибка: использование access token'а как доказательства идентичности ("OAuth as authentication" antipattern) было причиной, по которой OIDC вообще появился в 2014 году.

---

**Назовите четыре роли OAuth2 и объясните, почему backend-сервис может быть одновременно двумя из них.**

Resource Owner (пользователь), Client (приложение, запрашивающее доступ), Authorization Server (Keycloak — аутентифицирует и выдаёт токены), Resource Server (API, владеющее защищёнными данными). NestJS-бэкенд в связке "React SPA + API" — это Resource Server по отношению к SPA. Но тот же самый бэкенд, вызывая ДРУГОЙ внутренний сервис от своего имени (без пользователя, через Client Credentials Grant), в этот момент выступает как Client. Путаница "кто есть кто" в конкретной архитектуре — источник неправильных решений о том, кто должен обновлять токены и где их хранить.

---

**Что такое front-channel и back-channel, и почему это разделение важно?**

Front-channel — данные идут через браузер пользователя (редиректы, query-параметры, URL fragment) — видны в истории браузера, Referer-заголовке, логах прокси. Back-channel — прямое серверное соединение, минуя браузер, невидимое пользователю. Правило: секреты и токены должны передаваться по back-channel там, где возможно. Именно это разделение объясняет, почему Authorization Code Grant (только одноразовый code через front-channel, обмен на токены — по back-channel) безопаснее Implicit Grant (токен прямо в URL fragment — front-channel).

## Group 2: Grant Types

**Почему Implicit Grant считается устаревшим — дайте конкретный технический ответ, а не "он старый".**

Три конкретные причины: (1) токен передаётся через URL fragment — front-channel — и оказывается в истории браузера, Referer-заголовке при переходе по внешней ссылке, логах прокси; (2) токен выдаётся сразу на редиректе без дополнительной проверки клиента, в отличие от Authorization Code, где back-channel обмен code→token даёт возможность проверить PKCE code_verifier или client secret; (3) нет refresh token'а (это тоже было бы небезопасно через front-channel), поэтому продление сессии зависело от хрупкого iframe-механизма с `prompt=none`.

---

**Почему ROPC (Resource Owner Password Credentials) не подходит для современных приложений?**

Клиент физически собирает пароль пользователя в своей форме — это прямо противоречит цели OAuth2 "не раскрывать пароль третьей стороне". Практические потери: невозможен MFA/step-up без переизобретения его внутри клиента (Authorization Server не видит и не контролирует форму логина), невозможен SSO (пользователь логинится заново в каждом клиенте отдельно). Keycloak по умолчанию отключает Direct Access Grants для новых клиентов.

---

**Когда стоит использовать Client Credentials Grant, и что принципиально отличает его от логина пользователя?**

Когда за токеном обращается сервис от своего собственного имени, без пользователя — например, внутренний RPC между микросервисами. Принципиальное отличие: нет front-channel шага вообще (нет браузера, нет редиректа), весь обмен — один back-channel POST на `/token` с `client_id`+`client_secret`. Выданный токен не содержит `sub`, указывающий на реального пользователя, и не выдаётся ID Token — идентифицировать здесь некого.

## Group 3: Токены и валидация

**Объясните разницу между access token, ID token и refresh token — куда каждый отправляется и кто его использует.**

Access token — предназначен Resource Server'у, отправляется в заголовке `Authorization: Bearer` на каждый API-запрос, содержит scope/roles ("что разрешено"). ID Token — предназначен только клиентскому приложению для отображения информации о пользователе, никогда не должен отправляться на другие API как access token, содержит identity claims ("кто это"), обязан быть JWT по требованию OIDC. Refresh token — предназначен ТОЛЬКО Authorization Server'у, отправляется только на `/token` endpoint для получения нового access token'а, никогда не парсится и не используется клиентом напрямую.

---

**Как Resource Server проверяет подпись JWT, не обращаясь к Keycloak на каждый запрос?**

Через JWKS (JSON Web Key Set) — Keycloak публикует свои публичные ключи на `/protocol/openid-connect/certs`, Resource Server скачивает их один раз, кэширует, и дальше проверяет подпись локально криптографией, без сетевого запроса. Каждый JWT в header содержит `kid` (Key ID), указывающий, каким из нескольких ключей в JWKS он подписан — это позволяет Keycloak ротировать ключи без даунтайма: во время ротации в JWKS одновременно присутствуют старый и новый ключ.

```typescript
secretOrKeyProvider: passportJwtSecret({
  jwksUri: `${issuer}/protocol/openid-connect/certs`,
  cache: true,
  rateLimit: true,
}),
```

---

**В чём trade-off между локальной JWT-валидацией и Token Introspection?**

Локальная валидация — быстрая (доли миллисекунды, без сети), но Resource Server узнаёт об отзыве токена только по истечении TTL (revocation не мгновенный). Introspection (`POST /token/introspect`) — даёт мгновенное знание об отзыве, но добавляет сетевой round-trip на каждый запрос и делает Keycloak зависимостью каждого API-вызова, а не только логина. Практика: локальная валидация по умолчанию с коротким access token TTL (5-15 минут), introspection — точечно для высокочувствительных операций (переводы денег, admin-действия).

---

**Почему нельзя хардкодить публичный ключ Keycloak в конфиге приложения?**

Три причины: (1) ротация ключей на стороне Keycloak сломает валидацию у всех клиентов с захардкоженным ключом до ручного передеплоя; (2) при компрометации ключа единственный быстрый ответ — сгенерировать новый в Keycloak, хардкод исключает этот путь; (3) библиотеки типа jwks-rsa уже решают задачу кэширования и обновления по `kid` — изобретать своё не нужно.

## Group 4: Keycloak-специфика

**В чём разница между realm role и client role, и как выбрать, какую использовать?**

Realm role существует на уровне всего realm'а и имеет смысл во всех клиентах одновременно (`realm_access.roles`). Client role существует в контексте конкретного клиента и не имеет смысла для других (`resource_access.<client>.roles`). Правило выбора: если право имеет смысл "вообще для пользователя" — realm role; если специфично для одного сервиса ("может ли пользователь удалять инвойсы в billing-service") — client role этого сервиса. Заводить всё как realm roles "для простоты" со временем превращает `realm_access.roles` в свалку без понимания, к какому сервису что относится.

---

**Чем принципиально отличаются Identity Brokering и User Federation?**

Identity Brokering — Keycloak делегирует АУТЕНТИФИКАЦИЮ внешнему IdP (Google, другой Keycloak): пользователь редиректится на внешний провайдер, логинится там, Keycloak получает токен/assertion и создаёт локальную "тень"-учётку, привязанную к внешнему `sub`. Пароль Keycloak не видит вообще. User Federation — Keycloak сам проверяет пароль, но данные (и сам bind-запрос) идут во внешнее хранилище — типично LDAP/AD. Мнемоника: brokering — "ещё одна кнопка на экране логина" (видимый UX-выбор), federation — "невидимый бэкенд" для стандартной формы логина.

---

**Что такое Protocol Mapper, и когда нужен кастомный SPI-маппер вместо встроенного?**

Protocol Mapper — правило внутри Client Scope, превращающее данные (атрибут пользователя, роль, статичное значение) в конкретный claim токена. Встроенных мапперов достаточно, когда данные УЖЕ существуют как атрибут/роль/группа пользователя. Кастомный Protocol Mapper SPI (Java) нужен, когда claim требует данных, которых физически нет в Keycloak (например, "текущий тариф подписки" из внешнего billing-сервиса), или логики сложнее декларативного маппинга — с реальной ongoing maintenance-ценой (версионирование против версии Keycloak).

---

## Group 5: NestJS Resource Server

**Почему аутентификация и авторизация в NestJS должны быть двумя разными Guard'ами, а не одним?**

`AuthGuard('jwt')` отвечает на "кто это" (валидация токена, извлечение payload), `RolesGuard` — на "что ему разрешено" (сравнение ролей из payload с метаданными декоратора). Разделение позволяет переиспользовать `RolesGuard` для ДРУГИХ способов аутентификации (например, API-ключ для внутренних сервисов) без дублирования логики проверки ролей. Слитный Guard пришлось бы копировать целиком при появлении второго способа аутентификации.

---

**Когда простой role-based проверки недостаточно, и что даёт Keycloak Authorization Services в этом случае?**

Когда правило зависит от КОНКРЕТНОГО экземпляра ресурса (ownership: "только свои документы") или от контекста (время, атрибуты за пределами ролей). Authorization Services вводит модель Resource + Scope + Policy + Permission: Resource Server (Policy Enforcement Point) спрашивает Keycloak (Policy Decision Point) через UMA-ticket запрос "может ли этот пользователь выполнить scope 'edit' над resource 'Invoice:42'?". Цена — сетевой round-trip и когнитивная нагрузка модели; для простого "мои записи vs чужие" часто достаточно проверить `resource.ownerId === user.sub` прямо в коде, не разворачивая полноценный UMA.

---

**Кто должен обновлять access token — клиент или Resource Server, и что должен вернуть API при истёкшем токене?**

Всегда клиент — именно он держит refresh token (кроме BFF-архитектуры, где это отдельная, явно спроектированная роль). Resource Server физически не имеет refresh token'а пользователя и не должен пытаться его получить — это сломало бы stateless-модель API, превратив его в скрытый auth-клиент. Правильная реакция на истёкший/невалидный токен — 401 со структурированным телом ошибки (`{"error": "token_expired"}`), а дальнейшая реакция (refresh или релогин) целиком на стороне клиента.

---

**Какой архитектурный выбор безопаснее в микросервисах: каждый сервис валидирует JWT сам, или API Gateway валидирует один раз?**

Каждый сервис валидирует сам — более безопасный дефолт, особенно в k8s-окружениях, где сетевая изоляция не гарантирована (соседний под в том же namespace может физически достучаться до сервиса напрямую). Вариант с Gateway оправдан только как часть осознанной zero-trust архитектуры с mTLS между Gateway и сервисами — а не просто "экономия одного JWKS-запроса", тем более что JWKS-валидация и так дешёвая локальная операция.

## Group 6: React SPA, хранение токенов, BFF

**Почему Authorization Code + PKCE — единственный правильный флоу для SPA?**

React SPA — public client: весь код исполняется в браузере пользователя, любой "секрет" в JS-бандле доступен через DevTools. PKCE не требует client_secret вообще — `code_verifier` защищает от перехвата authorization code без всякого секрета, потому что перехваченный `code` бесполезен без оригинального `code_verifier`, который никогда не покидал память легитимного клиента.

---

**В чём заключается проблема silent-check-sso в Safari, и как её диагностировать?**

Механизм: невидимый iframe грузит Keycloak-страницу с `prompt=none`, и если у пользователя есть активная сессия — Keycloak внутри iframe тихо отдаёт authorization code через `postMessage`. Это требует отправки cookie сессии Keycloak в контексте iframe, встроенного в чужой (для Keycloak) домен — классический third-party cookie сценарий. Safari ITP блокирует third-party cookies по умолчанию, поэтому silent-check-sso молча "не находит" реально активную сессию, и приложение показывает экран логина пользователю, который формально уже залогинен. Диагностика: воспроизвести именно в Safari (не в Chrome с дефолтными настройками), проверить сетевые запросы iframe — cookie сессии Keycloak физически не уходит с запросом. Митигации: `login-required` вместо `check-sso` при отсутствии анонимного контента, либо переход на BFF-паттерн, устраняющий проблему архитектурно.

---

**Сравните trade-off'ы хранения токена в памяти, localStorage и httpOnly cookie.**

In-memory — недоступен XSS, но теряется при обновлении страницы (нужен silent refresh). localStorage — доступен ЛЮБОМУ JS, включая внедрённый через XSS — единственный вариант без реального обоснования, почему индустрия считает его недопустимым для токенов. httpOnly cookie — недоступен XSS, но отправляется браузером автоматически на каждый запрос к домену, включая инициированные вредоносной страницей (CSRF) — требует обязательного SameSite + Secure + точного CORS. Это выбор не "безопасно vs небезопасно", а выбор, какой вектор атаки вы принимаете как риск.

---

**Объясните паттерн BFF и когда он оправдан по сравнению с public client в браузере.**

BFF убирает проблему архитектурно: браузер никогда не видит access/refresh/ID token, только first-party session cookie самого приложения. BFF (confidential client) сам делает Authorization Code + PKCE обмен на сервере, хранит токены в Redis/БД по session ID, и проксирует API-запросы, прикрепляя реальный токен. Плюсы: XSS физически не может украсть токен (нечего читать), third-party cookie проблема исчезает архитектурно. Минусы: лишний сетевой хоп, доп. serverful-компонент, BFF сам становится критичной целью атаки. Оправдан для fintech/healthcare/enterprise с высокими ставками на безопасность; для MVP классический public client остаётся адекватным и быстрее в реализации.

## Group 7: Атаки и защита

**Почему PKCE важен даже для confidential-клиентов, у которых уже есть client_secret?**

`client_secret` защищает от того, что КТО-ТО ДРУГОЙ выдаёт себя за клиент на шаге обмена code→token. Но не защищает от сценария, где атакующий перехватил `code`, предназначенный именно этому клиенту, и пытается обменять его через ТОТ ЖЕ confidential client раньше легитимного пользователя (race condition на интерцепции). PKCE закрывает именно этот сценарий независимо от типа клиента, поэтому современный OAuth 2.0 Security BCP рекомендует его для всех клиентов.

---

**В чём разница между `state` и `nonce`, и почему нужны оба?**

`state` защищает сам redirect-обмен от CSRF/replay: клиент генерирует случайное значение до редиректа, сохраняет локально, сверяет на callback — предотвращает Login CSRF (привязку сессии жертвы к аккаунту атакующего). `nonce` защищает содержимое ID Token от повторного использования: Keycloak встраивает его В САМ токен как claim, клиент сверяет при получении — предотвращает повторное предъявление старого, ещё не истёкшего ID Token'а. Мнемоника: `state` — транспорт, `nonce` — содержимое; они не заменяют друг друга.

---

**Опишите механику JWT algorithm confusion атаки и как от неё защититься.**

Атака "alg: none" — атакующий меняет header токена на `{"alg": "none"}`, убирает подпись; уязвимая библиотека, доверяющая `alg` из самого токена, "проверяет" пустую подпись и принимает токен. Атака RS256/HS256 confusion — атакующий меняет header на `{"alg": "HS256"}` и подписывает токен HMAC'ом, используя ПУБЛИЧНЫЙ RSA-ключ Keycloak (открыто доступный через JWKS) как секрет; если библиотека не проверяет строго ожидаемый алгоритм, а "подстраивается" под то, что заявлено в токене — проверка пройдёт. Защита в обоих случаях одна: `algorithms` ВСЕГДА захардкожен в конфиге Resource Server'а (`algorithms: ['RS256']`), никогда не выводится из значения внутри токена.

---

**Почему refresh token rotation — это механизм обнаружения атаки, а не просто гигиена?**

Каждый обмен refresh token'а на новую пару отзывает старый. Если токен украден (например, через XSS до использования легитимным клиентом): если атакующий использует его первым — легитимное приложение при попытке использовать СВОЙ (уже отозванный) токен получит ошибку — сигнал компрометации. Если легитимный клиент использует первым — атакующий, пытаясь использовать уже отозванный токен, сигнализирует Keycloak о попытке reuse. Правильная реакция — отзыв ВСЕЙ цепочки токенов сессии, а не просто отклонение одного запроса, потому что невозможно достоверно отличить, какая копия токена "правильная".

## Group 8: Архитектура и сценарии

**В чём trade-off между realm-per-tenant и shared realm с группами для мультитенантного SaaS?**

Realm-per-tenant даёт полную изоляцию из коробки (своя политика паролей, тема, Identity Providers) — но операционная нагрузка растёт линейно с числом тенантов (realm-as-code конфигурация, мониторинг, апгрейды — всё умножается на N realm'ов). Shared realm с группами (`/tenants/acme-corp` + `tenant_id` claim через Protocol Mapper) не растёт линейно, но изоляция данных ложится на приложение — Resource Server ОБЯЗАН фильтровать по `tenant_id` на каждом запросе, и ошибка здесь — утечка данных между тенантами, уже не Keycloak-проблема. Практика: realm-per-tenant — для enterprise B2B с десятками-сотнями крупных клиентов и жёсткими compliance-требованиями; shared realm — для self-serve с тысячами мелких тенантов.

---

**Сценарий: пользователи на Safari время от времени внезапно "разлогиниваются", хотя ничего похожего на logout не делали. Как вы будете диагностировать проблему?**

Первая гипотеза — не logout, а сбой МЕХАНИЗМА ПРОВЕРКИ сессии: если приложение использует `onLoad: 'check-sso'` в `keycloak-js`, silent-check-sso полагается на iframe, встроенный с домена приложения, читающий cookie сессии Keycloak — это third-party cookie сценарий, который Safari ITP блокирует по умолчанию. Проверка: воспроизвести именно в Safari при активной Keycloak-сессии в соседней вкладке — check-sso не найдёт сессию, хотя она реально жива, и приложение покажет неаутентифицированное состояние. Если гипотеза подтверждается — три варианта решения: (1) принять и обеспечить нормальный UX для этого случая (видимая кнопка "Войти", не белый экран); (2) перейти на `login-required`, если нет анонимного контента; (3) архитектурно перейти на BFF-паттерн, где идентификация идёт через first-party cookie самого приложения, и third-party cookie проблема исчезает полностью. Второстепенные гипотезы, которые тоже стоит проверить и исключить: слишком короткий Access Token TTL в сочетании с багом в логике `updateToken()`/retry на фронтенде, и SSO Session Idle timeout, истёкший из-за реального периода неактивности.

**Спроектируйте auth-архитектуру для нового мультитенантного SaaS на Keycloak — какие решения вы примете и почему?**

Ключевые решения: (1) Мультитенантность — если ожидается небольшое число крупных enterprise-клиентов с индивидуальными требованиями (свой Identity Provider, кастомный брендинг логина, строгий compliance) — realm-per-tenant, несмотря на растущую операционную нагрузку; если self-serve модель с большим числом мелких тенантов — shared realm с group-based изоляцией и `tenant_id` claim'ом, обязательно фильтруемым в КАЖДОМ запросе Resource Server'а. (2) Хранение токенов — при наличии реальных требований к безопасности (что типично для B2B SaaS с корпоративными клиентами) начинать сразу с BFF-паттерна, а не с public client в браузере — убирает целый класс проблем (XSS-кража токена, third-party cookie хрупкость silent-check-sso) архитектурно. (3) Авторизация — realm/client roles для статичных правил, Keycloak Authorization Services только там, где реально нужна ownership-based или контекстная авторизация, не по умолчанию. (4) Эксплуатация — Keycloak с самого начала разворачивается как HA-кластер с настоящей БД (PostgreSQL) и realm-as-code (keycloak-config-cli/Terraform) для воспроизводимости окружений, а не кликами в консоли. (5) Логаут — back-channel logout, а не front-channel, чтобы не зависеть от состояния браузера пользователя при распространении logout по нескольким клиентам одной SSO-сессии.
