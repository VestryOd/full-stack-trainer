# Хранение токенов и паттерн BFF

## Центральное архитектурное решение SPA-безопасности

Всё, что разбиралось в статье 05 (silent-check-sso, refresh, логаут), происходит НА ФОНЕ одного решения, которое определяет весь профиль риска приложения: **где физически лежит токен в браузере**. Это не деталь реализации, которую можно поменять позже без последствий — это решение, вокруг которого строится вся модель угроз SPA. Эта статья разбирает варианты честно, без единственного "правильного" ответа на все случаи, а затем показывает архитектуру, которая всё чаще выбирается вместо компромисса вообще — BFF (Backend-for-Frontend).

Ключевой вывод из таблицы, который часто упускают: **это не выбор "безопасно vs небезопасно" — это выбор, КАКОЙ вектор атаки вы принимаете как риск**. In-memory и httpOnly cookie оба закрывают XSS-чтение токена, но открывают разные вторичные проблемы (потеря состояния при обновлении vs необходимость CSRF-защиты). localStorage — единственный вариант в таблице, который не решает НИ ОДНОЙ из проблем лучше остальных, поэтому индустриальный консенсус ("никогда не храните токен в localStorage") оправдан не догмой, а тем, что этот вариант доминируется (dominated) любым из двух других по параметру XSS без компенсирующих преимуществ.

## "httpOnly cookie" — не бесплатная победа

Частая ошибка при первом знакомстве с темой — услышать "httpOnly cookie защищает от XSS" и остановиться, посчитав вопрос закрытым. HttpOnly решает ровно одну проблему (JS не может прочитать cookie) и создаёт ровно одну новую: **браузер отправляет эту cookie АВТОМАТИЧЕСКИ на каждый запрос к домену, независимо от того, кто инициировал запрос** — в том числе запрос, инициированный вредоносной страницей, которую пользователь открыл в соседней вкладке (CSRF, Cross-Site Request Forgery — детальный механизм разобран в общей security-теме, здесь фокус на том, как это применимо именно к auth-cookie).

```txt
Обязательный минимум защиты для auth-cookie, а не опция "на будущее":

  SameSite=Strict или Lax:
    Strict — cookie не отправляется НИ ПРИ КАКОЙ кросс-сайтовой
             навигации, даже при переходе по ссылке с другого сайта.
             Самый безопасный вариант, но может сломать сценарий
             "пользователь перешёл по ссылке из письма — должен
             остаться залогинен".
    Lax    — cookie отправляется при top-level GET-навигации
             (переход по ссылке), но не при кросс-сайтовых POST/
             fetch/XHR с других доменов. Практический дефолт для
             большинства приложений.

  Secure:
    Cookie передаётся ТОЛЬКО по HTTPS — без этого флага cookie
    может быть перехвачена по незашифрованному каналу.

  CORS-конфигурация именно для auth-эндпоинтов:
    Access-Control-Allow-Origin должен быть КОНКРЕТНЫМ доменом,
    никогда "*" (wildcard) при Access-Control-Allow-Credentials: true —
    браузеры и не разрешат такую комбинацию, но неправильно
    настроенный сервер, отражающий Origin из запроса как есть без
    whitelist-проверки, эффективно создаёт тот же риск, что и wildcard.
```

Итог: httpOnly cookie убирает XSS-вектор кражи токена, но требует ТАКОЙ ЖЕ инженерной дисциплины (SameSite, Secure, точный CORS) как и любое другое решение — "просто используйте httpOnly cookie" без остального конфига не safer по умолчанию, это лишь смещённый набор требований.

## BFF (Backend-for-Frontend) — токены вообще не попадают в браузер

Все три варианта выше разделяют одну общую проблему: **браузер (в каком-то виде) всё равно держит артефакт, дающий доступ к API** — токен в памяти, в storage или cookie. BFF-паттерн убирает эту проблему архитектурно, а не выбором лучшего места хранения: **браузер вообще никогда не видит access/refresh/ID token**. Единственное, что попадает в браузер — обычная сессионная cookie самого приложения (first-party, не Keycloak).

```txt
Классический "public client в браузере" (статьи 01-05):

  Браузер ──(Auth Code + PKCE)──► Keycloak
  Браузер ──(держит access/refresh token)──► напрямую хранит их
  Браузер ──(Authorization: Bearer <token>)──► NestJS API

BFF-паттерн:

  Браузер ──(обычная HTTP-сессия, только first-party session cookie)──► BFF
  BFF (сервер, НЕ браузер) ──(Auth Code + PKCE, ЗДЕСЬ хранится
       client_secret — BFF это confidential client)──► Keycloak
  BFF ──(держит access/refresh token НА СЕРВЕРЕ, в своей сессии/Redis)──►
  BFF ──(проксирует запрос, прикрепляя реальный access token)──► NestJS API
```

```txt
Пошаговый request flow:

1. Браузер → GET /login (на BFF, не на Keycloak напрямую)
2. BFF генерирует code_verifier, редиректит браузер на Keycloak
   /authorize (Auth Code + PKCE, ТЕПЕРЬ BFF выступает как client)
3. Пользователь логинится на Keycloak как обычно
4. Keycloak редиректит браузер на BFF callback URL с authorization code
5. BFF (back-channel, СЕРВЕР-СЕРВЕР) обменивает code на access/id/
   refresh токены — эти токены НИКОГДА не попадают в HTTP-ответ браузеру
6. BFF создаёт СВОЮ СОБСТВЕННУЮ сессию (session ID), сохраняет токены
   Keycloak в серверном хранилище (Redis/БД) под этим session ID,
   и отдаёт браузеру ТОЛЬКО httpOnly first-party cookie с session ID
   BFF (НЕ токен Keycloak)
7. Дальнейшие запросы: браузер → GET /api/orders (обычная cookie
   сессии BFF) → BFF смотрит session ID в cookie → достаёт
   СОХРАНЁННЫЙ access token из Redis → проксирует запрос к NestJS
   Resource Server с Authorization: Bearer <реальный токен>
8. Refresh: BFF сам следит за TTL сохранённого access token'а и
   обновляет его через refresh token — ПОЛНОСТЬЮ на сервере,
   браузер вообще не участвует и не знает о самом факте refresh
```

```typescript
// NestJS BFF — упрощённый пример сессионного прокси-эндпоинта
@Controller()
export class BffController {
  constructor(
    private sessionStore: SessionTokenStore, // Redis-backed хранилище токенов по sessionId
    private http: HttpService,
  ) {}

  @Get('callback')
  async handleCallback(@Query('code') code: string, @Req() req: Request, @Res() res: Response) {
    const tokens = await this.exchangeCodeForTokens(code); // back-channel POST /token

    const sessionId = randomUUID();
    await this.sessionStore.save(sessionId, tokens); // токены живут ТОЛЬКО на сервере

    res.cookie('bff_session', sessionId, {
      httpOnly: true,
      secure: true,
      sameSite: 'lax',
    });
    res.redirect('/dashboard');
  }

  @All('api/*')
  async proxyToResourceServer(@Req() req: Request, @Res() res: Response) {
    const sessionId = req.cookies.bff_session;
    const tokens = await this.sessionStore.getFreshTokens(sessionId); // сам обновляет при истечении

    const upstream = await firstValueFrom(
      this.http.request({
        method: req.method,
        url: `https://api.internal${req.path.replace('/api', '')}`,
        headers: { Authorization: `Bearer ${tokens.accessToken}` },
        data: req.body,
      }),
    );
    res.status(upstream.status).json(upstream.data);
  }
}
```

Обратите внимание: `bff_session` — это не JWT и не токен Keycloak, это непрозрачный session ID собственной сессии BFF, семантически идентичный любой традиционной server-side веб-сессии (той же природы, что cookie у классического Express/Rails-приложения до всякого OAuth2). Именно поэтому BFF архитектурно устраняет проблему third-party cookie из статьи 05 — silent-check-sso вообще не нужен, потому что нет чужого домена Keycloak, чью cookie надо было бы читать из iframe: аутентификация теперь идёт через first-party cookie самого приложения, отправляемую браузером на СВОЙ ЖЕ домен обычным образом, как любая другая веб-сессия.

## Честное сравнение — BFF не бесплатен

```txt
Public client в браузере (классический SPA):

  ✓ Проще инфраструктурно — нет отдельного серверного компонента
    для auth, SPA может быть чисто статическим хостингом (CDN)
  ✓ Меньше latency — браузер обращается к API напрямую, без
    дополнительного прыжка через прокси-слой
  ✗ Токен физически присутствует в браузере в каком-то виде —
    остаточный XSS-риск, даже при in-memory хранении (память
    процесса рендерера доступна отладчику/расширениям браузера
    с достаточными правами, хотя это уже выходит за пределы
    типичной модели угроз)
  ✗ silent-check-sso хрупкость (статья 05) — architectural дефект,
    а не баг конкретной реализации

BFF:

  ✓ Токены НИКОГДА физически не существуют в браузере — XSS,
    даже успешный, не может украсть access/refresh token, потому
    что скрипту физически нечего читать (только session cookie,
    которая ничего не даёт без остального сервера BFF за ней)
  ✓ Third-party cookie проблема исчезает архитектурно
  ✓ Refresh-логика, ротация токенов, обработка отзыва — всё в
    одном месте на сервере, а не размазано по клиентскому коду
  ✗ Дополнительный сетевой прыжок на каждый API-запрос (браузер →
    BFF → Resource Server) — реальная, измеримая latency-стоимость
  ✗ Дополнительный serverful-компонент — SPA больше не может быть
    чисто статическим сайтом, BFF должен быть развёрнут, отмасштабирован,
    промониторен как полноценный сервис с состоянием (серверные сессии)
  ✗ BFF сам становится confidential client, хранящим client_secret и
    токены пользователей — это новая, критичная по данным цель атаки,
    которую нужно защищать так же серьёзно, как сам Resource Server
```

Практическая рекомендация, а не универсальный вердикт: **для нового проекта с реальными требованиями к безопасности (финтех, healthcare, корпоративные внутренние системы) BFF — оправданная стандартная точка старта сегодня**, потому что убирает целый класс проблем архитектурно, а не патчами, и растущее количество гайдов (включая рекомендации OAuth 2.0 Security Best Current Practice для браузерных приложений) склоняется именно к этому паттерну. Для небольшого MVP или внутреннего инструмента с невысокими ставками классический public-client-подход из статей 01-05 остаётся адекватным и значительно быстрее в реализации — важно понимать это как осознанный компромисс "скорость/простота сейчас vs меньшая площадь атаки", а не как "мы не знали про BFF".

## Итоговая связь понятий

```txt
[In-memory / localStorage /
 httpOnly cookie]              →  каждый вариант обменивает XSS-риск
                                 на CSRF-риск или на потерю состояния
                                 при перезагрузке — нет варианта
                                 без компромисса, кроме localStorage,
                                 который проигрывает по всем параметрам

[httpOnly ≠ безопасно само по
 себе]                          →  требует SameSite + Secure + точный
                                 CORS — та же инженерная дисциплина,
                                 просто другой набор требований

[BFF]                           →  архитектурное устранение проблемы:
                                 токены не покидают сервер вообще,
                                 браузер работает только с обычной
                                 first-party веб-сессией

[Trade-off BFF vs public
 client]                        →  меньшая площадь атаки и решённая
                                 third-party cookie проблема vs

                                 и latency — реальный архитектурный
                                 выбор, не "прогресс vs отсталость"
```

## Типичные ошибки на интервью

- **"localStorage удобен и достаточно безопасен, если приложение в целом хорошо защищено от XSS"** — рискованный ответ: "хорошо защищено от XSS" никогда не бывает гарантией (одна уязвимая зависимость в npm-дереве достаточна), а localStorage не даёт вообще никакой defense-in-depth на этот случай, в отличие от httpOnly cookie или in-memory хранения. Правильный ответ признаёт, что localStorage для токенов — не защищаемая позиция, а не "хорошая практика при определённых условиях".

- **"httpOnly cookie полностью решает проблему безопасности токенов"** — неполно: закрывает XSS-чтение, но открывает CSRF-вектор, требующий отдельной, обязательной защиты (SameSite, точный CORS). Ответ, не упоминающий CSRF, показывает поверхностное знание темы.

- **"BFF — это просто прокси, не даёт реальной security-выгоды, только лишний хоп"** — недооценка: BFF убирает токен из браузера АРХИТЕКТУРНО, а не просто перекладывает его — это меняет саму площадь атаки (XSS больше не может украсть access/refresh token, потому что их физически негде читать), а не просто добавляет сетевой слой без смысла.

- **"BFF — это всегда правильный выбор, public client в браузере устарел"** — избыточно: BFF добавляет реальную операционную сложность (serverful-компонент, latency, дополнительная критичная цель атаки) и оправдан для приложений с высокими ставками на безопасность, но не является безусловно превосходящим выбором для любого проекта — MVP и внутренние инструменты часто разумно выбирают более простой public-client-подход.

- **"Раз токены хранятся на сервере в BFF, refresh token rotation больше не нужна"** — нет, rotation (статья 03) защищает от кражи refresh token'а КАК АРТЕФАКТА — независимо от того, произошла кража из браузера или из скомпрометированного серверного хранилища BFF (Redis с неправильными правами доступа, например) — BFF снижает вероятность одного вектора кражи, но не отменяет ценность rotation как отдельного механизма breach-detection.
