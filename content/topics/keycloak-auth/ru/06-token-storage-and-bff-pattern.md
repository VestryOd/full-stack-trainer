# Хранение токенов и паттерн BFF

## Центральное архитектурное решение SPA-безопасности

SPA (single-page application, одностраничное приложение) обязано решить один вопрос раньше всех остальных: **где физически лежит токен в браузере**. Эта статья честно сравнивает три ответа, а затем разбирает четвёртый подход, который снимает сам вопрос: паттерн BFF (Backend-for-Frontend).

Это решение определяет весь профиль риска приложения. Это не деталь реализации, которую можно поменять позже без последствий: вокруг него строится вся модель угроз SPA. Всё, что разбиралось в статье 05 (silent-check-sso, refresh, логаут), лежит поверх него.

Единственного "правильного" ответа на все случаи нет. Всё чаще команды выбирают BFF, чтобы вообще не жить с этим компромиссом.

## Три варианта хранения — и что каждый ставит на кон

Таблицу определяют две атаки. XSS (cross-site scripting) — это код атакующего, который выполняется внутри вашей же страницы. CSRF (cross-site request forgery) — это чужой сайт, который заставляет браузер отправить запрос от имени пользователя.

| | In-memory (переменная в JS) | localStorage / sessionStorage | httpOnly cookie |
|---|---|---|---|
| **Доступен XSS-скрипту?** | **Нет** — токен живёт только в замыкании. Ни один API не даёт скрипту доступ к памяти другого скрипта. | **Да** — любой JS читает его через `localStorage.getItem`. Это же делает код, внедрённый через XSS. | **Нет** — JS физически не может его прочитать. В этом и весь смысл флага `httpOnly`. |
| **Переживает обновление страницы?** | **Нет** — полная перезагрузка теряет его. Дальше silent-check-sso приходится запускать заново (статья 05). | **Да** — переживает и обновление. Переживает и закрытие вкладки. | **Да** — браузер пересылает cookie на каждый запрос. В том числе на запросы после обновления. |
| **Уязвим к CSRF?** | **Нет** — токен никуда не отправляется сам. Без явного кода он не уходит никуда. | **Нет** — сам он тоже не отправляется. Отправка требует явного JS-кода. | **Да** — браузер шлёт cookie на каждый запрос к домену. В том числе на запрос, инициированный вредоносным сайтом. |
| **Практическое неудобство** | Требует silent-check-sso или refresh при каждой загрузке. Это та самая хрупкость из статьи 05. | Никогда не используйте его для access token. Это единственный вариант в таблице без реального обоснования. | Требует защиты `SameSite`/CSRF и аккуратной настройки CORS (cross-origin resource sharing). Подробности ниже. |

Ключевой вывод из таблицы часто упускают. **Это не выбор "безопасно vs небезопасно". Это выбор, какой вектор атаки вы принимаете как риск.**

In-memory и httpOnly cookie оба закрывают XSS-чтение токена. Взамен каждый открывает свою вторичную проблему: in-memory теряет состояние при обновлении, cookie требует защиты от CSRF.

localStorage — единственный вариант в таблице, который ни по одному параметру не лучше остальных. По защите от XSS он проигрывает и in-memory, и httpOnly cookie, а взамен не даёт ничего. Поэтому правило "никогда не храните токен в localStorage" — не догма индустрии, а прямой вывод из этого сравнения.

```txt
 Не "безопасно vs небезопасно", а какой вектор вы принимаете
┌─────────────────┬──────────────────┬───────────────────────┐
│ хранение        │ закрывает        │ открывает             │
├─────────────────┼──────────────────┼───────────────────────┤
│ in-memory       │ чтение через XSS │ потерю при обновлении │
├─────────────────┼──────────────────┼───────────────────────┤
│ localStorage    │ ничего           │ чтение через XSS      │
├─────────────────┼──────────────────┼───────────────────────┤
│ httpOnly cookie │ чтение через XSS │ CSRF                  │
└─────────────────┴──────────────────┴───────────────────────┘
```

## "httpOnly cookie" — не бесплатная победа

Частая ошибка при первом знакомстве с темой — услышать "httpOnly cookie защищает от XSS", остановиться и посчитать вопрос закрытым.

httpOnly решает ровно одну проблему: JS не может прочитать cookie. И создаёт ровно одну новую. **Браузер отправляет эту cookie автоматически на каждый запрос к домену, независимо от того, кто этот запрос инициировал.** В том числе на запрос, инициированный вредоносной страницей, которую пользователь открыл в соседней вкладке.

Это и есть атака CSRF. Её общий механизм разобран в теме про безопасность; здесь фокус узкий — что CSRF означает именно для auth-cookie.

```txt
          Что httpOnly не закрывает
┌───────────────────────────────────────────┐
│ Вредоносная страница в соседней вкладке   │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ Она инициирует запрос к вашему домену     │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ Браузер сам прикладывает httpOnly-cookie, │
│ кто бы запрос ни инициировал              │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ Ваш API видит аутентифицированный запрос: │
│ это и есть CSRF                           │
└───────────────────────────────────────────┘
```

**Обязательный минимум защиты для auth-cookie** — не опция "на будущее":

- **`SameSite=Strict`** — cookie не отправляется ни при какой кросс-сайтовой навигации, даже при переходе по ссылке с другого сайта. Самый безопасный вариант. Может сломать сценарий "пользователь перешёл по ссылке из письма и должен остаться залогинен".
- **`SameSite=Lax`** — cookie отправляется при top-level GET-навигации, то есть при переходе по ссылке. При кросс-сайтовых `POST`, `fetch` и `XHR` с других доменов она не отправляется. Практический дефолт для большинства приложений.
- **`Secure`** — cookie передаётся только по HTTPS (HTTP поверх шифрованного соединения). Без этого флага её можно перехватить по незашифрованному каналу.
- **Настройка CORS именно для auth-эндпоинтов** — `Access-Control-Allow-Origin` должен называть один конкретный домен, а не wildcard `"*"` при `Access-Control-Allow-Credentials: true`. Такую комбинацию браузеры и сами не разрешат. Но неправильно настроенный сервер, который отражает заголовок `Origin` из запроса как есть, без проверки по белому списку, создаёт тот же риск, что и wildcard.

Итог: httpOnly cookie убирает XSS-вектор кражи токена. Но она требует **той же** инженерной дисциплины, что и любое другое решение: `SameSite`, `Secure`, точный CORS. "Просто используйте httpOnly cookie" без остального конфига не делает систему безопаснее по умолчанию. Это другой набор требований, а не меньший.

## BFF (Backend-for-Frontend) — токены вообще не попадают в браузер

Все три варианта выше делят одну общую проблему. **Браузер в каком-то виде всё равно держит артефакт, дающий доступ к API** — токен в памяти, в storage или в cookie.

BFF-паттерн убирает эту проблему архитектурно, а не выбором лучшего места хранения. **Браузер вообще никогда не видит access, refresh или ID token.** Единственное, что попадает в браузер, — обычная сессионная cookie самого приложения: first-party, не Keycloak.

```txt
Классический "public client в браузере" (статьи 01-05):

  Браузер ──(Auth Code + PKCE)──► Keycloak
  Браузер ──(держит access/refresh token)──► напрямую хранит их
  Браузер ──(Authorization: Bearer <token>)──► NestJS API

BFF-паттерн:

  Браузер ──(обычная HTTP-сессия: одна first-party
             session cookie)──► BFF
  BFF — сервер, а не браузер
       ──(Auth Code + PKCE; здесь хранится client_secret,
          BFF — это confidential client)──► Keycloak
  BFF ──(держит access/refresh token на сервере,
          в своей сессии или Redis)──►
  BFF ──(проксирует запрос, прикрепляя реальный
          access token)──► NestJS API
```

```txt
Пошаговый request flow:

1. Браузер → GET /login (на BFF, не на Keycloak напрямую)
2. BFF генерирует code_verifier и редиректит браузер на
   Keycloak /authorize (Auth Code + PKCE; клиентом теперь
   выступает BFF)
3. Пользователь логинится на Keycloak как обычно
4. Keycloak редиректит браузер на callback URL самого BFF
   с authorization code
5. BFF обменивает code на access/id/refresh токены по
   back-channel, сервер к серверу. Эти токены никогда не
   попадают в HTTP-ответ браузеру
6. BFF создаёт собственную сессию (session ID) и сохраняет
   токены Keycloak в серверном хранилище (Redis или БД) под
   этим session ID. Браузеру уходит только httpOnly
   first-party cookie с session ID самого BFF, а не токен
   Keycloak
7. Дальнейшие запросы: браузер → GET /api/orders (обычная
   cookie сессии BFF) → BFF смотрит session ID в cookie →
   достаёт сохранённый access token из Redis → проксирует
   запрос к NestJS Resource Server с заголовком
   Authorization: Bearer <реальный токен>
8. Refresh: BFF сам следит за TTL сохранённого access token
   и обновляет его через refresh token. Всё это происходит
   полностью на сервере: браузер не участвует и не знает
   о самом факте refresh
```

```typescript
// NestJS BFF — упрощённый пример сессионного прокси-эндпоинта
@Controller()
export class BffController {
  constructor(
    private sessionStore: SessionTokenStore, // Redis-backed хранилище токенов по sessionId
    private http: HttpService,
  ) {}

  @Get('callback')
  async handleCallback(
    @Query('code') code: string,
    @Req() req: Request,
    @Res() res: Response,
  ) {
    const tokens = await this.exchangeCodeForTokens(code); // back-channel POST /token

    const sessionId = randomUUID();
    await this.sessionStore.save(sessionId, tokens); // токены живут только на сервере

    res.cookie('bff_session', sessionId, {
      httpOnly: true,
      secure: true,
      sameSite: 'lax',
    });
    res.redirect('/dashboard');
  }

  @All('api/*')
  async proxyToResourceServer(@Req() req: Request, @Res() res: Response) {
    const sessionId = req.cookies.bff_session;
    // getFreshTokens сам обновит access token, когда тот истечёт
    const tokens = await this.sessionStore.getFreshTokens(sessionId);

    const upstream = await firstValueFrom(
      this.http.request({
        method: req.method,
        url: `https://api.internal${req.path.replace('/api', '')}`,
        headers: { Authorization: `Bearer ${tokens.accessToken}` },
        data: req.body,
      }),
    );
    res.status(upstream.status).json(upstream.data);
  }
}
```

Обратите внимание: `bff_session` — это не JWT (JSON Web Token) и не токен Keycloak. Это непрозрачный session ID собственной сессии BFF. Семантически он ничем не отличается от любой традиционной серверной веб-сессии: такую же cookie ставило классическое приложение на Express или Rails задолго до всякого OAuth2.

Именно поэтому BFF архитектурно устраняет проблему third-party cookie из статьи 05. Нет чужого домена Keycloak, чью cookie надо было бы читать из iframe, поэтому silent-check-sso вообще не нужен. Аутентификация идёт через first-party cookie самого приложения, и браузер отправляет её на **свой же** домен обычным образом, как любую другую веб-сессию.

## Честное сравнение — BFF не бесплатен

```txt
Public client в браузере (классический SPA):

  ✓ Проще инфраструктурно — нет отдельного серверного компонента
    для auth, SPA может быть чисто статическим хостингом (CDN)
  ✓ Меньше latency — браузер обращается к API напрямую, без
    дополнительного прыжка через прокси-слой
  ✗ Токен физически присутствует в браузере в каком-то виде —
    остаточный XSS-риск даже при in-memory хранении (память
    процесса рендерера доступна отладчику и расширениям
    браузера с достаточными правами, хотя это уже выходит
    за пределы типичной модели угроз)
  ✗ Хрупкость silent-check-sso (статья 05) — архитектурный
    дефект, а не баг конкретной реализации

BFF:

  ✓ Токены никогда физически не существуют в браузере — даже
    успешный XSS не может украсть access/refresh token, потому
    что скрипту физически нечего читать (есть только session
    cookie, а она ничего не даёт без сервера BFF за ней)
  ✓ Проблема third-party cookie исчезает архитектурно
  ✓ Refresh-логика, ротация токенов, обработка отзыва — всё в
    одном месте на сервере, а не размазано по клиентскому коду
  ✗ Дополнительный сетевой прыжок на каждый API-запрос (браузер
    → BFF → Resource Server) — реальная, измеримая цена в latency
  ✗ Дополнительный serverful-компонент — SPA больше не может быть
    чисто статическим сайтом: BFF надо разворачивать, масштабировать
    и мониторить как полноценный сервис с состоянием (серверные
    сессии)
  ✗ BFF сам становится confidential client, хранящим client_secret
    и токены пользователей — это новая, критичная по данным цель
    атаки, которую нужно защищать так же серьёзно, как сам
    Resource Server
```

Практическая рекомендация, а не универсальный вердикт. **Для нового проекта с реальными требованиями к безопасности — финтех, медицина, корпоративные внутренние системы — BFF сегодня оправданная стандартная точка старта.**

Он убирает целый класс проблем архитектурно, а не патчами. К этому же паттерну склоняется всё больше гайдов, включая рекомендации OAuth 2.0 Security Best Current Practice для браузерных приложений.

Для небольшого MVP (minimum viable product, минимально жизнеспособный продукт) или внутреннего инструмента с невысокими ставками классический public-client-подход из статей 01-05 остаётся адекватным. И он значительно быстрее в реализации. Важно понимать это как осознанный компромисс: скорость и простота сейчас против меньшей площади атаки. Это не должно звучать как "мы не знали про BFF".

## Итоговая связь понятий

```txt
[In-memory / localStorage /
 httpOnly cookie]           →  каждый вариант меняет XSS-риск на
                               CSRF-риск или на потерю состояния
                               при перезагрузке. Варианта без
                               компромисса нет — кроме localStorage,
                               который проигрывает сразу по всем
                               параметрам

[httpOnly ≠ безопасно

                               CORS: та же инженерная дисциплина,
                               просто другой набор требований

                               токены не покидают сервер вообще,
                               браузер работает только с обычной
                               first-party веб-сессией

[Trade-off BFF vs public
 client]                    →  меньшая площадь атаки и решённая
                               проблема third-party cookie против

                               и latency — реальный архитектурный
                               выбор, а не "прогресс vs отсталость"
```

## Типичные ошибки на интервью

- **"localStorage удобен и достаточно безопасен, если приложение в целом хорошо защищено от XSS"** — рискованный ответ. "Хорошо защищено от XSS" никогда не бывает гарантией: достаточно одной уязвимой зависимости в npm-дереве. На этот случай localStorage не даёт вообще никакой эшелонированной защиты, в отличие от httpOnly cookie или in-memory хранения. Правильный ответ признаёт, что localStorage для токенов — позиция, которую нельзя защитить, а не "хорошая практика при определённых условиях".

- **"httpOnly cookie полностью решает проблему безопасности токенов"** — неполно. Она закрывает XSS-чтение, но открывает CSRF-вектор, а тому нужна отдельная обязательная защита: `SameSite` и точный CORS. Ответ, не упоминающий CSRF, показывает поверхностное знание темы.

- **"BFF — это просто прокси, не даёт реальной выгоды по безопасности, только лишний хоп"** — недооценка. BFF убирает токен из браузера **архитектурно**, а не просто перекладывает его. Это меняет саму площадь атаки: XSS больше не может украсть access или refresh token, потому что их физически негде читать. Это не просто ещё один сетевой слой без смысла.

- **"BFF — это всегда правильный выбор, public client в браузере устарел"** — избыточно. BFF добавляет реальную операционную сложность: serverful-компонент, latency и ещё одну критичную цель атаки. Эта цена оправдана для приложений с высокими ставками на безопасность. Но безусловно лучшим выбором для любого проекта BFF не является — MVP и внутренние инструменты часто разумно выбирают более простой public-client-подход.

- **"Раз токены хранятся на сервере в BFF, refresh token rotation больше не нужна"** — нет. Rotation (статья 03) защищает refresh token **как артефакт**, откуда бы его ни украли. Неважно, вытащили его из браузера или из скомпрометированного серверного хранилища BFF — например, из Redis с неправильными правами доступа. BFF снижает вероятность одного вектора кражи. Но он не отменяет ценность rotation как отдельного способа обнаружить взлом.
