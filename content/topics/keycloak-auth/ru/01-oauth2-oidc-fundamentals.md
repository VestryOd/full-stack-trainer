# OAuth2 / OIDC — фундамент протокола

## Почему без этого нельзя писать безопасный auth-код

Разработчик, который умеет вставить `keycloak-js` в React-приложение и увидеть, что логин работает, но не может объяснить, зачем в запросе участвует `code_challenge`, или почему backend не должен сам "обновлять токен", — работает по инструкции, а не по пониманию протокола. Это работает, пока всё идёт по счастливому пути, и ломается непредсказуемо в первом же нестандартном случае: мобильное приложение, микросервис без пользователя, редирект, который выглядит подозрительно похоже на легитимный.

Всё, что будет в следующих статьях этой темы — конкретная конфигурация Keycloak, конкретный код для NestJS-guard'а, конкретный `keycloak-js`-адаптер в React — это частные реализации ролей и потоков, описанных в этой статье. Если понять эту статью по-настоящему, 80% "странного поведения" Keycloak в проде перестаёт быть странным: становится видно, какая роль что обязана делать по спецификации.

## Роли протокола — с чего начинается любое рассуждение о любом флоу

OAuth2 (RFC 6749) описывает не "как войти на сайт", а более общую задачу: как **Client** получает ограниченный доступ к ресурсу, которым владеет **Resource Owner**, не получая при этом пароль владельца. В протоколе фиксированы четыре роли:

```txt
┌──────────────────┐                   ┌──────────────────────┐
│ Resource Owner   │ логин и согласие  │ Authorization Server │
│ (пользователь,   │◄─────────────────►│ (Keycloak: выдаёт    │
│ владелец данных) │                   │ и подписывает        │
└──────────────────┘                   │ токены)              │
                                       └──────────────────────┘
                                         │ выдаёт токен
                                         │
                                         │
┌───────────────────────┐                    ┌────────────────────┐
│ Client                │◄───────────────┘   │ Resource Server    │
│ (React SPA, мобильное │ предъявляет токен  │ (NestJS API,       │
│ приложение, backend)  │───────────────────►│ владеет защищённым │
└───────────────────────┘                    │ ресурсом)          │
                                             └────────────────────┘
```

- **Resource Owner** — пользователь, которому принадлежат данные (или сам ресурс, если это service-to-service сценарий без человека).
- **Client** — приложение, которое ХОЧЕТ получить доступ к ресурсу от имени Resource Owner. Это НЕ обязательно сервер: React SPA, мобильное приложение и backend-сервис — все три являются "клиентом" в терминах OAuth2, просто с разными свойствами (см. про public/confidential в статье [Keycloak Core Concepts]).
- **Authorization Server** (в нашем стеке — Keycloak) — сервис, который аутентифицирует Resource Owner, получает согласие и выдаёт токены Client'у. Это единственная роль, которая знает пароль пользователя и логику выдачи токенов.
- **Resource Server** — API, которое владеет защищёнными данными (в нашем стеке — NestJS-бэкенд) и принимает решение "пустить/не пустить" на основе предъявленного токена.

Важное следствие этой схемы, которое многие пропускают: **Client и Resource Server — это разные роли, даже если их пишет одна и та же команда**. NestJS-бэкенд в связке "React SPA + NestJS API" — это Resource Server. Но тот же самый NestJS-бэкенд, когда он сам делает запрос к другому внутреннему сервису от своего имени (без пользователя), в этот момент выступает уже как Client (см. Client Credentials Grant ниже). Путаница "кто есть кто" в конкретной архитектуре — источник половины неправильных решений о том, где хранить токен и кто должен его обновлять.

## "OAuth2 — это авторизация, а не аутентификация" — что это означает буквально

Это самая цитируемая фраза в этой теме, и важно понимать её не как лозунг, а как техническое ограничение спецификации.

OAuth2 отвечает на вопрос **"что этому клиенту разрешено делать?"** — он выдаёт **access token**, который говорит Resource Server'у "предъявитель этого токена имеет право на такие-то scope'ы". OAuth2 в чистом виде **не гарантирует** Client'у ничего про то, кто такой пользователь: спецификация не определяет обязательный, стандартизированный способ узнать личность (identity) владельца ресурса. Исторически это приводило к тому, что разработчики начали **злоупотреблять access token'ом** как доказательством идентичности ("если у меня есть валидный access token — значит, я знаю, кто залогинен") — это и есть источник исторически известной проблемы ["OAuth as authentication" antipattern], которую в 2014 году решил OpenID Connect.

```txt
OAuth2 в чистом виде отвечает:
  "Может ли предъявитель этого токена вызвать GET /api/orders?"
                        ↓
                       ДА / НЕТ

OAuth2 НЕ отвечает напрямую:
  "Кто ИМЕННО сейчас залогинен и как его зовут?"
```

**OpenID Connect (OIDC)** — это тонкий, стандартизированный слой идентичности, надстроенный НАД OAuth2 (используются те же эндпоинты, те же грант-типы, тот же флоу редиректов). OIDC добавляет ровно три вещи, которых не хватало:

1. **ID Token** — новый вид токена (всегда JWT, это требование спецификации OIDC, в отличие от access token, формат которого OAuth2 не диктует), который содержит именно claims об идентичности пользователя: `sub` (уникальный идентификатор), `email`, `name`, время аутентификации и т.д. ID Token предназначен **клиенту** — он должен быть верифицирован и **не должен отправляться на другие API** как access token.
2. **UserInfo endpoint** (`/protocol/openid-connect/userinfo` в Keycloak) — стандартизированный REST-эндпоинт, куда клиент может сходить с access token'ом и получить актуальный профиль пользователя (полезно, когда ID Token уже устарел, а профиль мог измениться).
3. **Discovery document** (`/.well-known/openid-configuration`) — JSON-документ, который публикует Authorization Server, описывающий ВСЕ свои эндпоинты и возможности, чтобы клиенту не нужно было хардкодить URL'ы.

```bash
curl https://keycloak.example.com/realms/myrealm/.well-known/openid-configuration
```

```json
{
  "issuer": "https://keycloak.example.com/realms/myrealm",
  "authorization_endpoint": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/auth",
  "token_endpoint": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token",
  "userinfo_endpoint": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/userinfo",
  "jwks_uri": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/certs",
  "end_session_endpoint": "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/logout",
  "grant_types_supported": ["authorization_code", "client_credentials", "refresh_token", "urn:ietf:params:oauth:grant-type:device_code"],
  "response_types_supported": ["code", "none"],
  "code_challenge_methods_supported": ["plain", "S256"]
}
```

Практическое следствие для инженерной работы: **любая нормальная библиотека (keycloak-js, oidc-client-ts, passport-jwt с oidc-стратегией) должна конфигурироваться через issuer URL и сама подтягивать этот документ**, а не через захардкоженные пути на все эндпоинты. Это то, что отличает "работающий у меня на деве" конфиг от конфига, переживающего апгрейд Keycloak, где пути внутри `/protocol/openid-connect/*` в теории могут меняться.

## Front-channel vs back-channel — концепция, которая будет всплывать в каждой статье

Это разделение — не деталь конкретного флоу, а сквозная модель, через которую стоит анализировать ЛЮБОЙ обмен данными в OAuth2/OIDC:

```txt
Front-channel (передний канал):
  Данные идут через БРАУЗЕР пользователя — redirect, query-параметры,
  fragment (#), postMessage. Виден пользователю (адресная строка),
  потенциально виден стороннему коду на странице, может быть
  перехвачен через историю браузера, referrer, логи прокси.
  Пример: редирект на /authorize с параметрами в query string.

Back-channel (задний канал):
  Данные идут СЕРВЕР-СЕРВЕР, напрямую, минуя браузер пользователя.
  TLS-соединение между Client (или Resource Server) и Authorization
  Server. Не виден пользователю, не проходит через историю браузера.
  Пример: обмен authorization code на токены — POST на /token
  напрямую с backend'а (или, для public-клиента, напрямую из
  JS-кода в браузере, но НЕ через redirect).
```

Почему это важно: **любые данные, которые должны остаться секретом (client secret, сами токены), стоит передавать по back-channel там, где это возможно**. Именно это стало причиной, по которой Implicit Grant (передача access token'а через URL fragment — front-channel) признан небезопасным паттерном (подробнее ниже), а Authorization Code Grant (только одноразовый `code` через front-channel, сам обмен на токены — через back-channel) стал стандартом. Дальше по тексту эта пара терминов будет использоваться без переопределения — если флоу что-то передаёт через redirect, это front-channel; если через прямой HTTP-запрос между серверами — back-channel.

## Access Token, ID Token, Refresh Token — три артефакта с разным назначением

Это источник №1 путаницы у разработчиков, впервые заходящих в эту область: все три — это "какие-то токены", выдаваемые в одном ответе, и легко начать использовать их взаимозаменяемо. Это ошибка с реальными последствиями.

```txt
┌────────────────┬──────────────────────┬────────────────────┬────────────────────────┐
│                │ Access Token         │ ID Token           │ Refresh Token          │
├────────────────┼──────────────────────┼────────────────────┼────────────────────────┤
│ Кому           │ Resource Server      │ Client (только!)   │ Authorization Server   │
│ предназначен   │ (API)                │ НЕ отправлять на   │ (только он его         │
│                │                      │ другие API         │ принимает — на /token) │
├────────────────┼──────────────────────┼────────────────────┼────────────────────────┤
│ Формат         │ По OAuth2 —          │ Обязательно JWT    │ По спецификации —      │
│                │ opaque (просто       │ (требование OIDC)  │ opaque (в Keycloak     │
│                │ строка); Keycloak    │                    │ по умолчанию тоже JWT, │
│                │ на практике делает   │                    │ но это деталь          │
│                │ его JWT              │                    │ реализации)            │
├────────────────┼──────────────────────┼────────────────────┼────────────────────────┤
│ Содержит       │ scope, roles,        │ Claims об          │ Как правило —          │
│                │ permissions —        │ идентичности:      │ минимум данных,        │
│                │ "что разрешено"      │ sub, email, name,  │ достаточных для        │
│                │                      │ auth_time —        │ Authorization Server,  │
│                │                      │ "кто это"          │ чтобы найти сессию     │
├────────────────┼──────────────────────┼────────────────────┼────────────────────────┤
│ TTL            │ Короткий             │ Столько же,        │ Длинный (часы/дни)     │
│                │ (минуты)             │ сколько access     │ или до logout          │
├────────────────┼──────────────────────┼────────────────────┼────────────────────────┤
│ Кто использует │ Resource Server      │ Клиентское         │ Клиент — ТОЛЬКО чтобы  │
│                │ на каждый API-запрос │ приложение — чтобы │ получить новую пару    │
│                │ (Authorization:      │ показать "Привет,  │ токенов через          │
│                │ Bearer <token>)      │ Имя" в UI          │ /token endpoint        │
└────────────────┴──────────────────────┴────────────────────┴────────────────────────┘
```

Формат access token и подробности его валидации (JWKS, `kid`, локальная валидация vs introspection) разобраны отдельно в статье [Tokens, Sessions, and Validation] — здесь важно зафиксировать именно смысловую границу трёх артефактов. Общая структура JWT (header.payload.signature) уже разбиралась в теме [JWT, Access Token и Refresh Token] — не повторяем это здесь, фокус этой статьи — на протокольной роли каждого токена, а не на его физическом формате.

Частая ошибка в реальном коде: React-приложение декодирует ID Token и использует его как `Authorization: Bearer <idToken>` при запросах к своему NestJS API. Технически это может даже сработать, если бэкенд слишком доверчиво валидирует любой JWT от того же issuer — но это неправильно по контракту: ID Token не предназначен для Resource Server, у него другой `aud` (audience — та самая аудитория, которая указана в токене как получатель), и ничего не гарантирует, что в нём вообще есть нужные для авторизации claims (roles, scope).

## Scopes vs Claims — то, что часто путают местами

- **Scope** — это запрос доступа. Клиент указывает scope'ы в запросе на `/authorize` (`scope=openid profile email`), тем самым говоря "мне нужен доступ к такой-то категории данных/действий". Scope — это то, о ЧЁМ клиент просит.
- **Claim** — это конкретный факт о пользователе или токене внутри выданного JWT (`email`, `sub`, `realm_access.roles`). Claim — это то, ЧТО клиент реально получил в результате.

```txt
Запрос scope        →  Authorization Server решает, какие claims дать
"scope=openid profile email"
                     →  ID Token содержит: sub, name, preferred_username,
                        email, email_verified ...
```

Связь между scope и набором claims в Keycloak настраивается через **Client Scopes** и **Protocol Mappers** — это чисто keycloak-специфичный механизм, разобранный в статье [Keycloak Core Concepts]. Здесь важно унести протокольный принцип: scope — запрос, claim — результат, и один scope обычно "включает" пачку claims сразу (scope `profile` — это не один claim, а группа: `name`, `family_name`, `given_name`, `picture` и т.д.).

## Grant Types — как конкретно клиент получает токен

Grant Type (иногда говорят "flow") — это конкретный протокольный сценарий обмена: какие сообщения идут между Client, Authorization Server и (иногда) браузером пользователя, чтобы в итоге у клиента оказались токены. Выбор grant type — это не вкусовщина, а прямое следствие того, ЧТО из себя представляет клиент: есть ли у него пользователь перед экраном, может ли он безопасно хранить секрет, какой у него input-интерфейс.

### Authorization Code + PKCE — современный дефолт

Это единственный правильный выбор для интерактивного логина пользователя сегодня — и для confidential-клиентов (backend с client secret), и, что важнее, для public-клиентов (SPA, мобильные приложения), которые физически не могут хранить секрет.

**PKCE** (Proof Key for Code Exchange, произносится "пикси", RFC 7636) — расширение, которое изначально придумали для мобильных приложений, а сегодня Keycloak и большинство современных гайдов рекомендуют для АБСОЛЮТНО всех клиентов, включая confidential — потому что это защита не "от отсутствия секрета", а от отдельного класса атак (authorization code interception), которая актуальна независимо от типа клиента. Полный механизм PKCE (что такое `code_verifier`/`code_challenge`, почему это защищает) разобран подробно в статье [Security Hardening and Attack Vectors] — здесь фиксируем протокольную последовательность шагов.

```txt
Участники: Браузер пользователя, React SPA (Client), Keycloak (AS), NestJS API (RS)

1. [Client, локально]     Сгенерировать случайный code_verifier,
                            вычислить code_challenge = SHA256(code_verifier)

2. [front-channel]        Браузер редиректится на:
                            GET /authorize?
                              response_type=code
                              &client_id=spa-client
                              &redirect_uri=https://app.example.com/callback
                              &scope=openid profile email
                              &state=<случайное значение — CSRF-защита>
                              &code_challenge=<вычислено на шаге 1>
                              &code_challenge_method=S256

3. [на стороне Keycloak]   Пользователь видит форму логина Keycloak
                            (НЕ форму клиента!), вводит логин/пароль,
                            Keycloak аутентифицирует его и запоминает
                            code_challenge вместе с authorization code

4. [front-channel]        Keycloak редиректит браузер обратно:
                            GET https://app.example.com/callback?
                              code=<одноразовый authorization code>
                              &state=<то же значение, что отправляли>

5. [Client]                Проверить, что state совпадает с отправленным
                            (защита от CSRF/replay на редирект)

6. [back-channel]          Client напрямую (не через браузер-редирект)
                            делает POST на /token:
                              grant_type=authorization_code
                              &code=<code с шага 4>
                              &redirect_uri=<тот же, что в шаге 2>
                              &code_verifier=<оригинал с шага 1>
                              &client_id=spa-client

7. [Keycloak, back-channel] Проверяет: SHA256(code_verifier) ==
                            code_challenge, сохранённый на шаге 3.
                            Если совпадает → выдаёт access_token,
                            id_token, refresh_token в JSON-ответе
```

Ключевая деталь, которую стоит проговорить явно: `code` с шага 4 сам по себе **бесполезен без `code_verifier`** — даже если атакующий перехватит его (например, через утечку в логах прокси или через вредоносное приложение, зарегистрированное на тот же custom URL scheme в мобильной ОС), обменять его на токены он не сможет, потому что не знает `code_verifier`, который никогда не покидал память легитимного клиента.

### Client Credentials Grant — service-to-service, без пользователя вообще

Используется, когда за токеном обращается не пользователь, а сам сервис — например, NestJS-сервис A вызывает NestJS-сервис B по внутреннему API, и никакого "залогиненного человека" в этом взаимодействии нет.

```txt
Участники: Service A (Client, confidential), Keycloak (AS)

1. [back-channel, напрямую, без браузера]
   POST /realms/myrealm/protocol/openid-connect/token
     grant_type=client_credentials
     &client_id=service-a
     &client_secret=<секрет, известный только Service A и Keycloak>

2. [Keycloak]
   Проверяет client_id + client_secret → выдаёт access_token
   (без id_token — идентифицировать здесь некого, ID Token
   не выдаётся в этом грант-типе)
```

```bash
curl -X POST https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token \
  -d "grant_type=client_credentials" \
  -d "client_id=service-a" \
  -d "client_secret=$SERVICE_A_SECRET"
```

Принципиальное отличие от Authorization Code: здесь ВООБЩЕ нет front-channel шага, нет браузера, нет пользователя — весь обмен это один back-channel HTTP-запрос. Это может выполнить только confidential-клиент (тот, кто способен безопасно хранить `client_secret` — сервер, а не браузер).

### Device Code Grant — устройства с ограниченным вводом

Нишевый, но реальный сценарий: приложение работает на устройстве без удобной клавиатуры/браузера (smart TV, консоль, CLI-инструмент), которому неудобно вводить логин/пароль напрямую.

```txt
1. [Device → AS, back-channel]
   POST /auth/device — устройство просит "код устройства"
   ← получает: device_code (для самого устройства),
               user_code (короткий, для человека — "ABCD-1234"),
               verification_uri ("https://keycloak.example.com/device")

2. [Device]  Показывает пользователю на экране:
   "Перейдите на keycloak.example.com/device и введите код ABCD-1234"

3. [Пользователь, на ДРУГОМ устройстве — телефоне/ноутбуке]
   Открывает verification_uri, логинится как обычно (Authorization
   Code-подобный флоу внутри), вводит user_code, подтверждает

4. [Device, параллельно]  Пуллит /token с device_code каждые N секунд:
   grant_type=urn:ietf:params:oauth:grant-type:device_code
   Пока пользователь не подтвердил — Keycloak отвечает
   "authorization_pending". После подтверждения — отдаёт токены.
```

Здесь стоит заметить главную идею: устройство с плохим input-интерфейсом само НИКОГДА не видит логин/пароль пользователя — вся аутентификация происходит на отдельном, удобном устройстве, а исходное устройство просто получает результат через polling.

### Почему Resource Owner Password Credentials (ROPC) устарел

ROPC (grant `password`) выглядит соблазнительно просто: клиент сам собирает логин/пароль в своей форме и одним запросом обменивает их на токен, без всяких редиректов.

```txt
POST /token
  grant_type=password
  &username=user@example.com
  &password=<пароль пользователя>
  &client_id=legacy-client
```

Проблема не в том, что "это старо" — а в конкретных архитектурных потерях:

- **Клиент физически держит пароль пользователя в памяти.** Это прямо противоречит исходной цели OAuth2 — "выдать доступ, не раскрывая пароль третьей стороне". Если у клиента (или библиотеки, которую он использует) есть уязвимость — компрометируется сам пароль, а не только токен.
- **Невозможен MFA/step-up без переусложнения.** Authorization Server не видит и не контролирует форму логина — значит, не может вставить туда SMS-код, WebAuthn-подтверждение, редирект на внешний IdP (см. Identity Brokering в [Keycloak Core Concepts]) — вся логика второго фактора должна быть изобретена клиентом заново.
- **Невозможен SSO.** Пользователь логинится заново в КАЖДОМ клиенте отдельно — потому что аутентификация происходит не на общем Authorization Server, а внутри формы каждого приложения.

Keycloak по умолчанию отключает Direct Access Grants (это внутреннее название ROPC в Keycloak) для новых клиентов — это осознанное решение, а не забытая галочка.

### Почему Implicit Grant устарел

Implicit Grant (response_type=token) был придуман для SPA до того, как CORS и PKCE стали повсеместно доступны — идея была в том, чтобы отдать access token прямо в redirect, без отдельного back-channel обмена, потому что браузер тогда не мог сделать кросс-доменный POST для обмена code на токен.

```txt
GET /authorize?response_type=token&client_id=spa&redirect_uri=...
                        ↓
Redirect: https://app.example.com/callback#access_token=eyJhbGci...&expires_in=300
                                            ▲
                                     токен в URL FRAGMENT
```

Конкретные, а не абстрактные причины, почему это признано небезопасным паттерном (OAuth 2.0 Security Best Current Practice прямо рекомендует не использовать Implicit):

- **Токен проходит через front-channel в открытом виде** — весь смысл разделения "code через front-channel, токен через back-channel" в Authorization Code Grant исчезает: сам access token оказывается в адресной строке, в истории браузера, в Referer-заголовке при переходе по внешней ссылке с этой страницы, в логах любого промежуточного прокси, который логирует полный URL.
- **Нет проверки клиента при выдаче токена** — в Authorization Code Grant обмен code→token на шаге 6 (back-channel) даёт Authorization Server возможность ещё раз убедиться, что запрос идёт от легитимного клиента (через PKCE `code_verifier`, а для confidential — через client secret). В Implicit токен выдаётся сразу на редиректе — без этой дополнительной проверки.
- **Токен нельзя обновить незаметно** — Implicit Grant не предусматривает refresh token (raньше это тоже было бы небезопасно — refresh token во front-channel), поэтому единственный способ продлить сессию — невидимый iframe-редирект с `prompt=none`, что само по себе хрупко (см. проблему silent-check-sso в статье [React SPA Integration]).

Сегодня и Keycloak, и все современные библиотеки (`keycloak-js`, `oidc-client-ts`) по умолчанию используют Authorization Code + PKCE даже для чистого browser-only SPA — Implicit сохранился только как исторический контекст, важный для понимания, ПОЧЕМУ современный флоу устроен именно так.

## Итоговая связь понятий

```txt
[OAuth2 Roles]              →  Client / Resource Owner / Authorization
                                Server / Resource Server — словарь для
                                любого следующего рассуждения

[OIDC поверх OAuth2]        →  ID Token + UserInfo + Discovery Document
                                добавляют стандартизированную идентичность

[Front-channel/back-channel] →  сквозная модель: что можно доверить
                                браузеру-редиректу, а что — только
                                прямому серверному соединению

[Access / ID / Refresh]      →  три артефакта с разным адресатом и
                                разным назначением — путать их означает
                                архитектурную ошибку, не мелкую неточность

[Grant Types]                 →  выбор диктуется природой клиента:
                                есть пользователь и браузер (Auth Code
                                + PKCE), сервис без пользователя (Client
                                Credentials), устройство с плохим input
                                (Device Code)
```

Следующая статья — [Keycloak Core Concepts] — переходит от протокольной теории к тому, как именно Keycloak физически моделирует Realms, Clients, роли и claims, чтобы всё описанное здесь можно было реально сконфигурировать.

## Типичные ошибки на интервью

- **"OAuth2 и OIDC — это одно и то же, просто разные названия"** — неверно. OIDC — это identity-слой, построенный НАД OAuth2 теми же механизмами (те же эндпоинты, grant types), но добавляющий то, чего в чистом OAuth2 нет и не может быть по спецификации: ID Token, UserInfo endpoint, стандартизированный способ узнать, кто пользователь.

- **"Access token говорит, кто залогинен"** — нет, это ответственность ID Token. Access token говорит, ЧТО разрешено предъявителю токена (scope/roles), а не КТО он. Путать эти два токена — использовать не тот артефакт не по назначению, а не мелкая неточность в терминах.

- **"PKCE нужен только потому, что у SPA нет client secret"** — неполный ответ. PKCE защищает от authorization code interception независимо от наличия секрета, поэтому современные гайды (и Keycloak) рекомендуют PKCE даже для confidential-клиентов. Правильный ответ должен объяснять МЕХАНИЗМ (code_verifier/code_challenge), а не только "для публичных клиентов".

- **"Implicit Grant устарел, потому что это старая версия спецификации"** — не объясняет ПОЧЕМУ. Правильный ответ: токен передаётся через front-channel (URL fragment) — открытым текстом в истории браузера, Referer, логах прокси — и без дополнительной верификации клиента при выдаче, в отличие от Authorization Code, где обмен code→token происходит по back-channel с PKCE-проверкой.

- **"Refresh token обязательно JWT, как и access token"** — нет, спецификация ничего не диктует про формат ни access, ни refresh token (кроме ID Token, который обязан быть JWT по требованию OIDC). Keycloak по умолчанию делает access token JWT-ом ради удобства локальной валидации, но это деталь реализации, а не требование протокола.

- **"Client Credentials Grant — это то же самое, что логин от имени сервисного пользователя"** — не совсем: в Client Credentials нет ни пользователя, ни ID Token, ни какого-либо намёка на identity — это авторизация самого клиента как субъекта, а не имперсонация человека. Смешение этих концепций ведёт к неправильному дизайну service-to-service авторизации (например, попыткам получить roles конкретного пользователя через client credentials, где взяться им неоткуда).
