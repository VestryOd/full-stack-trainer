# OAuth2 / OIDC — фундамент протокола

Эта статья фиксирует словарь, на котором держится вся тема: четыре роли OAuth2, три вида токенов и грант-типы, которые их выдают. Здесь же разбирается, что OpenID Connect (OIDC) добавляет поверх OAuth2. Всё, что дальше в теме — конфигурация Keycloak, guard в NestJS, адаптер `keycloak-js` в React, — частные реализации описанного здесь.

## Роли протокола — с чего начинается любое рассуждение о любом флоу

OAuth2 описан в RFC 6749 — это один из пронумерованных документов Request for Comments, которыми задают интернет-протоколы. Он описывает не "как войти на сайт", а более общую задачу. Задача такая: как **Client** получает ограниченный доступ к ресурсу, которым владеет **Resource Owner**, не получая при этом пароль владельца. В протоколе фиксированы четыре роли:

```txt
┌───────────────────────────────────────────────────┐
│ Resource Owner — пользователь, владелец данных    │
└───────────────────────────────────────────────────┘
                          │  логин и согласие
                          ▼
┌───────────────────────────────────────────────────┐
│ Authorization Server (Keycloak) — проверяет       │
│ пользователя, выдаёт и подписывает токены         │
└───────────────────────────────────────────────────┘
                          │  выдаёт токен
                          ▼
┌───────────────────────────────────────────────────┐
│ Client — React SPA, мобильное приложение, backend │
└───────────────────────────────────────────────────┘
                          │  предъявляет токен
                          ▼
┌───────────────────────────────────────────────────┐
│ Resource Server — NestJS API, владеет             │
│ защищённым ресурсом                               │
└───────────────────────────────────────────────────┘
```

- **Resource Owner** — пользователь, которому принадлежат данные (или сам ресурс, если это service-to-service сценарий без человека).
- **Client** — приложение, которое **хочет** получить доступ к ресурсу от имени Resource Owner. Это **не** обязательно сервер. React SPA (single-page application — одностраничное приложение), мобильное приложение и backend-сервис — все три клиенты в терминах OAuth2. Различаются они только свойствами: про public и confidential — в статье [Keycloak Core Concepts](./02-keycloak-core-concepts.md).
- **Authorization Server** (в нашем стеке — Keycloak) — сервис, который аутентифицирует Resource Owner, получает согласие и выдаёт токены клиенту. Это единственная роль, которая знает пароль пользователя и логику выдачи токенов.
- **Resource Server** — API, которое владеет защищёнными данными (в нашем стеке — NestJS-бэкенд) и принимает решение "пустить/не пустить" на основе предъявленного токена.

Важное следствие этой схемы, которое многие пропускают: **Client и Resource Server — это разные роли, даже если их пишет одна и та же команда**. NestJS-бэкенд в связке "React SPA + NestJS API" — это Resource Server.

Но тот же самый бэкенд становится Client, когда сам обращается к другому внутреннему сервису от своего имени, без пользователя. Это и есть Client Credentials Grant, он разобран ниже. Путаница "кто есть кто" в конкретной архитектуре — источник половины неправильных решений о том, где хранить токен и кто должен его обновлять.

## "OAuth2 — это авторизация, а не аутентификация" — что это означает буквально

OAuth2 отвечает на один вопрос: **что этому клиенту разрешено делать?** Он выдаёт **access token**: тот сообщает Resource Server, какие scope есть у предъявителя. Сам по себе OAuth2 **не гарантирует** клиенту ничего о том, кто пользователь. Стандартного способа узнать личность (identity) владельца ресурса спецификация не определяет. Самая цитируемая фраза темы — это ограничение спецификации, а не лозунг.

Исторически это привело к тому, что разработчики стали **использовать access token как доказательство личности**. Логика была такая: если у меня есть валидный access token, значит, я знаю, кто залогинен. Это и есть известный антипаттерн «OAuth as authentication», который в 2014 году закрыл OpenID Connect.

```txt
OAuth2 в чистом виде отвечает:
  "Может ли предъявитель этого токена вызвать GET /api/orders?"
                        ↓
                       ДА / НЕТ

OAuth2 не отвечает напрямую:
  "Кто именно сейчас залогинен и как его зовут?"
```

**OpenID Connect (OIDC)** — это тонкий, стандартизированный слой идентичности **поверх** OAuth2: те же эндпоинты, те же грант-типы, тот же флоу редиректов. OIDC добавляет ровно три вещи, которых не хватало:

1. **ID Token** — токен, который содержит claims об идентичности пользователя: `sub` (уникальный идентификатор), `email`, `name`, время аутентификации и так далее. ID Token — это всегда JSON Web Token (JWT), и это требование спецификации OIDC. Формат access token OAuth2, наоборот, не диктует. ID Token предназначен **клиенту**: его нужно верифицировать, и его **нельзя отправлять на другие API** вместо access token.
2. **UserInfo endpoint** (`/protocol/openid-connect/userinfo` в Keycloak) — стандартизированный HTTP-эндпоинт, куда клиент может сходить с access token. Он возвращает актуальный профиль пользователя: это полезно, когда ID Token уже устарел, а профиль мог измениться.
3. **Discovery document** (`/.well-known/openid-configuration`) — JSON-документ, который публикует Authorization Server. В нём описаны **все** эндпоинты и возможности сервера, чтобы клиенту не нужно было хардкодить URL.

```bash
curl https://keycloak.example.com/realms/myrealm/.well-known/openid-configuration
```

```json
{
  "issuer":
    "https://keycloak.example.com/realms/myrealm",
  "authorization_endpoint":
    "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/auth",
  "token_endpoint":
    "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token",
  "userinfo_endpoint":
    "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/userinfo",
  "jwks_uri":
    "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/certs",
  "end_session_endpoint":
    "https://keycloak.example.com/realms/myrealm/protocol/openid-connect/logout",
  "grant_types_supported": [
    "authorization_code",
    "client_credentials",
    "refresh_token",
    "urn:ietf:params:oauth:grant-type:device_code"
  ],
  "response_types_supported": ["code", "none"],
  "code_challenge_methods_supported": ["plain", "S256"]
}
```

Практическое следствие: **нормальная библиотека должна конфигурироваться через issuer URL и сама подтягивать этот документ**, а не через захардкоженные пути ко всем эндпоинтам. Так умеют `keycloak-js`, `oidc-client-ts` и `passport-jwt` со стратегией OIDC.

Это отличает конфиг, который "работает у меня на деве", от конфига, переживающего апгрейд Keycloak. Пути внутри `/protocol/openid-connect/*` в теории могут меняться.

## Front-channel vs back-channel — концепция, которая будет всплывать в каждой статье

Это разделение — не деталь конкретного флоу. Это сквозная модель, через которую стоит анализировать **любой** обмен данными в OAuth2/OIDC:

```txt
Front-channel (передний канал):
  Данные идут через браузер пользователя — redirect,
  query-параметры, fragment (#), postMessage. Виден
  пользователю в адресной строке, потенциально виден
  стороннему коду на странице, может утечь через историю
  браузера, referrer или логи прокси.
  Пример: редирект на /authorize с параметрами в query string.

Back-channel (задний канал):
  Данные идут сервер-сервер, напрямую, минуя браузер
  пользователя. TLS-соединение между Client (или Resource
  Server) и Authorization Server. Не виден пользователю,
  не проходит через историю браузера.
  Пример: обмен authorization code на токены — POST на /token
  напрямую с бэкенда, или, для public-клиента, прямо из
  JS-кода в браузере, но не через redirect.
```

Почему это важно: **любые данные, которые должны остаться секретом — client secret, сами токены, — стоит передавать по back-channel там, где это возможно**.

Именно поэтому Implicit Grant признан небезопасным: он передаёт access token через URL fragment, то есть по front-channel (подробнее ниже). Стандартом стал Authorization Code Grant. Он отправляет через front-channel только одноразовый `code`, а сам обмен на токены идёт по back-channel.

Дальше по тексту эта пара терминов используется без переопределения. Если флоу что-то передаёт через redirect — это front-channel. Если через прямой HTTP-запрос между серверами — back-channel.

## Access Token, ID Token, Refresh Token — три артефакта с разным назначением

Это источник путаницы номер один у разработчиков, впервые заходящих в эту область. Все три — это "какие-то токены", выданные в одном ответе, и легко начать использовать их взаимозаменяемо. Это ошибка с реальными последствиями.

|  | Access Token | ID Token | Refresh Token |
|---|---|---|---|
| Кому предназначен | Resource Server (API), в заголовке `Authorization: Bearer` | Только клиенту — не отправлять на другие API | Authorization Server, и только на `/token` |
| Формат | По OAuth2 — opaque, просто строка; в Keycloak это JWT | Всегда JWT (требование OIDC) | По спецификации opaque; в Keycloak тоже JWT, но это деталь реализации |
| Содержит | scope, roles, permissions — "что разрешено" | Claims об идентичности: `sub`, `email`, `name`, `auth_time` — "кто это" | Минимум данных, чтобы Authorization Server нашёл сессию |
| Время жизни | Короткое (минуты) | Столько же, сколько у access token | Длинное (часы или дни) или до logout |
| Кто использует | Resource Server, на каждый запрос к API | Клиентское приложение — показать "Привет, Имя" | Клиент — только чтобы получить новую пару токенов |

Формат access token и подробности его валидации разобраны отдельно в статье [Tokens, Sessions, and Validation](./03-tokens-sessions-and-validation.md). Там же — JWKS (JSON Web Key Set), заголовок `kid` и локальная валидация против introspection. Здесь важно зафиксировать смысловую границу трёх артефактов, а не формат передачи.

Общая структура JWT (header.payload.signature) разбиралась в теме «JWT, Access Token и Refresh Token». Эта статья — про протокольную роль каждого токена, а не про его физический формат.

Частая ошибка в реальном коде: React-приложение декодирует ID Token и отправляет его как `Authorization: Bearer <idToken>` в запросах к своему NestJS API. Технически это может даже сработать, если бэкенд слишком доверчиво принимает любой JWT от того же issuer. Но по контракту это неправильно.

ID Token не предназначен для Resource Server. У него другой `aud` — claim с аудиторией, то есть с получателем, для которого выпущен токен. И ничто не гарантирует, что в нём вообще есть нужные для авторизации claims: roles и scope.

## Scopes vs Claims — то, что часто путают местами

- **Scope** — это запрос доступа. Клиент указывает scope в запросе на `/authorize` (`scope=openid profile email`) и тем самым говорит, что ему нужен доступ к такой-то категории данных и действий. Scope — это то, **о чём** клиент просит.
- **Claim** — это конкретный факт о пользователе или токене внутри выданного JWT (`email`, `sub`, `realm_access.roles`). Claim — это то, **что** клиент реально получил.

```txt
Запрос scope:  "scope=openid profile email"
        ↓
Authorization Server решает, какие claims дать
        ↓
ID Token содержит: sub, name, preferred_username, email,
                   email_verified ...
```

В Keycloak связь между scope и набором claims настраивается через **Client Scopes** и **Protocol Mappers**. Это чисто keycloak-специфичный механизм, он разобран в статье [Keycloak Core Concepts](./02-keycloak-core-concepts.md).

Протокольный принцип отсюда простой: scope — это запрос, claim — это результат. Один scope обычно включает сразу пачку claims. Scope `profile` — это не один claim, а группа: `name`, `family_name`, `given_name`, `picture` и так далее.

## Grant Types — как конкретно клиент получает токен

Grant Type (иногда говорят "flow") — это конкретный протокольный сценарий обмена. Он фиксирует, какие сообщения идут между Client, Authorization Server и — иногда — браузером пользователя, чтобы в итоге у клиента оказались токены.

Выбор grant type — это не вкусовщина. Он прямо следует из того, **что** из себя представляет клиент:

- Есть ли у него пользователь перед экраном?
- Может ли он безопасно хранить секрет?
- Какой у него интерфейс ввода?

| Grant type | Для кого | Статус |
|---|---|---|
| Authorization Code + PKCE (Proof Key for Code Exchange) | Пользователь с браузером; public или confidential клиент | Дефолт сегодня |
| Client Credentials | Сервис действует от своего имени, без пользователя | Стандарт для вызовов между сервисами |
| Device Code | Устройство без клавиатуры и браузера | Нишевый, но стандартный |
| Resource Owner Password (ROPC) | Legacy-клиенты, которые сами собирают пароль | Устарел |
| Implicit | Браузерные приложения времён до PKCE | Устарел |

### Authorization Code + PKCE — современный дефолт

Это единственный правильный выбор для интерактивного логина пользователя сегодня. Он подходит confidential-клиентам, то есть бэкенду с client secret. И, что важнее, он подходит public-клиентам — SPA и мобильным приложениям, которые физически не могут хранить секрет.

**PKCE** произносится "пикси" и описано в RFC 7636. Изначально это расширение придумали для мобильных приложений. Сегодня Keycloak и большинство современных гайдов рекомендуют его **всем** клиентам, включая confidential.

Причина не в том, что у клиента нет секрета. PKCE защищает от отдельного класса атак — перехвата authorization code — и эта атака актуальна независимо от типа клиента.

Полный механизм PKCE — что такое `code_verifier` и `code_challenge` и почему они защищают от перехвата — разобран в статье [Security Hardening and Attack Vectors](./07-security-hardening-and-attack-vectors.md). Здесь фиксируем только последовательность шагов протокола.

```txt
Участники: браузер пользователя, React SPA (Client), Keycloak
  (Authorization Server), NestJS API (Resource Server)

1. [Client, локально]
   Сгенерировать случайный code_verifier, затем вычислить
   code_challenge = SHA256(code_verifier)

2. [front-channel]
   Браузер редиректится на:
     GET /authorize?
       response_type=code
       &client_id=spa-client
       &redirect_uri=https://app.example.com/callback
       &scope=openid profile email
       &state=<случайное значение — CSRF-защита>
       &code_challenge=<вычислено на шаге 1>
       &code_challenge_method=S256

3. [на стороне Keycloak]
   Пользователь видит форму логина Keycloak — не форму
   клиента — и вводит логин и пароль. Keycloak аутентифицирует
   его и запоминает code_challenge вместе с authorization code.

4. [front-channel]
   Keycloak редиректит браузер обратно:
     GET https://app.example.com/callback?
       code=<одноразовый authorization code>
       &state=<то же значение, что отправляли>

5. [Client]
   Проверить, что state совпадает с отправленным
   (защита от CSRF/replay на редирект)

6. [back-channel]
   Client делает POST на /token напрямую, не через
   браузер-редирект:
     grant_type=authorization_code
     &code=<code с шага 4>
     &redirect_uri=<тот же, что в шаге 2>
     &code_verifier=<оригинал с шага 1>
     &client_id=spa-client

7. [Keycloak, back-channel]
   Проверяет, что SHA256(code_verifier) равен code_challenge,
   сохранённому на шаге 3. Если совпадает, Keycloak выдаёт
   access_token, id_token и refresh_token в JSON-ответе.
```

Ключевая деталь, которую стоит проговорить явно: `code` с шага 4 сам по себе **бесполезен без `code_verifier`**. Даже если атакующий перехватит code, обменять его на токены он не сможет: он не знает `code_verifier`. Это значение никогда не покидало память легитимного клиента.

Перехват вполне реален: утечка в логах прокси или вредоносное приложение, зарегистрированное на тот же custom URL scheme в мобильной операционной системе.

### Client Credentials Grant — service-to-service, без пользователя вообще

Используется, когда за токеном обращается не пользователь, а сам сервис. Например, NestJS-сервис A вызывает NestJS-сервис B по внутреннему API. Залогиненного человека в этом взаимодействии нет вообще.

```txt
Участники: Service A (Client, confidential), Keycloak (AS)

1. [back-channel, напрямую, без браузера]
   POST /realms/myrealm/protocol/openid-connect/token
     grant_type=client_credentials
     &client_id=service-a
     &client_secret=<секрет, известный только Service A и Keycloak>

2. [Keycloak]
   Проверяет client_id + client_secret → выдаёт access_token
   (без id_token — идентифицировать здесь некого, ID Token
   не выдаётся в этом грант-типе)
```

```bash
curl -X POST https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token \
  -d "grant_type=client_credentials" \
  -d "client_id=service-a" \
  -d "client_secret=$SERVICE_A_SECRET"
```

Принципиальное отличие от Authorization Code: здесь **вообще** нет шага front-channel, нет браузера, нет пользователя — весь обмен это один back-channel HTTP-запрос. Выполнить его может только confidential-клиент, то есть тот, кто способен безопасно хранить `client_secret`: сервер, а не браузер.

### Device Code Grant — устройства с ограниченным вводом

Нишевый, но реальный сценарий: приложение работает на устройстве без удобной клавиатуры и браузера. Это может быть телевизор с интернетом, игровая консоль или инструмент командной строки. Вводить там логин и пароль неудобно.

```txt
1. [Device → Authorization Server, back-channel]
   POST /auth/device — устройство просит "код устройства".
   ← получает: device_code (для самого устройства),
               user_code (короткий, для человека — "ABCD-1234"),
               verification_uri
                 ("https://keycloak.example.com/device")

2. [Device]
   Показывает пользователю на экране: "Перейдите на
   keycloak.example.com/device и введите код ABCD-1234"

3. [Пользователь, на другом устройстве — телефоне, ноутбуке]
   Открывает verification_uri, логинится как обычно
   (внутри — флоу вроде Authorization Code), вводит user_code,
   подтверждает.

4. [Device, параллельно]
   Опрашивает /token с device_code каждые N секунд:
   grant_type=urn:ietf:params:oauth:grant-type:device_code
   Пока пользователь не подтвердил, Keycloak отвечает
   "authorization_pending". После подтверждения отдаёт токены.
```

Главная идея здесь такая: устройство с неудобным вводом само **никогда** не видит логин и пароль пользователя. Вся аутентификация происходит на отдельном, удобном устройстве. Исходное устройство просто получает результат через опрос (polling).

### Почему Resource Owner Password Credentials (ROPC) устарел

ROPC (grant `password`) выглядит соблазнительно просто: клиент сам собирает логин/пароль в своей форме и одним запросом обменивает их на токен, без всяких редиректов.

```txt
POST /token
  grant_type=password
  &username=user@example.com
  &password=<пароль пользователя>
  &client_id=legacy-client
```

Проблема не в том, что "это старо" — а в конкретных архитектурных потерях:

- **Клиент физически держит пароль пользователя в памяти.** Это прямо противоречит исходной цели OAuth2: выдать доступ, не раскрывая пароль третьей стороне. Если у клиента или у библиотеки, которую он использует, есть уязвимость, компрометируется сам пароль, а не только токен.
- **Многофакторную аутентификацию (MFA) и step-up становится трудно добавить.** Authorization Server не видит и не контролирует форму логина. Значит, он не может вставить туда код из текстового сообщения, подтверждение WebAuthn или редирект на внешний identity provider (IdP). Всю логику второго фактора пришлось бы изобретать заново внутри каждого клиента. Механизм для этого — Identity Brokering, он разобран в статье [Keycloak Core Concepts](./02-keycloak-core-concepts.md).
- **Single sign-on (SSO) становится невозможен.** Пользователь логинится заново в **каждом** клиенте отдельно, потому что аутентификация происходит внутри формы каждого приложения, а не на общем Authorization Server.

Keycloak по умолчанию отключает Direct Access Grants (это внутреннее название ROPC в Keycloak) для новых клиентов — это осознанное решение, а не забытая галочка.

### Почему Implicit Grant устарел

Implicit Grant (`response_type=token`) придумали для SPA до того, как CORS (cross-origin resource sharing) и PKCE стали повсеместно доступны. Идея была в том, чтобы отдать access token прямо в редиректе, без отдельного обмена по back-channel. Браузер тогда не мог надёжно сделать кросс-доменный POST, чтобы обменять code на токен.

```txt
GET /authorize?response_type=token&client_id=spa&redirect_uri=...
        ↓
Редирект на:
  https://app.example.com/callback
    #access_token=eyJhbGci...&expires_in=300
     ▲
     токен лежит в URL fragment
```

Конкретные, а не абстрактные причины, почему это признано небезопасным паттерном (OAuth 2.0 Security Best Current Practice прямо рекомендует не использовать Implicit):

- **Токен проходит через front-channel в открытом виде.** Весь смысл разделения "code через front-channel, токен через back-channel" в Authorization Code Grant исчезает. Сам access token оказывается в адресной строке и в истории браузера. Он попадает и в заголовок `Referer` при переходе по внешней ссылке, и в логи любого прокси, который пишет полный URL.
- **Нет проверки клиента при выдаче токена.** В Authorization Code Grant обмен code→token на шаге 6 идёт по back-channel. Это даёт Authorization Server ещё одну возможность убедиться, что запрос пришёл от легитимного клиента — через `code_verifier` в PKCE или через client secret. В Implicit токен выдаётся сразу на редиректе, без этой проверки.
- **Токен нельзя обновить незаметно.** Implicit Grant не предусматривает refresh token, да и refresh token во front-channel был бы небезопасен. Единственный способ продлить сессию — невидимый iframe-редирект с `prompt=none`, что само по себе хрупко. Про проблему `silent-check-sso` смотрите в статье [React SPA Integration](./05-react-spa-integration.md).

Сегодня и Keycloak, и все современные библиотеки — `keycloak-js`, `oidc-client-ts` — по умолчанию используют Authorization Code + PKCE даже для чистого browser-only SPA. Implicit сохранился только как исторический контекст, важный для понимания, **почему** современный флоу устроен именно так.

                             Document добавляют

 back-channel]               доверить браузеру-редиректу, а

## Типичные ошибки на интервью

- **"OAuth2 и OIDC — это одно и то же, просто разные названия"** — неверно. OIDC — это слой идентичности **поверх** OAuth2, использующий те же эндпоинты и те же grant types. Он добавляет то, чего в чистом OAuth2 нет и не может быть по спецификации: ID Token, UserInfo endpoint и стандартизированный способ узнать, кто пользователь.

- **"Access token говорит, кто залогинен"** — нет, это ответственность ID Token. Access token говорит, **что** разрешено предъявителю токена (scope и roles), а не **кто** он. Путать их — значит брать не тот артефакт, а не просто оговориться в терминах.

- **"PKCE нужен только потому, что у SPA нет client secret"** — неполный ответ. PKCE защищает от перехвата authorization code независимо от наличия секрета, поэтому современные гайды и Keycloak рекомендуют его даже для confidential-клиентов. Правильный ответ объясняет **механизм** — `code_verifier` и `code_challenge`, — а не только то, что он нужен публичным клиентам.

- **"Implicit Grant устарел, потому что это старая версия спецификации"** — это не объясняет **почему**. Настоящий ответ: токен передаётся через front-channel, в URL fragment. Он идёт открытым текстом — в истории браузера, в заголовке `Referer`, в логах прокси. Плюс нет дополнительной верификации клиента при выдаче, в отличие от Authorization Code, где обмен code→token происходит по back-channel с проверкой PKCE.

- **"Refresh token обязательно JWT, как и access token"** — нет. Спецификация ничего не диктует про формат ни access token, ни refresh token. Обязан быть JWT только ID Token, этого требует OIDC. Keycloak по умолчанию делает access token в формате JWT ради удобства локальной валидации, но это деталь реализации, а не требование протокола.

- **"Client Credentials Grant — это то же самое, что логин от имени сервисного пользователя"** — не совсем. В Client Credentials нет ни пользователя, ни ID Token, ни какого-либо намёка на identity. Здесь авторизуется сам клиент как субъект, а не выдаёт себя за человека. Смешение этих понятий ведёт к неправильному дизайну авторизации между сервисами. Типичный пример: попытка получить roles конкретного пользователя из client-credentials-токена, где им просто неоткуда взяться.
