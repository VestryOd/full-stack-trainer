# Токены, сессии и валидация в проде

## От "получили токен" к "токен работает правильно под нагрузкой"

Эта статья отвечает на три вопроса про токены в проде. Как Resource Server быстро решает, верить ли токену прямо сейчас? Что реально происходит, когда пользователь нажимает Logout? И почему "просто удалить токен на фронтенде" — это только половина логаута?

Статьи 01-02 объяснили, что такое access/ID/refresh token и как Keycloak их формирует. Здесь мы спускаемся на слой ниже: проверка подписи без обращения к Keycloak, отзыв токена, время жизни токенов, серверные сессии и логаут, который доходит до всех клиентов.

## JWKS — как Resource Server проверяет подпись, не спрашивая Keycloak каждый раз

Access token, выданный Keycloak, — это подписанный JWT (JSON Web Token), а алгоритм подписи по умолчанию — RS256, асимметричная подпись. Resource Server должен проверить подпись **без обращения к Keycloak на каждый запрос**. Иначе Keycloak станет узким местом производительности для всей системы.

Решение — **JWKS** (JSON Web Key Set). Keycloak публикует свои публичные ключи по стандартному эндпоинту. Resource Server скачивает их один раз и кэширует. Дальше он проверяет подпись **локально**, средствами обычной криптографии, без сетевого вызова на каждый входящий запрос.

```bash
curl https://keycloak.example.com/realms/myrealm/protocol/openid-connect/certs
```

```json
{
  "keys": [
    {
      "kid": "a1b2c3d4-key-id",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "xGOr-H7A-PWG...", 
      "e": "AQAB"
    }
  ]
}
```

Каждый JWT в своём header содержит `kid` (Key ID) — указатель на то, **каким** из ключей в JWKS он подписан:

```json
{ "alg": "RS256", "typ": "JWT", "kid": "a1b2c3d4-key-id" }
```

Это существует не просто "для порядка" — это механизм **ротации ключей без даунтайма**. Keycloak можно настроить на периодическую смену подписывающего ключа (Realm Settings → Keys → Key rotation).

В момент ротации в JWKS одновременно присутствуют **старый и новый** ключ. Токены, выданные до ротации, ещё живы, если их TTL (time to live, время жизни) не истёк. Они продолжают валидироваться старым ключом по его `kid`, а новые токены подписываются и проверяются новым.

Без `kid` Resource Server не смог бы понять, какой из нескольких ключей в JWKS применить к конкретному токену.

```txt
Почему нельзя хардкодить публичный ключ в конфиге приложения:
  1. Ротация ключей на стороне Keycloak сломает валидацию у всех
     клиентов с захардкоженным ключом — до ручного передеплоя
  2. При компрометации ключа единственный быстрый способ
     отреагировать — сгенерировать новый ключ в Keycloak;
     хардкод исключает этот путь
  3. Библиотеки вроде jwks-rsa и jose сами кэшируют JWKS с TTL
     и умеют переспросить, если встретили незнакомый kid, —
     задача решена стандартным способом, изобретать своё не нужно
```

```typescript
// NestJS: passport-jwt стратегия, валидирующая токен через JWKS
// Библиотека jwks-rsa сама кэширует ключи и обновляет при незнакомом kid
import { Strategy } from 'passport-jwt';
import { passportJwtSecret } from 'jwks-rsa';

export class KeycloakJwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      algorithms: ['RS256'],
      secretOrKeyProvider: passportJwtSecret({
        jwksUri: `${config.get('KEYCLOAK_ISSUER')}/protocol/openid-connect/certs`,
        cache: true,          // кэшировать полученный ключ по kid
        rateLimit: true,      // защита от избыточных запросов к JWKS-эндпоинту
        jwksRequestsPerMinute: 5,
      }),
      issuer: config.get('KEYCLOAK_ISSUER'),
    });
  }

  validate(payload: KeycloakJwtPayload) {
    return payload; // доступно дальше как req.user
  }
}
```

Guards и декораторы поверх этой стратегии разобраны в статье [NestJS Resource Server](./04-nestjs-resource-server.md). Здесь важно унести механику JWKS + `kid`: она даёт быструю проверку подписи и переживает ротацию ключей без ручного вмешательства.

## Локальная валидация vs Token Introspection — реальный trade-off

Проверка подписи через JWKS — это только половина вопроса "валиден ли токен". Есть второй, более тонкий вопрос: **не был ли этот токен отозван раньше, чем истёк его TTL?** Так бывает, когда пользователь разлогинился, администратор заблокировал аккаунт или обнаружена компрометация. Тут есть два принципиально разных подхода.

```txt
Локальная (offline) JWT-валидация:
  Resource Server проверяет подпись и exp/iss/aud локально,
  ключом из JWKS, без единого сетевого запроса к Keycloak.

  ✓ Latency:     доли миллисекунды, никакой сетевой зависимости
  ✓ Нагрузка:    Keycloak не участвует в hot path запросов вообще
  ✗ Revocation:  Resource Server узнает об отзыве токена только
                 когда истечёт TTL — если пользователя заблокировали
                 "прямо сейчас", у него есть валидный access token
                 ещё до N минут (TTL access token)

Token Introspection (RFC 7662):
  Resource Server на каждый запрос делает back-channel вызов к
  Keycloak: "этот токен всё ещё активен?"

  ✓ Revocation:  мгновенное знание об отзыве — Keycloak отвечает
                 "active: false" сразу после логаута/блокировки
  ✗ Latency:     дополнительный сетевой round-trip на каждый запрос
  ✗ Нагрузка:    Keycloak становится точкой, от доступности которой
                 зависит каждый запрос к API, а не только логин
```

```bash
# Introspection endpoint — confidential client спрашивает Keycloak
# про статус конкретного токена
curl -X POST \
  https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token/introspect \
  -u "backend-service:$CLIENT_SECRET" \
  -d "token=$ACCESS_TOKEN"
```

```json
{
  "active": true,
  "sub": "a1b2c3",
  "exp": 1719936000,
  "scope": "openid profile email",
  "client_id": "spa-client"
}
```

Практическое правило выбора: **начинать с локальной валидации по умолчанию** и держать TTL access token коротким, 5-15 минут. Это закрывает 95% реальных случаев с приемлемым риском: украденный токен живёт максимум 15 минут.

Переходить на introspection стоит точечно, не для всего API. Оставьте его для конкретных высокочувствительных операций: перевод денег, изменение прав доступа, административные действия. Там даже несколько минут задержки в распространении отзыва неприемлемы.

Introspection на **каждый** запрос всего API — типичная ошибка проектирования. Она превращает Keycloak в единую точку отказа для системы, которая изначально проектировалась как stateless.

## Opaque vs JWT-кодированный refresh token

Keycloak по умолчанию делает refresh token тоже JWT-ом (в отличие от чистого OAuth2, который вообще не диктует формат refresh token — см. статью 01). Это осознанный компромисс, а не требование спецификации:

```txt
Opaque refresh token (случайная строка, нужен запрос в базу):
  ✓ Ничего не раскрывает при декодировании — это просто
    случайные байты
  ✓ Естественно проверяется через базу или Keycloak: состояние
    отзыва всегда актуально, потому что сама проверка ходит
    в хранилище
  ✗ Требует централизованного хранилища на стороне
    Authorization Server

JWT refresh token (используется Keycloak по умолчанию):
  ✓ Keycloak может закодировать в него session ID и метаданные
    и за счёт этого быстрее находить сессию при обмене
    на новый access token
  ✗ Полезная нагрузка технически читаема (хотя клиент не должен
    её парсить и опираться на содержимое — refresh token для клиента
    должен оставаться "чёрным ящиком", предназначенным только
    для отправки на /token)
```

Для клиентского кода (React или NestJS) это различие **не должно влиять на реализацию**. В обоих случаях контракт одинаковый: refresh token отправляется на `/token` с `grant_type=refresh_token`, и клиент никогда не парсит его и не использует напрямую. Формат — деталь реализации Keycloak: относиться к refresh token нужно как к непрозрачному секрету в любом случае.

## Настройка TTL — короткий access token, длинный refresh, и почему это не произвольные числа

```txt
Access Token TTL
  (Keycloak: Realm Settings → Tokens → Access Token Lifespan)
  Типичное значение: 5-15 минут
  Логика: это верхняя граница "окна риска" при краже токена.
  Короче — безопаснее, но чаще происходит silent refresh
  (дополнительная сетевая нагрузка + больше точек отказа UX).
  15 минут — практический баланс для большинства web-приложений.

Refresh Token TTL (Keycloak: SSO Session Idle / SSO Session Max):
  SSO Session Idle: сколько времени сессия жива без активности
    (типично: несколько часов — "если ушёл на обед, не разлогинило")
  SSO Session Max: абсолютный потолок жизни сессии, даже при
    непрерывной активности (типично: дни — принудительный релогин)
  Логика: это про UX-компромисс "как часто пользователь видит
  форму логина заново", а не про защиту от кражи — за это отвечает
  rotation (ниже) и revocation.
```

**Refresh Token Rotation** — это политика. **Каждый** обмен refresh token на новую пару токенов выдаёт **новый** refresh token и делает старый недействительным. В Keycloak это настройка клиента: Advanced Settings → "Revoke Refresh Token"; для public-клиентов есть встроенный механизм.

Это не только гигиена, это **механизм обнаружения кражи**. Допустим, refresh token украли через XSS (cross-site scripting, межсайтовый скриптинг) до того, как приложение успело его использовать. Атакующий пытается обменять его после того, как это уже сделал легитимный клиент.

Keycloak видит повторное использование уже отозванного токена и может среагировать: отозвать всю цепочку, поднять алерт. Полный сценарий "reuse detection" разобран в статье [Security Hardening and Attack Vectors](./07-security-hardening-and-attack-vectors.md).

## Server-side сессии Keycloak vs stateless-валидация Resource Server — как две модели сосуществуют

Частая путаница звучит так. Если JWT валидируется локально и без обращения к серверу — при чём тут вообще сессии на Keycloak? Ответ: это **две разные сущности**, отвечающие за разные вещи.

```txt
┌────────────────────────────────────────────────────────────┐
│ Keycloak (Authorization Server)                            │
│                                                            │
│ Server-side SSO Session:                                   │
│   Хранится в БД или памяти Keycloak. Живёт, пока           │
│   пользователь не разлогинится или не истечёт              │
│   SSO Session Max/Idle.                                    │
│   Именно эта сессия даёт SSO: если пользователь уже        │
│   аутентифицирован в ней, при редиректе на /authorize от   │
│   другого клиента формы логина не будет.                   │
│   Эта сессия — источник истины, кто реально залогинен.     │
└────────────────────────────────────────────────────────────┘
                               │  выдаёт access/id/refresh токены
                               ▼
┌────────────────────────────────────────────────────────────┐
│ NestJS Resource Server (API)                               │
│                                                            │
│ Не хранит про сессию ничего. Каждый запрос проверяется     │
│ отдельно: подпись валидна? exp не истёк? aud правильный?   │
│ Это классическая stateless-модель, поэтому Resource Server │
│ не знает, жива ли ещё сессия Keycloak, из которой пришёл   │
│ токен, пока не истечёт exp.                                │
└────────────────────────────────────────────────────────────┘
```

Практическое следствие: **отзыв сессии Keycloak — логаут, блокировка админом — не отзывает мгновенно уже выданные access token.** Они продолжают проходить локальную валидацию на Resource Server до истечения `exp`, потому что тот не знает о состоянии серверной сессии.

Это не баг, а прямое следствие выбора stateless-модели для API. И именно поэтому короткий TTL access token — не перестраховка. Это единственный практический способ ограничить окно "токен валиден, а сессия уже мертва".

## Logout — почему "удалить токен на фронте" — это не логаут

Наивная реализация — "удалили `accessToken` из памяти или localStorage, всё" — чинит только удобство **одной вкладки одного клиента**. Реальный logout в системе с SSO (single sign-on, единый вход) и несколькими клиентами требует явно спроектированного распространения.

```txt
Front-channel logout:
  Клиент, инициировавший logout, редиректит браузер пользователя
  на эндпоинт Keycloak /protocol/openid-connect/logout. Keycloak
  убивает серверную сессию и, используя браузер как транспорт,
  по очереди редиректит (или рендерит невидимые iframe)
  на logout-эндпоинты всех других клиентов, у кого была
  активна эта же SSO-сессия.

  ✗ Хрупкость: зависит от того, что браузер пользователя вообще
    дойдёт до всех этих редиректов и iframe — если пользователь
    закрыл вкладку посреди процесса, часть клиентов не узнает
    о logout
  ✗ Та же проблема third-party cookie restrictions, что и у
    silent-check-sso (см. статью 05)

Back-channel logout (OIDC Back-Channel Logout, рекомендуется):
  Keycloak, убив серверную сессию, делает прямой server-to-server
  HTTP POST на заранее зарегистрированный backchannel_logout_uri
  каждого клиента, у кого была активна эта сессия, — без участия
  браузера пользователя вообще.

  ✓ Надёжность: не зависит от того, жив ли ещё браузер
    пользователя или его вкладка
  ✓ Работает даже для клиентов без открытого интерфейса:
    мобильное приложение в фоне, серверный BFF
```

```txt
Single Logout — распространение по нескольким клиентам:

React SPA, NestJS BFF и Mobile App получили токены
в рамках одной SSO-сессии.
                 │
                 ▼
    ┌─────────────────────────┐
    │ Keycloak SSO Session ID │
    └─────────────────────────┘
                 │  logout инициирован любым клиентом
                 ▼
Keycloak убивает сессию и рассылает back-channel logout
POST на backchannel_logout_uri всех трёх клиентов:

  React SPA   — чистит локальную копию токена
  NestJS BFF  — рвёт свою серверную сессию/куку
  Mobile App  — узнаёт через push или при следующем вызове
```

```typescript
// NestJS: минимальный обработчик back-channel logout
// Keycloak шлёт сюда JWT ("logout token") при разлогинивании сессии
@Post('backchannel-logout')
async handleBackchannelLogout(@Body('logout_token') logoutToken: string) {
  const payload = await this.verifyLogoutToken(logoutToken); // проверка через тот же JWKS
  const sessionId = payload.sid;

  // Отозвать всё, что бэкенд хранит для этой сессии:
  // серверные куки и сессии BFF, закэшированные refresh-токены и т.д.
  await this.sessionStore.revokeBySessionId(sessionId);

  return { status: 'ok' }; // Keycloak ожидает 200 OK
}
```

Ключевой вывод: **правильный logout — это не действие одного клиента. Это событие, которое надо спроектировать так, чтобы оно дошло до всех участников SSO-сессии.** В архитектурах 2024+ back-channel logout предпочтителен именно потому, что не зависит от состояния браузера пользователя в момент разлогинивания.

## Итоговая связь понятий

```txt
[JWKS + kid]                  →  как Resource Server проверяет
                                 подпись локально и переживает
                                 ротацию ключей без ручной работы

[Локальная валидация vs
 Introspection]                →  latency и нагрузка vs мгновенное
                                 знание об отзыве — выбор по
                                 чувствительности операции

[Opaque vs JWT refresh]        →  деталь реализации Authorization
                                 Server; для клиента refresh token
                                 всегда непрозрачен

[TTL access/refresh + rotation] →  короткий access = маленькое окно
                                 риска; rotation refresh token =
                                 обнаружение кражи, а не гигиена

[Серверная сессия Keycloak
 vs stateless Resource Server]  →  два разных источника истины;
                                 несовпадение их состояния — и есть
                                 причина, почему короткий TTL access
                                 token обязателен, а не опционален

[Front-channel vs back-channel
 logout]                        →  надёжность распространения logout
                                 по клиентам одной SSO-сессии
```

Следующая статья, [NestJS Resource Server](./04-nestjs-resource-server.md), берёт механику отсюда: валидацию JWKS, работу с `exp` и отзывом. На ней она строит конкретный слой авторизации в NestJS из Guards и декораторов.

## Типичные ошибки на интервью

- **"Приложение должно хардкодить публичный ключ Keycloak для проверки JWT"** — неверно и небезопасно. Правильный подход — JWKS endpoint с кэшированием по `kid`. Он переживает ротацию ключей без передеплоя приложения, а хардкод ломается в первое же плановое обслуживание Keycloak.

- **"Token Introspection всегда лучше локальной валидации, потому что даёт мгновенный отзыв"** — это упускает половину картины. Introspection делает Keycloak зависимостью **каждого** API-запроса, а не только логина. Это противоречит идее stateless resource server и добавляет latency на каждый вызов. Правильный ответ — точечное применение для высокочувствительных операций, а не тотальная замена локальной валидации.

- **"Раз access token — JWT, значит его можно отозвать, просто удалив из базы"** — нет. Если Resource Server валидирует его локально, а это типичный случай, удаление записи на стороне Keycloak ничего не меняет. Уже выданный JWT ещё не истёк, поэтому он продолжит проходить локальную проверку подписи до `exp`. Отзыв работает мгновенно только там, где есть явная проверка состояния: introspection или blacklist.

- **"Logout — это просто удалить токен из localStorage или памяти на фронтенде"** — неполно. Это разлогинивает только текущую вкладку текущего клиента. Серверную SSO-сессию в Keycloak это не завершает и другие клиенты, использовавшие ту же сессию, не уведомляет. Полноценный logout требует одного из двух: либо front-channel редиректа на logout-эндпоинт Keycloak, либо — надёжнее — back-channel logout, который рассылается на все зарегистрированные клиенты.

- **"Backend должен сам обновлять access token, когда он истекает"** — путаница ответственности. Refresh — обязанность **клиента**: того, кто держит refresh token и обращается к `/token`. Resource Server, получив истёкший токен, должен просто ответить 401 с понятным телом ошибки. Реакция на это, поход за новым токеном, целиком на стороне клиента. См. [NestJS Resource Server](./04-nestjs-resource-server.md) про сторону API и [React SPA Integration](./05-react-spa-integration.md) про сторону SPA (single-page application, одностраничное приложение).
