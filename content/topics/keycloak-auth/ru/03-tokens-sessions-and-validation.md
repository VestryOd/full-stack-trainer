# Токены, сессии и валидация в проде

## От "получили токен" к "токен работает правильно под нагрузкой"

Статьи 01-02 объяснили, ЧТО такое access/ID/refresh token и КАК Keycloak их формирует. Эта статья — про следующий, менее очевидный слой: как Resource Server (NestJS API) быстро и правильно решает "верить ли этому токену прямо сейчас", что происходит, когда пользователь нажимает Logout, и почему "просто удалить токен на фронтенде" - решение только наполовину. Это ровно тот уровень деталей, который отличает "подключил библиотеку по туториалу" от "могу объяснить, что произойдёт при ротации ключей Keycloak в 3 часа ночи".

## JWKS — как Resource Server проверяет подпись, не спрашивая Keycloak каждый раз

Access token, выданный Keycloak, — это подписанный JWT (RS256 по умолчанию — асимметричная подпись). Задача Resource Server'а — проверить подпись **без обращения к Keycloak на каждый запрос**, иначе Keycloak станет узким местом производительности для всей системы.

Решение — **JWKS** (JSON Web Key Set): Keycloak публикует свои публичные ключи по стандартному эндпоинту, и Resource Server скачивает их один раз, кэширует, и дальше проверяет подпись **локально**, средствами обычной криптографии, без сетевого запроса на каждый чих.

```bash
curl https://keycloak.example.com/realms/myrealm/protocol/openid-connect/certs
```

```json
{
  "keys": [
    {
      "kid": "a1b2c3d4-key-id",
      "kty": "RSA",
      "alg": "RS256",
      "use": "sig",
      "n": "xGOr-H7A-PWG...", 
      "e": "AQAB"
    }
  ]
}
```

Каждый JWT в своём header содержит `kid` (Key ID) — указатель на то, КАКИМ из ключей в JWKS он подписан:

```json
{ "alg": "RS256", "typ": "JWT", "kid": "a1b2c3d4-key-id" }
```

Это существует не просто "для порядка" — это механизм **ротации ключей без даунтайма**. Keycloak можно настроить на периодическую смену подписывающего ключа (Realm Settings → Keys → Key rotation). В момент ротации в JWKS одновременно присутствуют СТАРЫЙ и НОВЫЙ ключ: токены, выданные до ротации и всё ещё живые (TTL не истёк), продолжают валидироваться старым ключом по его `kid`, а новые токены подписываются и проверяются новым. Без `kid` Resource Server не смог бы понять, какой из нескольких ключей в JWKS применить к конкретному токену.

```txt
Почему НЕЛЬЗЯ хардкодить публичный ключ в конфиге приложения:
  1. Ротация ключей на стороне Keycloak сломает валидацию у ВСЕХ
     клиентов, использующих захардкоженный ключ, до ручного передеплоя
  2. При компрометации ключа единственный способ быстро отреагировать —
     сгенерировать новый ключ в Keycloak; хардкод исключает этот путь
  3. Библиотеки типа jwks-rsa/jose САМИ кэшируют JWKS с TTL и умеют
     переспросить, если встречают незнакомый kid — задача решена
     стандартным способом, изобретать своё не нужно
```

```typescript
// NestJS: passport-jwt стратегия, валидирующая токен через JWKS
// Библиотека jwks-rsa сама кэширует ключи и обновляет при незнакомом kid
import { Strategy } from 'passport-jwt';
import { passportJwtSecret } from 'jwks-rsa';

export class KeycloakJwtStrategy extends PassportStrategy(Strategy, 'jwt') {
  constructor(config: ConfigService) {
    super({
      jwtFromRequest: ExtractJwt.fromAuthHeaderAsBearerToken(),
      algorithms: ['RS256'],
      secretOrKeyProvider: passportJwtSecret({
        jwksUri: `${config.get('KEYCLOAK_ISSUER')}/protocol/openid-connect/certs`,
        cache: true,          // кэшировать полученный ключ по kid
        rateLimit: true,      // защита от избыточных запросов к JWKS-эндпоинту
        jwksRequestsPerMinute: 5,
      }),
      issuer: config.get('KEYCLOAK_ISSUER'),
    });
  }

  validate(payload: KeycloakJwtPayload) {
    return payload; // доступно дальше как req.user
  }
}
```

Полный разбор Guard'ов/декораторов поверх этой стратегии — в статье [NestJS Resource Server]; здесь важно унести именно механику JWKS + `kid` как способ проверять подпись быстро и переживать ротацию ключей без ручного вмешательства.

## Локальная валидация vs Token Introspection — реальный trade-off

Проверка подписи через JWKS — это только половина вопроса "валиден ли токен". Есть второй, более тонкий вопрос: **а не был ли этот токен отозван ДО истечения своего TTL** (пользователь разлогинился, admin заблокировал аккаунт, обнаружена компрометация)? Тут есть два принципиально разных подхода.

```txt
Локальная (offline) JWT-валидация:
  Resource Server проверяет подпись и exp/iss/aud ЛОКАЛЬНО, используя
  JWKS-ключ, без единого сетевого запроса к Keycloak на сам запрос.

  ✓ Latency:     доли миллисекунды, никакой сетевой зависимости
  ✓ Нагрузка:    Keycloak не участвует в hot path запросов вообще
  ✗ Revocation:  Resource Server узнает об отзыве токена ТОЛЬКО
                 когда истечёт TTL — если пользователя заблокировали
                 "прямо сейчас", у него есть валидный access token
                 ещё до N минут (TTL access token'а)

Token Introspection (RFC 7662):
  Resource Server на КАЖДЫЙ запрос делает back-channel вызов к
  Keycloak: "этот токен всё ещё активен?"

  ✓ Revocation:  мгновенное знание об отзыве — Keycloak отвечает
                 "active: false" сразу после логаута/блокировки
  ✗ Latency:     дополнительный сетевой round-trip на КАЖДЫЙ запрос
  ✗ Нагрузка:    Keycloak становится точкой, от доступности которой
                 зависит КАЖДЫЙ запрос к API, а не только логин
```

```bash
# Introspection endpoint — confidential client спрашивает Keycloak
# про статус конкретного токена
curl -X POST \
  https://keycloak.example.com/realms/myrealm/protocol/openid-connect/token/introspect \
  -u "backend-service:$CLIENT_SECRET" \
  -d "token=$ACCESS_TOKEN"
```

```json
{
  "active": true,
  "sub": "a1b2c3",
  "exp": 1719936000,
  "scope": "openid profile email",
  "client_id": "spa-client"
}
```

Практическое правило выбора: **начинать с локальной валидации по умолчанию** и держать TTL access token'а коротким (5-15 минут) — это закрывает 95% реальных случаев с приемлемым риском ("украденный токен живёт максимум 15 минут"). Переходить на introspection точечно — не для всего API, а для конкретных высокочувствительных операций (перевод денег, изменение прав доступа, административные действия), где даже несколько минут задержки в распространении revoke неприемлемы. Introspection на КАЖДЫЙ запрос всего API — типичная ошибка проектирования: превращает Keycloak в единую точку отказа для системы, которая изначально проектировалась как stateless.

## Opaque vs JWT-кодированный refresh token

Keycloak по умолчанию делает refresh token тоже JWT-ом (в отличие от чистого OAuth2, который вообще не диктует формат refresh token — см. статью 01). Это осознанный компромисс, а не требование спецификации:

```txt
Opaque refresh token (случайная строка, requires БД lookup):
  ✓ Ничего не раскрывает при декодировании (это просто случайные байты)
  ✓ Естественно проверяется через БД/Keycloak — состояние ревокации
    всегда актуально, потому что сама проверка ходит в хранилище
  ✗ Требует централизованного хранилища на стороне Authorization Server

JWT refresh token (используется Keycloak по умолчанию):
  ✓ Keycloak может закодировать в него session ID и метаданные,
    upскорить internal lookup при обмене на новый access token
  ✗ Полезная нагрузка технически читаема (хотя клиент не должен
    её парсить и опираться на содержимое — refresh token для клиента
    должен оставаться "чёрным ящиком", предназначенным только
    для отправки на /token)
```

Для клиентского кода (React/NestJS) это различие **не должно влиять на реализацию** — в обоих случаях контракт одинаковый: refresh token отправляется на `/token` с `grant_type=refresh_token` и никогда не парсится и не используется клиентом напрямую. Формат — деталь реализации Keycloak; относиться к refresh token нужно как к непрозрачному секрету в любом случае.

## Настройка TTL — короткий access token, длинный refresh, и почему это не произвольные числа

```txt
Access Token TTL (Keycloak: Realm Settings → Tokens → Access Token Lifespan):
  Типичное значение: 5-15 минут
  Логика: это верхняя граница "окна риска" при краже токена.
  Короче — безопаснее, но чаще происходит silent refresh
  (дополнительная сетевая нагрузка + больше точек отказа UX).
  15 минут — практический баланс для большинства web-приложений.

Refresh Token TTL (Keycloak: SSO Session Idle / SSO Session Max):
  SSO Session Idle: сколько времени сессия жива БЕЗ активности
    (типично: несколько часов — "если ушёл на обед, не разлогинило")
  SSO Session Max: абсолютный потолок жизни сессии, даже при
    непрерывной активности (типично: дни — принудительный релогин)
  Логика: это про UX-компромисс "как часто пользователь видит
  форму логина заново", а не про защиту от кражи — за это отвечает
  rotation (ниже) и revocation.
```

**Refresh Token Rotation** — политика, при которой КАЖДЫЙ обмен refresh token'а на новую пару токенов выдаёт НОВЫЙ refresh token и делает старый недействительным (Keycloak: клиент → Advanced Settings → "Revoke Refresh Token" / OAuth 2.0 Mutual-TLS настройки, а также встроенный механизм для public-клиентов). Это не только гигиена — это **механизм обнаружения кражи**: если refresh token был скомпрометирован (например, украден через XSS до того, как приложение успело его использовать) и атакующий пытается обменять его ПОСЛЕ того, как легитимный клиент уже это сделал — Keycloak видит попытку использовать уже отозванный token и может среагировать (revoke всей цепочки, алерт). Полный сценарий "reuse detection" разобран в статье [Security Hardening and Attack Vectors].

## Server-side сессии Keycloak vs stateless-валидация Resource Server — как две модели сосуществуют

Это источник частой путаницы: "если JWT валидируется локально и без обращения к серверу — при чём тут вообще сессии на Keycloak?" Ответ — потому что это **две разные сущности**, отвечающие за разные вещи.

```txt
┌───────────────────────────────────────────────────────────────────┐
│                  Keycloak (Authorization Server)                  │
│                                                                   │
│   Server-side SSO Session:                                        │
│     Хранится В БД/памяти Keycloak. Живёт, пока пользователь       │
│     не разлогинится или не истечёт SSO Session Max/Idle.          │
│     Именно эта сессия даёт SSO: если пользователь уже             │
│     аутентифицирован в этой сессии, при редиректе на /authorize   │
│     от ДРУГОГО клиента Keycloak НЕ покажет форму логина повторно. │
│     ЭТА сессия — источник истины, кто реально залогинен.          │
└─────────────────────────────────┬─────────────────────────────────┘
                                  │ на основе сессии Keycloak
                                  │ выдаёт access/id/refresh токены
                                  ▼
┌────────────────────────────────────────────────────────────────────────┐
│                      NestJS Resource Server (API)                      │
│                                                                        │
│   Ничего не хранит про сессию вообще. Каждый запрос проверяется        │
│   независимо: подпись валидна? exp не истёк? aud правильный?           │
│   Это классическая stateless-модель — Resource Server НЕ ЗНАЕТ,        │
│   жива ли ещё Keycloak-сессия, из которой этот токен появился,         │
│   пока не истечёт exp токена (см. trade-off локальной валидации выше). │
└────────────────────────────────────────────────────────────────────────┘
```

Практическое следствие: **отзыв Keycloak-сессии (logout, блокировка админом) не отзывает мгновенно уже выданные access token'ы** — они продолжают проходить локальную валидацию на Resource Server до истечения exp, потому что Resource Server физически не знает о состоянии server-side сессии. Это не баг, а прямое следствие выбора stateless-модели для API — и именно поэтому короткий TTL access token'а — это не перестраховка, а единственный практический способ ограничить окно "токен валиден, а сессия уже мертва".

## Logout — почему "удалить токен на фронте" — это не логаут

Наивная реализация ("удалили `accessToken` из памяти/localStorage, всё, разлогинили") решает только UX этой ОДНОЙ вкладки этого ОДНОГО клиента. Реальный logout в системе с SSO и несколькими клиентами требует явно спроектированного распространения.

```txt
Front-channel logout:
  Клиент, инициировавший logout, редиректит браузер пользователя на
  Keycloak-эндпоинт /protocol/openid-connect/logout. Keycloak убивает
  server-side сессию и, используя браузер как транспорт, по очереди
  редиректит (или рендерит невидимые iframe'ы) на logout-эндпоинты
  ВСЕХ ДРУГИХ клиентов, у кого была активна эта же SSO-сессия.

  ✗ Хрупкость: зависит от того, что браузер пользователя вообще
    ДОЙДЁТ до всех этих редиректов/iframe — если пользователь закрыл
    вкладку посреди процесса, часть клиентов не узнает о logout
  ✗ Та же проблема third-party cookie restrictions, что и у
    silent-check-sso (см. [React SPA Integration])

Back-channel logout (OIDC Back-Channel Logout, рекомендуется):
  Keycloak, убив server-side сессию, делает ПРЯМОЙ server-to-server
  HTTP POST на заранее зарегистрированный backchannel_logout_uri
  КАЖДОГО клиента, у кого была активна эта сессия — без участия
  браузера пользователя вообще.

  ✓ Надёжность: не зависит от того, жив ли ещё браузер пользователя
    или его вкладка
  ✓ Работает даже для клиентов без открытого UI (мобильное приложение
    в фоне, серверный BFF)
```

```txt
Single Logout — распространение по нескольким клиентам:

   React SPA          NestJS BFF            Mobile App
        │                  │                     │
        │  все три получили токены               │
        │  в рамках ОДНОЙ SSO-сессии             │
        └──────────────────┴─────────────────────┘
                           │
                           ▼
               ┌─────────────────────────┐
               │ Keycloak SSO Session ID │
               └───────────┬─────────────┘
                           │ logout инициирован ЛЮБЫМ из клиентов
                           ▼
               Keycloak убивает сессию → рассылает back-channel logout
               POST на backchannel_logout_uri ВСЕХ трёх клиентов
                           │
        ┌──────────────────┬─────────────────────┐
        ▼                  ▼                     ▼
React SPA чистит    NestJS BFF рвёт    Mobile App узнаёт
свою локальную      свою серверную     через push/при
копию токена        сессию/куку        следующем API-вызове
```

```typescript
// NestJS: минимальный обработчик back-channel logout
// Keycloak шлёт сюда JWT ("logout token") при разлогинивании сессии
@Post('backchannel-logout')
async handleBackchannelLogout(@Body('logout_token') logoutToken: string) {
  const payload = await this.verifyLogoutToken(logoutToken); // проверка через тот же JWKS
  const sessionId = payload.sid;

  // Отозвать всё, что бэкенд хранит для этой сессии:
  // серверные куки/сессии BFF, закэшированные refresh token'ы и т.д.
  await this.sessionStore.revokeBySessionId(sessionId);

  return { status: 'ok' }; // Keycloak ожидает 200 OK
}
```

Ключевой вывод: **правильный logout — это не действие одного клиента, а событие, которое должно быть спроектировано так, чтобы дойти до всех участников SSO-сессии**, и в 2024+ архитектурах back-channel logout — предпочтительный механизм именно потому, что не зависит от состояния браузера пользователя в момент разлогинивания.

## Итоговая связь понятий

```txt
[JWKS + kid]                  →  как Resource Server проверяет подпись
                                 локально и переживает ротацию ключей
                                 без ручного вмешательства

[Локальная валидация vs
 Introspection]                →  latency/нагрузка vs мгновенное знание
                                 об отзыве — выбор по чувствительности
                                 конкретной операции, а не глобально

[Opaque vs JWT refresh]        →  деталь реализации Authorization
                                 Server; для клиента refresh token
                                 всегда непрозрачен

[TTL access/refresh + rotation] →  короткий access = маленькое окно
                                 риска; rotation refresh token'а =
                                 обнаружение кражи, а не только гигиена

[Server-side сессия Keycloak
 vs stateless Resource Server]  →  два разных источника истины;
                                 несовпадение их состояния — и есть
                                 причина, почему короткий TTL access
                                 token'а обязателен, а не опционален

[Front-channel vs back-channel
 logout]                        →  надёжность распространения logout
                                 по нескольким клиентам одной SSO-сессии
```

## Типичные ошибки на интервью

- **"Приложение должно хардкодить публичный ключ Keycloak для проверки JWT"** — неверно и небезопасно: правильный подход — JWKS endpoint с кэшированием по `kid`, что переживает ротацию ключей без передеплоя приложения. Хардкод ключа — то, что ломается в первый же плановый security-maintenance Keycloak.

- **"Token Introspection всегда лучше локальной валидации, потому что даёт мгновенный revoke"** — упускает половину картины: introspection делает Keycloak зависимостью КАЖДОГО API-запроса, а не только логина, что противоречит идее stateless resource server и добавляет latency на каждый вызов. Правильный ответ — точечное применение для высокочувствительных операций, а не тотальная замена локальной валидации.

- **"Раз access token — JWT, значит его можно отозвать, просто удалив из БД"** — нет, если Resource Server валидирует его локально (что типично), удаление записи из БД Keycloak никак не влияет на уже выданный, ещё не истёкший JWT — он продолжит проходить локальную проверку подписи до истечения `exp`. Отзыв работает мгновенно только там, где есть явная проверка состояния (introspection, blacklist).

- **"Logout — это просто удалить токен из localStorage/памяти на фронтенде"** — неполно: это разлогинивает только текущую вкладку текущего клиента, но не завершает server-side SSO-сессию в Keycloak и не уведомляет другие клиенты, использовавшие ту же сессию. Полноценный logout требует either front-channel редиректа на Keycloak logout endpoint, либо (надёжнее) back-channel logout, распространяющегося на все зарегистрированные клиенты.

- **"Backend должен сам обновлять access token, когда он истекает"** — путаница ответственности: refresh — обязанность КЛИЕНТА (кто держит refresh token и обращается к `/token`), а не Resource Server'а. Resource Server, получив истёкший токен, должен просто ответить 401 с понятным телом ошибки — реакция на это (сходить за новым токеном) целиком на стороне клиента (см. [NestJS Resource Server] и [React SPA Integration]).
