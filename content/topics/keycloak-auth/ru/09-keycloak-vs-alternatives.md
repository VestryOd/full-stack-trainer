# Keycloak vs альтернативы — честный выбор, а не маркетинг

## Зачем это отдельная статья, если всё остальное было про Keycloak

Восемь предыдущих статей учили пользоваться Keycloak глубоко и правильно. Это не значит, что Keycloak всегда правильный выбор.

Senior-инженер отличается от того, кто просто хорошо знает инструмент, способностью честно сказать одну фразу: "в этом случае мы должны были взять не Keycloak". В том числе про случаи, когда Keycloak выбрали лично вы, а контекст с тех пор изменился.

Поэтому статья не про то, что "Keycloak лучше всех". Это фреймворк, чтобы принимать решение заново в каждом конкретном проекте.

## Игроки на поле — что они есть на самом деле

```txt
Keycloak:
  Open-source (лицензия Apache 2.0), self-hosted (или через managed
  предложения третьих сторон — Red Hat build of Keycloak, различные
  managed-Keycloak SaaS). Полный контроль над кодом,
  инфраструктурой, данными пользователей — и полная
  ответственность за их эксплуатацию.

Auth0 (теперь часть Okta):
  Managed identity-as-a-service. Богатый UI для конфигурации,
  большая экосистема "Actions"/"Rules" (кастомная логика без
  деплоя своего инстанса), сильная документация и DX.
  Ценообразование по MAU (monthly active users) — может расти
  нелинейно с ростом продукта.

Okta (как отдельный от Auth0 продукт — Okta Identity Cloud):
  Managed, исторически ориентирован сильнее на enterprise/workforce
  identity (сотрудники компании, B2E) и на глубокую интеграцию с
  корпоративными системами (SSO во внутренние
  enterprise-приложения), хотя современный Okta CIC (Customer
  Identity Cloud, экс-Auth0) покрывает и B2C/CIAM-сценарии.

AWS Cognito:
  Managed, глубоко интегрирован с остальным AWS (IAM, Lambda
  triggers для кастомизации флоу, API Gateway authorizers).
  Ценообразование по MAU, обычно ощутимо дешевле Auth0/Okta на
  сопоставимых объёмах. Известен более скудным UI/DX и менее
  гибкой кастомизацией флоу по сравнению с Auth0.

Supabase Auth (GoTrue):
  Open-source, обычно используется как часть Supabase (managed
  Postgres + auth + realtime + storage "из коробки"). Значительно
  проще концептуально, чем Keycloak/Auth0 — меньше конфигурации,
  меньше возможностей (нет полноценных Authorization Services,
  ограниченнее Identity Brokering) — рассчитан на быстрый старт,
  а не на enterprise-глубину.

Самописное решение:
  Собственная таблица users, свой JWT-issuing код, свой bcrypt.
  Полный контроль, ноль внешних зависимостей — и полная
  ответственность за каждый аспект: password reset flow, MFA,
  rate limiting на логине, брутфорс-защиту, соответствие
  security best practices, которые Keycloak/Auth0 уже реализовали
  и протестировали на миллионах инсталляций.
```

## Когда self-hosted Keycloak — правильный выбор

```txt
Стоимость на масштабе:
  Managed-провайдеры (Auth0, Okta, Cognito) берут плату по MAU —
  на малом масштабе это дёшево или бесплатно (free tier), но
  на масштабе в сотни тысяч-миллионы активных пользователей
  счёт может стать одной из крупнейших инфраструктурных статей
  расходов компании. Keycloak self-hosted — стоимость это
  инфраструктура: сервера, база данных, инженерное время на
  поддержку. Она растёт сублинейно относительно числа
  пользователей — в отличие от MAU-биллинга. При достаточном
  масштабе self-hosting экономически выгоднее, несмотря на
  инженерные накладные расходы.

Data residency и контроль данных:
  Регуляторные требования (GDPR-чувствительные юрисдикции,
  финансовый/медицинский compliance, государственный сектор)
  иногда буквально требуют, чтобы персональные данные пользователей
  не покидали конкретную юрисдикцию/инфраструктуру. Self-hosted
  Keycloak в вашем собственном дата-центре/облачном регионе даёт
  прямой контроль над этим конкретным требованием, вместо того
  чтобы полагаться на региональные гарантии managed-провайдера
  (которые тоже существуют, но добавляют дополнительный слой
  доверия третьей стороне).

Глубина кастомизации:
  Custom Authentication Flows, Protocol Mapper SPI, User Storage
  SPI (статья 08) — Keycloak даёт доступ к исходному коду и полной
  расширяемости через Java SPI. Managed-провайдеры дают
  кастомизацию через свои API/хуки (Auth0 Actions, Cognito Lambda
  triggers) — мощно, но в рамках того, что провайдер решил сделать
  расширяемым, а не произвольно.

Отсутствие vendor lock-in на биллинг:
  MAU-based pricing managed-провайдеров создаёт прямую финансовую
  зависимость от роста пользовательской базы, растущую нелинейно
  относительно фактической инженерной нагрузки на систему
  аутентификации.
```

## Когда managed-провайдер — лучший выбор

```txt
Сниженная операционная нагрузка:
  Keycloak self-hosted требует: HA-развёртывание (статья 08),
  мониторинг, патчинг security-уязвимостей, тестирование апгрейдов
  между мажорными версиями (breaking changes бывают), резервное
  копирование базы данных, дежурство при инцидентах auth-слоя.
  Managed-провайдер берёт всё это на себя — команда получает auth
  "как сервис" без необходимости нанимать или выделять инженеров
  на поддержку самого IdP.

Быстрый time-to-market:
  Managed-провайдеры оптимизированы под "настроить за час, а не
  за недели" — готовые SDK под все платформы, готовые UI-компоненты
  логина, готовая документация под частые интеграции. Для стартапа,
  которому критична скорость выхода на рынок, разница между
  "подключили Auth0 за день" и "развернули и настроили
  Keycloak-кластер за две недели" может быть решающей.

SLA и поддержка:
  Enterprise-контракт с Auth0/Okta даёт формальный SLA на аптайм,
  выделенную поддержку, ответственность провайдера за инциденты
  безопасности их платформы. Self-hosted Keycloak — ответственность
  целиком на вашей команде, включая 3 часа ночи в выходной.

Меньшая команда, меньше специализированной экспертизы:
  Если в команде нет и не планируется отдельный инженер/группа,
  специализирующаяся на identity-инфраструктуре — managed-решение
  снимает необходимость становиться экспертом по эксплуатации
  Keycloak именно для того, чтобы просто иметь работающий логин.
```

## Вопросы, которые реально задаёт senior-инженер — не чеклист фич

Выбор IdP (identity provider, провайдер идентичности) по табличке "функция X есть / функция Y нет" — поверхностный подход. Почти все нужные функции **есть** у всех крупных игроков в том или ином виде. Реальное решение строится на других вопросах:

```txt
1. "Какой размер команды и есть ли expertise по эксплуатации
    identity-инфраструктуры?"
   → Нет отдельной платформенной команды → managed сильно
     перевешивает. Есть выделенная platform/infra-команда →
     self-hosted становится реалистичной опцией.

2. "Какие есть compliance/регуляторные требования именно у этого
    бизнеса, а не абстрактно?"
   → Конкретное юридическое требование к data residency →
     сильный аргумент в пользу self-hosted ИЛИ managed-провайдера
     с гарантированным региональным размещением (уточнять
     контрактно, не предполагать).

3. "Каков ожидаемый auth-трафик и как он будет расти?"
   → MAU-биллинг на прогнозируемых сотнях тысяч+ активных
     пользователей — посчитать реальную стоимость на 12-24 месяца
     вперёд, не только на сегодняшний объём — managed-биллинг
     часто становится неприятным сюрпризом именно при быстром росте.

4. "Насколько глубокая кастомизация auth-флоу реально нужна бизнесу,
    а не хочется 'на всякий случай'?"
   → Сложные corporate SSO-интеграции, кастомные многошаговые
     флоу верификации, специфичная бизнес-логика в момент выдачи
     токена (статья 08, Protocol Mapper SPI) → self-hosted даёт
     полный доступ к этому. Стандартный email+password+social login
     → почти любой провайдер справится одинаково хорошо, разница
     не в возможностях, а в цене/операционной нагрузке.

5. "Что произойдёт, если провайдер поднимет цену/изменит условия/
    прекратит поддержку той функции, на которую мы завязались?"
   → Managed-провайдер — это ещё и business relationship с риском
     изменения условий не по вашей воле; self-hosted убирает этот
     конкретный риск ценой взятия на себя операционного.
```

## Итоговая связь понятий

```txt
[Self-hosted Keycloak оправдан]  →  масштаб делает MAU-биллинг
                                   дороже инфраструктуры и
                                   инженерного времени; жёсткие data
                                   residency требования; нужна
                                   кастомизация за пределами хуков
                                   провайдера

[Managed IdP оправдан]            →  команда без dedicated identity-
                                   экспертизы; критична скорость
                                   запуска; нужен формальный SLA;
                                   стандартные auth-сценарии без
                                   глубокой кастомизации

[Вопросы senior-инженера]          →  размер команды, реальные
                                   (не абстрактные) compliance-
                                   требования, прогноз трафика на
                                   12-24 месяца, реальная (не
                                   гипотетическая) потребность в
                                   кастомизации, риск vendor
                                   lock-in на биллинг/условия
```

## Типичные ошибки на интервью

- **"Keycloak всегда лучше managed-решений, потому что бесплатный и open-source"** — упрощение. "Бесплатный" относится только к лицензии, а не к общей стоимости владения. Инфраструктура и инженерное время на HA (high availability, высокая доступность), патчинг и апгрейды часто перевешивают биллинг managed-провайдера по MAU (monthly active users) на небольшом и среднем масштабе. Self-hosting выгоден именно **на масштабе**, а не по умолчанию.

- **"Выбор IdP — это сравнение таблицы фич, у кого их больше"** — поверхностный подход: почти все крупные игроки покрывают одинаковый базовый набор возможностей. Реальное решение строится на команде/compliance/трафике/vendor lock-in риске, а не на подсчёте пунктов в маркетинговой таблице сравнения.

- **"AWS Cognito — универсально худший выбор из-за скудного UI"** — контекстно неверно. UI (user interface) здесь — это админ-консоль, а AWS — это Amazon Web Services. Если инфраструктура и так на AWS, глубокая интеграция с IAM (Identity and Access Management), Lambda и API Gateway может это перевесить. Заметно более низкая цена на объёме тоже считается. Более слабые UI и DX (developer experience) делают это компромиссом, а не однозначным вердиктом.

- **"Managed-провайдер снимает всю ответственность за безопасность"** — нет. Managed-провайдер снимает операционную ответственность за инфраструктуру самого IdP: патчинг и аптайм. Ответственность за **правильное использование** протокола целиком остаётся на команде, которая разрабатывает приложение. Это валидация `redirect_uri`, PKCE (Proof Key for Code Exchange) и правильное хранение токенов на клиенте — статьи 05-07. Выбор провайдера здесь ничего не меняет.

- **"Supabase Auth и Keycloak — взаимозаменяемые варианты для любого проекта"** — нет. У них принципиально разный уровень зрелости и охват возможностей. У Supabase Auth нет полноценных Authorization Services, нет глубокого Identity Brokering и нет аналога расширяемости через SPI (Service Provider Interface), как у Keycloak. Выбор определяется не личными предпочтениями. Вопрос в том, нужна ли проекту enterprise-глубина Keycloak или достаточно быстрого старта Supabase.
