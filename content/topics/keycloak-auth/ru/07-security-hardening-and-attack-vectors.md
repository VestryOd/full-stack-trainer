# Security Hardening — атаки и защита конкретно для auth-флоу

## За каждым механизмом защиты стоит одна конкретная атака

Эта статья доводит каждый механизм защиты auth-флоу до той самой атаки, которую он закрывает.

В статьях 01-06 эти механизмы упоминались по мере необходимости: PKCE (Proof Key for Code Exchange), TTL токенов (time to live, время жизни), ротация refresh-токенов. Но саму атаку там не разбирали. Общая механика XSS (cross-site scripting), CSRF (cross-site request forgery) и CORS (cross-origin resource sharing) разобрана в общей теме Security. Здесь фокус узкий и прикладной:

- Что конкретно происходит, если PKCE отсутствует.
- Что именно ломается при слабой валидации `redirect_uri`.
- Как физически работает атака JWT (JSON Web Token) algorithm confusion.

Это тот уровень, который отличает два ответа. Первый — "я настроил Keycloak по гайду". Второй — "я могу объяснить атакующему сценарий, от которого защищает каждая галочка в конфиге".

## PKCE — механика защиты, не просто "рекомендуемая практика"

Полный sequence PKCE был показан в статье 01; здесь — что именно происходит математически и почему это защищает.

```txt
Шаг 1 (клиент, локально, никуда не отправляется):
  code_verifier = криптографически случайная строка,
                  43-128 символов
  Пример: "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

Шаг 2 (клиент вычисляет и отправляет производное значение):
  code_challenge = BASE64URL(SHA256(code_verifier))
  code_challenge_method = "S256"

Шаг 3 (клиент отправляет code_challenge на /authorize):
  GET /authorize?...
      &code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
      &code_challenge_method=S256
  Keycloak запоминает code_challenge вместе с выданным
  authorization code

Шаг 4 (клиент обменивает code на токены и отправляет
       оригинальный code_verifier):
  POST /token
    grant_type=authorization_code
    &code=<authorization code>
    &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

Шаг 5 (Keycloak проверяет):
  SHA256(code_verifier из шага 4) == code_challenge из шага 3 ?
  Совпадает → выдать токены
  Не совпадает → отклонить, 400 invalid_grant
```

Почему это защищает конкретно от **authorization code interception**: перехваченный `code` сам по себе бесполезен.

Допустим, атакующий каким-то образом его получил. Утечь `code` может через логи прокси. Может — через вредоносное приложение на устройстве, зарегистрированное на тот же custom URL scheme. Может — через систему аналитики, которая логирует полный URL редиректа. Без `code_verifier` это значение не даёт атакующему ничего.

Сам `code_verifier` **никогда не передаётся по сети до шага 4** и хранится только в памяти легитимного клиента. В SPA (single-page application, одностраничное приложение) он обычно лежит в `sessionStorage` на время флоу, между шагом 2 и шагом 4.

Вычислить `code_verifier` из `code_challenge` атакующий тоже не может. SHA256 — однонаправленная функция, и обратное вычисление криптографически неосуществимо.

```txt
              Перехваченный code — половина пары
┌───────────────┬───────────────────────┬────────────────────┐
│ значение      │ где передаётся        │ что стоит          │
├───────────────┼───────────────────────┼────────────────────┤
│ code          │ front-channel         │ сам по себе ничего │
├───────────────┼───────────────────────┼────────────────────┤
│ code_verifier │ только память клиента │ вторая половина    │
└───────────────┴───────────────────────┴────────────────────┘

┌────────────────────────────────────────────────┐
│ SHA256 однонаправлена: вычислить code_verifier │
│ из code_challenge нельзя                       │
└────────────────────────────────────────────────┘
```

**Почему PKCE важен даже для confidential-клиентов.** Это частый вопрос на собеседовании, уже поднятый в статье 01; здесь — механика.

Confidential-клиент защищён `client_secret` от того, чтобы **кто-то другой** выдавал себя за него на шаге обмена code→token. Но от другого сценария `client_secret` не защищает. Атакующий перехватывает `code`, предназначенный **именно этому** клиенту, и пытается обменять его через **тот же самый** confidential-клиент раньше легитимного пользователя. Это гонка на перехваченном code: успеть до легитимного запроса.

PKCE закрывает именно этот сценарий, независимо от типа клиента. Поэтому современный OAuth 2.0 Security Best Current Practice рекомендует PKCE как обязательный для **всех** типов клиентов, а не только для public.

## state vs nonce — два параметра, которые защищают от разных атак

Оба параметра — случайные строки. Клиент генерирует их, отправляет в запросе на `/authorize` и получает обратно. Именно из-за этого сходства их и путают. А защищают они от принципиально разных атак.

```txt
state — CSRF/replay-защита самого редиректа:

  Атака без state: атакующий запускает свой собственный логин-флоу
  на легитимном Keycloak и логинится в подконтрольный ему аккаунт.
  Он получает валидный authorization code на свой redirect. Дальше
  он подсовывает жертве ссылку на callback-URL приложения с этим
  code — например, в фишинговом письме. Если жертва по ней перейдёт,
  а приложение не проверит соответствие state, оно может связать
  сессию жертвы с аккаунтом атакующего. Это Login CSRF: жертва
  оказывается залогинена как атакующий и может ввести свои
  чувствительные данные в аккаунт, который контролирует атакующий.

  Защита: клиент генерирует случайный state перед редиректом на
  /authorize, сохраняет его локально (sessionStorage), передаёт
  в запросе, а на callback проверяет, что вернувшийся state
  совпадает с сохранённым. Чужой authorization code, полученный
  не в рамках этой локальной сессии клиента, такую проверку
  не пройдёт.

nonce — replay-защита ID Token:

  Атака без nonce: атакующий получил ранее выданный, ещё не
  истёкший ID Token легитимного пользователя — например, через
  логи или скомпрометированный канал. Он повторно предъявляет
  его клиентскому приложению как "результат нового логина".

  Защита: клиент генерирует случайный nonce перед редиректом.
  Keycloak встраивает его в сам ID Token как claim
  (`nonce: <значение>`) при выдаче. Получив ID Token, клиент
  сверяет claim `nonce` внутри токена с тем значением, которое
  сам сгенерировал для этой конкретной попытки логина. Повторно
  предъявленный старый ID Token содержит старый nonce, он с новым
  не совпадёт — и клиент отклонит его как невалидный для текущей
  сессии.
```

Мнемоника, которая реально разделяет эти два параметра. Параметр `state` **защищает транспорт**: сам redirect-обмен между клиентом и Keycloak на уровне HTTP. Параметр `nonce` **защищает содержимое**: сам ID Token, чтобы его нельзя было использовать в отрыве от конкретной попытки логина.

В потоке OIDC (OpenID Connect) оба параметра используются одновременно и не заменяют друг друга. И `keycloak-js`, и `oidc-client-ts` генерируют и проверяют оба автоматически. Знание механизма всё равно важно. Оно показывает, что именно ломается, если библиотека настроена неправильно — например, в кастомной реализации OIDC-клиента, где пропустили проверку nonce.

## Строгая валидация redirect_uri — как слабая проверка превращается в кражу токена

`redirect_uri` — это URL, куда Keycloak отправит браузер пользователя с authorization code после успешного логина. Если Keycloak (или сам клиент) валидирует этот параметр НЕТОЧНО, это открывает прямой путь к краже кода/токена.

```txt
Слабая валидация (частая ошибка конфигурации):
  Зарегистрированный redirect_uri в Keycloak:
  "https://app.example.com/*" — wildcard-паттерн, который
  некоторые старые или неаккуратные конфигурации разрешают
  "для удобства"

  Атака: допустим, на app.example.com где-то есть
  open-redirect-уязвимость — /some-legit-path?next=https://evil.com,
  который делает редирект на next без проверки домена. Атакующий
  конструирует authorization request с
  redirect_uri=https://app.example.com/some-legit-path?next=
  https://evil.com, и это технически совпадает с
  wildcard-паттерном. Пользователь логинится, и форма Keycloak
  выглядит абсолютно нормально: домен ведь настоящий. Keycloak
  редиректит на разрешённый redirect_uri, а тот делает
  open-redirect на evil.com — и передаёт туда authorization code
  через query string того же редиректа.

Правильная валидация:
  Зарегистрированный redirect_uri: точное совпадение,
  "https://app.example.com/callback" — без wildcard, без лишних
  query-параметров, посимвольное сравнение. OAuth 2.0 Security
  Best Current Practice явно требует exact string matching, а не
  префиксное или паттерн-совпадение.
```

Практическое следствие для конфигурации Keycloak: **никогда не используйте wildcard-паттерны в Valid Redirect URIs клиента "для удобства разработки"** — даже временно. Это одна из тех настроек, которую забывают убрать перед продом. И одна из самых частых находок в реальных аудитах безопасности OAuth2-интеграций.

## JWT Algorithm Confusion — классическая ловушка на собеседовании

Это атака на саму библиотеку валидации JWT, а не на Keycloak напрямую. Но она касается кода, который вы пишете в NestJS Resource Server (статья 04), поэтому знание механики обязательно.

```txt
Атака "alg: none":

  JWT header технически может содержать { "alg": "none" } — токен
  без подписи вообще. По спецификации JWT это валидный формат,
  хоть и бессмысленный для аутентификации. Атакующий берёт любой
  валидный токен, меняет payload как хочет (например,
  "role": "admin"), меняет header на { "alg": "none" } и убирает
  signature-часть.

  Уязвимая библиотека: если код валидации доверяет `alg` из
  header самого токена — то есть спрашивает у токена, каким
  алгоритмом его проверять, — она честно "проверит" подпись
  по алгоритму "none" (пустая проверка) и примет токен.

  Защита: никогда не давать библиотеке валидации выбирать
  алгоритм по значению из токена. Список algorithms должен быть
  явно захардкожен в конфиге на стороне Resource Server:

    algorithms: ['RS256']   // жёстко, не "что скажет токен"

  (см. пример KeycloakJwtStrategy в статье 03/04 — там algorithms
  уже передан явно именно по этой причине)

Атака RS256/HS256 key confusion:

  Keycloak по умолчанию подписывает RS256. Это асимметричный
  алгоритм: приватный ключ у Keycloak, публичный — у всех
  остальных через JWKS. HS256 — симметричный алгоритм, где один
  и тот же секрет используется и для подписи, и для верификации.

  Атака: допустим, библиотека валидации не проверяет строго, что
  `alg` в полученном токене совпадает с ожидаемым алгоритмом
  (RS256), а вместо этого подстраивается под `alg`, заявленный
  в токене. Атакующий меняет header на { "alg": "HS256" } и
  подписывает токен HMAC, используя публичный RSA-ключ Keycloak
  как секрет для HMAC — а этот ключ открыто доступен через
  JWKS-эндпоинт. Уязвимая библиотека видит `alg: HS256` и берёт
  "ключ для HS256". Если код неаккуратно передаёт туда тот же
  публичный ключ, который используется для RS256-верификации,
  проверка пройдёт: HMAC(payload, публичный_RSA_ключ_как_секрет)
  действительно совпадёт с подписью, которую вычислил атакующий,
  зная этот публичный ключ.

  Защита: та же, что и выше — algorithms: ['RS256'] захардкожен,
  и библиотека уже не пытается интерпретировать токен как HS256
  ни при каких условиях. Современные проверенные библиотеки
  закрывают этот вектор по умолчанию при правильной настройке:
  jose, jsonwebtoken 9+, passport-jwt с явным algorithms. Но
  правильная настройка — явный algorithms, а не дефолт
  библиотеки — это ответственность разработчика.
```

Это классический вопрос на собеседовании именно потому, что звучит эзотерично, а сводится к одному практическому правилу. **Алгоритм проверки задаётся конфигурацией Resource Server, а не значением из самого токена.** Правило легко проверить в код-ревью. JWT-валидация без явного списка разрешённых алгоритмов — красный флаг, какая бы библиотека ни использовалась.

## Refresh Token Rotation с Reuse Detection — полный разбор

В статье 03 rotation была упомянута как политика. Здесь — почему это именно механизм **обнаружения** атаки, а не просто гигиена.

```txt
Нормальный сценарий (без атаки):

  Клиент держит refresh_token_1
  → обменивает на access_token_2 + refresh_token_2 (Keycloak
    отзывает refresh_token_1 в момент выдачи refresh_token_2)
  → позже обменивает refresh_token_2 на refresh_token_3
  → и так далее, каждый обмен инвалидирует предыдущий токен

Сценарий кражи (refresh token скомпрометирован, например, через
XSS до того, как приложение успело им воспользоваться):

  Атакующий украл refresh_token_1 — например, из sessionStorage
  через XSS, до того как легитимное приложение успело его
  обменять

  Случай A — атакующий использует его первым:
    Атакующий → обменивает refresh_token_1 на refresh_token_2
    Легитимное приложение позже пытается обменять свой, уже
    отозванный refresh_token_1 → Keycloak отказывает, потому
    что refresh_token_1 уже был использован и, следовательно,
    отозван → приложение видит invalid_grant там, где не
    ожидало. Это сигнал компрометации, и трактовать его стоит
    не как "истекшую сессию", а как потенциальную кражу

  Случай B — легитимное приложение использует его первым:
    Приложение → обменивает refresh_token_1 на refresh_token_2
    Атакующий позже пытается использовать уже отозванный
    refresh_token_1 → Keycloak видит попытку повторно
    использовать токен, который уже был "потрачен" в обмене —
    явный сигнал, что копией этого токена владеет кто-то ещё,
    помимо легитимного клиента
```

Правильная реакция на обнаруженный reuse — не просто отклонить конкретный запрос. Нужно **отозвать всю цепочку токенов, связанных с этой сессией**; Keycloak поддерживает это как часть refresh token rotation policy.

Легитимному пользователю придётся пройти полный релогин. По-другому и нельзя: на этом этапе невозможно достоверно отличить, какая из двух копий токена "правильная" — у атакующего или у легитимного пользователя.

Именно это превращает rotation из "просто более свежих токенов" в реальный механизм **обнаружения взлома**. Без rotation украденный refresh token оставался бы незаметно валиден до истечения TTL и никак не сигнализировал бы о компрометации.

## Brute-force detection в Keycloak — встроенная защита, которую нужно включить осознанно

Keycloak имеет встроенный механизм защиты от подбора пароля (Realm Settings → Security Defenses → Brute Force Detection), который стоит настраивать явно, а не полагаться на дефолты без проверки:

```txt
Ключевые параметры:
  Max Login Failures       — сколько неудачных попыток до
                             временной блокировки аккаунта
                             (типично: 5-10)
  Wait Increment           — на сколько растёт время блокировки
                             с каждой следующей серией неудач
                             (задержка прогрессивная, а не
                             фиксированная)
  Max Wait                 — потолок времени блокировки
  Quick Login Check Millis — минимальный интервал между
                             попытками, ниже которого попытки
                             считаются "слишком быстрыми"
                             (защита от скриптовых атак, которые
                             делают сотни попыток в секунду)
  Permanent Lockout        — блокировать аккаунт навсегда, до
                             ручной разблокировки админом, после
                             превышения потолка попыток — вместо
                             временной задержки
```

Практический нюанс: слишком агрессивные настройки создают вектор для **отказа в обслуживании через чужие учётные записи**. Достаточно низкого `Max Login Failures` вместе с включённым `Permanent Lockout`.

Атакующий, который знает только email жертвы и не знает пароля, намеренно вводит неправильный пароль нужное число раз. Легитимный пользователь теряет доступ к собственному аккаунту. Баланс между защитой от подбора пароля и этим вторичным вектором DoS (denial of service, отказ в обслуживании) — осознанное решение, а не "чем строже, тем лучше".

## Clickjacking-защита конкретно для страницы логина

Страница логина Keycloak — особенно чувствительная цель для clickjacking. Атака выглядит так.

Атакующий встраивает страницу логина в невидимый `<iframe>` на своей странице, поверх, например, кнопки "Играть в игру". Свой UI (user interface, пользовательский интерфейс) он кладёт прозрачным слоем поверх формы логина.

```txt
По чему щёлкает пользователь и что получает щелчок
┌───────────────────────────────────────────┐
│ Страница атакующего, сверху:              │
│ прозрачный слой с кнопкой "Играть в игру" │
├───────────────────────────────────────────┤
│ Невидимый <iframe> под ней:               │
│ настоящая форма логина Keycloak           │
└───────────────────────────────────────────┘
```

Пользователь вводит реальные учётные данные, думая, что взаимодействует с чем-то другим. Данные при этом действительно уходят через форму, которая принадлежит Keycloak, — просто встроенную атакующим в свой контекст.

```txt
Настройка Keycloak (Realm Settings → Security Defenses → Headers):
  X-Frame-Options: SAMEORIGIN   (устаревший, но всё ещё
                                 поддерживаемый заголовок;
                                 ограничивает встраивание в
                                 iframe тем же origin)
  Content-Security-Policy:
    frame-ancestors 'self' https://app.example.com;
    (современный, более гибкий механизм — явный whitelist
     доменов, которым разрешено встраивать страницу Keycloak
     в iframe. Важно: не 'none' безоговорочно. silent-check-sso
     из статьи 05 сам является легитимным iframe-встраиванием
     страницы Keycloak с домена приложения, и 'none' его
     сломает. Нужен точный whitelist собственных доменов
     приложения, а не полный запрет)
```

Одна тонкость специфична именно для этой темы. **Страницу логина Keycloak легитимно может потребоваться встраивать в iframe** — из-за silent-check-sso. Это единственная такая страница в системе. Для большинства других страниц приложения правильным дефолтом был бы `frame-ancestors 'none'`.

Поэтому настройка должна разрешать iframe-встраивание **только** с доверенных доменов ваших собственных клиентов. Широкий whitelist здесь так же опасен, как и его отсутствие.

## CORS — специфика именно для auth-эндпоинтов

Общая механика CORS разобрана в теме Security. Здесь — конкретные ловушки применительно к Keycloak-эндпоинтам.

```txt
Web Origins в настройках Keycloak-клиента:
  Это не то же самое, что Valid Redirect URIs. Web Origins
  определяет, каким источникам разрешено делать CORS-запросы
  (fetch/XHR) напрямую к Keycloak-эндпоинтам — например,
  к /userinfo и /token из браузера. Куда можно редиректить
  браузер, эта настройка не определяет.

  Частая ошибка конфигурации: настроить Valid Redirect URIs
  правильно, но забыть про Web Origins. Тогда браузерный
  fetch-запрос к /userinfo или /token будет заблокирован
  CORS policy Keycloak, хотя сам редиректный флоу логина
  работает нормально: редирект не подчиняется CORS, а
  fetch/XHR подчиняется. Это разные механизмы защиты одного
  и того же клиента, и путаница между ними — специфичный для
  Keycloak источник багов вида "логин работает, а запрос
  userinfo из фронтенда — нет".

CORS на стороне вашего Resource Server (NestJS):
  Access-Control-Allow-Origin должен явно перечислять
  источники React-приложения, а также BFF, если он
  используется (статья 06). Никакого wildcard '*' в сочетании
  с Authorization-заголовком: браузеры и так не позволят
  credentials с wildcard origin, а сама попытка так настроить
  указывает на непонимание модели. Особое внимание, если API
  обслуживает несколько SPA-клиентов на разных доменах
  (multi-tenant frontend). Origin должен явно сверяться со
  списком разрешённых доменов, а не отражаться бездумно.
  `Access-Control-Allow-Origin: <req.headers.origin>` без
  проверки по whitelist функционально эквивалентен wildcard —
  просто не выглядит им при поверхностном код-ревью.
```

## Типичные ошибки на интервью

- **"PKCE нужен только public-клиентам, у которых нет client secret"** — неполный ответ. Это уже разобрано в статье 01, и здесь стоит уметь объяснить механизм. PKCE защищает от authorization code interception независимо от наличия секрета: гонка на перехваченном code возможна и для confidential-клиента.

- **"state и nonce — это одно и то же, просто OAuth2 и OIDC придумали разные имена для одной защиты"** — нет. Параметр `state` защищает сам редирект-обмен от CSRF и replay. Параметр `nonce` защищает содержимое ID Token от повторного использования. Оба нужны одновременно, и они не взаимозаменяемы.

- **"Раз redirect_uri зарегистрирован в Keycloak, дальше можно не думать о его безопасности"** — нет. Допустим, зарегистрированный паттерн — wildcard или слишком широкий префикс, а где-то на домене приложения есть open-redirect-уязвимость. Такая пара превращается в канал кражи authorization code, каким бы "формально зарегистрированным" ни был redirect_uri.

- **"Библиотека валидации JWT сама разберётся, каким алгоритмом проверять подпись, судя по токену"** — нет. Это ровно та конфигурация, которая уязвима к атаке algorithm confusion. Правильный ответ: алгоритм всегда явно захардкожен в конфигурации Resource Server (`algorithms: ['RS256']`). Из значения `alg` в самом токене он не выводится никогда.

- **"Refresh token rotation — это просто более частая замена токенов ради гигиены"** — неполно. Главная ценность rotation — возможность **обнаружить** кражу токена через факт его повторного использования (reuse detection). Именно обнаружение позволяет отреагировать и отозвать всю цепочку, а не просто "поддерживать токены свежими".
