# Security Hardening — атаки и защита конкретно для auth-флоу

## Зачем нужна отдельная статья про безопасность, если она уже упоминалась

В статьях 01-06 механизмы защиты (PKCE, TTL, ротация) упоминались по мере необходимости, но без полного разбора именно атаки, которую они закрывают. Общая механика XSS/CSRF/CORS уже разобрана в теме [Security] — здесь фокус узкий и прикладной: что конкретно происходит, если PKCE отсутствует; что именно ломается при слабой валидации `redirect_uri`; как физически работает JWT algorithm confusion атака. Это тот уровень, который отличает "я настроил Keycloak по гайду" от "я могу объяснить атакующему сценарий, от которого защищает каждая галочка в конфиге".

## PKCE — механика защиты, не просто "рекомендуемая практика"

Полный sequence PKCE был показан в статье 01; здесь — что именно происходит математически и почему это защищает.

```txt
Шаг 1 (клиент, ЛОКАЛЬНО, никуда не отправляется):
  code_verifier = криптографически случайная строка, 43-128 символов
  Пример: "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

Шаг 2 (клиент вычисляет и ОТПРАВЛЯЕТ производное значение):
  code_challenge = BASE64URL(SHA256(code_verifier))
  code_challenge_method = "S256"

Шаг 3 (клиент отправляет code_challenge на /authorize):
  GET /authorize?...&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
                    &code_challenge_method=S256
  Keycloak ЗАПОМИНАЕТ code_challenge вместе с выданным authorization code

Шаг 4 (клиент обменивает code на токены, отправляя ОРИГИНАЛ):
  POST /token
    grant_type=authorization_code
    &code=<authorization code>
    &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

Шаг 5 (Keycloak проверяет):
  SHA256(code_verifier из шага 4) == code_challenge из шага 3 ?
  Совпадает → выдать токены
  Не совпадает → отклонить, 400 invalid_grant
```

Почему это защищает конкретно от **authorization code interception**: если атакующий каким-то образом перехватывает `code` (например, через логи прокси, вредоносное приложение на устройстве, зарегистрированное на тот же custom URL scheme, или через утечку в системе аналитики, логирующей полный URL редиректа) — он получает ОДНОЗНАЧНО бесполезное значение без `code_verifier`. `code_verifier` **никогда не передаётся по сети до шага 4** и хранится только в памяти легитимного клиента (для SPA — обычно в `sessionStorage` на время флоу, между шагом 2 и шагом 4). Атакующий физически не может вычислить `code_verifier` из `code_challenge`, потому что SHA256 — однонаправленная функция: обратное вычисление криптографически неосуществимо.

**Почему PKCE важен даже для confidential-клиентов** (частый вопрос на собеседовании, уже поднятый в статье 01, здесь — с механикой): confidential-клиент защищён `client_secret` от того, чтобы КТО-ТО ДРУГОЙ выдавал себя за него на шаге обмена code→token. Но `client_secret` не защищает от сценария, где атакующий перехватил `code`, предназначенный ИМЕННО ЭТОМУ клиенту, и пытается обменять его через ТОТ ЖЕ самый confidential-клиент раньше легитимного пользователя (race condition на интерцепции code, до того как легитимный запрос успеет пройти). PKCE закрывает именно этот сценарий независимо от типа клиента — поэтому современный OAuth 2.0 Security Best Current Practice рекомендует PKCE как обязательный для ВСЕХ типов клиентов, а не только для public.

## state vs nonce — два параметра, которые защищают от разных атак

Оба параметра — случайные строки, генерируемые клиентом и отправляемые в запросе на `/authorize`, оба возвращаются обратно клиенту — и именно из-за этого сходства их путают. Защищают они от принципиально разных атак.

```txt
state — CSRF/replay-защита самого РЕДИРЕКТА:

  Атака без state: атакующий инициирует СВОЙ СОБСТВЕННЫЙ логин-флоу
  на легитимном Keycloak (например, логинится в свой собственный,
  подконтрольный ему аккаунт), получает валидный authorization code
  на СВОЙ redirect, и подсовывает жертве ССЫЛКУ на callback-URL
  приложения с ЭТИМ code (например, через фишинговое письмо).
  Если жертва по ней перейдёт, а приложение не проверяет соответствие
  state — оно может СВЯЗАТЬ сессию жертвы с аккаунтом атакующего
  (Login CSRF — жертва оказывается залогинена КАК атакующий, что
  может привести к тому, что жертва введёт свои чувствительные данные
  в аккаунт, контролируемый атакующим).

  Защита: клиент генерирует случайный state ПЕРЕД редиректом на
  /authorize, сохраняет его локально (sessionStorage), передаёт в
  запросе, и на callback ПРОВЕРЯЕТ, что вернувшийся state совпадает
  с сохранённым. Chuжой authorization code, полученный не в рамках
  ЭТОЙ конкретной локальной сессии клиента, не пройдёт эту проверку.

nonce — replay-защита ID Token'а:

  Атака без nonce: атакующий, получивший (например, через логи
  или скомпрометированный канал) ранее выданный, ещё не истёкший
  ID Token легитимного пользователя, повторно предъявляет его
  клиентскому приложению как "результат нового логина".

  Защита: клиент генерирует случайный nonce перед редиректом,
  Keycloak встраивает его В САМ ID Token как claim (`nonce: <значение>`)
  при выдаче. Клиент, получив ID Token, сверяет claim `nonce` внутри
  токена с тем, что сам сгенерировал для ЭТОЙ конкретной попытки
  логина. Повторно предъявленный старый ID Token будет содержать
  СТАРЫЙ nonce, не совпадающий с новым, сгенерированным для текущей
  попытки — клиент отклонит его как невалидный для текущей сессии.
```

Мнемоника, которая реально разделяет эти два: **`state` защищает транспорт (сам redirect-обмен между клиентом и Keycloak на уровне HTTP)**, **`nonce` защищает содержимое (сам ID Token, чтобы его нельзя было повторно использовать в отрыве от конкретной попытки логина)**. В OIDC-флоу оба параметра используются ОДНОВРЕМЕННО и не заменяют друг друга — `keycloak-js`/`oidc-client-ts` генерируют и проверяют оба автоматически, но знание МЕХАНИЗМА важно для того, чтобы понимать, что именно ломается, если библиотека настроена неправильно (например, кастомная реализация OIDC-клиента, пропустившая проверку nonce).

## Строгая валидация redirect_uri — как слабая проверка превращается в кражу токена

`redirect_uri` — это URL, куда Keycloak отправит браузер пользователя с authorization code после успешного логина. Если Keycloak (или сам клиент) валидирует этот параметр НЕТОЧНО, это открывает прямой путь к краже кода/токена.

```txt
Слабая валидация (частая ошибка конфигурации):
  Зарегистрированный redirect_uri в Keycloak: "https://app.example.com/*"
  (wildcard паттерн, разрешённый некоторыми старыми/неаккуратными
  конфигурациями "для удобства")

  Атака: если на app.example.com есть ЛЮБАЯ open-redirect-уязвимость
  (например, /some-legit-path?next=https://evil.com, который делает
  редирект на next без проверки домена) — атакующий конструирует
  authorization request с redirect_uri=https://app.example.com/some-
  legit-path?next=https://evil.com, что технически совпадает с
  wildcard-паттерном. Пользователь логинится (форма Keycloak выглядит
  абсолютно нормально — домен ведь настоящий!), Keycloak редиректит
  на разрешённый redirect_uri, тот, в свою очередь, делает open-redirect
  на evil.com — И ПЕРЕДАЁТ ЕМУ authorization code через query string
  того же редиректа.

Правильная валидация:
  Зарегистрированный redirect_uri: ТОЧНОЕ совпадение,
  "https://app.example.com/callback" — без wildcard, без query-параметров
  сверху, посимвольное сравнение. OAuth 2.0 Security Best Current
  Practice явно требует exact string matching, а не префиксное или
  паттерн-совпадение.
```

Практическое следствие для конфигурации Keycloak: **никогда не используйте wildcard-паттерны в Valid Redirect URIs клиента "для удобства разработки"**, даже временно — это одна из тех настроек, которую забывают убрать перед продом, и одна из самых частых находок в реальных security-аудитах OAuth2-интеграций.

## JWT Algorithm Confusion — классическая ловушка на собеседовании

Это атака на саму библиотеку валидации JWT, а не на Keycloak напрямую — но она напрямую касается кода, который вы пишете в NestJS Resource Server'е (статья 04), поэтому знание механики обязательно.

```txt
Атака "alg: none":

  JWT header технически МОЖЕТ содержать { "alg": "none" } — токен
  без подписи вообще (валидный по спецификации JWT как формат, хоть
  и бессмысленный для аутентификации). Атакующий берёт ЛЮБОЙ валидный
  токен, меняет payload как хочет (например, "role": "admin"),
  меняет header на { "alg": "none" }, убирает signature-часть.

  Уязвимая библиотека: если код валидации ДОВЕРЯЕТ `alg` из HEADER
  самого токена (то есть спрашивает у токена, каким алгоритмом его
  проверять), она честно "проверит" подпись по алгоритму "none"
  (пустая проверка) и примет токен.

  Защита: НИКОГДА не давать библиотеке валидации решать алгоритм
  на основе значения из токена — algorithms ДОЛЖЕН быть явно
  захардкожен в конфиге на стороне Resource Server'а:

    algorithms: ['RS256']   // жёстко, не "что скажет токен"

  (см. пример KeycloakJwtStrategy в статье 03/04 — там algorithms
  уже передан явно именно по этой причине)

Атака RS256/HS256 key confusion:

  Keycloak по умолчанию подписывает RS256 (асимметрично: приватный
  ключ у Keycloak, публичный — у всех остальных через JWKS). HS256 —
  симметричный алгоритм, где ОДИН И ТОТ ЖЕ секрет используется и для
  подписи, и для верификации.

  Атака: если библиотека валидации НЕ проверяет строго, что `alg` в
  полученном токене совпадает с ОЖИДАЕМЫМ алгоритмом (RS256), а вместо
  этого "подстраивается" под `alg`, заявленный в токене — атакующий
  меняет header на { "alg": "HS256" }, и подписывает токен HMAC'ом,
  используя ПУБЛИЧНЫЙ RSA-ключ Keycloak (который открыто доступен
  через JWKS-эндпоинт!) КАК СЕКРЕТ для HMAC. Уязвимая библиотека,
  видя `alg: HS256`, берёт "ключ для HS256" — и если код неаккуратно
  передаёт туда тот же самый публичный ключ, который используется
  для RS256-верификации — проверка ПРОЙДЕТ, потому что HMAC(payload,
  публичный_RSA_ключ_как_секрет) действительно совпадёт с подписью,
  которую вычислил атакующий, ЗНАЯ этот публичный ключ.

  Защита: та же, что и выше — algorithms: ['RS256'] захардкожен,
  библиотека физически не пытается интерпретировать токен как HS256
  ни при каких условиях. Современные проверенные библиотеки
  (jose, jsonwebtoken 9+, passport-jwt с явным algorithms) закрывают
  этот вектор по умолчанию при правильной конфигурации — но именно
  ПРАВИЛЬНАЯ конфигурация (явный algorithms, не полагаться на дефолт
  библиотеки) — ответственность разработчика.
```

Это классический "интервью-трюк" именно потому, что звучит эзотерично, но сводится к одному практическому правилу, которое легко проверить в коде: **алгоритм проверки задаётся конфигурацией Resource Server'а, а не значением из самого токена** — если в код-ревью встречается JWT-валидация без явного списка разрешённых алгоритмов, это красный флаг независимо от того, какая библиотека используется.

## Refresh Token Rotation с Reuse Detection — полный разбор

В статье 03 rotation была упомянута как политика, здесь — почему это именно механизм ОБНАРУЖЕНИЯ атаки, не просто гигиена.

```txt
Нормальный сценарий (без атаки):

  Клиент держит refresh_token_1
  → обменивает на access_token_2 + refresh_token_2 (Keycloak
    ОТЗЫВАЕТ refresh_token_1 в момент выдачи refresh_token_2)
  → позже обменивает refresh_token_2 на refresh_token_3
  → и так далее, каждый обмен инвалидирует предыдущий токен

Сценарий кражи (refresh token скомпрометирован, например, через
XSS до того, как приложение успело им воспользоваться):

  Атакующий украл refresh_token_1 (например, из sessionStorage
  через XSS, ДО того как легитимное приложение успело обменять его)

  Случай A — атакующий использует ПЕРВЫМ:
    Атакующий → обменивает refresh_token_1 на refresh_token_2
    Легитимное приложение позже пытается обменять СВОЙ (уже
    отозванный!) refresh_token_1 → Keycloak ОТКАЗЫВАЕТ, потому что
    refresh_token_1 уже был использован (и, следовательно, отозван)
    → приложение видит invalid_grant там, где не ожидало —
    ЭТО СИГНАЛ КОМПРОМЕТАЦИИ, который стоит трактовать не как
    "истекшая сессия", а как потенциальную кражу

  Случай B — легитимное приложение использует первым:
    Приложение → обменивает refresh_token_1 на refresh_token_2 первым
    Атакующий позже пытается использовать УЖЕ ОТОЗВАННЫЙ
    refresh_token_1 → Keycloak видит попытку ПОВТОРНОГО использования
    токена, который уже был "потрачен" (использован для обмена) —
    это явный сигнал, что кто-то ДРУГОЙ, помимо легитимного клиента,
    владеет копией этого токена
```

Правильная реакция на обнаружение reuse — не просто отклонить конкретный запрос, а **отозвать ВСЮ цепочку токенов, связанных с этой сессией** (Keycloak поддерживает это как часть refresh token rotation policy), заставляя легитимного пользователя пройти полный релогин — потому что на этом этапе невозможно достоверно отличить, какая из двух копий токена (у атакующего или у легитимного пользователя) "правильная". Именно это превращает rotation из "просто более свежие токены" в реальный **breach-detection механизм**: без rotation украденный refresh token оставался бы незаметно валиден до истечения TTL, никак не сигнализируя о своей компрометации.

## Brute-force detection в Keycloak — встроенная защита, которую нужно включить осознанно

Keycloak имеет встроенный механизм защиты от подбора пароля (Realm Settings → Security Defenses → Brute Force Detection), который стоит настраивать явно, а не полагаться на дефолты без проверки:

```txt
Ключевые параметры:
  Max Login Failures       — сколько неудачных попыток до временной
                              блокировки аккаунта (типично: 5-10)
  Wait Increment            — на сколько увеличивается время блокировки
                              с каждой последующей серией неудач
                              (прогрессивная задержка, а не фиксированная)
  Max Wait                  — потолок времени блокировки
  Quick Login Check Millis  — минимальный интервал между попытками,
                              ниже которого попытки считаются
                              "слишком быстрыми" (защита от скриптовых
                              атак, делающих сотни попыток в секунду)
  Permanent Lockout         — блокировать аккаунт НАВСЕГДА (до ручной
                              разблокировки админом) после превышения
                              потолка попыток, вместо временной задержки
```

Практический нюанс: слишком агрессивные настройки (низкий `Max Login Failures`, включённый `Permanent Lockout`) создают вектор для **denial-of-service через чужие учётные записи** — атакующий, зная только email жертвы (без пароля), может намеренно ввести неправильный пароль нужное число раз и заблокировать легитимному пользователю доступ к его же аккаунту. Баланс между защитой от подбора пароля и защитой от этого вторичного DoS-вектора — осознанное решение, а не "чем строже, тем лучше".

## Clickjacking-защита конкретно для страницы логина

Страница логина Keycloak — особенно чувствительная цель для clickjacking: если атакующий встраивает её в невидимый `<iframe>` на своей странице поверх, например, кнопки "Играть в игру", и накладывает свой UI визуально поверх формы логина (прозрачный слой) — пользователь может ввести реальные учётные данные, думая, что взаимодействует с чем-то другим, а данные при этом уходят через форму, физически принадлежащую Keycloak, но встроенную атакующим в свой контекст.

```txt
Keycloak-настройка (Realm Settings → Security Defenses → Headers):
  X-Frame-Options: SAMEORIGIN   (устаревший, но всё ещё поддерживаемый
                                  заголовок; ограничивает встраивание
                                  в iframe только тем же origin'ом)
  Content-Security-Policy:
    frame-ancestors 'self' https://app.example.com;
    (современный, более гибкий механизм — явный whitelist доменов,
     которым разрешено встраивать страницу Keycloak в iframe;
     ВАЖНО: не 'none' безоговорочно, потому что silent-check-sso
     из статьи 05 САМ является легитимным iframe-встраиванием
     страницы Keycloak с домена приложения — 'none' сломает эту
     механику; должен быть точный whitelist собственных доменов
     приложения, а не полный запрет)
```

Ключевая тонкость именно для этой темы: **страница логина Keycloak — единственная страница в системе, которую МОЖЕТ легитимно потребоваться встраивать в iframe** (silent-check-sso), в отличие от большинства других страниц приложения, где `frame-ancestors 'none'` было бы правильным дефолтом. Настройка должна разрешать iframe-встраивание ТОЛЬКО с доверенных доменов ваших собственных клиентов — широкий whitelist здесь так же опасен, как и его отсутствие.

## CORS — специфика именно для auth-эндпоинтов

Общая механика CORS разобрана в теме [Security]; здесь — конкретные ловушки применительно к Keycloak-эндпоинтам.

```txt
Web Origins в настройках Keycloak-клиента:
  Это НЕ то же самое, что Valid Redirect URIs. Web Origins определяет,
  каким origin'ам разрешено делать CORS-запросы (fetch/XHR) НАПРЯМУЮ
  к Keycloak-эндпоинтам (например, /userinfo, /token из браузера) —
  а не то, куда можно редиректить браузер.

  Частая ошибка конфигурации: настроить Valid Redirect URIs правильно,
  но забыть Web Origins — тогда браузерный fetch-запрос к /userinfo
  или /token будет заблокирован CORS policy Keycloak, хотя сам
  редирект-based флоу логина будет работать нормально (редирект не
  подчиняется CORS, а fetch/XHR — подчиняется). Это разные механизмы
  защиты одного и того же клиента, и путаница между ними — источник
  специфичного для Keycloak "работает логин, но не работает
  userinfo-запрос из фронтенда" бага.

CORS на стороне вашего Resource Server (NestJS):
  Access-Control-Allow-Origin должен явно перечислять origin'ы
  React-приложения (и BFF, если используется, статья 06) —
  НИКОГДА wildcard '*' в сочетании с Authorization-заголовком
  (браузеры и так не позволят credentials с wildcard origin, но
  сам факт попытки так настроить указывает на непонимание модели).
  Особое внимание — если API обслуживает несколько SPA-клиентов
  разных доменов (multi-tenant frontend) — Origin должен явно
  сверяться со списком РАЗРЕШЁННЫХ доменов, а не отражаться
  бездумно (`Access-Control-Allow-Origin: <req.headers.origin>`
  без проверки против whitelist — это функционально эквивалентно
  wildcard'у, просто не выглядит им при поверхностном код-ревью).
```

## Типичные ошибки на интервью

- **"PKCE нужен только public-клиентам, у которых нет client secret"** — неполный ответ (уже разобрано в статье 01, здесь стоит уметь объяснить МЕХАНИЗМ): PKCE защищает от authorization code interception независимо от наличия секрета — race condition на перехваченном code возможен и для confidential-клиента.

- **"state и nonce — это одно и то же, просто OAuth2 и OIDC придумали разные имена для одной защиты"** — нет: `state` защищает сам редирект-обмен от CSRF/replay, `nonce` защищает конкретно содержимое ID Token от повторного использования. Оба нужны одновременно, они не взаимозаменяемы.

- **"Раз redirect_uri зарегистрирован в Keycloak, дальше можно не думать о его безопасности"** — нет: если зарегистрированный паттерн — wildcard или слишком широкий префикс, а на самом домене приложения есть open-redirect-уязвимость, это превращается в канал кражи authorization code, несмотря на "формально зарегистрированный" redirect_uri.

- **"Библиотека валидации JWT сама разберётся, каким алгоритмом проверять подпись, судя по токену"** — это ровно уязвимая конфигурация algorithm confusion атаки. Правильный ответ: алгоритм всегда явно захардкожен в конфигурации Resource Server'а (`algorithms: ['RS256']`), никогда не выводится из значения `alg` в самом токене.

- **"Refresh token rotation — это просто более частая замена токенов ради гигиены"** — неполно: главная ценность rotation — это возможность ОБНАРУЖИТЬ кражу токена через факт его повторного использования (reuse detection), что позволяет отреагировать (отозвать всю цепочку), а не просто "поддерживать токены свежими".
