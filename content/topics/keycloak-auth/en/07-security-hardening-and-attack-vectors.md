# Security Hardening — attacks and defenses specific to auth flows

## Why a dedicated security article, when this was already mentioned

Articles 01-06 mentioned defense mechanisms (PKCE, TTLs, rotation) as needed, but without a full treatment of the specific attack each one closes off. The general mechanics of XSS/CSRF/CORS are already covered in the [Security] topic — the focus here is narrow and applied: what exactly happens without PKCE; what exactly breaks with loose `redirect_uri` validation; how a JWT algorithm confusion attack physically works. This is the level that separates "I configured Keycloak following a guide" from "I can walk an attacker's scenario through every checkbox in the config that defends against it."

## PKCE — the mechanics of the defense, not just "recommended practice"

The full PKCE sequence was shown in article 01; here's exactly what happens mathematically, and why it defends against interception.

```txt
Step 1 (client, LOCALLY, never sent anywhere):
  code_verifier = a cryptographically random string, 43-128 characters
  Example: "dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk"

Step 2 (the client computes and SENDS a derived value):
  code_challenge = BASE64URL(SHA256(code_verifier))
  code_challenge_method = "S256"

Step 3 (the client sends code_challenge to /authorize):
  GET /authorize?...&code_challenge=E9Melhoa2OwvFrEMTJguCHaoeK1t8URWbuGJSstw-cM
                    &code_challenge_method=S256
  Keycloak REMEMBERS the code_challenge alongside the issued authorization code

Step 4 (the client exchanges the code for tokens, sending the ORIGINAL):
  POST /token
    grant_type=authorization_code
    &code=<authorization code>
    &code_verifier=dBjftJeZ4CVP-mB92K27uhbUJU1p1r_wW1gFWFOEjXk

Step 5 (Keycloak checks):
  SHA256(code_verifier from step 4) == code_challenge from step 3 ?
  Match → issue tokens
  No match → reject, 400 invalid_grant
```

Why this specifically defends against **authorization code interception**: if an attacker somehow intercepts the `code` (say, via proxy logs, a malicious app on the device registered on the same custom URL scheme, or a leak in an analytics system that logs the full redirect URL) — they get an unambiguously useless value with no `code_verifier`. The `code_verifier` **never travels over the network before step 4** and lives only in the legitimate client's memory (for an SPA, typically in `sessionStorage` for the duration of the flow, between step 2 and step 4). The attacker can't physically compute the `code_verifier` from the `code_challenge`, because SHA256 is a one-way function: reversing it is cryptographically infeasible.

**Why PKCE matters even for confidential clients** (a common interview question, already raised in article 01 — here's the mechanics): a confidential client is protected by `client_secret` against SOMEONE ELSE impersonating it at the code→token exchange step. But `client_secret` doesn't protect against a scenario where an attacker intercepted a `code` meant for THIS SPECIFIC client and tries to exchange it through the SAME confidential client before the legitimate user does (a race condition on the intercepted code, ahead of the legitimate request). PKCE closes exactly this scenario regardless of client type — which is why the modern OAuth 2.0 Security Best Current Practice recommends PKCE as mandatory for ALL client types, not just public ones.

## state vs nonce — two parameters defending against two different attacks

Both parameters are random strings, generated by the client and sent in the `/authorize` request, both come back to the client — and it's exactly this similarity that gets them confused. They defend against fundamentally different attacks.

```txt
state — CSRF/replay protection for the REDIRECT itself:

  The attack without state: an attacker initiates THEIR OWN login
  flow against the legitimate Keycloak (say, logging into their own
  account they control), gets a valid authorization code on THEIR
  redirect, and hands the victim a LINK to the app's callback URL
  carrying THAT code (via a phishing email, say). If the victim
  follows it, and the app doesn't verify that state matches, the
  app can end up LINKING the victim's session to the attacker's
  account (Login CSRF — the victim ends up logged in AS the
  attacker, which can lead to the victim entering sensitive data
  into an account the attacker controls).

  Defense: the client generates a random state BEFORE redirecting to
  /authorize, stores it locally (sessionStorage), sends it in the
  request, and on the callback VERIFIES that the returned state
  matches the stored one. Someone else's authorization code, obtained
  outside THIS specific local client session, won't pass this check.

nonce — replay protection for the ID Token:

  The attack without nonce: an attacker who obtained (say, via logs
  or a compromised channel) a legitimate user's previously-issued,
  not-yet-expired ID Token, re-presents it to the client app as "the
  result of a new login."

  Defense: the client generates a random nonce before redirecting,
  Keycloak embeds it INSIDE the ID Token itself as a claim
  (`nonce: <value>`) when issuing it. The client, on receiving the
  ID Token, checks the `nonce` claim inside the token against what
  it itself generated for THIS SPECIFIC login attempt. A re-presented
  old ID Token will carry the OLD nonce, which won't match the new
  one generated for the current attempt — the client rejects it as
  invalid for the current session.
```

A mnemonic that actually separates the two: **`state` protects the transport (the redirect exchange itself, between the client and Keycloak, at the HTTP level)**, **`nonce` protects the content (the ID Token itself, so it can't be reused outside a specific login attempt)**. In an OIDC flow both parameters are used SIMULTANEOUSLY and don't substitute for each other — `keycloak-js`/`oidc-client-ts` generate and verify both automatically, but knowing the MECHANISM matters for understanding exactly what breaks if a library is misconfigured (say, a custom OIDC client implementation that skipped the nonce check).

## Strict redirect_uri validation — how loose matching turns into token theft

`redirect_uri` is the URL Keycloak sends the user's browser to, carrying an authorization code, after a successful login. If Keycloak (or the client itself) validates this parameter loosely, it opens a direct path to code/token theft.

```txt
Loose validation (a common configuration mistake):
  Registered redirect_uri in Keycloak: "https://app.example.com/*"
  (a wildcard pattern, allowed by some old/careless configs
  "for convenience")

  The attack: if app.example.com has ANY open-redirect vulnerability
  anywhere (e.g. /some-legit-path?next=https://evil.com that redirects
  to next with no domain check) — an attacker crafts an authorization
  request with redirect_uri=https://app.example.com/some-legit-path?
  next=https://evil.com, which technically matches the wildcard
  pattern. The user logs in (Keycloak's form looks completely normal
  — the domain really is the real one!), Keycloak redirects to the
  allowed redirect_uri, which in turn does an open redirect to
  evil.com — CARRYING the authorization code with it through the
  same redirect's query string.

Correct validation:
  Registered redirect_uri: an EXACT match,
  "https://app.example.com/callback" — no wildcard, no extra query
  parameters on top, character-for-character comparison. The OAuth
  2.0 Security Best Current Practice explicitly requires exact
  string matching, not prefix or pattern matching.
```

The practical consequence for Keycloak configuration: **never use wildcard patterns in a client's Valid Redirect URIs "for dev convenience,"** not even temporarily — this is one of those settings that gets forgotten before going to prod, and one of the most common findings in real security audits of OAuth2 integrations.

## JWT Algorithm Confusion — a classic interview trap

This is an attack on the JWT validation library itself, not on Keycloak directly — but it directly concerns the code you write in the NestJS Resource Server (article 04), so knowing the mechanics is mandatory.

```txt
The "alg: none" attack:

  A JWT header CAN technically contain { "alg": "none" } — a token
  with no signature at all (valid per the JWT spec as a format, even
  though meaningless as authentication). An attacker takes ANY valid
  token, changes the payload however they like (say, "role": "admin"),
  changes the header to { "alg": "none" }, drops the signature part.

  A vulnerable library: if the validation code TRUSTS the `alg` from
  the token's OWN HEADER (i.e. asks the token which algorithm to
  verify it with), it will honestly "verify" the signature against
  "none" (an empty check) and accept the token.

  Defense: NEVER let the validation library decide the algorithm
  based on a value inside the token — algorithms MUST be explicitly
  hardcoded in the Resource Server's config:

    algorithms: ['RS256']   // fixed, not "whatever the token says"

  (see the KeycloakJwtStrategy example in articles 03/04 — algorithms
  is already passed explicitly for exactly this reason)

The RS256/HS256 key confusion attack:

  Keycloak signs with RS256 by default (asymmetric: Keycloak holds
  the private key, everyone else has the public key via JWKS). HS256
  is a symmetric algorithm, where the SAME secret is used both to
  sign and to verify.

  The attack: if the validation library does NOT strictly check that
  the `alg` in the received token matches the EXPECTED algorithm
  (RS256), and instead "adapts" to whatever `alg` the token claims —
  an attacker changes the header to { "alg": "HS256" }, and signs the
  token with HMAC, using Keycloak's PUBLIC RSA key (openly available
  via the JWKS endpoint!) AS THE HMAC SECRET. A vulnerable library,
  seeing `alg: HS256`, grabs "the key for HS256" — and if the code
  carelessly passes in the same public key used for RS256
  verification — the check WILL PASS, because HMAC(payload,
  public_RSA_key_as_secret) genuinely matches the signature the
  attacker computed, KNOWING that public key.

  Defense: the same as above — algorithms: ['RS256'] hardcoded, the
  library never attempts to interpret the token as HS256 under any
  circumstances. Modern, well-vetted libraries (jose, jsonwebtoken 9+,
  passport-jwt with explicit algorithms) close this vector by default
  when configured correctly — but CORRECT configuration (an explicit
  algorithms list, not relying on the library's default) is the
  developer's responsibility.
```

This is a classic "interview gotcha" exactly because it sounds esoteric but boils down to one practical rule, easy to check in code review: **the verification algorithm is set by the Resource Server's configuration, not by a value from the token itself** — if a code review turns up JWT validation with no explicit list of allowed algorithms, that's a red flag regardless of which library is being used.

## Refresh Token Rotation with Reuse Detection — the full picture

Article 03 mentioned rotation as a policy; here's why it's specifically a DETECTION mechanism, not just hygiene.

```txt
The normal scenario (no attack):

  The client holds refresh_token_1
  → exchanges it for access_token_2 + refresh_token_2 (Keycloak
    REVOKES refresh_token_1 the moment refresh_token_2 is issued)
  → later exchanges refresh_token_2 for refresh_token_3
  → and so on, each exchange invalidates the previous token

A theft scenario (the refresh token is compromised, say via XSS,
before the app has had a chance to use it):

  An attacker stole refresh_token_1 (say, from sessionStorage via
  XSS, BEFORE the legitimate app got to exchange it)

  Case A — the attacker uses it FIRST:
    The attacker → exchanges refresh_token_1 for refresh_token_2
    The legitimate app later tries to exchange ITS (already revoked!)
    refresh_token_1 → Keycloak REJECTS it, because refresh_token_1
    was already used (and thus revoked) → the app sees invalid_grant
    where it didn't expect it — THIS IS A COMPROMISE SIGNAL that
    should be treated as a potential theft, not just "an expired
    session"

  Case B — the legitimate app uses it first:
    The app → exchanges refresh_token_1 for refresh_token_2 first
    The attacker later tries to use the ALREADY REVOKED
    refresh_token_1 → Keycloak sees an attempt to REUSE a token that
    was already "spent" (used in an exchange) — a clear signal that
    someone OTHER than the legitimate client holds a copy of this
    token
```

The correct reaction to detecting reuse isn't just to reject that one request — it's to **revoke the ENTIRE chain of tokens tied to that session** (Keycloak supports this as part of its refresh token rotation policy), forcing the legitimate user through a full re-login — because at this point there's no reliable way to tell which of the two copies of the token (the attacker's or the legitimate user's) is "the right one." This is exactly what turns rotation from "just fresher tokens" into a real **breach-detection mechanism**: without rotation, a stolen refresh token would stay quietly valid until its TTL expired, with no signal of its compromise at all.

## Brute-force detection in Keycloak — a built-in defense that needs deliberate configuration

Keycloak has a built-in password-guessing defense (Realm Settings → Security Defenses → Brute Force Detection) that's worth configuring explicitly, rather than relying on unchecked defaults:

```txt
Key parameters:
  Max Login Failures       — how many failed attempts before a
                              temporary account lockout (typically:
                              5-10)
  Wait Increment            — how much lockout time increases with
                              each subsequent burst of failures
                              (progressive delay, not fixed)
  Max Wait                  — the ceiling on lockout time
  Quick Login Check Millis  — the minimum interval between attempts,
                              below which attempts are considered
                              "too fast" (a defense against scripted
                              attacks making hundreds of attempts per
                              second)
  Permanent Lockout         — lock the account PERMANENTLY (until an
                              admin manually unlocks it) once the
                              attempt ceiling is exceeded, instead of
                              a temporary delay
```

A practical nuance: settings that are too aggressive (a low `Max Login Failures`, `Permanent Lockout` enabled) create a vector for **denial-of-service against other people's accounts** — an attacker who only knows the victim's email (no password) can deliberately enter a wrong password the required number of times and lock the legitimate user out of their own account. Balancing password-guessing defense against this secondary DoS vector is a deliberate decision, not "stricter is always better."

## Clickjacking protection specifically for the login page

Keycloak's login page is a particularly sensitive clickjacking target: if an attacker embeds it in an invisible `<iframe>` on their own page, laid underneath something like a "Play the game" button, and overlays their own UI visually on top of the login form (a transparent layer) — a user could type in real credentials thinking they're interacting with something else, while the data actually travels through a form that physically belongs to Keycloak, just embedded by the attacker in their own context.

```txt
Keycloak configuration (Realm Settings → Security Defenses → Headers):
  X-Frame-Options: SAMEORIGIN   (a legacy but still-honored header;
                                  restricts iframe embedding to the
                                  same origin only)
  Content-Security-Policy:
    frame-ancestors 'self' https://app.example.com;
    (the modern, more flexible mechanism — an explicit whitelist of
     domains allowed to embed the Keycloak page in an iframe;
     IMPORTANT: not an unconditional 'none', because silent-check-sso
     from article 05 IS ITSELF a legitimate iframe embedding of the
     Keycloak page from the app's domain — 'none' would break that
     mechanism; you need a precise whitelist of your own app's
     domains, not a blanket ban)
```

The key subtlety specific to this topic: **Keycloak's login page is the one page in the system that MIGHT legitimately need to be embedded in an iframe** (silent-check-sso), unlike most other pages in the app, where `frame-ancestors 'none'` would be the right default. The configuration should allow iframe embedding ONLY from your own clients' trusted domains — a broad whitelist here is just as dangerous as having none at all.

## CORS — the specifics for auth endpoints

The general mechanics of CORS are covered in the [Security] topic; here are the concrete gotchas specific to Keycloak endpoints.

```txt
Web Origins in a Keycloak client's settings:
  This is NOT the same thing as Valid Redirect URIs. Web Origins
  defines which origins are allowed to make CORS requests
  (fetch/XHR) DIRECTLY to Keycloak endpoints (e.g. /userinfo, /token
  from the browser) — not where the browser is allowed to be
  redirected to.

  A common configuration mistake: setting up Valid Redirect URIs
  correctly but forgetting Web Origins — then a browser fetch call
  to /userinfo or /token gets blocked by Keycloak's CORS policy,
  even though the redirect-based login flow works fine (a redirect
  isn't subject to CORS, but fetch/XHR is). These are two different
  defense mechanisms for the same client, and confusing them is a
  Keycloak-specific source of "login works but the frontend's
  userinfo call doesn't" bugs.

CORS on your Resource Server (NestJS):
  Access-Control-Allow-Origin should explicitly list the React app's
  origins (and the BFF's, if used, article 06) — NEVER a wildcard
  '*' alongside an Authorization header (browsers won't even allow
  credentials with a wildcard origin, but attempting to configure it
  that way still signals a misunderstanding of the model). Pay
  special attention if the API serves multiple SPA clients on
  different domains (a multi-tenant frontend) — the Origin should be
  explicitly checked against a list of ALLOWED domains, not reflected
  blindly (`Access-Control-Allow-Origin: <req.headers.origin>` with
  no whitelist check is functionally equivalent to a wildcard, it
  just doesn't look like one on a shallow code review).
```

## Common interview traps

- **"PKCE is only needed for public clients that don't have a client secret"** — an incomplete answer (already covered in article 01 — here you should be able to explain the MECHANISM): PKCE defends against authorization code interception regardless of whether a secret exists — a race condition on an intercepted code is possible for a confidential client too.

- **"state and nonce are the same thing, OAuth2 and OIDC just came up with different names for the same protection"** — no: `state` protects the redirect exchange itself from CSRF/replay, `nonce` specifically protects the ID Token's content from being reused. Both are needed simultaneously, they aren't interchangeable.

- **"Once redirect_uri is registered in Keycloak, you don't need to think about its security anymore"** — no: if the registered pattern is a wildcard or too broad a prefix, and the app's own domain has an open-redirect vulnerability anywhere, that turns into a channel for stealing the authorization code, despite the redirect_uri being "formally registered."

- **"A JWT validation library will figure out on its own which algorithm to verify the signature with, based on the token"** — that's exactly the vulnerable configuration for an algorithm confusion attack. The correct answer: the algorithm is always explicitly hardcoded in the Resource Server's config (`algorithms: ['RS256']`), never derived from the `alg` value inside the token itself.

- **"Refresh token rotation is just swapping tokens more often for hygiene"** — incomplete: rotation's main value is DETECTING token theft through the fact that it was reused (reuse detection), which lets you react (revoke the whole chain), not just "keep tokens fresh."
