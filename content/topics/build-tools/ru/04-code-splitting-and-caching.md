# Разделение кода и долгосрочное кеширование

## Две задачи, которые всегда решают вместе

Разделение кода отвечает на вопрос «как не отдавать пользователю то, что ему сейчас не нужно». Долгосрочное кеширование — на вопрос «как не отдавать повторно то, что у него уже есть». Разбирать их по отдельности бессмысленно: настраиваются они одними и теми же опциями, а неаккуратное разделение убивает кеш надёжнее, чем его отсутствие.

Обе задачи относятся исключительно к прод-сборке — в dev-режиме их не решают вообще (см. рамку в [Why Bundlers Exist]).

## `import()` — единственная точка разрыва графа

Статический `import` создаёт ребро **внутри** чанка: сборщик знает, что модуль нужен сразу, и кладёт его рядом. Динамический `import()` — единственная конструкция, которую сборщик трактует как **границу**: всё, что достижимо только через неё, уезжает в отдельный чанк.

```tsx
// src/App.tsx — разделение по маршрутам
import { lazy, Suspense } from 'react';
import { Routes, Route } from 'react-router-dom';

const Orders    = lazy(() => import('./routes/Orders'));
const Analytics = lazy(() => import('./routes/Analytics'));   // сюда уедет chart-lib
const Settings  = lazy(() => import('./routes/Settings'));

export function App() {
  return (
    <Suspense fallback={<PageSkeleton />}>
      <Routes>
        <Route path="/orders"    element={<Orders />} />
        <Route path="/analytics" element={<Analytics />} />
        <Route path="/settings"  element={<Settings />} />
      </Routes>
    </Suspense>
  );
}
```

```txt
                 ОДИН БАНДЛ                               РАЗБИЕНИЕ ПО МАРШРУТАМ
┌─────────────────────────────────────────┐    ┌──────────────────────────────────────────┐
│ что качает пользователь /orders         │    │ что качает пользователь /orders          │
│                                         │    │                                          │
│ main.js   620 КБ — весь код приложения, │    │ index.js       18 КБ — оболочка и роутер │
│           включая chart-lib и date-fns  │    │ vendor.js      140 КБ — react, react-dom │
│                                         │    │ orders.js      24 КБ — маршрут /orders   │
│ итого     620 КБ до первого рендера     │    │ analytics.js   430 КБ — НЕ скачивается   │
└─────────────────────────────────────────┘    │                                          │
        тот, кто никогда не откроет            │ итого          182 КБ до первого рендера │
    /analytics, всё равно за неё платит        └──────────────────────────────────────────┘
                                                     analytics.js приедет только при
                                                          переходе на /analytics
```

Три вещи, которые здесь стоит понимать точно:

- **Чанк создаёт только `import()`, а не «тяжесть» модуля.** Сборщик не умеет решать «эта библиотека большая, вынесу-ка её»: он режет граф ровно там, где вы поставили динамический импорт. `chart-lib` уехал в `analytics.js` не потому, что он большой, а потому, что достижим только через ленивый маршрут.
- **Условный статический импорт чанка не создаёт.** Конструкция `if (isAdmin) { import x from '...' }` в ESM невозможна, а `require()` внутри `if` не даёт границы: сборщик всё равно включит модуль (см. [The Module Graph and Resolution] про статичность ESM).
- **Модуль, достижимый из двух ленивых чанков, попадёт в оба.** Если `lib/api.ts` нужен и `Orders`, и `Analytics`, без общей группы он продублируется. Это именно то, что чинит `splitChunks`.

### Имя чанка

```tsx
// Webpack: magic comment — иначе чанк получит имя вида 247.a1b2c3.js
const Analytics = lazy(() => import(/* webpackChunkName: "analytics" */ './routes/Analytics'));
```

```ts
// Vite: имена задаются шаблоном в конфиге, magic comments не нужны
export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        chunkFileNames: 'assets/[name]-[hash].js',
      },
    },
  },
});
```

### Ловушка, которая ждёт в проде: чанк не загрузился

`import()` возвращает промис, а значит, может отклониться. Самый частый сценарий в реальной жизни: пользователь открыл вкладку, вы выкатили новый релиз со свежими хешами, старые файлы удалены с CDN — и переход по маршруту падает.

```txt
Webpack:  ChunkLoadError: Loading chunk 5 failed
Vite:     TypeError: Failed to fetch dynamically imported module
```

Лечится двумя вещами сразу: обработкой ошибки на стороне приложения (поймать, один раз попробовать снова, при повторной неудаче — перезагрузить страницу) и на стороне деплоя (не удалять ассеты предыдущих релизов сразу; хранить несколько версий). Кандидат, который сам вспоминает про этот сценарий, обычно вёл прод.

## Разделение по маршрутам: где проводить границу

Маршруты — самая естественная граница, потому что они совпадают с моментом, когда пользователь **психологически готов подождать**: переход по ссылке уже подразумевает паузу. Отсюда правило: дробить стоит там, где есть переход, и не стоит там, где пользователь просто прокручивает страницу.

Что имеет смысл выносить в ленивый чанк, кроме маршрутов:

- **Модальные окна и редакторы**, которые открывает меньшинство пользователей.
- **Тяжёлые библиотеки под конкретное действие**: экспорт в PDF, редактор кода, карта.
- **Административные разделы**, недоступные обычному пользователю.

Что выносить **не** стоит: всё, что видно на первом экране. Ленивая загрузка шапки или скелета страницы просто добавляет один лишний раунд запросов к критическому пути — ровно тот водопад, о котором шла речь в [Why Bundlers Exist].

## splitChunks: вендорные чанки и общий код

Разделение по `import()` решает только половину задачи. Вторая половина — вынести то, что нужно **всем** чанкам, чтобы не дублировать и чтобы кешировалось отдельно.

```js
// webpack.config.js — дефолты, о которых важно знать
module.exports = {
  optimization: {
    splitChunks: {
      chunks: 'async',          // ← ВАЖНО: по умолчанию трогаются только ленивые чанки
      minSize: 20000,
      minChunks: 1,
      maxAsyncRequests: 30,
      maxInitialRequests: 30,
      enforceSizeThreshold: 50000,
      cacheGroups: {
        defaultVendors: { test: /[\\/]node_modules[\\/]/, priority: -10, reuseExistingChunk: true },
        default:        { minChunks: 2, priority: -20, reuseExistingChunk: true },
      },
    },
  },
};
```

Первая строка — главный источник недоумения: **`chunks: 'async'` означает, что входной чанк не разбивается вообще**. То есть `react` и `react-dom`, попавшие в граф из `main.tsx`, по умолчанию останутся внутри входного чанка вместе с вашим кодом. Именно поэтому почти в любом реальном конфиге стоит `chunks: 'all'`.

Осмысленная настройка для `shop-admin` выглядит так:

```js
// webpack.config.js — группировка по частоте изменений, а не «всё в один vendor»
module.exports = {
  optimization: {
    runtimeChunk: 'single',
    splitChunks: {
      chunks: 'all',
      cacheGroups: {
        // меняется раз в год — отдельный чанк с долгой жизнью
        framework: {
          test: /[\\/]node_modules[\\/](react|react-dom|react-router)[\\/]/,
          name: 'framework',
          priority: 40,
        },
        // остальные зависимости — обновляются заметно чаще
        vendor: {
          test: /[\\/]node_modules[\\/]/,
          name: 'vendor',
          priority: 20,
        },
        // общий код приложения, нужный минимум двум чанкам
        common: {
          minChunks: 2,
          name: 'common',
          priority: 10,
          reuseExistingChunk: true,
        },
      },
    },
  },
};
```

Та же задача в Vite. Здесь важна свежая деталь: начиная с Vite 8, где бандлером стал Rolldown, объектная форма `output.manualChunks` больше не поддерживается, а функциональная помечена устаревшей. На смену пришёл `codeSplitting` с группами — структурно очень похожий на `cacheGroups` Webpack:

```ts
// vite.config.ts
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rolldownOptions: {
      output: {
        codeSplitting: {
          minSize: 20000,
          groups: [
            { name: 'framework', test: /node_modules[\\/](react|react-dom|react-router)/, priority: 40 },
            { name: 'vendor',    test: /node_modules/, priority: 20 },
            { name: 'common',    minShareCount: 2, minSize: 10000, priority: 10 },
          ],
        },
      },
    },
  },
});
```

Соответствие терминов читается почти построчно: `cacheGroups` ↔ `groups`, `minChunks` ↔ `minShareCount`, `priority` и `minSize` совпадают по имени. Это не совпадение: Rolldown осознанно перенял модель Webpack, потому что она оказалась удобнее плоского `manualChunks`. Поскольку это самая свежая часть экосистемы, точную форму опций стоит сверять с документацией Rolldown — она ещё уточняется.

**Главный антипаттерн этого раздела — один гигантский `vendor`.** Логика «сложим все зависимости в один чанк, он же кешируется» разбивается о простой факт: обновление любой из полусотни зависимостей меняет хеш всего чанка, и пользователь качает 400 КБ вместо 12. Правильный принцип группировки — **по частоте изменений**, а не по происхождению кода.

## Рантайм-чанк: маленький файл с большими последствиями

```txt
            Почему рантайм ломает кеш и зачем его выносить
┌────────────────────────────────────────────────────────────────────┐
│ сборка выдала index.[hash].js, vendor.[hash].js, orders.[hash].js  │
│                                 ↓                                  │
│ рантайму нужна таблица «id чанка → имя файла с хешем»              │
│                                 ↓                                  │
│ по умолчанию эта таблица лежит ВНУТРИ входного чанка               │
│                                 ↓                                  │
│ поменялся хеш ЛЮБОГО чанка → поменялась таблица → поменялся index  │
│                                 ↓                                  │
│ runtimeChunk: 'single' выносит таблицу в отдельный файл ~2 КБ      │
│                                 ↓                                  │
│ правка в orders меняет orders.js и runtime.js; index и vendor целы │
└────────────────────────────────────────────────────────────────────┘
           у Vite рантайм тоже выносится, но об этом обычно
           не думают: имена чанков там подставляются иначе
```

Рантайм — небольшой служебный код, который умеет загружать чанки по требованию и знает соответствие «идентификатор чанка → файл на диске». Пока эта таблица лежит внутри входного чанка, входной чанк меняется при **любом** изменении хешей — то есть практически при каждом релизе. Одна строка `runtimeChunk: 'single'` разрывает эту связь.

## Долгосрочное кеширование: contenthash и что его ломает

Схема простая: имя файла содержит хеш содержимого, а сервер отдаёт файл с максимально агрессивным заголовком.

```js
// webpack.config.js
output: {
  filename: '[name].[contenthash].js',        // входные чанки
  chunkFilename: '[name].[contenthash].js',   // ленивые чанки
}
```

```txt
Cache-Control: public, max-age=31536000, immutable
```

`immutable` означает «этот URL никогда не изменит содержимое» — браузер не станет даже проверять актуальность. Это безопасно ровно потому, что при изменении содержимого меняется имя, а значит, и URL. Только `index.html` кешировать нельзя: он и есть точка, из которой браузер узнаёт новые имена.

Три плейсхолдера легко перепутать, а разница существенная:

- `[hash]` — один хеш на всю сборку. Меняется что угодно — меняются имена всех файлов. Для кеша это худший вариант.
- `[chunkhash]` — хеш чанка, но считается до финальной обработки.
- `[contenthash]` — хеш содержимого конкретного ассета. Единственный правильный выбор, и именно он позволяет CSS-файлу не меняться, когда поменялся только JS.

```txt
                     Что перекачает пользователь после релиза
┌───────────────────────────┬────────────────────────────┬───────────────────────┐
│ что вы изменили           │ плохая настройка           │ хорошая настройка     │
├───────────────────────────┼────────────────────────────┼───────────────────────┤
│ одну строку в Orders.tsx  │ index + vendor + orders    │ orders + runtime      │
├───────────────────────────┼────────────────────────────┼───────────────────────┤
│ добавили новый модуль     │ index + vendor: съехали id │ index + runtime       │
├───────────────────────────┼────────────────────────────┼───────────────────────┤
│ обновили одну зависимость │ весь vendor целиком        │ чанк этой зависимости │
├───────────────────────────┼────────────────────────────┼───────────────────────┤
│ поменяли порядок импортов │ vendor: сдвинулся порядок  │ ничего                │
├───────────────────────────┼────────────────────────────┼───────────────────────┤
│ пересобрали без изменений │ всё: хеши нестабильны      │ ничего                │
└───────────────────────────┴────────────────────────────┴───────────────────────┘
             разница между колонками — это moduleIds: deterministic,
            вынесенный runtimeChunk и осмысленная группировка вендоров
```

### Почему «поменял одну строку — перекачался весь вендорный чанк»

Это классический вопрос на интервью, и у него три независимых причины.

**1. Нестабильные идентификаторы модулей.** Каждому модулю сборщик присваивает идентификатор, и этот идентификатор попадает в код других чанков (в местах, где модуль импортируется). Если идентификаторы выдаются по порядку обхода графа, то добавление одного файла в приложении сдвигает нумерацию — и содержимое вендорного чанка меняется, хотя ни одна зависимость не обновлялась.

Решение — детерминированные идентификаторы, зависящие только от самого модуля:

```js
optimization: {
  moduleIds: 'deterministic',
  chunkIds: 'deterministic',
}
```

В `mode: 'production'` это включено по умолчанию (см. таблицу дефолтов в [The Webpack Core Model]). Но в старых конфигах до сих пор встречаются `HashedModuleIdsPlugin` и `NamedModulesPlugin` — это способ решения той же задачи из эпохи Webpack 4. Первый помечен устаревшим, второй удалён; сегодня всё выражается опцией `optimization.moduleIds`.

**2. Рантайм внутри входного чанка** — разобрано выше.

**3. Хеш считается не от того.** Если хеш вычисляется до минификации, то любые изменения, которые минификатор всё равно съест (комментарии, имена переменных), всё равно меняют имя файла. За это отвечает `optimization.realContentHash: true`, включённый в проде по умолчанию: хеш берётся от **итогового** содержимого ассета.

У Vite `contenthash` в именах стоит из коробки, а плейсхолдеры настраиваются через `entryFileNames`, `chunkFileNames` и `assetFileNames` в `rolldownOptions.output`. Проблема нестабильных идентификаторов там проявляется реже, но группировка вендоров имеет ровно те же последствия.

## Подсказки браузеру: preload, prefetch, modulepreload

```txt
                     Подсказки браузеру: что просишь и чем платишь
┌───────────────┬────────────────────────────────────┬────────────────────────────────┐
│ подсказка     │ что делает браузер                 │ когда вредит                   │
├───────────────┼────────────────────────────────────┼────────────────────────────────┤
│ ничего        │ грузит в момент вызова import()    │ пауза при переходе по маршруту │
├───────────────┼────────────────────────────────────┼────────────────────────────────┤
│ prefetch      │ грузит в простое, приоритет низкий │ трафик на то, что не откроют   │
├───────────────┼────────────────────────────────────┼────────────────────────────────┤
│ modulepreload │ грузит сразу, приоритет высокий    │ конкурирует с критичным путём  │
├───────────────┼────────────────────────────────────┼────────────────────────────────┤
│ preload       │ грузит сразу, приоритет высший     │ вытесняет то, что нужно сейчас │
└───────────────┴────────────────────────────────────┴────────────────────────────────┘
            prefetch — про следующую навигацию, preload — про текущий экран;
             пометить prefetch все маршруты сразу = скачать всё приложение
```

```tsx
// Webpack: подсказки задаются magic comments прямо в import()
const Analytics = lazy(() => import(
  /* webpackChunkName: "analytics" */
  /* webpackPrefetch: true */          // «понадобится на следующей навигации»
  './routes/Analytics'
));
```

У Vite логика другая: `build.modulePreload` включён по умолчанию, и сборщик сам расставляет `<link rel="modulepreload">` для входного чанка и его прямых зависимостей. Смысл именно в водопаде: браузер узнаёт про зависимости второго уровня из HTML, а не после разбора первого файла. Дополнительно Vite подключает небольшой полифилл, потому что `modulepreload` поддерживается не везде.

Главная ошибка при работе с подсказками — считать их бесплатными. Полоса пропускания и очередь приоритетов конечны: помеченный `preload` ленивый маршрут конкурирует за них со шрифтом и CSS первого экрана. Практическое правило: `prefetch` — для одного-двух наиболее вероятных следующих переходов; `preload` — только для того, что нужно немедленно и о чём браузер не может узнать сам.

## Компромисс: много мелких чанков или мало крупных

```txt
                            Много мелких чанков или мало крупных
┌───────────────────┬─────────────────────────────────┬───────────────────────────────────┐
│ критерий          │ мало крупных                    │ много мелких                      │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ число запросов    │ мало                            │ много, но HTTP/2 мультиплексирует │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ глубина водопада  │ короткая                        │ риск цепочки зависимых загрузок   │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ попадание в кеш   │ низкое: правка бьёт по большому │ высокое: меняется один мелкий     │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ сжатие            │ лучше: общий словарь на файл    │ хуже: словарь на каждый файл      │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ накладные расходы │ минимальные                     │ запись в рантайме на каждый чанк  │
├───────────────────┼─────────────────────────────────┼───────────────────────────────────┤
│ когда выбирать    │ мало кода, редкие релизы        │ большое приложение, частые релизы │
└───────────────────┴─────────────────────────────────┴───────────────────────────────────┘
                 универсального числа чанков не существует: это выбор между
                  ценой первой загрузки и ценой каждого следующего релиза
```

Рецепта здесь нет — есть три вопроса, ответы на которые определяют выбор.

**Как часто вы релизите?** Если раз в квартал, кеш почти не работает: пользователь всё равно придёт с пустым. Если несколько раз в неделю, дробление окупается — большая часть ассетов при каждом релизе остаётся валидной.

**Какая доля кода нужна на первом экране?** Если 80% — дробить особо нечего, вы просто добавите раундов. Если 15% — разделение даёт основной выигрыш.

**Какая сеть у ваших пользователей?** На мобильной сети с высокой задержкой каждый дополнительный уровень водопада стоит сотни миллисекунд, и мелкие чанки, зависящие друг от друга, обходятся дороже, чем один средний.

Отдельный аргумент, о котором часто забывают, — **сжатие**. Gzip и Brotli строят словарь повторов в пределах одного файла. Десять файлов по 20 КБ сжимаются заметно хуже, чем один на 200 КБ, потому что каждый начинает со своего словаря. Поэтому очень мелкие чанки почти никогда не окупаются: не случайно `minSize` в Webpack по умолчанию равен 20 КБ, а Rolldown в примерах конфигурации использует то же значение.

Практический ориентир, а не догма: имеет смысл держать отдельно рантайм, фреймворк, остальные вендоры, общий код приложения и по чанку на крупный маршрут. Всё, что мельче нескольких десятков килобайт, разумнее вливать в соседа. Как проверить, что получилось, — методика анализа бандла в [Tree Shaking and Optimization].

## Типичные ошибки на интервью

- **«Code splitting — это когда webpack сам делит бандл на части»** — сам он делит только по правилам, которые вы задали. Точку разрыва графа создаёт исключительно `import()`; `splitChunks` перегруппировывает то, что уже есть, но не придумывает новые границы. Кандидат, который считает, что сборщик «сам вынесет тяжёлую библиотеку», не понимает механику.

- **Не знать, что `splitChunks.chunks` по умолчанию `'async'`.** Очень практичный вопрос: «почему я настроил `cacheGroups`, а `react` всё равно во входном чанке?» Ответ — потому что по умолчанию входные чанки не трогаются, нужен `chunks: 'all'`.

- **Один большой `vendor` «чтобы лучше кешировался»** — рассуждение, обратное истине. Чем крупнее чанк, тем выше вероятность, что очередной релиз его инвалидирует. Правильный принцип — группировать по частоте изменений: фреймворк отдельно от остальных зависимостей.

- **Не уметь объяснить, почему после правки одной строки перекачался вендорный чанк.** Это, пожалуй, главный вопрос темы. Полный ответ содержит три причины: идентификаторы модулей, рантайм внутри входного чанка и момент вычисления хеша. Ответ «нужно поставить contenthash» неполон — contenthash там уже стоял, иначе проблемы бы не заметили.

- **Путать `[hash]`, `[chunkhash]` и `[contenthash]`** — разница ровно в том, от чего считается значение, и именно она определяет, будет ли кеш работать.

- **«Prefetch лишним не бывает»** — бывает. Помеченные `prefetch` десять маршрутов означают, что приложение скачивается целиком, просто чуть позже. Сильный ответ формулирует это как выбор приоритета, а не как бесплатную оптимизацию.

- **«Чем больше чанков, тем лучше»** — тоже нет. Про сжатие (словарь на файл) и про водопад зависимых загрузок вспоминают редко, а это как раз то, что отличает заученный рецепт от понимания компромисса.

- **Не учитывать, что ленивый чанк может не загрузиться.** Вопрос «что увидит пользователь, если вы задеплоили новый релиз, пока у него открыта вкладка?» отлично отделяет тех, кто настраивал сборку в проде, от тех, кто читал про неё.
