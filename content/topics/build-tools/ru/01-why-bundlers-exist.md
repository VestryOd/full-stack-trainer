# Зачем существуют сборщики

## Одно предложение, из которого растёт весь топик

Сборщик берёт точку входа, обходит по ней граф импортов, преобразует каждый найденный файл и выдаёт набор готовых ассетов, которые браузер может скачать и выполнить. Всё остальное — лоадеры, плагины, чанки, хеши в именах — это детали того, как именно выполняются четыре глагола: *обойти*, *преобразовать*, *объединить*, *оптимизировать*.

Разбираться в сборщиках стоит не с конфига, а с вопроса «какую задачу этот конфиг закрывает». Иначе получается характерная картина: человек умеет скопировать рабочий `webpack.config.js`, но не может объяснить, почему после смены одной строки в коде пользователи перекачали два мегабайта вендорного кода.

## Три эпохи — как объяснение, а не как хронология

История здесь нужна ровно затем, чтобы показать: каждая следующая эпоха решала проблему предыдущей, и следы всех трёх до сих пор лежат в `node_modules`.

### Глобальные скрипты: порядок тегов вместо системы модулей

```html
<script src="/js/jquery.js"></script>
<script src="/js/utils.js"></script>
<script src="/js/app.js"></script>
```

Модулей нет — есть общий объект `window` и порядок подключения. Отсюда три хронические болячки:

- **Коллизии.** Две библиотеки объявляют `formatDate` — выигрывает та, что подключена последней. Ошибка проявится не в момент подключения, а через месяц в чужом коде.
- **Неявные зависимости.** То, что `app.js` не работает без `utils.js`, нигде не записано. Это знание живёт в голове и в порядке тегов.
- **Ручное управление порядком.** Переставили две строки в HTML — сломали приложение.

Частичное лекарство — IIFE-обёртка, которая прячет внутренности и отдаёт наружу один объект:

```js
var Utils = (function () {
  function formatDate(d) { /* ... */ }
  return { formatDate: formatDate };   // приватное скрыто, публичное — одно имя в window
})();
```

Это работает, но не решает главного: зависимости по-прежнему не описаны в коде.

### CommonJS и AMD: модули появились, а браузер о них не знает

Node.js принёс `require`/`module.exports` — синхронный поиск файла на диске. Это отличная модель для сервера и невозможная для браузера: у браузера нет файловой системы, а синхронный сетевой запрос заблокировал бы страницу. Параллельно для браузера придумали AMD (`define([...], factory)`) — асинхронный по конструкции, но многословный, и UMD — обёртку, которая пытается определить окружение и подойти всем сразу.

Ключевой момент для понимания сборщиков вот в чём: `require('lodash')` в браузере не работает **принципиально** — нет ни файловой системы, ни алгоритма поиска пакета. И тут появляется идея, из которой выросли все современные сборщики:

> Пусть граф модулей обойдёт инструмент — заранее, на машине разработчика, — и выдаст один файл, который браузер уже сможет выполнить.

Так работал browserify, так же — первые версии Webpack. Функция «свернуть граф в файл» и есть исходное определение bundler'а.

### Нативные ESM: браузер наконец получил модули

```html
<script type="module" src="/src/main.js"></script>
```

`import`/`export` работают в браузере без инструментов, а bare-спецификаторы (`import { format } from 'date-fns'`) можно объявить через import map. Именно здесь и возникает главный вопрос темы: если браузер умеет модули сам, зачем нужен сборщик? Ответ ниже, но сначала — что сборщик вообще делает.

## Пять задач, которые закрывает сборщик

```txt
                             Пять задач, ради которых существует сборщик
┌──────────────────────────┬─────────────────────────────────┬──────────────────────────────────────┐
│ задача                   │ что умеет браузер сам           │ что добавляет сборщик                │
├──────────────────────────┼─────────────────────────────────┼──────────────────────────────────────┤
│ найти модуль по имени    │ только URL и относительные пути │ node_modules, alias, поля exports    │
├──────────────────────────┼─────────────────────────────────┼──────────────────────────────────────┤
│ число запросов           │ один запрос на каждый модуль    │ граф свёрнут в несколько файлов      │
├──────────────────────────┼─────────────────────────────────┼──────────────────────────────────────┤
│ TS, JSX, новый синтаксис │ не понимает вообще              │ трансформация в поддерживаемый JS    │
├──────────────────────────┼─────────────────────────────────┼──────────────────────────────────────┤
│ CSS, картинки, шрифты    │ отдельные теги и пути вручную   │ ресурс становится узлом графа        │
├──────────────────────────┼─────────────────────────────────┼──────────────────────────────────────┤
│ размер и кеш в проде     │ ничего не делает                │ минификация, тришейкинг, хеш в имени │
└──────────────────────────┴─────────────────────────────────┴──────────────────────────────────────┘
                            первые четыре задачи нужны и в dev, и в проде;
                   пятая — только в прод-сборке, и именно она делает сборку долгой
```

**1. Резолвинг модулей.** Браузер понимает только URL: `./utils.js`, `/src/app.js`, `https://…`. Строка `'date-fns'` для него — не путь, а ошибка `Failed to resolve module specifier`. Сборщик знает алгоритм поиска: обойти `node_modules` вверх по дереву, прочитать `package.json`, выбрать нужный файл из поля `exports`, применить настроенные alias. Import maps закрывают часть этой задачи в браузере, но перечислять сотни транзитивных зависимостей руками никто не будет — а сгенерировать import map автоматически может только инструмент, который сам обошёл граф. Механика резолвинга разбирается в [The Module Graph and Resolution].

**2. Сокращение числа запросов.** Один модуль — один HTTP-запрос. В типичном приложении модулей тысячи, и это не абстракция: `lodash-es` — это около 600 отдельных файлов.

**3. Трансформация.** TypeScript, JSX и синтаксис, который старые браузеры не поддерживают, для браузера не существуют. Кто-то должен превратить их в исполняемый JS, и удобнее всего это делать по дороге — на том же обходе графа.

**4. Не-JS ресурсы.** Строка `import './Button.css'` не имеет смысла в спецификации ESM: модульная система языка ничего не знает про стили. Это соглашение придумали сборщики — и вместе с ним возможность считать стиль, картинку или SVG узлом того же графа, что и код. Практическое следствие: неиспользуемый компонент утаскивает из бандла и свои стили тоже.

**5. Оптимизация для прода.** Минификация, удаление недостижимого кода, разделение на чанки, хеши в именах для долгого кеша. Всё это требует видеть **весь** граф целиком — оптимизировать один файл в отрыве от остальных бессмысленно.

## Сквозной пример: панель `shop-admin`

Через весь топик проходит одно приложение — React SPA с тремя маршрутами, из которых тяжёлый только один:

```txt
shop-admin/
├─ index.html
├─ package.json
└─ src/
   ├─ main.tsx              — точка входа
   ├─ App.tsx               — layout и маршрутизатор
   ├─ routes/
   │  ├─ Orders.tsx         — таблица заказов, лёгкая
   │  ├─ Analytics.tsx      — графики: chart-lib + date-fns  ← тяжёлый маршрут
   │  └─ Settings.tsx       — форма, лёгкая
   ├─ lib/api.ts            — обёртка над fetch
   └─ ui/
      ├─ Button.tsx
      └─ Button.css
```

```tsx
// src/main.tsx — с этого файла начинается обход графа
import { createRoot } from 'react-dom/client';
import { App } from './App';
import './styles/global.css';

createRoot(document.getElementById('root')!).render(<App />);
```

```tsx
// src/routes/Analytics.tsx — единственный «тяжёлый» маршрут
import { LineChart } from 'chart-lib';
import { format } from 'date-fns';
import { fetchMetrics } from '../lib/api';

export function Analytics() {
  const points = fetchMetrics();
  return <LineChart data={points} formatX={(d: Date) => format(d, 'dd.MM')} />;
}
```

На этом примере дальше разбираются разделение кода ([Code Splitting and Long-Term Caching]), тришейкинг и анализ бандла ([Tree Shaking and Optimization]) и различия dev/prod ([The Vite Model]). Вопрос, который стоит держать в голове с самого начала: **почему пользователь, открывший `/orders`, вообще должен скачивать `chart-lib`?**

## Если браузеры умеют ESM и есть HTTP/2 — почему сборщики не исчезли

Это главный вопрос темы и очень частый вопрос на интервью. Ответ состоит из трёх независимых частей.

### Водопад запросов

```txt
       БЕЗ СБОРКИ: нативные ESM                       СО СБОРКОЙ
┌───────────────────────────────────┐    ┌──────────────────────────────────┐
│ раунд    что запрашивает браузер  │    │ раунд    что запрашивает браузер │
│                                   │    │                                  │
│ раунд 1   index.html              │    │ раунд 1   index.html             │
│ раунд 2   main.tsx                │    │ раунд 2   index-a1b2c3.js        │
│ раунд 3   App.tsx, router.ts      │    │           vendor-d4e5f6.js       │
│ раунд 4   Analytics.tsx, api.ts   │    │           index-9f8e7d.css       │
│ раунд 5   chart-lib/index.js      │    └──────────────────────────────────┘
│ раунд 6   ≈600 файлов chart-lib/* │    глубина графа на число раундов не влияет:
└───────────────────────────────────┘        сборщик прошёл граф заранее
   про уровень N+1 браузер узнаёт,
   только когда разобрал уровень N
```

HTTP/2 действительно снял старое ограничение в шесть параллельных соединений на домен: сто файлов одного уровня скачаются мультиплексировано и почти одновременно. Но HTTP/2 не отменяет **последовательность**: браузер не знает, что `Analytics.tsx` импортирует `chart-lib`, пока не скачал и не распарсил сам `Analytics.tsx`. Стоимость загрузки — это не «сколько файлов», а «сколько уровней в глубину», умноженное на задержку сети. На быстром локальном соединении разница незаметна, на мобильной сети с задержкой в 150 мс шесть раундов превращаются почти в секунду до первого рендера.

Частичное лекарство — `<link rel="modulepreload">`: заранее сказать браузеру, какие модули понадобятся. Но чтобы сгенерировать такой список, нужно предварительно обойти граф — то есть сделать ровно то, чем занимается сборщик. Про подсказки браузеру и их цену — в [Code Splitting and Long-Term Caching].

### Пакеты не приспособлены к раздаче «как есть»

Даже без учёта водопада: часть пакетов в `node_modules` до сих пор публикуется только в CommonJS, а его браузер не выполнит вообще. Часть — публикуется сотнями мелких файлов. Часть — ссылается на bare-спецификаторы внутри себя, и каждый из них тоже нужно разрешить. Именно поэтому Vite, идеологически построенный вокруг нативных ESM в dev-режиме, всё равно предварительно упаковывает зависимости перед стартом — подробно в [The Vite Model].

### Прод-оптимизации требуют видеть весь граф

Минификация, удаление неиспользуемого кода, объединение модулей, стабильные хеши для долгого кеша — ни одна из этих операций невозможна над отдельным файлом. Вопрос «можно ли удалить эту функцию» — это вопрос обо всём графе сразу.

### Когда без сборки действительно можно

Ниша «no-build» реальна и не является ересью: лендинг, демо, внутренний инструмент на пару экранов, страница документации со скриптом на сотню строк. Если модулей десятки, а не тысячи, и `node_modules` в браузер не едет — сборщик добавит больше сложности, чем пользы. Честный ответ на интервью звучит как «зависит от глубины графа и от того, нужны ли прод-оптимизации», а не как «сборщик нужен всегда».

## Рамка всего топика: dev-режим и прод-сборка — это разные задачи

```txt
               Рамка всего топика: dev-режим и прод-сборка — разные задачи
┌──────────────────┬────────────────────────────┬────────────────────────────────────────┐
│                  │ dev-режим                  │ прод-сборка                            │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ что важно        │ скорость обратной связи    │ размер, кеш, скорость загрузки         │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ как часто        │ на каждое сохранение файла │ один раз перед деплоем                 │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ приемлемое время │ десятки миллисекунд        │ минуты                                 │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ минификация      │ выключена                  │ включена                               │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ тришейкинг       │ не нужен                   │ обязателен                             │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ source maps      │ подробные и быстрые        │ компромисс по точности                 │
├──────────────────┼────────────────────────────┼────────────────────────────────────────┤
│ что выполняется  │ код, близкий к исходному   │ код, преобразованный до неузнаваемости │
└──────────────────┴────────────────────────────┴────────────────────────────────────────┘
                    Webpack описывает оба режима одной моделью сборки;
            Vite использует две разные — отсюда и его скорость, и его ловушки
```

Эта таблица — рамка, к которой топик будет возвращаться постоянно. Два инструмента отвечают на неё по-разному:

- **Webpack** использует одну модель для обоих режимов: собрать граф целиком, а dev-сервер построить поверх той же сборки (с отключёнными оптимизациями и добавленным хот-релоадом). Плюс — dev и prod ведут себя одинаково. Минус — время холодного старта растёт вместе с проектом. Модель разбирается в [The Webpack Core Model].
- **Vite** использует две разные модели: в dev браузер получает нативные ESM и файлы трансформируются по запросу, в проде выполняется полноценная сборка. Плюс — старт почти не зависит от размера проекта. Минус — целый класс багов «в dev работает, в проде сломалось». Разбор в [The Vite Model] и [Dev Server and HMR].

**О версиях.** На момент написания в ходу Webpack 5.x — он активно развивается, а опубликованная дорожная карта готовит шестую мажорную версию со встроенной поддержкой CSS, HTML и TypeScript вместо привычных плагинов и лоадеров. Vite вышел в версии 8, где и прод-сборка, и предварительная упаковка зависимостей выполняются одним бандлером Rolldown (Rust-порт Rollup), заменившим прежнюю связку esbuild + Rollup. Экосистема здесь движется быстрее, чем стареют статьи, поэтому статус конкретных инструментов имеет смысл сверять с первоисточниками — `webpack.js.org`, `vite.dev`, `rolldown.rs` — а не с чужим сравнением годичной давности. Карта экосистемы целиком — в [Ecosystem and Choosing a Tool].

## Типичные ошибки на интервью

- **«Сборщик нужен, чтобы склеить файлы в один»** — это описание browserify 2013 года. Склейка — только одна из пяти задач, и в современном приложении с разделением по маршрутам «один файл» как раз антицель. Ответ уровня middle+ перечисляет резолвинг, трансформацию, работу с не-JS ресурсами и прод-оптимизации отдельно от объединения.

- **«Браузеры умеют ESM, значит сборщики больше не нужны»** — половина правды, за которую хорошо цепляются на собеседовании. Проверяющий вопрос всегда один: *«а сколько раундов запросов уйдёт на граф глубиной в шесть уровней?»* Нативные ESM убирают необходимость в склейке ради синтаксиса, но не убирают водопад, CommonJS-пакеты в `node_modules` и прод-оптимизации.

- **«HTTP/2 решил проблему множества запросов»** — HTTP/2 решил проблему *параллельности* запросов одного уровня, но не *последовательности* уровней. Путаница между этими двумя вещами — очень частый признак поверхностного знания.

- **Не отличать dev от прода** — самый ценный водораздел в теме. Кандидат, который говорит «Vite быстрый, потому что он на Rust», не понимает механику; кандидат, который говорит «в dev он не собирает граф целиком, а отдаёт модули по запросу, и платит за это различиями поведения между dev и prod», понимает. Подробнее — в [The Vite Model].

- **«Сборщик — это webpack»** — Webpack задал словарь (module, chunk, loader, plugin), которым пользуются все, но это один инструмент из десятка. Ответ, в котором любой вопрос про сборку сводится к конфигу Webpack, читается как «умею копировать чужой конфиг».

- **Уверенные утверждения про то, «на чём сейчас работает Vite»** — эта часть экосистемы меняется каждые несколько месяцев. Гораздо лучше звучит формулировка с привязкой ко времени: «в версии, с которой я работал, прод собирался тем-то; актуальное состояние стоит смотреть в документации». Уверенно названная устаревшая деталь стоит дороже, чем честное «нужно свериться».
