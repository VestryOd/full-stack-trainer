# Зачем существуют сборщики

## Одно предложение, из которого растёт весь топик

Сборщик берёт точку входа, обходит по ней граф импортов, преобразует каждый найденный файл и выдаёт набор готовых ассетов, которые браузер может скачать и выполнить. Всё остальное — лоадеры, плагины, чанки, хеши в именах — это детали того, как именно выполняются четыре глагола: *обойти*, *преобразовать*, *объединить*, *оптимизировать*.

Разбираться в сборщиках стоит не с конфига, а с вопроса «какую задачу этот конфиг закрывает». Иначе получается характерная картина: человек умеет скопировать рабочий `webpack.config.js`, но не может объяснить, почему после смены одной строки в коде пользователи перекачали два мегабайта вендорного кода.

## Три эпохи — как объяснение, а не как хронология

История здесь нужна ровно затем, чтобы показать: каждая следующая эпоха решала проблему предыдущей, и следы всех трёх до сих пор лежат в `node_modules`.

### Глобальные скрипты: порядок тегов вместо системы модулей

```html
<script src="/js/jquery.js"></script>
<script src="/js/utils.js"></script>
<script src="/js/app.js"></script>
```

Модулей нет — есть общий объект `window` и порядок подключения. Отсюда три хронические болячки:

- **Коллизии.** Две библиотеки объявляют `formatDate` — выигрывает та, что подключена последней. Ошибка проявится не в момент подключения, а через месяц в чужом коде.
- **Неявные зависимости.** То, что `app.js` не работает без `utils.js`, нигде не записано. Это знание живёт в голове и в порядке тегов.
- **Ручное управление порядком.** Переставили две строки в HTML — сломали приложение.

Частичное лекарство — обёртка IIFE (immediately invoked function expression): функция, которую объявили и тут же вызвали. Она прячет внутренности и отдаёт наружу одно имя.

```js
var Utils = (function () {
  function formatDate(d) { /* ... */ }
  return { formatDate: formatDate };   // приватное скрыто, публичное — одно имя в window
})();
```

Это работает, но не решает главного: зависимости по-прежнему не описаны в коде.

### CommonJS и AMD: модули появились, а браузер о них не знает

Node.js принёс `require`/`module.exports` — синхронный поиск файла на диске. Это отличная модель для сервера и невозможная для браузера. У браузера нет файловой системы, а синхронный сетевой запрос заблокировал бы страницу.

Параллельно для браузера придумали AMD (asynchronous module definition — асинхронное объявление модуля), которое пишется как `define([...], factory)`. Оно асинхронно по конструкции, но многословно. Потом появился UMD (universal module definition) — обёртка, которая пытается определить окружение и подойти всем сразу.

Ключевой момент для понимания сборщиков вот в чём: `require('lodash')` в браузере не работает **принципиально** — нет ни файловой системы, ни алгоритма поиска пакета. И тут появляется идея, из которой выросли все современные сборщики:

> Пусть граф модулей обойдёт инструмент — заранее, на машине разработчика, — и выдаст один файл, который браузер уже сможет выполнить.

Так работал browserify, так же — первые версии Webpack. Функция «свернуть граф в файл» и есть исходное определение сборщика.

### Нативные ESM: браузер наконец получил модули

```html
<script type="module" src="/src/main.js"></script>
```

ESM расшифровывается как ECMAScript modules: это встроенный в язык синтаксис `import`/`export`. Он работает в браузере вообще без инструментов. Голые спецификаторы вида `import { format } from 'date-fns'` можно объявить через import map.

Именно здесь и возникает главный вопрос темы: если браузер умеет модули сам, зачем нужен сборщик? Ответ ниже, но сначала — что сборщик вообще делает.

## Пять задач, которые закрывает сборщик

| задача | что умеет браузер сам | что добавляет сборщик |
|---|---|---|
| найти модуль по имени | только URL и относительные пути | `node_modules`, alias, поля `exports` |
| число запросов | один запрос на каждый модуль | граф свёрнут в несколько файлов |
| TS, JSX (HTML-подобные теги внутри JS), новый синтаксис | не понимает вообще | трансформация в поддерживаемый JS |
| CSS, картинки, шрифты | отдельные теги и пути вручную | ресурс становится узлом графа |
| размер и кеш в проде | ничего не делает | минификация, тришейкинг, хеш в имени |

*Первые четыре задачи нужны и в dev, и в проде. Пятая нужна только в прод-сборке, и именно она делает сборку долгой.*

**1. Резолвинг модулей.** Браузер понимает только URL — `./utils.js`, `/src/app.js` или полный адрес вида `https://…`. Строка `'date-fns'` для него не путь. Это ошибка `Failed to resolve module specifier`.

Сборщик знает алгоритм поиска:

- обойти `node_modules` вверх по дереву;
- прочитать `package.json` и выбрать нужный файл из поля `exports`;
- применить настроенные для проекта псевдонимы (alias).

Import maps закрывают часть этой задачи в браузере. Но перечислять сотни транзитивных зависимостей руками никто не будет, а сгенерировать import map автоматически может только инструмент, который сам обошёл граф. Механика резолвинга разбирается в [Граф модулей и резолвинг](./02-module-graph-and-resolution.md).

**2. Сокращение числа запросов.** Один модуль — один HTTP-запрос. В типичном приложении модулей тысячи, и это не абстракция: `lodash-es` — это около 600 отдельных файлов.

**3. Трансформация.** TypeScript, JSX и синтаксис, который старые браузеры не поддерживают, для браузера не существуют. Кто-то должен превратить их в исполняемый JS, и удобнее всего это делать по дороге — на том же обходе графа.

**4. Не-JS ресурсы.** Строка `import './Button.css'` не имеет смысла в спецификации ESM: модульная система языка ничего не знает про стили. Это соглашение придумали сборщики. Стиль, картинка или SVG (scalable vector graphics — векторная картинка) становятся узлом того же графа, что и код. Практическое следствие: неиспользуемый компонент утаскивает из бандла и свои стили тоже.

**5. Оптимизация для прода.** Минификация, удаление недостижимого кода, разделение на чанки, хеши в именах для долгого кеша. Всё это требует видеть **весь** граф целиком — оптимизировать один файл в отрыве от остальных бессмысленно.

## Сквозной пример: панель `shop-admin`

Через весь топик проходит одно приложение — React SPA (single-page application, одностраничное приложение) с тремя маршрутами, из которых тяжёлый только один:

```txt
shop-admin/
├─ index.html
├─ package.json
└─ src/
   ├─ main.tsx            — точка входа
   ├─ App.tsx             — layout и маршрутизатор
   ├─ routes/
   │  ├─ Orders.tsx       — таблица заказов, лёгкая
   │  ├─ Analytics.tsx    — графики: chart-lib + date-fns  ← тяжёлый
   │  └─ Settings.tsx     — форма, лёгкая
   ├─ lib/api.ts          — обёртка над fetch
   └─ ui/
      ├─ Button.tsx
      └─ Button.css
```

```tsx
// src/main.tsx — с этого файла начинается обход графа
import { createRoot } from 'react-dom/client';
import { App } from './App';
import './styles/global.css';

createRoot(document.getElementById('root')!).render(<App />);
```

```tsx
// src/routes/Analytics.tsx — единственный «тяжёлый» маршрут
import { LineChart } from 'chart-lib';
import { format } from 'date-fns';
import { fetchMetrics } from '../lib/api';

export function Analytics() {
  const points = fetchMetrics();
  return <LineChart data={points} formatX={(d: Date) => format(d, 'dd.MM')} />;
}
```

Тот же пример проходит через остальные статьи топика:

- разделение кода — [Разделение кода и долгосрочное кеширование](./04-code-splitting-and-caching.md);
- тришейкинг и анализ бандла — [Тришейкинг и оптимизация бандла](./05-tree-shaking-and-optimization.md);
- различия dev и прода — [Модель Vite](./06-vite-model.md).

Вопрос, который стоит держать в голове с самого начала: **почему пользователь, открывший `/orders`, вообще должен скачивать `chart-lib`?**

## Если браузеры умеют ESM и есть HTTP/2 — почему сборщики не исчезли

Это главный вопрос темы и очень частый вопрос на интервью. Ответ состоит из трёх независимых частей.

### Водопад запросов

```txt
      БЕЗ СБОРКИ: нативные ESM
┌───────────────────────────────────┐
│ раунд    что запрашивает браузер  │
│                                   │
│ раунд 1   index.html              │
│ раунд 2   main.tsx                │
│ раунд 3   App.tsx, router.ts      │
│ раунд 4   Analytics.tsx, api.ts   │
│ раунд 5   chart-lib/index.js      │
│ раунд 6   ≈600 файлов chart-lib/* │
└───────────────────────────────────┘
   про уровень N+1 браузер узнаёт,
   только когда разобрал уровень N

             СО СБОРКОЙ
┌──────────────────────────────────┐
│ раунд    что запрашивает браузер │
│                                  │
│ раунд 1   index.html             │
│ раунд 2   index-a1b2c3.js        │
│           vendor-d4e5f6.js       │
│           index-9f8e7d.css       │
└──────────────────────────────────┘
  глубина графа на число раундов не влияет:
        сборщик прошёл граф заранее
```

HTTP/2 действительно снял старое ограничение в шесть параллельных соединений на домен. Сто файлов одного уровня скачаются мультиплексировано и почти одновременно.

Но HTTP/2 не отменяет **последовательность**. Браузер не знает, что `Analytics.tsx` импортирует `chart-lib`, пока не скачал и не распарсил сам `Analytics.tsx`. Стоимость загрузки — это не число файлов, а число уровней в глубину, умноженное на задержку сети.

На быстром локальном соединении разница незаметна. На мобильной сети с задержкой в 150 мс шесть раундов превращаются почти в секунду до первого рендера.

Частичное лекарство — `<link rel="modulepreload">`: заранее сказать браузеру, какие модули понадобятся. Но чтобы сгенерировать такой список, нужно предварительно обойти граф — то есть сделать ровно то, чем занимается сборщик. Про подсказки браузеру и их цену — в статье [Разделение кода и долгосрочное кеширование](./04-code-splitting-and-caching.md).

### Пакеты не приспособлены к раздаче «как есть»

Даже без учёта водопада: `node_modules` не готов к раздаче напрямую.

- Часть пакетов до сих пор публикуется только в CommonJS, а его браузер не выполнит вообще.
- Часть публикуется сотнями мелких файлов.
- Часть ссылается на голые спецификаторы внутри себя, и каждый из них тоже нужно разрешить.

Именно поэтому Vite всё равно предварительно упаковывает зависимости перед стартом, хотя идеологически он построен вокруг нативных ESM в dev-режиме. Подробно — в статье [Модель Vite](./06-vite-model.md).

### Прод-оптимизации требуют видеть весь граф

Минификация, удаление неиспользуемого кода, объединение модулей, стабильные хеши для долгого кеша — ни одна из этих операций невозможна над отдельным файлом. Вопрос «можно ли удалить эту функцию» — это вопрос обо всём графе сразу.

### Когда без сборки действительно можно

Ниша «no-build» реальна, и выбрать её — не ошибка. Она подходит для таких случаев:

- лендинг или демо;
- внутренний инструмент на пару экранов;
- страница документации со скриптом на сотню строк.

Если модулей десятки, а не тысячи, и `node_modules` в браузер не едет — сборщик добавит больше сложности, чем пользы. Честный ответ на интервью звучит как «зависит от глубины графа и от того, нужны ли прод-оптимизации», а не как «сборщик нужен всегда».

## Рамка всего топика: dev-режим и прод-сборка — это разные задачи

| | dev-режим | прод-сборка |
|---|---|---|
| что важно | скорость обратной связи | размер, кеш, скорость загрузки |
| как часто | на каждое сохранение файла | один раз перед деплоем |
| приемлемое время | десятки миллисекунд | минуты |
| минификация | выключена | включена |
| тришейкинг | не нужен | обязателен |
| source maps | подробные и быстрые | компромисс по точности |
| что выполняется | код, близкий к исходному | код, преобразованный до неузнаваемости |

*Webpack описывает оба режима одной моделью сборки. Vite использует две разные — отсюда и его скорость, и его ловушки.*

Эта таблица — рамка, к которой топик будет возвращаться постоянно. Два инструмента отвечают на неё по-разному:

- **Webpack** использует одну модель для обоих режимов. Он собирает граф целиком, а dev-сервер строит поверх той же сборки. Оптимизации при этом выключены, а сверху добавлена горячая замена модулей (HMR). Плюс — dev и прод ведут себя одинаково. Минус — время холодного старта растёт вместе с проектом. Модель разбирается в статье [Модель Webpack](./03-webpack-core-model.md).
- **Vite** использует две разные модели. В dev браузер получает нативные ESM и файлы трансформируются по запросу; в проде выполняется полноценная сборка. Плюс — старт почти не зависит от размера проекта. Минус — целый класс багов «в dev работает, в проде сломалось». Разбор в статьях [Модель Vite](./06-vite-model.md) и [Дев-сервер и горячая замена модулей](./07-dev-server-and-hmr.md).

**О версиях.** На момент написания в ходу Webpack 5.x, и он активно развивается. Опубликованная дорожная карта готовит шестую мажорную версию. В ней встроенная поддержка CSS, HTML и TypeScript заменит привычные плагины и лоадеры.

Vite вышел в версии 8. Там и прод-сборка, и предварительная упаковка зависимостей выполняются одним бандлером — Rolldown, Rust-портом Rollup. Он заменил прежнюю связку esbuild + Rollup.

Экосистема здесь движется быстрее, чем стареют статьи. Статус конкретных инструментов имеет смысл сверять с первоисточниками — `webpack.js.org`, `vite.dev`, `rolldown.rs` — а не с чужим сравнением годичной давности. Карта экосистемы целиком — в статье [Экосистема и выбор инструмента](./08-ecosystem-and-choosing.md).

## Типичные ошибки на интервью

- **«Сборщик нужен, чтобы склеить файлы в один»** — это описание browserify 2013 года. Склейка — только одна из пяти задач, и в современном приложении с разделением по маршрутам «один файл» как раз антицель. Ответ уровня middle+ перечисляет резолвинг, трансформацию, работу с не-JS ресурсами и прод-оптимизации отдельно от объединения.

- **«Браузеры умеют ESM, значит сборщики больше не нужны»** — половина правды, за которую хорошо цепляются на собеседовании. Нативные ESM убирают необходимость в склейке ради синтаксиса. Но они не убирают водопад, CommonJS-пакеты в `node_modules` и прод-оптимизации. Проверяющий вопрос всегда один: *сколько раундов запросов уйдёт на граф глубиной в шесть уровней?*

- **«HTTP/2 решил проблему множества запросов»** — HTTP/2 решил проблему *параллельности* запросов одного уровня, но не *последовательности* уровней. Путаница между этими двумя вещами — очень частый признак поверхностного знания.

- **Не отличать dev от прода** — самый ценный водораздел в теме. Фраза «Vite быстрый, потому что он на Rust» механику не описывает. Механика такая: в dev он не собирает граф целиком, а отдаёт модули по запросу. Платит он за это различиями поведения между dev и продом. Подробнее — в статье [Модель Vite](./06-vite-model.md).

- **«Сборщик — это webpack»** — Webpack задал словарь (module, chunk, loader, plugin), которым пользуются все, но это один инструмент из десятка. Ответ, в котором любой вопрос про сборку сводится к конфигу Webpack, читается как «умею копировать чужой конфиг».

- **Уверенные утверждения про то, «на чём сейчас работает Vite»** — эта часть экосистемы меняется каждые несколько месяцев. Гораздо лучше звучит формулировка с привязкой ко времени: «в версии, с которой я работал, прод собирался тем-то; актуальное состояние стоит смотреть в документации». Уверенно названная устаревшая деталь стоит дороже, чем честное «нужно свериться».
