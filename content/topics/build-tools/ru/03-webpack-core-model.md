# Модель Webpack

## Зачем разбираться в Webpack, даже если вы пишете на Vite

Webpack задал словарь, которым пользуется вся индустрия: *module*, *chunk*, *loader*, *plugin*, *code splitting*, *hot module replacement*. Vite, Rspack и Turbopack описывают себя в этих же терминах — иногда повторяя их, иногда сознательно отказываясь. Поэтому модель Webpack — это не «как настроить один инструмент», а базовый язык разговора о сборке, включая интервью.

Практическая часть тоже никуда не делась: Webpack 5 активно развивается, на нём собирается огромное количество живых проектов, а опубликованная дорожная карта готовит шестую мажорную версию. Так что «Webpack — легаси» — утверждение как минимум спорное.

## Словарь: module → chunk → asset

Эти три слова путают чаще всего, и путаница мешает даже сформулировать вопрос о проблеме.

```txt
        Словарь Webpack: module → chunk → asset
┌──────────────────────────────────────────────────────┐
│ MODULE — один файл после лоадеров                    │
│ Button.tsx, Button.css, logo.svg, react/index.js     │
│                          ↓                           │
│ группировка: точки входа + каждый import()           │
│                          ↓                           │
│ CHUNK — группа модулей, которую решено выдать вместе │
│ main, analytics, vendors, runtime                    │
│                          ↓                           │
│ генерация файлов, подстановка contenthash            │
│                          ↓                           │
│ ASSET — файл на диске                                │
│ main.a1b2c3.js, analytics.9f8e7d.js, main.4c5d6e.css │
└──────────────────────────────────────────────────────┘
   один чанк даёт несколько ассетов (js + css + map);
   один модуль может попасть сразу в несколько чанков
```

- **Module** — узел графа из [The Module Graph and Resolution], но уже после трансформации. Важно: модулем является не только JS. `Button.css` и `logo.svg` — тоже модули, потому что лоадер превратил их в нечто, что можно импортировать.
- **Chunk** — единица **решения сборщика**: «эти модули поедут вместе». Чанки появляются из точек входа, из каждого `import()` и из правил `splitChunks`. Чанк — сущность внутри сборки, у него есть имя и идентификатор, но на диске его может не существовать в виде одного файла.
- **Asset** — то, что реально записано в `dist/`. У одного чанка обычно несколько ассетов: JS, вынесенный CSS, source map.

Практическая ценность различия — в постановке вопроса. «У меня большой бандл» — бесполезная формулировка. Полезная: **«почему модуль `chart-lib` оказался в чанке `main`, а не в `analytics`?»** Ответ на неё находится, а на первую — нет. Инструменты анализа, которые показывают именно эту связь, разбираются в [Tree Shaking and Optimization].

Отдельно стоит запомнить: один и тот же модуль может попасть в **несколько чанков сразу**. Если `lib/api.ts` импортируется из двух ленивых маршрутов, без общей группы он продублируется в оба чанка — это одна из главных тем [Code Splitting and Long-Term Caching].

## Конфиг: из чего он состоит

```js
// webpack.config.js — минимум, достаточный для shop-admin
const path = require('path');
const HtmlWebpackPlugin = require('html-webpack-plugin');

module.exports = {
  mode: 'production',

  // 1. корни графа
  entry: './src/main.tsx',

  // 2. куда и под какими именами писать результат
  output: {
    path: path.resolve(__dirname, 'dist'),
    filename: '[name].[contenthash].js',
    clean: true,                        // чистить dist перед сборкой
  },

  // 3. как искать модули — разобрано в статье про резолвинг
  resolve: {
    extensions: ['.tsx', '.ts', '.js'],
    alias: { '@': path.resolve(__dirname, 'src') },
  },

  // 4. чем трансформировать найденные файлы
  module: {
    rules: [
      { test: /\.tsx?$/, exclude: /node_modules/, use: 'ts-loader' },
      { test: /\.s?css$/, use: ['style-loader', 'css-loader', 'sass-loader'] },
      { test: /\.(png|svg|woff2)$/, type: 'asset/resource' },
    ],
  },

  // 5. кто вмешивается в процесс сборки целиком
  plugins: [new HtmlWebpackPlugin({ template: './index.html' })],
};
```

Пять секций — пять разных вопросов: **откуда** начинать обход, **куда** писать, **как искать**, **чем трансформировать**, **кто вмешивается**. Всё остальное в конфиге — это `optimization` (тема [Code Splitting and Long-Term Caching] и [Tree Shaking and Optimization]) и `devServer` (тема [Dev Server and HMR]).

### mode: одна строка, которая меняет десяток дефолтов

```txt
                 Что на самом деле переключает одна строка mode
┌───────────────────────┬─────────────────────┬────────────────────────────────┐
│ опция                 │ mode: 'development' │ mode: 'production'             │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ devtool               │ 'eval'              │ false                          │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ cache                 │ { type: 'memory' }  │ false — файловый включают явно │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ output.pathinfo       │ true                │ false                          │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ optimization.minimize │ false               │ true                           │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ moduleIds / chunkIds  │ 'named'             │ 'deterministic'                │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ usedExports           │ false               │ true                           │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ concatenateModules    │ false               │ true                           │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ realContentHash       │ false               │ true                           │
├───────────────────────┼─────────────────────┼────────────────────────────────┤
│ nodeEnv               │ 'development'       │ 'production'                   │
└───────────────────────┴─────────────────────┴────────────────────────────────┘
        mode — не «переключатель скорости», а набор из десятка дефолтов,
     половина которых напрямую влияет на размер бандла и стабильность кеша
```

Три следствия, которые стоит понимать:

- **`moduleIds: 'named'` против `'deterministic'`.** В dev-режиме модуль получает читаемый идентификатор (путь к файлу) — удобно при отладке. В проде — короткий детерминированный, зависящий только от самого модуля. Именно от этого зависит, перестанут ли совпадать хеши вендорного чанка после добавления одного файла в приложение; подробно — в [Code Splitting and Long-Term Caching].
- **`nodeEnv` подставляет `process.env.NODE_ENV` через `DefinePlugin`.** Библиотеки пишут `if (process.env.NODE_ENV !== 'production') { warnAboutSomething() }`, значение подставляется как литерал, и минификатор выбрасывает мёртвую ветку целиком. Так React в проде становится заметно меньше. Механика — в [Tree Shaking and Optimization].
- **`cache` в production по умолчанию выключен.** Файловый кеш включается явно:

```js
// webpack.config.js — persistent caching, встроенный в Webpack 5
module.exports = {
  cache: {
    type: 'filesystem',
    buildDependencies: { config: [__filename] },  // пересобрать всё при правке конфига
  },
};
```

Именно это заменило устаревший способ ускорять пересборку — `cache-loader` и `hard-source-webpack-plugin`. Обе библиотеки сегодня не нужны и не поддерживаются: встроенный файловый кеш решает ту же задачу надёжнее, потому что видит зависимости сборки, а не только содержимое файлов. Увидеть в конфиге 2026 года `cache-loader` — верный признак, что конфиг не пересматривали много лет.

## Loaders: конвейер над одним файлом

Лоадер — это функция «содержимое файла → содержимое файла», которую применяют ко всем файлам, подходящим под `test`. Она ничего не знает ни про другие модули, ни про итоговые чанки: её работа локальна.

```txt
           Цепочка лоадеров: конвейер над ОДНИМ файлом
┌────────────────────────────────────────────────────────────────┐
│ use: ['style-loader', 'css-loader', 'sass-loader']             │
│                               ↓                                │
│ читается файл ui/Button.scss — просто текст                    │
│                               ↓                                │
│ sass-loader    SCSS → CSS                                      │
│                               ↓                                │
│ css-loader     CSS → JS-модуль, @import и url() → импорты      │
│                               ↓                                │
│ style-loader   JS-модуль → код, вставляющий <style> в документ │
│                               ↓                                │
│ на выходе валидный JS-модуль — узел графа                      │
└────────────────────────────────────────────────────────────────┘
          порядок обратен записи: это композиция функций
 style(css(sass(file))) — последний в массиве применяется первым
```

**Почему порядок обратный.** Это не прихоть, а прямое следствие того, что цепочка — композиция функций. Запись `use: [a, b, c]` читается как `a(b(c(file)))`: сначала внутренний вызов, потом внешний. Тот же принцип, что в математике и в `compose()` из функционального программирования. Поэтому в CSS-цепочке `sass-loader` (превращает SCSS в CSS) обязан идти последним в массиве — он работает первым.

Ключевое требование к концу цепочки: **последний применённый лоадер обязан вернуть валидный JavaScript**. Граф модулей состоит из JS-узлов, поэтому картинка, стиль или SVG в итоге всё равно превращаются в JS-модуль — либо экспортирующий URL файла, либо вставляющий стили в документ.

Порядок можно менять через `enforce`: правила делятся на три группы — `pre`, обычные и `post` — и внутри каждой действует то же «справа налево». Типичное применение `pre` — линтер, который должен увидеть исходник до трансформаций.

### Устаревшее: file-loader, url-loader, raw-loader

В Webpack 5 появились Asset Modules — встроенная обработка бинарных и текстовых ресурсов, без лоадеров вообще:

```js
module: {
  rules: [
    { test: /\.svg$/,  type: 'asset/resource' },   // отдельный файл + URL  (был file-loader)
    { test: /\.png$/,  type: 'asset/inline' },     // data URI              (был url-loader)
    { test: /\.txt$/,  type: 'asset/source' },     // содержимое строкой    (был raw-loader)
    { test: /\.jpg$/,  type: 'asset' },            // выбор по размеру, порог 8 КБ
  ],
}
```

Все три старых лоадера сегодня — легаси. Тот же процесс продолжается: по дорожной карте проекта в ядро переезжают CSS (`experiments.css`, ставший экспериментом ещё в пятой версии), обработка HTML и компиляция TypeScript. То есть направление развития Webpack — уменьшать число лоадеров и плагинов, необходимых для типового проекта.

### Та же задача в Vite

У Vite сущности «лоадер» нет вообще. Типовые трансформации встроены: TypeScript, JSX, CSS, PostCSS, препроцессоры, статические ресурсы обрабатываются без конфигурации. Всё нетиповое делается плагином с хуком `transform`.

```ts
// vite.config.ts — эквивалент конфига выше
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig({
  plugins: [react()],
  css: {
    preprocessorOptions: {
      scss: { additionalData: '@use "@/styles/vars" as *;' },
    },
  },
});
```

Важно правильно прочитать это сравнение. Конфиг Vite короче **не потому, что Vite «лучше устроен»**, а потому что у него другая политика: типовые случаи зашиты в инструмент, а не выражены через конфигурацию. Цена — меньше контроля в нетиповых случаях, и как только он понадобится, придётся писать плагин. Обратная сторона той же медали — в [The Vite Model].

## Plugins: подключение к жизненному циклу сборки

Плагин работает на другом уровне: он не трансформирует файлы, а вмешивается в **процесс**. Модель простая:

- **compiler** — объект, представляющий весь запуск Webpack. Живёт от старта до завершения (а в watch-режиме — всё время работы).
- **compilation** — объект одной конкретной сборки. В watch-режиме их будет много: по одной на каждую пересборку.

У обоих есть наборы хуков — точек, к которым можно подключиться: «граф построен», «чанки распределены», «сейчас будут записаны файлы». Плагин — это объект с методом `apply(compiler)`, который подписывается на нужные хуки. Внутренняя механика подписки (библиотека `tapable`, синхронные и асинхронные варианты хуков) для практической работы не нужна — достаточно модели «есть этапы, к ним можно подключиться».

Минимальный плагин целиком:

```js
// добавляет в dist файл с отметкой времени сборки
class BuildStampPlugin {
  apply(compiler) {
    compiler.hooks.thisCompilation.tap('BuildStampPlugin', (compilation) => {
      compilation.hooks.processAssets.tap(
        {
          name: 'BuildStampPlugin',
          stage: compiler.webpack.Compilation.PROCESS_ASSETS_STAGE_ADDITIONAL,
        },
        () => {
          const { RawSource } = compiler.webpack.sources;
          compilation.emitAsset('build-stamp.txt', new RawSource(`built at ${Date.now()}`));
        },
      );
    });
  }
}
```

Обратите внимание, чего здесь нет: никакого «содержимого файла» на входе. Плагин получает доступ к сборке целиком и сам решает, что с ней сделать — добавить ассет, изменить существующий, отменить сборку, дописать статистику.

```txt
                        Лоадер и плагин: разные единицы работы
┌─────────────────────┬────────────────────────────┬─────────────────────────────────┐
│                     │ loader                     │ plugin                          │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ единица работы      │ один файл                  │ вся сборка                      │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ когда вызывается    │ когда файл попал в граф    │ на хуках жизненного цикла       │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ что получает        │ содержимое файла           │ compiler и compilation          │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ что отдаёт          │ преобразованное содержимое │ ничего — меняет сборку сам      │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ видит другие модули │ нет                        │ да, весь граф целиком           │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ типичные примеры    │ ts-loader, sass-loader     │ HtmlWebpackPlugin, DefinePlugin │
├─────────────────────┼────────────────────────────┼─────────────────────────────────┤
│ аналог в Vite       │ хук transform плагина      │ остальные хуки того же плагина  │
└─────────────────────┴────────────────────────────┴─────────────────────────────────┘
             у Vite отдельной сущности «лоадер» нет: и то и другое — хуки
              одного плагина, поэтому словарь там короче на одно понятие
```

Проверочный критерий, по которому легко отличить одно от другого: **если задачу можно решить, глядя только на один файл — это лоадер; если нужно знать что-то про сборку в целом — это плагин.** Транспиляция TypeScript — лоадер. Генерация `index.html` со ссылками на итоговые ассеты — плагин, потому что имена ассетов известны только в конце сборки.

### Плагин в Vite

Тот же самый плагин в терминах Vite (а на самом деле — Rollup/Rolldown, чей интерфейс Vite использует):

```ts
import type { Plugin } from 'vite';

export function buildStamp(): Plugin {
  return {
    name: 'build-stamp',
    apply: 'build',                  // только в прод-сборке, не в dev-сервере
    generateBundle() {
      this.emitFile({
        type: 'asset',
        fileName: 'build-stamp.txt',
        source: `built at ${Date.now()}`,
      });
    },
  };
}
```

Отличия видны сразу: одна сущность вместо двух, `enforce: 'pre' | 'post'` для управления порядком относительно встроенных плагинов и `apply: 'build' | 'serve'` для выбора режима. Плюс vite-специфичные хуки поверх интерфейса Rollup: `config`, `configResolved`, `configureServer`, `transformIndexHtml`. Экосистемное следствие — совместимость с плагинами Rollup — разбирается в [The Vite Model].

## Почему конфиг Webpack разрастается

Три причины, и все три структурные, а не «плохой инструмент»:

1. **Каждый тип файла требует явного правила.** Ничего не работает по умолчанию — это цена гибкости.
2. **Dev и prod требуют разных значений одних и тех же опций.** `devtool`, `output.filename`, `optimization`, `devServer` — почти всё различается.
3. **Оптимизации задаются явно.** `splitChunks`, `runtimeChunk`, минимизаторы — всё это строки в конфиге.

Стандартный ответ — композиция конфигов под окружения:

```txt
config/
├─ webpack.common.js    entry, resolve, правила лоадеров — общее
├─ webpack.dev.js       devServer, devtool, mode: development
└─ webpack.prod.js      contenthash, splitChunks, mode: production
```

```js
// config/webpack.prod.js
const { merge } = require('webpack-merge');
const common = require('./webpack.common.js');

module.exports = merge(common, {
  mode: 'production',
  devtool: 'source-map',
  output: { filename: '[name].[contenthash].js' },
  optimization: {
    splitChunks: { chunks: 'all' },
    runtimeChunk: 'single',
  },
});
```

Альтернатива — конфиг-функция, получающая окружение:

```js
// webpack.config.js
module.exports = (env, argv) => ({
  mode: argv.mode,
  devtool: argv.mode === 'production' ? 'source-map' : 'eval-cheap-module-source-map',
  // ...
});
```

Критерий выбора простой: если различий между окружениями две-три строки, функция читается лучше; если различаются целые секции — `webpack-merge` честнее, потому что не превращает конфиг в дерево тернарных операторов.

Отдельный случай — монорепозитории и фреймворки с собственным CLI. Там конфиг обычно генерируется инструментом, а править его руками нельзя: нужно расширять сгенерированный. Как это устроено, разбирается в курсе NX (исполнители и настройка сборки) и в курсе Angular (глава про сборку и деплой).

## Типичные ошибки на интервью

- **Путать module, chunk и asset.** Самая частая и самая заметная ошибка. Кандидат, который говорит «чанк» про файл в `dist/` и «бандл» про всё сразу, не сможет объяснить ни дублирование модуля в двух чанках, ни почему CSS выносится в отдельный ассет. Хороший ответ разделяет три уровня: файл после трансформации, решение сборщика о группировке, результат на диске.

- **«Лоадер и плагин — это примерно одно и то же, просто по-разному подключаются»** — принципиально разные единицы работы. Проверочный вопрос интервьюера обычно звучит так: *«вам нужно сгенерировать `index.html` со ссылками на файлы с хешами — лоадер или плагин, и почему?»* Ответ «плагин, потому что имена ассетов известны только в конце сборки, а лоадер видит только один файл» показывает понимание модели, а не заученный список.

- **Не знать, почему лоадеры применяются справа налево.** Ответ «так исторически сложилось» слабый. Ответ «потому что цепочка — это композиция функций: `use: [a, b, c]` означает `a(b(c(file)))`» сильный и запоминается навсегда.

- **«`mode: 'production'` просто включает минификацию»** — это примерно десятая часть правды. За одной строкой стоит десяток дефолтов, включая `moduleIds: 'deterministic'` (влияет на стабильность кеша), `usedExports` и `concatenateModules` (тришейкинг и объединение модулей) и подстановку `NODE_ENV` через `DefinePlugin`.

- **Предлагать `cache-loader` или `hard-source-webpack-plugin` для ускорения сборки** — маркер знаний уровня Webpack 4. С пятой версии эту задачу решает встроенный `cache: { type: 'filesystem' }`, и он надёжнее, потому что учитывает зависимости самой сборки через `buildDependencies`. Тем же признаком выглядят `file-loader`/`url-loader`/`raw-loader` вместо Asset Modules.

- **«Конфиг Vite короче, значит Vite лучше»** — сравнение не тех вещей. Короткий конфиг означает, что типовые трансформации встроены в инструмент, а не что задач стало меньше. Сильный ответ формулирует это как выбор между «всё явно и настраиваемо» и «типовое работает само, нетиповое требует плагина» — и называет, в каких проектах какой выбор оправдан.
