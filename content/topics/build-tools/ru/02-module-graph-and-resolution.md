# Граф модулей и резолвинг

## Модуль — это узел графа, а не файл в папке

Сборка начинается с точки входа и разворачивается оттуда: сборщик читает файл, находит в нём импорты, для каждого импорта вычисляет конкретный путь на диске, читает найденный файл — и так, пока очередь не опустеет. Получается ориентированный граф: узлы — модули, рёбра — импорты.

```txt
      Граф модулей shop-admin: обход начинается с точки входа
┌──────────────────────────────────────────────────────────────────┐
│ обход в глубину от main.tsx                                      │
│                                                                  │
│ main.tsx                     ← точка входа: единственный корень  │
│ ├─ react-dom/client          bare specifier → node_modules       │
│ ├─ styles/global.css         не-JS ресурс — тоже узел графа      │
│ ╰─ App.tsx                                                       │
│    ├─ routes/Orders.tsx                                          │
│    │  ├─ lib/api.ts                                              │
│    │  ╰─ ui/Button.tsx       → ui/Button.css                     │
│    ├─ routes/Analytics.tsx                                       │
│    │  ├─ chart-lib           ≈600 модулей из node_modules        │
│    │  ├─ date-fns            bare specifier                      │
│    │  ╰─ lib/api.ts          ← уже посещён: узел один, рёбер два │
│    ╰─ routes/Settings.tsx                                        │
│       ╰─ ui/Button.tsx       ← тот же узел, второе ребро         │
└──────────────────────────────────────────────────────────────────┘
       это граф, а не дерево: модуль обрабатывается один раз,
               сколько бы файлов его ни импортировали
```

Из этой картинки следуют три вещи, о которых полезно помнить каждый день:

- **Файл, который никто не импортирует, в сборку не попадает вообще.** Не потому что его выбросили при оптимизации, а потому что до него не дошёл обход. Это принципиально другая история, чем тришейкинг (там модуль в графе есть, а его экспорты выкидываются) — разница разбирается в [Tree Shaking and Optimization].
- **Один добавленный импорт может утащить в бандл сотни модулей.** Строка `import { LineChart } from 'chart-lib'` в `Analytics.tsx` — это не один узел, а целое поддерево.
- **Модуль обрабатывается ровно один раз.** `lib/api.ts` импортируется из двух маршрутов, но трансформируется и попадает в бандл однократно — во время исполнения его тело тоже выполнится один раз, а результат закешируется. Отсюда, кстати, растёт весь класс «модулей-синглтонов»: экземпляр стора или клиента API, созданный на верхнем уровне модуля, существует в единственном числе — до тех пор, пока модуль не оказался в бандле дважды (см. ниже про дубли).

С каждым узлом сборщик делает одно и то же: прочитать → трансформировать → разобрать импорты → положить найденное в очередь. Из чего состоит шаг «трансформировать» — в [The Webpack Core Model].

### Точек входа может быть несколько

```js
// webpack.config.js — точки входа задаются явно
module.exports = {
  entry: {
    main:  './src/main.tsx',
    admin: './src/admin.tsx',
  },
};
```

```ts
// vite.config.ts — по умолчанию точка входа берётся из index.html
import { defineConfig } from 'vite';

export default defineConfig({
  build: {
    rolldownOptions: {              // прежнее имя rollupOptions работает как алиас
      input: {
        main:  'index.html',
        admin: 'admin.html',
      },
    },
  },
});
```

Разница здесь не косметическая. У Webpack корень графа — JS-файл, а HTML генерируется плагином сбоку. У Vite корень графа — **сам `index.html`**: сборщик читает его, находит `<script type="module" src="/src/main.tsx">` и идёт дальше уже по JS. Поэтому в Vite ссылки на ассеты прямо в HTML обрабатываются и переписываются, а в Webpack для этого нужен отдельный плагин. Подробнее — в [The Vite Model].

## Алгоритм резолвинга: из строки в файл на диске

Резолвинг — это функция «строка спецификатора + файл, откуда импортируют» → «конкретный путь на диске». Всё остальное в сборке зависит от того, что она вернёт.

```txt
                     Виды спецификаторов и что с ними делает сборщик
┌───────────────────┬────────────────┬──────────────────────────────────────────────────┐
│ вид спецификатора │ пример         │ что делает сборщик                               │
├───────────────────┼────────────────┼──────────────────────────────────────────────────┤
│ относительный     │ './lib/api'    │ путь от текущего файла + перебор расширений      │
├───────────────────┼────────────────┼──────────────────────────────────────────────────┤
│ абсолютный        │ '/src/lib/api' │ путь от корня проекта                            │
├───────────────────┼────────────────┼──────────────────────────────────────────────────┤
│ alias             │ '@/lib/api'    │ подстановка из конфига, дальше как относительный │
├───────────────────┼────────────────┼──────────────────────────────────────────────────┤
│ bare specifier    │ 'date-fns'     │ поиск пакета в node_modules вверх по дереву      │
├───────────────────┼────────────────┼──────────────────────────────────────────────────┤
│ внешний URL       │ 'https://…'    │ не резолвится, остаётся внешней ссылкой          │
└───────────────────┴────────────────┴──────────────────────────────────────────────────┘
                 браузер понимает только относительные, абсолютные и URL;
                alias и bare specifier работают только благодаря сборщику
```

### Относительные пути и перебор расширений

Строка `'./lib/api'` не указывает на существующий файл: на диске лежит `api.ts`. Сборщик перебирает расширения из списка и берёт первое совпадение, а если это директория — ищет в ней `index.*`.

Дефолты у инструментов разные, и это регулярный источник недоумения:

- **Webpack:** `resolve.extensions` по умолчанию `['.js', '.json', '.wasm']`. TypeScript и JSX нужно добавить руками — без этого сборка падает на первом же `.tsx`.
- **Vite:** `['.mjs', '.js', '.mts', '.ts', '.jsx', '.tsx', '.json']` — из коробки.

Перебор стоит обращений к файловой системе: каждое расширение из списка — это отдельная проверка «а существует ли такой файл». На проекте с тысячами модулей и длинным списком расширений это заметная часть времени сборки. Отсюда практический совет: не раздувать список и держать самые частые расширения в его начале. Как вообще измерять, куда уходит время сборки, — в [Ecosystem and Choosing a Tool].

### Alias

Одна и та же задача — «писать `@/lib/api` вместо `../../../lib/api`» — в двух конфигах:

```js
// webpack.config.js
const path = require('path');

module.exports = {
  resolve: {
    extensions: ['.tsx', '.ts', '.js', '.json'],
    alias: {
      '@': path.resolve(__dirname, 'src'),
      // трейлинг $ = только точное совпадение:
      // 'lodash' будет подменён, 'lodash/pick' — нет
      lodash$: path.resolve(__dirname, 'src/shims/lodash.ts'),
    },
  },
};
```

```ts
// vite.config.ts
import path from 'node:path';
import { defineConfig } from 'vite';

export default defineConfig({
  resolve: {
    alias: {
      '@': path.resolve(__dirname, 'src'),
    },
  },
});
```

Ловушка, которая стоит многим часов: **alias в сборщике и `paths` в `tsconfig.json` — разные механизмы.** TypeScript использует `paths` только для проверки типов и никогда не переписывает импорты в выходном коде; сборщик про `tsconfig.json` по умолчанию ничего не знает. Если настроить только `paths`, редактор будет доволен, а сборка упадёт с `Module not found`. Держать их синхронно вручную — источник расхождений, поэтому обычно ставят плагин, который читает `paths` и отдаёт их сборщику (`vite-tsconfig-paths` и аналоги). Webpack, начиная с версии 5.105, умеет читать пути из `tsconfig.json` самостоятельно — это часть общего движения к встроенной поддержке TypeScript, объявленного в дорожной карте проекта.

### Bare specifier: поиск по node_modules

```txt
             Как резолвится bare specifier
┌──────────────────────────────────────────────────────┐
│ import { format } from 'date-fns'                    │
│                          ↓                           │
│ есть ./node_modules/date-fns/ ?                      │
│ нет → ../node_modules/, и так вверх до корня ФС      │
│                          ↓                           │
│ читаем package.json найденного пакета                │
│                          ↓                           │
│ есть поле exports?                                   │
│ да  → выбираем ветку по условиям: import / require / │
│       browser / node / development / production      │
│ нет → идём по mainFields: browser → module → main    │
│                          ↓                           │
│ получили конкретный файл: date-fns/format.mjs        │
└──────────────────────────────────────────────────────┘
     падение на втором шаге — это Module not found;
«резолвится, но не тот файл» — расхождение условий сборщика и Node
```

Подъём вверх по дереву — важная деталь: пакет может лежать не рядом с импортирующим файлом, а в корне монорепозитория. Отдельная тонкость — симлинки: `pnpm` и workspace-ссылки создают именно их, и от того, разворачивает ли сборщик симлинк в реальный путь, зависит, окажется ли пакет «одним и тем же модулем». За это отвечают `resolve.symlinks` в Webpack (по умолчанию `true` — разворачивать) и `resolve.preserveSymlinks` в Vite (по умолчанию `false` — тоже разворачивать). В монорепозитории именно здесь чаще всего рождаются дубли; организация зависимостей в монорепозитории разбирается в курсе NX.

### Поля package.json и условные экспорты

```txt
                   Поля package.json: почему один пакет отдаёт разные файлы
┌─────────────────┬─────────────────────────────┬────────────────────────────────────────────┐
│ поле            │ кто его читает              │ что означает                               │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│ main            │ все, как последний резерв   │ исторический CJS-вход                      │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│ module          │ сборщики, но не Node        │ ESM-вход — условие тришейкинга             │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│ browser         │ сборщики с target web       │ подмена файла или заглушка вместо node-API │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│ exports         │ Node и современные сборщики │ источник правды; закрывает доступ к путям  │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│   "import"      │ при import из ESM           │ ESM-сборка пакета                          │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│   "require"     │ при require из CJS          │ CJS-сборка пакета                          │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│   "browser"     │ сборщик с target web        │ браузерная сборка                          │
├─────────────────┼─────────────────────────────┼────────────────────────────────────────────┤
│   "development" │ dev-режим сборщика          │ вариант с проверками и предупреждениями    │
└─────────────────┴─────────────────────────────┴────────────────────────────────────────────┘
           один и тот же import даёт РАЗНЫЕ файлы в Node, в сборщике и в браузере —
                      это не баг, а прямое назначение условных экспортов
```

Как это выглядит в реальном пакете:

```json
{
  "name": "chart-lib",
  "main": "./dist/index.cjs",
  "module": "./dist/index.mjs",
  "exports": {
    ".": {
      "types":   "./dist/index.d.ts",
      "browser": "./dist/index.browser.mjs",
      "import":  "./dist/index.mjs",
      "require": "./dist/index.cjs",
      "default": "./dist/index.mjs"
    },
    "./styles.css": "./dist/styles.css",
    "./package.json": "./package.json"
  }
}
```

Три правила, которые стоит знать про `exports`:

1. **Порядок ключей значим.** Резолвер идёт сверху вниз и берёт первое подходящее условие, поэтому `"types"` ставят первым, а `"default"` — последним. Перепутанный порядок — типичный баг в публикуемых библиотеках.
2. **`exports` закрывает всё, что в нём не перечислено.** До появления этого поля можно было импортировать любой файл пакета: `import util from 'chart-lib/dist/internal/util.js'`. После — только объявленные пути, остальное падает с `Package subpath './dist/internal/util.js' is not defined by "exports"`. Это частая причина того, что обновление минорной версии зависимости внезапно ломает сборку.
3. **Условия у разных потребителей разные.** Webpack при `target: 'web'` и `mode: 'production'` использует набор вроде `['webpack', 'production', 'browser']` плюс `import` или `require` в зависимости от того, из какого кода пришёл импорт. Vite по умолчанию использует `['module', 'browser', 'development|production']`, где последнее подставляется по режиму. Node не знает ни про `webpack`, ни про `module`, зато знает про `node`.

Вот отсюда и растёт целый класс ошибок «в тестах на Node работает, в браузере падает»: Jest резолвит `"require"`-ветку с CJS-сборкой, сборщик — `"browser"`-ветку с другим кодом. Это не расхождение реализаций, а именно то, для чего условные экспорты придуманы.

## CJS и ESM с точки зрения сборщика

Сами системы модулей — `require` против `import`, live bindings, порядок выполнения — разобраны в топике Node.js, в главе про CommonJS и ESM. Здесь важно ровно одно свойство и его последствия для сборки.

**ESM статичен.** `import` — это объявление, которое разбирается до выполнения кода: имя модуля обязано быть литералом, импорты нельзя объявить внутри `if`. `require` — обычный вызов функции, и его аргумент известен только в рантайме.

```js
// ESM: сборщик знает состав графа, ни строчки не выполнив
import { format } from 'date-fns';

// CJS: узнать, что здесь импортируется, можно только выполнив код
const name = isLegacy ? 'date-fns' : 'dayjs';
const lib = require(name);
```

Из этого следуют три вещи, на которых держится половина топика:

- **Граф строится без выполнения кода.** Сборщик читает и парсит, а не запускает. Именно поэтому сборка вообще возможна как статический анализ.
- **Тришейкинг работает только на ESM.** Чтобы доказать, что экспорт не используется, нужно знать все импорты заранее — с `require` это недоказуемо. Разбор в [Tree Shaking and Optimization].
- **Разделение кода опирается на `import()`.** Динамический импорт — единственная конструкция ESM, которую сборщик трактует как точку разрыва графа. См. [Code Splitting and Long-Term Caching].

### Что происходит, когда в граф попадает CJS-пакет

Сборщик не может отдать такой модуль браузеру как есть — `module` и `exports` в браузере не существуют. Поэтому модуль заворачивается в обёртку: тело превращается в функцию с локальными `module`/`exports`, функция вызывается при первом обращении, а результат кешируется и выдаётся как содержимое модуля. Практические следствия:

- **Именованные импорты из CJS — эвристика, а не гарантия.** Строка `import { pick } from 'lodash'` работает, пока сборщик способен статически распознать в коде пакета простые формы вроде `exports.pick = ...`. Если экспорты собираются динамически (в цикле, через `Object.assign`), анализ не срабатывает, и в браузере появляется `does not provide an export named 'pick'`. Ответ Vite на эту проблему — предварительная упаковка зависимостей, см. [The Vite Model].
- **Default-импорт требует interop-обёртки.** `import express from 'express'` даёт `module.exports` пакета целиком, потому что сборщик добавляет ту же прослойку, что и `esModuleInterop` в TypeScript. А `import * as express from 'express'` даёт объект-namespace, который нельзя вызвать как функцию — классическая ошибка `express is not a function`.
- **Dual package hazard.** Если пакет опубликован и в CJS, и в ESM, а разные части графа резолвят разные ветки, в бандл попадут **две копии** с независимым состоянием. Симптом — «синглтон почему-то не синглтон».

Общий вывод: CJS-зависимость — это узел, который сборщик обязан обернуть и не может оптимизировать. Именно такие узлы чаще всего и ломаются при переходе с Webpack на Vite ([Ecosystem and Choosing a Tool]).

## Типичные ошибки резолвинга и как их читать

### `Module not found`

Сообщение всегда содержит две части — **что** искали и **откуда**. Читать нужно обе:

```txt
Module not found: Error: Can't resolve 'crypto' in '/app/src/lib'
BREAKING CHANGE: webpack < 5 used to include polyfills for node.js core
modules by default. This is no longer the case.
```

Три причины по частоте:

1. **Опечатка или отсутствующее расширение** — самое частое и самое безобидное. Проверяется списком `resolve.extensions`.
2. **Пакета нет в `node_modules`** — не установлен или объявлен только в `peerDependencies`.
3. **Node-модуль в браузерном коде.** Webpack 4 автоматически подставлял браузерные полифиллы для `crypto`, `path`, `buffer`; Webpack 5 это убрал — и правильно сделал, потому что молча тащить в бандл эмуляцию `Buffer` дорого. Лечится либо `resolve.fallback` с явным полифиллом, либо (лучше) избавлением от зависимости, которой в браузере не место. У Vite аналогичная ситуация выглядит иначе: сборка проходит, а в рантайме появляется `process is not defined` — миграционные грабли разбираются в [Ecosystem and Choosing a Tool].

Отдельный вид того же класса — `Failed to resolve entry for package "chart-lib". The package may have incorrect main/module/exports specified`. Здесь пакет найден, но ни одно условие не привело к существующему файлу: обычно это сломанный `exports` в самой библиотеке.

### Дубли одной библиотеки в бандле

```txt
           ОДНА КОПИЯ react                             ДВЕ КОПИИ react
┌───────────────────────────────────┐    ┌───────────────────────────────────────────┐
│ node_modules/                     │    │ node_modules/                             │
│                                   │    │                                           │
│ ├─ react@18.3.1                   │    │ ├─ react@18.3.1                           │
│ ├─ chart-lib/     peer: react ^18 │    │ ├─ chart-lib/           peer: react ^18   │
│ ╰─ ui-kit/        peer: react ^18 │    │ ╰─ ui-kit/              требует react ^17 │
│                                   │    │    ╰─ node_modules/                       │
│ в бандле          react один раз  │    │       ╰─ react@17.0.2                     │
└───────────────────────────────────┘    │                                           │
       менеджер пакетов поднял           │ в бандле                react дважды      │
         общую версию наверх             └───────────────────────────────────────────┘
                                                  плюс Invalid hook call: два
                                                  модуля, два разных состояния
```

Дубли — самая коварная ошибка резолвинга, потому что сборка проходит успешно. Симптомы приходят с другой стороны: неожиданно вырос размер бандла, появился `Invalid hook call`, React-контекст оказался пустым в дочернем компоненте, стор ведёт себя как два разных стора. Причина всегда одна: два модуля с одинаковым именем, но разными путями — для сборщика это два разных узла графа.

Механика возникновения:

- вложенная установка из-за несовместимых диапазонов версий (картинка справа);
- симлинки в монорепозитории, если пакет резолвится и по реальному пути, и по ссылке;
- одна библиотека, попавшая в граф дважды в разных форматах — тот самый dual package hazard.

Порядок диагностики: сначала `npm ls react` (или `pnpm why react`) — он покажет все установленные копии; затем анализ бандла, чтобы увидеть, попали ли обе копии в вывод ([Tree Shaking and Optimization]).

Лечение — по возрастанию грубости:

```ts
// vite.config.ts — «эти пакеты всегда резолвить в одну копию»
export default defineConfig({
  resolve: {
    dedupe: ['react', 'react-dom'],
  },
});
```

```js
// webpack.config.js — тот же эффект через принудительный alias
module.exports = {
  resolve: {
    alias: {
      react:       path.resolve(__dirname, 'node_modules/react'),
      'react-dom': path.resolve(__dirname, 'node_modules/react-dom'),
    },
  },
};
```

Но и то и другое — лечение симптома. Правильный порядок действий: сначала выровнять версии и вынести общий пакет в `peerDependencies` библиотеки, и только если это невозможно — принудительно склеивать резолвинг.

### Циклические зависимости

Граф это допускает, и сборщик не упадёт. Упадёт рантайм: при цикле `A → B → A` один из модулей начинает выполняться раньше, чем другой успел присвоить свои экспорты, и на его месте оказывается `undefined`. Характерный симптом — «всё сломалось после того, как поменяли порядок импортов» или «падает только в прод-сборке», потому что объединение модулей меняет порядок инициализации ([Tree Shaking and Optimization]). Циклы стоит ловить линтером на раннем этапе, а не отлаживать по симптомам.

## Типичные ошибки на интервью

- **«Сборщик просто склеивает файлы по импортам»** — пропущен весь резолвинг, а это как раз то, где живут реальные проблемы. Хороший ответ разделяет два шага: превратить строку в путь на диске (резолвинг) и обработать найденный файл (трансформация).

- **Не знать, что такое bare specifier** — ключевое понятие темы. Вопрос «почему `import 'date-fns'` не работает в браузере без сборщика, а `import './api.js'` работает» разделяет тех, кто понимает механику, и тех, кто помнит рецепты.

- **Путать alias сборщика и `paths` в `tsconfig.json`** — очень частая практическая ошибка и хороший диагностический вопрос. Правильный ответ: TypeScript про сборку не знает, а сборщик про `tsconfig.json` по умолчанию не знает; синхронизация — отдельная задача.

- **«`exports` — это просто новое имя для `main`»** — нет. `exports` не только выбирает вход, но и **закрывает** все пути, которых в нём нет, и позволяет отдавать разные файлы по условиям. Кандидат, который может объяснить, почему после обновления пакета сломался импорт из его внутренней папки, явно работал с этим руками.

- **«Дубли библиотеки — это проблема npm»** — только отчасти. Для сборщика два пути к `react` — это два разных модуля, и он честно включит оба. Ожидаемый ответ включает симптомы (`Invalid hook call`, пустой контекст, раздувшийся бандл), диагностику (`npm ls`, анализ бандла) и лечение с правильным приоритетом: сначала версии и `peerDependencies`, потом `dedupe`/`alias`.

- **«CJS и ESM для сборщика одно и то же — он всё равно всё перепишет»** — переписать он может, но статически проанализировать `require(переменная)` — нет. Именно отсюда растут и невозможность тришейкинга для CJS-зависимости, и `does not provide an export named`, и dual package hazard. Ответ, связывающий статичность ESM с конкретными оптимизациями, звучит на порядок сильнее, чем пересказ различий синтаксиса.
