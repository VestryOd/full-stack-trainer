# Тришейкинг и оптимизация бандла

## Тришейкинг — это доказательство, а не уборка

Название «тряска дерева» вводит в заблуждение: кажется, будто сборщик встряхивает граф и всё лишнее осыпается само. На самом деле работа устроена наоборот — сборщик обязан **доказать**, что код можно удалить, и при малейшем сомнении оставляет его. Отсюда все практические проблемы: почти всегда вопрос звучит не «почему это удалилось», а «почему это **не** удалилось».

Механика состоит из двух шагов:

1. **Разметка (`usedExports`).** Сборщик проходит граф и для каждого модуля отмечает, какие его экспорты кто-то действительно импортирует. Неиспользуемые помечаются как таковые.
2. **Удаление.** Помеченный код выбрасывает минификатор — он видит, что объявление никем не используется, и удаляет его.

Из этого следует важное: **тришейкинг без минификации не работает.** Разметка сама по себе ничего не удаляет. Именно поэтому в Webpack `usedExports` включается в `mode: 'production'` вместе с `minimize` (см. таблицу дефолтов в статье [Модель Webpack](./03-webpack-core-model.md)).

### Почему условие — статичность ESM

ESM (модули ECMAScript) — это синтаксис `import`/`export`. Он разбирается до выполнения кода: имя модуля — литерал, список импортируемых имён известен из синтаксиса. Значит, вопрос «импортирует ли кто-нибудь `formatCurrency`?» имеет ответ, который можно вычислить, не запуская программу.

```js
// ESM: сборщик знает, что берут только format
import { format } from 'date-fns';

// CJS: доказать что-либо невозможно
const dateFns = require('date-fns');
const fn = dateFns[userChoice];       // какой именно экспорт нужен — решится в рантайме
```

С `require` доказательство недостижимо принципиально: обращение к экспорту — это обычное чтение свойства объекта, которое может быть вычислено динамически. Поэтому зависимость в формате CJS (CommonJS — формат `require`/`module.exports`) сборщик оборачивает целиком и не трогает её содержимое.

Сами системы модулей разобраны в топике Node.js, в главе про CommonJS и ESM. Взгляд сборщика на них — в статье [Граф модулей и резолвинг](./02-module-graph-and-resolution.md).

## Почему тришейкинг не сработал

```txt
   Почему тришейкинг не сработал: разбор по причинам
┌─────────────────────────────────────────────────────┐
│ зависимость только в CJS                            │
│   в бандле: обёртка вокруг module.exports           │
│   решение: искать ESM-сборку или другой пакет       │
├─────────────────────────────────────────────────────┤
│ TS или Babel переписал в CJS                        │
│   в бандле: module: "commonjs" в tsconfig           │
│   решение: module: "esnext", остальное — сборщику   │
├─────────────────────────────────────────────────────┤
│ нет флага sideEffects                               │
│   в бандле: модуль целиком, хотя нужен один экспорт │
│   решение: sideEffects: false или список файлов     │
├─────────────────────────────────────────────────────┤
│ импорт пакета целиком                               │
│   в бандле: import _ from 'lodash'                  │
│   решение: именованные импорты из ESM-сборки        │
├─────────────────────────────────────────────────────┤
│ эффект на верхнем уровне                            │
│   в бандле: запись в window, вызов registry         │
│   решение: убрать эффект или пометить PURE          │
├─────────────────────────────────────────────────────┤
│ barrel-файл                                         │
│   в бандле: index.ts притащил соседей               │

└─────────────────────────────────────────────────────┘
первые два пункта — про то, ЧТО пришло в граф; остальные —
  про то, что сборщик не смог ДОКАЗАТЬ ненужность кода
```

Отдельно про вторую причину, потому что она самая обидная. **Транспилятор может убить тришейкинг ещё до того, как сборщик увидит код.** Если в `tsconfig.json` стоит `"module": "commonjs"`, TypeScript превратит все `import` в `require` — и сборщик получит на вход CJS, из которого ничего не докажешь.

```json
// tsconfig.json — правильная настройка для сборки под браузер
{
  "compilerOptions": {
    "module": "esnext",           // НЕ commonjs: сохранить import/export
    "moduleResolution": "bundler",
    "target": "es2022"
  }
}
```

Тот же принцип для Babel: `@babel/preset-env` с `modules: false`, чтобы он не переписывал модульный синтаксис. Общее правило — **транспиляция синтаксиса отдельно, работа с модулями — только у сборщика.**

### Почему «неиспользуемый импорт» всё равно попадает в бандл

Самый частый источник недоумения. Есть три разных случая, и путать их дорого.

**Случай 1: у модуля есть побочные эффекты.** Если импорт модуля что-то делает, удалить модуль нельзя, даже если ни один его экспорт не нужен.

```ts
// lib/analytics.ts
export function track(event: string) { /* ... */ }

// побочные эффекты на верхнем уровне: выполняются просто при импорте модуля
window.__analyticsReady = true;
globalRegistry.register('analytics');
```

```ts
// Orders.tsx — импортируем ничего не используя
import { track } from '@/lib/analytics';   // модуль попадёт в бандл целиком
```

Сборщик не знает, важны ли `window.__analyticsReady` и `globalRegistry.register` для работы приложения. Раз не знает — оставляет.

**Случай 2: импорт ради эффекта.** Такой импорт удалять и не следует — в нём весь смысл:

```ts
import './styles/global.css';    // нужен именно эффект
import 'core-js/stable';         // полифиллы регистрируют себя сами
```

**Случай 3: `import type`.** Импорт типов исчезает при транспиляции и в бандл не попадает никогда — но только если написан явно:

```ts
import type { Order } from '@/types';        // гарантированно исчезнет
import { type Order, fetchOrders } from '@/lib/api';  // тип исчезнет, функция останется
```

## Флаг `sideEffects`: как разрешить удалять модули целиком

`usedExports` работает внутри модуля — выкидывает отдельные экспорты. `sideEffects` работает на уровне модулей — позволяет **не включать модуль в бандл вообще**. Второе эффективнее: удаляется не функция, а целое поддерево графа.

```json
// package.json библиотеки: «импорт любого моего файла ничего не делает»
{
  "name": "ui-kit",
  "sideEffects": false
}
```

```json
// а если эффекты всё-таки есть — перечислить их
{
  "name": "ui-kit",
  "sideEffects": ["./src/polyfills.ts", "*.css"]
}
```

Строка `"*.css"` здесь критична, и на ней обжигаются регулярно. Импортированный CSS-файл — такой же модуль, подлежащий тришейкингу. При `sideEffects: false` и агрессивной оптимизации стили могут исчезнуть из прод-сборки, хотя в dev всё работало. Классический баг «в dev стили есть, в проде нет». Паттерны в массиве — простые glob-выражения, и шаблон без `/` трактуется как `**/*.css`.

Обратная сторона: `sideEffects: false` — это **обещание**, которое проверяет не сборщик, а реальность. Если поставить флаг на пакет, у которого эффекты есть, сборка станет меньше и сломается.

### Аннотация `/*#__PURE__*/`

Иногда эффектов нет, но сборщик не может это доказать — например, при вызове функции на верхнем уровне модуля:

```ts
// сборщик не знает, что createIcon ничего не делает снаружи
export const CloseIcon = /*#__PURE__*/ createIcon('close');
```

Аннотация — прямое утверждение «этот вызов свободен от побочных эффектов, его результат можно удалить, если он не нужен». В Webpack она учитывается при `optimization.innerGraph: true` (включён в проде). Такие аннотации обычно расставляют авторы библиотек, а не авторы приложений.

### Barrel-файлы: удобство против размера

```ts
// ui/index.ts — barrel
export * from './Button';
export * from './DataTable';   // тянет за собой virtualized-list
export * from './Chart';       // тянет за собой chart-lib
```

```ts
// Orders.tsx
import { Button } from '@/ui';   // просили одну кнопку
```

В теории тришейкинг должен убрать лишнее. На практике это работает, только если **все** модули в цепочке свободны от эффектов и помечены как таковые. Одного `import './Chart.css'` внутри `Chart.tsx` достаточно, чтобы весь `chart-lib` остался в бандле. Поэтому в больших проектах импортируют напрямую (`@/ui/Button`), а barrel оставляют для публичного API библиотеки, где он уместен.

## Минификация: что реально уменьшает размер

```txt
         Что делает минификатор, кроме удаления пробелов
┌───────────────────────────┬──────────────────────────┬─────────┐
│ операция                  │ что происходит           │ размер  │
├───────────────────────────┼──────────────────────────┼─────────┤
│ пробелы и комментарии     │ форматирование убирается │ малый   │
├───────────────────────────┼──────────────────────────┼─────────┤
│ сокращение локальных имён │ const userName → const a │ средний │
├───────────────────────────┼──────────────────────────┼─────────┤
│ свёртка констант          │ 'a'+'b' → 'ab', 2*3 → 6  │ малый   │
├───────────────────────────┼──────────────────────────┼─────────┤
│ удаление мёртвого кода    │ if (false) { … } уходит  │ БОЛЬШОЙ │
├───────────────────────────┼──────────────────────────┼─────────┤
│ инлайн разовых вызовов    │ подстановка тела функции │ средний │
├───────────────────────────┼──────────────────────────┼─────────┤
│ сокращение имён экспортов │ formatCurrency → f       │ средний │
└───────────────────────────┴──────────────────────────┴─────────┘
   главный выигрыш даёт не «сжатие текста», а удаление ветвей,
         ставших недостижимыми после подстановки NODE_ENV
```

Механизм, дающий основной эффект, стоит проследить целиком:

```ts
// в исходнике библиотеки
if (process.env.NODE_ENV !== 'production') {
  validatePropTypes(props);
  console.warn('Component X is deprecated');
}
```

```ts
// после подстановки NODE_ENV сборщиком
if ('production' !== 'production') { /* ... */ }

// после свёртки констант минификатором
if (false) { /* ... */ }

// после удаления мёртвого кода
// ничего
```

Именно так React в проде оказывается заметно меньше, чем в dev: исчезают не пробелы, а целые подсистемы предупреждений и проверок. Подстановка `NODE_ENV` — часть дефолтов `mode`, разобранных в статье [Модель Webpack](./03-webpack-core-model.md).

### Современные минификаторы

Terser долгое время был стандартом, но он написан на JavaScript и на больших проектах занимает большую часть времени прод-сборки. Сегодня выбор шире, и он менялся буквально в последние версии инструментов:

- **Vite** на момент написания использует минификатор из семейства Oxc — это значение `build.minify` по умолчанию. Документация формулирует компромисс прямо: он в десятки раз быстрее Terser при проигрыше в степени сжатия порядка процента. Вариант `'esbuild'` помечен устаревшим, `'terser'` остаётся доступным для тех, кому важен последний процент размера.
- **Webpack** по умолчанию минифицирует с помощью Terser; заменить его можно через `optimization.minimizer`. Дорожная карта проекта при этом предполагает объединение отдельных минимизаторов (JS, CSS, HTML, JSON) в один плагин.

```js
// webpack.config.js — минификатор задаётся явно
const TerserPlugin = require('terser-webpack-plugin');

module.exports = {
  optimization: {
    minimizer: [new TerserPlugin({ terserOptions: { format: { comments: false } } })],
  },
};
```

```ts
// vite.config.ts — значение по умолчанию можно поменять
export default defineConfig({
  build: {
    minify: 'terser',   // вместо быстрого дефолта — если нужен максимум сжатия
  },
});
```

Практический вывод: выбор минификатора — это компромисс «время сборки против нескольких процентов размера», и почти всегда быстрый вариант правильнее. Замерять при этом надо сжатый размер, потому что gzip и brotli частично компенсируют разницу.

### Scope hoisting: объединение модулей

Каждый модуль в бандле по умолчанию — отдельная функция-обёртка со своей областью видимости. Scope hoisting (в Webpack — `optimization.concatenateModules`, он же `ModuleConcatenationPlugin`) склеивает модули, которые импортируются в одном месте, в одну область видимости.

```js
// без объединения: у каждого модуля своя обёртка, а до экспорта
// добираются через промежуточный объект
var chartModule = { render: function () { /* ... */ } };
chartModule.render();       // чтение свойства при каждом вызове

// с объединением: одна область видимости, обращение напрямую
function render() { /* ... */ }
render();                   // чтения свойства нет, минификатор может переименовать
```

Выигрыш двойной: меньше служебного кода и — что важнее — минификатору становится доступно больше. Имена, которые раньше были «публичными экспортами модуля», превращаются в обычные локальные переменные, а значит, их можно сократить до одной буквы.

Условие работы то же самое: **только ESM**. CJS-модуль объединить нельзя, потому что его экспорты формируются в рантайме. Это ещё одна причина, по которой одна CJS-зависимость в графе стоит дороже, чем кажется.

## Source maps: три компромисса в одной опции

```txt
            Source maps: три компромисса в одной опции
Значения для dev — карта не попадает в прод
┌──────────────────────────────┬───────────┬─────────────────────┐
│ значение                     │ сборка    │ что видно в стеке   │
├──────────────────────────────┼───────────┼─────────────────────┤
│ eval                         │ быстрая   │ сгенерированный код │
├──────────────────────────────┼───────────┼─────────────────────┤
│ eval-cheap-module-source-map │ средняя   │ строки исходника    │
├──────────────────────────────┼───────────┼─────────────────────┤
│ eval-source-map              │ медленная │ исходник полностью  │
└──────────────────────────────┴───────────┴─────────────────────┘

Значения для прода — вопрос в том, кто увидит ваш исходник
┌───────────────────────────────────────────────────┐
│ source-map                                        │
│   в стеке: исходник полностью                     │
│   в проде: файл .map лежит открыто                │
├───────────────────────────────────────────────────┤
│ hidden-source-map                                 │
│   в стеке: исходник, но только в трекере ошибок   │
│   в проде: карта загружена, ссылки в бандле нет   │
├───────────────────────────────────────────────────┤
│ nosources-source-map                              │
│   в стеке: имена и строки, без кода               │
│   в проде: карта публична, а исходников в ней нет │
├───────────────────────────────────────────────────┤
│ false                                             │
│   в стеке: минифицированный код                   │
│   в проде: карта не собирается вовсе              │
└───────────────────────────────────────────────────┘
     любое значение для прода, кроме false, замедляет сборку;
        выбор идёт между «удобно читать отчёты об ошибках»
                    и «не отдавать исходники»
```

Три оси компромисса стоит держать раздельно:

- **Точность.** «Cheap» означает отсутствие маппинга колонок — только номера строк. Для отладки JS этого часто достаточно, а для минифицированного кода в одну строку — уже нет. Слово `module` в названии означает, что учитываются карты, произведённые лоадерами, то есть вы увидите исходный TypeScript, а не результат его транспиляции.
- **Скорость.** В dev-режиме важна не первая сборка, а пересборка после сохранения файла. Варианты с `eval` выигрывают именно здесь.
- **Утечка исходников.** Это не паранойя, а частая реальная ошибка. Значение `devtool: 'source-map'` добавляет в конец бандла комментарий со ссылкой на `.map`. Если этот файл лежит рядом на CDN (сети доставки контента), весь исходный код приложения доступен любому. Правильных вариантов для прода два. Вариант `hidden-source-map` собирает карту и загружает её в трекер ошибок вроде Sentry, но ссылки в бандле не оставляет. Вариант `nosources-source-map` делает карту публичной, но без текста исходников: стек читается, код не виден.

```ts
// vite.config.ts — тот же выбор, короче словарь
export default defineConfig({
  build: {
    sourcemap: 'hidden',   // false | true | 'inline' | 'hidden'
  },
});
```

Про сами source maps как формат — в топике Web Performance. Про их роль в отладке в браузере — в главе [Дев-сервер и горячая замена модулей](./07-dev-server-and-hmr.md).

## Методика анализа бандла

```txt
            Порядок анализа бандла: от цифры к причине
┌───────────────────────────────────────────────────────────────┐
│ измерить: собрать прод и посмотреть размеры чанков            │
│                               ↓                               │
│ открыть карту бандла: что занимает место в КАЖДОМ чанке       │
│                               ↓                               │
│ для подозрительного модуля спросить: КТО его импортирует      │
│                               ↓                               │
│ проверить: ESM или CJS, есть ли sideEffects, не barrel ли это │
│                               ↓                               │
│ починить импорт, добавить флаг или заменить зависимость       │
│                               ↓                               │
│ пересобрать и сравнить цифры — иначе это не оптимизация,      │
│ а вера                                                        │
└───────────────────────────────────────────────────────────────┘
         смотреть надо на сжатый размер: 200 КБ в отчёте
         могут оказаться 55 КБ после brotli — и наоборот
```

Инструменты для шага «открыть карту»:

```bash
# Webpack: отчёт со статистикой и интерактивная карта
npx webpack --profile --json=stats.json
npx webpack-bundle-analyzer stats.json

# Vite: визуализатор поверх статистики сборки
npx vite-bundle-visualizer

# любой сборщик: карта по готовым source maps
npx source-map-explorer dist/assets/*.js
```

Ключевой шаг здесь — третий, и его чаще всего пропускают. Увидеть, что `date-fns` занимает 90 килобайт, недостаточно: нужно понять, **кто его туда привёл**.

Webpack отвечает на это в статистике: `stats.json` содержит `reasons` — список модулей, импортирующих данный. Vite и Rollup отвечают в отчёте визуализатора и в предупреждениях о попадании модуля в неожиданный чанк. Без ответа на вопрос «кто импортирует» оптимизация превращается в перебор.

Второе, о чём легко забыть: **сравнивать надо сжатые размеры**. Отчёты обычно показывают три числа — исходный размер, gzip, brotli. Решения принимаются по последним двум, потому что именно их скачивает пользователь. Библиотека с большим количеством повторяющегося кода сжимается в разы, а уже минифицированная и плотная — почти нет.

Разбор двух самых показательных находок на примере `shop-admin`.

**Библиотека дат целиком.** Классика — `moment`, который написан в CJS и подключает все локали разом, из-за чего в бандл приезжает около 300 килобайт там, где нужно форматирование одной даты. Тришейкинг здесь не поможет по двум причинам сразу: CJS не анализируется, а локали подключаются динамически. Решение — не «настроить сборщик», а сменить зависимость на модульную:

```ts
// было: весь moment со всеми локалями
import moment from 'moment';
const label = moment(order.createdAt).format('DD.MM');

// стало: в бандл попадает одна функция
import { format } from 'date-fns';
const label = format(order.createdAt, 'dd.MM');
```

**Полифиллы про запас.** `@babel/preset-env` с широким `browserslist` подключает `core-js` целиком — и получается, что современные браузеры качают эмуляцию возможностей, которые у них есть нативно. Лечится честным списком поддерживаемых браузеров:

```json
// package.json
{
  "browserslist": ["defaults and fully supports es6-module", "not dead"]
}
```

Vite решает это иначе. По умолчанию он собирает под современные браузеры: `build.target` привязан к набору Baseline Widely Available. Поддержка старых браузеров подключается отдельным плагином. То есть по умолчанию вы не платите за полифиллы вообще.

## Типичные ошибки на интервью

- **«Тришейкинг удаляет неиспользуемый код»** — слишком общая формулировка, за которой обычно нет механики. Сильный ответ: сборщик размечает неиспользуемые экспорты, а удаляет их минификатор; без минификации тришейкинга нет.

- **Не знать, почему CJS блокирует тришейкинг.** Ожидаемый ответ — про статичность: `import` разбирается до выполнения, а `require(x)[y]` вычисляется в рантайме, и доказать ненужность экспорта нельзя. Ответ «CJS старый формат» механику не объясняет.

- **Не подозревать, что `tsconfig.json` может убить тришейкинг.** Очень практичный вопрос: `"module": "commonjs"` превращает все импорты в `require` до того, как код попадёт в сборщик. Кандидат, который это знает, обычно сам разбирал реальную проблему с размером бандла.

- **«`sideEffects: false` — просто оптимизация, можно ставить всегда»** — это обещание, за нарушение которого приложение ломается в проде и продолжает работать в dev. Отдельный балл за упоминание, что CSS-импорты нужно перечислять в массиве, иначе стили могут исчезнуть.

- **Путать `usedExports` и `sideEffects`.** Первое работает внутри модуля (выкидывает экспорты), второе — на уровне модулей (позволяет не включать файл и всё его поддерево). Второе эффективнее, и документация Webpack говорит это прямым текстом.

- **«Минификатор убирает пробелы и переименовывает переменные»** — верно, но это малая часть выигрыша. Главное — удаление недостижимых ветвей после подстановки `NODE_ENV`, и умение проследить цепочку `process.env.NODE_ENV !== 'production'` → `'production' !== 'production'` → `if (false)` → пусто отличает понимание от пересказа.

- **`devtool: 'source-map'` в проде без оговорок** — так исходный код приложения выкладывается в открытый доступ. Ожидаемый ответ различает `hidden-source-map` (карта только для трекера ошибок) и `nosources-source-map` (стек читается, кода не видно).

- **Оптимизировать без замеров.** Ответ «я бы посмотрел, что там лежит, и понял, кто это импортирует» звучит гораздо сильнее списка рецептов. И почти всегда выясняется, что проблема не в «тяжёлой библиотеке», а в способе её импорта.
