# Модель Vite

## Главная идея: dev и prod — два разных инструмента под одной обёрткой

Всё остальное в этой статье — следствия одного архитектурного решения. Webpack описывает оба режима одной моделью: собрать граф целиком, а dev-сервер построить поверх той же сборки. Vite задаёт вопрос иначе: **а нужен ли в dev бандл вообще?** Раз браузер умеет ESM, в режиме разработки достаточно уметь отвечать на запрос одного файла.

```txt
            DEV: сервер на нативных ESM                            PROD: полноценная сборка
┌─────────────────────────────────────────────────┐    ┌──────────────────────────────────────────────┐
│ что происходит по шагам                         │    │ что происходит по шагам                      │
│                                                 │    │                                              │
│ 1. старт           пребандлинг зависимостей     │    │ 1. обход           весь граф от index.html   │
│ 2. запрос          браузер просит /src/App.tsx  │    │ 2. трансформация   все модули сразу          │
│ 3. трансформация   один файл, по требованию     │    │ 3. тришейкинг      удаление недостижимого    │
│ 4. ответ           валидный ES-модуль           │    │ 4. чанкование      разбиение и хеши в именах │
│ 5. импорты         браузер сам просит следующие │    │ 5. минификация     минификатор по умолчанию  │
│                                                 │    │                                              │
│ бандла нет         граф целиком не строится     │    │ бандл есть         выполняется ДРУГОЙ код    │
└─────────────────────────────────────────────────┘    └──────────────────────────────────────────────┘
          холодный старт почти не зависит                    по сути та же сборка, что у Webpack,
                 от размера проекта                               просто на другом бандлере
```

Из этой асимметрии растут и главное достоинство Vite, и его главная опасность. И то и другое стоит держать в одной голове: скорость холодного старта почти не зависит от размера проекта — но в dev и в проде выполняется **разный код**.

## Dev: браузер как загрузчик модулей

В dev-режиме Vite — это HTTP-сервер с трансформером. Он не собирает граф: он отвечает на запросы.

```txt
GET /src/routes/Orders.tsx
```

```js
// что примерно отдаёт Vite в ответ
import { jsx as _jsx } from "/node_modules/.vite/deps/react_jsx-runtime.js?v=8f4c1e";
import { fetchOrders } from "/src/lib/api.ts";
import "/src/ui/Button.css";

export function Orders() { /* JSX уже превращён в вызовы */ }
```

Ключевая деталь — **переписывание импортов**. Строку `'react/jsx-runtime'` браузер не понял бы, поэтому Vite на лету выполняет резолвинг (тот самый алгоритм из [The Module Graph and Resolution]) и подставляет путь, по которому браузер сможет сделать запрос. То есть резолвинг не исчез — он просто переехал из этапа сборки в обработку запроса.

**Почему это быстро.** Объём работы пропорционален числу файлов, которые нужны для текущего экрана, а не числу файлов в проекте. Открыли `/orders` — трансформировались модули этого маршрута. Модули `/analytics` не трогали вообще, пока туда не перешли. Отсюда и утверждение «холодный старт почти не зависит от размера проекта»: в проекте на пять тысяч модулей сервер поднимается примерно так же, как в проекте на пятьсот.

**Чем платят.** Число запросов в dev-режиме огромное: панель Network показывает сотни строк вместо десятка. Локально это дёшево (запрос идёт к процессу на той же машине), но не бесплатно — и на очень больших проектах становится заметно. Ответ на эту проблему в Vite 8 — экспериментальный режим полной сборки в dev (`full bundle mode`), в котором заявлены кратно более быстрый старт сервера и на порядок меньше запросов. На момент написания это эксперимент, и статус стоит проверять в документации `vite.dev`, а не считать состоявшимся фактом.

## Предварительная упаковка зависимостей

```txt
           Зачем Vite пребандлит зависимости
┌─────────────────────────────────────────────────────┐
│ в коде: import { debounce } from 'lodash-es'        │
│                          ↓                          │
│ без пребандлинга браузер пошёл бы по графу пакета   │
│                          ↓                          │
│ ≈600 отдельных запросов ради одной функции          │
│                          ↓                          │
│ а CJS-пакет браузер не выполнит вообще              │
│                          ↓                          │
│ пребандлинг: зависимость собирается в один ESM-файл │
│                          ↓                          │
│ результат кешируется в node_modules/.vite           │
│                          ↓                          │
│ браузер делает ОДИН запрос, CJS уже превращён в ESM │
└─────────────────────────────────────────────────────┘
кеш пересобирается при смене lock-файла, патчей, конфига
      или NODE_ENV; принудительно — флагом --force
```

Это самое неочевидное место модели, и вопрос «зачем Vite пребандлит зависимости, если он про нативные ESM?» на интервью работает как хороший фильтр. Причин ровно две, и обе практические:

**1. Interop с CommonJS.** Значительная часть `node_modules` до сих пор публикуется в CJS. Браузер не умеет `module.exports`, и никакие нативные ESM тут не помогут. Пребандлинг превращает такую зависимость в ESM-модуль с нормальными именованными экспортами — включая эвристику, позволяющую писать `import { pick } from 'lodash'` (см. разбор CJS-обёрток в [The Module Graph and Resolution]).

**2. Число запросов.** Пакет вроде `lodash-es` — это сотни мелких файлов. Раздавать их браузеру по одному означает воспроизвести тот самый водопад, из-за которого сборщики и появились ([Why Bundlers Exist]). Одна упакованная зависимость — один запрос.

Кеш живёт в `node_modules/.vite` и отдаётся браузеру с агрессивными заголовками кеширования, а инвалидация делается через версионный параметр в URL (`?v=8f4c1e` в примере выше). Пересборка кеша происходит при изменении lock-файла, патчей, релевантных полей конфига или `NODE_ENV`; принудительно — флагом `--force`.

Когда приходится вмешиваться руками:

```ts
// vite.config.ts
export default defineConfig({
  optimizeDeps: {
    // зависимость, которую Vite не находит при старте
    // (например, она импортируется только внутри другого пакета)
    include: ['chart-lib > date-fns'],
    // локальный пакет монорепозитория: пребандлить его не нужно,
    // иначе правки в нём не будут подхватываться
    exclude: ['@my-org/ui-kit'],
  },
});
```

Сообщение `new dependency optimized, reloading` в консоли — не ошибка, а сигнал, что Vite обнаружил зависимость поздно: она встретилась не при первичном сканировании, а в ленивом маршруте. Один-два раза это нормально, регулярно — повод перечислить такие пакеты в `optimizeDeps.include`.

**Оговорка про версии.** Механизм пребандлинга сохранился, а инструмент под ним менялся: раньше эту работу делал esbuild, в актуальной версии её выполняет Rolldown — тот же бандлер, что собирает прод. Поэтому распространённая формулировка «Vite быстрый в dev, потому что использует esbuild» устарела дважды: сначала она была неточной (esbuild отвечал за пребандлинг и трансформацию, а не за скорость dev-сервера как таковую), а теперь ещё и называет не тот инструмент.

## Prod: обычная полноценная сборка

В прод-режиме никакой магии нет — выполняется всё то, что разбиралось в [Code Splitting and Long-Term Caching] и [Tree Shaking and Optimization]: обход графа целиком, тришейкинг, разбиение на чанки, хеши в именах, минификация.

Что здесь стоит знать про актуальное состояние — и одновременно тот случай, когда важнее сверяться с документацией, чем с чужой статьёй:

- На момент написания прод-сборку выполняет **Rolldown** — Rust-порт Rollup, сохранивший совместимость с его интерфейсом плагинов. До этого связка была другой: бандлером был Rollup, а esbuild отвечал за трансформацию и минификацию. Проверять текущее состояние стоит на `vite.dev` и `rolldown.rs`.
- Отсюда переименования в конфиге: `build.rollupOptions` → `build.rolldownOptions` (прежнее имя работает как алиас), а объектная форма `output.manualChunks` больше не поддерживается — вместо неё `codeSplitting.groups`, разобранный в [Code Splitting and Long-Term Caching].
- Минификатор по умолчанию — из семейства Oxc; `'terser'` доступен, если нужны последние проценты сжатия. Разбор компромисса — в [Tree Shaking and Optimization].
- `build.target` по умолчанию привязан к набору широко поддерживаемых возможностей браузеров, а не к конкретным версиям в конфиге. Практическое следствие: полифиллов по умолчанию нет, и за поддержку старых браузеров отвечает отдельный плагин.

## Конфиг и плагины

```ts
// vite.config.ts — типовой конфиг для shop-admin
import path from 'node:path';
import { defineConfig } from 'vite';
import react from '@vitejs/plugin-react';

export default defineConfig(({ command, mode }) => ({
  plugins: [react()],

  resolve: {
    alias: { '@': path.resolve(__dirname, 'src') },
    dedupe: ['react', 'react-dom'],
  },

  server: {
    port: 5173,
    proxy: {
      '/api': { target: 'http://localhost:3000', changeOrigin: true },
    },
  },

  build: {
    sourcemap: mode === 'staging' ? 'hidden' : false,
    rolldownOptions: {
      output: {
        codeSplitting: {
          groups: [
            { name: 'framework', test: /node_modules[\\/](react|react-dom)/, priority: 40 },
            { name: 'vendor', test: /node_modules/, priority: 20 },
          ],
        },
      },
    },
  },
}));
```

Функциональная форма конфига здесь не для красоты: `command` (`'serve'` или `'build'`) и `mode` — единственный честный способ развести настройки двух режимов, и он же напоминание о том, что режимов действительно два.

**Плагины.** У Vite одна сущность расширения вместо двух — плагин с набором хуков, а не отдельные лоадеры и плагины (сравнение — в [The Webpack Core Model]). Интерфейс унаследован от Rollup: `resolveId`, `load`, `transform`, `generateBundle`. Поверх него добавлены vite-специфичные хуки:

```ts
import type { Plugin } from 'vite';

export function envBanner(): Plugin {
  return {
    name: 'env-banner',
    enforce: 'pre',              // до встроенных плагинов Vite
    apply: 'serve',              // только dev-сервер
    config(userConfig, { mode }) { /* поправить конфиг до его разрешения */ },
    configureServer(server) { /* добавить middleware к dev-серверу */ },
    transformIndexHtml(html) { return html.replace('<!--banner-->', '<div>dev</div>'); },
  };
}
```

Совместимость с экосистемой Rollup — не побочный эффект, а осознанная ставка: она дала Vite готовый набор плагинов с самого начала. Rolldown сохранил тот же интерфейс именно поэтому, и в анонсе Vite 8 совместимость сформулирована как «большинство существующих плагинов работает без изменений». Но «большинство» — не «все»: плагины, залезающие в специфику Rollup глубоко, могут потребовать обновления.

## Статические ресурсы и переменные окружения

```ts
// четыре разных способа получить ресурс — и все нужны
import logoUrl from '@/assets/logo.svg';          // URL с хешем после сборки
import logoRaw from '@/assets/logo.svg?raw';      // содержимое строкой
import iconUrl from '@/assets/icon.png?url';      // всегда URL, без инлайна
import styles from '@/ui/Button.css?inline';      // CSS строкой, без вставки в документ

// динамический путь — только через URL от import.meta.url
const flag = new URL(`./flags/${code}.svg`, import.meta.url).href;
```

Правила, которые стоит запомнить:

- **`public/`** отдаётся с корня в dev и копируется в корень `dist` как есть. Файлы оттуда не проходят через сборку: нет хеша в имени, нет проверки существования. Годится для `robots.txt` и `favicon`, не годится для того, что должно кешироваться навсегда.
- **Мелкие ресурсы инлайнятся** в base64, если меньше порога (`build.assetsInlineLimit`). Это экономит запрос, но раздувает JS-чанк — и потому ломает раздельное кеширование картинки и кода.
- **Путь, собранный строкой, не будет переписан.** Классическая ошибка: `<img src={'/assets/' + name + '.png'} />` работает в dev (файл лежит там, где ожидается) и ломается в проде (файл получил хеш в имени). Конструкция `new URL(..., import.meta.url)` — единственный способ, который сборщик умеет анализировать, и то при статически видимой части пути.

Переменные окружения устроены иначе, чем в Webpack, и это главный источник миграционных грабель:

```ts
// в браузерном коде доступно ТОЛЬКО это
import.meta.env.VITE_API_URL      // ваши переменные — с обязательным префиксом VITE_
import.meta.env.MODE              // текущий режим
import.meta.env.PROD              // boolean
import.meta.env.DEV               // boolean
import.meta.env.BASE_URL          // базовый путь приложения

// process.env в браузере не существует — это Node API
```

Порядок загрузки `.env`-файлов: `.env` → `.env.local` → `.env.[mode]` → `.env.[mode].local`, где более специфичный перекрывает менее специфичный, а уже установленные переменные окружения имеют высший приоритет и не перезаписываются. Префикс настраивается через `envPrefix`.

Про префикс важно понимать не механику, а смысл: **он существует, чтобы вы не выложили секреты в бандл случайно.** Всё, что попало в `VITE_*`, оказывается в исходном коде на клиенте — документация предупреждает об этом прямым текстом. Токен доступа к платёжному API в переменной с этим префиксом — это не «настройка», а инцидент.

## За что платят: класс багов «в dev работает, в проде сломалось»

```txt
                            Класс багов «в dev работает, в проде сломалось»
┌───────────────────────────────┬────────────────────────────────────┬─────────────────────────────────┐
│ симптом                       │ причина                            │ как поймать заранее             │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ в проде пустой экран          │ CJS-пакет жил за счёт пребандлинга │ прод-сборка в CI на каждый PR   │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ стили пропали                 │ sideEffects: false плюс тришейкинг │ открывать vite preview локально │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ process is not defined        │ в браузере process не существует   │ перейти на import.meta.env      │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ другой порядок инициализации  │ объединение модулей меняет порядок │ убрать циклы в графе            │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ ошибки типов доехали до прода │ Vite не проверяет типы вообще      │ tsc --noEmit отдельным шагом    │
├───────────────────────────────┼────────────────────────────────────┼─────────────────────────────────┤
│ ассет не нашёлся              │ путь к файлу собирался строкой     │ new URL(..., import.meta.url)   │
└───────────────────────────────┴────────────────────────────────────┴─────────────────────────────────┘
                      общий корень у всех строк один: в dev и в проде выполняется
                            РАЗНЫЙ код, и dev проверяет меньше, чем кажется
```

Две строки заслуживают отдельного внимания, потому что удивляют даже опытных.

**Vite не проверяет типы.** TypeScript обрабатывается как транспиляция: типы просто вырезаются из кода. Никакой проверки при этом не происходит — файл с ошибкой типов спокойно превратится в рабочий JS и уедет в прод. Это осознанное решение (проверка типов медленная и не нужна на каждое сохранение), но оно означает, что `tsc --noEmit` обязан быть отдельным шагом в CI. Разработчики, привыкшие к `ts-loader`, который падал на ошибке типов, попадают в эту ловушку регулярно.

**CJS-пакет, выживший за счёт пребандлинга.** В dev зависимость прошла через пребандлинг и получила аккуратные ESM-экспорты. В проде пребандлинга нет — сборка идёт по общему пути, и та же зависимость может дать `does not provide an export named` или пустой объект вместо модуля. Это ровно тот случай, когда dev-режим оказался *добрее* прода.

Практический вывод один и он простой: **прод-сборка должна выполняться в CI на каждый pull request**, а перед релизом её результат стоит открыть локально через `vite preview`. Асимметрия dev и prod — не повод не использовать Vite, но повод не считать зелёный dev-сервер доказательством работоспособности.

## Когда Vite — не решение

```txt
                                           Когда Vite — не решение
┌───────────────────────────────┬──────────────────────────────────────┬────────────────────────────────────┐
│ ситуация                      │ в чём именно проблема                │ что рассматривать вместо           │
├───────────────────────────────┼──────────────────────────────────────┼────────────────────────────────────┤
│ самописные webpack-плагины    │ API compiler/compilation несовместим │ Rspack: конфиг почти без правок    │
├───────────────────────────────┼──────────────────────────────────────┼────────────────────────────────────┤
│ Module Federation как основа  │ зрелая экосистема — вокруг webpack   │ взвесить зрелость плагина для Vite │
├───────────────────────────────┼──────────────────────────────────────┼────────────────────────────────────┤
│ поддержка старых браузеров    │ дефолтный target — современный       │ плагин legacy и его цена в размере │
├───────────────────────────────┼──────────────────────────────────────┼────────────────────────────────────┤
│ монолитный legacy-конфиг      │ инлайн-лоадеры, самописные правила   │ миграция по частям или Rspack      │
├───────────────────────────────┼──────────────────────────────────────┼────────────────────────────────────┤
│ нужна идентичность dev и prod │ две модели — это по конструкции      │ Webpack или Rspack: одна модель    │
└───────────────────────────────┴──────────────────────────────────────┴────────────────────────────────────┘
                             ни одна строка не про «Vite хуже» — все про то, что
                                   выигрыш в скорости имеет конкретную цену
```

Подробнее по двум пунктам, где чаще всего ошибаются в оценке.

**Самописные webpack-плагины.** Если в проекте есть плагин, работающий с `compilation` — правящий граф, генерирующий ассеты на основе всей сборки, вмешивающийся в чанкование, — переписать его под интерфейс Rollup не всегда возможно, а не только трудоёмко: моделей две, и они не изоморфны. Здесь честный ответ — смотреть на Rspack, который совместим с webpack-конфигами и плагинами и даёт выигрыш в скорости без смены модели ([Ecosystem and Choosing a Tool]).

**Module Federation.** Механизм придуман в экосистеме Webpack, и большая часть накопленного опыта и инструментов — оттуда. Для Vite существуют плагины, а в анонсе Vite 8 единый бандлер прямо назван тем, что «открывает» поддержку Module Federation. Но состояние здесь меняется быстро: часть решений зрелые, часть — на подходе. Если Module Federation — фундамент архитектуры, а не деталь, оценивать нужно конкретную реализацию на конкретной версии, а не общий тренд. Сам механизм разбирается обзорно в [Ecosystem and Choosing a Tool] и подробно — в курсе NX.

## Типичные ошибки на интервью

- **«Vite быстрый, потому что он на Rust»** (или «потому что на esbuild») — самая частая ошибка в теме и хороший фильтр. Быстрый язык даёт кратное ускорение отдельных шагов, но главный выигрыш даёт **смена задачи**: в dev граф целиком не строится, работа пропорциональна открытому экрану, а не размеру проекта. Ответ, который начинается с языка реализации, показывает, что человек читал заголовки, а не разбирался.

- **«В Vite нет сборки»** — в dev нет, в проде есть, и она полноценная: тришейкинг, чанкование, минификация, хеши. Кандидат, который этого не разделяет, обычно не сталкивался и с багами «в проде сломалось».

- **Не уметь ответить, зачем нужен пребандлинг.** Ожидаемых причин две: CJS-пакеты, которые браузер не выполнит, и число запросов при раздаче пакета по файлам. Ответ «для скорости» без уточнения механики — половина балла.

- **«Vite проверяет типы, ведь он понимает TypeScript»** — не проверяет. Типы вырезаются, ошибки не диагностируются, `tsc --noEmit` нужен отдельно. Это практическая ловушка, на которой ловятся живые проекты, а не абстрактный факт.

- **`process.env` в браузерном коде** — маркер того, что человек переносит привычки Webpack. В Vite это `import.meta.env` с префиксом `VITE_`, и заодно уместно упомянуть, что переменные с этим префиксом попадают в бандл, а значит, секретов там быть не должно.

- **Уверенные утверждения о том, «на чём Vite собирает прод».** Именно этот пункт менялся дважды за короткое время. Сильная формулировка звучит как «в версии, с которой я работал, это делал такой-то бандлер; актуальное состояние стоит смотреть в документации» — и она честнее уверенно названной устаревшей детали.

- **«Vite всегда лучше Webpack»** — на senior-интервью ценится обратное: способность назвать случаи, где Vite не подходит (самописные плагины на `compilation`, Module Federation как фундамент, требование идентичности dev и prod, старые браузеры) и назвать альтернативу вроде Rspack. Ответ без единого «не подходит» читается как отсутствие опыта миграций.
