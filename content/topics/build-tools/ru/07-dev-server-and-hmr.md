# Дев-сервер и горячая замена модулей

## HMR по сути: подменить модуль в работающем приложении

Формулировка, которую стоит держать в голове: **горячая замена модулей — это подмена кода одного модуля в уже запущенном приложении, без потери его состояния.** Не «быстрая перезагрузка» и не «автообновление страницы» — принципиально другая операция.

```txt
                Хот-релоад и перезагрузка страницы — это разные вещи
┌──────────────────────────┬────────────────────────┬─────────────────────────────┐
│ критерий                 │ live reload            │ HMR                         │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ что делает               │ перезагружает страницу │ подменяет модуль на месте   │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ состояние приложения     │ теряется               │ сохраняется                 │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ скролл, открытая модалка │ теряется               │ сохраняется                 │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ что летит по сети        │ сигнал «перезагрузись» │ код изменённого модуля      │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ нужна поддержка в коде   │ нет                    │ да: граница accept          │
├──────────────────────────┼────────────────────────┼─────────────────────────────┤
│ если границы нет         │ —                      │ откат к полной перезагрузке │
└──────────────────────────┴────────────────────────┴─────────────────────────────┘
           смысл HMR не в скорости самой по себе, а в том, что состояние
          приложения — заполненная форма, открытый шаг визарда — выживает
```

Разница особенно наглядна на живом сценарии: вы отлаживаете третий шаг визарда оформления заказа. Live reload вернёт вас на первый шаг с пустой формой, и каждую правку стилей придётся оплачивать повторным заполнением полей. HMR подменит стили, оставив вас там же, где вы были. Именно в этом ценность, а не в сэкономленных миллисекундах.

Важное следствие: **HMR требует поддержки в коде.** Кто-то должен объяснить рантайму, что делать с новой версией модуля: пересоздать компонент, перерисовать стили, заново подписать слушателя. Само по себе это не происходит.

## Граница принятия обновления и всплытие по графу

Механизм строится на одном примитиве — модуль может объявить, что умеет принять свою новую версию:

```ts
// Vite
if (import.meta.hot) {
  import.meta.hot.accept((newModule) => {
    // сюда приедет обновлённый модуль; решаем, что с ним делать
    applyTheme(newModule.theme);
  });
}
```

```js
// Webpack — тот же смысл, другой словарь
if (module.hot) {
  module.hot.accept('./theme', () => {
    applyTheme(require('./theme').theme);
  });
}
```

Модуль, объявивший `accept`, называется **границей** обновления. Дальше работает простое правило:

```txt
     Как обновление всплывает по графу до границы
┌───────────────────────────────────────────────────┐
│ изменён ui/Button.tsx — новый код модуля готов    │
│                         ↓                         │
│ есть ли accept в самом модуле? нет                │
│                         ↓                         │
│ поднимаемся к импортёру: routes/Orders.tsx        │
│                         ↓                         │
│ accept есть — его поставил Fast Refresh → ГРАНИЦА │
│                         ↓                         │
│ модуль подменён, состояние компонента цело        │
└───────────────────────────────────────────────────┘
если границы не окажется ни у одного импортёра, всплытие
дойдёт до точки входа — и это будет полная перезагрузка
```

Почему всплытие вверх, а не вниз, — вопрос логики, а не реализации. Если модуль изменился, но сам не знает, как себя переустановить, единственный, кто может это сделать, — тот, кто его импортировал: он держит ссылку и может взять новую версию. Не может и он — идём к его импортёру. Дойдя до точки входа без границы, рантайм честно сдаётся и перезагружает страницу.

Отсюда — **главный практический вывод всей статьи**: полная перезагрузка вместо HMR почти никогда не означает «HMR сломан». Она означает, что на пути от изменённого файла до точки входа не нашлось ни одного модуля, готового принять обновление.

Помимо `accept` в API есть ещё три полезных примитива:

```ts
if (import.meta.hot) {
  // убрать за прошлой версией модуля: таймеры, слушатели, подписки
  import.meta.hot.dispose(() => clearInterval(timer));

  // перенести данные в новую версию модуля
  import.meta.hot.data.scrollTop = el.scrollTop;

  // «я принял обновление, но понял, что не справлюсь» — отдать выше
  if (!canHandle(newModule)) import.meta.hot.invalidate();
}
```

`dispose` — самый недооценённый из них. Если модуль на верхнем уровне запускает таймер или подписывается на событие, а `dispose` не написан, каждая горячая замена оставляет прошлую версию работать. Симптом узнаваемый: после десяти правок запрос уходит на сервер десять раз вместо одного. Это не «баг HMR», а незакрытый ресурс.

## Как это устроено в Webpack и в Vite

```txt
   WEBPACK: пересборка затронутого            VITE: один файл по запросу
┌───────────────────────────────────┐    ┌──────────────────────────────────┐
│ после сохранения файла            │    │ после сохранения файла           │
│                                   │    │                                  │
│ 1   watcher заметил изменение     │    │ 1   watcher заметил изменение    │
│ 2   пересборка затронутых модулей │    │ 2   модуль помечен устаревшим    │
│ 3   генерация hot-update файлов   │    │ 3   сообщение по WebSocket       │
│ 4   сообщение по WebSocket        │    │ 4   браузер просит ОДИН модуль   │
│ 5   браузер качает hot-update     │    │ 5   трансформация одного файла   │
│ 6   рантайм подменяет модуль      │    │ 6   граница accept применяет его │
└───────────────────────────────────┘    └──────────────────────────────────┘
   работа зависит от того, сколько           работа не зависит от размера
     модулей затронула пересборка             проекта: файл всегда один
```

Модель обновления в обоих случаях одна и та же — граница `accept`, всплытие, откат к перезагрузке. Различается то, **сколько работы нужно сделать, чтобы обновление доехало.**

**Webpack** держит собранный граф в памяти и после изменения файла пересобирает затронутую часть. Затронутая часть — это не один файл: если изменённый модуль входит в чанк, требуется пересчитать чанк, а при использовании объединения модулей — и соседей. Результат записывается в служебные файлы обновления (`.hot-update.json` и `.hot-update.js`), про которые браузеру сообщают по WebSocket. Отсюда важное свойство: время реакции растёт вместе с проектом, потому что растёт объём пересборки.

**Vite** не держит бандла, поэтому и пересобирать нечего. Он помечает модуль устаревшим, отправляет в браузер сообщение, а браузер запрашивает **ровно один** модуль — который трансформируется по требованию, как и любой другой запрос в dev-режиме ([The Vite Model]). Объём работы не зависит ни от размера проекта, ни от того, в каком чанке модуль оказался бы в проде.

Именно это, а не язык реализации, объясняет, почему у Vite обновление почти мгновенно и на маленьком, и на большом проекте. Формулировка для интервью: **Webpack пересобирает затронутое, Vite инвалидирует один модуль и отдаёт его по запросу.**

Стоит отметить и то, что не различается: если в вашем коде нет ни одной границы `accept`, оба инструмента будут просто перезагружать страницу. Магии «HMR из коробки» не существует — её обеспечивает интеграция с фреймворком, и для React это Fast Refresh.

## Fast Refresh для React и его правила

Fast Refresh — это плагин (в Vite — `@vitejs/plugin-react`, в Webpack — `react-refresh-webpack-plugin`), который автоматически ставит `accept` в файлы с React-компонентами и умеет пересоздать компонент, сохранив его состояние. То есть он и есть тот механизм, который делает границы обновления за вас.

Но он работает по правилам, и когда правила нарушены, состояние теряется — без всякого сообщения об ошибке.

```txt
                  Fast Refresh: почему состояние компонента терялось
┌───────────────────────────┬────────────────────────┬───────────────────────────────┐
│ что в файле               │ что произойдёт         │ почему                        │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ function Button() { … }   │ состояние сохранится   │ компонент опознан по имени    │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ export default () => …    │ состояние потеряется   │ анонимную функцию не опознать │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ function example() { … }  │ состояние потеряется   │ имя не в PascalCase           │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ class Button extends …    │ состояние сбросится    │ классы не поддерживаются      │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ добавили или убрали хук   │ состояние сбросится    │ изменился порядок хуков       │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ в файле есть не-компонент │ обновление уйдёт вверх │ файл больше не граница        │
├───────────────────────────┼────────────────────────┼───────────────────────────────┤
│ export * from …           │ не поддерживается      │ состав экспортов не виден     │
└───────────────────────────┴────────────────────────┴───────────────────────────────┘
             практический вывод: один файл — один компонент, объявленный
              именованной функцией; константы и хелперы держать отдельно
```

Три правила из этой таблицы стоит разобрать подробнее, потому что они встречаются каждый день.

**Компонент должен быть опознаваем.** Fast Refresh связывает состояние с компонентом по его идентичности, а идентичность выводит из имени. Анонимная функция такой идентичности не имеет:

```tsx
// ❌ состояние будет теряться при каждой правке
export default () => <OrdersTable />;

// ✅ то же самое, но с именем
function Orders() {
  return <OrdersTable />;
}
export default Orders;
```

По той же причине имя должно быть в PascalCase: `function orders()` для React не компонент, а обычная функция.

**Файл должен экспортировать только компоненты.** Это самое неочевидное правило и самая частая причина неожиданных полных перезагрузок:

```tsx
// ❌ Orders.tsx перестаёт быть границей обновления
export const ORDERS_PER_PAGE = 20;
export function Orders() { /* ... */ }
```

Fast Refresh не может гарантировать, что подмена модуля безопасна, если из файла торчит константа: её мог использовать кто угодно, и просто пересоздать компонент недостаточно. Поэтому граница пропадает и обновление всплывает выше. Лечится вынесением не-компонентов в отдельный файл; поймать такие места заранее помогает `eslint-plugin-react-refresh`, который ровно об этом и предупреждает.

**Изменение хуков сбрасывает состояние.** И это правильно: состояние хуков хранится позиционно, поэтому если вы добавили `useState` в середину компонента, старое состояние уже не соответствует новому коду. Fast Refresh честно сбрасывает его вместо того, чтобы подсунуть значения не в те переменные. Классовые компоненты по той же причине всегда перемонтируются: сохранять их состояние Fast Refresh не умеет в принципе.

## Прокси к бэкенду и CORS в дев-режиме

В проде фронтенд и API обычно живут на одном домене (или API за тем же CDN), и вопроса CORS не возникает. В dev-режиме приложение работает на `localhost:5173`, а API — на `localhost:3000`, и это разные origin: браузер начинает требовать CORS-заголовки от бэкенда.

Правильное решение — не разрешать CORS ради разработки, а сделать так, чтобы разных origin не было: dev-сервер сам проксирует запросы к API.

```ts
// vite.config.ts
export default defineConfig({
  server: {
    proxy: {
      '/api': {
        target: 'http://localhost:3000',
        changeOrigin: true,                          // подменить заголовок Host
        rewrite: (path) => path.replace(/^\/api/, ''), // если у бэкенда нет префикса /api
      },
    },
  },
});
```

```js
// webpack.config.js — та же задача; обратите внимание на форму записи
module.exports = {
  devServer: {
    port: 8080,
    // в webpack-dev-server 5 proxy — МАССИВ, объектная форма из v4 больше не работает
    proxy: [
      {
        context: ['/api'],
        target: 'http://localhost:3000',
        changeOrigin: true,
      },
    ],
    historyApiFallback: true,   // SPA: отдавать index.html вместо 404
    hot: true,                  // включено по умолчанию
  },
};
```

Форма `proxy` — практическая ловушка при обновлении: в четвёртой версии `webpack-dev-server` это был объект, в пятой — массив объектов, и старый конфиг просто перестаёт работать.

Две настройки рядом заслуживают упоминания, потому что о них спрашивают:

- **`historyApiFallback`** (в Vite такое поведение включено для SPA по умолчанию) — отдавать `index.html` на любой путь. Без этого перезагрузка страницы на `/orders/42` даёт 404: файла с таким путём не существует, маршрутизация живёт в клиенте.
- **`hot: 'only'`** в Webpack — не откатываться к полной перезагрузке, если обновление применить не удалось. Полезно, когда сохранение состояния важнее актуальности экрана.

Отдельно про то, чего проксирование не решает: **это только dev-режим.** Если приложение в проде обращается к API на другом домене, CORS придётся настраивать на бэкенде по-настоящему, и dev-прокси эту работу скрывает, а не выполняет. Классический баг «в dev работает, в проде CORS» — из того же семейства, что и остальные различия dev и prod ([The Vite Model]). Механика самих CORS-заголовков разбирается в топиках HTTP/REST и Security.

## Source maps в дев-режиме

В dev у карт кода другой приоритет, чем в проде: там важна не полнота, а скорость **пересборки** — карта перестраивается на каждое сохранение.

```js
// webpack.config.js — разумный дев-дефолт
module.exports = {
  mode: 'development',
  devtool: 'eval-cheap-module-source-map',
};
```

Расшифровка названия: `eval` — код модулей выполняется через `eval` с указанием источника (быстро), `cheap` — маппинг только по строкам, без колонок, `module` — учитываются карты, произведённые лоадерами, то есть в стеке будет ваш TypeScript, а не результат его транспиляции. Полная таблица вариантов и компромиссов — в [Tree Shaking and Optimization].

У Vite отдельной настройки для dev нет: карты в dev-режиме включены, потому что трансформируется по одному файлу и делать их дёшево. Настраивается только прод — через `build.sourcemap`.

Практическая проверка, которую стоит сделать один раз на проекте: поставить точку останова в TSX-файле и убедиться, что отладчик показывает исходник с нормальными именами. Если вместо этого видно транспилированный код — значит, выбран вариант без `module`, и отлаживать будет мучительно.

## Диагностика: HMR не срабатывает

```txt
                                             Диагностика: HMR не срабатывает
┌──────────────────────────────────┬───────────────────────────────────┬─────────────────────────────────────────────────┐
│ симптом                          │ вероятная причина                 │ что проверить                                   │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ страница перезагружается целиком │ на пути вверх нет границы accept  │ файл экспортирует не только компонент           │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ состояние теряется без релоада   │ Fast Refresh не опознал компонент │ анонимный export default, класс, хуки           │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ вообще ничего не происходит      │ watcher не видит изменение файла  │ Docker, WSL, сетевой диск: опрос вместо событий │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ код новый, поведение старое      │ старый эффект не убран            │ таймеры, слушатели, подписки в dispose          │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ new dependency optimized         │ зависимость найдена поздно        │ перечислить в optimizeDeps.include              │
├──────────────────────────────────┼───────────────────────────────────┼─────────────────────────────────────────────────┤
│ в консоли ошибка WebSocket       │ соединение не дошло до сервера    │ прокси, https, порт и хост HMR-клиента          │
└──────────────────────────────────┴───────────────────────────────────┴─────────────────────────────────────────────────┘
                                 порядок разбора: сначала «доехало ли обновление вообще»,
                             потом «нашлась ли граница», и только потом правила Fast Refresh
```

Порядок важен, потому что симптомы похожи, а причины лежат на разных уровнях. Правильная последовательность:

**1. Доехало ли обновление до браузера?** Открыть консоль и посмотреть, появляется ли сообщение об обновлении после сохранения файла. Если тишина — проблема не в HMR, а в наблюдении за файлами или в соединении. Типичные виновники: код в Docker-контейнере или на смонтированном диске, где события файловой системы не пробрасываются, — лечится переключением на опрос (`server.watch.usePolling` в Vite, `watchOptions.poll` в Webpack, с оговоркой, что опрос ест процессор). Второй виновник — WebSocket не подключился: приложение открыто через собственный прокси или https, и клиенту нужно явно указать, куда стучаться (`server.hmr.clientPort`, `server.hmr.protocol`).

**2. Нашлась ли граница?** Если сообщение есть, но страница перезагружается целиком, значит, всплытие дошло до корня. Начинать надо не с настроек, а с изменённого файла: экспортирует ли он что-то кроме компонентов, нет ли в цепочке barrel-файла, не менялся ли файл, который импортируют все (например, конфиг темы) — обновление такого модуля закономерно приводит к перезагрузке.

**3. Правила Fast Refresh.** Если страница не перезагружается, но состояние всё равно теряется — дело в опознавании компонента: анонимный `export default`, имя не в PascalCase, классовый компонент, изменённый набор хуков.

**4. Незакрытые ресурсы.** Отдельный симптом: код обновился, а ведёт себя странно — запросы дублируются, обработчики срабатывают по нескольку раз. Это `dispose`, которого нет.

Финальная оговорка, которую полезно произнести вслух: **HMR — инструмент разработки, а не проверки корректности.** Приложение, живущее в браузере два часа под сотней горячих замен, находится в состоянии, которого не бывает у пользователя. Если поведение выглядит необъяснимым, первое, что стоит сделать, — перезагрузить страницу и проверить, воспроизводится ли проблема на чистом старте.

## Типичные ошибки на интервью

- **«HMR — это когда страница автоматически перезагружается»** — это live reload, и путаница здесь встречается часто. Ключевое отличие в одном слове: **состояние**. HMR подменяет модуль в работающем приложении, live reload перезапускает приложение целиком.

- **Не знать, почему вместо HMR происходит полная перезагрузка.** Ожидаемый ответ — про всплытие: обновление ищет вверх по графу модуль с `accept`, и если не находит до точки входа, откатывается к перезагрузке. Ответ «значит, HMR не настроен» без механики слабый.

- **«Vite быстрее обновляет, потому что он на Rust»** — снова не про то. Причина в объёме работы: Webpack пересобирает затронутую часть графа, а Vite инвалидирует один модуль и трансформирует его по запросу. Отсюда и независимость от размера проекта.

- **«Fast Refresh — часть React»** — это отдельная интеграция сборщика (плагин), которая автоматически расставляет границы `accept`. Без неё HMR в React-проекте сводился бы к перезагрузке страницы.

- **Не уметь объяснить, почему потерялось состояние компонента.** Это самый практичный вопрос темы, и хороший ответ перечисляет конкретные причины: анонимный `export default`, имя не в PascalCase, классовый компонент, изменённый набор хуков, экспорт не-компонента из файла. Последний пункт знают реже всего, а встречается он чаще всего.

- **Разрешать CORS на бэкенде ради локальной разработки** — работающее, но неправильное решение: оно ослабляет прод ради dev. Ожидаемый ответ — прокси на dev-сервере, плюс понимание, что прокси проблему CORS в проде не решает, а прячет.

- **Не знать про `dispose`.** Вопрос «после десяти правок запрос уходит десять раз — почему?» отлично отделяет тех, кто писал HMR-обработчики руками, от тех, кто пользовался готовыми. Ответ — прошлые версии модуля оставили после себя таймеры и подписки.

- **Считать поведение под HMR эквивалентным чистой загрузке.** Долго живущее приложение после множества горячих замен — это состояние, которого у пользователя не бывает. Перед серьёзной отладкой страницу надо перезагрузить.
