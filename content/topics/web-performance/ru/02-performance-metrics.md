# Performance Metrics: TTFB, FCP, TTI, TBT

## Диагностические метрики vs. пользовательские метрики

Эта статья — про четыре **диагностические метрики**. TTFB (Time to First Byte) и FCP (First Contentful Paint) описывают, как быстро что-то появляется. TTI (Time to Interactive) и TBT (Total Blocking Time) описывают, как долго страница остаётся неотзывчивой.

Core Web Vitals отвечают на другой вопрос: как страницу ощущает пользователь? Это три метрики: LCP (Largest Contentful Paint), CLS (Cumulative Layout Shift) и INP (Interaction to Next Paint). Диагностическая четвёрка отвечает на следующий вопрос: *почему* ощущение именно такое. Core Web Vitals говорят, что страница медленная, а TTFB, FCP, TTI и TBT говорят, где копать.

Типичный сеанс оптимизации выглядит так. Lighthouse показывает LCP 5.2 секунды и называет результат плохим, и вы открываете диагностику:

- **TTFB = 2.1 с** — сервер медленный.
- **FCP = 2.8 с** — ждал TTFB плюс рендер-блокирующие ресурсы.
- **TBT = 850 мс** — тяжёлый JS после загрузки.
- **TTI = 6.3 с** — страница не интерактивна из-за TBT.

Порядок работ следует из этих чисел. Сначала чинить TTFB, он самый дорогой. Потом рендер-блокирующие ресурсы, потом JS-бандл.

## TTFB — Time to First Byte

### Что именно измеряется

TTFB — время от начала навигации до **первого байта тела HTTP-ответа** от сервера. Навигация начинается, когда пользователь ввёл URL или кликнул по ссылке. Это время складывается из шести частей:

- время редиректов;
- запрос к DNS (система доменных имён);
- установка соединения TCP (протокол управления передачей);
- рукопожатие TLS (протокол защиты транспортного уровня);
- request time — время, за которое запрос долетает до сервера;
- server processing плюс response start — самая "управляемая" часть, в которую входят рендер страницы, запросы к базе данных и остальное.

Ту же разбивку видно в DevTools: Network → кликнуть на документ → вкладка Timing.

| Оценка | TTFB |
|---|---|
| ✅ Хорошо | меньше 800 мс |
| ⚠️ Требует работы | 800 мс — 1800 мс |
| ❌ Плохо | больше 1800 мс |

Здесь важен один нюанс. Lighthouse измеряет TTFB для первого HTML-документа. TTFB для API-запросов — отдельная история, потому что при keep-alive соединении нет ни редиректа, ни обращения к DNS.

### Главные причины плохого TTFB

1. **Нет CDN (сеть доставки контента).** Пользователь в Токио получает ответ от сервера в Вирджинии. Это примерно 150 мс только на круговую задержку, умноженные на два-три из-за TLS-рукопожатия — 300–450 мс ещё до начала обработки на сервере.
2. **Медленная обработка на сервере.** Типичные формы: ORM (объектно-реляционный маппер) генерирует N+1 запросов к базе данных. Нет кэширования результатов в Redis или в памяти. Холодные старты serverless-функций вроде Lambda или Vercel Edge.
3. **Редиректы.** Цепочка `HTTP → HTTPS → www` стоит трёх дополнительных круговых задержек до того, как браузер получит реальный контент.
4. **Нет HTTP/2.** Несколько параллельных ресурсов требуют каждый своего TCP-соединения, и начинается head-of-line blocking.

### Оптимизация TTFB

```ts
// ❌ SSR без кэша — каждый запрос пересчитывает страницу
export async function getServerSideProps() {
  const posts = await db.post.findMany({ take: 10 });
  return { props: { posts } };
}

// ✅ stale-while-revalidate через заголовки —
// CDN отдаёт кэшированный ответ, фоном обновляет
export async function getServerSideProps({ res }) {
  res.setHeader(
    'Cache-Control',
    'public, s-maxage=60, stale-while-revalidate=600'
  );
  const posts = await db.post.findMany({ take: 10 });
  return { props: { posts } };
}
```

```ts
// ✅ Streaming SSR (React 18) — первый байт HTML приходит
// немедленно, контент стримится по мере готовности
// (Next.js App Router делает это автоматически)
import { Suspense } from 'react';

export default function Page() {
  return (
    <>
      <Header />           {/* отправляется немедленно */}
      <Suspense fallback={<Skeleton />}>
        <SlowComponent />  {/* стримится когда готов */}
      </Suspense>
    </>
  );
}
```

```ts
// ✅ Кэширование на уровне приложения (Redis)
import { Redis } from 'ioredis';

const redis = new Redis(process.env.REDIS_URL!);

async function getPageData(slug: string) {
  const cached = await redis.get(`page:${slug}`);
  if (cached) return JSON.parse(cached);

  const data = await db.page.findUnique({ where: { slug } });
  await redis.setex(`page:${slug}`, 300, JSON.stringify(data)); // 5 min TTL
  return data;
}
```

**Диагностика TTFB в DevTools.** Откройте вкладку Network, кликните на главный HTML-документ и перейдите в Timing. Строка `Waiting for server response` — это время обработки на сервере, а `Initial connection` плюс `SSL` — сетевые задержки. Если строка ожидания больше 500 мс, проблема на сервере. Если `Initial connection` больше 200 мс, нет ни CDN, ни keep-alive.

## FCP — First Contentful Paint

### Что именно измеряется

FCP фиксирует момент, когда браузер отрисовывает **любой** контент из DOM (объектная модель документа). Текст, изображение, рисунок SVG (масштабируемая векторная графика), canvas — считается всё, что не белый экран.

FCP — это не LCP. FCP означает, что на экране появилось хоть что-то, а LCP означает, что отрисован самый важный контент. Лоадер-спиннер может быть FCP, а реальный контент появится позже и станет LCP.

Именно этот разрыв делает FCP полезным для диагностики. Если FCP быстрый, а LCP медленный, проблема в загрузке конкретного LCP-ресурса: картинки или шрифта. Общая скорость отдачи HTML при этом в порядке.

| Оценка | FCP |
|---|---|
| ✅ Хорошо | меньше 1.8 сек |
| ⚠️ Требует работы | 1.8 — 3.0 сек |
| ❌ Плохо | больше 3.0 сек |

### Что блокирует FCP — рендер-блокирующие ресурсы

Браузер **не рисует ничего** пока не загружены все CSS и синхронные JS-скрипты в `<head>`.

```html
<!-- ❌ Внешний CSS в <head> — блокирует рендер полностью
     пока не скачается (даже если стили только для футера) -->
<head>
  <link rel="stylesheet" href="https://cdn.example.com/styles.css" />
  <script src="/analytics.js"></script>  <!-- тоже блокирует -->
</head>
```

```html
<!-- ✅ Critical CSS inline + defer для остального -->
<head>
  <style>
    /* Только стили первого экрана — inline */
    header { background: #fff; }
    .hero { min-height: 100vh; }
  </style>

  <!-- defer: JS выполнится после парсинга HTML, не блокирует FCP -->
  <script defer src="/main.js"></script>

  <!-- async: независимый скрипт, не блокирует HTML-парсинг -->
  <script async src="/analytics.js"></script>

  <!-- Некритичный CSS — загружается асинхронно -->
  <link
    rel="preload"
    as="style"
    href="/non-critical.css"
    onload="this.rel='stylesheet'"
  />
</head>
```

```ts
// Измерение FCP в поле (реальные пользователи)
import { onFCP } from 'web-vitals';

onFCP((metric) => {
  // metric.value — в миллисекундах
  sendToAnalytics({ name: 'FCP', value: metric.value });
});
```

Ключевая диагностика FCP в Lighthouse:

- **Eliminate render-blocking resources** — главный аудит. Он показывает конкретные адреса и сколько миллисекунд стоит каждый из них.
- **Minify CSS** и **Remove unused CSS** — тоже влияют, потому что большая таблица стилей дольше скачивается и парсится.

### FCP и Server-Side Rendering

**CSR (client-side rendering — рендеринг на клиенте), как в Create React App.** Между TTFB и FCP браузер получает пустой HTML-документ и `bundle.js`. Между FCP и LCP выполняется JS, и React отрисовывает DOM. Поэтому FCP — это пустой экран или минимальный скелетон, а разрыв между FCP и LCP **долгий**.

**SSR (server-side rendering — рендеринг на сервере), как в `getServerSideProps`.** Между TTFB и FCP браузер получает готовый HTML, поэтому FCP уже показывает реальный контент. Плата за это — более высокий TTFB, потому что рендер оплачивает сервер.

**SSG (static site generation — статическая генерация).** HTML собран заранее, и CDN отдаёт его мгновенно, что даёт оптимальный TTFB **и** FCP. Плата за это — нет персонализации без гидратации.

## TTI — Time to Interactive

### Что означает "интерактивный" технически

TTI — момент, после которого страница **надёжно реагирует на взаимодействия в пределах 50ms**. Lighthouse считает его так, упрощённо:

1. Найти FCP — отсюда начинается поиск.
2. Искать "тихое окно" длиной пять секунд. Внутри него не должно быть Long Tasks, то есть задач дольше 50 мс на главном потоке. И не больше двух параллельных сетевых запросов.
3. TTI — начало этого тихого окна, то есть конец последней Long Task перед пятисекундным окном.

Между FCP и TTI страница **видна, но не реагирует**: клики буферизуются или игнорируются.

| Оценка | TTI |
|---|---|
| ✅ Хорошо | меньше 3.8 сек |
| ⚠️ Требует работы | 3.8 — 7.3 сек |
| ❌ Плохо | больше 7.3 сек |

Отличие TTI от FCP — как раз то, что бьёт на практике. Пользователь **видит** контент, то есть FCP уже наступил, тапает кнопку — и ничего не происходит, потому что JS ещё выполняется, а TTI не достигнут. Это один из самых раздражающих паттернов в мобильном вебе.

### Что увеличивает разрыв FCP → TTI

```ts
// ❌ Монолитный bundle — весь код приложения в одном файле
// Даже неиспользуемые на текущей странице части
// парсятся и компилируются браузером
import { CheckoutModule } from './checkout';   // не нужен на главной
import { AdminPanel } from './admin';          // не нужен большинству
import { ReportGenerator } from './reports';   // тяжёлый, нужен редко

// ✅ Dynamic import — код загружается только когда нужен
const CheckoutModule = lazy(() => import('./checkout'));
const AdminPanel = lazy(() =>
  import('./admin').then(m => ({ default: m.AdminPanel }))
);

// При клике на кнопку — загружается только тогда
async function handleCheckoutClick() {
  const { startCheckout } = await import('./checkout');
  startCheckout();
}
```

**Практическое правило для TTI:** суммарный JS, который парсится и выполняется до TTI, должен быть минимальным.

На мобильных устройствах парсинг JS примерно в три-четыре раза медленнее, чем на десктопе, потому что процессор слабее:

- 100 килобайт JS на MacBook Pro — примерно 50 мс.
- 100 килобайт JS на среднем Android — примерно 150–200 мс.

Эта разница напрямую удлиняет Long Tasks и сдвигает TTI.

## TBT — Total Blocking Time

### Формула и смысл

TBT — лабораторная метрика: её измеряет Lighthouse, а не реальное поле. Она суммирует **"избыточное" время** всех Long Tasks между FCP и TTI. Long Task — это любая задача на главном потоке дольше 50 мс.

```txt
TBT = сумма (длительность Long Task − 50ms)
      для всех Long Tasks между FCP и TTI
```

Разберём пример с тремя Long Tasks:

- 250 мс дают вклад 250 − 50 = 200 мс.
- 90 мс дают вклад 90 − 50 = 40 мс.
- 180 мс дают вклад 180 − 50 = 130 мс.

Итого TBT равен 370 мс. Почему именно 50 мс? Это порог, при котором взаимодействие ещё ощущается немедленным, то есть меньше 100 мс. Первые 50 мс Long Task "не считаются" и признаются нормальными, а всё сверх этого — реальная блокировка.

| Оценка | TBT |
|---|---|
| ✅ Хорошо | меньше 200 мс |
| ⚠️ Требует работы | 200 — 600 мс |
| ❌ Плохо | больше 600 мс |

### TBT как прокси для INP в лаборатории

INP — **полевая** метрика, она измеряется на реальных пользователях. TBT — **лабораторная** метрика, её выдаёт Lighthouse, и она воспроизводима. Корреляция между ними высокая, но не один к одному. TBT показывает **потенциал** плохого INP. Если Long Tasks много, взаимодействие, попавшее на такую задачу, даст плохой INP.

На практике TBT больше 600 мс делает INP больше 500 мс очень вероятным. TBT меньше 200 мс делает INP меньше 200 мс вероятным. Но INP может быть плохим и при хорошем TBT, если тяжёлый один конкретный обработчик события. TBT — это страница целиком, а INP — конкретные взаимодействия.

### Диагностика TBT — где искать Long Tasks

Откройте Chrome DevTools → Performance и запишите загрузку страницы. В треке главного потока (Main) красные прямоугольники над задачами — это Long Tasks. Кликните по одной и откройте Bottom-up или Call Tree, чтобы увидеть, что именно занимало время.

Типичные причины:

- парсинг и компиляция JS, в записи это Script Evaluation;
- гидратация React, Vue или Angular;
- сторонние скрипты: чаты, аналитика, A/B-тесты;
- большие операции с DOM, например рендер длинных списков.

```ts
// Программное обнаружение Long Tasks в браузере
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn(`Long Task: ${entry.duration.toFixed(0)}ms`, entry);
      sendToAnalytics({
        name: 'long_task',
        duration: entry.duration,
        startTime: entry.startTime,
      });
    }
  }
});

observer.observe({ type: 'longtask', buffered: true });
```

## Как метрики связаны между собой — цепочка причинности

```txt
Навигация начинается
        ↓
[TTFB] — сервер отвечает
        ↓ HTML получен
[FCP]  — браузер отрисовал первый контент
   ↑         ↑
   │         └─ блокируют: рендер-блокирующий CSS/JS
   └─────────── зависит от: TTFB + сетевые задержки
        ↓
[LCP]  — главный контент отрисован ← пользовательская CWV
   ↑
   └─── зависит от: FCP + загрузка LCP-ресурса
        ↓ JS-бандлы выполняются, страница hydrates
[TBT]  — сумма блокировок main thread (лаборатория)
        ↓
[TTI]  — страница полностью интерактивна
   ↑
   └─── зависит от: Long Tasks после FCP

[INP]  — отзывчивость конкретных взаимодействий ← CWV
   ↑
   └─── коррелирует с TBT, но измеряется в реальном поле
```

## DevTools-воркфлоу для диагностики

**Шаг 1. Аудит Lighthouse,** вкладкой или консольным инструментом. Он даёт все четыре метрики плюс Core Web Vitals и указывает на конкретные проблемы в виде аудитов. Запускать его нужно в режиме инкогнито, чтобы расширения не искажали числа.

**Шаг 2. Панель Performance, для TTFB и Long Tasks.** Откройте DevTools → Performance → ⏺ или нажмите Ctrl+Shift+E, чтобы перезагрузить страницу с записью.

- В треке Timings лежат маркеры FCP, LCP и TBT.
- Трек Network показывает, блокирует ли что-то рендер на раннем этапе.
- Трек Main показывает, где находятся Long Tasks.

**Шаг 3. Вкладка Network, для TTFB.** Наведите курсор на waterfall-бар документа, чтобы получить разбивку Timing, где `Waiting for server response` — реальное время сервера. Сравните его с TTFB, измеренным с ноды CDN. Если нода близко к пользователю, а ответ всё равно медленный, дело в сервере, а не в сети.

**Шаг 4. Вкладка Coverage.** Откройте DevTools → ⋮ → More tools → Coverage → ⏺ и перезагрузите страницу. Она показывает долю неиспользуемого JS и CSS при загрузке, а красные полосы отмечают код, который загрузился, но не понадобился.

## Типичные ошибки на интервью

- **"TTFB — это время загрузки страницы"** — нет. TTFB заканчивается на первом байте ответа. Загрузка всех ресурсов — это Load Event, совершенно другая метрика.

- **"FCP и LCP — это одно и то же"** — FCP фиксирует любой первый контент (включая лоадер), LCP фиксирует самый большой значимый элемент. Страница может иметь отличный FCP и плохой LCP.

- **"TTI — это когда страница загружена"** — TTI определяется наличием 5-секундного "тихого окна" без Long Tasks, а не Load-событием. Страница может быть "загружена" (все ресурсы скачаны), но TTI ещё не достигнут, потому что JS продолжает выполняться.

- **"TBT можно измерить в реальном поле"** — нет. TBT — лабораторная метрика (Lighthouse). В поле используется INP. Путать их — признак поверхностного знания.

- **Не знать пороги** — на интервью часто спрашивают "что считается хорошим TTFB". TTFB: <800ms; FCP: <1.8s; TTI: <3.8s; TBT: <200ms. Не обязательно знать наизусть, но порядок цифр важен.

- **"Добавил defer на все скрипты — FCP стал хороший"** — `defer` действительно помогает FCP. Но если сам CSS большой или не оптимизирован, FCP всё равно будет медленным. Нужна полная картина: TTFB, потом рендер-блокирующие ресурсы, потом размер критического CSS.

- **Игнорировать разницу mobile/desktop** — Lighthouse по умолчанию симулирует мобильное устройство: процессор замедлен вчетверо, сеть медленная. TTI и TBT на мобильном могут быть в 3-5 раз хуже, чем на desktop. Говорить "у нас TTI хороший" без уточнения устройства — неполный ответ.
