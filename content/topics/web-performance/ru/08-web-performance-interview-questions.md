# Веб-производительность — Вопросы для интервью (Middle → Senior)

## Как пользоваться этим файлом

Каждый ответ — сжатая версия того, что подробно разобрано в статьях раздела. На интервью уровня senior по производительности всегда углубляются на шаг дальше. Ждите трёх вопросов после каждого ответа: как бы вы это измерили, в чём компромисс и покажите порядок работы в DevTools. Каждая группа здесь заканчивается блоком **"Типичные follow-up вопросы"**, который показывает, куда обычно уходит разговор.

## Группа 1: Core Web Vitals

**1. Что такое три Core Web Vitals и что именно измеряет каждый из них?**

**LCP (Largest Contentful Paint):** время рендера наибольшего видимого элемента во вьюпорте (обычно hero-изображение или `<h1>`). Измеряет *производительность загрузки*. Хорошо: ≤ 2.5с.

**CLS (Cumulative Layout Shift):** сумма всех неожиданных сдвигов макета за время жизни страницы, взвешенная по impact fraction × distance fraction. Измеряет *визуальную стабильность*. Хорошо: ≤ 0.1.

**INP (Interaction to Next Paint):** сколько времени страница отвечает на действие пользователя. Замер идёт от ввода — клика, тапа, нажатия клавиши — до отрисовки следующего кадра.

Одно посещение страницы даёт одно значение. Для большинства страниц это самое медленное взаимодействие визита. На страницах с очень большим числом взаимодействий одно худшее отбрасывается на каждые 50, чтобы единичный выброс не определял оценку.

INP заменил FID (First Input Delay) в марте 2024 и измеряет *отзывчивость*. Хорошо: ≤ 200 мс. Этот порог проверяется по 75-му перцентилю загрузок страницы в полевых данных. Перцентилем по взаимодействиям внутри одного визита он не является.

---

**2. Почему Google заменил FID на INP, и что INP показывает такого, чего не показывал FID?**

FID измерял только *задержку до начала обработки* первого взаимодействия. Время самой обработки и отрисовку он не включал. Обработчик, блокирующий основной поток на 800 мс после старта, показывал FID = 5 мс и при этом ощущался полностью неотзывчивым.

INP смотрит на *все* взаимодействия визита, а не только на первое, и меряет *полную длительность* от ввода до следующего кадра. Значением визита становится худшее из них. Страница с медленными `onClick`-обработчиками на динамически загружаемом контенте получала хороший FID, но проваливала INP.

---

**3. Что вызывает CLS, и назовите три конкретных исправления.**

CLS вызывается элементами, сдвигающимися после первоначального макета.

**Изображения без размеров:**
```html
<!-- ❌ браузер не знает высоту → перерасчёт макета при загрузке -->
<img src="hero.jpg" alt="Hero">

<!-- ✅ зарезервировать место через aspect-ratio или явные размеры -->
<img src="hero.jpg" alt="Hero" width="1200" height="600">
<!-- или CSS: aspect-ratio: 2/1 -->
```

**Контент, вставляемый с задержкой:** рекламные блоки, куки-баннеры и динамические виджеты, вставляемые над существующим контентом, сдвигают его вниз. Исправление: зарезервировать место через `min-height` или skeleton-заглушки.

**Веб-шрифты, вызывающие FOUT (вспышка нестилизованного текста) или FOIT (вспышка невидимого текста):** у запасного шрифта другие метрики. Текст пересчитывается в тот момент, когда загрузился кастомный шрифт. Исправление: `font-display: optional` (никогда не перерасчитывает, может остаться запасным) или `font-display: swap` + `size-adjust` / `ascent-override` для совпадения метрик запасного шрифта.

---

**4. Что такое LCP и какие четыре элемента могут быть LCP-элементом?**

LCP — метка времени рендера наибольшего *содержательного* элемента, видимого во вьюпорте при первом просмотре страницы. Допустимых типов элементов четыре:

- `<img>`.
- `<image>` внутри документа SVG (масштабируемая векторная графика).
- `<video>` — через своё изображение-постер.
- Элемент с CSS-свойством `background-image`.

Текстовые блоки вроде `<p>` или `<h1>` тоже могут быть LCP-элементом, если они наибольшие. Фоновое изображение из CSS учитывается, только если оно загружается по URL, поэтому градиенты не в счёт.

---

**5. Пройдите через полный чеклист оптимизации LCP.**

Время LCP = задержка сети + TTFB (Time to First Byte) сервера + время загрузки ресурса + время рендера. Атакуем каждую часть:

**1. Снизить TTFB:** поставить впереди CDN (сеть доставки контента), кэшировать на границе сети, держать origin-сервер быстрым. TTFB выше 600 мс — главная причина медленного LCP.

**2. Убрать render-blocking ресурсы:** перенести некритичный CSS в `<link media="print">` или async-загрузку; defer для некритичного JS.

**3. Preload LCP-ресурс:**
```html
<link rel="preload" as="image" href="/hero.webp"
      imagesrcset="/hero-400.webp 400w, /hero-800.webp 800w"
      imagesizes="100vw">
```

**4. Современные форматы изображений:** WebP (формат Web Picture) при том же качестве примерно на 30% легче, чем JPEG (Joint Photographic Experts Group). AVIF (более новый формат изображений от Alliance for Open Media) легче примерно на 50%.

**5. Не делать lazy-load для LCP-изображения:** `loading="lazy"` на hero-изображении задерживает LCP на задержку наблюдения за скроллом. Используйте вместо этого `fetchpriority="high"`.

**6. Избегать рендеринга LCP-элемента на клиенте:** если LCP-элемент вставляет JavaScript, браузер сначала обязан скачать, распарсить и выполнить этот JS. Только потом он рисует. Рендеринг на сервере (SSR) или генерация статики на сборке (SSG) кладут элемент прямо в начальный HTML.

## Типичные follow-up вопросы (Группа 1)

**"Как измерять Core Web Vitals у реальных пользователей, а не только в DevTools?"**

Полевыми данными — замерами реальных пользователей. Обычно берут три источника:

- Chrome User Experience Report (CrUX) через PageSpeed Insights.
- Отчёт Core Web Vitals в Search Console.
- Библиотека `web-vitals`, отправляющая значения в вашу аналитику.

Лабораторные данные Lighthouse и DevTools синтетические. Они не отражают реальных условий: медленные устройства Android, сети 3G, фоновые вкладки. Ранжирует Google по полевым данным.

**"Страница проходит Lighthouse, но проваливает Core Web Vitals в Search Console — почему?"**

Lighthouse — лабораторные данные на одном симулированном устройстве. CrUX — полевые данные реальных пользователей Chrome, сведённые к 75-му перцентилю. У реальных пользователей медленные устройства, промахи кэша, фоновые вкладки и расширения.

Есть и разница в охвате. Lighthouse измеряет одну холодную загрузку, а полевой отчёт включает soft-навигации и повторные посещения.

**"Что такое TTFB и как он связан с LCP?"**

TTFB (Time to First Byte) — время от запроса до первого байта ответа. Это суб-метрика LCP: медленный сервер задерживает всё последующее. TTFB выше 600 мс почти гарантированно уводит LCP за 2.5 с даже при идеальной оптимизации фронтенда.

## Группа 2: Загрузка ресурсов

**6. Что такое critical rendering path и какие ресурсы его блокируют?**

Critical rendering path — последовательность шагов, которые браузер должен завершить до отрисовки первого пикселя:

```txt
DNS → TCP → TLS → HTTP-запрос → парсинг HTML →
построение DOM → построение CSSOM →
Render Tree → Layout → Paint
```

**Render-blocking ресурсов** ровно три вида:

- CSS-файлы в `<head>`. Браузер не рисует, пока не построен CSSOM (CSS Object Model — объектная модель стилей).
- Синхронные теги `<script>` без `defer` или `async`. Они останавливают парсинг HTML.
- `@import` внутри CSS, который создаёт дополнительные последовательные запросы.

Изображения, шрифты и async-скрипты первый рендер не блокируют.

---

**7. `defer` vs `async` vs модульные скрипты — в чём разница?**

```html
<!-- async: загружается параллельно, выполняется сразу при готовности
     (останавливает парсинг HTML). Порядок выполнения не гарантирован. -->
<script async src="analytics.js"></script>

<!-- defer: загружается параллельно, выполняется ПОСЛЕ полного парсинга HTML,
     В ПОРЯДКЕ. Безопасен для скриптов, зависящих от DOM. -->
<script defer src="app.js"></script>

<!-- type="module": всегда defer по умолчанию. Выполняется после парсинга
     HTML, поддерживает import/export, строгий режим, собственный scope. -->
<script type="module" src="main.js"></script>
```

Правило выбора:

- `defer` для скриптов, которым нужен DOM (Document Object Model — живое дерево узлов страницы).
- `async` для независимых скриптов вроде аналитики и рекламы, где порядок неважен.
- `type="module"` для бандлов ESM (ECMAScript Modules), которые откладываются автоматически.

---

**8. Что делает `rel="preload"` и когда использовать его против `rel="prefetch"`?**

Подсказка `preload` говорит браузеру: этот ресурс скоро понадобится, начинай загружать его сейчас и с высоким приоритетом. Она нужна для ресурсов, которые браузер обнаруживает поздно. Типичные случаи — hero-изображение, указанное в CSS, шрифт первого экрана и критичный скрипт. Сам ресурс `preload` не выполняет, а только загружает и кладёт в кэш.

Подсказка `prefetch` говорит вещь послабее: пользователь, возможно, перейдёт на страницу, которой нужен этот ресурс. Это фоновая загрузка с низким приоритетом, она хранится в HTTP-кэше и предназначена для ресурсов следующей навигации.

```html
<!-- preload: загрузить СЕЙЧАС, высокий приоритет, для текущей страницы -->
<link rel="preload" as="font" href="/fonts/inter.woff2" crossorigin>
<link rel="preload" as="image" href="/hero.webp">

<!-- prefetch: загрузить СКОРО, низкий приоритет, для следующей навигации -->
<link rel="prefetch" href="/checkout.js">
```

Злоупотребление `preload` для некритичных ресурсов тратит пропускную способность и конкурирует с критичными. Браузер также выдаст предупреждение: "preload был найден, но не использован в течение 3 секунд".

---

**9. Что такое connection waterfall и как диагностировать в DevTools?**

Connection waterfall — цепочка последовательных сетевых запросов, где каждый не может начаться до завершения предыдущего. Классический пример: HTML → JS-бандл → API-вызов → ещё один API-вызов. На панели Network в DevTools ищите длинные горизонтальные полосы в виде лесенки — каждый запрос начинается только после получения ответа на предыдущий.

Четыре исправления в том порядке, в каком к ним обычно тянутся:

- Resource hints (`preconnect`, `preload`), чтобы загрузки стартовали раньше.
- Сведение API-вызовов на сервер — паттерн backend-for-frontend (BFF).
- Мультиплексирование HTTP/2 или HTTP/3, когда несколько запросов делят одно соединение.
- Инлайнинг критичного CSS, который убирает отдельный CSS-запрос с critical path.

---

**10. Что такое HTTP/2 мультиплексирование и какую проблему производительности оно решает?**

HTTP/1.1 позволяет только один активный запрос на TCP-соединение (Transmission Control Protocol). Браузеры компенсируют это, открывая шесть соединений на домен, но каждое платит за медленный старт TCP. HTTP/2 отправляет несколько потоков по одному соединению одновременно, без блокировки очереди на уровне HTTP.

Две старые привычки от этого теряют смысл. Domain sharding — разбиение ресурсов на `static1.cdn.com` и `static2.cdn.com` только ради лишних соединений — становится анти-паттерном. Объединение всего в один огромный файл становится менее нужным, потому что много маленьких файлов на HTTP/2 работают отлично.

HTTP/3 идёт дальше и убирает блокировку очереди ещё и на уровне соединения. Он делает это, работая поверх QUIC — транспорта, построенного на UDP (User Datagram Protocol) вместо TCP.

## Типичные follow-up вопросы (Группа 2)

**"Когда preload шрифта ухудшает производительность?"**

Есть два случая. Первый — размещение. Если шрифт не используется в первом экране (above the fold), `preload` конкурирует за пропускную способность с ресурсами LCP: hero-изображением и критичным CSS.

Второй случай — размер. Файл вариативного шрифта может весить 500 килобайт и больше, и загружать его целиком ради нескольких символов расточительно.

Лучше загружать заранее только то подмножество символов, которое нужно в первом экране, а сам файл урезать инструментом вроде `pyftsubset` или Fonttools.

**"Какой порядок приоритетов у resource hints?"**

Порядок такой: `preconnect`, затем `preload`, затем `prefetch`, затем `dns-prefetch`. Обратите внимание: `preconnect` открывает всё соединение TCP и TLS (Transport Layer Security), а не только поиск в DNS (Domain Name System). Используйте его для двух-трёх критичных источников, потому что каждое удерживаемое соединение потребляет ресурсы браузера.

**"Lighthouse говорит 'eliminate render-blocking resources', а CSS уже в `<head>`. Что делать?"**

Разбить CSS. Извлечь стили первого экрана и вставить их прямо в тег `<style>` внутри `<head>`. Остальное загружать через `<link media="print">`: такой файл браузер запрашивает без блокировки, а затем в обработчике `onload` вы переключаете его на `media="all"`.

Второй вариант — решение CSS-in-JS, которое само извлекает критичный CSS для каждого компонента. Next.js делает это из коробки.

## Группа 3: Rendering Pipeline

**11. Опишите rendering pipeline браузера от HTML-байтов до пикселей.**

```txt
Байты → Символы → Токены → Узлы → DOM
                                       ↘
CSS Байты → Символы → Токены → Узлы → CSSOM
                                       ↙
             Render Tree (только видимые узлы)
                           ↓
             Layout (геометрия — x, y, ширина, высота)
                           ↓
             Paint (заполнение пикселей в слои)
                           ↓
             Composite (GPU объединяет слои → экран)
```

Четыре вывода из диаграммы:

- JS блокирует построение DOM в тот момент, когда парсер до него дошёл, если у тега нет `defer` или `async`.
- CSS блокирует рендер, потому что CSSOM должен быть построен до Render Tree.
- Layout и Paint дорогие. Избегайте их внутри циклов.
- Composite — самая дешёвая стадия. Без Layout и Paint анимируются только свойства, живущие на GPU-слоях (Graphics Processing Unit — видеопроцессор): `transform` и `opacity`.

---

**12. Что такое layout thrashing и как это исправить?**

Layout thrashing (принудительный синхронный макет): чтение layout-свойства (`offsetHeight`, `getBoundingClientRect()`) заставляет браузер сбросить ожидающие изменения стилей и синхронно пересчитать макет. Затем запись стиля инвалидирует его при следующем чтении. В цикле это вызывает N пересчётов макета за кадр вместо одного.

```ts
// ❌ Layout thrashing — чтение форсирует макет, запись инвалидирует, цикл
elements.forEach(el => {
  const height = el.offsetHeight;       // форсирует сброс макета
  el.style.height = height * 2 + 'px'; // инвалидирует макет
});

// ✅ Сначала пакетно читать, затем пакетно писать
const heights = elements.map(el => el.offsetHeight); // один сброс макета
elements.forEach((el, i) => {
  el.style.height = heights[i] * 2 + 'px';           // пакетная запись
});
// Или используйте requestAnimationFrame для пакетирования в следующем кадре
```

---

**13. Какие CSS-свойства дёшевы для анимации, а какие — дороги?**

**Дёшевые (только compositor, без Layout или Paint):**
- `transform` (translate, rotate, scale)
- `opacity`
- `filter` (на composited-слоях)
- `will-change: transform` (переводит элемент на отдельный слой)

**Дорогие (триггерят Layout → Paint → Composite):**
- `width`, `height`, `margin`, `padding`, `top`, `left` — триггерят Layout
- `background-color`, `color`, `border-color`, `box-shadow` — триггерят Paint

Правило: анимируйте `transform: translateX()` вместо `left`, `transform: scaleX()` вместо `width`. GPU обрабатывает `transform` и `opacity` нативно, а Layout и Paint работают на CPU (Central Processing Unit — центральный процессор).

---

**14. Что такое `requestAnimationFrame` и когда использовать его вместо `setTimeout`?**

Вызов `requestAnimationFrame(cb)` планирует `cb` один раз перед следующей перерисовкой браузера. Он синхронизирован с частотой обновления дисплея — обычно 60 кадров в секунду, то есть примерно каждые 16.7 мс. Отсюда три преимущества:

- Он не запускается, пока вкладка скрыта, и этим экономит батарею и время процессора.
- Он синхронизирован с дисплеем, поэтому нет разрывов и нет потраченного впустую кадра.
- Браузер может объединить его с другой визуальной работой в одном кадре.

`setTimeout(fn, 0)` может сработать в любое время — может разделиться между кадрами (визуальные дёргания) или сработать во время фазы layout. Используйте `requestAnimationFrame` для: всех визуальных анимаций, пакетной записи DOM после чтения layout-свойств, обновлений на основе скролла. Используйте `setTimeout` для несвязанной с визуалом отложенной работы.

---

**15. Что такое свойство `will-change` и каковы риски его чрезмерного использования?**

`will-change` подсказывает браузеру, что элемент будет анимироваться, побуждая его перевести элемент на отдельный compositor-слой *до* начала анимации (избегая стоимости перевода во время анимации). Для анимаций, запускаемых по hover или через JS, это убирает дёрганье первого кадра.

Риск: каждый composited-слой потребляет GPU-память. Использование `will-change: transform` на сотнях элементов одновременно может исчерпать GPU-память, заставив браузер убрать слои — хуже, чем без него. Применяйте только к элементам, которые *реально* будут анимироваться, и убирайте после:

```ts
el.addEventListener('mouseenter', () => { el.style.willChange = 'transform'; });
el.addEventListener('animationend', () => { el.style.willChange = 'auto'; });
```

## Типичные follow-up вопросы (Группа 3)

**"Что такое paint flashing в DevTools и как его включить?"**

Откройте DevTools, перейдите на вкладку Rendering и поставьте галочку 'Paint flashing'. Области, перерисовываемые в каждом кадре, мигают зелёным. Так вы находите компоненты, которые перерисовываются при скролле, — для плавного скролла их должно быть ноль.

Если при скролле мигает вся страница, что-то вызывает глобальную перерисовку. Обычно это элемент с `position: fixed` и тенью `box-shadow` или анимация, которую не вынесли на композитор.

**"Что такое stacking context и почему он важен для производительности?"**

Stacking context — трёхмерное пространство, в котором работает наложение по `z-index`. Его создают `position` вместе с `z-index`, `opacity` меньше единицы, а также `transform`, `will-change` и `filter`.

Каждый stacking context отрисовывается как единое целое. Слишком много вложенных контекстов мешает браузеру оптимизировать объединение слоёв. Неожиданные контексты объясняют и классическую загадку: почему этот элемент оказался поверх всего остального?

**"Когда CSS-анимация выигрывает у JS-анимации?"**

CSS-анимации на свойствах, живущих только в композиторе (`transform`, `opacity`), выполняются в потоке композитора. Заблокированный поток JS — long task — не роняет их кадры. JS-анимации на `requestAnimationFrame` идут в главном потоке, поэтому long task роняет и анимацию, и кадр.

Для анимаций «запустил и забыл» на `transform` или `opacity` безопаснее CSS. Для сложной физики и интерактивных анимаций берите JS с `requestAnimationFrame`.

## Группа 4: Стратегии кэширования

**16. Объясните разницу между `Cache-Control: max-age`, `no-cache` и `no-store`.**

**`max-age=N`:** кэшировать ответ N секунд. Браузер отдаёт из кэша без обращения к серверу. Используется для версионированных статических ресурсов (`bundle.abc123.js`).

**`no-cache`:** *всегда* ревалидировать с сервером перед использованием кэша. Браузер отправляет условный запрос (`If-None-Match` / `If-Modified-Since`). Сервер может ответить 304 Not Modified (без тела — быстро, но всё равно round-trip). Несмотря на название, `no-cache` *сохраняет* кэш.

**`no-store`:** никогда не сохранять ответ в кэше. Каждый запрос получает свежее с сервера. Для чувствительных данных (банковские сессии, личные медданные).

| Что за ответ | Значение `Cache-Control` |
|---|---|
| Статика с хэшем содержимого в имени | `max-age=31536000, immutable` |
| HTML-страница (всегда ревалидировать) | `no-cache` |
| Чувствительные данные | `no-store` |
| Ответ API с кэшем на минуту | `max-age=60, s-maxage=300` |

**17. Что такое ETags и как работает ревалидация кэша?**

ETag — токен, который генерирует сервер, обычно хэш содержимого. Поток состоит из четырёх шагов:

1. На первый запрос сервер отправляет в ответе `ETag: "abc123"`.
2. Браузер сохраняет ответ вместе с его ETag.
3. На следующем запросе, когда `max-age` уже истёк, браузер отправляет `If-None-Match: "abc123"`.
4. Сервер сравнивает этот ETag с текущим содержимым. Если ничего не изменилось, он отвечает `304 Not Modified` без тела, и это экономит трафик. Если содержимое изменилось, он отвечает `200` с новым содержимым и новым ETag.

`Last-Modified` / `If-Modified-Since` — старая альтернатива с временными метками вместо хэшей. ETags надёжнее (точность временных меток, дрейф часов на мультисерверных установках).

**18. Что такое Service Worker и как он обеспечивает offline-first опыт?**

Service Worker — JavaScript-файл, работающий в фоновом потоке (отдельно от страницы), перехватывающий сетевые запросы через событие `fetch`. Может: кэшировать ответы в Cache API, отдавать кэшированный контент без сети, реализовывать стратегии stale-while-revalidate, отправлять push-уведомления.

```ts
// service-worker.ts
const CACHE_NAME = 'v1';
const PRECACHE = ['/shell.html', '/app.js', '/styles.css'];

self.addEventListener('install', (event: ExtendableEvent) => {
  event.waitUntil(
    caches.open(CACHE_NAME).then(cache => cache.addAll(PRECACHE))
  );
});

self.addEventListener('fetch', (event: FetchEvent) => {
  event.respondWith(
    caches.match(event.request).then(cached => {
      // Stale-while-revalidate: сразу отдать кэш, обновить в фоне
      const networkFetch = fetch(event.request).then(response => {
        caches.open(CACHE_NAME).then(c => c.put(event.request, response.clone()));
        return response;
      });
      return cached ?? networkFetch;
    })
  );
});
```

**19. Что такое stale-while-revalidate и когда это уместно, а когда нет?**

Stale-while-revalidate (SWR): немедленно отдать кэшированный (устаревший) ответ, одновременно загружая свежую версию в фоне для следующего запроса. Нулевая задержка для пользователя; всегда в конечном счёте актуален.

```txt
Cache-Control: max-age=60, stale-while-revalidate=3600
```

Этот заголовок означает три вещи. Первые 60 секунд ответ считается свежим и отдаётся из кэша. После 60 секунд отдаётся устаревшая копия, а ревалидация идёт в фоне. После 3660 секунд суммарно ревалидация становится синхронной.

**Уместно:** контент, меняющийся, но не критично — статьи блога, списки товаров, данные дашборда. Небольшая устарелость допустима.

**Неуместно:** пользовательские real-time данные (баланс счёта, состояние корзины), отправка форм, состояние аутентификации. Отдать устаревшие личные данные не той сессии — это баг или проблема безопасности.

## Типичные follow-up вопросы (Группа 4)

**"В чём разница между браузерным кэшем и кэшем Service Worker?"**

Браузерный кэш, он же HTTP-кэш, работает автоматически. Им управляют заголовки `Cache-Control`, а распоряжается им сам браузер. Программно решить «отдай устаревшую копию, раз сеть отвалилась» вы не можете.

Кэш Service Worker, доступный через Cache API, программный и полностью под вашим контролем. Вы решаете, что кэшировать, когда обновлять и что отдавать без сети. Service Worker к тому же перехватывает запросы, которых HTTP-кэш никогда не увидит: ошибки cross-origin и запасные пути по таймауту.

**"Пользователь не видит свежих данных после деплоя, без жёсткой перезагрузки. Почему?"**

Устаревшая запись кэша с долгим `max-age` всё ещё отдаёт старый ресурс. Три решения:

- Хэш содержимого в имени файла. При деплое URL меняется, и старую запись больше никто не запросит.
- Для HTML — `max-age=0` или `no-cache`, чтобы точка входа всегда ревалидировалась.
- Service Worker, который вызывает `skipWaiting()` и `clients.claim()` и активируется сразу при обновлении.

**"Чем CDN-кэш отличается от браузерного?"**

Браузерный кэш индивидуален и лежит на устройстве пользователя. CDN-кэш общий и лежит на edge-сервере. `Cache-Control` управляет обоими, но `s-maxage` переопределяет `max-age` только для CDN. Заголовок `Vary` говорит CDN держать отдельные записи кэша для разных значений заголовка — например, `Vary: Accept-Encoding`.

## Группа 5: Производительность JavaScript

**20. Что такое long task и как он влияет на INP?**

Long task — любое выполнение JavaScript в main thread дольше 50мс. Во время long task браузер не может обрабатывать ввод пользователя — клики и нажатия клавиш ставятся в очередь. Когда long task завершается, браузер обрабатывает ввод (возможно несколько сразу) и рисует следующий кадр. INP измеряет эту задержку. Long task в 200мс после клика кнопки = INP ~200мс.

Диагностика в DevTools: панель Performance → Long Tasks помечены красными треугольниками. `PerformanceObserver` для программного мониторинга:

```ts
const observer = new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    if (entry.duration > 50) {
      console.warn('Long task:', entry.duration, entry.attribution);
    }
  }
});
observer.observe({ type: 'longtask', buffered: true });
```

**21. Что такое code splitting и как он сокращает начальное время загрузки?**

Code splitting откладывает загрузку JavaScript, не нужного для начального отображения. Без splitting браузер загружает, парсит и выполняет весь бандл до интерактивности страницы — включая код маршрутов, которые пользователь не посещал.

```tsx
// Без code splitting: CheckoutPage.js включён в main бандл
import CheckoutPage from './CheckoutPage';

// С React.lazy + Suspense: CheckoutPage загружается только при навигации
const CheckoutPage = React.lazy(() => import('./CheckoutPage'));

function App() {
  return (
    <Suspense fallback={<Spinner />}>
      <Routes>
        <Route path="/checkout" element={<CheckoutPage />} />
      </Routes>
    </Suspense>
  );
}
```

Next.js делает route-based code splitting автоматически. Эффект: сокращение начального JS-бандла с 500 килобайт до 150 килобайт может уменьшить Time to Interactive на 2-3 секунды на медленном устройстве.

**22. Что такое tree shaking и что мешает ему работать?**

Tree shaking — устранение неиспользуемых экспортов из ECMAScript-модулей бандлером. Основывается на статическом анализе `import`/`export` — бандлер определяет на этапе сборки, какие экспорты никогда не импортируются.

**Что мешает tree shaking:**

1. CommonJS (`require`) — динамический, не поддаётся статическому анализу
2. Импорты с побочными эффектами: `import 'polyfill'` — бандлер не знает, безопасно ли удалять
3. Отсутствие `"sideEffects": false` в `package.json` — бандлер считает все файлы с побочными эффектами
4. Реэкспорт всего: `export * from './utils'` — препятствует индивидуальному tree shaking
5. Динамические импорты с переменными путями: `import(variable)` — бандлер не знает, какие модули используются

**23. В чём разница между `debounce` и `throttle` и когда что использовать?**

**Debounce:** откладывает выполнение до N миллисекунд после *последнего* вызова. Функция срабатывает только когда пользователь *прекратил* триггерить события.

**Throttle:** гарантирует срабатывание функции не чаще одного раза в N миллисекунд, независимо от количества вызовов.

```ts
// Debounce: поле поиска — ждать пока пользователь не перестанет печатать
const debouncedSearch = debounce((query: string) => {
  fetchResults(query);
}, 300); // срабатывает через 300мс после последнего нажатия

// Throttle: обработчик скролла — ограничить обновления до 60fps
const throttledScroll = throttle(() => {
  updateScrollProgress();
}, 16); // срабатывает не чаще раза в 16мс (~60fps)
```

Правило: **debounce** для дорогих операций, триггерируемых *окончанием* активности пользователя (поиск, валидация формы, resize). **Throttle** для операций, которые должны продолжаться *во время* активности пользователя, но не перегружать браузер (прогресс скролла, отслеживание позиции мыши, рисование на canvas).

## Типичные follow-up вопросы (Группа 5)

**"Добавили `React.lazy()` везде, и INP ухудшился. Почему?"**

Ленивая загрузка при первом переходе на маршрут запускает сетевой запрос, затем парсинг, затем выполнение. Если пользователь нажал кнопку, которая запускает такую загрузку, обработчик клика стоит и ждёт бандл — INP растёт.

Исправление: заранее подгружать вероятные следующие маршруты, пока браузер простаивает, через `import(/* webpackPrefetch: true */ './Page')`. Тогда к моменту навигации бандл уже лежит в кэше.

**"Что такое Scheduler API и как он улучшает INP?"**

Вызов `scheduler.postTask()` позволяет планировать работу с явным приоритетом. Приоритетов три: `user-blocking` для обработки ввода, `user-visible` для рендера и `background` для аналитики и прочего некритичного.

Работа может уступать более приоритетным задачам прямо посреди выполнения. Так long task разбивается на мелкие куски без ручных вставок `setTimeout(0)`. Доступно в Chrome 94 и новее, полифиллится через `MessageChannel`.

**"Как понять, что именно вызывает long task?"**

Запишите взаимодействие на панели Performance в DevTools, найдите long task (красный треугольник), разверните стек вызовов и найдите горячую функцию.

Второй путь — LoAF (Long Animation Frame) API, доступный с Chrome 116. Он отдаёт не только длительность, но и полную атрибуцию: какие скрипты внесли вклад и какие обработчики событий выполнялись.

## Группа 6: Профилирование и измерения

**24. Опишите ваш workflow в DevTools для диагностики медленного взаимодействия со страницей.**

Пошагово:

1. **Открыть DevTools → панель Performance.** Установить CPU throttle 4x или 6x (симуляция среднего Android).

2. **Нажать "Record", выполнить взаимодействие** (клик кнопки, открытие дропдауна и т.д.), остановить запись.

3. **Найти взаимодействие на таймлайне.** Искать красный прямоугольник (long task) или проверить трек "Interactions". Полоса показывает длительность от ввода до отрисовки.

4. **Развернуть стек вызовов** под long task. Самая широкая полоса снизу — реальное узкое место: React-ре-рендер, сортировка, глубокое клонирование, синхронный вызов XHR (XMLHttpRequest).

5. **Проверить события "Layout" и "Paint".** Если Layout занимает > 20мс — найти что его триггерит (style recalculation → layout shift → forced synchronous layout).

6. **Использовать вкладку "Bottom-Up"** для сортировки по суммарному времени — показывает реальную горячую функцию, а не инициатор.

7. **Исправить, перезаписать, сравнить.** Измерить до и после для подтверждения эффекта.

**25. Что такое библиотека `web-vitals` и как отправлять с её помощью Core Web Vitals в аналитику?**

`web-vitals` — официальная JS-библиотека Google. Она измеряет Core Web Vitals той же логикой, какой Chrome считает их для CrUX. Отдаёт полевые данные (замеры реальных пользователей), а не синтетические лабораторные.

```ts
import { onCLS, onINP, onLCP, onFCP, onTTFB } from 'web-vitals';

function sendToAnalytics({ name, value, rating, id }: Metric) {
  // rating: 'good' | 'needs-improvement' | 'poor'
  navigator.sendBeacon('/analytics', JSON.stringify({
    metric: name,
    value: Math.round(name === 'CLS' ? value * 1000 : value),
    rating,
    id,   // уникален для посещения страницы, для дедупликации
    url: location.href,
    userAgent: navigator.userAgent,
  }));
}

onCLS(sendToAnalytics);
onINP(sendToAnalytics);
onLCP(sendToAnalytics);
onFCP(sendToAnalytics);
onTTFB(sendToAnalytics);
```

Ключевая деталь: `onCLS` и `onINP` отдают *финальное* значение при уходе страницы (или переходе в фон). Вызывайте один раз за посещение — они накапливают значения. Используйте `id` для дедупликации, если одно посещение отправляет несколько отчётов.

## Типичные follow-up вопросы (Группа 6)

**"В чём разница между лабораторными и полевыми данными?"**

Лабораторные данные приходят из синтетической контролируемой среды: Lighthouse, WebPageTest, DevTools. Их быстро снять, они воспроизводимы и полезны в разработке. Реальных условий они не отражают: разброс устройств, разброс сети, холодный и тёплый кэш, расширения браузера.

Полевые данные приходят от реальных пользователей — через CrUX или библиотеку `web-vitals`. Они отражают реальный опыт. Собирать их дольше, воспроизвести нельзя, но именно по ним Google ранжирует и именно их чувствует пользователь.

Ответ уровня senior: собирать оба вида. Лабораторные — чтобы найти проблему, полевые — чтобы подтвердить эффект и проверить исправление.

**"Как измерять производительность в непрерывной интеграции, чтобы ловить регрессии?"**

Запускайте Lighthouse CI — прогонщик Lighthouse для непрерывной интеграции — на каждый пул-реквест командой `lhci autorun`. Задайте бюджетные пороги: LCP меньше 2.5 с, размер бандла меньше 200 килобайт. Заваливайте пул-реквест при превышении порога. Берите фиксированный тестовый URL и прогретый сервер, чтобы снизить разброс.

Добавьте ещё пакет `bundlesize` или `size-limit`, чтобы ловить регрессии размера JS независимо от Lighthouse.

**"У React-приложения INP равен 800 мс. Какая первая гипотеза?"**

Тяжёлый ре-рендер на взаимодействии. React перерисовывает большое поддерево при изменении состояния, и время от ввода до следующего кадра включает всю эту работу.

Чтобы это увидеть, откройте React DevTools Profiler, запишите взаимодействие и найдите компоненты, отрисовавшиеся зря. Обычные исправления — `React.memo`, `useMemo` и `useCallback` на стабильных ссылках либо перенос состояния вниз к листовым компонентам, чтобы сузить область ре-рендера.
