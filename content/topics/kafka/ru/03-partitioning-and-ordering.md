# Партиционирование и порядок сообщений

## Как продюсер выбирает партицию

Когда продюсер отправляет сообщение, ему нужно решить, в какой из N партиций топика его записать. Это решение принимается **на стороне клиента** (а не брокером) по одной из трёх стратегий:

### Стратегия 1: Key-based (партиционирование по ключу)

Если сообщение отправлено с ключом (key ≠ null), Kafka вычисляет партицию по формуле:

```txt
partition = murmur2(key) % numPartitions
```

`murmur2` — некриптографическая хеш-функция. Важно: один и тот же ключ **всегда** попадает в одну и ту же партицию, пока число партиций не меняется.

```txt
Топик "order-events" (4 партиции):

hash("order-101") % 4 = 2   и   hash("order-202") % 4 = 0

{ key: "order-101", value: "placed"    } → Partition 2
{ key: "order-101", value: "shipped"   } → Partition 2
{ key: "order-101", value: "delivered" } → Partition 2
{ key: "order-202", value: "placed"    } → Partition 0
```

Результат: каждое событие `order-101` попадает в Partition 2. Их порядок поэтому гарантирован, и обрабатывает их один потребитель в правильной последовательности.

### Стратегия 2: Round-robin (без ключа)

Если ключ не задан (key = null), продюсер распределяет сообщения по партициям равномерно по кругу:

```txt
Топик "logs" (3 партиции), key = null:

Сообщение 1 → Partition 0
Сообщение 2 → Partition 1
Сообщение 3 → Partition 2
Сообщение 4 → Partition 0
Сообщение 5 → Partition 1
...
```

Преимущество: равномерная нагрузка. Недостаток: нет гарантий порядка — сообщения 1, 4, 7 (в partition 0) и 2, 5, 8 (в partition 1) читаются параллельно разными потребителями.

> **Заметка о sticky partitioner**: начиная с Kafka 2.4 при `key=null` по умолчанию работает sticky partitioner. Продюсер набирает целый батч в одну партицию, потом переключается на следующую. Это уменьшает число запросов к брокеру, и задержка падает. На гарантии порядка это не влияет.

### Стратегия 3: Явное указание партиции

Продюсер может задать партицию напрямую. Используется редко (специальные сценарии маршрутизации, тестирование):

```ts
await producer.send({
  topic: 'order-events',
  messages: [
    { partition: 2, key: 'order-101', value: JSON.stringify(event) }
  ]
});
```

## Почему порядок гарантирован только внутри партиции

Это самая частая тема на интервью по Kafka, и ответ нужно понимать механически, а не просто запомнить.

### Одна партиция = один лог = один порядок

Партиция — это последовательный файл, в который можно только дозаписывать (append-only). Сообщения записываются строго одно за другим, offset монотонно растёт. Читать их можно только в том порядке, в котором они записаны.

```txt
Partition 2:
  [off:0 "placed"]  [off:1 "payment-ok"]
  [off:2 "shipped"] [off:3 "delivered"]
  ───────────────────────────────────────────────────►
  Потребитель читает строго слева направо: 0 → 1 → 2 → 3
```

Потребитель, назначенный на Partition 2, получит эти сообщения строго в этом порядке. Гарантия абсолютная.

### Несколько партиций — нет глобального порядка

Когда топик имеет несколько партиций, разные партиции читаются параллельно разными потребителями. Нет механизма, который бы синхронизировал их прогресс:

```txt
Топик "order-events" (3 партиции):

Partition 0: [order-A: placed] [order-D: placed] [order-A: shipped]
Partition 1: [order-B: placed] [order-B: payment-ok]
Partition 2: [order-C: placed] [order-C: shipped]
             [order-D: payment-ok]

Потребитель A читает Partition 0: placed→A, placed→D, shipped→A
Потребитель B читает Partition 1: placed→B, payment-ok→B
Потребитель C читает Partition 2: placed→C, shipped→C, payment-ok→D

Вопрос: что произошло раньше — "order-A shipped" (P0, offset 2)
        или "order-D payment-ok" (P2, offset 2)?
Ответ: Kafka не знает. Offset 2 в P0 и offset 2 в P2 —
       это независимые счётчики.
```

Глобальной метки времени, по которой можно было бы сравнить сообщения из разных партиций, у Kafka нет. Метка времени пишется в каждое сообщение, но она ничего не гарантирует о порядке, когда пишут сразу несколько продюсеров.

### Практический вывод: ключ как инструмент изоляции порядка

Если порядок важен для определённой сущности (заказ, пользователь, сессия), используйте её ID как ключ:

```txt
✓ Правильно — порядок событий заказа гарантирован:
  key = "order-101" → все его события в одной партиции

✗ Неправильно — события заказа могут попасть в разные партиции:
  key = null (или key = случайный UUID каждый раз)
```

## Как выбрать хороший ключ партиции

Выбор ключа — это баланс между тремя факторами:

### 1. Гарантия порядка (correctness)

Ключ должен группировать сообщения, порядок которых имеет смысл. Вопрос: "Если эти два события поменять местами, сломается ли логика?"

```txt
✓ Хорошие ключи:
  - userId    (события пользователя: регистрация → логин → покупка)
  - orderId   (жизненный цикл: создан → оплачен → отгружен)
  - sessionId (события сессии)
  - deviceId  (телеметрия устройства)

✗ Плохие ключи для порядка:
  - null             (нет порядка вообще)
  - timestamp        (у каждого сообщения свой ключ → не группирует)
  - случайный UUID   (то же самое)
```

### 2. Равномерность распределения (cardinality)

Плохое распределение → одна партиция перегружена, остальные простаивают. Это называют **hot partition** (горячая партиция):

```txt
Топик "events" (4 партиции), key = countryCode:

Russia:  ████████████████████ (70% трафика) → P0 перегружен
Germany: ████ (15%)                          → P1 в норме
France:  ███ (10%)                           → P2 в норме
Other:   ██ (5%)                             → P3 простаивает

→ Потребитель, читающий P0, не успевает.
  Его отставание (lag) растёт.
  Потребители P1, P2, P3 простаивают.
  Добавление потребителей не помогает: узкое место в P0.
```

```txt
✓ Высокая кардинальность (много уникальных значений):
  - userId (миллионы пользователей → равномерно по партициям)
  - orderId
  - sessionId

✗ Низкая кардинальность (мало уникальных значений):
  - countryCode (10–200 значений → легко создаёт hot partition)
  - status ("active"/"inactive" — только 2 значения)
  - isVip (boolean)
```

### 3. Неизменность числа партиций (stability)

После увеличения числа партиций `hash(key) % numPartitions` даст другой результат для тех же ключей. Сообщения с одним ключом начнут попадать в другую партицию → гарантия порядка нарушается для новых сообщений относительно старых.

```txt
Было: 4 партиции
  hash("order-101") % 4 = 2  → Partition 2

Стало: 6 партиций
  hash("order-101") % 6 = 5  → Partition 5 (другой!)

Старые события order-101 в Partition 2,
новые события order-101 в Partition 5 →
потребители читают их независимо → порядок нарушен.
```

**Вывод**: число партиций нужно планировать заранее, с запасом на рост. Увеличение партиций — болезненная операция, если важен порядок.

Практическое правило: закладывайте в 2–4 раза больше партиций, чем планируемое число потребителей на старте.

## Rebalancing — что происходит при изменении состава группы

**Rebalancing (ребалансировка)** — это процесс перераспределения партиций между потребителями группы. Во время ребалансировки **вся группа приостанавливает обработку** — это важно.

### Что вызывает rebalancing

```txt
1. Потребитель присоединяется к группе
   (новый экземпляр запущен, горизонтальное масштабирование)

2. Потребитель покидает группу штатно
   (graceful shutdown, деплой новой версии)

3. Потребитель считается мёртвым
   (нет heartbeat в течение session.timeout.ms, по умолчанию 45 сек)

4. Добавление партиций в топик
   (изменение конфигурации топика)

5. Потребитель меняет подписку
   (изменение списка топиков)
```

### Механика rebalancing

До Kafka 2.3 использовался Eager Rebalancing:

```txt
Eager Rebalancing (старый протокол):

  До:   P0→C1, P1→C2, P2→C3
  
  C4 присоединяется:
  1. Все потребители отзывают все партиции
     (коммитят офсет и освобождают их)
  2. Group Coordinator (один из брокеров) пересчитывает назначения
  3. Все потребители получают новые назначения

  После: P0→C1, P1→C2, P2→C3, P3→C4 (если партиций 4)
         или P0→C1, P1→C2, P2→C4     (если C3 вышел)

  Проблема: пауза равна времени отзыва и пересчёта
            для всех партиций сразу
```

С Kafka 2.3+: Cooperative (Incremental) Rebalancing:

```txt
Cooperative Rebalancing (новый протокол):

  До:   P0→C1, P1→C2, P2→C3

  C4 присоединяется:
  1. Group Coordinator определяет минимальные изменения
  2. Только P2 revoked у C3 (остальные продолжают работу)
  3. P2 назначается C4

  После: P0→C1, P1→C2, P2→C4

  Преимущество: приостанавливаются только затронутые партиции,
                остальные обрабатывают сообщения без паузы
```

В `kafkajs` cooperative rebalancing включается через настройку `partitionAssigners`.

### session.timeout.ms vs heartbeat.interval.ms

```txt
heartbeat.interval.ms (по умолчанию: 3000 мс)
  — как часто потребитель шлёт "я живой" брокеру
  — должен быть значительно меньше session.timeout.ms

session.timeout.ms (по умолчанию: 45000 мс, min: 6000 мс)
  — нет heartbeat в течение этого времени → потребитель мёртв
  — брокер инициирует rebalancing

max.poll.interval.ms (по умолчанию: 300000 мс = 5 минут)
  — максимальное время между двумя вызовами poll()
  — обработка одного сообщения дольше этого → потребитель завис
  — брокер инициирует rebalancing, даже если heartbeat идут
```

Типичная проблема выглядит так:

1. Потребитель тратит на одно тяжёлое сообщение 6 минут.
2. Это больше `max.poll.interval.ms`, а там по умолчанию 5 минут.
3. Брокер исключает потребителя из группы и запускает rebalancing.
4. То же сообщение берёт другой потребитель и обрабатывает его повторно.

Решение: либо увеличить `max.poll.interval.ms`, либо уменьшить `max.poll.records` (читать меньше сообщений за один poll), либо ускорить обработку.

## Итоговая схема: ключ → партиция → порядок

```txt
Producer отправляет события заказа:

  { key: "ord-1", event: "placed"  }
  { key: "ord-2", event: "placed"  }
  { key: "ord-1", event: "paid"    }
  { key: "ord-3", event: "placed"  }        hash(key) % 3
  { key: "ord-1", event: "shipped" }   ────────────────────►
  { key: "ord-2", event: "paid"    }
  { key: "ord-3", event: "shipped" }

  P0: [ord-2:placed] [ord-2:paid]
  P1: [ord-1:placed] [ord-1:paid] [ord-1:shipped]
  P2: [ord-3:placed] [ord-3:shipped]

Группа потребителей (3 потребителя):
  Потребитель A читает P0 → ord-2 события строго по порядку ✓
  Потребитель B читает P1 → ord-1 события строго по порядку ✓
  Потребитель C читает P2 → ord-3 события строго по порядку ✓

  Глобальный порядок между ord-1, ord-2, ord-3 — не гарантирован ✗
  (но нам он и не нужен: заказы независимы)
```

## Типичные ошибки на интервью

**"Kafka гарантирует порядок сообщений"**

Неполный ответ. Kafka гарантирует порядок **внутри партиции**. При нескольких партициях глобальный порядок не гарантируется. Правильный ответ: "Kafka гарантирует порядок внутри партиции. Для гарантии порядка событий конкретной сущности используют её ID как ключ — тогда все её события попадают в одну партицию."

**"Можно увеличить число партиций без последствий для порядка"**

Нет. После увеличения `hash(key) % newNum` даст другие партиции для тех же ключей. Новые события одной сущности будут писаться в другую партицию, чем старые → порядок относительно старых событий нарушен. Число партиций нужно планировать заранее.

**"Hot partition — это нормально, просто один потребитель будет медленнее"**

Это хуже, чем кажется. Потребитель на горячей партиции становится узким местом для всей группы, и его отставание растёт. Отставание (lag) — это число сообщений между закоммиченным офсетом потребителя и концом партиции.

Помочь ему, добавив в ту же партицию ещё одного потребителя, нельзя: одна партиция — один потребитель в группе. Нужно либо менять ключ партиционирования, либо делить горячий поток на несколько топиков.

**"Rebalancing — мгновенная операция"**

Нет. Во время eager rebalancing вся группа приостанавливает обработку: сначала все потребители отзывают свои партиции, ждут координатора и получают новые назначения. На большом кластере с медленными потребителями это может занять секунды и больше. Именно поэтому стоит использовать cooperative rebalancing (Kafka 2.3+).

**"Если потребитель падает и перезапускается, он теряет неподтверждённые сообщения"**

Нет — при правильно настроенных офсетах. Потребитель возобновляет работу с последнего закоммиченного офсета. Если он упал до коммита, он перечитает сообщения с момента последнего коммита. Это at-least-once семантика — сообщения будут обработаны повторно, не потеряны. Подробнее — в статье о гарантиях доставки.
