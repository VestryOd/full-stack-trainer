# Kafka vs RabbitMQ

## Философская разница: лог против очереди

Это не сравнение "что быстрее" или "что надёжнее". Kafka и RabbitMQ решают принципиально разные задачи, потому что построены на разных моделях хранения данных.

```txt
               RabbitMQ — модель очереди
┌─────────────────────────────────────────────────────┐
│ Брокер хранит сообщение, пока его не прочитают и не │
│ подтвердят (ack). После ack сообщение удаляется.    │
│                                                     │
│ Producer ──▶ [msg1][msg2][msg3]                     │
│ потребитель читает msg1                             │
│          ──▶ [msg2][msg3]        msg1 удалён        │
└─────────────────────────────────────────────────────┘

                  Kafka — модель лога
┌─────────────────────────────────────────────────────┐
│ Брокер хранит лог (append-only) до истечения срока  │
│ хранения — независимо от того, прочитали сообщение  │
│ или нет.                                            │
│                                                     │
│ offset:      0     1     2     3     4              │
│           [msg1][msg2][msg3][msg4][msg5]            │
│                                                     │
│ Потребитель A: offset=2  (прочитал 0 и 1)           │
│ Потребитель B: offset=0  (читает с начала)          │
│ Потребитель C: offset=4  (почти в реальном времени) │
│                                                     │
│ msg1..msg5 по-прежнему все в логе                   │
└─────────────────────────────────────────────────────┘
```

Из этой разницы вытекает всё остальное: поведение при сбоях, масштабирование, поддержка нескольких потребителей, возможность replay.

## Retention: как долго хранятся данные

```txt
RabbitMQ — retention по событию:
  Сообщение существует ТОЛЬКО пока его не обработали.
  Прочитано + ack → удалено немедленно.
  Нет ack в течение N секунд → requeue, то есть возврат
  в очередь для повторной попытки.
  Опционально: очередь необработанных сообщений
  (dead letter queue).

  Проблема: нельзя "перемотать назад". Если analytics-сервис
  не читал очередь 2 часа — эти 2 часа событий потеряны
  навсегда.

Kafka — retention по времени:
  Сообщение хранится N дней (retention.ms) или до объёма
  M байт (retention.bytes), НЕЗАВИСИМО от того, прочитали
  его или нет.

  По умолчанию: 7 дней. Настраивается на уровне топика:
    retention.ms=-1 → хранить вечно (compact topics)
    retention.ms=3600000 → 1 час
    retention.bytes=1073741824 → удалять старые после 1GB

  Преимущество: analytics-сервис упал на 2 часа →
  перезапустился с последнего offset → догнал всё,
  что пропустил. Без потерь.
```

Это не просто техническая деталь, а архитектурная ценность Kafka. Лог здесь — источник правды (source of truth). Новый сервис может подключиться и получить всю историю событий с самого начала. RabbitMQ такой возможности не даёт.

## Модель доставки: push vs pull

```txt
RabbitMQ — push-модель:
  Брокер сам проталкивает сообщения подписчикам.
  Потребитель ограничивает поток окном prefetch — так в
  RabbitMQ устроен backpressure: basic.qos задаёт, сколько
  неподтверждённых сообщений брокер может отдать ему разом.

  Хорошо: низкая задержка, меньше миллисекунды на простых
          задачах
  Плохо: окно задаётся заранее, поэтому неверное значение
         prefetch всё равно завалит медленного потребителя

Kafka — pull-модель:
  Потребитель сам опрашивает брокер (poll).
  Потребитель ограничивает поток на каждой выборке:
  max.poll.records и fetch.max.bytes задают, сколько
  вернёт один poll.
  Брокер не знает о состоянии потребителя ничего, кроме
  закоммиченных offset.

  Хорошо: потребитель никогда не перегружен и читает
          в своём темпе
  Плохо: чуть выше задержка для задач реального времени,
         обычно до 10 мс

Поток ограничивают обе стороны. Разница в том, кто
инициирует передачу, а не в том, у кого есть контроль.
```

## Маршрутизация: где живёт логика

```txt
RabbitMQ — умная маршрутизация в брокере:

  ┌──────────────────────────────────────────────────┐
  │ Брокер RabbitMQ                                  │
  │                                                  │
  │ Producer ──▶ Exchange ──▶ Bindings ──▶ Очередь A │
  │                                        Очередь B │
  │                                        Очередь C │
  │                                                  │
  │ Очередь A ──▶ Потребитель A                      │
  │ Очередь B ──▶ Потребитель B                      │
  │ Очередь C ──▶ Потребитель C                      │
  └──────────────────────────────────────────────────┘

  Типы exchange:
  - direct:  точное совпадение routing key
  - fanout:  всем очередям (broadcast)
  - topic:   шаблоны в routing key (orders.*, *.critical)
  - headers: маршрутизация по заголовкам сообщения

  Богатая маршрутизация — сильная сторона RabbitMQ.
  Сложные топологии выстраиваются прямо в брокере.

Kafka — маршрутизация в клиентском коде:
  Брокер просто хранит топики.
  Вся логика "какой потребитель что читает" — в коде
  приложения.

  Нужен fanout? → несколько групп читают один топик.
  Нужна фильтрация? → потребитель читает всё и фильтрует сам.
  Нужна маршрутизация? → продюсер выбирает топик по условию.

  Это не недостаток, а осознанная простота брокера
  ("dumb broker").
```

## Когда выбирать Kafka

```txt
✓ Kafka — правильный выбор:

  1. Event Streaming / Event Sourcing
     Поток событий как источник правды.
     Нужен replay для новых сервисов или отладки.
     "Что произошло с этим заказом за последние 30 дней?"

  2. Несколько независимых потребителей одного потока
     События заказов → поиск + аналитика + рекомендации
     Все читают один топик независимо.
     Новый потребитель не требует изменений в продюсере.

  3. Высокая пропускная способность
     Миллионы событий в секунду.
     Аналитика в реальном времени, телеметрия интернета
     вещей, финансовые потоки.

  4. Агрегация логов (log aggregation)
     Централизованный сбор логов из микросервисов.
     Logstash/Filebeat → Kafka → Elasticsearch.

  5. Захват изменений базы данных (Change Data Capture, CDC)
     Стриминг изменений из базы (Debezium → Kafka).
     Синхронизация между хранилищами данных.

  6. Долгосрочное хранение событий
     История нужна для комплаенса, аудита, обучения моделей.
```

## Когда выбирать RabbitMQ

```txt
✓ RabbitMQ — правильный выбор:

  1. Очереди задач (task queues)
     "Отправить письмо", "изменить размер изображения",
     "сгенерировать PDF".
     Одна задача — один воркер — результат.
     Читать задачу повторно после выполнения не нужно.

  2. Паттерн "запрос — ответ" (RPC)
     Запрос → обработка → ответ в очередь для ответа.
     Вызывающая сторона ждёт результат от воркера.
     Kafka для этого неудобна.

  3. Сложная маршрутизация на уровне брокера
     Разные очереди для разных типов событий с шаблонами.
     Маршрутизация по условию без кода в потребителе.

  4. Приоритизация сообщений
     RabbitMQ поддерживает очереди с приоритетами.
     Kafka не поддерживает приоритизацию нативно.

  5. Короткоживущие задачи с немедленным результатом
     Таймаут на обработку имеет смысл.
     Повтор с очередью необработанных (DLQ) встроен в брокер.

  6. Низкая задержка для простых задач
     Доставка меньше миллисекунды при небольших объёмах.
```

## Честное сравнение по параметрам

| Параметр | Kafka | RabbitMQ |
|---|---|---|
| Модель хранения | Лог (append-only) | Очередь (удаляется после ack) |
| Retention | По времени или объёму, независимо от чтения | До чтения и подтверждения |
| Replay | Да — перемотать offset назад | Нет |
| Несколько потребителей | Да — consumer groups, каждая группа получает все сообщения | Ограничено: каждую очередь читает один набор потребителей |
| Пропускная способность | Очень высокая: миллионы сообщений в секунду | Десятки тысяч в секунду на очередь, порядка 50 тысяч на узел при нескольких очередях |
| Задержка | Миллисекунды (pull) | Меньше миллисекунды (push) |
| Контроль потока | Потребитель тянет; `max.poll.records` и `fetch.max.bytes` ограничивают выборку | Брокер толкает; окно prefetch (`basic.qos`) ограничивает неподтверждённые |
| Маршрутизация | В клиентском коде (простой брокер) | В брокере (умный брокер, exchange) |
| Порядок | Гарантирован внутри партиции | Гарантирован внутри одной очереди |
| Операционная сложность | Выше: брокеры, партиции, репликация, ZooKeeper или KRaft | Ниже: проще в настройке и управлении |
| Необработанные сообщения | Паттерн Dead Letter Topic в коде, не встроен в брокер | Встроен в брокер: dead letter exchange (DLX) |
| Приоритизация сообщений | Не поддерживается | Очереди с приоритетами (priority queues), нативно |

## Честная заметка про выбор в реальном мире

Книжный ответ на вопрос "Kafka или RabbitMQ?" — "смотри на требования: нужен replay? нужен высокий throughput? нужна сложная маршрутизация?". Это правильный ответ. Но в реальности всё немного иначе.

**Многие команды выбирают инструмент не по техническому соответствию, а по тому, что предлагает их облачный провайдер:**

```txt
AWS:
  → Amazon MSK (Managed Streaming for Kafka) — Kafka
  → Amazon SQS — простая очередь (не RabbitMQ, но аналог
    для очередей задач)
  → Amazon SNS — pub/sub поверх SQS

GCP:
  → Google Cloud Pub/Sub — managed messaging
    (семантика ближе к Kafka, но это не Kafka)

Azure:
  → Azure Event Hubs — совместимый с Kafka API (managed Kafka)
  → Azure Service Bus — messaging в духе RabbitMQ

Confluent Cloud:
  → Полностью managed Kafka с дополнительными инструментами
    (Schema Registry, ksqlDB, Kafka Connect)
```

Выбор Kafka обычно означает Amazon MSK (Managed Streaming for Kafka) или Confluent Cloud, а не собственный кластер. Это снижает операционную нагрузку, но добавляет привязку к поставщику (vendor lock-in) и стоимость.

**Ещё одна реальность**: многие стартапы начинают с RabbitMQ, который проще поднять и который даёт меньше накладных расходов. На Kafka они переходят при росте нагрузки или когда появляется нужда в replay и event sourcing. Kafka — не автоматически лучший выбор для любого нового проекта.

## Сценарий: order-сервис — что выбрать?

Чтобы прояснить, когда что использовать, рассмотрим конкретный сценарий:

**Требования**: при размещении заказа нужно отправить email, зарезервировать товар на складе и записать в аналитику.

```txt
Вариант A: RabbitMQ
  Order Service публикует три раза:
  │── в exchange "email" → Email Queue → Email Worker
  │── в exchange "inventory" → Inventory Queue → Inventory Worker
  └── в exchange "analytics" → Analytics Queue → Analytics Worker

  Плюсы: просто, задачи независимы, каждый воркер делает одно
  Минусы: Order Service знает о трёх системах-получателях;
          новый потребитель (recommendations) требует правок
          в Order Service; нет replay при сбое analytics
          на 2 часа

Вариант B: Kafka
  Order Service
    └── publish → topic "order-placed" (key: orderId)

  Email Consumer Group     ← читает "order-placed"
  Inventory Consumer Group ← читает "order-placed"
  Analytics Consumer Group ← читает "order-placed"

  Плюсы: Order Service ничего не знает о получателях;
         новый потребитель (recommendations) — просто новая
         группа, Order Service не меняется; analytics упала
         на 2 часа → перезапустилась → обработала всё
         с последнего offset
  Минусы: больше инфраструктуры; избыточно, если нужны только
          простые fire-and-forget задачи без replay
```

**Правило выбора**: если у вас **одно событие → несколько независимых потребителей** и/или **нужен replay** — Kafka. Если **одна задача → один воркер** без необходимости перечитывать — RabbitMQ или Amazon SQS (Simple Queue Service).

## Типичные ошибки на интервью

**"Kafka быстрее RabbitMQ — поэтому нужно выбирать Kafka"**

Неправильный критерий выбора. У RabbitMQ задержка меньше миллисекунды, и он держит десятки тысяч сообщений в секунду на очередь. При нескольких очередях это порядка 50 тысяч на узел, чего для большинства очередей задач более чем достаточно.

Kafka выше на порядок величины, потому что пишет в лог последовательно и группирует записи пачками. Но это не аргумент для задачи "отправить 1000 писем в день".

**"Kafka заменяет RabbitMQ"**

Нет. Есть вещи, которые RabbitMQ умеет, а Kafka нет:

- приоритизация очередей;
- встроенная очередь необработанных сообщений — dead letter exchange (DLX);
- богатая маршрутизация в брокере через exchange;
- паттерн удалённого вызова процедур (RPC) с очередью для ответа.

Это разные инструменты для разных задач, а не версии одного и того же.

**"RabbitMQ устарел, все переходят на Kafka"**

Это индустриальный хайп, не факт. RabbitMQ активно развивается, от линии 3.x к 4.x, и работает в миллионах продакшн-систем. Он остаётся правильным выбором для очередей задач, простых схем обмена сообщениями и умеренной нагрузки.

**"Нужен pub/sub → нужна Kafka"**

Не обязательно. RabbitMQ реализует pub/sub через fanout exchange. То же делает Amazon SNS (Simple Notification Service) вместе с SQS, вообще без Kafka. Kafka — один из способов реализации pub/sub, но не единственный. Выбор Kafka оправдан, если помимо pub/sub нужен replay, долгосрочное хранение или очень высокий throughput.

**"Если мы используем AWS — нужно брать SQS вместо Kafka"**

Amazon Web Services (AWS) предлагает и то и другое, но SQS и Kafka — разные инструменты. Amazon SQS — это управляемая очередь задач, по модели ближе к RabbitMQ. Amazon MSK — управляемая Kafka. Выбор между ними определяется той же логикой: replay нужен? → MSK. Простые task queues? → SQS.
