# Что такое Kafka на самом деле

## Один вопрос, который путает большинство

"Kafka — это очередь сообщений, как RabbitMQ, только быстрее?"

**Нет.** Это самое распространённое заблуждение, и именно с него начинают ломать голову на интервью. Kafka — это **распределённый лог (distributed log)**. Разница не терминологическая — она архитектурная, и влияет на всё: как данные хранятся, кто и когда их читает, что происходит после чтения.

Чтобы понять, зачем Kafka вообще появилась, нужно сначала понять, какую проблему она решает — и почему RabbitMQ с этой проблемой не справляется.

## Проблема, которую не решает очередь

Представьте LinkedIn в 2010 году. Пользователь обновляет профиль. Это событие нужно:
- Проиндексировать в поиске (немедленно)
- Обновить рекомендации связей (фоново, через секунды)
- Отправить аналитику поведения (фоново, через минуты)
- Добавить в журнал аудита (долгосрочное хранение)

С классической очередью — RabbitMQ или Amazon Simple Queue Service — это выглядит так:

```txt
[Profile Service]
     │
     ├──► [Queue: search-index]    ──► [Search Consumer]
     ├──► [Queue: recommendations] ──► [Reco Consumer]
     ├──► [Queue: analytics]       ──► [Analytics Consumer]
     └──► [Queue: audit-log]       ──► [Audit Consumer]

Каждый потребитель читает своё сообщение, и очередь его удаляет.
```

Проблемы:

1. **Рост числа потребителей**: появляется новый сервис — скажем, модель
   машинного обучения для ранжирования. Ему нужна новая очередь, а Profile
   Service обязан о ней знать и писать в неё.
2. **Нет повторного чтения**: сервис analytics упал на 2 часа. Все события за
   это время потеряны, потому что очередь удаляет сообщение после подтверждения
   (ack).
3. **Нет отладки и аудита**: завтра в Search Consumer нашёлся баг. Переиграть
   события с нуля нечем — они уже ушли из очереди.

Это и есть проблема, которую решает Kafka.

## Kafka как распределённый лог

Kafka хранит сообщения не в очереди, которая опустошается при чтении, а в **логе** (log) — последовательном, неизменяемом файле записей. Сообщение остаётся в логе после того, как его прочитали. Оно остаётся там, пока не истечёт настроенный срок хранения (по умолчанию 7 дней, но это конфигурируется вплоть до "хранить вечно").

```txt
Очередь (RabbitMQ, Amazon SQS):
┌──────────────────────────┐
│ [msg1][msg2][msg3][msg4] │
└──────────────────────────┘
Потребитель читает msg1, и дальше:
┌────────────────────┐
│ [msg2][msg3][msg4] │
└────────────────────┘
msg1 удалён из очереди

Лог (Kafka):
┌────────────────────────────────┐
│ [msg1][msg2][msg3][msg4][msg5] │
└────────────────────────────────┘
Потребитель A читает msg1 (offset=0)
Потребитель B читает msg1 (offset=0)
Потребитель A потом читает msg3 (offset=2)
msg1 остаётся в логе
```

Это меняет всё:
- **Любой новый потребитель может читать с самого начала** — можно добавить новый сервис и "воспроизвести" всю историю событий
- **Независимые потребители читают независимо** — Search Service и Analytics Service читают один и тот же лог, не мешая друг другу
- **Replay после сбоя** — если Analytics Service упал, он просто продолжит с того offset, на котором остановился

```txt
Kafka Topic "user-profile-updated":

  offset: 0        1        2        3        4
         [evt-A] [evt-B] [evt-C] [evt-D] [evt-E]

  Search Consumer      → offset 4  (почти в реальном времени)
  Reco Consumer        → offset 3  (немного отстаёт)
  Analytics Consumer   → offset 1  (упал, восстанавливается)
  Сервис ранжирования  → offset 0  (только запущен, догоняет)
```

## "Умный потребитель, тупой брокер" — в чём философия

В RabbitMQ брокер умный: он знает, кому доставить сообщение, отслеживает подтверждения (ack), управляет маршрутизацией через exchange, знает о состоянии каждой очереди.

Kafka устроена принципиально иначе — это называют **"dumb broker, smart consumer"** (тупой брокер, умный потребитель):

```txt
RabbitMQ — умный брокер:              Kafka — умный потребитель:
┌────────────────────────┐            ┌─────────────┐
│        Брокер          │            │   Брокер    │
│  - Знает потребителей  │            │  - Хранит   │
│  - Маршрутизирует      │            │    лог      │
│  - Удаляет после ack   │            │  - Больше   │
│  - Отслеживает ack     │            │    ничего   │
└────────────────────────┘            └─────────────┘
                                            │
                                Потребитель сам:
                                - помнит свой offset
                                - решает, когда коммитить
                                - читает в своём темпе
                                - перечитывает при необходимости
```

**Брокер (broker)** — узел Kafka, который принимает и хранит данные. Он не знает, прочитал ли потребитель сообщение: брокер просто хранит лог.

**Потребитель (consumer)** сам отслеживает, до какого места он прочитал лог. Это число называется **offset** — порядковый номер следующего сообщения, которое нужно прочитать. Потребитель коммитит (сохраняет) свой офсет сам, и именно это даёт возможность повторного чтения: достаточно сбросить офсет назад.

Практический результат этой философии — Kafka **горизонтально масштабируется** гораздо лучше классических брокеров. Брокер не хранит состояние по каждому потребителю. Он только последовательно пишет и читает данные с диска, а последовательный доступ к диску очень быстрый.

## Почему Kafka так быстра: последовательный ввод-вывод

Kafka пишет все сообщения **последовательно в конец файла**. Последовательная запись на обычный жёсткий диск быстрее случайной в 100–1000 раз. Kafka использует механизм операционной системы под названием `sendfile`, он же zero-copy. Данные идут прямо с дискового буфера в сетевой сокет, минуя копирование в пространство пользователя.

```txt
Традиционное чтение файла + отправка:
  Диск → kernel buffer → user buffer
       → kernel socket buffer → сеть
                         (копирование в userspace — дорого)

Kafka с zero-copy (sendfile):
  Диск → kernel buffer ──────────────────────────────────► сеть
         (данные никогда не покидают ядро ОС — быстро)
```

Это не академическая деталь — именно это позволяет одному брокеру Kafka обрабатывать миллионы сообщений в секунду на обычном железе.

## Когда Kafka — правильный выбор

Kafka решает конкретный класс задач лучше традиционных очередей:

```txt
Kafka хорошо подходит для:
  ✓ Event streaming — один поток, который читают много сервисов
  ✓ Повторное чтение событий (отладка, новые сервисы,
    восстановление после аварии)
  ✓ Высокая пропускная способность — миллионы сообщений в секунду
  ✓ Долгое хранение событий как источника правды (event sourcing)
  ✓ Log aggregation — сбор логов из множества сервисов
  ✓ Change Data Capture (CDC) — стриминг изменений из базы данных
  ✓ Аналитика в реальном времени — несколько потребителей
    читают один поток по-разному

Kafka — плохой выбор для:
  ✗ Простые очереди задач (отправить письмо, сжать картинку)
  ✗ Паттерны «запрос → ответ с результатом»
  ✗ Маршрутизация по содержимому сообщения (routing by content)
  ✗ Команды с немедленным результатом ("сделай и верни статус")
  ✗ Маленькие команды, где отдельные шаги транзакционно связаны
```

## Типичные ошибки на интервью

**"Kafka — это продвинутый RabbitMQ"**

Неправильная постановка. Это разные инструменты с разной философией. RabbitMQ — брокер сообщений (message broker): получил, маршрутизировал, доставил, удалил. Kafka — лог событий (event log / event streaming platform): получил, сохранил в порядке, дал читать всем желающим столько раз, сколько нужно. Нельзя сказать, что одно "лучше" другого — нужно объяснять, для каких задач.

**"В Kafka сообщение удаляется после прочтения"**

Нет. Это именно то, чего Kafka **не** делает, и в этом её ключевое отличие от очереди. Сообщение удаляется только по истечении срока хранения (`retention.ms`) или при превышении объёма (`retention.bytes`). Потребитель только двигает свой offset вперёд, не удаляя данные.

**"Kafka гарантирует глобальный порядок сообщений"**

Kafka гарантирует порядок только внутри одной партиции (partition). Если у топика несколько партиций, глобальный порядок **не** гарантируется. Это фундаментальный компромисс между порядком и параллелизмом. Подробнее — в статье [Партиционирование и порядок сообщений](./03-partitioning-and-ordering.md).

**"Offset — это глобальный счётчик"**

Offset уникален в пределах конкретной партиции, а не всего топика. Offset 5 в partition 0 и offset 5 в partition 1 — это два разных сообщения.
