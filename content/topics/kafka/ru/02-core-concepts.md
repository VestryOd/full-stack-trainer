# Ключевые концепции Kafka

## Топик (Topic)

**Топик (topic)** — это именованный канал, в который продюсеры пишут сообщения, а потребители их читают. Аналог: папка с журналом событий определённого типа.

```txt
topic: "order-placed"
┌──────────────────────┐
│ [order1][order2]...  │
└──────────────────────┘

topic: "payment-completed"
┌──────────────────────┐
│ [pay1][pay2][pay3]...│
└──────────────────────┘

topic: "user-registered"
┌──────────────────────┐
│ [usr1][usr2]...      │
└──────────────────────┘
```

Топик — логическая единица организации данных. Физически топик разбит на **партиции (partitions)**, которые и хранят реальные данные.

Важные свойства топика:
- Имя топика — строка (например, `"order-placed"`, `"user-events"`)
- Количество партиций задаётся при создании (можно увеличить, но уменьшить — нет)
- Срок хранения (`retention.ms`) настраивается на уровне топика
- Один топик может читать любое число consumer group — данные общие

## Партиция (Partition)

**Партиция (partition)** — это физическая часть топика: упорядоченный неизменяемый лог сообщений, который хранится на диске одного брокера.

Каждый топик разбивается на N партиций (N ≥ 1). Именно партиции позволяют Kafka масштабироваться горизонтально.

```txt
Topic "order-placed" с 3 партициями:

Partition 0:  [order-A] [order-B] [order-C] [order-D] ──►
              offset: 0    1         2         3
              новые сообщения дописываются справа

Partition 1:  [order-E] [order-F] [order-G] ──► ...
              offset: 0    1         2

Partition 2:  [order-H] [order-I] ──► ...
              offset: 0    1
```

**Зачем вообще нужны партиции?**

Один файл-лог — это один поток процессора на запись и чтение. Это узкое место. Партиции снимают такое ограничение:

1. **Параллелизм записи**: продюсер может писать в partition 0, 1, 2 одновременно
2. **Параллелизм чтения**: каждую партицию может читать отдельный потребитель — 3 партиции = 3 параллельных потребителя в одной группе
3. **Распределение по брокерам**: каждая партиция живёт на определённом брокере (с репликами на других), что позволяет распределить нагрузку по кластеру

```txt
Kafka Cluster с 3 брокерами, Topic с 3 партициями:

Broker 1          Broker 2          Broker 3
┌─────────────┐   ┌─────────────┐   ┌─────────────┐
│ P0 (leader) │   │ P1 (leader) │   │ P2 (leader) │
│ P1 (replica)│   │ P2 (replica)│   │ P0 (replica)│
│ P2 (replica)│   │ P0 (replica)│   │ P1 (replica)│
└─────────────┘   └─────────────┘   └─────────────┘
```

**Leader** — партиция, которая принимает записи от продюсеров. **Replica** — копия, которая синхронизируется с лидером. Если брокер с лидером падает, один из replica-брокеров автоматически становится новым лидером.

## Оффсет (Offset)

**Оффсет (offset)** — это порядковый номер сообщения внутри конкретного партиции. Начинается с 0, монотонно возрастает.

```txt
Partition 0:
  offset 0: { key: "user-1", value: "order placed" }
  offset 1: { key: "user-2", value: "order placed" }
  offset 2: { key: "user-1", value: "order shipped" }
  offset 3: { key: "user-3", value: "order placed" }
              ↑
        потребитель читает отсюда
        → он обработал всё вплоть до offset 2
```

**Ключевое свойство**: offset — это **per-partition**, не глобальный по топику. Offset 5 в partition 0 и offset 5 в partition 1 — это совершенно разные сообщения.

Кроме того, Kafka хранит offset **per-consumer-group** (об этом ниже). Это означает, что две разные группы могут читать один и тот же топик независимо, каждая со своим набором офсетов.

```txt
Topic "order-placed", Partition 0:
[msg0][msg1][msg2][msg3][msg4][msg5]

Группы, которые его читают:

Группа "search-service":  offset = 5  (прочитала всё)
Группа "analytics":       offset = 3  (отстаёт на 2 сообщения)
Группа "audit-log":       offset = 0  (читает с самого начала)
```

Потребитель сам **коммитит (commit) офсет**: сохраняет его в служебный топик Kafka `__consumer_offsets`. Коммит означает, что всё до этого места обработано. Подробнее о стратегиях коммита — в статье [Kafka в Node.js](./04-kafka-in-nodejs.md).

## Продюсер (Producer)

**Продюсер (producer)** — клиент, который пишет сообщения в топик.

Продюсер решает:
1. **В какой топик** писать (обязательно)
2. **С каким ключом** (key) — влияет на то, в какую партицию попадёт сообщение
3. **С какими заголовками (headers)** — метаданные (версия схемы, trace ID и т.п.)

```txt
Producer → [ topic: "order-placed",
             key:   "user-123",
             value: { orderId: 42, ... } ]
                │
                ▼
         Kafka выбирает партицию:
         - key задан → hash(key) % numPartitions
           → один и тот же ключ всегда идёт в одну партицию
         - key = null → round-robin по партициям
           → равномерное распределение
```

Ключ — это не уникальный идентификатор сообщения. Это инструмент **управления партиционированием**: все сообщения с одним ключом гарантированно попадают в одну партицию → их порядок гарантирован.

## Потребитель (Consumer)

**Потребитель (consumer)** — клиент, который читает сообщения из топика. Consumer подписывается на топик и Kafka назначает ему партиции.

Потребители работают в **pull-модели**: consumer сам опрашивает брокер (`poll()`), а не брокер "толкает" (push) сообщения к потребителю. Это отличие от некоторых других систем и от HTTP webhooks. Pull-модель позволяет потребителю читать в собственном темпе и не перегружаться.

```ts
// Упрощённая схема работы потребителя (псевдокод)
while (true) {
  const messages = consumer.poll(timeout: 1000ms); // pull у брокера
  for (const message of messages) {
    await processMessage(message);
  }
  consumer.commitOffset(); // сохранить прогресс
}
```

## Consumer Group — как Kafka объединяет pub/sub и queue в одном

**Consumer group (группа потребителей)** — это именованная группа процессов-потребителей, которые читают один топик сообща.

Правило распределения партиций: **каждая партиция топика назначается ровно одному потребителю внутри группы**.

Это правило — ключ к пониманию того, как Kafka реализует два принципиально разных паттерна в зависимости от конфигурации:

### Паттерн 1: Параллельная обработка (queue-like)

Одна группа, несколько потребителей — каждый читает свою партицию:

```txt
Topic "orders" (3 партиции), Consumer Group "order-processor":

Partition 0 ──► Consumer A  (обрабатывает треть всех заказов)
Partition 1 ──► Consumer B  (обрабатывает треть всех заказов)
Partition 2 ──► Consumer C  (обрабатывает треть всех заказов)

→ Горизонтальное масштабирование: добавить потребителя и партицию,
  и нагрузка разделится
→ Каждое сообщение обрабатывается ровно одним потребителем группы
```

Это аналог классической очереди с несколькими воркерами. Но с важным отличием: если consumer A падает, его партиции перераспределяются на B и C (rebalance) — автоматически.

### Паттерн 2: Pub/Sub (каждый получает копию)

Несколько групп, каждая получает все сообщения:

```txt
Topic "order-placed" (3 партиции):

Consumer Group "search-service":
  Partition 0 ──► Search Consumer 1
  Partition 1 ──► Search Consumer 2
  Partition 2 ──► Search Consumer 3

Consumer Group "analytics-service":
  Partition 0 ──► Analytics Consumer 1
  Partition 1 ──► Analytics Consumer 2
  Partition 2 ──► Analytics Consumer 3

→ Каждая группа получает ВСЕ сообщения топика
→ Группы абсолютно независимы: их офсеты не связаны
```

Это pub/sub: одно событие "заказ размещён" → и search, и analytics получают его полностью.

### Лимит параллелизма

Максимальное число "полезных" потребителей в группе = число партиций. Если потребителей больше, лишние сидят без дела:

```txt
3 партиции, 5 потребителей в одной группе:

Partition 0 ──► Consumer A  ✓ активен
Partition 1 ──► Consumer B  ✓ активен
Partition 2 ──► Consumer C  ✓ активен
(нет партиции) Consumer D  ✗ idle (не получает сообщений)
(нет партиции) Consumer E  ✗ idle (не получает сообщений)
```

Потребители D и E готовы взять на себя партицию при отказе A, B или C — это резерв. Но больше партиций, чем есть в топике, добавить нельзя без изменения топика.

## Брокер (Broker)

**Брокер (broker)** — это один узел (сервер/процесс) Kafka. Брокер принимает запросы от продюсеров, хранит партиции на диске, отдаёт данные потребителям.

Один брокер может хранить сотни партиций от разных топиков. Брокеры взаимодействуют между собой для репликации данных.

```txt
Broker — это:
  - Процесс kafka (JVM)
  - Хранилище партиций (сегменты файлов на диске)
  - Сервер для продюсеров и потребителей
  - Участник репликации

Broker — это НЕ:
  - Отдельная база данных
  - Знающий о состоянии потребителей
    (кроме офсетов в __consumer_offsets)
  - "Умный" маршрутизатор (это делает клиент)
```

## Кластер (Cluster)

**Кластер (cluster)** — это группа брокеров, работающих вместе. Один из брокеров исторически (при ZooKeeper) выполнял роль Controller — координировал выборы лидеров партиций и отслеживал состояние кластера.

```txt
Минимальный production-кластер (3 брокера):

  ┌──────────┐    ┌─────────────┐    ┌──────────┐
  │ Broker 1 │◄──►│ Broker 2    │◄──►│ Broker 3 │
  │          │    │ Controller  │    │          │
  └──────────┘    └─────────────┘    └──────────┘

  Все три брокера реплицируют партиции друг другу.

3 брокера → кластер переживает отказ 1 брокера
            (при replication factor = 3)
```

Почему минимум 3? Принцип кворума (quorum): для согласования нужно большинство (2 из 3). С 2 брокерами кластер не переживёт потерю одного — нет кворума.

## ZooKeeper vs KRaft — что изменилось и почему

Исторически Kafka использовала **ZooKeeper** (Apache ZooKeeper) — отдельный координационный сервис — для:
- Хранения метаданных кластера (какие брокеры существуют, какая партиция на каком брокере)
- Выборов лидера Controller
- Хранения конфигураций топиков

```txt
Kafka с ZooKeeper (до Kafka 3.x):

  ┌─────────────────────┐    ┌──────────┐
  │    ZooKeeper        │    │ Broker 1 │
  │   (отдельный        │◄──►│ Broker 2 │
  │    кластер!)        │    │ Broker 3 │
  └─────────────────────┘    └──────────┘
  
  → Нужно поднимать и поддерживать 2 отдельных кластера
  → ZooKeeper становился узким местом при больших кластерах
  → Усложнённые операции: смена конфигурации требовала ZooKeeper
```

**KRaft** (Kafka Raft) — встроенный протокол консенсуса Kafka, который заменяет ZooKeeper. Он пришёл с KIP-500, это Kafka Improvement Proposal:

```txt
Kafka с KRaft (Kafka 3.3+, default с Kafka 4.0):

  ┌───────────────────────────────────────────────┐
  │                 Kafka Cluster                 │
  │                                               │
  │  ┌─────────────┐  ┌──────────┐  ┌──────────┐  │
  │  │ Broker 1    │  │ Broker 2 │  │ Broker 3 │  │
  │  │ (Controller │  │          │  │          │  │
  │  │ mode)       │  │          │  │          │  │
  │  └─────────────┘  └──────────┘  └──────────┘  │
  │                                               │
  │  Метаданные хранятся внутри кластера          │
  │  в выделенном внутреннем топике               │
  └───────────────────────────────────────────────┘

  → Один кластер вместо двух
  → Быстрее переключение контроллера (миллисекунды против секунд)
  → Поддержка миллионов партиций (ZooKeeper масштабировался плохо)
```

**Практически**: если вы запускаете новый проект сегодня — используйте KRaft. ZooKeeper объявлен устаревшим и будет удалён в Kafka 4.x. В большинстве управляемых сервисов переход на KRaft уже произошёл незаметно для пользователя. Среди них Confluent Cloud и Amazon Managed Streaming for Apache Kafka.

## Типичные ошибки на интервью

**"Consumer Group — это несколько потребителей, которые дублируют друг друга"**

Нет. Внутри группы каждая партиция назначена ровно одному потребителю — дублирования нет. Дублирование возникает между группами: группа A и группа B оба получают все сообщения топика, но это не дублирование, а pub/sub паттерн.

**"Offset — это глобальный счётчик по всему топику"**

Нет. Offset уникален в пределах партиции. У топика с 3 партициями есть три независимых последовательности офсетов: 0..N в partition 0, 0..M в partition 1, 0..K в partition 2. Нет единого "offset 42 в топике".

**"Добавить потребителей в группу → линейный рост производительности"**

Только до числа партиций. После этого — лишние потребители просто ждут. Реальный рост производительности = увеличение числа партиций (плюс потребителей).

**"В одном партиции несколько потребителей из одной группы читают параллельно"**

Нет. Одному партиции — один consumer в группе. Это ограничение дизайна: именно оно гарантирует порядок обработки внутри партиции.

**"ZooKeeper — часть Kafka, которую всегда надо поднимать"**

Устаревшая информация. С Kafka 3.3+ KRaft стал production-ready и рекомендуется по умолчанию. С Kafka 4.0 ZooKeeper-режим удалён.
