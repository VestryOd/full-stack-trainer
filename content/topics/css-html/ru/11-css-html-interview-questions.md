# CSS и HTML продвинутого уровня — вопросы на интервью

## Группа 1: Блочная модель и раскладка

**Какова итоговая ширина элемента с `width: 300px`, `padding: 0 20px`, `border: 3px solid` и значением `box-sizing` по умолчанию?**

`346px`. По умолчанию `box-sizing: content-box` означает, что `width` задаёт только область контента, а padding и border добавляются сверх.

```css
.box { width: 300px; padding: 0 20px; border: 3px solid; }
/* content-box (умолчание): 300 + 20 + 20 + 3 + 3 = 346px на экране */
/* border-box:              300px на экране, контент сжат до 254px */
```

Поэтому современный универсальный сброс применяет `box-sizing: border-box` ко всем элементам, включая `::before` и `::after`.

---

**Объясните коллапс margin. Когда он происходит, а когда нет?**

Коллапс margin объединяет смежные вертикальные отступы в один, равный наибольшему из двух, а не их сумме.

```css
.first  { margin-bottom: 20px; }
.second { margin-top: 30px; }
/* Расстояние между ними: 30px, а не 50px */
```

Три сценария запускают его:

- Смежные блочные сиблинги: нижний margin первого и верхний margin второго схлопываются.
- Родитель и первый или последний потомок: если между ними нет border, padding или BFC (контекста блочного форматирования), margin потомка вытекает из родителя.
- Пустые блоки: элемент без высоты, border и padding схлопывает собственные верхний и нижний margin.

Коллапс **не** происходит во flex- и grid-контейнерах, у float-элементов и когда элементы разделяет BFC. Элементы с `position: absolute` и `position: fixed` тоже не участвуют. Частая ловушка: переключение с `display: block` на `display: flex` заставляет ранее схлопнутые margin внезапно складываться.

---

**Что такое Block Formatting Context (BFC) и что его создаёт?**

BFC — изолированная среда раскладки. Элементы внутри неё не взаимодействуют с внешними по части раскладки: margin не схлопывается через границу, float-элементы остаются внутри.

```css
.a { overflow: hidden; }    /* создаёт BFC, но заодно обрезает контент */
.b { display: flow-root; }  /* создаёт BFC без побочных эффектов */
```

BFC создают и другие вещи: `display: flex`, `display: grid`, `float`, `position: absolute`, `position: fixed`, а также `contain: layout` и `contain: paint`. Практическая разница между двумя строками выше — в побочном эффекте. Берите `display: flow-root`, когда нужен BFC и ничего больше.

---

**Почему `position: fixed` иногда не фиксируется относительно вьюпорта?**

Потому что у предка есть `transform`, `filter`, `will-change: transform`, `backdrop-filter` или `perspective`.

```css
.ancestor { transform: translateZ(0); } /* новый содержащий блок */
.child    { position: fixed; top: 0; }  /* фиксируется к .ancestor */
```

Любое из этих свойств создаёт новый содержащий блок, который захватывает потомков с `position: fixed`. Дальше они позиционируются относительно этого предка, а не вьюпорта. Даже `transform: none` может вызвать это в некоторых браузерах.

Архитектурное решение: рендерить фиксированные элементы — модалки, тосты, выдвижные панели — прямыми потомками `<body>`. Это паттерн портала, который используют React Portal и Vue Teleport.

## Группа 2: Flexbox

**В чём разница между `flex: 1` и `flex: 1 1 auto`?**

Значение `flex-basis`.

```css
.a { flex: 1; }        /* = flex: 1 1 0%   → равная ширина */
.b { flex: 1 1 auto; } /* старт от ширины контента → неравная */
```

С `flex: 1` все элементы начинают с нуля и растут пропорционально, поэтому получаются равными независимо от контента. С `flex: 1 1 auto` каждый элемент стартует от собственной ширины контента, и делится только оставшееся свободное пространство. Элемент с бо́льшим контентом остаётся крупнее. Для по-настоящему равных колонок берите `flex: 1` или, что то же самое, `flex-basis: 0`.

---

**Flex-элемент имеет `flex-shrink: 1`, но всё равно переполняет контейнер. Почему?**

Значение `min-width: auto` по умолчанию у flex-элементов.

```css
.item { flex-shrink: 1; min-width: 0; overflow: hidden; }
/* Без min-width: 0 элемент не сожмётся уже своего контента */
```

Когда flex-элемент содержит собственный контент — текст, изображения, элементы с явной шириной, — `min-width: auto` разрешается в минимальный размер контента. Это наименьший размер, при котором содержимое ещё не переполняется, и ниже этого порога `flex-shrink` не опустится.

Добавление `min-width: 0` убирает порог, и `flex-shrink` начинает работать. Следом ставьте `overflow: hidden`, чтобы удержать обрезанный контент. Именно поэтому усечение текста через `text-overflow: ellipsis` требует `min-width: 0` на flex-предке.

---

**Как `flex-shrink` распределяет переполнение между элементами — пропорционально значениям `flex-shrink`?**

Не совсем. Сжатие взвешивается обоими параметрами: вес элемента равен `flex-shrink × flex-basis`.

```
A: flex-shrink: 2, flex-basis: 200px → вес 400
B: flex-shrink: 1, flex-basis: 200px → вес 200
Переполнение делится в отношении 400 : 200
```

Поэтому при равных `flex-shrink` элементы с бо́льшим `flex-basis` сжимаются сильнее в абсолютных пикселях. Алгоритм так и задуман: чтобы мелкие элементы не сжимались непропорционально.

---

**Как выровнять один flex-элемент к дальнему концу главной оси, оставив остальные в начале?**

Поставьте `margin-left: auto` на элемент, который нужно сдвинуть вправо, или `margin-inline-start: auto`, если предпочитаете логические свойства.

```css
.nav { display: flex; }
.nav .login { margin-left: auto; } /* поглощает всё свободное место */
```

Во Flexbox `auto`-margin поглощает всё доступное свободное пространство в своём направлении. Учтите, что `justify-self` на flex-элементах не работает вовсе — это свойство только для grid. Тот же результат даёт `margin-right: auto` на последнем левостороннем элементе.

## Группа 3: CSS Grid

**Что точно означает `1fr` — это одна доля ширины контейнера?**

Нет — одна доля **доступного свободного пространства**, а не ширины контейнера. Свободное пространство остаётся после того, как разрешены все фиксированные треки (px, em, %) и все gap.

```
Контейнер 900px, колонка 200px, две колонки 1fr, gap 20px
Свободное место: 900 - 200 - 2×20 = 660px
Каждая fr:       660 / 2 = 330px
```

Поэтому `fr` предпочтительнее `%`. Процентные колонки считаются от полной ширины вместе с gap и потому переполняются, а колонка в `fr` вписывается всегда.

---

**В чём разница между `auto-fill` и `auto-fit` в `repeat()`?**

Оба создают максимально возможное количество треков. Разница проявляется, когда элементов меньше, чем слотов.

```css
grid-template-columns: repeat(auto-fill, minmax(200px, 1fr));
/* пустые треки остаются; элементы не растут за max из minmax */
grid-template-columns: repeat(auto-fit, minmax(200px, 1fr));
/* пустые треки схлопываются в 0; элементы тянутся на всю ширину */
```

Когда элементов хватает на все треки, оба ведут себя одинаково. Берите `auto-fit` для обычной адаптивной сетки без медиазапросов. Берите `auto-fill`, когда элементы должны сохранять минимальный размер, даже если остаются пустые колонки.

---

**Как работает `grid-column: 1 / -1` и что такое `-1`?**

Линия `-1` обозначает последнюю линию **явной** сетки, поэтому `grid-column: 1 / -1` тянется от первой до последней явной колоночной линии.

```css
.grid { grid-template-columns: repeat(4, 1fr); } /* 5 линий колонок */
.banner { grid-column: 1 / -1; }                 /* все четыре сразу */
```

Оговорка: `-1` работает только для явной сетки. Элементы в неявной сетке, в автоматически сгенерированных строках, не смогут занять полную ширину через `-1`, пока эти строки не объявлены в `grid-template-rows`.

---

**Что такое subgrid и какую проблему он решает?**

Subgrid позволяет grid-элементу, который сам является grid-контейнером, наследовать структуру треков родителя, а не копировать её.

```css
.card { display: grid; grid-row: span 3; grid-template-rows: subgrid; }
/* заголовок, тело и футер садятся на строковые треки родителя */
```

Решаемая проблема видна в сетке карточек. У каждой карточки есть заголовок, тело и футер, и карточки с разной высотой контента уводят футеры на разные уровни. С subgrid все карточки делят строковые треки родителя, и три части выравниваются сами. Все основные браузеры поддерживают это с Chrome 117 (август 2023).

## Группа 4: Контексты наложения и z-index

**Почему `z-index: 9999` не гарантирует, что элемент окажется поверх?**

Потому что z-index локален для контекста наложения. Элементы конкурируют по z-index только внутри одного контекста.

```css
.ctx-x { position: relative; z-index: 1; }  /* внутри элемент A */
.ctx-y { position: relative; z-index: 2; }  /* внутри элемент B */
.a     { z-index: 9999; }  /* всё равно под всем содержимым .ctx-y */
```

Контекст X целиком рендерится под контекстом Y, вместе с элементом A. Исправлять нужно на уровне контекста наложения, а не на внутреннем элементе.

---

**Назовите пять вещей, создающих контекст наложения, помимо `position` + `z-index`.**

Достаточно любого пункта из списка:

- `opacity` меньше 1, даже `opacity: 0.99`
- `transform` с любым значением, кроме `none`, включая хаки вроде `translateZ(0)`, которые выносят слой на GPU (graphics processing unit — графический процессор)
- `filter` с любым значением, кроме `none`
- `will-change`, указывающий на свойство композитинга, например `will-change: transform`
- `isolation: isolate`
- `contain: layout`, `paint`, `strict` или `content`
- `mix-blend-mode` не `normal` и `clip-path` не `none`
- `backdrop-filter`
- `position: fixed` и `position: sticky` — всегда, независимо от z-index

Практическое следствие стоит запомнить. Безобидный `transform: translateX(0)` на сайдбаре захватывает всех абсолютно позиционированных потомков, и их z-index конкурируют теперь только внутри сайдбара.

---

**Что такое `isolation: isolate` и когда его использовать?**

Создаёт контекст наложения без визуальных побочных эффектов: без изменения прозрачности, без трансформации, без фильтра.

```css
.widget { isolation: isolate; } /* z-index внутри остаётся внутри */
```

Два основных сценария. Первый — удержать внутренние z-index компонента, чтобы они не конкурировали с внешним миром. Компонент дизайн-системы может использовать `z-index: 10` внутри себя, не мешая модалке страницы с `z-index: 2`. Второй — не дать `mix-blend-mode` смешиваться с элементами за границей компонента. Это CSS-эквивалент границы модуля для наложения.

## Группа 5: Специфичность и каскад

**Какова специфичность `:is(div, .class, #id) p` и почему?**

`(1, 0, 1)`. Псевдокласс `:is()` берёт специфичность **самого специфичного аргумента**.

```css
:is(div, .class, #id) p     /* (1, 0, 0) от #id + (0, 0, 1) от p */
:where(div, .class, #id) p  /* (0, 0, 0) + (0, 0, 1) = (0, 0, 1) */
```

Максимум по списку берётся даже тогда, когда элемент совпал через `div` или `.class`. В этом ключевое отличие от `:where()`, которое всегда вносит `(0, 0, 0)`, какими бы ни были аргументы.

---

**Что такое каскадные слои (`@layer`) и зачем они введены?**

`@layer` объявляет явно упорядоченные корзины стилей. Правила в слое с более высоким приоритетом побеждают правила в слое с более низким, независимо от специфичности.

```css
@layer reset, base, components, utilities;
/* порядок объявления задаёт приоритет: utilities — самый сильный слой */
/* .p-4 (0,1,0) из utilities бьёт .card .title:hover (0,3,0) из components */
```

Стили, которые не лежат ни в каком слое, всегда побеждают слоевые. Слои ввели, чтобы прекратить войны специфичности в масштабе. Без них весь CSS конкурирует по специфичности и порядку, и это ведёт к бесконечной эскалации селекторов и к `!important` по всему коду.

---

**Что происходит, когда CSS-переменная содержит недопустимое для контекста использования значение?**

Это поведение invalid-at-computed-value-time. Свойство разрешается в **унаследованное значение**, если оно наследуется, или в **начальное значение**, если нет — и **не** в браузерное умолчание.

```css
:root { --color: 16px; }
p { color: var(--color); } /* недопустимо для color */
/* Результат: унаследованный цвет, а не чёрный */
```

Поэтому баги с CSS-переменными трудно отлаживать. В консоли нет ошибки, а запасное поведение не то, которое ожидаешь.

## Группа 6: Адаптивный и современный CSS

**Какую проблему решают container queries, которую медиазапросы не могут?**

Адаптацию компонентов к фактическому размеру их контейнера, а не к глобальному размеру вьюпорта.

```css
.sidebar, .main { container-type: inline-size; }
@container (min-width: 400px) { .card { display: grid; } }
```

Одна и та же карточка в сайдбаре 280px и в основной области 600px требует разных раскладок при одном и том же вьюпорте. Медиазапросы знают только вьюпорт и различить эти два размещения не могут. Container queries делают компонент по-настоящему переиспользуемым: один компонент, один CSS, корректная раскладка в контейнере любой ширины.

---

**Объясните `clamp(1rem, 2.5vw, 2rem)` точно.**

Значение равно `2.5vw` — предпочтительному выражению, зависящему от вьюпорта, — ограниченному минимумом `1rem` и максимумом `2rem`.

```
вьюпорт 400px:  2.5vw = 10px < 16px (1rem)  → берётся 1rem
вьюпорт 800px:  2.5vw = 20px, между границ  → берётся 20px
вьюпорт 1400px: 2.5vw = 35px > 32px (2rem)  → берётся 2rem
```

Между крайними точками значение меняется непрерывно, без скачков на брейкпоинтах. Одно объявление заменяет два медиазапроса.

---

**В чём разница между `margin-left` и `margin-inline-start`?**

`margin-left` — физическое свойство: это всегда левая сторона, независимо от направления письма. Логическое свойство `margin-inline-start` указывает на начало inline-направления и следует за `direction` и `writing-mode`.

```css
.icon { margin-inline-start: 8px; }
/* слева направо (LTR): margin-left  */
/* справа налево (RTL): margin-right */
/* вертикальный режим письма: верх или низ */
```

Преимущество: раскладки справа налево и вертикальные не требуют ни одного `[dir="rtl"]`-переопределения, потому что сопоставление делает браузер. Для международных приложений логические свойства должны быть стандартом.

## Группа 7: Конвейер рендеринга и производительность

**Назовите пять этапов конвейера рендеринга браузера и что каждый делает.**

```
Parse → Style → Layout → Paint → Composite → Экран
```

1. **Parse** — HTML превращается в DOM (Document Object Model), CSS — в CSSOM (CSS Object Model), и оба объединяются в Render Tree. CSS блокирует рендеринг, а `<script>` без `async` или `defer` блокирует парсер.
2. **Style (Recalculate Style)** — вычисляет итоговый стиль каждого элемента: каскад, наследование, кастомные свойства и относительные единицы в абсолютных пикселях.
3. **Layout (Reflow)** — вычисляет геометрию, позицию и размер каждого элемента. Самый дорогой этап, потому что каскадирует по всему документу.
4. **Paint** — записывает инструкции рисования, команды, а не пиксели, для каждого слоя: фоны, рамки, текст, тени.
5. **Composite** — GPU объединяет слои в финальный кадр, применяя трансформации и прозрачность.

Только два CSS-свойства запускают этот последний этап в одиночку: `transform` и `opacity`.

---

**Какие CSS-свойства запускают только Composite и почему? Почему не `left`/`top`?**

Только `transform` и `opacity`. Они не влияют на геометрию, поэтому Layout не нужен, и не меняют пиксельный вид самого элемента, поэтому не нужен Paint.

```css
.smooth { transition: transform 200ms; } /* только Composite */
.janky  { transition: left 200ms; }      /* Layout + Paint + Composite */
```

Браузер повышает элемент до GPU-слоя и загружает его текстуру один раз. Все последующие изменения обрабатывает сам GPU: матричная трансформация или альфа-смешивание на кадр.

`left` и `top` — layout-свойства. Их изменение двигает элемент в потоке документа, а значит пересчитываются позиции соседей, перезаписываются команды рисования, и только потом идёт композитинг. Это работа для CPU (central processing unit — центральный процессор) на каждом кадре. Поэтому анимации через `left` склонны к **рывкам** (jank): заметному подёргиванию, когда браузер не успевает отдать кадр.

---

**Что такое layout thrashing и как его устранить?**

Layout thrashing происходит, когда JavaScript чередует чтение и запись влияющих на layout DOM-свойств внутри цикла.

```javascript
// Thrashing: каждое чтение offsetWidth вызывает синхронный reflow
boxes.forEach(b => { b.style.width = b.offsetWidth * 2 + 'px'; });

// Исправлено: сначала читаем всё, потом пишем всё
const w = boxes.map(b => b.offsetWidth);
boxes.forEach((b, i) => { b.style.width = w[i] * 2 + 'px'; });
```

Каждое чтение вроде `offsetWidth` или `getBoundingClientRect()` заставляет браузер сбросить отложенные изменения стилей и layout, чтобы вернуть актуальное значение. Каждая запись снова инвалидирует layout.

Пакетирование превращает это в один reflow на все чтения и одно обновление layout на все записи. Планирование записей внутри `requestAnimationFrame` ставит их в нужную точку конвейера.

---

**Что реально делает `will-change: transform` и каковы риски?**

Сигнализирует браузеру, что `transform` элемента скоро изменится. Браузер обычно реагирует тем, что заранее, до начала анимации, повышает элемент до GPU-слоя. Создание слоя тогда не портит первый кадр.

```css
.card:hover { will-change: transform; } /* готовим на hover */
* { will-change: transform; }           /* так делать нельзя */
```

Рисков два. Каждый повышенный слой занимает видеопамять на графической карте. И когда повышенный элемент перекрывает множество неповышенных, браузер может повысить их все, чтобы не было артефактов отрисовки. Это и есть взрыв слоёв.

Правила ответственного использования: ставить непосредственно перед анимацией и снимать через `will-change: auto` сразу после. Никогда не применять ко всем элементам.

## Группа 8: CSS-архитектура и формы

**Почему BEM использует единственные классы вместо селекторов-потомков?**

Единственные классы имеют единообразную специфичность `(0, 1, 0)`, поэтому внутри кодовой базы на BEM (Block, Element, Modifier) конфликт специфичности невозможен.

```css
.card .title  { }  /* (0, 2, 0) — ломается, если .title уедет из .card */
.card__title  { }  /* (0, 1, 0) — отношение живёт в имени */
```

BEM кодирует отношение в имени, а не во вложенности селектора. Поэтому переопределить любой BEM-стиль тривиально: победит один класс выше `(0, 1, 0)`. Компромисс в том, что BEM не решает проблему глобальной области. Два разработчика по-прежнему могут создать `.card__title` с конфликтующими намерениями.

---

**Какова основная проблема производительности у runtime CSS-in-JS (Styled Components, Emotion)?**

Вставка стилей идёт в JavaScript на основном потоке во время рендеринга. Каждый рендер с новыми значениями props генерирует новые CSS-правила и вставляет или обновляет теги `<style>`, а это добавляет к Time to Interactive.

При SSR (server-side rendering — рендеринг на сервере) стили ещё и сериализуются в HTML-ответ и заново согласуются на клиенте при гидратации. Сверху этого дополнительный размер бандла от определений стилей увеличивает время парсинга JS.

Эти издержки стали блокирующей проблемой с React Server Components: runtime CSS-in-JS требует браузерного JS-окружения, которого у RSC нет. Zero-runtime альтернативы вроде vanilla-extract и StyleX генерируют CSS при сборке, и стоимость в runtime исчезает.

---

**Что делает `novalidate` на `<form>` и зачем это нужно?**

`novalidate` отключает нативный интерфейс браузерной валидации — платформенные всплывающие пузыри и фокусировку при отправке, — но оставляет Constraint Validation API полностью активным.

```html
<form novalidate>
  <!-- input.validity, checkValidity(), setCustomValidity() работают -->
</form>
```

Это нужно, когда вы строите собственный опыт валидации. То есть контролируете, когда появляются ошибки: при blur, а не только при submit. Сюда же входят визуальный дизайн сообщений, управление фокусом на невалидных полях, межполевая валидация и интеграция серверных ошибок. Нативный интерфейс не поддерживает ничего из этого.

---

**Что такое `setCustomValidity` и какое критическое правило очистки?**

`setCustomValidity(message)` устанавливает кастомное сообщение об ошибке на элементе управления формой. Непустая строка помечает поле невалидным, выставляет `validity.customError = true` и кладёт сообщение в `validationMessage`.

```javascript
input.setCustomValidity('Этот email уже зарегистрирован');
input.addEventListener('input', () => input.setCustomValidity(''));
```

Критическое правило — во второй строке. Сообщение нужно очистить пустой строкой, когда пользователь правит поле. Иначе ошибка сохраняется навсегда, и поле остаётся невалидным даже при абсолютно корректном вводе.

---

**Почему нативной HTML-валидации недостаточно для production, даже если сервер всё равно валидирует?**

Пять причин:

1. **Интерфейс валидации неконтролируем.** Нативные пузыри нельзя стилизовать и позиционировать под дизайн-систему.
2. **Тайминг неправильный.** Нативная валидация срабатывает только при отправке. Лучшая практика — проверять при blur, когда пользователь впервые уходит из поля, и дальше при каждом input после первой ошибки.
3. **Межполевая валидация невозможна.** Совпадение паролей, диапазоны дат и условно обязательные поля в HTML-атрибутах не выразить.
4. **Серверные ошибки нельзя показать.** У дублирующегося email или недействительного купона нет нативного механизма отображения, поэтому нужны `setCustomValidity` и JavaScript.
5. **Асинхронная валидация невозможна.** Проверка того, свободно ли имя пользователя, требует запроса к API, а атрибут `pattern` его не сделает.

## Группа 9: Доступность и семантика

**Что такое дерево доступности и почему оно важно?**

Дерево доступности — параллельное представление страницы, которое браузеры строят из семантического HTML и атрибутов ARIA (Accessible Rich Internet Applications). Скринридеры, брайлевские дисплеи, программы голосового управления и другие вспомогательные технологии читают именно это дерево, а не DOM и не визуальную раскладку.

```html
<div class="btn" onclick="submit()">Отправить</div> <!-- без роли -->
<button type="submit">Отправить</button>            <!-- роль и Tab -->
```

Элемент `<div>` есть в DOM, но в дереве доступности у него нет ни роли, ни клавиатурного поведения, ни состояния. У `<button>` есть `role=button`, он стоит в порядке Tab, активируется Пробелом и Enter и несёт состояние disabled. Каждый `<div>` на месте семантического элемента — это ручная переимплементация того, что браузер даёт бесплатно.

---

**Когда ARIA полезна, а когда вредна?**

Полезна в трёх случаях:

- Кастомные интерактивные виджеты без HTML-аналога: tab list, tree view, combobox.
- Динамически меняющиеся состояния, которые нужно объявить скринридеру, через `aria-expanded` или `aria-live`.
- Подписи для элементов, которым нельзя дать `<label>`: кнопки-иконки, регионы-ориентиры.

Вредна в трёх других:

- Когда переопределяет корректную нативную семантику, например `role="button"` на `<div>`, который клавиатуру не обрабатывает.
- Когда `aria-hidden="true"` стоит на контейнере с фокусируемыми потомками — получается дыра, в которой фокус пропадает.
- Когда некорректная роль вводит вспомогательные технологии в заблуждение.

Руководящий принцип: **отсутствие ARIA лучше плохой ARIA**. Всегда предпочитайте нативную семантику и добавляйте ARIA только там, где её не хватает.

---

**Что такое паттерн roving tabindex и когда применяется?**

Roving tabindex нужен для составных виджетов, где Tab перемещает между виджетами, а стрелки — внутри одного. Так устроены tab list, toolbar, radio group и tree view.

```html
<div role="tablist">
  <button role="tab" tabindex="0">Основные</button>   <!-- активный -->
  <button role="tab" tabindex="-1">Приватность</button> <!-- по стрелке -->
</div>
```

В любой момент ровно один элемент несёт `tabindex="0"`, а все остальные — `tabindex="-1"`. Обработчики стрелок перемещают фокус, меняя эти два значения местами.

Виджет тогда становится единственной точкой Tab на странице. Пользователю клавиатуры не приходится обходить табом каждую вкладку в tab list, чтобы выйти из компонента.

## Группа 10: Продвинутые и сквозные вопросы

**Как отладить проблему z-index, когда элемент оказывается позади другого несмотря на более высокий z-index?**

Четыре шага:

1. **Определить цепочку контекстов наложения для обоих элементов.** Пройти вверх по DOM от каждого и отметить всех предков, создающих контекст. Проверить `position` с `z-index`, `opacity` меньше 1, `transform`, `filter`, `will-change`, `isolation` и `contain`.
2. **Найти общий предок-контекст.** Сравнение, которое решает исход, происходит на этом уровне между двумя контекстами, а не между собственными z-index элементов.
3. **Исправить на правильном уровне.** Скорректировать z-index содержащего контекста наложения, а не внутреннего элемента.
4. **Рассмотреть паттерн портала.** Если элемент живёт внутри компонента вроде сайдбара или карточки, рендерите оверлеи потомками `<body>` и обходите захват целиком.

---

**В чём разница между `contain: layout`, `contain: paint` и `contain: strict`?**

Три уровня ограничения:

- `contain: layout` — внутренние изменения layout не влияют наружу и наоборот, поэтому браузер может делать reflow поддерева отдельно. Побочные эффекты: элемент становится контекстом наложения, BFC и содержащим блоком для позиционированных потомков.
- `contain: paint` — элемент работает как вьюпорт для своего поддерева, и потомки не могут визуально выйти за его пределы. Создаёт те же три вещи и ведёт себя как `overflow: hidden` с дополнительными подсказками производительности.
- `contain: strict` — `layout + paint + size + style`, самая строгая форма. Требует явных `width` и `height`, потому что ограничение размера означает, что браузер игнорирует потомков при вычислении размера элемента.

Берите `contain: strict` для компонентов фиксированного размера, которые часто обновляются: миниатюр, элементов сетки, где изолированный reflow важен для производительности.

---

**Сравните три подхода к адаптивной типографике: медиазапросы, единицы `vw` и `clamp()`.**

```css
@media (min-width: 768px) { html { font-size: 18px; } } /* шаги */
html { font-size: 2vw; }                                /* без границ */
html { font-size: clamp(1rem, 2.5vw, 1.5rem); }         /* с границами */
```

- **Медиазапросы** дают явные шаги: 16px до 768px, 18px выше. Просто, но на каждом брейкпоинте виден резкий скачок, а каждый новый брейкпоинт добавляет работы по поддержке.
- **Единицы `vw`** масштабируются непрерывно, но без пола и потолка. Текст становится нечитаемо мелким на телефонах и нечитаемо крупным на широких мониторах, так что его всё равно приходится ограничивать.
- **`clamp()`** сочетает непрерывное масштабирование с заданными границами. Значение плавно движется между мобильным полом и десктопным потолком, и медиазапросы не нужны вовсе.

Последний вариант и есть предпочтительный современный подход: одно объявление охватывает все размеры вьюпорта.

---

**Когда выбрать CSS Modules вместо Tailwind и наоборот?**

**CSS Modules вместо Tailwind** — когда стили компонента включают тонкую работу с псевдоэлементами, сложные анимации или глубоко условную логику. Сюда же случай, когда стили читаются лучше одним связным блоком, чем пятнадцатью utility-классами.

Тот же выбор подходит команде с сильной экспертизой в CSS, которая предпочитает писать стили явно, и дизайн-системе, построенной на CSS-переменных, а не на отображении в utility-классы.

**Tailwind вместо CSS Modules** — когда важна скорость итерации: файлы переключать не надо, стили стоят рядом с разметкой.

Он же выигрывает, когда нужна встроенная дизайн-система с ограничениями вроде шкалы `spacing-4`, и когда проект уже использует компонентный фреймворк, который прячет повторение списков классов. Третий аргумент — размер бандла: Tailwind вырезает неиспользуемые utility, и отгружаемый CSS остаётся минимальным.
