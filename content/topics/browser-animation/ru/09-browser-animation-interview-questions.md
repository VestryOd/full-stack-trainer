# Browser Animation — вопросы для интервью (Middle → Senior)

## Группа 1: Rendering Pipeline и основы

**Почему `transform` и `opacity` считаются "дешёвыми" для анимации, а `top`/`left`/`width` — "дорогими"?**

Потому что они запускают разные стадии конвейера рендеринга.

```txt
┌─────────────────────────────────────────────────────┐
│ Style      какие правила к какому элементу          │
├─────────────────────────────────────────────────────┤
│ Layout     позиции и размеры                        │
│            сюда входят width, top, left, margin     │
├─────────────────────────────────────────────────────┤
│ Paint      залить пиксели                           │
│            сюда входят background-color, box-shadow │
├─────────────────────────────────────────────────────┤
│ Composite  разместить и смешать готовые слои        │
│            сюда входят transform, opacity           │
└─────────────────────────────────────────────────────┘
```

Любое изменение геометрии (`width`, `top`, `left`, `margin`) требует Layout. Браузер обязан пересчитать позиции и размеры, возможно каскадно для соседних и дочерних элементов. Следом идёт Paint, чтобы перекрасить затронутые пиксели.

`transform` и `opacity` не меняют геометрию документа и не требуют перекраски уже отрисованного контента. Они меняют только то, как уже готовый, растеризованный слой позиционируется и смешивается на этапе Composite. Composite может выполняться на отдельном компоузитор-потоке, независимо от главного. Поэтому анимация на `transform`/`opacity` продолжает идти плавно, даже если главный поток занят тяжёлым JS.

Неточный, но часто звучащий ответ — "потому что GPU (graphics processing unit, графический процессор)". Он не объясняет механизм: `box-shadow` тоже может рендериться с использованием GPU и всё равно требует Paint.

---

**В чём разница между главным потоком (main thread) и компоузитор-потоком (compositor thread), и почему это важно для анимации?**

Главный поток — единственный поток, где выполняется JS, Style-recalc, Layout, Paint и обработчики событий.

```txt
┌────────────────────────────┐  ┌───────────────────────┐
│ Главный поток              │  │ Компоузитор-поток     │
│                            │  │                       │
│ JS                         │  │ Двигает, масштабирует │
│ Style-recalc               │  │ и гасит уже           │
│ Layout, Paint              │  │ растеризованные слои  │
│ Обработчики событий        │  │                       │
│                            │  │ Работает даже пока    │
│ Последовательный. Пока     │  │ главный поток занят   │
│ занят — ни кадра, ни клика │  │ тяжёлым JS            │
└────────────────────────────┘  └───────────────────────┘
```

Главный поток последовательный. Пока он занят, он не может обработать ни следующий кадр рендеринга, ни клик пользователя. Компоузитор-поток — отдельный, более лёгкий поток. Он умеет самостоятельно анимировать уже растеризованные слои: двигать, масштабировать, менять прозрачность — без обращения к главному потоку каждый кадр.

Практическое следствие: анимация, требующая Style, Layout или Paint, блокируется тяжёлым JS на главном потоке. Чисто композиторная анимация (`transform`/`opacity`) — почти нет, потому что физически исполняется в другом потоке.

---

**Что такое jank с точки зрения физики происходящего в браузере?**

Jank — это пропущенный кадр.

Браузер должен успеть подготовить новый кадр к моменту, когда дисплей готов его показать. Этот бюджет — 16.7 мс на 60 Гц или 8.3 мс на 120 Гц. Не успел — дисплей повторно показывает предыдущий кадр.

Визуально это выглядит как рывок. Вместо равномерной последовательности небольших шагов движения глаз видит один "прыжок". Этот прыжок покрывает расстояние двух шагов за то время, которое раньше уходило на один.

Причина пропуска кадра почти всегда одна. Главный поток был занят дольше, чем позволяет frame budget (JS, Layout, Paint), и не успел подготовить кадр вовремя.

---

**Когда элемент получает свой отдельный composited layer, что это стоит, и почему "добавь `will-change` на всякий случай везде" — плохая практика?**

Браузер создаёт отдельный слой в этих случаях:

- 3D-transform (`translateZ(0)`, `translate3d`).
- `will-change: transform/opacity`.
- Наличие `<video>`, `<canvas>` или `<iframe>`.
- Анимируемый `filter`.
- Активная CSS-анимация или переход по `transform`/`opacity`.

Каждый слой — отдельная GPU-текстура. Память под неё примерно равна `ширина × высота × 4 байта (RGBA)`.

`will-change`, развешенный на множество статичных элементов "про запас", резервирует эту память немедленно, а не в момент реальной анимации. Это называется layer explosion.

Десятки лишних слоёв тратят память и время на composite-стадию, и в сумме это **ухудшает** производительность именно там, где `will-change` должен был её улучшить. Особенно заметно на мобильных устройствах, где память общая для CPU (central processing unit, центральный процессор) и GPU.

Правильный паттерн — добавлять `will-change` непосредственно перед анимацией и снимать сразу после её завершения.

---

**Что такое layout thrashing, как его диагностировать и как исправить?**

Браузер по умолчанию батчит изменения стилей и откладывает пересчёт Layout до следующего кадра.

Но некоторые JS-свойства обязаны вернуть **актуальную** геометрию: `offsetHeight`, `offsetWidth`, `getBoundingClientRect()`, `scrollTop`. Если перед чтением были невыполненные изменения стилей, браузер вынужден немедленно, синхронно посчитать layout — forced synchronous layout.

Опасность не в одном таком чтении. Она в чередовании записи и чтения в цикле: каждая итерация форсирует полный reflow заново.

```javascript
// ❌ Layout thrashing
items.forEach((item) => {
  const h = item.offsetHeight;              // чтение → форсирует layout
  item.style.height = `${h + 10}px`;         // запись → инвалидирует layout
});

// ✅ Фикс: разделить фазы чтения и записи
const heights = items.map((item) => item.offsetHeight); // все чтения сначала
// потом все записи
items.forEach((item, i) => { item.style.height = `${heights[i] + 10}px`; });
```

Диагностика в production-коде — это DevTools Performance-панель. Подобные случаи явно помечаются фиолетовым блоком Layout с меткой "Forced reflow" и дают stack trace до конкретной строки кода. Читать весь код построчно не нужно.

## Группа 2: CSS Transitions и Keyframes

**Почему `transition: all` считается источником продакшен-багов, а не безобидным сокращением?**

Потому что это открытый контракт: **любое** будущее изменение **любого** CSS-свойства элемента начинает анимироваться. Сюда входят и изменения, добавленные другим разработчиком месяцы спустя, без осознания, что на элементе висит `transition`.

Классический сценарий: к элементу с `transition: all` добавляют `position: sticky` для адаптивной логики. При активации и деактивации sticky-состояния элемент начинает "проезжать" на новую позицию за время transition, хотя никто не планировал это анимировать.

Дополнительный, менее очевидный довод. Браузер вынужден отслеживать все animatable-свойства элемента, чтобы понять, нужно ли запускать переход. Это даёт небольшой, но постоянный оверхед, который снимается явным списком свойств.

---

**В чём разница между `transition` и `animation`/`@keyframes`? Когда что выбирать?**

`transition` требует триггера и описывает единственный переход. `animation` с `@keyframes` не требует триггера и описывает сколько угодно шагов.

| | `transition` | `animation` + `@keyframes` |
|---|---|---|
| Нужен триггер | Да: изменение состояния, класса или computed-значения | Нет: может начаться сама, при появлении элемента |
| Промежуточные точки | Один переход, из текущего значения в новое | Произвольное число |
| Повтор, направление | Не встроены | `animation-iteration-count`, `animation-direction` |

Выбор: `transition` — для реакции на изменение состояния, например hover или открыт/закрыт. Для самозапускающихся или циклических эффектов берут `animation`: спиннер, pulse, покадровая спрайт-анимация.

---

**Что делает `animation-fill-mode`, и какой баг возникает, если про него забыть?**

`animation-fill-mode` определяет, какие стили применяются к элементу **до** начала и **после** окончания keyframe-анимации. По умолчанию (`none`) вне времени анимации действуют обычные CSS-правила элемента, а **не** значения keyframes.

Классический баг: элемент анимируется из `opacity: 0` в `opacity: 1` через `@keyframes` с `animation-iteration-count: 1`. Анимация корректно проигрывается, но по завершении элемент внезапно исчезает. Без `forwards` браузер откатывает его к обычному состоянию, где `opacity` не задан значением последнего кадра.

Фикс: `animation-fill-mode: forwards`. Или `both`, если нужно ещё и применить первый кадр до `animation-delay`.

---

**Как анимировать `height: auto` (проблема аккордеона)? Назовите минимум два подхода.**

CSS исторически не умел анимировать переход к `auto` или от него. Причина: `auto` — не число, а инструкция "вычисли по контенту". А `transition` не знает целевого значения заранее.

Два рабочих подхода:

- **CSS Grid-трюк.** Обернуть контент в `display: grid` с `grid-template-rows: 0fr`, переключать на `1fr` при открытии, а на внутренний контейнер поставить `overflow: hidden`. Кросс-браузерно надёжный вариант.
- **`interpolate-size: allow-keywords` на `:root` в сочетании с `calc-size()`.** Эта современная пара позволяет напрямую анимировать `height: auto`. Поддержка в браузерах на момент написания ещё не универсальна, поэтому стоит проверять актуальную поддержку и давать фолбэк.

---

**В чём разница между `cubic-bezier()`, `steps()` и `linear()` как timing functions?**

Три разных механизма, а не три варианта одного.

| Функция | Механизм | Замечание |
|---|---|---|
| `cubic-bezier(x1, y1, x2, y2)` | Гладкая кривая по двум контрольным точкам. Координаты `y` могут выходить за [0, 1], что даёт overshoot или bounce. | Только одна гладкая форма: множественные осцилляции она не опишет. |
| `steps(n, jump-term)` | Не непрерывная интерполяция, а `n` дискретных скачков значения. | Для покадровой спрайт-анимации через `background-position`, а не для плавности. |
| `linear()` | Piecewise-линейная кривая через явный список точек `(значение, позиция%)`. | Описывает многократный bounce/spring-эффект в чистом CSS. Раньше это требовало JS. |

## Группа 3: Web Animations API

**Как WAAPI соотносится с CSS transitions/animations "под капотом"?**

WAAPI — это Web Animations API, и это не альтернативный движок. Это программный интерфейс к тому же самому движку, который исполняет `transition` и `@keyframes`.

`element.animate()` создаёт тот же внутренний `KeyframeEffect`, с той же интерполяцией по типу значения. И с той же возможностью работать на компоузиторе для `transform`/`opacity`/`filter`.

Разница не в производительности. Она в том, откуда берутся значения и кто управляет воспроизведением. CSS хорош для заранее известных keyframe-значений. WAAPI нужен, когда значение вычисляется в рантайме или анимацией нужно управлять программно: пауза, реверс, промис завершения.

---

**Объясните composite modes в WAAPI (`'replace'` vs `'add'`) и приведите практический случай использования `'add'`.**

`replace` — дефолт, он заменяет underlying-значение; `add` складывается с ним.

| `composite` | Underlying-значение свойства | Для `transform` |
|---|---|---|
| `'replace'` (по умолчанию) | Полностью заменяется значением анимации | Матрица заменяется |
| `'add'` | Значение анимации складывается с ним | Матрицы перемножаются |

Практический случай для `'add'`: базовая "живая" анимация, лёгкое постоянное покачивание элемента, плюс кратковременный bounce-эффект на клик — оба на `transform`.

С `composite: 'add'` вторая анимация накладывается поверх первой. Она не прерывает и не заменяет первую и не требует ручного вычисления комбинированной матрицы трансформации в JS.

Без `add` вторая анимация работала бы с дефолтным `replace` и перебила бы первую на время своего выполнения. После завершения элемент визуально "прыгнул" бы обратно.

---

**Почему для динамически вычисляемых значений анимации лучше использовать WAAPI, а не переключение CSS-классов?**

Переключение классов для произвольного, вычисленного в рантайме значения оставляет два плохих варианта. Либо генерировать CSS "на лету" — класс на каждое возможное значение не заведёшь. Либо использовать inline-стили.

Inline-стилям тогда нужен форсированный reflow-хак (`void el.offsetWidth`) для **повторного** запуска перехода на то же значение. Иначе браузер не увидит смены значения.

WAAPI принимает JS-значение напрямую в `element.animate()`, без промежуточного шага генерации CSS и без reflow-хаков. При этом сохраняется тот же compositor-friendly движок для `transform`/`opacity`.

---

**В чём разница между scroll-linked и scroll-triggered анимацией?**

Scroll-linked прогресс — это сама позиция скролла. Scroll-triggered анимация лишь запускается скроллом, а дальше идёт по своим часам.

| | Scroll-linked | Scroll-triggered |
|---|---|---|
| Прогресс | Равен позиции скролла | Своя длительность и easing |
| Свои "часы" | Нет | Есть |
| Прокрутка назад | Анимация идёт назад синхронно | Ничего не меняется, она доигрывает |
| Чем делается | `animation-timeline: scroll()`/`view()`, `ScrollTimeline`, `ViewTimeline` | `ScrollTrigger` в play-once режиме или `IntersectionObserver` плюс CSS-класс |

## Группа 4: requestAnimationFrame и JS-driven анимация

**Почему ручной `requestAnimationFrame`-цикл обязан учитывать delta time?**

Потому что "двигать значение на фиксированный шаг за кадр" (`x += 2`) даёт скорость, зависящую от частоты обновления дисплея. При идентичном коде на 60 Гц это 120px/сек, на 120 Гц — 240px/сек.

Правильный подход — вычислять время, прошедшее с предыдущего кадра (`timestamp - previousTimestamp`), и масштабировать движение на него. Скорость тогда выражается в единицах за секунду, а не за кадр.

Итоговая скорость получается одинаковой независимо от частоты дисплея. Просто складывается она из разного числа более мелких или более крупных шагов.

---

**Разложите технику FLIP по шагам. Почему она превращает дорогую layout-анимацию в дешёвую?**

FLIP — это First, Last, Invert, Play. Каждый шаг — одно измерение или одна запись.

```txt
┌─────────────────────────────────────────────┐
│ First — измерить старую позицию             │
│ getBoundingClientRect() до изменения DOM    │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ Last — применить изменение DOM              │
│ измерить новую позицию                      │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ Invert — применить компенсирующий transform │
│ без transition: элемент выглядит недвинутым │
└─────────────────────────────────────────────┘
                       │
                       ▼
┌─────────────────────────────────────────────┐
│ Play — включить transition                  │
│ обнулить компенсацию, элемент доезжает      │
└─────────────────────────────────────────────┘
```

First — измерить текущую позицию элемента (`getBoundingClientRect()`) **до** изменения DOM (document object model, дерево элементов страницы). Last — применить реальное изменение DOM, реордер или layout-сдвиг, и измерить новую позицию **после**.

Invert — вычислить разницу между First и Last и немедленно применить компенсирующий `transform` без transition. Элемент визуально остаётся на старом месте, хотя физически уже в новом.

Play — включить transition на `transform` и обнулить компенсацию. Элемент плавно "доезжает" от старой визуальной позиции до настоящей новой.

Дешевизна — в одном факте: вся видимая анимация происходит исключительно через `transform`, на Composite-стадии (статья 01). Реальные layout-свойства не анимируются, а они при большом количестве элементов физически не масштабируются без джанка.

---

**В чём практическая разница между duration-based easing-анимацией и spring-анимацией? Почему спринг можно прервать на полпути без видимого скачка, а duration-based — сложно?**

Duration-based твин идёт по фиксированной кривой, а спринг моделирует физику и всегда знает текущую скорость.

| | Duration-based твин | Спринг |
|---|---|---|
| Состояние | Позиция вдоль фиксированной кривой | Текущее значение и текущая скорость |
| Длительность | Задана заранее | Нет: останавливается, когда система успокоится |
| Смена цели на полпути | Резкий рестарт или ручной пересчёт | Физика сохраняет скорость, скачка нет |

Duration-based анимация — это функция `t → progress`, где `t` — нормализованное время внутри **заранее заданной** длительности. У неё нет понятия "текущая скорость", только позиция вдоль фиксированной кривой.

Spring-анимация моделирует физическую систему масса-пружина-демпфер. Её состояние — это `(текущее значение, текущая скорость)`, а фиксированной длительности у неё нет вообще: она останавливается сама, когда система физически успокаивается.

Смена цели (`target`) на середине движения для спринга тривиальна. Физика пересчитывает новую траекторию, сохраняя текущую скорость, без скачка.

Для duration-based анимации аналогичная смена цели потребовала бы резкого рестарта с видимым скачком. Альтернатива — вручную пересчитать оставшееся время и текущую "скорость" по касательной кривой, что нетривиально и обычно не делается.

---

**Когда `requestIdleCallback` — неправильный инструмент, и почему?**

Для самой анимации.

У `requestIdleCallback` нет никаких гарантий по частоте и таймингам. Колбэк может быть отложен на неопределённое время, если главный поток постоянно занят, и он никак не синхронизирован с частотой обновления дисплея.

Это инструмент для фоновой, неотложной работы: батчинг аналитики, прогрев кэша, ленивая инициализация. То есть для того, что должно произойти "когда будет минутка", а не "точно к следующему кадру".

## Группа 5: Библиотеки и экосистема

**Когда стоит выбрать GSAP вместо нативного CSS/WAAPI? Что конкретно даёт `ScrollTrigger`, чего нет у нативных scroll-driven animations?**

GSAP (GreenSock Animation Platform) оправдан, когда задача требует timeline-оркестрации множества независимых элементов. Это значит точное позиционирование — метки, относительные офсеты типа `'-=0.2'` — или сложную scroll-хореографию.

Ключевое конкретное отличие `ScrollTrigger` — способность **закреплять** (`pin: true`) секцию во вьюпорте на время скролла. Так логическая анимация растягивается на несколько экранов реальной высоты страницы. А `scrub` привязывает прогресс к скорости скролла со сглаживанием.

Нативный `animation-timeline: scroll()`/`view()` даёт scroll-linked прогресс для одиночного элемента, но не умеет "приклеивать" элемент к вьюпорту. Именно поэтому сложные scroll-сторителлинг-сайты всё ещё требуют GSAP, а не только нативного CSS.

---

**Какую проблему решает `AnimatePresence` в Framer Motion, и почему эта проблема вообще существует?**

React размонтирует DOM-узел **синхронно** в момент, когда условие рендера перестаёт быть истинным (`{isOpen && <Modal />}` → `isOpen: false`). У любой CSS- или JS-анимации на этом узле физически нет времени доиграть, потому что узла уже нет в дереве.

`AnimatePresence` перехватывает момент, когда React "хочет" убрать дочерний элемент. Он удерживает элемент в DOM ещё некоторое время, проигрывает `exit`-анимацию и только затем реально удаляет узел.

Без этого механизма пришлось бы вручную заводить двухфазное состояние: `isOpen` плюс отложенный `isRendered`.

---

**Когда Lottie — правильный выбор, а когда избыточен?**

Правильный выбор — когда сложная векторная motion-графика спроектирована дизайнером-аниматором в After Effects. Это персонажная анимация и детализированные onboarding-иллюстрации, а результат нужно доставить в браузер 1-в-1. Ручная переработка в CSS или JS стоила бы недель и всё равно разошлась бы с оригиналом.

Избыточен — для обычных переходов интерфейса (кнопка, карточка, модалка), которые можно выразить через `transform`/`opacity` в пару строк CSS. Там Lottie добавляет вес JSON-файла и оверхед рендерера (`svg` или `canvas`). Плюс жёсткую зависимость от пайплайна bodymovin-экспорта при любом изменении дизайна.

## Группа 6: Диагностика производительности

**Сценарий отладки: маркетинговая страница подтормаживает при скролле на бюджетном Android-телефоне, но на десктопном Chrome всё гладко. Опишите ваш процесс диагностики.**

Порядок действий — шесть шагов, у каждого свой инструмент:

1. **Воспроизвести проблему в DevTools с включённым CPU/network throttling**, эмулируя более слабое железо. Не пытаться диагностировать "на глаз" на мощном десктопе.
2. **Записать сессию в Performance-панели и посмотреть flame chart главного потока.** Искать Long Tasks (больше 50 мс) и повторяющийся паттерн Layout→Paint→Composite на каждом кадре анимации. Такой паттерн — сигнал, что анимируется layout-свойство, а не `transform`/`opacity`.
3. **Проверить наличие "Forced reflow".** Если есть, кликнуть на предупреждение и получить stack trace до конкретной строки, где чередуются чтение и запись геометрии.
4. **Открыть Layers-панель.** Проверить, не раздуто ли число composited-слоёв: layer explosion от `will-change` на статичных элементах или от множественных `filter`. Оценить memory estimate для полноэкранных слоёв: на мобильном, где память общая для CPU и GPU, они нагружают устройство сильнее, чем на десктопе.
5. **Включить paint flashing.** Проверить, не перерисовывается ли лишняя область экрана при скролле из-за отсутствия изоляции слоя.
6. **Если проблема в самом scroll-хендлере**, проверить, стоит ли `{ passive: true }` и не читается ли геометрия синхронно внутри обработчика.

Именно такая последовательность конкретных инструментов отличает системную диагностику от предположений по коду.

---

**Как диагностировать layout thrashing в DevTools?**

Записать сессию в Performance-панели, воспроизводя взаимодействие. Затем искать блоки Layout, явно помеченные "Forced reflow" — фиолетовый блок со значком предупреждения. Клик по предупреждению разворачивает stack trace с указанием на конкретную строку кода.

Во flame chart признак — плотный повторяющийся паттерн мелких блоков Layout, идущих вплотную и коррелирующих с циклом в коде. Это визуальная сигнатура чередования чтения и записи, которое и вызывает layout thrashing (статья 01). Одиночный крупный блок Layout — другое дело: он нормален и ожидаем для одного легитимного изменения стилей.

---

**Что такое INP, и как анимационный код может на него влиять?**

INP (Interaction to Next Paint) — метрика Core Web Vitals. Она измеряет задержку между действием пользователя и моментом, когда браузер физически показывает следующий обновлённый кадр в ответ. Действие — это клик, тап или нажатие клавиши.

Допустим, rAF-колбэк или JS-driven анимация занимает главный поток дольше frame budget. Если это происходит именно в момент взаимодействия пользователя, ответный кадр откладывается. Этим кадром может быть визуальное "нажатие" кнопки, и задержка напрямую ухудшает INP.

Практическое следствие: плохо спланированная анимация — не только "эстетическая" проблема. Это измеримый фактор, влияющий на тот же отчёт Web Vitals, что и LCP (Largest Contentful Paint) и CLS (Cumulative Layout Shift). А значит, и на SEO (search engine optimization, поисковую оптимизацию).

## Группа 7: Доступность и продуктовые решения

**Как правильно реализовать поддержку `prefers-reduced-motion`? Означает ли это полное отключение анимации?**

`prefers-reduced-motion` — настройка операционной системы, которую включают по медицинской причине. Это вестибулярные расстройства, при которых крупноамплитудное движение вызывает головокружение и тошноту. Эстетического предпочтения здесь нет.

Базовая реализация — глобальный CSS `@media (prefers-reduced-motion: reduce)`, зануляющий длительности анимаций и переходов. Это рабочая страховочная сетка, но не лучшее решение везде.

Правильный паттерн — заменить **движение** на opacity cross-fade, сохранив сам факт перехода между состояниями. В CSS это переменные, переключаемые внутри media query, например `--enter-transform: translateY(20px)` → `none`. Анимация при этом не убирается целиком.

В JS та же логика идёт через `window.matchMedia('(prefers-reduced-motion: reduce)')`. Подписка на `change` обязательна: пользователь может переключить настройку прямо во время сессии. На уровне библиотек есть `MotionConfig reducedMotion="user"` в Framer Motion, который применяет это автоматически ко всем дочерним компонентам.

---

**Почему управление фокусом не должно быть привязано к завершению анимации?**

Потому что это создаёт реальный барьер доступности. Пользователь, работающий с клавиатуры или скринридером, вынужден ждать окончания декоративной анимации, прежде чем фокус попадёт на нужный элемент. Например, `await animation.finished` перед `element.focus()`. Задержка в 200-300 мс незаметна для зрячего пользователя без вестибулярных нарушений, но барьером быть не перестаёт.

Состояние приложения меняется в момент действия пользователя — открытие модалки, переход между шагами. Фокус должен переместиться синхронно с этим изменением состояния. Анимация проигрывается параллельно, визуально иллюстрируя переход, и не блокирует доступность для пользователей, которые эту анимацию не воспринимают тем же образом.
