# CSS Transitions и Keyframes

## Почему декларативный путь — это не "простой", а правильный путь по умолчанию

CSS-анимация предпочтительна, и не потому что её "проще писать". Она предпочтительна потому, что браузер получает всю информацию заранее: начальное и конечное значение, длительность и кривую. Это позволяет браузеру спланировать работу компоузитор-потока (см. [Rendering Pipeline и Frame Budget](./01-rendering-pipeline-and-frame-budget.md)) без постоянного диалога с главным потоком.

JS-анимация через `requestAnimationFrame` (статья 04) обязана каждый кадр заново вычислять значение в главном потоке. CSS-переход или keyframe-анимация на `transform`/`opacity` может идти полностью на компоузиторе, даже если главный поток занят.

Отсюда практическое правило: **если анимацию можно выразить через CSS — выражайте через CSS**. Именно поэтому CSS transitions и keyframes — не "базовый, детский" уровень темы, а рабочий инструмент senior-разработчика для подавляющего большинства реальных интерфейсных анимаций. Переходите на JS только тогда, когда нужна логика, которую CSS выразить не может:

- динамическое целевое значение;
- зависимость от физики или скорости;
- прерывание на полпути с сохранением текущей скорости.

## Как `transition` работает изнутри

`transition` — это не "плавное появление", а точный контракт. Браузер отслеживает **computed value** указанного свойства. Когда значение меняется, браузер не подменяет его мгновенно: он проигрывает последовательность промежуточных значений между старым и новым за указанное время.

```css
.button {
  transition-property: background-color, transform;
  transition-duration: 0.2s, 0.3s;
  transition-timing-function: ease-out, cubic-bezier(0.34, 1.56, 0.64, 1);
  transition-delay: 0s, 0.05s;
}
/* Шорхенд с запятой = список независимых переходов,
   каждый со своими параметрами по позиции в списке */
```

Не все CSS-свойства умеют интерполироваться. Браузер группирует их по типу интерполяции:

| Группа интерполяции | Свойства |
|---|---|
| Числовые (интерполируются как число) | `width`, `opacity`, `font-size`, `line-height` |
| Цвет (интерполируется по каждому каналу) | `color`, `background-color`, `border-color` |
| Transform (интерполяция по компонентам матрицы, **не** как строка) | `transform` |
| Список значений той же длины | `box-shadow`, если совпадает число теней; `transform` с одинаковым списком функций |
| Дискретные (не интерполируются — скачок на 50% времени перехода) | `display`, `visibility` (частично), `grid-template-columns` со string-значениями, большинство keyword-свойств |

Ключевая деталь про дискретные свойства: `transition: display 0.3s` технически не ошибка. Браузер просто не умеет плавно интерполировать `display: block` в `display: none`. Поэтому значение переключается мгновенно **в середине** заданной длительности (по умолчанию), а не в начале и не в конце.

На практике это выглядит как "ничего не анимировалось". Именно это порождает баг-репорты "transition не работает". На самом деле он работает, просто на несмешиваемом свойстве.

Ещё один нюанс интервью-уровня: `transform` интерполируется **не как текстовая строка**, а через разложение матрицы преобразования на компоненты (translate/scale/rotate/skew) и раздельную интерполяцию каждого. Поэтому `transform: translateX(0) rotate(0deg)` → `transform: translateX(100px) rotate(45deg)` даёт плавное движение по дуге компонентов, а не резкий пересчёт.

## `transition: all` — не сокращение, а источник продакшен-багов

`transition: all 0.3s ease` выглядит как безобидный дефолт "анимируем всё, что поменяется". На практике это — открытый контракт: **любое** будущее изменение любого CSS-свойства на этом элементе теперь анимируется, включая те, что вы не планировали.

```css
/* ❌ transition: all — бомба замедленного действия */
.card {
  transition: all 0.3s ease;
}

/* Полгода спустя другой разработчик добавляет adaptive-логику: */
.card.is-pinned {
  position: sticky;
  top: 0;
}
/* Результат: при добавлении/снятии класса .is-pinned карточка
   визуально "проезжает" в новую позицию за 0.3s, потому что
   transition: all подхватил изменение top — хотя никто
   не собирался это анимировать. Баг-репорт: "карточка дёргается
   при скролле", найти причину — 40 минут в DevTools. */
```

```css
/* ✅ Явный список — анимируется только то, что задумано,
   и это самодокументирующийся код: читатель сразу видит,
   что здесь может измениться визуально плавно */
.card {
  transition: transform 0.3s ease, box-shadow 0.3s ease;
}
```

Есть и второй, менее очевидный довод против `all`. Браузер обязан **следить за всеми animatable-свойствами элемента**, чтобы понять, нужно ли запускать переход. Это небольшой, но постоянный оверхед, и явный список полностью его снимает.

Для production-кода `transition: all` допустим разве что в прототипах. Ещё он допустим там, где элемент гарантированно не получит новых стилей — что на практике почти никогда не гарантировано.

## `@keyframes` и `animation-*`: то, что путают на собеседованиях

`transition` умеет только "из текущего значения в новое". Это один переход по одной последовательности состояний. А `@keyframes` даёт произвольное количество промежуточных точек и не требует триггера через изменение состояния. Анимация может начаться сама, при появлении элемента.

```css
@keyframes pulse {
  0%   { transform: scale(1);    opacity: 1;   }
  50%  { transform: scale(1.08); opacity: 0.85; }
  100% { transform: scale(1);    opacity: 1;   }
}

.notification-dot {
  animation-name: pulse;
  animation-duration: 1.6s;
  animation-timing-function: ease-in-out;
  animation-iteration-count: infinite;
  animation-fill-mode: both;
}
```

Свойства, которые чаще всего путают или забывают на интервью:

**`animation-fill-mode`** — что происходит со стилями элемента **до** начала и **после** окончания анимации:

| Значение | Что применяется |
|---|---|
| `none` (по умолчанию) | До начала и после конца применяются обычные CSS-правила элемента, а не значения из keyframes |
| `forwards` | После окончания анимации остаются значения последнего кадра (100%) |
| `backwards` | До начала анимации, включая `animation-delay`, применяются значения первого кадра (0%) |
| `both` | Комбинация `forwards` и `backwards` |

Классический баг выглядит так. Элемент анимируется через `@keyframes` из `opacity: 0` в `opacity: 1`. Анимация корректно проигрывается один раз (`animation-iteration-count: 1`), а потом **элемент внезапно исчезает**.

Причина в том, что `animation-fill-mode` по умолчанию `none`. После конца анимации браузер откатывает элемент к его обычному CSS-состоянию, где `opacity` не задан или равен исходному значению до анимации. Фикс — `animation-fill-mode: forwards`.

**`animation-direction`** — часто забывают про `alternate`:

```css
.loader-bar {
  animation: slide 1s ease-in-out infinite alternate;
  /* alternate: чётные итерации — вперёд, нечётные — в обратном
     порядке (100% → 0%), без "телепорта" в начало на каждом цикле */
}
```

```txt
normal            — всегда 0% → 100%
reverse           — всегда 100% → 0%
alternate         — 0%→100%, потом 100%→0%, чередуя
alternate-reverse — 100%→0%, потом 0%→100%, чередуя
```

**`animation-play-state`** — единственный способ поставить CSS-анимацию на паузу без JS-манипуляций с классами:

```css
.spinner { animation: spin 1s linear infinite; }
.spinner:hover { animation-play-state: paused; }
```

**Несколько анимаций через запятую** — как и с transition, краткая запись с запятыми задаёт независимые анимации:

```css
.card {
  animation: fadeIn 0.3s ease-out forwards,
             pulse 2s ease-in-out 0.3s infinite;
  /* fadeIn проигрывается один раз сразу, pulse стартует
     через 0.3s (после fadeIn) и повторяется бесконечно */
}
```

## Timing functions: не просто "какая кривая красивее"

Timing function — это функция `t → progress`. Здесь `t` — нормализованное время от 0 до 1, то есть от 0% до 100% длительности. А `progress` — нормализованный прогресс интерполируемого значения, тоже обычно от 0 до 1. Не обязательно, впрочем: про овершут — ниже.

### Ключевые слова и что они значат физически

```txt
linear      — равномерная скорость, без ускорения/замедления.
              Ощущается "механически", подходит для непрерывных
              процессов (progress bar, крутящийся спиннер),
              но плохо подходит для интерфейсных переходов —
              выглядит неестественно резко в начале и в конце.
ease        — (по умолчанию для transition) плавный старт,
              ускорение, плавное замедление к концу.
ease-in     — медленный старт, резкое ускорение к концу.
              Подходит для элементов, уходящих со сцены.
ease-out    — резкий старт, плавное замедление к концу.
              Подходит для элементов, появляющихся на сцене —
              глаз воспринимает быстрый отклик как "отзывчивость".
ease-in-out — медленный старт и медленный конец, ускорение
              в середине. Подходит для переходов между двумя
              стабильными состояниями (открыт/закрыт).
```

### `cubic-bezier(x1, y1, x2, y2)` — как реально читать кривую

Все ключевые слова выше — это просто предустановленные `cubic-bezier()`. Кривая Безье здесь строится по двум контрольным точкам P1(x1, y1) и P2(x2, y2), при фиксированных P0(0,0) и P3(1,1):

```txt
ease         = cubic-bezier(0.25, 0.1, 0.25, 1.0)
ease-in      = cubic-bezier(0.42, 0.0, 1.0, 1.0)
ease-out     = cubic-bezier(0.0, 0.0, 0.58, 1.0)
ease-in-out  = cubic-bezier(0.42, 0.0, 0.58, 1.0)
linear       = cubic-bezier(0.0, 0.0, 1.0, 1.0)
               (эквивалентно ключевому слову linear)
```

Практическое чтение: `x` контрольных точек обязан лежать в диапазоне [0, 1] (это ось времени — она не может идти "назад"), а вот `y` — **может выходить за пределы [0, 1]**. Это и даёт эффект overshoot ("перелёт") — значение временно проскакивает дальше целевого и возвращается, создавая ощущение упругости без единой JS-строки:

```css
/* Материал-дизайновский "fast-out, slow-in" для входящих элементов */
.modal {
  transition: transform 0.3s cubic-bezier(0.05, 0.7, 0.1, 1);
}

/* "Пружинистое" появление за счёт y > 1 у второй контрольной точки */
.toast {
  transition: transform 0.4s cubic-bezier(0.34, 1.56, 0.64, 1);
  /* y2 = 1.56 → элемент проскакивает целевую позицию и
     возвращается — тот самый "bounce", который многие
     реализуют через JS-спринг, хотя это чистый CSS */
}
```

Проектировать кривую руками — не то, что делают в уме. Используют визуальный редактор. Он встроен в DevTools у Chrome и Firefox: достаточно кликнуть на `cubic-bezier(...)` в стилях. Есть и сайты вроде cubic-bezier.com. P1 и P2 подбирают визуально и копируют итоговые числа.

### `linear()` — piecewise-линейные кривые для bounce/spring в чистом CSS

`cubic-bezier()` физически не может описать **множественные** осцилляции (несколько "отскоков", как у настоящей пружины) — это одна гладкая кривая с максимум одним overshoot. Современный CSS-timing-function `linear()` решает это: вы задаёте список точек `(значение, позиция%)`, и браузер линейно интерполирует между ними — по сути, ручная кусочно-линейная аппроксимация любой кривой, включая многократные bounce-эффекты:

```css
.bouncy-ball {
  /* Явно заданные точки аппроксимируют затухающий отскок:
     проскочили выше 1, вернулись ниже, снова чуть выше,
     затухая к финальному значению 1 */
  transition: transform 0.8s linear(
    0, 0.5 15%, 0.9 30%, 1.1 45%, 0.98 60%, 1.02 75%, 1 100%
  );
}
```

Это тот же результат, которого раньше можно было добиться только JS-спрингом (статья 04) или библиотекой. Теперь он достижим декларативно, без единой строки JS. Цена — кривую нужно откуда-то взять. Либо генератором (easing-генераторы для `linear()` уже есть в вебе), либо посчитать самому.

### `steps(n, jump-term)` — не для easing, а для спрайтовой анимации

`steps()` — принципиально другой тип timing function: вместо непрерывной интерполяции значение **скачками** проходит `n` дискретных положений. Классическое применение — покадровая анимация по спрайт-листу через `background-position`:

```css
/* Спрайт-лист из 8 кадров ходьбы персонажа, каждый кадр 64px шириной */
.walking-sprite {
  width: 64px;
  height: 64px;
  background-image: url('walk-sprite.png'); /* 512px = 8 × 64px */
  animation: walk-cycle 0.8s steps(8, jump-end) infinite;
}

@keyframes walk-cycle {
  from { background-position: 0 0; }
  to   { background-position: -512px 0; }
}
/* steps(8, jump-end): диапазон от 0 до -512px делится на 8 равных
   скачков — background-position мгновенно "телепортируется"
   на каждую следующую позицию кадра, без промежуточного
   смаза между кадрами спрайта */
```

`jump-end` (по умолчанию) и `jump-start` определяют, происходит ли скачок в начале или в конце каждого шага-интервала. Обычно эта деталь не критична для спрайтов. Она важна там, где нужна точная синхронизация со звуком и событиями.

## `@starting-style` — переход из "элемент ещё не существовал"

Классическая проблема: у `transition` нет "состояния **до** появления". Допустим, элемент вставляется в DOM с `display: none → block` или монтируется впервые. DOM — это document object model, дерево объектов страницы в браузере. Браузеру не от чего интерполировать: вычисленного "предыдущего кадра" со старым значением до этого момента попросту не было.

Раньше это решали хаком: монтировать элемент с начальными стилями, затем в следующем тике менять класс на финальный, через `requestAnimationFrame` или `setTimeout(0)`. Это заставляет браузер зафиксировать первый кадр, прежде чем начинать переход.

`@starting-style` решает это декларативно: вы явно описываете, какими были бы стили элемента "за кадр до" его первого рендера или до перехода из `display: none`:

```css
.dialog {
  display: none;
  opacity: 0;
  transform: scale(0.9);
  transition: opacity 0.25s, transform 0.25s, display 0.25s allow-discrete;
}

.dialog[open] {
  display: block;
  opacity: 1;
  transform: scale(1);

  @starting-style {
    /* "Состояние на входе" — то, откуда стартует переход,
       когда элемент только что получил display: block */
    opacity: 0;
    transform: scale(0.9);
  }
}
```

Обратите внимание на `display: 0.25s allow-discrete` в `transition-property`: `display` — дискретное свойство (см. таблицу выше), и по умолчанию его нельзя анимировать.

Значение `transition-behavior: allow-discrete` (здесь — в краткой записи) явно разрешает дискретным свойствам участвовать в переходе. Браузер переключает `display: none → block` **в начале** перехода, чтобы элемент был видим для анимации остальных свойств. По умолчанию это происходило бы в середине.

Это убирает последнюю причину, по которой `display: none`-элементы требовали JS-хаков для входной анимации. Модалки, тултипы и дропдауны теперь анимируются на чистом CSS от и до, включая момент появления в DOM.

## Анимация `auto` — `interpolate-size` и `calc-size()`

Ещё одна классическая боль: CSS исторически не умел анимировать `height: auto` (или `width: auto`). Слово `auto` — не число, а инструкция "вычисли по контенту", и `transition` не знает целевого числового значения заранее. Годами это решали хаками:

| Хак | Проблема |
|---|---|
| `max-height` с заведомо большим значением | Ломается, если реальная высота больше. Анимация "проскакивает" пустое пространство, если высота меньше |
| CSS Grid с `grid-template-rows: 0fr → 1fr` | Работает, но требует обёртки в grid-контейнер и не всегда подходит |

Современное решение — свойство `interpolate-size` и функция `calc-size()`:

```css
:root {
  interpolate-size: allow-keywords;
  /* Явно разрешаем интерполяцию keyword-значений типа auto —
     обычно ставится глобально один раз */
}

.accordion-panel {
  height: 0;
  overflow: hidden;
  transition: height 0.3s ease;
}

.accordion-panel.is-open {
  height: auto;
  /* Раньше — не анимировалось. С interpolate-size: allow-keywords
     браузер сам вычисляет целевое числовое значение auto
     (через внутренний эквивалент calc-size(auto, size)) и
     интерполирует к нему как к обычному числу */
}
```

Поддержка этой связки в браузерах на момент написания — свежая. Проверяйте caniuse перед использованием в продакшене без фолбэка. Для проектов, которым нужна широкая поддержка прямо сейчас, grid-трюк с `0fr`/`1fr` остаётся рабочим и надёжным обходным путём:

```css
/* Проверенный кросс-браузерный обходной путь до широкой поддержки interpolate-size */
.accordion-wrapper {
  display: grid;
  grid-template-rows: 0fr;
  transition: grid-template-rows 0.3s ease;
}
.accordion-wrapper.is-open {
  grid-template-rows: 1fr;
}
.accordion-content {
  overflow: hidden; /* обязательно — иначе контент "вылезает" во время анимации fr-долей */
}
```

## CSS-переменные, которые "не анимируются", и `@property`

Обычная custom property (`--angle: 0deg`) для браузера — это **непрозрачная строка токенов**, а не типизированное значение. Браузер не знает, что `--angle` — это угол, а не произвольный текст. Поэтому он не умеет интерполировать её от `0deg` к `360deg`. Значение либо мгновенно скачет, как дискретное свойство, либо переход вовсе не запускается.

```css
/* ❌ Не анимируется плавно — браузер не знает тип значения --angle */
.gradient-box {
  --angle: 0deg;
  background: conic-gradient(from var(--angle), red, blue, red);
  transition: --angle 1s linear;
}
```

`@property` регистрирует custom property с явным типом (`syntax`), поведением наследования и начальным значением — после этого браузер знает, **что** интерполировать и **как**:

```css
@property --angle {
  syntax: '<angle>';
  inherits: false;
  initial-value: 0deg;
}

.gradient-box {
  --angle: 0deg;
  background: conic-gradient(from var(--angle), red, blue, red);
  transition: --angle 1s linear;
}

.gradient-box:hover {
  --angle: 360deg; /* теперь плавно вращается — CSS-переменная анимируется как <angle> */
}
```

Это открывает целый класс анимаций, которые раньше требовали JS:

- вращающиеся градиенты;
- числовые счётчики через `counter()` в связке с анимируемым `<number>`;
- плавные переходы между произвольными числовыми параметрами, влияющими сразу на несколько производных CSS-свойств через `calc()`.

`@property` также можно объявлять через JS API — `CSS.registerProperty()` — с идентичным эффектом. Эта форма нужна, если регистрация должна происходить динамически.

## Типичные ошибки на интервью

- **"`transition: all` — это просто краткая запись, ничего плохого"** — не видеть в этом реального источника продакшен-багов. Любое будущее изменение стилей элемента начинает неожиданно анимироваться. В том числе изменения, добавленные другим разработчиком месяцы спустя, который про этот `transition` не знает.

- **Путать `transition` и `animation`** — не суметь объяснить разницу по существу. Переход `transition` требует триггера — изменения состояния или класса — и описывает переход между двумя значениями. А `animation` с `@keyframes` не требует триггера, может стартовать сама и поддерживает произвольное число промежуточных точек и повторов.

- **Забыть про `animation-fill-mode: forwards`** — классический баг "анимация проигралась, а потом элемент вернулся в исходное состояние". Без `forwards` браузер после конца анимации откатывает элемент к обычным CSS-правилам, а не оставляет значения последнего кадра.

- **Думать, что `cubic-bezier()` не может дать эффект "пружины"** — не знать, что `y`-координата контрольных точек может выходить за пределы [0, 1]. Это и создаёт overshoot и bounce чистым CSS, без JS-спринга.

- **Не знать про `steps()`** — путать его с easing-кривой, хотя это принципиально другой механизм: дискретные скачки, а не непрерывная интерполяция, нужный конкретно для спрайтовой/покадровой анимации.

- **Не знать, что CSS исторически не умел анимировать `height: auto`** — и не знать ни одного из решений. Проверенный вариант — grid-трюк с `0fr`/`1fr`, современный — `interpolate-size` и `calc-size()`. Вопрос "как анимировать аккордеон с динамической высотой" почти гарантированно всплывает на практических интервью.

- **Не знать про `@property`** — думать, что CSS custom properties "просто не умеют" анимироваться в принципе. Дело в отсутствии типа у значения, и `@property` эту типизацию как раз добавляет.
