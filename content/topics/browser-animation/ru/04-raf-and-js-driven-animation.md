# requestAnimationFrame и JS-driven анимация

## Когда декларативных инструментов уже не хватает

CSS-переходы, keyframes и WAAPI (Web Animations API, статьи 02-03) покрывают подавляющее большинство интерфейсных анимаций. Они и должны оставаться выбором по умолчанию. Но есть класс задач, которые декларативно не выразить в принципе: в них нет фиксированной точки "откуда" и "куда" на момент старта:

```txt
- Непрерывная симуляция: физика (гравитация, столкновения,
  инерция курсора)
- Значение зависит от нескольких источников одновременно и в
  реальном времени: позиция курсора + скорость скролла + время.
  Их нельзя заранее описать как keyframes, потому что
  комбинация меняется каждый кадр
- Анимация, которую нужно прервать на полпути и продолжить
  с текущей скорости в новом направлении, а не доиграть
  по заранее заданной кривой
- Взаимодействие в реальном времени: drag с инерцией после
  отпускания, где итоговая траектория зависит от скорости
  жеста пользователя в момент отпускания, известной только
  в рантайме
```

Для этих случаев нужен полный контроль над тем, что происходит каждый кадр. Это и есть `requestAnimationFrame` (rAF).

Одну границу стоит обозначить сразу: rAF-анимация — это работа главного потока, см. [Rendering Pipeline и Frame Budget](./01-rendering-pipeline-and-frame-budget.md). В отличие от CSS и WAAPI на компоузиторе она никогда не "бесплатна". При перегруженном главном потоке она страдает первой. Выбор в её пользу — осознанный компромисс за контроль, а не апгрейд "более мощного" инструмента.

## Механика `requestAnimationFrame`: когда именно срабатывает колбэк

```javascript
function tick(timestamp) {
  // timestamp — DOMHighResTimeStamp, то же самое время,
  // что вернул бы performance.now() на момент начала кадра
  console.log(timestamp);
  requestAnimationFrame(tick); // планируем следующий вызов
}
requestAnimationFrame(tick);
```

Колбэк `rAF` вызывается браузером **перед** стадией Style/Layout/Paint текущего кадра, синхронизированно с частотой обновления дисплея (vsync). То есть ровно один раз за кадр, а не "как можно чаще".

Это принципиальное отличие от `setInterval(fn, 16)`, у которого нет никакой привязки к реальному циклу рендеринга:

- Он может сработать в середине уже идущей стадии рендеринга. Тогда изменение стиля попадёт только в **следующий** кадр, а не в текущий — впустую потраченный вызов.
- Он может накапливать отставание.
- Он не согласован с частотой дисплея, а она везде разная: 60 Гц, 120 Гц, 144 Гц.

Ключевая практическая деталь: **в фоновых вкладках `requestAnimationFrame` останавливается или резко замедляется браузером.** Обычно частота падает до одного раза в секунду или вызовы прекращаются совсем. Это экономит процессорное время и батарею для анимаций, которые пользователь физически не видит.

`setInterval`, в отличие от rAF, продолжает тикать в фоне. Современные браузеры троттлят его тоже, но менее агрессивно и менее предсказуемо. Это ещё одна причина использовать для анимации именно rAF, а не таймеры: браузер сам корректно ставит анимацию на паузу там, где пользователь всё равно ничего не увидит.

```javascript
const id = requestAnimationFrame(tick);
cancelAnimationFrame(id); // остановить запланированный вызов — обязательно
                          // делать при размонтировании компонента/удалении
                          // элемента, иначе колбэк продолжит выполняться
                          // и будет работать с несуществующим DOM-узлом
```

## Канонический rAF-цикл с delta time — и почему без него анимация ломается на 120 Гц

Самая частая ошибка новичков в ручной JS-анимации — двигать значение на фиксированный шаг **за кадр**, а не **за единицу времени**:

```javascript
// ❌ Скорость зависит от частоты обновления дисплея
let x = 0;
function tick() {
  x += 2; // "2 пикселя за кадр"
  element.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
// На 60 Гц-экране: 2px × 60 кадров/сек = 120px/сек
// На 120 Гц-экране: 2px × 120 кадров/сек = 240px/сек
// Один и тот же код движется вдвое быстрее на более
// частотном дисплее — баг, который сложно поймать локально,
// если у разработчика обычный 60 Гц-монитор
```

Фикс — считать **delta time**, то есть время, прошедшее с прошлого кадра. Шаг движения масштабируется на него, а скорость выражается в единицах **за секунду**, а не **за кадр**:

```javascript
// ✅ Скорость не зависит от частоты обновления дисплея
let x = 0;
const speedPerSecond = 120; // px/сек — одна и та же скорость на любом дисплее

let previousTimestamp;
function tick(timestamp) {
  if (previousTimestamp === undefined) previousTimestamp = timestamp;
  const deltaMs = timestamp - previousTimestamp;
  previousTimestamp = timestamp;

  x += speedPerSecond * (deltaMs / 1000);
  element.style.transform = `translateX(${x}px)`;

  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
// На 60 Гц: 60 кадров × 2px = 120px/сек. На 120 Гц: 120 кадров × 1px = 120px/сек.
// Разное количество более мелких шагов, одинаковая итоговая скорость.
```

Это не теоретическая деталь ради полноты. Это конкретный источник багрепортов вида "у меня на маке всё плавно". А у тестировщика на игровом ноуте с 144 Гц та же анимация летит в 2.4 раза быстрее и заканчивается раньше, чем должна.

## Интерполяция и нормализованный прогресс

Практически любая time-based JS-анимация сводится к одной и той же формуле. Нормализовать прошедшее время в диапазон `[0, 1]`. Применить easing-функцию к этому нормализованному `t`. Интерполировать между начальным и конечным значением по результату:

```javascript
function animateValue(from, to, duration, easingFn, onUpdate, onComplete) {
  const startTime = performance.now();

  function tick(now) {
    const elapsed = now - startTime;
    const t = Math.min(elapsed / duration, 1); // нормализованный прогресс [0, 1]
    const easedT = easingFn(t);                 // применяем кривую
    const value = from + (to - from) * easedT;   // линейная интерполяция (lerp)

    onUpdate(value);

    if (t < 1) requestAnimationFrame(tick);
    else onComplete?.();
  }

  requestAnimationFrame(tick);
}

animateValue(0, 300, 400, easeOutCubic, (v) => {
  element.style.transform = `translateX(${v}px)`;
});
```

`from + (to - from) * t` — это и есть `lerp` (linear interpolation). Базовая операция, на которой строится вся time-based анимация. CSS-движок внутри делает концептуально то же самое, просто на компоузиторе и без вашего JS-кода на каждый кадр.

## Easing как чистая функция от `t`

Easing-функция — это математически просто `f(t): [0,1] → ℝ`. Обычно она отображает в диапазон `[0,1]`, но не обязательно: овершут допустим, ровно как и в `cubic-bezier()` из статьи 02. В отличие от `cubic-bezier()`, JS-easing не ограничен кубической кривой Безье. Реализовать можно что угодно: bounce, elastic, ступенчатые эффекты.

```javascript
const easeOutCubic  = (t) => 1 - Math.pow(1 - t, 3);
const easeInOutQuad = (t) => (t < 0.5 ? 2 * t * t : 1 - Math.pow(-2 * t + 2, 2) / 2);

const easeOutBounce = (t) => {
  const n1 = 7.5625, d1 = 2.75;
  if (t < 1 / d1) return n1 * t * t;
  if (t < 2 / d1) return n1 * (t -= 1.5 / d1) * t + 0.75;
  if (t < 2.5 / d1) return n1 * (t -= 2.25 / d1) * t + 0.9375;
  return n1 * (t -= 2.625 / d1) * t + 0.984375;
};
```

Практический вывод для собеседования: `cubic-bezier()` и JS-easing-функция решают одну и ту же математическую задачу, `t → progress`. Различаются они только уровнем. Декларативный уровень — CSS: он ограничен формой кривой Безье, а сложные случаи закрывает `linear()` (статья 02). Императивный уровень — JS: произвольная формула, но всегда ценой работы на главном потоке.

## Springs и damping: физическая альтернатива длительности

У всех примеров выше есть общая черта: заранее заданная **длительность**. Это хорошо подходит для переходов "открыт → закрыт" с известными конечными точками. Но плохо подходит для интерактивной анимации. Там движение начинается с уже ненулевой скорости — например, пользователь бросил элемент после drag. Или его нужно прервать на полпути новым таргетом.

Spring-анимация моделирует не "прогресс по времени", а физическую систему масса-пружина-демпфер. Пружина тянет текущее значение к цели с силой, пропорциональной расстоянию. Демпфер гасит эту силу пропорционально скорости. У такой системы **нет фиксированной длительности**: она останавливается сама, когда скорость и расстояние до цели становятся пренебрежимо малыми:

```javascript
function springStep(
  current, velocity, target,
  { stiffness = 170, damping = 26, mass = 1 },
  dt,
) {
  const springForce = -stiffness * (current - target); // тянет к цели
  const dampingForce = -damping * velocity;             // гасит колебания
  const acceleration = (springForce + dampingForce) / mass;

  velocity += acceleration * dt;
  current += velocity * dt;

  return { current, velocity };
}

function animateSpring(from, to, onUpdate, config = {}) {
  let current = from;
  let velocity = 0;
  let previousTime;

  function tick(now) {
    if (previousTime === undefined) previousTime = now;
    const dt = Math.min((now - previousTime) / 1000, 1 / 30); // клампим dt на случай лагов
    previousTime = now;

    ({ current, velocity } = springStep(current, velocity, to, config, dt));
    onUpdate(current);

    // Останавливаемся, когда система практически успокоилась
    if (Math.abs(to - current) > 0.01 || Math.abs(velocity) > 0.01) {
      requestAnimationFrame(tick);
    }
  }
  requestAnimationFrame(tick);
}
```

Почему это "ощущается естественнее" — не эстетическая вкусовщина, а прямое следствие модели. В реальном мире объекты не движутся по заранее расписанному временному графику: они реагируют на силы здесь и сейчас.

И именно поэтому **spring можно прервать на полпути, а duration-based анимацию — нет**. Состояние спринга — это `(текущее значение, текущая скорость)`, а не `(t внутри фиксированной длительности)`. Сменить `target` на середине движения тривиально: физика сама пересчитает новую траекторию с сохранением текущей скорости, без видимого "скачка":

```javascript
// Пользователь двигает мышью — таргет меняется каждый кадр,
// а спринг продолжает движение плавно, без рестарта анимации
let springTarget = 0;
document.addEventListener('mousemove', (e) => { springTarget = e.clientX; });
// animateSpring(...) читает springTarget на каждом шаге вместо фиксированного to
```

Это ключевая причина, по которой современные интерфейсные тулкиты (iOS, Framer Motion, react-spring, Motion.dev) используют spring как дефолт для интерактивных элементов, которые можно прервать. Для некликабельных, "проигрывающихся один раз" переходов дефолт другой: duration плюс easing.

## Lerp-сглаживание для курсора и параллакса — и скрытая ловушка frame-rate

Частый паттерн — "плавное следование" за целью. Два примера: кастомный курсор, который догоняет реальный указатель мыши с задержкой, или параллакс-слой, сглаживающий резкие скачки скролла:

```javascript
// ❌ Наивный lerp — коэффициент "0.1" даёт разную скорость
// сходимости на разных частотах дисплея
let current = 0;
function tick() {
  current += (target - current) * 0.1; // "подтягиваем" на 10% расстояния за кадр
  cursor.style.transform = `translateX(${current}px)`;
  requestAnimationFrame(tick);
}
// На 120 Гц current "подтягивается" в 2 раза чаще за секунду,
// чем на 60 Гц → курсор физически догоняет цель заметно быстрее
```

Тот же класс проблемы, что и с "px += 2 за кадр" выше, только более скрытый. Код выглядит "уже время-независимым". Но коэффициент затухания `0.1` неявно завязан на частоту вызова. Правильная формула — экспоненциальное затухание, скорректированное на реальный `dt`:

```javascript
// ✅ Сходимость не зависит от частоты кадров
let current = 0;
let previousTime;
// время (сек), за которое расстояние до цели сокращается вдвое
const smoothingHalfLife = 0.08;

function tick(now) {
  if (previousTime === undefined) previousTime = now;
  const dt = (now - previousTime) / 1000;
  previousTime = now;

  const decay = 1 - Math.pow(2, -dt / smoothingHalfLife);
  current += (target - current) * decay;

  cursor.style.transform = `translateX(${current}px)`;
  requestAnimationFrame(tick);
}
```

Эта деталь редко всплывает в туториалах. Но именно её отсутствие — причина жалоб "у нас курсор-блоб на демо-мониторе 60 Гц ощущается иначе, чем на MacBook с ProMotion 120 Гц". Код при этом формально одинаковый.

## FLIP: превращаем дорогую layout-анимацию в дешёвую transform-анимацию

Классическая проблема: элементы списка переупорядочиваются — сортировка, drag-and-drop, фильтрация. Их положение в DOM (document object model, дерево объектов страницы в браузере) меняется мгновенно.

Единственный способ анимировать это "в лоб" — анимировать `top`, `left`, `grid-row` и подобные свойства. Они запускают Layout на каждый кадр (статья 01), поэтому подход физически не масштабируется на списки из полусотни элементов без заметного джанка.

**FLIP** (First → Last → Invert → Play) — техника, которая обходит эту проблему целиком, сводя анимацию исключительно к `transform`:

```txt
First  — до изменения DOM: измерить текущую позицию элемента
          (getBoundingClientRect())
Last   — применить изменение DOM, то есть реальный reorder
          или layout-сдвиг. Браузер мгновенно кладёт элемент
          в новую позицию, без анимации. Измерить эту новую
          позицию
Invert — вычислить разницу (delta) между First и Last, затем
          сразу применить к элементу transform, компенсирующий
          эту разницу. Визуально элемент как будто остался
          на старом месте, хотя в layout он уже в новом
Play   — включить transition на transform и обнулить
          компенсирующий transform. Элемент плавно
          "доезжает" от старой визуальной позиции до
          настоящей новой, и всё это — чистый
          compositor-transform, без единого reflow за кадр
```

Пошаговая реализация для переупорядочиваемого списка:

```javascript
function flipReorder(container, reorderFn) {
  const items = [...container.children];

  // FIRST — снимаем позиции до изменения DOM
  const firstRects = new Map(items.map((el) => [el, el.getBoundingClientRect()]));

  // (реальное изменение DOM — например, пересортировка по данным)
  reorderFn();

  // LAST — снимаем позиции после изменения DOM
  items.forEach((el) => {
    const first = firstRects.get(el);
    const last = el.getBoundingClientRect();

    const deltaX = first.left - last.left;
    const deltaY = first.top - last.top;

    if (deltaX === 0 && deltaY === 0) return; // элемент не сдвинулся — пропускаем

    // INVERT — компенсируем разницу через transform, без transition
    el.style.transition = 'none';
    el.style.transform = `translate(${deltaX}px, ${deltaY}px)`;

    // Форсируем layout один раз, чтобы браузер зафиксировал
    // инвертированное состояние перед тем, как мы включим transition
    el.getBoundingClientRect();

    // PLAY — включаем transition и убираем компенсацию
    el.style.transition = 'transform 0.3s ease';
    el.style.transform = '';
  });
}
```

Это в точности тот механизм, который лежит под капотом `react-flip-toolkit` и layout-анимаций Framer Motion (`layout` prop, статья 05). Они автоматизируют именно эти четыре шага. Разработчик больше не ведёт вручную учёт `getBoundingClientRect()` до и после и не синхронизирует его с ре-рендером фреймворка.

Понимание FLIP по шагам отличает два ответа. Первый — "я использую библиотеку с layout-анимациями". Второй — "я понимаю, **почему** они вообще работают и почему это не layout-анимация в буквальном смысле".

## `requestIdleCallback`: не для анимации, а для того, что не должно ей мешать

`requestIdleCallback` (rIC) планирует выполнение колбэка в свободное время браузера между кадрами. То есть тогда, когда до следующего кадра ещё есть запас, а главный поток не занят ничем срочным:

```javascript
function drainQueue(deadline) {
  while (deadline.timeRemaining() > 0 && tasksQueue.length > 0) {
    processTask(tasksQueue.shift());
  }
  // именованная функция: у стрелочной нет `arguments`, а
  // `arguments.callee` запрещён в strict mode и в модулях
  if (tasksQueue.length > 0) requestIdleCallback(drainQueue);
}

requestIdleCallback(drainQueue);
```

Ключевая ошибка — пытаться использовать `rIC` для анимации. У него **нет гарантии частоты и таймингов**: колбэк может быть отложен на неопределённое время, если главный поток постоянно занят. И он никак не синхронизирован с частотой обновления дисплея.

`rIC` — инструмент для фоновой, неотложной работы: батчинг аналитики, прогрев кэша, предзагрузка данных, ленивая инициализация. Всё это должно происходить "когда будет минутка", а не "точно в следующем кадре".

### Когда анимацию стоит вообще не запускать

Часть профессиональной работы с JS-анимацией — не запускать её там, где она не нужна:

```javascript
// Ставим rAF-цикл на паузу, когда элемент вне вьюпорта —
// нет смысла тратить процессорное время и батарею на анимацию,
// которую никто не видит
const observer = new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting) startAnimationLoop();
  else stopAnimationLoop();
});
observer.observe(element);
```

Это тот же принцип, что стоит за паузой rAF в фоновых вкладках, только применённый вручную к отдельным элементам на самой странице. Медиазапрос `prefers-reduced-motion` — ещё одна причина не запускать анимацию или заменить её на менее интенсивную, и статья 07 разбирает его подробно.

- [Диагностика производительности и охота за джанком](./06-performance-debugging-and-jank-hunting.md) — как увидеть в DevTools, что именно rAF-колбэк не укладывается в frame budget.

## Типичные ошибки на интервью

- **Двигать значение на фиксированный шаг за кадр, а не за единицу времени.** Не понимать, что такой код движется с разной скоростью на 60 Гц и 120/144 Гц дисплеях. Не знать про delta time как стандартный фикс.

- **Путать `requestAnimationFrame` и `setInterval`/`setTimeout`.** Не знать, что rAF синхронизирован с частотой обновления дисплея и автоматически приостанавливается в фоновых вкладках, а таймеры не делают ни того, ни другого.

- **Считать spring-анимацию "просто другим easing".** Не понимать, что у неё нет фиксированной длительности в принципе. Именно поэтому её можно прервать на середине движения без видимого скачка, в отличие от duration-based анимации.

- **Не знать про наивный lerp-баг с frame rate.** Использовать `current += (target - current) * 0.1` без поправки на `dt`, не осознавая, что скорость сходимости неявно завязана на частоту кадров.

- **Не суметь объяснить FLIP по шагам.** Знать название техники или библиотеку, которая её использует, но не суметь развернуть First/Last/Invert/Play. И не суметь объяснить, почему в итоге анимируется именно `transform`, а не layout-свойства.

- **Предлагать `requestIdleCallback` для анимации.** Не знать, что у него нет тайминг-гарантий и он не синхронизирован с кадром рендеринга. Поэтому он в принципе непригоден для визуальной анимации, только для фоновой неотложной работы.

- **Не ставить на паузу rAF-циклы для элементов вне вьюпорта.** Не задумываться о том, что бесконечный `requestAnimationFrame`-цикл на невидимом элементе продолжает тратить процессорное время и батарею впустую. Его нужно остановить вручную — через `IntersectionObserver` или аналогичный механизм.
