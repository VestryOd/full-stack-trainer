# requestAnimationFrame и JS-driven анимация

## Когда декларативных инструментов уже не хватает

CSS-переходы, keyframes и WAAPI (статьи 02-03) покрывают подавляющее большинство UI-анимаций — и должны оставаться выбором по умолчанию. Но есть класс задач, которые декларативно не выразить в принципе, потому что в них нет фиксированной точки "откуда" и "куда" на момент старта:

```txt
- Непрерывная симуляция: физика (гравитация, столкновения, инерция курсора)
- Значение зависит от НЕСКОЛЬКИХ источников одновременно и в реальном
  времени: позиция курсора + скорость скролла + время — их нельзя
  заранее описать как keyframes, потому что комбинация меняется каждый кадр
- Анимация, которую нужно прервать НА ПОЛПУТИ и продолжить с ТЕКУЩЕЙ
  скорости в новом направлении — а не доиграть по заранее заданной кривой
- Взаимодействие в реальном времени: drag с инерцией после отпускания,
  где итоговая траектория зависит от скорости жеста пользователя
  в момент отпускания, известной только в рантайме
```

Для этих случаев нужен полный контроль над тем, что происходит каждый кадр — а это и есть `requestAnimationFrame` (rAF). Важно сразу зафиксировать рамку: rAF-анимация — это работа главного потока (см. [Rendering Pipeline and Frame Budget]), и в отличие от CSS/WAAPI на компоузиторе она никогда не "бесплатна" — при перегруженном главном потоке она страдает первой. Выбор в её пользу — осознанный компромисс за контроль, а не апгрейд "более мощного" инструмента.

## Механика `requestAnimationFrame`: когда именно срабатывает колбэк

```javascript
function tick(timestamp) {
  // timestamp — DOMHighResTimeStamp, то же самое время,
  // что вернул бы performance.now() на момент начала кадра
  console.log(timestamp);
  requestAnimationFrame(tick); // планируем следующий вызов
}
requestAnimationFrame(tick);
```

Колбэк `rAF` вызывается браузером **перед** стадией Style/Layout/Paint текущего кадра, синхронизированно с частотой обновления дисплея (vsync) — то есть ровно один раз за кадр, а не "как можно чаще". Это принципиальное отличие от `setInterval(fn, 16)`, у которого нет никакой привязки к реальному циклу рендеринга: `setInterval` может сработать в середине уже идущей стадии рендеринга (тогда изменение стиля попадёт только в СЛЕДУЮЩИЙ кадр, а не в текущий — впустую потраченный вызов), может накапливать отставание, и не согласован с частотой дисплея (60 Гц, 120 Гц, 144 Гц — везде разные).

Ключевая практическая деталь: **в фоновых вкладках `requestAnimationFrame` останавливается или резко замедляется браузером** (обычно до ~1 раза в секунду или полностью приостанавливается) — это экономит CPU и батарею для анимаций, которые пользователь физически не видит. `setInterval`, в отличие от rAF, продолжает тикать в фоне (хотя современные браузеры тоже троттлят его, но менее агрессивно и менее предсказуемо). Это ещё одна причина, по которой для анимации нужно использовать именно rAF, а не таймеры: браузер сам корректно ставит анимацию на паузу там, где пользователь всё равно ничего не увидит.

```javascript
const id = requestAnimationFrame(tick);
cancelAnimationFrame(id); // остановить запланированный вызов — обязательно
                          // делать при размонтировании компонента/удалении
                          // элемента, иначе колбэк продолжит выполняться
                          // и будет пытаться работать с несуществующим DOM
```

## Канонический rAF-цикл с delta time — и почему без него анимация ломается на 120 Гц

Самая частая ошибка новичков в ручной JS-анимации — двигать значение на фиксированный шаг **за кадр**, а не **за единицу времени**:

```javascript
// ❌ Скорость зависит от частоты обновления дисплея
let x = 0;
function tick() {
  x += 2; // "2 пикселя за кадр"
  element.style.transform = `translateX(${x}px)`;
  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
// На 60 Гц-экране: 2px × 60 кадров/сек = 120px/сек
// На 120 Гц-экране: 2px × 120 кадров/сек = 240px/сек
// Один и тот же код движется ВДВОЕ быстрее на более
// частотном дисплее — баг, который сложно поймать локально,
// если у разработчика обычный 60 Гц-монитор
```

Фикс — считать **delta time** (время, прошедшее с прошлого кадра) и масштабировать шаг движения на него, выражая скорость в единицах **за секунду**, а не **за кадр**:

```javascript
// ✅ Скорость не зависит от частоты обновления дисплея
let x = 0;
const speedPerSecond = 120; // px/сек — одна и та же скорость на любом дисплее

let previousTimestamp;
function tick(timestamp) {
  if (previousTimestamp === undefined) previousTimestamp = timestamp;
  const deltaMs = timestamp - previousTimestamp;
  previousTimestamp = timestamp;

  x += speedPerSecond * (deltaMs / 1000);
  element.style.transform = `translateX(${x}px)`;

  requestAnimationFrame(tick);
}
requestAnimationFrame(tick);
// На 60 Гц: 60 кадров × 2px = 120px/сек. На 120 Гц: 120 кадров × 1px = 120px/сек.
// Разное количество более мелких шагов, ОДИНАКОВАЯ итоговая скорость.
```

Это не теоретическая деталь ради полноты — это конкретный источник различия "у меня на маке всё плавно, а у тестировщика на игровом ноуте с 144 Гц анимация летит в 2.4 раза быстрее и заканчивается раньше, чем должна".

## Интерполяция и нормализованный прогресс

Практически любая time-based JS-анимация сводится к одной и той же формуле: нормализовать прошедшее время в диапазон `[0, 1]`, применить easing-функцию к этому нормализованному `t`, и интерполировать между начальным и конечным значением по результату:

```javascript
function animateValue(from, to, duration, easingFn, onUpdate, onComplete) {
  const startTime = performance.now();

  function tick(now) {
    const elapsed = now - startTime;
    const t = Math.min(elapsed / duration, 1); // нормализованный прогресс [0, 1]
    const easedT = easingFn(t);                 // применяем кривую
    const value = from + (to - from) * easedT;   // линейная интерполяция (lerp)

    onUpdate(value);

    if (t < 1) requestAnimationFrame(tick);
    else onComplete?.();
  }

  requestAnimationFrame(tick);
}

animateValue(0, 300, 400, easeOutCubic, (v) => {
  element.style.transform = `translateX(${v}px)`;
});
```

`from + (to - from) * t` — это и есть `lerp` (linear interpolation), базовая операция, на которой строится вся time-based анимация: и CSS-движок внутри делает концептуально то же самое, просто на компоузиторе и без доступного вам JS-кода на каждый кадр.

## Easing как чистая функция от `t`

Easing-функция — это математически просто `f(t): [0,1] → ℝ` (обычно, но не обязательно, в диапазон `[0,1]` — овершут допустим, ровно как и в `cubic-bezier()`, см. статью 02). В отличие от `cubic-bezier()`, JS-easing не ограничен кубической кривой Безье — можно реализовать что угодно: bounce, elastic, ступенчатые эффекты.

```javascript
const easeOutCubic  = (t) => 1 - Math.pow(1 - t, 3);
const easeInOutQuad = (t) => (t < 0.5 ? 2 * t * t : 1 - Math.pow(-2 * t + 2, 2) / 2);

const easeOutBounce = (t) => {
  const n1 = 7.5625, d1 = 2.75;
  if (t < 1 / d1) return n1 * t * t;
  if (t < 2 / d1) return n1 * (t -= 1.5 / d1) * t + 0.75;
  if (t < 2.5 / d1) return n1 * (t -= 2.25 / d1) * t + 0.9375;
  return n1 * (t -= 2.625 / d1) * t + 0.984375;
};
```

Практический вывод для собеседования: `cubic-bezier()` и JS-easing-функция решают одну и ту же математическую задачу (`t → progress`), просто на разных уровнях — декларативном (CSS, ограничен формой кривой Безье, компенсируется `linear()` для сложных случаев, см. статью 02) и императивном (JS, произвольная формула, но всегда ценой работы на главном потоке).

## Springs и damping: физическая альтернатива длительности

У всех примеров выше есть общая черта: заранее заданная **длительность**. Это хорошо подходит для переходов "открыт → закрыт" с известными конечными точками. Но плохо подходит для интерактивной анимации, где движение начинается с уже ненулевой скорости (например, пользователь бросил элемент после drag) или должно быть прервано на полпути новым таргетом.

Spring-анимация моделирует не "прогресс по времени", а физическую систему масса-пружина-демпфер: пружина тянет текущее значение к цели с силой, пропорциональной расстоянию, демпфер гасит эту силу пропорционально скорости. У неё **нет фиксированной длительности** — она останавливается сама, когда скорость и расстояние до цели становятся пренебрежимо малыми:

```javascript
function springStep(current, velocity, target, { stiffness = 170, damping = 26, mass = 1 }, dt) {
  const springForce = -stiffness * (current - target); // тянет к цели
  const dampingForce = -damping * velocity;             // гасит колебания
  const acceleration = (springForce + dampingForce) / mass;

  velocity += acceleration * dt;
  current += velocity * dt;

  return { current, velocity };
}

function animateSpring(from, to, onUpdate, config = {}) {
  let current = from;
  let velocity = 0;
  let previousTime;

  function tick(now) {
    if (previousTime === undefined) previousTime = now;
    const dt = Math.min((now - previousTime) / 1000, 1 / 30); // клампим dt на случай лагов
    previousTime = now;

    ({ current, velocity } = springStep(current, velocity, to, config, dt));
    onUpdate(current);

    // Останавливаемся, когда система практически успокоилась
    if (Math.abs(to - current) > 0.01 || Math.abs(velocity) > 0.01) {
      requestAnimationFrame(tick);
    }
  }
  requestAnimationFrame(tick);
}
```

Почему это "ощущается естественнее" не эстетическая вкусовщина, а прямое следствие модели: в реальном мире объекты не движутся по заранее расписанному временному графику — они реагируют на силы здесь и сейчас. И именно поэтому spring **интерруптибелен там, где duration-based анимация — нет**: состояние спринга — это `(текущее значение, текущая скорость)`, а не `(t внутри фиксированной длительности)`. Сменить `target` на середине движения — тривиально, физика сама пересчитает новую траекторию с сохранением текущей скорости, без видимого "скачка":

```javascript
// Пользователь двигает мышью — таргет меняется каждый кадр,
// а спринг продолжает движение плавно, без рестарта анимации
let springTarget = 0;
document.addEventListener('mousemove', (e) => { springTarget = e.clientX; });
// animateSpring(...) читает springTarget на каждом шаге вместо фиксированного to
```

Это ключевая причина, по которой современные интерфейсные тулкиты (iOS, Framer Motion, react-spring, Motion.dev) используют spring как дефолт для интерактивных, прерываемых элементов — и duration+easing для некликабельных, "проигрывающихся один раз" переходов.

## Lerp-сглаживание для курсора и параллакса — и скрытая ловушка frame-rate

Частый паттерн — "плавное следование" за целью: кастомный курсор, который догоняет реальный указатель мыши с задержкой, или параллакс-слой, сглаживающий резкие скачки скролла:

```javascript
// ❌ Наивный lerp — коэффициент "0.1" даёт РАЗНУЮ скорость
// сходимости на разных частотах дисплея
let current = 0;
function tick() {
  current += (target - current) * 0.1; // "подтягиваем" на 10% расстояния за кадр
  cursor.style.transform = `translateX(${current}px)`;
  requestAnimationFrame(tick);
}
// На 120 Гц current "подтягивается" в 2 раза чаще за секунду,
// чем на 60 Гц → курсор физически догоняет цель заметно быстрее
```

Тот же класс проблемы, что и с "px += 2 за кадр" выше, только более скрытый — код выглядит "уже время-независимым", но коэффициент затухания `0.1` неявно завязан на частоту вызова. Правильная формула — экспоненциальное затухание, скорректированное на реальный `dt`:

```javascript
// ✅ Сходимость не зависит от частоты кадров
let current = 0;
let previousTime;
const smoothingHalfLife = 0.08; // время (сек), за которое расстояние до цели сокращается вдвое

function tick(now) {
  if (previousTime === undefined) previousTime = now;
  const dt = (now - previousTime) / 1000;
  previousTime = now;

  const decay = 1 - Math.pow(2, -dt / smoothingHalfLife);
  current += (target - current) * decay;

  cursor.style.transform = `translateX(${current}px)`;
  requestAnimationFrame(tick);
}
```

Эта деталь редко всплывает в туториалах, но именно её отсутствие — причина "у нас курсор-блоб на демо-мониторе 60 Гц ощущается иначе, чем на MacBook с ProMotion 120 Гц", хотя код формально "одинаковый".

## FLIP: превращаем дорогую layout-анимацию в дешёвую transform-анимацию

Классическая проблема: элементы списка переупорядочиваются (сортировка, drag-and-drop, фильтрация), их положение в DOM-потоке меняется мгновенно, и единственный способ анимировать это "в лоб" — анимировать `top`/`left`/`grid-row` и т.п., что запускает Layout на каждый кадр (статья 01) и физически не масштабируется на списки из полусотни элементов без заметного джанка.

**FLIP** (First → Last → Invert → Play) — техника, которая обходит эту проблему целиком, сводя анимацию исключительно к `transform`:

```txt
First  — ДО изменения DOM: измерить текущую позицию элемента
          (getBoundingClientRect())
Last   — применить изменение DOM (реальный reorder/layout-сдвиг) —
          браузер мгновенно кладёт элемент в НОВУЮ позицию,
          БЕЗ анимации, и измерить эту новую позицию
Invert — вычислить разницу (delta) между First и Last, и СРАЗУ
          применить к элементу transform, компенсирующий эту
          разницу — визуально элемент как будто остался на
          старом месте, хотя физически (в layout) он уже в новом
Play   — включить transition на transform и обнулить компенсирующий
          transform → элемент плавно "доезжает" от старой
          визуальной позиции до настоящей новой, и всё это —
          чистый compositor-transform, без единого reflow за кадр
```

Пошаговая реализация для переупорядочиваемого списка:

```javascript
function flipReorder(container, reorderFn) {
  const items = [...container.children];

  // FIRST — снимаем позиции ДО изменения DOM
  const firstRects = new Map(items.map((el) => [el, el.getBoundingClientRect()]));

  // (реальное изменение DOM — например, пересортировка по данным)
  reorderFn();

  // LAST — снимаем позиции ПОСЛЕ изменения DOM
  items.forEach((el) => {
    const first = firstRects.get(el);
    const last = el.getBoundingClientRect();

    const deltaX = first.left - last.left;
    const deltaY = first.top - last.top;

    if (deltaX === 0 && deltaY === 0) return; // элемент не сдвинулся — пропускаем

    // INVERT — компенсируем разницу transform'ом, БЕЗ transition
    el.style.transition = 'none';
    el.style.transform = `translate(${deltaX}px, ${deltaY}px)`;

    // Форсируем layout ОДИН раз, чтобы браузер зафиксировал
    // инвертированное состояние перед тем, как мы включим transition
    el.getBoundingClientRect();

    // PLAY — включаем transition и убираем компенсацию
    el.style.transition = 'transform 0.3s ease';
    el.style.transform = '';
  });
}
```

Это в точности тот механизм, который лежит под капотом `react-flip-toolkit` и layout-анимаций Framer Motion (`layout` prop, статья 05) — они автоматизируют именно эти четыре шага, снимая с разработчика ручной учёт `getBoundingClientRect()` до/после и синхронизацию с ре-рендером фреймворка. Понимание FLIP вручную — то, что отличает "я использую библиотеку с layout-анимациями" от "я понимаю, ПОЧЕМУ они вообще работают и почему это не layout-анимация в буквальном смысле".

## `requestIdleCallback`: не для анимации, а для того, что НЕ должно мешать анимации

`requestIdleCallback` (rIC) планирует выполнение колбэка в свободное время браузера между кадрами — когда до следующего кадра ещё есть запас, и главный поток не занят ничем срочным:

```javascript
requestIdleCallback((deadline) => {
  while (deadline.timeRemaining() > 0 && tasksQueue.length > 0) {
    processTask(tasksQueue.shift());
  }
  if (tasksQueue.length > 0) requestIdleCallback(arguments.callee);
});
```

Ключевая ошибка — пытаться использовать `rIC` ДЛЯ анимации: у него **нет гарантии частоты и таймингов** — колбэк может быть отложен на неопределённое время, если главный поток постоянно занят, и он никак не синхронизирован с частотой обновления дисплея. `rIC` — инструмент для фоновой, неотложной работы: батчинг аналитики, прогрев кэша, предзагрузка данных, ленивая инициализация — того, что должно происходить "когда будет минутка", а не "точно в следующем кадре".

### Когда анимацию стоит вообще не запускать

Часть профессиональной работы с JS-анимацией — не запускать её там, где она не нужна:

```javascript
// Ставим rAF-цикл на паузу, когда элемент вне вьюпорта —
// нет смысла тратить CPU/батарею на анимацию, которую никто не видит
const observer = new IntersectionObserver(([entry]) => {
  if (entry.isIntersecting) startAnimationLoop();
  else stopAnimationLoop();
});
observer.observe(element);
```

Это тот же принцип, что стоит за паузой rAF в фоновых вкладках браузером — только применённый вручную к отдельным элементам на самой странице. Про `prefers-reduced-motion` как ещё одну причину не запускать анимацию (или заменить её на менее интенсивную) — отдельно и подробно в статье 07.

## Типичные ошибки на интервью

- **Двигать значение на фиксированный шаг за кадр, а не за единицу времени** — не понимать, что такой код движется с разной скоростью на 60 Гц и 120/144 Гц дисплеях, и не знать про delta time как стандартный фикс.

- **Путать `requestAnimationFrame` и `setInterval`/`setTimeout`** — не знать, что rAF синхронизирован с частотой обновления дисплея и автоматически приостанавливается в фоновых вкладках, а таймеры — нет.

- **Считать spring-анимацию "просто другим easing"** — не понимать, что у неё нет фиксированной длительности в принципе, и что именно поэтому она интерруптибельна на середине движения без видимого скачка, в отличие от duration-based анимации.

- **Не знать про наивный lerp-баг с frame rate** — использовать `current += (target - current) * 0.1` без поправки на `dt`, не осознавая, что скорость сходимости неявно завязана на частоту кадров.

- **Не суметь объяснить FLIP по шагам** — знать название техники (или библиотеку, которая её использует), но не суметь развернуть First/Last/Invert/Play и объяснить, почему в итоге анимируется именно `transform`, а не layout-свойства.

- **Предлагать `requestIdleCallback` для анимации** — не знать, что у него нет тайминг-гарантий и он не синхронизирован с кадром рендеринга, поэтому он в принципе непригоден для visual-анимации, только для фоновой неотложной работы.

- **Не ставить на паузу rAF-циклы для элементов вне вьюпорта** — не задумываться о том, что бесконечный `requestAnimationFrame`-цикл на невидимом элементе продолжает тратить CPU/батарею впустую, если не остановлен вручную через `IntersectionObserver` или аналогичный механизм.
