# Диагностика производительности и охота за джанком

## От теории к "почему тормозит именно эта анимация и именно здесь"

Статьи 01-05 дали словарь и инструменты: конвейер рендеринга, дешёвые и дорогие свойства, WAAPI (Web Animations API), `requestAnimationFrame` (rAF), библиотеки.

Эта статья — про рабочий процесс senior-разработчика. Тимлид присылает скринкаст без единой другой детали. Подпись: "на iPhone SE лендинг тормозит при скролле" (SE — Special Edition). Джанк (jank) — это, физически, пропущенный кадр (статья 01). Диагностика джанка — не "посмотреть на код и предположить", а последовательность конкретных инструментов DevTools, каждый из которых отвечает на свой вопрос.

## Performance-панель: где физически теряется время

Запись (Record → воспроизвести проблемное взаимодействие → Stop) даёт flame chart главного потока — это первый и самый информативный инструмент.

```txt
Как читать flame chart:
┌───────────────────────────────────────────────────────────┐
│ Main                                                      │
│ ▓▓▓▓░░░▓▓▓▓▓▓▓▓▓▓▓▓░░░▓▓▓░░░░░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░       │
│  JS   Style Layout  Paint    JS (rAF callback)  Composite │
└───────────────────────────────────────────────────────────┘
  По горизонтали — время.
  Цвет блока = категория работы:
  жёлтый = Scripting (ваш JS)
  фиолетовый = Rendering (Style/Layout)
  зелёный = Painting (Paint)
  синий = Loading
```

Целенаправленно искать стоит три сигнала:

| Сигнал в flame chart | Что это значит |
|---|---|
| Блок JS на главном потоке дольше 50 мс, красный треугольник | Long Task. Пользователь чувствует задержку. |
| Фиолетовый блок Layout с пометкой "Forced reflow" | Чтение геометрии сразу после записи стиля. |
| Layout → Paint → Composite на каждый tick | Анимируется layout-свойство, а не `transform`. |

- **Long Tasks.** Любой непрерывный блок JS на главном потоке дольше 50 мс помечается красным треугольником в углу блока. Это эмпирический порог. Задачи короче 50 мс не воспринимаются как задержка отклика. Более длинные блокируют главный поток достаточно, чтобы пользователь заметил лаг. Этот же порог лежит в основе метрики INP (Interaction to Next Paint), о которой ниже.

- **Forced reflow.** Фиолетовый блок Layout с пометкой "Forced reflow" и жёлтым восклицательным знаком. Означает ровно то, что разобрано в статье 01: JS прочитал геометрию (`offsetHeight` и подобные) сразу после записи стиля, и браузер был вынужден посчитать layout синхронно, вне обычного batching. Клик по предупреждению в DevTools раскрывает **stack trace** — точную строку кода, которая это вызвала. Это самый быстрый способ найти layout thrashing в реальном приложении, не читая весь код построчно.

- **Повторяющийся паттерн Layout → Paint → Composite на каждый кадр анимации.** Если flame chart анимации показывает эти три блока на каждый tick, значит анимируется layout-triggering свойство, а не `transform`/`opacity`. Например `top` или `width`; полная таблица — в статье 01. Здоровая compositor-only анимация в идеале показывает только тонкие блоки Composite, без Layout/Paint между ними.

## Панель Layers: почему элементов-слоёв больше, чем ожидалось

`DevTools → More tools → Layers` даёт 3D-визуализацию всех composited-слоёв страницы. Панель расслаивает страницу по оси Z и показывает, что стало отдельным слоем и почему.

```txt
Для каждого слоя панель показывает:
  - Compositing Reasons — точная причина выноса в слой
    ("has a will-change: transform", "is animated", и т.п.) —
    не нужно гадать, что именно триггернуло слой
  - Memory estimate — сколько GPU-памяти занимает слой
    (напрямую связано с формулой width × height × 4 байта
    из статьи 01)
```

**Layer explosion** диагностируется здесь напрямую. Если панель показывает десятки-сотни слоёв там, где ожидалось 3-5 анимируемых элементов, значит кто-то создаёт слои за вас.

Почти всегда причина — `will-change`, оставленный на статичных элементах "про запас" (антипаттерн из статьи 01). Вторая частая причина — CSS-фильтр или 3D-transform на компоненте, который рендерится массово. Например, каждая карточка в списке из сотни штук получила `filter` для тени, и каждая стала отдельным слоем.

## Paint flashing и paint profiler: что перерисовывается, когда не должно

`DevTools → Rendering tab → Paint flashing` включает визуальную подсветку любой области экрана, которая была перерисована (Paint). Обычно это зелёный прямоугольник, и подсветка работает в реальном времени, пока вы взаимодействуете со страницей.

```txt
Диагностический сценарий: скролл ленты новостей мигает зелёным
по всей высоте видимой области при каждом кадре скролла —
хотя скроллится только список, а хедер и сайдбар должны
оставаться статичными.

Причина почти всегда: элемент без своего слоя перекрывает
или соседствует с анимируемым/скроллящимся контентом,
и браузер вынужден перерисовывать больше пикселей, чем
нужно, потому что paint происходит не по отдельным слоям,
а "заодно" для пересекающейся области.

Фикс: изолировать анимируемую или скроллящуюся область в
собственный composited layer (transform: translateZ(0) или
CSS containment, см. ниже) — чтобы paint затрагивал только
её пиксели, а не весь оверлеп с соседями.
```

Отдельно стоит смотреть на `box-shadow` и `filter: blur()`. Заметная "горячая зона" в paint flashing на статичном на вид элементе почти всегда означает одно. Тень или блюр перерисовывается заново каждый кадр.

Например, анимируется `box-shadow` вместо трансформации предрендеренной тени. Растеризация большого blur-радиуса на CPU (центральный процессор) или GPU (графический процессор) заметно дороже простой заливки.

## FPS meter и frame rendering stats: быстрая проверка "на глаз"

`DevTools → Rendering tab → Frame Rendering Stats` включает overlay прямо поверх страницы. Он показывает текущий FPS (frames per second, кадров в секунду), использование GPU-памяти и счётчик пропущенных кадров в реальном времени. Это не запись, а живой монитор для быстрой проверки гипотезы вида "не регрессировало ли только что это изменение". Ответ приходит без полноценной записи в Performance-панели.

## Частые причины джанка — и конкретные фиксы

| Причина | Диагностика | Фикс |
|---|---|---|
| Layout thrashing | Предупреждение "Forced reflow" | Разделить чтение и запись |
| Анимация layout-свойств | Layout+Paint на каждый кадр | Перейти на `transform`/`opacity` |
| Избыточные или большие слои | Layers-панель, Memory estimate | Не выносить декор |
| Анимация `box-shadow`/`filter` | Горячая зона в paint flashing | Анимировать псевдоэлемент |
| Scroll-хендлер читает геометрию | Forced reflow на каждый скролл | `{ passive: true }` |

### Layout thrashing

Разобрано детально в статье 01. Диагностика: "Forced reflow" в Performance-панели. Фикс: разделять фазы чтения (`offsetHeight` и т.п.) и записи стилей, не чередовать их в цикле.

### Анимация layout-свойств вместо transform/opacity

Диагностика: повторяющийся Layout+Paint на каждый кадр анимации в flame chart (см. выше). Фикс: см. таблицу в статье 01 — переписать через `transform`/`opacity`.

### Избыточные/переразмеренные слои на мобильных

```txt
Симптом: полноэкранное фоновое видео или изображение с
градиентом вынесено в отдельный слой на весь экран —
на десктопе незаметно, на бюджетном Android с общей
CPU/GPU-памятью вызывает заметные лаги во всей странице,
не только в области этого элемента.

Диагностика: Layers-панель → Memory estimate у этого слоя.

Фикс: не выносить декоративный фон в отдельный слой без
необходимости (не вешать на него will-change/3D-transform
без причины); для действительно больших фоновых изображений —
отдавать уменьшенную по разрешению версию под мобильные
брейкпоинты, а не масштабировать десктопное изображение
средствами CSS.
```

### `box-shadow`/`filter` в анимации

```css
/* ❌ Анимация box-shadow — каждый кадр перерисовывает тень заново */
.card {
  transition: box-shadow 0.3s;
}
.card:hover {
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
}
```

```css
/* ✅ Статичная предрендеренная тень на отдельном псевдоэлементе,
   анимируется её opacity (compositor-only) вместо перерисовки blur */
.card {
  position: relative;
}
.card::after {
  content: '';
  position: absolute;
  inset: 0;
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
  opacity: 0;
  transition: opacity 0.3s;
}
.card:hover::after {
  opacity: 1;
}
```

### Scroll-хендлеры с синхронным чтением layout

```javascript
// ❌ Non-passive listener + чтение геометрии на каждый scroll-event —
// браузер вынужден ждать выполнения хендлера (проверяя preventDefault),
// прежде чем сам скролл сможет визуально обновиться, и дополнительно
// форсирует layout при каждом чтении offsetTop
window.addEventListener('scroll', () => {
  const rect = header.getBoundingClientRect(); // читает геометрию —
  if (rect.top < 0) header.classList.add('is-stuck'); // потенциальный forced reflow
});
```

```javascript
// ✅ passive: true явно говорит браузеру "хендлер не вызовет
// preventDefault", убирая блокировку скролла на главном потоке
window.addEventListener('scroll', onScroll, { passive: true });

// ✅ Ещё лучше — IntersectionObserver вместо scroll-листенера
// вообще: работает асинхронно, вне главного потока на каждый кадр,
// не требует ручного чтения getBoundingClientRect
const observer = new IntersectionObserver(
  ([entry]) => header.classList.toggle('is-stuck', !entry.isIntersecting),
  { threshold: 0 },
);
observer.observe(sentinelElement);
```

`{ passive: true }` — не микрооптимизация. Без него браузер **обязан** синхронно дождаться завершения JS-обработчика на каждое событие скролла, прежде чем закоммитить визуальный скролл. Причина: теоретически обработчик мог вызвать `preventDefault()` и отменить этот скролл.

Гарантированно не блокировать нативный скролл вашим JS можно двумя способами. Первый — `{ passive: true }`. Второй — полный отказ от `scroll`-листенера в пользу `IntersectionObserver`.

## `content-visibility` и CSS containment: не рендерить то, чего не видно

Для длинных страниц с множеством секций — документация, лента, каталог — браузер по умолчанию считает Style/Layout/Paint для **всего** документа. Это включает контент далеко за пределами текущего вьюпорта. Объявление `content-visibility: auto` явно разрешает браузеру пропускать рендеринг-работу для контента, который сейчас не виден:

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: 0 800px; /* placeholder-размер до первого
    реального рендера — без него скролл-бар "скачет", потому что
    браузер не знает высоту ещё не отрендеренной секции */
}
```

```txt
Эффект: секции вне вьюпорта (и не рядом с ним) не проходят
Layout/Paint вообще, пока не приблизятся к области видимости —
это не lazy-loading контента (DOM остаётся на месте, доступен
для поиска по Ctrl+F и SEO), а именно пропуск рендеринг-работы.
На страницах с сотнями секций разница в первичном рендере
и отзывчивости скролла — заметно ощутима.
```

Свойство `contain` без `content-visibility` — более тонкий, ручной инструмент. Оно явно сообщает браузеру, что изменения **внутри** элемента не должны требовать пересчёта layout или paint **снаружи** него:

```css
.independent-widget {
  contain: layout paint; /* этот элемент — изолированный "контейнер":
    его внутренние изменения не заставляют браузер пересчитывать
    геометрию/перерисовывать что-либо за его границами */
}
```

Это сужает область пересчёта при layout thrashing внутри виджета до самого виджета, а не всего документа. Полезно для сложных виджетов, которые часто меняют внутреннюю разметку: data grid, canvas-обёртки, чат с частым обновлением сообщений.

## `OffscreenCanvas` — когда DOM-анимация вообще перестаёт масштабироваться

Есть точка, после которой DOM (document object model, дерево объектов страницы в браузере) — уже не тот инструмент для анимации. Три примера: тысячи независимо анимируемых частиц, сложная физическая симуляция, покадровый рендеринг, где каждый элемент — отдельный DOM-узел.

Каждый DOM-узел несёт с собой оверхед: собственный composited layer при анимации, собственную запись в дереве стилей, собственный hit-testing. Hit-testing — это проверка, на какой элемент попало событие указателя. На масштабе в тысячи элементов этот оверхед начинает доминировать над самой полезной работой.

```txt
┌──────────────────────────────────────────┐
│ Тысячи анимируемых DOM-узлов             │
└──────────────────────────────────────────┘
                      │  измерить
                      ▼
┌──────────────────────────────────────────┐
│ Профилировщик: время Style/Layout растёт │
│ с числом узлов, а не со сложностью       │
│ самой анимации                           │
└──────────────────────────────────────────┘
                      │  прочитать форму
                      ▼
┌──────────────────────────────────────────┐
│ Архитектурный потолок, а не недостающая  │
│ оптимизация                              │
└──────────────────────────────────────────┘
                      │  сменить инструмент
                      ▼
┌──────────────────────────────────────────┐
│ OffscreenCanvas: растровый рендеринг во  │
│ Worker-потоке, вне главного потока и DOM │
└──────────────────────────────────────────┘
```

Сигнал переключиться — не "стало чуть медленнее", а качественный. Смотреть надо на форму роста в профилировщике. Style/Layout-время может расти линейно с количеством анимируемых DOM-узлов, а не со сложностью самой анимации. Это архитектурная граница, а не повод для ещё одной оптимизации.

В этой точке `OffscreenCanvas` даёт возможность делать растровый рендеринг в отдельном Worker-потоке через Canvas 2D или WebGL (3D-графика в браузере). Это полностью в стороне от главного потока и DOM-дерева. Само рисование на Canvas и WebGL — тема отдельного топика Canvas & Graphics. Здесь важно только распознать момент, когда DOM/CSS-анимация упирается в архитектурный потолок.

## Измерение в продакшене: Long Animation Frames и INP

DevTools-профилирование работает на вашей машине, с вашей CPU/GPU и вашей сетью. Реальные пользователи почти всегда на менее мощном железе. Для продакшен-мониторинга нужны API, которые сообщают о проблемах с реальных устройств.

**Long Animation Frames API (LoAF)** — более детальный преемник Long Tasks API специально для проблем, связанных с рендерингом:

```javascript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log({
      duration: entry.duration,               // общая длительность "тяжёлого" кадра
      renderStart: entry.renderStart,          // когда начался рендеринг внутри кадра
      styleAndLayoutStart: entry.styleAndLayoutStart,
      scripts: entry.scripts.map((s) => ({     // какой именно скрипт виноват
        name: s.name,
        duration: s.duration,
        // например, конкретный event listener или rAF-колбэк
        invoker: s.invoker,
      })),
    });
  }
}).observe({ type: 'long-animation-frame', buffered: true });
```

Обычный Long Tasks API просто сообщает "что-то заняло больше 50 мс". LoAF идёт дальше. Он разбивает "тяжёлый" кадр на фазы: сколько ушло на скрипт, сколько на Style/Layout. И указывает конкретный виновный скрипт. На реальных пользовательских устройствах это даёт то же, что stack trace в Performance-панели, но без необходимости воспроизводить проблему локально.

**INP (Interaction to Next Paint)** — метрика Core Web Vitals. Она измеряет задержку между действием пользователя и моментом, когда браузер физически показывает следующий обновлённый кадр в ответ. Действием может быть клик, тап или нажатие клавиши.

Это прямая связка с темой этой статьи. Допустим, rAF-колбэк или JS-анимация занимает главный поток дольше frame budget (статья 01). И допустим, это происходит ровно в тот момент, когда пользователь взаимодействует со страницей. Тогда ответный кадр откладывается — например, визуальное "нажатие" кнопки. Это напрямую ухудшает INP, точно так же, как влияет на воспринимаемую плавность самой анимации.

Многие команды уже оптимизируют LCP (Largest Contentful Paint) и CLS (Cumulative Layout Shift). Для них стоит сказать это прямо. Тяжёлая, плохо спланированная анимация — не только "эстетическая" проблема. Это измеримый фактор в том же отчёте Web Vitals, с реальными последствиями для SEO (search engine optimization, поисковая оптимизация) и продуктовых метрик.

## Типичные ошибки на интервью

- **Не знать, как выглядит "forced reflow" в DevTools.** Не суметь описать, что Performance-панель явно помечает такие случаи фиолетовым блоком с предупреждением. И что она даёт stack trace до конкретной строки кода.

- **Путать paint flashing с FPS meter.** Не различать инструменты по назначению. Paint flashing показывает, **какие области** перерисовываются. FPS meter показывает только агрегированную частоту кадров, без локализации причины.

- **Не знать про `{ passive: true }`.** Непассивный scroll- или touch-листенер заставляет браузер синхронно ждать завершения JS-обработчика. Только после этого браузер может визуально закоммитить скролл. То есть речь не про "чуть быстрее выполнится JS", а про блокировку самого скролла.

- **Не знать `content-visibility`.** Предлагать виртуализацию списка, например `react-window`, как единственное решение проблемы длинных страниц. Не знать о более простой CSS-альтернативе для контента, который виртуализировать нельзя: обычный длинный документ, а не список одинаковых элементов.

- **Считать, что DevTools Performance-панель на локальной машине репрезентативна для продакшена.** Не знать про Long Animation Frames API и `PerformanceObserver` как способ получать те же данные с реальных пользовательских устройств.

- **Не связывать анимацию с INP.** Воспринимать плохую производительность анимации исключительно как "визуальную" проблему. Не понимать, что она напрямую бьёт по измеримой метрике Core Web Vitals и, соответственно, по SEO и продуктовым показателям.

- **Не знать, когда DOM/CSS-анимация физически перестаёт масштабироваться.** Пытаться оптимизировать тысячи анимируемых DOM-узлов точечными фиксами, вместо того чтобы распознать архитектурный потолок и перейти на Canvas или WebGL.
