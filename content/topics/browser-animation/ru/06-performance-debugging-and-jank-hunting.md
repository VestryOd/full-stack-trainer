# Диагностика производительности и охота за джанком

## От теории к "почему именно ЭТА анимация тормозит именно ЗДЕСЬ"

Статьи 01-05 дали словарь и инструменты: конвейер рендеринга, дешёвые/дорогие свойства, WAAPI, rAF, библиотеки. Эта статья — про рабочий процесс senior-разработчика, когда тимлид присылает скринкаст "на iPhone SE лендинг тормозит при скролле" без единой другой детали. Диагностика jank — это не "посмотреть на код и предположить", а последовательность конкретных инструментов DevTools, каждый из которых отвечает на свой вопрос.

## Performance-панель: где физически теряется время

Запись (Record → воспроизвести проблемное взаимодействие → Stop) даёт flame chart главного потока — это первый и самый информативный инструмент.

```txt
Как читать flame chart:
┌─────────────────────────────────────────────────────────┐
│ Main                                                      │
│ ▓▓▓▓░░░▓▓▓▓▓▓▓▓▓▓▓▓░░░▓▓▓░░░░░▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓▓░░░      │  ← временная шкала
│  JS   Style Layout  Paint    JS (rAF callback)  Composite│
└─────────────────────────────────────────────────────────┘
  Цвет блока = категория работы:
  жёлтый = Scripting (ваш JS)
  фиолетовый = Rendering (Style/Layout)
  зелёный = Painting (Paint)
  синий = Loading
```

Что искать целенаправленно:

**Long Tasks** — любой непрерывный блок JS на главном потоке дольше 50 мс помечается красным треугольником в углу блока. Это эмпирический порог: задачи короче 50 мс не воспринимаются как задержка отклика; длиннее — блокируют главный поток достаточно, чтобы пользователь заметил лаг (это тот же порог, что лежит в основе метрики INP, о которой ниже).

**Forced reflow** — предупреждение (фиолетовый блок Layout с пометкой "Forced reflow" и жёлтым восклицательным знаком) означает ровно то, что разобрано в статье 01: JS прочитал геометрию (`offsetHeight` и подобные) сразу после записи стиля, и браузер был вынужден посчитать layout синхронно, вне обычного batching. Клик по предупреждению в DevTools раскрывает **stack trace** — точную строку кода, которая это вызвала. Это самый быстрый способ найти layout thrashing в реальном приложении, не читая весь код построчно.

**Повторяющийся паттерн Layout → Paint → Composite на каждый кадр анимации** — если flame chart анимации показывает эти три блока на каждый tick, значит анимируется layout-triggering свойство (`top`, `width`, и т.п. — таблица из статьи 01), а не `transform`/`opacity`. Здоровая compositor-only анимация в идеале показывает только тонкие блоки Composite, без Layout/Paint между ними.

## Панель Layers: почему элементов-слоёв больше, чем ожидалось

`DevTools → More tools → Layers` даёт 3D-визуализацию всех composited-слоёв страницы — буквально "расслаивает" страницу по оси Z, показывая, что стало отдельным слоем и почему.

```txt
Для каждого слоя панель показывает:
  - Compositing Reasons — ТОЧНАЯ причина промоушена
    ("has a will-change: transform", "is animated", и т.п.) —
    не нужно гадать, что именно триггернуло слой
  - Memory estimate — сколько GPU-памяти занимает слой
    (напрямую связано с формулой width × height × 4 байта
    из статьи 01)
```

**Layer explosion** — диагностируется здесь напрямую: если панель показывает десятки-сотни слоёв там, где ожидалось 3-5 (анимируемые элементы), почти всегда причина — `will-change`, оставленный на статичных элементах "про запас" (антипаттерн из статьи 01), либо CSS-фильтр/3D-transform на компоненте, который рендерится массово (например, каждая карточка в списке из сотни штук получила `filter` для тени, и КАЖДАЯ стала отдельным слоем).

## Paint flashing и paint profiler: что перерисовывается, когда не должно

`DevTools → Rendering tab → Paint flashing` — включает визуальную подсветку (обычно зелёным прямоугольником) любой области экрана, которая была перерисована (Paint) в реальном времени, пока вы взаимодействуете со страницей.

```txt
Диагностический сценарий: скролл ленты новостей мигает зелёным
по ВСЕЙ высоте видимой области при каждом кадре скролла —
хотя скроллится только список, а хедер и сайдбар должны
оставаться статичными.

Причина почти всегда: элемент без своего слоя перекрывает
или соседствует с анимируемым/скроллящимся контентом,
и браузер вынужден перерисовывать больше пикселей, чем
нужно, потому что paint происходит не по отдельным слоям,
а "заодно" для пересекающейся области.

Fix: изолировать анимируемую/скроллящуюся область в
собственный composited layer (transform: translateZ(0) или
CSS containment, см. ниже) — чтобы paint затрагивал только
её пиксели, а не весь оверлеп с соседями.
```

Отдельно `box-shadow`/`filter: blur()` — заметная "горячая зона" в paint flashing на статичном на вид элементе почти всегда означает, что тень/блюр перерисовывается заново каждый кадр (например, анимируется `box-shadow` вместо трансформации предрендеренной тени) — растеризация большого blur-радиуса на CPU/GPU заметно дороже простой заливки.

## FPS meter и frame rendering stats: быстрая проверка "на глаз"

`DevTools → Rendering tab → Frame Rendering Stats` включает overlay прямо поверх страницы с текущим FPS, использованием GPU-памяти и счётчиком пропущенных кадров в реальном времени — не запись, а живой монитор для быстрой проверки гипотезы ("не регрессировало ли только что это изменение") без полноценной записи в Performance-панели.

## Частые причины джанка — и конкретные фиксы

### Layout thrashing

Разобрано детально в статье 01. Диагностика: "Forced reflow" в Performance-панели. Фикс: разделять фазы чтения (`offsetHeight` и т.п.) и записи стилей, не чередовать их в цикле.

### Анимация layout-свойств вместо transform/opacity

Диагностика: повторяющийся Layout+Paint на каждый кадр анимации в flame chart (см. выше). Фикс: см. таблицу в статье 01 — переписать через `transform`/`opacity`.

### Избыточные/переразмеренные слои на мобильных

```txt
Симптом: полноэкранное фоновое видео или изображение с
градиентом промотировано в отдельный слой на весь экран —
на десктопе незаметно, на бюджетном Android с общей
CPU/GPU-памятью вызывает заметные лаги во ВСЕЙ странице,
не только в области этого элемента.

Диагностика: Layers-панель → Memory estimate у этого слоя.

Fix: не промотировать декоративный фон в отдельный слой без
необходимости (не вешать на него will-change/3D-transform
без причины); для действительно больших фоновых изображений —
отдавать уменьшенную по разрешению версию под мобильные
брейкпоинты, а не масштабировать десктопное изображение
средствами CSS.
```

### `box-shadow`/`filter` в анимации

```css
/* ❌ Анимация box-shadow — каждый кадр перерисовывает тень заново */
.card {
  transition: box-shadow 0.3s;
}
.card:hover {
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
}
```

```css
/* ✅ Статичная предрендеренная тень на отдельном псевдоэлементе,
   анимируется её opacity (compositor-only) вместо перерисовки blur */
.card {
  position: relative;
}
.card::after {
  content: '';
  position: absolute;
  inset: 0;
  box-shadow: 0 20px 40px rgba(0,0,0,0.3);
  opacity: 0;
  transition: opacity 0.3s;
}
.card:hover::after {
  opacity: 1;
}
```

### Scroll-хендлеры с синхронным чтением layout

```javascript
// ❌ Non-passive listener + чтение геометрии на каждый scroll-event —
// браузер вынужден ждать выполнения хендлера (проверяя preventDefault),
// прежде чем сам скролл сможет визуально обновиться, и дополнительно
// форсирует layout при каждом чтении offsetTop
window.addEventListener('scroll', () => {
  const rect = header.getBoundingClientRect(); // читает геометрию —
  if (rect.top < 0) header.classList.add('is-stuck'); // потенциальный forced reflow
});
```

```javascript
// ✅ passive: true явно говорит браузеру "хендлер не вызовет
// preventDefault", убирая блокировку скролла на главном потоке
window.addEventListener('scroll', onScroll, { passive: true });

// ✅ Ещё лучше — IntersectionObserver вместо scroll-листенера
// вообще: работает асинхронно, вне главного потока на каждый кадр,
// не требует ручного чтения getBoundingClientRect
const observer = new IntersectionObserver(
  ([entry]) => header.classList.toggle('is-stuck', !entry.isIntersecting),
  { threshold: 0 },
);
observer.observe(sentinelElement);
```

`{ passive: true }` — не микрооптимизация: без него браузер ОБЯЗАН синхронно дождаться завершения JS-обработчика на каждое событие скролла, прежде чем закоммитить визуальный скролл, потому что теоретически обработчик мог вызвать `preventDefault()` и отменить его. Это единственный (наравне с полным отказом от `scroll`-листенера в пользу `IntersectionObserver`) способ гарантированно не блокировать нативный скролл вашим JS.

## `content-visibility` и CSS containment: не рендерить то, чего не видно

Для длинных страниц с множеством секций (документация, лента, каталог) браузер по умолчанию считает Style/Layout/Paint для ВСЕГО документа, включая контент далеко за пределами текущего вьюпорта. `content-visibility: auto` явно разрешает браузеру пропускать рендеринг-работу для контента, который сейчас не виден:

```css
.article-section {
  content-visibility: auto;
  contain-intrinsic-size: 0 800px; /* placeholder-размер до первого
    реального рендера — без него скролл-бар "скачет", потому что
    браузер не знает высоту ещё не отрендеренной секции */
}
```

```txt
Эффект: секции вне вьюпорта (и не рядом с ним) не проходят
Layout/Paint вообще, пока не приблизятся к области видимости —
это не lazy-loading контента (DOM остаётся на месте, доступен
для поиска по Ctrl+F и SEO), а именно пропуск рендеринг-работы.
На страницах с сотнями секций разница в первичном рендере
и отзывчивости скролла — заметно ощутима.
```

`contain` (без `content-visibility`) — более тонкий, ручной инструмент: явно сообщает браузеру, что изменения ВНУТРИ элемента не должны требовать пересчёта layout/paint СНАРУЖИ него:

```css
.independent-widget {
  contain: layout paint; /* этот элемент — изолированный "контейнер":
    его внутренние изменения не заставляют браузер пересчитывать
    геометрию/перерисовывать что-либо за его границами */
}
```

Это сужает область пересчёта при layout thrashing внутри виджета до самого виджета, а не всего документа — полезно для сложных виджетов (data grid, canvas-обёртки, чат с частым обновлением сообщений), которые часто меняют внутреннюю разметку.

## `OffscreenCanvas` — когда DOM-анимация вообще перестаёт масштабироваться

Есть точка, после которой DOM/CSS-анимация физически не тот инструмент: тысячи независимо анимируемых частиц, сложная физическая симуляция, покадровый рендеринг, где каждый элемент — отдельный DOM-узел. Каждый DOM-узел несёт с собой оверхед (собственный composited layer при анимации, собственную запись в дереве стилей, собственный hit-testing) — и на масштабе в тысячи элементов этот оверхед начинает доминировать над самой полезной работой.

Сигнал переключиться — не "стало чуть медленнее", а качественный: если профилировщик показывает, что Style/Layout-время растёт линейно с количеством анимируемых DOM-узлов, а не с сложностью самой анимации, это архитектурная граница, а не повод для ещё одной оптимизации. `OffscreenCanvas` в этой точке даёт возможность делать растровый рендеринг (Canvas 2D/WebGL) в отдельном Worker-потоке, полностью в стороне от главного потока и DOM-дерева. Само рисование на Canvas/WebGL — тема отдельного топика [Canvas & Graphics]; здесь важно только распознать сам момент, когда DOM/CSS-анимация упирается в архитектурный потолок.

## Измерение в продакшене: Long Animation Frames и INP

DevTools-профилирование работает на вашей машине, с вашей CPU/GPU и вашей сетью — реальные пользователи почти всегда на менее мощном железе. Для продакшен-мониторинга нужны API, которые сообщают о проблемах с реальных устройств.

**Long Animation Frames API (LoAF)** — более детальный преемник Long Tasks API специально для проблем, связанных с рендерингом:

```javascript
new PerformanceObserver((list) => {
  for (const entry of list.getEntries()) {
    console.log({
      duration: entry.duration,               // общая длительность "тяжёлого" кадра
      renderStart: entry.renderStart,          // когда начался рендеринг внутри кадра
      styleAndLayoutStart: entry.styleAndLayoutStart,
      scripts: entry.scripts.map((s) => ({     // КАКОЙ именно скрипт виноват
        name: s.name,
        duration: s.duration,
        invoker: s.invoker,                    // например, конкретный event listener или rAF-колбэк
      })),
    });
  }
}).observe({ type: 'long-animation-frame', buffered: true });
```

В отличие от обычного Long Tasks API (который просто сообщает "что-то заняло больше 50 мс"), LoAF разбивает "тяжёлый" кадр на фазы (сколько ушло на скрипт, сколько на Style/Layout) и указывает конкретный виновный скрипт — на реальных пользовательских устройствах это даёт то же самое, что stack trace в Performance-панели, но без необходимости воспроизводить проблему локально.

**INP (Interaction to Next Paint)** — метрика Core Web Vitals, измеряющая задержку между действием пользователя (клик, тап, нажатие клавиши) и моментом, когда браузер физически показывает следующий обновлённый кадр в ответ. Это прямая связка с темой этой статьи: если rAF-колбэк или JS-анимация занимает главный поток дольше frame budget (статья 01) в момент, когда пользователь взаимодействует со страницей, ответный кадр (например, визуальный "нажатие" кнопки) откладывается — и это напрямую ухудшает INP, точно так же, как влияет на воспринимаемую плавность самой анимации. Для команд, уже оптимизирующих LCP/CLS, важно понимать: тяжёлая, плохо спланированная анимация — не только "эстетическая" проблема, а измеримый, влияющий на SEO и продуктовые метрики фактор через тот же Web Vitals отчёт.

## Типичные ошибки на интервью

- **Не знать, как выглядит "forced reflow" в DevTools** — не суметь описать, что Performance-панель явно помечает такие случаи фиолетовым блоком с предупреждением и даёт stack trace до конкретной строки кода.

- **Путать paint flashing с FPS meter** — не различать инструменты по назначению: paint flashing показывает, КАКИЕ ОБЛАСТИ перерисовываются, FPS meter — только агрегированную частоту кадров, без локализации причины.

- **Не знать про `{ passive: true }`** — не понимать, что нон-пассивный scroll/touch-листенер заставляет браузер синхронно ждать завершения JS-обработчика перед тем, как визуально закоммитить сам скролл — то есть это не про "чуть быстрее выполнится JS", а про блокировку самого скролла.

- **Не знать `content-visibility`** — предлагать виртуализацию списка (react-window и подобное) как единственное решение проблемы длинных страниц, не зная о более простой CSS-альтернативе для случаев, когда контент не может быть виртуализирован (например, обычный длинный документ, не список одинаковых элементов).

- **Считать, что DevTools Performance-панель на локальной машине репрезентативна для продакшена** — не знать про Long Animation Frames API/`PerformanceObserver` как способ получать те же данные с реальных пользовательских устройств.

- **Не связывать анимацию с INP** — воспринимать плохую производительность анимации исключительно как "визуальную" проблему, не понимая, что она напрямую бьёт по измеримой Core Web Vitals метрике и, соответственно, по SEO/продуктовым показателям.

- **Не знать, когда DOM/CSS-анимация физически перестаёт масштабироваться** — пытаться оптимизировать тысячи анимируемых DOM-узлов точечными фиксами вместо распознавания архитектурного потолка и перехода на Canvas/WebGL.
