# Rendering Pipeline и Frame Budget

## Почему без этого не бывает "профессиональной" анимации

Разработчик, который умеет писать `transition: all 0.3s ease` и на этом останавливается, работает вслепую: он не может объяснить, почему одна анимация плавная, а другая — дёргается на слабом Android-телефоне, и чинит проблему методом тыка ("добавлю `will-change`, вдруг поможет"). Senior-разработчик понимает, что происходит между тем, как вы поменяли CSS-свойство, и тем, как пиксели появились на экране — потому что именно в этом промежутке рождается и умирает производительность.

Все следующие статьи этой темы — про то, *какой инструмент выбрать* (CSS transition, WAAPI, rAF, GSAP) и *как его использовать*. Эта статья — про то, что происходит физически внутри браузера в ответ на любой из этих инструментов. Без неё выбор между `top` и `transform` выглядит как суеверие ("говорят, transform быстрее"), а не инженерное решение.

## Путь одного кадра: Style → Layout → Paint → Composite

Браузер не "перерисовывает страницу" одним действием. Он проводит каждое изменение через конвейер из нескольких стадий, и то, **с какой стадии этот конвейер запускается**, определяет стоимость кадра.

```txt
┌──────────┐   ┌──────────┐   ┌─────────────┐   ┌───────────┐
│ Style    │──>│ Layout   │──>│ Paint       │──>│ Composite │──> пиксели на экране
│ (recalc) │   │ (reflow) │   │ (rasterize) │   │ (слои)    │
└──────────┘   └──────────┘   └─────────────┘   └───────────┘
```

**1. Style (recalculation)** — браузер вычисляет, какие CSS-правила применяются к каждому DOM-узлу, и разрешает итоговые computed-значения (каскад, наследование, специфичность). Результат — "computed style" для каждого элемента. Происходит почти всегда, когда меняется хоть что-то, влияющее на селекторы или свойства элемента.

**2. Layout (он же reflow)** — браузер вычисляет геометрию: точные размеры и координаты каждого элемента на странице. Это дорогая стадия, потому что она **каскадная** — элемент не существует в вакууме: изменение ширины одного `div` может сдвинуть все элементы после него, а если это flex- или grid-контейнер, пересчитать геометрию всех детей. В худшем случае layout затрагивает весь документ.

**3. Paint (rasterization)** — браузер закрашивает пиксели для каждого элемента: заливка фона, текст, тени, границы, изображения. Технически это происходит не на один "холст", а на набор слоёв (layers) — про них ниже. Paint дешевле layout, но всё ещё недёшев: закрасить `box-shadow` с большим blur-радиусом на весь экран — заметная нагрузка на CPU/GPU.

**4. Composite** — браузер собирает уже отрисованные слои в финальное изображение кадра, применяя к ним трансформации, opacity и порядок наложения. Эта стадия — единственная, которая может выполняться **без участия Style/Layout/Paint вообще**, если меняется только то, что затрагивает исключительно композитинг.

Ключевой факт, который объясняет всю статью: **чем раньше начинается конвейер, тем он дороже**. Изменение, которое запускает весь путь с Layout, всегда дороже изменения, которое запускает путь только с Composite — даже если визуальный результат кажется похожим.

```txt
Дорогой путь (меняем width):
  Style → Layout → Paint → Composite   (все 4 стадии)

Дешёвый путь (меняем transform):
  Composite                             (только 1 стадия)
```

## Главный и композиторный потоки: кто что делает

У браузера (в частности, у Chromium, на примере которого проще всего объяснять современную архитектуру) есть минимум два потока, важных для анимации:

```txt
┌─────────────────────────────────────────────────────┐
│                     Main Thread                     │
│   JS выполнение · Style · Layout · Paint (генерация │
│   display list) · обработчики событий · rAF-колбэки │
└──────────────────────────┬──────────────────────────┘
                           │ передаёт слои + display list
                           ▼
┌──────────────────────────────────────────────────────────┐
│                    Compositor Thread                     │
│   Растеризация тайлов (часто на GPU через отдельные      │
│   raster-потоки) · сборка слоёв · transform/opacity-     │
│   анимации · скролл · пересылка кадра в GPU на отрисовку │
└──────────────────────────────────────────────────────────┘
```

Главный поток — это тот же поток, где выполняется весь ваш JavaScript, где React делает reconciliation, где срабатывают обработчики событий. Он **один**, и он последовательный: пока главный поток занят долгой синхронной JS-задачей, он не может посчитать Style/Layout/Paint для следующего кадра — и не может обработать клик пользователя.

Компоузитор-поток — отдельный, более лёгкий поток (в Chromium часть работы дополнительно уходит на GPU-процесс). Он умеет самостоятельно, **без обращения к главному потоку**, анимировать уже готовые слои: сдвигать их (`transform`), менять прозрачность (`opacity`), масштабировать. Именно поэтому такие анимации не спотыкаются, даже если главный поток в этот момент занят тяжёлым JS — например, React рендерит большое дерево компонентов, а CSS-анимация на `transform` продолжает идти гладко, потому что она физически исполняется в другом потоке.

Это и есть ответ на вопрос "как вообще анимация может быть *не заблокирована* тяжёлым JS?" — она блокируется, только если требует пересчёта на главном потоке (Style/Layout/Paint). Если анимация чисто композиторная — она независима от главного потока почти полностью (за вычетом редких случаев, когда компоузитору всё же нужно что-то синхронно спросить у главного, например main-thread hit-testing для некоторых scroll-сценариев).

## Frame budget: 16.7 мс — это не круглое число ради красоты

Дисплей с частотой обновления 60 Гц показывает 60 кадров в секунду. Значит, у браузера есть:

```txt
1000 мс / 60 = 16.666... мс  на весь кадр
```

Внутри этого бюджета браузеру нужно успеть: выполнить JS (если есть), Style, Layout, Paint, Composite, растеризацию, и физически передать кадр на дисплей. На практике для комфортной 60 fps-анимации реалистичный бюджет для *вашего* кода — скорее 8-10 мс, потому что остальное съедают браузерные внутренние стадии и системные накладные расходы.

На 120 Гц-дисплеях (флагманские телефоны, часть ноутбуков и мониторов) бюджет вдвое жёстче:

```txt
1000 мс / 120 = 8.33... мс на кадр
```

Это не теоретическая деталь: анимация, которая выглядела гладкой на 60 Гц-мониторе разработчика, может начать заметно проседать на 120 Гц-телефоне тестировщика — не потому что она стала "тяжелее", а потому что бюджет на кадр сократился вдвое, а стоимость вашего JS осталась прежней.

**Jank — это физически пропущенный кадр.** Если браузер не успел подготовить новый кадр к моменту, когда дисплей готов его показать, дисплей повторно показывает предыдущий кадр (или показывает "рваный" кадр, если vsync не синхронизирован). Глаз воспринимает это как рывок, заминку, "неровность" движения — потому что вместо равномерной последовательности позиций (шаг за 16.7 мс) объект внезапно "прыгает" на позицию, которая соответствует двум шагам сразу.

```txt
Плавно (60 fps, каждый кадр успевает):
  кадр 1 →  кадр 2 →  кадр 3 →  кадр 4   (позиции: 0, 4, 8, 12px)

Джанк (кадр 3 пропущен, потому что не успел подготовиться):
  кадр 1 →  кадр 2 →  [пропуск]  →  кадр 4   (позиции: 0, 4,  —,  12px)
  Глаз видит скачок с 4px сразу на 12px за то же время,
  которое раньше занимали два равномерных шага.
```

## Почему transform и opacity дешёвые, а top/left/width/height — дорогие

Это САМЫЙ частый вопрос про анимацию на собеседованиях, и ответ должен опираться именно на конвейер выше, а не быть заученной фразой.

| Меняемое свойство | Какие стадии запускает | Почему |
|---|---|---|
| `width`, `height`, `top`, `left`, `margin`, `padding`, `font-size` | Style → **Layout** → Paint → Composite | Меняют геометрию элемента → браузер обязан пересчитать позиции и размеры (возможно, каскадно для соседей и детей) |
| `background-color`, `box-shadow`, `border-color`, `outline` | Style → Paint → Composite | Геометрия не меняется, но пиксели нужно перекрасить заново |
| `transform`, `opacity` | **Composite** (иногда только это) | Не меняют ни геометрию, ни то, "как выглядит" уже отрисованный контент — только то, как готовый слой накладывается и позиционируется на экране |

`transform: translateX(100px)` визуально выглядит идентично `left: 100px` для простого случая — но с точки зрения браузера это два разных мира. `left` говорит "элемент теперь физически занимает другое место в потоке документа" — это требует layout, потому что соседние элементы могут зависеть от новой позиции (хотя для `position: absolute`/`fixed` элементов out-of-flow влияние на соседей нет, но сам layout всё равно пересчитывается для самого элемента). `transform` говорит "нарисуй уже готовый слой этого элемента в другом месте экрана" — геометрия в документе не изменилась вообще, элемент просто визуально сдвинут поверх уже посчитанного layout.

То же с `opacity` против, скажем, анимации через `background-color` с прозрачностью или через class toggle, который меняет `display`: `opacity` меняет только альфа-канал уже растеризованного слоя при композитинге, без повторного paint.

```css
/* ❌ Дорого: каждый кадр анимации — Layout + Paint + Composite */
.dropdown {
  transition: top 0.2s ease, left 0.2s ease;
  position: absolute;
}
.dropdown.open {
  top: 40px;
  left: 0;
}

/* ✅ Дёшево: каждый кадр анимации — только Composite */
.dropdown {
  transition: transform 0.2s ease;
  position: absolute;
  top: 40px;
  left: 0;
  transform: translateY(-8px) scale(0.98);
  opacity: 0;
}
.dropdown.open {
  transform: translateY(0) scale(1);
  opacity: 1;
}
```

Практическое правило: **если можете выразить анимацию через `transform` и `opacity` — выражайте через них**. Это не догма "top — плохо, transform — хорошо" в отрыве от контекста, это прямое следствие того, какие стадии конвейера запускает каждое свойство.

## Layout thrashing: когда JS сам форсирует лишний reflow

Браузер по умолчанию **отложенный (lazy)**: если вы меняете `style.width` несколько раз подряд в JS, браузер не обязан пересчитывать layout после каждого изменения — он может накопить изменения и посчитать layout один раз, перед следующим кадром. Это называется *batching*.

Проблема в том, что некоторые JS-свойства **читают** геометрию (`offsetHeight`, `offsetWidth`, `getBoundingClientRect()`, `scrollTop`, `clientWidth` и десяток похожих). Чтобы вернуть корректное значение, браузер обязан отдать вам **актуальную** геометрию — а значит, если перед чтением были невыполненные изменения стилей, он вынужден немедленно, синхронно посчитать layout прямо сейчас, а не откладывать до следующего кадра. Это называется **forced synchronous layout** (форсированный синхронный reflow).

Опасность — не в одном таком чтении, а в **чередовании записи и чтения в цикле**: каждая итерация ломает batching и форсирует полный пересчёт layout заново.

```javascript
// ❌ Layout thrashing: чтение и запись чередуются в цикле —
// каждая итерация форсирует синхронный reflow
function resizeItemsToMatch(items, referenceHeight) {
  items.forEach((item) => {
    const currentHeight = item.offsetHeight; // ЧТЕНИЕ → форсирует layout,
                                              // если до этого была запись
    item.style.height = `${currentHeight + referenceHeight}px`; // ЗАПИСЬ →
                                              // инвалидирует layout
  });
  // При 100 элементах — до 100 полных синхронных reflow за один вызов.
  // В DevTools Performance это видно как повторяющиеся "Layout"
  // с пометкой "Forced reflow" рядом с этим кодом.
}
```

```javascript
// ✅ Фикс: разделяем фазу чтения и фазу записи —
// batching браузера работает нормально
function resizeItemsToMatch(items, referenceHeight) {
  // Фаза 1: читаем ВСЁ, что нужно, до единственного reflow
  const heights = items.map((item) => item.offsetHeight);

  // Фаза 2: пишем ВСЁ — запись не читает геометрию, reflow не форсируется
  items.forEach((item, i) => {
    item.style.height = `${heights[i] + referenceHeight}px`;
  });
  // Один reflow (максимум) на весь вызов вместо N.
}
```

Правило простое и хорошо запоминается: **сначала прочитай всё, что нужно, потом запиши всё, что нужно** — не чередуй read/write в цикле. Библиотеки вроде FastDOM автоматизируют это разделение, но понимать механизм важнее, чем помнить про конкретную библиотеку.

## GPU-слои: как элемент получает свой собственный слой и что это стоит

Чтобы `transform`/`opacity`-анимация была дешёвой (только Composite), элемент должен быть **промотирован в отдельный composited layer** — растеризован один раз в отдельную текстуру, которую GPU может свободно двигать, масштабировать и менять её прозрачность без повторного paint.

Браузер создаёт отдельный слой для элемента по ряду триггеров:

```txt
- 3D-трансформации: transform: translateZ(0), translate3d(...)
- CSS-свойство will-change: transform / opacity / ...
- <video>, <canvas>, <iframe>
- элементы с CSS-фильтром (filter), которые анимируются
- position: fixed / sticky в некоторых случаях (зависит от движка)
- элемент с активной CSS-анимацией/переходом по transform или opacity
- элемент с opacity < 1, если у него есть composited-потомки (в ряде случаев)
```

Слой — не бесплатный. Каждый composited layer — это отдельная текстура в GPU-памяти:

```txt
Память на слой ≈ ширина_px × высота_px × 4 байта (RGBA)

Пример: элемент 1920×1080 (полноэкранный) →
  1920 × 1080 × 4 ≈ 8.3 МБ на ОДИН слой

10 таких слоёв на странице → ~83 МБ только на текстуры слоёв,
не считая остальной GPU-памяти приложения
```

На десктопе с дискретной GPU 83 МБ незаметны. На бюджетном Android-телефоне с общей (unified) памятью между CPU и GPU — это заметный кусок бюджета, и при накоплении множества слоёв браузер начинает: заметно больше тратить на upload текстур в GPU, чаще упираться в лимиты памяти видеодрайвера, и в критичных случаях — принудительно "схлопывать" (squash) слои обратно, что бьёт по производительности ещё сильнее, чем если бы слоёв не было вовсе.

### Почему "просто добавь `will-change` везде" — антипаттерн

`will-change: transform` — это подсказка браузеру "готовься, этот элемент скоро будет анимироваться, промоутируй его в слой заранее". Проблема в том, что промоушен в слой стоит памяти и стоит времени на создание текстуры **сразу**, а не в момент анимации:

```css
/* ❌ Антипаттерн: will-change на статичный набор элементов "на всякий случай" */
.card {
  will-change: transform;
  /* каждая из 200 карточек на странице теперь занимает
     свой GPU-слой — даже если реально анимируются 2 из них */
}
```

```css
/* ✅ Правильно: will-change добавляется непосредственно перед
   анимацией и снимается сразу после её завершения */
.card--about-to-animate {
  will-change: transform;
}
```

```javascript
// ✅ Практический паттерн управления will-change из JS
function animateCard(card) {
  card.style.willChange = 'transform';
  card.addEventListener(
    'transitionend',
    () => { card.style.willChange = 'auto'; }, // снимаем слой после анимации
    { once: true },
  );
  card.style.transform = 'translateY(-8px)';
}
```

Это называется **layer explosion**: избыточное количество composited-слоёв, каждый из которых понемногу тратит память и время на composite-стадию, а в сумме — деградирует производительность именно там, где `will-change` должен был её улучшить. Диагностика такой проблемы — тема статьи [Performance Debugging and Jank Hunting], где разбирается Layers-панель DevTools; здесь важно унести правило: **`will-change` — это точечный, временный инструмент, а не универсальная "оптимизация по умолчанию"**.

## Типичные ошибки на интервью

- **"transform быстрее, потому что это GPU"** — неточный ответ. Правильная формулировка: `transform`/`opacity` дешевле, потому что они пропускают стадии Style-recalc-с-layout-эффектом, Layout и Paint, обрабатываясь только на композитинге — а не потому что "GPU быстрее CPU" в общем смысле. `box-shadow` тоже может рендериться на GPU, но всё равно требует Paint.

- **Путать Layout и Paint** — говорить "перекраска" (repaint) там, где на самом деле произошёл reflow (layout), и наоборот. Это разные стадии с разной стоимостью, и в DevTools Performance они показаны отдельными полосами.

- **Не знать про forced synchronous layout** — не суметь объяснить, почему цикл с чередованием `element.offsetHeight` и `element.style.x = ...` работает на порядок медленнее, чем тот же код с разделёнными фазами чтения/записи.

- **Считать `will-change` "бесплатной оптимизацией"** — не понимать, что это резервирование GPU-памяти под слой, и что развешивание `will-change` на много элементов "про запас" может УХУДШИТЬ производительность (layer explosion), а не улучшить.

- **Не знать про 120 Гц-бюджет** — предполагать, что 16.7 мс — универсальная константа, и не учитывать, что современные флагманские устройства требуют укладываться в 8.3 мс на кадр.

- **Путать main thread и compositor thread** — говорить "JS блокирует всю анимацию", не уточняя, что это верно только для анимаций, требующих Style/Layout/Paint на главном потоке; чисто композиторные `transform`/`opacity`-анимации продолжают идти плавно, даже когда главный поток занят тяжёлым синхронным JS.
