# Библиотеки анимации и экосистема

## Зачем библиотека, если есть CSS, WAAPI и rAF

Статьи 01-04 дают полный набор нативных примитивов, и для одиночной анимации одного элемента их достаточно. Библиотеки решают не "как анимировать один div", а три задачи, которые нативными средствами приходится собирать руками и легко собрать неправильно:

```txt
1. ОРКЕСТРАЦИЯ множества независимых элементов: timeline с точной
   синхронизацией (этот элемент стартует за 0.2с ДО конца предыдущего),
   stagger по десяткам элементов с управляемым паттерном распределения
2. СЛОЖНАЯ scroll-хореография: закрепление секции (pin) во время
   скролла, синхронизация прогресса анимации со скоростью скролла
   (scrub), множественные триггеры на одной странице — то, что
   нативный ScrollTimeline (статья 03) физически не умеет (он не
   умеет "приклеивать" элемент к вьюпорту во время скролла)
3. Интеграция с ЖИЗНЕННЫМ ЦИКЛОМ фреймворка: React размонтирует DOM
   синхронно — у exit-анимации в чистом React нет времени, чтобы
   доиграть, если не решить эту проблему на уровне библиотеки
```

Правило выбора здесь простое и должно оставаться дефолтом: **нативный инструмент — первый кандидат всегда**; библиотека оправдана, когда конкретная задача попадает в один из трёх пунктов выше, а не потому что "так привычнее" или "у всех в резюме есть GSAP".

## GSAP: индустриальный стандарт для scroll-хореографии

GSAP (GreenSock Animation Platform) — самая долгоживущая и предсказуемая по производительности JS-анимационная библиотека, стандарт де-факто на агентских/брендовых сайтах, где нужна кинематографичная scroll-хореография.

### Tween — базовая единица

```javascript
import gsap from 'gsap';

gsap.to('.hero-title', {
  x: 100,
  opacity: 1,
  duration: 0.8,
  ease: 'power3.out', // собственная библиотека easing-кривых GSAP
});

gsap.from('.card', { y: 40, opacity: 0, duration: 0.5 }); // "от" текущего значения к заданному
gsap.fromTo('.badge', { scale: 0 }, { scale: 1, duration: 0.4 }); // явные обе точки
```

### Timeline — оркестрация с точным позиционированием

```javascript
const tl = gsap.timeline({ defaults: { duration: 0.5, ease: 'power2.out' } });

tl.to('.logo', { opacity: 1, y: 0 })
  .to('.nav-item', { opacity: 1, stagger: 0.08 }, '-=0.2') // начать за 0.2с ДО конца предыдущего твина
  .to('.hero-title', { opacity: 1 }, 'reveal')              // именованная метка на текущей позиции
  .to('.hero-subtitle', { opacity: 1 }, 'reveal+=0.1');      // относительно метки 'reveal'
```

Позиционные параметры (`'-=0.2'`, именованные метки, `'<'`/`'>'` для "вместе с предыдущим"/"после предыдущего") — то, что превращает набор разрозненных твинов в единую хореографию, где легко перестроить тайминг всей последовательности, поменяв один параметр, вместо пересчёта абсолютных задержек вручную.

### Stagger — не просто "равномерная задержка"

```javascript
gsap.to('.grid-item', {
  opacity: 1,
  y: 0,
  stagger: {
    each: 0.05,
    from: 'center',   // волна расходится от центра сетки, а не слева направо
    grid: 'auto',      // GSAP сам определяет сетку по DOM-раскладке
  },
});
```

`stagger` в GSAP — не просто «i-й элемент стартует на i × delay позже», а полноценная система распределения (от центра, от края, случайно, по сетке с учётом расстояния) — то, что руками на `setTimeout` в цикле воспроизвести можно, но кода будет на порядок больше и он будет хрупче.

### ScrollTrigger: то, что нативный ScrollTimeline не умеет

```javascript
import { ScrollTrigger } from 'gsap/ScrollTrigger';
gsap.registerPlugin(ScrollTrigger);

gsap.to('.pinned-section .content', {
  xPercent: -100 * (sections.length - 1), // горизонтальная прокрутка карточек
  ease: 'none',
  scrollTrigger: {
    trigger: '.pinned-section',
    pin: true,           // ЗАКРЕПЛЯЕТ секцию во вьюпорте на время скролла — этого нет в нативном API
    scrub: 1,             // прогресс анимации ПРИВЯЗАН к скроллу, со сглаживанием в 1с
    end: () => `+=${sections.length * window.innerHeight}`,
    markers: process.env.NODE_ENV === 'development', // визуальные метки триггеров при отладке
  },
});
```

Ключевое отличие от `animation-timeline: scroll()`/`view()` (статья 03): нативный scroll-driven timeline даёт scroll-linked прогресс для одиночного элемента, но не умеет **закреплять (pin)** элемент во вьюпорте, растягивая логический "скролл секции" на несколько экранов реальной высоты страницы. Именно pin + scrub — механика, лежащая в основе большинства "сайтов-историй" (сложные лендинги, где секция остаётся на месте, пока проигрывается многошаговая анимация) — и на момент написания это остаётся территорией GSAP, а не нативного CSS.

### Лицензия

Исторически часть плагинов GSAP (включая ScrollTrigger, SplitText, MorphSVG) требовала платной подписки Club GreenSock для коммерческого использования. После приобретения GreenSock компанией Webflow вся платформа GSAP, включая все ранее платные плагины, стала бесплатной и доступна под MIT-подобной лицензией. Перед использованием в коммерческом проекте стоит свериться с актуальными условиями на официальном сайте — ситуации с лицензированием библиотек меняются, и это ровно тот тип решения, который нужно перепроверять, а не полагаться на память.

## Motion (Framer Motion): декларативный слой для React

Motion (ранее известный как Framer Motion) — не обёртка над GSAP, а собственный движок, построенный на WAAPI и spring-физике (статья 04), интегрированный в модель React-компонентов.

### Декларативные пропсы вместо императивных вызовов

```tsx
import { motion } from 'motion/react';

function Card() {
  return (
    <motion.div
      initial={{ opacity: 0, y: 20 }}
      animate={{ opacity: 1, y: 0 }}
      whileHover={{ scale: 1.03 }}
      whileTap={{ scale: 0.97 }}
      transition={{ type: 'spring', stiffness: 300, damping: 24 }}
    >
      Content
    </motion.div>
  );
}
```

`initial`/`animate` — не события, а **состояния**: React перерисовывает компонент, `animate` меняется на новый объект — Motion сам вычисляет диффф и анимирует изменившиеся значения. Это ложится на модель React естественно: анимация описывается как функция состояния, а не как последовательность императивных вызовов.

### `layout` prop: FLIP из статьи 04, но автоматический

```tsx
<motion.div layout className="list-item">
  {item.label}
</motion.div>
```

Один атрибут `layout` заставляет Motion автоматически выполнить FLIP-последовательность (First → Last → Invert → Play, статья 04) вокруг ЛЮБОГО изменения геометрии элемента между рендерами — реордер списка, изменение размера родителя, смена CSS-класса, влияющего на layout. Библиотека сама снимает `getBoundingClientRect()` до и после коммита React, и анимирует разницу через `transform`, даже если фактическое CSS-свойство, спровоцировавшее сдвиг, — layout-triggering (например, `flex-direction` или `grid-template-columns`).

### `AnimatePresence`: решает ровно ту проблему, которую React создаёт сам

React размонтирует DOM-узел **синхронно**, в момент, когда условие в JSX перестаёт быть истинным — у CSS/JS-анимации этого узла физически нет времени доиграть, потому что узла уже нет в дереве:

```tsx
// ❌ Без AnimatePresence — при isOpen: false узел удаляется МГНОВЕННО,
// exit-анимация просто не успевает начаться
{isOpen && <div className="modal">...</div>}
```

```tsx
// ✅ AnimatePresence откладывает фактическое размонтирование до
// завершения exit-анимации
import { AnimatePresence, motion } from 'motion/react';

<AnimatePresence>
  {isOpen && (
    <motion.div
      className="modal"
      initial={{ opacity: 0, scale: 0.95 }}
      animate={{ opacity: 1, scale: 1 }}
      exit={{ opacity: 0, scale: 0.95 }}
    >
      ...
    </motion.div>
  )}
</AnimatePresence>
```

Механика: `AnimatePresence` перехватывает момент, когда React "хочет" убрать дочерний элемент, удерживает его в DOM ещё на кадр, проигрывает `exit`-анимацию (используя `Animation.finished`-подобный механизм из статьи 03 под капотом) и удаляет узел из DOM только по-настоящему после её завершения. Это единственная причина, по которой в экосистеме React вообще существует надёжный способ анимировать уход элемента — без библиотеки пришлось бы вручную городить двухфазное состояние (`isOpen` + `isRendered` с задержкой снятия).

### Variants и оркестрация без ручных задержек

```tsx
const container = {
  hidden: { opacity: 1 },
  visible: { opacity: 1, transition: { staggerChildren: 0.08 } },
};
const item = {
  hidden: { opacity: 0, y: 10 },
  visible: { opacity: 1, y: 0 },
};

<motion.ul variants={container} initial="hidden" animate="visible">
  {items.map((it) => (
    <motion.li key={it.id} variants={item}>{it.label}</motion.li>
  ))}
</motion.ul>
```

Родитель распространяет именованное состояние (`"visible"`) на всех детей с `variants`, и `staggerChildren` на родителе автоматически распределяет задержки между ними — эквивалент GSAP-stagger, но выраженный через React-дерево компонентов, а не через селектор DOM-узлов.

## Motion One / "мини"-движок: когда важен каждый килобайт

Motion как проект сегодня объединяет два слоя: полноценный React-интегрированный API (описанный выше) и лёгкое ванильное ядро (исторически известное как Motion One), построенное напрямую поверх WAAPI без React-специфичного оверхеда:

```javascript
import { animate, stagger } from 'motion';

animate('.card', { opacity: [0, 1], y: [20, 0] }, { delay: stagger(0.05) });

animate(
  '.progress-bar',
  { transform: ['scaleX(0)', 'scaleX(1)'] },
  { duration: 0.6, easing: 'ease-out' },
);
```

Синтаксис почти дословно повторяет `element.animate()` из WAAPI (статья 03), с добавленными удобствами (селекторы строкой вместо ручного `querySelectorAll` + цикла, встроенный `stagger()`). Это осознанный выбор для проектов вне React (или где React есть, но полноразмерный Motion избыточен): минимальный бандл, максимальное использование нативного движка браузера, компоузиторное исполнение там, где оно доступно.

## Lottie + bodymovin: когда аниматор работает в After Effects

Lottie решает задачу, для которой CSS/JS-анимация в принципе не инструмент: сложная векторная motion-графика, спроектированная дизайнером-аниматором в Adobe After Effects (персонажная анимация, детализированные onboarding-иллюстрации, брендированные лоадеры) — код "переписать это руками в CSS keyframes" стоил бы недели и результат всё равно разошёлся бы с оригиналом дизайнера.

Механика: плагин **bodymovin** экспортирует таймлайн After Effects в JSON, описывающий векторные слои, keyframes, маски, шейпы — не растровое видео и не GIF, а полноценные векторные данные. **lottie-web** (и порты для React Native, iOS, Android, Flutter) воспроизводит этот JSON нативно в браузере:

```javascript
import lottie from 'lottie-web';

const animation = lottie.loadAnimation({
  container: document.querySelector('.onboarding-illustration'),
  renderer: 'svg', // 'svg' | 'canvas' | 'html' — выбор рендерера влияет на производительность
  loop: true,
  autoplay: true,
  path: '/animations/onboarding-hero.json',
});

animation.setSpeed(1.5);
animation.playSegments([30, 90], true); // проиграть только конкретный диапазон кадров
```

### Профиль производительности и подводные камни

```txt
Плюсы:
  - Векторная графика — масштабируется без потери качества,
    файл кардинально меньше сравнимого видео/GIF
  - Точное соответствие дизайну аниматора — не "апроксимация
    силами фронтенд-разработчика", а прямой экспорт оригинала
  - Программный контроль (setSpeed, playSegments, direction) —
    то, чего у видео/GIF нет вообще

Подводные камни:
  - JSON может быть тяжёлым для сложных сцен (сотни KB —
    единицы MB) — нужен lazy-load и НЕ грузить его в критическом
    рендер-пути
  - Рендерер имеет значение: 'svg' лучше масштабируется, но
    дороже для сложных сцен с множеством слоёв; 'canvas'
    производительнее для сложной графики, но растеризован
    (теряет часть преимуществ вектора при масштабировании)
  - ЛЮБОЕ изменение анимации требует пересборки в After Effects
    и повторного экспорта — фронтенд не может "подправить пиксель"
  - Требует отдельного внимания к prefers-reduced-motion
    (статья 07) — Lottie не даёт этого "из коробки" бесплатно,
    нужно явно проверять и либо не запускать autoplay, либо
    показывать статичный кадр
```

Практическое правило: Lottie — инструмент для конкретной ситуации ("у нас есть аниматор, который работает в After Effects, и результат нужно доставить 1-в-1"), а не универсальная замена CSS/WAAPI для обычных UI-переходов — там, где обычную кнопку можно анимировать через `transform`/`opacity` за пару строк CSS, Lottie избыточен по весу и сложности интеграции.

## `@formkit/auto-animate`: дешёвая победа без дизайна анимации

Отдельная категория — библиотеки, не требующие вообще никакой настройки, дающие "прилично выглядящую" анимацию бесплатно:

```javascript
import autoAnimate from '@formkit/auto-animate';

const list = document.querySelector('.todo-list');
autoAnimate(list);
// Дальше ЛЮБОЕ добавление/удаление/переупорядочивание дочерних
// элементов .todo-list анимируется автоматически — без единой
// строчки конфигурации на каждый конкретный случай
```

Под капотом — эвристика на основе FLIP (статья 04) и `MutationObserver`, отслеживающая изменения дочерних узлов контейнера. Это не замена GSAP/Motion для продуманной, брендированной анимации — это инструмент для мест, где анимация вообще не была бы сделана без него ("руки не дошли", "не наш приоритет"), но лёгкая плавность явно лучше резких скачков layout. Библиотека весит около 2 КБ и не требует API поверх существующего рендеринга списков.

## Честный фреймворк выбора

```txt
1. МОЖНО через CSS/WAAPI?
   → Да: используйте CSS/WAAPI (статьи 01-03). Это база
     в 90% реальных UI-анимаций, и она бесплатна по весу
     и по производительности (компоузитор).

2. НУЖНА сложная scroll-хореография (pin, scrub, множественные
   секции, "сайт-история")?
   → GSAP + ScrollTrigger — индустриальный стандарт именно
     для этого класса задач, альтернатив сравнимой зрелости нет.

3. React-приложение, и нужны layout-анимации / exit-анимации /
   декларативная оркестрация, завязанная на состояние компонентов?
   → Motion (Framer Motion) — единственный вариант, решающий
     AnimatePresence-проблему на уровне фреймворка, а не вручную.

4. Нужна лёгкая программная анимация без React и без scroll-
   хореографии, критичен размер бандла?
   → Motion "мини"-ядро (Motion One) — тонкая обёртка над WAAPI.

5. Дизайнер-аниматор поставляет анимацию из After Effects?
   → Lottie — единственный практичный путь доставить её 1-в-1,
     без ручной перерисовки в CSS/JS.

6. Списки/тогглы, где анимация не была бы сделана вообще?
   → auto-animate — минимальная цена входа, ноль конфигурации.
```

Размер бандла и лицензия — это не второстепенные детали, а реальные критерии выбора на production-проекте:

```txt
Ориентировочные размеры (min+gzip, порядок величины, не точные цифры —
проверяйте актуальные на bundlephobia перед решением):
  auto-animate        ~2 KB
  Motion "мини"-ядро   ~5-18 KB (зависит от используемых фич)
  Framer Motion (полный) ~30-50 KB (значительная часть tree-shakable)
  GSAP core            ~20-25 KB (+ плагины по необходимости, например ScrollTrigger)
  lottie-web            ~50-100+ KB (плюс вес самого JSON-файла анимации)
```

На лендинге с одной hero-анимацией разница в 40 КБ не критична. В мобильном PWA с бюджетом на JS в несколько сотен килобайт — критична, и это ровно тот случай, где "мы всегда ставим GSAP по умолчанию" превращается в необоснованное решение, а не инженерное.

## Типичные ошибки на интервью

- **"GSAP всегда лучше нативного CSS, потому что это профессиональный инструмент"** — не суметь объяснить, ЧТО именно GSAP даёт сверх нативных средств (timeline-оркестрация, ScrollTrigger pin/scrub) — а не то, что он "быстрее" или "плавнее" сам по себе; для одиночной transform-анимации выигрыша в производительности над CSS/WAAPI у GSAP нет.

- **Не знать разницы между нативным `animation-timeline: scroll()`/`view()` и GSAP ScrollTrigger** — не понимать, что нативный scroll-driven timeline не умеет закреплять (pin) элемент во вьюпорте, растягивая скролл на несколько экранов, а ScrollTrigger умеет — это и есть причина, по которой сложная scroll-хореография всё ещё требует библиотеки.

- **Не понимать, ЗАЧЕМ существует `AnimatePresence`** — не суметь объяснить, что React размонтирует DOM синхронно, и без механизма отложенного удаления у exit-анимации физически нет времени доиграть.

- **Считать Lottie заменой SVG/CSS-анимации "для всего"** — не видеть, что Lottie оправдан конкретно для сложной, дизайнерской, покадровой motion-графики из After Effects, а для обычных UI-переходов кнопок/карточек это избыточный и более тяжёлый путь.

- **Не учитывать размер бандла как критерий выбора** — предлагать GSAP или полный Framer Motion для одной простой fade-in анимации на лендинге без осознания веса, который это добавляет в критический путь загрузки.

- **Не знать о смене лицензии GSAP** — опираться на устаревшую информацию "ScrollTrigger платный", не проверив актуальные условия — хороший маркер того, что кандидат следит за экосистемой, а не воспроизводит заученный факт многолетней давности.
