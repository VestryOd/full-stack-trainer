# Библиотеки анимации и экосистема

## Зачем библиотека, если есть CSS, WAAPI и rAF

Статьи 01-04 дают полный набор нативных примитивов: CSS, WAAPI (Web Animations API) и `requestAnimationFrame`, для краткости rAF. Для одиночной анимации одного элемента их достаточно. Библиотеки решают не "как анимировать один div", а три задачи, которые нативными средствами приходится собирать руками и легко собрать неправильно:

```txt
1. Оркестрация множества независимых элементов: timeline с
   точной синхронизацией (этот элемент стартует за 0.2с до
   конца предыдущего), stagger по десяткам элементов с
   управляемым паттерном распределения
2. Сложная scroll-хореография: закрепление секции (pin) во
   время скролла, синхронизация прогресса анимации со
   скоростью скролла (scrub), множественные триггеры на одной
   странице. Нативный ScrollTimeline (статья 03) физически
   этого не умеет: он не умеет "приклеивать" элемент к
   вьюпорту во время скролла
3. Интеграция с жизненным циклом фреймворка: React размонтирует
   DOM синхронно, поэтому у exit-анимации в чистом React нет
   времени доиграть, если не решить эту проблему на уровне
   библиотеки
```

Правило выбора здесь простое, и оно должно оставаться дефолтом. **Нативный инструмент — всегда первый кандидат.** Библиотека оправдана, когда задача попадает в один из трёх пунктов выше. А не потому что "так привычнее" или "у всех в резюме есть GSAP".

## GSAP: индустриальный стандарт для scroll-хореографии

GSAP (GreenSock Animation Platform) — самая долгоживущая JS-анимационная библиотека и самая предсказуемая по производительности. Это стандарт де-факто на агентских и брендовых сайтах, где нужна кинематографичная scroll-хореография.

### Tween — базовая единица

```javascript
import gsap from 'gsap';

gsap.to('.hero-title', {
  x: 100,
  opacity: 1,
  duration: 0.8,
  ease: 'power3.out', // собственная библиотека easing-кривых GSAP
});

// "от" текущего значения к заданному
gsap.from('.card', { y: 40, opacity: 0, duration: 0.5 });

// явные обе точки
gsap.fromTo('.badge', { scale: 0 }, { scale: 1, duration: 0.4 });
```

### Timeline — оркестрация с точным позиционированием

```javascript
const tl = gsap.timeline({ defaults: { duration: 0.5, ease: 'power2.out' } });

tl.to('.logo', { opacity: 1, y: 0 })
  // начать за 0.2с до конца предыдущего твина
  .to('.nav-item', { opacity: 1, stagger: 0.08 }, '-=0.2')
  // 'reveal' — именованная метка на текущей позиции
  .to('.hero-title', { opacity: 1 }, 'reveal')
  // позиция задана относительно метки 'reveal'
  .to('.hero-subtitle', { opacity: 1 }, 'reveal+=0.1');
```

Позиционные параметры превращают набор разрозненных твинов в единую хореографию. Их три: `'-=0.2'`, именованные метки и `'<'`/`'>'`. Последняя пара означает "вместе с предыдущим" и "после предыдущего". С ними тайминг всей последовательности перестраивается сменой одного параметра, а не пересчётом абсолютных задержек вручную.

### Stagger — не просто "равномерная задержка"

```javascript
gsap.to('.grid-item', {
  opacity: 1,
  y: 0,
  stagger: {
    each: 0.05,
    // волна расходится от центра сетки, а не слева направо
    from: 'center',
    // GSAP сам определяет сетку по DOM-раскладке
    grid: 'auto',
  },
});
```

`stagger` в GSAP — не просто «i-й элемент стартует на i × delay позже». Это полноценная система распределения: от центра, от края, случайно, по сетке с учётом расстояния. Руками на `setTimeout` в цикле это воспроизвести можно. Но кода будет на порядок больше, и он будет хрупче.

### ScrollTrigger: то, что нативный ScrollTimeline не умеет

```javascript
import { ScrollTrigger } from 'gsap/ScrollTrigger';
gsap.registerPlugin(ScrollTrigger);

gsap.to('.pinned-section .content', {
  xPercent: -100 * (sections.length - 1), // горизонтальная прокрутка карточек
  ease: 'none',
  scrollTrigger: {
    trigger: '.pinned-section',
    // закрепляет секцию во вьюпорте на время скролла —
    // этого нет в нативном API
    pin: true,
    // прогресс анимации привязан к скроллу, сглаживание 1с
    scrub: 1,
    end: () => `+=${sections.length * window.innerHeight}`,
    // визуальные метки триггеров при отладке
    markers: process.env.NODE_ENV === 'development',
  },
});
```

Ключевое отличие от `animation-timeline: scroll()`/`view()` (статья 03) вот в чём. Нативный scroll-driven timeline даёт scroll-linked прогресс для одиночного элемента. Но он не умеет **закреплять (pin)** элемент во вьюпорте, растягивая логический "скролл секции" на несколько экранов реальной высоты страницы.

Именно pin плюс scrub — механика, лежащая в основе большинства "сайтов-историй". Это сложные лендинги, где секция остаётся на месте, пока проигрывается многошаговая анимация. И на момент написания это остаётся территорией GSAP, а не нативного CSS.

### Лицензия

| Период | ScrollTrigger, SplitText, MorphSVG |
|---|---|
| До покупки Webflow | Платно: подписка Club GreenSock для коммерческого использования |
| После покупки | Бесплатно, вместе со всей остальной платформой |

Исторически часть плагинов GSAP требовала платной подписки Club GreenSock для коммерческого использования. Среди них были ScrollTrigger, SplitText и MorphSVG. Затем Webflow приобрёл GreenSock, и вся платформа GSAP стала бесплатной, включая все ранее платные плагины. Новые условия близки к MIT (короткая разрешительная лицензия с правом коммерческого использования).

Перед использованием в коммерческом проекте сверьтесь с актуальными условиями на официальном сайте. Ситуации с лицензированием библиотек меняются, поэтому такой факт нужно перепроверять, а не вспоминать.

## Motion (Framer Motion): декларативный слой для React

Motion (ранее известный как Framer Motion) — не обёртка над GSAP. Это собственный движок, построенный на WAAPI и spring-физике (статья 04) и интегрированный в модель React-компонентов.

### Декларативные пропсы вместо императивных вызовов

```tsx
import { motion } from 'motion/react';

function Card() {
  return (
    <motion.div
      initial={{ opacity: 0, y: 20 }}
      animate={{ opacity: 1, y: 0 }}
      whileHover={{ scale: 1.03 }}
      whileTap={{ scale: 0.97 }}
      transition={{ type: 'spring', stiffness: 300, damping: 24 }}
    >
      Content
    </motion.div>
  );
}
```

`initial`/`animate` — не события, а **состояния**. React перерисовывает компонент, `animate` меняется на новый объект, а Motion сам вычисляет дифф и анимирует изменившиеся значения. Это ложится на модель React естественно: анимация описывается как функция состояния, а не как последовательность императивных вызовов.

### `layout` prop: FLIP из статьи 04, но автоматический

```tsx
<motion.div layout className="list-item">
  {item.label}
</motion.div>
```

Один атрибут `layout` заставляет Motion выполнить FLIP-последовательность (First → Last → Invert → Play, статья 04) автоматически. И делает это вокруг **любого** изменения геометрии элемента между рендерами: реордер списка, изменение размера родителя, смена CSS-класса, влияющего на layout.

Библиотека сама снимает `getBoundingClientRect()` до и после коммита React, а затем анимирует разницу через `transform`. Это работает даже если CSS-свойство, спровоцировавшее сдвиг, — layout-triggering, например `flex-direction` или `grid-template-columns`.

### `AnimatePresence`: решает ровно ту проблему, которую React создаёт сам

React размонтирует DOM-узел (document object model, дерево объектов страницы в браузере) **синхронно**. Это происходит в момент, когда условие в JSX (HTML-подобный синтаксис разметки внутри React-компонентов) перестаёт быть истинным. У CSS- или JS-анимации этого узла физически нет времени доиграть, потому что узла уже нет в дереве:

```tsx
// ❌ Без AnimatePresence — при isOpen: false узел удаляется МГНОВЕННО,
// exit-анимация просто не успевает начаться
{isOpen && <div className="modal">...</div>}
```

```tsx
// ✅ AnimatePresence откладывает фактическое размонтирование до
// завершения exit-анимации
import { AnimatePresence, motion } from 'motion/react';

<AnimatePresence>
  {isOpen && (
    <motion.div
      className="modal"
      initial={{ opacity: 0, scale: 0.95 }}
      animate={{ opacity: 1, scale: 1 }}
      exit={{ opacity: 0, scale: 0.95 }}
    >
      ...
    </motion.div>
  )}
</AnimatePresence>
```

Механика простая. `AnimatePresence` перехватывает момент, когда React "хочет" убрать дочерний элемент, и ещё на один кадр удерживает его в DOM. Затем проигрывает `exit`-анимацию, используя `Animation.finished`-подобный механизм из статьи 03 под капотом. И только после её завершения по-настоящему удаляет узел.

Это единственная причина, по которой в экосистеме React вообще есть надёжный способ анимировать уход элемента. Без библиотеки двухфазное состояние приходилось бы собирать вручную: `isOpen` плюс `isRendered` с задержкой снятия.

### Variants и оркестрация без ручных задержек

```tsx
const container = {
  hidden: { opacity: 1 },
  visible: { opacity: 1, transition: { staggerChildren: 0.08 } },
};
const item = {
  hidden: { opacity: 0, y: 10 },
  visible: { opacity: 1, y: 0 },
};

<motion.ul variants={container} initial="hidden" animate="visible">
  {items.map((it) => (
    <motion.li key={it.id} variants={item}>{it.label}</motion.li>
  ))}
</motion.ul>
```

Родитель распространяет именованное состояние (`"visible"`) на всех детей с `variants`. А `staggerChildren` на родителе автоматически распределяет задержки между ними. Это эквивалент GSAP-stagger, но выраженный через React-дерево компонентов, а не через селектор DOM-узлов.

## Motion One / "мини"-движок: когда важен каждый килобайт

Motion как проект сегодня объединяет два слоя. Первый — полноценный React-интегрированный API, описанный выше. Второй — лёгкое ванильное ядро, исторически известное как Motion One, построенное напрямую поверх WAAPI без React-специфичного оверхеда:

```javascript
import { animate, stagger } from 'motion';

animate('.card', { opacity: [0, 1], y: [20, 0] }, { delay: stagger(0.05) });

animate(
  '.progress-bar',
  { transform: ['scaleX(0)', 'scaleX(1)'] },
  { duration: 0.6, easing: 'ease-out' },
);
```

Синтаксис почти дословно повторяет `element.animate()` из WAAPI (статья 03), с добавленными удобствами. Селекторы задаются строкой вместо ручного `querySelectorAll` и цикла, а `stagger()` встроен.

Это осознанный выбор для проектов вне React, и для проектов, где React есть, но полноразмерный Motion избыточен. Вы получаете минимальный бандл, максимальное использование нативного движка браузера и компоузиторное исполнение там, где оно доступно.

## Lottie + bodymovin: когда аниматор работает в After Effects

Lottie решает задачу, для которой CSS- и JS-анимация в принципе не инструмент. Это сложная векторная motion-графика, спроектированная дизайнером-аниматором в Adobe After Effects: персонажная анимация, детализированные onboarding-иллюстрации, брендированные лоадеры. Переписать такое руками в CSS keyframes стоило бы недели, и результат всё равно разошёлся бы с оригиналом дизайнера.

Механика: плагин **bodymovin** экспортирует таймлайн After Effects в JSON, описывающий векторные слои, keyframes, маски и шейпы. Это полноценные векторные данные, а не растровое видео и не GIF (graphics interchange format). Библиотека **lottie-web**, а также порты для React Native, iOS, Android и Flutter, воспроизводит этот JSON нативно в браузере:

```javascript
import lottie from 'lottie-web';

const animation = lottie.loadAnimation({
  container: document.querySelector('.onboarding-illustration'),
  // 'svg' | 'canvas' | 'html' — выбор рендерера влияет
  // на производительность
  renderer: 'svg',
  loop: true,
  autoplay: true,
  path: '/animations/onboarding-hero.json',
});

animation.setSpeed(1.5);
animation.playSegments([30, 90], true); // проиграть только конкретный диапазон кадров
```

### Профиль производительности и подводные камни

```txt
Плюсы:
  - Векторная графика — масштабируется без потери качества,
    файл кардинально меньше сравнимого видео/GIF
  - Точное соответствие дизайну аниматора — не "аппроксимация
    силами фронтенд-разработчика", а прямой экспорт оригинала
  - Программный контроль (setSpeed, playSegments, direction) —
    то, чего у видео/GIF нет вообще

Подводные камни:
  - JSON может быть тяжёлым для сложных сцен (сотни KB —
    единицы MB) — нужен lazy-load, и грузить его в критическом
    рендер-пути нельзя
  - Рендерер имеет значение: 'svg' лучше масштабируется, но
    дороже для сложных сцен с множеством слоёв; 'canvas'
    производительнее для сложной графики, но растеризован
    (теряет часть преимуществ вектора при масштабировании)
  - Любое изменение анимации требует пересборки в After Effects
    и повторного экспорта — фронтенд не может "подправить
    один пиксель"
  - Требует отдельного внимания к prefers-reduced-motion
    (статья 07) — Lottie не даёт этого "из коробки" бесплатно,
    нужно явно проверять и либо не запускать autoplay, либо
    показывать статичный кадр
```

Практическое правило: Lottie — инструмент для одной конкретной ситуации. Эта ситуация — "у нас есть аниматор, который работает в After Effects, и результат нужно доставить 1-в-1". Это не универсальная замена CSS или WAAPI для обычных интерфейсных переходов. Обычную кнопку можно анимировать через `transform`/`opacity` за пару строк CSS, и там Lottie избыточен по весу и по сложности интеграции.

## `@formkit/auto-animate`: дешёвая победа без дизайна анимации

Отдельная категория — библиотеки, не требующие вообще никакой настройки, дающие "прилично выглядящую" анимацию бесплатно:

```javascript
import autoAnimate from '@formkit/auto-animate';

const list = document.querySelector('.todo-list');
autoAnimate(list);
// Дальше любое добавление, удаление или переупорядочивание дочерних
// элементов .todo-list анимируется автоматически — без единой
// строчки конфигурации на каждый конкретный случай
```

Под капотом — эвристика на основе FLIP (статья 04) и `MutationObserver`, отслеживающая изменения дочерних узлов контейнера.

Это не замена GSAP или Motion для продуманной, брендированной анимации. Это инструмент для мест, где анимация вообще не была бы сделана: "руки не дошли", "не наш приоритет". Там лёгкая плавность явно лучше резких скачков layout. Библиотека весит около 2 КБ (килобайта) и не требует API поверх существующего рендеринга списков.

## Честный фреймворк выбора

```txt
1. Можно ли через CSS или WAAPI?
   → Да: используйте CSS/WAAPI (статьи 01-03). Это база
     в 90% реальных интерфейсных анимаций, и она бесплатна
     по весу и по производительности (компоузитор).

2. Нужна сложная scroll-хореография (pin, scrub, множественные
   секции, "сайт-история")?
   → GSAP + ScrollTrigger — индустриальный стандарт именно
     для этого класса задач, альтернатив сравнимой зрелости нет.

3. React-приложение, и нужны layout-анимации / exit-анимации /
   декларативная оркестрация, завязанная на состояние компонентов?
   → Motion (Framer Motion) — единственный вариант, решающий
     AnimatePresence-проблему на уровне фреймворка, а не вручную.

4. Нужна лёгкая программная анимация без React и без scroll-
   хореографии, критичен размер бандла?
   → Motion "мини"-ядро (Motion One) — тонкая обёртка над WAAPI.

5. Дизайнер-аниматор поставляет анимацию из After Effects?
   → Lottie — единственный практичный путь доставить её 1-в-1,
     без ручной перерисовки в CSS/JS.

6. Списки/тогглы, где анимация не была бы сделана вообще?
   → auto-animate — минимальная цена входа, ноль конфигурации.
```

Размер бандла и лицензия — это не второстепенные детали, а реальные критерии выбора на production-проекте:

```txt
Ориентировочные размеры (min+gzip, порядок величины, не точные
цифры — проверяйте актуальные на bundlephobia перед решением):

  auto-animate           ~2 KB
  Motion "мини"-ядро     ~5-18 KB
                         зависит от используемых фич
  Framer Motion (полный) ~30-50 KB
                         значительная часть tree-shakable
  GSAP core              ~20-25 KB
                         плюс плагины, например ScrollTrigger
  lottie-web             ~50-100+ KB
                         плюс вес самого JSON-файла анимации
```

На лендинге с одной hero-анимацией разница в 40 КБ не критична. В мобильном PWA (progressive web app, веб-приложение с офлайн-возможностями) с бюджетом на JS в несколько сотен килобайт — критична. Это ровно тот случай, где "мы всегда ставим GSAP по умолчанию" превращается из инженерного решения в необоснованное.

## Типичные ошибки на интервью

- **"GSAP всегда лучше нативного CSS, потому что это профессиональный инструмент".** Не суметь объяснить, **что** именно GSAP даёт сверх нативных средств: timeline-оркестрацию, pin и scrub у ScrollTrigger. Сам по себе он не "быстрее" и не "плавнее". Для одиночной transform-анимации выигрыша в производительности над CSS или WAAPI у GSAP нет.

- **Не знать разницы между нативным `animation-timeline: scroll()`/`view()` и GSAP ScrollTrigger.** Нативный scroll-driven timeline не умеет закреплять (pin) элемент во вьюпорте, растягивая скролл на несколько экранов. ScrollTrigger умеет. Это и есть причина, по которой сложная scroll-хореография всё ещё требует библиотеки.

- **Не понимать, **зачем** существует `AnimatePresence`.** Не суметь объяснить, что React размонтирует DOM синхронно. Без механизма отложенного удаления у exit-анимации физически нет времени доиграть.

- **Считать Lottie заменой SVG (scalable vector graphics) и CSS-анимации "для всего".** Lottie оправдан конкретно для сложной, дизайнерской, покадровой motion-графики из After Effects. Для обычных переходов кнопок и карточек это избыточный и более тяжёлый путь.

- **Не учитывать размер бандла как критерий выбора.** Предлагать GSAP или полный Framer Motion для одной простой fade-in анимации на лендинге. Это игнорирует вес, который добавляется в критический путь загрузки.

- **Не знать о смене лицензии GSAP.** Опираться на устаревшую информацию "ScrollTrigger платный", не проверив актуальные условия. Здесь и видно, следит ли кандидат за экосистемой или воспроизводит заученный факт многолетней давности.
