# Fiber и Reconciliation

## Проблема, которую решает Fiber

До React 16 React использовал **stack reconciler** — единую рекурсивную функцию, которая синхронно обходила всё дерево компонентов. Однажды запущенная, она не могла быть прервана.

```txt
STACK RECONCILER (React < 16)

  reconcile(rootComponent)
    → reconcile(Header)
    → reconcile(Nav)
    → reconcile(Main)
        → reconcile(Sidebar)
        → reconcile(Content)
            → reconcile(ArticleList)
                → reconcile(Article) × 50  ← нельзя прервать
    → reconcile(Footer)

  Суммарное время: столько, сколько нужно на обход дерева.
  В это время: главный поток заблокирован.
  Браузер не может: обрабатывать ввод пользователя,
  запускать анимации, рисовать кадры.
  Результат: подвисание на больших деревьях
  и на медленных рендерах.
```

Фундаментальное ограничение: JavaScript однопоточен. Рекурсивный стек вызовов нельзя поставить на паузу — нужно дать ему завершиться. Если обход большого дерева занимал 150 мс, интерфейс зависал на 150 мс.

Fiber переписывает reconciler из рекурсивного алгоритма в **итеративный с явной очередью задач**, так что React может ставить работу на паузу, возобновлять её и расставлять приоритеты.

## Что такое узел Fiber

Fiber — объект JavaScript, представляющий единицу работы: один экземпляр компонента, один элемент DOM, один текстовый узел. DOM — это Document Object Model, дерево объектов, по которому браузер рисует страницу. Всё дерево компонентов зеркально отражается как дерево Fiber-узлов.

```ts
// Упрощено — реальный FiberNode имеет ~25 полей
type Fiber = {
  // Идентичность
  tag: number;             // FunctionComponent=0, ClassComponent=1, HostComponent=5...
  type: Function | string; // функция компонента, или 'div', 'span' и т.д.
  key: string | null;

  // Структура дерева — Fiber использует связную структуру, не массив
  return: Fiber | null;    // родитель
  child: Fiber | null;     // первый дочерний
  sibling: Fiber | null;   // следующий сиблинг

  // Состояние
  memoizedState: any;      // связный список хуков (useState, useEffect, ...)
  memoizedProps: any;      // props из последнего рендера

  // Работа
  pendingProps: any;       // props для предстоящего рендера
  flags: number;           // битовая маска: Placement | Update | Deletion | ...
  lanes: Lanes;            // приоритет ожидающей работы (см. ниже)

  // Двойная буферизация
  alternate: Fiber | null; // «другая» версия этого fiber (current ↔ work-in-progress)
};
```

### Дерево — это на самом деле связная структура

React не обходит массив дерева — он идёт по указателям: `child` для углубления, `sibling` для перехода вправо, `return` для подъёма. Поэтому обход можно прервать на любом Fiber-узле и возобновить позже, не держа открытым стек вызовов.

```txt
УКАЗАТЕЛИ, КОТОРЫЕ ХРАНИТ КАЖДЫЙ УЗЕЛ FIBER

  App      .child   → Header
  Header   .sibling → Nav
  Nav      .sibling → Main
  Main     .child   → Sidebar
  Sidebar  .sibling → Content

  Ещё каждый узел хранит .return — указатель обратно на родителя.

  Обход в глубину: идём по .child; если его нет — по .sibling;
  если и его нет — по .return, а дальше по .sibling родителя.
```

## Двойная буферизация — current и work-in-progress деревья

В любой момент React поддерживает два дерева:

```txt
CURRENT TREE                       WORK-IN-PROGRESS TREE
(что показано на экране)           (считается в фазе рендера)

  App ─────────────── alternate ──── App'
  │                                   │
  Header ──────────── alternate ──── Header'
  │                                   │
  Main ────────────── alternate ──── Main'
```

Во время фазы рендера React строит дерево work-in-progress, клонируя и обновляя Fiber-узлы. Дерево current он не трогает — браузер всё ещё показывает именно его. Когда фаза рендера завершается, React **атомарно переключает** дерево work-in-progress, делая его новым current. Старое дерево current становится новым пулом work-in-progress: его узлы переиспользуются для следующего рендера.

Вот почему фазу рендера безопасно прерывать и перезапускать: дерево current — то, что видит пользователь — во время reconciliation не меняется. Меняется только дерево work-in-progress.

## Lanes — система приоритетов

React 18 ввёл **Lanes** — систему битовых масок, присваивающую приоритет каждой единице работы. Несколько обновлений могут быть запланированы с разными приоритетами и обрабатываться по порядку приоритетности.

```ts
// Упрощённые значения lanes (реальные — битовые маски)
const SyncLane            = 0b0000000000000000000000000000001; // высший: ввод пользователя
const InputContinuousLane = 0b0000000000000000000000000000100; // drag, scroll
const DefaultLane         = 0b0000000000000000000000000010000; // обычный setState
const TransitionLane      = 0b0000000000000000001000000000000; // useTransition
const IdleLane            = 0b0100000000000000000000000000000; // низший: фоновая работа
```

```txt
ПОРЯДОК ПРИОРИТЕТОВ (высший → низший):
  SyncLane              ← onClick, onKeyDown
                          (результат нужен пользователю сразу)
  InputContinuousLane   ← onMouseMove, onScroll (нужна отзывчивость)
  DefaultLane           ← обычный setState в обработчиках событий
  TransitionLane        ← startTransition (может быть прерван)
  IdleLane              ← фоновый префетч, невидимая работа
```

Когда два обновления ожидают обработки, React берёт более приоритетное первым. Допустим, идёт низкоприоритетный рендер — transition, — и приходит высокоприоритетное обновление, например нажатие клавиши. React **прерывает** transition-рендер и синхронно обрабатывает нажатие. Затем он возобновляет transition с того места, где остановился, или перезапускает его, если нажатие изменило входные данные.

```tsx
// Без startTransition:
// DefaultLane: результаты поиска обновляются в том же батче,
// что и набор текста, поэтому большой список блокирует поле ввода.
setQuery(input);

// С startTransition:
startTransition(() => {
  setQuery(input);      // TransitionLane — может быть прерван новыми нажатиями клавиш
});
setInputValue(input);   // DefaultLane — поле ввода обновляется немедленно
```

## Алгоритм reconciliation — правила диффа

Когда фаза рендера создаёт новое дерево React-элементов, React сравнивает его с существующим Fiber-деревом, чтобы понять, что изменилось. У этого сравнения явные эвристики: это не обобщённый алгоритм диффа деревьев, который был бы O(n³).

### Правило 1: элементы разных типов создают разные деревья

```tsx
// До:
<div><Counter /></div>

// После:
<span><Counter /></span>

// div → span: разный тип → React размонтирует всё поддерево div
// (включая Counter и всё его состояние), затем монтирует свежее поддерево span.
// Состояние Counter ПОТЕРЯНО.
```

Именно поэтому изменение типа элемента-обёртки уничтожает состояние дочерних компонентов — даже если дети выглядят идентично.

### Правило 2: тот же тип → обновление на месте

```tsx
// До:
<input type="text" className="old" value="hello" />

// После:
<input type="text" className="new" value="world" />

// Тот же тип (input) → React обновляет только изменившиеся атрибуты
// на существующем DOM-узле. DOM-узел переиспользуется.
```

Для типов компонентов: та же функция/класс → React ре-рендерит существующий экземпляр компонента, сохраняя его состояние.

### Правило 3: ключи управляют идентичностью в списках

Без ключей React сопоставляет элементы списка по **позиции**:

```tsx
// До: ['Alice', 'Bob', 'Charlie']
<li>Alice</li>   // позиция 0
<li>Bob</li>     // позиция 1
<li>Charlie</li> // позиция 2

// После: ['Dave', 'Alice', 'Bob', 'Charlie'] (Dave добавлен в начало)
<li>Dave</li>    // позиция 0 ← React думает, что это всё ещё узел "Alice" → обновляет текст
<li>Alice</li>   // позиция 1 ← React думает, что это "Bob" → обновляет текст
<li>Bob</li>     // позиция 2 ← всё ещё "Charlie" → обновляет текст
<li>Charlie</li> // позиция 3 ← новый узел → монтирует
```

Результат: 3 обновления DOM + 1 монтирование, хотя достаточно было бы одного монтирования. Хуже того: если у элементов есть состояние (чекбоксы, поля ввода), это состояние привязано к позиции, а не к данным.

С ключами React сопоставляет по **идентичности**:

```tsx
<li key="alice">Alice</li>
<li key="bob">Bob</li>
<li key="charlie">Charlie</li>

// После: Dave добавлен в начало
<li key="dave">Dave</li>    // новый ключ → монтирует
<li key="alice">Alice</li>  // тот же ключ → берёт готовый DOM-узел
<li key="bob">Bob</li>      // тот же ключ → переиспользует
<li key="charlie">Charlie</li> // тот же ключ → переиспользует
```

Результат: 1 монтирование, 0 обновлений — оптимально.

## Почему индекс в роли ключа ломает списки

Для алгоритма диффа индекс массива в роли ключа (`key={index}`) равносилен полному отсутствию ключей: позиция *и есть* идентичность. Проблемы начинаются, когда порядок списка меняется — при сортировке, фильтрации или добавлении в начало:

```tsx
// Элементы: [{ id: 1, text: 'Купить молоко' }, { id: 2, text: 'Купить яйца' }]
<li key={0}><input defaultValue="Купить молоко" /></li>   // индекс 0
<li key={1}><input defaultValue="Купить яйца" /></li>     // индекс 1

// После удаления элемента 1:
// Элементы: [{ id: 2, text: 'Купить яйца' }]
<li key={0}><input defaultValue="Купить яйца" /></li>     // индекс 0

// React видит: key=0 существует до и после → ТОТ ЖЕ компонент → обновляет на месте.
// Но значение DOM инпута — "Купить молоко" (пользователь мог что-то ввести).
// React обновляет только атрибут `defaultValue` (неконтролируемый инпут),
// поэтому инпут всё ещё показывает "Купить молоко", хотя должен показывать "Купить яйца".
// Идентичность ключа была неверной — переиспользован неправильный DOM-узел.
```

**Безопасные случаи использования индекса как ключа:**
- Список статический: его никогда не переупорядочивают, не фильтруют и не дополняют в начало
- У элементов нет локального состояния: ни полей ввода, ни чекбоксов, ни анимаций
- Список только отображает данные, и элементы никогда не удаляются из середины

Если хотя бы одно из этих условий не выполняется — используйте стабильный уникальный ID из данных.

## Проп key — намеренный механизм сброса

Из того, что ключи управляют идентичностью компонентов, следует мощный паттерн: `key` можно использовать, чтобы принудительно перемонтировать компонент с нуля.

```tsx
// Проблема: EditForm кеширует состояние черновика. При изменении userId
// нужна свежая форма — не старый черновик.

// ❌ Требует ручного useEffect для сброса:
function EditForm({ userId }: { userId: string }) {
  const [draft, setDraft] = useState('');
  useEffect(() => {
    setDraft(''); // сбрасываем при изменении userId
  }, [userId]);
  return <input value={draft} onChange={e => setDraft(e.target.value)} />;
}

// ✅ key сообщает React, что это другой экземпляр компонента:
function Page({ userId }: { userId: string }) {
  return <EditForm key={userId} userId={userId} />;
  // При изменении userId React размонтирует старый EditForm и монтирует новый.
  // Состояние автоматически свежее — useEffect не нужен.
}
```

Это идиоматический React — использование собственных правил reconciler для явного выражения намерения.

## Time slicing — что это значит на практике

Time slicing (нарезка работы по времени) — это умение **разбивать фазу рендера на маленькие порции**. Между порциями React возвращает управление браузеру, чтобы тот успевал обрабатывать события ввода и рисовать кадры.

```txt
БЕЗ TIME SLICING (синхронный рендеринг):
  ─────────────────────────────────────────────────────────▶ время
  [     долгий рендер (100мс)     ][paint][input handler][paint]
        ↑ браузер заблокирован на 100мс во время этого рендера

С TIME SLICING (конкурентный рендеринг):
  ─────────────────────────────────────────────────────────▶ время
  [5мс рендер][ввод][5мс рендер][paint][5мс рендер][paint]
              ↑ браузер получает управление каждые ~5 мс
```

React использует планировщик, который после обработки каждого Fiber-узла проверяет, сколько времени прошло. Если бюджет кадра (~5 мс) исчерпан, React уступает управление браузеру и возобновляет рендер в следующей задаче планировщика.

Нарезка по времени применяется только к **прерываемым рендерам** — тем обновлениям, что запланированы через `startTransition` или с `TransitionLane`. Синхронные обновления (пользовательский ввод, `flushSync`) не прерываются никогда.

Результат для пользователей: большой медленный список, который рендерится в фоне, больше не замораживает поле ввода. Поисковая строка остаётся отзывчивой, потому что React прерывает рендер списка при каждом новом нажатии клавиши.

## Фаза коммита — порядок эффектов

После того как фаза рендера достроила дерево work-in-progress, фаза коммита выполняется в трёх подфазах и всегда синхронно:

```txt
BEFORE MUTATION
  → getSnapshotBeforeUpdate (только для классовых компонентов)
  → Чтение из DOM до мутаций (например, позиция скролла)

MUTATION
  → Применить все DOM-вставки, обновления, удаления
  → ref.current устанавливается в null для удалённых узлов

LAYOUT
  → cleanup useLayoutEffect (из предыдущего рендера)
  → setup useLayoutEffect (из этого рендера)
  → ref.current устанавливается на новый DOM-узел
  → вызовы setState здесь синхронны (батчатся в этот commit)

[Браузер рисует здесь]

PASSIVE (запланировано асинхронно, после paint)
  → cleanup useEffect (из предыдущего рендера)
  → setup useEffect (из этого рендера)
```

Различие важно. Код в `useLayoutEffect` запускается до отрисовки браузером, поэтому может читать геометрию элементов (layout). Если он вызывает `setState`, получившийся ре-рендер применяется синхронно до отрисовки, и мерцания нет.

Код в `useEffect` запускается уже после отрисовки. Он не может синхронно отменить визуальное обновление, но и не задерживает картинку для пользователя.

## Типичные ловушки на интервью

**«Что такое virtual DOM и как он связан с Fiber?»**
«Virtual DOM» — неформальное название дерева элементов, которое поддерживает reconciler React. Fiber — внутренняя структура данных, на которой этот reconciler реализован. Каждый Fiber-узел представляет один компонент или элемент.

То есть Fiber-дерево **и есть** то, что неформально называют «virtual DOM». Старое название появилось раньше Fiber и было точным в эпоху stack reconciler. Сегодня точнее говорить «Fiber-дерево».

**«Что делает React когда setState вызывается внутри useLayoutEffect?»**
`useLayoutEffect` запускается синхронно в подфазе layout внутри фазы коммита. Если внутри него вызывается `setState`, React планирует дополнительный синхронный рендер и применяет его до отрисовки браузером. Именно поэтому перепозиционирование тултипа через `useLayoutEffect` не даёт видимого мерцания: DOM обновляется дважды в одном кадре.

**«Почему удаление ключа вызывает перемонтирование компонентов?»**
Ключи управляют идентичностью Fiber. Если ключ есть в одном рендере и отсутствует в следующем (или наоборот), React считает элементы на этой позиции разными. Старый Fiber вместе со своим узлом DOM и состоянием компонента размонтируется, а на его место монтируется новый.

Отсюда требование: ключи должны быть стабильными и уникальными среди соседних элементов, и такими они должны оставаться всю жизнь списка.

**«Могут ли ключи дублироваться в списке?»**
Технически React не упадёт, но поведение не определено: он произвольно выберет один из дублей и отбросит другой. Одинаковые ключи среди соседних элементов — это баг. Правило ESLint `react/jsx-key` ловит отсутствующие ключи, но не дублирующиеся — для этого нужно `react/no-duplicate-key`.

**«Что такое lane в Fiber? Чем это отличается от приоритета?»**
Lane — это бит в 32-битной целочисленной битовой маске. Несколько обновлений могут находиться в разных lanes одновременно, и React умеет их батчить, разделять или перемежать.

До lanes (React < 18) React использовал простое целое число приоритета. Отслеживать он мог только один ожидающий уровень приоритета за раз. Если два обновления ждали с разными приоритетами, более высокое вытесняло более низкое, и низкоприоритетная работа могла не выполниться никогда. Lanes позволяют отслеживать множество параллельных обновлений и гарантируют, что низкоприоритетная работа в итоге всё же завершится.
