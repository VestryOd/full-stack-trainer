# JSX и конвейер рендеринга

## JSX — синтаксический сахар, но важно понимать, что именно он скрывает

JSX выглядит как HTML внутри JavaScript. Это точно, но неполно — за этим описанием скрыта механика, объясняющая почти каждое решение по производительности в React.

```tsx
// Что вы пишете
const element = <Button variant="primary" onClick={handleClick}>Сохранить</Button>;

// Что компилирует Babel/SWC
const element = React.createElement(
  Button,
  { variant: 'primary', onClick: handleClick },
  'Сохранить'
);

// React 17+ (новый JSX-трансформ) — импорт React не нужен:
import { jsx as _jsx } from 'react/jsx-runtime';
const element = _jsx(Button, {
  variant: 'primary', onClick: handleClick, children: 'Сохранить',
});
```

`React.createElement` (или `_jsx` нового JSX-трансформа) не создаёт узел DOM. DOM — это Document Object Model, дерево объектов, по которому браузер и рисует страницу. Вместо узла возвращается **обычный JavaScript-объект** — React element:

```ts
{
  $$typeof: Symbol(react.element),  // помечает объект как React-элемент (защита от XSS)
  type: Button,                      // строка для DOM-тегов, функция/класс для компонентов
  key: null,
  ref: null,
  props: { variant: 'primary', onClick: handleClick, children: 'Сохранить' },
}
```

Этот объект **иммутабельный** и **дёшевый в создании** — просто выделение `{}`. Реальная работа с DOM происходит намного позже, в отдельной фазе.

### Почему `$$typeof` — Symbol

`JSON.parse` не может породить Symbol. Если пользовательский JSON случайно попадёт в рендер (`{JSON.parse(userInput)}`), у него никогда не будет `$$typeof: Symbol(react.element)` — React отклонит его. Так закрывается один класс XSS-атак: те, что приходят через неосторожный рендеринг API-ответов. XSS — это cross-site scripting, когда атакующий протаскивает на вашу страницу свою разметку или свой скрипт.

## Две фазы каждого рендера: Render и Commit

Процесс рендеринга в React разбит на две принципиально разные фазы — фазу рендера (render phase) и фазу коммита (commit phase):

```txt
RENDER PHASE (чистая, прерываемая)
────────────────────────────────────
  1. React вызывает функцию вашего компонента с текущими props/state
  2. Компонент возвращает дерево React-элементов (обычных объектов)
  3. React запускает reconciler (алгоритм диффа Fiber)
  4. React вычисляет список нужных изменений DOM
  → DOM НЕ мутируется

COMMIT PHASE (нечистая, синхронная, непрерываемая)
────────────────────────────────────────────────────
  1. React применяет все DOM-мутации из шага 4
  2. Запускает layout effects:
       cleanup useLayoutEffect → callback useLayoutEffect
  3. Браузер рисует экран
  4. Запускает passive effects:
       cleanup useEffect → callback useEffect
```

Это разделение не деталь реализации — у него есть наблюдаемые последствия:

- Можно вызывать `setState` во время рендера (осторожно): в фазе рендера DOM ещё не тронут.
- `useLayoutEffect` срабатывает синхронно *после* изменений DOM, но *до* отрисовки браузером. Он задерживает отрисовку и поэтому годится для измерения геометрии элементов (layout).
- `useEffect` срабатывает *после* того, как браузер уже отрисовал экран. Это правильное место для подписок и невизуальных побочных эффектов.
- В StrictMode и в concurrent mode фазу рендера можно прервать, отбросить и запустить заново. Если в вашем рендере есть побочные эффекты, они выполнятся дважды. Фаза коммита не прерывается никогда.

## Что вызывает повторный рендер — полный список

```txt
ИСТОЧНИК → ЧТО ПРОИСХОДИТ
──────────────────────────────────────────────────
setState / useState setter
  → планирует повторный рендер компонента и его поддерева
useReducer dispatch
  → то же самое
Изменение значения Context
  → перерисовываются все потребители этого Context
Повторный рендер родителя
  → перерисовываются дети (если они не обёрнуты в memo)
forceUpdate (класс)
  → обходит shouldComponentUpdate, перерисовывает
```

Ключевое понимание: **повторный рендер — это не обновление DOM**. Повторный рендер означает «React снова вызвал вашу функцию компонента». Будет ли DOM обновлён — зависит целиком от того, найдёт ли reconciler различия.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  // Повторный рендер инициирован setCount.
  // Если count не изменился, React всё равно вызовет Counter() снова,
  // но после диффа не сделает никаких изменений в DOM.
  return <div>{count}</div>;
}
```

### Оптимизация «то же значение» (Object.is bail-out)

```tsx
const [count, setCount] = useState(0);
setCount(0); // count уже равен 0
```

React использует `Object.is` для сравнения нового значения состояния с текущим. Если они идентичны, React **может** пропустить ре-рендер — но только после первого пропуска, чтобы эффекты успели выполниться хотя бы раз. Поэтому запись в состояние той же ссылки на объект ре-рендер не вызывает, а запись нового объекта с той же структурой — вызывает:

```tsx
// Нет ре-рендера (та же ссылка):
setUser(user);

// Есть ре-рендер (новая ссылка, даже если структурно идентично):
setUser({ ...user });
```

## Почему обновления state батчатся — и что изменилось в React 18

Батчинг означает, что React собирает несколько вызовов `setState` из одного события и применяет их в одном проходе ре-рендера, вместо того чтобы перерисовывать после каждого вызова.

**До React 18** — батчинг работал только внутри обработчиков событий React:

```tsx
function handleClick() {
  setA(1); // нет ре-рендера
  setB(2); // нет ре-рендера
}        // → один ре-рендер с обоими обновлениями

// НЕ батчилось (до React 18):
setTimeout(() => {
  setA(1); // ре-рендер здесь
  setB(2); // ещё один ре-рендер
}, 0);
```

**React 18 — автоматический батчинг везде:**

```tsx
// Всё это теперь батчится в React 18:
setTimeout(() => { setA(1); setB(2); });
fetch('/api').then(() => { setA(1); setB(2); });
element.addEventListener('click', () => { setA(1); setB(2); });
```

Если нужно принудительное синхронное небатченное обновление (редко), `flushSync` из `react-dom` выходит из батчинга:

```tsx
import { flushSync } from 'react-dom';

flushSync(() => setA(1)); // DOM обновился здесь
flushSync(() => setB(2)); // DOM обновился ещё раз
```

**Почему батчинг важен:** два вызова `setState` → один вызов функции (вашего компонента) → один проход reconciliation → одно изменение DOM. Без батчинга: два вызова функции, два прохода, два изменения DOM. Для компонентов, где в одном обработчике меняется сразу много состояния, разница в производительности доходит до 2–10x.

## Функциональные обновления — правильный паттерн, когда новый state зависит от старого

```tsx
// Неправильно — захватывает устаревшее closure-значение count:
setCount(count + 1);
setCount(count + 1); // всё ещё использует то же устаревшее `count`

// Правильно — использует гарантированно актуальное значение:
setCount(c => c + 1);
setCount(c => c + 1); // каждый updater получает результат предыдущего
```

Функциональные обновления необходимы, когда вы вызываете `setState` несколько раз в одном батче и каждый вызов зависит от результата предыдущего. Также это безопасный паттерн внутри `useEffect` с пустым массивом зависимостей, когда эффект должен инкрементировать счётчик.

## StrictMode вызывает ваш компонент дважды — намеренно

В режиме разработки `<React.StrictMode>` специально делает **дважды** за каждый рендер сразу несколько вещей:

- Вызывает функцию вашего компонента.
- Вызывает инициализаторы состояния, переданные в `useState`.
- Вызывает редюсеры `useReducer`.
- Вызывает функции setup в `useEffect` — сначала setup, затем cleanup, затем setup снова.

```txt
ЧТО REACT ДЕЛАЕТ В STRICT MODE (только dev):
  1. Вызывает функцию компонента → сохраняет вывод
  2. Вызывает функцию компонента СНОВА → проверяет, что вывод тот же
  3. Если разный: выводит предупреждение

ЗАЧЕМ: проверяет, что ваш рендер — чистая функция от props + state.
       Рендер с побочными эффектами (мутация глобальной переменной,
       запись в DOM) будет вести себя непредсказуемо в concurrent
       mode, где React может отбросить рендер на полпути и
       перезапустить его.
```

Двойной вызов происходит **только в разработке**, не в production. Это исключительно инструмент проверки чистоты.

```tsx
let renderCount = 0;

function MyComponent() {
  renderCount++; // НЕПРАВИЛЬНО: мутирует внешнее состояние
  return <div>Отрендерено {renderCount} раз</div>;
}

// В StrictMode dev: рендерит "Отрендерено 2 раза", потом "4 раза" и т.д.
// В production:     рендерит "Отрендерено 1 раз", потом "2 раза" и т.д.
// Разница обнажает баг — renderCount не идемпотентен.
```

Двойной вызов `useEffect` (mount → cleanup → mount) добавили в React 18, чтобы проверять, что эффекты корректно убирают за собой. Классический сценарий, который это ловит:

```tsx
useEffect(() => {
  const sub = eventBus.subscribe(handler);
  // Если вы забыли cleanup:
  // return () => eventBus.unsubscribe(sub);
}, []);
// В StrictMode: subscribe вызывается дважды, unsubscribe — никогда.
// Вы увидите дублирующиеся обработчики событий в dev — баг обнаружен.
```

## Вывод рендера — это не HTML, а описание

Путаница между JSX и HTML — корень нескольких распространённых ошибок:

```tsx
// Это НЕ HTML-атрибуты. React маппит их на DOM-свойства:
<div className="box"        // className → element.className (не class)
     htmlFor="input-id"    // htmlFor → label.htmlFor (не for)
     onClick={handler}     // onClick → addEventListener('click', ...)
     style={{ color: 'red', fontSize: 16 }} // style — ОБЪЕКТ, не строка
/>

// React управляет системой событий (synthetic events):
// события всплывают через React-дерево, а не DOM-дерево.
// Важно для Portals (см. статью о паттернах).
```

Фрагменты (`<>...</>` или `<React.Fragment>`) нужны потому, что вызов `React.createElement` принимает один корневой аргумент. Вернуть несколько соседних элементов как отдельные корни нельзя. Fragment — это React-элемент с `type: Symbol(react.fragment)`, который reconciler умеет «разворачивать» без создания узла DOM.

## Типичные ловушки на интервью

**«Вызов setState немедленно перерисовывает компонент?»**
Нет. `setState` планирует ре-рендер. React батчит обновления и обрабатывает их асинхронно: в том же тике, но после того как отработает текущий синхронный код. Функция компонента вызывается снова в следующем проходе рендера, а не сразу по месту вызова.

**«JSX медленнее прямого вызова `React.createElement`?»**
Нет. JSX компилируется в `React.createElement` (или в новый JSX-трансформ) во время сборки. Накладных расходов во время выполнения нет: скомпилированный вывод идентичен.

**«Что React рендерит в React Native?»**
Не DOM. «Рендерер» заменяем:

- `react-dom` рендерит в браузерный DOM.
- `react-native` — в нативные элементы интерфейса (UI, user interface) мобильной платформы.
- `react-three-fiber` — в сцену Three.js.

Ядро React (reconciler, Fiber) при этом одно и то же.

**«Может ли фаза рендера иметь побочные эффекты?»**
Не должна. Фаза рендера обязана быть чистой функцией от props и state. В Concurrent Mode React может вызвать вашу функцию рендера несколько раз для одного коммита либо прервать и отбросить рендер на полпути. Поэтому побочные эффекты в рендере (подписки, мутации, таймеры) небезопасны: на один «логический» рендер они выполнятся ноль, один или несколько раз.

**«Зачем React использует Virtual DOM?»**
Формулировка немного неточная. Цель никогда не была в том, чтобы ускорить сами операции с DOM. Реальные изменения DOM выполняются один раз за коммит, и это уже максимально быстро.

Цель reconciler в другом — вычислить *минимальный* набор изменений DOM между рендерами. Тогда незатронутые узлы не трогаются вообще. Fiber-дерево — деталь реализации reconciler, а не «копия DOM».
