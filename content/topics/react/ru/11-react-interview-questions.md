# React — Вопросы для интервью (Senior)

## Группа 1: JSX, рендеринг и элементы

**Во что компилируется JSX и почему в старых версиях React должен быть в области видимости?**

JSX компилируется в обычные вызовы функций. JSX — это HTML-подобный синтаксис, на котором пишут компоненты React, и шаг сборки превращает каждый тег в вызов.

```tsx
// Вы пишете:
<Button color="blue">Нажми</Button>

// Классический трансформ ("jsx": "react" в tsconfig):
React.createElement(Button, { color: 'blue' }, 'Нажми');

// Новый JSX-трансформ, React 17+ ("jsx": "react-jsx"):
import { jsx as _jsx } from 'react/jsx-runtime';  // импорт вставят за вас
_jsx(Button, { color: 'blue', children: 'Нажми' });
```

При классическом трансформе `React.createElement` вызывался напрямую. Поэтому `React` обязан был быть в области видимости, даже если вы нигде не писали `React.` руками. Новый трансформ вставляет runtime-импорт сам, так что импортировать React только ради JSX больше не нужно.

---

**Что такое React-элемент и чем он отличается от компонента?**

Элемент — это обычный объект JavaScript, описывающий, что нужно отрендерить, и это не узел DOM. DOM — это Document Object Model, дерево объектов, из которого браузер рисует страницу. Компонент — функция или класс, который эти элементы создаёт.

```tsx
// Элемент — просто данные:
{
  $$typeof: Symbol(react.element),
  type: 'button',
  props: { color: 'blue' },
  key: null,
  ref: null,
}
```

Элемент — это описание, компонент — фабрика. `$$typeof` — это Symbol, а Symbol нельзя сериализовать в JSON. Это закрывает атаки межсайтового скриптинга (XSS), когда злоумышленник подсовывает данные, а страница их исполняет. Подставленный JSON не сможет притвориться React-элементом, потому что этот Symbol в нём не появится.

**Что вызывает ре-рендер в React?**

Четыре причины, и других нет:

1. Вызван `setState` или `dispatch`.
2. Изменился контекст, который читает компонент.
3. Родительский компонент перерисовался и передал новые пропсы.
4. Вызван `forceUpdate` — в класс-компонентах.

```tsx
const [n, setN] = useState(0);

setN(0);   // то же значение → выход по Object.is, ре-рендера нет
setN(1);   // другое значение → ре-рендер
```

Обратите внимание на третий пункт. Получение *тех же* пропсов ре-рендер не отменяет: если родитель перерисовался, React всё равно вызовет функцию компонента. Выход по `Object.is` срабатывает только когда состоянию присваивают то значение, которое в нём уже лежит.

---

**Что такое батчинг и как React 18 изменил его поведение?**

Батчинг — это когда React объединяет несколько вызовов `setState` в один ре-рендер. React 18 распространил его на все источники обновлений.

```tsx
function handleClick() {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React 17 и 18: один ре-рендер — оба вызова в обработчике React
}

setTimeout(() => {
  setCount(c => c + 1);
  setFlag(f => !f);
  // React 17: два ре-рендера. React 18: один — батчинг автоматический
}, 0);

flushSync(() => setCount(c => c + 1));  // отказ от батчинга: рендер сразу
```

В React 17 и раньше батчинг работал только внутри обработчиков событий React. `setState` внутри `setTimeout`, `Promise.then` или нативного события DOM давал отдельный ре-рендер на каждый вызов. React 18 ввёл **автоматический батчинг**: все обновления состояния группируются независимо от источника. Отказаться можно через `flushSync` — он выполняет этот один рендер синхронно.

---

**Что делает StrictMode и почему он дважды вызывает рендер компонентов в разработке?**

Он намеренно вызывает функции компонентов дважды в разработке, чтобы нечистый рендер стал заметен.

```txt
<React.StrictMode> в разработке
  render()  ← вызов 1
  render()  ← вызов 2, те же пропсы и состояние
  commit    ← только один раз

В production: один вызов, без удвоения.
```

Удваивается только фаза рендера, коммит — никогда. Если рендер действительно чистый, второй вызов даст тот же результат. Если он мутирует внешнее состояние, пишет в лог или неидемпотентен по другой причине, второй вызов это покажет. StrictMode ещё и обнаруживает устаревшие API и предупреждает об отсутствующей очистке в эффектах.

## Группа 2: Основы хуков

**Почему правила хуков не произвольны — что сломается при условном вызове хука?**

Состояние каждого хука молча съедет на одну позицию. Хуки хранятся односвязным списком на Fiber-узле, и React находит каждый хук по его позиции в этом списке.

```txt
Список хуков на Fiber — ищут по позиции, а не по имени

  рендер 1:  [1] useState   [2] useEffect   [3] useMemo
  рендер 2:  [1] useState   [2] useMemo     ← useEffect пропущен
                             ↑ useMemo читает узел от useEffect
```

Первый вызов читает первый узел, второй — второй, и так далее. Пропустите вызов хука на условной ветке, и каждый следующий хук сдвинется на одну позицию. React начнёт читать для них чужие узлы. Результат — молчаливая порча состояния: то, что принадлежало хуку N, читается как состояние хука N-1. Правило существует потому, что в связанном списке нет имён — только позиции.

---

**Какова разница между первым рендером и обновлением для useState?**

При монтировании React создаёт узел хука, при обновлении — находит существующий, пройдя по списку.

```tsx
// Вызывается ТОЛЬКО при монтировании — ленивый инициализатор:
const [rows, setRows] = useState(() => expensiveCalc());

// Вызывается при КАЖДОМ рендере — результат после монтирования выбрасывается:
const [rows2, setRows2] = useState(expensiveCalc());
```

При монтировании React создаёт новый узел хука на Fiber, выполняет инициализатор и сохраняет начальное значение. При обновлении React проходит по существующему связанному списку до нужного узла и читает его текущее значение. Сеттер из `useState` стабилен между рендерами: создаётся один раз и больше не меняется. Поэтому его безопасно не указывать в массиве зависимостей.

---

**Что такое устаревшее замыкание (stale closure) и когда оно появляется с useEffect?**

Функция захватила переменную из внешней области видимости. Потом переменная изменилась в следующем рендере, но функция по-прежнему держит то значение, которое видела при создании.

```tsx
function Counter() {
  const [count, setCount] = useState(0);

  useEffect(() => {
    const id = setInterval(() => console.log(count), 1000);  // всегда 0
    return () => clearInterval(id);
  }, []);  // ❌ count захвачен при монтировании и не обновляется
}
```

Есть два исправления. Добавить `count` в массив зависимостей — тогда эффект перезапустится при каждом изменении `count`. Либо держать актуальное значение в ref: его можно читать, вообще не перезапуская эффект.

---

**Какая разница между useEffect и useLayoutEffect?**

Оба запускаются после рендера, но в разные моменты: один до отрисовки браузером, другой после.

```txt
рендер → commit (React меняет DOM) → useLayoutEffect
       → браузер рисует кадр → useEffect
```

- `useEffect` запускается после того, как браузер нарисовал кадр. Он асинхронен относительно отрисовки и картинку не задерживает.
- `useLayoutEffect` запускается сразу после того, как React применил мутации DOM, но **до** отрисовки браузером. Он отрисовку задерживает.

Эта задержка и нужна, когда надо замерить layout — размеры и положение элементов — и по замеру обновить состояние. Без неё пользователь один кадр видит элемент не на месте.

```tsx
function Tooltip({ children }: { children: React.ReactNode }) {
  const ref = useRef<HTMLDivElement>(null);
  const [top, setTop] = useState(0);

  useLayoutEffect(() => {
    const box = ref.current!.getBoundingClientRect();  // замер
    setTop(-box.height - 8);                           // ставим выше
  }, []);                                              // до отрисовки

  return <div ref={ref} style={{ top }}>{children}</div>;
}
```

Правило по умолчанию: берите `useEffect`. За `useLayoutEffect` идите только тогда, когда видите мерцание, которое лечится лишь синхронным чтением размеров сразу после коммита. На сервере `useLayoutEffect` не делает ничего, потому что DOM там нет, и выводит предупреждение. Используйте `useEffect` или защиту через `typeof window !== 'undefined'`.

---

**Когда запускается очистка useEffect и в каком порядке?**

В двух случаях: перед повторным запуском эффекта из-за изменившейся зависимости и при размонтировании компонента.

```txt
Зависимость изменилась:
  очистка предыдущего эффекта  →  новый эффект

StrictMode, при монтировании, в разработке:
  эффект  →  очистка  →  эффект     ← намеренно удвоено
```

Порядок при изменении зависимости всегда один: сначала очистка, потом новый эффект. В StrictMode цикл «очистка — эффект» намеренно выполняется дважды при монтировании, и это вскрывает пропущенную очистку. Очистка — это та функция, которую вернул колбэк эффекта. Если колбэк ничего не вернул, очистки нет.

## Группа 3: Продвинутые хуки

**Когда useMemo реально улучшает производительность, а когда вредит?**

Помогает, когда вычисление действительно дорогое, а его входные данные меняются редко. Вредит, когда неверна любая из двух половин.

| Ситуация | Вердикт по `useMemo` |
|---|---|
| Вычисление дольше 1 мс, идёт каждый рендер, входы меняются редко | помогает |
| Дешёвое вычисление, например `filter` по 100 элементам | чистые накладные расходы |
| Массив зависимостей и так меняется каждый рендер | кеш никогда не срабатывает |
| Объект или функция создаются прямо внутри зависимостей | кеш никогда не срабатывает |

Перед добавлением `useMemo` замерьте через `console.time`. Стоимость сравнения плюс аллокация замыкания самого `useMemo` не бесплатны.

---

**Каковы два валидных сценария использования useCallback?**

Передача колбэка в мемоизированный дочерний компонент и попадание функции в массив зависимостей другого хука.

```tsx
// 1. Проп для React.memo-компонента: новая ссылка сломала бы memo
const handleSelect = useCallback((id: string) => select(id), [select]);
<MemoList onSelect={handleSelect} />

// 2. Функция внутри массива зависимостей другого хука:
const load = useCallback(() => fetch(`/api/items?q=${query}`), [query]);
useEffect(() => { void load(); }, [load]);  // перезапуск только по query
```

Без `useCallback` в первом случае при каждом рендере родителя создаётся новая ссылка на функцию, и оптимизация memo рушится. Без него во втором случае хук перезапускался бы на каждом рендере. Заметьте: `useCallback` — это тот же `useMemo`, но для функций. Запись `useCallback(fn, deps)` в точности равна `useMemo(() => fn, deps)`.

---

**Каковы четыре применения useRef помимо хранения ссылок на DOM?**

Четыре, и только последнее — исходный сценарий:

1. **Паттерн актуального значения** — держите в ref самое свежее значение пропа или состояния. Тогда его можно прочитать внутри устаревшего замыкания, не перезапуская эффект.
2. **Предыдущее значение** — запоминайте значение прошлого рендера, обновляя ref в `useEffect`, то есть после рендера.
3. **Переменные экземпляра** — храните изменяемые значения, которые обязаны переживать рендеры, но не должны вызывать ре-рендер: таймеры, подписки, объекты WebSocket.
4. **Ссылки на DOM** — прикрепление к элементу, чтобы вызывать императивные DOM API.

```tsx
// Пункты 1 и 2 в одном компоненте:
const latest = useRef(value);
const previous = useRef<string | undefined>(undefined);

useEffect(() => {
  previous.current = latest.current;  // значение прошлого рендера
  latest.current = value;             // значение этого рендера
}, [value]);
```

---

**Что делает useImperativeHandle и когда его применять?**

Он подменяет значение ref, которое получает родитель, на узкий API, выбранный вами.

```tsx
function FancyInput({ ref }: { ref?: React.Ref<{ focus(): void; clear(): void }> }) {
  const input = useRef<HTMLInputElement>(null);

  useImperativeHandle(ref, () => ({
    focus: () => input.current?.focus(),
    clear: () => { if (input.current) input.current.value = ''; },
  }), []);

  return <input ref={input} />;
}
// Родитель может вызвать focus() и clear() — и ничего больше.
```

Без него ref откроет родителю либо весь элемент DOM, либо ничего. С ним вы открываете ровно то, что задумали: примитивы компонентной библиотеки — свои инпуты, видеоплееры, управление фокусом модального окна. Родителю там правда нужен императивный доступ, но поверхность API вы ограничиваете. В React 19 `ref` — обычный проп, поэтому `forwardRef` для этого больше не нужен.

---

**Почему useId генерирует ID, стабильные между сервером и клиентом?**

Потому что значение выводится из позиции компонента в дереве Fiber, а не из счётчика.

```tsx
function Field({ label }: { label: string }) {
  const id = useId();  // например "_r_1_" — одинаково на сервере и клиенте
  return (
    <>
      <label htmlFor={id}>{label}</label>
      <input id={id} aria-describedby={`${id}-hint`} />
      <span id={`${id}-hint`}>Обязательное поле</span>
    </>
  );
}
```

Путь по дереву одинаков на сервере и на клиенте, поэтому и выведенный ID одинаков — расхождения при гидратации не будет. `Math.random()` и растущие счётчики расходятся: сервер и клиент выполняют один и тот же код независимо и получают разные значения.

- Используйте его для пар `htmlFor` и `id`.
- Используйте его для ARIA-атрибутов. ARIA — это Accessible Rich Internet Applications, атрибуты, которые описывают виджет для программы чтения экрана.
- Используйте его всюду, где нужен стабильный уникальный ID, выживающий при SSR. SSR — это server-side rendering, когда HTML собирается на сервере.
- Никогда не используйте его как React `key`.

## Группа 4: Контекст и управление состоянием

**Что заставляет всех потребителей контекста перерисовываться и как это предотвратить?**

Новая ссылка на значение контекста. React сравнивает значения контекста через `Object.is`.

```tsx
// ❌ Новый объект при каждом рендере Provider → перерисуются все потребители:
<UserContext.Provider value={{ user, setUser }}>

// ✅ Та же ссылка, пока не изменятся сами user или setUser:
const value = useMemo(() => ({ user, setUser }), [user, setUser]);
<UserContext.Provider value={value}>
```

Когда Provider перерисовывается, запись `{{ user, setUser }}` создаёт новый объект. Ссылка меняется, даже если `user` и `setUser` не менялись, поэтому `Object.is(prev, next)` даёт false и перерисовываются все потребители. Исправление — мемоизировать значение. `React.memo` на потребителе здесь **не** поможет: он защищает только от изменения пропсов, но не контекста.

---

**Почему состояние и dispatch стоит помещать в отдельные контексты?**

Потому что `dispatch` не меняется никогда, а состояние — постоянно. В одном контексте компоненты, которым нужен только `dispatch`, перерисовываются впустую.

```tsx
const StateContext = createContext<State | null>(null);
const DispatchContext = createContext<React.Dispatch<Action> | null>(null);

function Provider({ children }: { children: React.ReactNode }) {
  const [state, dispatch] = useReducer(reducer, initialState);
  return (
    <DispatchContext.Provider value={dispatch}>
      <StateContext.Provider value={state}>{children}</StateContext.Provider>
    </DispatchContext.Provider>
  );
}
```

У `dispatch` из `useReducer` стабильная ссылка: между рендерами она не меняется. Состояние же меняется при каждом обновлении. Положите оба в один объект контекста — и все потребители перерисуются при любом изменении состояния, включая те, что только вызывают `dispatch`. Разделите их, и компоненты вроде кнопок отправки и создателей экшнов перестанут перерисовываться из-за состояния.

---

**Когда использовать Zustand/Redux вместо Context + useReducer?**

Когда обновления частые или один срез состояния нужен многим не связанным между собой компонентам.

| Признак | Context + `useReducer` | Внешнее хранилище |
|---|---|---|
| Частота обновлений | низкая: авторизация, тема, язык | высокая: каждое нажатие, каждый кадр |
| Кто читает данные | несколько компонентов рядом | много несвязанных компонентов |
| Форма состояния | простая | большая, с независимыми срезами |
| Отладка перемоткой времени | нет | есть |
| Персистентность и синхронизация с внешними системами | пишете сами | встроена |

Главное механическое отличие: обновление хранилища не вызывает ре-рендер React, пока компонент не подписан на конкретный изменившийся срез. Контекст перерисовывает всех потребителей независимо от того, какая часть значения изменилась.

## Группа 5: Fiber, reconciliation и производительность

**Какую проблему решила архитектура Fiber, с которой не справлялся старый stack reconciler?**

Fiber сделал фазу рендера прерываемой. Старый stack reconciler был рекурсивным синхронным алгоритмом: раз запустившись, он доходил до конца и блокировал главный поток. На больших деревьях это давало 50–100 мс блокировки, а значит пропущенные кадры и неотзывчивый ввод.

```txt
Stack reconciler — рекурсия, всё или ничего
  reconcile(App) → reconcile(Main) → reconcile(Article) × 50
  Остановиться посередине нельзя.

Fiber — связанный список, который обходит цикл
  child → sibling → return, по одному узлу за шаг
  React может остановиться после любого узла.
```

Fiber заменил рекурсию связанным списком: указатели `child`, `sibling` и `return`. Обход стал итеративным циклом, который можно приостановить после любого узла. Это и даёт time slicing — нарезку работы по времени. React работает кусками примерно по 5 мс и между ними отдаёт управление браузеру, поэтому кадры не пропадают даже на большом дереве.

---

**Что такое техника двойной буферизации в архитектуре Fiber?**

React держит два дерева Fiber одновременно и меняет их местами одним коммитом.

```txt
дерево current            дерево work-in-progress
(на экране, во время      (строится, может быть
 рендера не трогают)       выброшено)
        │                          │
        └──────── alternate ───────┘
                    │
           один атомарный обмен на коммите
```

Дерево **current** — это то, что отображается. Дерево **work-in-progress** — то, что строится. Вся работа reconciliation идёт в дереве work-in-progress, поэтому дерево current остаётся целым и всегда готовым к отрисовке.

Когда дерево work-in-progress готово, React меняет деревья местами атомарно, одним коммитом. Браузер поэтому всегда видит целостный UI — user interface, то, что видит человек по другую сторону экрана. Указатель `alternate` на каждом Fiber-узле связывает текущую и work-in-progress версии одного и того же компонента.

---

**Объясните три правила reconciliation, которые React применяет при сравнении деревьев.**

1. **Другой тип — размонтировать и смонтировать заново.** Допустим, элемент на позиции сменился с `<div>` на `<span>` или с `<ComponentA>` на `<ComponentB>`. React полностью размонтирует старое поддерево и монтирует новое, не пытаясь обновить на месте.
2. **Тот же тип — обновить на месте.** React обновляет пропсы существующего Fiber, сохраняя узлы DOM и состояние компонента.
3. **Ключи — это идентичность.** Внутри списка дочерних элементов React сопоставляет их по `key`, а не по позиции.

```tsx
// Правило 1 в действии — Panel перемонтируется и потеряет состояние:
{isWide ? <div><Panel /></div> : <section><Panel /></section>}

// Правило 3 в действии — строка сохраняет состояние, куда бы ни переехала:
{rows.map(r => <Row key={r.id} row={r} />)}
```

Дочерний элемент с ключом `"a"` остаётся тем же элементом, куда бы он ни переехал в списке. React обновит его, а не размонтирует и смонтирует заново.

---

**Что не так с использованием индекса массива как ключа?**

Индексные ключи привязывают идентичность к позиции, поэтому любая перестановка, фильтрация или вставка не в конец заставляет React сопоставлять не те элементы.

```txt
было:   [A, B, C]   ключи [0, 1, 2]
удалили A
стало:  [B, C]      ключи [0, 1]

React видит ключ 0 и думает: «это всё ещё A».
Он обновляет Fiber элемента A данными B — вместо того чтобы
размонтировать A и переиспользовать готовый Fiber элемента B.
```

Для неконтролируемых инпутов это выглядит как чужой текст в чужом поле. Берите в качестве ключей стабильные уникальные идентификаторы из данных. Одно исключение: индексные ключи безопасны, если список статичен и никогда не переупорядочивается.

---

**В чём разница между фазой рендера и фазой коммита?**

Фаза рендера чистая и прерываемая, фаза коммита синхронная и прервать её нельзя.

| | Фаза рендера (reconciliation) | Фаза коммита |
|---|---|---|
| Что происходит | вызываются функции компонентов, результат сравнивается, строится дерево work-in-progress | применяются накопленные мутации DOM |
| Подэтапы | один проход по дереву | before mutation → mutation → layout |
| DOM трогается | нет | да |
| Прерываемость | да: можно приостановить, перезапустить или отменить | нет |
| Какие эффекты запускаются | никакие | очистки и колбэки `useLayoutEffect` |

После коммита браузер рисует кадр. И только потом React запускает очистки и колбэки `useEffect` — это фаза пассивных эффектов.

---

**Что означают приоритеты lanes в React и как их использует startTransition?**

Lanes — это система битовых масок, где каждый lane соответствует одному уровню приоритета. `startTransition` помечает своё обновление lane перехода, самым низким из интерактивных.

```txt
SyncLane             наивысший — дискретный ввод пользователя
InputContinuousLane  перетаскивание, наведение
DefaultLane          обычный setState
TransitionLane       фоновая работа  ← сюда пишет startTransition
IdleLane             наименьший
```

React планирует работу по lanes и обрабатывает более приоритетные первыми. Допустим, пока рендерится переход, приходит более приоритетное обновление — пользователь печатает в поле. React прерывает переход, обрабатывает срочное обновление, а затем возобновляет или перезапускает переход.

## Группа 6: Паттерны производительности

**Каковы три условия, которые должны выполняться одновременно для пользы от React.memo?**

1. Компонент рендерится часто — его родитель перерисовывается из-за несвязанных изменений состояния.
2. Ре-рендер дорогой — у компонента много дочерних элементов или тяжёлая работа в рендере.
3. Пропсы стабильны по ссылке между рендерами — примитивы не меняются, а объекты, массивы и функции мемоизированы через `useMemo` или `useCallback`.

```tsx
// ❌ Условие 3 нарушено — новый объект и новая функция каждый рендер:
<MemoChild config={{ theme: 'dark' }} onSelect={() => pick()} />

// ✅ Стабильные ссылки, и сравнение наконец может пройти успешно:
const config = useMemo(() => ({ theme: 'dark' }), []);
const onSelect = useCallback(() => pick(), []);
<MemoChild config={config} onSelect={onSelect} />
```

Если условие 3 не выполнено, сравнение пропсов всегда даёт «изменились»: при каждом рендере родителя создаются новые ссылки. `React.memo` тогда добавляет расходы на сравнение и не даёт ничего.

---

**Что такое паттерн children (подъём контента) и какую проблему производительности он решает?**

Вместо импорта тяжёлого компонента примите его через `children`. Тогда компонент, который владеет быстро меняющимся состоянием, не сможет его перерисовать.

```tsx
// ✅ MouseTracker владеет быстрым состоянием, но не тяжёлым ребёнком:
function MouseTracker({ children }: { children: React.ReactNode }) {
  const [pos, setPos] = useState({ x: 0, y: 0 });
  return (
    <div onMouseMove={e => setPos({ x: e.clientX, y: e.clientY })}>
      <p>Мышь: {pos.x}, {pos.y}</p>
      {children}
    </div>
  );
}

function Page() {
  return <MouseTracker><HeavyChart /></MouseTracker>;
}
```

Когда компонент владеет быстро меняющимся состоянием — позицией мыши, скроллом, таймерами, — всё, что он импортирует и рендерит, перерисовывается при каждом изменении этого состояния. С паттерном children тяжёлый компонент принадлежит `Page`, а `Page` за мышью не следит. Его Fiber уже создан дедом, и `MouseTracker` просто получает готовое значение и вставляет его в свой вывод.

---

**Когда применять виртуализацию и когда она не помогает?**

Она решает проблему количества узлов DOM. С частотой ре-рендеров она не делает ничего.

| | Виртуализация помогает | Виртуализация не помогает |
|---|---|---|
| Проблема | 10 000 строк дают 10 000 узлов DOM, их дорого создавать, измерять и рисовать | видимые строки перерисовываются на каждое нажатие клавиши |
| Длина списка | 500+ элементов | меньше примерно 100 |
| Содержимое строки | нетривиальное в рендере | тривиальное |
| Поведение пользователя | много прокручивает | почти не прокручивает |

Библиотеки: `react-window`, `@tanstack/react-virtual`. Они рендерят только видимые строки плюс небольшой запас (overscan). Не берите виртуализацию, когда список короткий — накладные расходы не оправданы, — или когда настоящее узкое место совсем в другом.

---

**Что измеряет React DevTools Profiler и что не измеряет?**

Он измеряет только фазу рендера: время на вызовы функций компонентов и сравнение их вывода. Три вещи в это измерение не входят:

- длительность фазы коммита, то есть применение мутаций DOM;
- время выполнения `useEffect`;
- время отрисовки браузером.

```tsx
// Компонент <Profiler> — это не панель DevTools, он работает и в production:
<Profiler
  id="ProductList"
  onRender={(id, phase, actualDuration, baseDuration) => {
    analytics.track('react_render', { id, phase, actualDuration, baseDuration });
  }}
>
  <ProductList />
</Profiler>
```

Поэтому компонент может выглядеть быстрым в Profiler и всё равно тормозить. Его коммит может давать много дорогих мутаций DOM, а его `useEffect` — тяжёлую работу. Полное время кадра, вместе с коммитом и отрисовкой, смотрите на вкладке Performance в Chrome DevTools.

## Группа 7: Конкурентные возможности

**В чём разница между startTransition и useDeferredValue?**

Оба помечают работу как низкоприоритетную. Отличаются они местом, где вы применяете контроль.

| | `startTransition` | `useDeferredValue` |
|---|---|---|
| Когда применять | вы владеете сеттером состояния | значение приходит извне |
| Что оборачиваете | вызов `setState` | само значение |
| Типичный источник | состояние вашего же компонента | проп, состояние родителя, библиотека |

```tsx
// Сеттер ваш:
startTransition(() => setResults(filter(data, query)));

// Значение вы только получаете:
const deferredQuery = useDeferredValue(query);
```

Выбирайте тот, который соответствует источнику значения. Контролируете обновление — берите `startTransition`. Только получаете значение — берите `useDeferredValue`.

---

**Как работает Suspense механически — что на самом деле означает «приостановиться»?**

Приостановиться — значит бросить промис во время фазы рендера. React его перехватывает и показывает fallback, пока промис не выполнится.

```txt
1. Компонент бросает промис во время рендера.
2. React перехватывает его на ближайшей границе <Suspense>.
3. React показывает fallback этой границы.
4. React подписывается на брошенный промис.
5. Промис выполнился → React повторяет рендер компонента.
6. Теперь компонент рендерится нормально → React коммитит результат.
```

При повторной попытке компонент не должен бросать снова: данные обязаны быть готовы. Библиотеки данных реализуют ровно этот протокол — кешируют запросы и при первом вызове бросают ещё не завершившийся промис. Так делают и React Query, и SWR. SWR — это stale-while-revalidate, стратегия кеширования, которая сначала отдаёт значение из кеша, а потом обновляет его в фоне.

---

**Почему оборачивание навигации в startTransition предотвращает мерцание Suspense fallback?**

Потому что переход оставляет старую страницу на экране, а не подменяет её на fallback.

```txt
Без startTransition — срочное обновление
  старая страница → fallback (мерцание!) → новая страница

С startTransition — низкоприоритетное обновление
  старая страница (isPending = true) ──────▶ новая страница
  новая страница рендерится в фоне
```

- **Без `startTransition`** навигация считается срочной. React сразу переключается на границу Suspense новой страницы и немедленно показывает fallback. Даже если данные придут через 50 мс, мерцание будет видно.
- **С `startTransition`** React помечает обновление как переход. Он оставляет текущую страницу на экране и ставит `isPending` в `true`, пока новая страница рендерится в фоне.

Когда Suspense новой страницы разрешится и её содержимое будет готово, React закоммитит весь переход одним шагом. Старая страница исчезнет, новая появится, и пустого экрана между ними не будет.

---

**Отличается ли useDeferredValue от дебаунсинга?**

Да, это разные механизмы. Дебаунсинг задерживает обновление состояния, а `useDeferredValue` не задерживает ничего.

| | Дебаунсинг | `useDeferredValue` |
|---|---|---|
| Что задерживается | само обновление состояния | только приоритет рендера |
| Есть ли таймер | да | нет |
| Промежуточные значения | отбрасываются | все в итоге отрендерятся |
| Когда вызван сеттер | после срабатывания таймера | сразу |

`useDeferredValue` получает уже обновлённое значение и говорит React отрендерить его с низким приоритетом. Текущий рендер продолжает показывать предыдущее отложенное значение, пока новый рендер идёт в фоне. React в итоге всегда отрендерит последнее значение. Заметная задержка возникает из-за того, что React понижает приоритет отложенного рендера при наличии более срочной работы, а не из-за искусственной паузы.

## Группа 8: Server Components и React 19

**Что такое граница сериализации и почему функции не могут её пересекать?**

Это черта, на которой серверный компонент передаёт данные клиентскому, и пересекать её могут только сериализуемые значения.

```tsx
// ✅ Границу пересекают:
<ClientComp str="привет" num={42} arr={[1, 2]} obj={{ a: 1 }}
            node={<AnotherServerComponent />} />

// ❌ Пересечь не могут:
<ClientComp fn={() => save()} inst={new MyClass()} map={new Map()} />
```

Когда серверный компонент рендерит клиентский, результат сериализуется в RSC payload — React Server Components payload, JSON-подобный формат передачи по сети. Пересекать границу могут примитивы, массивы, простые объекты и React-элементы. Функции — нет: сериализовать код означало бы отправить на клиент код на исполнение, а это угроза безопасности.

```txt
RSC payload — что может пересечь границу

  ✓ примитивы, массивы, простые объекты
  ✓ React-элементы (результат другого серверного компонента)
  ✗ функции, экземпляры классов, Symbol, Map, Set, undefined
```

Поэтому обработчики событий обязаны жить в клиентских компонентах. Их нельзя объявить на сервере и передать вниз пропсом.

---

**Означает ли 'use client', что компонент выполняется только на клиенте?**

Нет. Он маркирует **границу** между деревом серверных компонентов и деревом клиентских.

```txt
Где на самом деле выполняется клиентский компонент

  на сервере, для SSR и SSG  →  получается первый HTML
      SSG = static site generation: страницы становятся
            HTML на этапе сборки
  в браузере                 →  гидратация, а затем каждое
                                следующее обновление
```

Значит, `'use client'` означает более узкую вещь. Этот компонент и его поддерево используют клиентские возможности React — состояние, эффекты, браузерные API — и должны попасть в JavaScript-бандл, который уходит в браузер. Это не значит «никогда не выполнять на сервере».

---

**В чём разница между Server Actions и API routes?**

API route — это HTTP-эндпоинт, который вы пишете руками. Server Action — функция, которую фреймворк сам публикует как эндпоинт.

| | API route | Server Action |
|---|---|---|
| Как объявляется | файл маршрута с обработчиком запроса | функция с `'use server'` |
| Как вызывается | `fetch` по URL, который вы собрали | как обычная функция |
| Сериализация и транспорт | пишете сами | делает фреймворк |
| Работа без JavaScript | нет | да, через `<form action={...}>` |
| Сброс кеша | ваш собственный код | `revalidatePath` / `revalidateTag` |
| Для чего лучше | публичные API для сторонних клиентов | внутренние формы и мутации |

В API route вы сами определяете URL, разбираете тело запроса, проверяете аутентификацию и возвращаете ответ. Server Action вместо этого встраивается в модель форм React и умеет сбрасывать кеши Next.js напрямую.

---

**Каковы четыре основные причины расхождений при гидратации?**

1. **Браузерные API в рендере** — чтение `window`, `localStorage` или `document` внутри функции рендера. На сервере их нет.
2. **Рендер даты и времени** — `new Date().toLocaleTimeString()` даёт одно значение, когда рендерит сервер, и другое, когда клиент гидратирует миллисекунды спустя.
3. **Случайные значения** — `Math.random()` выдаёт разные числа на сервере и на клиенте.
4. **Условный рендер по чисто браузерным данным** — `typeof window !== 'undefined'` на сервере false, на клиенте true, поэтому вывод разный.

```tsx
// ❌ Сервер рендерит '', клиент рендерит 'dark':
const theme = window.localStorage.getItem('theme') ?? 'light';

// ✅ Одинаково на обоих, а после гидратации обновится:
const [theme, setTheme] = useState('light');
useEffect(() => setTheme(localStorage.getItem('theme') ?? 'light'), []);
```

Три приёма исправления покрывают почти всё:

- Читайте чисто браузерные значения в `useEffect`, после гидратации.
- Используйте детерминированные значения — например, хешируйте ID пользователя в цвет.
- Используйте `suppressHydrationWarning` для расхождений, о которых вы знаете и которые допускаете намеренно.

---

**В чём разница между useActionState и useFormStatus в React 19?**

`useActionState` владеет экшном. `useFormStatus` только читает форму, внутри которой находится.

| | `useActionState` | `useFormStatus` |
|---|---|---|
| Где живёт | в компоненте, владеющем формой | в любом компоненте *внутри* формы |
| Что даёт | результат экшна и `isPending` | `pending`, `data`, `method`, `action` |
| Откуда читает | из экшна, который обернул | из ближайшего родительского `<form>` |

`useActionState` оборачивает функцию экшна, хранит её результат — данные успеха или ошибку — и даёт `isPending`. Именно он отдаёт форме проп `action`. `useFormStatus` подходит компонентам внутри формы: кнопке отправки, индикатору загрузки. Экшном они не владеют, но статус формы им нужен. Эти два хука дополняют друг друга.

---

**Что на самом деле делает React Compiler (React Forget) и что он не может исправить?**

Он расставляет мемоизацию за вас на этапе сборки. Он не может исправить то, где живёт ваше состояние.

```tsx
// Вы пишете это:
const filtered = todos.filter(t => t.title.includes(filter));

// Компилятор выдаёт примерно это:
const filtered = useMemo(
  () => todos.filter(t => t.title.includes(filter)),
  [todos, filter]
);
```

Compiler — это плагин Babel для этапа сборки, и он же работает через SWC (Speedy Web Compiler, сборщик на Rust, который использует Next.js). Он определяет, какие значения «реактивны», то есть зависят от пропсов, состояния или других реактивных значений, и вставляет мемоизацию там, где это безопасно.

```txt
React Compiler
  исправляет   те useMemo / useCallback / React.memo,
               которые вы иначе писали бы руками
  не исправит  состояние, живущее слишком высоко в дереве
               объекты-значения контекста прямо в разметке
               ре-рендеры, идущие от архитектуры
```

Он оптимизирует отдельные компоненты. Дизайн, в котором состоянием владеет не тот компонент, он не исправит.

## Группа 9: Паттерны и архитектура

**Что такое паттерн Compound Components и чем он отличается от API на основе пропсов?**

Он разбивает один компонент на родителя, владеющего состоянием, и детей, читающих его из контекста, — и тогда разметкой управляет потребитель.

```tsx
// API на пропсах — автор обязан предугадать любую потребность:
<Select options={opts} renderOption={fn} maxHeight={300} showBorder />

// Compound Components — потребитель собирает сам:
<Select defaultValue="react">
  <div className="header">Выберите фреймворк</div>
  <Select.Option value="react">React</Select.Option>
  <Select.Option value="vue">Vue</Select.Option>
</Select>
```

Родитель владеет состоянием и логикой координации и отдаёт их через контекст. Дочерние компоненты читают этот контекст без prop drilling. API на пропсах вынуждает автора компонента заранее предугадать каждую потребность в настройке. Compound Components передают разметку и компоновку потребителю, и автору остаётся описать только логику координации.

**Что перехватывает Error Boundary и что нет?**

Он перехватывает ошибки, брошенные во время рендера, и ничего из того, что происходит вне цикла рендера.

```txt
✓ Перехватывает
    ошибки в фазе рендера (тело функции компонента)
    ошибки в методах жизненного цикла класс-компонентов
    ошибки в конструкторах дочерних компонентов

✗ Не перехватывает
    ошибки в обработчиках событий
    ошибки в асинхронном коде: setTimeout, отказ промиса,
      async/await
    ошибки самого Error Boundary
```

Для обработчика событий используйте `try/catch` внутри обработчика и сохраняйте ошибку в состоянии. Асинхронный код выполняется вне цикла рендера React, поэтому boundary его и не видит. Чтобы асинхронная ошибка дошла до boundary, поймайте её вручную и запишите в состояние. React бросит это значение при следующем рендере, и там boundary её поймает.

**Когда использовать Portal и чем он отличается от обычного рендера на месте?**

Portal рендерит ребёнка в узел DOM вне корня React, но оставляет его внутри React-дерева. Контекст и всплытие событий продолжают работать как обычно. Portal нужен, когда CSS предка запирает содержимое внутри себя, а это бывает в трёх видах:

- `overflow: hidden` обрезает содержимое.
- Низкий `z-index` прячет его под соседями.
- CSS-трансформация создаёт новый контекст наложения.

```txt
React-дерево              DOM-дерево
<Dashboard>               <body>
  <Modal>                   <div id="root"> ... </div>
    <ConfirmDialog />       <div class="modal-overlay">
  </Modal>                    <ConfirmDialog />
</Dashboard>                </div>
                          </body>
```

Классический пример — модальный диалог внутри прокручиваемой карточки с `overflow: hidden`. Отрендеренный на месте, он обрезается. Отрендеренный через Portal, он попадает в `document.body`, где ограничения CSS предков на него не действуют.

**Почему Higher-Order Components (HOC) вышли из моды по сравнению с кастомными хуками?**

HOC — это функция, которая берёт компонент и возвращает обёрнутый. Издержек накапливается четыре, и у кастомного хука нет ни одной.

| Издержка HOC | С кастомным хуком |
|---|---|
| каждый HOC добавляет компонент-обёртку, видимую в DevTools, и трассировки путаются | компонента-обёртки нет вообще |
| два HOC с одноимённым пропом молча перезаписывают друг друга | результат — переменные, которые называет вызывающий код |
| TypeScript требует писать руками `Omit<P, 'injectedProp'>` | тип возврата выводится сам |
| refs надо явно пробрасывать через `forwardRef` | пробрасывать нечего |

Кастомный хук даёт то же переиспользование логики, что обычная функция, чьи возвращаемые значения называет вызывающий код. Единственный оставшийся оправданный сценарий для HOC — обёртка вокруг Error Boundary, который обязан быть класс-компонентом.

**В чём разница между контролируемым и неконтролируемым компонентом, и почему React Hook Form по умолчанию использует неконтролируемые инпуты?**

Контролируемый инпут держит значение в состоянии React. Неконтролируемый держит его в DOM.

```tsx
// Контролируемый — ре-рендер на каждое нажатие клавиши:
<input value={value} onChange={e => setValue(e.target.value)} />

// Неконтролируемый — читаем по требованию, ре-рендеров нет:
<input ref={inputRef} defaultValue="" />
```

У контролируемого инпута `defaultValue` роли не играет: весь контракт — это `value` плюс `onChange`. У неконтролируемого `defaultValue` задаёт начальное значение, а текущее вы читаете через ref или через `FormData` при отправке.

React Hook Form использует неконтролируемые инпуты, чтобы не перерисовываться на каждое нажатие клавиши. В форме на 20 полей контролируемый подход мог бы дать 20 ре-рендеров на цепочку нажатий. React Hook Form регистрирует инпуты через ref и вызывает ре-рендеры только на изменение состояния валидации и на явные обновления уровня формы — но не на отдельные символы.
