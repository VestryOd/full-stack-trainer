# Redis — вопросы на интервью (Senior)

## Группа 1: Архитектура и производительность

**Почему Redis работает быстро?**

Три причины.

1. **Данные лежат в RAM (оперативной памяти).** Чтение из памяти занимает ~100 нс, чтение с диска — ~10 мс.
2. **Все команды выполняет один поток.** Данные не нужно защищать мьютексом, и процессор не тратится на переключение между потоками.
3. **Структуры данных заточены под задачу.** Hash Table для String и Hash, Skip List для Sorted Set, Linked List для List. Любая операция — O(1) или O(log N), и никакой планировщик не решает, как её выполнить.

---

**Разве однопоточность не является ограничением?**

Нет. Команды Redis выполняются за микросекунды (SET/GET — ~1–10 мкс), поэтому один поток обрабатывает сотни тысяч операций в секунду. Ограничение — не процессор, а сетевой I/O и диск.

Начиная с Redis 6.0 сетевой I/O вынесен в отдельные потоки (threaded I/O). Сохранение на диск тоже идёт в фоне через fork: снапшоты RDB (Redis Database) и лог AOF (Append Only File). Главный поток остаётся однопоточным — именно это делает каждую команду атомарной без блокировок.

---

**Когда Redis уступает PostgreSQL и когда дополняет его?**

**Redis уступает PostgreSQL, когда нужны:**

- Транзакции по нескольким таблицам. PostgreSQL даёт им гарантии ACID: atomicity, consistency, isolation, durability — атомарность, согласованность, изолированность, долговечность. Достигает он их через MVCC (multiversion concurrency control), когда читатель видит снимок данных вместо ожидания писателей.
- JOIN и другие сложные запросы.
- Долгосрочное хранение с полнотекстовым поиском.
- Данных больше, чем помещается в память.

**Redis дополняет PostgreSQL там, где нужны:** кеш горячих данных (Cache-Aside), счётчики (`INCR` атомарен без транзакции), rate limiting, сессии, очереди задач, pub/sub.

Типичная архитектура: PostgreSQL — источник правды, Redis — слой ускорения чтения.

---

**Что такое Eviction Policy и какую выбрать?**

Eviction Policy — стратегия вытеснения при исчерпании `maxmemory`. LRU ниже означает least recently used (давно не использованные), LFU — least frequently used (редко используемые), а TTL (time to live) — сколько ключу осталось жить.

- `noeviction` — возвращать ошибку при записи (для persistent store)
- `allkeys-lru` — выселять давно не использованные ключи среди всех (рекомендуется для cache)
- `volatile-lru` — LRU только среди ключей с TTL
- `allkeys-lfu` — выселять редко используемые (лучше при hot/cold распределении)
- `volatile-ttl` — выселять ближайшие к истечению срока

Для cache-only Redis: `allkeys-lru` или `allkeys-lfu`. Для mixed (cache + persistent): `volatile-lru` — тогда persistent ключи без TTL не вытесняются.

## Группа 2: Структуры данных

**Какие структуры данных предоставляет Redis и их сложность?**

```txt
String  — O(1) GET/SET/INCR/SETNX
Hash    — O(1) HGET/HSET, O(N) HGETALL (N = кол-во полей)
List    — O(1) LPUSH/RPOP/LLEN, O(N) LRANGE
Set     — O(1) SADD/SISMEMBER, O(N) SMEMBERS, O(N) SINTER/SUNION
Sorted Set — O(log N) ZADD/ZRANK
             O(log N + M) ZRANGEBYSCORE (M = результатов)
HyperLogLog — O(1) PFADD/PFCOUNT, ~1.5% погрешность, max 12KB
Bitmap  — O(1) SETBIT/GETBIT, O(N) BITCOUNT
Stream  — O(1) XADD, O(log N) XRANGE/XREAD
```

---

**Когда использовать Hash вместо отдельных String ключей?**

Hash — когда нужно хранить несколько атрибутов одного объекта: `HSET user:123 name "Alice" age "30" email "alice@..."`. Преимущества:

- Один ключ вместо трёх (`user:123:name`, `user:123:age`).
- Экономия памяти: маленькие Hash Redis упаковывает в ziplist/listpack.
- Атомарное чтение нескольких полей через `HMGET`.

Ограничение: `HGETALL` — это O(N), поэтому для хэшей с тысячами полей его не используют.

---

**Как реализовать leaderboard с обновлением рейтинга в реальном времени?**

Sorted Set: `ZADD leaderboard <score> <userId>`. Обновление: `ZINCRBY leaderboard 10 user:123` — атомарно увеличить score. Топ-10: `ZREVRANGE leaderboard 0 9 WITHSCORES`. Ранг пользователя: `ZREVRANK leaderboard user:123` — O(log N). Для sliding window рейтинга по времени: score = timestamp в миллисекундах, `ZRANGEBYSCORE` по диапазону времени + `ZREMRANGEBYSCORE` для удаления старых записей.

---

**Зачем HyperLogLog если есть Set?**

HyperLogLog считает уникальные значения с ~1.5% погрешностью, занимая максимум 12 килобайт независимо от количества элементов. Set с миллионом элементов занимает ~50 мегабайт и больше.

Для точного счёта уникальных пользователей за день берут Set. Для аналитики — дневная аудитория (DAU), уникальные просмотры, — где 1.5% погрешности допустимы: `PFADD dau:2024-01-15 userId` → `PFCOUNT dau:2024-01-15`. Объединение нескольких дней: `PFMERGE dau:week dau:2024-01-15 dau:2024-01-16`.

## Группа 3: Паттерны кеширования

**Объясните Cache-Aside и его недостатки.**

Cache-Aside (lazy loading): при чтении — сначала Redis, при промахе — PostgreSQL → запись в Redis → возврат. При обновлении — обновить базу, затем сделать `DEL` ключа в Redis. Удалять безопаснее, чем `SET`: параллельный читатель успел бы записать в кеш старые данные между `UPDATE` и `SET`.

Недостатки:

- Первый запрос после истечения TTL — всегда Cache Miss.
- Если Redis недоступен в момент `DEL`, устаревшие данные живут до истечения TTL.

Альтернатива — Write-Through: писать в Redis и в базу при каждом обновлении. Устаревших данных нет, но в кеш попадают строки, которые могут никому не понадобиться.

---

**Что такое Cache Stampede и как предотвратить?**

Cache Stampede (Thundering Herd): 1000 параллельных запросов приходят ровно в момент истечения TTL ключа, все они идут в базу, и та ложится. Три решения:

1. **Mutex Lock.** Первый процесс ставит блокировку (`SET mutex:key 1 NX EX 5`), остальные ждут и через мгновение читают из кеша. Проверку и чтение делают одним Lua-скриптом, чтобы это был атомарный шаг.
2. **Random TTL jitter.** Вместо фиксированного TTL=3600 используйте `3600 + random(0, 300)`. Тогда ключи истекают в разные моменты и нагрузка размазывается.
3. **Background refresh.** Перестраивать кеш асинхронно незадолго до истечения TTL (probabilistic early recomputation).

---

**Что такое Cache Penetration и Bloom Filter?**

Cache Penetration: запросы к данным, которых нет ни в Redis, ни в PostgreSQL (например, `GET /users/999999` — несуществующий пользователь). Каждый раз — Cache Miss → запрос в базу → `NULL` → ничего не кешируется → следующий такой же запрос снова идёт в базу. Два решения:

1. **Кешировать сам `null`.** Записать `SET user:999999 "null" EX 60`, а при чтении проверять `if cached === "null" return null`.
2. **Bloom Filter.** Вероятностная структура, которая отвечает «точно нет» или «вероятно есть». Проверяйте её до обращения к базе. False positive возможен, false negative — нет.

---

**Как реализовать rate limiting через Redis?**

Sliding window counter через `INCR` + `EXPIRE`:

```typescript
const key = `ratelimit:${userId}:${Math.floor(Date.now() / 60000)}`;
const count = await redis.incr(key);
if (count === 1) await redis.expire(key, 60);
if (count > 100) throw new Error('Rate limit exceeded');
```

Проблема: окно сбрасывается каждую минуту, возможен burst 200 запросов на стыке минут. Точный sliding window: Sorted Set с timestamp как score — `ZADD ratelimit:userId <timestamp> <uuid>`, удалять старые: `ZREMRANGEBYSCORE key 0 <timestamp-60s>`, считать: `ZCARD`. Точнее, но дороже по памяти.

---

## Группа 4: Pub/Sub и Streams

**В чём разница между Pub/Sub и Streams?**

Pub/Sub эфемерен: fire-and-forget, без хранения. Если subscriber offline, сообщение теряется. Идеален для broadcasting WebSocket-событий между инстансами, cache invalidation и live dashboard.

Streams — это append-only persistent log с уникальными ID, и сообщения лежат там до явного удаления.

```txt
                     Pub/Sub          Streams
Хранение:            Нет              До удаления
Подписчик упал:      Сообщение ушло   Сообщение ждёт
Доставка:            Каждому          Одному в группе
Подтверждение:       Нет              XACK; без него pending
Повтор истории:      Нет              Да
```

С Consumer Groups каждое сообщение достаётся ровно одному consumer в группе — так и балансируют воркеров. `XACK` — подтверждение того, что обработка закончилась; без него сообщение остаётся pending и может быть взято повторно. Streams — это Redis-аналог Kafka для low/medium throughput (~100k/sec).

---

**Почему нельзя использовать одно соединение для subscribe и обычных команд?**

После `SUBSCRIBE`/`PSUBSCRIBE` соединение переходит в режим подписки: разрешены только `SUBSCRIBE`, `UNSUBSCRIBE`, `PSUBSCRIBE`, `PUNSUBSCRIBE`, `PING`, `QUIT`. Попытка выполнить `SET`/`GET` вернёт ошибку. Поэтому всегда нужно два клиента: один для подписки (subscriber connection), другой для команд (publisher/command connection). В ioredis subscriber клиент создаётся через `redis.duplicate()`.

---

**Как масштабировать WebSocket с несколькими инстансами NestJS?**

Проблема: клиент подключён к инстансу A, событие генерируется на инстансе B, и клиент его не получает. Redis Pub/Sub — та шина, которая это чинит.

```txt
1. Инстанс B публикует в канал пользователя:
   redis.publish('user:123:events', JSON.stringify(event))
2. Все инстансы подписаны на этот канал
3. Получив сообщение, каждый инстанс ищет сокет этого
   пользователя среди своих соединений
4. Отправит только тот инстанс, у которого сокет и правда есть
```

У Socket.IO есть `@socket.io/redis-adapter` — официальная реализация ровно этого паттерна.

---

**Когда использовать Consumer Groups vs несколько SUBSCRIBE?**

Несколько `SUBSCRIBE` на один канал — это fan-out: каждый подписчик получает **все** сообщения. Так уведомляют несколько независимых сервисов.

Consumer Group — это competing consumers: каждое сообщение достаётся ровно **одному** consumer из группы, и обработка балансируется. Три воркера на заказы, каждый заказ обрабатывается один раз — Consumer Group.

Нужно и то и другое? Заведите две отдельные Consumer Groups на одном Stream. Каждая группа получает все сообщения независимо, поэтому сервис уведомлений и сервис аналитики увидят событие оба.

## Группа 5: Распределённые блокировки

**Как реализовать distributed lock и почему важен уникальный токен?**

`SET lock:resource <uuid> NX PX 30000` — атомарно: создать, только если ключа нет, и с TTL 30 секунд. UUID (universally unique identifier) — токен, который доказывает, что блокировка ваша, и не даёт освободить чужую.

Вот что происходит без токена:

```txt
1. Process A захватил lock с TTL=5 сек
2. Process A завис на 6 сек, TTL истёк, Redis удалил ключ
3. Process B захватил тот же lock
4. Process A очнулся и выполнил DEL lock
5. Process B только что потерял блокировку, которую
   считает своей
```

С токеном вы сначала делаете `GET lock` и удаляете, только если значение совпало с вашим UUID. Но `GET` и `DEL` — два отдельных шага с промежутком между ними, поэтому обязателен Lua-скрипт.

---

**Почему для освобождения lock нужен Lua-скрипт?**

Между `GET lock` (проверка токена) и `DEL lock` (удаление) — не атомарный промежуток. Если TTL истёк именно между ними: Process B захватил lock после `GET`, а Process A выполняет `DEL` и удаляет чужой lock. Lua-скрипт выполняется атомарно (Redis single-threaded гарантирует: между командами внутри Lua никто не вклинится):

```lua
if redis.call("get", KEYS[1]) == ARGV[1] then
  return redis.call("del", KEYS[1])
else
  return 0
end
```

Вернёт 1 (успешно удалено) или 0 (токен не совпал — lock уже у другого).

---

**Когда использовать Redlock вместо обычного Redis lock?**

Redlock нужен там, где потерять блокировку нельзя. Один инстанс Redis — единая точка отказа (SPOF). Если он упал сразу после выдачи блокировки, новый Master, выбранный Sentinel, о ней ничего не знает. Тогда два процесса одновременно считают, что блокировка у них.

```txt
Redlock по шагам:
1. startTime = сейчас
2. SET NX PX на всех N нодах (малый timeout, чтобы одна
   мёртвая нода не подвесила вызов)
3. Lock получен, только если >N/2 нод ответили OK
   И elapsed < ttl * 0.1
4. Эффективный TTL = TTL - elapsed - дрейф часов
5. Кворума нет → DEL на всех нодах и повтор
```

`N` — это 3 или 5 независимых инстансов, поэтому падение одного оставляет кворум. Большинству приложений хватает Single Redis + Sentinel. Redlock — для критичной инфраструктуры: финансовые операции, распределённые транзакции.

---

**Redis Lock vs PostgreSQL SELECT FOR UPDATE — когда что выбрать?**

PostgreSQL `FOR UPDATE` блокирует строку на время транзакции и снимает блокировку при commit или rollback. Redis не нужен. Используйте его, когда вся операция атомарна внутри одной транзакции PostgreSQL.

Redis Lock нужен, когда:

- Операция затрагивает несколько сервисов или баз.
- Блокировка нужна до начала транзакции.
- Заблокировать надо внешний вызов API, а не строку в базе.
- Cron job должен запуститься ровно на одном инстансе.

Пример: взять Redis Lock, вызвать Payment API, затем записать в базу. `FOR UPDATE` вызов Payment API не покрывает вообще.

## Группа 6: Сохранение данных и отказоустойчивость

**Чем RDB отличается от AOF и что выбрать для production?**

RDB — бинарный снапшот всей памяти, который делает `BGSAVE` (fork + Copy-on-Write). AOF — лог каждой write-команды; с `appendfsync everysec` теряется максимум секунда данных.

```txt
                   RDB                    AOF
Размер файла:      Компактный             Больше (вся история)
Скорость рестарта: Быстро (загрузка)      Медленнее (replay)
Худшая потеря:     Минуты                 1 сек (everysec)
Читаемость:        Нет (бинарный)         Да (обычные команды)
```

Рекомендация для production — держать оба. При рестарте Redis берёт AOF, потому что он точнее, а RDB остаётся быстрым файлом для disaster recovery. Cache-only Redis: оба выключить.

---

**Что такое AOF Rewrite и почему он нужен?**

AOF накапливает всю историю команд: 1000 `INCR counter` превращаются в 1000 строк файла. Но конечное состояние — один ключ с одним значением.

`BGREWRITEAOF` (или автоматический триггер `auto-aof-rewrite-percentage 100`) перезаписывает AOF в минимальный эквивалентный набор команд: 1000 `INCR` схлопываются в один `SET counter 1000`. Выполняется в фоне через fork и не блокирует Redis. Без Rewrite файл растёт без предела, а вместе с ним растёт и время рестарта.

---

**В чём разница между Sentinel и Cluster?**

Оба дают высокую доступность — автоматическое восстановление при падении узла, — но данные делит только Cluster.

```txt
                  Sentinel             Cluster
Шардинг:          Нет                  Да (16384 slots)
Данные:           Всё на одном Master  Разбиты по N Masters
Failover:         Голосование Sentinel Внутри кластера
Multi-key ops:    Работают всегда      Только в одном slot
Когда:            Данные влезают в     Данные переросли
                  RAM одного сервера   один сервер
```

Sentinel: за Master следят 3 или больше процессов Sentinel. При падении они голосуют, один Sentinel инициирует failover, Replica становится Master, а клиенты подхватывают новый адрес.

Cluster: данные распределены по N Master-нодам, у каждой свои Replicas, а failover происходит внутри кластера.

---

**Когда правильно выключить persistence у Redis?**

Для cache-only Redis: `appendonly no` + `save ""` (отключить RDB). Потеря кеша стоит одного Cache Miss и больше ничего, потому что источник правды — PostgreSQL. Persistence не бесплатен: fork для RDB может ударить по latency на большом dataset, а AOF нагружает диск. Конфигурация cache-only: `maxmemory 2gb` + `maxmemory-policy allkeys-lru` + persistence off.

Оставьте сохранение включённым, если Redis используется как:

- Очередь задач вроде BullMQ.
- Распределённые блокировки для критичных ресурсов.
- Основное хранилище сессий, где выкидывать всех при рестарте недопустимо.

---

**Что такое replica lag и как он влияет на приложение?**

Репликация в Redis асинхронная: Master записывает команду, отправляет её Replica, а Replica применяет. Lag обычно меньше 1ms, но при высокой нагрузке или медленной сети доходит до сотен мс.

Последствие: чтение с Replica сразу после записи в Master может вернуть устаревшие данные. Поэтому критичные чтения направляйте на Master, а некритичные (кеш, аналитика) — на Replica.

В приложении это два клиента: `masterClient` для записи и критичных чтений, `replicaClient` для масштабирования остальных. При failover через Sentinel клиент должен переподключиться к новому Master по адресу Sentinel, поэтому адрес Master никогда не хардкодят.
