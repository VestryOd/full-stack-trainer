# Планировщик запросов и EXPLAIN ANALYZE

## Планировщик — наиболее сложная часть PostgreSQL, от которой зависит разница между 5 мс и 5 минут

SQL (Structured Query Language) — декларативный язык: вы описываете **что** хотите получить, а не **как**. Задача планировщика (Planner, он же Optimizer) — превратить это декларативное "что" в конкретный план выполнения. Он решает, какие индексы использовать, в каком порядке обходить таблицы и какой алгоритм `JOIN` применить.

Два этапа в схеме ниже стоит расшифровать заранее. Парсер строит AST (abstract syntax tree — разобранное представление текста запроса в виде дерева). Дальше Rewriter применяет к этому дереву правила. Одно из них — RLS (row-level security, безопасность на уровне строк): политики доступа к отдельным строкам таблицы. Они незаметно дописывают условия в ваш запрос.

```txt
SQL-текст
    │  Parser: AST
    ↓
Query Tree
    │  Rewriter: VIEW expansion, RLS
    ↓
Logical Plan
    │  Planner: перебор планов, оценка стоимости каждого
    ↓
Best Physical Plan
    │  Executor: выполнение
    ↓
Результат
```

## Модель стоимости (Cost Model) — что именно оценивает Planner

Планировщик PostgreSQL — оптимизатор по стоимости (cost-based optimizer). Точного времени выполнения он не знает. Вместо этого он оценивает "стоимость" каждого плана-кандидата в условных единицах и выбирает план с минимальной оценкой.

Сама единица — это настройка. Чтение одной страницы подряд стоит 1.0 по определению, а все остальные параметры оценены относительно неё.

| Параметр | По умолчанию | Что оценивает |
|---|---|---|
| `seq_page_cost` | 1.0 | Чтение одной страницы при Sequential Scan — базовая единица |
| `random_page_cost` | 4.0 | Чтение одной страницы случайным доступом, как делает Index Scan |
| `cpu_tuple_cost` | 0.01 | Обработку одной строки |
| `cpu_index_tuple_cost` | 0.005 | Обработку одной записи индекса |
| `cpu_operator_cost` | 0.0025 | Вычисление одного оператора или вызова функции |

Стоимость плана — это сумма всех его чтений с диска и всей обработки строк, взвешенная по параметрам выше.

Значение `random_page_cost = 4.0` по умолчанию выбрано под вращающиеся диски. На другом железе оно искажает все планы:

- На HDD (hard disk drive — жёсткий диск с вращающимися пластинами) случайное чтение дороже последовательного в 10-100 раз. Там 4.0 примерно верно.
- На SSD (solid-state drive — флеш-память без движущихся частей) случайное чтение дороже всего примерно в 2 раза. Там значение стоит снизить до 1.1-2.0.

```sql
ALTER SYSTEM SET random_page_cost = 1.1;  -- для SSD/NVMe
SELECT pg_reload_conf();
```

Без этой настройки PostgreSQL на SSD-сервере продолжает избегать Index Scan. Он всё ещё считает доступ по индексу дорогим и предпочитает Seq Scan.

## Методы доступа к данным — что выбирает Planner

```sql
EXPLAIN SELECT * FROM users WHERE email = 'max@test.com';
```

Через весь раздел проходит один термин. **Селективность** (selectivity) — это доля таблицы, которую оставляет условие. `WHERE id = 42` селективно, потому что оставляет одну строку. `WHERE country = 'USA'` не селективно совсем, если такая страна почти у всех пользователей таблицы.

**Sequential Scan (Seq Scan)** читает все страницы таблицы подряд. Последовательное чтение быстрое, поэтому это часто правильный план, а не провал. Планировщик выбирает его, когда:

- на столбце нет индекса;
- индекс есть, но селективность низкая, и под условие всё равно попадает много строк;
- таблица маленькая, и индекс на ней только добавляет накладные расходы;
- таблица раздулась после интенсивных `UPDATE`, и в ней много почти пустых страниц.

```txt
Стоимость Seq Scan — линейна по размеру таблицы:
  seq_page_cost × N_pages + cpu_tuple_cost × N_rows
```

**Index Scan** работает в два шага. Сначала обход B-Tree за O(log N). Потом для каждого найденного ключа — одно случайное чтение в heap, чтобы забрать строку, на которую указывает `ctid`. Планировщик выбирает его при высокой селективности, когда подходит мало строк.

```txt
Стоимость Index Scan:
  O(log N + K × random_page_cost), где K = число подходящих строк
```

**Bitmap Index Scan + Bitmap Heap Scan** — промежуточный вариант, и он идёт в два прохода:

1. Обойти индекс и построить в памяти битовую карту. Она помечает, в каких страницах heap лежат подходящие строки.
2. Прочитать эти страницы heap в физическом порядке, и тогда случайные чтения снова превращаются в последовательные.

Эта пересортировка страниц и есть всё преимущество перед обычным Index Scan. Из-за неё планировщик и берёт этот метод при средней селективности: строк подходит много, но не все.

**Index Only Scan** может вообще не обращаться к heap. Так бывает, когда в индексе уже есть всё, что запрос выбирает: ключ плюс столбцы из `INCLUDE`. Heap пропускается всякий раз, когда Visibility Map помечает страницу как "all-visible". Это самый быстрый вариант и главная причина строить покрывающие индексы.

| Метод доступа | Когда выбирается | Чтения из heap |
|---|---|---|
| Seq Scan | нет индекса или подходит большинство строк | все страницы, подряд |
| Index Scan | подходит мало строк | по одному случайному чтению на строку |
| Bitmap Index Scan | подходит много строк, но не большинство | нужные страницы, в физическом порядке |
| Index Only Scan | в индексе есть все выбираемые столбцы | часто ни одного |

## Алгоритмы `JOIN` — три принципиально разных подхода

**Nested Loop Join** — самый прямолинейный. Для каждой строки внешней таблицы он сканирует внутреннюю в поисках строк, подходящих под условие соединения.

```txt
ДЛЯ КАЖДОЙ строки внешней таблицы:
  ДЛЯ КАЖДОЙ строки внутренней таблицы, где выполнено условие:
    отдать пару в результат
```

Его стоимость — O(N × M), и это приемлемо только для маленьких таблиц. С индексом на внутренней таблице она падает до O(N × log M). Поэтому планировщик берёт его, когда внешний результат мал, а внутренняя таблица проиндексирована.

**Hash Join** работает в две фазы. Фаза построения (build) складывает **меньшую** таблицу в хеш-таблицу. Фаза проверки (probe) идёт по большей таблице и ищет каждую строку в этой хеш-таблице. Стоимость — O(N + M), и это отлично для больших таблиц без подходящего индекса. Ограничений два: хеш-таблица должна влезть в `work_mem`, а условием соединения может быть только равенство (`=`).

**Merge Join** требует, чтобы оба входа были отсортированы по ключу соединения. Тогда достаточно одного прохода по обоим, то есть O(N + M). Если PostgreSQL приходится сортировать их сам, добавьте O(N×log N + M×log M). Он выигрывает, когда обе таблицы большие, а нужный порядок достаётся бесплатно: из индекса или потому что запросу всё равно нужен `ORDER BY`.

| Алгоритм | Что нужно | Лучший случай |
|---|---|---|
| Nested Loop | ничего; индекс на внутренней таблице сильно помогает | маленький внешний результат, индекс на внутренней |
| Hash Join | условие-равенство, `work_mem` под хеш-таблицу | две большие таблицы без подходящего индекса |
| Merge Join | оба входа отсортированы по ключу соединения | две большие таблицы уже в нужном порядке |

## EXPLAIN и EXPLAIN ANALYZE — читаем вывод

```sql
EXPLAIN ANALYZE BUFFERS
SELECT u.id, u.email, COUNT(o.id) AS order_count
FROM users u
LEFT JOIN orders o ON o.user_id = u.id
WHERE u.created_at > '2024-01-01'
GROUP BY u.id, u.email
ORDER BY order_count DESC
LIMIT 10;
```

```txt
Пример вывода (упрощённо):
 Limit  (cost=1245.67..1245.70 rows=10 width=40)
        (actual time=23.456..23.458 rows=10 loops=1)
   ->  Sort  (cost=1245.67..1248.17 rows=1000 width=40)
         (actual time=23.454..23.455 rows=10 loops=1)
       Sort Key: count(o.id) DESC
       Sort Method: top-N heapsort  Memory: 26kB
       ->  HashAggregate  (cost=...)
             (actual time=22.1..22.8 rows=1000 loops=1)
           ->  Hash Left Join  (cost=...)
                 Hash Cond: (o.user_id = u.id)
               ->  Index Scan using idx_users_created on users u
                     Index Cond: (created_at > '2024-01-01')
                     (actual time=0.08..5.2 rows=5000 loops=1)
               ->  Hash  (cost=...)
                     Buckets: 32768  Batches: 1  Memory: 1024kB
                   ->  Seq Scan on orders o
                         (actual time=0.02..8.3 rows=85000 loops=1)
 Planning Time: 1.2 ms
 Execution Time: 23.5 ms
```

Почти всю информацию в этом выводе несут четыре вещи:

1. **`cost=start..total`** — здесь два числа, а не одно. Начальная стоимость — это работа до появления первой строки, и именно она важна при `LIMIT`. Полная стоимость — оценка всего узла. Если `actual rows` далеко от `rows`, статистика устарела и пора делать `ANALYZE`.
2. **`actual time=X..Y rows=Z loops=N`** — измеренная сторона узла. X — время до первой строки, Y — время до последней, обе в миллисекундах. Z — сколько строк узел вернул на самом деле. А `loops=N` значит, что узел выполнялся N раз, поэтому на внутренней стороне Nested Loop реальные затраты равны Y × N.
3. **`Buffers`, печатается только с опцией `BUFFERS`** — откуда взялись страницы. Счётчик `shared hit` считает страницы из `shared_buffers`, то есть из кэша в памяти: это быстро. Счётчик `shared read` считает страницы, прочитанные с диска: это медленно. Много `shared read` значит, что данные не влезают в кэш или их там ещё не было.
4. **Красные флаги** — четыре картины, на которых стоит остановиться:
   - **Seq Scan на большой таблице с `WHERE`** — столбцу, скорее всего, нужен индекс.
   - **оценка строк много ниже фактической** (`rows=1000` против `actual=100000`) — устаревшая статистика, нужен `ANALYZE`.
   - **Nested Loop с `loops=10000`** — это 10000 проходов по внутренней стороне, тут нужен индекс.
   - **`Sort Method: external merge Disk`** — сортировка ушла на диск, потому что `work_mem` слишком мал. Для тяжёлых аналитических запросов поднимите его: `SET work_mem = '256MB'`.

## Типичные причины медленных запросов и диагностика

Пять причин покрывают почти все медленные запросы на практике, и у каждой есть проверка в один оператор.

```sql
-- 1. Нет индекса / не тот индекс
EXPLAIN ANALYZE SELECT * FROM orders
WHERE status = 'pending' AND user_id = 42;
-- Если Seq Scan: добавить индекс (user_id, status) или (status, user_id)

-- 2. Устаревшая статистика
ANALYZE orders;  -- обновить статистику
-- Или проверить: SELECT * FROM pg_stat_user_tables
--                WHERE relname = 'orders';
-- n_dead_tup большой → нужен VACUUM

-- 3. Неверный порядок соединения / hash join без памяти
SET work_mem = '256MB';  -- только для этой сессии, не глобально!
EXPLAIN ANALYZE ...;     -- повторить и сравнить план

-- 4. Функция в WHERE ломает использование индекса
-- ПЛОХО: WHERE LOWER(email) = 'max@test.com' — idx_users_email не
--        используется
-- ХОРОШО: создать функциональный индекс
CREATE INDEX idx_users_email_lower ON users (LOWER(email));

-- 5. Неявное приведение типа ломает индекс
-- Если user_id типа BIGINT, а передаётся VARCHAR:
WHERE user_id = '42'  -- приведение VARCHAR→BIGINT → индекс обычно
                      -- не используется
-- Исправление: передавать правильный тип
WHERE user_id = 42
```

## pg_stat_statements — мониторинг медленных запросов в production

`pg_stat_statements` — расширение, которое ведёт нарастающую статистику по всем запросам, выполненным сервером. Именно так находят дорогие запросы в production, не запуская `EXPLAIN ANALYZE` руками на каждом.

```sql
-- Включить расширение (в postgresql.conf):
-- shared_preload_libraries = 'pg_stat_statements'

CREATE EXTENSION IF NOT EXISTS pg_stat_statements;

-- Топ-10 самых дорогих запросов
SELECT
  round(total_exec_time::numeric, 2) AS total_ms,  -- все вызовы вместе
  calls,                                        -- сколько раз запускался
  round(mean_exec_time::numeric, 2)  AS avg_ms, -- один средний вызов
  -- Доля этого запроса в суммарном времени всех запросов.
  -- sum(...) OVER () — оконная функция: считает сумму по ВСЕМ строкам
  -- результата, но оставляет каждую строку на месте (в отличие от
  -- GROUP BY).
  round((100 * total_exec_time / sum(total_exec_time) OVER ())::numeric, 1)
    AS pct,
  left(query, 100) AS query_snippet             -- первые 100 символов
FROM pg_stat_statements
ORDER BY total_exec_time DESC
LIMIT 10;
```

## Типичные ошибки на интервью

- **"`EXPLAIN` показывает реальное время выполнения"** — `EXPLAIN` без `ANALYZE` показывает только оценочную стоимость и запрос не выполняет. Реально выполняет запрос и показывает фактическое время и число строк только `EXPLAIN ANALYZE`.

- **"Planner всегда выбирает правильный план"** — он ошибается в трёх ситуациях. Статистика устарела, и вы видите это как `actual rows` намного выше оценки. Данные распределены неравномерно, есть несколько очень частых значений. Либо корреляция близка к 0: строки лежат на диске без всякой связи с порядком значений столбца.

- **"Index Scan всегда быстрее Seq Scan"** — Seq Scan выигрывает при низкой селективности, когда подходит много строк. Он неплохо конкурирует и на SSD, где случайное и последовательное чтение стоят почти одинаково. А на маленьких таблицах он выигрывает всегда.

- **"`random_page_cost` всегда должен оставаться 4.0"** — это значение настроено под вращающийся диск. На SSD снизьте его до 1.1-2.0, иначе планировщик будет избегать Index Scan.

- **"`work_mem` — глобальная настройка для всего сервера"** — он выделяется **на каждую операцию** (каждая сортировка, каждый хеш) и **на каждое соединение**. `SET work_mem = '1GB'` при 100 конкурентных соединениях — это потенциально сто гигабайт памяти. Ставьте его внутри той сессии, где он нужен, и только для тяжёлых аналитических запросов.
