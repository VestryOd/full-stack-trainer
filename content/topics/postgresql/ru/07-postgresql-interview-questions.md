# PostgreSQL: Вопросы для интервью

Вопросы сгруппированы тематически. В каждой группе — полный senior-ответ и те уточняющие вопросы, которые обычно идут следом. Цель — отрепетировать всю цепочку: базовый вопрос → уточнения → нюансы.

## Группа 1: Основы и архитектура

### Что такое PostgreSQL и чем он отличается от других СУБД?

PostgreSQL — реляционная база данных с открытым исходным кодом. Её обычно называют объектно-реляционной системой управления базами данных — ORDBMS (object-relational database management system). Это значит, что она умеет не только таблицы, но и пользовательские типы с наследованием таблиц. Лицензия — PostgreSQL License, она близка к MIT: продукт можно бесплатно использовать в коммерческой разработке.

Её определяют четыре свойства:

- **ACID-транзакции.** ACID это атомарность, консистентность, изоляция и устойчивость. Держатся они на WAL (Write-Ahead Log, журнал предзаписи): каждое изменение сначала пишется в этот журнал и только потом в файл данных.
- **MVCC (Multi-Version Concurrency Control, многоверсионность).** Чтение никогда не берёт блокировку, потому что база хранит несколько версий одной строки.
- **Богатая система типов.** JSONB (бинарный, заранее разобранный JSON), массивы, `hstore` (плоский словарь ключ-значение), диапазоны (range types) и свои типы через `CREATE TYPE`.
- **Расширяемость.** PostGIS для геоданных, `pg_stat_statements` для статистики запросов, `pgcrypto` для шифрования.

```sql
-- "Объектно-реляционная" в двух операторах
CREATE TYPE address AS (city text, zip text);   -- свой тип данных
CREATE TABLE staff (id serial, home address);   -- и он же как тип столбца
```

По сравнению с MySQL, PostgreSQL строже следует стандарту SQL (Structured Query Language). Он также из коробки поддерживает более сложные формы запросов:

- **оконные функции** (window functions) — считают по группе строк, но оставляют каждую строку в результате. Так пишут рейтинги и накопительные суммы.
- **CTE** — обобщённые табличные выражения (common table expressions). Конструкция `WITH имя AS (...)` даёт подзапросу имя, и его можно переиспользовать.
- **`LATERAL JOIN`** — соединение, правая часть которого может ссылаться на каждую строку левой.
- **JSONB с GIN-индексами** — GIN это generalized inverted index, обобщённый обратный индекс. Он индексирует содержимое документа, поэтому искать можно по ключу внутри JSONB.

| Задача | Обычно PostgreSQL | Обычно MySQL |
|---|---|---|
| Сложные запросы, соединения, аналитика | да, стандарт соблюдается строго | исторически слабее |
| Простые короткие чтения и записи | справляется полностью | исторически быстрее |
| Документы и полуструктурированные данные | JSONB плюс GIN-индексы | поддержка JSON слабее |
| Геоданные | PostGIS | аналога нет |

MySQL исторически был быстрее на простом OLTP (online transaction processing — много коротких чтений и записей), но PostgreSQL давно сравнялся.

**Типичные уточняющие вопросы**

- *"Что значит «объектно-реляционная»?"* — Наследование таблиц (`CREATE TABLE child INHERITS parent`), пользовательские типы (`CREATE TYPE`), перегрузка операторов и массивы как родной тип данных. Всё это выходит за рамки чистой реляционной модели Кодда.
- *"Когда выбрать PostgreSQL вместо MySQL?"* — Для сложных запросов с соединениями, для аналитики, для работы с JSONB и для геоданных через PostGIS. А также когда важно соответствие стандарту. MySQL предпочтительнее для простой транзакционной нагрузки с очень высоким темпом записи (MySQL Cluster) или когда экосистема MySQL уже налажена.

### Как SQL-запрос проходит через PostgreSQL?

Запрос проходит шесть стадий, и название каждой на интервью ожидают услышать:

1. **Parser** → AST (abstract syntax tree — текст запроса, разобранный в дерево). Синтаксические ошибки находятся здесь.
2. **Analyzer** → дерево запроса. Разрешаются имена таблиц, имена столбцов и типы.
3. **Rewriter** → правила. Раскрываются представления (VIEW) и применяются политики RLS. RLS это row-level security: правила доступа к отдельным строкам таблицы.
4. **Planner / Optimizer** → оптимизация по стоимости, выбор одного плана из многих.
5. **Executor** → выполняет выбранный план и возвращает строки.
6. **Buffer Manager** → отдаёт страницы из `shared_buffers`, кэша страниц в памяти. При промахе идёт на диск.

```sql
-- Последняя стадия, показанная наглядно
SHOW shared_buffers;   -- 128MB на установке по умолчанию
EXPLAIN (ANALYZE, BUFFERS) SELECT * FROM users WHERE id = 1;
-- Buffers: shared hit=3 → три страницы пришли из кэша, а не с диска
```

**Типичные уточняющие вопросы**

- *"Что такое `shared_buffers`?"* — Общий кэш страниц данных в памяти. По умолчанию 128MB, обычно его настраивают примерно на 25% памяти машины. Страница читается с диска один раз и кэшируется, поэтому дальше её отдают из памяти.
- *"Что такое WAL?"* — Write-Ahead Log, журнал операций. Прежде чем данные дойдут до файла данных, запись попадает в WAL и сбрасывается вызовом `fsync`. Это и даёт A и D из ACID: после сбоя повторное применение WAL восстанавливает состояние.

## Группа 2: ACID и транзакции

### Объясните каждый из принципов ACID с примером реализации в PostgreSQL

- **A — атомарность.** Реализована через WAL (Write-Ahead Log — журнал, который пишется раньше файла данных). Либо все операции транзакции попадают в heap при `COMMIT`, либо WAL используется, чтобы отменить их все. Отмена работает и при `ROLLBACK`, и при восстановлении после сбоя. Примитивы — `BEGIN`, `COMMIT` и `ROLLBACK`.
- **C — консистентность.** PostgreSQL следит за ограничениями на момент `COMMIT`: `NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`. Бизнесовая консистентность вида "баланс не может уйти в минус" работает только если вы её записали как `CHECK (balance >= 0)`.
- **I — изоляция.** Реализована через снапшоты MVCC. MVCC это Multi-Version Concurrency Control, многоверсионность. Рабочих уровней три: `READ COMMITTED`, `REPEATABLE READ` и `SERIALIZABLE`. Первый берёт снапшот на каждый оператор, второй — один снапшот на транзакцию. `SERIALIZABLE` добавляет SSI (Serializable Snapshot Isolation), который отслеживает зависимости между транзакциями.
- **D — устойчивость.** WAL сбрасывается вызовом `fsync` до того, как клиенту подтвердят `COMMIT`. Настройка `synchronous_commit = on` гарантирует устойчивость. Значение `off` быстрее, но при сбое можно потерять около 200 мс данных.

```sql
-- SAVEPOINT: точка частичного отката внутри одной транзакции
BEGIN;
INSERT INTO orders (user_id, total) VALUES (1, 500);

SAVEPOINT after_order;
INSERT INTO payments (order_id, amount)
VALUES (currval('orders_id_seq'), 500);
-- Допустим, платёж не прошёл

ROLLBACK TO after_order;  -- отменяет платёж, заказ остаётся
INSERT INTO payments (order_id, method, amount)
VALUES (currval('orders_id_seq'), 'alternative', 500);
COMMIT;
```

**Типичные уточняющие вопросы**

- *"Что такое `SAVEPOINT`?"* — Точка частичного отката внутри транзакции, как в примере выше. `ROLLBACK TO SAVEPOINT` отменяет только операции после этой точки, а не всю транзакцию. Так пробуют операцию, при ошибке откатывают только её и продолжают ту же транзакцию другим путём.
- *"Что случится, если не вызвать `COMMIT` или `ROLLBACK`?"* — При разрыве соединения PostgreSQL сам откатит незавершённую транзакцию. Настоящая проблема — пул соединений. Соединение, возвращённое в пул без `COMMIT` или `ROLLBACK`, отдаст следующему клиенту транзакцию в состоянии "aborted". Все запросы будут отклоняться, пока кто-нибудь не выполнит явный `ROLLBACK`.

### Как работает Deadlock и как его предотвратить?

Deadlock — это циклическое ожидание блокировок. Транзакция A держит строку 1 и ждёт строку 2, а транзакция B держит строку 2 и ждёт строку 1. Двигаться не может ни одна, поэтому сама собой ни одна не завершится.

```sql
-- Классический deadlock (транзакции идут одновременно)
-- Транзакция A:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- (пауза; B выполняет свой первый UPDATE)
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- Транзакция B:
BEGIN;
UPDATE accounts SET balance = balance - 50  WHERE id = 2;
-- (пауза; A выполняет свой первый UPDATE)
UPDATE accounts SET balance = balance + 50  WHERE id = 1;
COMMIT;
-- → ERROR: deadlock detected — одна транзакция откатывается
```

PostgreSQL находит цикл в графе ожидания блокировок по истечении `deadlock_timeout`, по умолчанию это 1 секунда. Дальше он откатывает "жертву" с сообщением `ERROR: deadlock detected` и кодом ошибки `40P01`. Этот код — SQLSTATE, стандартный пятисимвольный идентификатор ошибки.

Профилактика — это дисциплина, а не настройка: блокируйте строки в **одинаковом порядке** во всех транзакциях. В примере выше обеим транзакциям надо было сначала брать `id = 1`, потом `id = 2`. Кроме этого, приложение обязано перехватывать `40P01` и повторять транзакцию.

**Типичные уточняющие вопросы**

- *"Чем deadlock отличается от конкуренции за блокировку (lock contention)?"* — Конкуренция за блокировку — это высокий спрос на одну блокировку. Вторая транзакция просто ждёт, пока первая её отпустит, поэтому всё разрешается само при `COMMIT` или `ROLLBACK`. Deadlock — **циклическое** ожидание, и само оно не разрешится никогда. Базе приходится откатить одну транзакцию.

## Группа 3: Уровни изоляции

### Опишите разницу между `READ COMMITTED`, `REPEATABLE READ` и `SERIALIZABLE`

Все три построены на снапшотах MVCC. MVCC это Multi-Version Concurrency Control: база хранит несколько версий строки, а снапшот решает, какую версию видит транзакция.

- **`READ COMMITTED`** (по умолчанию) берёт свежий снапшот на каждый **оператор**. Он видит всё, что зафиксировано до начала очередного `SELECT`. Поэтому возможно неповторяющееся чтение: повторите тот же `SELECT` и получите другое значение, если между ними другая транзакция сделала `COMMIT`.
- **`REPEATABLE READ`** берёт снапшот **один раз**, в начале транзакции. Дальше все `SELECT` видят одни и те же данные. Благодаря MVCC PostgreSQL здесь защищает ещё и от фантомных чтений, хотя стандарт SQL этого не требует. Аномалия write skew при этом остаётся возможной.
- **`SERIALIZABLE`** добавляет SSI — Serializable Snapshot Isolation. PostgreSQL отслеживает зависимости по чтению и записи между конкурентными транзакциями. Если их совместный результат не соответствует никакому последовательному порядку, одну из них откатывают. Код ошибки — `40001`, сообщение — `could not serialize access due to read/write dependencies among transactions`. Конфликт обновления на `REPEATABLE READ` даёт более короткое сообщение `could not serialize access due to concurrent update`. В любом случае приложение обязано делать повтор.

```sql
-- Write skew: оба врача уходят с дежурства, и не остаётся никого
-- Транзакция A (врач 1):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- → 2
UPDATE doctors SET on_call = false WHERE id = 1;
COMMIT;

-- Транзакция B (врач 2, в это же время):
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
SELECT COUNT(*) FROM doctors WHERE on_call = true;  -- → 2, тот же снапшот
UPDATE doctors SET on_call = false WHERE id = 2;
COMMIT;
-- Итог: дежурных нет. SERIALIZABLE откатил бы одну из транзакций.
```

**Типичные уточняющие вопросы**

- *"Что такое write skew?"* — Это аномалия из примера выше. Каждая транзакция по отдельности инвариант "кто-то остаётся на дежурстве" не нарушает, потому что каждая всё ещё видит двух врачей. А вместе они его нарушают. `REPEATABLE READ` здесь не защищает, а `SERIALIZABLE` обнаруживает конфликт через SSI.
- *"PostgreSQL поддерживает `READ UNCOMMITTED`?"* — Технически да: оператор `SET TRANSACTION ISOLATION LEVEL READ UNCOMMITTED` принимается. Ведёт он себя как `READ COMMITTED`, потому что из-за MVCC грязное чтение физически невозможно.

## Группа 4: Индексы и внутреннее устройство

### Объясните B-Tree индекс, Left Prefix Rule и когда Planner не использует индекс

**B-Tree** — сбалансированное дерево высотой O(log N). Его листовые узлы отсортированы и связаны в двусвязный список, и именно поэтому диапазонные запросы работают эффективно. Поддерживаются `=`, `<`, `<=`, `>`, `>=`, `BETWEEN` и `ORDER BY`.

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

**Left Prefix Rule** описывает, что такой составной индекс умеет. Ключи отсортированы сначала по `user_id`, потом по `status` внутри одного `user_id`. Если `user_id` не зафиксирован, значения `status` разбросаны по всему индексу и найти их эффективно нельзя. Поэтому индекс работает для `(user_id)` и для `(user_id, status)`, но не для одного `status`.

**Планировщик не использует индекс** в пяти случаях:

- селективность низкая, как в `WHERE country = 'USA'`, когда под условие попадает 90% пользователей — тогда Seq Scan просто дешевле;
- таблица маленькая, и индекс на ней только добавляет накладные расходы;
- столбец обёрнут функцией, как в `WHERE LOWER(email) = ...`;
- между столбцом и значением стоит неявное приведение типа;
- `random_page_cost` выставлен слишком высоким для реального диска, а это обычная ситуация на флеш-накопителях.

**Типичные уточняющие вопросы**

- *"Что такое частичный индекс (partial index)?"* — Индекс со своим условием `WHERE`, например `CREATE INDEX ... ON orders(created_at) WHERE status = 'pending'`. Он индексирует только часть строк, поэтому меньше и быстрее. Запрос с тем же условием `WHERE` использует его автоматически.
- *"Что такое Index-Only Scan?"* — Всё, что нужно `SELECT`, берётся прямо из индекса: ключ плюс столбцы из `INCLUDE`. Условий два. Все выбираемые поля есть в индексе, и Visibility Map помечает страницы heap как "all-visible".
- *"Чем BRIN отличается от B-Tree?"* — BRIN это Block Range INdex. Он хранит только минимум и максимум по диапазону блоков, поэтому измеряется десятками килобайт там, где B-Tree измеряется гигабайтами. Работает он только при сильной корреляции физического порядка строк и значения столбца: временны́е ряды или логи, куда только добавляют. На случайно расположенных данных BRIN бесполезен.

## Группа 5: MVCC, VACUUM, блокировки

### Объясните MVCC — механизм и зачем PostgreSQL хранит несколько версий строки

MVCC расшифровывается как Multi-Version Concurrency Control, многоверсионное управление конкурентностью. Вместо блокировки строки при чтении PostgreSQL хранит несколько версий этой строки одновременно.

```sql
UPDATE accounts SET balance = 200 WHERE id = 1;
-- Старая строка НЕ перезаписывается:
--   в её xmax ← попадает XID (идентификатор транзакции) этой транзакции
--   в heap вставляется новая строка, у неё xmin = тот же XID
```

У каждой читающей транзакции свой снапшот, и состоит он из `xmin`, `xmax` и `xip` (списка ещё работающих транзакций). Снапшот и решает, какую версию каждой строки этой транзакции видно.

Результат — фраза, которую стоит запомнить: читатели не блокируют писателей, а писатели не блокируют читателей. Это параллелизм без единой блокировки на чтение.

**Типичные уточняющие вопросы**

- *"Что такое мёртвый кортеж (dead tuple) и откуда он берётся?"* — Это старая версия строки после `UPDATE` или `DELETE`. Её `xmax` заполнен. Транзакциям она больше не нужна, но физически всё ещё лежит в heap. Она занимает место и замедляет Seq Scan, потому что видимость надо проверять у каждой версии.
- *"Что делает `VACUUM` и чем от него отличается `VACUUM FULL`?"* — Обычный `VACUUM` помечает место мёртвых кортежей свободным в FSM (Free Space Map). Ещё он удаляет мёртвые записи индекса и обновляет Visibility Map. Чего он не делает — не возвращает место операционной системе. `VACUUM FULL` перестраивает таблицу с нуля и место возвращает. Цена — блокировка `ACCESS EXCLUSIVE`, которая останавливает на таблице всё. В production вместо него берут `pg_repack`.
- *"Зачем `VACUUM` нужен против переполнения счётчика транзакций?"* — PostgreSQL считает транзакции 32-битным XID (идентификатором транзакции). `VACUUM` замораживает старые строки, то есть обнуляет `xmin` у строк, которые уже видны всем транзакциям. Без заморозки счётчик пойдёт по кругу через 2^32 транзакций. Тогда PostgreSQL перестанет принимать запросы, чтобы не потерять данные.
- *"Когда нужен `SELECT ... FOR UPDATE`?"* — В паттерне "check-then-act": прочитали значение, проверили бизнес-условие, обновили. Без `FOR UPDATE` возникает гонка. Две транзакции читают одно значение, обе считают условие выполненным, обе обновляют — и инвариант нарушен. Обычному чтению без последующего `UPDATE` он не нужен.

## Группа 6: Планировщик запросов и производительность

### Как работает EXPLAIN ANALYZE и что в нём искать?

`EXPLAIN` печатает план выполнения с оценочной стоимостью и оценочным числом строк, но запрос не выполняет. `EXPLAIN ANALYZE` действительно выполняет его и добавляет измеренные значения: actual time, actual rows и loops.

```sql
-- Всегда добавляйте BUFFERS для полной картины чтений с диска и из кэша
EXPLAIN (ANALYZE, BUFFERS, FORMAT TEXT) SELECT ...;
```

В выводе стоит искать пять вещей:

- **Seq Scan на большой таблице с `WHERE`** → этому столбцу нужен индекс.
- **оценка строк ≠ фактическое число** (`rows=100` против `actual=100000`) → статистика устарела, нужен `ANALYZE`.
- **Nested Loop с большим `loops`** → один и тот же поиск повторяется тысячи раз, это SQL-версия проблемы N+1. Внутренней стороне нужен индекс.
- **`Sort Method: external merge Disk`** → `work_mem` слишком мал, и сортировка ушла на диск. Поднимите его в сессии: `SET work_mem = '256MB'`.
- **высокий `shared read`** → данные не влезают в `shared_buffers`, поэтому запрос читает с диска.

**Типичные уточняющие вопросы**

- *"Почему Planner иногда выбирает Seq Scan при наличии индекса?"* — Потому что он сравнивает стоимости. При низкой селективности подходит много строк, и случайные чтения через индекс дороже одного последовательного прохода. Ещё две причины встречаются часто. `random_page_cost` может быть слишком высоким для SSD (solid-state drive), где его стоит снизить до 1.1-2.0. И функция вокруг столбца в `WHERE` полностью ломает использование индекса.
- *"Что такое `pg_stat_statements`?"* — Расширение, которое накапливает статистику по **всем** выполненным запросам: `total_exec_time`, `calls`, `mean_exec_time`. Оно позволяет найти дорогие запросы в production, не запуская `EXPLAIN ANALYZE` на каждом. Ему нужна настройка `shared_preload_libraries = 'pg_stat_statements'`.
- *"Как найти медленные запросы в production без остановки?"* — `pg_stat_statements` — тот ответ, которого ждут. Стоит назвать ещё три инструмента. `pg_stat_activity` показывает запросы, работающие прямо сейчас. `log_min_duration_statement` логирует все запросы медленнее N миллисекунд. `auto_explain` автоматически пишет в лог план медленного запроса.
