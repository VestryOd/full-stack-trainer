# Индексы и внутреннее устройство

## Индекс — отдельная структура данных, торгующая пространством и скоростью записи на скорость чтения

Индекс покупает скорость чтения, а платит за неё дисковым местом и скоростью записи. Весь компромисс укладывается в одно предложение.

Без индекса `WHERE email = 'max@test.com'` на таблице из 10 миллионов строк превращается в Sequential Scan. PostgreSQL читает **все** страницы heap-файла, по 8 КБ (8192 байта) каждая, и проверяет каждую строку. Сложность — O(n).

Индекс хранит отображение значений столбца в физическое расположение строк: номер страницы плюс смещение внутри этой страницы. Цена — дополнительное место на диске и работа при каждой записи: `INSERT`, `UPDATE` и `DELETE` обязаны обновлять ещё и структуру индекса.

## B-Tree — индекс по умолчанию, и почему он работает для большинства задач

```txt
           [50]
         /      \
     [25]        [75]
    /    \      /    \
[10,20] [30,40] [60,70] [80,90]
```

B-Tree расшифровывается как balanced tree, сбалансированное дерево. Выбор по умолчанию он получил за три свойства:

- Каждый узел содержит упорядоченные ключи и указатели на дочерние узлы. На листьях эти указатели ведут уже на строки в heap.
- Все листовые узлы лежат на одной глубине, поэтому дерево остаётся сбалансированным.
- Листья связаны между собой в двусвязный список. Благодаря этому эффективны запросы по диапазону: `BETWEEN`, `<`, `>`.

При 1 000 000 строк высота дерева — примерно log₁₀₀(1 000 000) ≈ 3 уровня. Узлы B-Tree в PostgreSQL хранят по сотне ключей и больше, так что это не двоичное дерево. Реальный поиск стоит 3-4 операции I/O (input/output — одно чтение или запись на диске). Seq Scan по той же таблице читает 10 000+ страниц.

B-Tree поддерживает `=`, `<`, `<=`, `>`, `>=`, `BETWEEN`, `LIKE 'prefix%'`, `IS NULL` и `ORDER BY`. Последнее работает потому, что индекс уже отсортирован, и шаг сортировки можно пропустить целиком.

B-Tree **не** поддерживает `LIKE '%suffix'`, полнотекстовый поиск и семейство операторов `@>`.

## Внутренности: как PostgreSQL хранит данные и индексы на диске

```txt
Heap file (таблица):
  ┌───────────┬───────────┬───────────┐
  │  Page 0   │  Page 1   │  Page 2   │  ← страницы по 8 КБ
  │ (8192 B)  │ (8192 B)  │ (8192 B)  │
  └───────────┴───────────┴───────────┘
```

Каждая страница состоит из четырёх частей:

- `PageHeader` — 24 байта.
- `ItemIdData` — массив указателей на строки.
- Свободное место, оставленное под новые строки.
- Tuple data — сами строки, которые PostgreSQL называет tuples.

Каждая строка состоит из двух частей:

- `HeapTupleHeader`, 23 байта: `xmin` и `xmax` (их использует MVCC, Multi-Version Concurrency Control), а также `natts`, `infomask` и другие.
- Собственно данные столбцов.

Файл индекса собран из таких же страниц по 8 КБ, но внутри них лежат узлы B-Tree. Листовые страницы хранят пары `(key_value, ctid)`, где `ctid` — это `(page_number, item_offset)`, физическое расположение строки в heap.

## Composite Index и Left Prefix Rule — самый частый вопрос на интервью

```sql
CREATE INDEX idx_orders_user_status ON orders(user_id, status);
```

Составной индекс хранит ключи как пару `(user_id, status)`. Они отсортированы сначала по `user_id`, а внутри одного `user_id` — по `status`.

Индекс **работает** для:

- `WHERE user_id = 5` — только левый префикс.
- `WHERE user_id = 5 AND status = 'paid'` — оба поля.
- `WHERE user_id = 5 AND status > 'paid'` — диапазон по правому полю.
- `ORDER BY user_id, status` — сортировка.

Индекс **не** работает эффективно для `WHERE status = 'paid'` — это правый столбец без левого. PostgreSQL всё ещё может сделать Index Scan с фильтром, но эффективность падает до O(n), потому что придётся просмотреть весь индекс.

Почему: данные в индексе отсортированы по `(user_id, status)`. Не зафиксировав `user_id`, нельзя прыгнуть прямо к нужному `status`. Этот status разбросан по всему индексу, внутри каждой секции `user_id`.

```sql
-- Правильный порядок столбцов в составном индексе:
-- 1. Столбцы с условием равенства (=) — первыми
-- 2. Столбцы с условием диапазона (<, >, BETWEEN) — последними
-- 3. Столбцы только для ORDER BY/GROUP BY — в конце

-- Запрос: WHERE user_id = 5 AND created_at > '2024-01-01'
-- Правильный индекс: (user_id, created_at), НЕ (created_at, user_id)
CREATE INDEX idx ON orders(user_id, created_at);
```

## Partial Index — индексируем только нужное подмножество строк

```sql
-- Индекс только для активных пользователей
CREATE INDEX idx_users_email_active ON users(email)
WHERE is_active = true;

-- Индекс для неоплаченных заказов (предположим, их 5% от всех)
CREATE INDEX idx_orders_pending ON orders(created_at)
WHERE status = 'pending';
```

Два преимущества:

- Размер индекса равен доле строк, которые проходят условие `WHERE`. Если неоплаченных заказов 5%, индекс получается в 20 раз меньше полного.
- Меньший индекс гораздо легче умещается в `shared_buffers` — это кэш страниц, который PostgreSQL держит в памяти.

Вдобавок запросы с тем же условием `WHERE` подхватывают такой индекс автоматически.

Одно ограничение: запрос **обязан** содержать то же условие или более строгое. Иначе планировщик вообще не сможет использовать частичный индекс.

## Covering Index — Index-Only Scan без обращения к heap

```sql
-- Запрос: SELECT id, email FROM users WHERE email = 'max@test.com'
-- Без INCLUDE: Index Scan (нашли строку в индексе → fetch из heap)
CREATE INDEX idx_users_email ON users(email);

-- С INCLUDE: Index-Only Scan (все нужные данные в индексе)
CREATE INDEX idx_users_email_covering ON users(email) INCLUDE (id);
```

Index-Only Scan работает только при двух условиях одновременно:

1. Все столбцы, которые просит `SELECT`, есть в индексе — как ключи или внутри `INCLUDE`.
2. Visibility Map говорит, что страница heap «all-visible». Это значит, что все строки на странице видны всем транзакциям, то есть `VACUUM` её уже обработал.

Без второго условия PostgreSQL всё равно идёт в heap: видимость определяется по версиям строк MVCC, которые лежат именно там. Поэтому свежая таблица с интенсивной записью часто не получает от Index-Only Scan никакого выигрыша.

## Специализированные типы индексов

Четыре названия, три из них — сокращения, которые стоит расшифровать:

- **GIN** — generalized inverted index, обобщённый инвертированный индекс. Для многозначных типов: JSONB (это JSON, разобранный в двоичную форму), массивы, полнотекстовый поиск.
- **GiST** — generalized search tree, обобщённое поисковое дерево. Для геометрии, диапазонов и PostGIS, расширения для геоданных.
- **BRIN** — block range index, индекс по диапазонам блоков. Для очень больших таблиц, где строки уже физически упорядочены по значению столбца.
- **Hash** — обычная хеш-таблица. O(1) для `=`, и больше ничего.

```sql
-- GIN (Generalized Inverted Index) — для многозначных типов
-- JSONB, массивы, полнотекстовый поиск (tsvector)
CREATE INDEX idx_products_attrs ON products USING GIN (attributes);
CREATE INDEX idx_articles_search ON articles
  USING GIN (to_tsvector('english', body));
-- GIN строит инвертированный индекс: значение → множество строк
-- Быстр для @>, ?, ?|, @@; медленнее при записи (перестройка списков)

-- GiST (Generalized Search Tree) — для геометрии, диапазонов, PostGIS
CREATE INDEX idx_geom ON places USING GIST (location);
CREATE INDEX idx_range ON events USING GIST (during);  -- tstzrange
-- GiST поддерживает: &&, @>, <->, <<, >>...

-- BRIN (Block Range INdex) — для очень больших таблиц с корреляцией
-- Хранит мин/макс значение по диапазонам страниц (блокам)
CREATE INDEX idx_logs_ts ON logs USING BRIN (created_at);
-- Эффективен, когда физический порядок строк коррелирует со значением
-- (временны́е ряды, append-only таблицы логов)
-- Размер индекса: несколько десятков КБ против десятков ГБ для B-Tree
```

```sql
-- Hash — O(1) для =, диапазоны не поддерживает,
-- а до PostgreSQL 10 он не журналировался в WAL
CREATE INDEX idx_users_email_hash ON users USING HASH (email);
-- В большинстве случаев B-Tree быстрее и функциональнее
```

## Когда планировщик НЕ использует индекс — и это правильно

```sql
-- Индекс на is_active (boolean), 99% строк = true
EXPLAIN SELECT * FROM users WHERE is_active = true;
-- → Seq Scan! (Planner оценил: индекс даст 99% строк,
--   Seq Scan дешевле, чем 990 000 random I/O через индекс)

-- Индекс на is_active используется, если:
EXPLAIN SELECT * FROM users WHERE is_active = false;
-- → Index Scan (строк всего 1% — их достаточно мало,
--   чтобы случайный доступ через индекс окупился)
```

Планировщик принимает решение по статистике из `pg_statistic`:

- `n_distinct` — сколько в столбце уникальных значений.
- `correlation` — насколько физический порядок строк совпадает с порядком значений в индексе. Высокая корреляция делает Seq Scan привлекательнее.
- `most_common_vals` и `most_common_freqs` — частоты самых частых значений.

Обновляет эту статистику `ANALYZE`, а устаревшая статистика даёт неверные планы. В PostgreSQL 14+ autovacuum запускает `ANALYZE` автоматически.

## Цена индексов при записи — как оценить trade-off

Каждый индекс добавляет работу к `INSERT`, `UPDATE` и `DELETE`:

- `INSERT` — в B-Tree добавляется новая запись, O(log n), возможно с расщеплением страницы (page split).
- `UPDATE` по индексируемому столбцу — логически это `DELETE` плюс `INSERT` в B-Tree. В PostgreSQL `UPDATE` создаёт новую версию строки через MVCC, поэтому индексная запись старой версии становится мёртвой.
- `DELETE` — запись индекса помечается мёртвой. Физически её удалит `VACUUM` позже.

Мёртвые записи в индексе — это раздувание (bloat), и убирает их `VACUUM`.

```sql
-- Сколько места занимает каждый индекс и как часто он реально нужен
SELECT indexrelname,
       pg_size_pretty(pg_relation_size(indexrelid)) AS size,
       idx_scan AS times_used
FROM pg_stat_user_indexes
WHERE relname = 'orders'
ORDER BY pg_relation_size(indexrelid) DESC;
```

```txt
     indexrelname        |  size  | times_used
-------------------------+--------+------------
 idx_orders_user_status  | 214 MB |    1840512
 idx_orders_created_at   | 198 MB |          0   ← только расходы
 idx_orders_pending      |  11 MB |      92310
```

На практике: не создавайте индексы «на всякий случай». Каждый индекс должен решать одну конкретную задачу, подтверждённую через `EXPLAIN ANALYZE`.

## Типичные ошибки на интервью

- **"Индекс всегда ускоряет `SELECT`"** — планировщик выбирает Seq Scan, когда селективность низкая. На таблице, где 99% строк имеют `is_active = true`, random I/O через индекс дороже последовательного чтения heap.

- **"Составной индекс (a, b) работает для `WHERE b = ?`"** — нет, и у причины есть название: Left Prefix Rule. Без левого столбца `a` в условии индекс используется неэффективно или не используется вовсе.

- **"Больше индексов = быстрее"** — каждый индекс замедляет `INSERT`, `UPDATE` и `DELETE`. Каждый индекс ещё и добавляет раздувание, которое потом вычищает `VACUUM`.

- **"`INCLUDE` в индексе — то же самое, что добавить столбец в ключ"** — это не так. Столбцы из `INCLUDE` не влияют на порядок сортировки в B-Tree, поэтому в поиске по дереву не участвуют. Они лежат в листовых узлах, и именно это делает возможным Index-Only Scan.

- **"BRIN-индекс подходит для всех таблиц"** — в общем случае нет. BRIN эффективен только тогда, когда физический порядок строк коррелирует со значением столбца, например `created_at` в append-only таблице. Для случайно вставляемых данных BRIN бесполезен.
