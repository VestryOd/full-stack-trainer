# Основы PostgreSQL

## PostgreSQL — не просто "реляционная БД", а объектно-реляционная СУБД с богатой системой типов

PostgreSQL — это ОРСУБД (объектно-реляционная система управления базами данных) с открытым исходным кодом. БД — это база данных, а СУБД — программа, которая ей управляет. В названии важны обе половины.

**«Объектно-реляционная»** значит, что PostgreSQL умеет больше, чем обычные таблицы. Она поддерживает наследование таблиц, пользовательские типы (`CREATE TYPE`), перегрузку операторов и собственные агрегатные функции. Все четыре возможности выходят за рамки стандарта SQL:2016 и за рамки классической реляционной модели Кодда.

SQL расшифровывается как Structured Query Language — стандартный язык запросов к реляционным данным.

```sql
-- "Объектно-реляционная" на одном примере: свой тип как тип столбца
CREATE TYPE address AS (city TEXT, street TEXT, zip TEXT);

CREATE TABLE customers (
    id      BIGSERIAL PRIMARY KEY,
    name    TEXT NOT NULL,
    billing address       -- одно составное значение, а не три столбца
);

INSERT INTO customers (name, billing)
VALUES ('Ada', ROW('Киев', 'Крещатик 1', '01001'));

SELECT name, (billing).city FROM customers;  -- → Ada | Киев
```

**«Открытый исходный код»** значит, что код полностью открыт под лицензией PostgreSQL. Эта лицензия близка к MIT: можно бесплатно поставлять PostgreSQL внутри коммерческого продукта. Сообщество развивает проект с 1996 года. Управляет им PostgreSQL Global Development Group.

На интервью важно: «PostgreSQL — самая продвинутая реляционная база данных с открытым исходным кодом» — это стандартная формулировка самого проекта. Три конкретных отличия от MySQL:

- PostgreSQL строже следует стандарту SQL.
- Она лучше обрабатывает сложные `JOIN`.
- Читатели никогда не берут блокировок — за это отвечает MVCC (Multi-Version Concurrency Control, многоверсионность: база хранит несколько версий одной строки). Подробнее — [MVCC, блокировки и VACUUM](./05-mvcc-locks-vacuum.md).

## Путь SQL-запроса через внутренние слои PostgreSQL

Запрос не попадает на диск напрямую. Он проходит пять стадий внутри сервера, и каждая переписывает его в более низкоуровневую форму.

```txt
Приложение (psql / Prisma / pg)
│  SQL-текст по TCP (протокол PostgreSQL wire protocol)
▼
  ┌─────────────────────────────────────────────────┐
  │ Parser            — строит AST из SQL           │
  │ Analyzer          — разрешает имена             │
  │                     (таблицы, столбцы,          │
  │                     типы) → Query Tree          │
  │ Rewriter          — применяет правила           │
  │                     (VIEW expansion,            │
  │                     RLS-политики)               │
  │ Planner/Optimizer — строит несколько планов,    │
  │                     выбирает план с минимальной │
  │                     оценочной стоимостью        │
  │ Executor          — выполняет план,             │
  │                     возвращает строки           │
  └─────────────────────────────────────────────────┘
│
▼
Buffer Manager (shared_buffers — кэш страниц в RAM)
│  промах кэша
▼
Storage (heap files, index files на диске)
```

Три сокращения на этой схеме стоит расшифровать:

- **AST** — abstract syntax tree, то есть разобранный запрос в виде дерева.
- **RLS** — row-level security, правила доступа на уровне строк. PostgreSQL подмешивает их в запрос как дополнительные условия `WHERE`.
- **RAM** — оперативная память сервера, в отличие от диска.

**Senior-нюанс:** планировщик (Planner) — самая сложная часть. Он оценивает стоимость по статистике (`pg_statistic`, её собирает `ANALYZE`) и выбирает между Seq Scan, Index Scan, Bitmap Scan, Hash Join, Merge Join и другими. Неверная статистика даёт неверный план, а неверный план — медленный запрос. Подробнее — [Планировщик запросов и EXPLAIN](./06-query-planner-explain.md).

## Иерархия объектов: Cluster → Database → Schema → Table → Row → Column

Шесть уровней — от целого сервера до одного значения:

- **Cluster** — весь экземпляр PostgreSQL: один процесс `postmaster`, один каталог данных. Содержит **несколько** баз данных.
- **Database** — логически изолированный контейнер. Транзакция не может затронуть данные в **другой** базе. Запросы между базами идут только через `dblink` или `postgres_fdw`.
- **Schema** — пространство имён внутри базы. По умолчанию это `public`. В одном экземпляре может быть много схем: например, по схеме на клиента в multi-tenant SaaS (software as a service — продукт как сервис по подписке).
- **Table** — набор строк одного «типа», то есть одной структуры столбцов. Физически это heap-файл: куча страниц по 8 КБ (8192 байта).
- **Row (tuple)** — одна запись. Во внутренней документации PostgreSQL строку называют «tuple».
- **Column** — атрибут таблицы. У него есть тип данных и набор ограничений (constraints).

```sql
-- Демонстрация иерархии
CREATE DATABASE app_db;

\c app_db

CREATE SCHEMA billing;

CREATE TABLE billing.invoices (
    id          BIGSERIAL PRIMARY KEY,
    user_id     BIGINT NOT NULL REFERENCES public.users(id),
    amount      NUMERIC(12, 2) NOT NULL CHECK (amount > 0),
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
```

## Типы данных — выбор типа влияет на размер, индексы и поведение

Выбор типа сразу решает три вещи. Он задаёт, сколько байт занимает строка, какие индексы можно по ней построить и как ведут себя сравнения.

Ниже — рабочий набор для прикладного кода, в каждой группе помечен предпочтительный вариант. В списке встречается одно название индекса: **GIN** — generalized inverted index, инвертированный индекс. Только он умеет индексировать содержимое значения JSONB, а JSONB — это JSON, разобранный в двоичную форму.

```sql
-- Числа
INTEGER        -- 4 байта, -2.1млрд..+2.1млрд
BIGINT         -- 8 байт, ±9.2×10^18  ← для user_id, счётчиков
SERIAL         -- автоинкремент на INTEGER (реализован через SEQUENCE)
BIGSERIAL      -- автоинкремент на BIGINT (предпочтительно для ключа)
NUMERIC(p, s)  -- произвольная точность, точные деньги; медленнее float
REAL / FLOAT8  -- IEEE 754 float; не для денег (потеря точности)

-- Строки
TEXT           -- переменная длина, нет ограничения (предпочтительно)
VARCHAR(n)     -- как TEXT, но с ограничением длины (в PostgreSQL нет
               -- разницы в производительности vs TEXT — оба VARLENA)
CHAR(n)        -- фиксированная длина, дополняется пробелами — почти
               -- никогда не нужен в современных приложениях

-- Дата и время
DATE           -- только дата (без времени суток)
TIMESTAMP      -- дата + время, без часового пояса (хранит "стену")
TIMESTAMPTZ    -- дата + время + нормализация к UTC (рекомендуется для
               -- всего, что увидят пользователи из разных поясов)
INTERVAL       -- промежуток времени (INTERVAL '3 months')

-- Булево
BOOLEAN        -- TRUE / FALSE / NULL (три состояния)

-- JSON
JSON           -- хранит исходный текст JSON как есть (разбор при
               -- каждом обращении)
JSONB          -- двоичный JSON: разобран при вставке, поддерживает
               -- GIN-индексы, операторы @>, ?, #>. Предпочтительно.
               -- Единственный минус: теряется порядок ключей и
               -- дублирующиеся ключи (как в dict в Python)

-- UUID
UUID           -- 128-битный UUID; хранится эффективнее, чем TEXT(36)
               -- gen_random_uuid() (встроено в PostgreSQL 13+)

-- Массивы
INTEGER[]      -- массив любого типа (нативная поддержка PostgreSQL,
TEXT[]         -- это НЕ JSON-массив). Поиск через @> или ANY().
```

**Senior-практика: всегда предпочитайте `TIMESTAMPTZ` вместо `TIMESTAMP`.** Обычный `TIMESTAMP` хранит «локальное» время без информации о часовом поясе. Поэтому при смене настройки timezone на сервере или у клиента уже сохранённые данные начинают читаться неверно.

`TIMESTAMPTZ` этого избегает. При записи он нормализует значение к UTC (Coordinated Universal Time — нулевой часовой пояс). При чтении он возвращает значение в часовом поясе сессии.

## Constraints — встроенная защита целостности данных

```sql
CREATE TABLE orders (
    id          BIGSERIAL PRIMARY KEY,           -- NOT NULL + UNIQUE
    user_id     BIGINT NOT NULL
                  REFERENCES users(id)
                  ON DELETE RESTRICT,            -- запрещает удаление
                  -- ON DELETE SET NULL          -- или: обнуляет ссылку
                  -- ON DELETE CASCADE,          -- или: удаляет каскадно
    status      TEXT NOT NULL
                  CHECK (status IN ('pending','paid','cancelled')),
    total       NUMERIC(12,2) NOT NULL CHECK (total >= 0),
    email       TEXT UNIQUE,                     -- NULL не нарушает UNIQUE
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);

-- Отложенные ограничения (проверка в КОНЦЕ транзакции, не на каждой строке)
ALTER TABLE orders
  ADD CONSTRAINT fk_user
  FOREIGN KEY (user_id) REFERENCES users(id)
  DEFERRABLE INITIALLY DEFERRED;
```

**Senior-нюанс: `UNIQUE` в PostgreSQL допускает несколько NULL**, потому что по стандарту SQL `NULL` никогда не равен `NULL`. Если нужно уникальное поле, где NULL разрешён ровно один раз, используйте частичный индекс:

```sql
CREATE UNIQUE INDEX ON t(col) WHERE col IS NOT NULL;
```

`ON DELETE RESTRICT` и `ON DELETE NO ACTION` оба запрещают удалить родительскую строку, пока есть дочерние. Разница — в момент проверки:

- `RESTRICT` проверяет сразу, внутри самого оператора.
- `NO ACTION` можно объявить `DEFERRABLE`, и тогда проверка уедет в конец транзакции.

## Связи и нормализация — практический уровень

```sql
-- Many-to-Many через таблицу-связку
CREATE TABLE user_roles (
    user_id BIGINT NOT NULL REFERENCES users(id) ON DELETE CASCADE,
    role_id BIGINT NOT NULL REFERENCES roles(id) ON DELETE CASCADE,
    granted_at TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    PRIMARY KEY (user_id, role_id)             -- составной ключ без дублей
);

-- JOIN — основа работы с нормализованными данными
SELECT u.id, u.name, r.name AS role
FROM users u
JOIN user_roles ur ON ur.user_id = u.id
JOIN roles r       ON r.id = ur.role_id
WHERE u.id = $1;
```

Для интервью достаточно трёх нормальных форм:

- **1NF** — атомарные значения (никаких массивов и групп внутри одного столбца) и никаких одинаковых строк.
- **2NF** — каждый неключевой атрибут зависит от **всего** ключа. Это важно только для составных первичных ключей: PK — это и есть primary key, первичный ключ.
- **3NF** — нет транзитивных зависимостей: неключевой столбец не должен зависеть от другого неключевого.

Денормализация — осознанный компромисс в обратную сторону. Столбец `orders.total_amount` хранит заранее посчитанную сумму, и тогда `SUM(items.price * items.qty)` не пересчитывается при каждом чтении. Цена — дублирование и риск расхождения. Прямой `UPDATE` по `items`, который забыл обновить `orders.total_amount`, оставляет эти два числа рассинхронизированными.

## JSONB — когда и как использовать с умом

```sql
CREATE TABLE products (
    id          BIGSERIAL PRIMARY KEY,
    name        TEXT NOT NULL,
    attributes  JSONB                       -- динамические поля
);

INSERT INTO products (name, attributes)
VALUES ('iPhone 15', '{"color": "black", "storage": 256, "tags": ["phone"]}');

-- Операторы JSONB
SELECT * FROM products WHERE attributes @> '{"color": "black"}';  -- содержит
SELECT attributes->>'color' FROM products WHERE id = 1;           -- достать строку
SELECT attributes->'storage' FROM products;                       -- достать значение

-- GIN-индекс для операторов @>, ?, ?|, ?&
CREATE INDEX idx_products_attrs ON products USING GIN (attributes);

-- Для path-операторов (jsonb_path_ops) — меньший индекс, только @>
CREATE INDEX idx_products_attrs_path ON products
  USING GIN (attributes jsonb_path_ops);
```

Когда JSONB уместен:

- ✓ Динамическая схема — атрибуты, которые сильно отличаются между записями. Пример: характеристики товара в интернет-магазине.
- ✓ Хранение ответов внешнего API без нормализации, например журнал аудита.
- ✓ Быстрое прототипирование, пока схема ещё не устоялась.

Когда JSONB — антипаттерн:

- ✗ Поля, по которым вы часто делаете `WHERE` или `JOIN`. Они должны быть обычными столбцами с обычными B-Tree-индексами.
- ✗ Связи между сущностями. `FOREIGN KEY` внутри JSONB невозможен.
- ✗ «Потому что гибко» — без реальной причины для динамической схемы.

## Типичные ошибки на интервью

- **"`TEXT` vs `VARCHAR` — `VARCHAR` быстрее"** — в PostgreSQL оба типа используют одно и то же внутреннее представление, VARLENA (variable-length array). Разница в производительности нулевая. `VARCHAR(n)` добавляет только проверку длины.

- **"`TIMESTAMP` и `TIMESTAMPTZ` — одно и то же"** — не объяснять, что `TIMESTAMP` хранит «наивную» дату без часового пояса. Смените пояс на сервере или у клиента, и эта дата начнёт читаться неверно.

- **"`SERIAL` — лучший способ создать автоинкремент"** — не знать, что `SERIAL` это синтаксический сахар: `CREATE SEQUENCE` плюс `DEFAULT nextval()`. В современном PostgreSQL предпочтительнее `GENERATED ALWAYS AS IDENTITY` — именно эту форму описывает стандарт SQL.

- **"`UNIQUE` запрещает два NULL"** — в PostgreSQL, как и в стандарте SQL, `NULL` не равен `NULL`. Поэтому `UNIQUE`-индекс принимает сколько угодно значений NULL.

- **"JSONB нужен для гибкости"** — не назвать конкретный компромисс. JSONB нарушает реляционную нормализацию, делает невозможными связи через `FOREIGN KEY` и закрывает обычный B-Tree-индекс по вложенным полям с хорошей селективностью.
