# MVCC, блокировки и VACUUM

## MVCC — фундаментальный механизм PostgreSQL, объясняющий почему "читатели не блокируют писателей"

Наивное решение конкурентного доступа — блокировки. Читатель берёт разделяемую блокировку (shared lock), и писатель ждёт. Писатель берёт исключительную блокировку (exclusive lock), и ждут все читатели. Это работает, но под нагрузкой превращается в узкое место.

PostgreSQL решает это через **MVCC (Multi-Version Concurrency Control, многоверсионное управление конкурентностью)**. Вместо блокировки строки при чтении база хранит несколько версий одной строки одновременно. Каждая транзакция видит консистентный "снапшот" данных на момент своего старта и никого не блокирует.

Два слова держат на себе всю статью. **Кортеж** (tuple) — это одна физическая версия строки на диске. **Heap** — основной файл таблицы, где эти версии лежат, то есть данные таблицы за пределами индексов.

## Как `UPDATE` на самом деле работает — не "перезапись", а "создание новой версии"

```sql
UPDATE accounts SET balance = 200 WHERE id = 1;
```

Физически этот один оператор делает четыре вещи:

1. Старая строка (`balance=100`) **не** удаляется. В её поле `xmax` записывается идентификатор текущей транзакции — XID (transaction id).
2. В heap вставляется новая строка (`balance=200`), у неё `xmin` равен XID текущей транзакции.
3. При `COMMIT` новая версия становится видимой для транзакций, которые стартуют после этого коммита.
4. У старой версии теперь непустой `xmax`, значит она мёртвая. Это и есть **мёртвый кортеж** (dead tuple).

```txt
Heap-файл после UPDATE (упрощённо):
  ┌──────────────────────────────┐
  │ xmin=100, xmax=200, bal=100  │  ← dead tuple (xmax заполнен)
  ├──────────────────────────────┤
  │ xmin=200, xmax=0,   bal=200  │  ← live tuple (xmax=0 → живой)
  └──────────────────────────────┘
```

У каждого кортежа в heap есть такие поля:

- `xmin` — XID транзакции, создавшей эту строку. Это либо `INSERT`, либо тот `UPDATE`, который создал данную версию.
- `xmax` — XID транзакции, "удалившей" строку: либо `DELETE`, либо старая сторона `UPDATE`. Значение 0 означает, что строка живая.
- `infomask` — битовые флаги (committed, aborted и так далее).
- `ctid` — указатель на самую свежую версию строки. `UPDATE` выстраивает цепочку: `ctid` старой версии → новая версия.

## Снапшот транзакции — как PostgreSQL решает "что видно?"

Транзакция берёт **снапшот** на старте: на первом операторе при `READ COMMITTED`, на `BEGIN` при `REPEATABLE READ`. Снапшот и определяет, что этой транзакции разрешено видеть.

Осторожно: у снапшота есть свои поля `xmin` и `xmax`, и они значат **не** то же, что одноимённые поля строки. У строки `xmin` — это "кто меня создал". У снапшота `xmin` — граница: "всё, что старше, уже завершилось". Ниже мы пишем `snapshot.xmin`, чтобы не путать эти два смысла.

- `snapshot.xmin` — самый маленький XID среди транзакций, которые ещё работали в момент снапшота.
- `snapshot.xmax` — следующий XID, который база пока никому не выдала.
- `xip` — список транзакций, активных (то есть незавершённых) на тот момент.

Строка видима для транзакции, когда выполнены оба условия:

1. Её `xmin` меньше `snapshot.xmin`, то есть строка создана раньше. Условие выполнено и в другом случае: `xmin` принадлежит транзакции, завершившейся до снапшота. Это PostgreSQL проверяет по журналу коммитов (`pg_clog` / `pg_xact`).
2. Её `xmax` равен 0. Либо этот `xmax` принадлежит откатившейся транзакции. Либо `xmax` больше или равен `snapshot.xmax` — тогда удаление произошло после снапшота.

```txt
Снапшот: snapshot.xmin = 100, snapshot.xmax = 150

Строка xmin=90,  xmax=0  → видна: создана давно, не удалена
Строка xmin=160, xmax=0  → не видна: 160 >= snapshot.xmax, значит
                           её создали позже снапшота
```

Уровни изоляции построены прямо на этом:

- `READ COMMITTED` — свежий снапшот на каждый оператор.
- `REPEATABLE READ` — один снапшот на всю транзакцию.

## HOT Update — оптимизация для частых UPDATE одной строки

Обычный `UPDATE` пишет новую версию строки. После этого нужно обновить ещё и все индексы таблицы, потому что новая версия лежит по новому `ctid`. На таблице с множеством индексов это дорого.

**HOT (Heap-Only Tuple) Update** эту работу не делает вовсе. PostgreSQL применяет его, когда выполнены два условия:

1. Новая версия влезает на **ту же** heap-страницу, где лежит старая.
2. Обновляемый столбец **не** индексирован.

Тогда PostgreSQL связывает две версии внутри страницы: `ctid` старой строки → `ctid` новой строки. Индексы вообще не трогаются. Они по-прежнему указывают на старую строку, а оттуда PostgreSQL проходит по HOT-цепочке к актуальной версии. Экономия ощутимая: нет разбиения страниц (page split) в индексах, меньше записи в журнал предзаписи (WAL), быстрее сам `UPDATE`.

```sql
ALTER TABLE accounts SET (fillfactor = 70);
-- 30% каждой страницы остаётся свободным под HOT Updates
```

`fillfactor` меньше 100 резервирует на каждой странице свободное место, и именно оно нужно HOT Update для новой версии. Поэтому на таблицах с частыми `UPDATE` понижение `fillfactor` и делает оптимизацию возможной.

## Dead Tuples и Table Bloat — почему таблицы "пухнут"

Каждый `UPDATE` и каждый `DELETE` оставляют после себя мёртвые кортежи:

- `UPDATE` оставляет старую версию строки с заполненным `xmax`.
- `DELETE` оставляет единственную версию строки с заполненным `xmax`.

Мёртвые кортежи занимают место на диске и "загрязняют" страницы. `SELECT` читает страницу, видит мёртвый кортеж, проверяет его видимость, понимает, что кортеж не виден, и пропускает его. Это лишние обращения к диску при каждом Seq Scan.

**Раздувание таблицы** (table bloat) — результат этого. После интенсивных `UPDATE` и `DELETE` таблица может занимать в 5-10 раз больше места, чем нужно её живым данным. В индексах появляются такие же "дыры" — мёртвые записи индекса.

## VACUUM — механизм очистки мёртвых кортежей

```sql
-- Ручной запуск (обычно не нужен при настроенном autovacuum)
VACUUM users;

-- Со статистикой
VACUUM VERBOSE ANALYZE users;
```

`VACUUM` делает пять вещей:

1. Сканирует таблицу и находит мёртвые кортежи.
2. Помечает их место как свободное в FSM (Free Space Map, карта свободного места), чтобы новые строки могли его переиспользовать.
3. Удаляет мёртвые записи индекса — для каждого индекса таблицы.
4. Обновляет Visibility Map, карту видимости: это список страниц, где все кортежи видны всем. Именно она делает возможным Index-Only Scan.
5. Обновляет `pg_class.relpages` и `pg_class.reltuples` — статистику, по которой работает планировщик.

Чего `VACUUM` **не** делает:

- Он не возвращает освобождённое место операционной системе. Страницы остаются в файле, просто помечаются как доступные для повторного использования.
- Он не дефрагментирует данные внутри страницы.

`VACUUM` не берёт блокировку `ACCESS EXCLUSIVE`, он берёт только `ShareUpdateExclusiveLock`. Поэтому его можно запускать одновременно с обычными `SELECT`, `INSERT`, `UPDATE` и `DELETE`.

## VACUUM FULL — радикальное средство от bloat

```sql
VACUUM FULL users;
-- Аналог: CLUSTER users USING idx_users_pk (с сортировкой)
```

`VACUUM FULL` идёт гораздо дальше, в три шага:

1. Перестраивает таблицу с нуля — как если бы вы сделали `CREATE TABLE ... AS SELECT` только по живым кортежам.
2. Перестраивает все индексы.
3. Возвращает освобождённое место операционной системе, и файл действительно уменьшается.

Цена — блокировка. `VACUUM FULL` берёт на таблицу блокировку `ACCESS EXCLUSIVE`, поэтому **все** запросы к этой таблице стоят всё время работы. Для таблицы на сто гигабайт это часы.

Для production есть `pg_repack`. Это расширение делает ту же работу без долгой блокировки — через временную таблицу и триггеры.

## Autovacuum — как настроить и почему нельзя отключать

Две настройки решают, когда autovacuum придёт за таблицей.

```txt
autovacuum_vacuum_threshold    = 50   -- минимум мёртвых кортежей
autovacuum_vacuum_scale_factor = 0.2  -- плюс 20% от числа строк

Autovacuum запускается, когда:
  dead_tuples > threshold + scale_factor * reltuples
```

Для таблицы на 1 000 000 строк порог равен 50 + 0.2 × 1 000 000 = 200 050 мёртвых кортежей. При высокой частоте `UPDATE` это значит, что таблица успеет сильно раздуться до первого autovacuum.

```sql
-- Тюнинг autovacuum для горячих таблиц (много UPDATE/DELETE)
ALTER TABLE orders SET (
  autovacuum_vacuum_scale_factor = 0.01,  -- запускать раньше: 1% вместо 20%
  autovacuum_vacuum_threshold    = 100,   -- и меньший минимальный порог
  autovacuum_analyze_scale_factor = 0.005 -- обновлять статистику чаще
);
```

Отключить autovacuum (`autovacuum = off`) нельзя по трём причинам:

1. Раздувание таблицы ухудшает производительность Seq Scan.
2. Раздувание индексов ухудшает производительность Index Scan.
3. Переполнение счётчика транзакций (XID wraparound) — это критическая причина. PostgreSQL считает транзакции 32-битным XID, поэтому после 2^32 ≈ 4 млрд транзакций счётчик идёт по кругу. `VACUUM` спасает от этого заморозкой старых XID: он обнуляет `xmin` у строк, которые уже видны всем. Без `VACUUM` PostgreSQL на опасном пороге перестаёт принимать запросы и пишет:

```txt
database is not accepting commands to avoid wraparound data loss
```

## Блокировки — когда MVCC недостаточно

MVCC убирает блокировки чтения, но не блокировки записи. Как только корректность обновления зависит от значения, которое вы только что прочитали, нужна явная блокировка.

```sql
-- Оптимистичный подход (MVCC): две транзакции читают, потом UPDATE
-- Проблема: гонка в паттерне "check-then-act" (прочитал, проверил, записал)
BEGIN;
SELECT balance FROM accounts WHERE id = 1;  -- читаем 100
-- Другая транзакция тоже прочитала 100 и делает UPDATE...
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;

-- Пессимистичный подход: явная блокировка строки
BEGIN;
SELECT balance FROM accounts WHERE id = 1 FOR UPDATE;
-- Теперь другие транзакции, которые пытаются сделать
-- SELECT ... FOR UPDATE на эту строку, ЖДУТ до COMMIT/ROLLBACK
UPDATE accounts SET balance = balance - 50 WHERE id = 1;
COMMIT;
```

```sql
-- FOR UPDATE NOWAIT — немедленная ошибка вместо ожидания
SELECT * FROM orders WHERE id = 1 FOR UPDATE NOWAIT;
-- ERROR: could not obtain lock on row in relation "orders"

-- FOR UPDATE SKIP LOCKED — пропустить заблокированные строки
-- (паттерн для очередей задач: каждый воркер берёт "свою" задачу)
SELECT * FROM tasks WHERE status = 'pending'
ORDER BY created_at
LIMIT 1
FOR UPDATE SKIP LOCKED;
```

Уровни блокировок таблицы, от самого мягкого к самому жёсткому:

| Уровень блокировки | Кто её берёт |
|---|---|
| `AccessShareLock` | `SELECT` (берётся автоматически) |
| `RowShareLock` | `SELECT ... FOR UPDATE` |
| `RowExclusiveLock` | `INSERT`, `UPDATE`, `DELETE` |
| `ShareUpdateExclusiveLock` | `VACUUM`, `CREATE INDEX CONCURRENTLY` |
| `ShareLock` | `CREATE INDEX` (без CONCURRENTLY) |
| `ExclusiveLock` | `REFRESH MATERIALIZED VIEW CONCURRENTLY` |
| `AccessExclusiveLock` | `ALTER TABLE`, `VACUUM FULL`, `DROP TABLE` — блокирует всё, включая `SELECT` |

Операции DDL (Data Definition Language — операторы, меняющие схему) в production требуют осторожности. `ALTER TABLE` берёт `AccessExclusiveLock` и блокирует все запросы к таблице.

## Типичные ошибки на интервью

- **"`UPDATE` изменяет строку на месте"** — в PostgreSQL `UPDATE` создаёт новую версию строки и помечает старую как мёртвую через `xmax`. Старая версия остаётся в heap до `VACUUM`.

- **"MVCC полностью устраняет блокировки"** — MVCC устраняет блокировки чтения, в этом и смысл фразы "читатели не блокируют писателей". Блокировки записи на уровне строки остаются: из двух конкурентных `UPDATE` одной строки второй ждёт первого.

- **"`VACUUM` уменьшает размер файла таблицы"** — обычный `VACUUM` только помечает место мёртвых кортежей как доступное для повторного использования. Физический размер файла уменьшают лишь `VACUUM FULL` с блокировкой `ACCESS EXCLUSIVE` или `pg_repack`.

- **"autovacuum можно отключить, если делать `VACUUM` вручную"** — это и есть риск переполнения счётчика XID. Без регулярной заморозки старых XID PostgreSQL вынужден остановить приём запросов, чтобы защитить данные.

- **"`SELECT ... FOR UPDATE` нужен всем транзакциям при чтении"** — `FOR UPDATE` нужен только в паттерне "check-then-act": прочитали значение, проверили условие, обновили. Там гонка может нарушить бизнес-инвариант. Обычному чтению достаточно MVCC.
