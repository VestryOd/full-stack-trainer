# ACID и транзакции

## Транзакция — единица работы с гарантированными свойствами, а не просто "группа запросов"

Транзакция — это последовательность операций с базой данных, которая переводит её из одного **консистентного состояния** в другое. ACID — это название четырёх гарантий, которые транзакция даёт: атомарность, консистентность, изоляция, устойчивость.

Ключевое слово выше — «консистентное». Транзакция — не просто «атомарная группа», а группа, которая не оставляет данные частично изменёнными или невалидными. Ниже разбираем четыре буквы по очереди.

```sql
-- Перевод средств: классический пример, где частичное обновление катастрофично
BEGIN;

UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- Если здесь упадёт сервер — без транзакции деньги "испарились" бы

UPDATE accounts SET balance = balance + 100 WHERE id = 2;

COMMIT;   -- только ЗДЕСЬ изменения становятся видимы другим транзакциям
-- либо:
ROLLBACK; -- откатывает ВСЕ изменения с момента BEGIN, как будто их не было
```

**Автокоммит.** В PostgreSQL каждый оператор SQL (Structured Query Language) вне явного `BEGIN`/`COMMIT` выполняется в собственной неявной транзакции. Сервер сам оборачивает его в `BEGIN` и `COMMIT`. Это поведение по умолчанию, его и называют режимом autocommit.

Практическое следствие: `INSERT` или `UPDATE` без `BEGIN` — это уже атомарная транзакция, просто из одного оператора. Несколько `UPDATE` без `BEGIN` попадают каждый в свою транзакцию, поэтому общего отката у них нет.

## A — Atomicity: "всё или ничего" на уровне реализации

Атомарность реализована через WAL — журнал предзаписи (write-ahead log), то есть журнал транзакций PostgreSQL. Три шага:

1. Перед любым изменением данных на диске PostgreSQL пишет запись в WAL.
2. При `COMMIT` эта запись в WAL помечается как закоммиченная, и данные можно применять к heap.
3. При `ROLLBACK` — или после падения до `COMMIT` — PostgreSQL при старте читает WAL и отматывает незавершённые транзакции.

Именно WAL даёт сразу и D (устойчивость), и A (атомарность).

```sql
-- SAVEPOINT — частичный откат внутри транзакции
BEGIN;

INSERT INTO orders (user_id, total) VALUES (1, 500);

SAVEPOINT after_order;

INSERT INTO payments (order_id, amount) VALUES (currval('orders_id_seq'), 500);
-- Предположим, платёж временно отклонён

ROLLBACK TO after_order;  -- откат только до SAVEPOINT, заказ сохранён

-- Можно попробовать другой способ оплаты
INSERT INTO payments (order_id, method, amount)
VALUES (currval('orders_id_seq'), 'alternative', 500);

COMMIT;
```

## C — Consistency: гарантии constraints, а не "логическая корректность бизнес-логики"

Популярное заблуждение говорит, что «consistency» в ACID гарантирует логическую правильность данных. Гарантирует она не это.

PostgreSQL обещает только одно: после `COMMIT` не нарушены ограничения `NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`. Бизнес-логика вроде «нельзя перевести больше, чем есть на счёте» — забота приложения или ограничения `CHECK`.

Разница на практике:

- С `CHECK (balance >= 0)` база заблокирует перевод сразу, как только правило нарушено.
- Без этого `CHECK` база спокойно позволит `balance` уйти в минус. Это логически неверно, и ACID тут не помогает: проверять нечего, ограничения нет.

```sql
-- Ограничения, обеспечивающие C (Consistency)
CREATE TABLE accounts (
    id      BIGSERIAL PRIMARY KEY,
    balance NUMERIC(15, 2) NOT NULL DEFAULT 0
              CHECK (balance >= 0),          -- C: база не позволит
    owner   TEXT NOT NULL                   --    уйти в минус
);

-- Транзакция нарушит CHECK → ROLLBACK автоматически
BEGIN;
UPDATE accounts SET balance = balance - 10000 WHERE id = 1;
-- откат, если balance < 10000
COMMIT;
```

## I — Isolation: "параллельные транзакции не мешают друг другу" — сложнее, чем кажется

Полная изоляция — уровень `SERIALIZABLE` — означает, что транзакции ведут себя так, будто выполняются по одной. На практике это дорого: блокировки снижают параллелизм.

Поэтому PostgreSQL даёт несколько уровней с разными компромиссами между изоляцией и параллелизмом. Все они построены на MVCC (Multi-Version Concurrency Control, многоверсионность): сервер хранит несколько версий строки вместо того, чтобы блокировать её от читателей.

```sql
-- Уровень выбирается для каждой транзакции
BEGIN TRANSACTION ISOLATION LEVEL READ COMMITTED;   -- по умолчанию
BEGIN TRANSACTION ISOLATION LEVEL REPEATABLE READ;
BEGIN TRANSACTION ISOLATION LEVEL SERIALIZABLE;
```

- `READ COMMITTED` — уровень по умолчанию. Видит данные, закоммиченные **до начала каждого оператора** внутри транзакции.
- `REPEATABLE READ` — видит один снапшот, снятый в **начале** транзакции.
- `SERIALIZABLE` — полная изоляция через SSI, то есть Serializable Snapshot Isolation.

Каждый уровень защищает от своего набора аномалий: dirty read, non-repeatable read, phantom read, serialization anomaly. Подробнее — [Уровни изоляции транзакций](./03-isolation-levels.md).

## D — Durability: COMMIT = данные на диске (но не так просто)

После `COMMIT` приложение получает подтверждение. С этого момента данные гарантированно выживут при сбое питания, падении процесса и перезагрузке операционной системы.

Механизм — `fsync`. Перед подтверждением `COMMIT` PostgreSQL вызывает `fsync()` (или `fdatasync()`) для файла WAL. Это **блокирующий** вызов: он ждёт, пока запись физически ляжет на диск.

Эту гарантию меняют три настройки:

| Настройка | Что делает | Риск |
|---|---|---|
| `synchronous_commit = on` | Стандарт. `fsync()` завершается до подтверждения `COMMIT`. | Нет. Устойчивость гарантирована. |
| `synchronous_commit = off` | Подтверждает `COMMIT` **до** `fsync()`. Быстрее. | При падении можно потерять около 200 мс данных. |
| `fsync = off` | Полностью убирает гарантию устойчивости. | Очень опасно. Только для массовой загрузки, которую можно повторить. |

## Deadlock — как возникает и как PostgreSQL его обнаруживает

Deadlock — это циклическое ожидание блокировок между двумя или более транзакциями. Транзакция A держит блокировку строки 1 и ждёт строку 2. Транзакция B держит блокировку строки 2 и ждёт строку 1. Ни одна не может двинуться, поэтому сама собой ситуация не разрешится.

```sql
-- Классический сценарий deadlock (запускаются конкурентно)
-- Транзакция A:
BEGIN;
UPDATE accounts SET balance = balance - 100 WHERE id = 1;
-- (пауза, B выполняет свой первый UPDATE)
UPDATE accounts SET balance = balance + 100 WHERE id = 2;
COMMIT;

-- Транзакция B:
BEGIN;
UPDATE accounts SET balance = balance - 50  WHERE id = 2;
-- (пауза, A выполняет свой первый UPDATE)
UPDATE accounts SET balance = balance + 50  WHERE id = 1;
COMMIT;
-- → PostgreSQL обнаружит deadlock и откатит одну из транзакций
--   с ошибкой: ERROR: deadlock detected
```

PostgreSQL находит deadlock через граф ожидания блокировок (lock wait graph). Через `deadlock_timeout` — по умолчанию 1 секунда — он проверяет этот граф на циклы. Найдя цикл, он выбирает жертву (обычно транзакцию с наименьшим объёмом работы) и откатывает её с `ERROR`.

Приложение **обязано** перехватывать SQLSTATE 40P01, код ошибки `deadlock detected`, и повторять транзакцию. SQLSTATE — это пятисимвольный код, который несёт каждая ошибка PostgreSQL.

Три способа профилактики:

- Всегда обновляйте строки в **одном и том же порядке**. Если обе транзакции сначала берут `id=1`, а потом `id=2`, deadlock невозможен.
- Держите транзакции короткими, чтобы окно для конкуренции было маленьким.
- Используйте `SELECT ... FOR UPDATE` с `NOWAIT` или `SKIP LOCKED`, когда нужен явный контроль над блокировками.

## Транзакции в приложении: Prisma, ошибки и длинные транзакции

```ts
// Prisma: интерактивная транзакция (рекомендуется для сложной
// бизнес-логики с условиями между запросами)
await prisma.$transaction(async (tx) => {
  const sender = await tx.account.findUniqueOrThrow({ where: { id: senderId } });

  if (sender.balance < amount) {
    throw new Error('Insufficient funds'); // автоматический ROLLBACK
  }

  await tx.account.update({
    where: { id: senderId },
    data: { balance: { decrement: amount } },
  });

  await tx.account.update({
    where: { id: recipientId },
    data: { balance: { increment: amount } },
  });
  // При выходе из коллбэка без ошибки → автоматический COMMIT
});
```

В production важны два правила.

**1. Транзакции должны быть короткими.** Пока транзакция открыта, она держит свои блокировки. Долгая транзакция ещё и блокирует `VACUUM` (см. [MVCC, блокировки и VACUUM](./05-mvcc-locks-vacuum.md)), и удерживает сегменты WAL, из-за чего журнал на диске растёт.

**2. Сетевые вызовы внутри транзакции — антипаттерн.**

```ts
await prisma.$transaction(async (tx) => {
  const user = await tx.user.findFirst();
  await fetch('https://external-api.com/notify'); // ← ПЛОХО
  // Если fetch завис на 30 секунд, транзакция все эти
  // 30 секунд продолжает держать блокировки.
});
```

Делайте наоборот: сначала завершите транзакцию, потом обращайтесь к внешним сервисам.

## Типичные ошибки на интервью

- **"C (Consistency) в ACID означает, что данные всегда логически корректны"** — означает не это. Consistency в ACID покрывает только собственные ограничения базы: `NOT NULL`, `CHECK`, `FOREIGN KEY`, `UNIQUE`. Логическая корректность бизнес-правил остаётся заботой приложения.

- **"ROLLBACK удаляет данные из таблицы"** — не понимать механизм. PostgreSQL через WAL отматывает изменения, ещё не применённые к heap, либо применяет undo через версии строк MVCC.

- **"deadlock — это когда два запроса ждут дольше обычного"** — не отличать deadlock от конкуренции за блокировку. Deadlock — это циклическое ожидание, оно не разрешается само. Конкуренция за блокировку (lock contention) — это высокий спрос на одну блокировку, и она проходит, как только блокировку снимут.

- **"В `prisma.$transaction` всегда безопасно делать внешние HTTP-вызовы"** — пока транзакция открыта, блокировки удерживаются. Поэтому зависший внешний API блокирует строки в базе на всё время ожидания.

- **"`synchronous_commit = off` небезопасно, надо всегда держать on"** — не знать сценария применения. Для некритичных данных вроде логов событий это даёт заметный прирост скорости. Риск — потеря нескольких сотен миллисекунд данных, и здесь он приемлем.
