# Упавший тест должен объяснять себя сам

После падения на диске остаётся всё, что нужно для разбора: журнал вызова, снимок
страницы текстом, картинка экрана, видео и запись прогона. Запись прогона здесь
называют трассировкой, и открывается она отдельным просмотрщиком. Настроенные
заранее, эти артефакты отвечают на вопрос «что случилось» без повторного запуска
теста.

## Отчёт называет не только тест, но и шаг, на котором он упал

Длинный тест без разметки сообщает лишь номер строки. Разметка на шаги
превращает отчёт в рассказ о том, докуда дело дошло.

```ts
// tests/pager.spec.ts
import { test, expect } from '@playwright/test';

test('пагинация листается вперёд', async ({ page }) => {
  await test.step('открыть список задач', async () => {
    await page.goto('/tasks');
    await expect(page.getByRole('listitem')).toHaveCount(20);
  });

  await test.step('перейти на вторую страницу', async () => {
    await page.getByRole('button', { name: 'Дальше' }).click();
    await expect(page.getByText('Страница 2 из 3')).toBeVisible();
  });

  await test.step('счётчик', async () => {
    await expect(page.getByText('Страница 2 из 5')).toBeVisible({ timeout: 2000 });
  });
});
```

Заголовок падения теперь содержит имя шага, и по нему видно, что первые два шага
прошли.

```txt
1) tests/pager.spec.ts:3:5 › пагинация листается вперёд › счётчик

  Error: expect(locator).toBeVisible() failed

  Locator: getByText('Страница 2 из 5')
  Expected: visible
  Timeout: 2000ms
  Error: element(s) not found
```

Те же шаги становятся сворачиваемыми группами в просмотрщике трассировок, поэтому
на них стоит тратить строки даже в коротких тестах. У шага есть две полезные
опции: `box: true` прячет внутренности шага, оставляя в отчёте только его имя, а
`params` добавляет к шагу произвольные данные, которые потом видно в
просмотрщике.

## Трассировка — это архив, а не картинка

Файл `trace.zip` собирают во время прогона, и внутри лежит несколько разных
записей.

```txt
       Что лежит внутри trace.zip
┌─────────────────────────────────────┐
│ Действия и шаги теста               │
│ test.trace, 1-trace.trace           │
├─────────────────────────────────────┤
│ Кадры экрана на каждое действие     │
│ screencast/*.jpeg                   │
├─────────────────────────────────────┤
│ Снимки страницы до и после действия │
│ resources/*.html и *.json           │
├─────────────────────────────────────┤
│ Сетевой обмен прогона               │
│ 1-trace.network                     │
├─────────────────────────────────────┤
│ Исходник теста и стеки вызовов      │
│ src/*.ts, *-trace.stacks            │
└─────────────────────────────────────┘
всё это снято на стороне браузера и теста:
логов сервера и состояния базы данных в архиве нет
```

Список файлов проверяется обычным распаковщиком. Ниже настоящий состав архива с
нашего стенда, длинные имена сокращены.

```txt
src/….ts
attachments/…
test.trace
1-trace.trace
1-trace.network
screencast/page@…-1789722786532.jpeg
screencast/page@…-1789722786542.jpeg
resources/….html
resources/….json
1-trace.stacks
```

Из этого набора и складывается то, что показывает просмотрщик: слева список
действий, сверху полоса кадров, снизу вкладки с сетью, консолью, исходником и
стеком вызова. Снимок страницы — не картинка, а сохранённая разметка, поэтому в
просмотрщике по ней можно водить мышью и выбирать элементы.

| что видно в трассировке | чего в ней нет |
|---|---|
| каждое действие с временем и длительностью | логи сервера |
| разметку страницы до, во время и после действия | состояние базы данных |
| запросы, ответы и их тела | события, случившиеся до старта записи |
| сообщения консоли браузера | то, что происходило в другом контексте |

Открывают архив командой `npx playwright show-trace trace.zip`. Файл
самодостаточный: его можно приложить к задаче, и коллега увидит ровно тот же
прогон, ничего не запуская.

## Снимок контекста ошибки читается прямо в терминале

Рядом с трассировкой падение оставляет текстовый файл `error-context.md`. Это
описание страницы на момент падения в виде дерева ролей.

```yaml
- heading "Задачи" [level=1]
- text: Статус
- combobox "Статус":
  - option "все" [selected]
  - option "открытые"
  - option "готовые"
- list:
  - listitem:
    - text: План спринта
    - button "Готово"
  - listitem:
    - text: Отчёт за май
    - button "Готово"
```

Такой снимок отвечает на самый частый вопрос при падении локатора: что вообще
было на странице. Видно, что заголовок называется «Задачи», что фильтр — это
`combobox` с тремя вариантами, а каждая строка списка содержит кнопку «Готово».
Дерево ролей — то же самое, из которого берёт элементы `getByRole`, поэтому по
файлу сразу понятно, каким локатором элемент достанется.

## Видео и картинки стоят места, поэтому их включают по условию

Артефакты собираются не бесплатно, и разница между «всегда» и «при падении»
заметна на длинном прогоне.

```ts
// playwright.config.ts
export default defineConfig({
  use: {
    trace: 'on-first-retry',        // запись только при первом повторе
    screenshot: 'only-on-failure',  // картинка экрана только у упавших
    video: 'retain-on-failure',     // видео пишется, но сохраняется у упавших
  },
});
```

Вот сколько занял один упавший тест на нашем стенде.

```txt
3.4K  error-context.md
60K   test-failed-1.png
57K   video.webm
199K  trace.zip
```

Двести килобайт на тест выглядят безобидно, пока тестов двадцать. На пятистах
тестах запись всего подряд превращается в сотню мегабайт артефактов на каждый
прогон, и это уже заметно и для диска, и для выгрузки в хранилище. Отсюда
дежурная настройка: `on-first-retry` для трассировки, `only-on-failure` для
картинки и видео.

| значение | когда артефакт остаётся |
|---|---|
| `off` | никогда |
| `on` | всегда, даже у прошедших тестов |
| `only-on-failure` | у упавших (`screenshot`) |
| `retain-on-failure` | пишется всегда, остаётся у упавших |
| `on-first-retry` | только на первом повторе (`trace`, `video`) |

## Режим наблюдения и пошаговая остановка нужны, пока тест пишется

Разбор упавшего прогона и написание нового теста — разные задачи, и инструменты у
них разные.

```bash
# интерактивный режим: список тестов, кадры, повтор по изменению файла
npx playwright test --ui

# пошаговая остановка: открывает инспектор и идёт по действиям
npx playwright test --debug

# то же самое из кода: остановка в нужном месте теста
# await page.pause();
```

Флаг `--ui` открывает окно, где тесты запускаются по одному, видно каждое
действие и запись прогона, а файл перезапускается сам после правки. Флаг
`--debug` включает инспектор с кнопкой «шаг вперёд» и подбором локаторов. Вызов
`page.pause()` делает то же самое, но останавливается ровно там, где вы его
поставили.

## `codegen` даёт черновик, а не готовый тест

Запись действий в браузере экономит время на рутине: команда открывает браузер и
пишет код по мере того, как вы кликаете.

```bash
npx playwright codegen http://localhost:3000/login --output tests/draft.spec.ts
```

Пока вы ничего не сделали, в файле лежит только заготовка — вот она целиком,
как её пишет сам инструмент.

```ts
import { test, expect } from '@playwright/test';

test('test', async ({ page }) => {
});
```

Дальше каждое действие дописывается в тело. Полезные флаги видны в справке:
`--target` выбирает язык, `--test-id-attribute` подсказывает, какой атрибут
считать признаком элемента, `--device` включает эмуляцию телефона, а `--browser`
меняет браузер записи.

Результат записи — именно черновик. Он содержит все ваши действия подряд, включая
лишние клики, и не содержит ни одной проверки.

```ts
// что получилось после записи
test('test', async ({ page }) => {
  await page.goto('http://localhost:3000/login');
  await page.getByRole('textbox', { name: 'Email' }).click();
  await page.getByRole('textbox', { name: 'Email' }).fill('maria@example.com');
  await page.getByRole('textbox', { name: 'Пароль' }).click();
  await page.getByRole('textbox', { name: 'Пароль' }).fill('correct-horse');
  await page.getByRole('button', { name: 'Войти' }).click();
  await page.getByRole('button', { name: 'Дальше' }).click();
});
```

```ts
// что из этого делают: имя, относительный адрес, проверки вместо кликов вслепую
test('вторая страница списка открывается кнопкой «Дальше»', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('maria@example.com');
  await page.getByLabel('Пароль').fill('correct-horse');
  await page.getByRole('button', { name: 'Войти' }).click();

  await expect(page.getByRole('listitem')).toHaveCount(20);
  await page.getByRole('button', { name: 'Дальше' }).click();

  await expect(page.getByText('Страница 2 из 3')).toBeVisible();
});
```

Разница между этими двумя кусками и есть работа, которую запись не делает: имя
теста вместо `test`, относительный адрес вместо полного, ожидания состояния
вместо цепочки кликов, проверки вместо их отсутствия.

## Типичные ошибки

- **Разбирать падение повторным запуском.** Симптом: тест на второй раз проходит,
  и причина остаётся неизвестной. Трассировка первого прогона уже лежит на диске.
- **Писать `trace: 'on'` в конфиге на постоянной основе.** Симптом: прогон
  замедлился, а артефакты занимают гигабайты.
- **Оставлять `page.pause()` в коде.** Симптом: прогон на машине сборки висит до
  таймаута, потому что ждёт человека.
- **Считать `codegen` генератором тестов.** Симптом: набор тестов из кликов без
  проверок, который зелёный при сломанном приложении.
