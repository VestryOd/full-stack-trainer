# Нестабильный тест хуже отсутствующего

Нестабильный тест — это тест, который при неизменном коде иногда падает, а иногда
проходит. Вреден он не самим падением, а тем, что отучает верить красному
прогону: команда привыкает перезапускать сборку вместо того, чтобы читать
сообщение. Отсутствующий тест хотя бы честен и никого не обманывает.

## Нестабильность видна только на повторах

Один зелёный прогон ничего не доказывает, поэтому подозрительный тест гоняют
несколько раз подряд.

```ts
// tests/flaky.spec.ts
import { test, expect } from '@playwright/test';

test('пауза угадывает', async ({ page }) => {
  await page.goto('/tasks');
  await page.getByLabel('Статус').selectOption('open');

  await page.waitForTimeout(200);            // ставка на 200 мс

  expect(await page.getByRole('listitem').count()).toBe(20);
});
```

Флаг `--repeat-each` запускает один и тот же тест заданное число раз. На нашем
стенде, где сервер отвечает за случайное время, восемь прогонов дают такую
картину.

```txt
Running 8 tests using 1 worker

✓  1 tests/flaky.spec.ts:3:5 › пауза угадывает (308ms)
✘  2 tests/flaky.spec.ts:3:5 › пауза угадывает (299ms)
✓  3 tests/flaky.spec.ts:3:5 › пауза угадывает (retry #1) (306ms)
✓  4 tests/flaky.spec.ts:3:5 › пауза угадывает (279ms)
✓  5 tests/flaky.spec.ts:3:5 › пауза угадывает (287ms)
✓  6 tests/flaky.spec.ts:3:5 › пауза угадывает (282ms)
✓  7 tests/flaky.spec.ts:3:5 › пауза угадывает (279ms)
✓  8 tests/flaky.spec.ts:3:5 › пауза угадывает (280ms)
✓  9 tests/flaky.spec.ts:3:5 › пауза угадывает (282ms)

1 flaky
7 passed (5.5s)
```

Слово `flaky` в итоге и означает «упал, а на повторе прошёл». Дальше в сообщении
видно, что именно случилось: тест успел проверить список до того, как тот
отрисовался.

```txt
Error: expect(received).toBe(expected) // Object.is equality

Expected: 20
Received: 0
```

## Фиксированная пауза — это ставка на скорость ответа

Вызов `waitForTimeout` просит подождать ровно столько, сколько вы назвали. Но
никакого «столько» не существует: сервер, сеть и отрисовка занимают разное время
на разной машине и при разной нагрузке.

Пауза либо короче реального ожидания — и тогда тест падает случайным образом,
либо длиннее — и тогда каждый тест дарит набору лишние секунды. Проверка,
которая ждёт признак, снимает обе беды разом.

```ts
// tests/stable.spec.ts
test('ассершен вместо паузы', async ({ page }) => {
  await page.goto('/tasks');
  await page.getByLabel('Статус').selectOption('open');

  await expect(page.getByRole('listitem')).toHaveCount(20);
});
```

Тот же прогон шести повторов на том же нестабильном сервере.

```txt
✓  3 tests/stable.spec.ts:3:5 › ассершен вместо паузы (144ms)
✓  4 tests/stable.spec.ts:3:5 › ассершен вместо паузы (250ms)
✓  5 tests/stable.spec.ts:3:5 › ассершен вместо паузы (252ms)
✓  6 tests/stable.spec.ts:3:5 › ассершен вместо паузы (71ms)

6 passed (3.2s)
```

Обратите внимание на время: там, где пауза честно ждала свои 200 миллисекунд,
ассершен уходит дальше через 70. Ожидание признака не только устойчивее, но и
быстрее.

## Общее состояние делает тесты зависимыми от порядка

Второй источник нестабильности не про время. Тесты, которые пишут в одну базу
или в один список, начинают мешать друг другу, и результат зависит от того, кто
успел первым.

```ts
// tests/shared.spec.ts
test('импорт добавляет задачи', async ({ request }) => {
  for (let i = 0; i < 20; i++) {
    await request.post('/api/tasks', { data: { title: `Импорт ${i}` } });
  }
});

test('три страницы', async ({ page }) => {          // рассчитывает на 45 задач
  await page.goto('/tasks');
  await expect(page.getByText('Страница 1 из 3')).toBeVisible();
});
```

Запущенный в одиночку, второй тест проходит.

```txt
Running 1 test using 1 worker

✓  1 tests/shared.spec.ts:9:5 › три страницы (522ms)

1 passed (1.2s)
```

Запущенный после первого — падает, и оба повтора падают так же.

```txt
Running 2 tests using 1 worker

✓  1 tests/shared.spec.ts:3:5 › импорт добавляет задачи (38ms)
✘  2 tests/shared.spec.ts:9:5 › три страницы (5.1s)
✘  3 tests/shared.spec.ts:9:5 › три страницы (retry #1) (5.1s)
✘  4 tests/shared.spec.ts:9:5 › три страницы (retry #2) (5.1s)
```

Три одинаковых падения подряд — это диагноз. Гонка со временем обычно исчезает
на повторе, а зависимость от общих данных воспроизводится каждый раз, пока
данные не вернут в исходное состояние.

## Симптом, причина, что делать

Большинство нестабильных тестов попадают в одну из пяти строк таблицы.

| симптом | причина | что делать |
|---|---|---|
| падает на медленной машине, проходит на быстрой | фиксированная пауза или проверка без ожидания | web-first-ассершен вместо `waitForTimeout` |
| падает только в общем прогоне, по одному проходит | общие данные на сервере | свои данные на тест или на воркер |
| падает при смене порядка файлов | состояние в переменной модуля | перенести состояние в фикстуру |
| клик не срабатывает, элемент «прыгает» | анимация или сдвиг вёрстки | дождаться устойчивости или отключить анимацию |
| падает в полночь, в конце месяца, на другой машине | время, часовой пояс, локаль | зафиксировать их в конфиге проекта |

Первая строка лечится тем, что уже разобрано в статье
[Проверка ждёт сама, если внутри локатор](./03-assertions.md). Последняя — тема
статьи
[Прогон в пайплайне: что Playwright требует от машины сборки](./09-ci-and-visual.md).

## Воркеры делят одну машину, шардирование делит машины

Ускорить прогон можно двумя способами, и они решают разные задачи.

```txt
    Восемь файлов тестов: два способа ускорить прогон
┌───────────────────────┐  ┌─────────────────────────────┐
│ Воркеры: одна машина  │  │ Шардирование: четыре машины │
│                       │  │                             │
│ --workers=4           │  │ --shard=1/4 … 4/4           │
│                       │  │                             │
│ процесс 1: файлы 1, 5 │  │ машина 1: файлы 1, 2        │
│ процесс 2: файлы 2, 6 │  │ машина 2: файлы 3, 4        │
│ процесс 3: файлы 3, 7 │  │ машина 3: файлы 5, 6        │
│ процесс 4: файлы 4, 8 │  │ машина 4: файлы 7, 8        │
│                       │  │                             │
│ один отчёт сразу      │  │ отчёты потом объединяют     │
└───────────────────────┘  └─────────────────────────────┘
обе схемы делят работу по файлам, а не по отдельным тестам:
тесты одного файла разъедутся только при явном разрешении
```

Воркеры — это процессы на той же машине. Каждый держит свой браузер, поэтому
четыре воркера занимают вчетверо больше памяти и процессора.

```txt
Running 8 tests using 4 workers
```

Шардирование делит набор между машинами: каждая берёт свою часть и не знает про
остальные. Флаг `--shard=1/2` означает «первая половина из двух».

```txt
Running 4 tests using 2 workers, shard 1 of 2

✓  1 tests/part1.spec.ts:3:5 › часть 1, сценарий A (369ms)
✓  3 tests/part1.spec.ts:8:5 › часть 1, сценарий B (154ms)
✓  2 tests/part2.spec.ts:3:5 › часть 2, сценарий A (881ms)
✓  4 tests/part2.spec.ts:8:5 › часть 2, сценарий B (880ms)
```

У обоих способов общая особенность: единицей деления служит файл, а не тест.
Восемь тестов в одном файле при `--workers=4` так и пойдут в один процесс. Чтобы
тесты одного файла разъехались по воркерам, это нужно разрешить явно.

```ts
// в начале файла: тесты этого файла независимы, их можно разнести
test.describe.configure({ mode: 'parallel' });

// либо в конфиге — для всех файлов сразу
export default defineConfig({ fullyParallel: true });
```

```txt
Running 4 tests using 4 workers
```

Обратная настройка тоже есть: `mode: 'serial'` держит тесты файла строго по
порядку и пропускает остальные, если один упал. Она честно говорит, что тесты
зависимы, но это признание, а не решение.

## Повтор лечит гонку и прячет дефект

Повторы включаются одной строкой, и соблазн поставить их побольше велик.

```ts
// playwright.config.ts
export default defineConfig({
  retries: process.env.CI ? 2 : 0,   // локально повторов нет: пусть видно сразу
});
```

Повтор уместен там, где причина внешняя и редкая: сеть моргнула, машина сборки
задумалась, соседний сервис ответил медленнее обычного. Он бесполезен там, где
причина внутри теста: зависимость от порядка воспроизведётся и на второй раз, и
на третий, что мы и видели выше.

Главное — не считать `flaky` разновидностью зелёного. Это отдельный статус
именно для того, чтобы такие тесты было видно в отчёте и можно было чинить.
Разумная привычка: раз в спринт смотреть список нестабильных тестов и брать
верхний в работу.

## Типичные ошибки

- **Ставить `waitForTimeout` в ответ на падение.** Симптом: тест снова падает
  через неделю, когда машина стала медленнее.
- **Поднимать число повторов вместо разбора.** Симптом: прогон стал втрое
  длиннее, а отчёт полон `flaky`.
- **Чинить нестабильность увеличением таймаутов.** Симптом: набор тестов идёт
  сорок минут, потому что каждый упавший ждёт свой максимум.
- **Включать `fullyParallel` без подготовки данных.** Симптом: тесты, которые
  годами шли подряд, начинают драться за одни и те же записи.
