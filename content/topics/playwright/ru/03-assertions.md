# Проверка ждёт сама, если внутри локатор

Проверка вида `expect(локатор)` повторяется до тех пор, пока не сойдётся или пока
не кончится отведённое ей время. Проверка вида `expect(значение)` сравнивает уже
полученное число или строку ровно один раз. Первую — ту, что знает про живую
страницу и умеет ждать, — называют web-first-ассершеном, и дальше в статье
встречается именно это слово.

## `expect(локатор)` повторяет проверку, `expect(значение)` — нет

Разница не в том, что проверяется, а в том, что попадает внутрь `expect`.

```txt
       Один признак, два способа его проверить
┌───────────────────────┐  ┌────────────────────────┐
│ expect(локатор)       │  │ expect(значение)       │
│ на входе описание     │  │ на входе готовое число │
│                       │  │                        │
│ проверить             │  │ сравнить один раз      │
│ не сошлось: ещё раз   │  │                        │
│ не сошлось: ещё раз   │  │                        │
│ сошлось: успех        │  │ вердикт сразу          │
│                       │  │                        │
│ иначе таймаут 5000 мс │  │ таймаута нет вовсе     │
└───────────────────────┘  └────────────────────────┘
правый столбец отвечает по состоянию, которое уже устарело:
страница живёт дальше, а число было снято до сравнения
```

Слева `expect` получает описание элемента и сам решает, когда спросить страницу
ещё раз. Справа он получает число, снятое до вызова, и сравнить его может только
с тем, что уже есть. Список задач, который дорисовался через сто миллисекунд,
левый вариант увидит, а правый — нет.

```ts
// tests/tasks.spec.ts
import { test, expect } from '@playwright/test';

test('после фильтра остаётся двадцать задач', async ({ page }) => {
  await page.goto('/tasks');
  await page.getByLabel('Статус').selectOption('open');

  // Нестабильно: число снято до того, как список перерисовался
  expect(await page.getByRole('listitem').count()).toBe(20);

  // Стабильно: проверка повторяется, пока не сойдётся
  await expect(page.getByRole('listitem')).toHaveCount(20);
});
```

Отличить одно от другого в коде помогает `await`. У web-first-ассершена он стоит
перед `expect`, потому что ожидание внутри. У обычного `await` стоит внутри
скобок, потому что значение надо получить до сравнения.

## Падение показывает, чего ждали, что получили и сколько ждали

Web-first-ассершен печатает четыре строки состояния и журнал вызова.

```txt
Error: expect(locator).toHaveCount(expected) failed

Locator:  getByRole('listitem')
Expected: 25
Received: 20
Timeout:  1500ms

Call log:
  - Expect "toHaveCount" getByRole('listitem') with timeout 1500ms
  - waiting for getByRole('listitem')
    16 × locator resolved to 20 elements
       - unexpected value "20"
```

Здесь видно всё, что нужно для разбора. Ожидали 25 строк, получили 20, ждали
полторы секунды. Строка `16 ×` говорит, что проверка повторилась шестнадцать раз
и каждый раз получала одно и то же. Значит дело не в гонке: список отрисовался и
больше не менялся, а ожидание в тесте просто неверное.

Обычный `expect` в той же ситуации печатает вдвое меньше.

```txt
Error: expect(received).toBe(expected) // Object.is equality

Expected: 25
Received: 20
```

Ни таймаута, ни журнала, ни локатора — сравнивались два числа, и разбираться
придётся самому. Это вторая причина предпочитать web-first-ассершен: он не
только ждёт, он ещё и объясняет.

## Для каждого признака есть своя готовая проверка

Проверять признак готовым ассершеном дешевле, чем собирать значение руками и
сравнивать его самому.

| что проверяем | чем | на сквозном примере |
|---|---|---|
| элемент на экране | `toBeVisible` | заголовок «Задачи» появился |
| элемента нет | `toBeHidden` | подсказка «Нет задач» скрыта |
| количество | `toHaveCount` | в списке двадцать строк |
| текст целиком | `toHaveText` | в счётчике страниц «Страница 2 из 5» |
| текст частично | `toContainText` | в строке есть слово «отчёт» |
| значение поля | `toHaveValue` | в поле «Email» остался адрес |
| выбранный пункт | `toHaveValues` | в фильтре выбран `open` |
| доступность кнопки | `toBeEnabled`, `toBeDisabled` | «Дальше» выключена на последней странице |
| адрес страницы | `toHaveURL` | после входа адрес `/tasks` |
| ответ сервера | `toBeOK` | `GET /api/tasks` вернул успех |

Все они повторяют проверку сами. Полный список в документации длиннее, и в него
входят снимок дерева доступности `toMatchAriaSnapshot`, сравнение картинки
`toHaveScreenshot` и проверки класса, атрибута и стиля.

```ts
// у каждого ассершена свой таймаут, он важнее общего
await expect(page.getByRole('heading', { name: 'Задачи' })).toBeVisible();
await expect(page.getByRole('listitem')).toHaveCount(20, { timeout: 10_000 });
await expect(page.getByText('Страница 2 из 5')).toBeVisible();
await expect(page.getByLabel('Email')).toHaveValue('maria@example.com');

// отрицание ждёт обратного: пока строка не исчезнет
await expect(page.getByText('Отчёт за май')).toBeHidden();
```

У отрицания есть тонкость, о которой легко забыть. Ассершен `not.toBeVisible()`
ждёт, пока условие станет ложным, а не проверяет его один раз. Поэтому проверка
«ничего не появилось» честно стоит полный таймаут и замедляет набор тестов.

## Таймаутов несколько, и самый строгий обрезает остальные

Таймаут ассершена — не единственный счётчик в тесте, и он не главный.

| таймаут | значение по умолчанию | где задаётся |
|---|---|---|
| теста | 30 000 мс | поле `timeout` в конфиге, `test.setTimeout()` |
| ассершена | 5 000 мс | `expect.timeout` в конфиге, опция у ассершена |
| действия | нет | `use.actionTimeout`, опция у действия |
| перехода | нет | `use.navigationTimeout`, опция у `goto` |
| всего прогона | нет | `globalTimeout` в конфиге |

```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  timeout: 30_000,                    // на весь тест
  expect: { timeout: 5_000 },         // на один web-first-ассершен
  use: { actionTimeout: 10_000 },     // на одно действие
});
```

Опция у конкретного ассершена перекрывает `expect.timeout`. Таймаут теста
перекрывает всё: когда он истекает, тест падает независимо от того, сколько
ждал ассершен.

```txt
Test timeout of 2000ms exceeded.

Error: expect(locator).toBeVisible() failed

Locator: getByText('Нет задач')
Expected: visible
Error: element(s) not found

Call log:
  - Expect "toBeVisible" getByText('Нет задач') with timeout 30000ms
  - waiting for getByText('Нет задач')
  - Test timeout of 2000ms exceeded.
```

Журнал показывает конфликт прямо: ассершену дали тридцать секунд, а тест жил две.
Поэтому большой таймаут у одной проверки бесполезен, пока не поднят таймаут
теста. Разбор нестабильности, которую лечат увеличением таймаутов, — в статье
[Нестабильный тест хуже отсутствующего](./08-flakiness-and-parallelism.md).

## Мягкая проверка не останавливает тест

Обычная проверка прекращает тест на первом же несовпадении. Мягкая записывает
ошибку и идёт дальше, а называется она так из-за формы записи: `expect.soft`.

```ts
test('карточка задачи показывает все поля', async ({ page }) => {
  await page.goto('/tasks');

  await expect.soft(page.getByRole('listitem')).toHaveCount(20);
  await expect.soft(page.getByRole('heading')).toHaveText('Задачи');

  // жёсткий ассершен: без него дальше проверять нечего
  await expect(page.getByRole('button', { name: 'Дальше' })).toBeEnabled();
});
```

Тест с мягкими ассершенами всё равно считается упавшим, но в отчёт попадают все
несовпадения сразу.

```txt
Error: expect(locator).toHaveCount(expected) failed
    Expected: 25
    Received: 20
      - Expect "soft toHaveCount" getByRole('listitem') …

Error: expect(locator).toHaveText(expected) failed
    Expected: "Входящие"
    Received: "Задачи"
      - Expect "soft toHaveText" getByRole('heading') …
```

Мягкие ассершены уместны там, где проверки независимы: несколько полей одной
карточки, несколько колонок одной строки. Они вредны там, где вторая проверка
бессмысленна без первой: если списка нет, проверять его пагинацию незачем.

Задать режим для группы проверок помогает `expect.configure`.

```ts
// один настроенный expect вместо повторения опций в каждой строке
const softExpect = expect.configure({ soft: true, timeout: 10_000 });

await softExpect(page.getByRole('listitem')).toHaveCount(20);
await softExpect(page.getByRole('heading')).toHaveText('Задачи');
```

## Когда признака на странице нет, ждать умеют `expect.poll` и `toPass`

Эти две формы переносят повтор на произвольный код, а не на локатор.

```ts
// ждём, пока ответ сервера начнёт отдавать нужное число задач
await expect.poll(async () => {
  const res = await page.request.get('/api/tasks?status=open&page=1');
  return (await res.json()).total;
}, { timeout: 10_000, intervals: [200, 500, 1_000] }).toBe(20);

// повторяем целый блок, пока он не пройдёт целиком
await expect(async () => {
  const res = await page.request.get('/api/tasks?status=open&page=1');
  expect(res.status()).toBe(200);
  expect((await res.json()).items).toHaveLength(20);
}).toPass({ timeout: 10_000, intervals: [500] });
```

Форма `expect.poll` повторяет функцию и применяет к результату обычный матчер.
Форма `toPass` повторяет блок целиком и считает его пройденным, когда внутри не
осталось ошибок. Обе падают с одинаковой припиской в журнале.

```txt
Error: expect(received).toBe(expected) // Object.is equality

Expected: 25
Received: 20

Call Log:
- Timeout 1500ms exceeded while waiting on the predicate
```

Пользуйтесь ими для того, что не видно на странице: состояние очереди, запись в
базе, ответ соседнего сервиса. Для того, что на странице видно, дешевле обычный
web-first-ассершен: он и ждёт, и печатает локатор в отчёте.

## Типичные ошибки

- **Проверять `count()` обычным `expect`.** Симптом: тест падает на медленной
  машине и проходит на быстрой. Проверку заменяют на `toHaveCount`.
- **Поднимать таймаут ассершена, не подняв таймаут теста.** Симптом: в журнале
  стоит «with timeout 30000ms», а тест падает через тридцать секунд общего
  лимита.
- **Ставить мягкий ассершен там, где дальше идти некуда.** Симптом: после
  первого несовпадения сыплются десять производных, и настоящую причину видно
  не сразу.
- **Проверять отсутствие через `not` в каждом тесте.** Симптом: набор тестов
  замедляется, потому что каждая такая проверка честно ждёт полный таймаут.
