# Локатор описывает элемент, а не находит его

Локатор — это описание элемента, а не ссылка на найденный элемент. Поиск
происходит в момент действия или проверки, и повторяется до тех пор, пока
элемент не окажется готов. Отсюда растут автоожидание, строгость и почти все
приёмы этой темы.

## Локатор можно создать раньше, чем появится элемент

Создание локатора ничего не ищет и ни к чему не обращается.

```ts
// tests/tasks.spec.ts
import { test, expect } from '@playwright/test';

test('фильтр оставляет только открытые задачи', async ({ page }) => {
  const rows = page.getByRole('listitem');          // страница ещё не открыта
  const filter = page.getByLabel('Статус');

  await page.goto('/tasks');
  await filter.selectOption('open');

  await expect(rows).toHaveCount(20);               // вот здесь произошёл поиск
});
```

Переменная `rows` создана до `page.goto()`, и это не ошибка. Внутри неё лежит
описание «элементы с ролью списочного пункта», а не найденный элемент. Каждое
обращение к `rows` ищет заново по текущему состоянию страницы.

Именно поэтому локатор не устаревает. Список перерисовался после фильтра — тот
же `rows` найдёт новые строки. Старый подход с сохранённой ссылкой на элемент
после перерисовки ломался, и в отчёте это выглядело как случайное падение.

## Между `click()` и настоящим кликом проходит очередь проверок

Действие не выполняется сразу: сначала Playwright убеждается, что элемент к нему
готов.

```txt
Что происходит между click() и настоящим кликом
┌──────────────────────────────┐
│ 1. Вызов click()             │
│ локатор пока только описание │
└──────────────────────────────┘
                │  поиска ещё не было
                ▼
┌──────────────────────────────┐
│ 2. Поиск по описанию         │
│ заново на каждой попытке     │
└──────────────────────────────┘
                │  элемент найден
                ▼
┌──────────────────────────────┐
│ 3. Проверки готовности       │
│ виден, устойчив, принимает   │
│ события, включён             │
└──────────────────────────────┘
                │  все проверки прошли
                ▼
┌──────────────────────────────┐
│ 4. Прокрутка к элементу      │
│ если он вне экрана           │
└──────────────────────────────┘
                │  элемент в зоне видимости
                ▼
┌──────────────────────────────┐
│ 5. Клик мышью в центр        │
│ и ожидание начатых переходов │
└──────────────────────────────┘
пока элемент не найден или проверка не прошла,
шаги 2 и 3 повторяются до истечения таймаута действия
```

Проверки готовности называются автоожиданием. Оно встроено в действия, и его не
надо включать. Набор проверок зависит от действия, потому что для клика и для
ввода текста готовность означает разное.

| действие | что проверяется перед ним |
|---|---|
| `click`, `dblclick`, `tap`, `check` | виден, устойчив, принимает события, включён |
| `hover`, `dragTo` | виден, устойчив, принимает события |
| `fill`, `clear` | виден, включён, доступен для редактирования |
| `selectOption` | виден, включён |
| `screenshot` | виден, устойчив |
| `press`, `focus`, `dispatchEvent` | ничего: событие отправляется напрямую |

Слова в правой колонке — это конкретные проверки, а не общие слова. Устойчивость
значит, что рамка элемента не менялась два кадра анимации подряд. «Принимает
события» значит, что в точке клика находится именно этот элемент, а не
всплывающая подсказка поверх него. Отсюда следует важный вывод: `press` и
`focus` не проверяют ничего, поэтому подменять ими клик небезопасно.

Опция `force: true` пропускает проверки, а `trial: true` выполняет их и
отменяет само действие. Первая нужна редко и обычно маскирует дефект. Вторая
удобна, чтобы проверить доступность кнопки, не нажимая её.

## Упавшее действие рассказывает, на какой проверке оно застряло

Падение по таймауту печатает журнал вызова, а не просто «элемент не найден».

```txt
TimeoutError: locator.click: Timeout 2000ms exceeded.
Call log:
  - waiting for getByRole('button', { name: 'Войти' })
    - locator resolved to <button disabled>Войти</button>
  - attempting click action
    2 × waiting for element to be visible, enabled and stable
      - element is not enabled
    - retrying click action
    - waiting 20ms
    2 × waiting for element to be visible, enabled and stable
      - element is not enabled
    - retrying click action
      - waiting 100ms
    4 × waiting for element to be visible, enabled and stable
      - element is not enabled
    - retrying click action
      - waiting 500ms
```

Журнал читается сверху вниз и отвечает на три вопроса сразу. Элемент найден —
значит локатор верный. Кнопка найдена в состоянии `disabled` — значит дело не в
поиске. Проверка «включён» не прошла — значит приложение не разблокировало
кнопку, и чинить надо не тест.

Число со знаком умножения слева показывает, сколько раз подряд повторилась одна
и та же строка журнала. Паузы между попытками растут: 20 миллисекунд, затем 100,
затем 500.

Этот же журнал попадает в отчёт и в запись прогона, которую здесь называют
трассировкой. Поэтому в CI (continuous
integration — непрерывная интеграция) он доступен без перезапуска. Подробнее —
в статье [Упавший тест должен объяснять себя сам](./07-debugging.md).

## Ролевой локатор переживает переверстку, а CSS-селектор — нет

Первым выбором идёт то, что видит пользователь: роль, подпись, текст.

```ts
// Хрупко: селектор описывает разметку, а не смысл
await page.locator('div.card > form > button.btn-primary').click();

// Устойчиво: описание совпадает с тем, что видит пользователь
await page.getByRole('button', { name: 'Войти' }).click();
await page.getByLabel('Пароль').fill('correct-horse');
await page.getByPlaceholder('Поиск по задачам').fill('отчёт');
await page.getByText('Страница 2 из 5').isVisible();
```

Роль берётся из дерева доступности, которое строит браузер по разметке и
атрибутам ARIA (accessible rich internet applications — набор атрибутов
доступности). Класс `btn-primary` переживёт ровно до следующего редизайна, а
роль «кнопка» с подписью «Войти» переживёт и его.

| что вы ищете | чем описывать | пример |
|---|---|---|
| кнопку, ссылку, заголовок, поле | `getByRole` | `getByRole('button', { name: 'Войти' })` |
| поле с подписью | `getByLabel` | `getByLabel('Пароль')` |
| поле с подсказкой внутри | `getByPlaceholder` | `getByPlaceholder('Поиск по задачам')` |
| текст на странице | `getByText` | `getByText('Нет задач')` |
| картинку | `getByAltText` | `getByAltText('Аватар Марии')` |
| элемент без видимых признаков | `getByTestId` | `getByTestId('task-row')` |

Локатор `getByTestId` стоит последним не потому, что он плохой. Он не ломается
от перевода интерфейса и от смены текста, но и не проверяет ничего из того, что
видит пользователь. Атрибут для него настраивается полем `testIdAttribute`, по
умолчанию это `data-testid`.

## Строгость ловит неоднозначность до того, как она станет нестабильностью

Локатор, под описание которого попадает больше одного элемента, роняет действие
с понятной ошибкой.

```txt
Error: expect(locator).toBeVisible() failed

Locator: locator('li')
Expected: visible
Error: strict mode violation: locator('li') resolved to 20 elements:
    1) <li>…</li> aka getByText('Отчёт за май Готово').first()
    2) <li>…</li> aka getByText('Проверить счета Готово').first()
    3) <li>…</li> aka getByText('План спринта Готово').first()
    4) <li>…</li> aka getByText('Отчёт за май Готово').nth(1)
    5) <li>…</li> aka getByText('Проверить счета Готово').nth(1)
    6) <li>…</li> aka getByText('План спринта Готово').nth(1)
    7) <li>…</li> aka getByText('Отчёт за май Готово').nth(2)
    8) <li>…</li> aka getByText('Проверить счета Готово').nth(2)
    9) <li>…</li> aka getByText('План спринта Готово').nth(2)
    10) <li>…</li> aka getByText('Отчёт за май Готово').nth(3)
    ...

Call log:
  - Expect "toBeVisible" locator('li') with timeout 1500ms
  - waiting for locator('li')
```

Другой инструмент взял бы первый подходящий элемент и пошёл дальше. Тест
проходил бы до тех пор, пока порядок строк не изменился, а потом стал бы
нестабильным без видимой причины. Строгость превращает эту будущую
нестабильность в честное падение на первом же прогоне.

Действие падает так же, только заголовок у сообщения свой:
`locator.click: Error: strict mode violation: …`. Список совпадений печатается
до десятого, дальше идёт многоточие.

Вывод полезен и как подсказка. После слова `aka` стоит готовый локатор для
каждого найденного элемента, и его можно скопировать в тест как отправную точку.

```ts
// 1. Сузить описание — годится почти всегда
await page.getByRole('listitem').filter({ hasText: 'Отчёт за май' }).click();

// 2. Взять элемент по номеру — когда важен именно порядок
await page.getByRole('listitem').first().click();

// 3. Проверить все совпадения сразу — когда элемент и должен быть не один
await expect(page.getByRole('listitem')).toHaveCount(20);
```

У строгости три законных выхода, и они показаны выше. Первый почти всегда лучше
остальных: он оставляет в тесте описание, а не позицию. Второй честен там, где
проверяется именно первая строка списка. Третий снимает вопрос вовсе, потому что
ассершен про количество и рассчитан на много элементов.

## Цепочка и фильтр сужают описание, а не ищут дважды

Каждое звено цепочки — это область поиска для следующего звена.

```txt
 Цепочка сужает описание, а не ищет заново
┌──────────────────────┐
│ Вся страница         │
│ page                 │
└──────────────────────┘
            │  .getByRole('list')
            ▼
┌──────────────────────┐
│ Список задач         │
│ role=list            │
└──────────────────────┘
            │  .getByRole('listitem')
            ▼
┌──────────────────────┐
│ Строки списка        │
│ role=listitem, их 20 │
└──────────────────────┘
            │  .filter({ hasText: 'отчёт' })
            ▼
┌──────────────────────┐
│ Строка про отчёт     │
│ ровно одна           │
└──────────────────────┘
поиск происходит один раз, в момент действия или ассершена:
промежуточные локаторы ничего не ищут и ничего не держат
```

Цепочка не делает нескольких поисков: она собирает одно описание, которое
выполнится целиком в момент действия. Поэтому промежуточные переменные ничего не
стоят, и их удобно держать в объекте страницы.

```ts
// tests/tasks.spec.ts
const list = page.getByRole('list');
const rows = list.getByRole('listitem');

// строка по тексту внутри неё
const reportRow = rows.filter({ hasText: 'Отчёт за май' });
await reportRow.getByRole('button', { name: 'Готово' }).click();

// строка, внутри которой есть значок «просрочено»
const overdue = rows.filter({ has: page.getByTestId('overdue-badge') });
await expect(overdue).toHaveCount(3);

// строки без метки «черновик»
const published = rows.filter({ hasNotText: 'черновик' });
await expect(published).toHaveCount(17);
```

Фильтр `has` принимает другой локатор и оставляет строки, внутри которых он
находится. Есть ещё два соединителя: `and()` требует совпадения обоих описаний,
`or()` — любого из двух. Последний удобен там, где интерфейс показывает либо
кнопку «Войти», либо имя уже вошедшего пользователя.

## Автоожидание есть не у всех методов

Методы, которые возвращают значение, не ждут ничего и отвечают по текущему
состоянию страницы.

```ts
// Нестабильно: count() отвечает сразу, список мог ещё не отрисоваться
const n = await page.getByRole('listitem').count();
expect(n).toBe(20);

// Нестабильно по той же причине: isVisible() не ждёт появления
if (await page.getByText('Нет задач').isVisible()) {
  await page.getByRole('button', { name: 'Создать задачу' }).click();
}

// Стабильно: ассершен повторяет проверку, пока не истечёт его таймаут
await expect(page.getByRole('listitem')).toHaveCount(20);
```

Методы `count()`, `isVisible()`, `textContent()`, `getAttribute()` и `all()`
возвращают результат немедленно. Они полезны в отладке и в редких ветвлениях, а
в проверках их место занимают проверки, которые ждут сами. Такие проверки
называют web-first-ассершенами, и о них статья
[Проверка ждёт сама, если внутри локатор](./03-assertions.md).

## Типичные ошибки

- **Описывать разметку вместо смысла.** Симптом: локатор ломается от правки
  вёрстки, которая не меняла поведение. Лечится переходом на `getByRole` и
  `getByLabel`.
- **Гасить строгость через `first()` наугад.** Симптом: тест проходит, но
  проверяет случайную строку списка. Сначала сужают описание фильтром.
- **Ветвиться по `isVisible()`.** Симптом: тест ведёт себя по-разному на быстрой
  и медленной машине. Проверку делают ассершеном.
- **Ставить `force: true` в ответ на падение.** Симптом: падение исчезает, а
  дефект интерфейса остаётся. Сначала читают журнал вызова.
