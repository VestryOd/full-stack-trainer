# Каждый тест начинается с чистого листа

Чистый лист получается не уборкой после теста, а тем, что каждый тест получает
новый контекст браузера. Собирает это окружение до теста и разбирает после него
отдельный механизм подготовки; в Playwright он называется фикстурой. Из того же
устройства следует, чего изоляция не покрывает.

## Фикстура — это аргумент теста, а не глобальная настройка

Тест объявляет в скобках то, что ему нужно, и получает готовое.

```ts
// tests/tasks.spec.ts
import { test, expect } from '@playwright/test';

test('фильтр оставляет только открытые задачи', async ({ page }) => {
  await page.goto('/tasks');
  await page.getByLabel('Статус').selectOption('open');

  await expect(page.getByRole('listitem')).toHaveCount(20);
});

test('проверка списка запросом, без интерфейса', async ({ request }) => {
  const res = await request.get('/api/tasks?status=open&page=1');

  await expect(res).toBeOK();
  expect((await res.json()).total).toBe(33);
});
```

Первый тест попросил `page` и получил страницу в своём контексте. Второй попросил
`request` и получил клиент для запросов без браузера вовсе. Фикстура, которую не
попросили, не создаётся: за неиспользованный `browser` тест не платит.

В таблице ниже есть колонка «область». Это срок жизни фикстуры: она живёт либо
один тест, либо весь процесс, в котором тесты идут подряд. Такой процесс называют
воркером, и их запускается несколько одновременно.

| фикстура | что даёт | область |
|---|---|---|
| `page` | страницу в своём контексте | тест |
| `context` | контекст браузера целиком | тест |
| `request` | клиент запросов без браузера | тест |
| `browser` | процесс браузера | воркер |
| `playwright` | точку входа во весь пакет | воркер |
| `browserName` | имя браузера строкой | воркер |

Фикстуры `page` и `context` связаны: `page` создаётся внутри того же `context`.
Поэтому запросить обе — не значит получить две разные страницы.

## Воркер живёт долго, тест — нет

Область видимости решает, что переживёт границу между тестами.

```txt
    Жизненный цикл фикстур внутри одного воркера
┌──────────────────────────────────────────────────┐
│ Воркер запускается                               │
│ создаются worker-фикстуры: browser, свой account │
├──────────────────────────────────────────────────┤
│ Тест 1                                           │
│ создаются: context → page → boardPage            │
│ тело теста                                       │
│ разбираются: boardPage → page → context          │
├──────────────────────────────────────────────────┤
│ Тест 2                                           │
│ браузер и account те же, context и page новые    │
│ тело теста                                       │
│ разбираются в обратном порядке                   │
├──────────────────────────────────────────────────┤
│ Воркер завершается                               │
│ разбираются worker-фикстуры: account → browser   │
└──────────────────────────────────────────────────┘
создание идёт от зависимостей к зависимым, разбор — наоборот:
между тестами переживает только то, что объявлено на воркер
```

Проверить порядок можно печатью из самой фикстуры. Вывод ниже снят на прогоне
двух тестов в один воркер.

```txt
Running 2 tests using 1 worker

  setup    account (воркер 0)
  setup    boardPage
  >>       тело теста 1
  teardown boardPage
  ✓  1 tests/fixtures.spec.ts:21:1 › первый тест (117ms)
  setup    boardPage
  >>       тело теста 2
  teardown boardPage
  ✓  2 tests/fixtures.spec.ts:26:1 › второй тест (75ms)
  teardown account

  2 passed (827ms)
```

Фикстура `account` объявлена на воркер, поэтому создалась один раз и разобралась
после последнего теста. Фикстура `boardPage` объявлена на тест, поэтому прошла
полный круг дважды. Такой вывод стоит снимать самому, когда порядок кажется
неочевидным: он отвечает быстрее, чем чтение документации.

## Своя фикстура убирает повторы из тестов

Фикстура объявляется через `test.extend`, а её тело делится на две части
вызовом `use`.

```ts
// tests/fixtures.ts
import { test as base, expect, type Page } from '@playwright/test';

export const test = base.extend<{ boardPage: Page }>({
  boardPage: async ({ page }, use) => {
    await page.goto('/tasks');                 // setup: до теста
    await page.getByLabel('Статус').selectOption('open');

    await use(page);                           // здесь выполняется тест

    await page.evaluate(() => localStorage.clear());   // teardown: после теста
  },
});

export { expect };
```

Всё до `use` выполняется перед телом теста, всё после — когда тест закончился,
включая падение. Значение, переданное в `use`, и станет аргументом теста.
Разбор выполняется даже тогда, когда тест упал, и это главное отличие фикстуры
от кода, дописанного в конец теста.

```ts
// tests/tasks.spec.ts
import { test, expect } from './fixtures';

test('пагинация листается вперёд', async ({ boardPage }) => {
  await boardPage.getByRole('button', { name: 'Дальше' }).click();

  await expect(boardPage.getByText('Страница 2 из 2')).toBeVisible();
});
```

У фикстуры есть три полезных модификатора. Флаг `auto: true` включает её для
всех тестов файла без упоминания в скобках. Флаг `option: true` превращает её в
настройку, которую задают в конфиге через `use`. Опция `timeout` ограничивает
саму фикстуру отдельно от теста.

```ts
// playwright.config.ts — значение option-фикстуры задаётся проектом
export default defineConfig({
  projects: [
    { name: 'открытые', use: { defaultStatus: 'open' } },
    { name: 'готовые',  use: { defaultStatus: 'done' } },
  ],
});
```

## Область видимости выбирается ценой, а не удобством

Область «тест» безопасна, область «воркер» быстра.

| признак | область «тест» | область «воркер» |
|---|---|---|
| когда создаётся | перед каждым тестом | один раз на процесс |
| что видит | только свой тест | все тесты воркера подряд |
| цена ошибки | теряется один тест | ломается вся цепочка тестов |
| типичный житель | страница, данные теста | браузер, учётная запись, сервер-заглушка |

```ts
// tests/fixtures.ts — своя учётная запись на каждый воркер
export const test = base.extend<{}, { account: string }>({
  account: [async ({}, use, workerInfo) => {
    const email = `maria+${workerInfo.workerIndex}@example.com`;
    await createUser(email);                   // дорого: делаем один раз

    await use(email);

    await deleteUser(email);
  }, { scope: 'worker' }],
});
```

Учётная запись в примере привязана к номеру воркера, поэтому два воркера не
дерутся за одного пользователя. Обратная зависимость запрещена: worker-фикстура
не может попросить `page`. Прогон даже не стартует, а падает с сообщением
`worker fixture "api" cannot depend on a test fixture "page"`.

Ограничение логично: `page` живёт один тест, а worker-фикстура переживает
десятки. Если worker-фикстуре нужна страница, она создаёт свой контекст из
`browser` и закрывает его сама.

## Изолируется браузер, а не ваш модуль

Контекст уносит с собой всё состояние страницы, но к процессу теста отношения не
имеет.

```txt
Running 2 tests using 1 worker

  записал filter=open и переменную модуля 42
  ✓  1 tests/iso.spec.ts:5:5 › тест 1 пишет (179ms)
  localStorage.filter = null
  переменная модуля   = 42
  ✓  2 tests/iso.spec.ts:12:5 › тест 2 читает (68ms)

  2 passed (875ms)
```

Запись в `localStorage` исчезла вместе с контекстом, а переменная модуля
пережила границу теста, потому что живёт в процессе прогонщика тестов. Отсюда
короткий список того, за чем следить самому:

- **Переменные модуля и одиночки.** Они общие для всех тестов файла в пределах
  воркера.
- **Данные в базе и файлы на диске.** Их никто не откатывает, если вы не сделали
  этого в фикстуре.
- **Внешние сервисы и очереди.** Заглушка, поднятая на весь прогон, помнит
  прошлый тест.

Каждый пункт — это готовая причина нестабильности, и разбор в статье
[Нестабильный тест хуже отсутствующего](./08-flakiness-and-parallelism.md).

## Фикстура сильнее, чем `beforeEach`

Оба механизма работают, но у фикстуры четыре преимущества, и они не
стилистические.

- **Тест виден целиком.** В скобках теста написано, что ему нужно, а хук про это
  молчит.
- **Ненужное не создаётся.** Хук выполняется для всех тестов файла, фикстура —
  только для тех, кто её попросил.
- **Разбор гарантирован.** Код после `use` выполняется и при падении теста.
- **Шаги видны в отчёте.** Фикстура попадает в трассировку отдельной строкой, и
  её можно скрыть опцией `box: true`.

Хуки при этом остаются уместны для действий, не создающих объектов: записать
заметку в отчёт, проверить общее предусловие, пропустить тест.

## Типичные ошибки

- **Хранить состояние в переменной модуля.** Симптом: тесты проходят по одному и
  падают вместе. Состояние переносят в фикстуру.
- **Объявлять дорогую подготовку на тест.** Симптом: прогон вырос втрое после
  добавления одной фикстуры. Помогает область «воркер».
- **Убирать за собой в конце теста.** Симптом: после падения мусор остаётся, и
  следующий тест падает уже по другой причине. Разбор переносят за `use`.
- **Создавать контекст руками при наличии `page`.** Симптом: в трассировке два
  контекста, а проверяется один. Второй контекст нужен только для второго
  пользователя.
