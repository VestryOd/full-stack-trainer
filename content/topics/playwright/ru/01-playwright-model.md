# Модель Playwright: браузер, контекст, страница

Playwright запускает настоящий браузер и управляет им по протоколу из процесса
Node.js. Изоляцию между тестами даёт не браузер, а контекст браузера — чистый
профиль внутри уже запущенного процесса. Из этих двух фактов выводится почти
всё остальное поведение платформы.

## Тест управляет настоящим браузером, а не его эмуляцией

Ваш тест — это обычный процесс Node.js, который запускает браузер рядом с собой
и держит с ним одно соединение.

```txt
           Кто с кем разговаривает во время теста
┌─────────────────────────────────────┐
│ Ваш тест                            │
│ процесс Node.js: прогонщик тестов   │
└─────────────────────────────────────┘
                   │  команды по протоколу, одно соединение
                   ▼
┌─────────────────────────────────────┐
│ Браузер                             │
│ сборка Chromium, Firefox или WebKit │
└─────────────────────────────────────┘
                   │  настоящий ввод: клик, набор текста
                   ▼
┌─────────────────────────────────────┐
│ Страница приложения                 │
│ ваш фронтенд на localhost:3000      │
└─────────────────────────────────────┘
     драйвера-посредника между тестом и браузером нет:
    сборку браузера Playwright ставит и версионирует сам
```

Процесс, который запускает тесты, называется прогонщиком тестов (test runner).
Он стартует сборку браузера как дочерний процесс и отправляет ей команды по
протоколу автоматизации. У Chromium этот протокол встроен в сам браузер и
называется `Chrome DevTools Protocol`. Для Firefox и WebKit (движок Safari)
Playwright поставляет собственные сборки с таким же уровнем доступа.

Сборки браузеров не приходят вместе с пакетом. Их ставят отдельной командой, и
она же тянет системные библиотеки.

```bash
# сборки браузеров ставятся отдельно от пакета
npx playwright install --with-deps chromium

# на момент написания последняя версия пакета — 1.63.0 от 4 сентября 2026 года
npx playwright --version
# Version 1.63.0
```

Актуальную версию проверяйте в примечаниях к релизам на сайте `playwright.dev`.
Пакет 1.63.0 приносит Chromium 153.0.8010.12, Firefox 155.0 и WebKit 26.6. Эти
номера лежат в файле `browsers.json` внутри пакета `playwright-core`, так что
проверить их можно прямо в `node_modules`, не заходя в документацию.

Из связки «пакет плюс своя сборка браузера» следуют две вещи, которые дальше
объясняют половину странностей:

- **Версия браузера привязана к версии пакета.** Обновление `@playwright/test`
  приносит новые сборки. Поэтому «у меня проходит, а в CI (continuous
  integration — непрерывная интеграция) падает» часто означает просто разные
  версии пакета на двух машинах.
- **Драйвера-посредника между тестом и браузером нет.** Соединение открывается
  один раз и живёт весь прогон, а команда доходит до браузера без промежуточного
  сервера.

По умолчанию браузер работает в безголовом режиме (headless) — без окна на
экране.

```bash
# тот же прогон, но с окном на экране и только в одном браузере
npx playwright test --headed --project=chromium
```

Флаг `--headed` открывает окно, и это единственное, что меняется: страница,
протокол и таймауты остаются теми же.

Прямой доступ к браузеру — это не только клики. По тому же соединению тест
получает вещи, которых у него нет в юнит-тесте:

- **Перехват и подмену сетевых запросов** — статья
  [Тест управляет сетью, а не надеется на неё](./05-network.md).
- **Снимок состояния входа и его переиспользование** — статья
  [Логин один раз, а не в каждом тесте](./06-auth-and-state.md).
- **Запись всего, что происходило на странице, вместе с сетью и кадрами
  экрана.** Такая запись называется трассировкой, и ей посвящена статья
  [Упавший тест должен объяснять себя сам](./07-debugging.md).
- **Эмуляцию окружения:** размер окна, локаль, часовой пояс, тему и разрешения.

## Изоляция живёт в контексте, а не в браузере

Контекст браузера — это отдельный профиль внутри процесса браузера, по смыслу
близкий к окну инкогнито. На картинке ниже встретится ещё одно слово: тесты идут
не в одном процессе, а в нескольких сразу, и такой процесс называют воркером.

```txt
Один воркер: браузер один, контекст на каждый тест
┌────────────────────────────────────────────────┐
│ Браузер: запускается один раз на воркер        │
│                                                │
│ ┌────────────────────┐ ┌─────────────────────┐ │
│ │ Контекст теста 1   │ │ Контекст теста 2    │ │
│ │ свои cookies       │ │ пустые cookies      │ │
│ │ свой localStorage  │ │ пустой localStorage │ │
│ │ свой кэш           │ │ пустой кэш          │ │
│ │                    │ │                     │ │
│ │ Страница (вкладка) │ │ Страница (вкладка)  │ │
│ └────────────────────┘ └─────────────────────┘ │
└────────────────────────────────────────────────┘
контексты не видят данных друг друга, хотя процесс общий:
поэтому порядок тестов внутри воркера ничего не решает
```

У контекста свои cookies, своё хранилище `localStorage` и `sessionStorage`, свой
кэш и свои разрешения. Создавать его дёшево: процесс браузера уже запущен, и
документация описывает контексты как быстрые и полностью изолированные. Именно
поэтому чистый лист достаётся каждому тесту, а не каждому файлу.

| уровень | что изолирует | когда создаётся | чего стоит |
|---|---|---|---|
| браузер | процесс, версию, флаги запуска | один раз на воркер | запуск процесса |
| контекст | cookies, хранилища, кэш, разрешения | на каждый тест | почти ничего |
| страница | вкладку: свой адрес и свою историю | на каждый тест | почти ничего |

Строка про браузер объясняет, почему прогон не становится вдвое медленнее от
удвоения числа тестов. Процесс запускается один раз на воркер и живёт дальше, а
перезапускают его только после падения теста.

## Проект — это один и тот же тест в другом окружении

Проект задаёт, с какими настройками прогоняются тесты, а не какие тесты
прогоняются.

```ts
// playwright.config.ts — три браузера и один мобильный размер экрана
import { defineConfig, devices } from '@playwright/test';

export default defineConfig({
  projects: [
    { name: 'chromium', use: { ...devices['Desktop Chrome'] } },
    { name: 'firefox',  use: { ...devices['Desktop Firefox'] } },
    { name: 'webkit',   use: { ...devices['Desktop Safari'] } },
    { name: 'mobile',   use: { ...devices['Pixel 7'] } },
  ],
});
```

Один и тот же файл `tests/login.spec.ts` прогонится четыре раза. Запустить
только один проект можно флагом `--project=chromium`, и локально так делают
почти всегда. Набор `devices` приносит готовые размеры экрана, коэффициент
плотности пикселей и строку `User-Agent`; список лежит в пакете и проверяется по
документации.

Проекты умеют ещё одно, и на этом держатся статьи 06 и 09: проект может зависеть
от другого проекта через поле `dependencies`. Зависимость прогоняется первой, и
её результат достаётся остальным.

## Фикстура `page` уже даёт вам чистый контекст

Аргументы, которые тест перечисляет в скобках, — это заранее собранное
окружение. Каждый такой аргумент называется фикстурой, и `page` приходит уже
внутри своего контекста.

```ts
// playwright.config.ts
import { defineConfig } from '@playwright/test';

export default defineConfig({
  testDir: './tests',
  use: {
    baseURL: 'http://localhost:3000',   // дальше можно писать page.goto('/login')
    trace: 'on-first-retry',            // трассировка только на первом повторе
  },
  webServer: {
    command: 'npm run dev',
    url: 'http://localhost:3000',
    reuseExistingServer: !process.env.CI,
  },
});
```

Блок `webServer` поднимает приложение перед прогоном и ждёт, пока адрес начнёт
отвечать. Параметр `reuseExistingServer` оставляет уже запущенный локальный
сервер в покое, а на машине сборки поднимает свой.

**Сквозной пример всей темы — доска задач.** Все девять статей разбирают один и
тот же интерфейс:

- `/login` — форма входа: поля «Email» и «Пароль», кнопка «Войти».
- `/tasks` — список задач с фильтром по статусу и пагинацией по двадцать штук.
- `POST /api/login` — принимает пару логин-пароль, отвечает токеном сессии.
- `GET /api/tasks?status=open&page=2` — отдаёт страницу списка и общее число задач.

Первый тест на этом стенде проверяет самый частый путь: вход и переход к списку.

```ts
// tests/login.spec.ts
import { test, expect } from '@playwright/test';

test('вход открывает список задач', async ({ page }) => {
  await page.goto('/login');
  await page.getByLabel('Email').fill('maria@example.com');
  await page.getByLabel('Пароль').fill('correct-horse');
  await page.getByRole('button', { name: 'Войти' }).click();

  await expect(page.getByRole('heading', { name: 'Задачи' })).toBeVisible();
  await expect(page).toHaveURL('/tasks');   // baseURL подставляется сам
});
```

Обратите внимание, чего в этом тесте нет. Ожиданий вида «подожди две секунды»
здесь нет: ждёт сам локатор, и это тема статьи
[Локатор описывает элемент, а не находит его](./02-locators.md). Очистки
состояния после теста тоже нет, потому что следующий тест получит новый контекст.

## Один тест может держать два контекста сразу

Второй контекст нужен там, где в сценарии участвуют два пользователя.

```ts
// tests/visibility.spec.ts
import { test, expect } from '@playwright/test';

test('задача Марии не видна Ивану', async ({ browser }) => {
  const mariaContext = await browser.newContext({ storageState: 'auth/maria.json' });
  const ivanContext = await browser.newContext({ storageState: 'auth/ivan.json' });
  const maria = await mariaContext.newPage();
  const ivan = await ivanContext.newPage();

  await maria.goto('/tasks');
  await expect(maria.getByText('Отчёт за май')).toBeVisible();

  await ivan.goto('/tasks');
  await expect(ivan.getByText('Отчёт за май')).toHaveCount(0);  // 0 совпадений

  await mariaContext.close();
  await ivanContext.close();
});
```

Два контекста внутри одного браузера не видят данных друг друга, поэтому вход
Марии не делает Ивана авторизованным. Вторая вкладка того же контекста так не
работает: она разделяет cookies и хранилище с первой. Откуда берутся файлы
`auth/maria.json`, разбирает статья
[Логин один раз, а не в каждом тесте](./06-auth-and-state.md).

## Типичные ошибки

- **Логиниться через форму в каждом тесте.** Симптом: набор тестов растёт по
  времени линейно, и половина шагов в отчёте — один и тот же вход. Состояние
  входа сохраняют один раз.
- **Ждать, что браузер перезапустится между тестами.** Симптом: тест
  рассчитывает на свежий процесс или другие флаги запуска, а получает прежние.
  Перезапуск даёт падение теста, и то не всегда.
- **Открывать вторую вкладку вместо второго контекста.** Симптом: второй
  пользователь оказывается тем же самым, потому что cookies общие.
- **Не закрывать контексты, созданные вручную.** Симптом: прогон держит память и
  долго не завершается. Фикстура `page` закрывается сама, `browser.newContext()`
  — нет.
