# CQRS и Event Sourcing — разделение моделей и журнал событий

> **Область применения:** CQRS (Command Query Responsibility Segregation — разделение команд и запросов) и Event Sourcing разобраны здесь как паттерны. Реализация на Nest.js — в статье [разделение команд и запросов в Nest.js](../../nestjs/ru/08-cqrs-pattern.md). Реплики для чтения — в статье [масштабирование базы данных](../../system-design/ru/04-database-scaling.md).

## CQRS разделяет модели, а не базы данных

Разделение ответственности команд и запросов означает, что запись и чтение описываются двумя разными моделями. Команда меняет состояние и защищает бизнес-правила. Запрос ничего не меняет и отдаёт данные в форме, удобной конкретному экрану.

Проблема, из которой это выросло, видна на обычном сервисе с одной моделью:

```ts
// Одна модель обслуживает и запись, и отчёт — и мешает обоим
// src/orders/orders.service.ts
interface OrderRow {
  id: string;
  customerId: string;
  status: 'pending' | 'paid' | 'shipped';
  totalUsd: number;
  createdAt: Date;
}

interface OrderTable {
  findOne(id: string): Promise<OrderRow | null>;
  findCreatedAfter(from: Date): Promise<OrderRow[]>;
  update(id: string, patch: Partial<OrderRow>): Promise<void>;
}

export class OrdersService {
  constructor(private readonly orders: OrderTable) {}

  // Запись: нужны правила перехода состояний
  async ship(orderId: string): Promise<void> {
    const order = await this.orders.findOne(orderId);
    if (!order) throw new Error(`Заказ ${orderId} не найден`);
    if (order.status !== 'paid') throw new Error('Отгрузка до оплаты запрещена');
    await this.orders.update(orderId, { status: 'shipped' });
  }

  // Чтение: экрану отчёта нужны имя клиента и регион, которых в OrderRow нет
  async report(from: Date): Promise<OrderRow[]> {
    return this.orders.findCreatedAfter(from); // клиентов добирают отдельно
  }
}
```

Модель `OrderRow` нормализована ради целостности данных. Экран отчёта хочет ровно противоположного: плоскую строку, где имя клиента и регион уже подставлены. Одна структура не может быть хороша для обеих задач.

CQRS отвечает на это двумя отдельными типами:

```ts
// Сторона записи: агрегат, который защищает правило перехода
// src/orders/write/order.aggregate.ts
export class Order {
  constructor(
    private readonly id: string,
    private status: 'pending' | 'paid' | 'shipped',
  ) {}

  ship(): void {
    if (this.status !== 'paid') {
      throw new Error(`Заказ ${this.id}: отгрузка до оплаты запрещена`);
    }
    this.status = 'shipped';
  }
}

const order = new Order('42', 'pending');
try {
  order.ship();
} catch (e) {
  console.log((e as Error).message); // Заказ 42: отгрузка до оплаты запрещена
}

// Сторона чтения: плоская строка ровно под экран отчёта, без правил
// src/orders/read/order-report.row.ts
export interface OrderReportRow {
  orderId: string;
  customerName: string; // подставлено заранее, не в момент запроса
  region: string;
  totalUsd: number;
  status: string;
}
```

Сторона записи не умеет отдавать `OrderReportRow`, а сторона чтения не знает про правило «нельзя отгрузить до оплаты». Это и есть разделение ответственности. Точки входа разделяют так же: команда `ShipOrder` идёт в свой обработчик, запрос `OrderReport` — в свой.

## Чего CQRS не означает

Половина ошибок на интервью — это лишние требования, которые паттерну приписывают. Их стоит перечислить прямо:

- **Не «две базы данных».** Разделение может целиком жить в одной схеме и одной транзакции.
- **Не «шина сообщений».** Команду можно выполнить синхронно, внутри того же запроса.
- **Не «Event Sourcing».** Это два независимых паттерна, и каждый работает без второго.
- **Не «команда обязана возвращать пустой ответ».** На практике команда возвращает id созданной записи, и это нормально.
- **Не про способ передачи данных.** Формат ответа и выбор протокола к паттерну отношения не имеют.

Разделение — это лестница, а не выключатель. Подняться можно на одну ступень и остановиться:

```txt
         Три уровня разделения записи и чтения
┌─────────────────────────────────────────────────────┐
│ Уровень 1. Два набора методов в одном сервисе       │
│   общее: модель, схема, база данных                 │
│   даёт: читаемость. Не даёт: масштабирования        │
├─────────────────────────────────────────────────────┤
│ Уровень 2. Две модели поверх одной базы данных      │
│   общее: база данных и транзакция                   │
│   даёт: запрос под конкретный экран                 │
├─────────────────────────────────────────────────────┤
│ Уровень 3. Два хранилища, связанные событиями       │
│   общее: только поток событий                       │
│   даёт: независимое масштабирование. Цена: задержка │
└─────────────────────────────────────────────────────┘
CQRS начинается на уровне 1 — второе хранилище необязательно
```

Уровень 1 — это старый принцип CQS (Command Query Separation — разделение команды и вопроса). По нему метод либо меняет состояние, либо отвечает на вопрос, но не делает то и другое сразу. Уровень 3 — тот, о котором обычно спрашивают. Запись идёт в нормализованные таблицы PostgreSQL, а чтение — из денормализованных документов или из Elasticsearch.

## Разделение окупается только при расхождении чтения и записи

Честный ответ для большинства проектов: подходит обычный CRUD (Create, Read, Update, Delete — создать, прочитать, обновить, удалить). Пока экран показывает те же поля, которые вы пишете, вторая модель не даёт ничего, кроме лишнего кода.

| Сигнал в требованиях | Что он значит для решения |
|---|---|
| Читают в десятки раз чаще, чем пишут | Стоит вынести чтение в отдельную модель |
| Отчёт собирает данные из 5–6 таблиц | Проекция уберёт соединения из момента запроса |
| Правила записи сложные и их много | Агрегат стоит освободить от формы для экрана |
| Поиск идёт по тексту, а запись реляционная | Второе хранилище оправдано (например, Elasticsearch) |
| Форма экрана совпадает с формой таблицы | Обычный CRUD, разделение не нужно |
| Команда меньше 5 человек, срок короткий | Обычный CRUD, разделение не нужно |

Типичный пример из практики — каталог товаров. Каталог читают тысячи раз в минуту, а склад пишет остатки редко, зато с проверками. Здесь разделение оправдано, потому что нагрузка и форма данных расходятся, а домен остаётся общим.

## Event Sourcing делает журнал событий источником правды

Event Sourcing — это хранение изменений вместо текущего состояния. В журнал добавляются неизменяемые события в прошедшем времени, и он и есть источник правды. Текущее состояние в базе не хранится: его выводят из журнала.

```sql
-- Классическое хранение: текущее состояние перезаписывается
UPDATE orders SET status = 'shipped' WHERE id = 42;
-- после этого в таблице осталось только слово 'shipped'

-- Event Sourcing: то же изменение — новая строка в журнале
INSERT INTO events (stream_id, version, type, payload)
VALUES ('42', 4, 'OrderShipped', '{"carrier":"DHL"}');
-- версии 1, 2 и 3 остаются на месте и остаются читаемыми
```

Разница в том, что `UPDATE` уничтожает предыдущее значение. Журнал не уничтожает ничего, поэтому даёт три вещи, которых у обычной таблицы нет:

- **Полный след изменений.** Видно, что произошло, в каком порядке и с какими данными.
- **Запросы к прошлому.** Можно ответить «каким был баланс тридцать дней назад».
- **Правила, зависящие от истории.** Например, скидка за третий заказ в месяц.

Вот как выглядит один заказ, сохранённый событиями:

```ts
// Журнал одного заказа: полная история вместо одной строки
// каждое событие неизменяемо и названо в прошедшем времени
const stream = [
  { version: 1, type: 'OrderPlaced', total: 120, at: '2026-03-01T10:00Z' },
  { version: 2, type: 'OrderPaid', amount: 120, at: '2026-03-01T10:04Z' },
  { version: 3, type: 'OrderItemRemoved', price: 20, at: '2026-03-02T09:10Z' },
  { version: 4, type: 'OrderShipped', carrier: 'DHL', at: '2026-03-03T08:00Z' },
];

console.log(stream.length); // 4 — и ни одна запись никогда не менялась
```

## Состояние восстанавливают свёрткой событий

Текущее состояние получают, прогоняя события по порядку через функцию перехода. Это обычная свёртка: начальное состояние плюс список событий дают результат. Никакой магии здесь нет — это `reduce`.

```ts
// Восстановление состояния: свёртка журнала слева направо
// src/orders/write/replay.ts
type OrderEvent =
  | { type: 'OrderPlaced'; total: number }
  | { type: 'OrderPaid'; amount: number }
  | { type: 'OrderItemRemoved'; price: number }
  | { type: 'OrderShipped'; carrier: string };

interface OrderState {
  total: number;
  status: 'none' | 'pending' | 'paid' | 'shipped';
}

const initial: OrderState = { total: 0, status: 'none' };

function apply(state: OrderState, event: OrderEvent): OrderState {
  switch (event.type) {
    case 'OrderPlaced':
      return { total: event.total, status: 'pending' };
    case 'OrderPaid':
      return { ...state, status: 'paid' };
    case 'OrderItemRemoved':
      return { ...state, total: state.total - event.price };
    case 'OrderShipped':
      return { ...state, status: 'shipped' };
  }
}

const events: OrderEvent[] = [
  { type: 'OrderPlaced', total: 120 },
  { type: 'OrderPaid', amount: 120 },
  { type: 'OrderItemRemoved', price: 20 },
  { type: 'OrderShipped', carrier: 'DHL' },
];

console.log(events.reduce(apply, initial));
// { total: 100, status: 'shipped' }
```

Порядок событий здесь несёт весь смысл. Поставьте `OrderPlaced` после `OrderItemRemoved` — и свёртка даст сумму 120 вместо 100. Поэтому событиям нужен номер версии внутри потока, а не только время: часы разных узлов расходятся, а номер версии — нет.

Так выглядит полный путь одной команды:

```txt
        Путь записи: журнал вместо UPDATE
┌───────────────────────────────────────────────┐
│ Команда ShipOrder(orderId=42)                 │
└───────────────────────────────────────────────┘
                        │  SELECT по streamId
                        ▼
┌───────────────────────────────────────────────┐
│ Читаем события заказа 42 из журнала           │
└───────────────────────────────────────────────┘
                        │  свёртка событий
                        ▼
┌───────────────────────────────────────────────┐
│ Восстанавливаем состояние и проверяем правила │
└───────────────────────────────────────────────┘
                        │  INSERT, без UPDATE
                        ▼
┌───────────────────────────────────────────────┐
│ Дописываем событие OrderShipped(42)           │
└───────────────────────────────────────────────┘
                        │  подписка на журнал
                        ▼
┌───────────────────────────────────────────────┐
│ Проектор обновляет строку модели чтения       │
└───────────────────────────────────────────────┘
        текущего состояния в журнале нет:
       оно каждый раз выводится из событий
```

Отсюда важный вывод против частого заблуждения: сам Event Sourcing чтение не ускоряет. Свёртка сорока тысяч событий медленнее, чем чтение одной строки по первичному ключу. Скорость чтения даёт не журнал, а снимки и проекции.

## Снимок сокращает свёртку, ничего не меняя в модели

Снимок (snapshot) — это сохранённое состояние на известной версии потока. При загрузке берут последний снимок и досчитывают только события после него.

```ts
// Снимок: состояние плюс версия последнего учтённого события
// src/orders/write/load-with-snapshot.ts
import { apply, initial, type OrderEvent, type OrderState } from './replay';

interface Snapshot {
  streamId: string;
  version: number;
  state: OrderState;
}

declare const snapshots: {
  findLatest(streamId: string): Promise<Snapshot | null>;
};
declare const eventStore: {
  readAfter(streamId: string, version: number): Promise<OrderEvent[]>;
};

async function loadOrder(streamId: string): Promise<OrderState> {
  const snap = await snapshots.findLatest(streamId);
  const tail = await eventStore.readAfter(streamId, snap?.version ?? 0);
  return tail.reduce(apply, snap?.state ?? initial);
}
// 40 000 событий, снимок на версии 39 900 → свёртка по 100 событиям
```

Снимок — оптимизация, а не отдельный источник правды. Его можно удалить и пересобрать из журнала в любой момент, и данные от этого не потеряются. Именно поэтому снимок не усложняет модель: он ничего не добавляет к смыслу событий.

## Проекции дают быстрые чтения ценой задержки

Проекция — это таблица или документ, построенные из событий под конкретный запрос. Проектор подписывается на журнал, обрабатывает события по одному и обновляет модель чтения. Бизнес-правил в проекторе нет — он только перекладывает данные.

Отдельный вопрос — как событие гарантированно доходит до проектора. В Event Sourcing журнал и есть источник, поэтому проектор читает его с сохранённой позиции. В CQRS без журнала событие пишут в той же транзакции, что и состояние, в таблицу исходящих сообщений (transactional outbox). Публикует её отдельный процесс.

```ts
// Проектор: одно событие → одна правка в модели чтения
// src/orders/read/order-report.projector.ts
import type { OrderReportRow } from './order-report.row';

interface OrderPlacedEvent {
  orderId: string;
  customerName: string; // положено в событие ещё при записи
  region: string;
  total: number;
}

interface ReportRowStore {
  insert(row: OrderReportRow): Promise<void>;
  setStatus(orderId: string, status: string): Promise<void>;
}

export class OrderReportProjector {
  constructor(private readonly rows: ReportRowStore) {}

  async onOrderPlaced(event: OrderPlacedEvent): Promise<void> {
    await this.rows.insert({
      orderId: event.orderId,
      customerName: event.customerName,
      region: event.region,
      totalUsd: event.total,
      status: 'pending',
    });
  }

  async onOrderShipped(event: { orderId: string }): Promise<void> {
    await this.rows.setStatus(event.orderId, 'shipped');
  }
}
```

Между записью и обновлением проекции есть окно. В нём команда уже принята, а экран, читающий проекцию, ещё показывает старые данные. Это и называется eventual consistency — согласованность в конечном счёте:

```txt
t = 0 мс    команда принята, событие OrderPlaced записано в журнал
t = 0 мс    клиент получил ответ 201 Created
t = 15 мс   проектор прочитал событие из журнала
t = 40 мс   строка в модели чтения обновлена

окно 0..40 мс: заказ уже существует, но в списке заказов его ещё нет
```

Пользователь замечает это очень быстро: он оформил заказ и сразу обновил страницу истории. Три рабочих способа закрыть окно, и выбор между ними — продуктовое решение:

- **Читать свою запись со стороны записи.** Страницу подтверждения строят из данных команды, минуя проекцию.
- **Показывать состояние «обрабатывается».** Проекция честно моделирует промежуточный статус, а экран его отображает.
- **Опрашивать проекцию.** Экран несколько сотен миллисекунд показывает индикатор и повторяет запрос.

Та же задержка возникает и без событий — на обычных репликах для чтения. Механику и её последствия разбирает статья [масштабирование базы данных](../../system-design/ru/04-database-scaling.md).

## Версионирование: старые события поднимают до новой формы при чтении

Журнал неизменяем, поэтому обычной миграции схемы у него не бывает. Событие, записанное два года назад, останется в старой форме навсегда. Читающий код должен понимать все формы, которые когда-либо писались.

```ts
// Версия 1 лежит в журнале навсегда — её нельзя переписать
interface UserRegisteredV1 {
  type: 'UserRegistered';
  v: 1;
  name: string;
}

// Версия 2 разделила имя на две части
interface UserRegisteredV2 {
  type: 'UserRegistered';
  v: 2;
  firstName: string;
  lastName: string;
}

// Преобразователь версии (upcaster) поднимает старую форму до новой
function upcast(event: UserRegisteredV1 | UserRegisteredV2): UserRegisteredV2 {
  if (event.v === 2) return event;
  const [firstName, ...rest] = event.name.split(' ');
  return { type: 'UserRegistered', v: 2, firstName, lastName: rest.join(' ') };
}

console.log(upcast({ type: 'UserRegistered', v: 1, name: 'Ада Лавлейс' }));
// { type: 'UserRegistered', v: 2, firstName: 'Ада', lastName: 'Лавлейс' }
```

Отсюда два практических правила. Номер версии в событие кладут с первого дня, иначе потом придётся угадывать форму по набору полей. Преобразователи держат в одном месте на границе чтения, чтобы остальной код знал только последнюю версию.

Три ошибки в версионировании встречаются чаще остальных:

- **Переименовать поле и молча перезаписать журнал.** Так теряется история, ради которой журнал и заводили.
- **Удалить обработчик события, которое больше не пишется.** Старые записи остались, и свёртка на них упадёт.
- **Сделать поле обязательным задним числом.** У прежних событий его нет, и преобразователю нечем его заполнить.

## CQRS без Event Sourcing и Event Sourcing без CQRS — разные вещи

Это два независимых паттерна, и на интервью их путают чаще всего. CQRS говорит про модели. Event Sourcing говорит про способ хранения.

```txt
             Что даёт каждый паттерн по отдельности
┌─────────────────┬───────────────────┬────────────────────────┐
│ признак         │ только CQRS       │ только Event Sourcing  │
├─────────────────┼───────────────────┼────────────────────────┤
│ источник правды │ текущее состояние │ журнал событий         │
├─────────────────┼───────────────────┼────────────────────────┤
│ чтение          │ отдельная модель  │ свёртка или проекция   │
├─────────────────┼───────────────────┼────────────────────────┤
│ удалить запись  │ обычный DELETE    │ обратное событие       │
├─────────────────┼───────────────────┼────────────────────────┤
│ смена схемы     │ ALTER TABLE       │ преобразователь версии │
├─────────────────┼───────────────────┼────────────────────────┤
│ нужен ли второй │ работает сам      │ почти всегда с CQRS    │
└─────────────────┴───────────────────┴────────────────────────┘
 колонки независимы: пары «CQRS = Event Sourcing» не существует
```

Асимметрия здесь важна, и её стоит проговорить вслух:

- **CQRS без Event Sourcing** — обычный и самый частый случай. Пишете текущее состояние, читаете из отдельной модели или реплики.
- **Event Sourcing без CQRS** — возможен, но неудобен. Каждое чтение придётся собирать свёрткой, а это медленно.
- **Оба вместе** — команды дописывают события, проекции обслуживают чтение. Именно эту связку обычно имеют в виду.

Как это выглядит в коде Nest.js — с `CommandBus`, `QueryBus`, обработчиками событий и сагами — разобрано в статье [паттерн разделения команд и запросов в Nest.js](../../nestjs/ru/08-cqrs-pattern.md).

## Цена: нет простого удаления, отладка сложнее, миграции превращаются в код

Журнал вместо текущего состояния стоит пяти вещей, и каждая всплывает в первый месяц работы.

| Что дорожает | Почему | Что делают на практике |
|---|---|---|
| Удаление данных | событие неизменяемо, `DELETE` не применить | компенсирующее событие |
| Объём хранения | храните все изменения, а не одну строку | архивация старых потоков |
| Отладка | статус выводится из потока, а не читается | инструмент просмотра потока |
| Смена формы события | миграции схемы у журнала не бывает | преобразователь при чтении |
| Конкурентная запись | журнал сам не мешает двум командам | уникальность пары «поток плюс версия» |

Один пункт заслуживает отдельной оговорки — удаление персональных данных. Компенсирующее событие требование не закрывает: прежние данные остаются в журнале. Рабочий приём для GDPR (General Data Protection Regulation — регламент о защите персональных данных) — хранить такие поля зашифрованными и удалять ключ.

Порядок событий и конкурентную запись тоже приходится обеспечивать самому. Журнал не мешает двум командам записать пятую версию одного потока. Защита строится прямо в схеме, на уникальности пары «поток плюс версия»:

```sql
-- Порядок и защита от конкурентной записи в самой схеме
CREATE TABLE events (
  stream_id   text        NOT NULL,
  version     integer     NOT NULL,
  type        text        NOT NULL,
  payload     jsonb       NOT NULL,
  occurred_at timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY (stream_id, version)
);

-- Две команды прочитали версию 4 и обе пытаются записать пятую:
INSERT INTO events (stream_id, version, type, payload)
VALUES ('42', 5, 'OrderShipped', '{"carrier":"DHL"}');
-- ERROR:  duplicate key value violates unique constraint "events_pkey"
```

Проигравшая команда получает ошибку, перечитывает поток и повторяет попытку. Это оптимистичная блокировка, и без неё «неизменяемый журнал» не спасает от гонок.

## Когда эта связка оправдана

Классический подходящий домен — платежи и всё, где история изменений обязательна по регламенту. Там нужны и полный след, и повторное проигрывание, и отдельная нагрузка на чтение отчётов. Собирается это так:

- **Сторона записи — Event Sourcing.** Журнал платёжных событий даёт неоспоримый след и возможность проиграть день заново.
- **Сторона чтения — проекции.** Отчётные экраны читают денормализованные таблицы, а не журнал.
- **Внешние платёжные шлюзы — порты и адаптеры.** Каждый провайдер становится заменяемым адаптером, см. [гексагональную архитектуру](./04-hexagonal-architecture.md).
- **Ядро домена — независимо от инфраструктуры.** Правила не знают ни про журнал, ни про шлюз, см. [чистую архитектуру](./03-clean-architecture.md).

Обратный пример столь же важен. Административная панель, справочники, настройки, внутренние инструменты — здесь берут обычный CRUD и слой репозитория из статьи [паттерны Repository и Service](./05-repository-and-service-patterns.md). Event Sourcing в таком проекте добавит журнал, преобразователи версий и проекторы, не решив ни одной реальной задачи.

Отдельная оговорка про распределённые системы. CQRS и Event Sourcing работают внутри одного приложения и не требуют микросервисов. Границы сервисов и владение данными — тема статьи [монолит против микросервисов](./06-monolith-vs-microservices.md).

## Типичные ошибки на интервью

- **«CQRS — это две базы данных».** Нет. Это две модели, и обе могут лежать в одной схеме. Второе хранилище — отдельное решение, которое принимают позже.

- **«CQRS и Event Sourcing — одно и то же».** Нет. CQRS про разделение моделей чтения и записи. Event Sourcing про хранение истории вместо текущего состояния. CQRS применяют без журнала событий постоянно.

- **«Event Sourcing ускоряет чтение».** Наоборот: свёртка потока медленнее чтения одной строки. Ускоряют снимки и проекции, а не сам журнал.

- **«Журнал событий гарантирует консистентность».** Не гарантирует. Порядок в потоке надо обеспечить самому, а конкурентную запись закрыть уникальностью пары «поток плюс версия».

- **«События можно поправить миграцией».** Журнал неизменяем. Изменение формы события означает новую версию и преобразователь при чтении, а не `ALTER TABLE`.

- **«Снимки усложняют модель».** Снимок — кэш свёртки. Его можно удалить и пересобрать из журнала, и ничего не потеряется.

- **«Раз есть CQRS, нужна шина сообщений».** Не нужна. Команда может выполняться синхронно, в том же HTTP-запросе. Шину добавляют, когда появляется второе хранилище для чтения.

- **Молчать про eventual consistency.** Это центральная плата за разделение. Ответ без окна рассинхронизации и без способа его закрыть выглядит выученным, а не прожитым.
