# SVG, D3 и выбор технологии визуализации

## Замыкаем пространство решений

Статьи 01-06 закрыли путь от immediate-mode Canvas 2D до WebGL/Pixi/three.js. Эта статья возвращает в картину SVG — технологию, которая не canvas и не WebGL, а третий, во многом недооценённый путь — и разбирает d3.js, вероятно, самую неправильно понимаемую библиотеку во всей области визуализации данных (не в последнюю очередь из-за схожего звучания названия с three.js, хотя это два совершенно не связанных инструмента для двух разных задач). Цель — дать целостную карту выбора: DOM/CSS → SVG → Canvas 2D → WebGL/Pixi → готовые чарт-библиотеки, и честное правило, когда переходить с одного уровня на следующий.

## SVG: retained-mode векторный DOM

SVG-элементы (`<circle>`, `<rect>`, `<path>`) — это НАСТОЯЩИЕ DOM-узлы, в буквальном смысле того же рода, что `<div>`, только рисующие себя как векторную геометрию, а не блочный layout:

```html
<svg width="400" height="300">
  <circle cx="100" cy="100" r="20" fill="steelblue" />
</svg>
```

Из этого следует всё остальное, что отличает SVG от canvas:

```txt
- Инспектируется в DevTools как обычный DOM-элемент
- Стилизуется через CSS (fill, stroke — обычные CSS-свойства),
  анимируется через CSS transitions/WAAPI (та же ретеинд-модель,
  что разобрана в browser-animation — SVG её полноценно разделяет)
- Доступен для скринридеров "из коробки": ARIA-атрибуты вешаются
  прямо на элементы, дерево SVG обходится вспомогательными
  технологиями так же, как обычный DOM
- Чёткий на любом зуме/DPI, потому что это вектор, а не растровый
  буфер — проблемы devicePixelRatio из статьи 01 для SVG попросту
  не существует
```

**Но каждый SVG-элемент — это реальный DOM-узел с реальными накладными расходами DOM** (пересчёт стилей, layout, память под каждый узел) — те же издержки, что разобраны применительно к DOM-анимации в browser-animation. Scatter-plot с 50 000 `<circle>` — это 50 000 живых DOM-узлов, и браузер платит за КАЖДЫЙ из них при первом рендере, при любом обновлении, при скролле страницы. Тот же scatter-plot на canvas — один DOM-узел (сам `<canvas>`) независимо от того, 50 или 50 000 точек внутри.

## Что такое d3 на самом деле — и чем он НЕ является

d3 — сокращение от **Data-Driven Documents** (документы, управляемые данными). Это НЕ 3D-библиотека (несмотря на созвучие с "three.js" — совпадение названий, не связанные вещи) и не в первую очередь чарт-библиотека — это набор небольших, независимых, компонуемых модулей:

```txt
d3-selection  — выборка и манипуляция DOM-узлами (концептуально
                 похоже на jQuery, но с осознанием привязанных данных)
d3-scale       — ЧИСТЫЕ функции: домен данных → визуальный диапазон
                 (линейные, временные, порядковые, логарифмические шкалы)
d3-shape       — ЧИСТЫЕ функции: массив данных → геометрия формы
                 (линия, площадь, дуга, "пирог")
d3-axis        — отрисовка делений и подписей осей для заданной шкалы
d3-force       — симуляция физики притяжения/отталкивания узлов графа
d3-geo         — картографические проекции
... и ещё несколько десятков узкоспециализированных модулей
```

Ключевое наблюдение: бо́льшая часть реальной ценности d3 — это МАТЕМАТИКА и УТИЛИТЫ ПРИВЯЗКИ ДАННЫХ, полностью независимые от того, КАК вы в итоге рисуете результат. `d3-scale`/`d3-shape` возвращают числа и строки геометрии — им всё равно, попадёт ли результат в атрибут `d` SVG-`<path>` или в вызов `ctx.lineTo()` на canvas.

## Selections и data join: enter/update/exit, и современный `.join()`

```javascript
d3.select('svg')
  .selectAll('circle')
  .data(dataset, (d) => d.id) // связываем DOM-узлы с элементами массива по id
  .join(
    (enter) => enter.append('circle').attr('r', 0)
      .call((e) => e.transition().attr('r', 5)), // НОВЫЕ данные — создаём узел
    (update) => update, // данные УЖЕ ЕСТЬ узел — просто обновляем атрибуты
    (exit) => exit.transition().attr('r', 0).remove(), // узел БЕЗ данных — удаляем
  )
  .attr('cx', (d) => xScale(d.x))
  .attr('cy', (d) => yScale(d.y));
```

Data join сверяет массив данных с уже существующими DOM-узлами, привязанными к ПРЕДЫДУЩЕМУ состоянию данных, и делит результат на три явные категории: **enter** — данные, для которых ещё нет DOM-узла (нужно создать), **update** — данные, для которых узел уже существует (нужно только обновить атрибуты), **exit** — узлы, для которых данных больше нет (нужно удалить). Это концептуально тот же вопрос, что решает React-реконсиляция (diff между предыдущим и новым деревом), только d3 делает это ЯВНО и вручную, а не через скрытый алгоритм виртуального DOM — и появился этот паттерн задолго до React. `.join()` — современный, консолидированный API, заменивший более многословную идиому с тремя отдельными переменными-селекциями enter/update/exit из ранних версий d3.

## Шкалы и генераторы форм: настоящее переиспользуемое ядро

```javascript
const xScale = d3.scaleLinear().domain([0, 100]).range([0, width]); // чистая математика: данные → пиксели
const yScale = d3.scaleLinear().domain([0, maxValue]).range([height, 0]);

const lineGenerator = d3.line()
  .x((d) => xScale(d.x))
  .y((d) => yScale(d.y)); // возвращает СТРОКУ для атрибута d="..." SVG-<path>
```

Это и есть настоящее, долговечное ценностное ядро d3 — не data join (который многие проекты вообще не используют, полагаясь на React/Vue для DOM) и не конкретно SVG-рендеринг, а именно рендерер-независимая математика шкал и генерация геометрии форм из данных.

## Гибридный паттерн: математика d3 + рендеринг на canvas

Поскольку `d3-scale`/`d3-shape` не привязаны к SVG, их можно использовать для больших датасетов, рисуя результат на canvas вместо тысяч DOM-узлов:

```javascript
const path = d3.line()
  .x((d) => xScale(d.x))
  .y((d) => yScale(d.y))
  .context(ctx); // КЛЮЧЕВОЙ метод: context() перенаправляет генератор
                  // формы рисовать через ctx.moveTo()/lineTo() вместо
                  // возврата строки SVG-пути

ctx.beginPath();
path(dataset); // та же математика шкал/форм, что и для SVG, но
                // результат идёт прямо в canvas-примитивы статьи 01
ctx.strokeStyle = 'steelblue';
ctx.stroke();
```

Это ровно тот приём, который senior-инженер должен уметь предложить на вопрос "как визуализировать 100 000 точек, если d3 обычно рисует в SVG": не отказываться от d3 полностью, а сохранить его превосходную математику шкал/форм, полностью убрав per-node DOM-издержки SVG и переключив рендеринг на canvas (статьи 01-03) — вопрос "SVG или canvas" и вопрос "использовать ли d3" на самом деле ОРТОГОНАЛЬНЫ друг другу.

## Честный фреймворк выбора

```txt
SVG            — интерактивные дашборды, до ~1-2 тысяч элементов,
                  когда важна доступность, CSS-стилизация, чёткость
                  на любом зуме, и богатая индивидуальная
                  интерактивность на КАЖДОМ элементе (обычные DOM-
                  события/hover-состояния проще всего подключаются
                  именно к отдельным SVG-узлам)

Canvas 2D      — 10 000+ точек, scatter-plot'ы, тепловые карты,
                  кастомная визуализация с попиксельным контролем —
                  там, где количество DOM-узлов само по себе стало
                  бы узким местом

WebGL/Pixi     — 100 000+ точек или обновление в реальном времени
                  на высокой частоте (потоковые данные, живые
                  дашборды с огромными сериями) — там, где даже
                  CPU-растеризация Canvas 2D упирается в потолок
                  (статья 04, батчинг и GPU-параллелизм)

Готовые чарт-  — ECharts, Chart.js и подобные закрывают ~90%
библиотеки       "стандартных" задач (bar/line/pie/scatter с
                  легендами, тултипами, адаптивным ресайзом)
                  заметно меньшим объёмом кода и более отполированным
                  поведением "из коробки" (доступность, интерактивность),
                  чем самостоятельная сборка на d3
```

**Честное build-vs-buy рассуждение senior-уровня:** ручная сборка на d3 оправдана для НЕСТАНДАРТНОЙ, самобытной визуализации, которая не укладывается в модель ни одной готовой чарт-библиотеки (уникальные layout'ы, нестандартные паттерны взаимодействия, оригинальные визуальные кодировки данных). Если задача — "построить bar chart с тултипами" — использование d3 напрямую вместо готовой библиотеки почти всегда означает переизобретение легенд, адаптивности и доступности, уже решённых где-то ещё, ради иллюзорной "гибкости", которая на практике редко становится реально нужной. Тянуться к d3 стоит не потому, что он мощный (это правда, но не аргумент сам по себе), а потому что конкретный дизайн визуализации ДЕЙСТВИТЕЛЬНО не может быть выражен ни одним готовым чарт-инструментом.

## Типичные ошибки на интервью

- **Путать d3.js с 3D/WebGL-библиотекой** — не знать, что "D3" означает Data-Driven Documents и не имеет отношения к трёхмерной графике — распространённая путаница из-за созвучия названий с three.js.

- **Не знать, почему SVG "не масштабируется" на больших датасетах** — не связывать деградацию производительности с тем, что каждый SVG-элемент — реальный DOM-узел с реальными издержками пересчёта стилей/layout/памяти, а не с расплывчатым "SVG медленный".

- **Не суметь объяснить enter/update/exit** — не знать, что это явный, ручной аналог того, что React делает через скрытую реконсиляцию virtual DOM, и что современный API для этого — `.join()`.

- **Считать d3 неотделимым от SVG** — не знать, что `d3-scale`/`d3-shape` — рендерер-независимая чистая математика, и что `d3.line().context(ctx)` позволяет рисовать ту же геометрию на canvas вместо SVG.

- **Не иметь фреймворка выбора между SVG/Canvas/WebGL по объёму данных** — не суметь дать даже приблизительные ориентиры (тысячи → SVG, десятки тысяч → canvas, сотни тысяч/реальное время → WebGL).

- **Всегда тянуться к ручной сборке на d3 вместо готовой чарт-библиотеки** — не иметь честного build-vs-buy рассуждения: для стандартных чартов готовая библиотека почти всегда выгоднее по времени разработки и качеству доступности/интерактивности "из коробки".
