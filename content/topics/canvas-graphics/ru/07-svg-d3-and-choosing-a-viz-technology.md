# SVG, d3.js и выбор технологии визуализации

## Замыкаем пространство решений

Эта статья возвращает SVG в картину выбора и разбирает d3.js. SVG (scalable vector graphics) — векторный формат, элементы которого это настоящие узлы DOM (document object model, дерево объектов страницы в браузере). Это не canvas и не WebGL (Web Graphics Library, низкоуровневый графический API браузера), а третий, во многом недооценённый путь.

Статьи 01-06 закрыли путь от immediate-mode Canvas 2D до WebGL/Pixi/three.js, и SVG — недостающий кусок этой картины. Самая неправильно понимаемая библиотека во всей визуализации данных — это, вероятно, d3.js. Причина отчасти в названии: оно созвучно three.js, хотя это два совершенно не связанных инструмента для разных задач.

Цель — дать целостную карту выбора: DOM/CSS → SVG → Canvas 2D → WebGL/Pixi → готовые чарт-библиотеки. К карте прилагается честное правило, когда переходить с одного уровня на следующий.

## SVG: retained-mode векторный DOM

SVG — это **retained-mode**, то есть режим с запоминанием: браузер хранит дерево элементов и перерисовывает его сам. SVG-элементы (`<circle>`, `<rect>`, `<path>`) — это **настоящие** DOM-узлы, в буквальном смысле того же рода, что `<div>`. Они лишь рисуют себя как векторную геометрию, а не блочный layout:

```html
<svg width="400" height="300">
  <circle cx="100" cy="100" r="20" fill="steelblue" />
</svg>
```

Из этого следует всё остальное, что отличает SVG от canvas:

```txt
- Инспектируется в DevTools как обычный DOM-элемент
- Стилизуется через CSS (fill, stroke — обычные CSS-свойства)
- Анимируется через CSS transitions и Web Animations API
  (WAAPI). Это та же retained-mode модель, что разобрана в
  browser-animation, и SVG пользуется ею целиком
- Доступен для скринридеров "из коробки": ARIA-атрибуты
  (accessible rich internet applications) вешаются прямо на
  элементы, а вспомогательные технологии обходят дерево SVG
  так же, как обычный DOM
- Чёткий на любом зуме и любом DPI (dots per inch, точек на
  дюйм), потому что это вектор, а не растровый буфер. Проблемы
  devicePixelRatio из статьи 01 для SVG попросту не существует
```

**Но каждый SVG-элемент — это реальный DOM-узел с реальными накладными расходами DOM**: пересчёт стилей, layout, память под каждый узел. Те же издержки разобраны применительно к DOM-анимации в browser-animation.

Диаграмма рассеяния (scatter plot) с 50 000 `<circle>` — это 50 000 живых DOM-узлов. Браузер платит за **каждый** из них при первом рендере, при любом обновлении, при скролле страницы. Та же диаграмма на canvas — один DOM-узел (сам `<canvas>`) независимо от того, 50 или 50 000 точек внутри.

## Что такое d3 на самом деле — и чем он не является

d3 — сокращение от **Data-Driven Documents** (документы, управляемые данными). Это **не** 3D-библиотека, несмотря на созвучие с "three.js": совпадение названий, не признак родства. И это не в первую очередь чарт-библиотека. Это набор небольших, независимых, компонуемых модулей:

```txt
d3-selection  — выборка и манипуляция DOM-узлами (концептуально
                 похоже на jQuery, но с учётом привязанных данных)
d3-scale       — чистые функции: домен данных → визуальный диапазон
                 (линейные, временные, порядковые,
                 логарифмические шкалы)
d3-shape       — чистые функции: массив данных → геометрия формы
                 (линия, площадь, дуга, "пирог")
d3-axis        — отрисовка делений и подписей осей для
                 заданной шкалы
d3-force       — симуляция физики притяжения/отталкивания
                 узлов графа
d3-geo         — картографические проекции
... и ещё несколько десятков узкоспециализированных модулей
```

Ключевое наблюдение: бо́льшая часть реальной ценности d3 — это **математика** и **утилиты привязки данных**, полностью независимые от того, **как** вы рисуете результат. И `d3-scale`, и `d3-shape` возвращают числа и строки геометрии. Им всё равно, попадёт ли результат в атрибут `d` SVG-`<path>` или в вызов `ctx.lineTo()` на canvas.

## Selections и data join: enter/update/exit, и современный `.join()`

```javascript
d3.select('svg')
  .selectAll('circle')
  .data(dataset, (d) => d.id) // связываем DOM-узлы с элементами массива по id
  .join(
    (enter) => enter.append('circle').attr('r', 0)
      .call((e) => e.transition().attr('r', 5)), // новые данные — создаём узел
    (update) => update, // у данных уже есть узел — обновляем атрибуты
    (exit) => exit.transition().attr('r', 0).remove(), // узел без данных — удаляем
  )
  .attr('cx', (d) => xScale(d.x))
  .attr('cy', (d) => yScale(d.y));
```

Data join сверяет массив данных с уже существующими DOM-узлами, привязанными к **предыдущему** состоянию данных. Результат делится на три явные категории:

- **enter** — данные, для которых DOM-узла ещё нет: узел нужно создать.
- **update** — данные, для которых узел уже существует: нужно обновить атрибуты.
- **exit** — узлы, для которых данных больше нет: их нужно удалить.

Концептуально это та же задача, что решает React-реконсиляция: сравнить предыдущее дерево с новым. Разница в том, что d3 делает это **явно** и вручную, а не через скрытый алгоритм виртуального DOM. И появился этот паттерн задолго до React.

Метод `.join()` — современный, консолидированный API для этого. Он заменил более многословную идиому с тремя отдельными переменными-селекциями enter/update/exit из ранних версий d3.

## Шкалы и генераторы форм: настоящее переиспользуемое ядро

```javascript
const width = 600;
const height = 400;
const maxValue = d3.max(dataset, (d) => d.y); // максимальный y в данных

// чистая математика: данные → пиксели
const xScale = d3.scaleLinear().domain([0, 100]).range([0, width]);
const yScale = d3.scaleLinear().domain([0, maxValue]).range([height, 0]);

const lineGenerator = d3.line()
  .x((d) => xScale(d.x))
  .y((d) => yScale(d.y)); // возвращает строку для атрибута d="..." SVG-<path>
```

Это и есть настоящее, долговечное ядро ценности d3. Не data join: многие проекты его вообще не используют, полагаясь на React/Vue для DOM. И не конкретно SVG-рендеринг. А рендерер-независимая математика шкал и генерация геометрии форм из данных.

## Гибридный паттерн: математика d3 + рендеринг на canvas

Модули `d3-scale` и `d3-shape` не привязаны к SVG. Их можно использовать для больших наборов данных, рисуя результат на canvas вместо тысяч DOM-узлов:

```javascript
// xScale/yScale — из сниппета со шкалами выше
const path = d3.line()
  .x((d) => xScale(d.x))
  .y((d) => yScale(d.y))
  .context(ctx); // ключевой метод: context() перенаправляет генератор
                  // формы рисовать через ctx.moveTo()/lineTo() вместо
                  // возврата строки SVG-пути

ctx.beginPath();
path(dataset); // та же математика шкал/форм, что и для SVG, но
                // результат идёт прямо в canvas-примитивы статьи 01
ctx.strokeStyle = 'steelblue';
ctx.stroke();
```

Это ровно тот приём, который senior-инженер должен предложить на вопрос "как визуализировать 100 000 точек, если d3 обычно рисует в SVG". Не отказываться от d3 полностью, а сохранить его математику шкал и форм, убрать per-node DOM-издержки SVG и переключить рендеринг на canvas (статьи 01-03).

Вопрос "SVG или canvas" и вопрос "использовать ли d3" на самом деле **ортогональны** друг другу.

## Честный фреймворк выбора

Ниже встречаются два аппаратных термина: CPU (central processing unit, центральный процессор) исполняет JS, а GPU (graphics processing unit, графический процессор) закрашивает пиксели.

```txt
SVG            — интерактивные дашборды, до ~1-2 тысяч элементов,
                  когда важна доступность, CSS-стилизация,
                  чёткость на любом зуме и богатая индивидуальная
                  интерактивность на каждом элементе (обычные
                  DOM-события и hover-состояния проще всего
                  подключаются именно к отдельным SVG-узлам)

Canvas 2D      — 10 000+ точек, диаграммы рассеяния, тепловые
                  карты, кастомная визуализация с попиксельным
                  контролем — там, где количество DOM-узлов само
                  по себе стало бы узким местом

WebGL/Pixi     — 100 000+ точек или обновление в реальном времени
                  на высокой частоте (потоковые данные, живые
                  дашборды с огромными сериями) — там, где даже
                  CPU-растеризация Canvas 2D упирается в потолок
                  (статья 04, батчинг и GPU-параллелизм)

Готовые чарт-  — ECharts, Chart.js и подобные закрывают ~90%
библиотеки       "стандартных" задач (bar/line/pie/scatter с
                  легендами, тултипами, адаптивным ресайзом)
                  заметно меньшим объёмом кода и более
                  отполированным поведением "из коробки"
                  (доступность, интерактивность), чем
                  самостоятельная сборка на d3
```

**Честное build-vs-buy рассуждение senior-уровня:** ручная сборка на d3 оправдана для нестандартной, самобытной визуализации, которая не укладывается в модель ни одной готовой чарт-библиотеки. Это уникальные раскладки, нестандартные паттерны взаимодействия, оригинальные визуальные кодировки данных.

Если задача — "построить bar chart с тултипами", то d3 напрямую вместо готовой библиотеки почти всегда означает переизобретение легенд, адаптивности и доступности. Всё это уже решено где-то ещё, а взамен вы получаете "гибкость", которая на практике редко оказывается нужной.

Тянуться к d3 стоит не потому, что он мощный: это правда, но не аргумент сам по себе. Тянуться стоит потому, что конкретный дизайн визуализации **действительно** не выражается ни одним готовым чарт-инструментом.

## Типичные ошибки на интервью

- **Путать d3.js с 3D/WebGL-библиотекой** — не знать, что `D3` означает Data-Driven Documents и не имеет отношения к трёхмерной графике. Путаница распространённая: название созвучно three.js.

- **Не знать, почему SVG "не масштабируется" на больших наборах данных** — не связывать деградацию производительности с конкретной причиной. Каждый SVG-элемент — реальный DOM-узел с реальными издержками пересчёта стилей, layout и памяти. Расплывчатое "SVG медленный" объяснением не считается.

- **Не суметь объяснить enter/update/exit** — не знать, что это явный, ручной аналог того, что React делает через скрытую реконсиляцию virtual DOM. Современный API для этого — `.join()`.

- **Считать d3 неотделимым от SVG** — не знать, что `d3-scale`/`d3-shape` — рендерер-независимая чистая математика, и что `d3.line().context(ctx)` позволяет рисовать ту же геометрию на canvas вместо SVG.

- **Не иметь фреймворка выбора между SVG/Canvas/WebGL по объёму данных** — не суметь дать даже приблизительные ориентиры. Тысячи элементов → SVG; десятки тысяч → canvas; сотни тысяч или реальное время → WebGL.

- **Всегда тянуться к ручной сборке на d3 вместо готовой чарт-библиотеки** — не иметь честного build-vs-buy рассуждения. Для стандартных чартов готовая библиотека почти всегда выгоднее по времени разработки и по качеству доступности и интерактивности "из коробки".
