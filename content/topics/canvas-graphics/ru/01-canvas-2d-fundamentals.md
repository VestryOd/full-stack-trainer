# Canvas 2D: фундамент

## Immediate mode: главный сдвиг мышления

Canvas забывает фигуру сразу после того, как её нарисовали. Возможно, вы пришли из DOM (document object model, дерево объектов страницы в браузере) или из SVG (scalable vector graphics, векторная графика). Тогда у вас есть рефлекс: создал элемент — он существует, его можно найти позже и изменить. На canvas этот рефлекс не работает.

И DOM, и SVG — **retained-mode** системы, то есть режим с запоминанием. Браузер хранит структуру объектов: дерево DOM-узлов или дерево `<circle>`/`<rect>`. Когда вы меняете `element.style.left`, браузер сам разбирается, что перерисовать. Эта сторона подробно разобрана в топике Browser Animation.

Canvas устроен принципиально иначе. Это **immediate-mode** система, немедленный режим: нарисовал и забыл. Вызов `ctx.fillRect(10, 10, 50, 50)` красит пиксели прямо сейчас и ничего не запоминает о том, что здесь был "прямоугольник".

Через мгновение для canvas это просто закрашенные пиксели в буфере, неотличимые от любых других. Нет объекта, которому можно сказать: подвинься на 10px вправо. Единственный способ что-либо изменить — **перерисовать всё заново** с нуля, или хотя бы ту часть, которая изменилась.

| DOM/SVG (retained mode) | Canvas (immediate mode) |
|---|---|
| `el.style.left = '110px'` | `ctx.clearRect(...)`, затем `ctx.fillRect(110, 10, 50, 50)` |
| Браузер сам перерисовывает только то, что нужно. | Вы сами решаете, что и когда перерисовать. |

Это не деталь синтаксиса. Именно поэтому вся архитектура canvas-приложений строится вокруг цикла "очистить → обновить состояние → нарисовать заново", а не вокруг мутации существующих объектов. На этом цикле стоят статьи 02 и 08.

## `getContext('2d')` и контекст как машина состояний

```javascript
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d');
```

`ctx` — не просто набор функций рисования, а **машина состояний**. У него есть текущие значения, которые сохраняются между вызовами, пока вы их явно не поменяете: `fillStyle`, `strokeStyle`, `lineWidth`, текущая трансформация, область отсечения. Это как перо, у которого есть текущий цвет и толщина: оно продолжает рисовать ими, пока вы не обмакнёте его в другой цвет.

```javascript
ctx.fillStyle = 'red';
ctx.fillRect(0, 0, 50, 50);   // красный квадрат
ctx.fillRect(60, 0, 50, 50);  // тоже красный — fillStyle не сбросился сам
ctx.fillStyle = 'blue';
ctx.fillRect(120, 0, 50, 50); // а теперь синий
```

`getContext('2d')` для одного и того же `<canvas>`-элемента всегда возвращает один и тот же объект контекста. Новый объект при каждом вызове не создаётся. Поэтому `ctx` можно смело кэшировать в переменную при инициализации компонента.

## Система координат

Начало координат — верхний левый угол. Ось X растёт вправо, ось Y растёт **вниз**. В математике Y растёт вверх, поэтому формулы из учебника физики нужно переносить с разворотом знака. Забытый разворот — источник постоянных ошибок.

Тонкость, о которой почти никто не думает до первого столкновения: тонкие линии (`lineWidth: 1`) на **целых** координатах выглядят размытыми. Линия шириной 1px рисуется "по центру" координаты и растекается на пол-пикселя в обе стороны. В итоге она попадает ровно на границу двух физических пикселей. Классический приём — сдвигать координаты линии на 0.5px:

```javascript
// ❌ Размытая линия — рисуется по границе пикселей 100 и 101
ctx.moveTo(100, 0);
ctx.lineTo(100, 200);

// ✅ Чёткая линия шириной в 1 физический пиксель
ctx.moveTo(100.5, 0);
ctx.lineTo(100.5, 200);
```

## Примитивы рисования

### Прямоугольники — без путей

```javascript
ctx.fillRect(x, y, width, height);   // залитый прямоугольник, немедленно
ctx.strokeRect(x, y, width, height); // обводка прямоугольника
ctx.clearRect(x, y, width, height);  // сделать область прозрачной
```

Это единственные примитивы, не требующие пути — вызов сразу рисует.

### Пути — универсальный механизм для всего остального

```javascript
ctx.beginPath();               // начать новый путь — сбрасывает накопленные точки
ctx.moveTo(50, 50);             // переместить "перо" без рисования линии
ctx.lineTo(150, 50);            // линия до точки
// дуга: центр, радиус, startAngle, endAngle, [anticlockwise]
ctx.arc(150, 100, 50, 0, Math.PI * 2);
// квадратичная кривая Безье (одна контрольная точка)
ctx.quadraticCurveTo(200, 150, 250, 50);
// кубическая кривая Безье (две контрольные точки)
ctx.bezierCurveTo(260, 0, 300, 0, 320, 50);
ctx.closePath();               // замкнуть путь линией к начальной точке

ctx.fill();   // залить накопленный путь
ctx.stroke(); // обвести накопленный путь
```

Забыть `beginPath()` перед новой фигурой — частый источник бага "рисуется какая-то каша". Предыдущие точки **не** сбрасываются автоматически: `moveTo`/`lineTo` продолжают накапливаться в том же пути. Дальше `fill()`/`stroke()` заливают и обводят **всё** накопленное с начала, включая фигуры из прошлых кадров.

### Правило заливки: nonzero vs evenodd

Когда путь самопересекается или содержит несколько под-контуров (например, круг внутри круга — "бублик"), браузер должен решить, какие области закрашивать. Правило по умолчанию — `nonzero`, то есть непустое правило. Для каждой точки считается, сколько раз контур "обвивает" её с учётом направления обхода. Если счётчик не равен нулю, точка закрашена.

```javascript
// "Бублик": внешний круг по часовой, внутренний — против часовой —
// направления противоположны, nonzero-правило даёт счётчик 0 внутри
// внутреннего круга → там дыра
ctx.beginPath();
ctx.arc(100, 100, 80, 0, Math.PI * 2, false); // внешний, по часовой
ctx.arc(100, 100, 40, 0, Math.PI * 2, true);  // внутренний, против часовой
ctx.fill(); // 'nonzero' — дефолт, даст правильный бублик с дырой

ctx.fill('evenodd'); // альтернативное правило — считает просто чётность
                      // пересечений луча с контуром, не заботясь о направлении
```

Практический вывод: если "бублик" внезапно закрасился сплошным кругом без дыры, оба контура почти всегда заданы в одном направлении обхода. Оба по часовой — значит, под правилом `nonzero` они не гасят друг друга. Разверните направление одного из них через параметр `anticlockwise` у `arc()` либо явно укажите `fill('evenodd')`.

## Стили: `fillStyle` — не только цвет

```javascript
// Цвет
ctx.fillStyle = '#3366ff';

// Линейный градиент
const gradient = ctx.createLinearGradient(0, 0, 200, 0); // x0,y0 → x1,y1
gradient.addColorStop(0, 'red');
gradient.addColorStop(1, 'blue');
ctx.fillStyle = gradient;

// Радиальный градиент — два круга (внутренний → внешний)
const radial = ctx.createRadialGradient(100, 100, 0, 100, 100, 80);
radial.addColorStop(0, 'white');
radial.addColorStop(1, 'transparent');

// Паттерн из изображения
const pattern = ctx.createPattern(imageElement, 'repeat');
ctx.fillStyle = pattern;
```

Стили для линий:

```javascript
ctx.lineWidth = 4;
ctx.lineCap = 'round';   // 'butt' | 'round' | 'square' — конец линии
ctx.lineJoin = 'round';  // 'miter' | 'round' | 'bevel' — угол между сегментами
ctx.setLineDash([8, 4]); // пунктир: 8px линия, 4px пробел
```

## Трансформации: порядок имеет значение

`translate`, `rotate`, `scale` не задают абсолютное состояние. Они **умножают** текущую матрицу трансформации на новую. Умножение матриц не коммутативно, поэтому `translate → rotate` и `rotate → translate` дают разный результат.

```javascript
// ❌ Вращение вокруг начала координат (0,0), а не вокруг центра фигуры —
// фигура "улетает" по окружности вместо вращения на месте
ctx.rotate(angle);
ctx.fillRect(centerX - 25, centerY - 25, 50, 50);
```

```javascript
// ✅ Классический паттерн "вращение вокруг точки":
// сдвинуть систему координат в точку вращения → повернуть →
// рисовать в локальных координатах относительно (0,0)
ctx.translate(centerX, centerY);
ctx.rotate(angle);
ctx.fillRect(-25, -25, 50, 50); // рисуем относительно нового (0,0)
```

Порядок вызовов читается как будто задом наперёд относительно интуиции. Запись `translate`, затем `rotate` означает: сначала перемести систему координат, затем поворачивай уже перемещённую. Это и даёт вращение вокруг новой точки, а не вокруг исходного начала координат.

`setTransform(a, b, c, d, e, f)` задаёт **абсолютную** матрицу вместо накопления поверх текущей. Это полезно, когда нужно точно знать итоговое состояние, не полагаясь на историю вызовов. Вызов `resetTransform()` сбрасывает матрицу к единичной.

## Стек состояний: `save()`/`restore()` — и классический баг утечки

`save()` кладёт в стек снимок **текущих** стилей и трансформации. Текущий путь в снимок **не** входит. Вызов `restore()` снимает верхний снимок со стека и возвращает состояние к нему.

```javascript
// ❌ Утечка трансформации: rotate() и fillStyle остаются в силе
// для всех последующих фигур в этом кадре — классический баг
// "почему следующий элемент рисуется повёрнутым/не тем цветом"
function drawRotatedIcon(ctx, x, y, angle) {
  ctx.translate(x, y);
  ctx.rotate(angle);
  ctx.fillStyle = 'red';
  ctx.fillRect(-10, -10, 20, 20);
  // Нет restore() — трансформация и fillStyle "утекли" дальше по коду
}
```

```javascript
// ✅ save()/restore() изолируют изменения состояния строго
// в рамках одной фигуры
function drawRotatedIcon(ctx, x, y, angle) {
  ctx.save();
  ctx.translate(x, y);
  ctx.rotate(angle);
  ctx.fillStyle = 'red';
  ctx.fillRect(-10, -10, 20, 20);
  ctx.restore(); // возвращает трансформацию и fillStyle к состоянию ДО этой функции
}
```

Правило для команд: оборачивайте в `save()`/`restore()` любую функцию рисования, которая меняет трансформацию или стили и вызывается в цикле. Иначе к третьему элементу список "унаследованных" искажений становится непредсказуемым и трудно отлаживаемым.

## Текст: рисование без автоматической вёрстки

```javascript
ctx.font = '16px system-ui'; // тот же синтаксис, что CSS font-shorthand
ctx.textAlign = 'center';    // 'left' | 'center' | 'right' — относительно X в fillText
ctx.textBaseline = 'middle'; // 'top' | 'middle' | 'alphabetic' | 'bottom' — относительно Y
ctx.fillText('Score: 100', x, y);
ctx.strokeText('Outlined', x, y);

const metrics = ctx.measureText('Score: 100');
console.log(metrics.width); // ширина текста в пикселях — единственный способ
                              // узнать, влезет ли строка, потому что canvas
                              // не переносит текст автоматически
```

В отличие от DOM, canvas не занимается переносом строк, обрезкой с многоточием или высотой строки. Многострочный текст с переносом по словам — это отдельная ручная логика поверх `measureText()`. Её пишет разработчик, готовой возможности у контекста нет.

## `devicePixelRatio`: причина №1, почему canvas "мылит" на retina

Это единственная деталь статьи, из-за незнания которой ломается буквально каждый второй canvas-проект новичка. У canvas есть **два** независимых размера:

- `canvas.width` / `canvas.height` — размер **буфера отрисовки** (backing store): реальное число пикселей в буфере, в который вы рисуете.
- `canvas.style.width` / `canvas.style.height` — размер элемента **на странице**, в CSS-пикселях, как у обычного DOM-элемента.

Если не задавать их раздельно, оба равны одному и тому же числу CSS-пикселей. На экране с `devicePixelRatio: 2` (обычный retina) такого буфера мало. Браузер растягивает, скажем, 400×300 реальных пикселей на 800×600 физических пикселей экрана. То есть **увеличивает** его, как маленькую картинку до большого размера. Результат — видимое размытие, одинаковое для текста, линий, всего содержимого.

```javascript
// ❌ Наивная настройка — размыто на любом retina-дисплее
canvas.width = 400;
canvas.height = 300;
```

```javascript
// ✅ Каноническая retina-корректная настройка
function setupCanvas(canvas) {
  const dpr = window.devicePixelRatio || 1;
  const rect = canvas.getBoundingClientRect(); // CSS-размер на странице

  canvas.width = rect.width * dpr;   // реальный размер буфера — больше, чем CSS-размер
  canvas.height = rect.height * dpr;
  canvas.style.width = `${rect.width}px`;   // CSS-размер остаётся прежним —
  canvas.style.height = `${rect.height}px`; // элемент не становится физически больше

  const ctx = canvas.getContext('2d');
  ctx.scale(dpr, dpr); // критично: дальше рисуем координатами в CSS-пикселях,
                        // контекст сам масштабирует их в реальные пиксели буфера
  return ctx;
}
```

После `ctx.scale(dpr, dpr)` весь остальной код рисования пишется в привычных "логических" координатах. Вы вызываете `fillRect(10, 10, 50, 50)`, как будто `dpr` равен 1, а масштабирование в реальные пиксели буфера контекст берёт на себя. Это единственный способ получить чёткую картинку без переписывания всей геометрии рисования под конкретный `dpr`.

## Стратегии очистки

```javascript
ctx.clearRect(0, 0, canvas.width, canvas.height); // ✅ штатный способ:
// делает область прозрачной, не трогая ни трансформацию, ни стили,
// ни что-либо ещё в состоянии контекста

canvas.width = canvas.width; // ⚠️ "хак" из старого кода: присвоение
// width сбрасывает буфер полностью — не только очищает пиксели,
// но и обнуляет всю трансформацию, стили, область отсечения — то есть
// это не просто очистка, а полный сброс контекста как побочный эффект
```

Второй вариант иногда используют намеренно — как способ разом сбросить всё, включая случайно накопленную трансформацию. Но чаще это неявный побочный эффект, который застаёт врасплох.

Если код меняет `canvas.width` при изменении размера, как в функции выше, он попутно очищает содержимое и сбрасывает состояние контекста. Об этом стоит помнить заранее, а не обнаруживать как "необъяснимый" баг после изменения размера окна.

## Типичные ошибки на интервью

- **Не суметь объяснить immediate vs retained mode.** Путать "canvas не хранит объекты" с "canvas медленнее DOM" — это разные утверждения. Immediate mode может быть и быстрее, и медленнее в зависимости от сценария. Ключевое отличие — в модели владения состоянием, а не в производительности как таковой.

- **Не знать, почему canvas размыт на retina.** Размытие идёт от расхождения `canvas.width`/`canvas.height` (буфер) и `canvas.style.width`/`style.height` (CSS-размер). Попытка "починить" через `image-rendering: crisp-edges` в CSS оставляет буфер отрисовки неверным.

- **Забывать `beginPath()`.** Путь накапливается между вызовами `fill()`/`stroke()`, если его явно не начать заново. В итоге поверх текущего кадра рисуется "каша" из фигур прошлых кадров.

- **Не знать разницу nonzero/evenodd.** Не суметь объяснить, почему "бублик" (круг с дырой) иногда рисуется сплошным. Причина — совпадающее направление обхода обоих контуров при правиле `nonzero` по умолчанию.

- **Не оборачивать трансформации в `save()`/`restore()`.** Писать функцию рисования, которая меняет `rotate`/`translate`/`fillStyle` и вызывается в цикле, без изоляции состояния. Состояние "утекает" в следующие итерации непредсказуемым образом.

- **Путать `clearRect()` и присвоение `canvas.width`.** Второе полностью сбрасывает контекст (трансформацию, стили), а не просто очищает пиксели. Отсюда удивление "исчезнувшей" трансформации после изменения размера canvas.
