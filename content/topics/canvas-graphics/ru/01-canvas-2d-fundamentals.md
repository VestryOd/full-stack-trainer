# Canvas 2D: фундамент

## Immediate mode: главный сдвиг мышления

Если вы пришли из DOM/SVG (или из [Browser Animation]), у вас уже есть рефлекс: "создал элемент → он существует → могу найти его позже и изменить". И DOM, и SVG — **retained-mode** системы (режим с запоминанием): браузер хранит структуру объектов (дерево DOM-узлов или дерево `<circle>`/`<rect>`), и когда вы меняете `element.style.left`, браузер сам разбирается, что перерисовать.

Canvas устроен принципиально иначе — это **immediate-mode** система (немедленный режим, "нарисовал и забыл"): вызов `ctx.fillRect(10, 10, 50, 50)` красит пиксели прямо сейчас и ничего не запоминает о том, что здесь был "прямоугольник". Через мгновение для canvas это просто закрашенные пиксели в буфере — неотличимые от любых других закрашенных пикселей. Нет объекта, к которому можно вернуться и сказать "подвинься на 10px вправо". Единственный способ что-либо изменить — **перерисовать всё заново** (или ту часть, которая изменилась) с нуля.

```txt
DOM/SVG (retained mode):                Canvas (immediate mode):
  el.style.left = '110px'                 ctx.clearRect(...)       // стереть
  → браузер сам перерисовывает            ctx.fillRect(110, 10, 50, 50) // нарисовать заново
    только то, что нужно                  → вы сами отвечаете за то,
                                             ЧТО и КОГДА перерисовать
```

Это не деталь синтаксиса — это причина, по которой вся архитектура canvas-приложений (статьи 02 и 08) строится вокруг цикла "очистить → обновить состояние → нарисовать заново", а не вокруг мутации существующих объектов.

## `getContext('2d')` и контекст как машина состояний

```javascript
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d');
```

`ctx` — не просто набор функций рисования, а **машина состояний**: у него есть текущие значения (`fillStyle`, `strokeStyle`, `lineWidth`, текущая трансформация, область отсечения) которые сохраняются между вызовами, пока вы их явно не поменяете — как перо, у которого есть текущий цвет и толщина, и оно продолжает рисовать этим цветом, пока вы не обмакнёте его в другой.

```javascript
ctx.fillStyle = 'red';
ctx.fillRect(0, 0, 50, 50);   // красный квадрат
ctx.fillRect(60, 0, 50, 50);  // ТОЖЕ красный — fillStyle не сбросился сам
ctx.fillStyle = 'blue';
ctx.fillRect(120, 0, 50, 50); // а теперь синий
```

`getContext('2d')` для одного и того же `<canvas>`-элемента всегда возвращает один и тот же объект контекста — вызов не создаёт новый каждый раз, поэтому смело кэшировать `ctx` в переменную при инициализации компонента.

## Система координат

Начало координат — верхний левый угол, ось X растёт вправо, ось Y растёт **вниз** (не как в математике, где Y растёт вверх — источник постоянных ошибок при портировании формул из учебников физики без разворота знака).

Тонкость, о которой почти никто не думает до первого столкновения: тонкие линии (`lineWidth: 1`) на **целых** координатах выглядят размытыми, потому что 1px-линия рисуется "по центру" координаты и растекается на пол-пикселя в обе стороны, попадая на границу двух физических пикселей. Классический фикс — сдвигать координаты линии на 0.5px:

```javascript
// ❌ Размытая линия — рисуется по границе пикселей 100 и 101
ctx.moveTo(100, 0);
ctx.lineTo(100, 200);

// ✅ Чёткая линия шириной в 1 физический пиксель
ctx.moveTo(100.5, 0);
ctx.lineTo(100.5, 200);
```

## Примитивы рисования

### Прямоугольники — без путей

```javascript
ctx.fillRect(x, y, width, height);   // залитый прямоугольник, немедленно
ctx.strokeRect(x, y, width, height); // обводка прямоугольника
ctx.clearRect(x, y, width, height);  // сделать область прозрачной
```

Это единственные примитивы, не требующие пути — вызов сразу рисует.

### Пути — универсальный механизм для всего остального

```javascript
ctx.beginPath();               // начать НОВЫЙ путь — сбрасывает накопленные точки
ctx.moveTo(50, 50);             // переместить "перо" без рисования линии
ctx.lineTo(150, 50);            // линия до точки
ctx.arc(150, 100, 50, 0, Math.PI * 2); // дуга: центр, радиус, startAngle, endAngle, [anticlockwise]
ctx.quadraticCurveTo(200, 150, 250, 50); // квадратичная кривая Безье (одна контрольная точка)
ctx.bezierCurveTo(260, 0, 300, 0, 320, 50); // кубическая кривая Безье (две контрольные точки)
ctx.closePath();               // замкнуть путь линией к начальной точке

ctx.fill();   // залить накопленный путь
ctx.stroke(); // обвести накопленный путь
```

Забыть `beginPath()` перед новой фигурой — частый источник бага "рисуется какая-то каша": предыдущие точки НЕ сбрасываются автоматически, `moveTo`/`lineTo` продолжают накапливаться в том же пути, и `fill()`/`stroke()` заливают/обводят ВСЁ накопленное с начала, включая фигуры из прошлых кадров.

### Правило заливки: nonzero vs evenodd

Когда путь самопересекается или содержит несколько под-контуров (например, круг внутри круга — "бублик"), браузер должен решить, какие области закрашивать. Правило по умолчанию — `nonzero` (непустое правило): для каждой точки считается, сколько раз контур "обвивает" её с учётом направления обхода; если счётчик не равен нулю — точка закрашена.

```javascript
// "Бублик": внешний круг по часовой, внутренний — ПРОТИВ часовой —
// направления противоположны, nonzero-правило даёт счётчик 0 внутри
// внутреннего круга → там дыра
ctx.beginPath();
ctx.arc(100, 100, 80, 0, Math.PI * 2, false); // внешний, по часовой
ctx.arc(100, 100, 40, 0, Math.PI * 2, true);  // внутренний, ПРОТИВ часовой
ctx.fill(); // 'nonzero' — дефолт, даст правильный бублик с дырой

ctx.fill('evenodd'); // альтернативное правило — считает просто чётность
                      // пересечений луча с контуром, не заботясь о направлении
```

Практический вывод: если "бублик" внезапно закрасился сплошным кругом без дыры — почти всегда оба контура заданы в одном направлении обхода (оба по часовой), и нужно развернуть направление одного из них через параметр `anticlockwise` у `arc()`, либо явно указать `fill('evenodd')`.

## Стили: `fillStyle` — не только цвет

```javascript
// Цвет
ctx.fillStyle = '#3366ff';

// Линейный градиент
const gradient = ctx.createLinearGradient(0, 0, 200, 0); // x0,y0 → x1,y1
gradient.addColorStop(0, 'red');
gradient.addColorStop(1, 'blue');
ctx.fillStyle = gradient;

// Радиальный градиент — два круга (внутренний → внешний)
const radial = ctx.createRadialGradient(100, 100, 0, 100, 100, 80);
radial.addColorStop(0, 'white');
radial.addColorStop(1, 'transparent');

// Паттерн из изображения
const pattern = ctx.createPattern(imageElement, 'repeat');
ctx.fillStyle = pattern;
```

Стили для линий:

```javascript
ctx.lineWidth = 4;
ctx.lineCap = 'round';   // 'butt' | 'round' | 'square' — как выглядит КОНЕЦ линии
ctx.lineJoin = 'round';  // 'miter' | 'round' | 'bevel' — как выглядит УГОЛ между сегментами
ctx.setLineDash([8, 4]); // пунктир: 8px линия, 4px пробел
```

## Трансформации: порядок имеет значение

`translate`, `rotate`, `scale` не задают абсолютное состояние — они **умножают** текущую матрицу трансформации на новую, а умножение матриц не коммутативно: `translate → rotate` и `rotate → translate` дают разный результат.

```javascript
// ❌ Вращение вокруг начала координат (0,0), а не вокруг центра фигуры —
// фигура "улетает" по окружности вместо вращения на месте
ctx.rotate(angle);
ctx.fillRect(centerX - 25, centerY - 25, 50, 50);
```

```javascript
// ✅ Классический паттерн "вращение вокруг точки":
// сдвинуть систему координат в точку вращения → повернуть →
// рисовать в локальных координатах относительно (0,0)
ctx.translate(centerX, centerY);
ctx.rotate(angle);
ctx.fillRect(-25, -25, 50, 50); // рисуем ОТНОСИТЕЛЬНО нового (0,0)
```

Порядок вызовов читается "как будто задом наперёд" относительно интуиции: `translate` затем `rotate` в коде означает "сначала перемести систему координат, ЗАТЕМ поворачивай уже перемещённую" — что и даёт вращение вокруг новой точки, а не вокруг исходного начала координат.

`setTransform(a, b, c, d, e, f)` — задаёт АБСОЛЮТНУЮ матрицу вместо накопления поверх текущей (полезно, когда нужно точно знать итоговое состояние, не полагаясь на историю вызовов); `resetTransform()` — сбросить к единичной матрице.

## Стек состояний: `save()`/`restore()` — и классический баг утечки

`save()` кладёт в стек снимок ТЕКУЩИХ стилей и трансформации (но НЕ текущий путь — пути в снимок не входят); `restore()` снимает верхний снимок со стека, возвращая состояние к нему.

```javascript
// ❌ Утечка трансформации: rotate() и fillStyle остаются в силе
// для ВСЕХ последующих фигур в этом кадре — классический баг
// "почему следующий элемент рисуется повёрнутым/не тем цветом"
function drawRotatedIcon(ctx, x, y, angle) {
  ctx.translate(x, y);
  ctx.rotate(angle);
  ctx.fillStyle = 'red';
  ctx.fillRect(-10, -10, 20, 20);
  // НЕТ restore() — трансформация и fillStyle "утекли" дальше по коду
}
```

```javascript
// ✅ save()/restore() изолируют изменения состояния строго
// в рамках одной фигуры
function drawRotatedIcon(ctx, x, y, angle) {
  ctx.save();
  ctx.translate(x, y);
  ctx.rotate(angle);
  ctx.fillStyle = 'red';
  ctx.fillRect(-10, -10, 20, 20);
  ctx.restore(); // возвращает трансформацию и fillStyle к состоянию ДО этой функции
}
```

Правило для команд: любая функция рисования, которая меняет трансформацию или стили и вызывается в цикле по множеству объектов, обязана быть обёрнута в `save()`/`restore()` — иначе к третьему элементу список "унаследованных" искажений становится непредсказуемым и трудно отлаживаемым.

## Текст: рисование без автоматического layout

```javascript
ctx.font = '16px system-ui'; // тот же синтаксис, что CSS font-shorthand
ctx.textAlign = 'center';    // 'left' | 'center' | 'right' — относительно X в fillText
ctx.textBaseline = 'middle'; // 'top' | 'middle' | 'alphabetic' | 'bottom' — относительно Y
ctx.fillText('Score: 100', x, y);
ctx.strokeText('Outlined', x, y);

const metrics = ctx.measureText('Score: 100');
console.log(metrics.width); // ширина текста в пикселях — ЕДИНСТВЕННЫЙ способ
                              // узнать, влезет ли строка, потому что canvas
                              // не переносит текст автоматически
```

В отличие от DOM, canvas не занимается переносом строк, эллипсисом или line-height — если нужен многострочный текст с переносом по словам, это отдельная ручная логика поверх `measureText()`, посчитанная разработчиком, а не встроенная возможность контекста.

## `devicePixelRatio`: причина №1, почему canvas "мылит" на retina

Это единственная деталь статьи, из-за незнания которой ломается буквально каждый второй canvas-проект новичка. У canvas есть ДВА независимых размера:

```txt
canvas.width / canvas.height       — размер БЭКИНГ-БАФФЕРА (реальное число
                                       пикселей в буфере, который вы рисуете)
canvas.style.width / style.height  — размер элемента НА СТРАНИЦЕ в CSS-пикселях
                                       (как обычный DOM-элемент)
```

Если не задавать их раздельно, оба равны одному и тому же числу CSS-пикселей — и на экране с `devicePixelRatio: 2` (обычный retina) браузер вынужден растянуть буфер с, скажем, 400×300 реальных пикселей на 800×600 физических пикселей экрана — то есть **апскейлит** его, как маленькую картинку, растянутую до большого размера. Результат — видимое размытие, одинаковое для текста, линий, всего содержимого.

```javascript
// ❌ Наивная настройка — размыто на любом retina-дисплее
canvas.width = 400;
canvas.height = 300;
```

```javascript
// ✅ Каноническая retina-корректная настройка
function setupCanvas(canvas) {
  const dpr = window.devicePixelRatio || 1;
  const rect = canvas.getBoundingClientRect(); // CSS-размер на странице

  canvas.width = rect.width * dpr;   // РЕАЛЬНЫЙ размер буфера — больше, чем CSS-размер
  canvas.height = rect.height * dpr;
  canvas.style.width = `${rect.width}px`;   // CSS-размер остаётся прежним —
  canvas.style.height = `${rect.height}px`; // элемент не становится физически больше

  const ctx = canvas.getContext('2d');
  ctx.scale(dpr, dpr); // критично: дальше рисуем координатами В CSS-ПИКСЕЛЯХ,
                        // context сам масштабирует их в реальные пиксели буфера
  return ctx;
}
```

После `ctx.scale(dpr, dpr)` весь остальной код рисования пишется в привычных "логических" координатах (`fillRect(10, 10, 50, 50)` — как будто dpr равен 1), а масштабирование в реальные пиксели буфера context берёт на себя сам — это единственный способ получить чёткую картинку БЕЗ переписывания всей геометрии рисования под конкретный dpr.

## Стратегии очистки

```javascript
ctx.clearRect(0, 0, canvas.width, canvas.height); // ✅ штатный способ:
// делает область прозрачной, НЕ трогая ни трансформацию, ни стили,
// ни что-либо ещё в состоянии контекста

canvas.width = canvas.width; // ⚠️ "хак" из старого кода: присвоение
// width СБРАСЫВАЕТ буфер полностью — не только очищает пиксели,
// но и обнуляет ВСЮ трансформацию, стили, clip-регион — то есть
// это не просто очистка, а полный ресет контекста как побочный эффект
```

Второй вариант иногда используют намеренно как способ "разом сбросить всё" (включая случайно накопленную трансформацию), но обычно это неявный побочный эффект, который удивляет: если код меняет `canvas.width` для ресайза (как в функции выше), это ПОПУТНО очищает содержимое и сбрасывает состояние контекста — стоит об этом явно помнить, а не обнаруживать как "необъяснимый" баг после ресайза окна.

## Типичные ошибки на интервью

- **Не суметь объяснить immediate vs retained mode** — путать "canvas не хранит объекты" с "canvas медленнее DOM" — это разные утверждения; immediate mode может быть и быстрее, и медленнее в зависимости от сценария, ключевое отличие — в модели владения состоянием, а не в производительности как таковой.

- **Не знать, почему canvas размыт на retina** — не связывать блюр с расхождением `canvas.width`/`canvas.height` (буфер) и `canvas.style.width`/`style.height` (CSS-размер), пытаться "починить" через `image-rendering: crisp-edges` в CSS вместо настройки backing store.

- **Забывать `beginPath()`** — не понимать, что путь накапливается между вызовами `fill()`/`stroke()`, если явно не начат заново, и получать "кашу" из фигур прошлых кадров поверх текущей.

- **Не знать разницу nonzero/evenodd** — не суметь объяснить, почему "бублик" (круг с дырой) иногда рисуется сплошным без дыры — из-за совпадающего направления обхода обоих контуров при правиле `nonzero` по умолчанию.

- **Не оборачивать трансформации в `save()`/`restore()`** — писать функцию рисования, которая меняет `rotate`/`translate`/`fillStyle` и вызывается в цикле, без изоляции состояния — что "утекает" в следующие итерации непредсказуемым образом.

- **Путать `clearRect()` и присвоение `canvas.width`** — не знать, что второе полностью сбрасывает контекст (трансформацию, стили), а не просто очищает пиксели, и удивляться "исчезнувшей" трансформации после ресайза canvas.
