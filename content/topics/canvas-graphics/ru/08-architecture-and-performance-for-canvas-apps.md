# Архитектура и производительность canvas-приложений

## От инструментов — к продакшен-фиче

Статьи 01-07 дали инструменты: примитивы, игровой цикл, пиксели, WebGL, Pixi, three.js, SVG/d3. Эта статья — про то, как собрать из них реальную фичу внутри реального React/Next.js-приложения, которая не тормозит на слабом железе, не течёт по памяти за час использования, доступна не только зрячим пользователям с мышью, и её можно осмысленно тестировать. Это тот же уровень, что статьи 06-07 в browser-animation — только применительно к canvas-миру.

## Canvas как escape hatch из модели рендеринга React

React перерисовывает компоненты декларативно, на основе state/props; canvas (сырой, Pixi, three.js) — императивная, **сохраняющая состояние** система: сцена/буфер живут между рендерами и не должны пересоздаваться на каждый ре-рендер React. Каноническое решение — **императивное ядро внутри декларативной оболочки**: сцена создаётся ОДИН РАЗ в `useEffect` с пустым списком зависимостей, а изменяющиеся пропсы синхронизируются в уже существующий "движок" через отдельные эффекты, вызывающие его методы — а не пересоздающие его целиком.

```tsx
function ParticleCanvas({ color, count }: { color: string; count: number }) {
  const canvasRef = useRef<HTMLCanvasElement>(null);
  const engineRef = useRef<ParticleEngine | null>(null);

  useEffect(() => {
    engineRef.current = new ParticleEngine(canvasRef.current!);
    engineRef.current.start();
    return () => engineRef.current?.destroy(); // ОБЯЗАТЕЛЬНАЯ очистка при размонтировании
  }, []); // ПУСТОЙ массив зависимостей — движок создаётся РОВНО ОДИН РАЗ

  useEffect(() => {
    engineRef.current?.setColor(color); // СИНХРОНИЗАЦИЯ пропа в уже
  }, [color]);                            // существующий движок, БЕЗ пересоздания

  useEffect(() => {
    engineRef.current?.setParticleCount(count);
  }, [count]);

  return <canvas ref={canvasRef} />;
}
```

Это ровно тот же паттерн, что был показан для Pixi `Application` (статья 05) и three.js-сцены (статья 06) — здесь он обобщён как канонический подход к ЛЮБОМУ императивному canvas-движку внутри React: создание в `useEffect` с пустыми зависимостями, синхронизация пропсов через отдельные эффекты с точечными зависимостями, обязательный `destroy()`/`cancelAnimationFrame` в cleanup-функции.

## Стратегия разрешения и масштабирования

**Ограничение `devicePixelRatio` на мобильных** — та же логика, что в three.js (статья 06, `renderer.setPixelRatio`), но актуальна для ЛЮБОГО canvas-рендеринга: рендер на полном retina-разрешении (dPR 3 на части телефонов) на слабом мобильном GPU часто оказывается единственной самой дорогой строчкой во всём приложении. Ограничение до 1.5-2x визуально почти неотличимо от полного разрешения, но заметно дешевле по объёму пикселей, которые реально нужно закрасить (fill-rate).

**Динамическое разрешение под нагрузкой** — техника из "настоящей" real-time графики, применимая и в вебе: мониторить время кадра (см. профилирование ниже) и адаптивно СНИЖАТЬ внутреннее разрешение рендера (с последующим апскейлом через CSS-размер canvas), когда время кадра стабильно превышает бюджет, и восстанавливать разрешение при снижении нагрузки. Это то, что превращает "частицы-героя тормозят намертво на слабом телефоне" в "частицы-герой аккуратно деградируют по чёткости, оставаясь плавными" — что почти всегда лучший компромисс для промо-страниц.

## Профилирование: CPU-bound vs GPU-bound

Тот же Performance-инструментарий, что и в browser-animation (статья 06), но здесь важно РАЗЛИЧАТЬ два разных источника медленного кадра:

```txt
CPU-bound — JS-код (ваша update()-логика, генерация геометрии на
             JS-стороне, циклы попиксельной обработки) занимает
             много времени ДО того, как GPU вообще получил команды
             на рисование. Видно напрямую в flame chart Performance-панели.

GPU-bound  — JS завершается быстро, draw call'ы отправлены, но сам
             GPU долго их реально исполняет (сложные шейдеры, слишком
             высокое разрешение, слишком много перекрывающихся
             прозрачных слоёв). Заметно как разрыв между "JS закончил
             работу" и "кадр реально появился на экране" — требует
             GPU-специфичных инструментов профилирования (вкладка GPU
             в DevTools, специализированные WebGL-инспекторы) для
             точной диагностики, обычный JS-flame-chart этого не покажет.
```

Практическая эвристика: если уменьшение числа сущностей на JS-стороне НЕ уменьшает время кадра, а снижение сложности шейдера/разрешения — уменьшает, проблема GPU-bound, и решение — упрощать шейдеры/снижать разрешение/сокращать draw call'ы (статья 04), а не оптимизировать JS. Верно и обратное: если оба симптома "зеркальны", проблема на JS-стороне, и решение — пулинг объектов, алгоритмическая оптимизация update-логики (ниже), а не попытки "упростить графику".

## Object pooling: тишина сборщика мусора

Классическая проблема давления на GC: создание и выбрасывание множества короткоживущих объектов (частицы рождаются и умирают постоянно) провоцирует частые паузы сборки мусора — они проявляются как периодические подёргивания кадра, никак не связанные с реальной нагрузкой на рендеринг, что делает их особенно неприятными для диагностики "на глаз".

```javascript
// ✅ Фиксированный пул, переиспользование вместо new/выбрасывания
class ParticlePool {
  constructor(size) {
    this.pool = Array.from({ length: size }, () => (
      { active: false, x: 0, y: 0, vx: 0, vy: 0, life: 0 }
    ));
  }

  spawn(x, y, vx, vy) {
    const p = this.pool.find((p) => !p.active); // переиспользуем существующий объект
    if (!p) return null; // пул исчерпан — просто не спавним ещё одну частицу,
                          // НЕ растим пул безгранично
    Object.assign(p, { active: true, x, y, vx, vy, life: 1 });
    return p;
  }

  release(particle) {
    particle.active = false; // "удаление" — это просто флаг,
                               // объект остаётся в пуле для переиспользования
  }
}
```

Правило: если сущности создаются и уничтожаются часто (десятки-сотни раз в секунду), фиксированный пул с переиспользованием полей вместо `new`/сборки мусора — не микрооптимизация, а способ убрать целый класс необъяснимых периодических лагов из профиля производительности.

## Dirty-rectangle рендеринг: перерисовывать только изменившееся

Статья 02 учит полной очистке (`clearRect` на весь canvas) каждый кадр — правильный дефолт для сцен, где большая часть содержимого динамична. Но там, где статики намного больше, чем движения (мигающий курсор в большом текстовом canvas, маленький HUD-элемент поверх в остальном статичной иллюстрации), выгоднее отслеживать, КАКИЕ прямоугольные области реально изменились с прошлого кадра, и очищать/перерисовывать только их:

```txt
Учёт "грязных" прямоугольников:
  1. Для каждого движущегося объекта запомнить его bounding box
     на ПРОШЛОМ кадре и на ТЕКУЩЕМ
  2. Объединить (union) все эти прямоугольники в список "грязных"
     областей
  3. clearRect + перерисовать ТОЛЬКО эти области, а не весь canvas
```

Дополнительная бухгалтерия (хранение прошлых bounding box'ов, объединение прямоугольников) окупается только тогда, когда соотношение статики к динамике достаточно велико — для сцен, где большая часть экрана и так меняется каждый кадр (частицы, игры с активным движением), полная очистка проще и не медленнее на практике.

## Отсечение объектов вне экрана (culling)

Не обновлять/не рисовать сущности, находящиеся далеко за пределами видимого вьюпорта (или, в 3D/Pixi-мирах шире экрана, — за границами текущей видимой области): простая проверка AABB-против-вьюпорта перед рисованием каждой сущности убирает и стоимость отрисовки, и (когда физика/логика объекта не критична вне экрана) стоимость update для невидимых объектов. В three.js часть этой работы уже делает автоматический frustum culling камеры на уровне отдельных объектов, но при больших количествах сущностей линейная проверка "каждый объект против границ" сама становится узким местом — тогда выгодна пространственная структура (quadtree/сетка), сужающая проверку до объектов, реально близких к видимой области.

## Кэширование текста и изображений в offscreen-canvas

Тот же принцип, что кэширование дорогого эффекта тени в статье 03, применённый широко: любой ДОРОГОЙ в вычислении, но СТАТИЧНЫЙ визуальный элемент (сложная вёрстка текста, предпосчитанный градиентный фон, составная иконка из нескольких слоёв) стоит отрисовать ОДИН РАЗ в offscreen-canvas/текстуру и дальше переиспользовать через `drawImage` каждый кадр, а не пересчитывать заново.

## Дисциплина памяти: бюджеты текстур и восстановление после потери контекста

Мобильные GPU располагают заметно меньшим объёмом видеопамяти, чем десктопные. Сцена, загружающая много текстур высокого разрешения без явного бюджета, может превысить доступную память, что приводит либо к вытеснению/перезагрузке текстур "на лету" (заметные лаги при первом появлении контента), либо к прямой потере GPU-контекста (статья 04).

```txt
Практические правила:
  - Явно задавать бюджет памяти текстур для мобильной сборки —
    и укладываться в него, а не полагаться "авось хватит"
  - Уменьшать разрешение/сжимать текстуры специально для мобильных
    сборок, а не отдавать одинаковые ассеты всем устройствам
  - Явно освобождать (dispose/destroy) текстуры контента, который
    сейчас не виден (например, в длинной прокручиваемой галерее
    3D-превью — держать загруженными только те, что близко к вьюпорту)
```

**Восстановление после потери контекста — не только обработчик события.** Статья 04 показывает `webglcontextlost`/`webglcontextrestored`, но реальная production-готовность требует, чтобы восстановление было НАСТОЯЩИМ, протестированным путём кода: держать исходные данные/URL, необходимые для полной пересборки сцены (а не только сами GPU-объекты, которые как раз и стали недействительны) — иначе обработчик события существует чисто формально, а реальное восстановление сцены не работает, потому что данных для пересборки уже нет под рукой.

## UX загрузки тяжёлых ассетов

Прогрессивная загрузка — сначала показать текстуру низкого разрешения-плейсхолдер, заменить на полное разрешение по готовности; в React — паттерн skeleton/placeholder на время загрузки `GLTFLoader`/`Assets` (статьи 05-06), пока тяжёлая модель или атлас грузятся. Это тот же принцип воспринимаемой производительности через skeleton screens, что разобран в browser-animation (статья 07) — применённый конкретно к тяжёлым 3D/canvas-ассетам, где реальное время загрузки может быть секундами, а не миллисекундами, и разница между "пустой экран" и "структура уже видна, контент подгружается" субъективно велика.

## Доступность содержимого canvas: "чёрный ящик" для скринридеров

Canvas — не просто хуже доступен, чем DOM/SVG (статья 07) — он структурно НЕВИДИМ для вспомогательных технологий: это пиксели без единой семантической структуры, скринридер в принципе не может "увидеть", что там нарисовано.

```html
<!-- Fallback-контент внутри <canvas> — работает ТОЛЬКО если браузер
  вообще не поддерживает canvas (крайне редкий случай сегодня) —
  screen reader, читающий страницу в браузере, который РЕНДЕРИТ canvas,
  этот fallback-контент НЕ увидит вообще -->
<canvas>
  <p>Fallback content — practically never reached today</p>
</canvas>
```

Практически рабочие решения:

```txt
- Для чисто декоративной графики (частицы на фоне, не несущие
  информации) — aria-hidden="true" корректен и достаточен, без
  дополнительной работы

- Для canvas, передающего РЕАЛЬНУЮ информацию (график, диаграмма) —
  role="img" + aria-label для простого случая, либо ПАРАЛЛЕЛЬНОЕ
  доступное представление тех же данных (визуально скрытая таблица
  данных, дублирующая график; aria-live регион, озвучивающий
  изменения состояния игры) — потому что fallback-контент внутри
  тега <canvas> НЕ подхватывается вспомогательными технологиями,
  когда canvas реально поддерживается и рендерится браузером

- Для ИНТЕРАКТИВНОГО canvas (canvas-игра, canvas-редактор) — у
  canvas нет собственной модели фокуса/клавиатурного взаимодействия
  вообще, поэтому нужен ПАРАЛЛЕЛЬНЫЙ слой обычных DOM-элементов
  (кнопок, реагирующих на Enter/Space), подключённый к ТОЙ ЖЕ
  логике, что и обработчики мыши/тач на canvas — это настоящая
  дублирующая реализация взаимодействия, а не декоративная добавка
```

Честный практический ориентир: если canvas чисто декоративен — `aria-hidden` закрывает вопрос полностью; если canvas несёт информацию или функциональность, параллельная доступная реализация — реальное инженерное требование, которое нужно закладывать в оценку сложности фичи с самого начала, а не дописывать в конце как "полировку".

## Тестирование canvas-кода

```txt
Извлекать ЧИСТУЮ логику из отрисовки — прямая выгода от разделения
update/draw, показанного в статье 02: физика, игровые правила,
расчёты d3-шкал/форм (статья 07) не должны знать о существовании
ctx — их можно протестировать обычными unit-тестами БЕЗ canvas
и БЕЗ DOM вообще.

Визуальное регрессионное тестирование — для самой ОТРИСОВКИ, где
нет простого "проверить одно JS-значение", используются инструменты
скриншот-диффинга (в духе Playwright/Percy): рендерят canvas в
изображение и сравнивают попиксельно с эталоном — ловят непреднамеренные
визуальные регрессии в коде отрисовки, которые чистые unit-тесты
структурно не способны поймать.

НЕ тестировать сами вызовы отрисовки напрямую (мокать ctx и
проверять "fillRect был вызван с такими-то аргументами") — это
хрупкий тест реализации, а не поведения: он ломается при любом
рефакторинге отрисовки, даже если визуальный результат идентичен.
```

Практическое разделение: unit-тесты — для логики (извлечённой из отрисовки согласно принципу статьи 02), визуальная регрессия — для рендеринга, и НИКАКОГО мокинга самого `ctx` в качестве замены того или другого.

## Типичные ошибки на интервью

- **Пересоздавать canvas-движок на каждый React-рендер** — не выносить создание в `useEffect` с пустым массивом зависимостей, из-за чего движок (и вся его внутренняя сцена/состояние) уничтожается и создаётся заново при каждом изменении любого несвязанного стейта родителя.

- **Не ограничивать `devicePixelRatio` на мобильных** — рендерить на полном retina-разрешении без осознания, что это часто самая дорогая единственная строчка кода во всём мобильном рендеринге.

- **Не различать CPU-bound и GPU-bound** — пытаться "оптимизировать JS" там, где узкое место — реальная работа GPU (сложные шейдеры, разрешение), и наоборот.

- **Не знать про object pooling** — создавать/выбрасывать множество недолгоживущих объектов (частицы) без осознания связи с паузами сборки мусора, видимыми как необъяснимые периодические подёргивания кадра.

- **Считать dirty-rectangle рендеринг универсальным улучшением** — не понимать, что дополнительная бухгалтерия окупается только при высоком соотношении статики к динамике, а не всегда лучше полной очистки.

- **Думать, что fallback-контент внутри тега `<canvas>` решает доступность** — не знать, что этот контент не подхватывается вспомогательными технологиями, когда canvas реально поддерживается и рендерится, и что для содержательного canvas нужна параллельная доступная реализация, а не декларация внутри тега.

- **Пытаться unit-тестировать сами вызовы отрисовки через мокинг `ctx`** — не разделять логику и отрисовку по принципу статьи 02, получая хрупкие тесты реализации вместо тестируемой чистой логики плюс визуальной регрессии для рендеринга.
