# Архитектура и производительность canvas-приложений

## От инструментов — к продакшен-фиче

Эта статья — про то, как собрать реальную canvas-фичу внутри реального React/Next.js-приложения. Статьи 01-07 дали инструменты: примитивы, игровой цикл, пиксели, WebGL (Web Graphics Library), Pixi, three.js, SVG (scalable vector graphics) и d3. Это тот же уровень, что статьи 06-07 в browser-animation — только применительно к canvas-миру.

Продакшен-фича должна пройти четыре планки:

- Она не тормозит на слабом железе.
- Она не течёт по памяти за час использования.
- Она доступна не только зрячим пользователям с мышью.
- Её можно осмысленно тестировать.

## Canvas как escape hatch из модели рендеринга React

React перерисовывает компоненты декларативно, на основе state и props. Canvas устроен противоположно: сырой canvas, Pixi и three.js — императивные, **сохраняющие состояние** системы. Отсюда и escape hatch, аварийный выход из декларативной модели: сцена и буфер живут между рендерами и не должны пересоздаваться на каждый ре-рендер React.

Каноническое решение — **императивное ядро внутри декларативной оболочки**. Сцена создаётся **один раз**, в `useEffect` с пустым списком зависимостей. Изменяющиеся пропсы синхронизируются в уже существующий "движок" через отдельные эффекты, которые вызывают его методы, а не пересоздают его целиком.

```tsx
function ParticleCanvas({ color, count }: { color: string; count: number }) {
  const canvasRef = useRef<HTMLCanvasElement>(null);
  const engineRef = useRef<ParticleEngine | null>(null);

  useEffect(() => {
    engineRef.current = new ParticleEngine(canvasRef.current!);
    engineRef.current.start();
    return () => engineRef.current?.destroy(); // обязательная очистка при размонтировании
  }, []); // пустой массив зависимостей — движок создаётся ровно один раз

  useEffect(() => {
    engineRef.current?.setColor(color); // синхронизация пропа в уже
  }, [color]);                            // существующий движок, без пересоздания

  useEffect(() => {
    engineRef.current?.setParticleCount(count);
  }, [count]);

  return <canvas ref={canvasRef} />;
}
```

Это ровно тот же паттерн, что был показан для Pixi `Application` (статья 05) и three.js-сцены (статья 06). Здесь он обобщён как канонический подход к **любому** императивному canvas-движку внутри React:

- Создание в `useEffect` с пустыми зависимостями.
- Синхронизация пропсов через отдельные эффекты с точечными зависимостями.
- Обязательный `destroy()`/`cancelAnimationFrame` в cleanup-функции.

## Стратегия разрешения и масштабирования

**Ограничение `devicePixelRatio` на мобильных** — та же логика, что в three.js (статья 06, `renderer.setPixelRatio`), но актуальна для **любого** canvas-рендеринга. GPU (graphics processing unit, графический процессор) — это чип, который закрашивает пиксели, и на слабом мобильном именно закраска становится узким местом.

На части телефонов `devicePixelRatio` равен 3, и рендер на полном retina-разрешении часто оказывается самой дорогой строчкой во всём приложении. Ограничение до 1.5-2x визуально почти неотличимо от полного разрешения, но заметно дешевле по объёму пикселей, которые реально нужно закрасить (fill-rate).

| `devicePixelRatio` | Пикселей закрасить, относительно CSS-размера |
|---|---|
| 1 | 1× |
| 1.5 | 2.25× |
| 2 | 4× |
| 3 | 9× |

**Динамическое разрешение под нагрузкой** — техника из "настоящей" real-time графики, применимая и в вебе. Мониторить время кадра (см. профилирование ниже). Когда оно стабильно превышает бюджет, адаптивно **снижать** внутреннее разрешение рендера и апскейлить его через CSS-размер canvas. Восстанавливать разрешение при снижении нагрузки.

Это то, что превращает "частицы-герой намертво тормозят на слабом телефоне" в "частицы-герой аккуратно теряют чёткость, оставаясь плавными". Для промо-страницы это почти всегда лучший компромисс.

## Профилирование: CPU-bound vs GPU-bound

Медленный кадр бывает по двум разным причинам, и здесь важно их **различать**. CPU (central processing unit, центральный процессор) — это главный процессор, который исполняет ваш JS. Инструментарий тот же, что в browser-animation (статья 06):

```txt
CPU-bound — JS-код (ваша update()-логика, генерация геометрии
             на JS-стороне, циклы попиксельной обработки)
             занимает много времени до того, как GPU вообще
             получил команды на рисование. Видно напрямую в
             flame chart панели Performance.

GPU-bound  — JS завершается быстро, вызовы отрисовки (draw call)
             отправлены, но сам GPU долго их исполняет (сложные
             шейдеры, слишком высокое разрешение, слишком много
             перекрывающихся прозрачных слоёв). Заметно как
             разрыв между "JS закончил работу" и "кадр реально
             появился на экране". Требует GPU-специфичных
             инструментов профилирования (вкладка GPU в DevTools,
             специализированные WebGL-инспекторы); обычный
             JS-flame-chart этого не покажет.
```

Практическая эвристика читает два симптома и даёт один вердикт:

- Уменьшение числа сущностей на JS-стороне **не** уменьшает время кадра, а снижение сложности шейдера или разрешения — **уменьшает**. Проблема GPU-bound. Упрощать шейдеры, снижать разрешение, сокращать вызовы отрисовки (статья 04). JS не оптимизировать.
- Уменьшение числа сущностей **уменьшает** время кадра, а снижение сложности шейдера или разрешения — **нет**. Проблема на JS-стороне. Пулинг объектов, алгоритмическая оптимизация update-логики (ниже). Графику не "упрощать".

## Object pooling: тишина сборщика мусора

Классическая проблема здесь — давление на GC (garbage collector, сборщик мусора, который освобождает неиспользуемую память).

Создание и выбрасывание множества короткоживущих объектов — частицы рождаются и умирают постоянно — провоцирует частые паузы сборки. Они проявляются как периодические подёргивания кадра, никак не связанные с реальной нагрузкой на рендеринг, и от этого их особенно неприятно диагностировать "на глаз".

```javascript
// ✅ Фиксированный пул, переиспользование вместо new/выбрасывания
class ParticlePool {
  constructor(size) {
    this.pool = Array.from({ length: size }, () => (
      { active: false, x: 0, y: 0, vx: 0, vy: 0, life: 0 }
    ));
  }

  spawn(x, y, vx, vy) {
    const p = this.pool.find((p) => !p.active); // переиспользуем существующий объект
    if (!p) return null; // пул исчерпан — просто не спавним ещё одну частицу,
                          // не растим пул безгранично
    Object.assign(p, { active: true, x, y, vx, vy, life: 1 });
    return p;
  }

  release(particle) {
    particle.active = false; // "удаление" — это просто флаг,
                               // объект остаётся в пуле для переиспользования
  }
}
```

Правило: если сущности создаются и уничтожаются часто — десятки-сотни раз в секунду — фиксированный пул это не микрооптимизация. Переиспользование полей вместо `new` и сборки мусора убирает целый класс необъяснимых периодических лагов из профиля производительности.

## Dirty-rectangle рендеринг: перерисовывать только изменившееся

Статья 02 учит полной очистке (`clearRect` на весь canvas) каждый кадр. Это правильный дефолт для сцен, где большая часть содержимого динамична.

Но в некоторых сценах статики намного больше, чем движения. Примеры: мигающий курсор в большом текстовом canvas или маленький HUD-элемент поверх в остальном статичной иллюстрации. HUD расшифровывается как heads-up display — накладной слой со статусом поверх сцены.

Там выгоднее отслеживать, **какие** прямоугольные области реально изменились с прошлого кадра, и очищать и перерисовывать только их:

```txt
Учёт "грязных" прямоугольников:
  1. Для каждого движущегося объекта запомнить его bounding box
     на прошлом кадре и на текущем
  2. Объединить (union) все эти прямоугольники в список "грязных"
     областей
  3. clearRect + перерисовать только эти области, а не весь canvas
```

Дополнительный учёт — хранение прошлых ограничивающих прямоугольников (bounding box) и объединение прямоугольников — окупается только тогда, когда соотношение статики к динамике достаточно велико. Для сцен, где большая часть экрана и так меняется каждый кадр (частицы, игры с активным движением), полная очистка проще и не медленнее на практике.

## Отсечение объектов вне экрана (culling)

Отсечение (culling) — это пропуск сущностей, которых камера в этом кадре не видит. Проверка стоит одного сравнения прямоугольников на сущность. Она убирает и стоимость отрисовки, и — когда физика и логика объекта вне экрана не важны — стоимость update.

AABB расшифровывается как axis-aligned bounding box: наименьший прямоугольник, целиком содержащий объект, со сторонами параллельно осям экрана. Два таких прямоугольника дёшево проверить на пересечение, поэтому отсечение работает с ними, а не с реальной формой объекта.

```txt
    Отсечение: одна проверка на сущность за кадр
┌─────────────────────────────────────────────────┐
│ Берём следующую сущность сцены                  │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ Её AABB пересекается с прямоугольником экрана?  │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ нет → отсечена: пропускаем и update(), и draw() │
│ да  → обновляем и рисуем как обычно             │
└─────────────────────────────────────────────────┘
  при большом числе сущностей линейный перебор сам
    становится узким местом → quadtree или сетка
```

В 3D- и Pixi-мирах, которые шире экрана, та же идея применяется к текущей видимой области, а не к области окна браузера. В three.js часть этой работы уже делает автоматический frustum culling камеры на уровне отдельных объектов. Frustum — это пирамида видимости, тот объём, который камера реально захватывает.

При больших количествах сущностей линейная проверка "каждый объект против границ" сама становится узким местом. Тогда выгодна пространственная структура. Quadtree рекурсивно делит область на четыре квадранта, обычная сетка делает то же самое фиксированными клетками. И то, и другое сужает проверку до объектов, реально близких к видимой области.

## Кэширование текста и изображений в offscreen-canvas

Тот же принцип, что кэширование дорогого эффекта тени в статье 03, применённый широко. Любой **дорогой** в вычислении, но **статичный** визуальный элемент стоит отрисовать **один раз** в offscreen-canvas или текстуру. Примеры: сложная вёрстка текста, предпосчитанный градиентный фон, составная иконка из нескольких слоёв. Дальше её переиспользуют через `drawImage` каждый кадр, а не пересчитывают заново.

## Дисциплина памяти: бюджеты текстур и восстановление после потери контекста

Мобильные GPU располагают заметно меньшим объёмом видеопамяти, чем десктопные. Сцена, загружающая много текстур высокого разрешения без явного бюджета, может превысить доступную память. Дальше возможны два исхода. Текстуры вытесняются и перезагружаются "на лету", что видно как заметные лаги при первом появлении контента. Либо GPU-контекст теряется совсем (статья 04).

```txt
Практические правила:
  - Явно задавать бюджет памяти текстур для мобильной сборки —
    и укладываться в него, а не полагаться "авось хватит"
  - Уменьшать разрешение/сжимать текстуры специально для мобильных
    сборок, а не отдавать одинаковые ассеты всем устройствам
  - Явно освобождать (dispose/destroy) текстуры контента, который
    сейчас не виден (например, в длинной прокручиваемой галерее
    3D-превью держать загруженными только те, что близко к
    видимой области)
```

**Восстановление после потери контекста — не только обработчик события.** Статья 04 показывает `webglcontextlost` и `webglcontextrestored`, но реальная production-готовность требует, чтобы восстановление было **настоящим**, протестированным путём кода.

Держите исходные данные и URL, необходимые для полной пересборки сцены, — а не только сами GPU-объекты, которые как раз и стали недействительны. Иначе обработчик события существует чисто формально, а реальное восстановление сцены не работает: данных для пересборки уже нет под рукой.

## UX загрузки тяжёлых ассетов

UX (user experience, опыт пользователя) при загрузке тяжёлого ассета строится прогрессивно: сначала показать текстуру-плейсхолдер низкого разрешения, затем заменить на полное разрешение по готовности. В React это паттерн skeleton или placeholder на время, пока `GLTFLoader`/`Assets` (статьи 05-06) грузят тяжёлую модель или атлас.

Это тот же принцип воспринимаемой производительности, что и skeleton screens в browser-animation (статья 07). Здесь он применён к тяжёлым 3D- и canvas-ассетам, где реальное время загрузки может быть секундами, а не миллисекундами. Разница между "пустой экран" и "структура уже видна, контент подгружается" субъективно велика.

## Доступность содержимого canvas: "чёрный ящик" для скринридеров

Canvas не просто хуже доступен, чем DOM (document object model, дерево объектов страницы в браузере) или SVG (статья 07). Он структурно **невидим** для вспомогательных технологий. Canvas — это пиксели без единой семантической структуры, и скринридер в принципе не может "увидеть", что там нарисовано.

```html
<!-- Fallback-контент внутри <canvas> — работает только если браузер
  вообще не поддерживает canvas (крайне редкий случай сегодня) —
  скринридер, читающий страницу в браузере, который рендерит canvas,
  этот fallback-контент не увидит вообще -->
<canvas>
  <p>Fallback content — practically never reached today</p>
</canvas>
```

Практически рабочие решения:

```txt
- Для чисто декоративной графики (частицы на фоне, не несущие
  информации) — aria-hidden="true" корректен и достаточен, без
  дополнительной работы

- Для canvas, передающего реальную информацию (график, диаграмма) —
  role="img" + aria-label для простого случая, либо параллельное
  доступное представление тех же данных (визуально скрытая таблица
  данных, дублирующая график; aria-live регион, озвучивающий
  изменения состояния игры) — потому что fallback-контент внутри
  тега <canvas> не подхватывается вспомогательными технологиями,
  когда canvas реально поддерживается и рендерится браузером

- Для интерактивного canvas (canvas-игра, canvas-редактор) — у
  canvas нет собственной модели фокуса/клавиатурного взаимодействия
  вообще, поэтому нужен параллельный слой обычных DOM-элементов
  (кнопок, реагирующих на Enter/Space), подключённый к той же
  логике, что и обработчики мыши/тач на canvas — это настоящая
  дублирующая реализация взаимодействия, а не декоративная добавка
```

Честный практический ориентир: если canvas чисто декоративен, `aria-hidden` закрывает вопрос полностью. Если canvas несёт информацию или функциональность, параллельная доступная реализация — реальное инженерное требование. Закладывайте её в оценку сложности фичи с самого начала, а не дописывайте в конце как "полировку".

## Тестирование canvas-кода

```txt
Извлекать чистую логику из отрисовки — прямая выгода от разделения
update/draw, показанного в статье 02: физика, игровые правила,
расчёты d3-шкал/форм (статья 07) не должны знать о существовании
ctx — их можно протестировать обычными unit-тестами без canvas
и без DOM вообще.

Визуальное регрессионное тестирование — для самой отрисовки, где
нет простого "проверить одно JS-значение", используются инструменты
скриншот-диффинга (в духе Playwright/Percy): они рендерят canvas в
изображение и сравнивают попиксельно с эталоном. Так ловятся
непреднамеренные визуальные регрессии в коде отрисовки, которые
чистые unit-тесты структурно не способны поймать.

Не тестировать сами вызовы отрисовки напрямую (подменять ctx моком
и проверять "fillRect был вызван с такими-то аргументами") — это
хрупкий тест реализации, а не поведения: он ломается при любом
рефакторинге отрисовки, даже если визуальный результат идентичен.
```

Практическое разделение: unit-тесты для логики, визуальная регрессия для рендеринга. Логика извлечена из отрисовки по принципу статьи 02, и `ctx` никогда не подменяется моком вместо того или другого.

## Типичные ошибки на интервью

- **Пересоздавать canvas-движок на каждый React-рендер** — не выносить создание в `useEffect` с пустым массивом зависимостей. Движок вместе со всей внутренней сценой и состоянием уничтожается и создаётся заново при каждом изменении любого несвязанного стейта родителя.

- **Не ограничивать `devicePixelRatio` на мобильных** — рендерить на полном retina-разрешении. Это часто самая дорогая единственная строчка кода во всём мобильном рендеринге.

- **Не различать CPU-bound и GPU-bound** — пытаться "оптимизировать JS" там, где узкое место — реальная работа GPU (сложные шейдеры, разрешение), и наоборот.

- **Не знать про object pooling** — создавать и выбрасывать множество недолгоживущих объектов вроде частиц, не связывая это с паузами сборки мусора. Они видны как необъяснимые периодические подёргивания кадра.

- **Считать dirty-rectangle рендеринг универсальным улучшением** — не понимать, что дополнительный учёт окупается только при высоком соотношении статики к динамике. Полной очистки он лучше не всегда.

- **Думать, что fallback-контент внутри тега `<canvas>` решает доступность** — не знать, что вспомогательные технологии игнорируют этот контент, когда canvas реально поддерживается и рендерится. Содержательному canvas нужна параллельная доступная реализация, а не декларация внутри тега.

- **Пытаться unit-тестировать сами вызовы отрисовки, подменяя `ctx` моком** — не разделять логику и отрисовку по принципу статьи 02. Результат — хрупкие тесты реализации вместо тестируемой чистой логики плюс визуальной регрессии для рендеринга.
