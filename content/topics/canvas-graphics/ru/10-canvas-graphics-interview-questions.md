# Canvas & Graphics — вопросы для интервью (Middle → Senior)

## Группа 1: Canvas 2D — фундамент

**В чём разница между immediate mode и retained mode, и почему это важно для canvas?**

Retained mode — браузер хранит структуру объектов и сам решает, что перерисовать при изменении свойства. Так устроены DOM (document object model, дерево объектов страницы в браузере) и SVG (scalable vector graphics, векторная графика в разметке). Immediate mode, на котором работает Canvas 2D, устроен наоборот: нарисованные пиксели ничего не помнят о себе.

```txt
┌──────────────────────────┐  ┌───────────────────────────────┐
│ Retained mode (DOM, SVG) │  │ Immediate mode (Canvas 2D)    │
│ el.style.left = "110px"  │  │ ctx.clearRect(...)            │
│ → браузер сам решает,    │  │ ctx.fillRect(110, 10, 50, 50) │
│   что перерисовать       │  │ → вы решаете, что и когда     │
└──────────────────────────┘  └───────────────────────────────┘
```

Вызов `ctx.fillRect(...)` красит пиксели прямо сейчас. После этого для canvas это просто закрашенные пиксели, неотличимые от любых других. Единственный способ что-либо изменить — перерисовать всё с нуля или хотя бы изменившуюся часть.

Поэтому любая canvas-анимация строится вокруг явного цикла «очистить → обновить состояние → нарисовать заново». CSS и WAAPI (Web Animations API) устроены иначе: там браузер сам перерисовывает страницу при изменении свойства.

**Почему canvas выглядит размытым на retina-дисплеях, и как это исправить?**

У canvas два независимых размера, и размытие появляется, когда они расходятся. Пара `canvas.width`/`canvas.height` задаёт буфер пикселей (backing store) — сколько пикселей на самом деле в том буфере, куда вы рисуете. Пара `canvas.style.width`/`style.height` задаёт CSS-размер элемента на странице.

```txt
┌──────────────────────────────────────────┐
│ canvas.width / canvas.height             │
│ буфер пикселей: сколько их на самом деле │
├──────────────────────────────────────────┤
│ canvas.style.width / .height             │
│ CSS-размер элемента на странице          │
└──────────────────────────────────────────┘
```

Если не задавать их раздельно, оба окажутся равны одному и тому же числу CSS-пикселей. Тогда на экране с `devicePixelRatio: 2` браузер растянет буфер на вдвое большее количество физических пикселей. Это растяжение вы и видите как размытие.

```javascript
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d');
const dpr = window.devicePixelRatio || 1;
const rect = canvas.getBoundingClientRect();

canvas.width = rect.width * dpr;         // буфер пикселей, реальные пиксели
canvas.height = rect.height * dpr;
canvas.style.width = `${rect.width}px`;  // CSS-размер остаётся прежним
canvas.style.height = `${rect.height}px`;

ctx.scale(dpr, dpr);  // код рисования остаётся в логических координатах
```

Вызов `ctx.scale(dpr, dpr)` — это то, что оставляет остальной код рисования нетронутым. Координаты остаются в привычных логических единицах, а браузер сам раскладывает их на более плотный буфер.

**В чём разница между `clearRect()` и присвоением `canvas.width = canvas.width`?**

`clearRect(x, y, w, h)` делает область прозрачной и не трогает больше ничего. Трансформация, стили и область отсечения (clip) переживают этот вызов. Присвоение `canvas.width`, даже того же значения, сбрасывает весь контекст как побочный эффект.

| Что происходит с | `clearRect(x, y, w, h)` | `canvas.width = canvas.width` |
|---|---|---|
| Пикселями | очищен заданный прямоугольник | очищен весь canvas |
| Трансформацией | сохраняется | сброс к единичной матрице |
| Стилями, толщиной линий | сохраняются | сброс к значениям по умолчанию |
| Областью отсечения | сохраняется | сброс |

Этот сброс легко получить случайно: изменение размера canvas — это и есть запись в `width`. Разработчик ждёт, что «исчезнет» только картинка, и с удивлением теряет ещё и накопленную трансформацию.

**Объясните правила заливки nonzero и evenodd. Когда «бублик» (круг с дырой) может отрисоваться сплошным, без дыры?**

Когда путь содержит несколько под-контуров, правило заливки решает, какие области закрасить. Внешний и внутренний круг «бублика» — как раз такая пара. По умолчанию работает правило `nonzero`. Для каждой точки оно считает, сколько раз контур обвивает её с учётом направления обхода. Точка закрашивается, если счётчик не нулевой.

| Оба контура заданы | `nonzero` | `evenodd` |
|---|---|---|
| В противоположных направлениях | дыра остаётся | дыра остаётся |
| В одном направлении | дыра исчезает | дыра остаётся |

То есть дыра пропадает, когда оба круга обойдены одинаково — например, оба по часовой стрелке. Их вклады перестают компенсировать друг друга, и `nonzero` закрашивает внутренний круг тоже.

Исправить это можно двумя способами. Задать контурам противоположные направления через параметр `anticlockwise` у `arc()`. Либо вызвать `fill('evenodd')`, которое считает только чётность пересечений луча с контуром и не смотрит на направление.

## Группа 2: Анимация на canvas и пиксели

**Почему ручной игровой цикл обязан использовать delta time, и в чём разница fixed vs variable timestep?**

Движение на фиксированный шаг за кадр (`x += 2`) привязывает скорость к частоте дисплея. Один и тот же код идёт вдвое быстрее на 120 Гц, чем на 60 Гц. Delta time (дельта времени, длина прошедшего кадра) превращает шаг в «единицы за секунду» и снимает эту зависимость.

```javascript
const STEP = 1 / 60;  // фиксированный шаг физики, в секундах
function updatePhysics(step) { /* сдвинуть тела на `step` секунд */ }
function draw(alpha) { /* alpha в [0, 1): насколько мы вошли в следующий шаг */ }

let last = performance.now();
let accumulator = 0;

function frame(now) {
  const dt = (now - last) / 1000;  // дельта времени, в секундах
  last = now;
  accumulator += dt;

  while (accumulator >= STEP) {    // одинаковые порции при любой частоте кадров
    updatePhysics(STEP);
    accumulator -= STEP;
  }
  draw(accumulator / STEP);        // остаток интерполирует картинку
  requestAnimationFrame(frame);
}
requestAnimationFrame(frame);
```

Variable timestep означает, что дельта времени в каждом кадре своя. Для визуальной анимации этого достаточно, но для физики возникают настоящие проблемы. Скачок `dt` приводит к «туннелированию»: быстрый объект проскакивает сквозь препятствие за один большой шаг. Симуляция при этом ведёт себя по-разному на разных устройствах.

Fixed timestep с аккумулятором решает обе проблемы. Физика всегда шагает одинаковыми маленькими порциями, какой бы ни была реальная частота кадров. Остаток времени между шагами идёт на интерполяцию визуальной позиции.

**Какие три подхода к определению попадания на canvas существуют, и когда какой использовать?**

Canvas не помнит объектов, поэтому клик — это только координата, и что под неё попало, решаете вы сами. Способов сделать это три.

| Подход | Для чего | Цена |
|---|---|---|
| Математика: прямоугольник или круг | простые формы | самый дешёвый, так пишут чаще всего |
| `isPointInPath()` | формы, уже описанные путём | один вызов контекста на форму |
| Подбор по цвету | сложные перекрывающиеся формы | лишний проход отрисовки на изменение |

Математический подход сравнивает точку с AABB (axis-aligned bounding box — прямоугольник, стороны которого параллельны осям) или с окружностью. Он самый дешёвый из трёх и покрывает подавляющее большинство реального кода.

Методы `isPointInPath()` и `isPointInStroke()` спрашивают у самого контекста, попадает ли точка в накопленный им путь. Это удобно для неправильных форм, которые уже описаны как canvas-путь.

Подбор по цвету (color-picking) рисует каждый объект сплошным уникальным цветом на невидимом внеэкранном canvas. По клику читается цвет пикселя под курсором, и по нему находится владелец этого цвета. Способ точен для сложных, перекрывающихся, произвольно неправильных форм. Стоит он одного лишнего прохода отрисовки (render pass) на каждое изменение сцены.

**Почему `getImageData` дорогая операция, и как снизить эту стоимость?**

Canvas 2D может рендериться на GPU (graphics processing unit — чип, который рисует пиксели), а запрос сырых пикселей на CPU (central processing unit, центральный процессор) вынуждает синхронизацию. Браузер обязан дождаться завершения текущей работы GPU. Только после этого он копирует буфер из памяти GPU в обычную память процесса.

```txt
┌──────────────────────────────────────┐
│ Память GPU                           │
│ кадр, который GPU ещё рисует         │
└──────────────────────────────────────┘
                    │  браузер ждёт GPU, потом копирует
                    ▼
┌──────────────────────────────────────┐
│ Память CPU                           │
│ массив ImageData, который вы просили │
└──────────────────────────────────────┘
```

Такая точка синхронизации стоит заметного времени внутри цикла, который крутится каждый кадр. Вызов `getImageData` на каждом кадре анимации — частая причина падения fps (frames per second, кадров в секунду).

Подсказка `willReadFrequently: true` при получении контекста говорит браузеру держать буфер в доступной для CPU памяти с самого начала. Это избавляет от повторных копий из GPU в CPU.

```javascript
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d', { willReadFrequently: true });
```

**Опишите, как бы вы реализовали эффект стирания защитного слоя (scratch card) средствами композитинга.**

Весь эффект — это три слоя и один режим композитинга, без единой дополнительной библиотеки.

- Базовый слой: контент, скрытый под «фольгой», — текст приза или изображение.
- Слой «фольги» поверх него, нарисованный обычным режимом `source-over`.
- Мазки кисти, которые рисуются при движении курсора с зажатой кнопкой.

```javascript
const canvas = document.querySelector('canvas');
const ctx = canvas.getContext('2d');
const prizeImage = document.querySelector('img');  // уже загружено

ctx.drawImage(prizeImage, 0, 0);                   // 1. базовый слой
ctx.fillStyle = '#bbbbbb';
ctx.fillRect(0, 0, canvas.width, canvas.height);   // 2. «фольга» поверх

canvas.addEventListener('pointermove', (e) => {
  if (e.buttons !== 1) return;                     // только с зажатой кнопкой
  ctx.globalCompositeOperation = 'destination-out';  // 3. стираем, не красим
  ctx.beginPath();
  ctx.arc(e.offsetX, e.offsetY, 20, 0, Math.PI * 2);
  ctx.fill();
});
```

Всю работу делают мазки. Перед каждым из них `globalCompositeOperation` переключается на `destination-out`. В этом режиме новая фигура стирает существующие пиксели вместо рисования поверх них. Каждый мазок пробивает дыру в слое фольги, и через неё становится виден базовый слой.

**Что такое ограничение tainted canvas, и как его избежать?**

Canvas становится «испорченным» (tainted), как только на нём нарисовано изображение с другого источника без корректных CORS-заголовков (cross-origin resource sharing). После этого браузер блокирует любое чтение его пиксельных данных — `getImageData`, `toDataURL`, `toBlob` — с ошибкой `SecurityError`.

Ограничение существует потому, что читаемый canvas иначе работал бы как оракул. Страница могла бы нарисовать приватную картинку с чужого источника и вычитать содержимое пользователя прямо из пикселей.

Чтобы этого избежать, нужны два условия одновременно, и по отдельности ни одного не хватает:

- На клиенте: задать `img.crossOrigin = 'anonymous'` до присваивания `img.src`.
- На сервере: ответ с изображением обязан нести заголовок `Access-Control-Allow-Origin`.

## Группа 3: WebGL и основы GPU

**Что такое вызов отрисовки (draw call), и почему минимизировать их число важнее, чем число треугольников?**

Вызов отрисовки (draw call) — одна команда для GPU: «нарисуй эти вершины этой шейдерной программой, с этими буферами, uniform-значениями и текстурой». WebGL (Web Graphics Library, браузерный API для рисования на GPU) выдаёт по одной такой команде на порцию геометрии.

Стоимость вызова — это в основном накладные расходы драйвера: проверка состояния, синхронизация CPU с GPU, загрузка изменившихся данных. Количество треугольников внутри вызова — не дорогая часть.

```txt
┌─────────────────────────┬─────────────────┬───────────┐
│ 100 спрайтов нарисованы │ Работа драйвера │ Геометрия │
├─────────────────────────┼─────────────────┼───────────┤
│ 100 отдельными вызовами │ 100x проверок   │ та же     │
├─────────────────────────┼─────────────────┼───────────┤
│ 1 вызовом (батч)        │ 1x проверка     │ та же     │
└─────────────────────────┴─────────────────┴───────────┘
```

Нарисовать 10 000 треугольников одним вызовом почти всегда дешевле, чем 100 треугольников сотней отдельных вызовов. Эти сто вызовов ещё и меняют текстуру или шейдер между собой, и платить приходится именно за это. Поэтому батчинг — объединение множества объектов в минимальное число вызовов отрисовки — центральная тема производительности и в Pixi, и в three.js.

---

**Объясните разницу между стадиями vertex shader и fragment shader.**

Две стадии отвечают на два разных вопроса, а между ними стоит растеризация.

```txt
┌──────────────────────────────────────┐
│ Вершинный шейдер (программируемый)   │
│ раз на вершину                       │
│ выход: gl_Position                   │
└──────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────┐
│ Растеризация (непрограммируемая)     │
│ какие пиксели покрыты треугольником  │
│ интерполирует varying-значения       │
└──────────────────────────────────────┘
                    │
                    ▼
┌──────────────────────────────────────┐
│ Фрагментный шейдер (программируемый) │
│ раз на покрытый пиксель              │
│ выход: gl_FragColor                  │
└──────────────────────────────────────┘
```

Вершинный шейдер (vertex shader) выполняется один раз на каждую вершину геометрии. Он отвечает на вопрос «где эта точка окажется на экране», а его выход — `gl_Position`.

Растеризация — единственная стадия, которую нельзя запрограммировать. GPU определяет, какие пиксели покрыты треугольником, и линейно интерполирует varying-значения между вершинами. Фрагментный шейдер (fragment shader) выполняется один раз на каждый покрытый пиксель. Он отвечает на вопрос «какого цвета этот конкретный пиксель», а его выход — `gl_FragColor`.

---

**В чём разница между attribute, uniform и varying?**

Эти три вещи различаются тем, сколько значений существует и кто их читает.

```txt
┌───────────┬─────────────────────────┬────────────────────┐
│ Что       │ Сколько значений        │ Кто читает         │
├───────────┼─────────────────────────┼────────────────────┤
│ attribute │ по одному на вершину    │ вершинный шейдер   │
├───────────┼─────────────────────────┼────────────────────┤
│ uniform   │ одно на вызов отрисовки │ оба шейдера        │
├───────────┼─────────────────────────┼────────────────────┤
│ varying   │ по одному на пиксель    │ фрагментный шейдер │
└───────────┴─────────────────────────┴────────────────────┘
```

`attribute` — данные, уникальные для каждой вершины: позиция, UV (координата текстуры, названная по своим осям u и v) или цвет вершины. Читает их вершинный шейдер.

`uniform` — одно значение, одинаковое для всех вершин и пикселей внутри одного вызова отрисовки. Матрица трансформации, время анимации и общий цвет — типичные uniform-значения.

`varying` — мост между двумя шейдерами. Вершинный шейдер его записывает, растеризация линейно интерполирует его между вершинами, а фрагментный шейдер читает по одному интерполированному значению на каждый обрабатываемый пиксель.

---

**Почему треугольник — универсальный примитив GPU-рендеринга?**

Любые три точки всегда лежат в одной плоскости, чего не скажешь о четырёх и более точках. Эта компланарность делает растеризацию треугольника простой и предсказуемой операцией, а десятилетия развития GPU довели её аппаратно до предела оптимизации.

```txt
┌───────────────────┬─────────────────────────────┐
│ Форма             │ Треугольников на уровне GPU │
├───────────────────┼─────────────────────────────┤
│ 2D-спрайт         │ 2                           │
├───────────────────┼─────────────────────────────┤
│ Сложная 3D-модель │ тысячи                      │
└───────────────────┴─────────────────────────────┘
```

Поэтому любая форма на уровне GPU превращается в набор треугольников: 2D-спрайт — в два, а сложная 3D-модель — в тысячи.

---

**Как обрабатывать потерю WebGL-контекста в продакшене?**

Слушайте событие `webglcontextlost` и обязательно вызывайте `event.preventDefault()` внутри обработчика. Без этого вызова браузер даже не попытается восстановить контекст. Ещё остановите цикл рендеринга через `cancelAnimationFrame()`: контекст сейчас недействителен.

```javascript
const canvas = document.querySelector('canvas');
let rafId = requestAnimationFrame(render);

canvas.addEventListener('webglcontextlost', (e) => {
  e.preventDefault();       // без этого восстановления не будет вовсе
  cancelAnimationFrame(rafId);
});

canvas.addEventListener('webglcontextrestored', () => {
  rebuildSceneResources();  // программы, буферы и текстуры уничтожены все
  rafId = requestAnimationFrame(render);
});

function render() { /* нарисовать кадр и запланировать следующий */ }
function rebuildSceneResources() { /* залить всё заново из исходных данных */ }
```

По событию `webglcontextrestored` пересоберите все GPU-ресурсы с нуля: шейдерные программы, буферы, текстуры. Просто «продолжить» рендеринг недостаточно, потому что все прежние GPU-объекты погибли вместе с контекстом.

Настоящая готовность к продакшену — это держать под рукой исходные данные и URL, нужные для полной пересборки сцены. Сами GPU-идентификаторы после потери ничего не стоят, и если сохранить только их, пересобирать будет не из чего.

## Группа 4: Pixi.js

**В чём разница между Texture и BaseTexture в Pixi, и почему это важно для спрайт-атласов?**

`BaseTexture` — это фактические пиксели, загруженные в память GPU. Это одна GPU-текстура и более тяжёлая из двух единиц. `Texture` — окно в область `BaseTexture`, то есть прямоугольник внутри неё. Много объектов `Texture` могут ссылаться на одну `BaseTexture` без повторной загрузки.

```txt
┌──────────────────────────────────────────────────────┐
│ BaseTexture                                          │
│ пиксели, один раз загруженные в память GPU           │
├──────────────────────────────────────────────────────┤
│ Texture #1 — прямоугольник внутри неё                │
│ Texture #2 — другой прямоугольник                    │
│ Texture #3 ... и ещё десятки, без повторной загрузки │
└──────────────────────────────────────────────────────┘
```

Именно это отношение делает спрайт-атлас механизмом батчинга. Один большой файл PNG (portable network graphics) становится одной `BaseTexture` и режется на десятки объектов `Texture`. Batch renderer Pixi (пакетный отрисовщик) затем рисует все эти спрайты одним вызовом отрисовки. Переключать текстурные юниты между ними GPU не приходится.

---

**Что ломает batch renderer в Pixi, и как архитектурно минимизировать число вызовов отрисовки?**

Батч ломается всякий раз, когда двум соседям по порядку отрисовки нужно разное состояние GPU. Причин этому три.

| Что ломает батч | Почему ломает |
|---|---|
| Смена `BaseTexture` между соседями | GPU вынужден привязать другую текстуру |
| Фильтр в середине порядка отрисовки | он рендерит во временную render-текстуру |
| Смена режима смешивания (blend mode) у соседей | состояние GPU меняется между ними |

Архитектурные меры следуют из этого списка:

- Группируйте спрайты с одинаковой текстурой рядом по порядку отрисовки, где это позволяет порядок наложения (z-order).
- Ограничивайте число различных фильтров в одной сцене.
- Для очень больших количеств простых однотипных спрайтов используйте `ParticleContainer`. Он жертвует частью гибкости ради максимальной пропускной способности батчинга.

---

**Почему `Graphics` в Pixi дороже обновлять каждый кадр, чем `Sprite`?**

Обновление `Sprite` меняет только матрицу, а обновление `Graphics` перестраивает геометрию.

| Операция | `Sprite` | `Graphics` |
|---|---|---|
| Сдвиг, поворот, масштаб | изменение матрицы трансформации | изменение матрицы трансформации |
| `clear()` и рисование заново | вообще не нужно | заново генерирует вершинный буфер |

Двигать, вращать и масштабировать `Sprite` дёшево: геометрия и текстура уже существуют. Вызвать `clear()` у `Graphics` и нарисовать заново — значит перестроить его геометрию, а это заметно дороже простой смены трансформации.

Правило следует отсюда напрямую:

- Берите `Graphics` для статичных или редко меняющихся форм.
- Для форм, которые действительно перерисовываются каждый кадр в больших количествах, берите `Sprite` с заранее подготовленной текстурой.
- Либо один раз закэшируйте результат `Graphics` в `RenderTexture` и дальше рисуйте её.

## Группа 5: three.js

**Почему нужно вызывать `camera.updateProjectionMatrix()` после изменения свойств камеры?**

Изменение `camera.aspect`, а также `fov`, `near`, `far`, само по себе не пересчитывает матрицу проекции. Матрица остаётся устаревшей, пока вы не попросите явный пересчёт.

```javascript
const camera = new THREE.PerspectiveCamera(75, 1, 0.1, 1000);
const renderer = new THREE.WebGLRenderer();

function onResize() {
  camera.aspect = window.innerWidth / window.innerHeight;
  camera.updateProjectionMatrix();  // без этого картинка останется искажённой
  renderer.setSize(window.innerWidth, window.innerHeight);
}
window.addEventListener('resize', onResize);
```

Забыть `updateProjectionMatrix()` после изменения размера окна — классический баг, дающий растянутое или искажённое изображение. Соотношение сторон изменилось в данных камеры, а проекция, реально используемая при рендере, всё ещё соответствует старому соотношению.

---

**Что такое баг «модель выглядит блёклой», и чем он вызван?**

Причина — рассогласование цветовых пространств, а не модель и не освещение. Текстуры обычно хранятся в sRGB, то есть с гамма-кодировкой под восприятие экрана. Математика освещения в рендерере при этом корректна только в линейном пространстве.

| Настройка | Что она сообщает three.js |
|---|---|
| `texture.colorSpace = THREE.SRGBColorSpace` | эта цветная текстура хранится в sRGB |
| `renderer.outputColorSpace` | в каком пространстве уходит готовая картинка |

Поэтому three.js обязан знать кодировку каждой текстуры, и вывод тоже должен быть настроен верно. Когда эти настройки расходятся, декодирование sRGB происходит дважды или не происходит вовсе. Видимый результат — плоское, блёклое или неестественно контрастное изображение.

---

**Почему `dispose()` необходим в three.js, и в чём классический сценарий утечки памяти?**

GPU-ресурсы — геометрия, материалы, текстуры — не освобождаются сборщиком мусора JS так, как обычные объекты. Обёрточный JS-объект может быть собран, а выделенная под него память GPU останется занятой, пока `dispose()` не вызван явно.

```javascript
// scene.clear() только отцепляет объекты; их память на GPU остаётся занятой
function releaseScene(scene) {
  scene.traverse((obj) => {
    obj.geometry?.dispose();
    obj.material?.map?.dispose();
    obj.material?.dispose();
  });
  scene.clear();
}
```

Классическая утечка — смена маршрута в SPA (single-page application, одностраничное приложение), которая грузит новую 3D-модель, не освободив предыдущую сцену. Вызов `scene.clear()` освобождением не является: он лишь убирает объекты из сцены.

Память GPU тогда растёт с каждым переключением модели, пока вкладка не рухнет. Заметнее всего это в продуктовых конфигураторах, где пользователь переключает варианты снова и снова.

---

**Объясните разницу между `MeshBasicMaterial`, `MeshPhongMaterial` и `MeshStandardMaterial`.**

Все три различаются тем, как обходятся со светом, и в том же порядке растёт их цена.

| Материал | Освещение | Вид | Где применять |
|---|---|---|---|
| `MeshBasicMaterial` | без света, игнорирует источники | плоский цвет или текстура | самый дешёвый; элементы в 3D |
| `MeshPhongMaterial` | со светом, блики по пикселям | глянцевый пластик | классический вид с бликом |
| `MeshStandardMaterial` | со светом, физическая модель | реалистичный | современный выбор по умолчанию |

`MeshBasicMaterial` полностью игнорирует источники света и показывает плоский цвет или текстуру. Это самый дешёвый вариант, и он подходит для элементов UI (user interface, пользовательский интерфейс) в 3D или намеренно стилизованного вида.

`MeshPhongMaterial` работает со светом и считает бликовые (specular) отражения по пикселям, что даёт знакомую поверхность «глянцевого пластика».

`MeshStandardMaterial` использует PBR (physically based rendering, физически корректный рендеринг). Он описывает материал через шероховатость и металличность, опираясь на приближение реальной физики света, а не на произвольную формулу блика. Результат получается реалистичнее и остаётся последовательным при разных условиях освещения, поэтому это современный выбор по умолчанию для реалистичных сцен.

## Группа 6: SVG, `D3` и выбор технологии

**Что такое d3.js на самом деле, и в чём распространённое заблуждение о нём?**

Заблуждение — считать d3 3D-библиотекой из-за созвучия с «three.js» либо прежде всего библиотекой графиков. Это два совершенно не связанных между собой инструмента.

На самом деле `D3` — это «Data-Driven Documents», набор небольших независимых модулей.

- `d3-selection` — работа с DOM с учётом привязанных к узлам данных.
- `d3-scale` — чистые функции из домена данных в визуальный диапазон.
- `d3-shape` — чистые функции из данных в геометрию формы.
- `d3-axis` и ещё десяток других.

Ключевая деталь в том, что `d3-scale` и `d3-shape` не зависят от способа отрисовки. Им всё равно, попадёт результат в SVG-`<path>` или в вызовы canvas через `.context(ctx)`.

---

**Как выбрать между SVG, Canvas 2D и WebGL для визуализации данных?**

Первым решает объём данных, остальное решают требования.

| Технология | Объём данных | Что даёт и чем платите |
|---|---|---|
| SVG | до ~1-2 тысяч элементов | доступность, CSS-стилизация, чёткость на любом зуме |
| Canvas 2D | 10 000+ точек | нет издержек DOM, но попадания считаете сами |
| WebGL, Pixi | 100 000+ точек | единственный выход, когда canvas упёрся в потолок |

Берите SVG, когда важны доступность, CSS-стилизация, чёткость на любом зуме и богатая интерактивность на каждом элементе. Каждый SVG-элемент — реальный DOM-узел с реальными издержками, и это как раз то, что ограничивает число элементов.

Берите Canvas 2D примерно с 10 000 точек, где узким местом стало бы уже само число DOM-узлов. Платите за это более ручным определением попаданий и отсутствием retained-mode сцены «из коробки».

Берите WebGL или Pixi примерно со 100 000 точек, а также при обновлениях в реальном времени на высокой частоте. Это тот диапазон, где даже растеризация canvas силами CPU упирается в потолок.

## Группа 7: Архитектура, производительность и диагностика

**Сценарий отладки: промо-страница на Pixi проседает до 20 fps на бюджетном Android-телефоне, но идёт 60 fps на вашем десктопе. Опишите процесс диагностики.**

Сначала воспроизведите проблему, затем пройдите пять проверок по порядку.

1. **Воспроизведите с включённым замедлением.** Включите замедление CPU и сети (throttling) в DevTools вместо диагностики «на глаз» на мощном железе.
2. **Запишите сессию в Performance и решите, CPU это или GPU.** Как читать результат — в таблице ниже.
3. **Проверьте панель Layers и метрики GPU.** Ищите взрывной рост числа слоёв и слишком большие текстуры. На мобильном, где CPU и GPU делят одну память, полноэкранные слои стоят заметно дороже, чем на десктопе.
4. **Проверьте, ограничен ли `devicePixelRatio`.** Рендер на полном retina-разрешении часто оказывается самой дорогой единственной строчкой в мобильном рендеринге.
5. **Проверьте саму сцену Pixi.** Ищите сломанный батчинг: смену текстур не из общего атласа, лишние фильтры. Затем ищите новые текстуры и render-текстуры, созданные внутри цикла рендера без `destroy()`.

| Что вы видите на шаге 2 | Что это значит |
|---|---|
| Сущностей в JS меньше, время кадра то же | проблема не на стороне CPU |
| Шейдеры проще или разрешение ниже, кадр быстрее | проблема на стороне GPU |

Последний пункт шага 5 — это утечка памяти GPU, и она ухудшается по ходу сессии. Системную диагностику от угадывания отличает именно такая последовательность конкретных проверок, а не общие догадки.

---

**Почему стоит извлекать чистую update-логику из кода отрисовки, и как это влияет на стратегию тестирования?**

Разделите `update` и `draw` — и каждая половина станет проверяемой своим способом. В `update` живёт чистая логика: физика, правила игры, расчёты шкал. `draw` — единственное место, которое трогает `ctx`.

| Слой | Чем тестируется |
|---|---|
| `update`, чистая логика | обычные unit-тесты, без canvas и без DOM |
| `draw`, трогает `ctx` | визуальная регрессия против эталонной картинки |
| Заглушка вместо `ctx` | анти-паттерн, см. ниже |

Обычные unit-тесты покрывают `update` целиком, потому что для их запуска ничего не нужно рисовать. У отрисовки нет простого «проверить одно значение», поэтому её берёт на себя визуальное регрессионное тестирование. Скриншоты сравниваются с эталоном попиксельно, и это ловит непреднамеренные визуальные регрессии, которые unit-тесты структурно поймать не способны.

Подменять сам `ctx` заглушкой и проверять, какие методы с какими аргументами были вызваны, — анти-паттерн. Это хрупкий тест реализации: он ломается при любом рефакторинге отрисовки, даже если визуальный результат идентичен.
