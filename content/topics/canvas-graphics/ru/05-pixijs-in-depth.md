# Pixi.js в деталях

## Pixi — retained-mode сцена поверх WebGL

Pixi держит сцену как дерево долгоживущих объектов поверх WebGL (Web Graphics Library) и перерисовывает её за вас. Это и есть **retained-mode**, то есть режим с запоминанием.

Вы создаёте объекты сцены **один раз**, а дальше просто **мутируете их свойства**: `sprite.x = 150`, `sprite.rotation += 0.02`. Pixi сам разбирается, что и как перерисовать. Он собирает эти изменения в минимальное число вызовов отрисовки (draw call) через встроенный batch renderer (статья 04).

Это противоположность **immediate-mode** модели Canvas 2D из статей 01-03, то есть немедленному режиму. Там вы рисуете пиксели, ничего не запоминается, и следующий кадр рисуете заново с нуля (статья 01).

```txt
Canvas 2D (immediate mode, статьи 01-03)
  каждый кадр:
    ctx.clearRect(...)
    ctx.drawImage(sprite, x, y)
    // вы сами отвечаете за каждый кадр

Pixi (retained mode)
  один раз:
    const sprite = new Sprite(texture);
    stage.addChild(sprite);
  каждый кадр:
    sprite.x += 1;   // просто мутация
    // Pixi сам знает, что перерисовать
```

Это не "Pixi отменяет immediate mode как концепцию". Под капотом Pixi всё равно рисует через WebGL-вызовы отрисовки каждый кадр. На уровне GPU (graphics processing unit — графический процессор) рендеринг остаётся полностью immediate-mode (статья 04).

Но с точки зрения **вашего** кода модель становится retained. Вы работаете с деревом долгоживущих объектов, а не с одноразовыми командами рисования.

## `Application`, `stage`, иерархия `Container`

```javascript
const app = new Application();
await app.init({ width: 800, height: 600, backgroundColor: 0x1a1a2e });
document.body.appendChild(app.canvas);

const group = new Container(); // Container — узел дерева сцены:
app.stage.addChild(group);       // держит детей И собственную трансформацию

const sprite = new Sprite(texture);
group.addChild(sprite);

group.rotation = 0.1; // трансформация Container применяется ко всем
                       // его детям автоматически — этого нет в чистом
                       // canvas без ручного save()/translate()/rotate()
                       // на каждый дочерний элемент (статья 01)
```

`app.stage` — корневой `Container` сцены. Любой `Container` — узел дерева, хранящий и список детей, и собственную трансформацию: позицию, поворот, масштаб, альфу.

Трансформация родителя автоматически композируется с трансформацией потомков при рендере. В чистом Canvas 2D это пришлось бы обеспечивать вручную, через `save()`/`translate()`/`rotate()` вокруг каждой отрисовки (статья 01). Здесь это встроено в саму структуру сцены.

## `Sprite`, `Texture` и `BaseTexture`

| Понятие | Что это |
|---|---|
| `BaseTexture` | Фактические пиксели, **загруженные в GPU-память**, одна GPU-текстура. Самая тяжёлая единица: именно она стоит памяти видеокарты. |
| `Texture` | "Окно" в область `BaseTexture`: прямоугольник x, y, width, height внутри неё. Много `Texture` могут ссылаться на **одну** `BaseTexture` без повторной загрузки. |
| `Sprite` | Объект отображения (display object), который рисует конкретную `Texture` в определённой позиции, повороте и масштабе. |

```javascript
const sprite = new Sprite(texture);
sprite.anchor.set(0.5); // точка привязки (0.5, 0.5) = центр —
                          // поворот/масштаб происходят вокруг центра,
                          // а не вокруг угла (0,0) по умолчанию
```

Именно разделение `Texture`/`BaseTexture` делает спрайт-атласы возможными. Один большой PNG (portable network graphics — растровый формат изображений) — это одна `BaseTexture` и одна загрузка в GPU-память. Он режется на десятки `Texture`-объектов, каждый из которых указывает на свой прямоугольник внутри общего изображения, без единой дополнительной GPU-загрузки на спрайт.

## Спрайт-атласы: почему они включают батчинг

Batch renderer в Pixi может объединить рисование множества спрайтов в один вызов отрисовки. Условие: у всех задействованных спрайтов есть общая `BaseTexture`.

Причина в том, что GPU не нужно переключать "юнит текстуры" между отрисовкой соседних спрайтов, если они читают пиксели из одного и того же загруженного изображения. Стоимость вызова отрисовки — это в основном накладные расходы на смену состояния, включая смену текстуры (статья 04).

```txt
❌ 200 отдельных PNG-файлов, каждый — своя BaseTexture:
   рисование 200 спрайтов ≈ до 200 вызовов отрисовки (или групп
   по смежным одинаковым текстурам) — расходы драйвера растут
   линейно

✅ Один атлас 2048×2048px, 200 спрайтов — 200 Texture, указывающих
   в разные прямоугольники одной BaseTexture:
   те же 200 спрайтов рисуются несколькими (в идеале — одним)
   вызовами отрисовки, независимо от количества
```

Практический вывод касается сцен с сотнями и тысячами похожих спрайтов: частицы, иконки интерфейса, тайлы карты. Там объединение изображений в атлас — не микрооптимизация.

Это архитектурное решение, и оно определяет, упрётся ли сцена в производительность на реальном количестве объектов.

## Batch renderer: что его ломает

```txt
Ломает батч (форсирует отдельный вызов отрисовки):
  - Смена BaseTexture между соседними по порядку отрисовки спрайтами
    (если они не из одного атласа)
  - Фильтр (Filter) на любом объекте в середине порядка отрисовки.
    Фильтр требует рендера во временную render-текстуру и обратно,
    что принципиально прерывает батч до и после себя
  - Смена режима смешивания (blend mode) между соседними объектами
  - Кастомный шейдер на отдельном объекте, отличный от остальных
    в батче
```

Из этого следуют три практических правила для архитектуры сцены:

- Группировать спрайты с одинаковой текстурой рядом по порядку отрисовки там, где визуальный порядок наложения (z-order) это позволяет.
- Ограничивать число **разных** фильтров в сцене. Не "фильтр на каждый десятый спрайт вперемешку с обычными", а либо на всех, либо ни на одном в данном визуальном слое.
- Для действительно огромного количества однотипных простых спрайтов — тысяч частиц — брать `ParticleContainer`. Это специализированный контейнер, заточенный под максимальную пропускную способность батчинга именно для этого случая. Чем он жертвует: упрощённая модель трансформаций и ограниченная поддержка отдельных фильтров на детях.

## `Graphics`: вектор — но не бесплатный на каждый кадр

`Graphics` — API для рисования векторных фигур, аналог `fillRect`/`arc`/путей из статьи 01. Результат при этом — WebGL-геометрия, а не canvas-пиксели:

```javascript
const graphics = new Graphics();
graphics.rect(0, 0, 100, 100).fill(0xff3366);
graphics.circle(150, 50, 40).fill(0x33ccff);
stage.addChild(graphics);
```

Ключевое отличие от `Sprite` — в стоимости. `Sprite` дёшево двигать, вращать и масштабировать каждый кадр: это просто изменение матрицы трансформации над уже существующей геометрией и текстурой.

`Graphics` ведёт себя иначе. Когда вы вызываете `clear()` и рисуете заново, он **перестраивает геометрию**, то есть заново генерирует вершинный буфер. Это заметно дороже простой смены трансформации.

```javascript
// ❌ Дорого: геометрия Graphics пересобирается 60 раз в секунду
app.ticker.add(() => {
  graphics.clear();
  graphics.circle(mouseX, mouseY, 20).fill(0xffffff);
});
```

```javascript
// ✅ Дёшево: Sprite просто двигается, геометрия/текстура не меняются
const cursorSprite = new Sprite(circleTexture); // текстура посчитана один раз
app.ticker.add(() => {
  cursorSprite.x = mouseX;
  cursorSprite.y = mouseY; // только трансформация, без перестройки геометрии
});
```

Правило: `Graphics` — для статичных или редко меняющихся векторных форм. Для форм, которые действительно нужно перерисовывать каждый кадр в больших количествах, берите `Sprite` с заранее подготовленной текстурой. Второй вариант — один раз закэшировать результат `Graphics` в `RenderTexture` или через `cacheAsTexture`, вместо пересборки геометрии на каждом тике.

## `Text` vs `BitmapText`

```javascript
const text = new Text({ text: 'Score: 0', style: { fontSize: 24, fill: 0xffffff } });
// Внутри Text рендерит строку через canvas 2D (измерение, растеризация
// глифов) и загружает результат как обычную текстуру — дорого на
// каждое изменение текста/стиля, нормально как статичная надпись

const bitmapText = new BitmapText({ text: 'Score: 0', style: { fontFamily: 'game-font' } });
// BitmapText собирает строку из готовых спрайтов-глифов заранее
// подготовленного bitmap-шрифта (спрайт-атласа символов) — обновление
// текста не требует растеризации canvas заново, дёшево на каждый кадр
```

Практический выбор зависит от того, как часто меняется строка. Счётчик очков, который обновляется раз в секунду или реже, — `Text` без проблем. Счётчик кадров в секунду или таймер, который обновляется каждый кадр, — `BitmapText`.

Причина в том, что растеризация через canvas на каждый кадр для `Text` создаёт заметную нагрузку. `BitmapText` полностью её избегает — ценой необходимости заранее подготовленного bitmap-шрифта.

## Взаимодействие: события указателя на объектах сцены

```javascript
sprite.eventMode = 'static'; // включить обработку событий для объекта
sprite.cursor = 'pointer';
sprite.on('pointerdown', () => console.log('clicked!'));
sprite.on('pointerover', () => { sprite.tint = 0xffcc00; });

sprite.hitArea = new Rectangle(0, 0, 200, 50); // явная область попадания,
// отличная от визуальных границ спрайта — полезно для увеличения
// кликабельной зоны маленькой иконки или сужения её под неправильную форму
```

Концептуально это та же задача, что определение попадания (hit detection) на чистом canvas: математическая проверка, `isPointInPath` или color-picking (статья 02). Pixi берёт её на себя через дерево сцены. Попадание проверяется автоматически по иерархии `Container`, с учётом трансформаций родителей и без ручного пересчёта координат.

## Фильтры: встроенные и кастомный fragment shader

```javascript
import { BlurFilter, ColorMatrixFilter } from 'pixi.js';

sprite.filters = [new BlurFilter({ strength: 8 })];

const colorMatrix = new ColorMatrixFilter();
colorMatrix.grayscale(0.8);
sprite.filters = [colorMatrix];
```

Фильтр применяется в три шага. Объект, а иногда и область вокруг него, рендерится во временную render-текстуру. Над этой текстурой прогоняется фрагментный шейдер (статья 04). Результат вставляется обратно в сцену.

Именно поэтому фильтры "ломают батч", как сказано выше. Это дополнительный изолированный проход рендеринга, а не часть обычного потока отрисовки.

```javascript
// Минимальный кастомный фильтр — grayscale через собственный fragment shader
import { Filter, GlProgram } from 'pixi.js';

const grayscaleFragment = `
  precision mediump float;
  varying vec2 vTextureCoord;
  uniform sampler2D uTexture;

  void main() {
    vec4 color = texture2D(uTexture, vTextureCoord);
    float gray = dot(color.rgb, vec3(0.299, 0.587, 0.114)); // та же формула
                                                              // яркости, что и в статье 03
    gl_FragColor = vec4(vec3(gray), color.a);
  }
`;

const customGrayscale = new Filter({
  glProgram: new GlProgram({ fragment: grayscaleFragment, vertex: defaultVertexShader }),
});
sprite.filters = [customGrayscale];
```

Это прямое применение модели GLSL (OpenGL Shading Language) из статьи 04. Pixi предоставляет `vTextureCoord` — varying, интерполированный растеризацией, и `uTexture` — uniform-сэмплер. Это избавляет от необходимости вручную настраивать буферы и атрибуты для полноэкранного прохода.

## `Ticker`: встроенный цикл обновления

```javascript
app.ticker.add((ticker) => {
  sprite.rotation += 0.02 * ticker.deltaTime; // deltaTime: 1.0 = "один кадр при 60fps",
                                                // масштабируется под реальную частоту —
                                                // тот же смысл, что delta time в статьях
                                                // browser-animation/04 и canvas/02,
                                                // но уже встроенный в рендерер
});
```

Pixi уже управляет собственным rAF-циклом (`requestAnimationFrame`) рендеринга внутри `Application`. Отдельный `requestAnimationFrame` рядом заводить не нужно и не стоит.

Пользовательская игровая логика подключается через `app.ticker.add()`. Она получает `deltaTime` в кадрах при целевых 60fps или `deltaMS` в миллисекундах.

## Управление памятью: `destroy()` и утечка "новая текстура на каждый кадр"

GPU-ресурсы, то есть текстуры и буферы, не освобождаются автоматической сборкой мусора JS так же, как обычные объекты. JS-объект-обёртка может быть собран, но выделенная под него GPU-память останется занятой, пока явно не вызван `destroy()`.

```javascript
sprite.destroy();                       // уничтожает объект отображения
texture.destroy(true);                   // true — уничтожить и BaseTexture тоже
container.destroy({ children: true });   // рекурсивно уничтожить всех детей
```

```javascript
// ❌ Классическая утечка: новая RenderTexture на каждый кадр,
// старые никогда не destroy() — GPU-память растёт без остановки
app.ticker.add(() => {
  const snapshot = RenderTexture.create({ width: 200, height: 200 });
  app.renderer.render({ container: someObject, target: snapshot });
  updatePreview(snapshot); // старый snapshot из прошлого кадра не уничтожен
});
```

```javascript
// ✅ Одна RenderTexture создаётся один раз и переиспользуется
const snapshot = RenderTexture.create({ width: 200, height: 200 });
app.ticker.add(() => {
  app.renderer.render({ container: someObject, target: snapshot }); // тот же
                                                                       // GPU-ресурс,
                                                                       // просто
                                                                       // перезаписывается
  updatePreview(snapshot);
});
```

Этот паттерн утечки особенно опасен на мобильных устройствах с ограниченной GPU-памятью. Приложение работает нормально несколько минут, затем вкладка вылетает или браузер принудительно освобождает контекст. Это типичный продакшен-баг, который сложно поймать в быстром локальном тестировании на мощном десктопе.

## Когда Pixi вместо чистого Canvas 2D, а когда — избыточно

**Когда Pixi оправдан:**

- Сотни и тысячи спрайтов или частиц одновременно. Батчинг решает то, на чём чистый Canvas 2D упирается в CPU (central processing unit — центральный процессор), отрисовывая каждый `drawImage` по отдельности.
- Композиции с несколькими фильтрами, режимами смешивания и сложной интерактивностью на множестве объектов.
- Проект, который будет расти в сложности: много слоёв, вложенная иерархия объектов, повторное использование текстур.

**Когда он избыточен:**

- Горстка простых фигур или иконок, разовая простая анимация. Вес библиотеки и её API поверх такой задачи не окупаются.
- Чистый Canvas 2D (статьи 01-03) для этого проще и вполне достаточен.

## Pixi с React: императивное ядро внутри декларативной оболочки

```tsx
function PixiCanvas() {
  const containerRef = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const app = new Application();
    let cancelled = false;

    (async () => {
      await app.init({ width: 800, height: 600 });
      if (cancelled) { app.destroy(true); return; } // размонтировали, пока init() шёл
      containerRef.current?.appendChild(app.canvas);
      // ...построение сцены
    })();

    return () => {
      cancelled = true;
      app.destroy(true, { children: true, texture: true }); // обязательная очистка —
                                                                // без неё каждый ремаунт
                                                                // компонента (route change,
                                                                // React StrictMode) утекает
                                                                // GPU-ресурсы
    };
  }, []);

  return <div ref={containerRef} />;
}
```

Это тот же принцип "canvas как аварийный выход из модели рендеринга React", который статья 08 подробно разбирает для чистого canvas. Pixi `Application` живёт в `useEffect`, вне цикла React-рендеров, и должна быть явно уничтожена в функции очистки.

Для более декларативного стиля существует `@pixi/react`. Это обёртка, позволяющая описывать сцену компонентами JSX (синтаксическое расширение JavaScript) вроде `<pixiSprite>`. Она остаётся тонким слоем поверх той же императивной модели Pixi, а не заменяет её.

## Типичные ошибки на интервью

- **Не суметь объяснить, чем Pixi отличается от чистого canvas по модели** — путать "Pixi использует WebGL" с "Pixi — retained mode". Оба утверждения верны, но это два **разных** факта. WebGL-рендеринг остаётся immediate на уровне GPU, а retained — это про то, как организован **ваш** код поверх него.

- **Путать `Texture` и `BaseTexture`** — не знать, что множество `Texture` могут ссылаться на одну `BaseTexture` без повторной загрузки в GPU. Именно это делает спрайт-атласы механизмом батчинга, а не просто удобной упаковкой файлов.

- **Не знать, что ломает батчинг** — не суметь назвать конкретные причины: смена текстуры, фильтр в середине порядка отрисовки, смена режима смешивания. И не суметь предложить архитектурные решения: атлас, группировка по текстуре, ограничение числа фильтров.

- **Считать `Graphics` таким же дешёвым, как `Sprite`, на каждый кадр** — не знать, что перерисовка `Graphics` пересобирает геометрию. Перемещение `Sprite` — это просто изменение матрицы трансформации над уже готовыми данными.

- **Не знать разницы `Text` и `BitmapText` по стоимости обновления** — предлагать `Text` для счётчика, обновляющегося каждый кадр. Это упускает растеризацию через canvas на каждое изменение.

- **Не вызывать `destroy()`** — создавать новые текстуры и render-текстуры в цикле рендера без освобождения старых. Результат — утечка GPU-памяти, особенно заметная на мобильных устройствах.

- **Не очищать Pixi `Application` при размонтировании React-компонента** — забывать `app.destroy()` в функции очистки `useEffect`. Утечки тогда накапливаются при каждом ремаунте: переход по роутам, React StrictMode в разработке.
