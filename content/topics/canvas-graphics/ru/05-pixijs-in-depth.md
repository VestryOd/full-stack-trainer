# Pixi.js в деталях

## Pixi — retained-mode сцена поверх WebGL

Статьи 01-03 — это immediate-mode Canvas 2D: нарисовал пиксели, ничего не запомнилось, следующий кадр рисуете заново с нуля (статья 01). Pixi переворачивает эту модель: вы создаёте объекты сцены ОДИН РАЗ, а дальше просто **мутируете их свойства** (`sprite.x = 150`, `sprite.rotation += 0.02`) — Pixi сам разбирается, что и как перерисовать, и сам собирает эти изменения в минимальное число WebGL draw call'ов (статья 04) через встроенный batch renderer.

```txt
Canvas 2D (immediate mode, статьи 01-03):     Pixi (retained mode):
  каждый кадр:                                  один раз:
    ctx.clearRect(...)                            const sprite = new Sprite(texture);
    ctx.drawImage(sprite, x, y)                   stage.addChild(sprite);
    // вы сами отвечаете за КАЖДЫЙ кадр            каждый кадр:
                                                     sprite.x += 1; // просто мутация
                                                     // Pixi сам знает, что перерисовать
```

Это не "Pixi отменяет immediate mode как концепцию" — под капотом Pixi всё равно рисует через WebGL draw call'ы каждый кадр (полностью immediate-mode рендеринг на уровне GPU, статья 04); но с точки зрения ВАШЕГО кода модель становится retained: вы работаете с деревом долгоживущих объектов, а не с одноразовыми командами рисования.

## `Application`, `stage`, иерархия `Container`

```javascript
const app = new Application();
await app.init({ width: 800, height: 600, backgroundColor: 0x1a1a2e });
document.body.appendChild(app.canvas);

const group = new Container(); // Container — узел дерева сцены:
app.stage.addChild(group);       // держит детей И собственную трансформацию

const sprite = new Sprite(texture);
group.addChild(sprite);

group.rotation = 0.1; // трансформация Container применяется КО ВСЕМ
                       // его детям автоматически — этого нет в чистом
                       // canvas без ручного save()/translate()/rotate()
                       // на каждый дочерний элемент (статья 01)
```

`app.stage` — корневой `Container` сцены. Любой `Container` — узел дерева, хранящий и список детей, и собственную трансформацию (позиция, поворот, масштаб, альфа); трансформация родителя автоматически композируется с трансформацией потомков при рендере — то, что в чистом Canvas 2D пришлось бы вручную обеспечивать через `save()`/`translate()`/`rotate()` вокруг каждой отрисовки (статья 01), здесь встроено в саму структуру сцены.

## `Sprite`, `Texture` и `BaseTexture`

```txt
BaseTexture — фактические пиксели, ЗАГРУЖЕННЫЕ В GPU-ПАМЯТЬ (одна
               GPU-текстура); самая "тяжёлая" единица — именно она
               стоит памяти видеокарты

Texture      — "окно" в область BaseTexture (прямоугольник x, y,
               width, height внутри неё); МНОГО Texture могут
               ссылаться на ОДНУ BaseTexture без повторной загрузки

Sprite       — display-объект, который рисует конкретную Texture
               в определённой позиции/повороте/масштабе
```

```javascript
const sprite = new Sprite(texture);
sprite.anchor.set(0.5); // точка привязки (0.5, 0.5) = центр —
                          // поворот/масштаб происходят вокруг центра,
                          // а не вокруг угла (0,0) по умолчанию
```

Именно разделение Texture/BaseTexture делает спрайт-атласы возможными: один большой PNG (одна `BaseTexture`, одна загрузка в GPU-память) режется на десятки `Texture`-объектов, каждый из которых указывает на свой прямоугольник внутри общего изображения — без единой дополнительной GPU-загрузки на спрайт.

## Спрайт-атласы: почему они включают батчинг

Batch renderer Pixi может объединить рисование множества спрайтов в ОДИН draw call, если у всех задействованных спрайтов есть общая `BaseTexture` — GPU не нужно переключать "юнит текстуры" между отрисовкой соседних спрайтов, если они читают пиксели из одного и того же загруженного изображения (статья 04, стоимость draw call'а — это в основном оверхед смены состояния, включая текстуру).

```txt
❌ 200 отдельных PNG-файлов, каждый — своя BaseTexture:
   рисование 200 спрайтов ≈ до 200 draw call'ов (или групп по
   смежным одинаковым текстурам) — оверхед драйвера растёт линейно

✅ Один атлас 2048×2048px, 200 спрайтов — 200 Texture, указывающих
   в разные прямоугольники ОДНОЙ BaseTexture:
   те же 200 спрайтов рисуются НЕСКОЛЬКИМИ (в идеале — одним)
   draw call'ами, независимо от количества
```

Практический вывод: для сцен с сотнями/тысячами похожих спрайтов (частицы, UI-иконки, тайлы карты) объединение изображений в атлас — не микрооптимизация, а архитектурное решение, определяющее, упрётся ли сцена в производительность на реальном количестве объектов.

## Batch renderer: что его ломает

```txt
Ломает батч (форсирует отдельный draw call):
  - Смена BaseTexture между соседними по порядку отрисовки спрайтами
    (если они не из одного атласа)
  - Фильтр (Filter) на ЛЮБОМ объекте в середине порядка отрисовки —
    фильтр требует рендера во ВРЕМЕННУЮ render-текстуру и обратно,
    что принципиально прерывает батч до и после себя
  - Смена blend mode между соседними объектами
  - Кастомный шейдер на отдельном объекте, отличный от остальных
    в батче
```

Практические следствия для архитектуры сцены: группировать спрайты с одинаковой текстурой рядом по порядку отрисовки там, где визуальный z-order это позволяет; ограничивать число РАЗНЫХ фильтров в сцене (не "фильтр на каждый десятый спрайт вперемешку с обычными", а либо на всех, либо ни на одном в данном визуальном слое); для действительно огромного количества однотипных простых спрайтов (тысячи частиц) — `ParticleContainer`, специализированный контейнер, жертвующий частью гибкости (упрощённая модель трансформаций, ограниченная поддержка отдельных фильтров на детях) ради максимальной пропускной способности батчинга именно для этого случая.

## `Graphics`: вектор — но не бесплатный на каждый кадр

`Graphics` — API для рисования векторных фигур (аналог `fillRect`/`arc`/путей из статьи 01), но результатом является WebGL-геометрия, а не canvas-пиксели:

```javascript
const graphics = new Graphics();
graphics.rect(0, 0, 100, 100).fill(0xff3366);
graphics.circle(150, 50, 40).fill(0x33ccff);
stage.addChild(graphics);
```

Ключевое отличие от `Sprite`: `Sprite` дёшево двигать/вращать/масштабировать каждый кадр — это просто изменение матрицы трансформации над УЖЕ существующей геометрией и текстурой. `Graphics`, когда вы вызываете `clear()` и рисуете заново, **перестраивает геометрию** (заново генерирует вершинный буфер) — операция заметно дороже простой смены трансформации.

```javascript
// ❌ Дорого: геометрия Graphics пересобирается 60 раз в секунду
app.ticker.add(() => {
  graphics.clear();
  graphics.circle(mouseX, mouseY, 20).fill(0xffffff);
});
```

```javascript
// ✅ Дёшево: Sprite просто двигается, геометрия/текстура не меняются
const cursorSprite = new Sprite(circleTexture); // текстура посчитана один раз
app.ticker.add(() => {
  cursorSprite.x = mouseX;
  cursorSprite.y = mouseY; // только трансформация, без перестройки геометрии
});
```

Правило: `Graphics` — для статичных или редко меняющихся векторных форм; для форм, которые действительно нужно перерисовывать каждый кадр в больших количествах, — либо `Sprite` с заранее подготовленной текстурой, либо кэширование результата `Graphics` в `RenderTexture`/`cacheAsTexture` один раз, вместо пересборки геометрии на каждом тике.

## `Text` vs `BitmapText`

```javascript
const text = new Text({ text: 'Score: 0', style: { fontSize: 24, fill: 0xffffff } });
// Внутри Text рендерит строку через canvas 2D (измерение, растеризация
// глифов) и загружает результат как ОБЫЧНУЮ текстуру — дорого на
// КАЖДОЕ изменение текста/стиля, нормально как статичная надпись

const bitmapText = new BitmapText({ text: 'Score: 0', style: { fontFamily: 'game-font' } });
// BitmapText собирает строку из ГОТОВЫХ спрайтов-глифов заранее
// подготовленного bitmap-шрифта (спрайт-атласа символов) — обновление
// текста НЕ требует растеризации canvas заново, дёшево на каждый кадр
```

Практический выбор: счётчик очков, обновляющийся раз в секунду или реже, — `Text` без проблем; счётчик FPS/таймер, обновляющийся каждый кадр, — `BitmapText`, потому что растеризация через canvas на каждый кадр для `Text` создаёт заметную нагрузку, которой `BitmapText` полностью избегает ценой необходимости заранее подготовленного bitmap-шрифта.

## Взаимодействие: события указателя на объектах сцены

```javascript
sprite.eventMode = 'static'; // включить обработку событий для объекта
sprite.cursor = 'pointer';
sprite.on('pointerdown', () => console.log('clicked!'));
sprite.on('pointerover', () => { sprite.tint = 0xffcc00; });

sprite.hitArea = new Rectangle(0, 0, 200, 50); // явная область попадания,
// отличная от визуальных границ спрайта — полезно для увеличения
// кликабельной зоны маленькой иконки или сужения её под неправильную форму
```

Это концептуально та же задача, что hit detection на чистом canvas (статья 02, математическая проверка/`isPointInPath`/color-picking), но Pixi берёт её на себя через дерево сцены: попадание проверяется автоматически по иерархии `Container`, с учётом трансформаций родителей, без ручного пересчёта координат.

## Фильтры: встроенные и кастомный fragment shader

```javascript
import { BlurFilter, ColorMatrixFilter } from 'pixi.js';

sprite.filters = [new BlurFilter({ strength: 8 })];

const colorMatrix = new ColorMatrixFilter();
colorMatrix.grayscale(0.8);
sprite.filters = [colorMatrix];
```

Фильтр применяется, рендеря объект (и иногда область вокруг него) во временную render-текстуру, затем прогоняя над ней фрагментный шейдер (статья 04) и вставляя результат обратно в сцену — именно поэтому фильтры "ломают батч" (см. выше): это дополнительный, изолированный render pass, а не часть обычного потока отрисовки.

```javascript
// Минимальный кастомный фильтр — grayscale через собственный fragment shader
import { Filter, GlProgram } from 'pixi.js';

const grayscaleFragment = `
  precision mediump float;
  varying vec2 vTextureCoord;
  uniform sampler2D uTexture;

  void main() {
    vec4 color = texture2D(uTexture, vTextureCoord);
    float gray = dot(color.rgb, vec3(0.299, 0.587, 0.114)); // та же формула
                                                              // яркости, что и в статье 03
    gl_FragColor = vec4(vec3(gray), color.a);
  }
`;

const customGrayscale = new Filter({
  glProgram: new GlProgram({ fragment: grayscaleFragment, vertex: defaultVertexShader }),
});
sprite.filters = [customGrayscale];
```

Это прямое применение GLSL-модели из статьи 04 — Pixi предоставляет `vTextureCoord` (varying, интерполированный растеризацией) и `uTexture` (uniform-сэмплер), избавляя от необходимости вручную настраивать буферы/атрибуты для полноэкранного прохода.

## `Ticker`: встроенный цикл обновления

```javascript
app.ticker.add((ticker) => {
  sprite.rotation += 0.02 * ticker.deltaTime; // deltaTime: 1.0 = "один кадр при 60fps",
                                                // масштабируется под реальную частоту —
                                                // тот же смысл, что delta time в статьях
                                                // browser-animation/04 и canvas/02,
                                                // но уже встроенный в рендерер
});
```

Pixi уже управляет собственным rAF-циклом рендеринга внутри `Application` — не нужно (и не стоит) заводить отдельный `requestAnimationFrame` рядом; пользовательская игровая логика подключается через `app.ticker.add()`, получая `deltaTime` (в "кадрах при целевых 60fps") или `deltaMS` (в миллисекундах) для собственных расчётов.

## Управление памятью: `destroy()` и утечка "новая текстура на каждый кадр"

GPU-ресурсы (текстуры, буферы) НЕ освобождаются автоматической сборкой мусора JS так же, как обычные объекты — JS-объект-обёртка может быть собран, но выделенная под него GPU-память останется занятой, пока явно не вызван `destroy()`.

```javascript
sprite.destroy();                       // уничтожает display-объект
texture.destroy(true);                   // true — уничтожить и BaseTexture тоже
container.destroy({ children: true });   // рекурсивно уничтожить всех детей
```

```javascript
// ❌ Классическая утечка: новая RenderTexture на каждый кадр,
// старые никогда не destroy() — GPU-память растёт без остановки
app.ticker.add(() => {
  const snapshot = RenderTexture.create({ width: 200, height: 200 });
  app.renderer.render({ container: someObject, target: snapshot });
  updatePreview(snapshot); // старый snapshot из прошлого кадра НЕ уничтожен
});
```

```javascript
// ✅ Одна RenderTexture создаётся один раз и переиспользуется
const snapshot = RenderTexture.create({ width: 200, height: 200 });
app.ticker.add(() => {
  app.renderer.render({ container: someObject, target: snapshot }); // тот же
                                                                       // GPU-ресурс,
                                                                       // просто
                                                                       // перезаписывается
  updatePreview(snapshot);
});
```

Этот паттерн утечки особенно опасен на мобильных устройствах с ограниченной GPU-памятью: приложение работает нормально несколько минут, затем вкладка вылетает или браузер принудительно освобождает контекст — типичный продакшен-баг, который сложно поймать в быстром локальном тестировании на мощном десктопе.

## Когда Pixi вместо чистого Canvas 2D, а когда — избыточно

```txt
Pixi оправдан:
  - Сотни-тысячи спрайтов/частиц одновременно (батчинг решает то,
    что в чистом Canvas 2D упирается в CPU на отрисовку каждого
    drawImage по отдельности)
  - Композиции с несколькими фильтрами, blend-режимами, сложной
    интерактивностью на множестве объектов
  - Проект, который будет расти в сложности (много слоёв, вложенная
    иерархия объектов, повторное использование текстур)

Избыточен:
  - Горстка простых фигур/иконок, разовая простая анимация —
    вес библиотеки и API поверх задачи не окупается; чистый
    Canvas 2D (статьи 01-03) проще и вполне достаточен
```

## Pixi с React: императивное ядро внутри декларативной оболочки

```tsx
function PixiCanvas() {
  const containerRef = useRef<HTMLDivElement>(null);

  useEffect(() => {
    const app = new Application();
    let cancelled = false;

    (async () => {
      await app.init({ width: 800, height: 600 });
      if (cancelled) { app.destroy(true); return; } // размонтировали, пока init() шёл
      containerRef.current?.appendChild(app.canvas);
      // ...построение сцены
    })();

    return () => {
      cancelled = true;
      app.destroy(true, { children: true, texture: true }); // ОБЯЗАТЕЛЬНАЯ очистка —
                                                                // без неё каждый ремаунт
                                                                // компонента (route change,
                                                                // React StrictMode) утекает
                                                                // GPU-ресурсы
    };
  }, []);

  return <div ref={containerRef} />;
}
```

Это тот же принцип "canvas как escape hatch из модели рендеринга React" (статья 08 разбирает его подробно для чистого canvas) — Pixi `Application` живёт в `useEffect`, вне цикла React-рендеров, и должна быть явно уничтожена в cleanup-функции. Для более декларативного стиля существует `@pixi/react` (обёртка, позволяющая описывать сцену JSX-компонентами вроде `<pixiSprite>`), но она остаётся тонким слоем поверх той же императивной модели Pixi, а не заменяет её.

## Типичные ошибки на интервью

- **Не суметь объяснить, чем Pixi отличается от чистого canvas по модели** — путать "Pixi использует WebGL" с "Pixi — retained mode" — оба утверждения верны, но это два РАЗНЫХ факта: WebGL-рендеринг остаётся immediate на уровне GPU, retained — это про то, как организован ВАШ код поверх него.

- **Путать Texture и BaseTexture** — не знать, что множество Texture могут ссылаться на одну BaseTexture без повторной загрузки в GPU, и что именно это делает спрайт-атласы механизмом батчинга, а не просто "удобной упаковкой файлов".

- **Не знать, что ломает батчинг** — не суметь назвать конкретные причины (смена текстуры, фильтр в середине порядка отрисовки, смена blend mode) и предложить архитектурные решения (атлас, группировка по текстуре, ограничение числа фильтров).

- **Считать `Graphics` таким же дешёвым, как `Sprite`, на каждый кадр** — не знать, что перерисовка `Graphics` пересобирает геометрию, тогда как перемещение `Sprite` — просто изменение матрицы трансформации над уже готовыми данными.

- **Не знать разницы `Text` и `BitmapText` по стоимости обновления** — предлагать `Text` для счётчика, обновляющегося каждый кадр, не зная о растеризации через canvas на каждое изменение.

- **Не вызывать `destroy()`** — создавать новые текстуры/render-текстуры в цикле рендера без освобождения старых, что приводит к утечке GPU-памяти, особенно заметной на мобильных устройствах.

- **Не очищать Pixi `Application` при размонтировании React-компонента** — забывать `app.destroy()` в cleanup-функции `useEffect`, что накапливает утечки при каждом ремаунте (переход по роутам, React StrictMode в разработке).
