# WebGL и основы GPU

## Зачем это знать, если почти всегда используется Pixi или three.js

Потому что Pixi и three.js — тонкие обёртки над той самой моделью, которую описывает эта статья. Обе библиотеки говорят с GPU (graphics processing unit — графический процессор) через WebGL (Web Graphics Library) и не изобретают собственную модель рендеринга. Все их правила производительности растут из конвейера, разобранного ниже.

Два вопроса делают это наглядным. Почему добавление ещё одного фильтра в Pixi настолько замедлило сцену? Почему смена текстуры между спрайтами дороже, чем кажется? Ни на один из них нельзя ответить на уровне библиотеки. Pixi — это статья 05, three.js — статья 06, и обе отсылают сюда.

Без этого фундамента работа с обеими библиотеками сводится к копированию примеров из документации "потому что так работает". С ним те же решения становятся инженерными: они опираются на реальную стоимость операций.

## Почему GPU-рендеринг быстрый: массовый параллелизм

CPU (central processing unit — центральный процессор) — это несколько мощных ядер, обычно 4-16. Каждое умеет исполнять сложную ветвящуюся логику последовательно и быстро. GPU устроен принципиально иначе: тысячи простых вычислительных ядер. Каждое ядро исполняет **одну и ту же** небольшую программу одновременно над разными данными. Это классическая модель SIMD (одна инструкция, много данных).

| Свойство | CPU | GPU |
|---|---|---|
| Ядер | несколько, обычно 4-16 | тысячи простых |
| Что исполняет ядро | сложную ветвящуюся логику | ту же программу, что и все остальные ядра |
| Как идёт работа | быстро, шаг за шагом | одновременно, над разными данными |

Задача рендеринга ложится на эту модель идеально. Возьмите "посчитать позицию на экране для каждой из миллиона вершин". Или "посчитать цвет каждого из двух миллионов пикселей".

Такие операции независимы друг от друга и идентичны по вычислениям, отличаясь только входными данными. Именно эта независимость и позволяет распараллелить работу на тысячи ядер вместо последовательного перебора на CPU.

**Треугольник — универсальный примитив** GPU-рендеринга, и не случайно. Три точки **всегда** лежат в одной плоскости, в отличие от четырёх и более точек, которые могут не быть компланарны. Поэтому растеризация треугольника — простая и предсказуемая операция, давно доведённая до предела аппаратного ускорения.

На уровне GPU в набор треугольников превращается любая форма. 2D-спрайт в Pixi — это прямоугольник, то есть два треугольника. Сложная 3D-модель в three.js — тысячи треугольников, формирующих поверхность.

## Программируемый конвейер: vertex shader → растеризация → fragment shader

```txt
vertex shader  ->  растеризация  ->  fragment shader

1. Vertex shader (программируемый)
   вход : атрибуты вершины (позиция, UV, ...) + uniform-переменные
   выход: позиция на экране (gl_Position)
   когда: один раз на вершину

2. Растеризация (фиксированная функция, не программируется)
   вход : позиции вершин треугольника на экране
   выход: список "фрагментов" (потенциальных пикселей) внутри
          треугольника, с интерполированными "varying"-значениями

3. Fragment shader (программируемый)
   вход : интерполированные значения на пиксель,
          текстуры, uniform-переменные
   выход: итоговый цвет пикселя (gl_FragColor)
   когда: один раз на пиксель
```

**Vertex shader** запускается один раз на каждую вершину геометрии. Он отвечает на один вопрос: "где эта точка окажется на экране".

**Растеризация** — единственная стадия конвейера, которую нельзя программировать. Аппаратная логика GPU определяет, какие пиксели покрыты треугольником. Для каждого покрытого пикселя она линейно интерполирует "varying"-значения между тремя вершинами: UV (координаты текстуры), цвет вершины и тому подобное.

Именно эта интерполяция и объясняет, почему градиент между тремя разноцветными вершинами треугольника "просто работает" без единой дополнительной строчки кода.

**Fragment shader** запускается один раз на каждый покрытый пиксель ("фрагмент") и отвечает на вопрос "какого цвета этот конкретный пиксель".

## GLSL: минимальный читаемый пример

Шейдеры пишутся на GLSL (OpenGL Shading Language) — C-подобном языке с встроенными векторными типами (`vec2`, `vec3`, `vec4`) и матричными (`mat3`, `mat4`).

```glsl
// Vertex shader — считает позицию на экране и передаёт UV дальше
attribute vec2 position;   // атрибут: своё значение для каждой вершины
attribute vec2 uv;
uniform mat3 transform;     // uniform: одно значение на весь вызов отрисовки
varying vec2 vUv;           // varying: передаётся в fragment shader,
                             // интерполируется растеризацией между вершинами

void main() {
  vUv = uv;
  vec3 transformed = transform * vec3(position, 1.0);
  gl_Position = vec4(transformed.xy, 0.0, 1.0); // обязательная встроенная переменная
}
```

```glsl
// Fragment shader — превращает интерполированный UV в цветовой градиент
precision mediump float; // обязательная директива точности —
                          // mediump достаточно для большинства случаев
                          // и заметно дешевле на мобильных GPU, чем highp

varying vec2 vUv; // те же координаты, что вышли из vertex shader,
                   // но уже интерполированные растеризацией для
                   // текущего пикселя внутри треугольника

void main() {
  // Красный канал растёт слева направо, зелёный — сверху вниз —
  // простейший двумерный градиент, посчитанный на GPU для каждого пикселя
  gl_FragColor = vec4(vUv.x, vUv.y, 0.5, 1.0); // обязательная встроенная переменная
}
```

Ключевая деталь для интервью — чем эти три вещи различаются:

- `varying` — это **мост** между вершинным и фрагментным шейдером. Растеризация выполняет линейную интерполяцию значения между вершинами автоматически.
- `uniform` — единственное значение, одинаковое для всех вершин и пикселей одного вызова отрисовки (draw call): например, общая для всей геометрии матрица трансформации или время анимации.
- `attribute` — данные, уникальные для каждой отдельной вершины: позиция, UV, цвет вершины.

## Данные, попадающие на GPU: буферы, атрибуты, uniform-ы, текстуры

| Понятие | Что это |
|---|---|
| Buffer | Сырой блок памяти на GPU с данными вершин: позиции, UV, нормали. Загружается один раз и переиспользуется многими вызовами отрисовки без повторной передачи данных. |
| Attribute | Описание того, **как** vertex shader читает свой кусок буфера для текущей вершины: какое смещение, какой формат данных. |
| Uniform | Единственное значение на весь вызов отрисовки, одинаковое для всех вершин и пикселей: матрица трансформации, цвет, время. |
| Texture | Изображение, из которого fragment shader читает цвет по UV-координатам через `sampler2D` и вызов `texture2D()`/`texture()`. |

Эта модель данных — не абстракция ради абстракции. Она напрямую объясняет две статьи расходов. Буферы геометрии выгодно создавать один раз и переиспользовать, в отличие от uniform-переменных, которые ожидаемо меняются на каждый вызов отрисовки. А смена текстуры между отрисовками — операция с реальной стоимостью, а не бесплатная деталь.

## Вызов отрисовки: настоящая валюта производительности GPU

**Вызов отрисовки** — единственная команда "нарисуй вот эти вершины вот этой шейдерной программой, вот с этими буферами, uniform-переменными и текстурой".

Дальше идёт ключевой и не всегда очевидный факт. Стоимость вызова отрисовки — это в основном **накладные расходы драйвера**: проверка состояния, синхронизация CPU↔GPU, загрузка изменившихся данных. Это **не** количество треугольников внутри вызова.

Нарисовать 10 000 треугольников одним вызовом почти всегда дешевле, чем нарисовать 100 треугольников в 100 отдельных вызовах. Эти 100 вызовов меняют текстуру, шейдер или режим смешивания между собой, и платить приходится именно за это.

```txt
❌ 100 отдельных вызовов отрисовки (например, 100 спрайтов с разными
   текстурами, рисуемых по одному): 100× накладные расходы драйвера
   на проверку состояния и синхронизацию, независимо от того, что
   суммарная геометрия крошечная

✅ 1 вызов отрисовки с общим "атласом" текстур (статья 05,
   спрайт-атласы) и одним буфером с геометрией всех 100 спрайтов:
   тот же результат, накладных расходов драйвера в 100 раз меньше
```

Именно поэтому важен **батчинг**. Батчинг — это объединение множества объектов в минимальное число вызовов отрисовки. Это центральная тема производительности в обоих движках. В Pixi это batch renderer и то, что его "ломает" (статья 05). В three.js это instancing и слияние геометрий (статья 06).

В большинстве сцен, насыщенных двумерной графикой и элементами интерфейса, реальный лимит производительности — не число треугольников, а число вызовов отрисовки.

## Почему "чистый" WebGL настолько многословен

"Hello triangle" — простейший возможный пример: нарисовать один цветной треугольник. На чистом WebGL он требует шести шагов настройки.

1. Написать GLSL-код вершинного и фрагментного шейдера как строки.
2. Скомпилировать и слинковать их в шейдерную программу, вручную проверив ошибки компиляции.
3. Создать и заполнить буфер геометрии.
4. Вручную описать раскладку атрибутов: смещения и шаги в байтах.
5. Найти локации uniform-переменных по имени и присвоить им значения.
6. И только затем вызвать `drawArrays`/`drawElements`.

Типично это несколько десятков строк низкоуровневой настройки. Ни одна из них не описывает, *что* нарисовать. Все они описывают, как донести эти данные до GPU.

Тот же треугольник в three.js — порядка десятка строк, потому что вся эта настройка инкапсулирована внутри `Mesh`/`Geometry`/`Material` (статья 06). Это прямое объяснение того, зачем вообще существуют движки поверх WebGL. Не "для удобства": без них объём необходимого шаблонного кода для содержательной сцены становится неуправляемым.

## WebGL1 против WebGL2 — коротко

WebGL1 базируется на OpenGL ES 2.0 (ES — Embedded Systems, встраиваемые системы). WebGL2 базируется на OpenGL ES 3.0 и добавляет сверху пять вещей.

| Возможность | WebGL1 | WebGL2 |
|---|---|---|
| Основа | OpenGL ES 2.0 | OpenGL ES 3.0 |
| Instancing | только через расширение, которое могло отсутствовать | нативный |
| Multiple render targets | нет | есть |
| 3D-текстуры | нет | есть |
| Uniform buffer objects | нет | есть |
| Версия GLSL ES | старее | 3.00, с дополнительными возможностями языка |

На практике современные движки по умолчанию целятся в WebGL2, а на WebGL1 откатываются там, где это требуется. Поддержка WebGL2 в браузерах уже практически повсеместна, поэтому для нового проекта редко есть причина специально ограничивать себя возможностями WebGL1.

## WebGPU: что меняется, и текущий статус

WebGPU — это более новый графический API браузера, приходящий на смену модели WebGL. Это не "WebGL 3", а именно новый API, спроектированный по образцу современных низкоуровневых графических API: Vulkan, Metal, Direct3D 12.

Ключевое отличие — в том, где происходит проверка состояния. WebGL исторически проектировался с большим количеством неявной, скрытой от разработчика проверки, которую драйвер делает на каждый вызов. Это удобно, но дорого по нагрузке на CPU.

WebGPU переносит значительную часть этой работы на этап явной, заранее выполненной настройки. Объекты конвейера рендеринга создаются целиком и заранее, а не накапливаются состоянием от вызова к вызову. Это снижает нагрузку на CPU в каждом кадре и позволяет отдавать GPU заметно больше вызовов отрисовки при той же цене.

Отдельно WebGPU даёт полноценные **compute shaders** — программы, исполняемые на GPU для вычислений общего назначения, а не только для рендеринга. Сюда попадают физика, машинное обучение и обработка данных. В WebGL такого практически не было.

| Аспект | WebGL | WebGPU |
|---|---|---|
| Проверка состояния | неявная, драйвером на каждый вызов | явная, один раз при создании объекта конвейера |
| Нагрузка на CPU в кадре | выше | ниже, поэтому в тот же бюджет влезает больше вызовов |
| Compute shaders | практически не было | полноценные, для вычислений общего назначения |

Статус поддержки на момент написания: WebGPU уже доступен в части основных браузеров, но не универсально везде. Прежде чем закладывать WebGPU как единственный путь в продакшен-проекте, явно проверьте актуальную поддержку в целевых браузерах и устройствах. Это область, которая меняется быстро, и полагаться на память вместо проверки здесь не стоит.

## Потеря контекста: то, о чём все забывают до первого реального инцидента

GPU-контекст может быть потерян в любой момент по причинам, полностью вне контроля вашего кода:

- Сброс или сбой драйвера видеокарты.
- ОС (операционная система) отбирает GPU-ресурсы под давлением памяти.
- Другая вкладка монополизировала GPU.
- Мобильное приложение свернули, а потом развернули.

Продакшен-код **обязан** обрабатывать это явно:

```javascript
canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault(); // без этого браузер вообще не попытается
                          // восстановить контекст
  cancelAnimationFrame(animationFrameId); // остановить цикл рендеринга —
                                            // контекст сейчас недействителен
  console.warn('WebGL context lost — waiting for restoration');
});

canvas.addEventListener('webglcontextrestored', () => {
  // критично: все GPU-ресурсы (буферы, текстуры, шейдерные программы)
  // были уничтожены вместе с контекстом — их нужно пересоздать
  // полностью заново, а не просто "продолжить" рендеринг
  initShaders();
  initBuffers();
  reloadTextures();
  startRenderLoop();
});
```

Без `event.preventDefault()` в обработчике `webglcontextlost` браузер даже не попытается восстановить контекст. Сцена останется чёрным экраном навсегда.

Без полной пересборки ресурсов в `webglcontextrestored` попытки рисовать буферами и текстурами со старыми, теперь недействительными идентификаторами будут тихо проваливаться или бросать ошибки. Это особенно частый сценарий на мобильных устройствах с ограниченной GPU-памятью, и он реже всего тестируется до первого продакшен-инцидента.

## Типичные ошибки на интервью

- **Считать, что "больше треугольников = медленнее"** — в большинстве сцен реальная стоимость определяется **количеством вызовов отрисовки**, а не сырым числом треугольников. Платите вы за накладные расходы драйвера на каждый вызов. Отрисовать миллион треугольников одним вызовом часто дешевле сотни треугольников в сотне вызовов.

- **Путать vertex и fragment shader** — не суметь объяснить, который из них когда работает. Vertex shader выполняется один раз **на вершину** и решает "где". Fragment shader выполняется один раз **на пиксель** и решает "какого цвета".

- **Не понимать разницу attribute/uniform/varying** — attribute это данные, уникальные для каждой вершины. Uniform — одно значение на весь вызов отрисовки. Varying — интерполируемый растеризацией мост между вершинным и фрагментным шейдером.

- **Не понимать, почему именно треугольники** — не связывать выбор треугольника как примитива с одним фактом. Три точки всегда компланарны, то есть лежат в одной плоскости, в отличие от произвольного многоугольника.

- **Не знать про батчинг как решение проблемы вызовов отрисовки** — предлагать "просто уменьшить число полигонов". Реальная же проблема — количество отдельных вызовов рисования из-за смены текстур и шейдеров между объектами.

- **Не знать про потерю WebGL-контекста** — не иметь ответа на вопрос, что произойдёт с вашим WebGL-приложением при сбросе графического драйвера у пользователя. Второй пробел — не знать про `webglcontextlost`/`webglcontextrestored` и необходимость полной пересборки GPU-ресурсов.
