# WebGL и основы GPU

## Зачем это знать, если почти всегда используется Pixi или three.js

Ответ на вопрос "почему добавление ещё одного фильтра в Pixi настолько замедлило сцену" или "почему смена текстуры между спрайтами дороже, чем кажется" требует понимания того, ЧТО происходит под капотом у любого GPU-движка — Pixi (статья 05) и three.js (статья 06) не изобретают собственную модель рендеринга, они лишь удобно оборачивают ровно то, что описано в этой статье. Без этого фундамента работа с обеими библиотеками сводится к копированию примеров из документации "потому что так работает"; с ним — к инженерным решениям на основе понимания реальной стоимости операций.

## Почему GPU-рендеринг быстрый: массовый параллелизм

CPU — несколько (обычно 4-16) мощных ядер, каждое умеет исполнять сложную ветвящуюся логику последовательно и быстро. GPU устроен принципиально иначе: тысячи простых вычислительных ядер, каждое из которых исполняет ОДНУ И ТУ ЖЕ небольшую программу одновременно над разными данными — классическая модель SIMD (одна инструкция, много данных). Это идеально ложится на задачу рендеринга: "посчитать позицию на экране для КАЖДОЙ из миллиона вершин" или "посчитать цвет КАЖДОГО из двух миллионов пикселей" — операции независимы друг от друга и идентичны по вычислениям, отличаясь только входными данными. Именно эта независимость и позволяет распараллелить работу на тысячи ядер вместо последовательного перебора на CPU.

**Треугольник — универсальный примитив** GPU-рендеринга не случайно: три точки ВСЕГДА лежат в одной плоскости (в отличие от четырёх и более точек, которые могут не быть компланарны), поэтому растеризация треугольника — простая, предсказуемая, давно доведённая до предела аппаратного ускорения операция. Любая форма — от 2D-спрайта в Pixi (прямоугольник = два треугольника) до сложной 3D-модели в three.js (тысячи треугольников, формирующих поверхность) — на уровне GPU превращается именно в набор треугольников.

## Программируемый конвейер: vertex shader → растеризация → fragment shader

```txt
Vertex Shader                 Растеризация              Fragment Shader
(программируемый)             (фиксированная функция,    (программируемый)
                                НЕ программируется)

Вход: атрибуты вершины        Вход: позиции вершин        Вход: интерполированные
  (позиция, UV, ...)            треугольника на экране       значения на пиксель +
  + uniform-переменные                                       текстуры + uniform
Выход: позиция на экране       Выход: список "фрагментов"   Выход: итоговый цвет
  (gl_Position)                 (потенциальных пикселей)      пикселя (gl_FragColor)
  ОДИН РАЗ НА ВЕРШИНУ            внутри треугольника,          ОДИН РАЗ НА ПИКСЕЛЬ
                                 с интерполированными
                                 "varying"-значениями
```

**Vertex shader** запускается один раз на каждую вершину геометрии и отвечает на вопрос "где эта точка окажется на экране". **Растеризация** — единственная НЕпрограммируемая стадия конвейера: аппаратная логика GPU определяет, какие пиксели покрыты треугольником, и линейно интерполирует любые "varying"-значения (UV-координаты, цвет вершины и т.п.) между тремя вершинами для каждого покрытого пикселя — именно поэтому градиент между тремя разноцветными вершинами треугольника "просто работает" без единой дополнительной строчки кода. **Fragment shader** запускается один раз на каждый покрытый пиксель ("фрагмент") и отвечает на вопрос "какого цвета этот конкретный пиксель".

## GLSL: минимальный читаемый пример

Шейдеры пишутся на GLSL (OpenGL Shading Language) — C-подобном языке с встроенными векторными типами (`vec2`, `vec3`, `vec4`) и матричными (`mat3`, `mat4`).

```glsl
// Vertex shader — считает позицию на экране и передаёт UV дальше
attribute vec2 position;   // атрибут: своё значение для КАЖДОЙ вершины
attribute vec2 uv;
uniform mat3 transform;     // uniform: ОДНО значение на весь draw call
varying vec2 vUv;           // varying: передаётся в fragment shader,
                             // интерполируется растеризацией между вершинами

void main() {
  vUv = uv;
  vec3 transformed = transform * vec3(position, 1.0);
  gl_Position = vec4(transformed.xy, 0.0, 1.0); // обязательная встроенная переменная
}
```

```glsl
// Fragment shader — превращает интерполированный UV в цветовой градиент
precision mediump float; // обязательная директива точности —
                          // mediump достаточно для большинства случаев
                          // и заметно дешевле на мобильных GPU, чем highp

varying vec2 vUv; // те же координаты, что вышли из vertex shader,
                   // но уже интерполированные растеризацией для
                   // ТЕКУЩЕГО пикселя внутри треугольника

void main() {
  // Красный канал растёт слева направо, зелёный — сверху вниз —
  // простейший двумерный градиент, посчитанный на GPU для каждого пикселя
  gl_FragColor = vec4(vUv.x, vUv.y, 0.5, 1.0); // обязательная встроенная переменная
}
```

Ключевая деталь для интервью: `varying` — это МОСТ между вершинным и фрагментным шейдером, где растеризация выполняет линейную интерполяцию значения между вершинами автоматически; `uniform` — единственное значение, одинаковое для ВСЕХ вершин/пикселей одного draw call (например, общая для всей геометрии матрица трансформации или время анимации); `attribute` — данные, уникальные для каждой отдельной вершины (позиция, UV, цвет вершины).

## Данные, попадающие на GPU: буферы, атрибуты, uniform-ы, текстуры

```txt
Buffer     — сырой блок памяти НА GPU с данными вершин (позиции, UV,
              нормали...), загружается один раз, может переиспользоваться
              многими draw call'ами без повторной передачи данных
Attribute  — то, КАК vertex shader читает свой кусок буфера для
              текущей вершины (какое смещение, какой формат данных)
Uniform    — единственное значение на весь draw call, одинаковое для
              всех вершин/пикселей (матрица трансформации, цвет, время)
Texture    — изображение, из которого fragment shader читает цвет
              по UV-координатам через sampler2D + texture2D()/texture()
```

Эта модель данных — не абстракция ради абстракции: она напрямую объясняет, почему буферы геометрии выгодно создавать один раз и переиспользовать (в отличие от uniform-ов, которые ожидаемо меняются на каждый draw call), и почему смена текстуры между отрисовками — операция с реальной стоимостью, а не бесплатная деталь.

## Draw call: настоящая валюта производительности GPU

**Draw call** — единственная команда "нарисуй вот эти вершины вот этой шейдерной программой, вот с этими буферами, uniform-ами и текстурой". Ключевой, не всегда очевидный факт: стоимость draw call'а — это в основном **оверхед драйвера** (проверка состояния, синхронизация CPU↔GPU, загрузка изменившихся данных), а НЕ количество треугольников внутри него. Нарисовать 10 000 треугольников ОДНИМ draw call'ом почти всегда дешевле, чем нарисовать 100 треугольников в 100 отдельных draw call'ах со сменой текстуры/шейдера/blend-режима между ними.

```txt
❌ 100 отдельных draw call'ов (например, 100 спрайтов с разными
   текстурами, рисуемых по одному): 100× оверхед драйвера на
   валидацию состояния и синхронизацию, независимо от того, что
   суммарная геометрия крошечная

✅ 1 draw call с общим "атласом" текстур (статья 05, спрайт-атласы)
   и одним буфером, содержащим геометрию всех 100 спрайтов:
   тот же визуальный результат, оверхед драйвера — в 100 раз меньше
```

Именно поэтому **батчинг** (объединение множества объектов в минимальное число draw call'ов) — центральная тема производительности и в Pixi (статья 05, batch renderer и что его "ломает"), и в three.js (статья 06, instancing/merging geometries): реальный лимит производительности в большинстве 2D/UI-насыщенных сцен — не число треугольников, а число draw call'ов.

## Почему "чистый" WebGL настолько многословен

"Hello triangle" — простейший возможный пример (нарисовать один цветной треугольник) — на чистом WebGL требует: написать GLSL-код вершинного и фрагментного шейдера как строки, скомпилировать и слинковать их в шейдерную программу с ручной проверкой ошибок компиляции, создать и заполнить буфер геометрии, вручную описать layout атрибутов (смещения и шаги в байтах), найти локации uniform-переменных по имени и присвоить им значения, и только затем вызвать `drawArrays`/`drawElements`. Типично это несколько десятков строк низкоуровневой настройки — ни одна из которых не описывает непосредственно "что нарисовать", только КАК донести эти данные до GPU. Тот же треугольник в three.js — порядка десятка строк, потому что вся эта настройка инкапсулирована внутри `Mesh`/`Geometry`/`Material` (статья 06). Это прямое объяснение того, зачем вообще существуют движки поверх WebGL — не "для удобства", а потому что объём необходимого boilerplate-кода для содержательной сцены иначе становится неуправляемым.

## WebGL1 vs WebGL2 — в двух словах

WebGL1 базируется на OpenGL ES 2.0, WebGL2 — на OpenGL ES 3.0, добавляя: нативную поддержку instancing (без расширений, которые могли отсутствовать в WebGL1), multiple render targets, 3D-текстуры, uniform buffer objects, более новую версию GLSL ES (3.00) с дополнительными возможностями языка. На практике: современные движки по умолчанию целятся в WebGL2 с фолбэком на WebGL1 там, где это требуется; поддержка WebGL2 в браузерах уже практически повсеместна, поэтому для нового проекта редко есть причина специально ограничивать себя возможностями WebGL1.

## WebGPU: что меняется, и текущий статус

WebGPU — не "WebGL 3", а новый API, спроектированный по образцу современных низкоуровневых графических API (Vulkan, Metal, Direct3D 12). Ключевое отличие: WebGL исторически проектировался с большим количеством НЕЯВНОЙ, скрытой от разработчика проверки состояния драйвером на каждый вызов — это удобно, но дорого по CPU-накладным расходам. WebGPU переносит значительную часть этой работы на этап ЯВНОЙ, заранее выполненной настройки (создание объектов конвейера рендеринга целиком, заранее, а не накопление состояния вызов за вызовом), что снижает CPU-оверхед на кадр и позволяет отдавать GPU заметно больше draw call'ов при той же нагрузке на CPU. Отдельно WebGPU даёт полноценные **compute shaders** — программы, исполняемые на GPU для ОБЩИХ вычислений (не только рендеринга: физика, машинное обучение, обработка данных), чего в WebGL практически не было.

Статус поддержки на момент написания — WebGPU уже доступен в части основных браузеров, но не универсально везде; перед тем как закладывать WebGPU как единственный путь в продакшен-проекте, стоит явно проверить актуальную поддержку в целевых браузерах/устройствах — это область, которая меняется быстро, и полагаться на память вместо проверки здесь не стоит.

## Потеря контекста: то, о чём все забывают до первого реального инцидента

GPU-контекст может быть потерян в любой момент по причинам, полностью вне контроля вашего кода: сброс/крэш драйвера видеокарты, ОС отбирает GPU-ресурсы под давлением памяти, другая вкладка монополизировала GPU, сворачивание/разворачивание мобильного приложения. Production-код ОБЯЗАН обрабатывать это явно:

```javascript
canvas.addEventListener('webglcontextlost', (event) => {
  event.preventDefault(); // БЕЗ этого браузер не попытается восстановить контекст вообще
  cancelAnimationFrame(animationFrameId); // остановить цикл рендеринга —
                                            // контекст сейчас недействителен
  console.warn('WebGL context lost — waiting for restoration');
});

canvas.addEventListener('webglcontextrestored', () => {
  // КРИТИЧНО: все GPU-ресурсы (буферы, текстуры, шейдерные программы)
  // были уничтожены вместе с контекстом — их нужно пересоздать
  // ПОЛНОСТЬЮ заново, а не просто "продолжить" рендеринг
  initShaders();
  initBuffers();
  reloadTextures();
  startRenderLoop();
});
```

Без `event.preventDefault()` в обработчике `webglcontextlost` браузер даже не попытается восстановить контекст — сцена останется чёрным экраном навсегда. Без полной пересборки ресурсов в `webglcontextrestored` попытки рисовать буферами/текстурами со старыми (теперь недействительными) идентификаторами будут тихо проваливаться или бросать ошибки. Это особенно частый сценарий на мобильных устройствах с ограниченной GPU-памятью — и то, что реже всего тестируется до первого продакшен-инцидента.

## Типичные ошибки на интервью

- **Считать, что "больше треугольников = медленнее"** — не знать, что реальная стоимость в большинстве сцен определяется КОЛИЧЕСТВОМ DRAW CALL'ОВ (оверхед драйвера на вызов), а не сырым числом треугольников — отрисовать миллион треугольников одним вызовом часто дешевле сотни треугольников в сотне вызовов.

- **Путать vertex и fragment shader** — не суметь объяснить, что vertex shader выполняется один раз НА ВЕРШИНУ и решает "где", а fragment shader — один раз НА ПИКСЕЛЬ и решает "какого цвета".

- **Не понимать разницу attribute/uniform/varying** — не знать, что attribute — данные, уникальные для каждой вершины, uniform — одно значение на весь draw call, varying — интерполируемый растеризацией мост между вершинным и фрагментным шейдером.

- **Не понимать, почему именно треугольники** — не связывать выбор треугольника как примитива с фактом, что три точки всегда компланарны (лежат в одной плоскости), в отличие от произвольного многоугольника.

- **Не знать про батчинг как решение draw-call-проблемы** — предлагать "просто уменьшить число полигонов" там, где реальная проблема — количество отдельных вызовов рисования из-за смены текстур/шейдеров между объектами.

- **Не знать про потерю WebGL-контекста** — не иметь ответа на вопрос "что произойдёт с вашим WebGL-приложением, если у пользователя произойдёт сброс графического драйвера", и не знать про `webglcontextlost`/`webglcontextrestored` и необходимость полной пересборки GPU-ресурсов.
