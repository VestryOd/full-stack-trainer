# Стилизация и изоляция

## Почему утечка глобального CSS — самый частый реальный баг микрофронтендов

У CSS по умолчанию нет никакой инкапсуляции. Допустим, команда catalog пишет `.button { padding: 8px; }`. Это правило перезапишет визуально идентичный `.button` в DOM (document object model — живое дерево элементов страницы) команды checkout.

Весь отрендеренный код оказывается в одном документе и делит один глобальный CSSOM (CSS object model — такое же дерево стилевых правил). Насколько независимо каждая команда собирала свой код, значения не имеет.

Это хуже, чем конфликт shared-зависимостей из статьи [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md). Там хотя бы иногда бросается ошибка (`Invalid hook call`), и её можно найти по стектрейсу.

Конфликт CSS просто молча выглядит неправильно: бейдж не того цвета, отступ сбит. Дойти до того, чей именно стилевой файл виноват, гораздо труднее — особенно когда команды физически не видят код друг друга.

## Решение 1 — CSS Modules

Механика: на этапе сборки имена классов хешируются (`.button` → `.button_a3f9d1`) и становятся локально уникальными в рамках файла. Коллизия имён практически исключена, потому что хеш почти глобально уникален.

```css
/* CheckoutApp.module.css */
.button { padding: 8px 16px; }
```

```tsx
import styles from './CheckoutApp.module.css';
<button className={styles.button}>Оплатить</button>
```

**Плюсы:** работает с обычным CSS-тулингом, нулевая цена в рантайме, поддерживается большинством сборщиков из коробки.

**Минусы:** гарантия покрывает только **имена классов**. Высокоспецифичный глобальный селектор в другом месте страницы всё равно применится. Пример — глобальный тег-селектор `button { ... }` из чужого reset-стиля. И CSS Modules помогают лишь тогда, когда их последовательно применяет **каждая** команда. Соседний remote, отказавшийся от них, по-прежнему может сломать вам вёрстку.

## Решение 2 — Shadow DOM

Настоящая, браузерная изоляция DOM и CSS — не конвенция сборки, а реальная граница. Custom Element оборачивает содержимое в shadow root; стили внутри shadow root не просачиваются наружу, а внешние стили (в основном) не просачиваются внутрь.

```ts
class CheckoutWidget extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: 'open' });
    shadow.innerHTML = `
      <style>.button { padding: 8px 16px; }</style>
      <button class="button">Оплатить</button>
    `;
  }
}
customElements.define('checkout-widget', CheckoutWidget);
```

**Реальные компромиссы, а не только плюсы:**

- **Ретаргетинг событий (event retargeting).** Событие, отправленное внутри shadow DOM, снаружи видно с `target`, переуказанным на shadow host. Это не тот элемент, который событие вызвал. Так ломается наивный код делегирования событий, а вместе с ним аналитические скрипты, читающие `event.target` напрямую.
- **Совместимость со сторонними библиотеками.** Многие библиотеки рассчитывают, что обратятся к DOM глобально через `document.querySelector`. Другие внедряют глобальные стили и порталы: React-порталы, модальные библиотеки, наборы компонентов, скрипты тег-менеджеров. Такие библиотеки часто молча не находят элементы внутри shadow root. Это отдельное поддерево DOM, и обычный глобальный `document.querySelector` до него не дотягивается без явного «прокалывания» границы.
- **CSS custom properties (переменные) пересекают границу shadow DOM по умолчанию** — наследование через них продолжает работать. Это удобно: общие токены дизайна (цвета, отступы) доходят и до изолированного shadow-контента. Часто ошибочно считают, что shadow DOM блокирует вообще всё. Не блокирует — только обычные стилевые правила.

## Решение 3 — скоуп-изолированный CSS-in-JS

Библиотеки вроде styled-components или Emotion генерируют уникальные имена классов **в рантайме** и внедряют `<style>`-теги, скоупленные на компонент, прямо в `<head>`. Та же идея, что у CSS Modules, только резолвится не на сборке, а во время выполнения.

```tsx
const Button = styled.button`
  padding: 8px 16px;
`;
```

**Плюсы:** стили лежат рядом с компонентом, могут быть динамическими на основе props, та же гарантия от коллизий (хешированные имена классов), что и у CSS Modules.

**Минусы:** стили стоят времени в рантайме, потому что вычисляются и внедряются на каждый рендер. Есть и ловушка, специфичная для микрофронтендов, и у неё несколько лиц.

Допустим, два независимо собранных ремоута упаковали **каждый свою копию** styled-components вместо одного общего singleton через `shared`-конфигурацию Module Federation. Тогда ломается сразу несколько вещей:

- Копии внедряют конфликтующие глобальные reset-стили.
- Они работают на несовместимых мажорных версиях библиотеки с разным поведением SSR (server-side rendering — рендеринг на сервере) и гидратации.
- Порядок `<style>`-тегов, которые они внедряют независимо друг от друга, не определён.

Последний пункт кусается сильнее всего. Позже внедрённый тег может выиграть по специфичности вне зависимости от того, какого порядка ждал разработчик. Симптом — случайный, «плавающий» визуальный баг, привязанный к порядку и таймингу загрузки, а не к логической ошибке в чьём-то коде.

Про `shared`-конфигурацию подробно рассказывает статья [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md).

## Решение 4 — дисциплина именования (BEM-подобный префиксинг)

Прагматичный вариант по умолчанию, не требующий никакого тулинга: префиксовать все имена классов пространством имён, уникальным для каждого микрофронтенда. BEM (block, element, modifier — блок, элемент, модификатор) — та самая схема именования, у которой приём позаимствован.

```css
/* checkout-mfe */
.checkout__button--primary { padding: 8px 16px; }

/* catalog-mfe */
.catalog__button--primary { padding: 8px 16px; }
```

**Плюсы:** работает где угодно, не требует тулинга, легко читается в devtools, годится для legacy-кода и постепенной миграции.

**Минусы:** всё держится на дисциплине и код-ревью. Технически префикс ничем не принуждается. Новый разработчик, не знакомый с конвенцией, легко напишет глобальный селектор без префикса, и тот молча столкнётся с чужим.

Именно поэтому этот вариант называют прагматичным дефолтом. Это низший общий знаменатель, и он работает тогда, когда невозможно разом перевести все команды на один CSS-тулинг.

## Общая дизайн-система как версионированный пакет — и проблема рассинхрона версий

В реальном продакшене общие строительные блоки — кнопки, инпуты, модалки, типографика — не оставляют каждой команде. Их выносят в общий пакет дизайн-системы, например `@company/design-system`. Пакет версионируется и публикуется как обычный npm-пакет. Его же можно раздавать как singleton через `shared`-конфигурацию Module Federation.

**Проблема рассинхрона версий.** Допустим, catalog-mfe закреплён на `@company/design-system@2.1.0`, а checkout-mfe — на `@company/design-system@3.0.0`. Этот мажорный скачок несёт ломающие визуальные изменения: новая шкала отступов, другие токены `border-radius`.

Теперь скомпонуем обе части рядом на одной странице — например, модалка чекаута открывается поверх страницы каталога. Пользователь буквально видит **два визуально разных** стиля кнопок на одном экране, и оба претендуют быть одной и той же дизайн-системой.

Это CSS-двойник бага «две копии React» из статьи [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md). Только здесь не бросается вообще никакой ошибки. Страница просто выглядит несогласованно, и это в некотором смысле хуже: проблема молчит, пока на экран не посмотрит живой человек.

**Как снижать риск:** та же организационная дисциплина, что и для shared JS-зависимостей в статье [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md). Относитесь к мажорной версии дизайн-системы как к требованию singleton во всех потребляющих микрофронтендах.

Принуждает к этому проверка в CI (continuous integration — непрерывная интеграция), сравнивающая версии по всем репозиториям. Добавьте явное окно апгрейда и процесс раскатки вместо того, чтобы каждая команда обновляла ломающую версию по собственному расписанию.

## Сводная таблица подходов

| Подход | Механизм изоляции | Цена в рантайме | Совместимость со сторонними библиотеками | Принуждение к соблюдению |
|---|---|---|---|---|
| CSS Modules | Хеш имён на сборке | Нет | Нормальная | Только конвенция сборки |
| Shadow DOM | Реальная граница DOM | Небольшая (парсинг shadow root) | Плохая — многие библиотеки ждут глобальный `document` | Принудительно браузером |
| CSS-in-JS | Хеш и внедрение `<style>` в рантайме | Есть (вычисление стилей) | Нормальная, но порядок тегов между ремоутами не определён | Конвенция сборки и рантайма |
| BEM-префиксинг | Соглашение об именовании | Нет | Нормальная | Никакого — чистая дисциплина |

## Типичные ошибки на интервью

- **«Один из этих подходов решает проблему изоляции стилей полностью»** — ни один не решает. Зрелые организации комбинируют все сразу. BEM-префиксинг — базовая дисциплина, общий пакет дизайн-системы закрывает типовые элементы, а CSS Modules или CSS-in-JS работают внутри уникальных компонентов каждого микрофронтенда.

- **«Shadow DOM строго превосходит остальные подходы, потому что это единственная настоящая изоляция»** — изоляция DOM здесь действительно настоящая. Но за неё платят ретаргетингом событий и библиотеками, которые ждут глобального доступа к DOM и больше его не находят. Это осознанный компромисс, а не бесплатное превосходство.

- **«CSS Modules защищают от всей утечки стилей»** — они хешируют только имена классов из ваших собственных модулей. Глобальный тег-селектор из чужого CSS всё ещё перезапишет ваши стили, и высокоспецифичный reset-стиль тоже.

- **«Общая дизайн-система решает проблему рассинхрона версий автоматически, раз она общая»** — сама по себе — нет. Ей нужна та же дисциплина версионирования, что и shared JS-зависимостям из статьи [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md). Без проверки версий в CI по всем репозиториям рассинхрон мажорных версий даёт молчаливую визуальную несогласованность, а не брошенную ошибку.

- **«CSS-переменные (custom properties) блокируются границей Shadow DOM так же, как обычные стили»** — нет. Они пересекают эту границу по умолчанию, через наследование. Именно поэтому они — удобный способ передать общие токены дизайна в изолированный контент.
