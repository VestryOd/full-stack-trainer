# Стилизация и изоляция

## Почему утечка глобального CSS — самый частый реальный баг в MFE

У CSS по умолчанию нет никакой инкапсуляции. `.button { padding: 8px; }`, написанный командой catalog, перезапишет визуально идентичный `.button` из DOM команды checkout — потому что весь отрендеренный DOM в итоге оказывается в одном документе, разделяя один глобальный CSSOM, вне зависимости от того, насколько независимо каждая команда собирала свой код.

Это отличается от конфликта shared-зависимостей из статьи 03 в худшую сторону: там хотя бы иногда бросается ошибка (`Invalid hook call`), которую можно найти по стектрейсу. Конфликт CSS просто молча выглядит неправильно — бейдж не того цвета, отступ сбит — и это гораздо труднее проследить до того, чей именно стилевой файл виноват, особенно когда команды физически не видят код друг друга.

## Решение 1 — CSS Modules

Механика: на этапе сборки имена классов хешируются (`.button` → `.button_a3f9d1`), становясь локально уникальными в рамках файла — коллизия имён практически исключена, потому что хеш (почти) глобально уникален.

```css
/* CheckoutApp.module.css */
.button { padding: 8px 16px; }
```

```tsx
import styles from './CheckoutApp.module.css';
<button className={styles.button}>Оплатить</button>
```

**Плюсы:** работает с обычным CSS-тулингом, нулевая цена в рантайме, поддерживается большинством сборщиков из коробки.

**Минусы:** гарантирует уникальность только **имён классов** — не защищает от высокоспецифичных глобальных селекторов в другом месте страницы (например, глобальный тег-селектор `button { ... }` из чужого reset-стиля всё равно применится). И требует, чтобы **каждая** команда реально и последовательно использовала CSS Modules — само по себе это никак не защищает от CSS соседнего remote'а, который решил их не использовать.

## Решение 2 — Shadow DOM

Настоящая, браузерная изоляция DOM и CSS — не конвенция сборки, а реальная граница. Custom Element оборачивает содержимое в shadow root; стили внутри shadow root не просачиваются наружу, а внешние стили (в основном) не просачиваются внутрь.

```ts
class CheckoutWidget extends HTMLElement {
  connectedCallback() {
    const shadow = this.attachShadow({ mode: 'open' });
    shadow.innerHTML = `
      <style>.button { padding: 8px 16px; }</style>
      <button class="button">Оплатить</button>
    `;
  }
}
customElements.define('checkout-widget', CheckoutWidget);
```

**Реальные трейд-оффы, а не только плюсы:**

- **Ретаргетинг событий (event retargeting).** События, диспатчнутые внутри shadow DOM, при наблюдении снаружи получают `target`, переуказанный на shadow host, а не на реальный элемент, который их вызвал. Это ломает наивный код делегирования событий и некоторые аналитические/трекинговые скрипты, читающие `event.target` напрямую.
- **Совместимость со сторонними библиотеками.** Многие библиотеки исходят из того, что могут глобально обратиться к DOM (`document.querySelector`) или внедрить глобальные стили/порталы (React-порталы, модальные библиотеки, некоторые UI-киты, скрипты тег-менеджеров). Такие библиотеки часто молча не находят элементы внутри shadow root, потому что он — отдельное поддерево DOM, недостижимое обычным глобальным `document.querySelector` без явного «прокалывания» границы.
- **CSS custom properties (переменные) пересекают границу shadow DOM по умолчанию** — наследование через них продолжает работать. Это удобно для передачи общих design-токенов (цвета, отступы) даже в изолированный shadow-контент, но часто ошибочно предполагается, что shadow DOM блокирует вообще всё — не блокирует, только «обычные» стилевые правила.

## Решение 3 — скоуп-изолированный CSS-in-JS

Библиотеки вроде styled-components или Emotion генерируют уникальные имена классов **в рантайме** и внедряют `<style>`-теги, скоупленные на компонент, прямо в `<head>`. Та же идея, что у CSS Modules, только резолвится не на сборке, а во время выполнения.

```tsx
const Button = styled.button`
  padding: 8px 16px;
`;
```

**Плюсы:** стили лежат рядом с компонентом, могут быть динамическими на основе props, та же гарантия от коллизий (хешированные имена классов), что и у CSS Modules.

**Минусы:** рантайм-цена (вычисление и внедрение стилей на каждый рендер), и специфичная для MFE ловушка: если два независимо собранных remote'а используют styled-components как **отдельные** упакованные копии (а не общий singleton через shared-конфигурацию Module Federation — статья 03), они могут внедрять конфликтующие глобальные reset-стили или — тоньше — использовать несовместимые между собой мажорные версии библиотеки с разным поведением SSR/гидратации. Порядок `<style>`-тегов, внедрённых независимо разными remote'ами, по сути не определён — позже внедрённый тег может выиграть по специфичности вне зависимости от порядка, ожидаемого разработчиком, что выглядит как случайный, «плавающий» визуальный баг, привязанный к порядку/таймингу загрузки, а не к логической ошибке в коде какой-либо из команд.

## Решение 4 — дисциплина именования (BEM-подобный префиксинг)

Прагматичный вариант по умолчанию, не требующий никакого тулинга: префиксовать все имена классов уникальным для каждого MFE неймспейсом.

```css
/* checkout-mfe */
.checkout__button--primary { padding: 8px 16px; }

/* catalog-mfe */
.catalog__button--primary { padding: 8px 16px; }
```

**Плюсы:** работает где угодно, не требует тулинга, легко читается в devtools, годится для legacy-кода и постепенной миграции.

**Минусы:** целиком держится на дисциплине и код-ревью — ничто технически не принуждает к префиксу, и новому разработчику, не знакомому с конвенцией, ничего не стоит случайно написать неймспейс-незащищённый глобальный селектор, который молча коллизирует с чужим.

Именно поэтому этот вариант называют «прагматичным дефолтом» — это низший общий знаменатель, работающий тогда, когда невозможно заставить все команды перейти на один и тот же CSS-тулинг одновременно.

## Общая дизайн-система как версионированный пакет — и проблема рассинхрона версий

Реальная продакшн-практика: чтобы вообще не иметь дела с перечисленными выше проблемами для общих строительных блоков (кнопки, инпуты, модалки, типографика), их выносят в общий пакет дизайн-системы, например `@company/design-system`, версионируемый и публикуемый как обычный npm-пакет (или разделяемый через `shared`-конфигурацию Module Federation как singleton — см. статью 03).

**Проблема рассинхрона версий:** если catalog-mfe закреплён на `@company/design-system@2.1.0`, а checkout-mfe — на `@company/design-system@3.0.0` (мажорная версия с ломающими визуальными изменениями — новая шкала отступов, другие токены border-radius), и обе части композируются рядом на одной странице (например, модалка чекаута открывается поверх страницы каталога), пользователь буквально видит **два визуально разных** стиля кнопок, оба претендующих быть одной и той же дизайн-системой, на одном экране.

Это ровно CSS-эквивалент бага «две копии React» из статьи 03 — только здесь не бросается никакая ошибка; всё просто выглядит визуально несогласованно, что в некотором смысле хуже — проблема молчаливая и обнаруживается только тогда, когда живой человек смотрит на экран.

**Как снижать риск:** та же организационная дисциплина, что и для shared JS-зависимостей в статье 03— относиться к мажорной версии дизайн-системы как к требованию singleton, соблюдаемому во всех потребляющих MFE (CI-проверка версий по всем репозиториям), с явным окном апгрейда и процессом раскатки, а не разрешать каждой команде обновлять ломающие версии по собственному расписанию.

## Типичные ошибки на интервью

- **«Один из этих подходов решает проблему изоляции стилей полностью»** — на практике зрелые организации комбинируют: BEM-префиксинг как базовую дисциплину, общий пакет дизайн-системы для типовых элементов, и CSS Modules/CSS-in-JS внутри уникальных компонентов каждого MFE.

- **«Shadow DOM строго превосходит остальные подходы, потому что это единственная настоящая изоляция»** — реальная изоляция DOM — да, но за неё платят ретаргетингом событий и несовместимостью с библиотеками, которые ожидают глобального доступа к DOM. Это осознанный трейд-офф, а не бесплатное превосходство.

- **«CSS Modules защищают от всей утечки стилей»** — они хешируют только имена классов из ваших собственных модулей; глобальный тег-селектор или высокоспецифичный reset-стиль из чужого CSS всё ещё способен перезаписать ваши стили.

- **«Общая дизайн-система решает проблему рассинхрона версий автоматически, раз она общая»** — сама по себе — нет. Дизайн-система нуждается в той же дисциплине версионирования, что и shared JS-зависимости из статьи 03: без CI-проверки версий по всем репозиториям рассинхрон мажорных версий приводит к молчаливой визуальной несогласованности, а не к брошенной ошибке.

- **«CSS-переменные (custom properties) блокируются границей Shadow DOM так же, как обычные стили»** — нет, они наследуются сквозь границу shadow DOM по умолчанию, что как раз и делает их удобным механизмом передачи общих design-токенов в изолированный контент.
