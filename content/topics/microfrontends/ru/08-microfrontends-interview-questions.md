# Микрофронтенды — вопросы для интервью (Middle/Senior)

## Группа 1: Организационный паттерн vs разбиение на компоненты

**В чём принципиальное отличие микрофронтендов от модульного монолита фронтенда?**

Оба подхода могут иметь идентично чистый, хорошо модуляризованный код с явными границами между частями. Разница не в структуре кода, а в модели деплоя. Модульный монолит — одна сборка, один деплой-артефакт: изменение в одном модуле требует пересборки и передеплоя всего приложения. Микрофронтенды — N независимых сборок и N независимых деплоев, композируемых после того, как каждая часть уже задеплоена — во время сборки хоста (build-time), на сервере при запросе (SSI) или в браузере в рантайме (Module Federation, single-spa). Модульность кода и независимость деплоя — два ортогональных свойства; можно иметь одно без другого.

---

**Какой практический критерий позволяет отличить «настоящие» микрофронтенды от модульного монолита?**

Вопрос: может ли команда X задеплоить свою часть в продакшен прямо сейчас, не дожидаясь и не координируясь с командой Y, и без пересборки/передеплоя частей, принадлежащих Y? Если ответ «нет» — потому что всё собирается одним `webpack build` и деплоится одним артефактом — это модульный монолит, сколь угодно хорошо структурированный. Если «да» — потому что композиция происходит после того, как каждая часть уже собрана и задеплоена отдельно — это микрофронтенды. Сам факт использования технологии вроде Module Federation ничего не доказывает: её можно применять и внутри модульного монолита одной командой просто ради динамической загрузки кода.

---

**Почему «наше приложение большое» само по себе не является достаточным основанием для перехода на микрофронтенды?**

Микрофронтенды решают организационную проблему — как позволить нескольким независимым командам деплоить без координации друг с другом, — а не техническую проблему «слишком много кода». Большое приложение, которым владеет одна команда, почти всегда лучше решается модульным монолитом (feature-sliced структура, чёткие границы модулей, публичные API между ними) — без единой из цен микрофронтендов: рантайм-сложности согласования shared-зависимостей, издержек на визуальную согласованность, необходимости в отдельной CI/CD-инфраструктуре на каждую часть. Медленная сборка или медленные тесты — это проблема тулинга (code splitting, кэш тест-раннера), а не повод для независимого деплоя.

---

**Как проявляется закон Конвея применительно к фронтенд-архитектуре?**

Закон Конвея (Melvin Conway, 1967): организации, проектирующие системы, вынуждены создавать дизайны, копирующие структуру коммуникаций этих организаций. Применительно к фронтенду: если продуктом владеют N независимых команд, продукт стремится структурироваться в N крупных фронтенд-единиц — с рабочим API между ними или без него. Практическое следствие: микрофронтенды оправданы, когда несколько команд уже организационно независимы и нуждаются в независимом деплое; для одной команды закон Конвея просто неприменим — не от кого быть автономным, а координационные издержки многосервисной структуры остаются. Закон описателен, а не предписателен — Inverse Conway Maneuver (намеренное структурирование команд под желаемую архитектуру) — это уже осознанная, предписательная стратегия.

## Группа 2: Способы интеграции

**Сравните build-time интеграцию через npm-пакеты и клиентскую runtime-интеграцию — по какой оси их правильно сравнивать?**

Правильная ось сравнения — в какой момент решается, какой код какой версии куда попадёт, и кто это решение принимает. При build-time интеграции резолюция происходит на сборке хоста: команда remote может публиковать новые версии пакета когда угодно, но пользователь не увидит изменений, пока хост не обновит зависимость и не пересоберётся — независимость разработки есть, независимости деплоя работающего приложения нет. При клиентской runtime-интеграции (Module Federation, single-spa, import maps) резолюция происходит в браузере в момент навигации пользователя — версию remote'а можно поменять без пересборки хоста, но резолюция теперь может сломаться именно в тот момент, когда пользователь смотрит на экран, а не быть пойманной на CI хоста.

---

**Когда iframe — правильный архитектурный выбор, а не компромисс от безысходности?**

Когда изоляция — это требование, а не побочный эффект: встраивание виджета от недоверенного стороннего вендора (платёжная форма, чат-виджет, реклама), где сознательно не нужно, чтобы этот код имел доступ к DOM и cookies остальной страницы. Iframe даёт единственную настоящую изоляцию JS/CSS/DOM среди всех подходов — отдельный browsing context со своим `window`. Цена этой изоляции — невозможность естественного шеринга стилей, проблемы с подгонкой высоты, потеря нативного поведения кнопки «назад» и deep-linking без ручной синхронизации через `postMessage` и `history.pushState` — и эта цена оправдана именно тогда, когда изоляция и есть цель, а не то, с чем приходится мириться.

---

**Чем server-side composition (SSI) выгодно отличается от клиентской runtime-композиции, и какова его цена?**

При server-side composition сборка страницы из HTML-фрагментов происходит на сервере или edge на каждый входящий запрос — до того, как что-либо уходит в браузер. Это даёт быстрый TTFB, работу без JS на клиенте (прогрессивное улучшение) и отличные показатели для SEO. Версию каждого фрагмента можно менять мгновенно и независимо, потому что композиция пересчитывается заново на каждый запрос, а не фиксируется единожды при сборке хоста. Цена: нужна отдельная инфраструктура композиции (edge-слой или compositor-сервис), а согласование клиентской интерактивности между независимо отрендеренными фрагментами (гидратация, общий JS-стейт) — заметно сложнее, чем при чисто клиентской композиции.

## Группа 3: Внутреннее устройство Module Federation

**Что именно содержится в remoteEntry.js и что происходит, когда его загружает хост?**

`remoteEntry.js` — не бандл приложения, а маленький контейнер с двумя функциями: `init(shareScope)`, который регистрирует версии shared-зависимостей этого remote'а в общей share scope хоста, и `get(moduleRequest)`, который возвращает асинхронную фабрику для запрошенного экспортированного модуля. Сам код экспортированных модулей лежит в отдельных чанках, которые `get()` подгружает лениво — именно поэтому `remoteEntry.js` сам по себе крошечный. Когда хост делает `import('checkout/CheckoutApp')`, это резолвится в: сходить за `remoteEntry.js` remote'а `checkout`, вызвать `init()` для согласования зависимостей, вызвать `get('./CheckoutApp')`, выполнить вернувшуюся фабрику.

---

**Опишите алгоритм согласования shared-зависимостей в Module Federation. Что означают singleton, strictVersion и eager?**

Каждый контейнер при инициализации регистрирует версии своих shared-модулей в общей share scope. Когда код обращается к shared-зависимости (например, `react`), рантайм проверяет share scope: если там уже есть совместимая версия и указан `singleton: true`, переиспользуется существующий инстанс без нового сетевого запроса. Если совместимой версии нет — контейнер загружает собственную резервную (fallback) копию зависимости, которая на этот случай всегда упакована внутри его же бандла. `strictVersion: true` меняет поведение при несовместимости: вместо тихой загрузки fallback'а рантайм бросает явную ошибку — полезно на стейджинге, чтобы ловить рассинхрон версий до прода. `eager: true` включает модуль прямо в основной чанк вместо ленивой асинхронной загрузки — необходимо для entry-точки хоста, но вне неё способно сломать негоциацию, зарегистрировав версию раньше, чем другие контейнеры успели договориться.

```js
shared: {
  react: {
    singleton: true,
    requiredVersion: '^18.2.0',
    strictVersion: true,
    eager: false,
  },
}
```

---

**Почему в проде иногда загружаются две копии React, хотя всё работало в dev? Как это дебажить?**

Три типичных сценария. Первый — гонка инициализации: негоциация share scope зависит от порядка вызова `init()` разными контейнерами; в dev-режиме порядок стабилен (всё локально), в проде remote грузится с другого CDN с другой латентностью и может не успеть найти совместимую версию в share scope к моменту своей инициализации, из-за чего загружает собственный fallback. Второй — реальный рассинхрон версий: `requiredVersion` формально удовлетворён по semver, но без `strictVersion` рантайм может тихо выбрать не ту версию, которую тестировала команда remote'а. Третий — симптом: ошибка `Invalid hook call`, потому что React хранит dispatcher хуков как module-level singleton, и при двух инстансах `react-dom` в памяти он перестаёт «узнавать» собственный рендер. Дебажить: смотреть вкладку Network на дублирующийся чанк `react`, инспектировать `window.__webpack_share_scopes__.default` в консоли, временно включить `strictVersion: true` на стейджинге, чтобы получить явную ошибку вместо молчаливого дублирования.

---

**Зачем нужен паттерн `import('./bootstrap')` вместо обычного статического импорта в точке входа?**

Webpack должен успеть выполнить `init()` контейнера (согласование shared-зависимостей) до того, как код начнёт реально импортировать `react`. Статический `import` на верхнем уровне модуля выполняется синхронно при загрузке скрипта — раньше, чем у рантайма появляется шанс дождаться `init()` от других контейнеров. Динамический `import()` создаёт асинхронную границу, после которой webpack гарантированно успел согласовать share scope. Без этого паттерна возникает ошибка рантайма вида `Shared module is not available for eager consumption`.

```ts
// index.ts
import('./bootstrap'); // асинхронная граница перед потреблением shared-зависимостей
```

---

**В чём разница между static и dynamic remotes, и когда каждый из них уместен?**

Static remote — URL зашит в `webpack.config.js` хоста на этапе его сборки (`checkout: 'checkout@http://.../remoteEntry.js'`); просто, но версию remote'а нельзя сменить без пересборки хоста. Dynamic remote резолвит URL в рантайме — обычно через манифест, который хост запрашивает до того, как узнать, куда идти за `remoteEntry.js`. Это позволяет менять версию remote'а (например, откатить при инциденте или выкатить постепенным роллаутом через feature flag) правкой манифеста, без единого передеплоя хоста — ценой дополнительного сетевого round-trip к манифесту и более позднего момента резолюции.

## Группа 4: Коммуникация и обмен состоянием

**Какие есть каналы коммуникации между независимо задеплоенными микрофронтендами и в чём их trade-off?**

Событийная шина на `window`/`document` (CustomEvent) — слабая связанность, фреймворк-агностична, но не даёт compile-time проверки контракта без отдельного версионированного пакета типов событий. Общий инстанс store (Redux/Zustand через shared-конфигурацию Module Federation) — одна источник правды без задержки синхронизации, но воссоздаёт проблему связанности, оправдан только когда MFE деплоятся в лок-степе. Props/callbacks от хоста — типобезопасно и явно, но работает только когда хост непосредственно монтирует компонент, не годится для общения «братских» remote'ов напрямую. URL/query-параметры — самый примитивный, но самый надёжный канал: переживает перезагрузку страницы, не требует общей рантайм-зависимости, но ограничен сериализуемыми примитивами.

---

**Почему прямой импорт внутренней реализации соседнего remote'а считается антипаттерном, даже если технически это возможно через Module Federation exposes?**

Потому что это создаёт скрытую связанность, которая не проявляется ни в одной сборке, ни в одном тесте ни одной из команд: изменение внутренней формы `cartStore` команды catalog не ломает CI ни catalog, ни checkout, потому что их сборки происходят независимо и никогда не видят код друг друга напрямую. Поломка проявляется только в браузере пользователя, в рантайме, когда бандл checkout выполняется рядом с новой версией бандла catalog — то есть ровно там, где её труднее всего поймать. Правило: импортировать можно только то, что явно и осознанно выставлено как публичный контракт (аналог REST/gRPC API микросервиса), а к этой поверхности нужно относиться с версионной дисциплиной, как к публичному API.

```ts
// ❌ Антипаттерн: внутренняя реализация, случайно доступная через exposes
import { cartStore } from 'catalog/src/internal/cartStore';

// ✅ Правильно: только осознанно экспортированный публичный контракт
import { getCartSummary } from 'catalog/PublicApi';
```

---

**В каком случае оправдан общий (shared) инстанс store между микрофронтендами, а в каком — нет?**

Оправдан, когда микрофронтенды и так деплоятся в лок-степе (одна команда, единый релизный цикл) или когда контракт формы store версионируется и поддерживается с той же строгостью, что и версионированный публичный API. В общем случае — не оправдан: изменение формы store требует синхронного обновления всех потребителей, что воссоздаёт ровно ту проблему связанности, которую независимый деплой должен был устранить. Более устойчивая к независимым деплоям альтернатива — изолированный store у каждого MFE плюс синхронизация изменений через событийную шину, где единственный контракт — формат события на проводе, а внутренняя форма store каждого MFE остаётся приватной деталью реализации.

## Группа 5: Роутинг и навигация

**Как распределяется владение маршрутизацией между хостом и remote'ами в типичной production-системе?**

Доминирующий на практике паттерн — гибрид: хост владеет только верхнеуровневой сегментацией (например, `/checkout/*` монтирует `CheckoutApp`), а всё, что происходит внутри этого префикса — целиком в ведении команды checkout, включая произвольное добавление, удаление или переименование внутренних маршрутов без единой правки в хосте. Хост знает только префикс — это и есть минимальный публичный контракт между ним и remote'ом.

---

**Что произойдёт, если хост и remote создадут каждый свой независимый инстанс роутера (например, два `<BrowserRouter>`), и как этого избежать?**

У браузера один `window.history` — два независимых инстанса роутера будут оба слушать `popstate` и независимо вызывать `pushState`, из-за чего кнопка «назад» и навигация начинают вести себя непредсказуемо: один роутер перезаписывает решение другого. Правило — только одна сущность должна вызывать `history.pushState`/`replaceState` для конкретного перехода; остальные должны выводить своё состояние из `window.location`. На практике: хост создаёт один общий инстанс `history`, а remote переиспользует его вместо создания собственного `<BrowserRouter>` (либо, как в single-spa, глобальный патч `history` рассылает единое событие навигации всем зарегистрированным приложениям).

## Группа 6: Стилизация и изоляция

**Какие есть подходы к изоляции стилей между микрофронтендами и какие у Shadow DOM реальные trade-off'ы?**

CSS Modules — хеширование имён классов на сборке, ноль рантайм-цены, но защищает только от коллизии имён, а не от высокоспецифичных глобальных селекторов извне. Shadow DOM — единственная настоящая браузерная изоляция DOM и CSS, но с реальной ценой: ретаргетинг событий (снаружи `event.target` указывает на shadow host, а не на реальный источник события), несовместимость со многими библиотеками, ожидающими глобального `document.querySelector` или использующими порталы. CSS-in-JS (styled-components/Emotion) — та же защита от коллизий, что у CSS Modules, но в рантайме, с ценой в виде непредсказуемого порядка независимо внедрённых `<style>`-тегов между разными remote'ами. BEM-префиксинг — прагматичный дефолт без всякого тулинга, но целиком держится на дисциплине команды.

---

**Как может произойти визуальный «рассинхрон» дизайн-системы между микрофронтендами, и чем это опасно?**

Если catalog-mfe закреплён на `@company/design-system@2.1.0`, а checkout-mfe — на `@company/design-system@3.0.0` (мажорная версия с ломающими визуальными изменениями), и обе части композируются рядом на одной странице, пользователь буквально видит два визуально разных стиля кнопок, оба претендующих быть одной дизайн-системой. Это CSS-эквивалент бага «две копии React» — только здесь не бросается ошибка, всё просто выглядит несогласованно, и обнаруживается только тогда, когда живой человек смотрит на экран. Митигация — та же организационная дисциплина, что и для shared JS-зависимостей: относиться к мажорной версии дизайн-системы как к singleton-требованию с CI-проверкой по всем репозиториям и явным окном апгрейда.

## Группа 7: Деплой, версионирование, тестирование, observability

**Что именно нужно версионировать в микрофронтендной архитектуре — приложение целиком или что-то более узкое?**

Версионированию подлежит не всё приложение, а конкретно поверхность, пересекающая границу хост/remote: форма props/API экспортированных модулей, мажорные версии shared-зависимостей, версия дизайн-системы, владение префиксом маршрута. Всё остальное — внутренняя реализация — может меняться свободно и без координации, именно потому что не входит в контракт. При ломающем изменении контракта: выставляется новый версионированный путь модуля рядом со старым (`./CheckoutAppV2`), либо новые props делаются опциональными на один релиз перед тем как стать обязательными — паттерн «expand and contract», аналогичный безопасным миграциям схемы БД.

**Опишите пирамиду тестирования для микрофронтендов — какую роль в ней играют контрактные тесты?**

Unit-тесты — внутри репозитория каждого MFE, тестируют внутреннюю логику, ничего специфичного для MFE. Контрактные тесты — проверяют, что публичная поверхность конкретного MFE (props экспортированного компонента, форма событий, версия shared-зависимости) соответствует задокументированному контракту; запускаются в CI этого MFE на каждый коммит без необходимости, чтобы другая сторона была реально задеплоена — это именно то, что позволяет командам деплоить независимо, не дожидаясь полного e2e-прогона против всех остальных. E2E-тесты через собранное приложение — единственный уровень, реально проверяющий интеграцию (провал негоциации share scope, коллизии CSS), но дорогой и медленный, поэтому запускается реже.

**Как feature-флаги используются для безопасного роллаута новой версии remote'а?**

Резолюция того, какую версию remote'а отдавать, ставится за feature flag на уровне резолвинга dynamic remote: вместо мгновенного переключения на 100% пользователей новая версия выкатывается на небольшой процент, за которым наблюдают через observability, и откатывается простым переключением флага без единого передеплоя чего-либо, включая хост. Без такого постепенного роллаута «независимый деплой» на практике означает «блэст-радиус — 100% пользователей в момент пуша», что сводит на нет изоляцию отказов, которую микрофронтенды должны были обеспечить.

```ts
async function resolveCheckoutRemoteUrl(userId: string): Promise<string> {
  const isInRollout = await featureFlags.isEnabled('checkout-v2-4-1', { userId });
  return isInRollout
    ? 'https://cdn.company.com/checkout@2.4.1/remoteEntry.js'
    : 'https://cdn.company.com/checkout@2.3.0/remoteEntry.js';
}
```

**Почему отладка ошибок (observability) в микрофронтендной архитектуре сложнее, чем в монолите?**

В монолите один стектрейс покрывает весь запрос: один деплой-артефакт, одна source map, один поток логов. В MFE одна ошибка пользователя может пересекать несколько независимо задеплоенных бандлов разных версий, включая потенциально разные копии shared-зависимостей. Чтобы восстановить, что реально произошло, нужно: сопоставить версии деплоя всех вовлечённых MFE на точный момент времени ошибки (с учётом процента feature-flag-роллаута), иметь source maps для каждого бандла, загруженные в систему observability с тегом версии конкретного MFE, и прокидывать общий trace/session ID через границы MFE, чтобы сгруппировать события одной пользовательской сессии из нескольких раздельно инструментированных приложений. Без этого «где-то произошла ошибка» и «какая именно версия какой части её вызвала» — два разных вопроса, и в разрыве между ними теряется время реакции на инцидент.
