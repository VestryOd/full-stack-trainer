# Микрофронтенды — вопросы для интервью (Middle/Senior)

## Группа 1: Организационный паттерн vs разбиение на компоненты

**В чём принципиальное отличие микрофронтендов от модульного монолита фронтенда?**

Оба подхода могут иметь идентично чистый, хорошо модуляризованный код с явными границами между частями. Разница не в структуре кода, а в модели деплоя.

| | Модульный монолит | Микрофронтенды |
|---|---|---|
| Сборки и деплой-артефакты | один | N независимых |
| Изменение модуля | пересобрать и передеплоить всё | задеплоить только его |
| Композиция | внутри единственной сборки | после деплоя каждой части |

Сама композиция идёт во время сборки хоста, на сервере при каждом запросе или в браузере в рантайме. Серверный вариант делают server-side includes (SSI), рантаймовый — Module Federation и single-spa.

Модульность кода и независимость деплоя — ортогональные свойства: можно иметь одно без другого.

---

**Какой практический критерий позволяет отличить «настоящие» микрофронтенды от модульного монолита?**

Всё решает один вопрос. Может ли команда X задеплоить свою часть в продакшен прямо сейчас, не дожидаясь команды Y и не пересобирая её части?

- **Нет** — всё собирается одним `webpack build` и деплоится одним артефактом. Это модульный монолит, сколь угодно хорошо структурированный.
- **Да** — композиция происходит после того, как каждая часть уже собрана и задеплоена отдельно. Это микрофронтенды.

Сам факт использования Module Federation ничего не доказывает. Одна команда может применять его и внутри модульного монолита, ради динамической загрузки кода.

---

**Почему «наше приложение большое» само по себе не является достаточным основанием для перехода на микрофронтенды?**

Микрофронтенды решают организационную проблему: как позволить нескольким независимым командам деплоить без координации друг с другом. Техническую проблему «слишком много кода» они не решают.

Большое приложение, которым владеет одна команда, почти всегда лучше решается модульным монолитом — feature-sliced структура, чёткие границы модулей, публичные API между ними. Так вы избегаете трёх цен микрофронтендов:

- рантайм-сложности согласования shared-зависимостей;
- издержек на визуальную согласованность частей;
- отдельной инфраструктуры непрерывной интеграции (CI) и поставки (CD) на каждую часть.

Медленная сборка или медленные тесты — проблема тулинга (code splitting, кэш тест-раннера), а не повод для независимого деплоя.

---

**Как проявляется закон Конвея применительно к фронтенд-архитектуре?**

Закон Конвея (Melvin Conway, 1967): организации, проектирующие системы, вынуждены создавать дизайны, копирующие структуру собственных коммуникаций.

Применительно к фронтенду: если продуктом владеют N независимых команд, продукт стремится структурироваться в N крупных фронтенд-единиц. Так происходит независимо от того, есть между ними рабочий API.

Практическое следствие:

- Микрофронтенды оправданы, когда несколько команд уже организационно независимы и нуждаются в независимом деплое.
- Для одной команды закон просто неприменим. Не от кого быть автономным, а координационные издержки многосервисной структуры остаются.

Закон описателен, а не предписателен. Inverse Conway Maneuver — намеренное структурирование команд под желаемую архитектуру — это уже предписательная стратегия.

## Группа 2: Способы интеграции

**Сравните build-time интеграцию через npm-пакеты и клиентскую runtime-интеграцию — по какой оси их правильно сравнивать?**

Два термина проходят через весь раздел. **Хост** во время выполнения загружает чужой код, а **ремоут** публикует свой для загрузки другими.

Правильная ось — *когда* решается, какой код какой версии куда попадёт, и кто принимает это решение.

**Build-time интеграция.** Резолюция происходит на сборке хоста. Команда ремоута может публиковать новые версии пакета когда угодно, но пользователь ничего не увидит, пока хост не обновит зависимость и не пересоберётся. Независимость разработки есть, независимости деплоя работающего приложения нет.

**Клиентская runtime-интеграция** (Module Federation, single-spa, import maps). Резолюция происходит в браузере в момент навигации пользователя. Версию ремоута можно поменять без пересборки хоста. Обратная сторона: резолюция может сломаться прямо когда пользователь смотрит на экран, а не быть пойманной на CI хоста.

---

**Когда iframe — правильный архитектурный выбор, а не компромисс от безысходности?**

Когда изоляция — это требование, а не побочный эффект. Случай — виджет от недоверенного стороннего вендора: платёжная форма, чат-виджет, реклама. Вы сознательно не хотите пускать этот код к DOM (document object model — живому дереву элементов страницы) и cookies остальной страницы.

Iframe даёт единственную настоящую изоляцию JS, CSS и DOM среди всех подходов: отдельный browsing context со своим `window`. Цена:

- стили нельзя разделять естественно;
- подгонка высоты требует хаков;
- нативное поведение кнопки «назад» и deep-linking теряются, пока вы не синхронизируете их вручную через `postMessage` и `history.pushState`.

Эта цена оправдана именно тогда, когда изоляция и есть цель, а не то, с чем приходится мириться.

---

**Чем server-side composition (SSI) выгодно отличается от клиентской runtime-композиции, и какова его цена?**

При server-side composition страница собирается из HTML-фрагментов на сервере или edge на каждый входящий запрос, до того как что-либо уходит в браузер. Отсюда и преимущества:

- быстрый TTFB (time to first byte): браузер получает готовый HTML;
- работает без JS на клиенте (прогрессивное улучшение);
- отличные показатели для SEO (search engine optimization);
- версию каждого фрагмента можно менять мгновенно, потому что композиция пересчитывается на каждый запрос, а не фиксируется при сборке хоста.

Цена — инфраструктура: отдельный слой композиции на edge или compositor-сервис. Согласование клиентской интерактивности между независимо отрендеренными фрагментами — гидратация, общий JS-стейт — тоже заметно сложнее, чем при чисто клиентской композиции.

## Группа 3: Внутреннее устройство Module Federation

**Что именно содержится в remoteEntry.js и что происходит, когда его загружает хост?**

`remoteEntry.js` — не бандл приложения. Это маленький контейнер с двумя функциями:

- `init(shareScope)` — регистрирует версии shared-зависимостей этого ремоута в общей share scope хоста.
- `get(moduleRequest)` — возвращает асинхронную фабрику для запрошенного экспортированного модуля.

Сам код экспортированных модулей лежит в отдельных чанках, которые `get()` подгружает лениво. Поэтому `remoteEntry.js` сам по себе крошечный.

Поэтому `import('checkout/CheckoutApp')` на хосте разворачивается в четыре шага:

1. Сходить за `remoteEntry.js` ремоута `checkout`.
2. Вызвать `init()` для согласования зависимостей.
3. Вызвать `get('./CheckoutApp')`.
4. Выполнить вернувшуюся фабрику.

---

**Опишите алгоритм согласования shared-зависимостей в Module Federation. Что означают singleton, strictVersion и eager?**

Согласование идёт в пять шагов.

1. При инициализации каждый контейнер регистрирует версии своих shared-модулей в общей share scope.
2. Код обращается к shared-зависимости, например к `react`.
3. Рантайм ищет в share scope совместимую версию.
4. Если она есть и указан `singleton: true`, переиспользуется существующий инстанс, без нового сетевого запроса.
5. Если её нет, контейнер загружает собственную резервную копию — она всегда упакована внутри его бандла.

**Три флага**

- `singleton: true` — переиспользовать один инстанс вместо загрузки второй копии.
- `strictVersion: true` — при несовместимости бросать явную ошибку вместо тихой загрузки резервной копии. Полезно на стейджинге, чтобы ловить рассинхрон версий до прода.
- `eager: true` — включить модуль прямо в основной чанк вместо асинхронной загрузки. Необходимо для entry-точки хоста. Вне неё это способно сломать согласование, зарегистрировав версию раньше других контейнеров.

```js
shared: {
  react: {
    singleton: true,
    requiredVersion: '^18.2.0',
    strictVersion: true,
    eager: false,
  },
}
```

---

**Почему в проде иногда загружаются две копии React, хотя всё работало в dev? Как это дебажить?**

Три типичных сценария.

1. **Гонка инициализации.** Согласование share scope зависит от порядка вызова `init()` контейнерами. В dev этот порядок стабилен, потому что всё локально. В проде remote грузится с другого CDN (content delivery network — сети доставки контента), с другой латентностью. Он может не успеть найти совместимую версию и загружает собственную резервную копию.
2. **Реальный рассинхрон версий.** Semver формально удовлетворяет `requiredVersion`. Но без `strictVersion` рантайм может тихо выбрать не ту версию, которую тестировала команда ремоута.
3. **Симптом, который вы видите.** Ошибка `Invalid hook call`. React хранит dispatcher хуков как module-level singleton, и при двух инстансах `react-dom` в памяти он перестаёт «узнавать» собственный рендер.

Как дебажить:

- посмотреть во вкладке Network, не дублируется ли чанк `react`;
- проинспектировать `window.__webpack_share_scopes__.default` в консоли;
- временно включить `strictVersion: true` на стейджинге, чтобы получить явную ошибку вместо молчаливого дублирования.

---

**Зачем нужен паттерн `import('./bootstrap')` вместо обычного статического импорта в точке входа?**

Webpack должен успеть выполнить `init()` контейнера — согласование shared-зависимостей — до того, как код реально импортирует `react`.

Статический `import` на верхнем уровне модуля выполняется синхронно при загрузке скрипта, раньше, чем у рантайма появляется шанс дождаться `init()` от других контейнеров. Динамический `import()` создаёт асинхронную границу, после которой webpack гарантированно согласовал share scope. Без этого паттерна возникает ошибка рантайма: `Shared module is not available for eager consumption`.

```ts
// index.ts
import('./bootstrap'); // асинхронная граница перед потреблением shared-зависимостей
```

---

**В чём разница между static и dynamic remotes, и когда каждый из них уместен?**

**Static remote** — запись `checkout: 'checkout@http://.../remoteEntry.js'` зашита в `webpack.config.js` хоста на сборке.

**Dynamic remote** резолвит URL в рантайме, через манифест, который хост запрашивает до того, как узнает, куда идти за `remoteEntry.js`.

| | Static remote | Dynamic remote |
|---|---|---|
| URL известен | на сборке хоста | в рантайме |
| Смена версии | пересборка хоста | правка манифеста |
| Лишняя сеть | нет | round-trip к манифесту |
| Резолюция ломается | в сборке хоста | в браузере пользователя |

Именно это позволяет откатить версию при инциденте или выкатить постепенный роллаут через feature flag без передеплоя хоста.

## Группа 4: Коммуникация и обмен состоянием

**Какие есть каналы коммуникации между независимо задеплоенными микрофронтендами и в чём их компромиссы?**

Четыре канала, у каждого свой компромисс.

| Канал | Сильная сторона | Слабая сторона |
|---|---|---|
| Событийная шина на `window`/`document` | слабая связанность, фреймворк-агностична | нет проверки контракта на компиляции без версионированного пакета типов |
| Общий store (Redux/Zustand через `shared`) | единственный источник правды без задержки синхронизации | воссоздаёт связанность; оправдан, только если части деплоятся синхронно |
| Props и колбэки от хоста | типобезопасно и явно | только там, где хост сам монтирует компонент, но не между «братскими» ремоутами |
| URL и query-параметры | переживает перезагрузку, не требует общей рантайм-зависимости | только сериализуемые примитивы |

URL-канал самый примитивный и поэтому самый надёжный.

---

**Почему прямой импорт внутренней реализации соседнего ремоута считается антипаттерном, даже если технически это возможно через Module Federation exposes?**

Потому что это создаёт скрытую связанность, которую не ловит ни сборка, ни тесты ни одной из команд. Изменение внутренней формы `cartStore` команды catalog не ломает CI ни catalog, ни checkout. Их сборки происходят независимо и никогда не видят код друг друга напрямую.

Поломка проявляется только в браузере пользователя, в рантайме, когда бандл checkout выполняется рядом с новой версией бандла catalog. То есть ровно там, где её труднее всего поймать.

Правило: импортировать можно только то, что явно и осознанно выставлено как публичный контракт. Это аналог публичного REST (representational state transfer) или gRPC API микросервиса, и версионная дисциплина нужна та же, что и для публичного API.

```ts
// ❌ Антипаттерн: внутренняя реализация, случайно доступная через exposes
import { cartStore } from 'catalog/src/internal/cartStore';

// ✅ Правильно: только осознанно экспортированный публичный контракт
import { getCartSummary } from 'catalog/PublicApi';
```

---

**В каком случае оправдан общий (shared) инстанс store между микрофронтендами, а в каком — нет?**

Оправдан в двух случаях:

- микрофронтенды и так деплоятся синхронно — одна команда, единый релизный цикл;
- контракт формы store версионируется и поддерживается так же строго, как публичный API.

В общем случае — не оправдан. Изменение формы store требует синхронного обновления всех потребителей, а это воссоздаёт ровно ту связанность, которую независимый деплой должен был устранить.

Более устойчивая к независимым деплоям альтернатива — изолированный store у каждого микрофронтенда (MFE) плюс синхронизация изменений через событийную шину. Тогда единственный контракт — формат события на проводе, а внутренняя форма store каждого MFE остаётся приватной деталью реализации.

## Группа 5: Роутинг и навигация

**Как распределяется владение маршрутизацией между хостом и ремоутами в типичной production-системе?**

Доминирующий на практике паттерн — гибрид.

- Хост владеет только верхнеуровневой сегментацией: `/checkout/*` монтирует `CheckoutApp`.
- Всё, что происходит внутри этого префикса, целиком в ведении команды checkout — включая произвольное добавление, удаление или переименование внутренних маршрутов без единой правки в хосте.

Хост знает только префикс, и это минимальный публичный контракт между ним и ремоутом.

---

**Что произойдёт, если хост и remote создадут каждый свой независимый инстанс роутера (например, два `<BrowserRouter>`), и как этого избежать?**

У браузера один `window.history`. Два независимых инстанса роутера оба слушают `popstate` и оба сами вызывают `pushState`. Кнопка «назад» и навигация после этого ведут себя непредсказуемо: один роутер перезаписывает решение другого.

Правило: только одна сущность вызывает `history.pushState` или `replaceState` для перехода, а остальные выводят своё состояние из `window.location`.

На практике хост создаёт один общий инстанс `history`, а remote переиспользует его вместо создания собственного `<BrowserRouter>`. В single-spa та же цель достигается иначе: глобальный патч `history` рассылает единое событие навигации всем зарегистрированным приложениям.

## Группа 6: Стилизация и изоляция

**Какие есть подходы к изоляции стилей между микрофронтендами и какие у Shadow DOM реальные компромиссы?**

Четыре подхода, ни один не бесплатный.

| Подход | Изоляция | Цена |
|---|---|---|
| CSS Modules | хеширование имён классов на сборке | только коллизии имён, но не высокоспецифичные глобальные селекторы |
| Shadow DOM | единственная настоящая браузерная изоляция DOM и CSS | ретаргетинг событий; ломаются библиотеки, ждущие глобальный `document` |
| CSS-in-JS (styled-components, Emotion) | та же защита от коллизий, но в рантайме | порядок внедрённых `<style>`-тегов между ремоутами непредсказуем |
| Префиксы в стиле BEM (block, element, modifier) | соглашение об именовании | держится на дисциплине команды |

Цену Shadow DOM стоит расписать. Снаружи границы `event.target` указывает на shadow host, а не на реальный источник события. Библиотеки, которые лезут к глобальному `document.querySelector` или используют порталы, внутри неё часто ломаются.

---

**Как может произойти визуальный «рассинхрон» дизайн-системы между микрофронтендами, и чем это опасно?**

Допустим, `catalog-mfe` закреплён на `@company/design-system@2.1.0`, а `checkout-mfe` — на `@company/design-system@3.0.0`, мажорной версии с ломающими визуальными изменениями. Скомпонуйте обе части рядом на одной странице. Пользователь буквально увидит два разных стиля кнопок, оба претендующих быть одной дизайн-системой.

Это CSS-эквивалент бага «две копии React», с одной разницей: ошибка не бросается. Страница просто выглядит несогласованно, и это обнаруживается, только когда живой человек смотрит на экран.

Риск снижают той же организационной дисциплиной, что и для shared JS-зависимостей. Мажорную версию дизайн-системы считают singleton-требованием, с CI-проверкой по всем репозиториям и явным окном апгрейда.

## Группа 7: Деплой, версионирование, тестирование, observability

**Что именно нужно версионировать в микрофронтендной архитектуре — приложение целиком или что-то более узкое?**

Не всё приложение, а конкретно поверхность, пересекающая границу хост/remote:

- форма props/API экспортированных модулей;
- мажорные версии shared-зависимостей;
- версия дизайн-системы;
- владение префиксом маршрута.

Всё остальное — внутренняя реализация — может меняться свободно и без координации, потому что не входит в контракт.

При ломающем изменении контракта есть два хода. Выставить новый версионированный путь модуля рядом со старым, например `./CheckoutAppV2`. Либо сделать новые props опциональными на один релиз, а обязательными — в следующем. Это паттерн «расширить и сжать», как при миграциях схемы базы данных.

**Опишите пирамиду тестирования для микрофронтендов — какую роль в ней играют контрактные тесты?**

Три уровня; специфичен для этой архитектуры только средний.

**Unit-тесты** — внутри репозитория каждого MFE, тестируют внутреннюю логику. Ничего специфичного для микрофронтендов.

**Контрактные тесты** — проверяют, что публичная поверхность конкретного MFE соответствует задокументированному контракту: props экспортированного компонента, форма событий, версия shared-зависимости. Запускаются в CI этого MFE на каждый коммит, без необходимости, чтобы другая сторона была задеплоена.

Последнее и есть суть: именно оно позволяет командам деплоить независимо, не дожидаясь полного прогона E2E (end-to-end) против всех остальных.

**E2E-тесты через собранное приложение** — единственный уровень, реально проверяющий интеграцию: провал согласования share scope, коллизия CSS. Дорого и медленно, поэтому запускается реже.

**Как feature-флаги используются для безопасного роллаута новой версии ремоута?**

Резолюция того, какую версию ремоута отдавать, ставится за feature flag на уровне резолвинга dynamic remote. Вместо мгновенного переключения на 100% пользователей новая версия выкатывается на небольшой процент. За ней наблюдают через observability и откатывают простым переключением флага. Ничего не передеплоивается, включая хост.

Без такого постепенного роллаута «независимый деплой» на практике означает, что новую версию получают 100% пользователей в момент пуша. Это сводит на нет изоляцию отказов, которую микрофронтенды должны были обеспечить.

```ts
async function resolveCheckoutRemoteUrl(userId: string): Promise<string> {
  const isInRollout = await featureFlags.isEnabled('checkout-v2-4-1', { userId });
  return isInRollout
    ? 'https://cdn.company.com/checkout@2.4.1/remoteEntry.js'
    : 'https://cdn.company.com/checkout@2.3.0/remoteEntry.js';
}
```

**Почему отладка ошибок (observability) в микрофронтендной архитектуре сложнее, чем в монолите?**

В монолите один стектрейс покрывает весь запрос: один деплой-артефакт, одна source map, один поток логов. В MFE-архитектуре одна ошибка пользователя может пересекать несколько независимо задеплоенных бандлов разных версий. В эти бандлы могут входить и разные копии shared-зависимостей.

Чтобы восстановить, что реально произошло, нужны три вещи:

1. Сопоставить версии деплоя всех вовлечённых MFE на точный момент ошибки, с учётом процента feature-flag-роллаута.
2. Иметь source maps для каждого бандла, загруженные в систему observability с тегом версии конкретного MFE.
3. Прокидывать общий trace- или session-идентификатор через границы MFE, чтобы группировать события одной сессии из нескольких раздельно инструментированных приложений.

Без этого «где-то произошла ошибка» и «какая именно версия какой части её вызвала» — два разных вопроса. В разрыве между ними теряется время реакции на инцидент.
