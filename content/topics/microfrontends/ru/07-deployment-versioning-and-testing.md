# Деплой, версионирование и тестирование

## Независимые CI/CD-пайплайны на каждый микрофронтенд

```txt
checkout-repo/  CI: lint → unit-тесты → build
                → публикация remoteEntry.js@2.4.1 на CDN
                → обновление манифеста

catalog-repo/   CI: lint → unit-тесты → build
                → публикация remoteEntry.js@1.8.0 на CDN
                → обновление манифеста
```

Непрерывная интеграция (CI) и непрерывная поставка (CD) идут по репозиториям, и ни один не блокирует другой. Это и есть механически реализованная организационная выгода из статьи [Основы микрофронтендов](./01-microfrontends-fundamentals.md). Каждый пайплайн идёт по своему расписанию. Заблокировать его могут только собственные тесты, а не флейки-тест соседней команды.

## Версионировать нужно контракт, а не всё приложение целиком

Частое заблуждение: раз это «микрофронтенд», значит его нужно версионировать целиком, как единый артефакт. На деле версионированию подлежит не всё приложение, а конкретно та поверхность, что пересекает границу между хостом и ремоутом:

- форма props/API экспортированных модулей ([Коммуникация и обмен состоянием между микрофронтендами](./04-communication-and-state-sharing.md)),
- мажорные версии shared-зависимостей ([Module Federation: как это работает внутри](./03-module-federation-deep-dive.md)),
- версия дизайн-системы ([Стилизация и изоляция](./06-styling-and-isolation.md)),
- владение префиксом маршрута ([Роутинг и навигация между микрофронтендами](./05-routing-and-navigation.md)).

Всё остальное — внутренняя реализация — может меняться свободно, без какой-либо координации, именно потому что не входит в контракт.

```json
// checkout-mfe/module-federation.manifest.json — публикуемый контракт, а не реализация
{
  "name": "checkout",
  "version": "2.4.1",
  "exposedModules": {
    "./CheckoutApp": {
      "propsSchema": { "onOrderComplete": "(orderId: string) => void" }
    }
  },
  "sharedDependencies": {
    "react": "^18.2.0"
  }
}
```

## Стратегии обратной совместимости при ломающих изменениях

Допустим, ремоуту нужно ломающее изменение в контракте: `CheckoutApp` теперь требует новый обязательный prop. Задеплоить это напрямую нельзя: хост и другие потребители молча сломаются в рантайме — ровно как при рассинхроне версий дизайн-системы из статьи [Стилизация и изоляция](./06-styling-and-isolation.md).

1. **Выставить новый версионированный путь модуля рядом со старым.** `./CheckoutApp` (v1) продолжает работать, а рядом добавляется `./CheckoutAppV2`. Хост мигрирует по собственному расписанию, старый путь позже объявляют устаревшим. Прямая параллель — версионирование REST (representational state transfer) API: `/v1/`, `/v2/`.
2. **Сделать новые props опциональными с разумными значениями по умолчанию** на один релиз. Обязательными они станут в следующем мажорном, когда у потребителей уже было окно на миграцию. Тот же паттерн «расширить и сжать» применяют при миграциях схемы базы данных. См. вопрос о добавлении `NOT NULL`-колонки в статье про Prisma.
3. **Сообщать об отказе от старого пути через тот же контрактный пакет**, что и типы с документацией. Например, `@company/checkout-contract` с задокументированным графиком отказа, а не устная договорённость в Slack.

## Пирамида тестирования через границы микрофронтендов

**Unit-тесты** — внутри репозитория каждого микрофронтенда, тестируют его собственную внутреннюю логику и компоненты, как в любом обычном приложении. Ничего специфичного для микрофронтендов (MFE) здесь нет.

**Контрактные тесты** — проверяют, что публичная поверхность этого микрофронтенда соответствует задокументированному контракту. Поверхность — это props экспортированного компонента, форма публикуемых событий и версия shared-зависимости. Тесты идут в собственном CI на каждый коммит, **без необходимости, чтобы другая сторона была задеплоена**.

Это аналог consumer-driven contract testing из микросервисов, в духе Pact. Хост определяет, что ожидает от ремоута, а проверка идёт против реально собранного артефакта ремоута.

```tsx
// checkout-mfe: контрактный тест — работает в своём CI, хост не нужен
import React from 'react';
import { render } from '@testing-library/react';
import { CheckoutApp } from './CheckoutApp';

test('CheckoutApp exposes onOrderComplete callback prop', () => {
  // Контракт проверяет аннотация типа, а не ассершен: если CheckoutApp
  // потеряет onOrderComplete, файл перестанет компилироваться.
  const props: React.ComponentProps<typeof CheckoutApp> = {
    onOrderComplete: (orderId: string) => {},
  };
  // Ассершен добавляет только «и он всё ещё монтируется».
  expect(() => render(<CheckoutApp {...props} />)).not.toThrow();
});
```

**E2E-тесты через собранное приложение целиком.** E2E — это end-to-end, сквозной прогон, единственный уровень, который реально проверяет интеграцию. Хост и настоящие ремоуты загружаются вместе в браузере — Playwright или Cypress. Стейджинг держит все ремоуты в текущих версиях.

Дорого и медленно, поэтому запускается ночью или перед релизом. Зато только этот уровень ловит реальные интеграционные баги — провал согласования share scope, коллизию CSS. Контрактные тесты их в принципе не поймают: тестируют каждую сторону изолированно.

## Постепенный роллаут новой версии ремоута через feature flag

Когда checkout выкатывает новую версию ремоута, всех пользователей не переключают разом. Какую версию отдавать, **решает feature flag**: LaunchDarkly, GrowthBook или простой процентный роллаут собственной разработки. Флаг стоит на уровне резолвинга dynamic remote из статьи [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md):

```ts
// резолюция манифеста теперь зависит от feature flag / процента роллаута
async function resolveCheckoutRemoteUrl(userId: string): Promise<string> {
  const isInRollout = await featureFlags.isEnabled('checkout-v2-4-1', { userId });
  return isInRollout
    ? 'https://cdn.company.com/checkout@2.4.1/remoteEntry.js'
    : 'https://cdn.company.com/checkout@2.3.0/remoteEntry.js';
}
```

Команда может выкатить новую версию ремоута на 5% пользователей и посмотреть на уровень ошибок в системе наблюдаемости (observability). Откат — одно переключение флага, и ничего не передеплоивается, включая хост. Это и есть операционная отдача от dynamic remotes из статьи [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md) в связке с независимыми CI/CD-пайплайнами.

## Почему наблюдаемость между микрофронтендами сложнее, чем в монолите

В монолите один стектрейс покрывает весь запрос целиком: один деплой-артефакт, одна source map, один поток логов. В MFE-архитектуре одна ошибка, которую видит пользователь, может пересекать несколько независимо задеплоенных бандлов.

Ошибка возникает в компоненте из `checkout-mfe@2.4.1`. Её перехватывает error boundary в `host@8.1.0`. Дальше стек вызовов проходит через `react@18.2.0` из той копии, которая оказалась живой в этот момент. Живых копий может быть больше одной — об этом статья [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md).

Чтобы восстановить, что реально произошло, нужно:

1. **Сопоставить версии деплоя всех вовлечённых MFE на точный момент возникновения ошибки.** Какая именно версия checkout была активна для этого пользователя в ту секунду, с учётом процента feature-flag-роллаута? Ответ «то, что сейчас в main» не годится.
2. **Source maps для каждого независимо собранного бандла**, загруженные в систему observability (Sentry) с тегом версии конкретного MFE. Без тега стектрейс — минифицированный мусор не той сборки.
3. **Общий trace- или session-идентификатор, прокидываемый через границы MFE.** Его внедряют при первой загрузке страницы, и библиотека трекинга ошибок каждого MFE читает его при старте. Тогда один дашборд сгруппирует события одной сессии, хотя пришли они из нескольких раздельно инструментированных приложений.

Пока эти три пункта не сделаны осознанно, у вас два разных вопроса. Первый мягкий: где-то в приложении произошла ошибка. Второй нужен на самом деле: какая из шести независимо задеплоенных частей и в какой версии её вызвала. В разрыве между ними и теряется время реакции.

## Типичные ошибки на интервью

- **«Версионирование микрофронтенда означает версионирование всего приложения как единого целого»** — версионированию подлежит только выставленный публичный контракт: props, shared-зависимости, дизайн-система, владение маршрутом. Внутренняя реализация может меняться без координации.

- **«Юнит-тестов и E2E-тестов достаточно, контрактные тесты — лишний уровень»** — контрактные тесты как раз и позволяют каждой команде деплоить независимо. Они снимают **ожидание** полного прогона E2E против задеплоенных версий остальных команд. Без них интеграцию проверяет только дорогой и медленный E2E, а он снова синхронизирует релизы всех команд.

- **«E2E-тесты через всё приложение заменяют необходимость в независимых пайплайнах»** — E2E по природе медленнее и происходит позже в пайплайне. Сделайте его единственным барьером перед деплоем — и вы воссоздадите единый релизный поезд для всех команд. Это уничтожает саму цель независимости деплоя.

- **«Проблемы observability в MFE — те же самые, что в монолите, просто распределённые»** — специфическая сложность именно в сопоставлении версий. Какая версия каждого независимо задеплоенного ремоута, закрытого feature-флагом, была активна для конкретного пользователя в конкретный момент? Монолиту с единой историей деплоя восстанавливать это не приходится.

- **«Feature flag для роллаута новой версии ремоута — это приятное дополнение, а не необходимость»** — это и есть механизм, который делает независимый деплой операционно безопасным. Без постепенного роллаута «независимый деплой» означает, что новая версия достаётся 100% пользователей в момент пуша. Это сводит на нет изоляцию отказов, обещанную в статье [Основы микрофронтендов](./01-microfrontends-fundamentals.md).
