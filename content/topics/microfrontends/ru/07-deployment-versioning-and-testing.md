# Деплой, версионирование и тестирование

## Независимые CI/CD-пайплайны на каждый микрофронтенд

```txt
checkout-repo/  → CI: lint → unit-тесты → build → публикация remoteEntry.js@2.4.1 на CDN → обновление манифеста
catalog-repo/   → CI: lint → unit-тесты → build → публикация remoteEntry.js@1.8.0 на CDN → обновление манифеста
```

Ни один из этих пайплайнов не блокируется другим. Это и есть организационная выгода из статьи 01, механически реализованная: каждый пайплайн работает по своему расписанию, и единственное, что может его заблокировать — его собственные тесты, а не флейки-тест соседней команды.

## Версионировать нужно контракт, а не всё приложение целиком

Частое заблуждение: раз это «микрофронтенд», значит его нужно версионировать целиком, как единый артефакт. На деле версионированию подлежит не всё приложение, а конкретно та поверхность, что пересекает границу между хостом и remote'ом:

- форма props/API экспортированных модулей (статья 04),
- мажорные версии shared-зависимостей (статья 03),
- версия дизайн-системы (статья 06),
- владение префиксом маршрута (статья 05).

Всё остальное — внутренняя реализация — может меняться свободно, без какой-либо координации, именно потому что не входит в контракт.

```json
// checkout-mfe/module-federation.manifest.json — публикуемый контракт, а не реализация
{
  "name": "checkout",
  "version": "2.4.1",
  "exposedModules": {
    "./CheckoutApp": {
      "propsSchema": { "onOrderComplete": "(orderId: string) => void" }
    }
  },
  "sharedDependencies": {
    "react": "^18.2.0"
  }
}
```

## Стратегии обратной совместимости при ломающих изменениях

Когда remote'у нужно внести ломающее изменение в свой экспортируемый контракт (например, `CheckoutApp` теперь требует новый обязательный prop), он не может просто задеплоить это — хост и любые другие потребители сломаются в рантайме, молча, ровно как в примере с рассинхроном версий дизайн-системы из статьи 06.

1. **Выставить новый версионированный путь модуля рядом со старым.** `./CheckoutApp` (v1) продолжает работать, добавляется `./CheckoutAppV2`; хост мигрирует по собственному расписанию, старый путь депрекейтится позже. Прямая параллель с версионированием REST API (`/v1/`, `/v2/`).
2. **Сделать новые props опциональными с разумными значениями по умолчанию** на один релиз, и только в следующем мажорном сделать их обязательными — после того как у потребителей было окно на миграцию. Тот же паттерн «expand and contract», что используется при безопасных миграциях схемы БД (см. вопрос о добавлении `NOT NULL`-колонки в статье про Prisma).
3. **Сообщать о депрекейшене через тот же контрактный пакет**, что используется для типов и документации — например, `@company/checkout-contract` с задокументированным таймлайном депрекейшена, а не устной договорённостью в Slack.

## Пирамида тестирования через границы MFE

**Unit-тесты** — внутри репозитория каждого микрофронтенда, тестируют его собственную внутреннюю логику и компоненты, как в любом обычном приложении. Здесь ничего специфичного для MFE нет.

**Контрактные тесты** — специально проверяют, что публичная поверхность именно этого микрофронтенда (props экспортированного компонента, форма публикуемых событий, версия shared-зависимости) соответствует задокументированному контракту. Запускаются в CI этого микрофронтенда на каждый коммит, **без необходимости, чтобы другая сторона была реально задеплоена**. Аналог consumer-driven contract testing из мира микросервисов (в духе Pact): хост определяет, что он ожидает от remote'а, а проверка запускается против реально собранного артефакта remote'а.

```ts
// checkout-mfe: контрактный тест — работает в CI checkout'а, хост не нужен
import { CheckoutApp } from './CheckoutApp';

test('CheckoutApp exposes onOrderComplete callback prop', () => {
  const props: React.ComponentProps<typeof CheckoutApp> = {
    onOrderComplete: (orderId: string) => {},
  };
  expect(() => render(<CheckoutApp {...props} />)).not.toThrow();
});
```

**E2E-тесты через собранное приложение целиком** — единственный уровень, который реально проверяет интеграцию: хост и настоящие remote'ы, загруженные вместе в браузере, например через Playwright/Cypress на стейджинге, где все remote'ы задеплоены в своих текущих версиях. Дорого, медленно, запускается реже (ночью или перед релизом) — но только этот уровень ловит реальные интеграционные баги (провал негоциации share scope, коллизии CSS), которые контрактные тесты в принципе не могут поймать, потому что тестируют каждую сторону изолированно.

## Постепенный роллаут новой версии remote'а через feature flag

Когда checkout выкатывает новую версию своего remote'а, вместо мгновенного переключения на 100% пользователей резолюция того, **какую версию отдавать**, ставится за feature flag (LaunchDarkly, GrowthBook или простой процентный роллаут собственной разработки) — обычно на уровне резолвинга dynamic remote (см. статью 03):

```ts
// резолюция манифеста теперь зависит от feature flag / процента роллаута
async function resolveCheckoutRemoteUrl(userId: string): Promise<string> {
  const isInRollout = await featureFlags.isEnabled('checkout-v2-4-1', { userId });
  return isInRollout
    ? 'https://cdn.company.com/checkout@2.4.1/remoteEntry.js'
    : 'https://cdn.company.com/checkout@2.3.0/remoteEntry.js';
}
```

Это позволяет команде выкатить новую версию remote'а на 5% пользователей, понаблюдать за уровнем ошибок в observability, и откатиться простым переключением флага — без единого передеплоя чего-либо, включая хост. Это и есть операционная отдача от dynamic remotes из статьи 03 в связке с независимыми CI/CD-пайплайнами.

## Почему cross-MFE observability сложнее, чем в монолите

В монолите один стектрейс покрывает весь запрос целиком: один деплой-артефакт, одна source map, один поток логов. В MFE-архитектуре одна ошибка, которую видит пользователь, может пересекать несколько независимо задеплоенных бандлов: ошибка возникает в компоненте из `checkout-mfe@2.4.1`, перехватывается error boundary в `host@8.1.0`, и стек вызовов проходит через `react@18.2.0`, загруженный из одной из нескольких потенциально активных копий (см. статью 03). Чтобы восстановить, что реально произошло, нужно:

1. **Сопоставить версии деплоя всех вовлечённых MFE на точный момент времени возникновения ошибки** (какая именно версия checkout была активна для этого пользователя в эту секунду, с учётом процента feature-flag-роллаута) — а не просто «текущий main branch».
2. **Source maps для каждого независимо собранного бандла**, загруженные в систему observability (Sentry и т.п.) с тегом версии конкретного MFE — иначе стектрейс превращается в бесполезный минифицированный мусор совсем не той сборки.
3. **Общий trace/session ID, прокидываемый через границы MFE** (например, внедрённый при первой загрузке страницы и считываемый инициализацией собственного error-tracking SDK каждого MFE), чтобы один дашборд мог сгруппировать все события одной пользовательской сессии, произошедшие в нескольких раздельно инструментированных приложениях.

Без осознанной инженерной работы над этими тремя пунктами «где-то в собранном приложении произошла ошибка» и «какая из 6 независимо задеплоенных частей, в какой именно версии, реально её вызвала» — это два принципиально разных вопроса, и именно в разрыве между ними теряется время реакции на инцидент.

## Типичные ошибки на интервью

- **«Версионирование микрофронтенда означает версионирование всего приложения как единого целого»** — версионированию подлежит только выставленный публичный контракт (props, shared-зависимости, дизайн-система, владение маршрутом); внутренняя реализация может меняться без какой-либо координации.

- **«Юнит-тестов и e2e-тестов достаточно, контрактные тесты — лишний уровень»** — контрактные тесты — это именно то, что позволяет каждой команде деплоить независимо, **не дожидаясь** прогона полного e2e против текущей задеплоенной версии всех остальных команд. Без них единственный способ проверить интеграцию — дорогой и медленный e2e, что на практике снова синхронизирует релизы всех команд.

- **«E2E-тесты через всё приложение заменяют необходимость в независимых пайплайнах»** — e2e по природе медленнее и происходит позже в пайплайне; если сделать его единственным гейтом перед деплоем, вы фактически воссоздаёте единый релизный поезд для всех команд — то есть уничтожаете саму цель независимости деплоя.

- **«Проблемы observability в MFE — те же самые, что в монолите, просто распределённые»** — специфическая сложность именно в том, чтобы сопоставить, **какая версия** каждого независимо задеплоенного, гейтованного feature-флагом remote'а была активна для конкретного пользователя в конкретный момент — монолиту с единой историей деплоя никогда не приходится это восстанавливать.

- **«Feature flag для роллаута новой версии remote'а — это приятное дополнение, а не необходимость»** — это фактический механизм, который делает независимый деплой операционно безопасным. Без постепенного роллаута «независимый деплой» на практике означает «блэст-радиус — 100% пользователей в момент пуша», что сводит на нет изоляцию отказов, обещанную в статье 01.
