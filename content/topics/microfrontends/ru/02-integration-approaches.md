# Способы интеграции микрофронтендов

## Ось сравнения: кто и когда разрешает зависимость

У всех способов интеграции микрофронтендов есть один общий вопрос, на который они отвечают по-разному: **в какой момент решается, какой код какой версии куда попадёт, и кто это решение принимает**. Это и есть ось, по которой интервьюеры на самом деле хотят, чтобы вы сравнивали подходы — не «какой лучше», а «когда происходит resolution»:

```txt
Build time                    Request time                  Runtime (браузер)
(на CI команды-хоста)          (на сервере/edge при запросе)  (при выполнении JS у пользователя)
       │                              │                               │
       ▼                              ▼                               ▼
npm-пакет собран в             Сервер/edge собирает           Браузер догружает remoteEntry.js
единый бандл хоста             HTML-фрагменты в одну          или резолвит import map в момент
заранее, до деплоя             страницу на каждый запрос      навигации пользователя
```

Чем правее на этой оси — тем позже принимается решение, тем больше гибкости (можно менять версию ремоута без пересборки хоста), но тем больше риск, что resolution упадёт или дублируется именно в момент, когда пользователь смотрит на экран.

## 1. Build-time интеграция (npm-пакеты)

Каждый микрофронтенд публикуется как версионированный npm-пакет. Хост устанавливает нужную версию и импортирует её как обычную зависимость — **во время своей сборки**.

```json
// host-app/package.json
{
  "dependencies": {
    "@company/checkout-mfe": "^2.3.0",
    "@company/catalog-mfe": "^1.8.1"
  }
}
```

```tsx
// host-app/src/App.tsx
import { CheckoutWidget } from '@company/checkout-mfe';
// Резолвится компилятором ХОСТА во время его собственной сборки —
// как любой обычный npm-импорт.

export function App() {
  return <CheckoutWidget />;
}
```

**Кто резолвит и когда:** сборщик хоста, во время `build` хоста. Никакой рантайм-магии — это просто импорт скомпилированного пакета.

**Плюсы:** максимально просто, полная типобезопасность (обычные `.d.ts`), tree-shaking работает как обычно, нет сетевых запросов в рантайме, нет риска рассинхрона версий React в браузере пользователя — все зависимости зафиксированы на этапе сборки хоста.

**Минусы — и здесь кроется частая путаница:** команда checkout может публиковать новую версию своего пакета когда угодно (это независимая разработка), но пока хост не обновит `package.json` и не пересоберёт/передеплоит своё приложение, пользователь новую версию не увидит. То есть build-time интеграция даёт **независимость разработки и версионирования**, но не даёт **независимости релиза работающего приложения** — деплой хоста остаётся узким местом. Если основная боль организации именно в том, что нужно ждать релизного окна хоста — этот подход её не решает.

## 2. Композиция на сервере (Server-Side Includes / шаблонная композиция)

Композиция происходит **на сервере или на edge, на каждый входящий запрос**. Слой композиции (обратный прокси, edge-функция, или отдельный «compositor» сервис вроде Tailor.js в экосистеме Node) запрашивает HTML-фрагмент у сервера каждого микрофронтенда и склеивает их в одну страницу до того, как она уйдёт в браузер.

```txt
                    ┌────────────────────────────┐
Запрос браузера ──► │ Compositor (edge/reverse   │
                    │ proxy, например Tailor.js) │
                    └────────────────────────────┘
                            │                │                │
                            ▼                ▼                ▼
                       Header MFE      Checkout MFE      Footer MFE
                      (свой сервер)    (свой сервер)    (свой сервер)
                       возвращает       возвращает       возвращает
                      HTML-фрагмент    HTML-фрагмент    HTML-фрагмент

                            │                │                │
                            ▼                ▼                ▼
                    Compositor склеивает фрагменты в один HTML
                    и отдаёт браузеру ОДНУ готовую страницу
```

```nginx
# Пример edge-композиции через SSI (Server Side Includes) в nginx
location / {
    ssi on;
}
```

```html
<!-- shell.html, отдаётся хостовым сервером -->
<body>
  <!--# include virtual="/fragments/header" -->
  <!--# include virtual="/fragments/checkout" -->
  <!--# include virtual="/fragments/footer" -->
</body>
```

**Кто резолвит и когда:** compositor (сервер/edge), на каждый HTTP-запрос. Это значит, что версию каждого фрагмента можно менять независимо и мгновенно — без пересборки других частей — потому что решение принимается заново при каждом запросе, а не один раз при сборке хоста.

**Плюсы:** страница приходит в браузер уже собранной — быстрый TTFB, работает даже без JS на клиенте (прогрессивно улучшаемо), отлично для SEO и контента, критичного для первой отрисовки.

**Минусы:** нужна инфраструктура композиции (edge-слой или отдельный сервис), интерактивность внутри фрагмента (клиентский JS, гидратация) — это уже отдельная забота каждого фрагмента, и синхронизировать поведение разных фрагментов друг с другом на клиенте сложнее, чем при клиентской композиции.

## 3. Iframe — «безопасный, но плохой» вариант по умолчанию

Iframe — единственный способ получить настоящую изоляцию JS, CSS и DOM: каждый iframe — отдельный browsing context со своим глобальным объектом `window`, своим деревом DOM, своими стилями. Ничто не «протекает» между родителем и iframe без явного `postMessage`.

```html
<!-- host shell -->
<iframe src="https://checkout.company.com/widget" title="Checkout"></iframe>
```

```ts
// Единственный канал общения — postMessage. Никакого прямого доступа к DOM/состоянию.
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://checkout.company.com') return; // всегда проверяем origin
  if (event.data.type === 'CHECKOUT_COMPLETE') {
    // обновить состояние хоста
  }
});
```

**Кто резолвит и когда:** браузер, в момент загрузки `<iframe src>` — полностью независимый навигационный контекст, никакой резолюции зависимостей между хостом и iframe не происходит вообще (в этом и есть изоляция).

**Почему это вариант «по умолчанию, но плохой»:**

- **Цена изоляции.** Именно то, что делает iframe безопасным (полностью отдельный контекст), делает шеринг общего дизайн-системного CSS, шрифтов, глобальных стилей практически невозможным без дублирования — каждый iframe тянет свои стили заново.
- **Цена UX.** Вложенные скроллбары, автоматическая подгонка высоты iframe под контент — известный хак (`ResizeObserver` + `postMessage`), фокус и таб-навигация не работают «сквозь» границу естественно, печать страницы часто ломается.
- **Боль роутинга и deep-linking.** URL в адресной строке браузера не отражает состояние внутри iframe само по себе — если пользователь на шаге 3 чекаута внутри iframe и обновит страницу или скопирует ссылку, состояние потеряется, если явно не синхронизировать через `history.pushState` и `postMessage`. Кнопка «назад» в браузере по умолчанию не работает так, как ожидает пользователь.

**Когда iframe — правильный выбор, а не компромисс.** Когда изоляция — это требование, а не побочный эффект: встраивание виджета от стороннего непроверенного вендора (платёжная форма, чат-виджет, реклама), где вы **сознательно** не хотите, чтобы этот код имел доступ к DOM и cookies остальной страницы. В этом случае недостатки iframe — это ровно та цена, которую вы готовы платить за настоящую песочницу.

## 4. Клиентская runtime-интеграция

Композиция происходит **в браузере пользователя, в момент выполнения JS** — обычно при переходе на маршрут, которому нужен конкретный микрофронтенд.

### Module Federation (Webpack 5 / Rspack)

Хост в рантайме загружает `remoteEntry.js` удалённого приложения и запрашивает у него нужный экспортированный модуль. Механика подробно разбирается в статье 03 — здесь важно зафиксировать: **резолюция происходит в браузере, в момент запроса модуля**, включая согласование версий общих зависимостей (React и т.д.) между хостом и ремоутом.

```ts
// host: динамическая загрузка удалённого модуля во время навигации
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));
```

### single-spa

Фреймворк-агностичный оркестратор: root-конфиг регистрирует набор «приложений», каждое со своей activity-функцией (когда это приложение должно быть смонтировано, обычно на основе маршрута), и каждое приложение — отдельный бандл, который single-spa монтирует/размонтирует по своему жизненному циклу. Приложения могут быть на разных фреймворках (React, Angular, Vue) одновременно на одной странице.

```ts
// root-config.js
registerApplication({
  name: '@company/checkout',
  app: () => System.import('@company/checkout'),
  activeWhen: (location) => location.pathname.startsWith('/checkout'),
});
start();
```

### Нативные ESM + import maps

Без сборщик-специфичного рантайма вообще: браузер нативно резолвит граф импортов, а **import map** позволяет переопределить, куда указывает голый спецификатор (`"react"`) — на CDN-URL с конкретной версией.

```html
<script type="importmap">
{
  "imports": {
    "react": "https://cdn.company.com/react@18.2.0/index.js",
    "checkout-mfe": "https://cdn.company.com/checkout-mfe@2.3.0/index.js"
  }
}
</script>
<script type="module">
  import { CheckoutWidget } from 'checkout-mfe'; // резолвится браузером по import map
</script>
```

**Общее для всех трёх:** resolution происходит на клиенте, значит его можно поменять без пересборки хоста (обновили import map или манифест ремоута — все получили новую версию при следующей загрузке), но и сломаться он может тоже на клиенте, у живого пользователя, без единой точки, где ошибку можно перехватить до того, как она долетит до продакшена.

## Типичные ошибки на интервью

- **«Микрофронтенды — это всегда Module Federation»** — Module Federation лишь один из четырёх реальных подходов, и не всегда правильный. Server-side composition часто лучше для контент-хэви страниц, iframe — единственно верный выбор для недоверенного стороннего кода.

- **«Iframe — это всегда плохо, современные подходы его заменили»** — iframe остаётся правильным выбором именно тогда, когда нужна настоящая изоляция от недоверенного кода (сторонние виджеты, встраиваемые платёжные формы). Недостатки iframe (UX, роутинг) — это цена реальной песочницы, а не признак устаревшего инструмента.

- **«npm-пакет с версионированием — это уже полноценные микрофронтенды»** — build-time интеграция даёт независимость разработки, но не независимость деплоя работающего приложения: пользователь не увидит новую версию, пока хост не пересоберётся и не передеплоится. Это частичное решение организационной проблемы, не полное.

- **«Все подходы одинаково решают проблему общих зависимостей»** — нет: чем позже происходит resolution (ближе к рантайму браузера), тем острее встаёт вопрос синхронизации версий React, дизайн-системы и роутера между независимо задеплоенными частями — эта проблема специфична для client-side runtime интеграции и разбирается детально в статье 03.

- **«Правильный подход можно выбрать один раз для всего продукта»** — на практике зрелые организации комбинируют подходы: server-side composition для контентных страниц (SEO-критично), client-side runtime для интерактивных SPA-разделов, iframe точечно для стороннего эмбеда. Это не признак незрелой архитектуры, а осознанный выбор под разные требования разных частей продукта.
