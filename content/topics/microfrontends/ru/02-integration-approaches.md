# Способы интеграции микрофронтендов

## Ось сравнения: кто и когда разрешает зависимость

У всех способов интеграции микрофронтендов есть один общий вопрос, и отвечают они на него по-разному. **В какой момент решается, какой код какой версии куда попадёт? И кто принимает это решение?** Это и есть ось, по которой интервьюеры хотят, чтобы вы сравнивали подходы. Вопрос не в том, какой подход лучше, а в том, когда происходит разрешение зависимостей (resolution):

```txt
Build time — на CI команды-хоста
  npm-пакет собран в единый бандл хоста заранее, до деплоя.
    │
    ▼
Request time — на сервере или edge, на каждый запрос
  Сервер собирает HTML-фрагменты в одну страницу на каждый
  входящий запрос.
    │
    ▼
Runtime — в браузере, при выполнении JS у пользователя
  Браузер догружает remoteEntry.js или резолвит import map
  в момент навигации пользователя.
```

Чем ниже по этому списку — тем позже принимается решение. Позже значит гибче: версию ремоута можно менять без пересборки хоста. Позже значит и рискованнее. Разрешение может упасть или подтянуть зависимость дважды ровно в тот момент, когда пользователь смотрит на экран.

## 1. Build-time интеграция (npm-пакеты)

Каждый микрофронтенд публикуется как версионированный npm-пакет. Хост устанавливает нужную версию и импортирует её как обычную зависимость — **во время своей сборки**.

```json
// host-app/package.json
{
  "dependencies": {
    "@company/checkout-mfe": "^2.3.0",
    "@company/catalog-mfe": "^1.8.1"
  }
}
```

```tsx
// host-app/src/App.tsx
import { CheckoutWidget } from '@company/checkout-mfe';
// Резолвится компилятором ХОСТА во время его собственной сборки —
// как любой обычный npm-импорт.

export function App() {
  return <CheckoutWidget />;
}
```

**Кто резолвит и когда:** сборщик хоста, во время `build` хоста. Никакой рантайм-магии — это просто импорт скомпилированного пакета.

**Плюсы:**

- Максимально просто.
- Полная типобезопасность через обычные `.d.ts`.
- Tree-shaking работает как обычно.
- Нет сетевых запросов в рантайме.
- Нет риска рассинхрона версий React в браузере пользователя: все зависимости зафиксированы на этапе сборки хоста.

**Минусы — и здесь кроется частая путаница.** Команда checkout может публиковать новую версию своего пакета когда угодно, и это действительно независимая разработка. Но пока хост не обновит `package.json` и не передеплоит своё приложение, пользователь новую версию не увидит.

Build-time интеграция даёт **независимость разработки и версионирования**. Независимости релиза работающего приложения она не даёт: деплой хоста остаётся узким местом. Если основная боль организации именно в ожидании релизного окна хоста, этот подход её не решает.

## 2. Композиция на сервере (Server-Side Includes / шаблонная композиция)

Композиция происходит **на сервере или на edge, на каждый входящий запрос**. Слой композиции — это обратный прокси, edge-функция или отдельный сервис-compositor вроде Tailor.js в экосистеме Node. Он запрашивает HTML-фрагмент у сервера каждого микрофронтенда. Затем он склеивает фрагменты в одну страницу, до того как она уйдёт в браузер.

```txt
                  ┌────────────────────────────┐
Запрос браузера ─►│ Compositor (edge/reverse   │
                  │ proxy, например Tailor.js) │
                  └────────────────────────────┘
                          │                │                │
                          ▼                ▼                ▼
                     Header MFE      Checkout MFE      Footer MFE
                    (свой сервер)    (свой сервер)    (свой сервер)
                     возвращает       возвращает       возвращает
                    HTML-фрагмент    HTML-фрагмент    HTML-фрагмент

                          │                │                │
                          ▼                ▼                ▼
                  Compositor склеивает фрагменты в один HTML
                  и отдаёт браузеру одну готовую страницу
```

```nginx
# Пример edge-композиции через SSI (Server Side Includes) в nginx
location / {
    ssi on;
}
```

```html
<!-- shell.html, отдаётся хостовым сервером -->
<body>
  <!--# include virtual="/fragments/header" -->
  <!--# include virtual="/fragments/checkout" -->
  <!--# include virtual="/fragments/footer" -->
</body>
```

**Кто резолвит и когда:** compositor (сервер/edge), на каждый HTTP-запрос. Это значит, что версию каждого фрагмента можно менять независимо и мгновенно, без пересборки других частей. Решение принимается заново при каждом запросе, а не один раз при сборке хоста.

**Плюсы:** страница приходит в браузер уже собранной. Это даёт быстрый TTFB (time to first byte — время до первого байта) и работает даже без JS на клиенте. Способ отлично подходит для поисковой оптимизации (SEO) и для контента, критичного для первой отрисовки.

**Минусы:**

- Нужна инфраструктура композиции: edge-слой или отдельный сервис.
- Интерактивность внутри фрагмента (клиентский JS, гидратация) — забота самого фрагмента.
- Синхронизировать поведение фрагментов друг с другом на клиенте сложнее, чем при клиентской композиции.

## 3. Iframe — «безопасный, но плохой» вариант по умолчанию

Iframe — единственный способ получить настоящую изоляцию JS, CSS и DOM (document object model, дерево документа). Каждый iframe — это отдельный browsing context, отдельный контекст просмотра со своим глобальным объектом `window`, своим деревом DOM и своими стилями. Ничто не «протекает» между родителем и iframe без явного `postMessage`.

```html
<!-- host shell -->
<iframe src="https://checkout.company.com/widget" title="Checkout"></iframe>
```

```ts
// Единственный канал общения — postMessage. Никакого прямого доступа к DOM/состоянию.
window.addEventListener('message', (event) => {
  if (event.origin !== 'https://checkout.company.com') return; // всегда проверяем origin
  if (event.data.type === 'CHECKOUT_COMPLETE') {
    // обновить состояние хоста
  }
});
```

**Кто резолвит и когда:** браузер, в момент загрузки `<iframe src>`. Это полностью независимый навигационный контекст. Никакого разрешения зависимостей между хостом и iframe не происходит вообще — в этом и есть изоляция.

**Почему это вариант «по умолчанию, но плохой»:**

- **Цена изоляции.** Iframe безопасен именно потому, что это полностью отдельный контекст. Та же отдельность делает переиспользование общего CSS дизайн-системы, шрифтов и глобальных стилей практически невозможным без дублирования. Каждый iframe тянет свои стили заново.
- **Цена удобства.** Вложенные скроллбары. Автоматическая подгонка высоты iframe под контент — известный хак на `ResizeObserver` и `postMessage`. Фокус и таб-навигация не работают «сквозь» границу естественно. Печать страницы часто ломается.
- **Боль роутинга и глубоких ссылок.** URL в адресной строке браузера сам по себе не отражает состояние внутри iframe. Допустим, пользователь на шаге 3 чекаута внутри iframe обновит страницу или скопирует ссылку. Состояние потеряется, если явно не синхронизировать его через `history.pushState` и `postMessage`. Кнопка «назад» тоже по умолчанию работает не так, как ожидает пользователь.

**Когда iframe — правильный выбор, а не компромисс.** Когда изоляция это требование, а не побочный эффект. Так бывает при встраивании виджета от стороннего непроверенного вендора: платёжная форма, чат-виджет, реклама. Вы **сознательно** не хотите, чтобы этот код имел доступ к DOM и cookies остальной страницы. В этом случае недостатки iframe — ровно та цена, которую вы платите за настоящую песочницу.

## 4. Клиентская runtime-интеграция

Композиция происходит **в браузере пользователя, в момент выполнения JS** — обычно при переходе на маршрут, которому нужен конкретный микрофронтенд.

### Module Federation (Webpack 5 / Rspack)

Хост в рантайме загружает `remoteEntry.js` удалённого приложения и запрашивает у него нужный экспортированный модуль. Статья [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md) разбирает механику подробно. Здесь важно зафиксировать другое: **резолюция происходит в браузере, в момент запроса модуля**. Сюда же входит согласование версий общих зависимостей — например, React — между хостом и ремоутом.

```ts
// host: динамическая загрузка удалённого модуля во время навигации
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));
```

### single-spa

Фреймворк-агностичный оркестратор. Root-конфиг регистрирует набор именованных приложений. У каждого своя activity-функция: она решает, когда это приложение должно быть смонтировано, — обычно на основе маршрута. Каждое приложение это отдельный бандл, который single-spa монтирует и размонтирует по своему жизненному циклу. Приложения могут быть на разных фреймворках (React, Angular, Vue) одновременно на одной странице.

```ts
// root-config.js
registerApplication({
  name: '@company/checkout',
  app: () => System.import('@company/checkout'),
  activeWhen: (location) => location.pathname.startsWith('/checkout'),
});
start();
```

### Нативные ESM + import maps

Без сборщик-специфичного рантайма вообще. Браузер нативно резолвит граф импортов ECMAScript-модулей (ESM). А **import map** позволяет переопределить, куда указывает голый спецификатор (`"react"`) — на URL в CDN (content delivery network, сеть доставки контента) с конкретной версией.

```html
<script type="importmap">
{
  "imports": {
    "react": "https://cdn.company.com/react@18.2.0/index.js",
    "checkout-mfe": "https://cdn.company.com/checkout-mfe@2.3.0/index.js"
  }
}
</script>
<script type="module">
  // резолвится браузером по import map
  import { CheckoutWidget } from 'checkout-mfe';
</script>
```

**Общее для всех трёх:** разрешение зависимостей происходит на клиенте. Значит, его можно поменять без пересборки хоста: обновили import map или манифест ремоута — и все получают новую версию при следующей загрузке.

Значит и сломаться оно может на клиенте, у живого пользователя. Нет единой точки, где ошибку можно перехватить до того, как она долетит до продакшена.

## Сводная таблица

| | Build-time (npm-пакет) | Композиция на сервере (SSI — server-side includes) | Iframe | Клиентский рантайм (Module Federation, single-spa, ESM) |
|---|---|---|---|---|
| **Когда резолвится** | Сборка хоста | Каждый HTTP-запрос | Загрузка iframe | Рантайм браузера |
| **Изоляция** | Нет (общий бандл) | Нет на клиенте (общий DOM) | Полная (отдельный browsing context) | Частичная (общий DOM, общий JS-realm) |
| **Реальная независимость деплоя** | Только разработки | Да, на каждый запрос | Да, полная | Да, на каждую загрузку |
| **Общие CSS и шрифты** | Тривиально | Нужна дисциплина | Практически невозможно без дублирования | Нужна дисциплина, см. [Стилизация и изоляция](./06-styling-and-isolation.md) |
| **Выдача в поиске / без JS** | Как у хоста | Отлично | Плохо | Плохо без SSR (server-side rendering) |
| **Типичный кейс** | Внутренняя библиотека команды | Страницы, насыщенные контентом: медиа, e-commerce лендинг | Недоверенный сторонний виджет | Много команд, одно одностраничное приложение, разные фреймворки |

## Типичные ошибки на интервью

- **«Микрофронтенды — это всегда Module Federation»** — Module Federation лишь один из четырёх реальных подходов, и не всегда правильный. Композиция на сервере часто лучше для страниц, насыщенных контентом. Iframe — единственно верный выбор для недоверенного стороннего кода.

- **«Iframe — это всегда плохо, современные подходы его заменили»** — iframe остаётся правильным выбором, когда нужна настоящая изоляция от недоверенного кода. Обычные случаи — сторонние виджеты и встраиваемые платёжные формы. Недостатки iframe в удобстве и роутинге — это цена реальной песочницы, а не признак устаревшего инструмента.

- **«npm-пакет с версионированием — это уже полноценные микрофронтенды»** — build-time интеграция даёт независимость разработки, но не независимость деплоя работающего приложения. Пользователь не увидит новую версию, пока хост не пересоберётся и не передеплоится. Это частичное решение организационной проблемы, не полное.

- **«Все подходы одинаково решают проблему общих зависимостей»** — нет. Чем позже происходит разрешение зависимостей, тем острее встаёт вопрос синхронизации версий React, дизайн-системы и роутера между независимо задеплоенными частями. Статья [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md) разбирает эту проблему детально: она специфична для клиентской runtime-интеграции.

- **«Правильный подход можно выбрать один раз для всего продукта»** — на практике зрелые организации комбинируют подходы. Композиция на сервере идёт на контентные страницы, где важна выдача в поиске. Клиентский рантайм идёт в интерактивные одностраничные разделы, а iframe используют точечно для стороннего встраивания. Это не признак незрелой архитектуры, а осознанный выбор под разные требования разных частей продукта.
