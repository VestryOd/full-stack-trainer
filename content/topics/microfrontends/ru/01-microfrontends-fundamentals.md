# Основы микрофронтендов

## Что такое микрофронтенд архитектура

**Микрофронтенд (micro-frontend, MFE)** — независимо деплоящаяся, независимо разрабатываемая единица фронтенда, которая на этапе сборки, запроса или выполнения в браузере композируется с другими такими же единицами в одно работающее приложение для пользователя.

Ключевое слово здесь — **независимо деплоящаяся**. Это не про то, как выглядит код в репозитории, а про то, что происходит в CI/CD и в проде:

```txt
Модульный монолит фронтенда:              Микрофронтенд-архитектура:

repo/                                      checkout-team/repo/  → свой пайплайн → свой деплой
├── modules/                               catalog-team/repo/   → свой пайплайн → свой деплой
│   ├── checkout/                          account-team/repo/   → свой пайплайн → свой деплой
│   ├── catalog/
│   └── account/                           Композиция происходит ОТДЕЛЬНО от каждого
└── main.tsx                               из этих деплоев — во время сборки шелла,
                                            на сервере (SSI) или в браузере (runtime).
Один build, один deploy.
Изменение в checkout требует              Команда checkout может задеплоить свою часть
пересборки и передеплоя ВСЕГО.            в 15:00, ничего не спрашивая у catalog и account.
```

Это прямая параллель модульному монолиту в бэкенде (см. статью «Монолит vs Микросервисы» в разделе Architecture): модульность кода и независимость деплоя — два разных, ортогональных свойства. Можно иметь прекрасно модульный код и один общий деплой (модульный монолит), а можно иметь плохо изолированный код, который тем не менее деплоится по частям (плохо спроектированные, но всё же микрофронтенды).

## Почему эта архитектура вообще существует

Микрофронтенды не решают техническую проблему «слишком много кода». Они решают **организационную** проблему: как позволить нескольким командам разрабатывать один пользовательский продукт, не блокируя друг друга.

### 1. Масштабирование организации, а не кода

Если над одним SPA работает 3 фронтенд-инженера — единый репозиторий и общий деплой почти всегда выигрывают. Если над одним продуктом работает 150 фронтенд-инженеров в 12 командах — единый пайплайн деплоя становится узким местом: любой мердж-конфликт, любой флейки-тест, любой сломанный E2E блокирует релиз для всех 12 команд одновременно.

```txt
Закон Конвея для фронтенда:
если продукт владеют N независимых команд, продукт стремится
структурироваться в N крупных фронтенд-единиц — с рабочим API
между ними или без него.
```

### 2. Независимые циклы релизов

Команда checkout может хотеть деплоить 10 раз в день (эксперименты с конверсией). Команда account может деплоить раз в неделю (изменения затрагивают комплаенс и требуют ручного ревью). В едином деплое обе команды вынуждены двигаться со скоростью самой медленной и самой осторожной части системы.

### 3. Гетерогенность стека (реже основная причина, чем кажется)

Иногда MFE позволяют одной команде остаться на Angular, пока остальная организация переходит на React — например, после слияния компаний (M&A) с двумя разными фронтенд-платформами, или при постепенной замене legacy-приложения (см. паттерн Strangler Fig в статье о routing). Это реальная причина, но на практике она встречается реже, чем организационная автономия — большинство компаний со временем всё равно стандартизируются на одном фреймворке.

## Основной trade-off — сформулируем явно

```txt
┌────────────────────────────────┬───────────────────────────────────┐
│ Вы получаете                   │ Вы платите                        │
├────────────────────────────────┼───────────────────────────────────┤
│ Автономию команд:              │ Рантайм-сложность:                │
│ деплой без координации         │ версии, зависимости и композиция  │
│                                │ должны согласовываться в браузере │
│                                │ или на сервере во время запроса   │
├────────────────────────────────┼───────────────────────────────────┤
│ Изоляцию отказов на уровне     │ Накладные расходы на общие        │
│ деплоя: сломанный релиз одной  │ зависимости: React, дизайн-       │
│ команды не блокирует другие    │ система, роутер — их версии       │
│                                │ нужно явно согласовывать          │
├────────────────────────────────┼───────────────────────────────────┤
│ Возможность гетерогенного      │ Cтоимость согласованности:        │
│ стека (реже нужна на практике) │ UX, стили, поведение должны       │
│                                │ выглядеть как ОДИН продукт,       │
│                                │ хотя пишутся разными командами    │
└────────────────────────────────┴───────────────────────────────────┘
```

Это ровно тот же trade-off, что и «монолит vs микросервисы», перенесённый в браузер — с одним отличием: на бэкенде границы сервисов невидимы пользователю. Во фронтенде плохо проведённая граница между микрофронтендами пользователь видит буквально — разъезжающиеся шрифты, дублирующиеся модальные окна, доля секунды белого экрана между переходами.

## Самая частая ошибка на интервью: MFE ≠ просто разбиение на папки

Это единственная самая распространённая путаница на тему микрофронтендов, и интервьюеры целенаправленно её проверяют.

**Неверно:** «У нас большое приложение, мы разбили его на модули `checkout/`, `catalog/`, `account/`, у каждого свой публичный API — значит, у нас микрофронтенды».

Это описывает **модульный монолит**, а не микрофронтенды. Признак, который отличает одно от другого — не структура папок, а ответ на один конкретный вопрос:

> **Может ли команда X задеплоить свою часть в продакшен прямо сейчас, не дожидаясь и не координируясь с командой Y, и без пересборки/передеплоя частей, которые принадлежат Y?**

Если ответ «нет» — потому что всё собирается одним `webpack build` и деплоится одним артефактом — перед вами модульный монолит, сколь угодно хорошо структурированный. Микрофронтенды начинаются только там, где композиция происходит **после** того, как каждая часть уже собрана и задеплоена независимо — во время запроса на сервере или во время выполнения в браузере пользователя.

```txt
Модульный монолит фронтенда:              Настоящие микрофронтенды:

Разработка: раздельные модули             Разработка: раздельные репозитории
Сборка:     ОДИН build                    Сборка:     N независимых build'ов
Деплой:     ОДИН артефакт                 Деплой:     N независимых деплоев
Композиция: во время сборки (import)      Композиция: во время запроса/рантайма
                                                       (remoteEntry, SSI, iframe)
```

Держите этот критерий в голове для всех следующих статей — особенно для разбора Module Federation: сам факт использования `ModuleFederationPlugin` ничего не говорит о том, есть ли у вас микрофронтенды. Module Federation можно использовать и внутри модульного монолита (одна команда, один общий релизный цикл) просто ради динамической загрузки кода — это не делает архитектуру микрофронтендной. Микрофронтендной её делает организационное решение о независимом деплое, а Module Federation — лишь один из механизмов, которым эту независимость можно технически реализовать (подробнее — в статье 03).

## Когда микрофронтенды оправданы

- Несколько **действительно независимых** команд, которым нужно деплоить без координации друг с другом — и это уже так организационно, не в теории.
- Продукт состоит из ясно очерченных бизнес-доменов (checkout, каталог, личный кабинет), которыми исторически или организационно владеют разные команды.
- Слияние компаний или поглощение: две существующих кодовых базы нужно показывать под одним доменом без немедленной полной переписи.
- Инкрементальная замена легаси-приложения (Strangler Fig для фронтенда): новый функционал добавляется как отдельный микрофронтенд, старое приложение постепенно съёживается.

## Когда микрофронтенды — плохая идея (и почему это главная ловушка)

- **«У нас большое приложение» — само по себе не причина.** Большое приложение с одной командой решается модульным монолитом (feature-sliced структура, чёткие границы модулей, публичные API между ними) — без единой из описанных выше цен.
- **«У нас медленная сборка / медленные тесты»** — это проблема тулинга (code splitting, incremental build, кэш тест-раннера), а не проблема, которую решает независимый деплой.
- **«Это модно и хорошо смотрится в резюме»** — реальная и частая причина на практике, но не инженерное обоснование. Микрофронтенды добавляют операционную сложность, которая должна окупаться реальной организационной автономией — иначе это чистый убыток.
- **Одна команда, которая искусственно создаёт себе несколько «микрофронтендов»** — координационные издержки те же, что при нескольких командах, а выгоды автономии нет: не от кого быть автономным.

## Итог

Микрофронтенды — это организационный паттерн, реализованный через рантайм- или билд-тайм-механизм. Решение принимается на уровне «сколько у нас независимых команд и как часто им нужно деплоить порознь», а не на уровне «как разбить компоненты на файлы». Следующая статья разбирает, какими конкретно механизмами эта независимость технически достигается — от iframe до Module Federation — и по какой оси их стоит сравнивать.

## Типичные ошибки на интервью

- **«Мы разбили приложение на модули с чёткими границами — значит, у нас микрофронтенды»** — нет, это модульный монолит. Микрофронтенды определяются независимостью деплоя, а не структурой кода. Проверочный вопрос: может ли одна команда задеплоить свою часть без пересборки/передеплоя частей других команд?

- **«Использование Module Federation означает, что у нас микрофронтенды»** — Module Federation — механизм динамической загрузки модулей в рантайме. Его можно использовать внутри единого релизного цикла одной командой просто для code splitting — это не микрофронтенды. Архитектуру определяет организационное решение о независимом деплое, а не конкретный инструмент.

- **«Микрофронтенды всегда улучшают производительность»** — обычно наоборот: без аккуратного управления shared-зависимостями (см. статью 03) микрофронтенды приводят к дублирующейся загрузке React, дизайн-системы и других общих библиотек, что делает страницу тяжелее, а не легче.

- **«Раз приложение большое, нужны микрофронтенды»** — размер кода не является достаточным основанием. Определяющий фактор — организационная структура и потребность в независимых циклах релиза. Большое приложение с одной командой почти всегда лучше решается модульным монолитом.

- **«Микрофронтенды = микросервисы для фронтенда, поэтому все трейдоффы идентичны»** — общая идея (независимый деплой, cost автономии vs сложности) переносится, но во фронтенде цена согласованности видна пользователю напрямую (визуальные и UX-несоответствия), а рантайм-композиция происходит в браузере пользователя, а не на защищённом внутреннем сервере — это создаёт свои специфичные проблемы (см. статьи 03 и 06).
