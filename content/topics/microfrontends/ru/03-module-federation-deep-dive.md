# Module Federation: как это работает внутри

Эта статья — самая техническая в разделе. Предыдущие две отвечали, что такое микрофронтенд (MFE) и какие бывают способы интеграции. Здесь разбирается механика конкретно Module Federation (Webpack 5 / Rspack). Именно на её деталях интервьюеры проверяют, работали ли вы с этим в проде или только читали документацию.

## Модель host/remote

**Host** — приложение, которое во время выполнения загружает и монтирует код, которым не владеет. **Remote** — приложение, которое публикует часть своего кода для загрузки другими. Это не архитектурная иерархия, а роль в конкретном отношении. Одно и то же приложение может быть хостом для одних модулей и ремоутом для других.

```txt
                    ┌──────────────────────────────┐
                    │ Host (shell)                 │
                    │ webpack.config.js:           │
                    │ remotes: {                   │
                    │   checkout: 'checkout@       │
                    │   http://.../remoteEntry.js' │
                    │ }                            │
                    └──────────────────────────────┘
                                   │ рантайм fetch
                                   ▼
                    ┌──────────────────────────────┐
                    │ Remote (checkout)            │
                    │ webpack.config.js:           │
                    │ exposes: {                   │
                    │   './CheckoutApp': ...       │
                    │ }                            │
                    │ filename: 'remoteEntry.js'   │
                    └──────────────────────────────┘
```

## remoteEntry.js — что внутри

`remoteEntry.js` — это не бандл приложения. Это маленький **контейнер** (container), который выполняет две задачи и ничего больше. Концептуально (сильно упрощённо, реальный код генерируется webpack-рантаймом) его форма выглядит так:

```js
// Упрощённая концептуальная форма того, что публикует remoteEntry.js
window.checkout = {
  // 1. Регистрирует версии зависимостей ремоута в общей share scope хоста
  init: (hostShareScope) => {
    // сверяет react/react-dom этого ремоута с тем, что уже есть в hostShareScope
  },

  // 2. Возвращает асинхронную фабрику для запрошенного экспортированного модуля
  get: (moduleRequest) => {
    // moduleRequest === './CheckoutApp' → возвращает Promise<() => Module>
  },
};
```

Сам код `CheckoutApp` и всё, что он использует, лежит в **отдельных чанках**, которые `get()` подгружает лениво. Файл `remoteEntry.js` сам по себе крошечный: это точка входа, а не приложение целиком.

```js
// webpack.config.js — remote "checkout"
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'checkout',
      filename: 'remoteEntry.js',
      exposes: {
        './CheckoutApp': './src/CheckoutApp',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
      },
    }),
  ],
};
```

```js
// webpack.config.js — host
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        checkout: 'checkout@http://localhost:3001/remoteEntry.js',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
      },
    }),
  ],
};
```

```tsx
// host: динамическая загрузка экспортированного модуля во время навигации
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));
// "checkout/CheckoutApp" резолвится в: сходить за remoteEntry.js ремоута "checkout",
// вызвать его get('./CheckoutApp'), выполнить вернувшуюся фабрику.
```

## Bootstrap-паттерн — зачем нужен странный `import('./bootstrap')`

Почти в каждом примере Module Federation входная точка выглядит так:

```ts
// index.ts
import('./bootstrap'); // именно динамический import, не статический
```

```tsx
// bootstrap.tsx — реальная точка входа приложения
import ReactDOM from 'react-dom/client';
import App from './App';
ReactDOM.createRoot(document.getElementById('root')!).render(<App />);
```

Причина не стилистическая. Webpack должен успеть выполнить `init()` контейнера — это и есть согласование общих зависимостей — **до того**, как любой код начнёт реально импортировать `react`. Статический `import` на верхнем уровне модуля выполняется синхронно при загрузке скрипта, до того как у рантайма появляется шанс дождаться `init()` от других контейнеров.

Динамический `import()` создаёт асинхронную границу, за которой webpack гарантированно успевает согласовать share scope. Без этого паттерна вы получаете ошибку рантайма: `Shared module is not available for eager consumption`. Обычно это первый признак, что кто-то из команды убрал `bootstrap.ts` ради «более чистого» кода.

## Static vs Dynamic remotes

**Static remote** — URL ремоута зашит в `webpack.config.js` во время сборки хоста:

```js
remotes: {
  checkout: 'checkout@http://localhost:3001/remoteEntry.js',
}
```

Просто, но URL нельзя поменять без пересборки хоста. Это тот же компромисс, что у build-time интеграции из статьи [Способы интеграции микрофронтендов](./02-integration-approaches.md), только на один уровень глубже. Сама *ссылка* на ремоут фиксируется во время сборки, хотя код ремоута всё ещё грузится в рантайме.

**Dynamic remote** — URL резолвится в рантайме, обычно через манифест, который хост запрашивает ещё до того, как узнает, куда идти за `remoteEntry.js`:

```js
// webpack.config.js — host, dynamic remote
remotes: {
  checkout: `promise new Promise((resolve) => {
    fetch('/api/remotes-manifest.json')
      .then((res) => res.json())
      .then((manifest) => {
        const script = document.createElement('script');
        script.src = manifest.checkout.url; // например, .../checkout@2.4.1/remoteEntry.js
        script.onload = () => {
          const proxy = {
            get: (request) => window.checkout.get(request),
            init: (shareScope) => {
              try {
                return window.checkout.init(shareScope);
              } catch (e) {
                console.warn('checkout container already initialized');
              }
            },
          };
          resolve(proxy);
        };
        document.head.appendChild(script);
      });
  })`,
}
```

Это позволяет менять версию ремоута (например, откатить на предыдущую при инциденте) правкой манифеста, без пересборки хоста. Цена: разрешение зависимостей происходит позже и добавляет лишний поход в сеть за манифестом, ещё до загрузки самого `remoteEntry.js`.

## Алгоритм согласования shared-зависимостей

Это раздел, ради которого сеньоров и спрашивают про Module Federation. Именно здесь возникают продовые баги, которые невозможно отладить, не понимая механику.

Каждый контейнер — и хост, и каждый ремоут — при инициализации регистрирует версии своих общих модулей в общем объекте. Этот объект называется **share scope**. Теперь допустим, что модуль внутри контейнера делает `import React from 'react'`. Скомпилированный код обращается не напрямую к своей локальной копии `react`, а к рантайм-функции разрешения через share scope.

Алгоритм:

1. **Проверить share scope.** Есть ли там уже версия `react`, удовлетворяющая `requiredVersion` этого консьюмера?
2. **Если да и `singleton: true`** — переиспользовать уже загруженный инстанс. Новый сетевой запрос не делается, вторая копия `react` в память не грузится.
3. **Если совместимой версии нет** или требование не выполняется, контейнер загружает **свою собственную резервную копию** зависимости. Именно поэтому каждый remote-бандл содержит собственный fallback-чанк с `react` внутри. Это не ошибка сборки: Module Federation обязан иметь fallback на случай, если в share scope ничего подходящего не окажется.
4. **`strictVersion: true`** — если требуемая версия не подходит, рантайм бросает ошибку вместо тихой загрузки резервной копии. Полезно на стейджинге и в CI (continuous integration): так рассинхрон версий ловится явно, а не превращается молча во вторую копию React в проде.
5. **`eager: true`** — модуль включается прямо в основной чанк вместо ленивой асинхронной загрузки. Это **альтернатива** асинхронной границе `import('./bootstrap')` из раздела выше, а не дополнение к ней. Документация webpack предлагает эти два способа как два выхода из одной ошибки и рекомендует асинхронную границу. Ставьте `eager`, когда точка входа хоста обязана потреблять общие модули синхронно. Вне точки входа с ним надо быть осторожным. Такой модуль регистрируется в share scope немедленно при выполнении, до того как у других контейнеров появился шанс договориться. Так он способен сломать всё согласование, зарегистрировав версию раньше времени.

```js
shared: {
  react: {
    // один инстанс на всё приложение — обязателен для React
    singleton: true,
    // semver-диапазон, который ожидает этот контейнер
    requiredVersion: '^18.2.0',
    // бросить ошибку, а не тихо задублировать, если диапазон не подходит
    strictVersion: true,
    // грузить лениво и асинхронно — рекомендуемое значение по умолчанию
    eager: false,
  },
}
```

## Почему «в деве работает, а в проде две копии React» — и как это дебажить

Это самый известный класс продовых инцидентов в Module Federation, и он почти всегда сводится к одному из трёх сценариев.

**Сценарий 1 — гонка инициализации.** Согласование share scope зависит от **порядка**, в котором контейнеры успевают вызвать `init()`. В dev-режиме этот порядок почти всегда одинаковый: webpack-dev-server, HMR (hot module replacement, горячая замена модулей), всё локально, задержки сети минимальны и стабильны.

В проде ремоут грузится с другого CDN (content delivery network, сеть доставки контента) или origin, с другой латентностью. Он может прийти раньше, чем хост успел зарегистрировать свою версию `react` в share scope. Тогда ремоут не находит совместимой версии в момент своей инициализации и грузит собственный fallback `react`. На странице оказывается два инстанса React одновременно.

**Сценарий 2 — реальный рассинхрон версий.** Хост собран с `react@18.2.0`. Ремоут со своим независимым релизным циклом обновился до `react@18.3.0`, а `requiredVersion` остался `^18.0.0` без `strictVersion`. Semver формально совместим.

Но при `singleton: true` без `strictVersion` рантайм может выбрать версию, которую команда ремоута не тестировала. Сработает это молча, без ошибки, где-то в глубине компонентного дерева.

**Сценарий 3 — симптом, по которому это обычно и находят.** Классическая ошибка — `Invalid hook call. Hooks can only be called inside the body of a function component`, при том что с виду хуки используются правильно.

Причина: React хранит внутренний диспетчер хуков как синглтон на уровне модуля. Допустим, в память загружены два инстанса модуля `react` или, что чаще, `react-dom`. Компонент, отрендеренный одним инстансом, и хуки, вызванные внутри него, ссылаются на диспетчер **другого** инстанса. React в буквальном смысле не узнаёт свой собственный рендер.

**Как реально дебажить:**

1. **Вкладка Network в DevTools.** Ищите, не грузится ли чанк с `react`/`react-dom` дважды — с разных источников, под разными хешами. Если да — вот она, вторая копия.
2. **`window.__webpack_share_scopes__.default` в консоли браузера.** Там видно, какие версии каждого общего модуля реально зарегистрированы в рантайме прямо сейчас. Имя внутреннего объекта может отличаться между версиями webpack.
3. **Временно включить `strictVersion: true`** на стейджинге для всех общих зависимостей. Вместо тихого дублирования вы получите явную ошибку. Она точно укажет, чья версия и чему не удовлетворяет, — на стейджинге, а не у живого пользователя.
4. **Проверить, не появился ли случайный `eager: true`** где-то в глубине ремоута, а не на точке входа хоста. Это типичная причина того, что согласование «выигрывается» раньше, чем должно.
5. **Организационное решение, а не только техническое.** Самая надёжная защита — проверка в CI: линт-правило или простой скрипт. Она сверяет версии `react` и `react-dom` во всех репозиториях микрофронтендов при каждом релизе. Сверху нужна явная политика: `singleton`-зависимости обновляются по согласованному расписанию, а не когда каждой команде вздумается.

## Итог

Module Federation резолвит зависимости в браузере пользователя, в момент навигации. Это даёт гибкость: обновить ремоут можно без пересборки хоста. Но согласование версий переезжает с проверки TypeScript во время компиляции на согласование в рантайме, а оно может молча отработать неправильно.

Понимание алгоритма `singleton`, `strictVersion` и `eager` — это ровно то, что проверяет интервью. Оно отделяет «читал доку» от «чинил это в проде в 2 часа ночи».

## Типичные ошибки на интервью

- **«Module Federation просто подгружает удалённый бандл, как обычный `<script>`»** — нет. Ключевая часть — это согласование общих зависимостей через share scope при инициализации контейнера, а не просто загрузка файла. Именно в этом согласовании и есть вся сложность.

- **«`singleton: true` гарантирует, что будет ровно один инстанс React»** — гарантирует только *попытку* переиспользовать существующий инстанс, если версия удовлетворяет `requiredVersion`. Без `strictVersion` при несовместимости система молча создаст fallback вместо того, чтобы упасть с ошибкой. То есть singleton не исключает дублирование, а лишь снижает его вероятность.

- **«Ошибка "Invalid hook call" — это баг в коде компонента»** — в контексте Module Federation это почти всегда симптом двух копий `react` или `react-dom` в рантайме. Это не ошибка использования хуков. Первым делом стоит проверить вкладку Network на дублирующиеся чанки, а не искать баг в самом компоненте.

- **«Динамический `import('./bootstrap')` — просто стилистический выбор ради разделения кода»** — это структурный механизм. Без асинхронной границы перед импортом общих зависимостей webpack не успевает согласовать share scope. Код, который эти зависимости использует, выполнится раньше.

- **«Dynamic remotes нужны только для гибкости, static remotes технически проще и всегда предпочтительнее»** — динамические ремоуты решают операционную проблему, которую статические решить принципиально не могут. Версию или URL ремоута можно поменять без пересборки хоста и быстро откатить при инциденте. Это не вопрос простоты. Это вопрос того, у кого физически есть возможность управлять деплоем каждой части независимо.
