# Module Federation: как это работает внутри

Эта статья — самая техническая в разделе. Если предыдущие две отвечали на вопросы «что такое MFE» и «какие бывают способы интеграции», то здесь разбирается механика конкретно Module Federation (Webpack 5 / Rspack) — потому что именно на её деталях интервьюеры проверяют, работали ли вы с этим в проде, а не читали ли документацию.

## Модель host/remote

**Host** — приложение, которое во время выполнения загружает и монтирует код, которым не владеет. **Remote** — приложение, которое публикует часть своего кода для загрузки другими. Это не архитектурная иерархия, а роль в конкретном отношении: одно и то же приложение может быть host'ом для одних модулей и remote'ом для других.

```txt
                    ┌─────────────────────────┐
                    │   Host (shell)          │
                    │  webpack.config.js:      │
                    │  remotes: {              │
                    │    checkout: 'checkout@  │
                    │    http://.../remoteEntry.js' │
                    │  }                       │
                    └───────────┬─────────────┘
                                │ рантайм fetch
                                ▼
                    ┌─────────────────────────┐
                    │  Remote (checkout)      │
                    │  webpack.config.js:      │
                    │  exposes: {              │
                    │    './CheckoutApp': ...  │
                    │  }                       │
                    │  filename: 'remoteEntry.js'│
                    └─────────────────────────┘
```

## remoteEntry.js — что внутри

`remoteEntry.js` — это не бандл приложения. Это маленький **контейнер** (container), который выполняет две задачи и ничего больше. Концептуально (сильно упрощённо, реальный код генерируется webpack-рантаймом) его форма выглядит так:

```js
// Упрощённая концептуальная форма того, что publичит remoteEntry.js
window.checkout = {
  // 1. Регистрирует версии зависимостей remote'а в общей "share scope" хоста
  init: (hostShareScope) => {
    // сверяет react/react-dom этого remote'а с тем, что уже есть в hostShareScope
  },

  // 2. Возвращает асинхронную фабрику для запрошенного экспортированного модуля
  get: (moduleRequest) => {
    // moduleRequest === './CheckoutApp' → возвращает Promise<() => Module>
  },
};
```

Сам код `CheckoutApp` и всё, что он использует, лежит в **отдельных чанках**, которые `get()` подгружает лениво — `remoteEntry.js` сам по себе крошечный, это точка входа, а не приложение целиком.

```js
// webpack.config.js — remote "checkout"
const { ModuleFederationPlugin } = require('webpack').container;

module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'checkout',
      filename: 'remoteEntry.js',
      exposes: {
        './CheckoutApp': './src/CheckoutApp',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
      },
    }),
  ],
};
```

```js
// webpack.config.js — host
module.exports = {
  plugins: [
    new ModuleFederationPlugin({
      name: 'host',
      remotes: {
        checkout: 'checkout@http://localhost:3001/remoteEntry.js',
      },
      shared: {
        react: { singleton: true, requiredVersion: '^18.2.0' },
        'react-dom': { singleton: true, requiredVersion: '^18.2.0' },
      },
    }),
  ],
};
```

```tsx
// host: динамическая загрузка экспортированного модуля во время навигации
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));
// "checkout/CheckoutApp" резолвится в: сходить за remoteEntry.js remote'а "checkout",
// вызвать его get('./CheckoutApp'), выполнить вернувшуюся фабрику.
```

## Bootstrap-паттерн — зачем нужен странный `import('./bootstrap')`

Почти в каждом примере Module Federation входная точка выглядит так:

```ts
// index.ts
import('./bootstrap'); // именно динамический import, не статический
```

```tsx
// bootstrap.tsx — реальная точка входа приложения
import ReactDOM from 'react-dom/client';
import App from './App';
ReactDOM.createRoot(document.getElementById('root')!).render(<App />);
```

Причина не стилистическая. Webpack должен успеть выполнить `init()` контейнера (согласование shared-зависимостей) **до того**, как любой код начнёт реально импортировать `react`. Статический `import` в топ-левеле модуля выполняется синхронно при загрузке скрипта — до того, как у рантайма появляется шанс дождаться `init()` от других контейнеров. Динамический `import()` создаёт асинхронную границу, за которой webpack гарантированно успевает согласовать share scope. Без этого паттерна вы получаете ошибку рантайма вида `Shared module is not available for eager consumption` — это первый признак, что кто-то из вашей команды убрал `bootstrap.ts` ради «более чистого» кода.

## Static vs Dynamic remotes

**Static remote** — URL remote'а зашит в `webpack.config.js` во время сборки хоста:

```js
remotes: {
  checkout: 'checkout@http://localhost:3001/remoteEntry.js',
}
```

Просто, но URL нельзя поменять без пересборки хоста — тот же трейд-офф, что у build-time интеграции из статьи 02, только на один уровень глубже (сама *ссылка* на remote фиксируется во время сборки, хотя код remote'а всё ещё грузится в рантайме).

**Dynamic remote** — URL резолвится в рантайме, обычно через манифест, который хост запрашивает перед тем как знать, куда идти за `remoteEntry.js`:

```js
// webpack.config.js — host, dynamic remote
remotes: {
  checkout: `promise new Promise((resolve) => {
    fetch('/api/remotes-manifest.json')
      .then((res) => res.json())
      .then((manifest) => {
        const script = document.createElement('script');
        script.src = manifest.checkout.url; // например, .../checkout@2.4.1/remoteEntry.js
        script.onload = () => {
          const proxy = {
            get: (request) => window.checkout.get(request),
            init: (shareScope) => {
              try {
                return window.checkout.init(shareScope);
              } catch (e) {
                console.warn('checkout container already initialized');
              }
            },
          };
          resolve(proxy);
        };
        document.head.appendChild(script);
      });
  })`,
}
```

Это позволяет менять версию remote'а (например, откатить на предыдущую при инциденте) правкой манифеста — без пересборки хоста. Цена: resolution происходит позже и добавляет сетевой round-trip до манифеста ещё до того, как начнётся загрузка самого `remoteEntry.js`.

## Алгоритм согласования shared-зависимостей

Это раздел, ради которого сеньоров и спрашивают про Module Federation — потому что именно здесь возникают продовые баги, которые невозможно отладить, не понимая механику.

Каждый контейнер (и хост, и каждый remote) при инициализации регистрирует версии своих shared-модулей в общем объекте — **share scope**. Когда любой модуль внутри любого контейнера делает `import React from 'react'`, скомпилированный код обращается не напрямую к своей локальной копии `react`, а к рантайм-функции разрешения через share scope. Алгоритм:

1. **Проверить share scope.** Есть ли там уже версия `react`, удовлетворяющая `requiredVersion` этого консьюмера?
2. **Если да и `singleton: true`** — переиспользовать уже загруженный инстанс. Новый сетевой запрос не делается, вторая копия `react` в память не грузится.
3. **Если совместимой версии нет** (или требование не удовлетворено) — контейнер загружает **свою собственную резервную копию** зависимости. Именно поэтому каждый remote-бандл фактически содержит собственный fallback-чанк с `react` внутри — не потому что это ошибка сборки, а потому что Module Federation обязан иметь fallback на случай, если в share scope ничего подходящего не окажется.
4. **`strictVersion: true`** — если требуемая версия не satisfied, вместо тихой загрузки fallback'а рантайм бросает ошибку. Полезно на стейджинге/CI, чтобы ловить рассинхрон версий явно, а не молча получать вторую копию React в проде.
5. **`eager: true`** — модуль включается прямо в основной чанк вместо ленивой асинхронной загрузки. Нужно для entry-точки хоста (у неё физически нет времени ждать асинхронного резолвинга), но `eager`-модуль регистрируется в share scope немедленно при выполнении, до того как у других контейнеров появился шанс договориться — то есть eager вне entry-точки способен сломать всю негоциацию, зарегистрировав версию раньше времени.

```js
shared: {
  react: {
    singleton: true,           // один инстанс на всё приложение — обязателен для React
    requiredVersion: '^18.2.0', // semver-диапазон, который ожидает ЭТОТ контейнер
    strictVersion: true,        // бросить ошибку, а не тихо задублировать, если диапазон не satisfied
    eager: false,                // грузить лениво, асинхронно (кроме entry-точки хоста)
  },
}
```

## Почему «в деве работает, а в проде две копии React» — и как это дебажить

Это самый известный класс production-инцидентов в Module Federation, и он почти всегда сводится к одному из трёх сценариев.

**Сценарий 1 — гонка инициализации.** Негоциация share scope зависит от **порядка**, в котором контейнеры успевают вызвать `init()`. В dev-режиме (webpack-dev-server, HMR, всё локально, задержки сети минимальны и стабильны) порядок почти всегда одинаковый. В проде remote грузится с другого CDN/origin, с другой латентностью, иногда до того как хост успел зарегистрировать свою версию `react` в share scope. Remote не находит совместимой версии в момент своей инициализации → грузит собственный fallback `react` → теперь на странице два инстанса React одновременно.

**Сценарий 2 — реальный рассинхрон версий.** Хост собран с `react@18.2.0`, remote со своим независимым релизным циклом обновился до `react@18.3.0`, а `requiredVersion` был `^18.0.0` без `strictVersion`. Semver формально совместим, но при `singleton: true` без `strictVersion` рантайм может выбрать не ту версию, которую тестировала команда remote'а, — сработает молча, без ошибки, просто где-то в глубине компонентного дерева.

**Сценарий 3 — симптом, по которому это обычно и находят.** Классическая ошибка `Invalid hook call. Hooks can only be called inside the body of a function component` — при том что с виду хуки используются правильно. Причина: React хранит внутренний dispatcher хуков как module-level singleton. Если в память загружены два инстанса модуля `react` (или чаще `react-dom`), компонент, отрендеренный одним инстансом, и хуки, вызванные внутри него, ссылаются на dispatcher **другого** инстанса — react в буквальном смысле не узнаёт свой собственный рендер.

**Как реально дебажить:**

1. **Вкладка Network в DevTools.** Ищите, не грузится ли чанк с `react`/`react-dom` дважды — с разных origin'ов, под разными хешами. Если да — вот она, вторая копия.
2. **`window.__webpack_share_scopes__.default` в консоли браузера** (имя внутреннего объекта может отличаться между версиями webpack) — там видно, какие версии каждого shared-модуля реально зарегистрированы в рантайме прямо сейчас.
3. **Временно включить `strictVersion: true`** на стейджинге для всех shared-зависимостей. Вместо тихого дублирования вы получите явную ошибку с точным указанием, чья версия и чему не удовлетворяет — на стейджинге, не у живого пользователя.
4. **Проверить, не появился ли случайный `eager: true`** не на entry-точке хоста, а где-то в глубине remote'а — типичная причина того, что негоциация «выигрывается» раньше, чем должна.
5. **Организационное решение, а не только техническое.** Самая надёжная защита — CI-проверка (линт-правило или простой скрипт), сверяющая версии `react`/`react-dom` во всех репозиториях микрофронтендов при каждом релизе, и явная политика: `singleton`-зависимости обновляются по согласованному расписанию, а не когда каждой команде вздумается.

## Итог

Module Federation резолвит зависимости в браузере пользователя, в момент навигации — это даёт гибкость (обновить remote без пересборки хоста), но перекладывает согласование версий с compile-time проверки TypeScript на рантайм-негоциацию, которая может отработать неправильно молча. Понимание алгоритма `singleton`/`strictVersion`/`eager` — это ровно то отличие между «читал доку» и «чинил это в проде в 2 часа ночи», которое интервью на самом деле проверяет.

## Типичные ошибки на интервью

- **«Module Federation просто подгружает удалённый бандл, как обычный `<script>`»** — нет, ключевая часть — это согласование shared-зависимостей через share scope при инициализации контейнера, а не просто загрузка файла. Именно в этом согласовании и есть вся сложность.

- **«`singleton: true` гарантирует, что будет ровно один инстанс React»** — гарантирует только *попытку* переиспользовать существующий инстанс, если версия удовлетворяет `requiredVersion`. Без `strictVersion` при несовместимости система молча создаст fallback вместо того, чтобы упасть с ошибкой — то есть singleton не исключает дублирование, а лишь снижает его вероятность.

- **«Ошибка "Invalid hook call" — это баг в коде компонента»** — в контексте Module Federation это почти всегда симптом двух копий `react`/`react-dom` в рантайме, а не ошибка использования хуков. Первым делом стоит проверить Network tab на дублирующиеся чанки, а не искать баг в самом компоненте.

- **«Динамический `import('./bootstrap')` — просто стилистический выбор code splitting»** — это структурный механизм: без асинхронной границы перед импортом shared-зависимостей webpack не успевает согласовать share scope до выполнения кода, который эти зависимости использует.

- **«Dynamic remotes нужны только для гибкости, static remotes технически проще и всегда предпочтительнее»** — dynamic remotes решают реальную операционную проблему (смена версии/URL remote'а без пересборки хоста, быстрый откат при инциденте), которую static remotes принципиально не могут решить — это не просто вопрос простоты, а вопрос того, у кого физически есть возможность управлять деплоем каждой части независимо.
