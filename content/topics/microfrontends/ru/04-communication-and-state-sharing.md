# Коммуникация и обмен состоянием между микрофронтендами

## Почему это не то же самое, что общение компонентов в React

Внутри одного SPA общение между компонентами — это просто props, context, общий store. Все части приложения собираются одним бандлером, компилируются вместе, деплоятся одновременно — импорт откуда угодно безопасен, потому что TypeScript проверит совместимость на этапе сборки, и любое несоответствие типов остановит именно этот один деплой.

Между микрофронтендами это условие не выполняется: каждая часть потенциально собрана отдельно, задеплоена в своё время, может быть на другом фреймворке, может выполняться в другом JS-realm (если это iframe). Прямой импорт между такими частями либо технически невозможен, либо создаёт скрытую связанность, которая ломает саму причину, по которой микрофронтенды вообще существуют — независимость деплоя (см. статью 01). Отсюда — набор паттернов ниже, каждый со своей ценой.

## 1. Кастомная событийная шина на window/document

Простейший канал: один микрофронтенд диспатчит `CustomEvent` на `window`, другие подписываются через `addEventListener`. Издатель не обязан ничего знать о том, кто (и есть ли вообще кто-то) слушает.

```ts
// checkout-mfe: публикация события
window.dispatchEvent(
  new CustomEvent('cart:updated', { detail: { itemCount: 3 } }),
);

// header-mfe: подписка — независимо собран, независимо задеплоен
window.addEventListener('cart:updated', (event) => {
  const { itemCount } = (event as CustomEvent<{ itemCount: number }>).detail;
  updateCartBadge(itemCount);
});
```

**Плюсы:** фреймворк-агностично, работает через границы Module Federation и (в варианте с `postMessage`) через iframe, не требует общего инстанса состояния.

**Минусы:** никакой compile-time проверки контракта — имя события и форма `detail` держатся на честном слове, если не формализованы отдельно. Дебажить сложнее: нет понятного call stack, приходится искать строку `'cart:updated'` по всему проекту.

**Как снизить риск:** вынести имена событий и типы payload'ов в отдельный версионированный пакет (например, `@company/mfe-events`), который каждая команда подключает как обычную зависимость. Это превращает событие из «строки по договорённости» в настоящий контракт — тот же принцип версионирования контрактов подробно разбирается в статье 07.

## 2. Общий инстанс store vs изолированный store + синхронизация через pub/sub

**Вариант А — общий инстанс store.** Буквально один и тот же инстанс Redux/Zustand шарится между микрофронтендами через Module Federation:

```js
// webpack.config.js — и хост, и remote указывают одну shared-зависимость
shared: {
  '@company/shared-store': { singleton: true, requiredVersion: '^3.0.0' },
}
```

Это даёт одну единственную источник правды без задержки синхронизации — но воспроизводит ровно ту проблему связанности, которую независимый деплой должен был устранить. Если форма store меняется, **все** потребляющие её микрофронтенды обязаны обновиться синхронно — фактически вы получаете распределённый монолит с дополнительными шагами. Это оправданный паттерн только тогда, когда микрофронтенды и так деплоятся в лок-степе (одна команда, один релизный цикл), либо когда к контракту store относятся с той же строгостью, что и к версионированному публичному API.

**Вариант Б — изолированный store + pub/sub-синхронизация.** Каждый микрофронтенд владеет собственным локальным состоянием; изменения транслируются через событийную шину (паттерн 1), а каждый получатель сам решает, как встроить их в свой собственный store.

```ts
// catalog-mfe: свой локальный store, ничего не шарит напрямую
window.dispatchEvent(new CustomEvent('catalog:item-selected', { detail: { sku: 'ABC-123' } }));

// checkout-mfe: получает событие и решает сам, как обновить СВОЙ store
window.addEventListener('catalog:item-selected', (event) => {
  const { sku } = (event as CustomEvent<{ sku: string }>).detail;
  checkoutStore.dispatch(addItemToCart(sku)); // форма checkoutStore — приватная деталь checkout
});
```

Это устойчивее к независимым деплоям: внутренняя форма store каждого микрофронтенда — приватная деталь реализации, единственный контракт — формат события на проводе.

## 3. Props/callbacks, передаваемые хостом

Когда хост напрямую монтирует микрофронтенд (не просто композиция по маршруту, а явное встраивание компонента), он может передать функции обратного вызова как канал коммуникации:

```tsx
<CheckoutApp
  onOrderComplete={(orderId) => router.push(`/confirmation/${orderId}`)}
/>
```

**Плюсы:** типобезопасно (если микрофронтенд экспортирует нормальные TS-типы для своих props), контракт явный и обнаруживаемый прямо в сигнатуре компонента.

**Минусы:** работает только когда хост непосредственно управляет монтированием — не годится для общения между «братскими» микрофронтендами напрямую, без посредничества хоста. Хост при этом становится связан с интерфейсом props каждого удалённого компонента — та же проблема версионирования, что и с shared-зависимостями в статье 03.

## 4. URL / query-параметры — «самый примитивный, но самый надёжный» канал

```txt
/catalog/item/42?returnUrl=/checkout&promoCode=SUMMER20
```

**Плюсы:** переживает полную перезагрузку страницы, тривиально работает через границу iframe (не нужен `postMessage`), совместим с server-side композицией из статьи 02, полностью фреймворк-агностичен и не требует вообще никакой общей рантайм-зависимости между частями.

**Минусы:** ограничен сериализуемыми примитивами, засоряет URL, не годится для высокочастотных обновлений (например, ввода текста в форме посимвольно), нельзя передать функцию.

**Когда предпочесть:** передача состояния между микрофронтендами при навигации (хост ведёт пользователя из каталога в чекаут с выбранным товаром), любое состояние, которое и так должно переживать перезагрузку или быть доступным по прямой ссылке.

## Антипаттерн: прямой импорт внутренностей соседнего remote'а

Это самая частая ошибка кандидатов на интервью по теме микрофронтендов — и она прямое следствие многолетней привычки к обычной композиции React-компонентов. Внутри одного SPA импортировать что угодно откуда угодно — нормально и безопасно, потому что весь код компилируется и тестируется вместе. Разработчики инстинктивно переносят эту же ментальную модель на границу микрофронтендов — и это ломает саму архитектуру.

```ts
// ❌ АНТИПАТТЕРН: залезание во внутреннюю реализацию соседнего remote'а
import { cartStore } from 'catalog/src/internal/cartStore';
// это НЕ осознанно экспортированный публичный контракт —
// просто путь, который случайно оказался доступен через exposes

// ✅ Правильно: потреблять только то, что явно экспортировано как публичный контракт модуля
import { getCartSummary } from 'catalog/PublicApi'; // явно выставлено, версионируется отдельно
```

Почему это опасно именно скрыто: изменение внутренней формы `cartStore` в команде catalog не ломает ни один тест, ни один build — ни у catalog, ни у checkout, потому что их сборки происходят независимо и никогда не видят код друг друга напрямую. Поломка проявляется только в браузере пользователя, в рантайме, когда бандл checkout выполняется рядом с новой версией бандла catalog — то есть ровно тогда и там, где её труднее всего поймать.

**Правило:** импортировать можно только то, что явно, осознанно выставлено как публичный контракт (аналог REST/gRPC API у микросервиса) — и к этой выставленной поверхности нужно относиться с той же дисциплиной, что и к публичному API: версионирование, документация, обратная совместимость, политика деприкейшена (см. статью 07).

## Типичные ошибки на интервью

- **«Между микрофронтендами можно общаться так же, как между React-компонентами — просто импортировать нужное»** — это и есть главный антипаттерн раздела. Прямой импорт внутренней реализации соседнего remote'а создаёт скрытую связанность, которая не ловится ни одной сборкой или тестом ни одной из команд — только в рантайме браузера пользователя.

- **«Общий инстанс store — лучшее решение, потому что оно проще всего»** — проще для разработки, но воспроизводит проблему связанности, которую независимый деплой должен был устранить: изменение формы store требует синхронного обновления всех потребителей.

- **«Событийная шина не нуждается в контракте — это же просто строка и объект»** — без отдельного версионированного пакета с именами событий и типами payload'ов событийная шина превращается в скрытый, недокументированный API, который так же легко сломать несогласованным изменением, как и прямой импорт.

- **«URL/query-параметры — слишком примитивный канал, не стоит рассматривать всерьёз»** — недооценка: это часто самый надёжный канал именно потому, что не требует вообще никакой общей рантайм-зависимости между частями и естественно переживает перезагрузку страницы.

- **«Props/callbacks от хоста работают для любой пары микрофронтендов»** — работают только когда хост напрямую монтирует компонент. Для общения между двумя «братскими» микрофронтендами, независимо смонтированными по маршруту, нужен хост как явный посредник или один из остальных трёх каналов.
