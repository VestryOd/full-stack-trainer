# Коммуникация и обмен состоянием между микрофронтендами

## Почему это не то же самое, что общение компонентов в React

Внутри одного SPA (single-page application, одностраничное приложение) общение между компонентами — это просто props, context, общий store. Все части приложения собираются одним бандлером, компилируются вместе и деплоятся одновременно. Импорт откуда угодно безопасен: TypeScript проверит совместимость на этапе сборки, и любое несоответствие типов остановит именно этот один деплой.

Между микрофронтендами это условие не выполняется. Каждая часть потенциально собрана отдельно и задеплоена в своё время. Она может быть на другом фреймворке и может выполняться в другом JS-realm — так бывает с iframe.

Прямой импорт между такими частями либо технически невозможен, либо создаёт скрытую связанность. Эта связанность ломает независимость деплоя — а ведь ровно ради неё, как объясняют [Основы микрофронтендов](./01-microfrontends-fundamentals.md), микрофронтенды и существуют. Отсюда набор паттернов ниже, каждый со своей ценой.

## 1. Кастомная событийная шина на window/document

Простейший канал: один микрофронтенд диспатчит `CustomEvent` на `window`, другие подписываются через `addEventListener`. Издатель не обязан ничего знать о том, кто (и есть ли вообще кто-то) слушает.

```ts
// checkout-mfe: публикация события
window.dispatchEvent(
  new CustomEvent('cart:updated', { detail: { itemCount: 3 } }),
);

// header-mfe: подписка — независимо собран, независимо задеплоен
window.addEventListener('cart:updated', (event) => {
  const { itemCount } = (event as CustomEvent<{ itemCount: number }>).detail;
  updateCartBadge(itemCount);
});
```

**Плюсы:** фреймворк-агностично, работает через границы Module Federation и (в варианте с `postMessage`) через iframe, не требует общего инстанса состояния.

**Минусы:** никакой проверки контракта на этапе компиляции — имя события и форма `detail` держатся на честном слове, если не формализованы отдельно. Дебажить сложнее: нет понятного стека вызовов, приходится искать строку `'cart:updated'` по всему проекту.

**Как снизить риск:** вынести имена событий и типы полезной нагрузки в отдельный версионированный пакет, например `@company/mfe-events`. Каждая команда подключает его как обычную зависимость. Это превращает событие из «строки по договорённости» в настоящий контракт. Статья [Деплой, версионирование и тестирование](./07-deployment-versioning-and-testing.md) подробно разбирает тот же принцип версионирования контрактов.

## 2. Общий инстанс store vs изолированный store + синхронизация через pub/sub

**Вариант А — общий инстанс store.** Буквально один и тот же инстанс Redux/Zustand шарится между микрофронтендами через Module Federation:

```js
// webpack.config.js — и хост, и ремоут указывают одну общую зависимость
shared: {
  '@company/shared-store': { singleton: true, requiredVersion: '^3.0.0' },
}
```

Это даёт **единый источник правды** без задержки синхронизации. Но такой вариант воспроизводит ровно ту проблему связанности, которую независимый деплой должен был устранить. Если форма store меняется, **все** потребляющие её микрофронтенды обязаны обновиться синхронно — фактически вы получаете распределённый монолит с лишними шагами.

Этот паттерн оправдан только в двух случаях. Первый — когда микрофронтенды и так деплоятся синхронно: одна команда, один релизный цикл. Второй — когда к контракту store относятся с той же строгостью, что и к версионированному публичному API.

**Вариант Б — изолированный store и синхронизация через pub/sub.** Каждый микрофронтенд владеет собственным локальным состоянием. Изменения транслируются через событийную шину из паттерна 1, а каждый получатель сам решает, как встроить их в свой store.

```ts
// catalog-mfe: свой локальный store, ничего не шарит напрямую
window.dispatchEvent(
  new CustomEvent('catalog:item-selected', { detail: { sku: 'ABC-123' } }),
);

// checkout-mfe: получает событие и решает сам, как обновить свой store
window.addEventListener('catalog:item-selected', (event) => {
  const { sku } = (event as CustomEvent<{ sku: string }>).detail;
  // форма checkoutStore — приватная деталь checkout
  checkoutStore.dispatch(addItemToCart(sku));
});
```

Это устойчивее к независимым деплоям. Внутренняя форма store каждого микрофронтенда — приватная деталь реализации, а единственный контракт — формат события на проводе.

## 3. Props/callbacks, передаваемые хостом

Когда хост напрямую монтирует микрофронтенд (не просто композиция по маршруту, а явное встраивание компонента), он может передать функции обратного вызова как канал коммуникации:

```tsx
<CheckoutApp
  onOrderComplete={(orderId) => router.push(`/confirmation/${orderId}`)}
/>
```

**Плюсы:** типобезопасно (если микрофронтенд экспортирует нормальные TS-типы для своих props), контракт явный и обнаруживаемый прямо в сигнатуре компонента.

**Минусы:** работает только когда хост непосредственно управляет монтированием. Для общения «братских» микрофронтендов напрямую, без посредничества хоста, способ не годится. Хост при этом становится связан с интерфейсом props каждого удалённого компонента. Это та же проблема версионирования, о которой [Module Federation: как это работает внутри](./03-module-federation-deep-dive.md) говорит применительно к общим зависимостям.

## 4. URL / query-параметры — «самый примитивный, но самый надёжный» канал

```txt
/catalog/item/42?returnUrl=/checkout&promoCode=SUMMER20
```

**Плюсы:**

- Переживает полную перезагрузку страницы.
- Тривиально работает через границу iframe, `postMessage` не нужен.
- Совместим с композицией на сервере из статьи [Способы интеграции микрофронтендов](./02-integration-approaches.md).
- Полностью фреймворк-агностичен.
- Не требует вообще никакой общей рантайм-зависимости между частями.

**Минусы:** ограничен сериализуемыми примитивами, засоряет URL, не годится для высокочастотных обновлений (например, ввода текста в форме посимвольно), нельзя передать функцию.

**Когда предпочесть:** передача состояния при навигации — например, хост ведёт пользователя из каталога в чекаут с выбранным товаром. Годится и для любого состояния, которое и так должно переживать перезагрузку или быть доступным по прямой ссылке.

## Антипаттерн: прямой импорт внутренностей соседнего ремоута

Это самая частая ошибка кандидатов на интервью по микрофронтендам. Она прямое следствие многолетней привычки к обычной композиции React-компонентов.

Внутри одного SPA импортировать что угодно откуда угодно нормально и безопасно: весь код компилируется и тестируется вместе. Разработчики инстинктивно переносят ту же ментальную модель на границу микрофронтендов, и это ломает саму архитектуру.

```ts
// ❌ АНТИПАТТЕРН: залезание во внутреннюю реализацию соседнего ремоута
import { cartStore } from 'catalog/src/internal/cartStore';
// это не осознанно выставленный публичный контракт —
// просто путь, который случайно оказался доступен через exposes

// ✅ Правильно: потреблять только то, что явно выставлено как публичный контракт
// выставлено осознанно, версионируется отдельно
import { getCartSummary } from 'catalog/PublicApi';
```

Почему это опасно именно своей скрытостью? Изменение внутренней формы `cartStore` в команде catalog не ломает ни один тест и ни одну сборку — ни у catalog, ни у checkout. Их сборки происходят независимо и никогда не видят код друг друга напрямую.

Поломка проявляется только в браузере пользователя, в рантайме, когда бандл checkout выполняется рядом с новой версией бандла catalog. Это ровно то время и место, где её труднее всего поймать.

**Правило:** импортировать можно только то, что явно и осознанно выставлено как публичный контракт. Это фронтендовый аналог публичного API микросервиса поверх REST (representational state transfer) или gRPC.

К выставленной поверхности нужно относиться с той же дисциплиной, что и к любому публичному API: версионирование, документация, обратная совместимость, политика устаревания. Эту дисциплину разбирает статья [Деплой, версионирование и тестирование](./07-deployment-versioning-and-testing.md).

## Сводная таблица каналов

| Канал | Связанность | Типобезопасность | Переживает перезагрузку | Когда использовать |
|---|---|---|---|---|
| Событийная шина | Слабая | Слабая (нужен отдельный пакет контрактов) | Нет | Уведомления pub/sub: корзина обновилась, пользователь вышел |
| Общий инстанс store | Сильная | Сильная (общий код) | Нет | Только когда микрофронтенды деплоятся синхронно |
| Props/callbacks от хоста | Средняя (через хост) | Сильная | Нет | Навигация и действия, оркестрируемые хостом |
| URL / query-параметры | Нет или слабая | Нет (строки) | Да | Передача состояния при навигации, прямые ссылки |

## Типичные ошибки на интервью

- **«Между микрофронтендами можно общаться так же, как между React-компонентами — просто импортировать нужное»** — это и есть главный антипаттерн раздела. Прямой импорт внутренней реализации соседнего ремоута создаёт скрытую связанность. Её не поймает ни сборка, ни тесты ни одной из команд — только рантайм браузера у пользователя.

- **«Общий инстанс store — лучшее решение, потому что оно проще всего»** — проще для разработки, да. Но он воспроизводит проблему связанности, которую независимый деплой должен был устранить. Изменение формы store требует синхронного обновления всех потребителей.

- **«Событийная шина не нуждается в контракте — это же просто строка и объект»** — нуждается. Без отдельного версионированного пакета с именами событий и типами полезной нагрузки шина превращается в скрытый, недокументированный API. Сломать его несогласованным изменением так же легко, как и прямой импорт.

- **«URL/query-параметры — слишком примитивный канал, не стоит рассматривать всерьёз»** — это недооценка. Часто это самый надёжный канал именно потому, что не требует вообще никакой общей рантайм-зависимости между частями. Он ещё и естественно переживает перезагрузку страницы.

- **«Props/callbacks от хоста работают для любой пары микрофронтендов»** — работают только когда хост напрямую монтирует компонент. Для общения между двумя «братскими» микрофронтендами, независимо смонтированными по маршруту, нужен хост как явный посредник или один из остальных трёх каналов.
