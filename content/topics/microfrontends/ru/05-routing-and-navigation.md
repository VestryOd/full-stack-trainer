# Роутинг и навигация между микрофронтендами

## Кто владеет роутингом

Есть два полюса, и почти все реальные системы — гибрид между ними.

**Хост владеет роутером целиком.** Один инстанс роутера (например, React Router в shell-приложении) знает все top-level маршруты и решает, какой микрофронтенд смонтировать для какого пути. Микрофронтенд получает управление уже внутри своего сегмента.

**Каждый микрофронтенд владеет своим роутером.** Хост не знает ничего о внутренней структуре маршрутов конкретного микрофронтенда. Он знает только префикс пути, который этот микрофронтенд активирует. В терминологии single-spa это правило называется `activeWhen`.

На практике доминирует гибрид: **хост владеет верхнеуровневой сегментацией, каждый remote владеет своим поддеревом.**

| Маршрут хоста | Монтирует | За всё, что дальше, отвечает |
|---|---|---|
| `/catalog/*` | `CatalogApp` | команда catalog |
| `/checkout/*` | `CheckoutApp` | команда checkout |
| `/account/*` | `AccountApp` | команда account |

```txt
Внутри CheckoutApp — отдельный remote, свой репозиторий:
  /checkout/cart
  /checkout/payment
  /checkout/confirmation
```

Эти три пути полностью в ведении команды checkout, и хост о них ничего не знает. Это даёт независимость: команда checkout может добавить, убрать или переименовать любой из своих внутренних маршрутов без единой правки в хосте. Хост знает только префикс `/checkout/*` — тот самый минимальный публичный контракт.

## Как синхронизировать историю браузера между микрофронтендами

У браузера **один** `window.history`. Два независимых стека истории одновременно физически невозможны.

Теперь представьте, что и хост, и remote создали собственный инстанс роутера — например, каждый свой `<BrowserRouter>`. Оба слушают `popstate` и оба сами вызывают `pushState`. Кнопка «назад» после этого ведёт себя непредсказуемо: один роутер перезаписывает решение другого.

**Правило:** только одна сущность должна вызывать `history.pushState`/`replaceState` для конкретного перехода; все остальные обязаны выводить своё внутреннее состояние из `window.location`, а не наоборот.

На практике хост создаёт **один общий инстанс history**. Remote, которому нужен собственный внутренний роутинг, переиспользует этот инстанс, а не создаёт новый `<BrowserRouter>`.

```ts
// host: единственный общий инстанс history на всё приложение
import { createBrowserHistory } from 'history';
export const sharedHistory = createBrowserHistory();
```

```tsx
// remote (CheckoutApp): переиспользует ОБЩИЙ history, полученный от хоста,
// вместо того чтобы создавать собственный <BrowserRouter>
import { Router } from 'react-router-dom';
// экспортировано хостом через Module Federation
import { sharedHistory } from 'host/sharedHistory';

export function CheckoutApp() {
  return (
    <Router location={sharedHistory.location} navigator={sharedHistory}>
      <Routes>
        <Route path="/checkout/cart" element={<Cart />} />
        <Route path="/checkout/payment" element={<Payment />} />
      </Routes>
    </Router>
  );
}
```

single-spa приходит к той же цели другим путём. Он глобально патчит `history.pushState` и `replaceState`, а при каждой навигации рассылает кастомное событие. У каждого зарегистрированного приложения свой роутер внутри, но все они видят одно и то же событие и синхронизируются с ним. Бороться за контроль над `window.history` никому не приходится.

## Ленивая загрузка ремоута в момент совпадения маршрута

Соедините `React.lazy` и `Suspense` прямо в маршруте. Тогда `remoteEntry.js` подгружается **только тогда**, когда пользователь реально переходит на этот маршрут. В первую загрузку хоста он не попадает:

```tsx
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));

<Routes>
  <Route
    path="/checkout/*"
    element={
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutApp />
      </Suspense>
    }
  />
</Routes>
```

Пока пользователь не зашёл в `/checkout/*`, ни `remoteEntry.js` ремоута checkout, ни его чанки в сеть не уходят. Экономия ровно та же, что и у обычного разбиения кода по маршрутам в одностраничном приложении. Отличается только объект загрузки: не локальный чанк, а целый независимо задеплоенный remote.

## Что делать, если remote не загрузился

Здесь важно различать два разных отказа.

**Отказ на уровне сети** — `remoteEntry.js` недоступен. Причиной бывает авария CDN (content delivery network — сеть доставки контента), таймаут или 404 после отката версии. Без явной обработки `import()` просто зависнет или отклонится без осмысленного фолбэка.

Решение — обернуть загрузку таймаутом. Тогда отклонённый промис долетает до `React.lazy`, `Suspense` и `ErrorBoundary` предсказуемо, а не через неопределённое время:

```ts
function loadRemoteWithTimeout<T>(importPromise: Promise<T>, ms = 5000): Promise<T> {
  return Promise.race([
    importPromise,
    new Promise<T>((_, reject) =>
      setTimeout(() => reject(new Error('Remote load timed out')), ms),
    ),
  ]);
}

const CheckoutApp = React.lazy(() =>
  loadRemoteWithTimeout(import('checkout/CheckoutApp')),
);
```

**Отказ на уровне рендера** — remote загрузился, но упал во время выполнения. Достаточно одного бага, задеплоенного командой checkout.

По умолчанию необработанная ошибка всплывает вверх по дереву React до ближайшей error boundary. Если границы нет **на каждой точке монтирования ремоута**, ближайшей окажется граница самого shell-приложения. Баг одной команды тогда роняет **весь продукт** для всех пользователей, включая части, не связанные со сломанным ремоутом.

```tsx
class RemoteErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error) {
    // сквозная observability между ремоутами — см. статью про деплой
    logToObservability('remote-mount-failed', error);
  }

  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}
```

```tsx
<Route
  path="/checkout/*"
  element={
    <RemoteErrorBoundary fallback={<CheckoutUnavailableBanner />}>
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutApp />
      </Suspense>
    </RemoteErrorBoundary>
  }
/>
```

Так технически исполняется обещание «изоляция отказов на уровне деплоя» из статьи [Основы микрофронтендов](./01-microfrontends-fundamentals.md). Само по себе Module Federation даёт только механизм независимого деплоя. Изоляцию отказов в рантайме оно автоматически **не** даёт.

Пропустите одну точку монтирования — и сбой одной команды по-прежнему уронит всё приложение целиком. Обещанная выгода остаётся теоретической, пока команда хоста осознанно её не реализует.

## Типичные ошибки на интервью

- **«Единый роутер на всё приложение означает, что микрофронтенды не могут иметь собственные вложенные маршруты»** — неверно. Доминирующий на практике паттерн — гибрид: хост владеет только верхнеуровневой сегментацией (`/checkout/*`), а всё, что происходит внутри этого префикса, — целиком в ведении ремоута.

- **«Каждый remote может свободно создавать свой собственный `<BrowserRouter>`»** — нет. Два инстанса роутера, одновременно управляющие одним `window.history`, делают кнопку «назад» и навигацию непредсказуемыми. Нужен один общий инстанс history или глобальный механизм синхронизации, как в single-spa. Независимые роутеры, каждый из которых уверен, что владеет URL, не работают.

- **«Раз Module Federation даёт независимый деплой, значит сбой одного ремоута автоматически не влияет на остальные»** — независимость деплоя не равна изоляции отказов в рантайме. Без явной error boundary на каждой точке монтирования ремоута необработанная ошибка одной команды всплывает до ближайшей границы. Обычно это сам shell, и падает весь продукт.

- **«Ленивая загрузка по маршруту происходит автоматически, достаточно `React.lazy`»** — нет. `React.lazy` нужен `Suspense`-фолбэк вокруг него и таймаут на сетевой запрос за `remoteEntry.js`. Без этих двух вещей пользователь получит либо бесконечное зависание, либо необработанное исключение, когда CDN ремоута недоступен.

- **«Роутинг между микрофронтендами — чисто техническая деталь, к организационной автономии отношения не имеет»** — он и есть эта автономия. Граница маршрута (`/checkout/*` целиком принадлежит одной команде) — то же самое разделение ответственности, о котором говорит [Основы микрофронтендов](./01-microfrontends-fundamentals.md). Чёткая граница маршрута — это публичный контракт между хостом и ремоутом. Именно она позволяет команде checkout менять свои внутренние страницы, ничего не согласовывая с остальными.
