# Роутинг и навигация между микрофронтендами

## Кто владеет роутингом

Есть два полюса, и почти все реальные системы — гибрид между ними.

**Хост владеет роутером целиком.** Один инстанс роутера (например, React Router в shell-приложении) знает все top-level маршруты и решает, какой микрофронтенд смонтировать для какого пути. Микрофронтенд получает управление уже внутри своего сегмента.

**Каждый микрофронтенд владеет своим роутером.** Хост не знает ничего о внутренней структуре маршрутов конкретного микрофронтенда — только то, для какого префикса пути его нужно активировать (в терминологии single-spa это `activeWhen`).

На практике доминирует гибрид: **хост владеет верхнеуровневой сегментацией, каждый remote владеет своим поддеревом.**

```txt
Хост:
  /catalog/*   → монтирует CatalogApp     (дальше маршруты — забота catalog-команды)
  /checkout/*  → монтирует CheckoutApp    (дальше маршруты — забота checkout-команды)
  /account/*   → монтирует AccountApp     (дальше маршруты — забота account-команды)

Внутри CheckoutApp (отдельный remote, свой репозиторий):
  /checkout/cart
  /checkout/payment
  /checkout/confirmation
  ← полностью в ведении команды checkout, хост об этих путях ничего не знает
```

Это даёт независимость: команда checkout может добавить, убрать или переименовать любой из своих внутренних маршрутов без единой правки в хосте. Хост знает только префикс `/checkout/*` — тот самый минимальный публичный контракт.

## Как синхронизировать browser history между границами MFE

У браузера **один** `window.history` — физически невозможно иметь два независимых стека истории одновременно. Если и хост, и remote создают собственный независимый инстанс роутера (например, каждый — свой `<BrowserRouter>`), оба будут слушать `popstate` и пытаться вызывать `pushState` независимо друг от друга — result: кнопка «назад» ведёт себя непредсказуемо, один роутер перезаписывает решение другого.

**Правило:** только одна сущность должна вызывать `history.pushState`/`replaceState` для конкретного перехода; все остальные обязаны выводить своё внутреннее состояние из `window.location`, а не наоборот.

На практике это означает: хост создаёт **один общий инстанс history**, и remote, когда ему нужен собственный внутренний роутинг, переиспользует этот инстанс вместо создания нового `<BrowserRouter>`.

```ts
// host: единственный общий инстанс history на всё приложение
import { createBrowserHistory } from 'history';
export const sharedHistory = createBrowserHistory();
```

```tsx
// remote (CheckoutApp): переиспользует ОБЩИЙ history, полученный от хоста,
// вместо того чтобы создавать собственный <BrowserRouter>
import { Router } from 'react-router-dom';
import { sharedHistory } from 'host/sharedHistory'; // экспортировано через Module Federation

export function CheckoutApp() {
  return (
    <Router location={sharedHistory.location} navigator={sharedHistory}>
      <Routes>
        <Route path="/checkout/cart" element={<Cart />} />
        <Route path="/checkout/payment" element={<Payment />} />
      </Routes>
    </Router>
  );
}
```

single-spa решает ту же проблему иначе — но с той же целью: он патчит `history.pushState`/`replaceState` глобально и рассылает кастомное событие при любой навигации, так что каждое зарегистрированное приложение (со своим собственным роутером внутри) видит одно и то же событие навигации и синхронизируется с ним, вместо того чтобы независимо бороться за контроль над `window.history`.

## Ленивая загрузка remote'а в момент совпадения маршрута

Комбинация `React.lazy` + `Suspense` с роутингом — естественный способ гарантировать, что `remoteEntry.js` подгружается **только тогда**, когда пользователь реально переходит на нужный маршрут, а не при первой загрузке хоста:

```tsx
const CheckoutApp = React.lazy(() => import('checkout/CheckoutApp'));

<Routes>
  <Route
    path="/checkout/*"
    element={
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutApp />
      </Suspense>
    }
  />
</Routes>
```

Пока пользователь не зашёл в `/checkout/*`, ни `remoteEntry.js` remote'а checkout, ни его чанки в сеть не уходят — ровно та же экономия, что и обычный route-based code splitting в SPA, только объект загрузки — не локальный чанк, а целый независимо задеплоенный remote.

## Что делать, если remote не загрузился

Здесь важно различать два разных отказа.

**Отказ на уровне сети** — `remoteEntry.js` недоступен (упал CDN, таймаут, 404 после отката версии). Без явной обработки `import()` просто зависнет или отклонится без осмысленного фолбэка. Решение — обернуть загрузку таймаутом, чтобы отклонённый промис долетел до `React.lazy`/`Suspense`/`ErrorBoundary` предсказуемо, а не через неопределённое время:

```ts
function loadRemoteWithTimeout<T>(importPromise: Promise<T>, ms = 5000): Promise<T> {
  return Promise.race([
    importPromise,
    new Promise<T>((_, reject) =>
      setTimeout(() => reject(new Error('Remote load timed out')), ms),
    ),
  ]);
}

const CheckoutApp = React.lazy(() =>
  loadRemoteWithTimeout(import('checkout/CheckoutApp')),
);
```

**Отказ на уровне рендера** — remote загрузился, но упал во время выполнения (баг, задеплоенный командой checkout). Без изоляции необработанная ошибка внутри дерева одного remote'а по умолчанию всплывает вверх по дереву React до ближайшей error boundary — если она не расставлена **на каждую точку монтирования remote'а**, ближайшей окажется граница самого shell'а, и баг одной команды роняет **весь продукт** для всех пользователей, включая части, вообще не связанные со сломанным remote'ом.

```tsx
class RemoteErrorBoundary extends React.Component<
  { fallback: React.ReactNode; children: React.ReactNode },
  { hasError: boolean }
> {
  state = { hasError: false };

  static getDerivedStateFromError() {
    return { hasError: true };
  }

  componentDidCatch(error: Error) {
    logToObservability('remote-mount-failed', error); // см. статью 07 про cross-MFE observability
  }

  render() {
    return this.state.hasError ? this.props.fallback : this.props.children;
  }
}
```

```tsx
<Route
  path="/checkout/*"
  element={
    <RemoteErrorBoundary fallback={<CheckoutUnavailableBanner />}>
      <Suspense fallback={<PageSkeleton />}>
        <CheckoutApp />
      </Suspense>
    </RemoteErrorBoundary>
  }
/>
```

Это техническое воплощение обещания «изоляция отказов на уровне деплоя» из статьи 01. Само по себе Module Federation даёт только механизм независимого деплоя — оно **не** даёт изоляцию отказов в рантайме автоматически. Если хост не расставил error boundary на каждую точку монтирования remote'а, сбой одной команды по-прежнему способен уронить всё приложение целиком — обещанная выгода остаётся чисто теоретической, пока команда хоста осознанно её не реализует.

## Типичные ошибки на интервью

- **«Единый роутер на всё приложение означает, что микрофронтенды не могут иметь собственные вложенные маршруты»** — неверно. Доминирующий на практике паттерн — гибрид: хост владеет только верхнеуровневой сегментацией (`/checkout/*`), а всё, что происходит внутри этого префикса, — целиком в ведении remote'а.

- **«Каждый remote может свободно создавать свой собственный `<BrowserRouter>`»** — если два независимых инстанса роутера пытаются одновременно управлять одним и тем же `window.history`, кнопка «назад» и навигация начинают вести себя непредсказуемо. Нужен один общий инстанс history (или глобальный механизм синхронизации, как в single-spa), а не независимые роутеры, каждый уверенный, что владеет URL.

- **«Раз Module Federation даёт независимый деплой, значит сбой одного remote'а автоматически не влияет на остальные»** — независимость деплоя не равна изоляции отказов в рантайме. Без явной error boundary на каждой точке монтирования remote'а необработанная ошибка одной команды всплывает до ближайшей границы — обычно до самого shell'а — и роняет весь продукт.

- **«Ленивая загрузка по маршруту происходит автоматически, достаточно `React.lazy`»** — `React.lazy` без обёрнутого в `Suspense` fallback'а и без обработки таймаута сетевого запроса за `remoteEntry.js` оставляет пользователя либо с бесконечным зависанием, либо с необработанным исключением, если CDN remote'а недоступен.

- **«Роутинг между микрофронтендами — чисто техническая деталь, к организационной автономии отношения не имеет»** — граница маршрутов (`/checkout/*` целиком принадлежит одной команде) — это ровно то же самое разделение ответственности, о котором была статья 01: чёткая граница маршрута — это публичный контракт между хостом и remote'ом, и именно она позволяет команде checkout менять свои внутренние страницы, ничего не согласовывая с остальными.
