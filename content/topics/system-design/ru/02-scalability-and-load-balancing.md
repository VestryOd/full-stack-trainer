# Scalability и Load Balancing

## Масштабирование: напоминание про vertical vs horizontal

Горизонтальное масштабирование **невозможно без балансировщика нагрузки (load balancer)**. Без него у вас просто N независимых серверов. Клиент должен сам выбирать между ними — или у каждого свой адрес в DNS (система доменных имён). Это не масштабируется и не даёт отказоустойчивости. (Различие вертикального и горизонтального масштабирования разобрано в статье System Design Fundamentals.)

Поэтому "добавить ещё серверов" — это половина ответа на вопрос о масштабировании. Вторая половина — **как трафик распределяется между ними** и **что происходит, когда один из них падает**. Это и есть тема Load Balancing.

## L4 vs L7 Load Balancer — разный уровень принятия решений

Это одно из самых важных различий, и его часто упускают. **L4 (transport layer) load balancer** работает на уровне TCP (transmission control protocol) и UDP (user datagram protocol). Он видит только адреса IP (internet protocol) и порты и не заглядывает в содержимое запроса.

```txt
Решение о маршрутизации принимается по:
  source IP, destination IP, source port, destination port

Преимущества: очень быстрый (не парсит payload), низкий overhead
Ограничения: не может маршрутизировать по URL, headers, cookies
```

**L7 (application layer) load balancer** работает на уровне HTTP. Он видит URL, headers, cookies и тело запроса.

```txt
Решение о маршрутизации принимается по:
  path (/api/* → backend A, /static/* → CDN/backend B)
  headers (Authorization, User-Agent)
  cookies (sticky sessions)

Преимущества: гибкая маршрутизация, A/B тесты, canary deploy
Минусы: выше latency (нужно терминировать TLS
        и парсить HTTP), дороже в вычислениях
```

Senior-нюанс: L7-балансировщик обычно **терминирует TLS** (transport layer security), превращая HTTPS (HTTP с шифрованием) в обычный HTTP внутри сети. Именно так он получает доступ к содержимому запроса. Цена — шаг расшифровки и шифрования на каждый запрос, и это нужно учитывать в latency-бюджете.

Реальные системы часто комбинируют оба уровня. L4 стоит на входе, для грубого распределения по регионам и availability zones — например, AWS (Amazon Web Services) NLB, network load balancer. L7 работает внутри, для маршрутизации между сервисами: AWS ALB (application load balancer), Nginx, Envoy.

## Алгоритмы балансировки

| Алгоритм | Как работает | Когда хорош | Когда плох |
|---|---|---|---|
| **Round Robin** | По кругу: A → B → C → A → ... | Серверы одинаковой мощности, запросы примерно одной "тяжести" | Не учитывает текущую нагрузку — медленный сервер получит столько же запросов, сколько быстрый |
| **Weighted Round Robin** | Как Round Robin, но с весами (сервер мощнее → больше запросов) | Серверы разной мощности (например, постепенный canary rollout) | Веса статичны, не реагируют на реальную нагрузку |
| **Least Connections** | Запрос идёт на сервер с наименьшим числом активных соединений | Запросы сильно различаются по длительности обработки | Балансировщику нужно отслеживать состояние соединений — чуть дороже |
| **IP Hash / Consistent Hashing** | Маршрутизация — функция от хеша клиентского IP (или другого ключа) | Нужна "липкость" без cookies, или cache-aware routing | С обычным хешем (`hash % N`) добавление сервера перераспределяет **почти весь** трафик |

### Consistent Hashing — почему это отдельная большая тема

Простой `hash(key) % N` ломается при изменении числа серверов. Добавили пятый сервер к четырём — и у **большинства** ключей меняется `hash % N`, они "переезжают" на другой сервер. Для кеша это означает массовый cache miss, для шардированной базы данных (БД) — масштабную перебалансировку данных.

**Consistent hashing** решает это, размещая и серверы, и ключи на одном "кольце" хешей. Тогда при добавлении или удалении сервера перемещается только доля ключей `~1/N`, а не весь набор:

```ts
// Упрощённая реализация consistent hashing с виртуальными узлами
class ConsistentHashRing {
  private ring = new Map<number, string>(); // hash -> server
  private sortedHashes: number[] = [];
  private readonly virtualNodesPerServer = 150; // снижает неравномерность

  addServer(serverId: string): void {
    for (let i = 0; i < this.virtualNodesPerServer; i++) {
      const hash = this.hash(`${serverId}#${i}`);
      this.ring.set(hash, serverId);
    }
    this.sortedHashes = [...this.ring.keys()].sort((a, b) => a - b);
  }

  getServer(key: string): string {
    const hash = this.hash(key);
    // находим первый узел на кольце с hash >= hash(key) (по кругу)
    const index = this.sortedHashes.findIndex((h) => h >= hash);
    const ringIndex = index === -1 ? 0 : index;
    return this.ring.get(this.sortedHashes[ringIndex])!;
  }

  private hash(input: string): number {
    // в реальной реализации — стабильная хеш-функция (например, MurmurHash)
    let h = 0;
    for (const char of input) h = (h * 31 + char.charCodeAt(0)) >>> 0;
    return h;
  }
}
```

**Virtual nodes** — несколько точек на кольце для каждого реального сервера — решают проблему неравномерного распределения, когда серверов мало. Без них один сервер может случайно получить значительно больший диапазон кольца, чем другой.

Это не только про load balancing. Тот же принцип лежит в основе шардинга в Cassandra и DynamoDB, а также в распределённых кешах (memcached с consistent hashing на клиенте).

## Health Checks: active vs passive

Балансировщик должен знать, какие backend-инстансы живы, **до** отправки трафика на них.

```txt
Active health checks:
  балансировщик сам периодически шлёт запрос
  (например, GET /health)
  Backend отвечает 200 OK, если готов принимать трафик
  Если N проверок подряд провалились → инстанс убирается из пула

Passive health checks:
  балансировщик следит за реальными запросами
  Если процент ошибок или таймаутов превышает порог
  → инстанс временно убирается
```

Senior-нюанс: эндпоинт `/health` не должен быть тривиальным "always 200". Но он и не должен проверять **всё**.

Допустим, он проверяет соединение с БД, а БД временно перегружена. Тогда health check может начать снимать с пула *все* инстансы одновременно. Это **cascading failure**: механизм, призванный защищать систему, сам её обрушивает. Хороший health check проверяет именно то, без чего инстанс не может обслуживать запросы, и не более того.

## Sticky Sessions — когда это всё-таки нужно

Sticky sessions привязывают пользователя к конкретному серверу — обычно через cookie с id инстанса. При stateless-архитектуре это почти всегда антипаттерн, как разобрано в статье System Design Fundamentals. Но есть легитимные случаи:

```txt
- WebSocket-соединения: соединение физически держится
  одним сервером, и "переключить" его на другой сервер
  без разрыва невозможно
- Серверный кеш в памяти процесса (in-memory cache
  конкретного инстанса) — но это нужно явно обосновать,
  обычно лучше Redis
```

Если sticky sessions используются, нужно явно проговорить последствия. При падении инстанса все прилипшие к нему клиенты теряют соединение и состояние и должны переподключиться. Для WebSocket это означает явную логику переподключения на клиенте.

## CDN как "масштабирование на уровне сети"

CDN (content delivery network — сеть доставки контента) — это, по сути, географически распределённый слой кеширования **перед** вашим бэкендом:

```txt
User (Berlin) → CDN edge (Frankfurt) → cache hit
  → ответ без запроса к origin
User (Tokyo)  → CDN edge (Tokyo) → cache miss
  → запрос к origin → кешируется
```

CDN снижает нагрузку на origin: статика, изображения, видео, иногда целые HTML-страницы для сайтов на статической генерации (SSG). Он также снижает latency за счёт географической близости к пользователю.

Для динамического API CDN обычно не кеширует напрямую. Но его можно использовать для **edge-вычислений**: проверка авторизации, geo-роутинг, A/B-тесты до похода к origin.

## Auto Scaling — не только "добавить сервер при высокой нагрузке"

```txt
Reactive scaling:
  metric (CPU > 70%, queue depth > 1000, p99 latency > 500ms)
  → scale-out (новые инстансы)
  → cooldown period (например, 5 минут — не масштабироваться
     повторно, пока новые инстансы не "разогрелись")

Predictive/scheduled scaling:
  заранее известные паттерны нагрузки (утренний пик, Black Friday)
  → масштабирование заранее, а не в реакции на пик
```

Senior-нюансы по auto scaling:

- **Cold start**: новый инстанс может запускаться минуты, особенно если ему нужно прогреть кеш и соединения с БД. Reactive scaling опаздывает на этот промежуток, и именно тогда происходит деградация. Поэтому для предсказуемых пиков (распродажи) используют scheduled scaling.
- **Загрузка процессора не всегда правильный сигнал.** Для I/O-bound сервисов — много ожидания ответов от БД и внешних API — CPU (процессор) может простаивать при перегруженном сервисе. Более показательные метрики: глубина очереди запросов, latency, число активных соединений.
- **Connection limits на БД.** Если auto scaling добавляет app-инстансы без ограничения, каждый открывает свой пул соединений к БД. Можно упереться в `max_connections` базы раньше, чем в CPU app-серверов. Это частый практический подвох, и его упоминание показывает глубину понимания.

## Cache Layer как способ масштабирования

```txt
Client → App Server → Redis (cache) → Database
                         ↑
      cache hit: ответ за ~1ms, без похода в БД
      cache miss: читаем из БД, кладём в кеш
```

Кеш — это не "ускорение". Это **снятие нагрузки с БД**, что позволяет обслуживать больше запросов тем же количеством ресурсов базы.

Детали стратегий кеширования — cache-aside, write-through, TTL (time to live, время жизни), инвалидация — разобраны в статье про кеширование. Здесь важно зафиксировать, что кеш — один из главных рычагов масштабирования системы в целом, а не мелкая оптимизация.

## Типичные ошибки на интервью

- **Путать L4 и L7 балансировку** или вообще не называть это различие. L7 нужен для маршрутизации по URL, cookies и headers; L4 — для грубой быстрой балансировки на транспортном уровне.

- **Предлагать `hash(key) % N` как consistent hashing.** При таком подходе изменение N перераспределяет ключи — и именно эту проблему consistent hashing решает.

- **Считать sticky sessions "плохими всегда".** Для WebSocket-соединений они архитектурно необходимы: соединение физически держится одним инстансом. Важно понимать, *когда* они нужны, а не отвергать концепцию целиком.

- **Health check, который проверяет слишком много** — и приводит к cascading failure. Временная проблема одной зависимости (БД) выводит из пула все инстансы одновременно.

- **Auto scaling по CPU для I/O-bound сервисов** — не замечая, что сервис может быть перегружен по latency или глубине очереди при простаивающем процессоре.

- **"CDN решит проблему динамического API".** CDN эффективен для статики и кешируемого контента. Для персонализированных и динамических ответов нужен другой подход: кеш на уровне приложения или edge compute.

- **Игнорировать connection limits БД при auto scaling app-серверов** — классический случай, когда "масштабирование одного слоя" создаёт узкое место в другом.
