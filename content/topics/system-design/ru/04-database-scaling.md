# Масштабирование базы данных

## Почему именно БД — самое частое узкое место

App-серверы stateless, их легко масштабировать горизонтально: добавили инстансы за балансировщиком нагрузки (load balancer) — и готово. База данных (БД) — это, по определению, **stateful** компонент. Её данные физически живут в одном месте, поэтому просто "добавить ещё одну БД" не работает так же просто, как с app-сервером. Нужно решить, **где** какие данные находятся и как поддерживать консистентность между копиями.

Путь масштабирования БД почти всегда идёт в таком порядке, и каждый следующий шаг сложнее предыдущего:

```txt
1. Vertical scaling (больше RAM/CPU/диска под БД)
2. Индексы и оптимизация запросов
   (часто решает 80% проблем без инфраструктурных изменений)
3. Read Replicas (масштабирование чтения)
4. Caching layer (см. отдельную статью)
5. Sharding / Partitioning (масштабирование записи и объёма)
6. Database per service / CQRS (архитектурное разделение)
```

Senior-ответ начинается не с шардинга. Он начинается с замечания, что **большая часть "проблем с БД" на практике решается индексами, оптимизацией запросов и кешем**. Переход к шардингу — значимая архитектурная инвестиция со своими долгосрочными издержками, и её стоит делать только когда более простые шаги исчерпаны.

## Read Replicas — синхронная vs асинхронная репликация

```txt
Write
 ↓
Primary DB ──replication──→ Replica 1
                ──────────→ Replica 2
                ──────────→ Replica 3

App: записи → Primary
     чтения → Replicas (round-robin / least-lag)
```

Это работает потому, что в типичных read-heavy системах read:write часто 10:1-1000:1, как показано в статье про основы System Design. Несколько read-реплик снимают основную нагрузку с primary, оставляя ему только записи.

**Синхронная репликация**: primary ждёт подтверждения от реплики или реплик, прежде чем считать запись успешной.

```txt
Плюсы: реплика гарантированно содержит последние данные
       (zero data loss при failover)
Минусы: latency записи = latency самой медленной
        синхронной реплики; если реплика недоступна,
        запись может блокироваться
```

**Асинхронная репликация**: primary подтверждает запись клиенту немедленно, а реплики применяют изменения "когда смогут".

```txt
Плюсы: запись быстрая, не зависит от состояния реплик
Минусы: replication lag — реплика временно отстаёт
        от primary (обычно миллисекунды, но под
        нагрузкой может быть секунды)
```

### Replication Lag и проблема "read-your-own-writes"

Классический сценарий, который почти всегда всплывает на интервью:

```txt
1. Пользователь обновляет профиль → запись идёт в Primary
2. Сразу после этого он делает GET своего профиля
   → запрос идёт на Replica
3. Replication Lag = 200ms,
   Replica ещё не применила изменение
4. Пользователь видит старые данные сразу после сохранения
```

Решения, каждое со своим trade-off:

- **Читать с primary сразу после записи** — для того же пользователя. Часто реализуется как "read-your-writes" routing: следующие N секунд после записи чтения этого пользователя или сессии идут на primary.
- **Session affinity к конкретной реплике**, которая гарантированно получила обновление. Сложно отследить.
- **Версионирование**: клиент передаёт "минимальную приемлемую версию данных", и реплика, отставшая сильнее, для этого запроса не используется.
- **Принять устаревание данных (staleness) как часть UX** — опыта пользователя. Для большинства данных это нормально: "лайк" не обязан появляться мгновенно у самого автора.

Это не "теоретическая" проблема. В продакшене она проявляется как баг "сохранил — а старые данные показались". И это частая причина тикетов поддержки.

## Sharding (Partitioning) — разделение данных между узлами

Иногда реплик не хватает: **объём записи** или **объём данных** превышает возможности одного узла. Тогда данные физически разделяются между независимыми узлами-шардами. Каждый шард хранит свою часть данных.

Есть три распространённых способа решить, в какой шард попадает строка. Выбор определяет, будет ли нагрузка равномерной и останутся ли дешёвыми range-запросы. Он же определяет, сможете ли вы выполнить требования к месту хранения данных — например, GDPR (General Data Protection Regulation):

```txt
Range-based sharding:
  Users A-M  → Shard 1
  Users N-Z  → Shard 2

  Плюсы: просто, легко выполнять range-запросы
         внутри одного шарда
  Минусы: неравномерное распределение (hot shard, если,
          например, много пользователей с фамилиями
          на одну букву)

Hash-based sharding:
  shard = hash(user_id) % N

  Плюсы: равномерное распределение
  Минусы: range-запросы ("все пользователи с id 1000-2000")
          требуют обращения ко всем шардам; решардинг при
          изменении N — массовое перемещение данных
          (см. consistent hashing в статье про балансировку)

Geo-based sharding:
  EU users → Shard EU, US users → Shard US

  Плюсы: соответствие требованиям data residency,
         низкая latency (данные ближе к пользователю)
  Минусы: cross-region запросы (например, друзья
          в разных регионах) становятся сложными
```

### Главная проблема шардинга: операции, которые раньше были "бесплатными", становятся дорогими

Шардинг превращает три обычные операции в трудные задачи. На одном узле каждая из них дешёвая: JOIN — это один запрос на SQL (structured query language), агрегация — тоже один запрос. А транзакция получает ACID (atomicity, consistency, isolation, durability) бесплатно.

| Операция | До шардинга (одна БД) | После шардинга |
|---|---|---|
| `JOIN users, orders` | Один SQL-запрос | На уровне БД невозможен; делать в приложении — несколько запросов плюс merge в коде |
| Транзакция: списать с A, зачислить на B | Один шард, и ACID гарантирует атомарность | A и B могут быть в разных шардах; нужен 2-Phase Commit или Saga |
| `SELECT COUNT(*) WHERE status = X` | Один запрос | Результат нужно агрегировать со всех шардов и просуммировать в приложении |

Перевод между шардами становится распределённой транзакцией. Оба способа её выполнить — 2-Phase Commit и Saga — приносят свои сложности и свою latency.

**Выбор shard key — самое важное решение в шардинге**, и его почти невозможно изменить без полной миграции данных. Хороший shard key:

- обеспечивает равномерное распределение нагрузки и избегает hot shard: не стоит шардировать по `tenant_id`, если один клиент даёт 90% трафика;
- покрывает большинство запросов. Если 95% запросов идут с `user_id`, шардирование по `user_id` оставляет их внутри одного шарда. Но запросы по `order_id` теперь требуют обращения ко всем шардам, если `order_id` не связан с `user_id` предсказуемо.

## SQL vs NoSQL — это не "какая БД лучше", а "какие гарантии нужны"

Вопрос не в том, какое семейство лучше. Вопрос в том, какие гарантии вам нужны. SQL — это реляционная база с фиксированной схемой; NoSQL (нереляционные хранилища) — это несколько очень разных семейств:

```txt
SQL (PostgreSQL, MySQL):
  + строгая схема, ACID-транзакции, JOIN, зрелая экосистема
  - горизонтальное масштабирование (шардинг) сложнее
    и менее "из коробки"

NoSQL — Document (MongoDB):
  + гибкая схема, удобно для denormalized/nested данных
  - нет JOIN на уровне БД, ACID обычно только
    в рамках одного документа

NoSQL — Key-Value (DynamoDB, Redis):
  + предсказуемая latency при больших объёмах,
    встроенный шардинг
  - запросы только по ключу (или ограниченным индексам)

NoSQL — Wide-Column (Cassandra):
  + write-heavy нагрузка, встроенная multi-region репликация
  - eventual consistency по умолчанию, модель данных
    заточена под конкретные query patterns
    (denormalization обязательна)
```

Senior-ответ на "SQL или NoSQL?" — это про **паттерн доступа к данным и требования к консистентности**, а не про "NoSQL масштабируется лучше". Современный PostgreSQL с репликами и партиционированием прекрасно держит огромные нагрузки: Instagram много лет работал на шардированном PostgreSQL.

## CQRS и Database per Service

**CQRS (Command Query Responsibility Segregation)** — это разделение модели данных для записи и для чтения:

```txt
Write Model (нормализованная, оптимизирована
             для целостности данных)
  ↓ события/синхронизация
Read Model (денормализованная, оптимизирована
            под конкретные запросы UI, может быть
            в другой БД — например, Elasticsearch
            для поиска)
```

Это позволяет независимо масштабировать и оптимизировать пути чтения и записи. Цена — задержка синхронизации между write- и read-моделью, обычно через очередь событий. То есть осознанный переход к eventual consistency для чтения.

**Database per Service** — микросервисная практика: у каждого сервиса своя БД, и никто не лезет в чужую БД напрямую. Это даёт изоляцию — изменение схемы одного сервиса не ломает другие — и позволяет каждому сервису масштабироваться независимо.

Но появляется классическая проблема: а что с запросом, которому нужны данные из нескольких сервисов? Есть два варианта. Либо сделать несколько запросов и объединить результаты на уровне API Gateway или BFF (Backend For Frontend). Либо держать денормализованную копию данных внутри сервиса, которому она нужна, и синхронизировать её событиями.

## Типичные ошибки на интервью

- **Предлагать шардинг как первый шаг масштабирования БД**, не упомянув индексы, read-реплики и кеш. Они решают значительно больший процент реальных проблем с гораздо меньшей сложностью.

- **Не упоминать replication lag и read-your-writes** при добавлении read-реплик. Это один из самых ожидаемых follow-up вопросов, и его отсутствие сразу заметно.

- **Считать шардинг "бесплатным" масштабированием** — не проговаривая, что JOIN-ы, транзакции и агрегации становятся кратно сложнее.

- **Выбирать shard key без объяснения** — особенно не упоминая риск hot shard и цену миграции при изменении схемы шардирования.

- **"NoSQL масштабируется, SQL — нет".** Это игнорирует то, как далеко масштабируется современный PostgreSQL с партиционированием и репликами. Выбор должен основываться на паттернах доступа и требованиях к консистентности.

- **CQRS как "просто разделить чтение и запись"**, без упоминания eventual consistency между write- и read-моделью. Это центральный trade-off паттерна.
