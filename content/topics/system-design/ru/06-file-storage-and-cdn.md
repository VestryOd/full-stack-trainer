# File Storage и CDN

## Почему "файл через backend" — это плохая архитектура

Почти любая система работает с файлами через два компонента. Объектное хранилище вроде S3 (Simple Storage Service) держит сами байты. CDN (content delivery network — сеть доставки контента) отдаёт их близко к пользователю. Наивная реализация толком не использует ни то, ни другое и гонит каждый байт через ваш собственный бэкенд:

```txt
Frontend → Backend → File System / S3
```

Проблема не только в "нагрузке" в абстрактном смысле — она конкретна:

```txt
- Бэкенд держит HTTP-соединение открытым на всё время
  загрузки (для видео в 1 GB это могут быть минуты) и
  блокирует поток или воркер, который мог бы
  обслуживать другие запросы
- Файл проходит через память или диск бэкенда дважды:
  принять от клиента → переслать в S3
- Бэкенд должен масштабироваться под нагрузку загрузки
  файлов, хотя его основная роль — бизнес-логика
```

## Pre-Signed URLs — правильный паттерн

```txt
1. Frontend → Backend: "хочу загрузить файл report.pdf,
   5MB, application/pdf"
2. Backend проверяет права доступа, генерирует
   pre-signed URL (подписанный временный URL с
   ограниченным сроком действия, например 15 минут,
   и конкретными разрешёнными параметрами)
3. Backend → Frontend: возвращает pre-signed URL
4. Frontend → S3: загружает файл прямо в S3
   по этому URL (PUT-запрос)
5. Backend узнаёт о завершении загрузки через:
   - callback/webhook от S3 (S3 Event Notifications), или
   - явный запрос от frontend "я загрузил, вот его id"
```

```ts
// Backend: генерация pre-signed URL (AWS SDK v3)
import { S3Client, PutObjectCommand } from '@aws-sdk/client-s3';
import { getSignedUrl } from '@aws-sdk/s3-request-presigner';

const s3Client = new S3Client({ region: 'eu-central-1' });

async function createUploadUrl(
  userId: string,
  fileName: string,
  contentType: string,
) {
  const key = `uploads/${userId}/${crypto.randomUUID()}-${fileName}`;

  const command = new PutObjectCommand({
    Bucket: 'my-app-uploads',
    Key: key,
    ContentType: contentType, // ограничивает, какой Content-Type примет S3
  });

  // ссылка действует 15 минут
  const url = await getSignedUrl(s3Client, command, { expiresIn: 900 });
  return { uploadUrl: url, key };
}
```

Почему это решает проблему:

```txt
+ Бэкенд больше не передаёт через себя сами байты файла —
  только метаданные запроса
  (миллисекунды CPU вместо минут I/O)
+ S3 масштабируется горизонтально "из коробки" —
  бэкенду не нужно об этом думать
+ Дешевле — трафик идёт напрямую в объектное хранилище,
  минуя compute-ресурсы бэкенда
```

Senior-нюанс про безопасность: pre-signed URL должен **ограничивать** параметры загрузки — `ContentType`, максимальный размер через `Content-Length-Range` в policy, конкретный `key`.

Без этих ограничений пользователь, получивший URL для загрузки своего аватара, теоретически может загрузить почти что угодно. Любой файл, любого размера, в любое место бакета. И это возможно всё время жизни ссылки — весь её TTL (time to live).

## Метаданные: что в S3, что в БД

```txt
S3 (объектное хранилище):
  - сами байты файла
  - URL/key для доступа

PostgreSQL (метаданные):
  - id, userId, originalFileName
  - s3Key, size, mimeType
  - status (uploading / processing / ready / failed)
  - createdAt, processedAt
```

Почему не хранить файлы в базе данных (БД), в полях типа BLOB (binary large object)? Реляционные БД физически не предназначены для больших бинарных объектов. Это раздувает размер БД и замедляет бэкапы: бэкап базы с терабайтами видео занимает часы. Плюс это плохо работает с репликацией и кешированием на уровне БД.

Объектное хранилище спроектировано именно под это: дешёвое хранение, встроенное geo-распределение, прямая отдача через CDN.

Поле `status` — важная деталь, которую часто упускают. После получения pre-signed URL клиент может вообще не загрузить файл — например, закрыл вкладку. Запись в БД должна отражать это состояние, чтобы не показывать пользователю "файл загружен", когда в S3 ничего нет. Ещё нужна периодическая очистка "осиротевших" записей со статусом `uploading`, которые никогда не перешли в `ready`.

## CDN: как кеш, но для файлов, и с нюансами приватности

CDN держит копии ваших файлов на edge-серверах по всему миру:

```txt
Без CDN:
  User (Australia) → Origin (S3 bucket в eu-west-1)
  → latency определяется расстоянием до Ирландии

С CDN:
  User (Australia) → CDN Edge (Sydney)
  → cache hit: ответ с edge-сервера, минимальная latency
  → cache miss: edge идёт в Origin, кеширует результат,
    отдаёт пользователю
```

### Публичный контент vs приватный контент

Для публичных файлов (аватары, изображения товаров) всё просто: CDN кеширует по URL, а заголовки `Cache-Control` определяют TTL.

Для **приватного** контента (документы пользователя, платное видео) кеширование по URL не подходит: URL не должен быть доступен без авторизации. Работает это так:

- **Signed CDN URLs** (CloudFront Signed URLs или Cookies) — CDN сам проверяет подпись и срок действия перед тем как отдать закешированный контент.
- Кеш на уровне CDN всё равно работает, потому что контент лежит на edge. Доступ контролируется срок-ограниченной подписью, а не секретностью URL.

### Cache invalidation для CDN

Проблема: пользователь обновил аватар, но CDN ещё 24 часа — весь TTL из `Cache-Control` — отдаёт старую версию всем. Есть два решения:

1. **Versioned URLs**: `avatar-v2.jpg` вместо `avatar.jpg`. Новый URL означает гарантированный cache miss, то есть новый контент. Это лучший подход, потому что явная инвалидация не нужна вообще.
2. **Явный invalidation API** (CloudFront Invalidation) — запрос "сбросить кеш для этого пути на всех edge-нодах". Медленнее (минуты) и стоит денег при частом использовании.

Versioned URLs — практически всегда лучший выбор для пользовательского контента. Они превращают вопрос "когда инвалидировать кеш" в "кеш живёт вечно, потому что URL уникален для каждой версии контента".

## Image/Video Processing Pipeline

```txt
1. Client → pre-signed URL → S3 (оригинал)
2. S3 Event Notification → Queue
3. Воркер читает событие, скачивает оригинал из S3
4. Воркер генерирует производные версии:
   - thumbnails разных размеров
   - конвертация формата (HEIC → JPEG,
     видео → несколько разрешений)
5. Воркер загружает результаты обратно в S3
   (отдельные keys/bucket)
6. Воркер обновляет статус в БД
   (status: ready, добавляет URL производных)
7. Frontend узнаёт, что обработка завершена — через
   polling, WebSocket или server-sent events
```

Очередь здесь решает ту же задачу, что и в статье про Message Queues. В стеке Amazon эта очередь — SQS (Simple Queue Service) или SNS (Simple Notification Service).

10 000 одновременных загрузок не создают 10 000 параллельных тяжёлых задач обработки видео. Они становятся 10 000 сообщений в очереди, которые пул воркеров обрабатывает с постоянной скоростью. Без очереди резкий всплеск загрузок — например, после вирусного поста — уронит processing-сервис.

## Multipart Upload — для больших файлов

```txt
Файл 5 GB:
  - разбивается на части по 5-100 MB
  - каждая часть загружается отдельным PUT-запросом
    (можно параллельно, можно с retry
    для конкретной части)
  - после загрузки всех частей
    CompleteMultipartUpload собирает их в один объект
```

Зачем: при загрузке файла одним запросом любой сетевой сбой на 99% означает retry **всего файла с нуля**. Multipart позволяет повторить только неудачную часть. Он же позволяет параллелить загрузку, что быстрее на быстром интернете. И поддерживает файлы больше лимита на один PUT — для S3 это 5GB.

## Безопасность загрузок — частый follow-up

- Валидируйте `Content-Type` на бэкенде при выдаче pre-signed URL. Не доверяйте расширению файла от клиента.
- Сканируйте на вирусы и malware **после** загрузки, но **до** того как файл станет доступен другим пользователям: статус "scanning" → "ready".
- Ограничивайте размер через policy в pre-signed URL, а не только проверкой на клиенте. Клиент можно обойти.
- Изолируйте загруженный пользовательский контент от исполняемого кода — отдельный домен или bucket без возможности выполнения. Это защищает от XSS (cross-site scripting) через загруженный "image.svg" с JS внутри.

## Типичные ошибки на интервью

- **Предлагать "загрузку через backend" как финальный ответ**, не упоминая pre-signed URLs. Это ожидаемое "правильное" решение для этой темы.

- **Хранить файлы как BLOB в реляционной БД**, без объяснения, почему это плохо масштабируется: размер БД, бэкапы, репликация.

- **Не разделять метаданные и сам файл** — путать "где хранится файл" с "где хранится информация о файле".

- **CDN как "просто кеш".** Это упускает разницу между публичным и приватным контентом, и упускает, что приватному контенту нужны signed URLs, а не отсутствие CDN.

- **Явный вызов invalidation API как единственное решение**, без упоминания versioned URLs, которые избегают проблемы инвалидации вообще.

- **Не упоминать очередь для обработки медиа.** Синхронная генерация thumbnail при загрузке означает, что пользователь ждёт обработку видео внутри HTTP-запроса.

- **Игнорировать безопасность загрузок** — pre-signed URL без ограничений на размер и тип, отсутствие проверки контента перед публикацией.
