# Caching

## Зачем нужен кеш — снятие нагрузки, а не "ускорение"

Кеш сокращает latency конкретного запроса. Но важнее другое: он снимает **общую нагрузку с базы данных (БД)**, и та же БД начинает обслуживать кратно больше пользователей.

Цифры, из которых это следует:

- запрос к Redis или memcached занимает ~0.1-1ms;
- запрос к реляционной БД с обращением к диску — единицы-десятки миллисекунд;
- сложный JOIN или агрегация — до сотен миллисекунд.

| | Без кеша | С кешом (cache hit) |
|---|---|---|
| Путь запроса | Client → API → Database | Client → API → Redis → Response |
| При 10 000 req/s | все 10 000 идут в БД | 9 000 обслужены из Redis, 1 000 (miss) идут в БД |

Главный вопрос на интервью не "что такое кеш". Главный вопрос — **где именно в архитектуре он стоит, что в нём хранится, как он инвалидируется и что происходит при cache miss на масштабе**. Именно эти детали отличают senior-ответ от "добавим Redis".

## Cache-Aside (Lazy Loading) — паттерн по умолчанию

Приложение явно управляет кешем: читает из кеша, а при промахе идёт в БД и сохраняет результат.

```ts
async function getUser(userId: string): Promise<User> {
  const cached = await redis.get(`user:${userId}`);
  if (cached) {
    return JSON.parse(cached); // cache hit
  }

  const user = await db.user.findUnique({ where: { id: userId } });
  if (user) {
    // TTL обязателен — иначе устаревшие данные могут жить вечно
    await redis.set(`user:${userId}`, JSON.stringify(user), 'EX', 300);
  }
  return user;
}
```

- **Плюсы**: кешируется только то, что реально запрашивается (lazy). Если Redis упал, система продолжает работать — просто медленнее, идёт прямо в БД.
- **Минусы**: первый запрос после промаха или инвалидации всегда медленный (cache miss penalty). И есть короткое окно несогласованности между БД и кешом.

## Write-Through и Write-Behind — альтернативы для записи

| Паттерн | Как работает | Плюсы | Минусы |
|---|---|---|---|
| **Cache-Aside** | Чтение через кеш, запись — напрямую в БД (с инвалидацией кеша) | Просто, кеш не "грязный" | Cache miss penalty |
| **Write-Through** | Запись синхронно идёт и в кеш, и в БД | Кеш всегда согласован с БД | Каждая запись медленнее (две операции) |
| **Write-Behind (Write-Back)** | Запись идёт в кеш, в БД сбрасывается асинхронно (batched) | Очень быстрая запись | Риск потери данных при падении кеша до flush; сложность |

Write-behind — это явный обмен durability на latency записи. На собеседовании скажите прямо. "Write-behind подходит для метрик и счётчиков, где потеря последних нескольких секунд данных приемлема. Для платежей — нет."

## Eviction Policies — что выкидывать, когда кеш заполнен

| Политика | Что выкидывает | Когда лучше |
|---|---|---|
| **Least recently used (LRU)** | То, что дольше всего не запрашивали | "Горячие" данные с временной локальностью |
| **Least frequently used (LFU)** | То, что запрашивали реже всего | Популярность стабильна во времени |
| **Time to live (TTL)** | Всё, у чего истекло время жизни, независимо от частоты использования | — |

Redis поддерживает несколько политик из коробки: `allkeys-lru`, `allkeys-lfu`, `volatile-ttl` и другие. Выбор должен соответствовать паттерну доступа. Для feed- и trending-данных LFU часто лучше LRU. Популярный пост может временно "не запрашиваться" несколько минут, но в среднем остаётся горячим.

## Cache Invalidation — "одна из двух действительно сложных вещей в CS"

Известная шутка ("There are only two hard things in Computer Science: cache invalidation and naming things") — не просто шутка. Проблема в том, что у вас появляется **два источника правды**: БД и кеш. Любая запись создаёт окно, в котором они расходятся.

Три стратегии инвалидации, от самой простой к самой развязанной:

1. **TTL** — самая простая. Данные могут быть устаревшими всё время жизни ключа. Подходит, когда устаревание данных (staleness) допустимо бизнес-логикой.
2. **Explicit invalidation** (`DEL` после `UPDATE`) — кеш удаляется или обновляется синхронно с изменением данных. Точнее, но **все** пути записи должны не забывать инвалидировать кеш, а это легко упустить при росте кодовой базы.
3. **Event-based invalidation** — изменение данных публикует событие через очередь или CDC (change data capture), и кеш инвалидирует асинхронный обработчик. Это развязывает запись от инвалидации, но добавляет задержку: кеш становится eventually consistent.

Senior-нюанс — **race condition при cache-aside записи**:

```txt
T1: читает из БД старое значение V1 (cache miss)
T2: обновляет БД на V2, инвалидирует кеш
T1: записывает в кеш V1 (устаревшее!) —
    после того, как T2 уже всё сделал

Результат: кеш содержит V1, БД содержит V2 —
           несогласованность до истечения TTL
```

Это редкий, но реальный крайний случай (edge case) в высоконагруженных системах. Есть три решения:

- короткий TTL как страховочная сетка: даже если инвалидация не сработала, данные не зависнут навечно;
- версионирование ключей кеша (`user:123:v{version}`);
- распределённый лок на запись.

## Cache Stampede (Thundering Herd) — классический вопрос

Ключ с очень высоким трафиком — например, главная страница — истекает по TTL. **Тысячи одновременных запросов** видят cache miss и **все** одновременно идут в БД. Это внезапная пиковая нагрузка, способная уронить БД именно в момент истечения TTL.

```ts
// ❌ Без защиты: при истечении TTL все параллельные запросы
// одновременно бьют в БД
async function getHomepage(): Promise<Homepage> {
  const cached = await redis.get('homepage');
  if (cached) return JSON.parse(cached);
  const data = await db.buildHomepage(); // 10 000 параллельных вызовов!
  await redis.set('homepage', JSON.stringify(data), 'EX', 60);
  return data;
}

// ✅ С распределённым локом: только один запрос идёт в БД,
// остальные либо ждут, либо получают немного устаревшие данные
async function getHomepageSafe(): Promise<Homepage> {
  const cached = await redis.get('homepage');
  if (cached) return JSON.parse(cached);

  const lockAcquired = await redis.set('homepage:lock', '1', 'NX', 'EX', 10);
  if (!lockAcquired) {
    // другой инстанс уже пересчитывает — отдаём слегка устаревшие данные
    // или ждём и повторяем (с коротким polling)
    const stale = await redis.get('homepage:stale');
    if (stale) return JSON.parse(stale);
    await sleep(50);
    return getHomepageSafe();
  }

  const data = await db.buildHomepage();
  await redis.set('homepage', JSON.stringify(data), 'EX', 60);
  // резервная копия на час
  await redis.set('homepage:stale', JSON.stringify(data), 'EX', 3600);
  await redis.del('homepage:lock');
  return data;
}
```

Другие решения:

```txt
Random TTL jitter:  TTL = 60 + random(0, 10) секунд
   → ключи истекают не одновременно, нагрузка размазывается

Probabilistic early expiration (XFetch):
   чем ближе к истечению TTL, тем выше шанс,
   что один из запросов досрочно пересчитает значение,
   пока остальные продолжают использовать старое

Background refresh:
   отдельный воркер обновляет горячие ключи заранее,
   до истечения TTL — пользовательские запросы
   никогда не видят промах по ним
```

## Multi-Level Caching — кеш как иерархия, а не один слой

Кеш редко бывает одним слоем. В реальной системе запрос проваливается через несколько — от браузера до базы, включая edge-серверы CDN (content delivery network). Каждый уровень отсекает часть трафика для следующего:

```txt
Browser Cache (HTTP cache-control, Service Worker)
  ↓ miss
CDN Edge Cache (статика, иногда полные HTML-страницы)
  ↓ miss
Application-level Cache (in-process, например LRU-кеш
  в памяти самого инстанса)
  ↓ miss
Distributed Cache (Redis/Memcached — общий для всех инстансов)
  ↓ miss
Database
```

Senior-нюанс: **in-process кеш на каждом инстансе** — самый быстрый уровень: нет сетевого round-trip. Но он размножается по инстансам и плохо инвалидируется: чтобы сбросить локальные кеши сразу везде, нужно broadcast-сообщение через Redis Pub/Sub. Поэтому их используют для данных, которые почти никогда не меняются (конфигурация, feature flags) либо допускают устаревание в несколько секунд.

## Что кешировать, а что — нет

Хорошие кандидаты:

- профили пользователей и каталоги товаров — read-heavy, меняются редко;
- результаты тяжёлых агрегаций и JOIN-ов;
- сессии, если они не stateless через JWT (JSON Web Token);
- счётчики rate limit и фиче-флаги.

Плохие кандидаты или те, что требуют особой осторожности:

- балансы счетов и состояние платежей — здесь устаревание равно бизнес-риску. Источник истины запрашивайте напрямую, либо используйте кеш в режиме CP (consistency over availability) с явной инвалидацией в той же транзакции;
- данные, уникальные почти для каждого запроса: hit ratio низкий, кеш не помогает и только добавляет накладные расходы.

Метрика, на которую стоит ориентироваться — **cache hit ratio**, доля попаданий в кеш. Если она ниже ~70-80% для конкретного типа ключей, кеш, возможно, не оправдывает добавленную сложность для этих данных.

## Типичные ошибки на интервью

- **"Добавим Redis" без указания паттерна (cache-aside vs write-through) и стратегии инвалидации** — самый частый поверхностный ответ. Интервьюер ожидает конкретику.

- **Не упоминать cache stampede** при обсуждении высоконагруженного популярного ключа с TTL. Это один из самых ожидаемых follow-up вопросов.

- **Путать TTL и eviction policy.** TTL — это явное время жизни конкретного ключа. Eviction policy (LRU/LFU) — это что происходит, когда кеш **переполнен**, независимо от TTL.

- **Игнорировать race condition при cache-aside** — считать, что "прочитал из БД, записал в кеш" атомарно и безопасно при конкурентных записях.

- **Кешировать данные, требующие строгой консистентности** (балансы, инвентарь с лимитом), без обсуждения того, что устаревание здесь может означать прямые денежные потери.

- **Забывать про in-process кеш при горизонтальном масштабировании.** Если кеш живёт в памяти каждого инстанса, инвалидация на одном инстансе не затрагивает остальные.

- **Не давать числовую оценку cache hit ratio.** "Кеш поможет" — это не ответ. Назовите соотношение read:write и hit ratio, при которых кеш действительно снижает нагрузку на БД на порядок.
