# Система чата

## Requirements Clarification и scope

"Спроектируй чат как WhatsApp/Slack" — слишком широко. Сильный ответ начинается с сужения scope:

**Functional Requirements (для обсуждения выбираем 1:1 + группы небольшого размера):**

```txt
- 1:1 сообщения
- групповые чаты (уточнить: лимит участников — 10 человек или 10 000,
  это РАЗНЫЕ архитектурные задачи, см. ниже)
- история сообщений
- online/offline статус, read receipts, typing indicator
- (отдельно уточнить, "вне scope" на первой итерации) голос/видео,
  end-to-end шифрование, файлы/медиа
```

**Non-Functional Requirements:**

```txt
- Latency доставки сообщения: десятки-сотни мс
- Сообщение не должно теряться (durability) — это явное отличие
  от "лайка" или presence-статуса, которые можно потерять без катастрофы
- Поддержка миллионов одновременных WebSocket-соединений
- Ordering: сообщения в рамках одного чата должны приходить
  в консистентном порядке у всех участников
```

Эта статья берёт транспортный слой как данность и говорит о специфике чата: хранение сообщений, порядок, доставка, группы. Сам транспорт разобран в статье про системы реального времени: WebSocket, проблема привязки соединения к серверу, Pub/Sub для межсерверной доставки и presence через TTL. TTL — это time to live, срок жизни ключа, по истечении которого хранилище его удаляет.

## Send Message Flow — порядок шагов критичен

```txt
User A → WebSocket → Chat Service
                          │
                          ▼
                 1. Persist в БД (source of truth)
                          │
                          ▼
                 2. ACK отправителю ("delivered to server")
                          │
                          ▼
                 3. Попытка доставки User B (если online)
                          │
                          ▼
                 4. Если offline → push-уведомление через очередь
```

Почему **persist строго до ACK**, а не наоборот? ACK — это подтверждение, которое сервер отправляет обратно отправителю. Если сначала отправить ACK, а потом упасть при записи в БД (база данных), отправитель будет думать, что сообщение доставлено, а оно потеряно навсегда.

Это прямое применение принципа "WebSocket — транспорт, БД — источник истины" из статьи про WebSocket. Любая "оптимизация", меняющая этот порядок ради latency, превращает durability в "обычно работает".

## Message Ordering — почему "просто timestamp" не работает

Наивный подход — сортировать сообщения по `created_at`. Проблема: при высокой нагрузке несколько сообщений могут получить **одинаковый timestamp**. Особенно если время хранится с точностью до миллисекунды, а БД принимает тысячи записей в секунду. Вдобавок часы на разных серверах слегка расходятся — это называют clock skew (расхождение часов).

```txt
Решение: составной упорядочивающий ключ —

  (chat_id, sequence_number) — монотонно возрастающий номер
  ВНУТРИ конкретного чата, а не глобально

  message_id = snowflake-подобный ID:
    [timestamp][server_id][sequence] — упорядочен по времени
    создания и глобально уникален без координации между серверами
```

Snowflake ID (подход Twitter и Discord) — это тот же принцип, что Ticket Server из статьи про сервис коротких ссылок. Каждый сервер генерирует ID локально, из своего диапазона или пространства имён. Блокирующего похода в центральную БД на каждое сообщение нет, а итоговые ID всё равно упорядочены по времени.

## Хранение сообщений: схема и партиционирование

```sql
messages (
  id           BIGINT PRIMARY KEY,  -- snowflake ID, сортируем по нему
  chat_id      BIGINT NOT NULL,
  sender_id    BIGINT NOT NULL,
  content      TEXT,
  created_at   TIMESTAMP,
  INDEX (chat_id, id)  -- основной паттерн чтения: "сообщения чата X, по порядку"
)
```

Главный паттерн чтения — "последние N сообщений чата X". Это почти всегда **range scan по индексу `(chat_id, id)`**. Поэтому PostgreSQL или MySQL — вполне адекватный выбор даже при больших объёмах, если данные правильно индексированы.

**Партиционирование по `chat_id`** (а не по времени) становится нужным, когда объём сообщений превышает возможности одного узла. Это прямое применение hash-based sharding из статьи про масштабирование базы данных. При shard key = `chat_id` все сообщения одного чата остаются в одном шарде. А чтение одного чата и есть основной паттерн, так что самая частая операция никогда не требует запроса по нескольким шардам.

## Групповые чаты: fan-out — главный senior-вопрос темы

Это разница между "просто доставить сообщение одному человеку" и реальной сложностью группового чата.

### Fan-out on write (push model)

```txt
User отправляет сообщение в группу из 500 человек
  → Chat Service создаёт 500 "записей о доставке"
    (или публикует в Pub/Sub-каналы всех 500 участников)
  → каждый участник получает push немедленно при подключении
```

```txt
Плюсы: чтение истории — простая выборка "мои сообщения" (если используется
       модель per-user inbox), быстрая отдача непрочитанных
Минусы: ОДНО сообщение в группе из 500 человек = 500 операций записи/публикации.
        Для очень больших групп (10 000+ участников, как публичные каналы
        Telegram) — это становится узким местом на запись.
```

### Fan-out on read (pull model)

```txt
Сообщение пишется ОДИН раз в общую таблицу группы (shared timeline)
  → каждый участник при подключении/запросе читает
    "сообщения группы X с моего last_read_id"
```

```txt
Плюсы: запись O(1) независимо от размера группы
Минусы: чтение дороже (нужно вычислять "что я ещё не видел"
        для каждого пользователя при каждом запросе)
```

**Практическое решение, которое используют крупные системы** — гибрид:

- Fan-out on write для небольших групп: большинство чатов, до сотен участников. Стоимость записи здесь приемлема.
- Fan-out on read для огромных каналов и broadcast-групп — например, Telegram-каналов с миллионами подписчиков. "Разослать всем при каждом сообщении" на таком размере немыслимо, поэтому читатели сами подтягивают новые сообщения общего канала.

Это прямая параллель с read-heavy и write-heavy из статьи про основы System Design. Маленькая группа фактически read-heavy с точки зрения каждого участника: он читает свой inbox чаще, чем пишет. Огромный broadcast-канал структурно ближе к "один пишет, миллионы читают", и там push-модель не масштабируется.

## Read Receipts и Typing Indicators — разная durability

```txt
Read Receipts (прочитано/доставлено):
  ХРАНЯТСЯ в БД — это часть истории переписки,
  пользователь ожидает, что статус "прочитано" сохранится
  между сессиями.

  message_status (message_id, user_id, status, updated_at)
  status: sent | delivered | read

Typing Indicator ("печатает..."):
  НЕ хранится в БД — это эфемерное состояние с TTL в несколько секунд.
  Передаётся как WebSocket-событие напрямую между клиентами
  (через тот же Pub/Sub-механизм, что и сообщения).
  Если событие "потеряется" — последствие нулевое
  (просто индикатор не появится/не исчезнет на секунду раньше).
```

Это иллюстрирует общий принцип: **не всё в realtime-системе требует одинаковых гарантий доставки**. Применение durability "сообщения" (persist-then-ACK-then-deliver) к typing indicator — избыточная сложность; применение "fire and forget" к самому сообщению — потеря данных.

## Offline Delivery и Push Notifications

```txt
User B offline в момент отправки сообщения
  → сообщение сохранено в БД (status: sent)
  → Chat Service публикует в Notification Queue
  → Push Worker → APNs/FCM → push-уведомление на устройство

При следующем подключении User B:
  → клиент запрашивает "сообщения чатов X, Y, Z с last_synced_id"
  → догружает пропущенное, помечает delivered/read
```

Очередь для push здесь — снова паттерн из статьи про очереди сообщений. Отправка push-уведомления может быть медленной и нестабильной, потому что идёт через внешний сервис: APNs (Apple Push Notification service) или FCM (Firebase Cloud Messaging). Этот вызов не должен блокировать основной поток сообщений.

## Финальная архитектура

```txt
Clients
  ↓ (WebSocket)
Load Balancer (L4 — отдаёт TCP-соединение как есть, поэтому upgrade доходит)
  ↓
WebSocket Gateway servers (stateless для HTTP, но держат
                            долгоживущие соединения)
  ↓                                    ↑
Chat Service ──→ PostgreSQL/MySQL    Redis Pub/Sub
  (persist,         (messages,        (межсерверная доставка,
   sequence IDs)     chat_members,     presence — см. WebSocket-тему)
                      message_status)
  ↓
Notification Queue → Push Worker → APNs/FCM
```

## Типичные ошибки на интервью

- **Не обсуждать порядок persist → ACK → deliver.** Это самый частый "детальный" вопрос вслед. Пропуск выглядит как незнание того, почему сообщения не теряются при сбоях.

- **Сортировка по `created_at` без обсуждения коллизий timestamp и clock skew** — не предлагать snowflake-ID или составной ключ `(chat_id, sequence)`.

- **Не различать fan-out on write и fan-out on read для групп.** Это центральный вопрос для "что если группа из 100 000 человек". Ответ "просто разошлём всем" не масштабируется.

- **Хранить typing indicator в БД** — или, наоборот, делать сообщения "fire and forget" как presence. И то, и другое путает требования к durability у разных типов данных.

- **Партиционировать сообщения по времени, а не по `chat_id`.** Это ломает основной паттерн чтения "история конкретного чата" и заставляет ходить в несколько шардов на самой частой операции.

- **Игнорировать межсерверную доставку** — проектировать так, будто все WebSocket-соединения живут на одном сервере, без Redis Pub/Sub или Kafka под ними.

- **Push-уведомления синхронно в основном потоке** — блокировать ответ пользователю на время вызова внешнего APNs/FCM API.
