# Очереди сообщений и событийная архитектура

## Главная идея: развязка во времени и по доступности

Без очереди синхронный вызов связывает время жизни и доступность двух сервисов:

```txt
API → Email Service (синхронный HTTP-вызов)

Если Email Service медленный → API медленный
Если Email Service упал     → API падает
  (или возвращает ошибку клиенту)
```

С очередью производитель (producer) и потребитель (consumer) развязаны:

```txt
API → Queue → Email Worker

API записал сообщение в очередь и сразу ответил
клиенту 200 OK.
Email Worker обрабатывает сообщение когда сможет —
даже если он сейчас недоступен, сообщение просто
ждёт в очереди.
```

Это даёт четыре конкретные выгоды. На интервью важно не просто их перечислить, а связать каждую с конкретной задачей:

- **Асинхронность** — клиент не ждёт результат долгой операции.
- **Буферизация** — всплеск из 10 000 запросов "размазывается" во времени для потребителя, который обрабатывает с постоянной скоростью.
- **Изоляция сбоев** — падение потребителя не приводит к падению производителя.
- **Независимое масштабирование** — можно добавить больше воркеров без изменений в API.

## Queue vs Pub/Sub vs Event Streaming — это разные модели, не синонимы

Это различие путают чаще всего, и оно принципиально влияет на архитектуру. В примерах ниже — сервисы Amazon: SQS (Simple Queue Service) и SNS (Simple Notification Service).

| | Point-to-Point Queue (SQS, RabbitMQ) | Pub/Sub (SNS, Redis Pub/Sub) | Event Streaming (Kafka, Kinesis) |
|---|---|---|---|
| Кто получает сообщение | **Один** потребитель из группы забирает и удаляет его | **Все** подписчики получают копию | Все группы потребителей читают независимо; сообщение остаётся после чтения |
| Хранение после обработки | Удаляется | Не сохраняется (если нет подписчика — потеряно) | Хранится N дней или часов (retention), можно "перечитать" |
| Порядок | Обычно не гарантирован, либо очереди first-in-first-out (FIFO) с ограничениями throughput | Не гарантирован | Гарантирован **в рамках партиции** |
| Типичный кейс | Задачи на обработку (отправить email, сгенерировать отчёт) | Уведомить несколько сервисов о событии | Event sourcing, аналитика в реальном времени, replay событий |

Senior-нюанс: "очередь" в духе SQS — это **task queue**: задача обрабатывается ровно одним воркером и исчезает. Kafka — это **журнал событий (log)**, который многие потребители читают независимо и могут перечитать с начала.

Путать их в дизайне — частая ошибка. Если несколько сервисов должны знать о "UserCreated", обычная очередь не подходит: сообщение исчезает после обработки одним потребителем. Нужен Pub/Sub или журнал событий.

## Fan-Out: одно событие → много подписчиков

Одно событие может накормить сразу почтовый сервис, аналитику и CRM (customer relationship management — систему работы с клиентами):

```txt
User Service
   │ публикует "UserCreated"
   ▼
 Event Bus / Topic
   ├──→ Email Service     (отправить welcome email)
   ├──→ Analytics Service (записать в аналитику)
   └──→ CRM Service        (создать карточку клиента)
```

Ключевое архитектурное преимущество: **User Service не знает**, сколько у "UserCreated" подписчиков и зачем они им нужны. Добавление нового подписчика — например, Fraud Detection Service — не требует изменений в User Service. Это снижает связанность между командами и сервисами кратно сильнее, чем прямые HTTP-вызовы "на всякий случай".

## Delivery Guarantees — at-most-once, at-least-once, exactly-once

| Гарантия | Что означает | Типичный пример |
|---|---|---|
| **At-most-once** | Доставка 0 или 1 раз: может быть потеряно, но никогда не дублируется | "Fire and forget", как в UDP (user datagram protocol) |
| **At-least-once** | Доставка 1 или более раз: никогда не теряется, но может дублироваться | Стандарт для большинства очередей — SQS и Kafka по умолчанию |
| **Exactly-once** | Доставка ровно 1 раз | На практике недостижимо — см. ниже |

Senior-нюанс про exactly-once: в распределённых системах **истинный exactly-once на уровне сети практически недостижим**. То, что маркетируется как "exactly-once" — например, Kafka transactions — на практике реализуется как **at-least-once доставка плюс идемпотентная обработка на стороне потребителя**. Эта комбинация даёт *эффект* exactly-once.

Поэтому хороший ответ на "как обеспечить exactly-once" — не "включить флаг exactly-once". Это "спроектировать потребителя идемпотентным, потому что доставка с повторами неизбежна".

### Идемпотентность — практическая реализация

```ts
import { db } from './db'; // уже созданный PrismaClient

interface PaymentMessage { id: string; userId: string; amount: number }

declare function chargeCard(userId: string, amount: number): Promise<void>;

// ❌ Не идемпотентно: повторная обработка того же сообщения
// списывает деньги дважды
async function processPayment(message: PaymentMessage): Promise<void> {
  await chargeCard(message.userId, message.amount);
}

// ✅ Идемпотентно: idempotency key проверяется перед побочным эффектом
async function processPaymentIdempotent(message: PaymentMessage): Promise<void> {
  const alreadyProcessed = await db.processedMessages.findUnique({
    where: { messageId: message.id },
  });
  if (alreadyProcessed) {
    return; // уже обработано — безопасный no-op
  }

  await db.$transaction(async (tx) => {
    await chargeCard(message.userId, message.amount);
    await tx.processedMessages.create({ data: { messageId: message.id } });
  });
}
```

Ключевая деталь: запись в `processedMessages` и побочный эффект (`chargeCard`) должны быть атомарны — в одной транзакции или с компенсирующей логикой. Иначе появляется новое окно для дублирования между "выполнили операцию" и "записали, что выполнили".

## Ordering — гарантия, за которую вы платите

По умолчанию большинство очередей **не гарантируют порядок** при параллельной обработке несколькими потребителями. Два сообщения об одном пользователе могут быть обработаны не в том порядке, если их забрали разные воркеры.

```txt
Kafka гарантирует порядок только внутри одной партиции.

  Partition key = user_id
  → все события для user_id=42 всегда попадают
    в одну партицию
  → обрабатываются одним потребителем строго по порядку

  Но: события для разных user_id могут обрабатываться
  параллельно в разных партициях — порядок между ними
  не гарантирован (и обычно не нужен)
```

Практический вывод: иногда порядок важен. Например, "UserUpdated" должно быть обработано после "UserCreated" для того же пользователя. Тогда выбирайте partition key так, чтобы связанные события **всегда** попадали в одну партицию — обычно это id сущности.

## Dead Letter Queue и retry с backoff

Dead letter queue (DLQ) — это место, куда сообщение попадает после неудачных повторов:

```txt
Message → Worker → ошибка обработки
                       ↓
                  Retry с экспоненциальным backoff
                  (1s, 2s, 4s, 8s, ...)
                       ↓
              После N неудачных попыток
                       ↓
                 Dead Letter Queue (DLQ)
```

DLQ решает конкретную проблему: "ядовитое сообщение" (poison message), которое **не может** быть обработано из-за бага в данных — например, невалидный JSON. Без DLQ такое сообщение повторялось бы бесконечно, занимая ресурсы потребителя и блокируя остальные сообщения, если очередь FIFO.

Senior-нюанс: DLQ — это не "конец истории". Это сигнал для **человека или алертинга**. Сообщения в DLQ нужно мониторить. Рост DLQ часто означает баг в коде потребителя или несовместимое изменение схемы события со стороны производителя.

## Backpressure — что происходит, когда производитель быстрее потребителя

```txt
Producer публикует 10 000 msg/sec
Consumer обрабатывает 1 000 msg/sec

→ очередь растёт без ограничений
→ растёт latency обработки (сообщение из конца
  очереди ждёт всё дольше)
→ в крайнем случае очередь исчерпывает
  память или диск брокера
```

Есть три решения:

- добавить потребителей — то самое горизонтальное масштабирование воркеров, о котором говорилось в начале;
- ограничить размер очереди с явным отбрасыванием или возвратом ошибки производителю (back-pressure "наружу");
- применить rate limiting на стороне производителя.

## Когда очередь — не то решение

```txt
✅ Подходит:
  - отправка email и push-уведомлений
  - генерация отчётов, обработка видео
    (долгие операции)
  - синхронизация данных между сервисами (event-driven)
  - сглаживание всплесков нагрузки
    (пакетная обработка заказов)

❌ Не подходит:
  - запросы, требующие немедленного ответа в том же
    HTTP-цикле (например, "проверить наличие товара
    перед показом цены")
  - real-time чат и игры — там нужен WebSocket или прямое
    соединение, очередь добавляет latency, неприемлемую
    для интерактивности
  - операции, где порядок и атомарность критичны
    "из коробки" — проще сделать синхронной транзакцией
    в одной базе данных, чем городить распределённую
    логику вокруг очереди
```

Главный признак "не используй очередь здесь" — если ответ пользователю **зависит** от результата операции в реальном времени. Очередь подходит, когда можно сказать "приняли, обработаем" (202 Accepted). Она не подходит, когда нужно "вот результат прямо сейчас" (200 OK с данными).

## Типичные ошибки на интервью

- **Путать queue и pub/sub.** Point-to-point очередь доставляет сообщение только одному потребителю. Поэтому предлагать SQS-подобную очередь для сценария "несколько сервисов должны узнать о событии" — ошибка.

- **Говорить "exactly-once delivery" как о решённой проблеме**, не упоминая, что на практике это всегда at-least-once плюс идемпотентность.

- **Не упоминать идемпотентность потребителя вообще.** Если очередь обсуждается, идемпотентность — обязательная часть ответа, а не опция.

- **Считать, что Kafka гарантирует глобальный порядок.** Порядок гарантирован только внутри партиции, и выбор partition key напрямую на него влияет.

- **DLQ как "мусорка, и забыли".** Без мониторинга DLQ означает, что часть сообщений теряется незаметно для команды.

- **Предлагать очередь для синхронных операций** — "проверить остаток товара перед оплатой через очередь" добавляет latency и сложность там, где нужен прямой синхронный запрос.

- **Не обсуждать backpressure** — что происходит, если производитель стабильно быстрее потребителя, и как система деградирует (рост latency, переполнение очереди).
