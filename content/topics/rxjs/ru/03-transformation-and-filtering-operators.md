# Операторы трансформации и фильтрации

## Оператор — чистая функция над потоком

Оператор в RxJS — это функция, принимающая Observable и возвращающая **новый** Observable. Исходный поток при этом не меняется:

```ts
import { map, Observable, OperatorFunction } from 'rxjs';

// именно так выглядит любой оператор изнутри
type Op = <T, R>(project: (value: T) => R) => OperatorFunction<T, R>;

const source$ = of(1, 2, 3);
const doubled$ = source$.pipe(map((x) => x * 2));

// source$ не изменился: он по-прежнему отдаёт 1, 2, 3
source$.subscribe(console.log);   // 1 2 3
doubled$.subscribe(console.log);  // 2 4 6
```

`pipe()` — это композиция функций, а не «применение методов по очереди»: каждый оператор оборачивает предыдущий поток. Отсюда два практических следствия.

Первое: **порядок операторов меняет результат**, потому что каждый следующий работает с выходом предыдущего:

```ts
// Сначала фильтруем 100 значений, потом дорого преобразуем 3
source$.pipe(filter(isRelevant), map(expensiveTransform));

// Сначала дорого преобразуем 100 значений, потом выбрасываем 97
source$.pipe(map(expensiveTransform), filter(isRelevant));
```

Второе: **свой оператор — это просто функция**, возвращающая композицию существующих. Ничего писать «с нуля» не нужно:

```ts
import { pipe, filter, map, distinctUntilChanged } from 'rxjs';

// оператор = pipe() без источника
export function searchQuery(minLength = 2) {
  return pipe(
    map((value: string) => value.trim()),
    filter((value) => value.length >= minLength),
    distinctUntilChanged(),
  );
}

// использование ничем не отличается от встроенных
input$.pipe(searchQuery(3)).subscribe(load);
```

> **Legacy.** До RxJS 5.5 операторы были **методами прототипа**: `source.map(fn).filter(pred)`. Такой «patch-оператор» синтаксис требовал импортов вида `import 'rxjs/add/operator/map'`, ломал tree-shaking (в бандл попадал весь RxJS) и приводил к конфликтам при разных версиях библиотеки в одном проекте. Сегодня это удалено; `.pipe()` с отдельными импортами — единственная норма, а не «новый стиль».

## Как читать marble-диаграммы

Marble-нотация — язык, на котором написана документация RxJS и все объяснения таймингов. Пять минут на её чтение экономят часы:

```
                       Как читать marble-диаграмму
источник   --a---b-----c--|
             ^ значение a пришло рано
                 ^ значение b — позже
                       ^ значение c — ещё позже
                          ^ complete: поток завершён

           дефис = течение времени (условная единица, не миллисекунды)

источник   --a---b-----c--|
           map(x => x.toUpperCase())
результат  --A---B-----C--|
           map не меняет тайминги: одно значение на входе — одно на выходе

источник   --a---b-----c--|
           filter(x => x !== "b")
результат  --a---------c--|
           filter не сдвигает значения во времени, а только выбрасывает их
```

Читать нужно так: горизонтальная ось — время слева направо, символы — значения, `|` — `complete`, `X` — `error`. Дефисы не означают конкретное число миллисекунд: они показывают *относительные* интервалы. Главный вопрос, который вы задаёте диаграмме: **сдвинулись ли значения по времени и изменилось ли их количество**. По этим двум признакам операторы делятся на группы: `map` не меняет ни того, ни другого; `filter` меняет количество; `debounceTime` меняет и количество, и тайминги.

## Трансформация

### map: один к одному

```ts
import { map } from 'rxjs';

users$.pipe(map((user) => user.name));            // User → string
responses$.pipe(map((r) => r.data.items ?? []));  // безопасное извлечение
```

> **Legacy.** Для «достать поле» существовал `pluck('data', 'items')`. В RxJS 7 он помечен deprecated с прямой заменой в описании: `map(x => x?.data?.items)`. Причина — optional chaining решает задачу лучше и типизируется точнее, чем строковые ключи.

### scan: аккумулятор для бесконечного потока

`scan` — это `reduce`, который отдаёт промежуточный результат на каждом шаге:

```ts
import { scan, reduce } from 'rxjs';

// scan: значение после КАЖДОГО шага
of(1, 2, 3).pipe(scan((acc, x) => acc + x, 0)).subscribe(console.log);
// 1, 3, 6

// reduce: только итог, и только при complete
of(1, 2, 3).pipe(reduce((acc, x) => acc + x, 0)).subscribe(console.log);
// 6
```

Отсюда правило: для бесконечных потоков `reduce` бесполезен (он ждёт `complete`, которого не будет), а `scan` — основной инструмент накопления состояния:

```ts
// счётчик кликов
clicks$.pipe(scan((count) => count + 1, 0));

// накопление списка сообщений
messages$.pipe(scan((all, message) => [...all, message], [] as Message[]));

// редьюсер состояния поверх потока действий
actions$.pipe(scan(reducer, initialState));
```

Последний пример — то, на чём построены Redux-подобные сторы: поток действий плюс `scan` с редьюсером даёт поток состояний.

## Фильтрация и ограничение

```
                                     Фильтрация и ограничение потока
┌────────────────────────┬───────────────────────────────────┬───────────────────────────────────────────┐
│ оператор               │ что делает                        │ нюанс, который спрашивают                 │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ filter(pred)           │ пропускает подходящие значения    │ поток продолжается, complete не наступает │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ take(n)                │ первые n значений, затем complete │ сам завершает поток и снимает подписку    │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ takeWhile(pred)        │ пока условие истинно              │ inclusive: true отдаёт и значение-стоп    │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ takeUntil(notifier$)   │ пока notifier$ не эмитнет         │ основной приём отписки                    │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ first(pred?)           │ первое подходящее и complete      │ бросает EmptyError, если ничего не было   │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ last(pred?)            │ последнее подходящее при complete │ ждёт complete — не для бесконечных        │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ skip(n) / skipWhile    │ пропускает начало потока          │ значения теряются, не буферизуются        │
├────────────────────────┼───────────────────────────────────┼───────────────────────────────────────────┤
│ distinctUntilChanged() │ отбрасывает повтор подряд         │ сравнение по ссылке, нужен компаратор     │
└────────────────────────┴───────────────────────────────────┴───────────────────────────────────────────┘
                take(1) и first() отличаются на пустом потоке: take(1) просто завершится,
                      first() выбросит EmptyError — иногда это именно то, что нужно
```

Два места, где ошибаются регулярно.

**`take(n)` завершает поток.** Это не «пропустить n значений», а «взять n и закрыть подписку». Свойство используют осознанно: `take(1)` — стандартный способ получить одно значение и не думать об отписке.

**`distinctUntilChanged` сравнивает по ссылке.** Для объектов это означает, что два одинаковых по содержанию объекта считаются разными:

```ts
import { distinctUntilChanged, distinctUntilKeyChanged } from 'rxjs';

// НЕ работает для объектов: каждый ответ API — новый объект
state$.pipe(distinctUntilChanged());

// Вариант 1: компаратор
state$.pipe(distinctUntilChanged((a, b) => a.status === b.status && a.query === b.query));

// Вариант 2: сравнение по конкретному полю
state$.pipe(distinctUntilKeyChanged('status'));

// Вариант 3: сначала сузить до примитива
state$.pipe(map((s) => s.status), distinctUntilChanged());
```

Третий вариант обычно предпочтительнее: сравнение примитивов дёшево и не требует поддерживать компаратор при изменении модели.

## Операторы времени: debounce, throttle, audit

```
         debounceTime, throttleTime, auditTime на одном всплеске
источник         -a-b-c---------d-e-------|

debounceTime(4)  ---------c---------e-----|
                          ^ ждёт ПАУЗУ, отдаёт последнее значение всплеска

throttleTime(4)  -a-------------d---------|
                  ^ отдаёт ПЕРВОЕ, затем молчит окно

auditTime(4)     -----c-------------e-----|
                      ^ ждёт окно после первого, отдаёт ПОСЛЕДНЕЕ за окно
      поиск по вводу — debounceTime; кнопка и скролл — throttleTime;
              "не чаще, но всегда самое свежее" — auditTime
```

Три оператора решают одну задачу — «уменьшить частоту» — но с разной семантикой, и выбор определяется вопросом «какое значение из всплеска мне нужно».

**`debounceTime(ms)`** ждёт паузу указанной длины и отдаёт последнее значение. Идеален для ввода: пока пользователь печатает, запросов нет; как только он остановился — уходит один запрос с финальным текстом.

```ts
searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),           // не искать то же самое повторно
  switchMap((q) => api.search(q)),  // отменить предыдущий запрос
);
```

Обратная сторона: при непрерывном вводе значение может не появиться вообще. Для «жать не чаще раза в секунду, но реагировать сразу» `debounceTime` не подходит.

**`throttleTime(ms)`** отдаёт первое значение немедленно и затем игнорирует всё в течение окна. Это про мгновенную реакцию с ограничением частоты: обработка скролла, защита кнопки от серии кликов, отправка аналитики.

```ts
scroll$.pipe(throttleTime(100), map(getScrollPosition));
saveClicks$.pipe(throttleTime(1000)); // первый клик сработал, повторные в секунду — нет
```

По умолчанию у `throttleTime` `leading: true, trailing: false` — то есть «первое да, последнее нет». Конфигурацией это меняется: `throttleTime(1000, undefined, { leading: false, trailing: true })` превращает его в поведение, близкое к `auditTime`.

**`auditTime(ms)`** — обратная сторона throttle: при получении значения он ждёт окно и отдаёт **последнее** значение, пришедшее за это время. Применение: «обновлять индикатор не чаще раза в 100 мс, но всегда показывать актуальное состояние».

Рядом стоит **`sampleTime(ms)`** — «отдавай последнее значение каждые ms по таймеру», то есть частота фиксирована и не зависит от активности источника. Пригодится для метрик и графиков в реальном времени.

Практический критерий выбора: нужно **последнее** значение после затишья — `debounceTime`; нужна **немедленная** реакция с ограничением — `throttleTime`; нужно **самое свежее** значение с фиксированным ритмом — `auditTime` или `sampleTime`.

## tap: побочные эффекты и злоупотребление

`tap` не меняет поток — он позволяет «подсмотреть» проходящие значения. Законных применений три: логирование, отладка и побочные эффекты, не связанные с данными (аналитика, синхронизация с внешним хранилищем).

```ts
import { tap } from 'rxjs';

// Отладка: увидеть, что реально проходит через конкретный участок цепочки
source$.pipe(
  tap((value) => console.debug('до фильтра', value)),
  filter(isRelevant),
  tap((value) => console.debug('после фильтра', value)),
);

// Наблюдение за жизненным циклом: объект вместо позиционных колбэков
request$.pipe(
  tap({
    subscribe: () => metrics.start('load-tickets'),
    next: (response) => metrics.mark('first-byte', response.length),
    error: (err) => logger.error('load failed', err),
    complete: () => metrics.end('load-tickets'),
    finalize: () => spinner.hide(),        // и при complete, и при error, и при отписке
  }),
);
```

> **Legacy.** Форма `tap(nextFn, errorFn, completeFn)` с раздельными колбэками помечена deprecated в RxJS 7 — ожидается объект-наблюдатель. Плюс к единообразию с `subscribe({...})` объект даёт доступ к `subscribe`, `unsubscribe` и `finalize`, которых у позиционной формы нет.

Злоупотребление выглядит так:

```ts
// ПЛОХО: tap меняет состояние — поток перестаёт быть описанием данных
tickets$.pipe(
  tap((tickets) => (this.tickets = tickets)),          // запись в поле
  tap((tickets) => (this.count = tickets.length)),     // производное значение
  tap(() => this.loading = false),                     // управление UI
).subscribe();
```

Чем это плохо конкретно: результат работы цепочки оказывается не в её значении, а в побочных эффектах — такую цепочку нельзя переиспользовать и трудно тестировать; порядок эффектов зависит от порядка операторов; при повторной подписке эффекты выполнятся дважды; а `subscribe()` без аргументов сигнализирует, что настоящий результат «спрятан» в `tap`.

Правильная форма — вернуть данные из потока и обработать их в одном месте:

```ts
// Производные значения — операторами, а не эффектами
readonly tickets$ = source$;
readonly count$ = source$.pipe(map((tickets) => tickets.length));

// Единственный побочный эффект — там, где поток потребляется
tickets$.subscribe((tickets) => this.render(tickets));
```

Правило-ориентир: если убрать все `tap` из цепочки и она перестанет работать — значит `tap` использован не по назначению.

## Типичные ошибки на интервью

- **«Операторы изменяют поток»** — нет: каждый оператор возвращает новый Observable, исходный остаётся неизменным. Отсюда следует, что `source$.pipe(map(...))` без присваивания результата не делает ничего, а один и тот же `source$` можно использовать в нескольких цепочках независимо.

- **Не различать `scan` и `reduce`** — `scan` отдаёт промежуточный результат на каждом значении, `reduce` — только итог при `complete`. Проверочный вопрос: «что вернёт `reduce` на `interval(1000)`?» Правильный ответ: ничего, поток никогда не завершится, и подписчик не получит ни одного значения.

- **Путать `debounceTime` и `throttleTime`** — самая частая пара на интервью. Ожидается не определение, а критерий: нужно последнее значение после затишья (поиск) — `debounce`; нужна немедленная реакция с ограничением частоты (скролл, клики) — `throttle`. Follow-up: «а если пользователь печатает без остановки минуту?» — с `debounceTime` запрос не уйдёт вообще.

- **`distinctUntilChanged()` на объектах** — сравнение по ссылке, поэтому для ответов API оператор бесполезен: каждый объект новый. Ожидаемый ответ — компаратор, `distinctUntilKeyChanged` или предварительный `map` до примитива.

- **Не знать, что `take(n)` завершает поток** — это не «взять и продолжить»: после n-го значения приходит `complete`, подписка снимается, teardown выполняется. Именно поэтому `take(1)` — законный способ обойтись без ручной отписки.

- **`first()` вместо `take(1)` без понимания разницы** — на пустом потоке `first()` бросает `EmptyError`, `take(1)` тихо завершается. Выбор зависит от того, является ли отсутствие значения ошибкой в вашем сценарии.

- **`tap`, в котором живёт логика** — маркер того, что кандидат использует поток как «цикл с колбэками». Хороший ответ называет конкретные последствия: цепочку нельзя переиспользовать, эффекты дублируются при второй подписке, тестировать приходится через шпионы вместо проверки значений.

- **`pluck('a', 'b')` в ответе** — deprecated в RxJS 7, замена `map(x => x?.a?.b)` указана прямо в сообщении об устаревании. Аналогично `tap(next, error, complete)` с позиционными аргументами — ожидается объект-наблюдатель.
