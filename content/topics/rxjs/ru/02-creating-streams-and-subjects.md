# Создание потоков и Subjects

## Откуда берутся потоки

```
                                                  Чем создать поток
┌─────────────────────────┬────────────────────────────────────────────────┬─────────────────────────────────────────┐
│ функция                 │ что отдаёт                                     │ когда брать                             │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ of(a, b, c)             │ значения как есть, синхронно, затем complete   │ константы, тесты, значение по умолчанию │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ from(источник)          │ массив, промис, итератор, async-итератор       │ мост из существующих структур           │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ fromEvent(target, name) │ значения на каждое событие, без complete       │ DOM-события, EventEmitter               │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ timer(delay, period?)   │ одно значение через delay или дальше по period │ отложенный старт, поллинг               │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ interval(period)        │ счётчик каждые period, без complete            │ таймеры, тики                           │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ defer(() => поток)      │ создаёт источник заново на каждую подписку     │ ленивость поверх eager-кода             │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ EMPTY / NEVER           │ сразу complete / никогда ничего                │ нейтральный элемент, заглушка           │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ throwError(() => err)   │ сразу error                                    │ ветка ошибки в catchError/switchMap     │
├─────────────────────────┼────────────────────────────────────────────────┼─────────────────────────────────────────┤
│ new Observable(fn)      │ что угодно + teardown                          │ обёртка над чужим API                   │
└─────────────────────────┴────────────────────────────────────────────────┴─────────────────────────────────────────┘
                           throwError принимает ФАБРИКУ: throwError(() => new Error(...)) —
                               передача готового значения помечена deprecated в RxJS 7
```

### of и from: разные вещи с похожим видом

```ts
import { of, from } from 'rxjs';

of([1, 2, 3]).subscribe(console.log);    // [1, 2, 3] — ОДНО значение-массив
from([1, 2, 3]).subscribe(console.log);  // 1, затем 2, затем 3 — три значения
```

`of` отдаёт аргументы как есть, `from` разворачивает итерируемое. Это первая ловушка новичка: `of(array)` там, где нужен поток элементов.

`from` работает с промисами, итераторами и async-итераторами, поэтому служит универсальным мостом:

```ts
from(fetch('/api/users'));          // Promise → Observable (одно значение + complete)
from(new Set([1, 2, 3]));           // любой Iterable
from(asyncGenerator());             // AsyncIterable — значения по мере готовности
```

### defer: ленивость поверх eager-кода

Проблема `from(promise)` в том, что промис уже начал работу (см. [Reactive Model and Observables]): такой поток не ленив и при повторной подписке отдаст тот же результат, а не сделает новый запрос. `defer` исправляет это, откладывая создание источника до момента подписки:

```ts
import { defer, from } from 'rxjs';

// НЕ ленивый: fetch выполнится один раз, при создании
const eager$ = from(fetch('/api/time'));

// Ленивый: fetch выполняется на КАЖДУЮ подписку
const lazy$ = defer(() => from(fetch('/api/time')));

lazy$.subscribe(console.log);  // запрос №1
lazy$.subscribe(console.log);  // запрос №2, свежее значение
```

Второе применение `defer` — когда значение зависит от состояния на момент подписки:

```ts
// Вычислит Date.now() один раз, при создании потока
const wrong$ = of(Date.now());

// Вычислит Date.now() при каждой подписке
const right$ = defer(() => of(Date.now()));
```

### timer и interval

```ts
import { timer, interval } from 'rxjs';

timer(1000);              // одно значение (0) через секунду, затем complete
timer(1000, 5000);        // первое через секунду, дальше каждые 5 секунд
interval(5000);           // первое через 5 секунд (сразу ничего не даёт!), затем каждые 5
```

Практическая разница: `interval(5000)` заставляет ждать первый интервал, поэтому для поллинга обычно берут `timer(0, 5000)` — «сразу и затем каждые 5 секунд». Ни один из них не завершается сам: остановка — через `take`, `takeUntil` или отписку (см. [Transformation and Filtering Operators]).

### EMPTY, NEVER, throwError

Три «вырожденных» потока, которые постоянно нужны в ветвлениях:

```ts
import { EMPTY, NEVER, throwError, of } from 'rxjs';

EMPTY;                                  // ничего не эмитит, сразу complete
NEVER;                                  // не эмитит и не завершается никогда
throwError(() => new Error('boom'));    // сразу error

// типичное применение: ветка «нечего загружать»
const users$ = query.length < 2 ? EMPTY : api.search(query);
```

Обратите внимание на форму `throwError`: в RxJS 7 он принимает **фабрику**, а передача готового значения помечена deprecated. Смысл не в косметике: фабрика создаёт ошибку в момент, когда та должна возникнуть, и стек-трейс получается осмысленным.

`EMPTY` против `of()`: оба завершаются без значений, но `EMPTY` — это готовая константа, а `of()` создаёт новый поток. `NEVER` в продакшен-коде встречается редко — в основном в тестах и как «заглушка, которая ничего не делает».

### Свой Observable

Когда нужно обернуть API, для которого нет готовой фабрики, пишут конструктор напрямую. Главное здесь — вернуть teardown:

```ts
import { Observable } from 'rxjs';

function fromWebSocket<T>(url: string): Observable<T> {
  return new Observable<T>((subscriber) => {
    const socket = new WebSocket(url);

    socket.onmessage = (event) => subscriber.next(JSON.parse(event.data) as T);
    socket.onerror = () => subscriber.error(new Error(`WebSocket failed: ${url}`));
    socket.onclose = (event) => {
      // нормальное закрытие — complete, аварийное — error
      if (event.wasClean) subscriber.complete();
      else subscriber.error(new Error(`WebSocket closed: ${event.code}`));
    };

    // teardown: вызывается при unsubscribe, complete и error
    return () => {
      if (socket.readyState === WebSocket.OPEN) socket.close();
    };
  });
}
```

Три правила для собственных Observable: соблюдать контракт (`next` много раз, затем один `error` или `complete`), всегда возвращать teardown, и не забывать, что функция-подписчик выполняется заново на каждую подписку — то есть каждый подписчик получит **свой** WebSocket. Если это не то, что нужно, поток надо разделить между подписчиками — см. [Multicasting and Subscription Management].

## Subject: мост из императивного кода

`Subject` — это одновременно **Observable и Observer**: у него есть и `subscribe`, и `next`/`error`/`complete`. Отсюда его роль: точка, куда императивный код «толкает» значения, а реактивный код их читает.

```ts
import { Subject } from 'rxjs';

const notifications$ = new Subject<string>();

// императивная сторона: любой код может вызвать next
notifications$.next('Ticket saved');

// реактивная сторона: подписчики получают значения
notifications$.subscribe((message) => showToast(message));
```

Ключевое отличие от обычного Observable: Subject **горячий** и мультикастовый. Он не создаёт работу на каждую подписку, а раздаёт одни и те же значения всем подписчикам — как `EventEmitter`, но с операторами и контрактом завершения.

### Четыре вида и что видит поздний подписчик

```
                      Что увидит подписчик, пришедший поздно
                    источник эмитит 1, 2, 3; подписчик B приходит между 2 и 3

Subject             --1--2--3--
  A с начала        --1--2--3--
  B поздно          -------3--
                           ^ значения 1 и 2 потеряны навсегда

BehaviorSubject(0)  0-1--2--3--
  A с начала        0-1--2--3--
  B поздно          ------2-3--
                          ^ сразу получил ТЕКУЩЕЕ значение (2), затем поток

ReplaySubject(2)    --1--2--3--
  B поздно          ------12-3--
                          ^ догнал буфер из двух последних значений

AsyncSubject        --1--2--3--|
  любой подписчик   -----------3|
                               ^ только последнее значение, и только при complete
```

- **`Subject`** — без памяти. Подписался позже — предыдущие значения потеряны. Годится для событий («пользователь нажал сохранить»), где история не нужна.
- **`BehaviorSubject(initial)`** — хранит текущее значение и отдаёт его новому подписчику немедленно. Требует начального значения. Это рабочая лошадка для **состояния**: у состояния всегда есть значение «сейчас», и любой новый читатель должен его получить.
- **`ReplaySubject(bufferSize?, windowTime?)`** — буфер последних N значений (или всех за последние `windowTime` мс). Полезен для «истории последних событий»; опасен при большом буфере — он удерживает значения в памяти.
- **`AsyncSubject`** — отдаёт только последнее значение и только при `complete`. Встречается редко, ближе всего по смыслу к промису.

### BehaviorSubject как состояние: рабочий паттерн

```ts
import { BehaviorSubject, Observable } from 'rxjs';

interface Filters {
  readonly status: string | null;
  readonly query: string;
}

export class TicketFiltersStore {
  // приватная запись: наружу Subject не отдаём
  private readonly state = new BehaviorSubject<Filters>({ status: null, query: '' });

  // публичное чтение: тип Observable, а не Subject — снаружи next() не вызвать
  readonly filters$: Observable<Filters> = this.state.asObservable();

  // текущее значение доступно синхронно — этого нет у обычного Subject
  get snapshot(): Filters {
    return this.state.getValue();
  }

  setStatus(status: string | null): void {
    this.state.next({ ...this.snapshot, status });
  }

  reset(): void {
    this.state.next({ status: null, query: '' });
  }
}
```

Три детали, которые делают этот паттерн правильным:

1. **`asObservable()`** сужает тип: потребитель видит `Observable<Filters>` и физически не может вызвать `next`. Без этого любой компонент может писать в состояние, минуя методы стора.
2. **`getValue()`** даёт синхронный доступ к текущему значению — именно то, чего не хватает у `Subject` и что делает `BehaviorSubject` пригодным для состояния.
3. **Иммутабельное обновление** (`{ ...this.snapshot, status }`): подписчики сравнивают ссылки, а мутация объекта на месте не будет замечена операторами вроде `distinctUntilChanged`.

> **Angular-контекст.** Именно этот паттерн — «приватный `BehaviorSubject` + публичный `Observable`» — был стандартным способом держать состояние в сервисах до появления сигналов. Сегодня в Angular ту же роль играет `signal` с `asReadonly()`, а взаимные переходы делаются через `toSignal`/`toObservable`. Подробно — в курсе Angular, главы про сигналы, состояние в сервисах и RxJS в Angular.

## Когда Subject не нужен

Самый частый анти-паттерн: Subject там, где достаточно обычного Observable.

```ts
// ПЛОХО: Subject как переупаковка готового потока
export class UserService {
  private readonly users = new Subject<User[]>();
  readonly users$ = this.users.asObservable();

  loadUsers(): void {
    this.http.get<User[]>('/api/users').subscribe((users) => this.users.next(users));
  }
}
```

Что здесь не так: появилась подписка, которую никто не закрывает; ошибка HTTP-запроса терминирует `users` навсегда (см. [Error Handling and Retries]); поздний подписчик не получит уже загруженные данные; а главное — поток «превращён» в императивный код без всякой выгоды.

```ts
// ХОРОШО: поток остаётся потоком
export class UserService {
  readonly users$ = this.http.get<User[]>('/api/users');
  // подписка произойдёт там, где данные нужны;
  // многократные подписки решаются через share (см. Multicasting)
}
```

Признаки, что Subject **действительно** нужен:

- источник значений — императивный код, которым вы не управляете (обработчик, колбэк библиотеки, метод компонента);
- нужен мультикаст: одно значение — много независимых подписчиков;
- нужно хранить текущее состояние и отдавать его новым читателям (`BehaviorSubject`);
- нужен «ручной» триггер: `refresh$ = new Subject<void>()` и `refresh$.pipe(switchMap(() => load()))`.

И правило, которое стоит запомнить: **Subject не отдают наружу**. Публичный тип — всегда `Observable` через `asObservable()`. Иначе инкапсуляция теряется, а отладка «кто именно позвал next» превращается в поиск по всему проекту.

## Типичные ошибки на интервью

- **Путать `of(array)` и `from(array)`** — `of([1,2,3])` отдаёт один элемент (сам массив), `from([1,2,3])` — три значения. Простая проверка знаний, но она же вскрывает непонимание того, что поток может содержать значение любого типа, включая массив.

- **«`from(promise)` делает поток ленивым»** — нет: промис уже начал работу при создании. Ленивость возвращает `defer(() => from(fetch(...)))`. Follow-up, на котором обычно спотыкаются: «а если подписаться дважды на `from(promise)`?» — оба подписчика получат один и тот же результат, второго запроса не будет.

- **`interval(5000)` для поллинга «каждые 5 секунд начиная сразу»** — `interval` молчит первый интервал. Нужен `timer(0, 5000)`. Мелочь, которая на практике превращается в «данные появляются с задержкой при открытии экрана».

- **Отдавать `Subject` из публичного API** — тогда любой потребитель может вызвать `next()` или `complete()` на вашем состоянии. Ожидаемый ответ: приватный Subject + публичный `asObservable()`; в Angular-контексте — приватный `signal` + публичный `asReadonly()`.

- **Не знать, зачем `BehaviorSubject` вместо `Subject` для состояния** — ключ в том, что у состояния всегда есть значение «сейчас»: новый подписчик обязан его получить, а код — иметь синхронный доступ через `getValue()`. С обычным `Subject` компонент, подписавшийся после последнего `next`, увидит пустой экран до следующего обновления.

- **`ReplaySubject` без ограничения буфера** — `new ReplaySubject()` хранит **все** значения навсегда. На потоке событий это утечка памяти, растущая линейно со временем работы приложения. Правильный ответ упоминает `bufferSize` и `windowTime`.

- **`throwError(new Error(...))` вместо фабрики** — форма из RxJS 6. В седьмой версии передача значения помечена deprecated: ожидается `throwError(() => new Error(...))`, и объяснение «ошибка создаётся в момент возникновения, поэтому стек-трейс осмысленный».

- **Subject как «переупаковка» HTTP-запроса** — самый частый архитектурный анти-паттерн: `subscribe` внутри сервиса + `next` в Subject. Хороший ответ показывает три конкретных последствия: незакрытая подписка, терминирование Subject при ошибке запроса и потеря данных для позднего подписчика.
