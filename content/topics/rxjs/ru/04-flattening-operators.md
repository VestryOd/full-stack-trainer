# Операторы выпрямления потоков

## Higher-order Observable: поток потоков

`map` из статьи [Операторы трансформации и фильтрации](./03-transformation-and-filtering-operators.md) превращает значение в значение. Но чаще всего в ответ на значение нужно **начать новую асинхронную работу**: пользователь ввёл текст — надо сделать запрос. И тогда `map` возвращает не данные, а ещё один Observable:

```
                  Откуда берётся поток потоков
ввод       --a-------b-------|
           map(q => api.search(q))  ← Observable, а не значение
результат  --O-------O-------|
             ^ O — это объект Observable, ещё не подписанный

           подписчик получит два Observable вместо данных:
           Observable { … }  Observable { … }

           switchMap(q => api.search(q))  ← подписывается сам
результат  ------A-------B---|
                 ^ A — уже результат запроса,
                   задержка = время ответа
```

Такой поток называют **higher-order Observable** — поток, значениями которого являются другие потоки. Работать с ним напрямую бессмысленно: подписчик получит объекты `Observable`, а не данные.

```ts
import { map, switchMap } from 'rxjs';

// Проблема: в next приходит Observable
input$.pipe(map((q) => api.search(q))).subscribe((value) => {
  console.log(value); // Observable { ... } — не результат поиска
});

// Решение: оператор выпрямления подписывается на внутренний поток сам
// (в этом и смысл «выпрямления»: поток потоков становится одним потоком)
input$.pipe(switchMap((q) => api.search(q))).subscribe((results) => {
  console.log(results); // Ticket[] — то, что нужно
});
```

Выпрямление (flattening) — это ответ на вопрос: **что делать с предыдущей внутренней работой, когда пришло новое значение?** Возможных ответов ровно четыре, и каждый из них — отдельный оператор.

## Четыре стратегии на одном примере

Возьмём сквозной сценарий: пользователь вводит текст в поиск, каждое значение запускает HTTP-запрос, запрос отвечает не мгновенно.

```
             Четыре стратегии на одном источнике
            запрос по каждому значению отвечает через 4 такта:
            a→A, b→B, c→C

источник    --a--b--------c-----|

switchMap   ---------B--------C-|
                     ^ запрос по a отменён приходом b:
                       A не пришёл никогда

mergeMap    ------A--B--------C-|
                  ^ оба запроса шли параллельно,
                    порядок — по времени ответа

concatMap   ------A---B-------C-|
                      ^ b ждал завершения a: порядок
                        гарантирован, но позже

exhaustMap  ------A-----------C-|
                  ^ b проигнорирован: во время a
                    новые значения отбрасываются
    легенда: a b c — входные значения, A B C — результаты,
| — complete. Отменённый или отброшенный запрос ничего не даёт
```

Обратите внимание на главное различие: **все четыре получили одинаковый вход и дали разный выход**. Это не оптимизация и не стилистика — это разная бизнес-логика, выраженная одним словом.

### switchMap: отменить предыдущее

```ts
import { debounceTime, distinctUntilChanged, switchMap } from 'rxjs';

const results$ = searchInput$.pipe(
  debounceTime(300),
  distinctUntilChanged(),
  // при новом запросе предыдущий отменяется: отписка от внутреннего потока
  // прерывает HTTP-запрос (см. Reactive Model and Observables)
  switchMap((query) => api.search(query)),
);
```

Смысл: «результат устаревшего запроса мне не нужен». Это верно для любого **чтения**, где важен только актуальный результат:

- поиск и автокомплит;
- перезагрузка списка при смене фильтра;
- загрузка данных при смене параметра маршрута (`:id`);
- переключение вкладок с разными данными.

Дополнительная выгода — экономия сети: отменённый запрос прерывается, а не просто игнорируется.

### mergeMap: всё параллельно

```ts
import { mergeMap } from 'rxjs';

// Загрузить детали для каждого id — порядок не важен, ждать друг друга не нужно
const details$ = ids$.pipe(mergeMap((id) => api.getTicket(id)));

// Ограничение параллелизма вторым аргументом: не больше 4 запросов одновременно
const throttled$ = ids$.pipe(mergeMap((id) => api.getTicket(id), 4));
```

Смысл: «все операции нужны, порядок безразличен». Подходит для независимых загрузок, отправки телеметрии, параллельной обработки элементов. Ключевая деталь — **порядок результатов не гарантирован**: они приходят по времени ответа, поэтому медленный первый запрос доедет после быстрого второго.

Про второй аргумент (`concurrent`) стоит помнить всегда: `mergeMap` без ограничения на потоке из тысячи значений создаст тысячу одновременных запросов.

### concatMap: строго по очереди

```ts
import { concatMap } from 'rxjs';

// Каждое изменение сохраняется по очереди: порядок записей = порядок действий
const saved$ = changes$.pipe(concatMap((change) => api.patch(change)));
```

Смысл: «выполнить все, сохранив порядок». Это `mergeMap` с `concurrent: 1`, и именно он нужен для **записи**, где порядок операций определяет итоговое состояние: последовательные `PATCH`, применение очереди офлайн-действий, загрузка файлов один за другим.

Цена — задержка: если первая операция висит, вся очередь ждёт. И если источник эмитит быстрее, чем обрабатывается очередь, она растёт неограниченно.

### exhaustMap: игнорировать новое

```ts
import { exhaustMap } from 'rxjs';

// Повторные нажатия во время сохранения отбрасываются
const submitted$ = submitClicks$.pipe(exhaustMap((form) => api.create(form)));
```

Смысл: «текущая операция важнее новых». Классика — защита от двойного клика: пока идёт `POST`, повторные нажатия не создают вторую сущность. Также используется для «обновить сейчас» в поллинге, чтобы кнопка не порождала параллельные обновления.

Обратная сторона: значения теряются молча. Допустим, пользователь нажал «сохранить» с изменённой формой, пока шло предыдущее сохранение. Его последнее действие **не выполнится**, и об этом нужно сообщить в интерфейсе.

## Таблица выбора

Все четыре оператора собраны в одной таблице — вместе с ценой неверного выбора.

| оператор | что делает с предыдущим | сценарий | если выбрать неверно |
|---|---|---|---|
| `switchMap` | отменяет | поиск, автокомплит, смена фильтра, `:id` | потерянные записи при `POST` |
| `mergeMap` | выполняет параллельно | независимые загрузки, аналитика | гонка: ответы вперемешку |
| `concatMap` | ставит в очередь | последовательные записи, порядок важен | очередь растёт, лаг копится |
| `exhaustMap` | игнорирует новые | двойной клик, повторный submit | потерянные действия пользователя |

По умолчанию для **чтения** берут `switchMap`. Для **записи** — `concatMap` или `exhaustMap`, потому что отменённый `POST` мог уже выполниться на сервере.

Практический алгоритм выбора — три вопроса:

1. **Нужен ли результат предыдущей операции?** Нет — `switchMap`. Да — идём дальше.
2. **Важен ли порядок?** Да — `concatMap`. Нет — `mergeMap` (не забыв про `concurrent`).
3. **Нужно ли вообще принимать новые значения, пока идёт текущая операция?** Нет — `exhaustMap`.

## Цена неверного выбора

### switchMap на записи: потерянные данные

```ts
// опасно: пользователь быстро меняет два поля
formChanges$.pipe(switchMap((data) => api.patch(data))).subscribe();
```

Первый `PATCH` отменяется вторым. Отмена на клиенте **не отменяет уже начатую обработку на сервере**: запрос мог дойти и примениться, а мог быть прерван на середине. Итог — недетерминированное состояние: иногда сохранилось всё, иногда только последнее, иногда частично. Для записи это неприемлемо; правильный выбор — `concatMap` (сохранить все по порядку) или `exhaustMap` (отбросить лишние клики).

### mergeMap там, где нужен порядок: гонка

```ts
// Пользователь дважды переключил фильтр: "open", затем "closed"
filter$.pipe(mergeMap((f) => api.list(f))).subscribe((list) => this.render(list));
```

Запрос по `"open"` оказался медленнее, поэтому его ответ придёт **после** ответа по `"closed"`. На экране окажется список для фильтра, который уже не выбран. Это классическая гонка в интерфейсе, которую `switchMap` исключает по построению: устаревший запрос отменён, и его ответ не отрендерится.

### concatMap на поиске: растущая очередь

```ts
// Каждое нажатие клавиши встаёт в очередь
searchInput$.pipe(concatMap((q) => api.search(q))).subscribe();
```

Десять символов — десять запросов, выполняемых последовательно. Пользователь видит, как результаты «догоняют» его ввод с растущим отставанием, а последний, единственно нужный, приходит последним. Здесь нужен `switchMap`.

### exhaustMap на поиске: молчание

С `exhaustMap` первый запрос выполнится, а весь дальнейший ввод во время его выполнения будет отброшен — поиск покажет результат для первых введённых символов и «замрёт».

## Вложенность и как её избегать

Самая частая структурная ошибка — подписка внутри подписки:

```ts
// плохо: подписка в подписке
route.params.subscribe((params) => {
  api.getTicket(params.id).subscribe((ticket) => {
    api.getComments(ticket.id).subscribe((comments) => {
      this.render(ticket, comments);
    });
  });
});
```

Здесь не так сразу четыре вещи — и именно их ждут услышать на интервью:

1. Внутренние подписки никто не закрывает: при быстрой смене `:id` они копятся.
2. Предыдущие запросы не отменяются, поэтому на экран может приехать ответ для старого тикета.
3. Ошибка на любом уровне ломает всю конструкцию, и обработать её в одном месте негде.
4. Отписаться от этого невозможно: внешняя отписка не остановит внутренние.

Плоская версия читается и ведёт себя предсказуемо:

```ts
import { switchMap, map } from 'rxjs';

const view$ = route.params.pipe(
  map((params) => params['id'] as string),
  distinctUntilChanged(),
  // смена id отменяет незавершённые запросы предыдущего
  switchMap((id) =>
    api.getTicket(id).pipe(
      switchMap((ticket) =>
        api.getComments(ticket.id).pipe(map((comments) => ({ ticket, comments }))),
      ),
    ),
  ),
);
```

Когда нужны **и** родительское значение, **и** результат внутреннего запроса, есть два приёма без лишней вложенности:

```ts
// 1) второй аргумент проектора: (внешнее, внутреннее) => результат
route$.pipe(switchMap((id) => api.getTicket(id), (id, ticket) => ({ id, ticket })));

// 2) чаще читаемее — собрать объект внутри
route$.pipe(switchMap((id) => api.getTicket(id).pipe(map((ticket) => ({ id, ticket })))));
```

А когда внутренние запросы независимы — их не нужно вкладывать вовсе: параллельная загрузка выражается через `forkJoin`/`combineLatest`, см. [Операторы комбинирования потоков](./05-combination-operators.md).

```ts
import { forkJoin, switchMap } from 'rxjs';

const page$ = route.params.pipe(
  switchMap((params) =>
    forkJoin({
      ticket: api.getTicket(params['id']),
      comments: api.getComments(params['id']),
      history: api.getHistory(params['id']),
    }),
  ),
);
```

> **Angular-контекст.** Именно так устроены два самых частых RxJS-места в Angular-приложении: загрузка данных по параметру маршрута (`route.params` + `switchMap`) и живой поиск (`debounceTime` + `switchMap`). Подробный разбор с сигналами и `takeUntilDestroyed` — в курсе Angular, глава про RxJS в Angular.

## Обработка ошибок внутри выпрямления

Одна деталь, которая объединяет эту статью со следующей: **место `catchError` меняет поведение**.

```ts
// catchError снаружи: ошибка одного запроса убивает весь поток ввода —
// поиск перестанет работать навсегда
input$.pipe(
  switchMap((q) => api.search(q)),
  catchError(() => of([])),
);

// catchError внутри: падает только текущий запрос, поток ввода жив
input$.pipe(
  switchMap((q) => api.search(q).pipe(catchError(() => of([])))),
);
```

Причина в том, что ошибка терминирует поток, в котором возникла. Снаружи это внешний поток (`input$`), внутри — только внутренний. Полный разбор — в статье [Обработка ошибок и повторы](./06-error-handling-and-retries.md).

## Типичные ошибки на интервью

- **«switchMap — это `map` для асинхронного»** — описание, из которого не следует главное: отмена предыдущей внутренней работы. Ожидается ответ через вопрос «что делать с предыдущим запросом»: отменить (`switchMap`), выполнить параллельно (`mergeMap`), поставить в очередь (`concatMap`), проигнорировать новое (`exhaustMap`).

- **`switchMap` для операций записи** — самая дорогая по последствиям ошибка. Отмена на клиенте не откатывает то, что сервер уже начал обрабатывать: результат — недетерминированное состояние. Для `POST`/`PATCH` ожидается `concatMap` (все по порядку) или `exhaustMap` (отбросить лишние нажатия).

- **Не знать про `concurrent` у `mergeMap`** — `mergeMap` без ограничения на большом потоке открывает столько параллельных запросов, сколько пришло значений. Дальше обычно уточняют: «что будет с тысячей id?» Тысяча одновременных запросов, отказ сервера или браузерный лимит соединений.

- **«`concatMap` — это просто безопасный `mergeMap`»** — нет: он сериализует работу, поэтому медленная первая операция задерживает всю очередь, а быстрый источник заставляет очередь расти неограниченно. Это осознанный компромисс ради порядка, а не «более надёжный вариант».

- **Подписка внутри подписки** — маркер того, что кандидат не освоил выпрямление. Хороший ответ называет четыре конкретных последствия:

  - незакрытые внутренние подписки;
  - отсутствие отмены устаревших запросов;
  - невозможность обработать ошибку в одном месте;
  - неработающая внешняя отписка.

- **`catchError` в конце цепочки на потоке пользовательских событий** — после первой ошибки поток мёртв, и интерфейс «перестаёт реагировать». Ожидается понимание, что `catchError` ставят **внутри** `switchMap`, чтобы ограничить область терминирования внутренним потоком.

- **Не различать «отменён» и «проигнорирован»** — `switchMap` отменяет уже начатую работу (запрос прерывается), `exhaustMap` не начинает новую (значение отбрасывается). Разница видна в Network: в первом случае будет запрос со статусом cancelled, во втором запроса не будет вовсе.

- **Гонка ответов как «баг бэкенда»** — если при быстром переключении фильтров на экране оказываются чужие данные, причина в `mergeMap` там, где нужен `switchMap`. Способность связать симптом («иногда показывается список для предыдущего фильтра») с выбором оператора — то, что отличает senior-ответ.
