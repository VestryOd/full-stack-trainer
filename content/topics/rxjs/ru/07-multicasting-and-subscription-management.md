# Multicasting и управление подписками

## Cold vs hot: почему запросов оказалось два

Ленивость из [Reactive Model and Observables] означает, что функция-подписчик выполняется **на каждую подписку**. Для HTTP это значит буквально: две подписки — два запроса.

```
            Cold и hot: сколько раз выполнится работа
            один и тот же users$ = http.get(...), две подписки

            БЕЗ share (cold):
подписка A  --R-----D--|
подписка B  -----R-----D--|
                 ^ ВТОРОЙ запрос: работа началась заново

            С share() (hot после первой подписки):
подписка A  --R-----D--|
подписка B  --------D--|
                    ^ запроса нет: подписалась на общий результат
  легенда: R — запрос ушёл в сеть, D — данные пришли подписчику.
      Каждая подписка на cold-поток запускает работу с нуля
```

**Cold Observable** создаёт свой источник для каждого подписчика: `http.get()`, `new Observable(...)`, `defer(...)`, `interval(...)`. **Hot Observable** имеет источник, существующий независимо от подписчиков, и раздаёт им одни и те же значения: `Subject`, `fromEvent` (событие происходит независимо от того, слушаете вы его или нет), результат `share()`.

Самая частая практическая ловушка выглядит так:

```ts
// Сервис отдаёт cold-поток
readonly tickets$ = this.http.get<Ticket[]>('/api/tickets');

// Шаблон подписывается дважды — и уходят ДВА запроса
// {{ (tickets$ | async)?.length }} — подписка 1
// @for (t of tickets$ | async) — подписка 2
```

Диагностика однозначная: откройте Network и посчитайте запросы. Если их больше, чем логических операций, значит на cold-поток подписались несколько раз. Второй способ — временно добавить `tap({ subscribe: () => console.count('subscribe') })` в начало цепочки.

## share и shareReplay

```
                                           share и shareReplay: что выбрать
┌────────────────────────────────┬────────────────────────────────────────────┬──────────────────────────────────────┐
│ вызов                          │ что делает                                 │ риск                                 │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│ share()                        │ один источник на всех активных подписчиков │ поздний подписчик не увидит прошлое  │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│ shareReplay(1)                 │ то же + отдаёт последнее значение          │ refCount по умолчанию FALSE → утечка │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│ shareReplay({ bufferSize: 1,   │ источник отписывается, когда               │ при новом подписчике работа          │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│   refCount: true })            │ подписчиков не осталось                    │ начнётся заново                      │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│ share({ resetOnRefCountZero:   │ полный контроль: сброс по                  │ нужно понимать все четыре флага      │
├────────────────────────────────┼────────────────────────────────────────────┼──────────────────────────────────────┤
│   false, resetOnError: true }) │ нулю подписчиков, ошибке, complete         │                                      │
└────────────────────────────────┴────────────────────────────────────────────┴──────────────────────────────────────┘
                         документация RxJS прямо предупреждает: при refCount: false источник
                          НЕ отписывается при нуле подписчиков и «potentially run for ever»
```

`share()` вставляет между источником и подписчиками `Subject`: первая подписка запускает источник, остальные присоединяются к тому же результату. Когда подписчиков не остаётся, источник отписывается — и следующая подписка запустит работу заново.

`shareReplay(bufferSize)` делает то же, но с буфером: поздний подписчик немедленно получает последние N значений. Именно это нужно для «загрузить справочник один раз и раздавать всем».

### Утечка в shareReplay

Ключевая деталь, о которой документация RxJS предупреждает дословно: при `refCount: false` (а это **значение по умолчанию** для формы `shareReplay(1)`) источник **не отписывается**, когда счётчик подписчиков падает до нуля, и внутренний `ReplaySubject` может «run for ever».

```ts
import { interval, shareReplay } from 'rxjs';

// УТЕЧКА: интервал продолжает тикать даже после того,
// как все подписчики отписались — и держит в памяти буфер
const ticks$ = interval(1000).pipe(shareReplay(1));

const sub = ticks$.subscribe();
sub.unsubscribe();   // интервал ЖИВ, значения продолжают идти в ReplaySubject

// БЕЗ УТЕЧКИ: источник отписывается, когда подписчиков не осталось
const safeTicks$ = interval(1000).pipe(
  shareReplay({ bufferSize: 1, refCount: true }),
);
```

Правило простое:

- **`refCount: true`** — для всего, что имеет побочный эффект во времени: `interval`, WebSocket, подписка на события, поллинг. Иначе поток живёт после ухода последнего подписчика.
- **`refCount: false`** (по умолчанию) — осмысленно для одноразовых дорогих вычислений и HTTP-запросов, которые вы хотите закешировать до конца жизни приложения: справочник, конфиг, профиль пользователя. Здесь «источник не отписывается» — не утечка, а желаемое поведение, потому что источник уже завершился.

Второй нюанс — поведение при ошибке. У `share()` есть флаги `resetOnError` (по умолчанию `true`), `resetOnComplete` и `resetOnRefCountZero`. Если поток с `shareReplay` упал, все текущие подписчики получат ошибку, а вот получит ли следующий подписчик новую попытку или закешированную ошибку — зависит от конфигурации. Для кеширующего справочника обычно нужен «сброс при ошибке», чтобы следующая подписка попробовала снова.

```ts
// Кеш справочника: держим значение навсегда, но ошибку не кешируем
readonly categories$ = this.http.get<Category[]>('/api/categories').pipe(
  shareReplay({ bufferSize: 1, refCount: false }),
);
```

> **Legacy.** Раньше мультикаст собирали вручную: `multicast(() => new Subject()), refCount()` или `publishReplay(1), refCount()`. В RxJS 7 всё семейство `multicast`/`publish`/`publishReplay`/`publishBehavior`/`refCount` помечено deprecated с удалением в v8. Замены: `share()`/`shareReplay()` для обычных случаев и `connectable(source, { connector })` — если нужен именно поток, который подключается вручную через `connect()`. Если видите `publish().refCount()` — это код эпохи RxJS 5–6.

## Правило «подписывайся ближе к краю»

Самое практичное правило управления подписками формулируется так: **чем меньше `subscribe` в коде, тем меньше вещей нужно закрывать**. Сервисы возвращают потоки; подписывается тот, кто действительно потребляет данные — компонент, эффект, точка входа.

```ts
// ПЛОХО: сервис подписался сам — теперь он владеет подпиской,
// должен её закрывать, и наружу отдаёт не поток, а «состояние»
class TicketService {
  tickets: Ticket[] = [];
  load(): void {
    this.http.get<Ticket[]>('/api/tickets').subscribe((t) => (this.tickets = t));
  }
}

// ХОРОШО: сервис возвращает поток, подписка живёт у потребителя
class TicketService {
  readonly tickets$ = this.http.get<Ticket[]>('/api/tickets');
}
```

Второй уровень того же правила: если значение нужно только для отображения, подписку лучше отдать фреймворку — `async`-пайп в шаблоне или `toSignal` в Angular. Тогда закрывать нечего вообще.

```
                                         Как закрывать подписки
┌───────────────────────┬─────────────────────────────────────┬────────────────────────────────────────┐
│ приём                 │ когда подходит                      │ замечание                              │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ оператор завершения   │ take(1), first(), takeWhile         │ поток закрывается сам — лучший вариант │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ takeUntil(destroy$)   │ долгоживущий поток в компоненте     │ ставить ПОСЛЕДНИМ в pipe               │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ takeUntilDestroyed()  │ Angular: привязка к жизни контекста │ см. курс Angular, глава про RxJS       │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ sub.unsubscribe()     │ императивный код, тесты             │ легко забыть при раннем return         │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ sub.add(other)        │ дерево подписок из одной точки      │ исторический приём, сегодня редкость   │
├───────────────────────┼─────────────────────────────────────┼────────────────────────────────────────┤
│ async-пайп / toSignal │ значение нужно только шаблону       │ отписка полностью на фреймворке        │
└───────────────────────┴─────────────────────────────────────┴────────────────────────────────────────┘
                       правило: подписывайся как можно ближе к краю приложения —
                          в сервисах возвращай поток, а не подписывайся внутри
```

### takeUntil и почему он должен быть последним

```ts
import { Subject, takeUntil } from 'rxjs';

private readonly destroy$ = new Subject<void>();

ngOnInit(): void {
  source$.pipe(
    switchMap((x) => load(x)),
    takeUntil(this.destroy$),   // ПОСЛЕДНИМ
  ).subscribe(render);
}

ngOnDestroy(): void {
  this.destroy$.next();
  this.destroy$.complete();
}
```

Порядок здесь не стилистический. `takeUntil`, поставленный **не последним**, оставляет живыми операторы после него: если после `takeUntil` стоит `switchMap`, его внутренние подписки продолжат жить, потому что `takeUntil` завершил только ту часть цепочки, что была до него. Это одна из редких ситуаций, где порядок операторов влияет на утечку, а не на результат.

> **Legacy.** Ручное управление через `new Subscription()` с `add()` и вызовом `unsubscribe()` в `ngOnDestroy` — предыдущее поколение решений. Оно работает, но требует дисциплины на каждом добавлении подписки. Сегодня в компонентах используют `takeUntil(destroy$)`, а в Angular — `takeUntilDestroyed()`, который берёт контекст уничтожения автоматически.

## Диагностика: поток не завершается, подписка жива

Утечки в RxJS не проявляются как ошибки — приложение просто медленно тяжелеет. Признаки и способы проверки:

**Признак 1: работа продолжается после закрытия экрана.** Запросы в Network после перехода на другую страницу, тики таймера в консоли, растущий счётчик в логах.

**Признак 2: обработчик вызывается несколько раз на одно действие.** Каждое открытие экрана добавляет ещё одну живую подписку, и на третий раз клик обрабатывается трижды.

**Способ проверки — логирование жизненного цикла:**

```ts
import { tap, finalize } from 'rxjs';

source$.pipe(
  tap({
    subscribe: () => console.log('SUB', label),
    unsubscribe: () => console.log('UNSUB', label),
    complete: () => console.log('COMPLETE', label),
  }),
  finalize(() => console.log('FINALIZE', label)),
);
```

Если в логе на десять `SUB` приходится два `UNSUB` — утечка найдена. Обратите внимание, что `tap` с объектом-наблюдателем видит и подписку, и отписку (глава [Transformation and Filtering Operators]), а `finalize` срабатывает при любом финале (глава [Error Handling and Retries]).

**Способ проверки в браузере:** снимок памяти (Heap snapshot) до и после многократного открытия/закрытия экрана. Растущее число объектов `Subscriber`, `SafeSubscriber` или ваших компонентов — прямое указание на удержанные подписки.

Три вопроса, которые быстро локализуют проблему:

1. **Завершается ли поток сам?** `http.get()` — да; `interval`, `fromEvent`, `Subject` — нет. Незавершающийся источник + подписка без ограничителя = утечка.
2. **Есть ли `shareReplay` без `refCount: true` над незавершающимся источником?** Тогда источник живёт после ухода всех подписчиков.
3. **Стоит ли `takeUntil` последним?** Если после него есть flattening-операторы, внутренние подписки не закроются.

## Типичные ошибки на интервью

- **«Почему один и тот же Observable сделал три HTTP-запроса?»** — потому что он cold: каждая подписка запускает работу заново, а три `| async` в шаблоне — это три подписки. Ожидается не только диагноз, но и лечение: `shareReplay({ bufferSize: 1, refCount: true })` либо одна подписка с `as`-переменной в шаблоне.

- **Не различать cold и hot по источнику** — `http.get()`, `defer`, `interval` холодные; `Subject`, `fromEvent`, результат `share()` горячие. Практический критерий: существует ли источник значений независимо от подписчика.

- **`shareReplay(1)` как «просто кеш»** — по умолчанию `refCount: false`, поэтому над `interval` или сокетом это утечка: источник не отписывается при нуле подписчиков. Ожидаемый ответ содержит и различение случаев: для завершившегося HTTP-запроса `refCount: false` безопасен и желателен, для бесконечного источника нужен `refCount: true`.

- **Не знать про поведение при ошибке** — упавший `shareReplay` может отдать закешированную ошибку следующему подписчику вместо новой попытки. Управляется флагами `resetOnError`/`resetOnComplete`/`resetOnRefCountZero` у `share`.

- **`takeUntil` не последним в `pipe()`** — операторы после него продолжат работать, и внутренние подписки flattening-операторов не закроются. Это классический вопрос «на внимательность», у которого есть техническое объяснение, а не просто соглашение.

- **`subscribe` внутри сервиса** — сервис становится владельцем подписки и состояния, наружу отдаёт массив вместо потока, а ошибка запроса терминирует его навсегда. Ожидается правило «подписывайся ближе к краю»: сервис возвращает поток, подписывается потребитель.

- **`publish().refCount()` или `multicast` в ответе** — всё это семейство помечено deprecated в RxJS 7 и удаляется в v8. Ожидается `share`/`shareReplay`, а для ручного подключения — `connectable()`.

- **«Утечки в RxJS — это когда забыл unsubscribe»** — неполно. Утечка возникает и при `shareReplay` без `refCount`, и при вложенных подписках (внешняя отписка их не закрывает), и при `takeUntil` не на последнем месте. Хороший ответ включает способ **обнаружения**: логирование `subscribe`/`unsubscribe` через `tap` и heap snapshot после многократного открытия экрана.
