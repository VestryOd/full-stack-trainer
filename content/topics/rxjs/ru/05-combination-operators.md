# Операторы комбинирования потоков

## Три вопроса перед выбором оператора

Комбинирующих операторов много, но выбор всегда сводится к трём вопросам:

1. **Кто задаёт момент эмита?** Любой источник (`combineLatest`, `merge`) или один ведущий (`withLatestFrom`)?
2. **Нужны все значения или только последние?** Пары по индексу (`zip`) или актуальные значения (`combineLatest`)?
3. **Когда результат готов?** Постоянно по мере изменений или один раз после завершения всех (`forkJoin`)?

Три ответа приводят к одному из этих восьми операторов.

| оператор | когда эмитит | сценарий |
|---|---|---|
| `combineLatest` | на любое изменение любого источника | связанные фильтры формы |
| `forkJoin` | один раз, после complete всех | параллельная загрузка независимых ресурсов |
| `zip` | парами по индексу | строгое соответствие значений (редко) |
| `withLatestFrom` | только на значение ведущего | действие + текущее состояние |
| `merge` | на любое значение любого источника | несколько источников одного события |
| `concat` | по очереди, после complete предыдущего | этапы: сначала кеш, потом сеть |
| `race` | только у первого, кто эмитнул | таймаут через гонку, выбор быстрейшего |
| `startWith` | значение перед потоком | начальное состояние, скелетон |

Одно замечание про форму записи: операторные формы `combineLatest`, `merge` и `zip` внутри `pipe()` помечены deprecated. Внутри пайпа берут `combineLatestWith`, `mergeWith` или `zipWith`.

> **Legacy.** `combineLatest(a$, b$)`, `merge(a$, b$)`, `zip(a$, b$)` как **статические функции** — норма. А те же имена как **операторы внутри `pipe()`** помечены deprecated в RxJS 7 с удалением в v8. Причина в путанице: `a$.pipe(combineLatest(b$))` и `combineLatest(a$, b$)` выглядели похоже, но имели разный порядок аргументов.

## combineLatest и его ловушка

`combineLatest` держит последнее значение каждого источника и эмитит новый набор при изменении любого из них.

```
        combineLatest и withLatestFrom на одних источниках
status$         --1-----2--------3--|
query$          ------x-----y-------|

combineLatest   ------A-B---C----D--|
                      ^ A=(1,x) — первый эмит только тогда,
                        когда у query$ появилось значение;
                        B=(2,x) C=(2,y) D=(3,y): любой источник

withLatestFrom  --------A--------B--|
                        ^ A=(2,x): значение 1 потеряно — у query$
                          ещё не было значения; эмитит только по
                          ведущему status$
combineLatest — 4 значения (любое изменение), withLatestFrom — 2:
      ведущий поток задаёт момент, ведомый добавляет снимок
```

**Ловушка**: `combineLatest` не эмитит ничего, пока **каждый** источник не выдал хотя бы одно значение. На диаграмме видно: значение `1` пришло в такте 2, но результат появился только в такте 6 — когда заговорил второй поток.

Практическое проявление — экран, который остаётся пустым «без причины»:

```ts
import { combineLatest, map } from 'rxjs';

// ловушка: если categories$ или sort$ не эмитят при старте,
// vm$ не выдаст ни одного значения — экран пустой навсегда
const vm$ = combineLatest([tickets$, categories$, sort$]).pipe(
  map(([tickets, categories, sort]) => buildViewModel(tickets, categories, sort)),
);
```

Три способа гарантировать первое значение:

```ts
import { combineLatest, startWith, of } from 'rxjs';

// 1) startWith на «молчаливых» источниках
combineLatest([
  tickets$,
  categories$.pipe(startWith([] as Category[])),
  sort$.pipe(startWith<SortOrder>('created-desc')),
]);

// 2) BehaviorSubject вместо Subject: у него всегда есть текущее значение
//    (см. Creating Streams and Subjects)
private readonly sort = new BehaviorSubject<SortOrder>('created-desc');

// 3) для форм в Angular: valueChanges не эмитит начальное значение,
//    поэтому его добавляют явно
form.valueChanges.pipe(startWith(form.getRawValue()));
```

Второе, о чём стоит помнить: `combineLatest` эмитит на **каждое** изменение, поэтому три фильтра, изменённые программно один за другим, дадут три эмита и три запроса. Лечится `debounceTime(0)` (склеить синхронную серию) или `distinctUntilChanged` с компаратором.

Типичный правильный сценарий — связанные фильтры:

```ts
const results$ = combineLatest({
  status: statusFilter$,
  query: searchQuery$.pipe(debounceTime(300)),
  page: page$,
}).pipe(
  // combineLatest с объектом (RxJS 6.5+) читается лучше, чем массив с деструктуризацией
  switchMap(({ status, query, page }) => api.list({ status, query, page })),
);
```

## withLatestFrom: ведущий и ведомый

`withLatestFrom` асимметричен: эмит происходит **только** на значение основного потока, а из остальных берётся снимок последнего значения.

```ts
import { withLatestFrom, map } from 'rxjs';

// «Сохранить по клику, взяв текущее состояние формы»
saveClicks$.pipe(
  withLatestFrom(formValue$, currentUser$),
  map(([, form, user]) => ({ ...form, updatedBy: user.id })),
  concatMap((payload) => api.save(payload)),
);
```

Здесь `combineLatest` был бы прямой ошибкой: он сохранял бы данные при каждом изменении формы, а не по нажатию кнопки. И наоборот — для фильтров `withLatestFrom` не подойдёт, потому что изменение «ведомого» фильтра не вызовет перезагрузку.

Критерий выбора формулируется одним вопросом: **«что должно вызывать пересчёт?»** Если любое из значений — `combineLatest`. Если только одно, а остальные лишь дополняют контекст — `withLatestFrom`.

Вторая ловушка `withLatestFrom` видна на диаграмме: значение ведущего потока, пришедшее до того, как ведомый выдал первое значение, **теряется молча**. Клик, сделанный до загрузки профиля пользователя, не приведёт ни к чему — без ошибок и логов. Если такое поведение недопустимо, ведомый поток снабжают `startWith` или заменяют конструкцию на `switchMap`, который дождётся значения.

## forkJoin и zip: одноразовые комбинации

```
          forkJoin и zip: чем отличаются от combineLatest
a$        --1-----2-----|
b$        ----x---------y----|

forkJoin  -------------------(2,y)|
                             ^ одно значение: последние из каждого,
                               и только после complete всех
                               источников

zip       ----A---------B----|
              ^ A=(1,x): пары по индексу — первое с первым,
                B=(2,y): второе со вторым;
                лишние значения буферизуются
     forkJoin на бесконечном источнике не даст ничего никогда;
    zip при разной скорости источников копит буфер — риск памяти
```

### forkJoin — это Promise.all

```ts
import { forkJoin } from 'rxjs';

// Три независимых запроса параллельно, результат — когда пришли все
const page$ = forkJoin({
  ticket: api.getTicket(id),
  comments: api.getComments(id),
  history: api.getHistory(id),
});
// { ticket, comments, history } — один эмит, затем complete
```

Три свойства, которые нужно знать про `forkJoin`, и все три вытекают из «ждёт `complete`»:

- **Бесконечный источник ломает всё.** `forkJoin([http$, interval(1000)])` не эмитит никогда: второй поток не завершается. Это самая частая причина «forkJoin молчит».
- **Ошибка любого источника терминирует результат.** Как и `Promise.all`, `forkJoin` падает целиком: чтобы получить частичный результат, ошибки гасят внутри каждого источника через `catchError` (см. [Обработка ошибок и повторы](./06-error-handling-and-retries.md)).
- **Источник, завершившийся без значений, даёт пустой результат.** Если один из потоков завершился, не эмитнув ничего, `forkJoin` завершится, не выдав вообще ничего — молча.

```ts
// Частичный результат: одна упавшая загрузка не ломает страницу
forkJoin({
  ticket: api.getTicket(id),
  comments: api.getComments(id).pipe(catchError(() => of([] as Comment[]))),
  history: api.getHistory(id).pipe(catchError(() => of([] as Event[]))),
});
```

### zip — по индексу, а не по времени

`zip` собирает первое значение с первым, второе со вторым и так далее. Если один источник быстрее, его значения **буферизуются** в ожидании пары — а значит растут в памяти.

Практически `zip` нужен редко: почти всегда, когда кажется, что нужен `zip`, на самом деле нужен `forkJoin` (одноразовые запросы) или `combineLatest` (актуальные значения). Законный случай — строгое попарное соответствие двух потоков одинаковой длины: например, поток команд и поток подтверждений.

## merge, concat, race, startWith

```ts
import { merge, concat, race, startWith, of, timer, map } from 'rxjs';

// merge: несколько источников одного события — «обновить» с трёх кнопок
const refresh$ = merge(toolbarRefresh$, keyboardShortcut$, timer(0, 60_000));

// concat: этапы по очереди — сначала кеш, потом сеть
const data$ = concat(cache.read(key), api.load(key));

// race: кто первый — тот и победил, остальные отписываются
const fastest$ = race(primaryApi.load(), mirrorApi.load());

// startWith: начальное состояние до первого настоящего значения
const state$ = updates$.pipe(startWith<State>({ status: 'loading' }));
```

Что важно про каждый:

- **`merge`** объединяет по времени: значения идут в порядке появления, из всех источников. Есть ограничение параллелизма вторым аргументом, как у `mergeMap`.
- **`concat`** подписывается на следующий источник только после `complete` предыдущего. Отсюда ловушка: `concat(interval(1000), api.load())` никогда не дойдёт до запроса — первый поток бесконечен.
- **`race`** выбирает победителя по **первому эмиту**, а не по завершению, и отписывается от проигравших. Классический приём — таймаут: `race(api.load(), timer(5000).pipe(switchMap(() => throwError(() => new Error('timeout')))))`. Правда, для таймаута есть готовый оператор `timeout` — см. статью [Обработка ошибок и повторы](./06-error-handling-and-retries.md).
- **`startWith`** просто добавляет значения в начало. Полезен для `combineLatest`, для показа скелетона и для того, чтобы поток «имел значение» с первого такта.

## Разбор частых ошибок выбора

**`combineLatest` вместо `withLatestFrom` для действия.** Кнопка «сохранить» с `combineLatest([clicks$, form$])` сохраняет данные при каждом изменении формы — то есть на каждый введённый символ. Признак ошибки: действие срабатывает без действия пользователя.

**`withLatestFrom` вместо `combineLatest` для фильтров.** Список перезагружается только при смене статуса, а изменение поисковой строки «не работает». Признак: часть фильтров действует, часть — нет.

**`forkJoin` на потоке, который не завершается.** Ничего не происходит, ошибок нет. Проверка: добавить `take(1)` к каждому источнику или посмотреть, есть ли `complete` в цепочке.

**`combineLatest` там, где нужен `forkJoin`.** Три HTTP-запроса в `combineLatest` дадут не один результат, а три промежуточных набора (по мере ответов), потому что каждый ответ — изменение источника. Если нужен один результат «когда всё готово» — `forkJoin`.

**`merge` вместо `concat` для этапов.** «Сначала кеш, потом сеть» с `merge` даст оба значения в произвольном порядке, и свежие данные могут быть перезаписаны кешем.

## Типичные ошибки на интервью

- **Не знать про «молчание» `combineLatest`** — он не эмитит, пока каждый источник не выдал значение. Ожидаемый ответ включает симптом («экран пустой, хотя данные загрузились») и три решения: `startWith`, `BehaviorSubject`, либо пересмотр конструкции. Follow-up: «а что если один источник вообще никогда не эмитит?» — результат не появится никогда, и ошибки не будет.

- **Путать `combineLatest` и `withLatestFrom`** — самая частая пара после `switchMap`/`mergeMap`. Ожидается критерий, а не определение: «что должно вызывать пересчёт». Дополнительный вопрос на понимание: «что произойдёт с клике, если ведомый поток ещё не эмитил?» — значение потеряется молча.

- **«`forkJoin` — это `combineLatest` для запросов»** — нет: `forkJoin` эмитит один раз после `complete` всех источников, `combineLatest` — на каждое изменение. Для трёх HTTP-запросов `combineLatest` выдаст три промежуточных результата вместо одного финального.

- **Не связывать «`forkJoin` молчит» с отсутствием `complete`** — самая частая практическая проблема. Причина всегда одна: среди источников есть незавершающийся поток (`interval`, `Subject`, `fromEvent`).

- **Ожидать частичный результат от `forkJoin`** — как и `Promise.all`, он падает целиком при ошибке любого источника. Правильный ответ — `catchError` внутри каждого источника, чтобы упавшая часть превратилась в значение по умолчанию.

- **`zip` вместо `forkJoin`** — работает в простом случае, но семантика другая: `zip` собирает пары по индексу и буферизует опережающие значения. На потоках разной скорости это утечка памяти, а на одноразовых запросах разница видна только при повторных значениях.

- **`concat` с бесконечным первым источником** — второй никогда не подпишется. Хороший ответ сразу называет проверку: завершается ли первый поток вообще.

- **Операторные формы в `pipe()`** — `a$.pipe(combineLatest(b$))`, `a$.pipe(merge(b$))`, `a$.pipe(zip(b$))` помечены deprecated в RxJS 7. Ожидается `combineLatestWith`/`mergeWith`/`zipWith` внутри `pipe()` либо статические функции `combineLatest(a$, b$)` снаружи.
