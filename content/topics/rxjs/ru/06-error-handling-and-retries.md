# Обработка ошибок и повторы

## Ошибка терминирует поток

Контракт подписки из статьи [Реактивная модель и Observable](./01-reactive-model-and-observables.md) жёсткий: `next` много раз, затем **один раз** либо `complete`, либо `error`. Это значит, что ошибка — не «одно плохое значение среди хороших», а конец потока:

```ts
import { fromEvent, map } from 'rxjs';

// первая же ошибка в парсинге убивает поток кликов навсегда
fromEvent(button, 'click')
  .pipe(map((event) => JSON.parse((event.target as HTMLElement).dataset['payload']!)))
  .subscribe({
    next: (payload) => save(payload),
    error: (err) => console.error(err), // вызовется один раз, и всё
  });
```

Практическое следствие, которое стоит помнить дословно: **кнопка визуально работает, а обработчик мёртв**. Никаких признаков, кроме одной записи в консоли. Слушатель в DOM (Document Object Model — дерево элементов страницы) снят, потому что поток завершился, и следующие клики никуда не идут.

Именно этот класс ошибок делает обработку ошибок в RxJS не «хорошей практикой», а условием работоспособности.

Отдельно стоит различать два вида ошибок:

```ts
source$.pipe(
  map((x) => risky(x)),      // ошибка здесь проходит по потоку → её поймает catchError
).subscribe({
  next: (value) => risky(value), // ошибка здесь уже вне потока → catchError её не увидит
});
```

Ошибка, брошенная внутри колбэка `next` у `subscribe`, не является ошибкой потока: она уходит в глобальный обработчик необработанных ошибок RxJS. Поэтому логику из `subscribe` полезно переносить в операторы — там она хотя бы поддаётся обработке.

## catchError и три стратегии восстановления

`catchError` перехватывает ошибку и **обязан вернуть новый Observable** — тот, которым продолжится поток. Отсюда три стратегии:

```ts
import { catchError, of, EMPTY, throwError } from 'rxjs';

// 1) Подставить значение: экран рисуется, пользователь видит «нет данных»
api.list().pipe(catchError(() => of([] as Ticket[])));

// 2) Переключиться на запасной поток: сеть упала — читаем кеш
api.list().pipe(catchError(() => cache.read('tickets')));

// 3) Преобразовать ошибку и пробросить дальше: наверху ждут доменную ошибку,
//    а не HttpErrorResponse
api.list().pipe(
  catchError((err: HttpErrorResponse) =>
    throwError(() => new TicketsUnavailableError(err.status)),
  ),
);
```

Четвёртая, отдельная форма — `EMPTY`: поток завершается без значений и без ошибки. Это «молча ничего не делать», и применять её стоит осознанно — она скрывает проблему от вызывающего кода.

```ts
// Аналитика: если отправка метрики упала, приложению это неинтересно
metrics.send(event).pipe(catchError(() => EMPTY));
```

У `catchError` есть второй аргумент — исходный Observable, что даёт компактную форму бесконечного повтора:

```ts
// caught — это тот же источник; вернув его, мы подписываемся заново
socket$.pipe(catchError((err, caught) => caught));
```

Работает, но опасно. Без задержки и ограничения это бесконечный цикл переподписок. Если сервер уже упал, ваш же клиент шлёт запросы без пауз и только усугубляет аварию. Для повторов есть `retry` с конфигурацией — см. ниже.

## Где ставить catchError: внутри или снаружи

```
 Где стоит catchError — от этого зависит, жив ли поток
           клики: 1-й и 3-й запросы успешны, 2-й падает

clicks$    --c--c-------c--|

           switchMap(req), catchError снаружи:
результат  ----A--X
                  ^ поток терминирован: третий клик уже
                    не обработается; кнопка визуально
                    работает, но обработчик мёртв

           switchMap(req.pipe(catchError)) — внутри:
результат  ----A--E-------A|
                  ^ E — значение по умолчанию вместо
                    ошибки; внешний поток кликов жив,
                    третий клик обработан
   ошибка терминирует тот поток, в котором возникла:
внутри flattening — только внутренний, снаружи — весь конвейер
```

Это главный практический вывод статьи. Код различается одной парой скобок, поведение — принципиально:

```ts
// снаружи: ошибка одного запроса убивает поток кликов
clicks$.pipe(
  switchMap((id) => api.load(id)),
  catchError(() => of(fallback)),   // сработает один раз, дальше поток мёртв
);

// внутри: падает только конкретный запрос, поток кликов жив
clicks$.pipe(
  switchMap((id) => api.load(id).pipe(catchError(() => of(fallback)))),
);
```

Причина в том, что ошибка терминирует **тот поток, в котором возникла**. Внутри `switchMap` ошибка возникает во внутреннем потоке (`api.load(id)`). `catchError` внутри превращает её в значение до того, как она дойдёт до внешнего.

Снаружи ошибка уже прошла через `switchMap` и стала ошибкой внешнего потока. А внешний поток здесь и есть источник пользовательских событий.

Flattening-оператор здесь — это `switchMap` или `mergeMap`, то есть оператор, который сам подписывается на вложенный поток. Правило выбора места:

- источник — **долгоживущий** (события, `interval`, `Subject`, роут-параметры) → `catchError` **внутри** flattening-оператора;
- источник — **одноразовый** (один HTTP-запрос, `forkJoin` на старте экрана) → `catchError` снаружи допустим: терминировать нечего;
- нужен и локальный fallback, и глобальная реакция → два `catchError`: внутри для значения по умолчанию, снаружи для «совсем всё плохо».

## retry: повтор с задержкой

`retry` переподписывается на источник при ошибке. Ключевое — конфигурация, потому что `retry(3)` без задержки повторяет мгновенно:

```
          retry с экспоненциальной задержкой
источник   --X
             ^ первая попытка упала

           retry({ count: 3, delay: (_, n) =>
                    timer(500 * 2 ** (n - 1)) })

попытка 1  --X
попытка 2  -----X
                ^ через 500 мс
попытка 3  ----------X
                     ^ через 1000 мс
попытка 4  --------------------V--|
                               ^ через 2000 мс — успех
без delay retry повторяет мгновенно и добивает падающий сервер;
resetOnSuccess: true обнуляет счётчик после удачного значения
```

```ts
import { retry, timer, throwError } from 'rxjs';

api.load().pipe(
  retry({
    count: 3,
    // delay может быть числом (фиксированная пауза) или функцией:
    // (error, retryCount) => Observable — здесь экспоненциальный backoff
    delay: (error: HttpErrorResponse, retryCount) => {
      // повторять только то, что имеет смысл повторять
      if (error.status < 500 && error.status !== 0) {
        return throwError(() => error); // 4xx повторять бессмысленно
      }
      return timer(500 * 2 ** (retryCount - 1)); // 500, 1000, 2000 мс
    },
    resetOnSuccess: true, // счётчик обнуляется после каждого удачного значения
  }),
);
```

Три вещи, которые отличают рабочий `retry` от опасного:

1. **Ограничение по количеству.** `retry()` без `count` повторяет бесконечно.
2. **Задержка, лучше растущая.** Мгновенные повторы к уже упавшему сервису усугубляют аварию, а клиента блокируют по ограничению частоты (rate limit).
3. **Фильтр по типу ошибки.** Повторять `401` или `422` бессмысленно: результат не изменится. Повторять стоит `5xx`, таймауты и `status === 0` (сеть недоступна).

Про `resetOnSuccess`: он важен для долгоживущих потоков вроде WebSocket. Без него три разрыва за неделю работы приложения исчерпают лимит; с ним счётчик обнуляется после каждого успешного значения.

> **Legacy.** Раньше для повторов с задержкой использовали `retryWhen(errors => errors.pipe(delay(1000)))`. В RxJS 7 `retryWhen` помечен deprecated с прямой заменой в сообщении: `retry({ delay })`. Причина — `retryWhen` требовал понимать «поток ошибок» как отдельную сущность, а конфигурация `retry` выражает то же самое явно. Аналогично устарела ручная реализация backoff через `scan` внутри `retryWhen`.

## timeout: ошибка вместо тишины

Запрос, который не отвечает, — не ошибка с точки зрения потока: он просто молчит. Спиннер крутится вечно. `timeout` превращает тишину в ошибку:

```ts
import { timeout, TimeoutError, catchError, of } from 'rxjs';

api.load().pipe(
  // first — сколько ждать первое значение; each — максимальную паузу между значениями
  timeout({ first: 5000 }),
  catchError((err) =>
    err instanceof TimeoutError
      ? of({ status: 'timeout' as const })
      : throwError(() => err),
  ),
);

// Для потоков с продолжающимися значениями (сокет, поллинг) — each
socket$.pipe(timeout({ each: 30_000 })); // молчит больше 30 секунд → ошибка
```

Есть и форма `timeout({ with: () => fallback$ })` — вместо ошибки переключиться на запасной поток. Полезно, когда таймаут означает «покажи кеш», а не «покажи ошибку».

## Инструменты обработки ошибок

Все инструменты этой статьи в одной таблице — прежде чем последнему из них достанется свой раздел.

| оператор | что делает | типичное применение |
|---|---|---|
| `catchError(() => of(x))` | подставляет значение вместо ошибки | пустой список, значение по умолчанию |
| `catchError(() => other$)` | переключает на запасной поток | кеш вместо сети, зеркало API |
| `catchError(e => throwError(…))` | преобразует ошибку и пробрасывает | `HttpErrorResponse` в домен-ошибку |
| `catchError((e, caught) => caught)` | повторно подписывается на источник | бесконечный повтор (осторожно!) |
| `retry({ count, delay })` | повторяет подписку после ошибки | нестабильная сеть, `5xx` |
| `timeout({ each, first })` | бросает `TimeoutError` по тишине | зависший запрос, медленный сокет |
| `finalize(fn)` | выполняется при любом финале | скрыть спиннер, закрыть ресурс |
| `EMPTY` в `catchError` | завершает поток без значений | «молча ничего», без ветки ошибки |

## finalize: гарантированная очистка

`finalize` — единственный оператор, срабатывающий при **любом** окончании: `complete`, `error` и `unsubscribe`. Это делает его правильным местом для освобождения ресурсов и единственным местом, где очистка гарантирована:

```ts
import { finalize } from 'rxjs';

loading.set(true);
api.load().pipe(
  finalize(() => loading.set(false)),  // сработает во всех трёх случаях
).subscribe({ next: render, error: showError });
```

Сравните с попыткой сделать то же в `subscribe`. Пришлось бы дублировать `loading.set(false)` в `next`, `error` и `complete` — и всё равно не покрыть случай отписки, когда пользователь уходит с экрана. Именно поэтому «скрыть спиннер» почти всегда живёт в `finalize`.

Важный порядок: `finalize` ставят **после** `catchError`, если нужно, чтобы очистка выполнилась и при обработанной ошибке. При этом `finalize` не «глотает» ошибку. Он только выполняет побочный эффект.

## Практический пример: устойчивый запрос

Соберём всё вместе — запрос, который переживает нестабильную сеть, не висит вечно, отдаёт наружу понятную ошибку и всегда закрывает спиннер:

```ts
import {
  catchError, finalize, map, retry, throwError, timeout, TimeoutError, timer,
} from 'rxjs';

export class TicketsUnavailableError extends Error {
  constructor(readonly reason: 'timeout' | 'server' | 'network') {
    super(`Tickets unavailable: ${reason}`);
  }
}

function loadTickets(api: TicketApi, ui: LoadingUi) {
  ui.setLoading(true);

  return api.list().pipe(
    // 1. не ждать вечно: тишина превращается в TimeoutError
    timeout({ first: 8000 }),

    // 2. повторять только то, что имеет смысл, с растущей паузой
    retry({
      count: 2,
      delay: (error, attempt) => {
        const retryable =
          error instanceof TimeoutError ||
          (error as HttpErrorResponse).status >= 500 ||
          (error as HttpErrorResponse).status === 0;

        return retryable ? timer(500 * 2 ** (attempt - 1)) : throwError(() => error);
      },
    }),

    // 3. наружу — доменная ошибка вместо транспортной
    catchError((error) => {
      if (error instanceof TimeoutError) {
        return throwError(() => new TicketsUnavailableError('timeout'));
      }
      const status = (error as HttpErrorResponse).status;
      return throwError(
        () => new TicketsUnavailableError(status === 0 ? 'network' : 'server'),
      );
    }),

    // 4. спиннер закрывается при успехе, ошибке и уходе с экрана
    finalize(() => ui.setLoading(false)),
  );
}
```

Порядок операторов здесь не случаен:

- `timeout` до `retry`, иначе таймаут будет считаться на все попытки суммарно;
- `retry` до `catchError`, иначе преобразованная ошибка не будет распознана как повторяемая;
- `finalize` последним.

> **Angular-контекст.** В Angular эта логика обычно живёт не в сервисе, а в HTTP-интерсепторе. Тогда повторы и маппинг ошибок применяются ко всем запросам сразу, а ветка «показать баннер» отделена от ветки «показать ошибку у поля». Разбор с кодом — в курсе Angular, глава про HTTP и интерсепторы.

## Типичные ошибки на интервью

- **«Ошибка — это просто ещё одно уведомление в потоке»** — нет: после `error` поток мёртв, `next` и `complete` уже не придут, teardown выполнен. Ожидаемая иллюстрация — поток пользовательских событий, который «перестал работать» после одной неудачной операции.

- **`catchError` в конце цепочки над долгоживущим источником** — самая частая ошибка по последствиям. После первой ошибки поток кликов или `route.params` терминируется, и интерфейс перестаёт реагировать без видимых признаков. Ожидается ответ про размещение `catchError` **внутри** flattening-оператора и объяснение причины: ошибка терминирует тот поток, в котором возникла.

- **`catchError`, который ничего не возвращает** — оператор обязан вернуть Observable. Возврат `undefined` или просто логирование без `return` — ошибка типизации, а по смыслу — попытка «проглотить» ошибку, для чего есть `EMPTY`.

- **`retry` без задержки и без ограничения** — `retry()` повторяет бесконечно и мгновенно: упавший сервис получает шквал запросов, а клиент — бан по rate limit. Ожидается `retry({ count, delay })` с растущей задержкой и фильтром: `4xx` повторять бессмысленно.

- **Не различать «повторяемые» и «неповторяемые» ошибки** — повтор `422 Unprocessable Entity` или `401` не изменит результат. Хороший ответ называет критерий: повторять `5xx`, таймауты и `status === 0`.

- **`retryWhen` в ответе** — deprecated в RxJS 7 с прямой заменой `retry({ delay })`. Знание этого показывает, что кандидат работал с актуальной версией, а не переносит рецепты из статей 2018 года.

- **Скрывать спиннер в `subscribe`, а не в `finalize`** — тогда `loading = false` дублируется в трёх колбэках. И всё равно не срабатывает при отписке, когда пользователь уходит с экрана во время загрузки. А `finalize` — единственное место, срабатывающее при `complete`, `error` и `unsubscribe` одинаково.

- **Не знать про `timeout`** — «запрос завис, спиннер вечный» решается не таймером в компоненте, а `timeout({ first })`, который превращает тишину в `TimeoutError` и включает её в обычную обработку ошибок.

- **Путать ошибку потока и ошибку в подписчике** — исключение, брошенное внутри колбэка `next` у `subscribe`, не проходит через `catchError`: оно уходит в глобальный обработчик. Это аргумент за то, чтобы логика жила в операторах, а не в `subscribe`.
