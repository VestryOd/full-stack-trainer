# Reactive Model и Observables

## Поток значений во времени как первичная абстракция

Обычные структуры данных описывают значения, доступные *сейчас*: массив — это все элементы сразу, промис — одно значение, которое будет позже. RxJS вводит другую абстракцию: **поток** — последовательность значений, распределённая во времени, с которой можно работать как с целым.

Практический смысл в том, что события, ранее требовавшие разных механизмов, получают один интерфейс:

```ts
import { fromEvent, interval } from 'rxjs';

const clicks$ = fromEvent<PointerEvent>(document, 'click'); // много значений, бесконечно
const ticks$ = interval(1000);                              // значения по таймеру
const response$ = ajax.getJSON<User[]>('/api/users');       // одно значение и complete
```

Все три — `Observable`, и к любому применимы одни и те же операторы: отфильтровать, задержать, объединить с другим потоком, отменить. Именно эта унификация — а не «замена промисов» — главная причина существования RxJS. Как только задача формулируется словами «когда произошло A, но не чаще чем раз в секунду, и только если B уже дало значение, а предыдущий запрос надо отменить» — императивный код превращается в набор флагов и таймеров, а поток описывает это декларативно.

Соглашение об именовании: переменные-потоки принято помечать суффиксом `$` (`clicks$`, `user$`). Это не требование языка, но оно экономит время при чтении кода — сразу видно, что значение нужно подписать, а не использовать напрямую.

## Observable vs Promise: четыре оси

```
                     Observable и Promise: четыре оси различий
┌──────────────────┬─────────────────────────────┬─────────────────────────────────┐
│ ось              │ Promise                     │ Observable                      │
├──────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ запуск работы    │ сразу при создании (eager)  │ при подписке (lazy)             │
├──────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ сколько значений │ ровно одно                  │ ноль, одно, много, бесконечно   │
├──────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ отмена           │ нет: then просто не позовут │ unsubscribe прерывает работу    │
├──────────────────┼─────────────────────────────┼─────────────────────────────────┤
│ синхронность     │ колбэк всегда в микротаске  │ может отдать значение синхронно │
└──────────────────┴─────────────────────────────┴─────────────────────────────────┘
         следствие ленивости: пока нет подписки — нет запроса, нет таймера,
          нет слушателя события; поток описывает работу, а не выполняет её
```

### 1. Ленивость

Промис начинает работу в момент создания — конструктор выполняется немедленно:

```ts
const promise = fetch('/api/users'); // запрос УЖЕ ушёл
// даже без .then() сервер получил запрос
```

Observable — это *описание* работы. Функция-подписчик выполняется на каждую подписку:

```ts
import { Observable } from 'rxjs';

const users$ = new Observable<User[]>((subscriber) => {
  console.log('запрос ушёл');           // не выполнится до первой подписки
  fetch('/api/users')
    .then((r) => r.json())
    .then((users) => {
      subscriber.next(users);
      subscriber.complete();
    })
    .catch((err) => subscriber.error(err));
});

// здесь ничего не произошло: ни одного запроса
users$.subscribe();                     // "запрос ушёл" — первый запрос
users$.subscribe();                     // "запрос ушёл" — ВТОРОЙ запрос
```

Две подписки — две независимые работы. Это не баг, а прямое следствие ленивости, и одновременно источник классической ошибки «почему у меня два HTTP-запроса вместо одного» — механика и решение разобраны в [Multicasting and Subscription Management].

### 2. Количество значений

Промис по контракту разрешается один раз: `resolve(a); resolve(b)` — второй вызов игнорируется. Observable может вызвать `next` сколько угодно раз, в том числе никогда не завершиться:

```ts
import { of, interval, EMPTY } from 'rxjs';

of(1, 2, 3);      // три значения, затем complete
interval(1000);   // бесконечный поток: 0, 1, 2, ... без complete
EMPTY;            // ноль значений, сразу complete
```

Отсюда практическое следствие: код, работающий с потоком, обязан отвечать на вопрос «что делать, если значений будет много» — тогда как с промисом этот вопрос не возникает.

### 3. Отменяемость

Промис отменить нельзя: можно проигнорировать результат, но работа продолжится (запрос дойдёт до сервера, таймер сработает). Отмена в промисах существует только через внешний механизм — `AbortController`, — и его нужно прокидывать вручную.

У Observable отмена встроена в модель: `unsubscribe()` не просто отключает колбэки, а выполняет **teardown-логику** — код, освобождающий ресурсы:

```ts
import { Observable } from 'rxjs';

const timer$ = new Observable<number>((subscriber) => {
  let count = 0;
  const id = setInterval(() => subscriber.next(count++), 1000);

  // teardown: вызывается при unsubscribe, complete и error
  return () => {
    clearInterval(id);
    console.log('таймер очищен');
  };
});

const sub = timer$.subscribe(console.log);
setTimeout(() => sub.unsubscribe(), 3500); // "таймер очищен", интервал остановлен
```

Тот же принцип работает и с сетью: `HttpClient` в Angular прерывает запрос при отписке (через `AbortController` под капотом), а оператор `switchMap` использует это, чтобы автоматически отменять устаревшие запросы — центральный сюжет статьи [Flattening Operators].

### 4. Синхронность

Промис всегда асинхронный: даже `Promise.resolve(1).then(fn)` вызовет `fn` в микротаске, то есть после текущего синхронного кода. Observable такого требования не имеет:

```ts
import { of } from 'rxjs';

console.log('до');
of(1, 2).subscribe((v) => console.log('значение', v)); // синхронно!
console.log('после');

// вывод: до → значение 1 → значение 2 → после
```

Это свойство полезно (нет лишней задержки для уже готовых данных) и опасно одновременно: код, который «иногда синхронный, иногда нет», ведёт к трудноуловимым различиям в порядке выполнения. Правило: не полагайтесь на синхронность конкретного потока, если она не гарантирована его конструкцией.

## Анатомия подписки

Подписка — это передача потоку **наблюдателя** (observer): объекта с методами `next`, `error`, `complete`. Контракт жёсткий: `next` может вызываться много раз, затем ровно один раз либо `error`, либо `complete` — и после этого поток мёртв.

```
       Контракт подписки: next* (error | complete)?
успех    --1--2--3--|
                    ^ complete: значений больше не будет,
                      teardown выполнен
ошибка   --1--2--X
                 ^ error: поток ТЕРМИНИРОВАН,
                   next и complete уже не придут
отписка  --1--2--!
                 ^ unsubscribe: работа прервана,
                   но это не error и не complete
легенда:  1 2 3 — значения,  | — complete,  X — error,  ! — unsubscribe
```

```ts
const sub = source$.subscribe({
  next: (value) => console.log('значение', value),
  error: (err) => console.error('ошибка', err),   // вызовется максимум один раз
  complete: () => console.log('завершено'),        // вызовется максимум один раз
});

sub.unsubscribe(); // прекращает получение значений и запускает teardown
```

Что здесь важно понимать:

- **`error` терминирует поток.** Это самое частое место, где ломаются подписки на пользовательские события: если в цепочке произошла ошибка, поток кликов больше не работает, и кнопка «перестала нажиматься». Стратегии обработки — в [Error Handling and Retries].
- **`complete` и `error` взаимоисключающие** и оба запускают teardown автоматически: после них отписываться не нужно.
- **`unsubscribe` — не то же самое, что `complete`.** Отписка означает «мне больше не интересно», а не «данные закончились»: колбэк `complete` при этом не вызывается.
- **`Subscription` умеет складываться**: `sub.add(otherSub)` привязывает время жизни одной подписки к другой, а `unsubscribe()` на родительской закрывает всё дерево. В компонентах это исторический способ управления подписками — сегодня предпочтительнее `takeUntil`/`takeUntilDestroyed`, см. [Multicasting and Subscription Management].

## Когда Promise честно лучше

RxJS — не универсальная замена промисам. Промис (и `async`/`await`) выигрывает, когда задача по своей природе одноразовая:

```ts
// Одно значение, отмена не нужна, никакой композиции во времени
async function loadConfig(): Promise<AppConfig> {
  const response = await fetch('/api/config');
  if (!response.ok) throw new Error(`Config load failed: ${response.status}`);
  return response.json();
}
```

Признаки, что Observable здесь избыточен: значение ровно одно, отмена не требуется, нет комбинирования с другими источниками, а линейная последовательность шагов читается через `await` понятнее, чем через цепочку операторов. Навязывать поток такому коду — способ усложнить его без выгоды.

Мост между моделями существует в обе стороны:

```ts
import { from, firstValueFrom, lastValueFrom } from 'rxjs';

const stream$ = from(fetch('/api/users'));    // Promise → Observable
const users = await firstValueFrom(users$);   // Observable → Promise (первое значение)
const total = await lastValueFrom(count$);    // Observable → Promise (последнее значение)
```

Важная деталь про `from(promise)`: промис уже начал работу, поэтому такой Observable **не ленив** — он лишь оборачивает результат. Чтобы вернуть ленивость, нужен `defer(() => from(fetch(...)))` — приём разобран в [Creating Streams and Subjects].

Отдельно про `toPromise()`: в RxJS 7 он помечен deprecated и удалён в дальнейших версиях. Причина — неоднозначная семантика (что возвращать для потока без значений?). Замена — `firstValueFrom`/`lastValueFrom` с явным выбором и понятным поведением при пустом потоке (они отклоняют промис с `EmptyError`).

## Типичные ошибки на интервью

- **«Observable — это Promise, который может вернуть много значений»** — описание одной оси из четырёх, и обычно за ним следует непонимание ленивости. Ленивость важнее «многозначности»: именно из неё следуют повторные запросы при нескольких подписках, работоспособность отмены и возможность безопасно описывать поток заранее, не начиная работу.

- **«Observable всегда асинхронный»** — нет: `of(1)` и `from([1, 2])` доставляют значения синхронно, в момент подписки. Отсюда практическое следствие: код, полагающийся на то, что «подписка отработает позже», может получить значение до того, как выполнится следующая строка.

- **Путать `unsubscribe` и `complete`** — отписка означает «мне больше не нужно», завершение означает «данных больше нет». Колбэк `complete` при отписке не вызывается, и это ломает логику вида «в complete закрою модалку». Проверочный вопрос на интервью: «выполнится ли teardown при unsubscribe?» — да, выполнится, это единственное, что гарантированно происходит в обоих случаях.

- **Не знать, что `error` терминирует поток** — самая дорогая по последствиям ошибка. Поток кликов, в цепочке которого один раз упал HTTP-запрос, мёртв навсегда: кнопка визуально работает, но обработчик больше не вызывается. Именно поэтому `catchError` ставят *внутри* flattening-оператора, а не в конце цепочки — разбор в [Error Handling and Retries].

- **`toPromise()` в ответе** — маркер знаний уровня RxJS 6. В RxJS 7 он deprecated; ожидаемый ответ — `firstValueFrom`/`lastValueFrom`, причём с пониманием, что они отклоняются с `EmptyError`, если поток завершился без значений.

- **«RxJS всегда лучше async/await»** — на senior-интервью ценится обратное: способность назвать случаи, где поток избыточен (одно значение, отмена не нужна, нет комбинирования) и где `await` читается лучше. Ответ «использую RxJS везде, потому что это Angular» показывает отсутствие критерия выбора.
