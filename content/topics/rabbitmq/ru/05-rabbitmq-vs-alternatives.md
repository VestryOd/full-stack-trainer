# RabbitMQ vs Альтернативы

## Рамка, которая делает сравнения полезными

Сравнивать брокеры по спискам функций — значит промахиваться мимо цели. Строчка вроде "у Kafka есть log compaction, у RabbitMQ — per-message TTL" верна, но не говорит, какой брокер подходит вашей задаче. TTL — это time to live, время жизни: возраст, после которого брокер выбрасывает ещё не доставленное сообщение. Полезная рамка — **какую задачу каждая система решала в первую очередь**:

- **RabbitMQ** создавался для маршрутизации и доставки отдельных сообщений. Ключевой вопрос: как доставить конкретное сообщение нужному потребителю?
- **Kafka** создавался для надёжных, упорядоченных, воспроизводимых журналов событий в масштабе. Ключевой вопрос: как хранить поток событий, который любой потребитель может читать по порядку с любого момента времени?
- **Redis Pub/Sub** создавался для вещания в реальном времени подключённым клиентам, целиком в памяти. Ключевой вопрос: как разослать сигнал всем слушающим подписчикам с минимальной задержкой?
- **AWS SQS** (Simple Queue Service — управляемая очередь Amazon Web Services) создавался для развязанных управляемых очередей задач с гарантией at-least-once и без расходов на эксплуатацию. Ключевой вопрос: как надёжно ставить фоновые задачи в очередь, не управляя инфраструктурой?

Понимание исходного замысла даёт больше, чем любой список функций.

## RabbitMQ vs Kafka

Это самое частое сравнение на senior-собеседованиях, обычно формулируемое как "умный брокер, тупой потребитель" vs "тупой брокер, умный потребитель".

### Архитектурное различие

| | RabbitMQ, «умный брокер» | Kafka, «умный потребитель» |
|---|---|---|
| Раскладка сообщений | Маршрутизируются по правилам exchange и binding в очереди | Дописываются в упорядоченные неизменяемые логи: топики, разбитые на партиции (partition) |
| Что отслеживает брокер | Какие сообщения доставлены каждому потребителю | Ничего по потребителям. Он только дописывает и отдаёт |
| Что отслеживает потребитель | Ничего. Он просто обрабатывает приходящее | Свою позицию в логе — число, которое называют offset |
| После обработки | Брокер удаляет сообщение после ack потребителя | Ничего не удаляется. Потребитель может перечитать с любого offset: вчера, неделю назад, с самого начала |
| Доставка | Push: брокер сам отправляет потребителю | Pull: потребитель опрашивает брокер |

Владение offset — это ключевое различие. В RabbitMQ после ack сообщение исчезает: перечитать его невозможно. В Kafka данные хранятся настраиваемый период (дни, недели, вечно), и любой новый потребитель может читать с самого начала.

Push против pull — это не про то, кто управляет скоростью. Потребитель RabbitMQ задаёт окно prefetch через `basic.qos`, и оно ограничивает число неподтверждённых сообщений, которые брокер вправе ему отдать. Потребитель Kafka ограничивает собственные выборки через `max.poll.records` и `fetch.max.bytes`. Скоростью управляют обе стороны, просто с разных концов соединения.

### Пропускная способность и сценарии использования

- **Сильные стороны RabbitMQ**
  - Сложная маршрутизация: 4 типа exchange, wildcard-паттерны, сопоставление по заголовкам.
  - Per-message TTL, приоритетные очереди и очередь мёртвых писем — DLQ (dead letter queue) — из коробки.
  - Push-доставка, а значит меньшая задержка для отдельного сообщения.
  - Простые конкурирующие потребители: несколько воркеров на одну очередь.
  - Понятная операционная модель, веб-интерфейс управления в комплекте.
  - Десятки тысяч сообщений в секунду на очередь и порядка 50k в секунду на узел, когда очередей на узле несколько. Выше — только без персистентности или за счёт числа очередей.
- **Сильные стороны Kafka**
  - Воспроизводимый журнал событий: потребители могут перечитывать историю.
  - Exactly-once внутри Kafka, через транзакции Kafka. Гарантия работает от Kafka к Kafka: offset потребителя пишется в **ту же транзакцию**, что и выходные топики. Документация Kafka прямо говорит, что большинство внешних систем не поддерживает two-phase commit. Поэтому потребитель, который пишет в базу данных, гарантии exactly-once не получает — если только не хранит offset в той же базе.
  - На порядок больше пропускной способности — миллионы сообщений в секунду на скромном кластере — потому что запись последовательная и идёт пакетами.
  - Несколько независимых групп потребителей, у каждой свой offset.
  - Потоковая обработка через Kafka Streams и ksqlDB.
  - Долгосрочное хранение событий: event sourcing, журналы аудита, инжест в data lake.
- **Слабые стороны RabbitMQ**
  - Нет replay сообщений. После ack сообщение исчезает.
  - Нет групп потребителей с независимыми offset.
  - Хуже подходит для широкого fan-out, где каждому потребителю нужен свой replay.
- **Слабые стороны Kafka**
  - Нет нативной маршрутизации на уровне сообщения. Маршрут задаётся только топиком и партицией.
  - Нет per-message TTL, только политики retention на уровне лога.
  - Выше операционная сложность: ZooKeeper или KRaft плюс управление партициями.
  - Pull-модель добавляет задержку на поллинг.
  - Нет встроенного DLQ. Его реализуют в коде приложения.
  - Гарантия порядка — на уровне партиции, а не топика.

### Гарантии порядка

- **RabbitMQ**
  - Один потребитель на очередь даёт гарантированный порядок FIFO (first in, first out — первым пришёл, первым ушёл).
  - Несколько потребителей на одну очередь не дают гарантии глобального порядка. Потребитель A может обработать сообщение 2, пока B ещё обрабатывает сообщение 1.
  - Конкурирующие потребители жертвуют порядком ради пропускной способности.
- **Kafka**
  - Внутри одной партиции сообщения строго упорядочены.
  - Между партициями гарантии порядка нет.
  - Чтобы гарантировать порядок для одной сущности — скажем, для всех событий `user_id=42` — используйте partition key. Сообщения с одним ключом всегда идут в одну партицию.

```ts
// Kafka: принудительный порядок для событий конкретного пользователя
producer.send({
  topic: 'user-events',
  messages: [{
    key: userId.toString(),  // одинаковый ключ → одна партиция → порядок
    value: JSON.stringify(event),
  }],
});
```

### Когда выбирать RabbitMQ вместо Kafka

- Нужна сложная маршрутизация (wildcards, заголовки, фильтрация на потребителя)
- Сообщения — это задачи или команды, а не события: должны быть обработаны один раз, затем удалены
- Нужен per-message TTL или приоритет
- Нужны DLQ и логика повторов с минимальным кодом в приложении
- Малая или средняя система, и вы не хотите операционной сложности Kafka

### Когда выбирать Kafka вместо RabbitMQ

- Нужно воспроизводить события (новый сервис должен догнать с первого дня)
- Несколько независимых групп потребителей с разной скоростью обработки
- Event sourcing или audit log, который никогда не должен терять данные
- Очень высокая пропускная способность (миллионы/сек)
- Уже работаете в экосистеме Kafka (Kafka Connect, Kafka Streams, ksqlDB)

## RabbitMQ vs Redis Pub/Sub

Redis Pub/Sub — самый быстрый способ разослать сигнал подключённым клиентам — и самый хрупкий.

| | Redis Pub/Sub | RabbitMQ |
|---|---|---|
| Хранение | Только в памяти. Перезапуск Redis теряет все ожидающие сообщения | Персистентность по умолчанию: durable queue плюс persistent messages |
| Потребитель офлайн | Сообщение пропущено навсегда | Сообщение ждёт в очереди, потребитель догоняет при переподключении |
| Подтверждения | Нет. Fire-and-forget на уровне протокола | Полная семантика ack, nack и retry |
| Очередь | Очереди нет. Сообщения рассылаются и исчезают | Сообщения ждут, пока потребитель не подключится и не подтвердит их |

Взамен Redis Pub/Sub даёт задержку меньше миллисекунды для Redis внутри того же процесса.

Redis также предлагает **Redis Streams**, добавленные в Redis 5.0, и это ближе к Kafka, чем к Pub/Sub. Там есть группы потребителей, персистентное хранилище и идентификаторы сообщений для отслеживания позиции. Redis Streams — разумная лёгкая альтернатива Kafka для событийного стриминга малого и среднего объёма.

- **Выбирайте Redis Pub/Sub, когда**
  - Нужно вещание в реальном времени подключённым клиентам: чат, живой дашборд, уведомления.
  - Вы шлёте сигналы инвалидации кеша, то есть просите серверы приложений сбросить ключ.
  - Потеря сигнала допустима, потому что следующий придёт скоро.
  - Redis уже есть, и не хочется отдельного брокера.
- **Выбирайте RabbitMQ, когда**
  - Доставка должна быть гарантирована даже при офлайн-потребителе.
  - Нужны durable queues, DLQ и логика повторов.
  - Операции бизнес-критичны и не могут терять сообщения.

## RabbitMQ vs AWS SQS

AWS SQS — полностью управляемый сервис очередей: нет серверов для развёртывания, нет брокеров для сопровождения.

- **AWS SQS**
  - Полностью управляемый: нет кластера, автоматическое масштабирование, SLA (service level agreement — соглашение об уровне сервиса) 99.9%.
  - Доставка at-least-once, гарантированная AWS.
  - Standard queues: очень высокая пропускная способность, но сообщения могут прийти не по порядку.
  - FIFO queues: обработка exactly-once плюс порядок, при меньшей пропускной способности — около 3k TPS (transactions per second, транзакций в секунду).
  - Visibility timeout: сообщение становится "невидимым" на время обработки. Это не настоящая блокировка: другой потребитель может взять его, когда timeout истечёт.
  - Встроенная поддержка DLQ через redrive policy, без дополнительной топологии.
  - Pull-based: потребители сами вызывают `ReceiveMessage`, поддерживается long polling.
  - Нет exchange и нет маршрутизации: одна очередь на логический поток.
  - Цена за сообщение — около $0.40 за миллион сообщений на Standard.
- **RabbitMQ**
  - Self-hosted или через управляемый вариант: CloudAMQP либо Amazon MQ (managed queue — управляемая очередь).
  - Сложная маршрутизация через exchange.
  - Push-доставка, а значит меньшая задержка для отдельного сообщения.
  - Больше контроля над топологией, поведением и настройкой.
  - Нет цены за сообщение, только фиксированная стоимость инфраструктуры.

### Visibility timeout в SQS — концепция, которую проверяют на интервью

В SQS при получении сообщения потребителем оно становится **невидимым** для других потребителей на время visibility timeout (по умолчанию 30 секунд). Если потребитель не удаляет сообщение до истечения timeout — оно становится видимым снова, и другой потребитель может его получить.

```txt
Поток visibility timeout в SQS:
  Потребитель A получает сообщение → оно невидимо 30с
  A обрабатывает и вызывает DeleteMessage → сообщение удалено ✓
  
  Потребитель A падает после получения, но до удаления:
  → visibility timeout истекает → сообщение снова видимо
  → Потребитель B получает и обрабатывает его
  (Так SQS обеспечивает at-least-once без явных ack)
```

Это отличается от модели ack в RabbitMQ. В SQS вы удаляете сообщение, а не подтверждаете его. Повторную доставку при сбое обеспечивает истёкший timeout, а не явный nack.

### SQS FIFO queues — когда важен exactly-once в AWS

| | Standard SQS | FIFO SQS |
|---|---|---|
| Пропускная способность | Практически неограниченная | 300 TPS, или 3 000 при пакетной отправке |
| Порядок | Best-effort, не гарантирован | Гарантирован внутри группы сообщений |
| Доставка | At-least-once, возможны дубликаты | Exactly-once, идентификатор дедупликации не пропускает дубликаты |

FIFO-очереди нужны для таких случаев, как финансовые транзакции и последовательности обработки заказов, где дубликат или переставленная пара — это настоящий баг.

### Когда выбирать SQS вместо RabbitMQ

- Вы уже на AWS и хотите нулевого управления инфраструктурой
- Нужно автоматическое масштабирование без планирования ёмкости
- Требования к маршрутизации простые: point-to-point или fan-out через SNS (Simple Notification Service)
- Предсказуемость стоимости за сообщение важнее задержки
- Хотите управляемый DLQ без конфигурации (redrive policy)

### Когда выбирать RabbitMQ вместо SQS

- Нужна сложная маршрутизация на основе exchange (topic wildcards, атрибуты сообщений)
- Не на AWS или нужно избежать vendor lock-in
- Нужна push-доставка для меньшей задержки на уровне сообщения
- Высокий объём, и цена за сообщение становится заградительной
- Нужен тонкий контроль над поведением retry, prefetch, приоритетом

## Типичные ошибки на интервью

- **"Kafka всегда лучше RabbitMQ, потому что быстрее"** — Kafka быстрее по суммарной пропускной способности и по потоковой обработке. У RabbitMQ меньше задержка на доставку одного сообщения, потому что он толкает его сам, а не ждёт опроса. Для очередей задач со сложной маршрутизацией RabbitMQ проще и подходит лучше. "Лучше" полностью зависит от задачи.

- **"Redis Pub/Sub — хорошая замена RabbitMQ"** — только если вы готовы терять сообщения при офлайн-потребителях. Redis Pub/Sub не имеет персистентности, нет очереди, нет гарантий доставки. Это механизм вещания, а не очередь сообщений.

- **"Kafka гарантирует exactly-once по всему топику"** — гарантии порядка и exactly-once в Kafka работают на уровне партиции, а не топика. Топик с 10 партициями — это 10 независимых упорядоченных логов. События одной сущности надо маршрутизировать в одну партицию через partition key, иначе порядок не сохранится. И сам exactly-once работает от Kafka к Kafka: на базу данных, в которую вы пишете, он не распространяется.

- **"SQS FIFO гарантирует глобальный порядок"** — SQS FIFO гарантирует порядок внутри **группы сообщений** (`MessageGroupId`). Сообщения из разных групп могут обрабатываться параллельно и в произвольном порядке относительно друг друга. Одна FIFO-очередь с одной группой сообщений — фактически однопоточная.

- **"Нужно всегда использовать Kafka, это отраслевой стандарт"** — операционная сложность Kafka стоит реальных денег: управление партициями, ребалансировка групп потребителей, управление offset. Представьте команду из трёх инженеров и продукт с умеренным трафиком. Поднимать там Kafka-кластер ради фоновой отправки писем — это оверинжиниринг. Используйте простейший инструмент, который отвечает требованиям.

- **"RabbitMQ подойдёт для event sourcing"** — плохо. RabbitMQ не хранит сообщения после ack, не умеет replay и не имеет log-семантики. Event sourcing требует append-only хранилища, которое можно воспроизвести с нуля. Для event sourcing используйте Kafka, EventStoreDB или базу данных с подходом CDC (change data capture).
