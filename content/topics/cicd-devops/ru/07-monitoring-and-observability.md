# Мониторинг и наблюдаемость

## Мониторинг vs Observability — различие

Эти два термина часто используют как синонимы, но они описывают разные вещи:

**Мониторинг** (monitoring) — практика сбора заранее определённых сигналов от системы и отправки алертов, когда эти сигналы превышают пороговые значения. Отвечает на вопрос: "Что-то идёт не так?"

**Observability** (наблюдаемость) — свойство системы, позволяющее понять её внутреннее состояние, исследуя внешние выходные данные. Отвечает на вопрос: "Почему что-то идёт не так?" — даже для режимов отказа, которые вы не предвидели при проектировании системы.

```txt
Мониторинг (известные неизвестные):
  "Оповести меня, когда частота ошибок > 1%"
  — вы заранее знали, что за ошибками надо следить

Observability (неизвестные неизвестные):
  "Почему оформление заказа втрое медленнее только у пользователей
   из Германии, на Safari под iOS, после 18:00 в будни?"
  — вы не предвидели этот режим отказа;
    observability позволяет найти его в данных
```

Система с большим количеством мониторинга может всё равно быть плохо наблюдаемой — если вы собираете только агрегированные метрики, вы видите *что* что-то не так, но не *почему*.

## Три столпа observability

Три сигнала, которые вместе дают полную картину здоровья распределённой системы — это **логи**, **метрики** и **трейсы**. Каждый отвечает на разный вопрос.

### Столп 1: Логи (Logs)

**Лог** — это запись с временной меткой об одном дискретном событии в системе. Примеры: пришёл запрос, возникла ошибка, пользователь вошёл, выполнился запрос к БД (базе данных).

```txt
Логи отвечают: "Что именно произошло в этот конкретный момент?"
```

Пример вывода лога (структурированный JSON — отраслевой стандарт):

```json
{
  "timestamp": "2025-03-15T14:32:01.234Z",
  "level": "error",
  "message": "Database query failed",
  "service": "user-service",
  "requestId": "req-abc123",
  "userId": "usr-456",
  "query": "SELECT * FROM users WHERE id = $1",
  "error": "connection timeout after 5000ms",
  "duration_ms": 5002
}
```

**Структурированное логирование** (JSON) vs **неструктурированное** (простой текст):

```ts
// ❌ Неструктурированное — читаемо для человека, но неудобно для машины
console.log(`User ${userId} failed login attempt from IP ${ip}`);

// ✅ Структурированное — по нему можно искать, фильтровать и агрегировать
logger.warn('login_failed', {
  userId,
  ip,
  attempt: attemptCount,
  reason: 'invalid_password',
});
```

Инструмент агрегации логов умеет фильтровать и агрегировать структурированные логи. Например: Datadog, Grafana Loki, CloudWatch в AWS (Amazon Web Services) или ELK Stack (Elasticsearch, Logstash, Kibana). Спросить его можно так:

- "Показать все ошибки для userId = usr-456 за последний час"
- "Посчитать неудачные попытки входа по адресу IP (Internet Protocol)"
- "Алерт, когда количество ошибок для service = payment-service > 50 за 5 минут"

**Уровни логирования** (от наименее до наиболее серьёзного):

- `DEBUG` — детальная диагностика. Включайте только на время отладки. В production на этом уровне не логируют: слишком шумно и дорого по производительности.
- `INFO` — нормальные, ожидаемые события: получен запрос, пользователь вошёл, задача завершена. Это уровень по умолчанию в production.
- `WARN` — произошло что-то неожиданное, но система справилась. Примеры: retry удался со второй попытки, использован устаревший API, приближается лимит rate limit. Разобраться стоит в спокойный период.
- `ERROR` — что-то сломалось и требует внимания прямо сейчас: база недоступна, не прошёл платёж, необработанное исключение.
- `FATAL` — приложение не может продолжать работу; процесс вот-вот завершится.

**Senior-нюанс #1 — что не следует логировать:**

```ts
// ❌ Никогда не логировать учётные данные или PII (Personally Identifiable Information —
//    персональные данные, по которым можно идентифицировать конкретного человека:
//    имя, email, телефон, адрес)
logger.info('user login', { email, password });        // логирует пароль!
logger.info('payment', { cardNumber, cvv });           // нарушение PCI DSS

// ✅ Логировать идентификаторы, не чувствительные данные
logger.info('user login', { userId, email: maskEmail(email) });
logger.info('payment initiated', { userId, orderId, last4: card.last4 });
```

Логирование учётных данных или PII нарушает и правила безопасности, и закон. PII — personally identifiable information, персональные данные: имя, email, телефон, адрес. Защищать их требуют сразу несколько регламентов:

- **GDPR** — General Data Protection Regulation, регламент Евросоюза о защите персональных данных.
- **PCI DSS** — Payment Card Industry Data Security Standard, стандарт безопасности данных платёжных карт.
- **HIPAA** — Health Insurance Portability and Accountability Act, американский закон о медицинских данных.

Многие компании были оштрафованы за логирование email или телефонов.

### Столп 2: Метрики (Metrics)

**Метрика** — это числовое измерение свойства системы, собираемое во времени. Метрики агрегированы — они говорят *сколько* или *как быстро*, а не *что конкретно произошло*.

```txt
Метрики отвечают: "Как система работает в целом со временем?"
```

Четыре "золотых сигнала" из книги Google SRE (Site Reliability Engineering, инженерия надёжности сайтов):

1. **Latency (задержка)** — сколько времени занимает обработка запросов. Смотрите перцентили p50, p95, p99: среднее обычно вводит в заблуждение.
2. **Traffic (трафик)** — сколько нагрузки получает система: запросов в секунду, сообщений в секунду, одновременных соединений.
3. **Errors (ошибки)** — доля неудачных запросов: 5xx-ответы ко всем ответам, частота исключений, частота таймаутов.
4. **Saturation (насыщенность)** — насколько система "заполнена" и как близко она к пределу мощности: загрузка процессора, памяти и диска, глубина очереди, занятость пула соединений.

**Перцентили vs среднее** — критически важное различие:

```txt
Представьте 100 запросов: 99 занимают 10мс, 1 занимает 10,000мс.
  Средняя задержка:  ~110мс   ← выглядит нормально
  p99 задержка:   10,000мс   ← 1% ждёт 10 секунд — это кризис

Среднее маскирует выбросы. Для задержки всегда смотрите p95 и p99.
p99 = "99% запросов завершаются за это время"
      (худший 1% исключён — самые недовольные ваши пользователи)
```

Распространённые типы метрик:

- **Counter** — число, которое только растёт: всего запросов, всего ошибок. Удобно, чтобы считать частоты — например, ошибок в секунду.
- **Gauge** — значение, которое может расти и падать: текущая память, глубина очереди, активные соединения.
- **Histogram** — раскладывает значения по корзинам (buckets); так считают перцентили задержки. Сколько запросов уложились в 0-10мс? 10-50мс? 50-200мс? Больше 200мс?
- **Summary** — как histogram, но перцентили считаются на стороне клиента. Менее гибок для агрегации по многим экземплярам.

Пример — инструментирование Express-приложения Node.js с метриками Prometheus (Prometheus — open-source система сбора метрик и алертинга):

```ts
import { Registry, Counter, Histogram } from 'prom-client';

const registry = new Registry();

const httpRequestsTotal = new Counter({
  name: 'http_requests_total',
  help: 'Total number of HTTP requests',
  labelNames: ['method', 'route', 'status_code'],
  registers: [registry],
});

const httpRequestDuration = new Histogram({
  name: 'http_request_duration_seconds',
  help: 'HTTP request duration in seconds',
  labelNames: ['method', 'route'],
  buckets: [0.01, 0.05, 0.1, 0.5, 1, 5],   // границы корзин в секундах
  registers: [registry],
});

// Middleware для инструментирования всех запросов
app.use((req, res, next) => {
  const end = httpRequestDuration.startTimer({ method: req.method, route: req.path });
  res.on('finish', () => {
    httpRequestsTotal.inc({
      method: req.method,
      route: req.path,
      status_code: res.statusCode,
    });
    end();   // записывает длительность
  });
  next();
});

// Эндпоинт метрик, который опрашивает Prometheus
app.get('/metrics', async (req, res) => {
  res.set('Content-Type', registry.contentType);
  res.end(await registry.metrics());
});
```

### Столп 3: Распределённая трассировка (Distributed Tracing)

**Трейс** (trace) — это след одного запроса, который проходит через все сервисы и компоненты распределённой системы. Он фиксирует, сколько времени ушло на каждом шаге.

```txt
Трейсы отвечают: "Каков полный путь этого конкретного запроса,
                 и где именно он замедлился или провалился?"
```

В монолитном приложении один stack trace рассказывает всё. В микросервисной архитектуре один пользовательский запрос может затронуть 8 сервисов:

```txt
Запрос пользователя: "Загрузить дашборд"
  │
  ├── API Gateway (2мс)
  │   │
  │   ├── Auth Service — проверить JWT (5мс)
  │   │
  │   ├── User Service — получить профиль (8мс)
  │   │   └── запрос к PostgreSQL (6мс)
  │   │
  │   └── Feed Service — лента активности (230мс)  ← 🐌 МЕДЛЕННО
  │       ├── проверка Redis cache (1мс) — MISS (промах)
  │       └── запрос к PostgreSQL (225мс)  ← УЗКОЕ МЕСТО
  │
  Итого: 245мс
```

Без трейсинга вы видите, что дашборд загружается за 245мс — медленно. С трейсингом вы сразу видите, что запрос к PostgreSQL в Feed Service отвечает за 225мс (92%) от общего времени.

**Как работает трейсинг:**

Каждому запросу присваивается уникальный **trace ID** в точке входа (API Gateway или первом сервисе). По мере прохождения через каждый сервис запрос несёт этот ID в заголовке: `traceparent` из стандарта W3C (World Wide Web Consortium) Trace Context. Каждый сервис создаёт **span** — именованную, хронометрированную единицу работы внутри трейса.

```txt
Trace ID: abc-123

  Span: "api-gateway"     [0мс ─────────────────────────── 245мс]
    Span: "auth-service"  [2мс ─────── 7мс]
    Span: "user-service"  [7мс ─────────── 15мс]
      Span: "db-query"    [9мс ──────── 15мс]
    Span: "feed-service"  [15мс ─────────────────────────── 245мс]
      Span: "redis-check" [15мс ── 16мс]
      Span: "db-query"    [16мс ─────────────────────────── 241мс]
```

**OpenTelemetry** (OTel) стал отраслевым стандартом инструментирования. Это SDK (software development kit), не привязанный к поставщику. Код инструментируется один раз, а трейсы — вместе с метриками и логами — уходят в любой бэкенд: Jaeger, Zipkin, Datadog, Honeycomb.

```ts
import { NodeSDK } from '@opentelemetry/sdk-node';
import { OTLPTraceExporter } from '@opentelemetry/exporter-trace-otlp-http';
import { HttpInstrumentation } from '@opentelemetry/instrumentation-http';
import { ExpressInstrumentation } from '@opentelemetry/instrumentation-express';
import { PgInstrumentation } from '@opentelemetry/instrumentation-pg';

const sdk = new NodeSDK({
  traceExporter: new OTLPTraceExporter({
    url: 'http://otel-collector:4318/v1/traces',
  }),
  instrumentations: [
    new HttpInstrumentation(),      // авто-инструментирует все HTTP запросы/ответы
    new ExpressInstrumentation(),   // авто-инструментирует роуты и middleware Express
    new PgInstrumentation(),        // авто-инструментирует запросы PostgreSQL
  ],
});

sdk.start();
```

При такой настройке каждый HTTP-запрос, обработчик роута Express и запрос к БД автоматически трейсится — ручная инструментация для общих случаев не нужна.

## APM — Application Performance Monitoring

**APM** (Application Performance Monitoring — мониторинг производительности приложений) — категория инструментов, объединяющих метрики, трейсы и иногда логи в единое представление, специально сфокусированное на производительности на уровне приложения.

APM-инструменты обычно предоставляют:

- **Transaction tracing**: автоматически трейсить каждый запрос через приложение
- **Code-level profiling**: определять, какая строка кода / вызов функции работает медленно
- **Error tracking**: группировать похожие ошибки, показывать стек вызовов, считать вхождения
- **Dependency mapping**: визуализировать, какие сервисы вызывают другие сервисы
- **Alerting**: уведомлять при деградации производительности ниже порога

Популярные APM-инструменты:

- **Datadog APM** — SaaS (software as a service), отличная авто-инструментация, широкая экосистема. Дорого на масштабе. "Datadog APM" — их продукт для трейсинга; на той же платформе есть метрики и логи.
- **New Relic** — SaaS, один из первых APM-инструментов. Хорош для традиционных монолитов, для микросервисов есть более новые функции.
- **Sentry** — прежде всего отслеживание ошибок, плюс мониторинг производительности. Очень популярен во frontend- и fullstack-мире. Есть open-source-версия для self-hosted.
- **Elastic APM** — часть ELK Stack (Elasticsearch, Logstash, Kibana). Open-source, удобен командам, которые уже используют Elasticsearch.
- **Grafana Stack** — open-source-вариант: Grafana для дашбордов, Prometheus для метрик, Loki для логов, Tempo для трейсов. Настройки больше, но полностью бесплатно.

Разница между APM-инструментом и отдельными столпами:

| Тип инструмента | Что делает |
|---|---|
| Логирование (Grafana Loki, CloudWatch Logs) | Хранит логи и отвечает на запросы к ним |
| Метрики (Prometheus, Datadog Metrics) | Хранит метрики и отвечает на запросы к ним |
| Трейсинг (Jaeger, Zipkin, Tempo) | Хранит трейсы и отвечает на запросы к ним |
| APM-платформа (Datadog, New Relic, Sentry) | Объединяет все три в одном интерфейсе, сфокусированном на здоровье приложения |

## Uptime-мониторинг

**Uptime-мониторинг** — простейшая форма мониторинга. По расписанию отправляйте запрос к сервису снаружи и поднимайте алерт, если ответ неправильный.

```txt
Каждую минуту, с серверов в 5 регионах:
  HTTP GET https://api.myapp.com/health
    → ожидаем: HTTP 200 в течение 3 секунд
    → после 2 неудач подряд: алерт в PagerDuty, Slack или email
```

Это "внешний" мониторинг — он имитирует то, что испытывает реальный пользователь при попытке обратиться к сервису. Он отличается от "внутреннего" мониторинга (метрики изнутри приложения). Приложение может быть здоровым изнутри и всё равно недоступным снаружи. Причины: изменилось правило firewall, не разошлись записи DNS (Domain Name System), неверно настроен load balancer.

Популярные сервисы uptime-мониторинга:

- **Pingdom** — SaaS, мониторинг из 100+ локаций, оповещения текстовым сообщением и по email.
- **UptimeRobot** — есть бесплатный тариф с интервалом 5 минут. Популярен для пет-проектов.
- **Checkly** — мониторинг синтетическими скриптами, а не только ping. Умеет проигрывать сценарий: логин, добавить в корзину, оформить заказ.
- **AWS CloudWatch** — встроен, если вы уже в AWS. Умеет создавать health check по URL.
- **StatusPage.io** — не сам мониторинг, а сервис публичных страниц статуса — то, что вы видите на status.stripe.com или githubstatus.com.

## Эндпоинты health check

**Health check endpoint** (эндпоинт проверки работоспособности) — отдельный маршрут API, который сообщает, здоров ли сервис и готов ли он принимать трафик. Этот маршрут нужен не пользователям, а инфраструктуре: его опрашивают Kubernetes и балансировщик нагрузки.

```txt
GET /health
  → 200 OK
    {"status": "ok"}
  → 503 Service Unavailable
    {"status": "degraded", "reason": "database unreachable"}
```

Существуют два типа health check, и их путаница вызывает проблемы:

**Liveness probe** (проба живучести) — "Жив ли процесс? Нужно ли его перезапустить?"

Liveness check падает, если процесс приложения находится в невосстановимом состоянии (дедлок, нехватка памяти, заблокированный event loop). Ответ на неудачный liveness check — **перезапустить контейнер**.

```ts
// Liveness: просто убедиться, что процесс может ответить
app.get('/health/live', (_req, res) => {
  res.status(200).json({ status: 'ok' });
});
```

**Readiness probe** (проба готовности) — "Готов ли сервис принимать трафик?"

Readiness check падает, когда приложение работает, но ещё не может обслуживать запросы. Оно может прогреваться, или соединение с базой либо кэш ещё не готовы. Ответ на неудачный readiness check — **убрать pod из load balancer**, но не перезапускать его.

```ts
// Readiness: проверить, что все зависимости доступны
app.get('/health/ready', async (_req, res) => {
  const checks = await Promise.allSettled([
    db.query('SELECT 1'),        // БД доступна?
    redis.ping(),                // Redis доступен?
  ]);

  const dbOk = checks[0].status === 'fulfilled';
  const redisOk = checks[1].status === 'fulfilled';

  if (dbOk && redisOk) {
    res.status(200).json({ status: 'ok', db: 'ok', redis: 'ok' });
  } else {
    res.status(503).json({
      status: 'degraded',
      db: dbOk ? 'ok' : 'unreachable',
      redis: redisOk ? 'ok' : 'unreachable',
    });
  }
});
```

Kubernetes использует обе пробы:

```yaml
livenessProbe:
  httpGet:
    path: /health/live
    port: 3000
  initialDelaySeconds: 10     # ждать 10с перед первой проверкой (время запуска)
  periodSeconds: 10
  failureThreshold: 3         # перезапустить после 3 последовательных неудач

readinessProbe:
  httpGet:
    path: /health/ready
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 5
  failureThreshold: 2         # убрать из load balancer после 2 неудач
```

### Senior-нюанс #2 — антипаттерны health check

```ts
// ❌ Антипаттерн 1: health check, который может вызвать каскадный сбой
// Если у сервиса 50 подов, и каждый /health делает запрос к БД,
// это 50 запросов/минуту только для health checks.
// Под высокой нагрузкой это может перегрузить БД.
app.get('/health', async (req, res) => {
  await db.query('SELECT COUNT(*) FROM users');   // полное сканирование таблицы — плохо!
  res.json({ status: 'ok' });
});

// ✅ Используйте дешёвый, целевой запрос
app.get('/health/ready', async (req, res) => {
  await db.query('SELECT 1');   // просто проверяет соединение, не данные
  res.json({ status: 'ok' });
});

// ❌ Антипаттерн 2: liveness check, проверяющий внешние зависимости
// Если БД недоступна, падающий liveness probe перезапустит все поды.
// Но перезапуск подов не починит базу — вы получите бесконечный цикл перезапусков.
// Liveness должна проверять ТОЛЬКО то, что ЭТОТ ПРОЦЕСС жив.
app.get('/health/live', async (req, res) => {
  await db.query('SELECT 1');   // ← неправильно для liveness
  res.json({ status: 'ok' });
});
```

## SLA, SLO, SLI — терминология уровней сервиса

Три аббревиатуры описывают, как определяются, измеряются и согласовываются обязательства по надёжности. SLI — service level indicator, SLO — service level objective, SLA — service level agreement. Это разные уровни:

| Аббревиатура | Что это |
|---|---|
| SLI | Что вы измеряете |
| SLO | Чему вы обязуетесь внутри компании |
| SLA | Что вы обещаете клиентам — с последствиями при нарушении |

### SLI — Service Level Indicator (Индикатор уровня сервиса)

**SLI** — конкретная, измеримая метрика, отражающая то, насколько хорошо сервис работает для пользователей. Это сырое измерение.

Примеры:

- **Доступность** — успешные запросы, делённые на все запросы, в процентах.
- **Задержка** — доля запросов, завершающихся быстрее 200мс.
- **Частота ошибок** — доля запросов, возвращающих статус 5xx.
- **Пропускная способность** — количество транзакций в секунду.

### SLO — Service Level Objective (Цель уровня сервиса)

**SLO** — внутренний целевой показатель для SLI — порог, ниже которого вы считаете, что сервис не соответствует требованиям пользователей. Это цель, а не обещание клиентам.

Примеры:

- Доступность не ниже 99.9% в скользящем 30-дневном окне.
- Задержка p99 не выше 500мс для всех эндпоинтов API.
- Частота ошибок ниже 0.1% в любом 5-минутном окне.

**Error budget** (бюджет ошибок) — идея, которая делает SLO применимым на практике. Это то количество ненадёжности, которое вы можете себе позволить до нарушения SLO.

```txt
SLO: доступность 99.9% в течение 30 дней
  30 дней               = 43,200 минут
  0.1% от 43,200 минут  = 43.2 минуты простоя в месяц

Error budget = 43.2 минуты в месяц
```

Допустим, 40 минут в этом месяце вы уже израсходовали. Остаётся 3.2 минуты, поэтому рискованные деплои замораживаются до начала нового месяца, а инженерные силы уходят на надёжность. Если бюджет стабильно не расходуется, можно двигаться быстрее: деплоить чаще, брать больше рисков.

Идея error budget пришла из книги Google SRE. Она устраняет разрыв между продуктовыми командами, которые хотят двигаться быстро, и ops-командами, которые хотят стабильности. Она измеряет допустимый риск в единицах, понятных всем.

### SLA — Service Level Agreement (Соглашение об уровне сервиса)

**SLA** — контрактное обязательство между поставщиком сервиса и клиентом. Оно определяет ожидаемый уровень сервиса и последствия, если этот уровень не достигнут: кредиты, возврат средств, право расторгнуть договор.

Примеры:

- **AWS S3 (Simple Storage Service)** — 99.9% ежемесячного uptime. Ниже 99% — 10% сервисного кредита, ниже 95% — 25%.
- **Stripe** — 99.99% uptime API. Простои компенсируются сервисными кредитами, а не деньгами. Читайте мелкий шрифт.
- **Типичный enterprise-контракт SaaS** — 99.9% uptime. Ниже — пропорциональный возврат; ниже 95% клиент может расторгнуть договор.

Отношения между тремя понятиями:

```txt
SLI (измерение) → SLO (внутренняя цель) → SLA (внешнее обещание)
```

SLO **строже**, чем SLA. Если SLA обещает 99.9%, внутренний SLO может быть 99.95%. Разрыв между ними — ваш запас безопасности: сползая к SLO, вы замечаете это и чинитесь до нарушения SLA и его финансовых последствий.

**"Девятки" доступности** — распространённое сокращение:

| Сокращение | Доступность | Простой в год |
|---|---|---|
| Две девятки | 99% | 3.65 дня (87.6 часа) |
| Три девятки | 99.9% | 8.76 часа |
| Четыре девятки | 99.99% | 52.6 минуты |
| Пять девяток | 99.999% | 5.26 минуты |

Пять девяток крайне сложно достичь даже крупнейшим компаниям. Большинство SaaS-продуктов целятся в три или четыре девятки. Четыре девятки обычно требуют мультирегиональной избыточности, деплоев без простоя, автоматического failover и подробных runbook-инструкций.

## Всё вместе: практическая настройка observability

Для Node.js + PostgreSQL приложения, развёрнутого на AWS:

- **Логи.** Приложение пишет структурированный JSON в stdout; оттуда он идёт в CloudWatch Logs, Datadog или Loki. Хранение: 30 дней для INFO, 90 дней для ERROR. Алерт в PagerDuty, если ERROR-логов больше 10 за 5 минут.
- **Метрики.** Библиотека Prometheus client отдаёт эндпоинт `/metrics`; Prometheus опрашивает его каждые 15 секунд. Дашборды Grafana показывают запросы в секунду, задержку p95 и p99, частоту ошибок и размер пула базы. Алерт в Slack, когда p99 больше 1с в течение 5 минут; в PagerDuty, когда ошибок больше 1% в течение 2 минут.
- **Трейсы.** OpenTelemetry SDK экспортирует в Jaeger, Tempo или Datadog APM. Частота выборки: 100% на staging, 10% на prod; полная выборка дорога. Трейсы нужны, чтобы отлаживать медленные запросы и понимать межсервисные зависимости.
- **Uptime-мониторинг.** UptimeRobot или Checkly пингуют `/health/live` каждые 60 секунд из 3 регионов. Алерт текстовым сообщением и в Slack после 2 неудач подряд.
- **Health check.** Kubernetes liveness на `/health/live` — только отзывчивость процесса. Kubernetes readiness на `/health/ready` — проверка соединения с базой и Redis.

## Типичные ошибки на интервью

- **"Мониторинг и observability — одно и то же"** — мониторинг это практика наблюдения за заранее определёнными метриками. Observability — свойство системы, позволяющее обнаружить неизвестные режимы отказа. Систему можно плотно обвесить мониторингом и всё равно плохо её наблюдать.

- **"Мы всё логируем через console.log"** — сигнал незнакомства с production-логированием. Проблемы: `console.log` синхронный и кратко блокирует event loop. Он выдаёт неструктурированные строки. Его нельзя фильтровать по уровню. В нём нет метаданных — ни имени сервиса, ни request ID, ни user ID. Используйте структурированный логгер: winston, pino.

- **Не знать разницу между liveness и readiness пробами** — очень распространённый вопрос на собеседованиях. Путаница обходится дорого. Liveness probe, проверяющая внешние зависимости, перезапустит все поды, когда упадёт база. Readiness probe просто вывела бы эти поды из-под балансировщика.

- **"Наш SLA — 99.99%"** — интервьюеры спросят: "Каков ваш error budget? Как вы его отслеживаете?" Если не можете ответить, это сигнал, что вы реально не работаете на таком уровне. Знайте, сколько минут допустимого простоя соответствует вашему SLA.

- **Путать SLI, SLO и SLA** — очень распространённая путаница на собеседованиях, особенно на senior/staff позиции. Запомните: SLI = измерение, SLO = внутренняя цель, SLA = контракт с клиентом. SLO строже SLA для создания буфера безопасности.

- **"Мы используем среднюю задержку как метрику"** — среднее маскирует выбросы. Задержка p99 в 3 секунды означает, что 1% пользователей ждёт 3 секунды. Среднее при этом может выглядеть как 200мс, потому что 99% запросов быстрые. Всегда смотрите перцентили.

- **"У нас есть /health эндпоинт, который просто возвращает 200"** — нормально для uptime-мониторинга, но недостаточно для Kubernetes liveness/readiness. Процесс может возвращать 200, находясь в деградированном состоянии (БД недоступна, но возвращаются кэшированные данные). Readiness probe должна реально проверять доступность зависимостей.
