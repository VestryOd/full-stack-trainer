# Глоссарий CI/CD и DevOps

Все аббревиатуры и термины, с которыми фуллстек-разработчик столкнётся на собеседованиях, в описаниях вакансий и в повседневной работе. CI (Continuous Integration) — непрерывная интеграция, слияние кода в общую ветку по нескольку раз в день. CD (Continuous Delivery или Continuous Deployment) — непрерывная доставка или непрерывный деплой. DevOps (Development + Operations) — разработка и эксплуатация одним процессом.

Записи упорядочены по алфавиту латинских терминов: в индустрии они используются именно так. У термина, которому посвящена отдельная статья, здесь короткое определение и ссылка.

---

## A

**Agent (Агент)**

Другое название для **runner** — машина, на которой выполняются задания (jobs) CI/CD-пайплайна. Термин «agent» используется в Jenkins, Azure Pipelines и других инструментах; «runner» — в GitHub Actions и GitLab CI.

См.: *Runner*.

**ALB — Application Load Balancer (Балансировщик нагрузки приложения)**

Управляемый балансировщик нагрузки AWS (Amazon Web Services). Работает на прикладном уровне — седьмом уровне модели взаимодействия открытых систем (OSI). Поэтому он видит трафик HTTP и HTTPS (HTTP Secure), а не только пакеты.

Классический балансировщик маршрутизирует только по сетевому адресу (IP) и порту. ALB умеет по пути URL, имени хоста, заголовкам и параметрам запроса. Отсюда его роль в blue-green и canary-деплоях: он переключает трафик между окружениями.

**APM — Application Performance Monitoring (Мониторинг производительности приложений)**

Категория инструментов, объединяющих распределённые трейсы, метрики и логи в единый интерфейс с фокусом на производительности приложения. APM-инструменты автоматически инструментируют ваш код, отслеживают каждый запрос, выявляют медленные участки кода и группируют ошибки. Примеры: Datadog APM, New Relic, Sentry, Elastic APM.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Artifact (Артефакт)**

Любой файл или набор файлов, созданный на этапе сборки и сохранённый для следующего этапа или для деплоя. Примеры: скомпилированный JavaScript-бандл, Docker-образ, `.zip`-архив с кодом Lambda-функции, отчёт о покрытии тестами.

Ключевой принцип: соберите артефакт один раз и деплойте один и тот же артефакт во все окружения — и в staging, и в production. Пересобирать из исходного кода под каждое окружение нельзя.

См.: [Основы CI/CD](./01-cicd-fundamentals.md).

**Artifact Registry (Реестр артефактов)** (также: **Container Registry** применительно к Docker-образам)

Сервис хранения, где собранные артефакты загружаются, версионируются и откуда их скачивают во время деплоя. Для Docker-образов: GitHub Container Registry (ghcr.io), Docker Hub, AWS ECR (Elastic Container Registry), Google Artifact Registry. Реестр — это не то же самое, что система контроля версий (git): он хранит скомпилированный/упакованный результат, а не исходный код.

## B

**Base Image (Базовый образ)**

Отправная точка для Docker-образа, указываемая в инструкции `FROM` в Dockerfile. Каждый образ строится поверх базового. Распространённые примеры: `node:20-alpine` (Node.js на Alpine Linux), `python:3.12-slim`, `ubuntu:22.04`. `FROM scratch` начинает с полностью пустого образа — для минимальных однобинарных приложений.

**Blast Radius (Зона поражения)**

Масштаб последствий при неудачном деплое. Стратегии деплоя вроде canary-релизов и feature flags нужны ровно для того, чтобы этот масштаб оставался небольшим.

Если в новой версии есть баг, его увидит лишь малая доля пользователей. Проблему обнаружат и откатят раньше, чем она дойдёт до остальных. «Минимизация blast radius» — стандартная фраза в инженерии надёжности.

**Blue-Green Deployment (Сине-зелёный деплой)**

Стратегия деплоя, при которой поддерживаются два идентичных production-окружения — «синее» и «зелёное». Новую версию разворачивают в простаивающем окружении, тестируют, а затем мгновенно переключают на него трафик через балансировщик нагрузки.

Старое окружение продолжает работать, и это даёт быстрый откат. В отличие от rolling, периода одновременной работы двух версий нет — зато инфраструктура стоит вдвое дороже.

См.: [Стратегии деплоя](./05-deployment-strategies.md).

**Build Context (Контекст сборки)** (Docker)

Набор файлов, передаваемых Docker-демону при выполнении `docker build` — обычно содержимое текущей директории. Файлы, перечисленные в `.dockerignore`, исключаются из контекста сборки. Большой контекст сборки (например, включающий `node_modules/`) замедляет сборку, потому что все эти файлы передаются демону перед выполнением первой инструкции Dockerfile.

## C

**Canary Release (Канареечный релиз)**

Назван по аналогии с канарейкой в угольной шахте. Стратегия деплоя, при которой малая доля реального пользовательского трафика — скажем, 5% — уходит на новую версию, а все остальные остаются на стабильной.

За новой версией следят: ошибки, просадки производительности. Если всё в порядке, её доля трафика растёт шаг за шагом. В отличие от feature flag, canary — это разделение трафика на уровне инфраструктуры, между двумя задеплоенными версиями.

См.: [Стратегии деплоя](./05-deployment-strategies.md).

**CDK — Cloud Development Kit (Набор инструментов разработки облака)**

Инструмент «инфраструктура как код» (IaC) от AWS. Инфраструктуру описывают на TypeScript, Python, Java или другом настоящем языке, а не шаблонами в JSON или YAML (человекочитаемый формат конфигурации). CDK-код компилируется в шаблоны CloudFormation: вы пишете код приложения, а на выходе получаете конфигурацию.

См.: *IaC*, *CloudFormation*.

**cgroups — Control Groups (Контрольные группы)**

Возможность ядра Linux, которая ограничивает группе процессов доступ к ресурсам: процессорному времени (CPU), памяти, дисковому вводу-выводу, пропускной способности сети.

Вместе с namespaces cgroups — технология, на которой работают Docker-контейнеры. Потребление ресурсов каждого контейнера ограничено его cgroup, поэтому один контейнер не может «уморить голодом» соседей на том же хосте.

**CI — Continuous Integration (Непрерывная интеграция)**

Практика частого слияния изменений кода в общую основную ветку (несколько раз в день), при этом каждое слияние автоматически запускает пайплайн, который собирает и тестирует код. Цель: обнаруживать проблемы интеграции через минуты после их появления, а не через дни. CI — фундамент, на котором строится CD.

См.: [Основы CI/CD](./01-cicd-fundamentals.md).

**CD — Continuous Delivery / Continuous Deployment (Непрерывная доставка / Непрерывный деплой)**

Два разных понятия за одной аббревиатурой.

- **Continuous Delivery (непрерывная доставка)** — каждая успешная сборка упаковывается в готовый к деплою артефакт и автоматически уезжает на staging. Деплой в production по-прежнему требует ручного подтверждения.
- **Continuous Deployment (непрерывный деплой)** — ручного подтверждения нет, каждая успешная сборка автоматически уезжает в production.

Разница — в одном слове и одном человеческом клике.

См.: [Основы CI/CD](./01-cicd-fundamentals.md).

**CloudFormation**

Нативный сервис «инфраструктура как код» от AWS. Вы описываете ресурсы в шаблонах JSON или YAML, а CloudFormation создаёт их и дальше ими управляет:

- EC2 (Elastic Compute Cloud) — виртуальные машины.
- S3 (Simple Storage Service) — бакеты объектного хранилища.
- RDS (Relational Database Service) — управляемые базы данных.
- Балансировщики нагрузки, сети, очереди и остальной AWS.

Зрелый сервис, глубоко интегрированный с AWS, но многословный. Многие команды предпочитают CDK, который компилируется в CloudFormation.

**Composite Action (Составное действие)** (GitHub Actions)

Повторно используемая группа шагов, упакованная в один вызов `uses:`, встраиваемый в job. Composite actions хранятся как файлы `action.yml` (обычно в `.github/actions/`). В отличие от reusable workflows — это полноценные jobs — composite action запускается как часть job наряду с другими шагами. Используется для абстрагирования последовательности шагов установки/сборки.

См.: [GitHub Actions](./02-github-actions.md).

**Configuration Drift (Дрейф конфигурации)**

Постепенное расхождение окружений — staging против production — из-за ручных изменений, внесённых в одно, но не в другое. Кто-то правит production «просто на этот раз» и никогда не переносит правку в staging.

Дрейф — главная причина «работает на staging, сломано в production». Infrastructure as Code предотвращает его, делая код единственным источником истины о том, что существует.

См.: *IaC*.

**Configuration Management (управление конфигурацией)**

Текущее обслуживание уже существующих серверов: установка пакетов, правка конфигурационных файлов, запуск сервисов, поддержание одинакового состояния на всех машинах. Инструменты: Ansible, Chef, Puppet, SaltStack.

В отличие от *Provisioning*, который эти машины создаёт.

**Container (Контейнер)**

Запущенный экземпляр Docker-образа: сам образ плюс перезаписываемый слой поверх него, работающий как изолированный процесс на хосте. Контейнеры разделяют ядро операционной системы (ОС) хоста — в отличие от виртуальных машин, у которых ядро своё. Запускаются и останавливаются за миллисекунды, а живут недолго: контейнер эфемерен, его в любой момент заменяют новым.

См.: [Основы Docker](./04-docker-essentials.md).

**Container Registry (Реестр контейнеров)**

См.: *Artifact Registry*.

**CRD — Custom Resource Definition (Определение пользовательского ресурса)** (Kubernetes)

Механизм расширения в Kubernetes, позволяющий добавлять собственные типы ресурсов в API Kubernetes. Инструменты вроде Argo Rollouts и Cert-Manager работают, устанавливая CRD в кластер и предоставляя контроллеры, которые реагируют на эти пользовательские ресурсы. Когда вы видите `apiVersion: argoproj.io/v1alpha1` в YAML-файле, это ресурс, созданный через CRD.

## D

**DAG — Directed Acyclic Graph (Направленный ациклический граф)**

Граф, все рёбра которого — связи между узлами — направлены в одну сторону, и циклов в нём нет. Ни один путь не возвращается к начальной точке.

В CI/CD такой граф описывает зависимости между заданиями пайплайна. Задание B зависит от задания A — это направленность. Никакая цепочка зависимостей не замыкается на себя — это ацикличность. Ключевое слово `needs:` в GitLab CI и GitHub Actions строит пайплайны именно такой формы.

См.: [GitLab CI](./03-gitlab-ci.md).

**dind — Docker-in-Docker**

Конфигурация, при которой Docker-демон запускается внутри Docker-контейнера. Так команды `docker build` и `docker push` можно выполнять внутри CI-задания, которое само работает в контейнере.

Нужна в GitLab CI, если вы используете Docker executor и собираете образы. Объявляется как сервис: `services: - docker:24-dind`. У неё есть цена по безопасности: контейнеру требуется привилегированный режим.

См.: [GitLab CI](./03-gitlab-ci.md).

**DNS — Domain Name System (Система доменных имён)**

Телефонная книга интернета: распределённая база данных, которая переводит человекочитаемые доменные имена вроде `api.myapp.com` в сетевые адреса.

Для DevOps это важно при переключении трафика. Переключение через DNS в blue-green деплое расходится по сети не быстрее, чем позволяет TTL (Time To Live), — от минут до часов. Для мгновенного отката это не годится, поэтому предпочитают переключение через балансировщик нагрузки.

**Dockerfile**

Текстовый файл, содержащий последовательность инструкций, которые Docker выполняет для создания образа. Каждая инструкция (`FROM`, `RUN`, `COPY`, `CMD` и т.д.) создаёт слой в образе. Dockerfile хранится в репозитории и служит воспроизводимым рецептом сборки контейнерного образа приложения.

См.: [Основы Docker](./04-docker-essentials.md).

**Dotenv (файл `.env`)**

Обычный текстовый файл в корне проекта, который хранит переменные окружения в формате `КЛЮЧ=ЗНАЧЕНИЕ`, по одной на строку. Загружается при старте приложения библиотекой `dotenv` (`import 'dotenv/config'`).

Он предназначен только для локальной разработки и в систему контроля версий не коммитится. Вместо него коммитят `.env.example` — с именами переменных, но без реальных значений, как шаблон для других разработчиков.

См.: [Окружения и конфигурация](./06-environments-and-config.md).

## E

**ECR — Elastic Container Registry**

Управляемый реестр Docker-контейнеров от AWS. Вы загружаете Docker-образы в ECR и скачиваете их при деплоях в ECS (Elastic Container Service), Lambda и другие сервисы AWS. Образы тегируются — например, хешем коммита — и версионируются. По умолчанию приватный: доступ управляется политиками AWS IAM (Identity and Access Management).

**ECS — Elastic Container Service**

Управляемый сервис оркестрации контейнеров от AWS. Вы описываете две вещи:

- **task definition** — какой Docker-образ запускать, сколько процессорного времени и памяти выделить, какие переменные окружения передать;
- **service** — сколько копий запускать и к какому балансировщику нагрузки их подключить.

Дальше ECS сам запускает, останавливает и проверяет работоспособность контейнеров. Альтернатива Kubernetes: проще в эксплуатации, но менее гибкая.

**ELK Stack — Elasticsearch + Logstash + Kibana**

Популярный стек управления логами с открытым исходным кодом, названный по трём своим частям:

- **Elasticsearch** — распределённый поисковый и аналитический движок, который хранит и индексирует данные логов;
- **Logstash** — пайплайн: принимает логи из многих источников, преобразует их и пересылает в Elasticsearch;
- **Kibana** — веб-интерфейс для запросов и визуализации данных в Elasticsearch.

Часто дополняется **Beats** (легковесные агенты сбора логов) и тогда называется **Elastic Stack**.

**Error Budget (Бюджет ошибок)**

Допустимый объём ненадёжности (простоев, ошибок, нарушений задержек), разрешённый до нарушения SLO — выраженный в единицах времени или в количестве событий. Формула: `error budget = 1 − целевой SLO`. Пример: SLO доступности 99,9% → бюджет ошибок 0,1% → 43,2 минуты допустимого простоя за 30 дней. Когда бюджет ошибок почти исчерпан, команды замораживают рискованные изменения; когда его много — могут двигаться быстрее.

См.: *SLO*, [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Exec Form (exec-форма)** (Docker)

Способ записать `CMD` и `ENTRYPOINT` через JSON-массив: `CMD ["node", "server.js"]`. Docker запускает бинарник напрямую, поэтому идентификатор процесса (PID) вашего приложения равен 1 и оно получает `SIGTERM`.

В shell-форме — `CMD node server.js` — идентификатор 1 достаётся `sh`, и сигнал до приложения не доходит.

См.: *PID 1*, *SIGTERM*, [Основы Docker](./04-docker-essentials.md).

**Expand-Contract Migration (Миграция «расширить — сжать»)** (также: паттерн параллельного изменения)

Безопасная стратегия миграции базы данных для деплоя без простоев. Вместо одного деплоя с ломающим изменением схемы изменение растягивают на четыре деплоя:

- **Expand (расширение)** — добавляем новую колонку как nullable, старый код продолжает работать;
- **Migrate (миграция)** — заполняем данные в фоновом режиме;
- **Contract (сжатие)** — делаем колонку `NOT NULL`, когда значение есть у всех строк;
- **Cleanup (очистка)** — удаляем старую колонку, когда старый код исчез.

Смысл в том, что старая и новая версии приложения могут работать одновременно с одной базой данных.

См.: [Стратегии деплоя](./05-deployment-strategies.md).

## F

**Feature Flag** (также: Feature Toggle, Feature Switch — переключатель функциональности)

Механизм в коде приложения, который включает и отключает функцию во время работы, без деплоя нового кода. Код функции уже задеплоен, но закрыт условной проверкой вида `if (flagClient.variation('new-checkout', user, false))`.

Что это даёт:

- постепенный выкат по проценту пользователей;
- мгновенное отключение без повторного деплоя;
- A/B-тестирование;
- деплой незавершённой функции в production под флагом.

Feature flag — не стратегия деплоя, а приём внутри кода приложения.

См.: [Стратегии деплоя](./05-deployment-strategies.md).

## G

**GDPR — General Data Protection Regulation (Общий регламент по защите данных)**

Регламент Европейского союза, регулирующий сбор, хранение, обработку и передачу персональных данных жителей ЕС. Актуально для DevOps: логирование PII (Personally Identifiable Information — персональные данные), таких как адреса электронной почты, телефонные номера или IP-адреса, может нарушать GDPR. В логах следует хранить идентификаторы пользователей (псевдонимизированные), а не «сырые» персональные данные.

**GitOps** (Git + эксплуатация)

Практика, при которой желаемое состояние инфраструктуры и деплоев описано в Git. Автоматика непрерывно приводит фактическое состояние в соответствие с тем, что записано в Git.

Изменения инфраструктуры вносят через пул-реквесты — их рецензируют, тестируют, мержат, — а не прямыми командами. Инструменты: Argo CD, Flux. Девиз: «если этого нет в Git — этого не существует».

**Graceful Shutdown (Плавное завершение)**

Процесс, при котором приложение корректно обрабатывает сигнал завершения (`SIGTERM`) перед выходом. По порядку оно:

- прекращает принимать новые соединения;
- дорабатывает запросы, которые уже в обработке;
- закрывает соединения с базой данных;
- завершается с кодом 0.

Без graceful shutdown при каждом деплое теряются запросы, которые были в работе. Для деплоя без простоев это обязательный шаг.

См.: [Стратегии деплоя](./05-deployment-strategies.md), *SIGTERM*.

## H

**HCL — HashiCorp Configuration Language**

Предметно-ориентированный язык, используемый в Terraform и других инструментах HashiCorp для определения инфраструктуры. HCL — декларативный язык: вы описываете желаемое конечное состояние, а Terraform сам определяет, как его достичь. Человекочитаемый, поддерживает выражения, переменные, циклы и модули. Альтернатива написанию CloudFormation YAML или CDK-кода на TypeScript.

**Health Check (Проверка работоспособности)**

Периодический тест, который определяет, жив ли сервис и готов ли он принимать трафик. В Kubernetes таких проверок две:

- **liveness probe** проверяет, жив ли процесс. Неудача — контейнер перезапускают;
- **readiness probe** проверяет, готов ли сервис к трафику. Неудача — его убирают из пула балансировщика, но не перезапускают.

В Docker Compose такую команду задаёт ключ `healthcheck`; `depends_on: condition: service_healthy` её дожидается.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Hosted Runner (Управляемый раннер)**

Раннер, который предоставляет и обслуживает сама CI-платформа: GitHub, GitLab и прочие. На каждый запуск пайплайна выделяется свежая виртуальная машина с предустановленными инструментами, обслуживать её вам не нужно.

Чем за это платят:

- поминутной оплатой процессорного времени;
- общим железом с другими пользователями платформы;
- отсутствием доступа к вашей приватной сети.

В отличие от *Self-Hosted Runner*.

## I

**IaC — Infrastructure as Code (Инфраструктура как код)**

Практика описания инфраструктуры кодом в файлах, которые лежат в системе контроля версий, — вместо кликов по веб-консоли и ручных команд. Инфраструктура здесь — это серверы, сети, базы данных, балансировщики нагрузки.

Что это даёт: воспроизводимость, историю изменений с возможностью аудита, паритет окружений, восстановление после катастроф и ревью изменений инфраструктуры через пул-реквесты (PR). Инструменты: Terraform, AWS CDK, CloudFormation, Pulumi, Ansible.

См.: [Окружения и конфигурация](./06-environments-and-config.md).

**Image** (Docker Image — Образ Docker)

Доступный только для чтения слоёный снимок файловой системы. В нём есть всё, что нужно приложению для запуска:

- базовая операционная система;
- среда выполнения — Node.js, Python и так далее;
- зависимости;
- скомпилированный код и конфигурационные файлы.

Образ строится из Dockerfile. Из одного образа можно одновременно запустить много контейнеров. Образ — единица деплоя: собирают его один раз, дальше продвигают по окружениям.

См.: *Container*, [Основы Docker](./04-docker-essentials.md).

**Immutable Infrastructure (Неизменяемая инфраструктура)**

Практика, при которой серверы и контейнеры после деплоя не изменяют. Вместо правки собирают новый образ, разворачивают его, а старый заменяют.

Чтобы обновить приложение, вы собираете новый Docker-образ и заменяете запущенные контейнеры. Вы не заходите в контейнер по SSH (Secure Shell), чтобы поправить файлы руками. Именно это делает деплои воспроизводимыми и не даёт configuration drift накапливаться на работающих инстансах.

## J

**Job (Задание)** (CI/CD)

Единица работы в пайплайне, выполняемая на одной машине раннера/агента. Job состоит из последовательности шагов (команд). Задания в одном stage пайплайна по умолчанию выполняются параллельно (в GitLab CI) или при наличии зависимостей `needs:` (в GitHub Actions). Job создаёт артефакты и сообщает результат (успех/неудача).

См.: *Stage*, *Step*, [Основы CI/CD](./01-cicd-fundamentals.md).

---

## K

**K8s — Kubernetes**

Платформа оркестрации контейнеров с открытым исходным кодом, изначально разработанная в Google. Название — нумероним: K, потом 8 букв, потом s. Kubernetes автоматизирует деплой, масштабирование и управление контейнеризированными приложениями в кластере машин.

Ключевые понятия:

- **pod** — группа контейнеров, которые планируются вместе;
- **deployment** — объявление желаемого состояния;
- **service** — постоянная сетевая точка входа;
- **ingress** — маршрутизация трафика извне;
- **namespace** — изоляция ресурсов внутри кластера.

Де-факто стандарт для запуска контейнеров на больших объёмах.

## L

**Layer (Слой)** (Docker)

Отдельное инкрементальное изменение файловой системы Docker-образа, которое создаёт одна инструкция Dockerfile (`FROM`, `RUN`, `COPY`, `ADD`). Слои складываются стопкой, и каждый записывает только разницу с тем, что под ним.

Слои кешируются. Если инструкция и её входные данные не изменились с прошлой сборки, Docker берёт слой из кеша. Порядок инструкций от наименее изменяемых к наиболее изменяемым даёт больше попаданий в кеш и ускоряет сборку.

См.: [Основы Docker](./04-docker-essentials.md).

**Liveness Probe (Проба живости)**

Проверка работоспособности в Kubernetes, определяющая, жив ли процесс контейнера и должен ли он продолжать работу. При неудаче liveness probe Kubernetes перезапускает контейнер. Liveness probe должна проверять только то, отвечает ли сам процесс — а не доступны ли внешние зависимости (база данных, кеш). Если она проверяет внешние зависимости, отказ базы данных приведёт к перезапуску всех pod в бесконечном цикле.

См.: *Readiness Probe*, [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Loki** (Grafana Loki)

Горизонтально масштабируемая система агрегации логов от Grafana Labs, сделанная по образцу Prometheus. В отличие от Elasticsearch, Loki не индексирует содержимое логов целиком — только их метки (labels), метаданные каждого потока. Поэтому на больших объёмах он заметно дешевле в эксплуатации.

Запросы к Loki пишут на LogQL (язык запросов, похожий на PromQL), а результат смотрят в дашбордах Grafana. Вместе с Prometheus (метрики) и Tempo (трейсы) он даёт полный стек наблюдаемости с открытым исходным кодом.

## M

**Metrics (Метрики)**

Числовые измерения свойств системы, снимаемые во времени и агрегируемые. Логи — это дискретные события, а метрики показывают «сколько» и «как быстро»: частоту запросов, частоту ошибок, загрузку процессора, перцентили задержек.

Четыре золотых сигнала из книги Google по инженерии надёжности сервисов (SRE): Latency (задержка), Traffic (трафик), Errors (ошибки), Saturation (насыщенность). Стандартные типы метрик: Counter (только растёт), Gauge (растёт и падает), Histogram (корзины). Инструмент: Prometheus.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Monitoring (мониторинг)**

Наблюдение за набором сигналов, выбранных заранее, и оповещение, когда один из них выходит за порог. Частота ошибок выше 1%, задержка выше 500 мс, диск заполнен больше чем на 90%.

Мониторинг отвечает на вопросы, которые вы догадались задать. *Observability* — свойство шире: ответы на те, которых вы не предвидели.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Multi-Stage Build (Многоэтапная сборка)** (Docker)

Техника Dockerfile: несколько инструкций `FROM`, каждая из которых начинает новый этап сборки. Файлы копируют с этапа на этап через `COPY --from=имя-этапа`, и в финальный образ попадает только то, что доехало до последнего этапа.

Инструменты сборки, dev-зависимости и исходники остаются позади. Размер production-образа от этого сильно падает: со всем инструментарием — около 400 МБ (мегабайт), только со средой выполнения и скомпилированным кодом — около 80 МБ.

См.: [Основы Docker](./04-docker-essentials.md).

---

## N

**Namespace (Пространство имён)** (Kubernetes)

Механизм изоляции групп ресурсов внутри одного кластера Kubernetes. Ресурсы (pod, service, deployment) в одном namespace изолированы от ресурсов в другом. Обычно используется для разделения окружений (dev, staging, prod) внутри одного кластера или для разделения команд/приложений. Стандартные пространства имён: `default`, `kube-system` (компоненты кластера), `kube-public`.

**Non-Root User (Непривилегированный пользователь)** (Docker)

Практика безопасности: запускать процессы контейнера от непривилегированного пользователя, а не от root с идентификатором 0. По умолчанию контейнеры Docker работают от root, и злоумышленник, выбравшийся из контейнера, получает права root на хосте.

Строка `USER node` в Dockerfile — или любой другой непривилегированный пользователь — снижает этот риск. В базовых образах `node:*` уже есть встроенный пользователь `node` с идентификатором 1000 ровно для этого.

См.: [Основы Docker](./04-docker-essentials.md).

---

## O

**Observability (Наблюдаемость)**

Свойство системы, которое позволяет понять её внутреннее состояние по тому, что она выдаёт наружу: по логам, метрикам и трейсам. Система наблюдаема, если по этим данным можно разобрать любой сценарий отказа — включая тот, которого никто не предвидел.

Три столпа наблюдаемости — логирование, метрики и распределённая трассировка. *Monitoring* следит за сигналами, которые вы определили заранее; наблюдаемость — это способность найти отказ, которого вы не ждали.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**OpenTelemetry (OTel)**

Независимый от вендоров стандарт с открытым исходным кодом и комплект разработки (SDK) для инструментирования приложений. Собирает три вида телеметрии: трейсы, метрики и логи.

OpenTelemetry заменяет собой агенты отдельных вендоров. Код инструментируют один раз, а данные экспортируют в любой совместимый бэкенд — Jaeger, Datadog, Honeycomb, Grafana Tempo. Проектом управляет CNCF (Cloud Native Computing Foundation), и сегодня это отраслевой стандарт инструментирования наблюдаемости.

**Orchestration (Оркестрация контейнеров)**

Автоматизированное управление контейнеризированными приложениями в кластере машин. Оркестратор:

- размещает контейнеры на узлах;
- перезапускает неработоспособные контейнеры;
- масштабирует число реплик под нагрузку;
- управляет сетевой маршрутизацией между сервисами;
- выкатывает новые версии.

Kubernetes — доминирующая платформа оркестрации. AWS ECS и HashiCorp Nomad — альтернативы.

## P

**PCI DSS — Payment Card Industry Data Security Standard (Стандарт безопасности данных индустрии платёжных карт)**

Стандарт безопасности для организаций, которые обрабатывают данные кредитных карт. Для логирования он значит одно: номера карт, коды проверки подлинности карты (CVV) и полные имена держателей никогда не должны попадать в логи и храниться незашифрованными.

Нарушения приводят к штрафам и к потере права обрабатывать карточные платежи. Если приложение принимает платежи, PCI DSS определяет, что вы можете логировать, как хранить данные и как управлять секретами.

**PII — Personally Identifiable Information (Персональные данные)**

Любые данные, по которым можно опознать конкретного человека: имя, адрес электронной почты, номер телефона, домашний адрес, идентификационный номер. В некоторых юрисдикциях сюда же относится IP-адрес.

Законы, которые регулируют обращение с ними в логах, базах данных и аналитических пайплайнах:

- GDPR — регламент по защите данных Европейского союза;
- HIPAA — закон о приватности медицинских данных в Соединённых Штатах;
- CCPA — закон Калифорнии о приватности потребителей.

В логах храните псевдонимизированные идентификаторы пользователей, а не «сырые» адреса почты или имена.

**PID 1 — Process ID 1 (Идентификатор процесса 1)**

В Linux у каждого процесса есть PID (идентификатор процесса). PID 1 — это init-процесс, первый процесс, который запускает ядро. Он отвечает за запуск всех остальных процессов и за уборку зомби: дочерних процессов, которые завершились, но остались в таблице процессов.

В Docker-контейнере PID 1 — главный процесс. Если задать `CMD` в shell-форме (`CMD node server.js`), то PID 1 станет `sh`, а Node.js будет его дочерним процессом. Такой `sh` не пересылает `SIGTERM` детям и не убирает зомби.

Всегда используйте exec-форму (`CMD ["node", "server.js"]`), чтобы PID 1 было именно ваше приложение.

См.: *Exec Form*, *SIGTERM*, [Основы Docker](./04-docker-essentials.md).

**Pipeline (Пайплайн)**

Последовательность автоматизированных шагов — заданий, — которые выполняются в заданном порядке, когда срабатывает триггер. Триггером бывает push кода, пул-реквест, расписание или ручной запуск.

Пайплайн описывают кодом, обычно в YAML, и хранят в репозитории рядом с кодом приложения. Его же называют «CI/CD-пайплайн», «build pipeline» или «workflow» в GitHub Actions.

См.: *Pipeline as Code*, [Основы CI/CD](./01-cicd-fundamentals.md).

**Pipeline as Code (Пайплайн как код)**

Практика, при которой CI/CD-пайплайны описывают в конфигурационных файлах (YAML), лежащих в репозитории исходного кода и версионируемых вместе с ним.

Что это даёт:

- изменения пайплайна проходят то же ревью через пул-реквест, что и изменения кода;
- история пайплайна видна в `git log`;
- пайплайн воспроизводим в разных окружениях.

Так работают все современные CI/CD-платформы: GitHub Actions, GitLab CI, Jenkins Pipelines.

**Prometheus**

Система мониторинга с открытым исходным кодом и база данных временных рядов, созданная в SoundCloud и теперь входящая в CNCF. Prometheus сам забирает метрики (scrape): с заданным интервалом, скажем каждые 15 секунд, он опрашивает HTTP-эндпоинты вроде `/metrics`, которые открывают инструментированные приложения.

Метрики хранятся как временные ряды, а запросы к ним пишут на PromQL (Prometheus Query Language). Смотрят их обычно в дашбордах Grafana, а оповещения строят через Alertmanager.

**Provisioning (Инициализация/Подготовка инфраструктуры)**

Процесс создания и настройки ресурсов инфраструктуры до состояния готовности к работе:

- создание виртуальных машин;
- настройка сети;
- установка операционной системы и программного обеспечения;
- выделение хранилища.

Provisioning обычно выполняют один раз или по расписанию, когда ресурсы заменяют. Инструменты Infrastructure as Code — Terraform, CloudFormation — автоматизируют его. В отличие от *Configuration Management*: то текущее обслуживание уже поднятых систем, область Ansible.

## R

**Readiness Probe (Проба готовности)**

Проверка работоспособности в Kubernetes, которая определяет, готов ли контейнер принимать трафик. При её неудаче Kubernetes убирает pod из пула маршрутизации балансировщика нагрузки, но контейнер не перезапускает.

Readiness probe должна проверять доступность всех внешних зависимостей: базы данных, кеша, сервисов, от которых приложение зависит. Этим она отличается от *Liveness Probe*, которая решает, нужен ли перезапуск.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**Rolling Deployment (Скользящее обновление)**

Стратегия деплоя, при которой старые экземпляры заменяют новыми по несколько штук за раз, пока сервис продолжает работать. Каждый новый экземпляр сначала проходит проверку работоспособности, и только потом со старого снимают трафик и останавливают его.

Во время выкатки обе версии работают одновременно, поэтому миграции базы данных обязаны оставаться обратно совместимыми. Встроено в Kubernetes, ECS и большинство платформ вида «платформа как услуга» (PaaS).

См.: [Стратегии деплоя](./05-deployment-strategies.md).

**Runner (Раннер)** (также: Agent)

Машина — виртуальная или физическая — на которой фактически выполняются задания CI/CD-пайплайна. При срабатывании пайплайна планировщик CI назначает задания доступным раннерам. **Hosted runners** предоставляются CI-платформой (GitHub-hosted, GitLab.com shared). **Self-hosted runners** — машины, которыми вы владеете и управляете, зарегистрированные в CI-платформе.

См.: [Основы CI/CD](./01-cicd-fundamentals.md), [GitHub Actions](./02-github-actions.md), [GitLab CI](./03-gitlab-ci.md).

---

## S

**Secrets Manager (Менеджер секретов)**

Специализированный сервис для хранения, выдачи, аудита и ротации чувствительных учётных данных: паролей, API-ключей, сертификатов TLS (Transport Layer Security), ключей шифрования.

Он даёт шифрование хранимых данных, журнал аудита (кто и когда что запрашивал), детальный контроль доступа, автоматическую ротацию и версионирование. Примеры: AWS Secrets Manager, HashiCorp Vault, Google Cloud Secret Manager, Azure Key Vault, Doppler, Infisical. Это не менеджер паролей — тот сделан для людей.

См.: [Окружения и конфигурация](./06-environments-and-config.md).

**Self-Hosted Runner (собственный раннер)**

Раннер, которым владеете и управляете вы сами: программное обеспечение раннера установлено на вашей машине и зарегистрировано в вашей CI/CD-платформе.

Он достаёт до приватных сетей, несёт специфическое железо — графический ускоритель (GPU) или нужную архитектуру процессора, — и при больших объёмах пайплайнов обходится дешевле.

Проблема безопасности: в публичном репозитории вредоносный пул-реквест может изменить YAML воркфлоу и выполнить произвольный код на вашей машине.

См.: [GitHub Actions](./02-github-actions.md), [GitLab CI](./03-gitlab-ci.md).

**Service Mesh (Сервисная сетка)**

Выделенный инфраструктурный уровень, который берёт на себя общение сервисов между собой в микросервисной архитектуре:

- балансировку нагрузки и маршрутизацию трафика;
- mTLS — взаимное TLS-шифрование между сервисами;
- повторные попытки и размыкание цепи при отказах (circuit breaking);
- наблюдаемость.

Реализуется как sidecar-прокси, внедряемые в каждый pod. Примеры: Istio, Linkerd. Для canary-релизов это важно: service mesh делит трафик с точностью до процента, не трогая код приложения.

См.: *Sidecar*.

**Sidecar (сайдкар)**

Вспомогательный контейнер, который работает рядом с основным контейнером приложения в том же pod и делит с ним сеть, а часто и хранилище. Само приложение о нём не знает.

Типичные роли: прокси сервисной сетки, агент отправки логов, экспортёр метрик. Приём позволяет не тащить инфраструктуру в код приложения.

См.: *Service Mesh*.

**SIGTERM — Signal Terminate (Сигнал завершения)**

Сигнал Unix и Linux под номером 15. Операционная система или оркестратор отправляет его процессу, чтобы попросить того завершиться плавно.

SIGKILL (сигнал 9) убивает процесс мгновенно. SIGTERM можно перехватить, и тогда у процесса есть время прибраться: дообработать текущие запросы, закрыть соединения с базой данных и выйти. Kubernetes шлёт SIGTERM перед остановкой pod, а SIGKILL — по истечении льготного периода (grace period), по умолчанию 30 секунд.

См.: *Graceful Shutdown*, *PID 1*.

**SLA — Service Level Agreement (Соглашение об уровне сервиса)**

Договорное обязательство между поставщиком услуг и его клиентами. В нём записан ожидаемый уровень сервиса: доступность, время отклика, частота ошибок. Там же записана цена невыполнения — кредиты за сервис, возвраты, право на расторжение.

SLA — внешний, юридически обязывающий документ. Он всегда мягче внутреннего SLO, и этот зазор служит буфером безопасности. Пример: SLA AWS S3 гарантирует 99,9% доступности в месяц, а при нарушении — кредиты за сервис.

См.: *SLO*, *SLI*, [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**SLI — Service Level Indicator (Индикатор уровня сервиса)**

Конкретная измеримая метрика, которая показывает, насколько хорошо сервис работает для пользователей — само измерение. Примеры: процент запросов, завершающихся менее чем за 200 мс; процент запросов, возвращающих статус не 5xx; процент заданий, завершающихся в срок. SLI — это входные данные для SLO.

См.: *SLO*, *SLA*.

**SLO — Service Level Objective (Целевой показатель уровня сервиса)**

Внутренняя цель для SLI: порог, ниже которого команда считает, что сервис не справляется. Это не обязательство перед клиентами — им занимается SLA, — а внутренняя инженерная цель, и зазор между ними и есть буфер безопасности.

SLO вместе с error budget делает надёжность торгуемым ресурсом. Бюджета много — можно деплоить агрессивнее. Бюджет почти исчерпан — рискованные изменения замораживают.

См.: *SLA*, *SLI*, *Error Budget*.

**Span (спан)**

Единица работы внутри распределённого трейса: одна операция в одном сервисе. Span записывает своё имя, время начала и окончания, ссылку на родительский span и ошибки.

Трейс — это дерево span. Когда запрос шёл слишком долго, ищут самый медленный span.

См.: *Trace*, *OpenTelemetry*.

**SRE — Site Reliability Engineering (Инженерия надёжности сайтов)**

Дисциплина и должностная роль, придуманные в Google: принципы разработки программного обеспечения применяют к задачам инфраструктуры и эксплуатации.

SRE-инженеры определяют и поддерживают SLO, управляют error budget, автоматизируют ручную операционную работу и реагируют на инциденты. Четыре золотых сигнала — Latency, Traffic, Errors, Saturation — пришли из книги Google по SRE. Цель — надёжные системы без потери скорости разработки.

**Stage (Этап)** (CI/CD)

Именованная группа заданий в пайплайне, которые выполняются параллельно (в пределах этапа), и все они должны завершиться успешно, прежде чем начнётся следующий этап. Ключ `stages:` в GitLab CI задаёт как имена этапов, так и порядок их выполнения. В GitHub Actions нет первоклассной концепции «stage» — порядок задаётся через ключ `needs:` между заданиями.

См.: *Job*, [Основы CI/CD](./01-cicd-fundamentals.md), [GitLab CI](./03-gitlab-ci.md).

**State File (Файл состояния)** (Terraform)

JSON-файл, в котором Terraform отслеживает текущее состояние всей управляемой им инфраструктуры.

При выполнении `terraform apply` Terraform сравнивает желаемое состояние из файлов `.tf` с текущим состоянием из этого файла. По разнице он вычисляет минимальный набор изменений.

В команде файл состояния должен храниться удалённо, чтобы двое не могли менять его одновременно. Обычное решение — S3-бакет с DynamoDB для блокировки. В файле бывают чувствительные значения, поэтому коммитить его в git нельзя.

**Step (Шаг)** (GitHub Actions)

Отдельная команда или действие внутри задания (job). Шаг либо выполняет команду оболочки (`run: npm test`), либо вызывает готовое действие (`uses: actions/checkout@v4`). Шаги внутри задания выполняются последовательно. Для сравнения: *Job* — это несколько шагов на одной машине, *Stage* — несколько заданий.

См.: [GitHub Actions](./02-github-actions.md).

## T

**Terraform**

Самый распространённый инструмент Infrastructure as Code, созданный в HashiCorp. Конфигурации пишут на HCL (HashiCorp Configuration Language).

Terraform не привязан к провайдеру: у него есть провайдеры для AWS, Google Cloud, Azure, Cloudflare, Vercel, GitHub, Kubernetes и сотен других. Рабочий цикл: `terraform init` → `terraform plan` (предпросмотр изменений) → `terraform apply` (применить) → `terraform destroy` (снести). Состояние хранится в файле состояния.

См.: *IaC*, *HCL*, *State File*.

**Trace (Трейс — распределённая трассировка)**

Запись полного пути одного запроса через все сервисы и компоненты распределённой системы. Трейс состоит из **span** — по одному на сервис или компонент. Каждый span записывает имя операции, время начала и окончания и ошибки, если они были.

Trace ID путешествует со всеми межсервисными вызовами в HTTP-заголовке `traceparent`. Этот заголовок описан в стандарте Trace Context консорциума W3C (World Wide Web Consortium). Трейсы отвечают на один вопрос: где конкретный запрос провёл своё время и где сломался. См.: *Span*, *OpenTelemetry*, [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

**TTL — Time To Live (Время жизни)**

В DNS — количество секунд, в течение которых запись живёт в кеше резолверов и клиентов, прежде чем её запросят у авторитетного сервера заново.

Для blue-green деплоев это важно. Переключите трафик обновлением DNS-записи с TTL 3600, то есть час, — и часть пользователей ещё час будет попадать в старое окружение. Перед плановым переключением уменьшите TTL до 60 секунд. У переключения через балансировщик нагрузки этой проблемы нет вовсе.

## U

**Uptime Monitoring (мониторинг доступности)**

Практика: снаружи и по расписанию отправлять запросы к вашему сервису и поднимать тревогу, когда он отвечает неправильно. Такой мониторинг воспроизводит то, что видит реальный пользователь.

Он отличается от внутреннего мониторинга, который опирается на метрики самого приложения. Изнутри сервис бывает здоров, а снаружи недоступен — из-за сети, DNS или файервола. Инструменты: UptimeRobot, Pingdom, Checkly.

См.: [Мониторинг и наблюдаемость](./07-monitoring-and-observability.md).

---

## V

**Vault** (HashiCorp Vault)

Инструмент управления секретами от HashiCorp с открытым исходным кодом. Даёт централизованное хранилище секретов с шифрованием хранимых данных, детальными политиками доступа, журналом аудита и ротацией. Умеет и динамические секреты: учётные данные, которые генерируются по запросу и отзываются автоматически.

Vault можно развернуть у себя или взять управляемый HashiCorp Cloud Platform (HCP) Vault. Он сложнее в эксплуатации, чем управляемый облачный сервис вроде AWS Secrets Manager, зато гибче и не привязан к одному провайдеру.

См.: *Secrets Manager*.

**VPC — Virtual Private Cloud (Виртуальное приватное облако)**

Логически изолированный раздел сети облачного провайдера, который вы определяете и контролируете сами.

Ваши EC2-инстансы, RDS-базы данных, Lambda-функции и прочие ресурсы живут внутри VPC. Из публичного интернета они недоступны, пока вы явно не настроите маршрутизацию.

Для CI/CD это важно: собственный раннер внутри VPC достаёт до приватных баз данных и внутренних сервисов, а GitHub-hosted runner снаружи — нет.

## W

**Workflow (Воркфлоу)** (GitHub Actions)

YAML-файл в `.github/workflows/`, определяющий автоматизацию CI/CD: когда запускается (триггеры), что делает (задания и шаги) и где запускается (тип раннера). Репозиторий может иметь несколько файлов воркфлоу для разных целей (CI, деплой, релиз, запланированные задачи).

См.: [GitHub Actions](./02-github-actions.md), *Pipeline as Code*.

## Y

**YAML — YAML Ain't Markup Language (YAML — не язык разметки)**

Человекочитаемый формат сериализации данных, широко используемый для конфигурационных файлов. Название — рекурсивный акроним: определение ссылается на само себя. На YAML описывают CI/CD-пайплайны: воркфлоу GitHub Actions, `.gitlab-ci.yml`, манифесты Kubernetes, файлы Docker Compose.

Ключевые правила синтаксиса:

- отступы значимы, и это должны быть пробелы, никогда не табуляция;
- `:` отделяет ключ от значения;
- `-` обозначает элемент списка;
- `#` начинает комментарий.

Чувствительность к пробелам — частый источник труднодиагностируемых ошибок. Запускайте в пайплайне YAML-линтер, например `yamllint`.

## Zero-Downtime Deployment (Деплой без простоев)

Требование, при котором деплой сохраняет сервис доступным непрерывно — ни секунды простоя. Достигается тремя приёмами, которые работают вместе:

- **rolling updates** — инстансы заменяют по одному, каждый новый только после успешной проверки работоспособности;
- **blue-green switching** — трафик переключают мгновенно, после того как новое окружение проверено;
- **graceful shutdown** — приложение дообрабатывает текущие запросы перед выходом.

Деплой без простоев на уровне инфраструктуры необходим, но недостаточен. Приложение тоже обязано корректно обрабатывать `SIGTERM`.

См.: [Стратегии деплоя](./05-deployment-strategies.md), *Graceful Shutdown*.
