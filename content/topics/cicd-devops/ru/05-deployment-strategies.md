# Стратегии деплоя

## Почему стратегия деплоя важна

Деплой новой версии кода на продакшн — самый рискованный момент в жизненном цикле доставки программного обеспечения. Если что-то пойдёт не так — баг прошёл через тестирование, деградация производительности, сломанная сторонняя интеграция — пользователи затронуты немедленно. Стратегии деплоя — это техники для управления тем, *как* новая версия кода заменяет старую, с целями:

1. **Минимизация простоя** — пользователи воспринимают сервис как непрерывно доступный
2. **Ограничение blast radius** — доли пользователей, до которых доберётся плохая версия. Если в новой версии есть баг, его увидит только часть из них, прежде чем вы это заметите
3. **Быстрый откат** — если что-то не так, можно быстро вернуться к предыдущему состоянию

Каждая стратегия делает разные компромиссы между сложностью, стоимостью ресурсов и риском.

## Zero-downtime deployment (деплой без простоя)

**Zero-downtime deployment** (развёртывание без простоя) — это общее требование: деплой не должен делать сервис недоступным для пользователей — даже на секунду. Звучит очевидно, но достичь этого нетривиально.

Наивный подход — остановить старую версию, запустить новую — создаёт разрыв:

```txt
Наивный деплой (с простоем):
  t=0с    Старая версия работает, обслуживает трафик
  t=10с   ОСТАНОВКА старой версии  ← "connection refused" или 503
  t=25с   ЗАПУСК новой версии      ← 15 секунд простоя
  t=30с   Новая версия работает, обслуживает трафик
```

Все стратегии ниже — это вариации на тему того, как устранить этот разрыв.

У zero-downtime deployment есть предварительное условие: **приложение должно поддерживать graceful shutdown** (корректное завершение). Оркестратор посылает сигнал `SIGTERM` перед тем, как остановить процесс. По этому сигналу приложение должно:

1. Перестать принимать новые соединения
2. Завершить обработку in-flight запросов (тех, что уже в процессе)
3. Корректно закрыть соединения с базой данных
4. Завершиться с кодом 0

Без graceful shutdown даже самая сложная стратегия деплоя будет терять запросы в момент остановки контейнера.

## Rolling deployment (скользящее обновление)

**Rolling deployment** (также *rolling update* — скользящее обновление) заменяет старые экземпляры новыми **постепенно**, пока сервис продолжает работать. Замена идёт по одному экземпляру или по несколько за раз.

```txt
Сервис имеет 4 экземпляра (pod/контейнера/VM) версии v1:
  [v1] [v1] [v1] [v1]   ← все обслуживают трафик

Шаг 1: заменяем один экземпляр
  [v2] [v1] [v1] [v1]   ← v2 стартует, v1 выводится из-под нагрузки

Шаг 2: заменяем ещё один
  [v2] [v2] [v1] [v1]

Шаг 3:
  [v2] [v2] [v2] [v1]

Шаг 4: завершено
  [v2] [v2] [v2] [v2]   ← все экземпляры работают на v2
```

**Как происходит замена одного экземпляра (zero-downtime на уровне экземпляра):**

1. Новый экземпляр v2 стартует и проходит health check (проверку работоспособности).
2. Load balancer или прокси добавляет v2 в пул маршрутизации.
3. Load balancer выводит v1 из-под нагрузки: новые запросы туда больше не идут, а уже начатые он даёт доработать. Ожидание обычно длится 30–60 секунд.
4. Экземпляр v1 останавливается, когда ожидание закончилось.

**Преимущества:**

- Просто реализовать — встроено в Kubernetes, в Amazon ECS (Elastic Container Service) и в большинство платформ уровня PaaS (platform as a service).
- Не нужна дополнительная инфраструктура — используются уже имеющиеся экземпляры.
- Низкая стоимость ресурсов по сравнению с blue-green.

**Недостатки:**

- Во время развёртывания v1 и v2 работают одновременно, поэтому запрос может попасть в любую из них. Возможна несогласованность ответов.
- Если в v2 есть баг, одни пользователи видят его, другие нет. Доля растёт по мере продвижения rollout.
- Откат требует ещё одного rolling update в обратном направлении, и это медленно.
- Миграции базы данных должны быть совместимы и с v1, и с v2, потому что во время rollout работают обе версии.

Конфигурация rolling deployment в Kubernetes:

```yaml
# kubernetes deployment.yaml
spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1        # разрешить максимум 1 дополнительный pod сверх желаемого числа
      maxUnavailable: 0  # никогда не опускаться ниже желаемого числа (zero-downtime)
  template:
    spec:
      containers:
        - name: app
          image: my-app:v2
          readinessProbe:         # pod попадёт к load balancer только после этой проверки
            httpGet:
              path: /health
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 5
```

Именно `readinessProbe` делает rolling deployment zero-downtime. Pod получает трафик только после того, как проба прошла. Поэтому глючный v2, не прошедший health check, никогда не увидит реального пользовательского трафика: rollout останавливается и срабатывают оповещения.

## Blue-green deployment

**Blue-green deployment** поддерживает **два идентичных production-окружения** — называемых "blue" (синий) и "green" (зелёный) — и мгновенно переключает трафик между ними.

```txt
Текущее состояние — живёт "blue":
  [blue:  v1 v1 v1 v1]  ←── 100% трафика пользователей
  [green: простаивает]      в резерве (или отсутствует)

Деплой v2 в green:
  [blue:  v1 v1 v1 v1]  ←── по-прежнему 100% трафика
  [green: v2 v2 v2 v2]      задеплоен и тестируется, трафика нет

Переключаем load balancer (или DNS) на green:
  [blue:  v1 v1 v1 v1]      теперь простаивает, оставлен для отката
  [green: v2 v2 v2 v2]  ←── 100% трафика пользователей

Если в v2 баг — переключаем обратно, это занимает секунды:
  [blue:  v1 v1 v1 v1]  ←── снова 100% трафика пользователей
  [green: v2 v2 v2 v2]      снова простаивает
```

Само переключение — небольшое изменение: запись DNS (Domain Name System, система доменных имён), правило load balancer или перезагрузка конфигурации reverse proxy. Любое из трёх занимает меньше секунды.

**Преимущества:**

- Мгновенный откат — переключить load balancer обратно, это секунды, а не минуты.
- Нет смешанного трафика версий: в каждый момент времени все пользователи видят одну версию.
- Полное окружение v2 можно протестировать изолированно до переключения — smoke-тесты, нагрузочные тесты, подтверждение QA (quality assurance, отдел тестирования).

**Недостатки:**

- Удвоенная стоимость инфраструктуры: два полных production-окружения существуют одновременно.
- Миграции базы данных сложнее. Если в v2 меняется схема, v1 должен продолжать работать с ней до переключения, поэтому миграции нужны обратно совместимые.
- Переключение через DNS не мгновенно: у записи есть задержка распространения, заданная её TTL (time to live, время жизни). Переключайтесь на уровне load balancer.

Blue-green с reverse proxy (nginx или аналог):

```nginx
# Переключение путём обновления upstream и перезагрузки nginx (zero-downtime reload)
upstream app {
    server green:3000;   # было: server blue:3000;
}
```

Или через облачный load balancer. В AWS (Amazon Web Services) вы перенаправляете listener у Application Load Balancer. В Google Cloud вместо этого обновляете Backend Service:

```bash
# AWS: переключить правило listener балансировщика на green target group
aws elbv2 modify-listener \
  --listener-arn arn:aws:elasticloadbalancing:... \
  --default-actions Type=forward,TargetGroupArn=<green-target-group-arn>
```

## Canary release

**Canary release** (канареечный релиз) отправляет **небольшой процент реального пользовательского трафика** на новую версию, пока большинство по-прежнему попадает на старую. Вы следите за новой версией — ошибки, деградация производительности — и затем шаг за шагом поднимаете её долю до 100%. Название пришло от канарейки в угольной шахте: птицу запускали туда первой, чтобы обнаружить токсичный газ.

```txt
Фаза 1: 5% канарейки
  [v2] ←── 5% трафика ("канарейка")
  [v1] [v1] [v1] [v1] ←── 95% трафика

  Мониторинг: частота ошибок, задержка, бизнес-метрики
  Если всё в порядке → увеличиваем

Фаза 2: 20% канарейки
  [v2] [v2] ←── 20% трафика
  [v1] [v1] [v1] [v1] ←── 80% трафика

Фаза 3: 50%
  ...

Фаза 4: 100% (rollout завершён)
  [v2] [v2] [v2] [v2] ←── 100% трафика
  (v1 выведен из эксплуатации)
```

Ключевое отличие от rolling deployment — в том, чем именно вы управляете. Rolling update заменяет экземпляры один за другим, пока новыми не станут все. Сказать "отправить 5% трафика на v2" здесь нельзя: доля — лишь побочный результат того, насколько далеко продвинулся rollout. Canary управляет *разделением трафика* напрямую — по весу в load balancer, а не по числу экземпляров.

**Где реализуется canary:**

- **Взвешенная маршрутизация load balancer** — weighted target groups у AWS Application Load Balancer, `weight` в nginx, Kubernetes Gateway API
- **Service mesh** (Istio, Linkerd) — детальный контроль трафика на сетевом уровне без изменения приложения
- **На уровне платформы** — Vercel (traffic splitting), AWS CodeDeploy с конфигурацией canary

```yaml
# Kubernetes Gateway API — взвешенное разделение трафика
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
spec:
  rules:
    - backendRefs:
        - name: app-v1
          port: 3000
          weight: 95
        - name: app-v2
          port: 3000
          weight: 5      # 5% канарейки
```

**Преимущества:**

- Реальный пользовательский трафик тестирует новую версию и ловит баги, которые пропустил staging.
- Малый blast radius: баг в v2 изначально доходит только до 5% пользователей.
- Постепенный rollout даёт время обнаружить деградацию производительности, которая проявляется только под реальной нагрузкой.

**Недостатки:**

- Обе версии работают одновременно — с теми же ограничениями на миграции базы данных, что и при rolling update.
- Нужен load balancer с поддержкой взвешенной маршрутизации.
- Observability приходится настраивать по версиям, а не только по сервису.
- Анализ канарейки — решение о том, когда безопасно поднять долю, — либо автоматизирован (Argo Rollouts, Flagger), либо ручной. Ручной подвержен ошибкам под давлением времени.

## Feature flags

**Feature flag** (флаг фичи) — это переключатель в коде приложения, который включает и отключает функциональность во время выполнения, без деплоя нового кода. Его также называют *feature toggle* или *feature switch*.

**Feature flags — не стратегия деплоя.** Это техника на уровне кода, которая дополняет стратегии деплоя. Различие:

| Механизм | Чем управляет |
|---|---|
| Стратегия деплоя | Тем, *как* новый код попадает в production-окружение: rolling, blue-green или canary. |
| Feature flag | Тем, *активна ли* функциональность в уже задеплоенном коде для конкретного пользователя. Код в production в любом случае; флаг управляет видимостью. |

Простая реализация:

```ts
// Feature flag проверяется во время выполнения
const ENABLE_NEW_CHECKOUT = process.env.ENABLE_NEW_CHECKOUT === 'true';

app.get('/checkout', (req, res) => {
  if (ENABLE_NEW_CHECKOUT) {
    return newCheckoutHandler(req, res);
  }
  return legacyCheckoutHandler(req, res);
});
```

**Почему feature flags хорошо сочетаются с CI/CD — continuous integration и continuous delivery, непрерывная интеграция и непрерывная поставка:**

```txt
Без feature flags:
  Feature-ветка → PR → мёрж когда готово → деплой → фича живая
  Проблема: долгоживущие feature-ветки → integration hell

С feature flags:
  Код фичи смёржен в main за флагом (флаг = off)
  → деплои происходят в штатном режиме, код за флагом инертен
  → тестирование на production с флагом = on,
    но только для внутренних пользователей
  → постепенный rollout: включить для 1% → 10% → 50% → 100%
  → мгновенный откат: выключить флаг (новый деплой не нужен)
```

**Сервисы feature flags** (мощнее, чем переменные окружения):

```ts
// Использование сервиса feature flags (LaunchDarkly, GrowthBook, Unleash и т.д.)
const variation = await flagClient.variation('new-checkout', user, false);

if (variation) {
  return newCheckoutHandler(req, res);
}
return legacyCheckoutHandler(req, res);
```

Такие сервисы позволяют:
- **Таргетинг пользователей** — включить для конкретных пользователей, групп или процента
- **Постепенный rollout** — начать с 1%, увеличивать со временем
- **Kill switch** — мгновенно отключить для всех пользователей без деплоя
- **A/B-тестирование** — измерить бизнес-влияние новой фичи до полного rollout

**Критическое различие с canary release:**

| | Canary release | Feature flag |
|---|---|---|
| Где происходит разделение | В инфраструктуре, в load balancer | В приложении, внутри кода |
| Кто обрабатывает запрос | Разные серверы | Тот же сервер, но другая ветка кода |
| Что задеплоено | И v1-код, и v2-код | Одна версия кода |

## Стратегии отката

Ни одна стратегия деплоя не устраняет возможность того, что что-то пойдёт не так. Каждый план деплоя должен включать путь отката.

### Откат при rolling deployment

Rolling откат = ещё один rolling update, но с деплоем предыдущего тега образа:

```bash
# Kubernetes: откат к предыдущему deployment
kubectl rollout undo deployment/my-app

# Или к конкретной ревизии
kubectl rollout undo deployment/my-app --to-revision=3

# Проверить статус rollout
kubectl rollout status deployment/my-app
```

Недостаток: откат занимает столько же времени, сколько и исходный rollout. Если полный rollout занимает 5 минут, откат тоже займёт 5 минут.

### Откат при blue-green deployment

```bash
# Переключить load balancer обратно на blue (предыдущая версия, которая всё ещё работает)
# Занимает секунды — blue никогда не был уничтожен
aws elbv2 modify-listener --default-actions Type=forward,TargetGroupArn=<blue-arn>
```

Вот почему двойная стоимость инфраструктуры blue-green часто оправдана: откат мгновенный.

### Откат при canary release

```yaml
# Установить вес канарейки на 0 — весь трафик обратно на стабильную версию
# (используя Argo Rollouts CRD — Custom Resource Definition)
kubectl argo rollouts set weight my-app 0
# Или просто прервать rollout
kubectl argo rollouts abort my-app
```

### Миграции БД и откат

Самая сложная часть отката — как правило, база данных. Допустим, v2 выполнил миграцию, которая добавила колонку и заполнила её. Откат к v1 оставит v1 в неведении об этой колонке. Хуже того: v2 мог удалить колонку, от которой v1 зависит.

Безопасный паттерн — **expand-contract migration**, он же *parallel-change pattern* (паттерн параллельного изменения). Он идёт в четыре фазы:

1. **Expand** (расширение) — деплоим `v2a`, который добавляет новую колонку как nullable. Изменение остаётся обратно совместимым. Теперь v1 и `v2a` работают бок о бок: v1 игнорирует новую колонку, `v2a` пишет в неё.
2. **Migrate** (миграция) — заполняем новую колонку данными для существующих строк. Делается в фоне, не как часть деплоя.
3. **Contract** (сжатие) — деплоим `v2b`. Данные есть во всех строках, поэтому `v2b` может сделать колонку `NOT NULL` и убрать из кода ссылки на старую. Старого v1-кода в production к этому моменту уже нет.
4. **Cleanup** (очистка) — деплоим v3 и удаляем старую колонку, когда `v2b` достаточно долго проработал стабильно.

Это означает: **никогда не удаляйте колонку в той же миграции, что добавляет её замену**. Никогда не делайте колонку `NOT NULL` в первой миграции. Всегда деплойте в несколько фаз, чтобы откат на любой фазе был безопасным.

## Какую стратегию выбирать

| Тип проекта или ограничение | Рекомендуемая стратегия |
|---|---|
| Простое приложение, небольшая команда, ограниченная инфраструктура | Rolling update |
| Смешанные версии недопустимы, нужен мгновенный откат, можно позволить 2× инфраструктуры | Blue-green |
| Высокий трафик, и новую версию хочется проверить на реальном трафике | Canary release |
| Код готов, а фича — нет, или нужен постепенный пользовательский rollout без повторного деплоя | Feature flag |

На практике большинство зрелых пайплайнов комбинируют стратегии: rolling или blue-green для деплоя на уровне инфраструктуры, feature flags для контроля на уровне приложения, и canary для высокорисковых релизов.

## Типичные ошибки на интервью

- **Путать canary release с feature flags** — это крайне распространено и специально проверяется на собеседованиях. Canary = разделение трафика на уровне инфраструктуры между двумя задеплоенными версиями. Feature flag = ветвление кода на уровне приложения внутри одной задеплоенной версии. Их можно использовать вместе, но это не одно и то же.

- **"Blue-green — это просто задеплоить дважды"** — суть blue-green в том, что старая версия продолжает работать до переключения, делая откат мгновенным. Если уничтожить blue после деплоя green, вы потеряли ключевое преимущество.

- **Забывать о миграциях БД при rolling deployments** — когда v1 и v2 работают одновременно, обе версии обращаются к одной БД. Если миграция v2 удалит колонку, которую читает v1 — v1 сломается. Все миграции при rolling update должны быть обратно совместимы (в одной волне деплоя — только аддитивные; удаления — в следующей волне, после исчезновения v1).

- **Считать `maxUnavailable: 1` и `maxSurge: 0` zero-downtime** — с этими настройками Kubernetes остановит один старый pod прежде, чем запустит новый. Мощность временно упадёт. Для zero-downtime используйте `maxUnavailable: 0` (никогда не опускаться ниже желаемого числа) и `maxSurge: 1` (временно запустить один дополнительный pod).

- **"Откат — это просто заново задеплоить старый Docker-образ"** — верно для stateless-кода. Но если схема базы данных ушла вперёд и старый код её не понимает, повторный деплой старого кода сломает приложение. Откат должен быть спланирован как часть стратегии миграций.

- **Заявлять о zero-downtime без упоминания graceful shutdown** — zero-downtime deployment на уровне инфраструктуры сводится на нет, если приложение не обрабатывает `SIGTERM` корректно. Платформа ждёт, пока соединения завершатся (drain) — но если приложение немедленно выходит по `SIGTERM`, уже начатые запросы теряются. Код приложения должен участвовать в этом.
