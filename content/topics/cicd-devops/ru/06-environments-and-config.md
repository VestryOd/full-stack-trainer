# Окружения и конфигурация

## Что означает "окружение" в DevOps

DevOps — это совместная работа разработки и эксплуатации. **Окружение** (environment) в нём — автономное развёртывание вашего приложения со своей инфраструктурой, конфигурацией и данными. Разные окружения служат разным целям в жизненном цикле разработки.

Канонический набор окружений для веб-приложения:

- **Local** — ноутбук разработчика. Зачем: писать и вручную проверять код. Данные: примеры или фикции, локальная база. Кто пользуется: сам разработчик.
- **Test** — CI-пайплайн (continuous integration, непрерывная интеграция), создаётся заново на каждый запуск. Зачем: автоматические unit- и интеграционные тесты. Данные: фикстуры, in-memory или одноразовая база. Кто пользуется: CI-раннер, автоматически.
- **Development, или "dev"** — общий сервер. Зачем: интеграция между сервисами и проверка фич до staging. Данные: синтетические или анонимизированные. Кто пользуется: разработчики, иногда QA (quality assurance, тестирование).
- **Staging, он же "pre-prod"** — сервер QA или предпродакшна. Зачем: финальная проверка, максимально близко к production. Данные: анонимизированная копия боевых данных или реалистичная синтетика. Кто пользуется: QA, продакт-менеджеры, демо для клиентов.
- **Production, или "prod"** — боевые серверы. Зачем: обслуживать реальных пользователей. Данные: реальные пользовательские данные. Кто пользуется: конечные пользователи.

Не все команды используют все окружения. Многие стартапы работают только с тремя: local → staging → production. В крупных организациях появляются ещё окружения: отдельное QA, UAT, нагрузочное тестирование, аварийное восстановление. UAT расшифровывается как user acceptance testing: клиент или владелец продукта проверяет фичу перед запуском.

### Почему "staging должен зеркалить production"

Staging существует для поиска багов, которые проявляются только в production-условиях. Это данные боевого масштаба, боевой размер инфраструктуры, реальные ответы сторонних API, боевые сертификаты TLS (Transport Layer Security) и настроенный CDN (content delivery network, сеть доставки контента). Если staging существенно отличается от production, он не выполняет свою главную задачу.

Распространённые расхождения staging-production, вызывающие баги "работает на staging, сломано в prod":

- Разные переменные окружения — на staging mock-провайдер платежей, на prod реальный.
- Разные характеристики серверов — на staging `1 CPU / 1 ГБ RAM`, на prod `4 CPU / 16 ГБ RAM`.
- Разные версии базы данных — staging на Postgres 14, prod на Postgres 15.
- Разное поведение CDN и кэширования — на staging CDN нет, на prod работает CloudFront.
- Один экземпляр на staging против нескольких на prod — именно это выявляет гонки состояний и проблемы с session affinity.

## Переменные окружения

**Переменная окружения** (environment variable) — это пара ключ-значение, которую процесс читает во время выполнения. Её задаёт операционная система или то, что запускает процесс, а не исходный код приложения.

```bash
# Установка переменной окружения в shell
export DATABASE_URL="postgres://user:password@localhost:5432/myapp"
export NODE_ENV="production"
export PORT="3000"

# Запущенное приложение читает их
node dist/server.js
```

В Node.js:

```ts
const dbUrl = process.env.DATABASE_URL;
const port = parseInt(process.env.PORT ?? '3000', 10);
const isProd = process.env.NODE_ENV === 'production';
```

Почему переменные окружения — не захардкоженные значения или конфиг-файлы, закоммиченные в репозиторий:

1. **Безопасность.** Учётные данные — пароли базы, ключи API — не должны лежать в version control. Любой, у кого есть доступ на чтение, их увидит; история коммитов вечна.
2. **Гибкость.** Один и тот же Docker-образ идёт на staging со staging-учётками и на prod с боевыми. Сам образ при этом не меняется: собрали однажды, запускаем везде.
3. **Принцип 12-factor app.** Один из его основополагающих принципов (12factor.net) — хранить конфиг в окружении. Конфиг здесь — всё, что меняется между деплоями: dev, staging, prod.

### `NODE_ENV` — специальная конвенция

`NODE_ENV` — де-факто стандарт в экосистеме Node.js. Его значение меняет поведение многих библиотек:

| | `NODE_ENV=development` | `NODE_ENV=production` |
|---|---|---|
| React | Полные сообщения об ошибках и dev-предупреждения | Dev-предупреждения убраны, имена компонентов минифицированы |
| Express | Stack trace в ответах на ошибки | Stack trace скрыт — ради безопасности |
| Webpack / Vite | Без минификации, с source maps | Минификация, tree-shaking, оптимизация бандла |
| Многие библиотеки | Оптимизации пропущены, чтобы было проще отлаживать | Включены кэширование и быстрые пути |

```ts
// Распространённый паттерн: разное поведение по окружению
if (process.env.NODE_ENV !== 'production') {
  app.use(morgan('dev'));          // подробное HTTP-логирование в dev
  app.use(errorHandler());        // детальные ответы на ошибки в dev
}
```

**Никогда не устанавливайте `NODE_ENV=development` на staging.** Staging должен работать с `NODE_ENV=production`, чтобы ловить production-mode баги (проблемы минификации, отсутствующие error boundary и т.д.).

## Конвенция файла `.env`

Файл `.env` — обычный текстовый файл в корне проекта. Он хранит переменные окружения в формате `КЛЮЧ=ЗНАЧЕНИЕ`, по одной на строку:

```bash
# .env  (пример)
DATABASE_URL=postgres://postgres:password@localhost:5432/myapp_dev
REDIS_URL=redis://localhost:6379
JWT_SECRET=local-dev-secret-not-for-production
PORT=3000
NODE_ENV=development
STRIPE_SECRET_KEY=sk_test_...
```

Библиотеки вроде **dotenv** (Node.js) читают этот файл при запуске приложения и загружают переменные в `process.env`:

```ts
// В самом начале точки входа (до любых других импортов, использующих process.env)
import 'dotenv/config';
// или
import dotenv from 'dotenv';
dotenv.config();
```

**`.env` только для локальной разработки. Он никогда не должен попадать в version control.**

Правильная настройка `.gitignore`:

```gitignore
# .gitignore
.env
.env.local
.env.*.local
```

Что вместо этого коммитится в репозиторий — файл `.env.example` (также называемый `.env.template`) с именами переменных, но без реальных значений:

```bash
# .env.example  — коммитится в репозиторий, безопасно для публикации
DATABASE_URL=postgres://user:password@localhost:5432/dbname
REDIS_URL=redis://localhost:6379
JWT_SECRET=change-this-to-a-random-secret
PORT=3000
NODE_ENV=development
STRIPE_SECRET_KEY=sk_test_your_key_here
```

Этот файл сообщает каждому разработчику, какие переменные нужны, не раскрывая реальные учётные данные. Новые члены команды копируют его (`cp .env.example .env`) и вносят реальные локальные значения.

### Несколько `.env`-файлов

В некоторых проектах используется несколько `.env`-файлов для разных окружений:

| Файл | Роль |
|---|---|
| `.env` | Значения по умолчанию. Наименьший приоритет, обычно безопасные дефолты. |
| `.env.local` | Локальные переопределения. Наивысший приоритет, не коммитится. |
| `.env.development` | Значения для dev-окружения. |
| `.env.test` | Значения для тестов, загружается при `NODE_ENV=test`. |
| `.env.production` | Значения для prod — часто просто заглушка; реальные приходят из CI-секретов. |

Эта конвенция встроена во фреймворки Next.js, Vite и Create React App. Порядок загрузки и правила приоритетов специфичны для фреймворка — знайте правила того фреймворка, который используете.

## Секреты vs переменные окружения vs конфиг-файлы

Эти три механизма часто путают. Они отличаются как тем, что хранят, так и тем, как управляются:

| | Переменные окружения | Конфиг-файлы | Secrets manager |
|---|---|---|---|
| Что хранит | Runtime-конфиг, нечувствительный | Статический конфиг приложения: флаги фич, таймауты | Пароли, ключи API, TLS-сертификаты, ключи шифрования |
| Где живёт | Окружение процесса, CI-секреты, переменные платформы | Файл в репозитории или в деплое | Внешний сервис: AWS (Amazon Web Services) Secrets Manager, Vault |
| Кто задаёт | Ops или CI-пайплайн | Разработчик | Ops или команда безопасности |
| Версионируется | Нет — лежит в хранилище CI-секретов | Да, в репозитории | Нет — ротируется отдельно от кода |
| Ротация без деплоя | Вручную, правкой CI-переменной | Нет, нужен деплой | Да, у большинства менеджеров автоматически |

### Когда что использовать

**Переменные окружения** для значений, которые:
- Меняются между окружениями (URL dev ≠ URL prod)
- Нечувствительны (номера портов, флаги фич, уровни логирования)
- Или чувствительны, но платформа подставит их во время выполнения (URL базы приходит из CI, а не зашит в код)

**Конфиг-файлы** для значений, которые:
- Одинаковы во всех окружениях (дефолтные таймауты запросов, лимиты пагинации, константы алгоритмов)
- Безопасны для нахождения в кодовой базе
- Выигрывают от версионирования и ревью как код

```ts
// config/defaults.ts — коммитится в репозиторий
export const config = {
  pagination: { defaultLimit: 20, maxLimit: 100 },
  cache: { ttlSeconds: 300 },
  upload: { maxFileSizeMb: 10 },
};
```

**Secrets manager** для значений, которые:
- Высоко чувствительны: боевой пароль базы данных, приватные ключи, учётные данные платёжного процессора
- Требуют audit log (кто обращался к этому секрету и когда)
- Требуют ротации — автоматической, периодической, без повторного деплоя
- Требуют детального контроля доступа — читать этот секрет может только эта Lambda-функция

## Управление секретами

### Почему нельзя коммитить секреты в репозиторий

**Причина 1 — история git вечна.** Удалите секрет из файла, закоммитьте удаление — он всё равно останется. Он виден в `git log` и `git blame` на старом коммите. Найти его сможет любой, у кого есть доступ к репозиторию — сейчас или раньше. Инструменты вроде truffleHog и gitleaks сканируют историю git на предмет утечек.

**Причина 2 — доступ к репозиторию не равен доступу к production.** Разработчики, подрядчики, боты GitHub Actions и Dependabot — у всех есть доступ на чтение. Ни один не должен автоматически получать боевые пароли базы или ключи платёжных API.

**Причина 3 — секрет в публичном репозитории скомпрометирован сразу.** Боты сканируют GitHub на предмет утёкших AWS-ключей и секретов Stripe — в течение секунд после пуша. AWS запускает собственные сканеры и уведомляет вас, но к тому моменту может быть поздно.

Что делать, если вы случайно закоммитили секрет:

```bash
# Шаг 1: НЕМЕДЛЕННО ротируйте секрет (измените пароль/перегенерируйте ключ)
# История git не может быть полностью очищена в общем репозитории без force-push
# на все ветки и повторного клонирования всеми — это непрактично.
# Единственное безопасное средство — ротация.

# Шаг 2: Удалить из истории git (необязательно, но не заменяет ротацию)
git filter-repo --path .env --invert-paths
# или: BFG Repo Cleaner (внешний инструмент)
# Внимание: нужен force-push; всем участникам придётся склонировать репозиторий заново
```

### Что такое secrets manager

**Secrets manager** (менеджер секретов) — специализированный сервис для хранения, доступа и ротации чувствительных учётных данных. Он обеспечивает:

- **Шифрование at rest**: секреты хранятся зашифрованными, не в открытом виде
- **Audit log**: каждый доступ записывается (какой сервис, какой пользователь, в какое время)
- **Контроль доступа**: детальные права — читать секрет может только вот этот инстанс EC2 (Elastic Compute Cloud)
- **Автоматическая ротация**: менять секрет по расписанию, без изменения кода и без повторного деплоя
- **Версионирование**: хранить предыдущие версии секрета для отката

Распространённые менеджеры секретов:

- **AWS Secrets Manager** — управляется AWS; интегрируется с Lambda, ECS (Elastic Container Service) и RDS (Relational Database Service). Ротация паролей RDS встроена. Около $0.40 за секрет в месяц.
- **HashiCorp Vault** — open-source, self-hosted или в облаке как HCP Vault (HashiCorp Cloud Platform). Бэкенды: базы данных, PKI (public key infrastructure), SSH (secure shell), облака. Эксплуатировать сложнее, чем managed-сервис.
- **Google Secret Manager**, **Azure Key Vault** — эквиваленты в Google Cloud и Azure.
- **Doppler / Infisical** — удобные хостинговые менеджеры секретов. Встраиваются в локальную разработку и CI/CD-пайплайны: continuous integration, continuous delivery.

Как секреты попадают в работающее приложение:

```txt
Вариант A: подставить как переменные окружения при деплое
  CI-пайплайн получает секрет из AWS Secrets Manager
  → кладёт его в env-переменную контейнера или функции
  → приложение читает process.env.DATABASE_URL
  Минус: секрет лежит в env-переменной, читается из /proc на Linux

Вариант B: приложение получает секрет при запуске
  Приложение вызывает SDK AWS Secrets Manager при старте
  → получает секрет напрямую
  → хранит в памяти (никогда не в env-переменной)
  Лучше для: высокочувствительных секретов, ротации без перезапуска

Вариант C: sidecar или агент
  Sidecar-контейнер (напр. Vault Agent) работает рядом с app,
  получает секреты и пишет их в общий in-memory volume
  Приложение читает их из файлов в /vault/secrets/
  Лучше для: Kubernetes-окружений с Vault
```

Пример — получение секрета из AWS Secrets Manager в Node.js:

```ts
import {
  SecretsManagerClient,
  GetSecretValueCommand,
} from '@aws-sdk/client-secrets-manager';

const client = new SecretsManagerClient({ region: 'us-east-1' });

async function getDbPassword(): Promise<string> {
  const response = await client.send(
    new GetSecretValueCommand({ SecretId: 'prod/myapp/db-password' }),
  );
  if (!response.SecretString) throw new Error('Secret not found');
  const { password } = JSON.parse(response.SecretString);
  return password;
}
```

## Infrastructure as Code (IaC)

**Infrastructure as Code** (IaC — инфраструктура как код) — это описание инфраструктуры файлами кода вместо кликов в веб-консоли и ручных shell-команд. Инфраструктура здесь — серверы, сети, базы данных, балансировщики нагрузки, записи DNS (Domain Name System, система доменных имён). Файлы — обычно YAML (текстовый формат для структурированных данных), JSON или предметно-ориентированный язык.

```txt
Без IaC (вручную, "ClickOps"):
  Инженер идёт в консоль AWS
  → кликает "Create EC2 instance"
  → выбирает тип инстанса, AMI (образ машины), security group
  → вручную настраивает load balancer
  → вручную обновляет DNS
  Проблема: не воспроизводимо, не поддаётся аудиту, конфигурации
            расходятся между окружениями, нечего показать на ревью

С IaC:
  Инженер пишет конфигурационный файл
  → файл коммитится в version control
  → изменения проверяются в pull request
  → CI-пайплайн применяет изменения автоматически
  → staging и production описаны в коде одинаково
  Выгода: воспроизводимость, аудит, паритет окружений,
          аварийное восстановление
```

### Configuration drift (дрейф конфигурации)

Без IaC **configuration drift** (дрейф конфигурации) неизбежен. Окружения, начинавшиеся одинаковыми, постепенно расходятся: кто-то внёс ручную правку в production ("только на этот раз") и забыл повторить её на staging. Теперь два окружения незаметно отличаются. Это главный источник "работает на staging, сломано в prod".

IaC решает это, делая код единственным источником истины — если чего-то нет в коде, этого не существует.

### Инструменты IaC — краткая карта

- **HashiCorp Terraform** — самый распространённый и не привязан к провайдеру: AWS, Google Cloud, Azure, Cloudflare, Vercel. Синтаксис HCL (HashiCorp Configuration Language). State-файл отслеживает, что задеплоено.
- **AWS CDK (Cloud Development Kit)** — описывает AWS-инфраструктуру на TypeScript, Python или Java и компилируется в CloudFormation. Ощущается как обычный код приложения.
- **AWS CloudFormation** — нативный для AWS вариант: шаблоны JSON и YAML, зрелые и глубоко интегрированные. Многословно, но надёжно.
- **Pulumi** — как CDK, но не привязан к провайдеру. Инфраструктура пишется на TypeScript, Python, Go и так далее.
- **Ansible** — управление конфигурацией: установка пакетов, работа с файлами, запуск команд на серверах. Фокус иной, чем у Terraform: Terraform создаёт инфраструктуру, Ansible настраивает то, что на ней работает.

### Что fullstack-разработчику реально нужно знать об IaC

Скорее всего, вы не будете писать Terraform или CDK с нуля как fullstack-инженер — это обычно работа DevOps/platform-инженера. Но вы должны понимать:

1. **Зачем нужен IaC.** Альтернатива — ручные клики в консоли — не масштабируется, не воспроизводится и не поддаётся аудиту.
2. **Порядок "plan before apply".** `terraform plan` показывает, что изменится, — это diff для инфраструктуры. `terraform apply` вносит изменения. Та же привычка, что git diff перед мёржем.
3. **State-файлы.** Terraform хранит state-файл: запись того, что задеплоено. В команде он должен лежать удалённо, в бакете S3 (Simple Storage Service) с блокировкой. Не коммитьте его в git: там бывают чувствительные выходные данные.
4. **Модули.** Переиспользуемые компоненты инфраструктуры, аналог функций или npm-пакетов.
5. **Разделение окружений.** Staging и production — обычно отдельные рабочие пространства Terraform или state-файлы, даже если код модуля общий.

Базовый пример Terraform — создаём S3-бакет для хранения объектов:

```hcl
# main.tf

terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 5.0"
    }
  }
}

provider "aws" {
  region = "us-east-1"
}

resource "aws_s3_bucket" "app_assets" {
  bucket = "my-app-assets-${var.environment}"   # напр. "my-app-assets-staging"

  tags = {
    Environment = var.environment
    ManagedBy   = "terraform"
  }
}

variable "environment" {
  type    = string
  default = "staging"
}

output "bucket_name" {
  value = aws_s3_bucket.app_assets.bucket
}
```

```bash
terraform init       # скачать провайдеры
terraform plan       # предварительный просмотр изменений
terraform apply      # создать бакет
terraform destroy    # уничтожить (осторожно с prod!)
```

## Всё вместе: поток конфигурации в реальном проекте

```txt
Локальная разработка:
  .env файл (не коммитится) → process.env → приложение читает конфиг

CI-пайплайн (GitHub Actions / GitLab CI):
  Секреты из интерфейса GitHub/GitLab → env-переменные раннера
  → тесты идут с URL тестовой базы и mock-ключами API

Деплой на staging:
  CI получает секреты из AWS Secrets Manager
  → они попадают в env-переменные контейнера (ECS task definition)
    или в Kubernetes secrets
  → приложение читает DATABASE_URL, REDIS_URL из process.env

Деплой на production:
  Тот же механизм, другие значения секретов
  → приложение на prod читает боевой URL базы
    и реальные ключи платежей

Инфраструктура (серверы, базы данных, сети):
  Terraform / CDK → описывают, что существует
    в AWS, Google Cloud или Azure
  → проверяется в pull request, применяется CI при мёрже в main
```

## Типичные ошибки на интервью

- **"Мы храним конфиг в config.json в репозитории"** — если этот файл содержит что-либо, меняющееся между окружениями (особенно учётные данные), это красный флаг. Нечувствительный конфиг, одинаковый во всех окружениях, может жить в репозитории; всё что меняется или чувствительно должно быть переменной окружения или секретом.

- **"Мы кладём секреты в `.env` и они в безопасности, потому что добавили `.env` в `.gitignore`"** — `.gitignore` только предотвращает будущие коммиты. Если `.env` был когда-либо закоммичен до добавления в `.gitignore`, секрет уже в истории git. И `.gitignore` не защищает от случайного коммита файла с другим именем, содержащего те же секреты.

- **Путать "secrets manager" с "password manager"** — менеджер паролей (1Password, Bitwarden) нужен людям, чтобы хранить личные учётные данные. Secrets manager (AWS Secrets Manager, Vault) — программный сервис для приложений и CI-систем. Он хранит и выдаёт учётные данные во время выполнения через API, с audit-логами и автоматической ротацией.

- **Устанавливать `NODE_ENV=development` на staging** — staging должен работать точно как production. `NODE_ENV=development` активирует development-режим во многих библиотеках (подробные ошибки, неминифицированный код, отключённые кэши), что может скрывать production-баги.

- **Не знать, что такое IaC** — на собеседовании уровня senior fullstack ответ "DevOps-команда настраивает серверы" слабый. Вы должны знать что такое IaC, зачем оно существует, и уметь назвать хотя бы один инструмент (Terraform, CDK, CloudFormation).

- **"Мы используем переменные окружения для всего, включая секреты"** — обычные переменные окружения читаются из среды процесса на хосте (`/proc/<pid>/environ` на Linux). Для высокочувствительных секретов в production забирайте их из secrets manager внутри приложения. Как минимум — подставляйте их так, чтобы значение не попадало в листинг окружения.

- **Не знать паттерн `.env.example`** — `.env` в репозиторий не попадает, а `.env.example` попадает. Знание этого — сильный сигнал, что разработчик работал в зрелых проектах. Интервьюеры это ищут.
