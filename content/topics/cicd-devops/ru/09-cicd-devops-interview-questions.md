# CI/CD и DevOps — вопросы для собеседования

CI — это continuous integration, непрерывная интеграция: каждое слияние в основную ветку запускает автоматическую сборку и тесты. CD — это continuous delivery или continuous deployment; первый вопрос ниже как раз про эту разницу. DevOps — это практика, когда одна команда отвечает и за разработку, и за эксплуатацию.

## Группа 1: Основы CI/CD

**В чём разница между Continuous Delivery и Continuous Deployment?**

Разница — в одном ручном подтверждении перед production.

Оба подхода начинаются одинаково: каждое изменение кода, прошедшее автоматический пайплайн, упаковывается в готовый к деплою артефакт и выкатывается на staging.

- **Continuous Delivery** на этом останавливается: деплой в production ждёт, пока кнопку нажмёт человек.
- **Continuous Deployment** эту кнопку убирает: каждая успешная сборка уходит в production сама.

Оба подхода требуют пайплайна, надёжного настолько, чтобы упавшая сборка действительно означала «не деплоить».

---

**Что такое CI-пайплайн и какие шаги он обычно включает?**

CI-пайплайн — последовательность автоматизированных шагов, которые запускает изменение кода: push или pull request. Типичный порядок:

1. Получить исходный код.
2. Установить зависимости.
3. Запустить линтер и проверку типов.
4. Запустить юнит- и интеграционные тесты.
5. Собрать приложение.
6. Опубликовать артефакт: Docker-образ в реестр, бандл в S3 (Simple Storage Service, объектное хранилище Amazon Web Services) и так далее.
7. Опционально задеплоить на staging.

Шаги идут от самых дешёвых к самым дорогим: дешёвый сбой вроде ошибки линтера ловит проблему до полного набора тестов или Docker-сборки.

---

**Что такое артефакт и почему его следует собирать один раз и продвигать по окружениям?**

Артефакт — любой файл, созданный на этапе сборки: скомпилированный JS-бандл, Docker-образ, Lambda-архив, скомпилированный бинарник.

«Собери один раз, деплой везде» означает, что один и тот же артефакт уходит на staging, а затем в production, без пересборки под каждое окружение. Пересборка вносит вариативность:

- npm-пакет резолвится в другую версию.
- Переменные окружения вшиваются иначе.
- Случайная загрузка падает.

То, что вы тестировали на staging, должно быть побайтово идентично тому, что уходит в production. Артефакт загружается в реестр: Docker Hub, ECR (Elastic Container Registry) или S3. Тегом служит хеш коммита, поэтому любую версию можно воспроизвести точно.

---

**Что означает «pipeline as code» и какие у этого подхода преимущества?**

Pipeline as code означает, что CI/CD-пайплайн описан в конфигурационном файле, который лежит в том же репозитории, что и код приложения. Обычно это YAML — формат конфигурации, где вложенность задаётся отступами. Четыре преимущества:

- Изменения пайплайна проходят то же ревью через pull request, что и изменения кода. Никаких «случайных» правок.
- История этих изменений видна в `git log`.
- Пайплайн воспроизводим: у каждой ветки может быть свой конфиг, и он работает одинаково для всех разработчиков.
- Откат — это `git revert`.

Для сравнения — Jenkins эпохи 2010-х, где пайплайны настраивались кликами в веб-интерфейсе: невидимые, не поддающиеся ни аудиту, ни версионированию.

---

**Что такое раннер (агент) и каковы компромиссы между hosted и self-hosted раннерами?**

Раннер — машина, на которой фактически выполняются задания пайплайна. Планировщик CI отдаёт задание свободному раннеру, тот клонирует репозиторий, выполняет шаги и сообщает результат.

**Hosted runners**, раннеры платформы (GitHub-hosted, GitLab.com shared):

- Свежая виртуальная машина (VM) на каждое задание.
- Нулевое обслуживание, оплата поминутно.
- Нет доступа к вашим приватным сетям.

**Self-hosted runners** — ваши собственные машины, зарегистрированные в CI-платформе:

- Они дотягиваются до приватных баз данных и приватных сегментов сети — например, до VPC (virtual private cloud, виртуальное частное облако).
- Железо полностью ваше, стоимость фиксированная: это ваши серверы.
- Обновления операционной системы, патчи безопасности и очистку диска вы делаете сами.

Правило безопасности: никогда не используйте self-hosted runners в публичных репозиториях. Злоумышленник может изменить воркфлоу в pull request и выполнить произвольный код на вашей машине.

## Группа 2: GitHub Actions и GitLab CI

**В чём разница между триггерами `on: push` и `on: pull_request` в GitHub Actions?**

Триггер `on: push` срабатывает, когда коммит попадает в репозиторий: в main, в feature-ветку или в любую ветку по паттерну. Триггер `on: pull_request` срабатывает при открытии pull request, при новом коммите или при синхронизации.

Типичная схема:

- `on: pull_request` запускает тесты и линтер — проверяет предлагаемое изменение.
- `on: push` в `main`, уже после мержа, запускает пайплайн деплоя.

Важное отличие: `on: pull_request` из форка получает только права на чтение и не видит секретов репозитория.

---

**Как работают matrix builds и когда они полезны?**

Matrix build — определение одного задания, которое GitHub Actions разворачивает в несколько параллельных заданий, комбинируя значения из матрицы.

Например, `matrix: { node: [18, 20, 22] }` порождает три параллельных задания, каждое со своей версией Node.js. Матрицы бывают многомерными: `matrix: { os: [ubuntu-latest, windows-latest], node: [18, 20] }` даёт 4 задания.

Когда это полезно:

- Тестирование на нескольких версиях Node.js, Python или Java.
- Тестирование на нескольких операционных системах.
- Тестирование с несколькими версиями базы данных.

Каждая комбинация матрицы — полностью изолированное задание со своим раннером.

---

**В чём разница между reusable workflow и composite action в GitHub Actions?**

**Reusable workflow** — полноценный воркфлоу, который запускается как отдельное задание на своём раннере. Определяется через `on: workflow_call`, вызывается через `uses: ./.github/workflows/deploy.yml`. Может содержать много шагов и собственные `env:` и `with:` входы, работает в полной изоляции.

**Composite action** — повторно используемая последовательность шагов, которая выполняется *внутри существующего задания* и делит с ним один раннер. Определяется в файле `action.yml` с `runs.using: composite`.

Что выбрать:

- Composite action — чтобы вынести повторяющиеся шаги подготовки внутри одного задания: установка, авторизация, настройка.
- Reusable workflow — чтобы переиспользовать целое задание или флоу деплоя между репозиториями.

---

**В чём разница между `only/except` и `rules` в GitLab CI? Что использовать?**

Всегда используйте `rules`. Ключевое слово `only/except` устарело и будет удалено.

Устаревшая форма — `only: [main, merge_requests]`: задание выполняется только на перечисленных ветках или событиях. Её ограничения:

- Условия нельзя комбинировать.
- CI-переменные внутри условия недоступны.
- `when: manual` нельзя задать условно.

Современное `rules` — упорядоченный список условий `if/when/changes`, которые проверяются сверху вниз; выигрывает первое совпавшее. Поддерживаются:

- `if: $CI_COMMIT_BRANCH == "main"`
- `changes: [src/**/*]` — запускать только при изменении исходных файлов
- `when: manual`
- `allow_failure: true` на уровне правила

---

**Что делает ключевое слово `needs:` в GitLab CI и какую структуру оно создаёт?**

Ключевое слово `needs:` задаёт явные зависимости между заданиями. Оно превращает пайплайн из последовательности этапов в DAG (Directed Acyclic Graph) — направленный ациклический граф, где рёбра направлены в одну сторону и ни один путь не возвращается назад.

Без `needs:` задания каждого этапа ждут завершения всего предыдущего этапа. С `needs:` задание стартует сразу после своих конкретных зависимостей, в каком бы этапе оно ни находилось. Например, `deploy-preview` может зависеть только от `build` и не ждать `test-e2e` в том же этапе, что заметно сокращает общее время пайплайна.

В GitHub Actions то же делается ключом `needs:` на уровне задания.

---

**Как безопасно работать с секретами в GitHub Actions?**

Секреты хранятся в разделе Settings → Secrets репозитория или организации и после первоначальной настройки в логах не показываются. В воркфлоу вы читаете их через `${{ secrets.MY_SECRET }}`.

Пять правил:

1. Никогда не хардкодьте секрет в YAML-файле воркфлоу.
2. Никогда не делайте `echo` значения секрета. GitHub маскирует известные ему значения, но маска не абсолютна.
3. Для production-доступов используйте секреты уровня окружения (`environment: production`). Задание с ними ждёт подтверждения человека перед запуском.
4. Для сторонних API-ключей предпочитайте федеративные токены OIDC (OpenID Connect) вечным статическим ключам. AWS (Amazon Web Services), GCP (Google Cloud Platform) и Azure это поддерживают.
5. Проверяйте, какие воркфлоу могут читать какие секреты.

---

**Что такое Docker-in-Docker (dind) и когда он нужен в GitLab CI?**

Docker-in-Docker (dind) — конфигурация, при которой Docker-демон запускается *внутри* Docker-контейнера. Это позволяет выполнять `docker build` и `docker push` внутри CI-задания, которое само работает в контейнере.

В GitLab CI это нужно, когда Docker executor запускает задания как контейнеры, а заданию надо собирать Docker-образы. Объявляется как сервис — `services: - docker:24-dind` — с переменной `DOCKER_HOST: tcp://docker:2376`.

Последствие для безопасности: dind требует **привилегированного режима**, то есть полного доступа контейнера к ядру хоста. В разделяемой среде это значительный риск. Альтернатива — Kaniko: он собирает Docker-образы без демона и без привилегий.

## Группа 3: Docker

**В чём разница между Docker-образом и контейнером?**

Образ — доступный только для чтения слоёный снимок файловой системы. В нём есть всё, что нужно для запуска приложения: базовая операционная система, среда выполнения, зависимости, скомпилированный код. Образ собирается из Dockerfile и хранится в реестре.

Контейнер — запущенный экземпляр образа: файловая система образа плюс перезаписываемый верхний слой, работающий как изолированный процесс на хосте.

Аналогия: образ — определение класса, контейнер — его экземпляр. Из одного образа могут работать несколько контейнеров. Образы собираются один раз и продвигаются по окружениям; контейнеры эфемерны и заменяемы.

---

**Что такое слои Docker-образа и почему они важны для производительности сборки?**

Каждая инструкция Dockerfile (`FROM`, `RUN`, `COPY`, `ADD`) создаёт новый слой — дифф относительно нижнего слоя.

Слои кешируются. Если инструкция и её входные данные не изменились с прошлой сборки, Docker берёт кешированный слой и не выполняет её заново. Изменение любого слоя инвалидирует кеш всех слоёв ниже него.

Поэтому порядок инструкций критичен. Сначала — то, что меняется редко:

- Установка системных пакетов.
- Копирование `package.json`.
- Запуск `npm install`.

Дальше — то, что меняется почти на каждом коммите: копирование исходного кода. Правило `COPY package*.json ./` → `RUN npm ci` → `COPY . .` оставляет слой с `npm ci` закешированным при изменениях исходников.

---

**В чём разница между `CMD` и `ENTRYPOINT`, и между exec-формой и shell-формой?**

`ENTRYPOINT` задаёт фиксированный исполняемый файл, который запускается всегда. `CMD` даёт аргументы по умолчанию, и их можно переопределить при `docker run`. Когда есть оба, контейнер запускает `ENTRYPOINT` с аргументами из `CMD`.

Форма записи важнее, чем кажется:

- **Shell-форма** (`CMD node server.js`) вызывает `sh -c "node server.js"`. Тогда `sh` становится в контейнере процессом с PID (process identifier, идентификатор процесса) 1, а Node.js — его дочерним процессом. Сигнал `SIGTERM` дочерним процессам `sh` не пробрасывает, и graceful shutdown ломается.
- **Exec-форма** (`CMD ["node", "server.js"]`) запускает Node.js напрямую как PID 1. Он получает `SIGTERM` и может корректно завершиться.

Для главного процесса всегда используйте exec-форму. Shell-форма допустима для инструкций `RUN` на этапе сборки.

---

**Что такое PID 1 в контейнере и почему это важно?**

В Linux PID 1 — это init-процесс, первый процесс, который запускает ядро. Он собирает зомби-процессы и пробрасывает сигналы. В Docker-контейнере PID 1 — это процесс, заданный в `CMD` или `ENTRYPOINT`.

Если PID 1 оказывается `sh` — так бывает при shell-форме, — сигнал `SIGTERM` до дочерних процессов не доходит. Дальше цепочка короткая:

1. Kubernetes останавливает pod и отправляет `SIGTERM`.
2. Процесс `sh` игнорирует сигнал.
3. Kubernetes ждёт grace period — по умолчанию 30 секунд.
4. Kubernetes отправляет `SIGKILL`. Контейнер уничтожается принудительно, и все запросы в обработке обрываются.

С exec-формой ваше приложение само становится PID 1, получает `SIGTERM` напрямую и может корректно завершиться. Для Node.js это `CMD ["node", "server.js"]`, а не `CMD node server.js`.

---

**Что такое multi-stage build и какую проблему он решает?**

Multi-stage build использует несколько инструкций `FROM` в одном Dockerfile, каждая начинает новый этап сборки. Файлы переносятся между этапами через `COPY --from=builder`.

Финальный образ содержит только то, что явно скопировано на последний этап. Инструменты сборки, dev-зависимости, компилятор TypeScript и тестовые файлы остаются на предыдущих этапах. В production-образе оказывается только среда выполнения Node.js и скомпилированный JS: без TypeScript-компилятора, без пакетов `@types/*`, без тестовых фреймворков.

Типичное уменьшение размера: с 400 мегабайт со всеми инструментами сборки до 80 на одной среде выполнения. Маленький образ быстрее скачивается, даёт меньшую поверхность атаки и дешевле в хранении.

---

**Почему контейнеры должны работать от непривилегированного пользователя?**

По умолчанию процесс внутри Docker-контейнера работает от root — пользователя с идентификатором 0. Если злоумышленник эксплуатирует уязвимость в приложении и выбирается из контейнера через баг ядра или неверную конфигурацию, у него оказывается полный root-доступ к хост-машине.

Запуск от непривилегированного пользователя ограничивает радиус поражения: сбежавший процесс получает те же права, что и обычный пользователь операционной системы.

В Dockerfile это `USER node`: в базовых образах `node:*` пользователь `node` с идентификатором 1000 уже заведён. Убедитесь, что файлы, в которые пишет приложение, принадлежат этому пользователю. Некоторые среды выполнения контейнеров умеют требовать этого политикой — Kubernetes делает это через Pod Security Admission.

## Группа 4: Стратегии деплоя

**Что такое деплой без простоев и как он достигается?**

Деплой без простоев означает, что сервис остаётся доступным во время обновления кода: ни один запрос не теряется, ни один пользователь не видит ошибок. Нужны две вещи одновременно.

- Инфраструктурная стратегия, которая держит старые инстансы живыми, пока поднимаются новые: rolling update, blue-green или canary.
- Graceful shutdown в приложении. По сигналу `SIGTERM` инстанс перестаёт принимать новые соединения, но дорабатывает уже начатые запросы.

Без graceful shutdown даже идеальный rolling update теряет запросы при каждой замене pod. Миграции базы данных тоже должны быть обратно совместимы: старая и новая версии приложения работают одновременно.

---

**В чём разница между rolling, blue-green и canary деплоями?**

Три стратегии:

- **Rolling update, скользящее обновление.** Инстансы заменяются по одному или небольшими группами. Во время выкатки трафик обслуживают обе версии, поэтому API и схема базы данных должны быть обратно совместимы. Самая дешёвая из трёх, встроена в Kubernetes и ECS (Elastic Container Service).
- **Blue-green.** Поддерживаются два идентичных окружения. Новая версия целиком разворачивается и тестируется в простаивающем, затем балансировщик мгновенно переключает трафик. Периода одновременной работы версий нет, откат — это переключение обратно, но вы платите за двойную инфраструктуру.
- **Canary.** Небольшая доля трафика, например 5%, идёт на новую версию, остальное остаётся на старой. За новой версией наблюдают и постепенно увеличивают долю. Радиус поражения самый маленький из трёх, но нужна инфраструктура для разделения трафика: service mesh или умный балансировщик.

---

**Что такое паттерн expand-contract migration и когда он нужен?**

Паттерн expand-contract позволяет внести ломающее изменение схемы базы данных без простоя. Во время rolling-деплоя старая и новая версии работают с одной базой, поэтому одна опасная миграция разбивается на три деплоя:

1. **Expand, расширение.** Добавляем новую колонку как nullable. Блокировки нет, обратная совместимость есть, старый код колонку просто игнорирует.
2. **Backfill, заполнение.** Деплоим код, который пишет и в старую, и в новую колонку, а фоновым заданием заполняем новую колонку в существующих строках.
3. **Contract, сжатие.** Когда все строки заполнены и старый код ушёл, делаем колонку `NOT NULL` и удаляем старую.

Частая ловушка: добавить колонку `NOT NULL` с `DEFAULT` одной миграцией на большой таблице. PostgreSQL перезапишет всю таблицу и возьмёт полную блокировку.

---

**Что такое feature flag и чем он отличается от canary release?**

Feature flag (переключатель функциональности) — это `if`-условие в коде приложения, которое во время выполнения проверяет значение конфигурации: `if (flags.isEnabled('new-checkout', user))`. Код уже задеплоен в production, но неактивен до включения флага.

Canary release работает уровнем ниже, в инфраструктуре. Две версии сервиса задеплоены одновременно, а балансировщик нагрузки или service mesh направляет на новую часть трафика.

Практическая разница:

- Флаг переключается для конкретного пользователя, организации или процента — без деплоя вообще.
- Canary release означает, что реально работают две задеплоенные версии.

Они дополняют друг друга: canary release проверяет новый бинарник, feature flags контролируют раскрытие функциональности.

---

**Что такое graceful shutdown и как его реализовать в Node.js?**

Graceful shutdown означает, что процесс перехватывает `SIGTERM` и завершается по порядку:

1. Перестаёт принимать новые соединения.
2. Дожидается завершения запросов в обработке.
3. Освобождает ресурсы: соединения с базой данных, потребителей очередей сообщений.
4. Выходит с кодом 0.

В Node.js с Express:
```javascript
process.on('SIGTERM', async () => {
  server.close(async () => {        // прекращаем принимать новые HTTP-соединения
    await prisma.$disconnect();     // закрываем пул соединений с базой
    process.exit(0);
  });
});
```
Kubernetes отправляет `SIGTERM` и ждёт `terminationGracePeriodSeconds` — по умолчанию 30 секунд — перед отправкой `SIGKILL`. Приложение должно уложиться в это окно. Для NestJS `app.enableShutdownHooks()` подключает это через lifecycle-хук `OnApplicationShutdown`.

## Группа 5: Окружения, конфигурация и секреты

**В чём разница между переменной окружения, конфигурационным файлом и секретом?**

Три вида настроек, разделённых по чувствительности:

- **Переменные окружения** — несекретные параметры времени выполнения: feature flags, уровень логирования, URL внешних API, имя окружения. Простые пары ключ-значение, легко переопределяются под окружение, доступны через `process.env`.
- **Конфигурационные файлы** — структурированные несекретные настройки: имя схемы базы данных, значения пагинации по умолчанию, поддерживаемые локали. Лежат в репозитории и загружаются при старте.
- **Секреты** — чувствительные учётные данные, которым нельзя появляться в исходном коде, логах и незашифрованном хранилище. Это пароли от баз данных, API-ключи, ключи подписи JWT (JSON Web Token), приватные ключи TLS (Transport Layer Security).

Секреты хранятся в secrets manager (AWS Secrets Manager, HashiCorp Vault) и подставляются в процесс во время выполнения через переменные окружения. Граница простая: если утечка значения повлечёт инцидент безопасности, это секрет.

---

**Почему `.env` файлы нельзя коммитить в систему контроля версий?**

Как только секрет закоммичен, он фактически стал постоянным. Удаление в следующем коммите не спасает: секрет остаётся в git-истории, и `git log -p` его достанет. Прочитать его может любой, у кого есть доступ к репозиторию: нынешние и будущие члены команды, автоматизированные инструменты, индексирование самого GitHub. Атаки на цепочки поставок собирают секреты именно из истории.

Правильный паттерн: `.env` лежит в `.gitignore`, а вместо него коммитится `.env.example` — те же ключи, без реальных значений. Так документируется, какие переменные нужны, и значения не раскрываются. Дополнительно запускайте в CI сканер секретов: встроенный сканер GitHub, `trufflehog` или `gitleaks`.

---

**Что такое configuration drift и как его предотвращает Infrastructure as Code?**

Configuration drift — расхождение окружений между собой и с задуманным состоянием из-за ручных правок. Кто-то заходит в консоль облака и думает: «я просто быстро изменю эту настройку». Со временем staging и production отличаются в тонкостях, которые никто не задокументировал, и получается «работает на staging, падает в production».

Infrastructure as Code это предотвращает. Terraform и AWS CDK (Cloud Development Kit) описывают инфраструктуру декларативно, в файлах кода, которые хранятся в git.

Инструмент вычисляет разницу между объявленным состоянием и фактическим состоянием облака и применяет только необходимые изменения. Ручная правка перезаписывается на следующем `terraform apply`: источник истины — всегда код.

---

**Что даёт secrets manager в отличие от простых переменных окружения?**

Простые переменные окружения не дают ни аудируемости, ни ротации, ни гранулированного контроля доступа, ни версионирования. Это верно и для `.env` на сервере, и для значения, захардкоженного в Kubernetes-манифесте. Secrets manager (AWS Secrets Manager, HashiCorp Vault) добавляет шесть вещей:

- **Шифрование в покое.** Секреты никогда не хранятся в открытом виде.
- **Журнал аудита.** Записывается каждое обращение: кто, какой секрет и когда прочитал.
- **Гранулированные политики доступа.** Через IAM (Identity and Access Management) платёжный сервис читает `STRIPE_SECRET_KEY`, но не `SENDGRID_API_KEY`.
- **Автоматическая ротация.** Пароли баз данных меняются по расписанию.
- **Версионирование.** Можно откатиться к предыдущему значению секрета.
- **Динамические секреты.** Учётные данные генерируются по запросу и автоматически отзываются после использования.

---

## Группа 6: Мониторинг и наблюдаемость

**В чём разница между мониторингом и наблюдаемостью (observability)?**

Мониторинг — это наблюдение за заранее определёнными сигналами: дашборды, алерты, проверки аптайма. Он отвечает на вопросы, которые вы уже знаете как задать. Частота ошибок выше 1%? Загрузка CPU (central processing unit, центральный процессор) выше 80%?

Наблюдаемость — свойство системы, которое позволяет понять её внутреннее состояние по внешним выходным данным: логам, метрикам, трейсам. Она отвечает на вопросы, которых вы не предвидели. Почему запрос именно этого пользователя упал иначе, чем у всех остальных?

Хорошо отмониторенная система сообщает, что что-то пошло не так. Хорошо наблюдаемая объясняет *почему* и *где*. Наблюдаемость стоит на трёх китах: логи, метрики и распределённые трейсы.

---

**Каковы три кита наблюдаемости и на что каждый отвечает?**

- **Логи** — записи дискретных событий с временными метками, например «пользователь 42 создал заказ 891». Отвечают на вопрос *что произошло*. Лучшая практика: структурированные (JSON) логи с согласованными полями — `traceId`, `userId`, `level`, `message`.
- **Метрики** — числовые измерения, агрегированные во времени: запросы в секунду, задержка p99, частота ошибок, загрузка процессора. Отвечают на вопрос *сколько и как быстро*. Инструменты: Prometheus и Grafana.
- **Трейсы** — записи пути одного запроса через все сервисы распределённой системы, разбитые на spans. Отвечают на вопрос *где конкретно запрос потратил время и где упал*. Инструменты: Jaeger, Zipkin, OpenTelemetry с любым совместимым бэкендом.

На практике вы идёте по ним в этом же порядке. Срабатывает алерт по метрике, вы углубляетесь в логи за контекстом, берёте оттуда traceId и вытягиваете полный распределённый трейс.

---

**Каковы четыре золотых сигнала и что каждый из них измеряет?**

В книге Google по SRE (site reliability engineering) названы четыре метрики, которых хватает, чтобы судить о здоровье сервиса с точки зрения пользователя.

1. **Latency, задержка** — сколько времени занимают запросы. Всегда отслеживайте перцентили (p50, p95, p99), а не средние значения. p99 в 200 мс означает, что 1% пользователей ждёт 200 мс и дольше.
2. **Traffic, трафик** — какой спрос обрабатывает система: запросы в секунду, сообщения в секунду, активные пользователи. Задаёт базовую линию «нормы».
3. **Errors, ошибки** — частота неудачных запросов. Различайте 5xx (ошибки сервера), 4xx (ошибки клиента) и тихие ошибки, когда с кодом 200 возвращаются неверные данные.
4. **Saturation, насыщенность** — насколько «заполнена» система: процессор, память, использование пула соединений, глубина очереди. Насыщенность предсказывает сбои до их наступления.

---

**В чём разница между liveness probe и readiness probe в Kubernetes?**

| | Liveness probe | Readiness probe |
|---|---|---|
| Вопрос | Жив ли контейнер или его нужно перезапустить? | Готов ли контейнер принимать трафик? |
| При неудаче | Kubernetes перезапускает контейнер | Kubernetes убирает pod из пула балансировщика, без перезапуска |
| Что проверяет | Только собственное состояние процесса | Доступность всех необходимых зависимостей |

Liveness probe должна быть простым HTTP-эндпоинтом, который возвращает 200, пока сервер работает. Проверять внешние зависимости она **не** должна. Если она проверяет базу данных, а база недоступна, все поды перезапускаются в бесконечном цикле и недоступность только усугубляется.

Readiness probe не пускает трафик на pod, который запустился, но ещё не подключился к базе данных.

---

**Что такое distributed tracing и какую проблему он решает?**

В монолите медленный запрос легко локализовать: добавить логи с замерами, профилировать код. В микросервисной системе одно действие пользователя запускает вызовы через 5-10 сервисов, и когда ответ медленный, непонятно, какой сервис виноват.

Distributed tracing записывает полный путь. Когда сервис A вызывает B, а тот вызывает C, каждый сервис добавляет к общему трейсу свой span: время начала, время конца, имя сервиса, ошибки. Значение `traceId` генерируется в точке входа и передаётся через все вызовы в HTTP-заголовке `traceparent`.

Результат — визуализация всего запроса в виде диаграммы Ганта: видно, какой span был медленным и почему. OpenTelemetry — стандартный инструментарий для трассировки.

---

**В чём разница между SLA, SLO и SLI?**

Три слоя одного и того же обещания: Service Level Indicator (SLI), Service Level Objective (SLO) и Service Level Agreement (SLA).

- **SLI** — само измерение, конкретная метрика, которую вы отслеживаете. Пример: доля запросов, завершающихся менее чем за 300 мс, за 5-минутный период.
- **SLO** — внутренняя цель для SLI, порог, ниже которого вы считаете, что сервис подводит пользователей. Пример: 99,5% запросов должны завершаться менее чем за 300 мс. Это не обязательство перед клиентами.
- **SLA** — внешнее договорное обязательство перед клиентами, с финансовыми последствиями за нарушение. Пример: мы гарантируем 99,9% аптайма в месяц, а при нарушении клиенты получают кредиты.

SLA всегда менее строгий, чем SLO: так остаётся буфер. Нарушение SLO — внутренний сигнал тревоги, нарушение SLA влечёт финансовые и юридические последствия.

---

**Что такое error budget и как он меняет поведение команды?**

Error budget — дополнение целевого SLO: допустимый объём ненадёжности за период. Формула: `error budget = 1 − SLO`. При SLO аптайма 99,9% бюджет равен 0,1%, то есть 43,2 минуты допустимого простоя за 30 дней.

Бюджет — общий ресурс двух команд, тянущих в разные стороны. Разработка хочет деплоить фичи, и каждый деплой рискует потратить бюджет. Команда надёжности хочет его сохранить.

- Пока бюджет велик, команды деплоят агрессивнее и берут больше рисков.
- Когда бюджет почти исчерпан, рискованные деплои замораживают и занимаются надёжностью.

Так надёжность превращается в измеримый и торгуемый ресурс вместо размытой цели, а противостояние «разработка хочет деплоить» против «эксплуатация хочет стабильности» исчезает.

---

**Что такое структурированное логирование и чем оно лучше обычного текстового?**

Неструктурированный лог — `"Пользователь 42 разместил заказ 891 в 14:30"` — читаем для человека, но враждебен к машине. Парсинг регуляркой для поиска по userId среди миллионов строк медленный и хрупкий.

Структурированный лог — объект JSON на каждое событие: `{ "level": "info", "msg": "order placed", "userId": 42, "orderId": 891, "traceId": "abc123", "timestamp": "2026-01-15T14:30:00Z" }`.

Четыре преимущества:

- Системы агрегации логов (Loki, Elasticsearch) индексируют поля, и запрос `userId=42 AND level=error` выполняется мгновенно.
- Поле `traceId` связывает строки логов с распределёнными трейсами.
- Поля типизированы. Длительность — число, а не строка «заняло 120мс».
- Дашборды и алерты можно строить по значениям полей.

Используйте `pino` или `winston` в JSON-режиме для Node.js-приложений.

## Группа 7: Аббревиатуры и концепции

**Объясните CI, CD, IaC, SLA, SLO и SLI в одном предложении каждый.**

- **CI (Continuous Integration)** — частое слияние кода в основную ветку, при котором каждое слияние запускает автоматический пайплайн сборки и тестов и сразу вскрывает проблемы интеграции.
- **CD (Continuous Delivery / Deployment)** — при Continuous Delivery каждая успешная сборка готова к деплою в любой момент, но за ручным подтверждением. При Continuous Deployment это подтверждение автоматизировано.
- **IaC (Infrastructure as Code)** — описание инфраструктуры (серверы, сети, базы данных) в файлах кода под контролем версий, чтобы окружения были воспроизводимы, аудируемы и не расходились.
- **SLA (Service Level Agreement)** — внешнее договорное обязательство перед клиентами: минимальное качество сервиса и финансовые штрафы за нарушение.
- **SLO (Service Level Objective)** — внутренняя цель надёжности, более строгая, чем SLA: порог, ниже которого команда считает, что сервис подводит пользователей.
- **SLI (Service Level Indicator)** — метрика, которая питает SLO: например, доля запросов быстрее 300 мс.

---

**Что означает APM и какую проблему он решает?**

APM расшифровывается как Application Performance Monitoring — мониторинг производительности приложений. Он закрывает разрыв между мониторингом инфраструктуры (процессор, память, диск) и пониманием того, что приложение даёт бизнесу.

APM-инструменты автоматически инструментируют приложение и захватывают:

- Длительность и код статуса каждого запроса.
- Медленные запросы к базе данных, вместе с текстом на SQL (Structured Query Language).
- Внешние HTTP-вызовы.
- Ошибки с полными стектрейсами.
- Распределённые трейсы.

Эти данные агрегируются по эндпоинтам, сервисам и сегментам пользователей.

Проблема, которую они решают: сервер выглядит здоровым — процессор 30%, память 60%, — а пользователи жалуются, что чекаут медленный. APM показывает, что у `POST /checkout` p99 равен 4 с и 80% этого времени занимает один неиндексированный запрос к базе. Примеры: Datadog APM, New Relic, Sentry Performance, Elastic APM.

---

**Что такое Kubernetes (K8s) и какую проблему он решает для деплоев?**

Kubernetes — платформа оркестрации контейнеров. Восьмёрка в K8s — это 8 букв между K и s.

Запускать контейнеры на одном сервере просто с помощью Docker. Запускать сотни контейнеров на десятках серверов — уже сложная задача распределённых систем:

- Планировать, какой контейнер работает на каком сервере.
- Перезапускать упавшие контейнеры.
- Масштабироваться с 2 до 20 реплик под нагрузкой.
- Маршрутизировать сетевой трафик.
- Выкатывать новые версии без простоев.
- Раздавать секреты.

Kubernetes решает это декларативной моделью. Вы описываете желаемое состояние: 5 реплик этого образа, доступных на порту 8080, по 512 мегабайт памяти каждая. Дальше Kubernetes приводит фактическое состояние в соответствие и сам занимается планированием, проверками работоспособности, масштабированием и rolling update.

---

**Что такое GitOps?**

GitOps — это практика, при которой желаемое состояние деплоев приложений и инфраструктуры целиком хранится в Git. Автоматизированные системы (Argo CD, Flux) непрерывно приводят живое состояние в соответствие с тем, что объявлено в Git. Все изменения, включая инфраструктурные, вносятся через pull request.

Преимущества:

- Каждое изменение проходит ревью, аудируется и версионируется.
- История git — это журнал деплоев.
- Откат — это `git revert`.
- Расхождение объявленного и фактического состояния обнаруживается и исправляется автоматически.

GitOps — точка схождения Infrastructure as Code, CI/CD и принципа «Git — единственный источник истины». Сильнее всего он проявляется в Kubernetes, где манифесты могут быть полностью декларативными.

---

**Что такое DAG в контексте CI/CD-пайплайнов?**

DAG расшифровывается как Directed Acyclic Graph — направленный ациклический граф. Это структура, где рёбра направленные и ни один путь не возвращается к своей начальной точке.

В CI/CD граф DAG описывает зависимости заданий: задание B должно выполняться после задания A. «Directed» — это A → B, а не B → A. «Acyclic» — нет циклической зависимости вида A → B → A.

Традиционный stage-based пайплайн — простой DAG: все задания 2-го этапа ждут всех заданий 1-го.

Современные пайплайны допускают произвольные формы DAG через ключ `needs:` в GitLab CI и GitHub Actions. Тогда `deploy-preview` зависит только от `build` и выполняется параллельно с `test-e2e`, что резко сокращает общее время пайплайна.

---

**Что такое OpenTelemetry (OTel) и почему он стал стандартом?**

OpenTelemetry — нейтральный по отношению к вендорам open-source фреймворк наблюдаемости. Он даёт API, библиотеки и инструменты для генерации, сбора и экспорта телеметрии: трейсов, метрик и логов.

Раньше инструментирование приложения означало выбрать вендора (Datadog, New Relic, Jaeger) и поставить его проприетарный агент. Смена вендора требовала переинструментировать всю кодовую базу.

OpenTelemetry снимает эту привязку. Вы инструментируете код один раз по стандартным API, экспортируете в OpenTelemetry Collector, а дальше маршрутизируете из коллектора в любой бэкенд: Jaeger, Datadog, Honeycomb, Grafana Tempo. Смена бэкенда — это правка конфига экспортёра коллектора, а не кода приложения.

Проект поддерживают CNCF (Cloud Native Computing Foundation) и все крупные вендоры наблюдаемости. Для новых проектов это единственный разумный выбор.

**В чём разница между uptime monitoring и APM?**

Uptime monitoring — внешний синтетический мониторинг. Проба за пределами вашей инфраструктуры по расписанию отправляет HTTP-запросы на ваши публичные URL и сигналит, если успешный ответ не пришёл за таймаут. Она симулирует базовый пользовательский опыт: может ли пользователь вообще зайти на сайт? Инструменты: UptimeRobot, Pingdom, Checkly.

Обнаруживает:

- Сбои DNS (Domain Name System, система доменных имён).
- Перебои CDN (content delivery network, сеть доставки контента).
- Неверную конфигурацию балансировщика нагрузки.
- Полную недоступность сервиса.

APM — внутреннее инструментирование. Агенты внутри приложения захватывают детальные данные о каждом запросе: SQL-запросы, внешние API-вызовы, стектрейсы ошибок, задержку по эндпоинтам. Так находятся медленные участки кода, неиндексированные запросы, утечки памяти и всплески ошибок на конкретных эндпоинтах.

Нужны оба. Uptime monitoring ловит «сайт недоступен», а APM объясняет «этот эндпоинт медленный для пользователей из Европы из-за отсутствующего индекса в базе».
