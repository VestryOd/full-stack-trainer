# Capstone: reviewing the project and where to grow next

## Theory

**The road so far, briefly.** `taskman` started in chapter 00 as an `argparse` skeleton, printing an in-memory list to the console. Along the way it picked up: typed models instead of bare dicts (`@dataclass`, chapter 04), a package structure instead of a single file (chapter 05), real persistence instead of process memory (SQLite, chapter 08), static type checking as part of everyday development (`mypy --strict`, chapter 10), fully asynchronous data access (chapter 12), a REST API on top of the **exact same** storage layer, never touched for that purpose (chapters 13–14), multi-user authentication (chapter 15), a thorough test suite (chapter 16), and finally, packaging into a container with configuration from the environment (chapter 17). The key architectural bet that paid off across all of this was the `TaskStorage` protocol (chapter 10): both the CLI and the API, across all 8 subsequent chapters, called the same set of functions, never once knowing whether they were backed by `sqlite3` or `aiosqlite`, a file or something else entirely.

It's worth naming another thread that ran through the whole course: almost every chapter that added something new also had something it **deliberately didn't add** — not out of oversight, but because the project's current scale didn't call for it. Chapter 06 didn't add locking around task writes, because chapter 08 hadn't introduced them yet. Chapter 14 didn't add a session-per-request, because no endpoint did more than one database operation per call. Chapter 15 didn't add login to the CLI, because the CLI is a single-user tool by nature. These aren't coincidences — they're one consistent line of reasoning: infrastructure should answer a real need, not a hypothetical one — a theme this final chapter returns to, now at the scale of the whole project.

One more thing worth stating plainly at the end: several times during the course, tests (chapter 09: `capsys` can't see `print_err`; chapter 16: `monkeypatch` doesn't touch `users_storage.py` because of a bad import) and `mypy --strict` (chapter 10: `log_command` mistyped via `ParamSpec`; chapter 17: `Settings()` without the plugin) caught **real** bugs, not textbook hypotheticals. That's the practical case for why chapters 09/10/16 exist at all, rather than being a course formality.

**The "senior polish" checklist.**

*Configuration* — done in chapter 17 (`pydantic-settings`, a required `SECRET_KEY` with no default). What's still missing for a genuinely mature project: separate configuration profiles for dev/staging/prod (right now the same `.env`/environment variables apply everywhere), validating not just the type but the content of a secret (an explicit minimum-length check on `SECRET_KEY`, not just PyJWT's warning), and a way to rotate secrets without downtime.

*Logging* — structured as JSON (chapter 17), but missing a **request id**: right now, if two requests run concurrently (chapters 12/16), their log lines interleave in the same output stream with no way to tell which line belongs to which request. The real fix is generating a unique id when a request enters the middleware, storing it in context (via `contextvars`, for instance), and attaching it to every log entry produced within that request. Also, structured logs to `stdout` are only half the journey: in production they still need to be **collected** and shipped somewhere searchable and aggregatable (Fluentd/Vector/Promtail feeding into Loki/ELK/CloudWatch) — logs becoming JSON doesn't by itself mean they're going anywhere.

*Graceful shutdown* — a topic the project hasn't touched at all yet. Our `lifespan` (chapters 13/17) does nothing after `yield` today — and that's not an oversight, it's a direct consequence of chapter 08's architectural choice: the storage layer opens and closes a **separate** connection on every call, rather than holding one long-lived pool — so there's simply nothing to close in an orderly way when the process stops. If a connection pool were used instead (which becomes necessary moving to Postgres — see below), code after `yield` would be mandatory: `await pool.close()`, waiting for already-started database calls to finish before closing the pool. Separately from application code: the ASGI server (`uvicorn`) already knows how to finish in-flight HTTP requests on `SIGTERM` rather than cutting them off mid-response — but in an orchestrator (Kubernetes), one more thing matters: the **readiness** check should start failing immediately on receiving the stop signal, before the grace period even elapses, so new traffic stops arriving while old requests finish up. Our one `/health` endpoint (chapter 17) covers both liveness ("the process is alive") and readiness ("ready to accept new traffic") at once — in real production these are usually two separate endpoints with different logic.

*Rate limiting* — also entirely absent. The idea is simple (don't let more than N requests per unit of time through from one client/token), and the complexity is in where to keep the counter: for a single process instance, an in-memory counter is enough (a token bucket/sliding window algorithm), but the moment the app runs as several replicas at once (which real traffic eventually demands), an in-memory counter on one process knows nothing about requests that landed on a different replica — the limit's state has to move into shared storage (usually Redis). The FastAPI ecosystem has ready-made libraries for this (`slowapi`, built on Starlette middleware, for instance) — implementing the limiting algorithm from scratch is almost never worth it.

**Where to grow next.**

*Postgres instead of SQLite.* Swapping the database isn't about SQL syntax (it barely changes) — it's about SQLite being an embedded file, while Postgres is a separate network service. That carries three consequences: (1) a real async driver for Postgres specifically is needed (`asyncpg` or `psycopg` in async mode), replacing `aiosqlite`; (2) opening a new TCP connection on **every** storage-function call (our current pattern since chapter 08) becomes expensive and doesn't scale — this is exactly where a **connection pool** earns its keep, the one deferred back in chapter 14 because it wasn't needed then; (3) `CREATE TABLE IF NOT EXISTS` on every startup stops being a sufficient way to manage the schema — a migration tool (Alembic) is needed, one that explicitly versions table-structure changes and lets you roll them back.

*Celery for background work.* Anything that shouldn't hold up the HTTP response — sending an email notification when a task is completed, generating a daily summary, heavy batch processing — is a candidate for moving off to the background. We already have `asyncio`/FastAPI's `BackgroundTasks` for lightweight, one-off work that doesn't need to outlive the process — but if the work needs to: survive a process restart, automatically retry on failure, run on a machine physically separate from the web server — a full task broker is needed. Celery, in that role, is a queue (Redis/RabbitMQ as the message broker) plus separate worker processes pulling jobs off the queue independently of whether the web server that enqueued them is even still alive.

### Parallels with JS/TS/Node:

- Request ids in logs are the same pattern as `express-request-id`/`AsyncLocalStorage` in Node, for tracing one request through every log line it produces.
- Graceful shutdown in Node services is the same idea (finish active connections on `SIGTERM`, don't cut them off abruptly), just implemented via `server.close()` instead of an ASGI lifespan.
- Celery ~ Bull/BullMQ in the Node ecosystem — a queue with a broker (Redis) and separate worker processes; the meaning and architectural role are identical, only the specific library differs.
- Moving from SQLite to Postgres with a connection pool is the same logic as moving from `better-sqlite3` to `pg`/Prisma with a pool in a Node app: an embedded file vs. a network service with a limited number of simultaneous connections.

## What we're adding to the project

Nothing — this is a review chapter, with no new code. Its job isn't to bolt one more feature onto `taskman`, but to honestly assess what "serious, mature" infrastructure is already there, and what's been deliberately deferred, waiting for a real need to justify it.

## Worked solution

An example of such an audit — not the only correct one, but a sample of the kind of reasoning expected here.

**1. Checklist against the current state:**

- *Configuration*: done (`pydantic-settings`, `SECRET_KEY` with no default, `.env.example` committed). Missing: separate dev/prod profiles, explicit validation of the secret's length.
- *Logging*: JSON structure is there (chapter 17). Missing: a request id to trace one request across several log lines, and actually shipping logs anywhere beyond the container's `stdout`.
- *Graceful shutdown*: not implemented, deliberately, and at today's scale (SQLite, a connection per call) that's justified: there's simply nothing to close after `yield`.
- *Rate limiting*: entirely absent. For a single instance with no external traffic, not critical; becomes necessary the moment the service gets real, untrusted clients.

**2. What to add first, and why.** Out of the whole list — a request id in the logs, not rate limiting or Postgres. Justification: a concrete failure scenario — a user reports "my task didn't get created," and the container's logs for that second show a dozen interleaved lines from different requests (chapter 16's concurrency test explicitly showed that parallel requests aren't hypothetical, they're the norm). Without a request id, there's no reliable way to reconstruct what happened to THIS specific request, short of guessing from matching timestamps. This is a cheap change (one line in the middleware plus `contextvars`) that closes a concrete, already-observed blind spot — unlike rate limiting or Postgres, neither of which solves any real problem the project has today.

**3. A Postgres migration sketch:**

- `pyproject.toml`: `aiosqlite` gets replaced with `asyncpg` (or `psycopg[binary,pool]`); the driver is added to `dependencies`, and probably `alembic` to `dev` dependencies.
- `storage/sqlite_storage.py` (or its renamed counterpart, `postgres_storage.py`): `db_connection()` stops opening a new connection on every call — instead, one pool is created at app startup (in `lifespan`, before `yield`), and `db_connection()` borrows a connection **from the pool** for the duration of the operation, returning it rather than closing it. `DB_PATH` is replaced with `DATABASE_URL` (a network connection string, not a file path).
- `CREATE TABLE IF NOT EXISTS` in `init_db()` is replaced with running Alembic migrations at startup (or as a separate deploy step, before the app itself starts).
- Unchanged: `models/`, and all the code in `cli/` and `api/` that accesses data exclusively through the `TaskStorage` protocol (chapter 10) — this is exactly what that protocol was introduced for.

**4. A Celery candidate.** Sending an email notification when a `high`-priority task is created ("you have an urgent task"). The critical property is "retries on failure": if the external mail service is briefly unavailable at the exact moment of the HTTP request, `BackgroundTasks` simply loses that attempt without a trace, while a Celery task stays queued and gets retried per the worker's policy — the user gets the email a bit later, not never.

**5. A moment where intuition was wrong.** Chapter 16: it intuitively seemed obvious that the `db` fixture, with its in-memory connection and `monkeypatch`, fully isolated the tests from the real file on disk — the code looked correct on read. Only a real run of the full test suite showed that `users_storage.py` was writing to the actual `taskman.db`, because it had imported the function by name instead of the module as a whole (chapter 05). Without running the tests, this bug would have stayed unnoticed — it doesn't show up reading the code, and it doesn't show up in the real running application (there's no monkeypatch there at all) — only when trying to test, in isolation, code that had never been checked that rigorously before.

<summary>Answers</summary>

1. Because the storage layer (chapters 08/12) opens a **separate** database connection for every individual call and closes it immediately when it's done — there's simply no long-lived, shared resource in the system (a connection pool, a background worker, a file descriptor outliving one request) that would need explicit closing when the process stops. "Graceful shutdown = code after `yield`" is the general template for systems that DO have such a resource; our specific architectural choice doesn't, so the template formally applies, but has nothing to fill it with.
2. Each app replica is a separate process with its own memory; a request counter held in one replica's RAM has no visibility into requests served by other replicas of the same service. If a limit needs to apply to a client regardless of which replica happened to handle their request (and it usually does), the counter's state can't live in one process's memory — it has to live in storage shared across all replicas, which is why Redis is the typical choice: a single source of truth every replica consults equally.
3. `asyncio.create_task`/`BackgroundTasks` live strictly within the lifetime of the process that started them: if the process restarts or crashes before the task finishes, it's simply lost without a trace, and there's no retry. Celery stores tasks in a separate, persistent broker (Redis/RabbitMQ) — they survive both the web server and any specific worker crashing, can automatically retry per a configured policy on failure, and run on a machine physically separate from the web server process. The choice depends on which of these three properties is actually needed for the specific piece of work: if it's lightweight, not critical if lost, and fits within one request's lifecycle, `BackgroundTasks` is enough; if even one of the three is genuinely required, a full broker is needed.
4. Because `TaskStorage` describes the **shape** of interacting with the storage layer (what methods exist, what types they take and return), not how those methods are implemented underneath. Code in `cli/`/`api/` calls `db.add_task(...)`/`db.list_tasks(...)` and so on, never looking inside the concrete implementation (`sqlite_storage.py`) — swapping that implementation for a module talking to Postgres through a connection pool, but satisfying the same protocol, changes nothing from the point of view of the code calling those functions. That's the direct, practical payoff of an investment made in chapter 10, long before the question of switching databases ever came up.
5. General statement: infrastructure added "for later" carries a real cost today (more moving parts, more code to maintain, more surface for bugs) in exchange for a benefit that may never materialize, and if it does, often not in the shape you predicted in advance. A concrete example from the course: chapter 14 explicitly declined to introduce the "one session per request" pattern for the database, even though it's standard practice in many real FastAPI applications — the justification was precisely that none of the project's three endpoints at that point did more than one storage operation per call, so the very reason that would justify the pattern's complexity simply didn't exist. The same move shows up in chapter 11, which explicitly demonstrated that `multiprocessing` isn't "better" than `threading` by default — it's only justified when there's a genuine need for parallelism on CPU-bound work.

## Common mistake

Two opposite, equally real mistakes close out this course.

The first is seeing a checklist like this one and wanting to adopt all of it at once, regardless of whether it's needed right now: adding Postgres because "it's more serious," standing up Celery because "that's what real projects do," turning on rate limiting because "what if we need it." Every one of these adds real operational complexity — more services to deploy, more configuration to keep in sync, more places something can break — in exchange for a benefit that, at the project's current scale, has nowhere to come from. The whole course, from chapter 05 (don't over-complicate the package structure ahead of time) to chapter 14 (don't introduce a session-per-request without a real multi-step transaction), consistently demonstrated the opposite principle: infrastructure gets introduced once its absence is already causing concrete, observable pain — not before.

The second mistake is the mirror image, and no less real: getting the project to a "it works" state, walking through a checklist like this one exactly once, and never coming back to it, treating the matter as permanently settled. A pet project serving one user on one machine today might suddenly be serving a hundred tomorrow — and that's exactly when every item that seemed irrelevant "for now" surfaces at once. This checklist isn't a one-time box to tick before the first deployment — it's a set of questions worth revisiting every time the project's real scale or context of use changes — which is exactly the same discipline as writing tests or running `mypy --strict`: not because some formality demands it, but because that's precisely how this course, more than once, found real problems instead of imagined ones.
