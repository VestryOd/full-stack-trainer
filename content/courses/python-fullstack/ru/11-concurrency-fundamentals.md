# GIL, потоки и процессы — концептуальный мост к asyncio

## Теория

**Что такое GIL.** Global Interpreter Lock — единственный мьютекс в CPython (это деталь конкретно реализации CPython, а не языка Python как спецификации — у Jython/IronPython его нет вовсе, а в CPython 3.13+ появилась экспериментальная "free-threaded"-сборка без GIL, PEP 703, пока не режим по умолчанию), гарантирующий, что байткод Python в любой момент времени исполняет **ровно один** поток, даже на многоядерной машине. GIL появился на заре CPython как простое решение конкретной проблемы: сборка мусора в CPython основана на подсчёте ссылок (reference counting), а инкремент/декремент счётчика ссылок сам по себе не потокобезопасен без какой-то блокировки. Вместо тонкой, поэлементной блокировки (сложной и, как показала практика ранних экспериментов, замедляющей однопоточный код) выбрали одну глобальную блокировку на весь интерпретатор.

Практически это означает: можно создать сколько угодно потоков (`threading.Thread`), и ОС будет по-настоящему переключать их на уровне ядра — но исполнять байткод Python в любой конкретный момент времени будет только тот поток, у которого сейчас "в руках" GIL. CPython периодически заставляет исполняющийся поток отдать GIL — по времени (настраивается через `sys.setswitchinterval`, по умолчанию каждые ~5 мс) и, что важно, **сразу при входе в блокирующий вызов** (сетевой запрос, чтение файла, `time.sleep`) — на это время GIL явно освобождается, и другой поток может его подхватить.

**Почему это НЕ то же самое, что однопоточный event loop в Node — частая путаница у JS-разработчиков.** Услышав "в любой момент времени исполняется только один поток", легко решить: "а, это то же самое, что у Node — один поток, всё по очереди, просто по-другому называется". Это не так, и разница принципиальна:

```txt
Node:
  Один-единственный OS-поток исполняет ваш JS-код. Точка. Никакого
  переключения между несколькими потоками для вашего кода не происходит
  вообще — конкурентность для I/O даёт event loop + libuv (главы про
  Node в content/topics), а не несколько потоков, борющихся за очередь.

Python (CPython) с GIL:
  РЕАЛЬНО существует несколько OS-потоков (threading.Thread), и ОС
  по-настоящему переключает их на уровне ядра (preemptive scheduling).
  GIL — это дополнительный мьютекс ПОВЕРХ уже реально многопоточной
  модели, ограничивающий, что байткод исполняет только один поток
  зараз — а не "весь Python однопоточен по архитектуре", как в Node.
```

Практическое следствие этой разницы — там, где обе модели ведут себя *по-разному*, а не одинаково: если в Node случайно написать синхронный, тяжёлый по CPU код в обработчике — он блокирует **абсолютно всё**, весь процесс, потому что другого потока для чего угодно ещё просто не существует. Если то же самое сделать в Python с несколькими `threading.Thread`, CPython всё равно периодически будет переключать GIL между потоками (по таймеру) — то есть другие потоки получат **какие-то** кванты времени, просто настоящего ускорения от этого не будет (см. ниже) — это не "то же самое, что блокировка Node", это архитектурно другая ситуация с внешне похожим, но не идентичным результатом.

**Когда GIL мешает (CPU-bound), а когда — нет (I/O-bound).**

Для **CPU-bound** работы (чистые вычисления в байткоде Python: циклы, арифметика, парсинг) — GIL мешает по-настоящему: сколько потоков ни создавай, байткод в любой момент времени выполняет только один из них, поэтому суммарная работа не ускоряется, а на переключение GIL между потоками ещё и тратится время. `threading` для CPU-bound задач в Python — не инструмент ускорения.

Для **I/O-bound** работы (сеть, диск, ожидание ответа от БД) GIL **не мешает**, потому что на время блокирующего вызова CPython явно отпускает GIL — другой поток может исполняться, пока первый ждёт ответа от ОС. Здесь `threading` даёт реальный, измеримый выигрыш: суммарное время нескольких конкурентных I/O-ожиданий приближается к времени **самого медленного** из них, а не к сумме всех.

Важная оговорка для полноты: некоторые C-расширения (например, тяжёлые вычислительные части numpy) сами явно освобождают GIL на время долгих C-циклов — то есть "CPU-bound = GIL мешает" верно для чистого Python-байткода, но не абсолютно для любого CPU-bound кода вообще, если под капотом работает C-код, который сам управляет GIL.

**`threading` vs `multiprocessing` — разный инструмент для разной задачи.**

```python
import threading

t = threading.Thread(target=fn, args=(...,))
t.start()
t.join()
```

Лёгкий, разделяет память процесса (все потоки видят одни и те же объекты) — подходит для I/O-bound конкурентности; для CPU-bound не даёт параллелизма из-за GIL.

```python
import multiprocessing

p = multiprocessing.Process(target=fn, args=(...,))
p.start()
p.join()
```

Тяжелее (отдельный процесс, отдельный интерпретатор, отдельный GIL — GIL просто не мешает, потому что у каждого процесса он **свой**), реально исполняется параллельно на разных ядрах — подходит для CPU-bound; данные между процессами по умолчанию не разделяются, а передаются через сериализацию (pickle), а не через общую память.

Полезная параллель для JS-разработчика: Node's Worker Threads — тоже отдельные потоки со своим V8-изолятом и своей кучей, данные между ними по умолчанию тоже не разделяются напрямую, а передаются через сообщения/сериализацию — концептуально это ближе к `multiprocessing.Process` в Python, чем можно было бы подумать по названию "поток". И Node, и Python в конце концов приходят к одному и тому же архитектурному решению для настоящего параллелизма CPU-bound работы: изолированный контекст исполнения + передача данных через сообщения, а не свободно разделяемая мутируемая память.

### Параллели с JS/TS/Node:

- Node — один OS-поток для JS в принципе; Python с GIL — реально несколько OS-потоков, но лишь один исполняет байткод в конкретный момент. Похожий внешний эффект ("один за раз"), разная архитектура.
- Синхронный CPU-bound код в Node блокирует процесс целиком (другого потока просто нет); тот же код в Python на нескольких `threading.Thread` всё равно будет периодически переключаться между потоками — но без реального ускорения.
- I/O-bound конкурентность: у Node — через event loop на одном потоке; у Python — через несколько реальных потоков, между которыми GIL передаётся во время блокирующих вызовов. Разные механизмы, схожий практический результат.
- `multiprocessing.Process` в Python и Worker Threads в Node решают одну и ту же задачу (настоящий параллелизм для CPU-bound работы) похожим способом: изолированный контекст + сообщения вместо разделяемой памяти.

3. **I/O-bound + threading.** Функция, имитирующая блокирующий I/O через `time.sleep(1)`. Замерьте последовательный вызов дважды и вызов через два потока.

## Разбор решения

Эксперимент 1 — CPU-bound работа через `threading`:

```python
import threading
import time


def cpu_bound_work(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 80_000_000

start = time.perf_counter()
cpu_bound_work(N)
cpu_bound_work(N)
print(f"sequential (2x, one thread):  {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
t1 = threading.Thread(target=cpu_bound_work, args=(N,))
t2 = threading.Thread(target=cpu_bound_work, args=(N,))
t1.start()
t2.start()
t1.join()
t2.join()
print(f"two threads (same work):      {time.perf_counter() - start:.2f}s")
```

Реальный замер (11-ядерная машина):

```txt
sequential (2x, one thread):  6.17s
two threads (same work):      5.66s
```

Два потока НЕ дают ускорения, близкого к 2x — разница (~8%) укладывается в шум планировщика и случайные окна перекрытия вокруг передачи GIL, а не в настоящий параллелизм. GIL продолжает пускать к исполнению байткода только один поток в любой момент — оба потока просто по очереди получают короткие кванты времени.

Эксперимент 2 — та же CPU-bound работа через `multiprocessing`:

```python
import multiprocessing
import time


def cpu_bound_work(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 80_000_000

if __name__ == "__main__":
    start = time.perf_counter()
    cpu_bound_work(N)
    cpu_bound_work(N)
    print(f"sequential (2x, one process): {time.perf_counter() - start:.2f}s")

    start = time.perf_counter()
    p1 = multiprocessing.Process(target=cpu_bound_work, args=(N,))
    p2 = multiprocessing.Process(target=cpu_bound_work, args=(N,))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
    print(f"two processes (same work):   {time.perf_counter() - start:.2f}s")
```

Реальный замер:

```txt
sequential (2x, one process): 6.31s
two processes (same work):   3.26s
```

~48% сокращения времени — близко к теоретическим 2x для двух по-настоящему параллельных процессов на разных ядрах. Разница с экспериментом 1 — не в коде задачи (он идентичен), а исключительно в том, что у каждого процесса свой собственный интерпретатор и свой собственный GIL, который не конкурирует с GIL другого процесса.

Эксперимент 3 — I/O-bound работа через `threading`:

```python
import threading
import time


def io_bound_work() -> None:
    time.sleep(1)  # имитация блокирующего сетевого/дискового ожидания


start = time.perf_counter()
io_bound_work()
io_bound_work()
print(f"sequential (2x, one thread): {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
t1 = threading.Thread(target=io_bound_work)
t2 = threading.Thread(target=io_bound_work)
t1.start()
t2.start()
t1.join()
t2.join()
print(f"two threads (same work):     {time.perf_counter() - start:.2f}s")
```

Реальный замер:

```txt
sequential (2x, one thread): 2.01s
two threads (same work):     1.01s
```

Почти идеальное перекрытие — ровно потому, что `time.sleep` (и любой блокирующий вызов, уходящий на уровень ОС) явно отпускает GIL на время ожидания. Пока один поток "спит", GIL свободен, и другой поток может исполняться — оба ожидания перекрываются, и суммарное время приближается к времени одного ожидания, а не к сумме двух.

## Проверь себя

1. Почему создание десяти `threading.Thread` в Python не даёт десятикратного ускорения чисто вычислительной задачи, даже на десятиядерной машине?
2. В чём именно принципиальная разница между "в Node в любой момент времени исполняется один поток" и "в CPython в любой момент времени байткод исполняет один поток", если оба утверждения звучат почти одинаково?
3. Почему блокирующий вызов вроде `time.sleep()` или сетевого запроса позволяет GIL "отпуститься", а обычный Python-цикл — нет? Что именно в природе блокирующего вызова делает это возможным?
4. Если задача CPU-bound, почему `multiprocessing.Process` даёт реальное ускорение, а `threading.Thread` — нет, при том что оба технически создают что-то похожее на "параллельно исполняющуюся единицу работы"?
5. Чем `multiprocessing.Process` в Python концептуально похож на Worker Threads в Node, а не на "ещё один поток в том же смысле, что и threading.Thread"?

<summary>Ответы</summary>

1. Потому что GIL гарантирует, что байткод Python в любой момент времени исполняет ровно один поток, вне зависимости от того, сколько ядер доступно и сколько потоков создано. Десять потоков просто по очереди получают короткие кванты процессорного времени на одном ядре (с точки зрения исполнения именно Python-байткода) — суммарный объём вычислительной работы, которую нужно проделать, не уменьшается и не распределяется по ядрам, поэтому итоговое время примерно равно времени последовательного выполнения той же работы, плюс небольшие накладные расходы на переключение между потоками.
2. В Node "один поток в любой момент времени" — это буквально единственный существующий OS-поток для вашего кода: переключаться не с чем, других потоков, борющихся за исполнение, попросту нет. В CPython "байткод исполняет один поток" описывает мьютекс поверх **реально существующих нескольких** OS-потоков, которые ОС по-настоящему переключает на уровне ядра (preemptive scheduling) — GIL лишь ограничивает, какой из них имеет право исполнять именно Python-байткод прямо сейчас. Внешне оба утверждения про "один за раз" звучат похоже, но за ними стоят принципиально разные архитектуры — с разными практическими следствиями (см. вопрос 4 и I/O-bound эксперимент).
3. Блокирующий вызов передаёт управление операционной системе и ждёт её ответа (данные с диска, пакет из сети, истечение таймера) — в это время интерпретатору Python физически нечего исполнять для этого потока, поэтому CPython явно освобождает GIL на время ожидания, отдавая его другому потоку, у которого действительно есть байткод для выполнения. Обычный Python-цикл, наоборот, всё время что-то реально вычисляет на уровне байткода — отпустить GIL можно только принудительно, по таймеру переключения, а не потому, что потоку "нечего делать".
4. `multiprocessing.Process` создаёт полностью отдельный процесс со своим собственным экземпляром интерпретатора Python и, соответственно, своим собственным GIL — GIL одного процесса физически не может помешать байткоду другого процесса исполняться одновременно на другом ядре, потому что это два независимых мьютекса в двух независимых адресных пространствах. `threading.Thread` создаёт потоки **внутри одного и того же** процесса, с одним и тем же, общим на всех, GIL — сколько бы потоков ни было, право исполнять байткод Python в любой момент есть только у одного из них.
5. Оба решают задачу "получить настоящий параллелизм для тяжёлой по CPU работы" одним и тем же архитектурным способом: изолированный контекст исполнения (отдельный процесс с собственной памятью у Python, отдельный поток со своим V8-изолятом и кучей у Node) плюс обмен данными через сообщения/сериализацию, а не через свободно разделяемую мутируемую память. И `threading.Thread` в Python, и обычный однопоточный код в самом Node этому определению не соответствуют — оба делят один общий контекст исполнения (общую память и, в случае Python, общий GIL), а не изолируют вычисления друг от друга.

## Частая ошибка

Самая частая ошибка JS-разработчика при первом знакомстве с GIL — сделать ровно тот вывод, который явно разобран выше: "у Python GIL, значит, он тоже однопоточный, как Node, просто под другим названием" — и на основе этого решить, что `threading` в Python вообще бесполезен, раз "всё равно один поток за раз". Это заводит в тупик с обеих сторон: `threading` в Python **действительно** бесполезен для ускорения CPU-bound работы (тут интуиция не подводит), но абсолютно рабочий и идиоматичный инструмент для I/O-bound конкурентности — то есть ровно те задачи, для которых JS-разработчик привычно использует единственный поток с event loop в Node. Спутав архитектурную деталь (GIL) с общим выводом "многопоточность в Python бессмысленна", легко упустить, что `threading` в Python для I/O-bound кода даёт результат, практически неотличимый по духу от того, что даёт event loop в Node — просто через другой механизм.

Вторая типичная ошибка, зеркальная первой, — увидеть, что `multiprocessing` даёт реальное ускорение для CPU-bound задачи, и решить, что это "просто более мощная версия threading", которую стоит использовать всегда и для всего, включая I/O-bound работу. `multiprocessing` — это не "threading, только лучше": каждый процесс — это отдельный интерпретатор с собственной памятью, запуск процесса заметно дороже запуска потока, а данные между процессами по умолчанию не разделяются напрямую, а сериализуются через pickle при каждой передаче — то есть накладные расходы, оправданные для тяжёлых, редких CPU-bound задач, становятся чистыми потерями для лёгких, частых I/O-bound операций, где `threading` (или, что ещё уместнее, `asyncio` из следующей главы) окажется и быстрее, и заметно легче по ресурсам.
