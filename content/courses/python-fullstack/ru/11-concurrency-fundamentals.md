# GIL, потоки и процессы — концептуальный мост к asyncio

## Теория

**Что такое GIL.** Global Interpreter Lock — единственный мьютекс в CPython. Он гарантирует, что байткод Python в любой момент времени исполняет **ровно один** поток, даже на многоядерной машине.

GIL — деталь конкретно реализации CPython, а не языка Python как спецификации. У Jython и IronPython его нет вовсе. В CPython 3.13+ появилась экспериментальная "free-threaded"-сборка без GIL, описанная в PEP 703 (Python Enhancement Proposal). Режимом по умолчанию она пока не стала.

GIL появился на заре CPython как простое решение конкретной проблемы. Сборка мусора в CPython основана на подсчёте ссылок (reference counting), а инкремент и декремент счётчика ссылок сами по себе не потокобезопасны без какой-то блокировки.

Альтернативой была тонкая, поэлементная блокировка. Она сложна, и ранние эксперименты показали, что она замедляет однопоточный код. Поэтому выбрали одну глобальную блокировку на весь интерпретатор.

Практически это означает две вещи. Можно создать сколько угодно потоков (`threading.Thread`), и ОС (операционная система) будет по-настоящему переключать их на уровне ядра. Но исполнять байткод Python в любой конкретный момент времени будет только тот поток, у которого сейчас "в руках" GIL.

CPython периодически заставляет исполняющийся поток отдать GIL. Во-первых, по времени: интервал настраивается через `sys.setswitchinterval` и по умолчанию равен примерно 5 мс. Во-вторых, что важнее, **сразу при входе в блокирующий вызов** — сетевой запрос, чтение файла, `time.sleep`. На это время GIL явно освобождается, и другой поток может его подхватить.

**Почему это не то же самое, что однопоточный event loop в Node — частая путаница у JS-разработчиков.** Услышав "в любой момент времени исполняется только один поток", легко решить, что Node делает то же самое, просто под другим названием. Это не так, и разница принципиальна:

```txt
Node:
  Один-единственный поток ОС исполняет ваш JS-код. Точка. Никакого
  переключения между несколькими потоками для вашего кода не
  происходит вообще: конкурентность для I/O даёт event loop плюс
  libuv (главы про Node в content/topics), а не несколько
  потоков, борющихся за очередь.

Python (CPython) с GIL:
  Реально существует несколько потоков ОС (threading.Thread), и
  ОС по-настоящему переключает их на уровне ядра (preemptive
  scheduling). GIL — это дополнительный мьютекс поверх уже
  реально многопоточной модели. Он ограничивает исполнение
  байткода одним потоком зараз. Это не "весь Python однопоточен
  по архитектуре", как в Node.
```

Практическое следствие этой разницы видно там, где обе модели ведут себя *по-разному*, а не одинаково. Напишите в обработчике Node синхронный код, тяжёлый по CPU (central processing unit, центральный процессор), — и он заблокирует **абсолютно всё**, весь процесс. Другого потока, на котором могло бы исполниться что-то ещё, просто не существует.

Если то же самое сделать в Python с несколькими `threading.Thread`, результат будет другим. CPython всё равно периодически переключает GIL между потоками по таймеру, поэтому другие потоки получат **какие-то** кванты времени. Настоящего ускорения от этого не будет (см. ниже). То есть это не "то же самое, что блокировка Node": снаружи похоже, а внутри архитектура другая.

**Когда GIL мешает (CPU-bound), а когда — нет (I/O-bound).**

**CPU-bound** работа — это чистые вычисления в байткоде Python: циклы, арифметика, парсинг. Здесь GIL мешает по-настоящему. Сколько потоков ни создавай, байткод в любой момент времени выполняет только один из них, поэтому суммарная работа не ускоряется. Вдобавок время тратится на само переключение GIL между потоками. Так что `threading` для CPU-bound задач в Python — не инструмент ускорения.

**I/O-bound** работа ждёт ввода-вывода: сеть, диск, ответ от БД (базы данных). Здесь GIL **не мешает**, потому что на время блокирующего вызова CPython явно отпускает GIL. Другой поток может исполняться, пока первый ждёт ответа от ОС.

Здесь `threading` даёт реальный, измеримый выигрыш: суммарное время нескольких конкурентных ожиданий приближается к времени **самого медленного** из них, а не к сумме всех.

Одна оговорка для полноты. Некоторые C-расширения сами явно освобождают GIL на время долгих C-циклов; пример — тяжёлые вычислительные части numpy. То есть правило "CPU-bound значит GIL мешает" верно для чистого Python-байткода. Для любого CPU-bound кода вообще оно не абсолютно: под капотом может работать C-код, который сам управляет GIL.

**`threading` vs `multiprocessing` — разный инструмент для разной задачи.**

```python
import threading

t = threading.Thread(target=fn, args=(...,))
t.start()
t.join()
```

Лёгкий, разделяет память процесса: все потоки видят одни и те же объекты. Подходит для I/O-bound конкурентности. Для CPU-bound параллелизма не даёт из-за GIL.

```python
import multiprocessing

p = multiprocessing.Process(target=fn, args=(...,))
p.start()
p.join()
```

Тяжелее: отдельный процесс, отдельный интерпретатор, отдельный GIL. GIL просто перестаёт мешать, потому что у каждого процесса он **свой**. Такой код реально исполняется параллельно на разных ядрах и потому подходит для CPU-bound. Данные между процессами по умолчанию не разделяются: они передаются через сериализацию (pickle), а не через общую память.

Полезная параллель для JS-разработчика: Worker Threads в Node — тоже отдельные потоки со своим V8-изолятом и своей кучей. Данные между ними по умолчанию тоже не разделяются напрямую, а передаются через сообщения и сериализацию. Концептуально это ближе к `multiprocessing.Process` в Python, чем можно было бы подумать по названию "поток".

И Node, и Python в конце концов приходят к одному и тому же архитектурному решению для настоящего параллелизма CPU-bound работы. Это изолированный контекст исполнения плюс передача данных через сообщения, а не свободно разделяемая мутируемая память.

### Параллели с JS/TS/Node:

- Node — один поток ОС для JS в принципе. Python с GIL — реально несколько потоков ОС, но лишь один исполняет байткод в конкретный момент. Похожий внешний эффект ("один за раз"), разная архитектура.
- Синхронный CPU-bound код в Node блокирует процесс целиком, потому что другого потока просто нет. Тот же код в Python на нескольких `threading.Thread` всё равно будет периодически переключаться между потоками, но без реального ускорения.
- I/O-bound конкурентность: у Node — через event loop на одном потоке; у Python — через несколько реальных потоков, между которыми GIL передаётся во время блокирующих вызовов. Разные механизмы, схожий практический результат.
- `multiprocessing.Process` в Python и Worker Threads в Node решают одну и ту же задачу (настоящий параллелизм для CPU-bound работы) похожим способом: изолированный контекст + сообщения вместо разделяемой памяти.

## Практическое задание

Вместо изменений в `taskman` — три маленьких, отдельных скрипта-эксперимента (можно писать вне пакета, в любом scratch-месте). Для каждого — сначала предсказать результат, потом измерить и сравнить с предсказанием.

1. **CPU-bound + threading.** Функция, гоняющая чистый вычислительный цикл на Python (`for i in range(N): total += i * i`) с достаточно большим `N`, чтобы выполнение занимало пару секунд. Замерьте время последовательного вызова функции дважды в одном потоке, затем — вызова через два `threading.Thread`. Ожидаете ли вы ускорение почти в 2 раза?

2. **CPU-bound + multiprocessing.** Та же функция, но через два `multiprocessing.Process` вместо потоков. Замерьте и сравните с экспериментом 1.

3. **I/O-bound + threading.** Функция, имитирующая блокирующий I/O через `time.sleep(1)`. Замерьте последовательный вызов дважды и вызов через два потока.

Вопросы на подумать перед тем, как смотреть разбор:

- В эксперименте 1 сравните числа: они одинаковые, вдвое быстрее или где-то посередине? Что бы это ни оказалось — как это объясняется механикой GIL, а не просто "накладными расходами на потоки"?
- Почему в эксперименте 3 `time.sleep` вообще позволяет потокам "работать одновременно", если GIL разрешает исполнять байткод только одному потоку зараз?

## Разбор решения

Эксперимент 1 — CPU-bound работа через `threading`:

```python
import threading
import time


def cpu_bound_work(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 80_000_000

start = time.perf_counter()
cpu_bound_work(N)
cpu_bound_work(N)
print(f"sequential (2x, one thread):  {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
t1 = threading.Thread(target=cpu_bound_work, args=(N,))
t2 = threading.Thread(target=cpu_bound_work, args=(N,))
t1.start()
t2.start()
t1.join()
t2.join()
print(f"two threads (same work):      {time.perf_counter() - start:.2f}s")
```

Реальный замер (11-ядерная машина):

```txt
sequential (2x, one thread):  6.17s
two threads (same work):      5.66s
```

Два потока **не** дают ускорения, близкого к 2x: разница (~8%) укладывается в шум планировщика и случайные окна перекрытия вокруг передачи GIL, а не в настоящий параллелизм. GIL продолжает пускать к исполнению байткода только один поток в любой момент, и оба потока просто по очереди получают короткие кванты времени.

Эксперимент 2 — та же CPU-bound работа через `multiprocessing`:

```python
import multiprocessing
import time


def cpu_bound_work(n: int) -> int:
    total = 0
    for i in range(n):
        total += i * i
    return total


N = 80_000_000

if __name__ == "__main__":
    start = time.perf_counter()
    cpu_bound_work(N)
    cpu_bound_work(N)
    print(f"sequential (2x, one process): {time.perf_counter() - start:.2f}s")

    start = time.perf_counter()
    p1 = multiprocessing.Process(target=cpu_bound_work, args=(N,))
    p2 = multiprocessing.Process(target=cpu_bound_work, args=(N,))
    p1.start()
    p2.start()
    p1.join()
    p2.join()
    print(f"two processes (same work):   {time.perf_counter() - start:.2f}s")
```

Реальный замер:

```txt
sequential (2x, one process): 6.31s
two processes (same work):   3.26s
```

~48% сокращения времени — близко к теоретическим 2x для двух по-настоящему параллельных процессов на разных ядрах. Разница с экспериментом 1 не в коде задачи: он идентичен. Дело исключительно в том, что у каждого процесса свой собственный интерпретатор и свой собственный GIL, который не конкурирует с GIL другого процесса.

Эксперимент 3 — I/O-bound работа через `threading`:

```python
import threading
import time


def io_bound_work() -> None:
    time.sleep(1)  # имитация блокирующего сетевого/дискового ожидания


start = time.perf_counter()
io_bound_work()
io_bound_work()
print(f"sequential (2x, one thread): {time.perf_counter() - start:.2f}s")

start = time.perf_counter()
t1 = threading.Thread(target=io_bound_work)
t2 = threading.Thread(target=io_bound_work)
t1.start()
t2.start()
t1.join()
t2.join()
print(f"two threads (same work):     {time.perf_counter() - start:.2f}s")
```

Реальный замер:

```txt
sequential (2x, one thread): 2.01s
two threads (same work):     1.01s
```

Почти идеальное перекрытие — ровно потому, что `time.sleep` (и любой блокирующий вызов, уходящий на уровень ОС) явно отпускает GIL на время ожидания. Пока один поток "спит", GIL свободен, и другой поток может исполняться — оба ожидания перекрываются, и суммарное время приближается к времени одного ожидания, а не к сумме двух.

## Проверь себя

1. Почему создание десяти `threading.Thread` в Python не даёт десятикратного ускорения чисто вычислительной задачи, даже на десятиядерной машине?
2. Два утверждения звучат почти одинаково: "в Node в любой момент времени исполняется один поток" и "в CPython в любой момент времени байткод исполняет один поток". В чём именно принципиальная разница между ними?
3. Почему блокирующий вызов вроде `time.sleep()` или сетевого запроса позволяет GIL "отпуститься", а обычный Python-цикл — нет? Что именно в природе блокирующего вызова делает это возможным?
4. Если задача CPU-bound, почему `multiprocessing.Process` даёт реальное ускорение, а `threading.Thread` — нет, при том что оба технически создают что-то похожее на "параллельно исполняющуюся единицу работы"?
5. Чем `multiprocessing.Process` в Python концептуально похож на Worker Threads в Node, а не на "ещё один поток в том же смысле, что и threading.Thread"?

<summary>Ответы</summary>

1. Потому что GIL гарантирует, что байткод Python в любой момент времени исполняет ровно один поток, вне зависимости от того, сколько ядер доступно и сколько потоков создано. Десять потоков просто по очереди получают короткие кванты процессорного времени на одном ядре — с точки зрения исполнения именно Python-байткода. Суммарный объём вычислительной работы не уменьшается и не распределяется по ядрам. Поэтому итоговое время примерно равно времени последовательного выполнения той же работы плюс небольшие накладные расходы на переключение между потоками.
2. В Node "один поток в любой момент времени" — это буквально единственный существующий поток ОС для вашего кода: переключаться не с чем, других потоков, борющихся за исполнение, попросту нет. В CPython "байткод исполняет один поток" описывает мьютекс поверх **реально существующих нескольких** потоков ОС. Эти потоки ОС по-настоящему переключает на уровне ядра (preemptive scheduling), а GIL лишь ограничивает, какой из них имеет право исполнять именно Python-байткод прямо сейчас. Внешне оба утверждения про "один за раз" звучат похоже, но за ними стоят принципиально разные архитектуры с разными практическими следствиями (см. вопрос 4 и I/O-bound эксперимент).
3. Блокирующий вызов передаёт управление операционной системе и ждёт её ответа: данные с диска, пакет из сети, истечение таймера. В это время интерпретатору Python физически нечего исполнять для этого потока. Поэтому CPython явно освобождает GIL на время ожидания и отдаёт его другому потоку, у которого действительно есть байткод для выполнения. Обычный Python-цикл, наоборот, всё время что-то реально вычисляет на уровне байткода. Отпустить GIL можно только принудительно, по таймеру переключения, а не потому, что потоку "нечего делать".
4. `multiprocessing.Process` создаёт полностью отдельный процесс со своим собственным экземпляром интерпретатора Python и, соответственно, своим собственным GIL. GIL одного процесса физически не может помешать байткоду другого процесса исполняться одновременно на другом ядре: это два независимых мьютекса в двух независимых адресных пространствах. А `threading.Thread` создаёт потоки **внутри одного и того же** процесса, с одним и тем же, общим на всех, GIL. Сколько бы потоков ни было, право исполнять байткод Python в любой момент есть только у одного из них.
5. Оба решают задачу "получить настоящий параллелизм для тяжёлой по CPU работы" одним и тем же архитектурным способом. Это изолированный контекст исполнения плюс обмен данными через сообщения и сериализацию, а не через свободно разделяемую мутируемую память. У Python изолированный контекст — отдельный процесс с собственной памятью, у Node — отдельный поток со своим V8-изолятом и кучей. И `threading.Thread` в Python, и обычный однопоточный код в самом Node этому определению не соответствуют. Оба делят один общий контекст исполнения — общую память и, в случае Python, общий GIL — а не изолируют вычисления друг от друга.

## Частая ошибка

Самая частая ошибка JS-разработчика при первом знакомстве с GIL — сделать ровно тот вывод, который разобран выше. Звучит он так: "у Python GIL, значит, он тоже однопоточный, как Node, просто под другим названием". Следующий шаг — решить, что `threading` в Python вообще бесполезен, раз всё равно один поток за раз.

Ошибка именно во втором шаге. Инструмент `threading` в Python **действительно** бесполезен для ускорения CPU-bound работы, тут интуиция не подводит. Но для I/O-bound конкурентности это абсолютно рабочий и идиоматичный инструмент — ровно для тех задач, которые JS-разработчик привычно отдаёт единственному потоку с event loop в Node.

Спутав архитектурную деталь (GIL) с общим выводом "многопоточность в Python бессмысленна", легко упустить важное. Для I/O-bound кода `threading` в Python даёт результат, практически неотличимый по духу от того, что даёт event loop в Node, — просто через другой механизм.

Вторая типичная ошибка зеркальна первой. Вы видите, что `multiprocessing` даёт реальное ускорение для CPU-bound задачи. И решаете, что это просто более мощная версия `threading`, которую стоит использовать всегда и для всего, включая I/O-bound работу.

Но это не "threading, только лучше". Каждый процесс — отдельный интерпретатор с собственной памятью. Запуск процесса заметно дороже запуска потока. Данные между процессами по умолчанию не разделяются напрямую, а сериализуются через pickle при каждой передаче.

Эти накладные расходы оправданы для тяжёлых, редких CPU-bound задач. Для лёгких, частых I/O-bound операций они становятся чистыми потерями. Там `threading` — или, что ещё уместнее, `asyncio` из следующей главы — окажется и быстрее, и заметно легче по ресурсам.
