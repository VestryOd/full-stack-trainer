# Capstone: обзор проекта и куда расти дальше

## Теория

**Пройденный путь — коротко.** `taskman` начался в главе 00 как скелет на `argparse`, печатающий в консоль список в памяти процесса. По пути он последовательно приобрёл:

- типизированные модели вместо голых словарей (`@dataclass`, глава 04);
- пакетную структуру вместо одного файла (глава 05);
- настоящую персистентность вместо памяти процесса (SQLite, глава 08);
- статическую проверку типов как часть повседневной разработки (`mypy --strict`, глава 10);
- полностью асинхронный доступ к данным (глава 12);
- REST (Representational State Transfer) API поверх **того же самого** storage-слоя, ни разу не тронутого ради этого (главы 13–14);
- многопользовательскую аутентификацию (глава 15);
- исчерпывающий набор тестов (глава 16);
- упаковку в контейнер с конфигурацией из окружения (глава 17).

Ключевая архитектурная ставка, которая себя оправдала на всём этом пути, — `TaskStorage`-протокол (глава 10). И CLI (интерфейс командной строки), и API все 8 последующих глав вызывали один и тот же набор функций. Ни один из них ни разу не знал, реализованы ли эти функции через `sqlite3` или `aiosqlite`, через файл или через что-то ещё.

Стоит явно назвать и другую сквозную тему курса. Почти в каждой главе, добавляющей что-то новое, находилось что-то, что **сознательно не добавлялось**. Не потому что забыли, а потому что текущий масштаб проекта этого не требовал.

Глава 06 не добавляла блокировку на запись задач, потому что глава 08 её ещё не ввела. Глава 14 не добавляла сессию на весь запрос, потому что ни один эндпоинт не делал больше одной операции с БД (базой данных) за раз. Глава 15 не добавляла логин в CLI, потому что CLI — однопользовательский инструмент по своей природе.

Это не совпадения, а единая линия рассуждения: инфраструктура должна отвечать на реальную, а не гипотетическую потребность. К этой теме глава возвращается напоследок, уже в масштабе всего проекта.

Ещё одну вещь стоит явно проговорить в конце. Несколько раз за курс тесты и `mypy --strict` находили **настоящие** ошибки, а не гипотетические примеры для учебника.

Тесты нашли две: `print_err` не виден `capsys` (глава 09) и `monkeypatch` не действует на `users_storage.py` из-за неправильного импорта (глава 16). Статическая проверка нашла ещё две: `log_command` неверно типизирован через `ParamSpec` (глава 10) и `Settings()` без плагина (глава 17).

Это практический аргумент в пользу того, зачем вообще нужны главы 09/10/16, а не просто формальность курса.

**Чеклист "senior polish".**

*Конфигурация* — сделана в главе 17 (`pydantic-settings`, обязательный `SECRET_KEY` без дефолта). Для по-настоящему взрослого проекта не хватает трёх вещей:

- разных профилей конфигурации на dev, staging и prod (сейчас один и тот же `.env` и одни переменные окружения для всех сред);
- валидации не только типа, но и содержимого секрета — например, явной проверки минимальной длины `SECRET_KEY`, а не одного лишь предупреждения от библиотеки `PyJWT`;
- механизма ротации секретов без простоя сервиса.

*Логирование* — структурировано в JSON (глава 17), но не хватает **request id**. Сейчас, если два запроса выполняются конкурентно (глава 12/16), их лог-строки перемешиваются в общем потоке вывода. Ничто не подсказывает, к какому именно запросу какая строка относится.

Реальное решение состоит из трёх шагов. Генерировать уникальный id на входе в middleware. Класть его в контекст, например через `contextvars`. Добавлять его во все лог-записи, порождённые в рамках этого запроса.

Структурированные логи в `stdout` — это к тому же только половина пути. В продакшене их ещё нужно **забирать** и складывать туда, где по ним можно искать. Это две отдельные части: агент-сборщик, который читает вывод контейнера, и хранилище логов, куда он их отправляет.

```txt
приложение -> stdout (строки JSON)
  -> агент-сборщик     (Fluentd, Vector или Promtail)
  -> хранилище логов   (Loki, CloudWatch или ELK)
  -> вы ищете по нему
```

ELK — это Elasticsearch, Logstash и Kibana в связке. Сам факт, что логи стали JSON, ещё не значит, что они куда-то долетают.

*Graceful shutdown* — тема, которой в проекте пока вообще не было. Наш `lifespan` (глава 13/17) сегодня ничего не делает после `yield`.

Это не недосмотр, а прямое следствие архитектурного решения главы 08. Storage-слой открывает и закрывает **отдельное** соединение на каждый вызов, а не держит один долгоживущий пул. Поэтому при остановке процесса попросту нечего закрывать организованно.

Если бы вместо этого использовался пул соединений — а он понадобится при переходе на Postgres, см. ниже, — код после `yield` был бы обязателен. Он вызывал бы `await pool.close()` и дожидался завершения уже начатых запросов к БД перед закрытием пула.

Сам сервер тоже помогает. ASGI (Asynchronous Server Gateway Interface) — это протокол между Python-приложением и сервером, который его запускает. Наш ASGI-сервер — `uvicorn`.

Получив SIGTERM, `uvicorn` доигрывает уже начатые HTTP-запросы, а не обрывает их на середине. SIGTERM — это сигнал "пожалуйста, остановись", который оркестратор посылает процессу перед тем, как убить его.

Но оркестратору вроде Kubernetes нужно от приложения кое-что ещё. Останавливающемуся процессу он даёт grace period — несколько секунд на сворачивание работы. Всё это время он продолжает слать новые запросы, если ему не сказать обратного.

Сказать обратное — работа **readiness**-проверки. Она должна начать проваливаться сразу при получении сигнала остановки, чтобы новый трафик уходил на другие реплики, пока здешние запросы дорабатывают.

```txt
пришёл SIGTERM
  -> /readyz начинает отвечать 503  (новый трафик не приходит)
  -> начатые запросы дорабатывают   (это делает uvicorn)
  -> pool.close(), процесс выходит
```

Наш единственный `/health` (глава 17) отвечает и за liveness ("процесс жив"), и за readiness ("готов принимать новый трафик") одновременно. Для реального продакшена это обычно два разных эндпоинта с разной логикой.

*Лимиты / rate limiting* — тоже полностью отсутствует. Идея простая: не пускать больше N запросов в единицу времени с одного клиента или токена. Сложность — в том, где хранить счётчик.

Для одного инстанса процесса достаточно счётчика в памяти. Стандартных алгоритма два: token bucket и sliding window; оба просто считают запросы в скользящем окне времени.

Реальный трафик рано или поздно потребует нескольких реплик сразу. С этого момента счётчик в памяти одного процесса ничего не знает о запросах, попавших на другую реплику. Состояние лимита приходится выносить в общее хранилище, обычно в Redis.

В экосистеме FastAPI для этого есть готовые библиотеки — например, `slowapi`, построенная поверх Starlette middleware. Реализовывать алгоритм лимитирования с нуля почти никогда не оправдано.

**Куда расти дальше.**

*Postgres вместо SQLite.* Замена базы — не про синтаксис SQL (Structured Query Language, язык запросов к базам данных), он почти не меняется. Дело в том, что SQLite — встроенный файл, а Postgres — отдельный сетевой сервис.

Это тянет за собой три следствия:

1. Нужен async-драйвер именно под Postgres — `asyncpg` или `psycopg` в асинхронном режиме — вместо `aiosqlite`.
2. Открывать новое соединение TCP (Transmission Control Protocol) на **каждый** вызов storage-функции — наш текущий паттерн с главы 08. Для сетевого сервиса это становится дорого и не масштабируется. Здесь как раз оправдан **пул соединений**, который отложили в главе 14, потому что тогда он был не нужен.
3. `CREATE TABLE IF NOT EXISTS` при каждом старте перестаёт быть достаточным способом управления схемой. Нужен инструмент миграций вроде Alembic: он явно версионирует изменения структуры таблиц и позволяет откатывать их.

*Celery для фоновых задач.* Всё, что не должно задерживать ответ на HTTP-запрос, — кандидат на вынос в фон. Например: отправка email-уведомления при выполнении задачи, генерация ежедневной сводки, тяжёлая пакетная обработка.

У нас уже есть `asyncio` и `BackgroundTasks` из FastAPI для лёгких, одноразовых операций, живущих не дольше самого процесса. Полноценный брокер задач нужен, когда работа должна уметь одно из трёх:

- переживать перезапуск процесса;
- автоматически повторяться при сбое;
- выполняться на отдельной, физически другой машине от веб-сервера.

Celery в этой роли — очередь, где брокером сообщений выступает Redis или RabbitMQ, плюс отдельные worker-процессы. Эти воркеры разбирают задачи из очереди независимо от того, жив ли веб-сервер, который их туда положил.

### Параллели с JS/TS/Node:

- Request id в логах — тот же паттерн, что `express-request-id`/`AsyncLocalStorage` в Node для сквозной трассировки одного запроса через все логи.
- Graceful shutdown в Node-сервисах — та же идея (дослушать активные соединения на `SIGTERM`, не обрывать резко), просто реализуется через `server.close()` вместо ASGI-lifespan.
- Celery ~ Bull/BullMQ в Node-экосистеме — очередь с брокером (Redis) и отдельными worker-процессами; смысл и архитектурная роль идентичны, различается только конкретная библиотека.
- Переход с SQLite на Postgres с пулом соединений — та же логика, что переход с `better-sqlite3` на `pg` или Prisma в Node-приложении. В обоих случаях встроенный файл превращается в сетевой сервис с ограниченным числом одновременных подключений.

## Разбор решения

Пример такого аудита — не единственно верный, но образец того, какого рода рассуждение здесь ожидается.

**1. Чеклист по текущему состоянию:**

- *Конфигурация*: сделана (`pydantic-settings`, `SECRET_KEY` без дефолта, `.env.example` в репозитории). Не хватает: разделения на профили dev/prod, явной валидации длины секрета.
- *Логирование*: JSON-структура есть (глава 17). Не хватает: request id для трассировки одного запроса через несколько строк лога, реального шиппинга логов куда-либо за пределы `stdout` контейнера.
- *Graceful shutdown*: не реализовано специально, и на сегодняшнем масштабе (SQLite, соединение на вызов) — оправданно: закрывать после `yield` попросту нечего.
- *Rate limiting*: отсутствует полностью. На один инстанс без внешнего трафика — не критично; станет нужным, как только сервис получит реальных, недоверенных клиентов.

**2. Что добавить первым и почему.** Из всего списка — request id в логах, а не rate limiting или Postgres.

Обоснование — конкретный сценарий отказа. Пользователь сообщает "у меня не создалась задача", а в логах контейнера за нужную секунду — десяток вперемешку идущих строк от разных запросов. Тест на конкурентность из главы 16 явно показал, что параллельные запросы — не гипотетика, а норма.

Без request id невозможно достоверно восстановить, что произошло именно с **этим** запросом, не полагаясь на угадывание по совпадению временных меток. Это дешёвое по трудозатратам изменение — одна строка в middleware плюс `contextvars` — и оно устраняет конкретную, уже наблюдаемую слепую зону. Rate limiting и Postgres сегодня не решают ни одной реальной проблемы проекта.

**3. Набросок перехода на Postgres:**

- `pyproject.toml`: `aiosqlite` заменяется на `asyncpg` (или `psycopg[binary,pool]`); в `dependencies` добавляется драйвер плюс, вероятно, `alembic` — в `dev`-зависимости.
- `storage/sqlite_storage.py` (или его переименованный аналог `postgres_storage.py`): `db_connection()` перестаёт открывать новое соединение на каждый вызов. Вместо этого создаётся один пул при старте приложения — в `lifespan`, до `yield`. Дальше `db_connection()` берёт соединение **из пула** на время операции и возвращает его обратно, а не закрывает. `DB_PATH` заменяется на `DATABASE_URL` — строку сетевого подключения, а не путь к файлу.
- `CREATE TABLE IF NOT EXISTS` в `init_db()` заменяется на прогон Alembic-миграций при старте (или отдельным шагом деплоя, до запуска самого приложения).
- Без изменений: `models/`, весь код в `cli/` и `api/`, обращающийся к данным исключительно через `TaskStorage`-протокол (глава 10) — именно ради этого протокол и вводился.

**4. Кандидат на Celery.** Отправка email-уведомления при создании задачи с приоритетом `high` ("у вас появилась срочная задача"). Критичное свойство — "повторяется при сбое".

Допустим, внешний почтовый сервис на секунду недоступен именно в момент HTTP-запроса. `BackgroundTasks` эту попытку просто потеряет без следа. Задача Celery останется в очереди и будет повторена по политике воркера, так что пользователь получит письмо чуть позже, а не никогда.

**5. Момент, где интуиция подвела.** Глава 16: `db`-fixture с in-memory соединением и `monkeypatch` вроде бы полностью изолировала тесты от реального файла на диске. Это казалось очевидным, и код выглядел правильным при чтении.

Только реальный прогон полного набора тестов показал, что `users_storage.py` писал в настоящий `taskman.db`. Он импортировал функцию по имени, а не модуль целиком (глава 05).

Без запуска тестов эта ошибка осталась бы незамеченной. Она не проявляется ни при чтении кода, ни при работе настоящего приложения, где никакого monkeypatch и нет. Проявляется она только при попытке изолированно протестировать код, который до этого никогда так строго не проверялся.

## Проверь себя

1. Почему сегодняшний `lifespan` в `taskman` не нуждается в коде после `yield`, хотя "graceful shutdown" в общем случае — это именно код после `yield`? Что именно в архитектуре storage-слоя делает это ненужным прямо сейчас?
2. Почему rate limiting в памяти одного процесса перестаёт работать корректно, как только приложение запущено в нескольких репликах? Что из этого следует про то, где должно храниться состояние лимита?
3. В чём принципиальная разница между `asyncio.create_task` или `BackgroundTasks` из FastAPI и полноценным брокером задач вроде Celery? Какое из трёх свойств решает вопрос выбора в каждом конкретном случае: переживаемость рестарта, повтор при сбое или отдельная машина?
4. Почему `TaskStorage`-протокол (глава 10) означает, что переход на Postgres не должен потребовать ни строчки изменений в `models/`, `cli/` или `api/`?
5. Приведите свою формулировку того, почему "добавить X на будущее, вдруг понадобится" — в общем случае плохая эвристика для решения об архитектуре. Опирайтесь хотя бы на один пример из самого курса, где эта эвристика была явно отвергнута в пользу противоположной.

<summary>Ответы</summary>

1. Потому что storage-слой (глава 08/12) открывает **отдельное** соединение с базой на каждый отдельный вызов и закрывает его сразу же по завершении. В системе просто нет долгоживущего, разделяемого ресурса, который нужно было бы явно закрывать при остановке процесса. Ни пула соединений, ни фонового воркера, ни файлового дескриптора, живущего дольше одного запроса. "Graceful shutdown = код после `yield`" — это общий шаблон для систем, у которых такой ресурс **есть**. У нашего конкретного архитектурного решения его нет, поэтому шаблон формально применим, но пуст.
2. Каждая реплика приложения — отдельный процесс с собственной памятью. Счётчик запросов, хранящийся в памяти одной реплики, не видит запросы, обслуженные другими репликами того же сервиса. Обычно лимит должен применяться к клиенту независимо от того, на какую именно реплику попал его запрос. Значит, состояние счётчика должно жить не в памяти конкретного процесса, а в общем для всех реплик хранилище. Отсюда типичный выбор Redis: единственный источник истины, к которому обращаются все реплики одинаково.
3. `asyncio.create_task` и `BackgroundTasks` живут строго в рамках процесса, который их запустил. Если процесс перезапускается или падает до завершения задачи, она просто теряется без следа, и повторных попыток не будет. Celery хранит задачи в отдельном, персистентном брокере — Redis или RabbitMQ. Они переживают падение и веб-сервера, и конкретного воркера. Они могут автоматически повторяться по настроенной политике при сбое и выполняться на физически отдельной машине, никак не связанной с процессом веб-сервера. Выбор зависит от того, какое именно из этих трёх свойств реально нужно для конкретной задачи. Если работа лёгкая, не критичная к потере и укладывается в жизненный цикл одного запроса, `BackgroundTasks` достаточно. Если хотя бы одно из трёх свойств действительно требуется, нужен полноценный брокер.
4. Потому что `TaskStorage` описывает **форму** взаимодействия со storage-слоем, а не то, как именно эти методы реализованы внутри. Форма — это то, какие методы есть и какие типы они принимают и возвращают. Код в `cli/` и `api/` вызывает `db.add_task(...)`, `db.list_tasks(...)` и так далее, никогда не заглядывая внутрь конкретной реализации `sqlite_storage.py`. Замените эту реализацию на модуль, работающий с Postgres через пул соединений, — и для вызывающего кода ничего не изменится. Новому модулю достаточно удовлетворять тому же протоколу. Это прямая, практическая выплата инвестиции, сделанной в главе 10 задолго до того, как вопрос о смене базы вообще возник.
5. Общая формулировка: инфраструктура, добавленная "на будущее", несёт реальную стоимость уже сегодня — больше движущихся частей, больше кода для поддержки, больше поверхности для багов. Взамен вы получаете выгоду, которая может никогда не понадобиться. А если понадобится — часто не в том виде, который вы предугадали заранее. Конкретный пример из курса: глава 14 явно не стала вводить паттерн "одна сессия на запрос" для БД. Это стандартная практика для многих реальных FastAPI-приложений. Обоснование было именно в том, что ни один из трёх эндпоинтов проекта на тот момент не делал больше одной storage-операции за вызов. Самой причины, оправдывающей сложность паттерна, попросту не существовало. Тот же приём — глава 11. Она явно показала, что `multiprocessing` не "лучше" `threading` по умолчанию. Он оправдан только при реальной необходимости в параллелизме для работы, упирающейся в CPU (центральный процессор).

</details>

## Частая ошибка

Две противоположные, но одинаково реальные ошибки закрывают этот курс.

Первая — увидеть чеклист вроде того, что в этой главе, и захотеть внедрить всё сразу, независимо от реальной нужды. Добавить Postgres, потому что "он серьёзнее". Завести Celery, потому что "так делают в реальных проектах". Включить rate limiting, потому что "а вдруг понадобится".

Каждый из этих пунктов добавляет реальную операционную сложность: больше сервисов для деплоя, больше конфигурации для синхронизации, больше мест, где что-то может сломаться. При текущем масштабе проекта эта сложность ничего не возвращает взамен.

Весь курс последовательно демонстрировал обратный принцип. Глава 05 говорила: не переусложнять пакетную структуру раньше времени. Глава 14 говорила: не вводить сессию на запрос без реальной многошаговой транзакции. Инфраструктура вводится тогда, когда её отсутствие уже причиняет конкретную, наблюдаемую боль — не раньше.

Вторая ошибка — зеркальная и не менее реальная. Довести проект до состояния "работает", один раз пройтись по чеклисту вроде этого и больше никогда к нему не возвращаться. Вопрос кажется закрытым навсегда.

Пет-проект, который сегодня обслуживает одного пользователя на одной машине, завтра может внезапно обслуживать сотню. Именно тогда всплывут все пункты, которые казались неактуальными "пока".

Этот чеклист — не разовая формальность перед первым деплоем. Это список вопросов, к которым стоит возвращаться каждый раз, когда меняется реальный масштаб или контекст использования проекта.

Это ровно та же дисциплина, что и написание тестов или прогон `mypy --strict`. Не потому что того требует формальность, а потому что именно так в этом курсе несколько раз находились настоящие, а не воображаемые проблемы.
