# Синтаксис и типы

## Теория

**Отступы как синтаксис.** Блок кода после `if`, `for`, `def`, `class` и так далее начинается с `:` и состоит из строк с одинаковым отступом. Обычно это 4 пробела — так требует PEP 8, один из нумерованных документов Python Enhancement Proposal. Смешивание табов и пробелов в одном блоке — не предупреждение, а `TabError`. Никаких `{}`: закрывающей скобки нет, конец блока определяется падением отступа обратно.

```python
if age >= 18:
    print("adult")       # часть блока if — отступ 4 пробела
    print("can vote")    # тоже часть блока
print("done")             # отступ вернулся к 0 — это уже вне if
```

**Переменные — без `let`/`const`/`var`.** Присваивание — это просто `name = value`, без ключевого слова объявления. Более важное отличие: в Python **нет блочной области видимости** для `if`/`for`/`while` — только область видимости функции и модуля. Переменная, созданная внутри `if`, живёт и после его окончания, в отличие от `let`/`const` в JS, которые ограничены `{}`:

```python
if True:
    x = 5
print(x)  # 5 — переменная доступна и здесь, в JS с let это был бы ReferenceError
```

`def` и `class` создают свою область видимости, `if`/`for`/`while`/`with` — нет. Это часто ловит JS-разработчиков, привыкших, что `let i` внутри `for` не "утекает" за пределы цикла.

**Динамическая, но строгая типизация.** В JS типы существуют в рантайме и без объявления (`typeof x`), но многие операции делают неявное приведение типов (`"3" + 3 === "33"`, `"3" - 3 === 0`). В Python типы тоже существуют без объявления в рантайме, но **неявного приведения между несовместимыми типами почти нет**:

```python
"3" + 3        # TypeError: can only concatenate str (not "int") to str
"3" + str(3)   # "33" — приведение только явное
```

Это и значит "строгая, но динамическая": проверка типов происходит в рантайме (не на этапе компиляции, как в TS), но интерпретатор не пытается "угадать" совместимость типов сам.

**Базовые типы.** У `int` произвольная точность: переполнения нет, аналог `BigInt` не нужен. Тип `float` — это IEEE754 double, тот же 64-битный формат чисел с плавающей точкой, что и `number` в JS. Дальше идут `bool` (`True`/`False`, с заглавной буквы), `str` и `None`.

Важно: в Python **только одно** значение "пусто" — `None`. Различия `null` vs `undefined` из JS здесь нет: непроинициализированной переменной в Python просто не существует (обращение к ней — `NameError`), а не значение `undefined`.

**f-strings.** Прямой аналог template literals:

```python
name = "Max"
count = 3
print(f"{name} has {count} tasks")        # интерполяция
print(f"{3.14159:.2f}")                    # "3.14" — format spec после ":"
print(f"{count=}")                         # "count=3" — debug-шорткат, аналога в JS нет
```

**Операторы.** `==` в Python сравнивает **значения**, то есть вызывает `__eq__`. Отдельного оператора "строгого" сравнения, как `===` в JS, здесь нет. Он и не нужен: `==` не делает неявных приведений, которые строгому варианту пришлось бы обходить.

Оператор `is` сравнивает **идентичность объекта** — тот же адрес в памяти, а не значение. Используется он почти исключительно для `x is None`, и это идиома, а не вопрос стиля. Инкремента и декремента `++`/`--` нет, есть только `x += 1`. Неоднозначность pre/post-инкремента сочли не стоящей своей цены — философия "explicit is better than implicit".

Работают цепочки сравнений: `0 < x < 10` эквивалентно `0 < x and x < 10`. В JS `0 < x < 10` тоже "работает", но считается по шагам слева направо, через приведение bool→number, и для многих значений даёт неверный результат.

**Truthy/falsy — ловушка №1 при переходе с JS.** В Python falsy-значений немного и они зафиксированы: `False`, `None`, `0`, `0.0`, `""`, `[]`, `{}`, `set()`, `()`. То есть **любая пустая коллекция falsy**.

В JS же пустой массив и пустой объект — всегда truthy (`Boolean([]) === true`, `Boolean({}) === true`), а falsy там только `0`, `""`, `null`, `undefined`, `NaN`, `false`. Это прямо противоположное поведение для главного случая, который встречается в реальном коде каждый день, — проверки вида `if tasks:`.

### Параллели с JS/TS/Node:

- **Нет блочной области видимости** — `if`/`for`/`while` не создают новую область видимости, в отличие от `let`/`const` в `{}`. Она бывает только у функции и у модуля.
- **`==` не делает неявных приведений** между несовместимыми типами — в отличие от JS `==`, печально известного своими правилами приведения. В Python `"5" == 5` — это просто `False`, не `TypeError` и не `True`.
- **Пустые коллекции — falsy**, а не truthy, как в JS: `if []:` в Python не выполнится, `if ([])` в JS — выполнится всегда.
- **Только `None`**, нет пары `null`/`undefined`.

## Разбор решения

```python
import argparse

tasks: list[dict] = []


def add_task(text: str) -> dict:
    task = {"id": len(tasks) + 1, "text": text, "done": False}
    tasks.append(task)
    return task


def find_task(task_id: int) -> dict | None:
    for task in tasks:
        if task["id"] == task_id:
            return task
    return None


def mark_done(task_id: int) -> dict | None:
    task = find_task(task_id)
    if task is not None:
        task["done"] = True
    return task


def format_task(task: dict) -> str:
    mark = "x" if task["done"] else " "
    return f"[{mark}] {task['id']} {task['text']}"


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="taskman", description="Simple task manager")
    subparsers = parser.add_subparsers(dest="command", required=True)

    add_parser = subparsers.add_parser("add", help="Add a new task")
    add_parser.add_argument("text", help="Task description")

    subparsers.add_parser("list", help="List all tasks")

    done_parser = subparsers.add_parser("done", help="Mark a task as done")
    done_parser.add_argument("id", type=int, help="Task id")

    return parser


def main() -> None:
    parser = build_parser()
    args = parser.parse_args()

    if args.command == "add":
        task = add_task(args.text)
        print(f"Added: [{task['id']}] {task['text']}")
    elif args.command == "list":
        if not tasks:
            print("No tasks yet.")
        else:
            for task in tasks:
                print(format_task(task))
    elif args.command == "done":
        task = mark_done(args.id)
        if task is None:
            print(f"Task with id {args.id} not found.")
        else:
            print(f"Marked done: [{task['id']}] {task['text']}")


if __name__ == "__main__":
    main()
```

Ключевые решения:

- `dict | None` (PEP 604, Python 3.10+) — union-тип прямо через `|`, аналог `dict | null` в TS без `Optional[dict]`/`Union[dict, None]` из старого `typing`.
- `find_task` возвращает `None`, если ничего не нашла — обычная идиома "искать и вернуть Optional" вместо исключения. Исключения для доменных ошибок (`TaskNotFoundError`) появятся в главе 06, когда для них будет подходящий контекст: контекстные менеджеры и иерархия ошибок.
- `if not tasks:` — использует falsy пустого списка напрямую, идиоматичнее, чем `if len(tasks) == 0:`.
- `type=int` в `add_argument` — argparse сам валидирует и конвертирует строку в `int`, и сам печатает понятную ошибку при невалидном вводе — не нужно ловить `ValueError` вручную на этом уровне.

## Проверь себя

1. Почему `if []:` — `False` в Python, а `if ([])` в JS — всегда `true`? В чём принципиальная разница в правилах truthy/falsy для коллекций между языками?
2. Что произойдёт с переменной, созданной внутри блока `if`, но не внутри функции, после выхода из этого блока? Почему это в корне отличается от `let`/`const` в JS с их блочной областью видимости?
3. Почему `"3" + 3` в Python бросает `TypeError`, а `"3" + 3` в JS возвращает `"33"`? Что это говорит о разнице между "динамической, но строгой" типизацией Python и типизацией JS?
4. Чем отличаются `==` и `is` в Python? Почему `x is None` — идиоматично, а `x == None` — нет (хотя оба технически сработают для `None`)?
5. Почему в Python нет `++`/`--`? Что это говорит о философии языка по сравнению с C-подобным синтаксисом, который унаследовал JS?

<summary>Ответы</summary>

1. В Python правила truthy/falsy для коллекций основаны на **длине**. Любая коллекция — список, словарь, множество, кортеж, строка — falsy, если пуста, и truthy, если в ней есть хотя бы один элемент. Под капотом это работает через `__bool__`/`__len__`. В JS же правила для примитивов и для объектов разные и исторически зафиксированы: falsy там только `0`, `""`, `null`, `undefined`, `NaN`, `false`. Любой объект truthy просто потому, что это объект, вне зависимости от содержимого — пустой массив и пустой объект в том числе.
2. Переменная останется доступной и после блока `if`. Единицы области видимости в Python — только функция, модуль и класс. Точнее: `def`, `class` и comprehension создают новую область видимости, а `if`/`for`/`while`/`with`/`try` — нет. В JS `let`/`const` дополнительно ограничены ближайшим `{}`, поэтому переменная, объявленная внутри `if { let x = 5 }`, недоступна снаружи и выбросит `ReferenceError`.
3. В Python оператор `+` для `str` требует одинакового типа операндов, кроме числовых типов между собой. Попытка сложить `str` и `int` явно запрещена и бросает исключение, а не пытается угадать намерение. В JS `+` перегружен исторически: если хотя бы один операнд `string`, оба значения приводятся к строке и конкатенируются. Это решение осталось от ранних версий языка и породило многие классические JS-баги ("wat"-примеры).
4. `==` сравнивает значения через `__eq__`, и класс может его переопределить. Оператор `is` сравнивает идентичность — тот же объект в памяти, эквивалент сравнения указателей. Для `None` идиоматично именно `is`, потому что `None` — синглтон: в рантайме существует ровно один объект `None`. Сравнение через `is` явно говорит "это именно тот единственный объект", а не "значение, равное None". Это важно, если кто-то переопределит `__eq__` в своём классе так, что `obj == None` вернёт `True` для непустого объекта.
5. Инкремент/декремент через `++`/`--` в C-подобных языках имеет неоднозначную семантику pre/post (`x++` vs `++x`), которая исторически была источником путаницы и багов, завязанных на порядок вычисления выражений. Python следует принципу "explicit is better than implicit" (из Zen of Python) — `x += 1` не оставляет вопроса, когда именно происходит инкремент относительно остального выражения, ценой одного лишнего символа.

## Частая ошибка

JS-разработчик, у которого `"5" == 5` в голове означает "true, потому что JS приводит типы", часто ожидает от Python одного из двух. Либо такого же поведения: "наверное, Python тоже приведёт". Либо ошибки времени выполнения: "Python строгий — значит, кинет исключение при сравнении разных типов".

На деле происходит третье: `"5" == 5` в Python — это просто `False`, без единого предупреждения. Разные типы без общего протокола сравнения считаются "просто не равны", а не ошибкой и не поводом для приведения.

Это особенно коварно в CLI-коде вроде этого проекта. Допустим, `args.id` вдруг оказался строкой — например, из-за бага в парсинге, где забыли `type=int`. Тогда сравнение `task["id"] == args.id` молча всегда будет `False`: задача "не найдётся", и никакого traceback, чтобы это заметить, не будет.

Отсюда практический вывод: полагаться на `type=int`/`type=str` в argparse и на type hints. Не полагаться на надежду, что Python сам приведёт типы при сравнении — он этого не делает.
