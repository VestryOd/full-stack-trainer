# Установка и первый CLI-скелет

## Теория

Эта глава заканчивается рабочим скелетом интерфейса командной строки (CLI). А начинается она с двух вещей, которые сбивают JS-разработчика первыми: как ставится Python и как он изолирует зависимости.

Python — интерпретируемый, динамически типизированный язык (в рантайме у каждого значения есть конкретный тип, просто вы не объявляете его в сигнатуре без явных type hints). Ключевое синтаксическое отличие, которое будет мозолить глаза первую неделю: блоки кода определяются отступом, а не `{}`. Отступ — не стилистика, а синтаксис: неправильный отступ — это `IndentationError`, а не warning линтера.

**Установка.** На macOS/Linux почти всегда уже стоит какой-то `python3` — но полагаться на системный Python не стоит: он может быть старой версии и используется самой операционной системой. Практика: ставить актуальный Python отдельно — через [pyenv](https://github.com/pyenv/pyenv) (аналог `nvm`, если он вам знаком) или официальный установщик с python.org. Для курса нужен **Python 3.11+**. Проверка версии:

```bash
python3 --version
# Python 3.12.3
```

**venv — виртуальное окружение.** Это самое важное отличие от Node-экосистемы, и его нужно понять сразу. В Node каждый проект автоматически изолирован: `npm install` кладёт пакеты в локальный `node_modules`. Два проекта с разными версиями одной библиотеки не конфликтуют.

В Python **изоляции по умолчанию нет** — `pip install requests` без дополнительных действий поставит `requests` в site-packages *самого интерпретатора* (глобально для этого Python). Если у вас два проекта с разными версиями Django — они столкнутся.

`venv` решает это, создавая копию/симлинк интерпретатора и собственную папку site-packages для конкретного проекта:

```bash
python3 -m venv .venv          # создать окружение в папке .venv
source .venv/bin/activate      # активировать (Linux/macOS)
# .venv\Scripts\activate       # активировать (Windows)
python --version               # теперь "python" внутри активного venv — это тот самый 3.11+
pip install requests           # ставится только в .venv, не глобально
deactivate                     # выйти из окружения
```

После `activate` команды `python` и `pip` в терминале указывают на бинарники внутри `.venv/bin/`, а не на системные. Это одновременно и `nvm use`, и `node_modules` в одном механизме — venv фиксирует и версию интерпретатора (если вы создали его нужным `python3`), и набор пакетов.

**pip и pyproject.toml.** `pip` — это `npm`/`yarn`, но исторически без единого lock-файла из коробки. Раньше это решали руками через `pip freeze > requirements.txt`. Настоящие lock-файлы (poetry, uv) — отдельная тема в главе про модули и пакеты. Современный стандарт метаданных проекта — `pyproject.toml`, прямой аналог `package.json`:

| package.json | pyproject.toml | Назначение |
|---|---|---|
| `"name"` | `[project] name` | имя пакета |
| `"version"` | `[project] version` | версия |
| `"dependencies"` | `[project] dependencies` | зависимости (формат иной — список строк с версией внутри строки, не объект) |
| `"scripts"` | нет прямого аналога в стандарте; `[project.scripts]` — это про entry points CLI, не про произвольные команды | npm-скрипты обычно заменяют `Makefile`/`invoke`/`nox` |
| `"eslintConfig"` и подобные секции | `[tool.ruff]`, `[tool.mypy]`, `[tool.pytest.ini_options]` | конфиги сторонних инструментов живут прямо в том же файле |

**Структура проекта и запуск.** Нет единого "create-react-app"-стандарта, но есть две общепринятые схемы: flat (`main.py` прямо в корне рядом с `pyproject.toml`) и src-layout (`src/package_name/...`). Для маленького CLI на старте — flat, к src-layout перейдём в главе про модули и пакеты, когда это станет оправдано.

Запуск скрипта:

```bash
python main.py add "Buy milk"
```

Идиома `if __name__ == "__main__":` означает: выполнить этот код, только если файл запущен напрямую, а не импортирован как модуль. Здесь `__name__` — специальная переменная модуля. Она равна `"__main__"`, только когда файл является точкой входа процесса. Когда файл импортируют откуда-то ещё, она равна имени самого модуля — `"main"`, `"taskman.cli"` и так далее.

**argparse.** Это встроенный (не нужно `pip install`) модуль для разбора CLI-аргументов — прямой аналог `commander`/`yargs`, но в stdlib. Ключевая концепция для CLI с подкомандами (`add`, `list`, `done`, ...) — `subparsers`: один parser верхнего уровня плюс отдельный sub-parser на каждую команду со своими аргументами.

### Параллели с JS/TS/Node:

- **venv ≈ `nvm` + `node_modules` в одном механизме.** В Node изоляция проекта — по умолчанию (локальный `node_modules`); в Python изоляции нет, пока вы явно не создали и не активировали venv.
- **pyproject.toml ≈ package.json**, но конфиги линтеров и тайпчекеров лежат прямо в нём под `[tool.x]`, а не в отдельных файлах вроде `.eslintrc` и `tsconfig.json`. Многие инструменты при этом поддерживают и отдельные файлы.
- **argparse ≈ commander/yargs**, только не нужно ничего ставить — это часть стандартной библиотеки, как раньше `readline` в Node.
- **pip без venv ≈ `npm install -g`** — глобальная установка, которая ломается при первом же конфликте версий между проектами. В Python это, к сожалению, поведение *по умолчанию*, а не опция, которую нужно специально включить.

## Что добавляем в проект

С нуля создаём скелет CLI-менеджера задач `taskman`. Это два файла: `pyproject.toml` с метаданными проекта и один `main.py`. В `main.py` будет команда `add <text>`, которая кладёт задачу в список **в памяти процесса** и печатает подтверждение.

Персистентность (JSON, потом SQLite) появится в главе 08. Сейчас цель только в том, чтобы прожить полный цикл руками: venv → pyproject.toml → argparse → запуск.

## Практическое задание

1. Установите Python 3.11+, убедитесь через `python3 --version`.
2. Создайте папку проекта `taskman/`, внутри — venv (`python3 -m venv .venv`), активируйте его.
3. Создайте `pyproject.toml` с секцией `[project]`: `name = "taskman"`, `version = "0.1.0"`, `requires-python = ">=3.11"`.
4. Создайте `main.py` с CLI на `argparse`, поддерживающим одну подкоманду:
   - `add <text>` — добавляет задачу `{"id": ..., "text": ..., "done": False}` в module-level список в памяти и печатает `Added: [id] text`.
5. Убедитесь, что `python main.py add "Buy milk"` печатает `Added: [1] Buy milk`.

Вопросы на подумать (не нужно решать все прямо сейчас, но зафиксируйте для себя ответ):

- Что произойдёт, если запустить `python main.py add "Buy milk"` дважды подряд? Почему второй раз тоже выведет `[1] ...`, а не `[2] ...`? Это баг?
- Что выведет `python main.py` без аргументов вообще? А `python main.py add` без текста? Присмотритесь к сообщению об ошибке — это поведение argparse "из коробки", вы его не писали.
- Разрешать ли пустую строку/строку из пробелов как текст задачи? Решение оставьте на своё усмотрение — но обоснуйте его для себя.

## Разбор решения

`pyproject.toml`:

```toml
[project]
name = "taskman"
version = "0.1.0"
requires-python = ">=3.11"
dependencies = []
```

`main.py`:

```python
import argparse

# Пока нет персистентности — просто список в памяти процесса.
# Он пропадает при каждом завершении процесса; это ожидаемо
# для этой главы и будет исправлено в главе про persistence.
tasks: list[dict] = []


def add_task(text: str) -> dict:
    task = {"id": len(tasks) + 1, "text": text, "done": False}
    tasks.append(task)
    return task


def build_parser() -> argparse.ArgumentParser:
    parser = argparse.ArgumentParser(prog="taskman", description="Simple task manager")
    subparsers = parser.add_subparsers(dest="command", required=True)

    add_parser = subparsers.add_parser("add", help="Add a new task")
    add_parser.add_argument("text", help="Task description")

    return parser


def main() -> None:
    parser = build_parser()
    args = parser.parse_args()

    if args.command == "add":
        task = add_task(args.text)
        print(f"Added: [{task['id']}] {task['text']}")


if __name__ == "__main__":
    main()
```

Ключевые решения:

- `subparsers = parser.add_subparsers(dest="command", required=True)` — `dest="command"` кладёт имя выбранной подкоманды в `args.command`. Параметр `required=True` заставляет argparse вывести ошибку и завершить процесс, если подкоманда не указана. Без него отсутствие подкоманды в некоторых версиях Python не считалось ошибкой.
- `list[dict]` — начиная с Python 3.9 встроенные generic-типы `list[int]` и `dict[str, int]` не требуют импорта `from typing import List, Dict`. Это ближе к тому, как вы пишете `string[]` в TS, чем к громоздкому generic из отдельного модуля.
- `if __name__ == "__main__": main()` — гарантирует, что запуск `python main.py` выполнит `main()`. Позже `main.py` может стать модулем, который кто-то импортирует, например в тестах в главе 09. Тогда импорт не вызовет CLI-логику как побочный эффект.

## Проверь себя

1. `python3 -m venv .venv` создаёт целую структуру: копию или симлинк интерпретатора и свою папку site-packages. Почему не просто список установленных пакетов? И чем это отличается от того, как npm изолирует зависимости через `node_modules`?
2. Что произойдёт, если запускать `pip install` без активированного venv в проекте, где системный Python уже используется чем-то ещё? Почему это на практике приводит к трудноуловимым багам?
3. Зачем нужен `if __name__ == "__main__":`, если можно было бы просто вызвать `main()` последней строкой файла без всякого условия? Что изменится, если `main.py` импортируют из другого файла?
4. Чем секция `[project]` в `pyproject.toml` отличается от `package.json` в управлении версиями зависимостей? Чего `pyproject.toml` сам по себе **не** решает без дополнительных инструментов?
5. Почему `add_subparsers` требует `required=True` явным параметром, а не считает подкоманду обязательной по умолчанию?

<details>
<summary>Ответы</summary>

1. Изоляция в Python — не только про пакеты, но и про сам интерпретатор. Окружение venv фиксирует, каким именно `python` и `pip` вы пользуетесь. В системе может быть несколько версий Python одновременно, и без явного окружения `pip install` уйдёт в site-packages того интерпретатора, который первым найдётся в `PATH`. В Node изоляция версий пакетов уже встроена в `node_modules` для каждого проекта, а версия самого рантайма — отдельная забота (`nvm`). В Python venv объединяет обе задачи в одном месте.
2. Пакет ставится в глобальный site-packages системного (или первого найденного в `PATH`) Python. Если два разных проекта на машине требуют разные версии одной библиотеки, более поздняя установка молча перезатирает более раннюю. Второй проект начинает падать без видимой причины в своём собственном коде. Настоящая причина в том, что кто-то в другом терминале сделал `pip install` без venv.
3. Без `if __name__ == "__main__":` вызов `main()` произойдёт при **любом** импорте файла. В том числе тогда, когда тесты в главе 09 захотят импортировать `add_task` или `build_parser` из `main.py`, не запуская CLI. Переменная `__name__` равна `"__main__"` только тогда, когда файл — точка входа процесса. При импорте она равна имени модуля, и код внутри `if` не выполнится.
4. `pyproject.toml` описывает *метаданные* и заявленные версии зависимостей. Сам по себе он не создаёт воспроизводимый lock-файл с точными зафиксированными версиями всего дерева зависимостей. Сравните с `package-lock.json` и `yarn.lock`: они генерируются автоматически и фиксируют всё дерево. Для настоящего lock-файла в Python нужен отдельный инструмент поверх (poetry, uv, pip-tools) — это разберём в главе про модули и пакеты.
5. Потому что исторически argparse разрешал делать подкоманду необязательной. Так можно было написать CLI, где отсутствие подкоманды — валидный случай, например вывод справки. Разработчики сохранили это как явный выбор, а не как поведение по умолчанию, чтобы не ломать обратную совместимость при обновлениях Python. Это типичный пример того, насколько осторожно стандартная библиотека меняет поведение по умолчанию между минорными версиями.

</details>

## Частая ошибка

JS/TS-разработчик привык, что зависимость проекта — это всегда что-то локальное и изолированное: `node_modules` создаётся автоматически при `npm install`, где бы вы ни находились. Такой разработчик почти гарантированно хотя бы раз забудет активировать venv перед `pip install`.

Разница в том, что в Node забытая изоляция проявляется сразу и явно: нет `node_modules` — ничего не работает, ошибка "module not found" очевидна. А в Python пакет **всё равно установится** — просто не туда, куда вы думали.

Скрипт может даже успешно импортировать пакет, если он случайно оказался и в системном Python. Возникает ложное ощущение, что всё работает. Оно держится, пока вы не окажетесь на другой машине или в системе непрерывной интеграции (CI), где этого "случайного" глобального пакета нет.

Второй частый момент — путаница между `python` и `python3` как именем бинарника. На некоторых системах `python` может не существовать вовсе или указывать на Python 2. Так бывает на старых Linux-дистрибутивах и на свежем macOS без явно поставленного Python.

Внутри активированного venv это не имеет значения: там `python` всегда указывает на интерпретатор, с которым venv был создан. До активации всё иначе. Команда `python script.py` может упасть с синтаксической ошибкой на f-строках или type hints, которых Python 2 просто не понимает.
