# Shared dependencies и подводные камни федерации

## Теория

Это самая "болевая" глава курса: всё, что здесь описано, — реальные инциденты, которые случаются в MF-проектах регулярно. Хорошая новость: список конечен, и почти всё диагностируется за минуты, если знать механику.

### Что Nx шарит по умолчанию

В `module-federation.config.ts` мы не написали ни слова про shared — но negotiation из главы 09 работает. Потому что плагин Nx делает shared **всё сам**: каждый npm-пакет из package.json (с `requiredVersion` из него же; react и его семейство — как singleton) и — важная Nx-специфика — **workspace-либы тоже**: `shared-ui`, `shared-util` и прочие попадают в shared scope как singleton-модули. Настройка — функция `shared` в конфиге:

```ts
const config: ModuleFederationConfig = {
  name: 'catalog',
  exposes: { './Module': './src/remote-entry.ts' },
  // на каждый кандидат: false = не шарить, undefined = дефолт Nx,
  // объект = свои singleton/strictVersion/requiredVersion
  shared: (name, defaults) => {
    if (name === 'react') return { ...defaults, strictVersion: true };
    return undefined;
  },
};
```

### Два react-а: почему ломаются именно хуки

Из главы 09 мы знаем — react всегда `singleton: true`. Вот механика поломки, если это нарушить. React хранит состояние *на уровне экземпляра модуля*: у каждой копии react — собственный внутренний диспетчер хуков (та самая ссылка, которую `useState` разыменовывает при вызове). Рендерит компонент host-овский react → диспетчер установлен у **его** копии. Но компонент каталога скомпилирован против **своей** копии react — его `useState` смотрит в диспетчер второй копии, а там `null`. Результат — знаменитое **"Invalid hook call"**, у которого в списке официальных причин так и написано: "more than one copy of React".

То же с Context: `createContext` в копии A и `useContext` в копии B оперируют разными объектами — провайдер темы из host невидим для компонентов remote. Симптом коварнее хуков: ничего не падает, просто у remote «не применилась тема» или `useContext` вернул дефолт.

Диагностика двух react-ов — 30 секунд: в консоли `__REACT_DEVTOOLS_GLOBAL_HOOK__.renderers.size` (больше 1 — приехали), и Network tab: чанки react внутри бандла remote-а, хотя должен браться из shared.

### Версии: warning, который нельзя игнорировать

Когда singleton есть, но версии разъехались (host собран с react 18.3, remote требует ^19), в консоли появляется warning вида `Unsatisfied version 19.0.0 ... of shared singleton module react (required ^18.3.0)` — и **выигрывает первый загрузившийся**. Приложение продолжает работать на "не той" версии: может, обойдётся, а может, remote вызовет API, которого нет. `strictVersion: true` превращает это в ошибку загрузки remote-а — жёстко, зато на границе (где её поймает наш RemoteBoundary из главы 10), а не в глубине рендера. Прагматика: для react/роутера/стейт-либ — strictVersion в связке с дисциплиной обновлений; предупреждения в консоли prod-а — не шум, а телеметрия рассинхрона.

### Workspace-либы в федерации: самый тонкий момент

Раз Nx шарит `shared-ui` как singleton, экземпляр Button на страницу — один. Звучит хорошо, пока не вспомнить главную суперсилу MF — **независимый деплой**:

- в понедельник задеплоили catalog — внутри его артефакта shared-ui *вчерашняя*;
- в среду поменяли Button и задеплоили только checkout — в его артефакте shared-ui *новая*;
- у пользователя открылась страница: shared scope выбрал **один** экземпляр shared-ui — чей? Обе стороны декларируют одну и ту же "версию" (workspace-либа не имеет npm-версии), так что берётся первый загрузившийся. Загрузился catalog первым — и checkout работает со *вчерашним* Button, которого в его исходниках уже нет.

Это и есть строка "у remote чужой/старый UI" из таблицы ниже. Монорепо *не защищает* от version skew, если деплой рассинхронный: собираетесь вы из одного коммита, а *живёте* в проде с артефактами разных коммитов. Три рабочие стратегии:

1. **Обратная совместимость shared-либ** как норма: меняем Button добавлением, а не переделкой; ломающие изменения — через новый компонент/проп с деприкацией старого.
2. **Согласованный деплой** затронутых частей: изменилась shared-ui → `nx affected` знает всех потребителей (глава 05) → деплоим их вместе. Честная цена: чем толще shared-слой, тем менее независим деплой.
3. **Не шарить** конкретную либу (`shared: (n) => n === '@mini-shop/shared-ui' ? false : undefined`): каждый remote возит свою копию. Цена — размер бандлов и запрет на Context/состояние внутри либы (копии-то теперь две); выгода — полная независимость версий.

Выбор между 1–3 — архитектурное решение уровня команды, а не строчка конфига "по вкусу".

### Типизация между host и remote

`remotes.d.ts` из главы 10 — ручное обещание. Module Federation 2.0 умеет лучше: при сборке remote генерируется пакет типов его exposes (`@mf-types`), а host подтягивает их — IDE и tsc видят реальную сигнатуру `catalog/Module`. Важно трезво понимать гарантию: типы соответствуют remote-у **на момент генерации**. Прод-remote, задеплоенный позже, мог измениться — компиляция host против свежих типов это не поймает. Поэтому типы MF — инструмент *разработки*, а контракт *прода* охраняется процессом: контрактные/e2e-тесты связки и канареечные деплои remote-ов.

Про "eager consumption" — механика из глав 09–10: код, синхронно потребляющий shared-модуль, исполнился раньше, чем negotiation успела положить модуль в shared scope. Лечится восстановлением async boundary (`import('./bootstrap')`) — или, для действительно стартовых зависимостей host-а, флагом `eager: true` (модуль кладётся в начальный бандл и не ждёт negotiation).

## В рабочем монорепо

- Прод, консоль браузера: фильтр по "Unsatisfied" и "shared" — есть warnings? Это карта рассинхрона версий вашей федерации, бесплатная телеметрия.
- `__REACT_DEVTOOLS_GLOBAL_HOOK__.renderers.size` на проде — быстрый тест на дубли react (заодно проверьте дизайн-систему в Network: не приезжает ли она в чанках нескольких remotes).
- В module-federation.config всех приложений: есть ли функция `shared` с переопределениями и почему (git blame по строкам — обычно за каждым `false` стоит инцидент).
- Выясните стратегию команды для shared workspace-либ: совместимость / согласованный деплой / не шарить? Если никто не может ответить — стратегия "как получится", и инцидент из раздела про first-wins у вас впереди.
- Есть ли генерация MF-типов (`@mf-types` в артефактах, dts-опции в конфиге) и собирается ли host в CI против свежих типов remote-ов — это и есть контракт-чек.

**Edge cases на подумать:**

- Дизайн-система хранит текущую тему в React Context. Что случится, если её перестать шарить?

## Разбор решения

**Шаг 1.** Лог выполняется **один раз**, при первом заходе на любой из remote-ов: shared-ui попала в shared scope как singleton, и второй remote получил уже инициализированный модуль. Это и есть Nx-дефолт для workspace-либ в действии.

**Шаг 2.** После инлайна bootstrap:

```
Uncaught Error: Shared module is not available for eager consumption: webpack/sharing/consume/default/react/react
```

Механика: `createRoot`/JSX исполняются в синхронном стартовом чанке; shared react к этому моменту ещё не согласован (negotiation асинхронна). `import('./bootstrap')` возвращает бандлеру точку разрыва: сначала init контейнеров и shared scope, потом — код приложения. Откат = вернуть двухфайловую пару.

**Шаг 3.** Конфиг эксперимента:

```ts
// apps/catalog/module-federation.config.ts — ЭКСПЕРИМЕНТ, не мерджить
const config: ModuleFederationConfig = {
  name: 'catalog',
  exposes: { './Module': './src/remote-entry.ts' },
  shared: (name) => (name === 'react' ? false : undefined),
};
```

Теперь catalog бандлит собственный react. Host рендерит CatalogPage своим react-ом, но её код зовёт `useState` из копии каталога — диспетчер чужой:

```
Uncaught Error: Invalid hook call. Hooks can only be called inside of the body of a function component.
```

Диагностика подтверждает: `__REACT_DEVTOOLS_GLOBAL_HOOK__.renderers.size === 2`, в Network react-чанк приезжает вместе с бандлом каталога. Заметьте: ошибку поймал RemoteBoundary из главы 10 — упал роут каталога, не всё приложение. Откат конфига возвращает singleton.

**Шаг 4.** Ужесточение:

```ts
// apps/shell/module-federation.config.ts
const config: ModuleFederationConfig = {
  name: 'shell',
  remotes: ['catalog', 'checkout'],
  shared: (name, defaults) =>
    name === 'react' || name === 'react-dom'
      ? { ...defaults, singleton: true, strictVersion: true }
      : undefined,
};
```

При будущем рассинхроне (remote собран против react 19) вместо warning + first-wins будет ошибка **на этапе загрузки remote-а** — то есть на границе, где RemoteBoundary покажет fallback. Осознанный трейд-офф: недоступный каталог с внятной ошибкой в мониторинге против "работает, но непредсказуемо".

**Шаг 5.** Пользователь на `/checkout` увидит **вчерашний** Button, если первым успел инициализироваться catalog (например, пользователь зашёл через `/catalog`): его shared-ui заняла слот singleton-а, и checkout, задеплоенный с новой версией, получил чужой старый модуль. Хуже того — поведение зависит от порядка навигации: зашёл сразу на `/checkout` — новая кнопка, через каталог — старая. Для mini-shop выбираем стратегию 1+2: shared-ui эволюционирует обратно-совместимо, а при ломающих изменениях `nx affected` говорит, кого деплоить вместе (глава 05 + глава 13 делают это автоматикой CI).

Ответы на edge cases:

- Глобальный `false` для workspace-либ лечит first-wins ценой отказа от всего, ради чего либы шарят: каждый remote возит копии ui/util (размер), а главное — любые Context/состояние в этих либах перестают быть общими. Дублирование по умолчанию — это микрофронтенды без монорепо-выгод; точечный `false` для конкретной проблемной либы — легитимный инструмент.
- Тема в Context + нешаренная дизайн-система = ровно кейс "два createContext": ThemeProvider из host-копии невидим для remote-копий — у remote-ов дефолтная тема. Либы с Context/состоянием шарить обязательно (singleton) — или выносить состояние из них.
- Нет: strictVersion сравнивает версии, а у workspace-либ версии нет (или она у всех одинаковая "0.0.0") — рассинхрон *контента* при одинаковой "версии" strictVersion не видит. Против first-wins работают только стратегии из теории: совместимость, согласованный деплой или отказ от шаринга.

<details>
<summary>Ответы</summary>

1. React-модуль хранит внутри себя ссылку на текущий диспетчер хуков, которую рендерер выставляет перед вызовом компонента. Host-react рендерит компонент и выставляет диспетчер **своей** копии; код компонента скомпилирован с импортом **другой** копии react — его `useState` читает диспетчер той копии, где он не установлен. Аналогично расходятся объекты Context и планировщик. Состояние "какой сейчас диспетчер" — модульное, поэтому две копии модуля = два несвязанных мира.
2. Сборка и деплой — разные оси времени: собираются все из одного коммита, но артефакты в проде — от разных коммитов (каждый remote деплоился в свой момент). Workspace-либа в shared scope — singleton без осмысленной версии: побеждает первый загрузившийся, и его версия контента может быть старее, чем у остальных. Стратегии: (а) обратная совместимость shared-либ — цена: дисциплина эволюции API; (б) согласованный деплой всех затронутых (через affected) — цена: деплой менее независим; (в) не шарить конкретную либу — цена: дубли в бандлах и запрет на общий Context/состояние в ней.
3. Negotiation обнаружила, что задекларированный диапазон одного участника не покрывается версией, оказавшейся в shared scope, — но из-за singleton взяла имеющуюся и продолжила. Грозит рантайм-поведением "не той" версии: от безобидного до вызова несуществующего API в глубине рендера. strictVersion переносит отказ на момент загрузки remote-а: ошибка на границе (ловится error boundary, видна в мониторинге как отказ загрузки) вместо непредсказуемости внутри.
4. Гарантирует: на момент *генерации* типов сигнатуры exposes реального кода remote-а — IDE-автокомплит и падение tsc при несовместимости в момент сборки host. Не гарантирует: что в проде в момент рантайма стоит тот же remote — он мог быть задеплоен позже с другим контрактом. Дополняется процессом: сборка host в CI против свежих типов всех remote-ов (контракт-чек), e2e связки, канареечный деплой remote-ов.
5. Все три действия лечат причину "в node_modules двух версий react" — это болезнь single-app/npm-мира. В федерации второй react приезжает не из node_modules host-а, а **из бандла remote-а по сети**: дедупликация локальных зависимостей на это не влияет. Правильная последовательность: (1) `renderers.size` в консоли — подтвердить дубль; (2) Network — чей бандл привёз второй react; (3) module-federation.config этого приложения — почему react не в shared (исключён, или сломан singleton); (4) починить shared-конфиг.

## Частая ошибка

"Invalid hook call" — ошибка с огромным интернет-шлейфом из single-app мира, где её причина — две версии react в node_modules. Разработчик, пришедший оттуда, привычно лечит её `npm dedupe`, resolutions и пересозданием lock-файла — и не помогает, потому что в федерации второй react приезжает **по сети из бандла соседнего приложения**, куда npm-инструменты не смотрят в принципе. Первый рефлекс в MF-проекте другой: `renderers.size` → Network → shared-конфиг. Направление диагностики — "что загрузилось в браузер", а не "что лежит в node_modules".

Вторая ошибка — стратегическая: команда считает, что монорепо автоматически защищает федерацию от рассинхрона ("мы же всё собираем из одного коммита"). Собираете — да; *живёте* в проде — с артефактами разных коммитов, потому что деплой независимый, в этом весь смысл MF. Пока shared workspace-либы меняются обратно-совместимо, иллюзия держится; первый же ломающий рефакторинг Button + рассинхронный деплой remote-ов даёт плавающий баг, зависящий от порядка навигации пользователя. Стратегия работы с shared-либами (совместимость / согласованный деплой / не шарить) должна быть выбрана и записана до первого инцидента, а не после.
