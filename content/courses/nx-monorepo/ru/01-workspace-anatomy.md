# Анатомия workspace

## Теория

### nx.json — конфигурация самого Nx

`nx.json` в корне — единственный файл, который описывает поведение *самого Nx* (а не отдельных проектов). Три ключевых блока, с которыми вы будете сталкиваться постоянно:

- **`plugins`** — список зарегистрированных плагинов с опциями. Это не просто "установленные пакеты": каждая запись здесь означает "этот плагин сканирует репу и *выводит* targets из конфигов инструментов". Запись `@nx/vite/plugin` — причина, по которой у проекта с `vite.config.ts` есть `build` и `serve`, хотя project.json у него пустой.
- **`targetDefaults`** — дефолты для одноимённых target-ов всех проектов: `"build": { "dependsOn": ["^build"], "cache": true }` означает "любой build сначала собирает зависимости и кешируется". Разберём в главе 03.
- **`namedInputs`** — именованные наборы файлов (`default`, `production`, `sharedGlobals`), от которых зависит хеш кеша. Центральная тема главы 04.

Есть ещё три блока поменьше. Блок `generators` задаёт дефолтные опции генераторов, чтобы каждый `nx g @nx/react:lib` в этой репе получал нужный bundler и линтер. Рядом с ним живут `defaultBase` (для affected) и `release` (версионирование и публикация).

### Что вообще делает папку "проектом"

Nx не сканирует "всё подряд": узлы графа появляются из трёх источников. Папка становится проектом, если верно одно из трёх:

- в ней есть **`project.json`**;
- в ней есть **`package.json`** (классика package-based);
- её "усыновил" плагин из `nx.json`, чей `createNodes` сматчился на конфиг инструмента. Так `@nx/playwright` создаёт e2e-проект (end-to-end — тесты, которые гоняют приложение целиком) из `playwright.config.ts`.

Понимание этого списка снимает главную растерянность в чужой репе: "почему `nx show projects` показывает проект, у которого нет project.json?"

### project.json vs inferred targets: до и после crystal

Это самое крупное поведенческое изменение в истории Nx, и в рабочих репах вы встретите обе эпохи:

- **Старый мир (до Nx 17.2)**: у каждого проекта — "толстый" `project.json`, где каждый target прописан руками: executor, options, configurations, outputs. Десятки строк на проект, дублирование по всей репе, и правка "поменять outDir всем" — это массовый find-and-replace.
- **Project crystal (Nx 18+, мейнстрим с 19)**: targets *выводятся* (inferred) плагинами из конфигов самих инструментов. Если есть `vite.config.ts`, плагин `@nx/vite` даёт проекту `build`, `serve`, `preview` и `test`, прочитав опции прямо из этого конфига. Тогда `project.json` худеет до имени, типа и tags — или исчезает совсем.

Итоговая конфигурация target-а собирается из трёх слоёв — и в незнакомой репе важно понимать, какой слой "победил":

```
              приоритет: выше = сильнее
┌────────────────────────────────────────────────────┐
│ 3. project.json проекта (и ключ "nx"               │
│    в package.json) — точечные переопределения      │
├────────────────────────────────────────────────────┤
│ 2. nx.json: targetDefaults — дефолты для всех      │
│    одноимённых target-ов workspace                 │
├────────────────────────────────────────────────────┤
│ 1. inferred targets от плагинов (crystal):         │
│    vite.config.ts → build / serve / preview / test │
└────────────────────────────────────────────────────┘
          итог: nx show project shell --web
```

Инструмент, который делает эти слои видимыми, — **`nx show project shell --web`**. Он открывает интерактивную страницу со **всеми** target-ами проекта. У каждой опции там подписан источник: какой плагин или файл её принёс. Без `--web` та же команда печатает итоговый JSON в терминал. Это ответ на вопрос "что вообще запустится при `nx build shell`" — и им мы будем пользоваться в каждой главе.

> **Версии.** Имена inferred target-ов — не константы Nx, а опции плагина в `nx.json`: `"serveTargetName": "serve"`. В одних репах dev-сервер — это `nx serve app`, в других — `nx dev app`. Причина в том, что кто-то — или другая версия генератора — назвал target иначе. Прежде чем жаловаться, что "команда из туториала не работает", посмотрите `plugins` в nx.json своей репы.

### apps/ vs libs/ — почему такое деление

Конвенция Nx: **приложения тонкие, библиотеки толстые** (ориентир — 20% кода в apps, 80% в libs). Приложение — это точка сборки и деплоя: роутинг, композиция, конфигурация. Вся логика, UI-компоненты (user interface — пользовательский интерфейс) и работа с данными живут в libs — даже если приложение одно.

Причины прагматичные:

- только у libs бывают границы (`tags` + module boundaries, глава 06);
- только мелкие libs дают точный affected — изменил `catalog/data-access`, и тесты `checkout` не запускаются;
- только вынесенный в lib код можно переиспользовать в будущем втором приложении, а в этом курсе их будет четыре.

Сами имена папок — конвенция: `workspaceLayout` в nx.json может их поменять, а новые preset-ы используют `packages/`.

## В рабочем монорепо

- `npx nx show projects` — плоский список всех проектов репы. Быстрее, чем `nx graph`, когда нужно просто узнать имена и масштаб.
- `npx nx show project <имя> --web` — главная команда главы: все реальные targets проекта и источник каждой опции. Ищите подписи "inferred by @nx/..." против "from project.json".
- `cat nx.json | python3 -m json.tool` — блок `plugins` есть и непустой → репа на crystal, конфиги инструментов = источник правды. Блока нет, а project.json толстые → старый стиль, правда живёт в project.json.
- `find . -name project.json -not -path "*/node_modules/*" -exec wc -l {} +` — толщина project.json по всей репе за секунду. Файлы по 10 строк — это crystal, по 100+ строк — явные executors.
- `npx nx list @nx/react` — какие генераторы и executors даёт установленный плагин; работает для любого `@nx/*`.

## Что добавляем в проект

Генерируем первое приложение — `shell`, будущий host микрофронтенда (глав 10–11). Пока это обычное React-приложение на Vite. Заодно workspace получает первые плагины в `nx.json` и `tsconfig.base.json`.

## Практическое задание

**Вход:** workspace `mini-shop` из главы 00 (пустой, один коммит).

**Задача:**

1. Добавить плагин React командой `npx nx add @nx/react` и посмотреть diff: что изменилось в `package.json` и `nx.json`?
2. Сгенерировать приложение `shell` в `apps/shell`: bundler — vite, стили — css, тесты — vitest, e2e — не нужен. Сначала прогнать генератор с `--dry-run` и прочитать список файлов, потом — по-настоящему.
3. Изучить результат и письменно ответить:
   - Сколько target-ов задекларировано в `apps/shell/project.json` — и сколько показывает `nx show project shell`? Откуда взялась разница?
   - Что появилось в `plugins` в nx.json и какие имена target-ов там заданы?
   - Почему `tsconfig.base.json` появился в корне только сейчас, а не в главе 00?
4. Запустить `nx serve shell` (проверить в браузере) и `nx build shell`. Затем найти на диске артефакт сборки и файл, в котором задан его путь.

**Edge cases на подумать:**

- Что произойдёт при повторном запуске того же генератора? А с флагом `--dry-run`?
- Как переименовать target `serve` в `dev` для всех vite-проектов сразу, не трогая ни один project.json?
- Почему `nx add @nx/react` лучше, чем `npm install -D @nx/react` вручную?

## Разбор решения

Установка плагина и генерация:

```bash
npx nx add @nx/react
# ставит @nx/react ТОЧНО той же версии, что nx, и запускает его init-генератор

npx nx g @nx/react:app shell --directory=apps/shell --dry-run
# CREATE apps/shell/project.json ... — только план, диск не тронут

npx nx g @nx/react:app shell --directory=apps/shell \
  --bundler=vite --style=css --unitTestRunner=vitest \
  --e2eTestRunner=none --linter=eslint
```

> **Версии.** С Nx 18 путь проекта задаётся ровно так, как вы его написали: `--directory=apps/shell` — это буквально та самая папка. В старых версиях (`projectNameAndRootFormat=derived`) Nx сам конструировал путь из имени и вложенных папок. Та же команда могла положить проект совсем в другое место.

> **Версии.** Команда `nx add` появилась в Nx 17. До неё плагин ставили руками, и главный риск был поставить версию, не совпадающую с ядром (глава 00).

Что появилось (плюс мелочи вроде favicon — состав зависит от версии):

```
mini-shop/
├── apps/shell/
│   ├── index.html            # dev-вход vite
│   ├── project.json          # ТОНКИЙ: имя, тип, tags — targets нет
│   ├── vite.config.ts        # источник правды для build/serve/test
│   ├── tsconfig.json         # + tsconfig.app.json, .spec.json
│   └── src/
│       ├── main.tsx          # bootstrap: createRoot + <App/>
│       ├── styles.css
│       └── app/
│           ├── app.tsx
│           └── app.spec.tsx  # vitest, тот же vite.config.ts
├── tsconfig.base.json        # появился с первым TS-проектом
└── eslint.config.mjs         # в новых версиях — flat config
```

`apps/shell/project.json` — весь, целиком:

```json
{
  "name": "shell",
  "$schema": "../../node_modules/nx/schemas/project-schema.json",
  "projectType": "application",
  "sourceRoot": "apps/shell/src",
  "tags": []
}
```

Target-ов здесь **ноль**. При этом:

```bash
npx nx show project shell
# {
#   "name": "shell",
#   "targets": {
#     "build":   { "command": "vite build", ... },
#     "serve":   { "command": "vite serve", ... },
#     "preview": { "command": "vite preview", ... },
#     "test":    { "command": "vitest", ... },
#     "lint":    { "command": "eslint .", ... }
#   }
# }
```

Все пять target-ов — inferred: их принесли плагины, зарегистрированные `nx add` в nx.json. Обратите внимание: crystal-таргеты запускают **CLI самого инструмента** (command-line interface — интерфейс командной строки). `vite build` — та же команда, что вы набрали бы руками. Nx добавляет вокруг неё граф, кеш и pipeline; как это устроено — глава 03.

```json
{
  "plugins": [
    {
      "plugin": "@nx/vite/plugin",
      "options": {
        "buildTargetName": "build",
        "serveTargetName": "serve",
        "previewTargetName": "preview",
        "testTargetName": "test"
      }
    },
    { "plugin": "@nx/eslint/plugin", "options": { "targetName": "lint" } }
  ],
  "generators": {
    "@nx/react": {
      "application": {
        "babel": true, "style": "css", "linter": "eslint", "bundler": "vite"
      }
    }
  }
}
```

Ключевые решения:

- Ответ на edge case про переименование: поменять `"serveTargetName": "serve"` на `"dev"` в этом блоке. И у **всех** vite-проектов репы target станет `nx dev <проект>`. Ни один файл проекта не трогается — вот что значит "target-ы принадлежат плагину, а не проекту".
- `generators."@nx/react"` — записанные ответы визарда: следующий `nx g @nx/react:lib` в этой репе молча возьмёт те же опции. Так команда получает единообразные проекты без "у Пети lib на styled-components, у Маши на css".
- `tsconfig.base.json` появился только сейчас, потому что его создаёт init-генератор первого JS/TS-плагина, а не `create-nx-workspace`. Пустому workspace он не нужен. Пока в нём нет `paths` — первый алиас появится с первой либой в главе 02.

Запуск и сборка:

```bash
npx nx serve shell     # vite dev-server, по умолчанию http://localhost:4200
npx nx build shell     # артефакт: dist/apps/shell/
```

Путь артефакта задан не "где-то в Nx", а в `apps/shell/vite.config.ts` → `build.outDir`. Плагин прочитал его оттуда и сообщил Nx как output этого target-а — это важно для кеша (глава 04).

Повторный запуск генератора поверх существующего проекта упадёт на конфликте имён. Генераторы не обещают идемпотентности — свойства давать один и тот же результат при каждом запуске. Для проверки "что изменится" и существует `--dry-run`.

## Проверь себя

1. В project.json проекта нет ни одного target-а, но `nx build` для него работает. Объясни механику: кто и из чего создал этот target?
2. В каком порядке сливаются три слоя конфигурации target-а и какой побеждает? Где это увидеть для конкретного проекта?
3. Почему "тонкие apps, толстые libs" — это не эстетика, а требование механики Nx? Назови минимум две фичи, которые деградируют, если вся логика лежит в приложении.
4. Какие три вещи делают папку "проектом" в глазах Nx? Почему `nx show projects` может показывать больше проектов, чем есть файлов project.json?
5. В одной репе dev-сервер запускается `nx serve app`, в другой — `nx dev app`. Где физически лежит причина различия и что это говорит о природе имён target-ов?

<details>
<summary>Ответы</summary>

1. При построении графа плагин из `nx.json` (например, `@nx/vite/plugin`) сканирует репу своим `createNodes`. Он находит `vite.config.ts`, читает его и *выводит* target-ы (`build`, `serve`, ...) с уже заполненными опциями. Target существует только в памяти графа — в файлах проекта его нет. Конфиг инструмента и есть источник правды. Поэтому правка `vite.config.ts` меняет поведение `nx build` без единого изменения в project.json.
2. Снизу вверх: inferred targets плагинов, поверх них `targetDefaults` из nx.json, а поверх — точечные переопределения из project.json. Ключ `"nx"` в package.json проекта работает так же, как project.json, и побеждает именно project.json. Итоговый результат слияния показывает `nx show project <имя>` (с `--web` — ещё и источник каждой опции).
3. Во-первых, affected: если вся логика в одном app, любое изменение затрагивает "весь app" — пересобирается и перетестируется всё, гранулярность теряется. Во-вторых, module boundaries: tags и boundary-правила (глава 06) вешаются на библиотеки — монолитному app нечего ограничивать. В-третьих, переиспользование: код из app нельзя импортировать в другое приложение (и в этом курсе их будет четыре), из lib — можно.
4. Три вещи. Файл `project.json` в папке. Файл `package.json` в папке. Либо плагин из nx.json, чей `createNodes` сматчился на конфиг инструмента в этой папке. Третий источник и объясняет "лишние" проекты. У e2e-проекта, созданного `@nx/playwright` из одного `playwright.config.ts`, файла project.json может не быть вовсе.
5. В nx.json, в опциях плагина: `"serveTargetName": "serve"` или `"dev"`. Имена target-ов — не зашитые в Nx константы, а конфигурируемые опции конкретной репы. Поэтому первый рефлекс в чужом workspace — не гуглить "правильную" команду. Вместо этого посмотрите `plugins` в nx.json или запустите `nx show project <имя>`.

</details>

## Частая ошибка

Разработчик из single-app мира открывает `apps/shell/project.json` и видит пять строк без единого target-а. Вывод: "конфигурация где-то прячется, Nx — магия". Дальше два плохих сценария.

Первый: он находит в интернете статью 2022 года (мир до crystal) и вписывает в project.json полный target `build` с executor и options. Теперь в репе **два источника правды**. Его ручной target молча перекрывает inferred, и правки vite.config.ts частично перестают влиять на сборку.

Второй: он правит `vite.config.ts`, не зная, что конкретная опция переопределена в `targetDefaults`, и не понимает, почему ничего не меняется. Лекарство в обоих случаях одно: `nx show project shell --web`. Увидеть итоговую конфигурацию и *источник* каждой опции, прежде чем что-либо править.

Родственный рефлекс — создать новое приложение копированием папки существующего: "скопирую shell, переименую — быстрее, чем разбираться с генераторами". Ломается сразу три вещи. В скопированном project.json остаётся старое имя, а это конфликт при построении графа. Tags и алиасы уезжают. Половина файлов, которые генератор бы адаптировал, остаётся от донора.

Генератор с `--dry-run` покажет полный список того, что должно быть создано и изменено. Это и есть честный ответ на вопрос "что входит в новый проект".
