# Affected: пересобирать только затронутое

## Теория

### Механика: от git diff до списка задач

`nx affected` отвечает на вопрос "что могло сломаться от *этих* изменений" — и запускает задачи только для этого подмножества. Конвейер:

```
┌────────────────────────────────────────────────────────────┐
│ git merge-base(base, head) → git diff                      │
│ список изменённых файлов                                   │
└────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌────────────────────────────────────────────────────────────┐
│ каждый файл → проект-владелец                              │
│ (по projectRoot; вне всех проектов = глобальное изменение) │
└────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌────────────────────────────────────────────────────────────┐
│ замыкание ВВЕРХ по графу:                                  │
│ + все, кто зависит от изменённых (транзитивно)             │
└────────────────────────────────────────────────────────────┘
                               │
                               ▼
┌────────────────────────────────────────────────────────────┐
│ nx affected -t lint,test,build:                            │
│ обычный task graph, но только для затронутых               │
└────────────────────────────────────────────────────────────┘
```

Три детали, которые тут важно увидеть:

- **merge-base, а не прямой diff.** Nx сравнивает head не с самим `--base`, а с *точкой ветвления* (`git merge-base`). Поэтому коммиты, влитые в main после того, как вы отвели ветку, не раздувают ваш affected: сравнивается только то, что сделали вы. База по умолчанию — `defaultBase` из nx.json (мы видели его ещё в главе 00).
- **Замыкание идёт вверх — к зависимым.** Изменили `shared-ui` → затронуты `shared-ui` и все, кто от неё зависит (`shell`), транзитивно до самого верха. Вниз (зависимости `shared-ui`) замыкание не идёт: их никто не менял. Но не путайте уровни: когда для затронутого `shell` создаётся задача `build`, правило `dependsOn: ["^build"]` из главы 03 как обычно дотянет build-задачи его зависимостей — уже как предпосылки, и они, скорее всего, отдадутся из кеша.
- **Файл вне всех проектов = глобальное изменение.** У `nx.json`, корневого `package.json`, lock-файла нет проекта-владельца — Nx консервативно считает затронутым **всё**. Это фича: изменение версий зависимостей или правил пайплайна честно может сломать что угодно. Практическое следствие — массовые обновления зависимостей стоит возить отдельными PR, не смешивая с фичами.

### Почему affected — основной механизм масштабирования CI

Вспомните арифметику из главы 00: время наивного CI = число проектов × среднее время задач, и первый множитель растёт с репой. Кеш (глава 04) убирает повторное выполнение *неизменившегося*, но список задач всё равно линейный: тысяча cache-hit-ов — это тысяча обращений к кешу. Affected атакует сам список: задач создаётся ровно столько, сколько затронуто. Эти два механизма работают на разных уровнях и складываются: **affected сужает "что запускать", кеш убирает повторы внутри этого списка**. PR, меняющий одну либу в репе на 300 проектов, порождает десяток задач — и часть из них ещё и хиты.

Важный нюанс на стыке уровней: affected оперирует *проектами*, кеш — *хешами*. Правка `app.spec.tsx` делает проект `shell` затронутым → задача `shell:build` будет создана. Но её хеш не изменился (спеки вычтены из `production`, глава 04) → задача мгновенно отдастся из кеша. Affected — грубый фильтр, кеш — точный; они не дублируют, а страхуют друг друга.

### Бесполезен без правильного графа

`nx affected` не умнее графа, по которому считает замыкание. Три способа получить от него мусор:

- **Пропущенные рёбра.** Классика — e2e-проект без `implicitDependencies` (глава 02): меняете приложение, e2e не в affected, CI зелёный, регрессия в проде. Ребро, которого нет в графе, — это тест, который не запустится.
- **Слишком крупные либы.** Одна `shared/utils` на всю репу, куда сваливают всё подряд, → от неё зависят все → любая правка в ней даёт affected ≈ вся репа. Точность affected равна гранулярности графа; курс на мелкие либы с ясными границами (глава 06) — это в том числе курс на дешёвый CI.
- **Связи мимо импортов.** Скрипт читает файл чужого проекта через `fs.readFile`, сборка подтягивает артефакт соседа по захардкоженному пути — граф таких связей не видит, affected их не учитывает. Правило то же, что в главе 02: зависимость должна быть выражена импортом либо implicit-ребром.

### Команды

```bash
nx affected -t build                       # затронутые build-задачи (base = defaultBase)
nx affected -t lint,test,build             # конвейер по затронутым
nx show projects --affected                # только СПИСОК проектов, без запуска
nx affected --graph                        # визуально: кто затронут и через какие рёбра
nx affected -t test --base=origin/main --head=HEAD   # явные границы сравнения
nx affected -t build --exclude='*-e2e'     # исключить по шаблону
```

## В рабочем монорепо

- Перед пушем: `nx affected -t lint,test --base=origin/main` — прогнать локально ровно то, что заденет ваш PR, а не всю репу.
- `nx show projects --affected --base=origin/main` — секундный ответ "кого я задел"; полезно перед ревью, чтобы понимать масштаб.
- `nx affected --graph --base=origin/main` — когда список удивляет: покажет цепочку рёбер от вашей правки до неожиданного проекта (та же задача, что path tracing из главы 02, но для текущего diff).
- В CI-конфиге репы найдите, как вычисляется base: хардкод `--base=HEAD~1` — красный флаг (при squash-merge и пропущенных прогонах теряются изменения); правильный паттерн — SHA последнего успешного прогона (в GitHub Actions это делает `nrwl/nx-set-shas`, глава 13).
- Метрика здоровья графа: правка в самой популярной либе → `nx show projects --affected | wc -l`. Если почти любая правка затрагивает почти всё — у репы проблема гранулярности, и лечится она главой 06, а не отключением affected.

## Что добавляем в проект

Код mini-shop не меняется — мы имитируем CI локально: ветка с правкой одной либы, разбор списка affected на всех уровнях (проекты → задачи → кеш) и проверка глобальной границы через правку nx.json.

## Практическое задание

**Вход:** workspace после главы 04 (настроенные namedInputs, всё закоммичено в `main`).

**Задача:**

1. Отвести ветку `feat/ghost-button` и внести правку в `libs/shared/ui/src/lib/button.tsx` (например, новый вариант кнопки). Закоммитить.
2. Не запуская задач, получить список затронутых проектов относительно `main` и объяснить каждый элемент списка.
3. Запустить `nx affected -t lint,test,typecheck,build --base=main` и разобрать: какие задачи создались, для каких проектов, почему `build` создался только для shell.
4. Вторым коммитом поменять **только** `apps/shell/src/app/app.spec.tsx` и снова запустить affected c build: объяснить, почему задача `shell:build` создана, но выполнилась из кеша.
5. Третьим коммитом внести правку в `nx.json` — и показать, что затронутыми стали все проекты. Объяснить механизм.
6. Проверить merge-base: сделать коммит в `main` (правка README) после ветвления — убедиться, что affected ветки не изменился.

**Edge cases на подумать:**

- Удаление файла — изменение? А переименование папки либы?
- Что покажет affected на ветке, у которой ещё нет ни одного коммита?
- Почему `--base=HEAD~1` в CI на push-событиях теряет изменения?

## Разбор решения

Шаги 1–3 — правка либы:

```bash
git switch -c feat/ghost-button
# ... правка button.tsx ...
git commit -am "feat: ghost button variant"

npx nx show projects --affected --base=main
# shared-ui
# shell

npx nx affected -t lint,test,typecheck,build --base=main
#    ✔  nx run shared-ui:lint
#    ✔  nx run shared-ui:test
#    ✔  nx run shell:lint
#    ✔  nx run shell:typecheck
#    ✔  nx run shell:test
#    ✔  nx run shell:build
```

Разбор списка: `shared-ui` — владелец изменённого файла; `shell` — замыкание вверх (зависит от shared-ui через ребро из главы 02). Задача `build` создана только для shell: у shared-ui target-а `build` нет (non-buildable), а правило `^build` для shell задач не добавило — нечего. `lint` у shared-ui и `typecheck`+`test` у shell — обычный параллелизм из главы 03.

Шаг 4 — правка только спека:

```bash
npx nx affected -t build --base=main
#    ✔  nx run shell:build  [local cache]
```

Два фильтра на разных уровнях: affected видит "проект shell изменился" (спек — файл проекта) и создаёт задачу; кеш видит "хеш не изменился" (спеки вычтены из production-inputs) и отдаёт replay. Ни один уровень не ошибся — они просто отвечают на разные вопросы.

Шаг 5 — глобальная граница:

```bash
# правка targetDefaults в nx.json
npx nx show projects --affected --base=main
# shared-ui
# shell          ← все проекты репы
```

У nx.json нет проекта-владельца → Nx считает изменение глобальным → затронуто всё. То же самое с package.json и lock-файлом: PR "подняли 40 зависимостей + маленькая фича" прогонит полный CI — поэтому массовые обновления возят отдельно.

Шаг 6 — merge-base: коммит в main после ветвления не попадает в diff, потому что сравнение идёт от точки ветвления (`git merge-base main HEAD`), а не от кончика main. Affected ветки не изменился.

Ответы на edge cases:

- Удаление файла — полноценное изменение файлов проекта (diff его видит), проект затронут. Переименование папки либы — изменение всех её файлов + правка tsconfig.base.json (глобальный файл!) → фактически затронется вся репа; переезды либ лучше делать выделенным PR (и генератором `@nx/workspace:move`, глава 07).
- Ветка без коммитов: diff пуст — affected пуст; но незакоммиченные файлы Nx тоже учитывает (uncommitted/untracked входят в сравнение) — поэтому локально affected работает и до коммита.
- `--base=HEAD~1` сравнивает только с предыдущим коммитом: squash-merge из пяти коммитов, пропущенный прогон CI, force-push — и часть изменений никогда не попадёт ни в один diff. База должна быть "последним состоянием, которое CI реально проверил" — этим и занимается nx-set-shas.

## Проверь себя

1. Опиши полный конвейер `nx affected -t test --base=main`: четыре стадии от git до задач.
2. Почему замыкание по графу идёт только вверх (к зависимым), и как при этом build-задачи зависимостей всё же попадают в выполнение?
3. Разработчик влил в main большой рефакторинг; твоя ветка отведена неделю назад. Раздует ли это твой affected и почему?
4. Правка спек-файла: почему `nx affected -t build` создаёт build-задачу, но она не выполняется? Какие два механизма и на каких уровнях сработали?
5. В репе одна гигантская либа `shared/common`, от которой зависят все 50 приложений. Что происходит с affected при любой правке в ней и каким курсом это лечится?

При этом если затронутому проекту для `build` нужны собранные зависимости, `dependsOn: ["^build"]` создаст эти задачи как предпосылки в task graph — они не "затронуты", просто выполняются (и почти всегда закрываются кешем).
3. Нет. Nx сравнивает не с кончиком main, а с merge-base — общим предком ветки и main. Рефакторинг влит после ветвления и в вашей истории отсутствует; в diff попадают только ваши изменения. (Отдельный вопрос — что после rebase на свежий main affected честно вырастет, если рефакторинг задел ваши зависимости.)
4. Affected работает на уровне проектов: спек принадлежит shell → shell затронут → задача `shell:build` попадает в план. Кеш работает на уровне хешей: inputs у build — `production`, спеки из него вычтены → хеш совпал с прежним → replay из `.nx/cache` вместо выполнения. Грубый фильтр решил "проверить", точный — "выполнять нечего".
5. Любая правка в `shared/common` затрагивает её + всех 50 потребителей — affected вырождается в "всё", CI снова линейный. Лечение — гранулярность: распилить либу по назначению (ui / util / data-access, глава 06), чтобы у каждой части был свой, узкий круг потребителей. Отключать affected или дробить репу обратно на polyrepo — борьба с симптомом.

## Частая ошибка

Разработчик из single-app мира не доверяет "частичному" CI: как это — PR прошёл, а собиралась не вся репа? И в CI появляется `nx run-many -t build` "на всякий случай" — весь смысл масштабирования выброшен, конвейер снова растёт линейно с репой, а команда через полгода жалуется на сорокаминутные пайплайны. Доверие к affected — это доверие к графу: если граф полон (рёбра + implicit для e2e), то "не затронуто" математически означает "не могло сломаться от этого diff-а". Чинить надо неполный граф, а не расширять список запусков.

Обратная крайность — самодельный affected: `--base=HEAD~1`, "сравним с прошлым коммитом, чего мелочиться". На push после squash-merge из пяти коммитов CI сравнит только с четырьмя из них уже проверенное состояние... и молча пропустит первый. Пропущенный прогон, ручной re-run, force-push — каждый сценарий оставляет непроверенные изменения. База для affected — не "предыдущий коммит", а "последнее состояние, которое CI успешно проверил"; в экосистеме это решено готовым действием (`nrwl/nx-set-shas`), и в главе 13 мы его подключим.
