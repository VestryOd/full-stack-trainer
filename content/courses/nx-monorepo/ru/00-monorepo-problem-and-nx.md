# Проблема монорепо и место Nx

## Теория

### Какие проблемы монорепо решает — и какие создаёт

Спор "polyrepo vs monorepo" часто ведут на уровне вкусов, но за ним стоят три вполне конкретные инженерные проблемы polyrepo:

1. **Шаринг кода.** В polyrepo общий код (ui-kit, типы API-контрактов, утилиты) распространяется через npm publish: собрать → поднять версию → запаблишить → обновить в каждом потребителе. Это часы-дни задержки на каждое изменение, и в каждый момент времени разные приложения сидят на разных версиях одной либы.
2. **Атомарные изменения через границы.** Поменяли контракт API — нужно синхронно поправить бэкенд и всех фронтовых потребителей. В polyrepo это несколько PR (pull request — запрос на слияние ветки) в разных репах, и смержить их атомарно нельзя. Между мержами система остаётся в несогласованном состоянии. Никакой CI (continuous integration — сборка и тесты на сервере при каждом пуше) этого не ловит.
3. **Единые версии зависимостей.** Пять реп — пять package.json, пять версий React, пять конфигураций TypeScript. Обновление зависимости превращается в кампанию на квартал.

```
POLYREPO: репозиторий на приложение      MONOREPO: один репозиторий
┌────────────┐ ┌───────────┐            ┌─────────────────────────┐
│ shop-web   │ │ shop-api  │            │ mini-shop/              │
│            │ │           │            │                         │
│ ui-kit@1.2 │ │ types@2.1 │            │ apps/  shell · catalog  │
│ types@1.8  │ │           │            │        checkout · api   │
└────────────┘ └───────────┘            │ libs/  shared/ui        │
шаринг кода — через npm publish;        │        shared/api-types │
версии расходятся, изменение            └─────────────────────────┘
контракта = несколько PR и релизов      один граф импортов,
                                        единые версии зависимостей,
                                        атомарные PR через границы
```

Монорепо решает все три ценой двух новых проблем, и обе — про масштаб:

- **Сборка и тесты растут линейно с размером репы.** Наивный CI-скрипт "собери и протестируй всё" на 50 проектах — это часы на каждый PR. И так будет, даже если PR меняет один файл в одной либе.
- **Хаос связей.** Когда весь код в одной репе, импортировать можно всё отовсюду. Без явных правил через год получается "big ball of mud" — большой ком грязи, кодовая база без видимой структуры, где каждая либа зависит от каждой.

Именно эти две проблемы и решает Nx. Всё остальное — генераторы, миграции, плагины — полезная обвязка. Ядро ценности — это две вещи: **не собирать то, что не изменилось** (computation caching + affected) и **держать границы** (project graph + module boundaries).

### Место Nx среди альтернатив

Важно понимать слои. Workspaces пакетного менеджера (npm/pnpm/yarn) решают только установку зависимостей: один `node_modules`, локальные пакеты доступны друг другу через симлинки. Они ничего не знают о том, *что от чего зависит на уровне задач* и *что нужно пересобрать*.

```
┌──────────────────────────────────────────────────┐
│ плагины: @nx/react, @nx/node, @nx/eslint, ...    │
│ генераторы · executors · inferred targets        │
├──────────────────────────────────────────────────┤
│ ядро Nx: project graph · task pipeline           │
│ computation cache · affected                     │
├──────────────────────────────────────────────────┤
│ workspaces пакетного менеджера (npm/pnpm/yarn):  │
│ установка зависимостей, симлинки пакетов         │
├──────────────────────────────────────────────────┤
│ обычный git-репозиторий: apps/ · libs/ · nx.json │
└──────────────────────────────────────────────────┘
```

- **Lerna** — исторически первый популярный тул, в первую очередь про версионирование и публикацию пакетов. С 2022 года Lerna поддерживается командой Nx и под капотом делегирует таски Nx.
- **Turborepo** — task runner + кеш поверх package-based монорепо. Идейно близок к ядру Nx, но граф строится из `package.json`-зависимостей, а не из анализа импортов. Слоя генераторов, плагинов и boundary-правил здесь нет.
- **Nx** добавляет сверху несколько слоёв:
  - **project graph из статического анализа импортов** (глава 02);
  - **computation caching** с точной моделью inputs/outputs (глава 04);
  - **affected** (глава 05);
  - **генераторы и миграции** (глава 07);
  - **module boundaries** через ESLint (глава 06);
  - плагины, которые понимают конкретные инструменты: webpack, vite, jest, playwright.

Ключевое отличие Nx от Turborepo для повседневной работы — в том, откуда берутся рёбра графа. Nx видит зависимость `shell → shared/ui`, даже если она выражена только TS-импортом, без записи в package.json. Это точнее и не требует дисциплины "не забудь задекларировать зависимость".

### Integrated vs package-based

Классификация из документации Nx, которую вы встретите в статьях и на собеседованиях:

- **Package-based**: каждый проект — полноценный npm-пакет со своим `package.json` и своими зависимостями. Связи идут через workspaces пакетного менеджера. Nx здесь — только task runner + кеш.
- **Integrated**: единый `package.json` в корне на всю репу — это правило и называется single version policy. Проекты связаны через алиасы в `tsconfig.base.json`: `@mini-shop/shared-ui` → `libs/shared/ui/src/index.ts`. Nx управляет всем через плагины и генераторы.

> **Версии.** В старых версиях (Nx 15–16) это была жёсткая развилка прямо в визарде (интерактивном мастере) `create-nx-workspace`: "package-based or integrated?". Начиная с Nx 19–20 граница размыта, и тому две причины.

> **Причина первая — project crystal.** Плагины сами выводят targets проекта из конфигов инструментов вроде `vite.config.ts` (глава 01). Из-за этого integrated-режим стал таким же "лёгким", как package-based. **Причина вторая — новый TS-preset** (Nx 20+): он связывает проекты через workspaces пакетного менеджера и TypeScript project references, а не через алиасы в `tsconfig.base.json`.

> **Что вы встретите на практике.** В реальном рабочем проекте, начатом на Nx 15–17, вы почти наверняка увидите классический integrated-вариант с `tsconfig.base.json`. В свежесозданном — возможно, уже новый. Уметь опознать оба важнее, чем спорить, какой "правильный".

### Что такое Nx технически

Никакой магии: `nx` — это обычный npm-пакет с CLI (command-line interface — интерфейс командной строки), который ставится в devDependencies. Команда `npx nx build shell` запускает локальный бинарник `node_modules/.bin/nx`. Этот бинарник читает `nx.json` + конфиги проектов, строит граф, считает хеши и запускает таски.

Всё, что Nx производит, лежит в обычных файлах. Кеш — это папка `.nx/cache` на диске (до Nx 17 — `node_modules/.cache/nx`), данные графа — `.nx/workspace-data`. Всё это можно посмотреть руками, чем мы регулярно будем заниматься.

## В рабочем монорепо

Как опознать пройденное в существующем workspace, куда вас только что добавили:

- `npx nx report` — первая команда в незнакомой репе: версия Nx, версии всех `@nx/*`-плагинов, пакетный менеджер. Если версии плагинов не совпадают с версией nx — репу давно не мигрировали (глава 13).
- `ls` в корне. Если есть `nx.json` — репа под Nx. Репа с `apps/` + `libs/` + `tsconfig.base.json` с блоком `paths` — классический integrated. Репа с `packages/` + полем `workspaces` в package.json (или `pnpm-workspace.yaml`) и без paths-алиасов — package-based или новый TS-preset.
- `cat package.json | head -30`. Один корневой package.json со всеми зависимостями = single version policy. Если у каждого проекта свой package.json с dependencies — это package-based.
- `npx nx graph` — откроет интерактивный граф в браузере: сколько вообще проектов, есть ли островки, что в центре. Первое, что стоит сделать в новой репе после `nx report`.
- `git log --oneline --follow nx.json | tail -5` — когда репу перевели на Nx и с чего она начиналась.

## Что добавляем в проект

Стартуем сквозной проект курса: пустой workspace `mini-shop`, из которого за 15 глав вырастет host + два remote-микрофронтенда + Node API. В этой главе — только `create-nx-workspace` и разбор каждого сгенерированного файла.

## Практическое задание

**Вход:** машина с Node 20+, пустая директория.

**Задача:** создать workspace `mini-shop` командой `npx create-nx-workspace@latest`. Preset (заготовка воркспейса) — пустой `apps`, пакетный менеджер — npm. Nx Cloud и CI не подключать, это глава 13.

**Выход:** git-репозиторий с первым коммитом, сделанным самим Nx, и письменные ответы на вопросы:

1. Какие файлы сгенерировались в корне и зачем нужен каждый?
2. Что лежит в `nx.json` сразу после генерации?
3. Где Nx хранит кеш и данные графа, и почему эти пути в `.gitignore`?
4. Как зафиксирована версия `nx` в package.json — диапазоном или точно, и почему это важно?
5. Что показывают `npx nx list` и `npx nx report` на пустом workspace?

**Edge cases на подумать:**

- Что произойдёт, если запустить `create-nx-workspace` внутри уже существующего git-репозитория?
- Чем `nx init` (добавить Nx в существующий проект) отличается от `create-nx-workspace`?
- Почему `nx` ставится в devDependencies проекта, а не глобально через `npm i -g nx`?

## Разбор решения

Создание workspace (визард задаст вопросы; их же можно передать флагами, чтобы результат был воспроизводимым):

```bash
npx create-nx-workspace@latest mini-shop --preset=apps --pm=npm --nxCloud=skip

cd mini-shop
git log --oneline
# abc1234 Initial commit  ← коммит сделал сам create-nx-workspace
```

> **Версии.** Точный список вопросов визарда заметно менялся между мажорами. Старые версии спрашивали "integrated vs package-based". Новые спрашивают стек (None/React/Vue/Node), бандлер и CI-провайдера. Флаг `--preset=apps` — стабильный способ получить пустой workspace. Если ваша версия его не поддерживает, ближайший аналог — `--preset=ts`.

Что сгенерировалось (preset `apps`, состав может немного отличаться от версии к версии — сверяйте со своим выводом):

```
mini-shop/
├── apps/            # сюда генерируются приложения (пока пусто)
├── nx.json          # конфигурация самого Nx
├── package.json     # ЕДИНЫЙ package.json — single version policy
├── .gitignore       # node_modules, dist,
│                    # .nx/cache, .nx/workspace-data
├── .prettierrc      # в некоторых версиях — prettier из коробки
└── README.md
```

`package.json` — обратите внимание на точную версию:

```json
{
  "name": "@mini-shop/source",
  "version": "0.0.0",
  "license": "MIT",
  "scripts": {},
  "private": true,
  "devDependencies": {
    "@nx/workspace": "21.3.1",
    "nx": "21.3.1"
  }
}
```

Ключевые решения:

- Версии `nx` и `@nx/*` зафиксированы **точно, без `^`** — генератор пишет их так намеренно. Ядро и плагины Nx должны быть строго одной версии. Разъезд на minor между `nx` и `@nx/react` — источник трудноуловимых поломок. Обновление — только через `nx migrate` (глава 13), который поднимает всё синхронно.
- `scripts` пустой — и это нормально. В Nx-репе задачи запускаются не через npm-скрипты, а через `nx <target> <project>`: npm-скрипт обошёл бы граф, кеш и task pipeline.

`nx.json` сразу после генерации минимален:

```json
{
  "$schema": "./node_modules/nx/schemas/nx-schema.json",
  "defaultBase": "main"
}
```

- `$schema` даёт автокомплит в IDE (integrated development environment — среда разработки) — полезно, когда начнём добавлять `namedInputs` и `targetDefaults` (главы 03–04).
- `defaultBase` — базовая ветка для `nx affected` (глава 05). В старых версиях то же самое лежало глубже, в `affected.defaultBase`.

Проверка инструментов на пустом workspace:

```bash
npx nx report
# NX   Report complete - copy this into the issue template
# Node    : 20.x
# npm     : 10.x
# nx      : 21.3.1
# @nx/workspace : 21.3.1

npx nx list
# установлен только @nx/workspace;
# ниже — список плагинов, которые МОЖНО поставить (@nx/react, @nx/node, ...)

npx nx graph
# открывает браузер с пустым графом — проектов ещё нет
```

Ответы на edge cases:

- Внутри существующего git-репо `create-nx-workspace` создаст **вложенную** директорию со своим `.git` — почти всегда не то, что нужно. Для существующего проекта есть `nx init`: он добавляет `nx` в devDependencies и генерирует `nx.json`, не трогая структуру.
- Глобальная установка `nx` допустима как удобный лаунчер: глобальный `nx` находит и вызывает **локальную** версию из node_modules. Но источник правды всегда локальная версия. Поведение `nx build` должно зависеть от репы, а не от того, что стоит на конкретной машине разработчика.

## Проверь себя

1. Почему CI наивного монорепо ("собрать и протестировать всё на каждый PR") деградирует линейно с ростом репы, и какие два механизма Nx разрывают эту зависимость?
2. Чем project graph Nx принципиально отличается от того, что знают о зависимостях npm/pnpm workspaces? Почему симлинков недостаточно, чтобы ответить на вопрос "что пересобирать?"
3. По каким файлам в корне незнакомой репы вы отличите классический integrated-workspace от package-based? Почему эта дихотомия размылась в новых версиях Nx?
4. Почему генератор фиксирует версии `nx` и `@nx/*` точно, без `^`? Что может сломаться, если `nx` обновится на minor, а плагины — нет?
5. Команда сборки в Nx-репе — `nx build shell`, а не npm-скрипт `"build": "webpack ..."`. Что именно теряется, если запустить инструмент напрямую, в обход Nx?

<details>
<summary>Ответы</summary>

1. Время CI = (число проектов) × (среднее время сборки/тестов). Первый множитель растёт с репой, хотя объём изменений в одном PR — нет. Nx разрывает зависимость двумя механизмами. **Affected** сокращает список задач до затронутых изменением проектов — по графу. **Computation caching** превращает повторные запуски незатронутого в мгновенный cache hit. Вместе они делают стоимость PR пропорциональной размеру *изменения*, а не размеру *репозитория*.
2. Workspaces знают только декларации из `package.json` — "пакет A установлен и досягаем". Nx строит граф **статическим анализом импортов исходников**. Реальное ребро `shell → shared/ui` появляется потому, что в коде есть `import ... from '@mini-shop/shared-ui'`, даже без записи в package.json. Для ответа "что пересобирать" нужны фактические связи кода, а не декларации установки. Задекларированная, но неиспользуемая зависимость даёт лишние пересборки, а незадекларированная фактическая (в package-based тулах) — пропущенные.
3. Integrated: единый корневой `package.json` со всеми зависимостями + `tsconfig.base.json` с блоком `paths`-алиасов + `apps/`/`libs/`. Package-based: `packages/`, у каждого пакета свой `package.json` с dependencies, поле `workspaces` (или `pnpm-workspace.yaml`) в корне. Размылась она по двум причинам. Project crystal убрал главную "тяжесть" integrated — ручные project.json с executors. А новый TS-preset Nx 20+ сам использует workspaces + project references. В итоге современный integrated-workspace выглядит наполовину как package-based.
4. Ядро (`nx`) и плагины (`@nx/*`) — один продукт, выпускаемый синхронно: плагины зовут внутренние API ядра, не имеющие semver-гарантий. С `^` обычный `npm install` мог бы поднять `nx` на минор, оставив плагины старыми. И тогда `nx build` падал бы с ошибками внутри node_modules, которые никак не связаны с вашим кодом. Точные версии + `nx migrate` гарантируют согласованное обновление всего набора сразу.
5. Теряются три вещи. **Кеш**: результат не сохранится и не переиспользуется — ни локально, ни в CI. **Task pipeline**: `dependsOn: ["^build"]` не отработает, и зависимости не будут собраны перед проектом. **Граф/affected**: запуск не попадёт в модель "что затронуто". Инструмент отработает, но репа перестанет получать главную выгоду Nx. О том, какой executor Nx вызывает под капотом той же команды, — глава 03.

## Частая ошибка

Разработчик из мира single-app приносит в монорепо один рефлекс: "package.json — центр управления проектом". Он добавляет npm-скрипты `"build:shell": "nx build shell"`, а то и `"build": "cd apps/shell && vite build"`, и запускает всё через `npm run`.

Первое — безвредный, но лишний слой: Nx-команды и сами принимают параметры, например `nx build shell --configuration=production`. Второе — уже саботаж. Прямой вызов инструмента обходит кеш, task pipeline и affected. А в CI такая команда честно собирает всё с нуля каждый раз, и пользы от Nx у репы не остаётся.

Второй рефлекс оттуда же — `npm install <pkg>` внутри папки приложения, "чтобы поставить зависимость только ему". В integrated-репе это создаёт вложенный package.json и второй node_modules. Так ломается single version policy, а Nx и TypeScript сбиваются с толку.

Зависимости в integrated-монорепо ставятся в корень. "Принадлежность" зависимости проекту существует на уровне графа, потому что Nx сам видит, кто её импортирует. На уровне отдельного node_modules её нет.
