# CI для монорепо и Nx Cloud

## Теория

### Сборка конструктора: affected + кеш + правильная base

Все детали пайплайна непрерывной интеграции (CI — continuous integration) мы уже выучили по отдельности. Глава собирает их в конвейер:

```
┌─────────────────────────────────────────────────┐
│ событие: push в main / pull_request             │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ nrwl/nx-set-shas: NX_BASE = SHA                 │
│ последнего УСПЕШНОГО прогона CI                 │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ nx affected -t lint,test,typecheck,build:       │
│ задачи только затронутых проектов               │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ каждая задача: хеш → remote cache:              │
│ hit → replay за мс; miss → выполнить и записать │
└─────────────────────────────────────────────────┘
                         │
                         ▼
┌─────────────────────────────────────────────────┐
│ только push в main: nx affected -t deploy —     │
│ независимый деплой затронутых remote-ов         │
└─────────────────────────────────────────────────┘
```

Единственная новая деталь во втором блоке — экшен `nrwl/nx-set-shas`. Из главы 05 мы знаем, какой должна быть base: это последнее состояние, которое CI реально проверил. Для PR (pull request, запрос на слияние) это merge-base с main, и Nx посчитает его сам. А вот для push в main `HEAD~1` — ловушка.

nx-set-shas спрашивает у GitHub API хеш коммита (SHA) последнего **успешного** прогона workflow на main. Найденный хеш он кладёт в `NX_BASE`, а текущий — в `NX_HEAD`. Обе переменные affected читает автоматически. Упал вчерашний прогон — сегодняшний сравнит с позавчерашним успешным, и ни один коммит не останется непроверенным.

### Почему локального кеша мало

Локальный `.nx/cache` (глава 04) живёт на одной машине. А CI-агенты эфемерны: каждый прогон стартует с чистой файловой системой, и весь кеш выбрасывается вместе с контейнером. Плюс командная арифметика: двадцать разработчиков собирают одну и ту же не изменившуюся либу двадцать раз.

Ответ — **remote cache**: общее хранилище "хеш → артефакты + stdout" поверх той же механики. Здесь окупается контент-адресация из главы 04. Хеш считается от содержимого файлов, значит, одинаковый коммит даёт одинаковый ключ на любой машине. Задача, выполненная одним агентом или коллегой, становится replay-ем для всех.

Реализаций две. **Nx Cloud** — официальный облачный сервис, подключается за минуту: `npx nx connect`. Тем, кому нельзя отдавать данные наружу, подойдёт свой сервер кеша, реализующий Nx remote-cache API: адрес указывается в `NX_SELF_HOSTED_REMOTE_CACHE_SERVER`. Раньше хранилищем служил Amazon S3 (Simple Storage Service) или похожий бакет — именно об этом врезка ниже.

> **Версии.** В старых репах встречаются community-плагины remote-кеша поверх Amazon S3. Они работали через недокументированное API task runner-а, которое Nx официально закрыл. Видите в nx.json `tasksRunnerOptions` с кастомным runner-ом — это тот самый слой, и при миграции его придётся пересматривать.

> **Безопасность.** Пакеты кеша поверх бакетов не просто устарели, а сняты. Четыре из них объявлены устаревшими 21 мая 2026 года: `@nx/s3-cache`, `@nx/gcs-cache`, `@nx/azure-cache` и `@nx/shared-fs-cache`.

> Причина — CREEP (гонка в кеше, позволяющая его отравить). Она зарегистрирована как CVE-2025-36852 с оценкой 9.4: опубликованная уязвимость получает номер в списке общеизвестных уязвимостей (CVE).

> Сама атака описывается коротко. Любой участник, которому разрешено открывать пул-реквесты, может подложить артефакт, который потом исполнится в продакшене. Nx пишет, что дефект заложен в самой конструкции этих пакетов и не чинится патчем, так что в новый репозиторий их ставить не надо.

### Токены и отравление кеша

Remote cache — это исполняемые артефакты, которые скачиваются и запускаются, поэтому у доступа два уровня:

- **read-only** токен: можно получать хиты, нельзя записывать. Для локальных машин разработчиков и особенно для CI на PR из форков.
- **read-write**: полный доступ. Только для доверенных пайплайнов (main), токен — в секретах CI, не в nx.json.

Угроза, ради которой это всё, — **cache poisoning**. Тот, кто может писать в кеш, может подложить вредоносный артефакт под хеш, который завтра совпадёт у прод-сборки. Его код тогда молча "восстановится из кеша" в прод-бандл. Отсюда правило без исключений: недоверенный код из форков и с локальных машин никогда не получает write-доступ.

### Distributed task execution: шардинг по графу

Когда даже affected-список велик, задачи можно раскидать по машинам. Ручной путь — матрица джоб в CI: "агент 1 собирает apps/a…", "агент 2 тестит libs/x…". Такая матрица статична и игнорирует зависимости.

**Distributed task execution (DTE)** в Nx Cloud делает это динамически. Главный джоб публикует task graph, а N агентов разбирают задачи с него. Агенты соблюдают `dependsOn` и балансируются по историческим таймингам. Кеш у всех общий, а логи собираются в один поток, как будто всё шло на одной машине.

Включается это одной строкой: `--distribute-on="5 linux-medium-js"`. Главное отличие от матрицы — что именно шардится: не список проектов, а **граф задач**.

### nx migrate: обновление как кодмоды

Обновлять Nx руками нельзя — мы знаем это с главы 00 (ядро и плагины идут в ногу, версии точные). Штатный механизм — двухфазный:

```bash
npx nx migrate latest        # фаза 1: правит версии в package.json
                             # и генерит migrations.json — список кодмодов
npm install
npx nx migrate --run-migrations   # фаза 2: прогоняет кодмоды над репой
```

Миграции — те же генераторы из главы 07, только написанные командой Nx. Они переписывают nx.json под новую схему, переносят project.json на inferred targets, обновляют конфиги инструментов. Именно так репы переживали переезды вроде "executors → crystal" без ручного рефакторинга.

Файл `migrations.json` стоит закоммитить в PR апгрейда: коллеги и CI смогут воспроизвести прогон, а после мержа файл удаляется. Копить мажоры — копить миграционный долг: два-три пропущенных мажора превращают часовой апгрейд в недельный проект.

## В рабочем монорепо

- Откройте CI-конфиг: там `nx affected` (и как вычисляется base — nx-set-shas или хардкод?) или `run-many`/ручные списки? Это диагноз зрелости пайплайна за 30 секунд.
- В логах CI поищите `[remote cache]` / "Nx Cloud": есть ли удалённые хиты. Каждый прогон собирает всё с нуля → remote-кеша нет, команда платит за одни и те же сборки многократно.
- `grep -i "nxCloud\|accessToken" nx.json .env* 2>/dev/null` — как подключён Nx Cloud и, главное, не закоммичен ли write-токен в репу (должен жить в секретах CI).
- `git log --oneline -- package.json | head` + поищите PR с `migrations.json`: как команда обновляет Nx — через migrate или "руками" (второе объясняет многие странности конфигов).
- Сравните два прогона: PR, меняющий `README` одной либы, и PR в популярную либу. Если оба собираются одинаково долго — affected или кеш не работают. Вы нашли самый дешёвый способ ускорить сборку в компании.

## Что добавляем в проект

CI на GitHub Actions: PR-пайплайн на `nx affected` с правильной base и деплой-джоб на main, который через наш executor из главы 08 независимо "деплоит" только затронутые приложения федерации.

## Практическое задание

**Вход:** workspace после главы 12 (репозиторий на GitHub или готовность прочитать workflow локально).

**Задача:**

1. Написать `.github/workflows/ci.yml`: триггеры push в main + pull_request; checkout с полной историей; `nrwl/nx-set-shas`; setup-node с npm-кешем; `npm ci`; `nx affected -t lint,test,typecheck,build`. Объяснить (в комментариях в самом файле), зачем нужны `fetch-depth: 0` и set-shas.
2. Добавить джоб `deploy`, выполняющийся только на push в main после успешного `main`-джоба: `nx affected -t deploy`. Объяснить, почему это и есть "независимый деплой микрофронтендов" в автоматическом виде.
3. Проверить конвейер локально, имитируя CI: `NX_BASE=<SHA> NX_HEAD=HEAD npx nx affected -t lint,test,typecheck,build` с разными base — убедиться, что список задач меняется соответственно.
4. Письменно спроектировать схему токенов remote-кеша для команды из 10 человек с публичными PR от подрядчиков: кто получает read, кто write, где хранится каждый токен и почему.
5. Изучить механику migrate без риска. В одноразовой ветке выполнить `npx nx migrate latest`, затем прочитать diff package.json и `migrations.json`. Посмотреть, какие кодмоды запланированы и к каким пакетам относятся, и откатить ветку. Если версия уже последняя — взять предыдущий мажор: `nx migrate 20.0.0` из более старой копии. Можно и просто разобрать структуру migrations.json по документации.

**Edge cases на подумать:**

- Флаки-тест прошёл в CI и лёг в remote cache. Что увидят следующие прогоны и почему это опаснее флаки-теста без кеша?
- Сборка вшивает в бандл секрет из env. Что окажется в remote cache и кто его сможет прочитать?
- PR одновременно меняет либу и nx.json. Что произойдёт со списком affected и временем прогона?

## Разбор решения

Шаги 1–2 — workflow целиком:

```yaml
# .github/workflows/ci.yml
name: CI

on:
  push:
    branches: [main]
  pull_request:

jobs:
  main:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          # полная история: merge-base и set-shas не работают на shallow-клоне
          fetch-depth: 0

      # NX_BASE = SHA последнего успешного прогона на main (для PR — merge-base);
      # без этого affected на push сравнивал бы с HEAD~1 и терял коммиты (гл. 05)
      - uses: nrwl/nx-set-shas@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm

      - run: npm ci

      - run: npx nx affected -t lint,test,typecheck,build

  deploy:
    # деплоим только с main и только после зелёной проверки
    if: github.event_name == 'push' && github.ref == 'refs/heads/main'
    needs: main
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with:
          fetch-depth: 0
      - uses: nrwl/nx-set-shas@v4
      - uses: actions/setup-node@v4
        with:
          node-version: 20
          cache: npm
      - run: npm ci
      - run: npx nx affected -t deploy
```

Ключевые решения:

- **Одна команда вместо стадий** — `affected -t lint,test,typecheck,build`: порядок и параллелизм отдаём task graph-у (глава 03), никаких "сначала весь lint".
- **Деплой через affected**: поменялась catalog-feature → задеплоится только catalog. Поменялась shared-ui → задеплоятся все её потребители: это стратегия "согласованный деплой" из главы 11 в автоматическом виде. PR с правкой `README` не деплоит ничего. Наш deploy-executor из главы 08 не изменился ни на строчку — контекст сделал его переносимым.
- Без remote-кеша этот пайплайн уже корректен, просто холоднее: каждый агент пересчитывает свои miss-ы. Подключение Nx Cloud (`npx nx connect`) добавляет межпрогонные хиты без правок в файле workflow.

Шаг 4 — схема токенов. Read-only токен лежит в `nx.json`: он не секрет, потому что умеет только читать хиты. Этот токен — для локальных машин.

Read-write токен лежит исключительно в GitHub Secrets и доступен только workflow на `main`. Джобы PR из форков секреты не получают вовсе — это дефолт GitHub, и он нам на руку. Подрядчики и форки автоматически остаются в read-only.

Любую схему проверяем одним вопросом. Может ли код из недоверенного PR записать что-то, что потом исполнится у другого? Ответ обязан быть отрицательным.

Шаг 5 — типичный migrations.json:

```json
{
  "migrations": [
    {
      "package": "@nx/react",
      "version": "21.0.0-beta.3",
      "name": "update-module-federation-config",
      "description": "Migrate MF config to the new @nx/module-federation format"
    }
  ]
}
```

Каждая запись — генератор (глава 07) из конкретного пакета: фаза 1 только *планирует* список от вашей текущей версии до целевой, фаза 2 исполняет. Поэтому апгрейд воспроизводим: закоммитили migrations.json — любой коллега прогонит те же кодмоды.

Ответы на edge cases:

- Флаки-тест + кеш: зелёный результат ляжет в remote cache, и **все** прогоны с тем же хешем будут воспроизводить его без выполнения — флак "зафиксирован" до первого изменения inputs. Это глава 04 (кеш честен, тест — нет) в масштабе команды: лечится починкой/карантином флаки-тестов, а не отключением кеша.
- Секрет, вшитый в бандл, оказывается в remote cache как часть артефакта — и его прочитает любой обладатель read-токена, то есть при нашей схеме вся команда и все форки. Секретам не место в артефактах сборки в принципе; кеш лишь делает утечку шире и долговечнее.
- nx.json — глобальный файл (глава 05): affected = вся репа, прогон максимально долгий (смягчённый кешем). Поэтому конфиг-правки и массовые обновления зависимостей стоит возить отдельными PR — иначе каждая фича, случайно зацепившая nx.json, оплачивает полный прогон.

## Проверь себя

1. Почему кеш Nx переносим между машинами без всякой синхронизации состояния? Какое свойство хеша это обеспечивает и какое условие из главы 04 должно выполняться?
2. Опиши атаку cache poisoning и перечисли, какие решения в схеме токенов ей противостоят.
3. Push в main упал, следующий прошёл. С каким SHA сравнивался второй прогон при nx-set-shas и что было бы при `--base=HEAD~1`?
4. Чем DTE принципиально отличается от матрицы джоб с ручным разбиением проектов по агентам?
5. Коллега предлагает обновить Nx, руками поправив версии в package.json: "npm install и готово". Какие два класса проблем он получит и как выглядит правильный процесс?

<details>
<summary>Ответы</summary>

1. Хеш считается от содержимого (файлы по inputs, конфигурация, версии зависимостей), а не от путей, времени или состояния машины, — одинаковый коммит даёт одинаковый ключ где угодно. Условие то же, что для локального кеша: задекларированные inputs/outputs совпадают с фактическими; незадекларированный вход, различающийся между машинами (env, глобальный конфиг), превращает переносимость в источник "чужих" артефактов.
2. Атакующий с write-доступом кладёт в кеш вредоносный артефакт под ключом, который совпадёт с хешем будущей доверенной сборки, — и прод-пайплайн "восстановит" его код из кеша без выполнения. Противостоят: write-токен только у доверенных пайплайнов и только в секретах CI; PR из форков и локальные машины — строго read-only; секреты недоступны джобам форков (дефолт GitHub).
3. С SHA последнего **успешного** прогона — то есть позапрошлого коммита: диапазон покрыл и упавший, и новый коммит, ничего не потерялось. При `HEAD~1` второй прогон сравнился бы только с упавшим коммитом — изменения из него формально "проверены" красным прогоном, которого никто не чинил, и часть регрессий уехала бы непроверенной.
4. Матрица шардит статический список без знания зависимостей: агенту может достаться build приложения раньше, чем другой агент собрал его либу, а балансировка — на глазок. DTE раздаёт задачи из task graph динамически: соблюдает dependsOn между агентами, использует общий кеш, балансирует по фактическим таймингам и склеивает логи в единый вывод. Шардится граф, а не список.
5. Первый класс — разъезд версий. Ядро nx и плагины @nx/* обязаны совпадать (глава 00), а ручное обновление легко оставляет часть пакетов позади. Ошибки при этом прилетают из недр node_modules. Второй класс — пропущенные кодмоды. Новая версия ждёт новый формат конфигов: nx.json, конфиги module federation (MF), inferred targets. А репа осталась в старом формате. Всё вроде работает, но на недокументированной обратной совместимости, и следующий апгрейд станет ещё тяжелее. Правильный порядок: `nx migrate latest` → npm install → `nx migrate --run-migrations` → прогнать affected-проверки → закоммитить вместе с migrations.json.

## Частая ошибка

Разработчик из single-app мира переносит в монорепо привычный CI-шаблон. Появляются джоба lint, джоба test и джоба build. В каждой — `npm run <script>` на всю репу, между ними — артефакты и ожидание. Пайплайн работает, но не использует ни граф, ни кеш, ни affected. Время прогона поэтому растёт линейно с числом проектов.

Диагноз ставится одним взглядом на конфиг: есть ли `nx affected` и как задана base? Лечение — почти всегда *упрощение*. Три джобы схлопываются в одну команду, которая знает о зависимостях больше, чем любой рукописный конфиг. Признак успеха обратный интуиции: чем меньше оркестрации в CI-конфиге, тем больше её делает Nx.

Вторая ошибка — обновлять Nx как обычную зависимость: поднять цифры в package.json и надеяться на semver. Nx — это не либа, а платформа со схемой конфигов. Между мажорами меняются форматы nx.json, project.json, MF-конфигов, и весь этот рефакторинг зашит в миграции-кодмоды. При ручном обновлении они просто не запускаются.

Репа после такого "апгрейда" работает на старых форматах через слой обратной совместимости. Странности копятся, команда делает вывод "обновляться опасно" и замораживает версию, наращивая миграционный долг. Правильный цикл дешёв, если крутить его регулярно: migrate на каждый мажор, прогон миграций, affected-проверки. Тогда репа всегда в шаге от актуальной версии.
