# Targets, executors и task pipeline

## Теория

### Терминология: project, target, task

Три слова, которые в Nx имеют строгий смысл. **Target** — именованная *способность* проекта ("shell умеет build, serve, lint"). **Task** — конкретный запуск: `проект:target`, опционально с конфигурацией: `shell:build:production`. Полная форма запуска — `nx run shell:build`; `nx build shell` — её сокращение, они идентичны. **Configurations** — именованные пресеты опций внутри target-а (`production`/`development`), выбираются флагом `--configuration=production` (сокращение `--prod` живо, но считается легаси).

### Executor: что физически выполняет задачу

Executor — функция, которой Nx отдаёт задачу. Форма записи в конфигурации — `пакет:имя`:

- **Специализированные**: `@nx/vite:build`, `@nx/eslint:lint` — программно вызывают API инструмента, умеют доп. опции. Основная форма в pre-crystal репах.
- **`nx:run-commands`** — универсальный: запускает произвольную shell-команду. Настолько частый, что у него есть сахар: `"command": "tsc --noEmit"` в конфигурации target-а — это краткая запись `{"executor": "nx:run-commands", "options": {"command": "tsc --noEmit"}}`.

Crystal-плагины (глава 01) выводят target-ы именно в командной форме: inferred `build` у shell — это буквально `vite build` с `cwd: apps/shell`. Философия: инструмент запускается своим родным CLI, как вы запустили бы руками, — Nx добавляет вокруг граф, кеш и пайплайн.

Executor — это код в node_modules, и его всегда можно найти. Карта executor-ов пакета лежит в его `executors.json`:

```bash
cat node_modules/nx/executors.json
# { "executors": { "run-commands": { "implementation": "./src/executors/run-commands/run-commands.impl", ... } } }

less node_modules/nx/src/executors/run-commands/run-commands.impl.js
# внутри — обычный Node-код: spawn команды, обработка вывода, код возврата
```

Этот навык — "открыть impl executor-а" — главный инструмент дебага, когда таска ведёт себя необъяснимо: вы читаете, что *на самом деле* запускается, вместо того чтобы гадать.

### Task pipeline: dependsOn

Задачи зависят друг от друга: собрать приложение нельзя раньше, чем собраны его библиотеки. Это выражается в `dependsOn`:

- **`"^build"`** — "сначала target `build` у всех *зависимостей* проекта" (символ `^` = "у соседей по графу вверх"). Каноническая запись для build.
- **`"build"`** (без `^`) — "сначала target `build` у *этого же* проекта" (например, `test` может требовать предварительный `build`).
- Объектная форма — для тонкой настройки: `{ "dependsOn": [{ "target": "build", "dependencies": true, "params": "forward" }] }`.

Правила `dependsOn` объявляются либо в `targetDefaults` в nx.json (для всех одноимённых target-ов репы — обычно так), либо в project.json конкретного проекта (точечно). Ключом в `targetDefaults` может быть и имя target-а (`"build"`), и executor (`"@nx/vite:build"`) — второе точнее, когда одноимённые target-ы в репе делают разное.

Важный нюанс: `"^build"` **не падает**, если у зависимости нет target-а `build` — задача просто не создаётся. Поэтому non-buildable либы (наша shared-ui) спокойно живут в пайплайне: у них нечего собирать, и `nx build shell` их пропускает.

### Что происходит при nx build shell

```
┌─────────────────────────────────────────┐
│ nx build shell  (= nx run shell:build)  │
└─────────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────┐
│ project graph + dependsOn → TASK GRAPH: │
│ узлы — задачи вида проект:target        │
└─────────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────┐
│ хеш каждой задачи → проверка кеша:      │
│ hit → мгновенный replay из .nx/cache    │
└─────────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────┐
│ miss → запуск executor-а задачи         │
│ параллельно, в топологическом порядке   │
└─────────────────────────────────────────┘
                     │
                     ▼
┌─────────────────────────────────────────┐
│ outputs + stdout сохраняются в кеш      │
│ (механика хеша — глава 04)              │
└─────────────────────────────────────────┘
```

Ключевой момент: **task graph — отдельная структура**, производная от project graph. Узлы project graph — проекты; узлы task graph — задачи. Из одного project graph получаются разные task graph-ы в зависимости от того, что попросили: у `nx build shell` один task graph, у `nx run-many -t test` — другой. Посмотреть его можно без запуска: `nx build shell --graph`. Цикл в task graph (A ждёт B, B ждёт A) — ошибка запуска, и это одна из причин, почему цикл `shared-ui ⇄ shell` из главы 02 нежизнеспособен.

Параллелизм: Nx выполняет независимые задачи одновременно (`--parallel`, по умолчанию 3), соблюдая топологический порядок — задача стартует, когда завершились все, от кого она зависит. Отсюда практическое следствие для CI: `nx run-many -t lint,test,build` — одна команда вместо трёх последовательных стадий; lint и test всех проектов не ждут друг друга, а build стартует по мере готовности зависимостей.

> **Версии.** Долгоживущие задачи (dev-серверы) исторически ломали пайплайн: задача "не завершается", и всё, что от неё зависит, ждёт вечно. В Nx 21 появились **continuous tasks** (`"continuous": true`): пайплайн не ждёт их завершения — на этом построен дев-режим микрофронтендов (глава 10), где serve host-а тянет за собой serve всех remote-ов. В старых версиях это решалось костылями типа `run-many` с ручным списком serve-задач.

## В рабочем монорепо

- `npx nx build <проект> --graph` — task graph конкретного запуска без выполнения: что и в каком порядке запустится. Первый вопрос "почему build так долго" начинается отсюда.
- `npx nx show project <проект> --web` — у каждого target-а видно: командная форма или executor, его `dependsOn` и откуда он унаследован (targetDefaults / плагин / project.json).
- `cat node_modules/<пакет>/executors.json` → путь к `implementation` → открыть impl-файл. Работает для любого executor-а любого плагина.
- `grep -A5 targetDefaults nx.json` — пайплайн репы объявлен здесь; если у target-а неожиданные предзависимости — ищите и в project.json (`grep -rn dependsOn --include=project.json`).
- В CI-конфиге репы посмотрите, чем запускаются задачи: `nx run-many` / `nx affected` — норма; последовательность отдельных `npm run ...` по проектам — красный флаг (глава 13).

## Что добавляем в проект

`vite build` не проверяет типы (esbuild их просто отбрасывает) — сломанная типизация может уехать в прод при зелёной сборке. Добавляем shell target `typecheck` на `nx:run-commands` и включаем его в конвейер репы наравне с lint/test/build.

## Практическое задание

**Вход:** workspace после главы 02 (shell + shared-ui, ребро в графе).

**Задача:**

1. Выяснить, что физически запускает `nx build shell`: найти target в `nx show project shell`, определить его форму (команда или executor) и найти на диске код `nx:run-commands`.
2. Посмотреть task graph: `nx build shell --graph`. Объяснить, почему в нём нет задачи `shared-ui:build`, хотя `dependsOn: ["^build"]` у build есть.
3. Добавить в `apps/shell/project.json` target `typecheck`: команда `tsc -p tsconfig.app.json --noEmit`, рабочая директория — папка проекта.
4. Сделать `typecheck` кешируемым для всей репы через `targetDefaults` (не в project.json).
5. Прогнать конвейер: `nx run-many -t lint,test,typecheck,build` — прочитать вывод: что шло параллельно, что ждало.

**Требования:** `nx typecheck shell` падает при намеренно сломанном типе в app.tsx и проходит после исправления; повторный запуск без изменений — из кеша.

**Edge cases на подумать:**

- Что будет, если у `typecheck` объявить `dependsOn: ["typecheck"]` (сам на себя)? А `["^typecheck"]`?
- Почему `tsc --noEmit` не имеет outputs — и что тогда кешируется?
- Зачем `--parallel=1` при дебаге пайплайна?

## Разбор решения

Шаг 1 — форма target-а и код executor-а:

```bash
npx nx show project shell | python3 -m json.tool | grep -A4 '"build"'
# "build": {
#   "executor": "nx:run-commands",
#   "options": { "command": "vite build", "cwd": "apps/shell" },
#   ...

cat node_modules/nx/executors.json | python3 -m json.tool | grep -A2 run-commands
# "run-commands": { "implementation": "./src/executors/run-commands/run-commands.impl", ...
```

То есть даже "магический" inferred build — это `nx:run-commands`, чей impl (обычный Node-файл в `node_modules/nx/src/executors/run-commands/`) спавнит `vite build` в папке проекта. Вся цепочка читается глазами.

Шаг 2: в task graph для `nx build shell` одна задача — `shell:build`. Правило `^build` просмотрело зависимости shell (shared-ui), не нашло у них target-а `build` (либа non-buildable, bundler=none) и молча не создало задач. Появится буквально в главе 06, когда сделаем buildable-либу, и в главе 12 у api.

Шаги 3–4 — target и глобальный кеш для него:

```json
// apps/shell/project.json
{
  "name": "shell",
  "$schema": "../../node_modules/nx/schemas/project-schema.json",
  "projectType": "application",
  "sourceRoot": "apps/shell/src",
  "tags": [],
  "targets": {
    "typecheck": {
      "command": "tsc -p tsconfig.app.json --noEmit",
      "options": { "cwd": "apps/shell" }
    }
  }
}
```

```json
// nx.json
{
  "targetDefaults": {
    "typecheck": { "cache": true }
  }
}
```

Ключевые решения:

- `"command"` — тот самый сахар над `nx:run-commands`: полная форма с `"executor"` + `"options"` эквивалентна, но длиннее. Проверить, что развернулось правильно, — `nx show project shell`.
- `cache: true` уехал в `targetDefaults`, а не в project.json — когда в главе 06 у либ появятся свои typecheck-таргеты, они станут кешируемыми автоматически, без копипасты по проектам. Правило: свойства, общие для одноимённых target-ов, живут в nx.json; в project.json — только специфика проекта.
- У `tsc --noEmit` нет файловых outputs — кешируется **терминальный вывод и код возврата**. Replay из кеша воспроизводит и то и другое; для проверочных задач (lint, typecheck) этого достаточно. Что такое outputs и как их декларировать — глава 04.

Шаг 5 — конвейер:

```bash
npx nx run-many -t lint,test,typecheck,build
#    ✔  nx run shared-ui:lint
#    ✔  nx run shell:typecheck
#    ✔  nx run shell:lint
#    ✔  nx run shared-ui:test
#    ✔  nx run shell:test
#    ✔  nx run shell:build
# Successfully ran targets lint, test, typecheck, build for 2 projects
```

Порядок в выводе — это гонка параллельных задач (по умолчанию 3 одновременно), а не стадии: lint шёл рядом с test, build shell стартовал независимо, потому что ждать ему нечего. Ручное упорядочивание "сначала весь lint, потом все тесты" в CI не нужно и вредно — оно навязывает барьеры, которых нет в графе.

Ответы на edge cases:

- `dependsOn: ["typecheck"]` сам на себя — цикл в task graph, Nx откажется строить план и упадёт с ошибкой. `["^typecheck"]` — легально: сначала typecheck зависимостей; пока у либ нет такого target-а — no-op.
- `--parallel=1` сериализует выполнение: логи задач не перемешиваются, порядок детерминирован — стандартный приём, чтобы понять, *какая именно* задача валит конвейер.

## Проверь себя

1. Чем task graph отличается от project graph и почему это два разных графа? Из чего складывается task graph для `nx build shell`?
2. Расшифруй `"dependsOn": ["^build"]` дословно. Что произойдёт с задачей, у зависимости которой нет target-а `build`?
3. `"command": "vite build"` в конфигурации target-а — что это на самом деле? Опиши путь от этой строки до запущенного процесса vite.
4. Почему `nx run-many -t lint,test,build` в CI лучше трёх последовательных стадий lint → test → build?
5. По какому принципу решать, где объявлять свойство target-а — в `targetDefaults` nx.json или в project.json проекта?

<details>
<summary>Ответы</summary>

1. Project graph — статическая карта "кто от кого зависит" (узлы — проекты, рёбра — импорты). Task graph — план конкретного запуска (узлы — задачи `проект:target`), строится из project graph разворачиванием правил `dependsOn` от запрошенных задач. Разные команды дают разные task graph-ы над одним project graph. Для `nx build shell`: берётся `shell:build`, правило `^build` добавляет build-задачи зависимостей (у кого этот target есть) — рекурсивно вниз по графу.
2. "Прежде чем выполнять этот target, выполни target `build` у всех проектов, от которых текущий зависит по project graph". Если у зависимости target-а `build` нет — задача для неё просто не создаётся, ошибки нет. Поэтому non-buildable либы не мешают пайплайну.
3. Сахар: конфигурация нормализуется в `{"executor": "nx:run-commands", "options": {"command": "vite build", ...}}`. При выполнении Nx находит в `node_modules/nx/executors.json` путь к реализации run-commands, загружает impl-модуль и тот спавнит дочерний процесс `vite build` с `cwd` проекта, транслируя вывод и код возврата обратно в Nx (который их кеширует).
4. Стадии — искусственные барьеры: вся стадия test ждёт самый медленный lint, хотя тесты проекта X не зависят от линта проекта Y. `run-many` с несколькими target-ами отдаёт Nx все задачи сразу, и он выполняет их с максимальным параллелизмом, соблюдая только реальные зависимости из task graph. Итог — то же самое выполняется быстрее, и порядок гарантирован графом, а не жёсткой последовательностью.
5. Общее правило: то, что верно для *всех* одноимённых target-ов репы (кешируемость, `^build`, общие inputs), — в `targetDefaults`; то, что специфично для проекта (сама команда, особые опции, точечное переопределение), — в project.json. Так новые проекты получают правильное поведение автоматически, а project.json остаются тонкими.

</details>

## Частая ошибка

Разработчик из single-app мира воспроизводит в монорепо привычный CI: последовательные стадии `lint → test → build`, каждая — циклом по проектам или через `npm run`. Работает, но выбрасывает главное: Nx уже знает и порядок, и допустимый параллелизм — из task graph. Ручные стадии добавляют искусственные барьеры (build ждёт окончания *всех* тестов, хотя его зависимости готовы) и, что хуже, дублируют знание о зависимостях: когда появится новая либа, её нужно не забыть вписать в самодельный порядок — а `dependsOn` подхватил бы её автоматически.

Второй классический промах — вписать долгоживущую задачу в обычный пайплайн: сделать `e2e` зависимым от `serve` и удивляться, что конвейер повис. `serve` не завершается — а пайплайн ждёт именно *завершения*. До Nx 21 это решали обходами (запуск сервера вне Nx, скрипты wait-on); в новых версиях для этого есть `"continuous": true`, на котором построен и дев-режим Module Federation (глава 10). Если ваша репа старше — знайте, что зависший `dependsOn: ["serve"]` не баг, а неправильно выбранный инструмент.
