# Project graph: как Nx видит репозиторий

## Теория

### Граф строится из кода, а не из деклараций

Project graph — структура данных, на которой держится всё остальное. На ней стоят task pipeline (глава 03), кеш (глава 04), affected (глава 05) и boundaries (глава 06). Узлы мы разобрали в главе 01 (project.json / package.json / createNodes плагинов). Эта глава — про **рёбра**.

Главный факт, отличающий Nx от Turborepo и Lerna: ребро `shell → shared-ui` появляется потому, что **в исходниках shell есть импорт из shared-ui**. Не потому, что кто-то записал зависимость в package.json. Механика по шагам:

```
┌───────────────────────────────────────────┐
│ исходники всех проектов                   │
│ *.ts / *.tsx / *.js                       │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ парсинг импортов (дерево кода, не grep):  │
│ import / require / import()               │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ резолв каждого импорта в проект:          │
│ paths-алиасы / workspaces / имена пакетов │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ рёбра графа                               │
│ + implicitDependencies из project.json    │
└───────────────────────────────────────────┘
```

Разберём каждый шаг:

- **Парсинг идёт через AST (abstract syntax tree — синтаксическое дерево, разобранная форма кода), а не текстовым поиском.** Nx разбирает синтаксическое дерево файла и собирает `import ... from`, `export ... from`, `require(...)` и динамические `import(...)`. Упоминание пути в строковом литерале или комментарии ребра не создаст. А вот `import type` — создаст: для Nx это такой же импорт. И это правильно: изменение типов либы обязано затрагивать её потребителей, иначе affected пропускал бы сломанную типизацию.
- **Резолв в проект.** Спецификатор — это строка внутри импорта, например `@mini-shop/shared-ui`. Nx прогоняет её через `paths` из `tsconfig.base.json` (integrated) или через workspaces пакетного менеджера (package-based), и она попадает в корень какого-то проекта. Не попала никуда — значит, это npm-пакет и внешний узел.
- **Типы рёбер**: `static` (обычный импорт), `dynamic` (`import()` — важно для микрофронтендов, глава 10) и `implicit` (см. ниже).

> **Версии.** В новых версиях парсинг импортов и хеширование вынесены в нативный Rust-код — на репе в сотни проектов граф строится за секунды. Для вас это деталь производительности: механика та же, что и раньше.

Пересчитывать граф на каждый запуск было бы дорого, поэтому Nx держит **daemon** — фоновый процесс, который следит за файлами и обновляет граф инкрементально. Сериализованный граф лежит в `.nx/workspace-data`.

Отсюда главный приём диагностики. Если граф ведёт себя странно — ребро не появилось или не исчезло — запустите `npx nx reset`. Он убивает daemon и стирает все производные данные, а следующая команда построит граф с нуля.

### implicitDependencies — рёбра, которых нет в коде

Иногда зависимость реальна, но импортом не выражена:

- e2e-проект (end-to-end — тесты, которые гоняют приложение целиком) тестирует приложение. В коде e2e нет ни одного импорта из app; он знает только URL приложения;
- проект читает сгенерированный артефакт другого проекта;
- деплой-конфиг зависит от собранного бандла.

Для этого в project.json есть ручное ребро:

```json
{
  "name": "shell-e2e",
  "implicitDependencies": ["shell"]
}
```

Теперь изменение shell делает `shell-e2e` "затронутым" для affected, хотя статический анализ связи не видит. Это инструмент точечный: если implicitDependencies в репе десятки — команда воюет с графом вместо того, чтобы выражать зависимости кодом.

### npm-пакеты — тоже узлы

Внешние зависимости присутствуют в графе как узлы вида `npm:react`. Ребро `shared-ui → npm:react` означает "исходники shared-ui импортируют react". Nx это нужно для двух вещей:

- версия внешней зависимости входит в хеш кеша. Обновили react — кеш сборок всех, кто его импортирует, инвалидировался (глава 04);
- команда `nx graph` умеет показать, кто в репе реально использует конкретный пакет — не по package.json, а по факту импортов.

После этой главы граф mini-shop выглядит так:

```
┌────────────┐  static  ┌────────────────┐  static  ┌───────────┐
│ apps/shell │ ───────▶ │ libs/shared/ui │ ───────▶ │ npm:react │
└────────────┘          └────────────────┘          └───────────┘
```

### nx graph — главный инструмент навигации

`npx nx graph` поднимает локальный веб-интерфейс. Ключевые режимы, которыми стоит пользоваться осознанно:

- **Focus** (`nx graph --focus=shell` или клик в интерфейсе) — только выбранный проект и его прямые/транзитивные связи. На репе в 200 проектов "Select all" бесполезен — focus обязателен.
- **Path tracing** — в интерфейсе выбираете два проекта, Nx показывает все пути между ними. Ответ на классический вопрос "почему изменение либы X перетестировало приложение Y".
- **`nx graph --file=graph.json`** — тот же граф в JSON для скриптов. Посчитать входящие рёбра, найти самый нагруженный узел или проверить архитектурное правило в CI (continuous integration — сборка и тесты на сервере при каждом пуше).
- **`nx graph --affected`** — подграф затронутого изменениями (глава 05).

## В рабочем монорепо

- `npx nx graph` → focus на проект, над которым работаете: его реальные зависимости и зависимые — за 10 секунд, без чтения кода.
- Path tracing между "моя либа" и "прод-приложение" покажет, через какие слои изменение доедет до деплоя. Этим же отвечают на "почему мой PR (pull request) запустил 40 тестовых джоб".
- `npx nx graph --file=graph.json` — весь граф в виде JSON. Скрипт ниже печатает топ-10 узлов по входящим рёбрам. Это и есть проекты в центре репы, которые опаснее всего трогать.
- `grep -rn "implicitDependencies" --include=project.json .` — все ручные рёбра репы. У каждого должна быть внятная причина; куча implicitDependencies — симптом, что граф не отражает реальность.
- Граф "врёт" — удалили импорт, а ребро висит? Запустите `npx nx reset`, потом снова `nx graph`. В 9 случаях из 10 это протухший daemon.

```bash
npx nx graph --file=graph.json
python3 - <<'PY'
import json, collections
deps = json.load(open('graph.json'))['graph']['dependencies']
print(collections.Counter(t['target'] for v in deps.values() for t in v).most_common(10))
PY
```

## Что добавляем в проект

Первая библиотека — `shared/ui` с компонентом `Button`. Shell перестаёт быть единственным узлом, в графе появляется первое ребро, а в `tsconfig.base.json` — первый алиас. Это фундамент для рефакторинга на слои в главе 06.

## Практическое задание

**Вход:** workspace после главы 01 (приложение shell, плагины @nx/react + vite).

**Задача:**

1. Сгенерировать React-библиотеку `shared-ui` в `libs/shared/ui`: bundler — none (почему none — тема главы 06), тесты — vitest, import path — `@mini-shop/shared-ui`.
2. Добавить в либу компонент `Button` (обычная кнопка с `variant: 'primary' | 'ghost'`) и экспортировать его через публичный вход `src/index.ts`.
3. Использовать `Button` в `app.tsx` приложения shell. Убедиться, что `nx serve shell` рендерит кнопку.
4. Проверить ребро тремя способами. В интерфейсе `nx graph`. В `nx graph --file=graph.json`, где надо найти запись про shell. И глазами — в diff `tsconfig.base.json`.
5. Сломать связь: закомментировать импорт в app.tsx — и убедиться, что ребро исчезло. Вернуть импорт.
6. Добавить в `shell` → `implicitDependencies: ["shared-ui"]`, посмотреть на тип ребра в graph.json, затем убрать.

**Edge cases на подумать:**

- Если заменить импорт на `import type { ButtonProps } ...` — останется ли ребро? А должно ли?
- Что будет с графом, если импортировать Button по относительному пути `../../../libs/shared/ui/src/lib/button` в обход алиаса? Чем это плохо, если "работает же"?
- Может ли shared-ui импортировать что-то из shell? Что скажет граф и что должно сказать ревью?

## Разбор решения

Генерация либы:

```bash
npx nx g @nx/react:lib shared-ui --directory=libs/shared/ui \
  --bundler=none --unitTestRunner=vitest --linter=eslint \
  --importPath=@mini-shop/shared-ui
```

Diff `tsconfig.base.json` — первый алиас (это и есть "проводка", по которой резолвится импорт):

```json
{
  "compilerOptions": {
    "paths": {
      "@mini-shop/shared-ui": ["libs/shared/ui/src/index.ts"]
    }
  }
}
```

Компонент и публичный вход:

```tsx
// libs/shared/ui/src/lib/button.tsx
import type { ReactNode } from 'react';

export interface ButtonProps {
  variant?: 'primary' | 'ghost';
  onClick?: () => void;
  children: ReactNode;
}

export function Button({ variant = 'primary', onClick, children }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}
```

```ts
// libs/shared/ui/src/index.ts — ПУБЛИЧНЫЙ API либы:
// только то, что экспортировано отсюда, доступно другим проектам
export { Button } from './lib/button';
export type { ButtonProps } from './lib/button';
```

Использование в shell:

```tsx
// apps/shell/src/app/app.tsx
import { Button } from '@mini-shop/shared-ui';

export function App() {
  return (
    <div>
      <h1>mini-shop</h1>
      <Button onClick={() => console.log('go to catalog')}>Каталог</Button>
    </div>
  );
}

export default App;
```

Проверка ребра в JSON:

```bash
npx nx graph --file=graph.json
python3 - <<'PY'
import json
g = json.load(open('graph.json'))['graph']
print(g['dependencies']['shell'])
PY
# [{'source': 'shell', 'target': 'shared-ui', 'type': 'static'},
#  {'source': 'shell', 'target': 'npm:react', 'type': 'static'}, ...]
```

Ключевые решения:

- Ребро `shell → shared-ui` появилось в момент, когда в app.tsx появилась строка импорта. Мы не редактировали ни одного конфига зависимостей — в этом и есть суть главы.
- `src/index.ts` — единственная точка входа, barrel-файл: один файл, который реэкспортирует всё, что либа отдаёт наружу. Алиас в tsconfig.base.json указывает на этот файл, а не на папку. Всё, что не реэкспортировано из index.ts, остаётся приватным для либы. Пока это договорённость между людьми; в главе 06 сделаем её правилом линтера.
- После комментирования импорта ребро исчезает при следующем построении графа, потому что daemon подхватывает изменение файла. Если открытый `nx graph` всё ещё показывает старую картинку — обновите страницу, в крайнем случае запустите `nx reset`.
- С `implicitDependencies: ["shared-ui"]` в graph.json появляется ребро `{'type': 'implicit'}` — оно живёт, даже когда импорта нет. Рабочий кейс — e2e → app; для обычной связи "код импортирует код" implicit-ребро избыточно, поэтому убираем.

Ответы на edge cases:

- `import type` оставляет ребро — и обязан: поменяли `ButtonProps` → shell должен попасть в affected, иначе CI пропустит сломанную типизацию.
- Относительный импорт в обход алиаса ребро тоже создаст, потому что резолвер понимает относительные пути. Но он дырявит публичный API: вы прицепились к внутреннему файлу либы, минуя index.ts. Рефакторинг внутренностей либы теперь ломает чужой код. В главе 06 такие импорты запретит `@nx/enforce-module-boundaries`.
- Технически `shared-ui → shell` возможен, и граф покорно нарисует цикл `shell ⇄ shared-ui`. А вот task pipeline (глава 03) на цикле сломается, и это правильно. Библиотека, знающая о приложении, — это перевёрнутая архитектура. Ревью должно завернуть такой импорт до всякого Nx.

5. Зачем npm-пакеты присутствуют в графе отдельными узлами? Назови два механизма Nx, которым нужны рёбра на `npm:*`.

<details>
<summary>Ответы</summary>

1. Nx (через daemon) парсит AST файла app.tsx и находит импорт-спецификатор `@mini-shop/shared-ui`. Резолвер прогоняет его через `paths` в `tsconfig.base.json` и получает `libs/shared/ui/src/index.ts`. Этот путь лежит внутри корня проекта `shared-ui`, узел которого известен из project.json либы. Значит, файл проекта `shell` зависит от проекта `shared-ui`, и в граф добавляется ребро `shell → shared-ui` типа `static`. Участвуют: исходник app.tsx, tsconfig.base.json (paths), project.json обеих сторон (границы проектов).
2. Ребро в графе отвечает не на вопрос "что попадёт в бандл", а на вопрос "чьё изменение меня затрагивает". Изменение `ButtonProps` в shared-ui может сломать компиляцию shell, не изменив ни байта в рантайме, — affected обязан перепроверить shell (typecheck, тесты). Если бы type-импорты игнорировались, CI зеленел бы на репе, которая не собирается.
3. Напишите `implicitDependencies: ["shell"]` в project.json e2e-проекта. Это ручное ребро для связей, не выраженных импортами: e2e ходит в приложение по URL и ничего из него не импортирует. Без него граф считает e2e изолированным узлом. Изменение shell не делает e2e затронутым, и affected-пайплайн в CI молча пропустит регрессию, которую e2e должен был поймать.
4. Граф пересчитывается не с нуля. Daemon следит за файловой системой и инкрементально обновляет граф при изменениях, а сериализованное состояние живёт в `.nx/workspace-data`. Поэтому запуск любой команды использует уже готовый граф. Сброс — `nx reset`: убивает daemon и стирает производные данные. Следующая команда строит всё заново — это первый приём при "граф врёт".
5. Во-первых, кеш: версия npm-пакета — input хеша (глава 04). Обновление react должно инвалидировать сборки всех, кто его импортирует, и для этого нужны рёбра `проект → npm:react`. Во-вторых, анализ использования: `nx graph` показывает фактических потребителей пакета по импортам, а не по декларациям. Это точный ответ на "можно ли выпилить зависимость X".

## Частая ошибка

Разработчик из single-app мира приносит убеждение "зависимость существует, только если она задекларирована". Он ищет, где "подключена" shared-ui к shell, и не находит записи ни в одном package.json. Дальше он идёт одним из двух путей.

Первый путь — добавить декларацию руками: лишний implicitDependencies или запись в package.json, дублирующая то, что граф уже знает. Второй — решить наоборот. Раз декларировать ничего не надо, то и порядка нет. Он начинает импортировать из чужих либ что угодно, вот так: `import { helper } from '../../../libs/checkout/feature/src/lib/internal/utils'`.

Граф это переварит, ребро появится. Но это **deep-import** — импорт, залезающий внутрь либы мимо её публичного входа. Он прицеплен к внутреннему файлу, поэтому владелец либы переставит файлы и уронит половину репы, не изменив ни одного экспорта из index.ts.

Правильная ментальная модель обратная: **декларация — это импорт**. Ребро создаётся кодом. Файл index.ts — контракт, и внутри этого контракта либа свободна. Запись implicitDependencies — исключение с обоснованием в ревью, а не инструмент на каждый день. Хочется ребро без импорта или импорт мимо index.ts? Это почти всегда сигнал, что код лежит не в той либе.
