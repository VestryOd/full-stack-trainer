# Project graph: как Nx видит репозиторий

## Теория

### Граф строится из кода, а не из деклараций

Project graph — структура данных, на которой держится всё остальное: task pipeline (глава 03), кеш (глава 04), affected (глава 05), boundaries (глава 06). Узлы мы разобрали в главе 01 (project.json / package.json / createNodes плагинов); эта глава — про **рёбра**.

Главный факт, отличающий Nx от Turborepo и Lerna: ребро `shell → shared-ui` появляется потому, что **в исходниках shell есть импорт из shared-ui**. Не потому, что кто-то записал зависимость в package.json. Механика по шагам:

```
┌───────────────────────────────────────────┐
│ исходники всех проектов                   │
│ *.ts / *.tsx / *.js                       │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ парсинг импортов (AST, не grep):          │
│ import / require / import()               │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ резолв каждого импорта в проект:          │
│ paths-алиасы / workspaces / имена пакетов │
└───────────────────────────────────────────┘
                      │
                      ▼
┌───────────────────────────────────────────┐
│ рёбра графа                               │
│ + implicitDependencies из project.json    │
└───────────────────────────────────────────┘
```

Разберём каждый шаг:

- **Парсинг — это AST, а не текстовый поиск.** Nx разбирает синтаксическое дерево файла и собирает `import ... from`, `export ... from`, `require(...)` и динамические `import(...)`. Упоминание пути в строковом литерале или комментарии ребра не создаст. `import type` — создаст: для Nx это такой же импорт, и это правильно (изменение типов либы обязано затрагивать её потребителей — иначе affected пропускал бы сломанную типизацию).
- **Резолв в проект.** Спецификатор `@mini-shop/shared-ui` прогоняется через `paths` из `tsconfig.base.json` (integrated), через workspaces пакетного менеджера (package-based) — и попадает в корень какого-то проекта. Не попал никуда (npm-пакет) — это внешний узел.
- **Типы рёбер**: `static` (обычный импорт), `dynamic` (`import()` — важно для микрофронтендов, глава 10) и `implicit` (см. ниже).

> **Версии.** В новых версиях парсинг импортов и хеширование вынесены в нативный Rust-код — на репе в сотни проектов граф строится за секунды. Для вас это деталь производительности: механика та же, что и раньше.

Пересчитывать граф на каждый запуск было бы дорого, поэтому Nx держит **daemon** — фоновый процесс, который следит за файлами и обновляет граф инкрементально. Сериализованный граф лежит в `.nx/workspace-data`. Отсюда главный приём диагностики: если граф ведёт себя странно (ребро не появилось/не исчезло), `npx nx reset` убивает daemon и стирает все производные данные — следующая команда построит граф с нуля.

### implicitDependencies — рёбра, которых нет в коде

Иногда зависимость реальна, но импортом не выражена: e2e-проект тестирует приложение (в коде e2e нет ни одного импорта из app — только URL), проект читает сгенерированный артефакт другого проекта, деплой-конфиг зависит от собранного бандла. Для этого в project.json есть ручное ребро:

```json
{
  "name": "shell-e2e",
  "implicitDependencies": ["shell"]
}
```

Теперь изменение shell делает `shell-e2e` "затронутым" для affected, хотя статический анализ связи не видит. Это инструмент точечный: если implicitDependencies в репе десятки — команда воюет с графом вместо того, чтобы выражать зависимости кодом.

### npm-пакеты — тоже узлы

Внешние зависимости присутствуют в графе как узлы вида `npm:react`. Ребро `shared-ui → npm:react` означает "исходники shared-ui импортируют react". Зачем это Nx: во-первых, версия внешней зависимости входит в хеш кеша (обновили react — кеш сборок всех, кто его импортирует, инвалидировался; глава 04); во-вторых, `nx graph` умеет показать, кто в репе реально использует конкретный пакет — не по package.json, а по факту импортов.

После этой главы граф mini-shop выглядит так:

```
┌────────────┐  static  ┌────────────────┐  static  ┌───────────┐
│ apps/shell │ ───────▶ │ libs/shared/ui │ ───────▶ │ npm:react │
└────────────┘          └────────────────┘          └───────────┘
```

### nx graph — главный инструмент навигации

`npx nx graph` поднимает локальный веб-UI. Ключевые режимы, которыми стоит пользоваться осознанно:

- **Focus** (`nx graph --focus=shell` или клик в UI) — только выбранный проект и его прямые/транзитивные связи. На репе в 200 проектов "Select all" бесполезен — focus обязателен.
- **Path tracing** — в UI выбираете два проекта, Nx показывает все пути между ними. Ответ на классический вопрос "почему изменение либы X перетестировало приложение Y".
- **`nx graph --file=graph.json`** — тот же граф в JSON для скриптов: посчитать входящие рёбра, найти самый нагруженный узел, проверить архитектурное правило в CI.
- **`nx graph --affected`** — подграф затронутого изменениями (глава 05).

## В рабочем монорепо

- `npx nx graph` → focus на проект, над которым работаете: его реальные зависимости и зависимые — за 10 секунд, без чтения кода.
- Path tracing между "моя либа" и "прод-приложение" — покажет, через какие слои изменение доедет до деплоя; этим же отвечают на "почему мой PR запустил 40 тестовых джоб".
- `npx nx graph --file=graph.json`, затем `python3 -c "import json; d=json.load(open('graph.json'))['graph']['dependencies']; import collections; c=collections.Counter(t['target'] for deps in d.values() for t in deps); print(c.most_common(10))"` — топ-10 узлов по входящим рёбрам: что в центре репы и что опаснее всего трогать.
- `grep -rn "implicitDependencies" --include=project.json .` — все ручные рёбра репы. У каждого должна быть внятная причина; куча implicitDependencies — симптом, что граф не отражает реальность.
- Граф "врёт" (удалили импорт, а ребро висит)? `npx nx reset`, потом снова `nx graph` — в 9 случаях из 10 это протухший daemon.

## Что добавляем в проект

Первая библиотека — `shared/ui` с компонентом `Button`: shell перестаёт быть единственным узлом, в графе появляется первое ребро, а в `tsconfig.base.json` — первый алиас. Это фундамент для рефакторинга на слои в главе 06.

## Практическое задание

**Вход:** workspace после главы 01 (приложение shell, плагины @nx/react + vite).

**Задача:**

1. Сгенерировать React-библиотеку `shared-ui` в `libs/shared/ui`: bundler — none (почему none — тема главы 06), тесты — vitest, import path — `@mini-shop/shared-ui`.
2. Добавить в либу компонент `Button` (обычная кнопка с `variant: 'primary' | 'ghost'`) и экспортировать его через публичный вход `src/index.ts`.
3. Использовать `Button` в `app.tsx` приложения shell. Убедиться, что `nx serve shell` рендерит кнопку.
4. Проверить ребро тремя способами: в UI `nx graph`; в `nx graph --file=graph.json` (найти запись про shell); и глазами — в diff `tsconfig.base.json`.
5. Сломать связь: закомментировать импорт в app.tsx — и убедиться, что ребро исчезло. Вернуть импорт.
6. Добавить в `shell` → `implicitDependencies: ["shared-ui"]`, посмотреть на тип ребра в graph.json, затем убрать.

**Edge cases на подумать:**

- Если заменить импорт на `import type { ButtonProps } ...` — останется ли ребро? А должно ли?
- Что будет с графом, если импортировать Button по относительному пути `../../../libs/shared/ui/src/lib/button` в обход алиаса? Чем это плохо, если "работает же"?
- Может ли shared-ui импортировать что-то из shell? Что скажет граф и что должно сказать ревью?

## Разбор решения

Генерация либы:

```bash
npx nx g @nx/react:lib shared-ui --directory=libs/shared/ui \
  --bundler=none --unitTestRunner=vitest --linter=eslint \
  --importPath=@mini-shop/shared-ui
```

Diff `tsconfig.base.json` — первый алиас (это и есть "проводка", по которой резолвится импорт):

```json
{
  "compilerOptions": {
    "paths": {
      "@mini-shop/shared-ui": ["libs/shared/ui/src/index.ts"]
    }
  }
}
```

Компонент и публичный вход:

```tsx
// libs/shared/ui/src/lib/button.tsx
import type { ReactNode } from 'react';

export interface ButtonProps {
  variant?: 'primary' | 'ghost';
  onClick?: () => void;
  children: ReactNode;
}

export function Button({ variant = 'primary', onClick, children }: ButtonProps) {
  return (
    <button className={`btn btn-${variant}`} onClick={onClick}>
      {children}
    </button>
  );
}
```

```ts
// libs/shared/ui/src/index.ts — ПУБЛИЧНЫЙ API либы:
// только то, что экспортировано отсюда, доступно другим проектам
export { Button } from './lib/button';
export type { ButtonProps } from './lib/button';
```

Использование в shell:

```tsx
// apps/shell/src/app/app.tsx
import { Button } from '@mini-shop/shared-ui';

export function App() {
  return (
    <div>
      <h1>mini-shop</h1>
      <Button onClick={() => console.log('go to catalog')}>Каталог</Button>
    </div>
  );
}

export default App;
```

Проверка ребра в JSON:

```bash
npx nx graph --file=graph.json
python3 -c "import json; print(json.load(open('graph.json'))['graph']['dependencies']['shell'])"
# [{'source': 'shell', 'target': 'shared-ui', 'type': 'static'},
#  {'source': 'shell', 'target': 'npm:react', 'type': 'static'}, ...]
```

Ключевые решения:

- Ребро `shell → shared-ui` появилось в момент, когда в app.tsx появилась строка импорта. Мы не редактировали ни одного конфига зависимостей — в этом пойнт главы.
- `src/index.ts` (barrel) — единственная точка входа: алиас в tsconfig.base.json указывает на этот файл, а не на папку. Всё, что не реэкспортировано из index.ts, — приватная кухня либы. Пока это джентльменское соглашение; в главе 06 сделаем его правилом линтера.
- После комментирования импорта ребро исчезает при следующем построении графа (daemon подхватывает изменение файла; если открытый `nx graph` показывает старое — обновите страницу, в крайнем случае `nx reset`).
- С `implicitDependencies: ["shared-ui"]` в graph.json появляется ребро `{'type': 'implicit'}` — оно живёт, даже когда импорта нет. Рабочий кейс — e2e → app; для обычной связи "код импортирует код" implicit-ребро избыточно, поэтому убираем.

Ответы на edge cases:

- `import type` оставляет ребро — и обязан: поменяли `ButtonProps` → shell должен попасть в affected, иначе CI пропустит сломанную типизацию.
- Относительный импорт в обход алиаса ребро тоже создаст (резолвер понимает относительные пути), но он дырявит публичный API: вы прицепились к внутреннему файлу либы, минуя index.ts. Рефакторинг внутренностей либы теперь ломает чужой код. В главе 06 такие импорты запретит `@nx/enforce-module-boundaries`.
- Технически `shared-ui → shell` возможен, и граф покорно нарисует цикл `shell ⇄ shared-ui` — а вот task pipeline (глава 03) на цикле сломается, и это правильно: библиотека, знающая о приложении, — перевёрнутая архитектура. Ревью должно завернуть такой импорт до всякого Nx.

2. Почему `import type` создаёт ребро, хотя из бандла такой импорт исчезает бесследно? Свяжи ответ с affected.
3. У e2e-проекта нет ни одного импорта из тестируемого приложения. Как выразить зависимость и почему без неё affected будет пропускать e2e при изменениях приложения?
4. Почему повторный `nx graph` открывается мгновенно, хотя репа большая? Кто поддерживает граф в актуальном состоянии, где он лежит на диске и какой командой его сбросить?
5. Зачем npm-пакеты присутствуют в графе отдельными узлами? Назови два механизма Nx, которым нужны рёбра на `npm:*`.

<details>
<summary>Ответы</summary>

1. Nx (через daemon) парсит AST файла app.tsx и находит импорт-спецификатор `@mini-shop/shared-ui`. Резолвер прогоняет его через `paths` в `tsconfig.base.json` и получает `libs/shared/ui/src/index.ts`. Этот путь лежит внутри корня проекта `shared-ui` (узел известен из project.json либы) — значит, файл проекта `shell` зависит от проекта `shared-ui`: в граф добавляется ребро `shell → shared-ui` типа `static`. Участвуют: исходник app.tsx, tsconfig.base.json (paths), project.json обеих сторон (границы проектов).
2. Ребро в графе отвечает не на вопрос "что попадёт в бандл", а на вопрос "чьё изменение меня затрагивает". Изменение `ButtonProps` в shared-ui может сломать компиляцию shell, не изменив ни байта в рантайме, — affected обязан перепроверить shell (typecheck, тесты). Если бы type-импорты игнорировались, CI зеленел бы на репе, которая не собирается.
3. `implicitDependencies: ["shell"]` в project.json e2e-проекта — ручное ребро для связей, не выраженных импортами (e2e ходит в приложение по URL). Без него граф считает e2e изолированным узлом: изменение shell не делает e2e затронутым, и affected-пайплайн в CI молча пропустит регрессию, которую e2e должен был поймать.
4. Граф пересчитывается не с нуля: daemon следит за файловой системой и инкрементально обновляет граф при изменениях, а сериализованное состояние живёт в `.nx/workspace-data`. Поэтому запуск любой команды использует уже готовый граф. Сброс — `nx reset`: убивает daemon и стирает производные данные; следующая команда строит всё заново (первый приём при "граф врёт").
5. Во-первых, кеш: версия npm-пакета — input хеша (глава 04); обновление react должно инвалидировать сборки всех, кто его импортирует, — для этого нужны рёбра `проект → npm:react`. Во-вторых, анализ использования: `nx graph` показывает фактических потребителей пакета по импортам, а не по декларациям, — это точный ответ на "можно ли выпилить зависимость X".

</details>

## Частая ошибка

Разработчик из single-app мира приносит убеждение "зависимость существует, только если она задекларирована". Он ищет, где "подключена" shared-ui к shell, не находит записи ни в одном package.json — и делает одно из двух: либо добавляет декларацию руками (лишний implicitDependencies или запись в package.json, дублирующая то, что граф уже знает), либо, наоборот, решает, что раз декларировать ничего не надо, то и порядка нет — и начинает импортировать из чужих либ что угодно: `import { helper } from '../../../libs/checkout/feature/src/lib/internal/utils'`. Граф это переварит (ребро появится), но такой deep-import прицеплен к внутреннему файлу мимо публичного API: владелец либы переставит файлы — и уронит половину репы, не изменив ни одного экспорта из index.ts.

Правильная ментальная модель обратная: **декларация — это импорт**. Ребро создаётся кодом; index.ts — контракт, внутри которого либа свободна; implicitDependencies — исключение с обоснованием в ревью, а не инструмент на каждый день. Если хочется ребро без импорта или импорт мимо index.ts — это почти всегда сигнал, что код лежит не в той либе.
