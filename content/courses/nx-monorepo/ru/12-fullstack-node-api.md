# Фулл-стек в монорепо: Node API и общие контракты

## Теория

### Зачем бэкенду жить в той же репе

До сих пор монорепо-выгоды работали внутри фронтенда. Настоящий масштаб они набирают, когда в ту же репу въезжает бэкенд. Причина: самая хрупкая граница в вебе проходит не между либами, а **между фронтом и бэком**. Эта граница — контракт API.

В polyrepo он охраняется вручную: swagger-страницей, пакетом типов с версионированием, перепиской "а вы поле переименовали?". В монорепо контракт — это код:

```
                  контракт как код

           ┌────────────────────────────┐
           │ libs/shared/api-types      │
           │ Product · ProductsResponse │
           │ (type:util, чистые типы)   │
           └────────────────────────────┘
import type: обе стороны компилируются против ОДНОГО контракта
                         ▼
┌───────────────────────┐    ┌─────────────────────┐
│ apps/api (Express)    │    │ catalog-data-access │
│ GET /api/products     │    │ fetch + типизация   │
│ GET /api/products/:id │    │ запросов и ответов  │
└───────────────────────┘    └─────────────────────┘

        в рантайме между ними обычный HTTP:
      типы проверил компилятор, данные — никто
```

Дальше срабатывает вся механика курса разом. Переименовали поле в `api-types` → tsc мгновенно краснеет **во всех** потребителях по обе стороны HTTP. Причём не через неделю на интеграционном стенде, а до коммита.

Команда `nx affected` (глава 05) видит правку типовой либы и сама решает: тестировать и api, и data-access, и всё, что выше. Boundaries (глава 06) следят, чтобы контракт не оброс чужими зависимостями. Это главный практический выигрыш монорепо для фулл-стек-разработчика — и главное, что стоит показывать на собеседовании.

Честная оговорка: выигрыш общих типов достаётся TS-бэкенду. Если бэкенд на Go или Java, контракт остаётся кодом через кодогенерацию: OpenAPI-схема генерирует типы для обеих сторон. Механика affected продолжает работать через implicit-связи, но прямого "одна либа типов" уже нет.

### @nx/node: третий вид приложения в графе

Для Nx бэкенд — просто ещё один узел: `nx g @nx/node:app` с выбором фреймворка (express / fastify / none; для Nest — отдельный пакет `@nx/nest` со своими генераторами). Существенные отличия от фронтовых приложений:

- **Сборка — esbuild** (в свежих версиях по умолчанию): бандлит main.ts вместе со всеми workspace-либами в `dist/apps/api/main.js`, как vite/rspack бандлят фронт. Следствие: non-buildable либы работают и здесь.
- **serve** — сборка в watch-режиме + перезапуск Node-процесса при изменениях.

> **Версии.** Глава 06 обещала показать "техническую необходимость buildable-либ" здесь, в главе 12. Закрываем обещание честно: с esbuild-бандлером она **не возникает**. Либы компилируются из исходников через алиасы, как на фронте.

> Необходимость была реальной в старых Node-сетапах, где приложение компилировалось через `@nx/js:tsc` без бандлинга. Там каждой workspace-либе требовался собственный скомпилированный артефакт с декларациями, и все они становились buildable. Встретите в легаси-репе лес buildable-либ вокруг Node-приложений — теперь вы знаете, откуда он.

### Контракт — платформенно-нейтральная либа

`shared/api-types` — обычная `@nx/js`-либа с тегами `scope:shared, type:util`, но с дополнительным требованием: **ни рантайм-кода, ни платформенных API**. Её импортируют браузерный бандл и Node-процесс. Значит, внутри только типы и, максимум, изоморфные константы: никакого `fs`, `window`, побочных эффектов.

В больших репах это требование оформляют третьей осью тегов: `platform:web / platform:node / platform:agnostic`. Boundary-правило тогда говорит, что web не импортирует node. Это и есть та самая "третья ось", о которой шла речь в главе 06.

### Чего типы не гарантируют

Компилятор проверил, что обе стороны *написаны* против одного контракта. В рантайме между ними — сеть, и никто не проверяет, что фактический JSON соответствует `Product`: типы стёрты. Пока api и фронт деплоятся из одного коммита, расхождение невозможно. Но деплой у нас независимый (глава 11 передаёт привет), и вчерашний фронт может получить ответ от сегодняшнего api.

Правила выживания те же, что для shared-либ. Первое: обратно-совместимая эволюция API — добавлять поля, не переименовывать, депрекация вместо удаления. Второе: на границах с внешними и нестабильными источниками нужна рантайм-валидация (zod и аналоги). Она превращает "тихо неправильные данные" в явную ошибку.

## В рабочем монорепо

- `nx show projects | grep -v e2e` + `nx graph`: есть ли в репе Node-приложения и через какие либы они связаны с фронтом. Узлы-"мосты" между фронтом и бэком — почти всегда контрактные либы.
- Найдите контракт: `ls libs/shared | grep -iE 'types|contracts|dto|api'`. Проверьте её чистоту: `grep -rn "from 'fs'\|window\." libs/shared/api-types/src` — платформенные импорты в контрактной либе означают, что однажды она уронит чужой бандл.
- Правка контрактной либы: `nx show projects --affected` должен показать проекты **по обе стороны** HTTP. Показывает только фронт — бэкенд связан с контрактом не импортом, а копипастой: дрейф уже идёт.
- Как фронт узнаёт адрес API: grep по `API_URL`/`baseUrl`/proxy-конфигам. Хардкод продового домена в data-access — находка для ревью.
- Если бэкенд не в репе: поищите кодоген (`openapi`, `orval`, `graphql-codegen` в devDeps) — контракт может быть кодом и без общей репы.

## Что добавляем в проект

Настоящий бэкенд: приложение `api` на Express с эндпоинтами каталога, контрактная либа `shared/api-types` — и `catalog-data-access` наконец меняет моки из главы 06 на реальный HTTP. Обещание "ни один потребитель не изменится" из комментария в products.ts — проверим.

## Практическое задание

**Вход:** workspace после главы 11.

**Задача:**

1. Сгенерировать контрактную либу `shared-api-types` (`libs/shared/api-types`, `scope:shared,type:util`, bundler none). Перенести в неё интерфейс `Product` из catalog-data-access и добавить тип ответа списка `ProductsResponse`.
2. Сгенерировать приложение `api` (`@nx/node`, framework express, `apps/api`, теги `scope:api,type:app`); добавить scope-правило в boundaries (api видит только shared).
3. Эндпоинты: `GET /api/products` (список, `ProductsResponse`) и `GET /api/products/:id` (продукт или 404). Данные — in-memory массив из бывших моков, типизированный `Product[]` из контрактной либы.
4. Включить CORS (cross-origin resource sharing) для dev-портов фронта 4200–4202 и запустить `nx serve api`.
5. Переписать `catalog-data-access`: `getProducts()` и новый `getProduct(id)` ходят по HTTP с типами из api-types, ошибки сети/статусов превращаются в исключения. Убедиться, что `catalog-feature` не изменился ни на строчку.
6. Полный стек локально: `nx serve api` + `nx serve shell --devRemotes=catalog` — каталог рендерит данные с бэкенда.
7. **Контракт-эксперимент** (ядро главы): переименовать в api-types поле `title` → `name`. Зафиксировать: (а) список `nx show projects --affected`; (б) где и с какими текстами упали `typecheck`/`build`. Затем (в) починить все стороны и добиться зелёного `nx affected -t lint,test,typecheck,build`.

**Требования:** теги и boundaries зелёные; у api есть target `typecheck`; фронт не импортирует ничего из `apps/api` (проверить график).

**Edge cases на подумать:**

- Почему `Product` должен переехать в api-types, а не реэкспортироваться из catalog-data-access "для совместимости"?
- Что произойдёт, если задеплоить новый api (поле `name`) при старом фронте (ждёт `title`)? Чем это отличается от first-wins главы 11?
- Где в этой схеме место рантайм-валидации (zod), а где она — лишняя?

## Разбор решения

Шаги 1–2 — генерация:

```bash
npx nx g @nx/js:lib shared-api-types --directory=libs/shared/api-types \
  --bundler=none --unitTestRunner=vitest --linter=eslint \
  --importPath=@mini-shop/shared-api-types --tags=scope:shared,type:util

npx nx add @nx/node
npx nx g @nx/node:app api --directory=apps/api --framework=express \
  --e2eTestRunner=none --tags=scope:api,type:app
```

Контракт:

```ts
// libs/shared/api-types/src/lib/products.ts — ЕДИНСТВЕННОЕ место, где описан контракт
export interface Product {
  id: string;
  title: string;
  priceCents: number;
}

export interface ProductsResponse {
  products: Product[];
  total: number;
}
```

Шаги 3–4 — бэкенд (тонкий, как и договаривались в главе 01 — для курса логика прямо в main.ts; в реальном api она уехала бы в `api/feature`-либы):

```ts
// apps/api/src/main.ts
import express from 'express';
import cors from 'cors';
import type { Product, ProductsResponse } from '@mini-shop/shared-api-types';

const PRODUCTS: Product[] = [
  { id: 'p1', title: 'Mechanical keyboard', priceCents: 12900 },
  { id: 'p2', title: 'USB-C dock', priceCents: 8900 },
  { id: 'p3', title: '4K monitor', priceCents: 41900 },
];

const app = express();
app.use(cors({ origin: /localhost:42\d\d$/ }));

app.get('/api/products', (_req, res) => {
  const body: ProductsResponse = { products: PRODUCTS, total: PRODUCTS.length };
  res.json(body);
});

app.get('/api/products/:id', (req, res) => {
  const product = PRODUCTS.find((p) => p.id === req.params.id);
  if (!product) return res.status(404).json({ message: 'Product not found' });
  return res.json(product);
});

const port = process.env.PORT ? Number(process.env.PORT) : 3333;
app.listen(port, () => console.log(`[api] http://localhost:${port}`));
```

Шаг 5 — data-access переходит на HTTP; сигнатуры не меняются, поэтому catalog-feature не трогаем вообще (тот самый асинхронный контракт из главы 06):

```ts
// libs/catalog/data-access/src/lib/products.ts
import type { Product, ProductsResponse } from '@mini-shop/shared-api-types';

// Конфигурация адреса — задача деплоя; для dev достаточно константы
const API_BASE = 'http://localhost:3333';

async function request<T>(path: string): Promise<T> {
  const res = await fetch(`${API_BASE}${path}`);
  if (!res.ok) throw new Error(`API ${res.status}: ${path}`);
  return res.json() as Promise<T>;
}

export async function getProducts(): Promise<Product[]> {
  const { products } = await request<ProductsResponse>('/api/products');
  return products;
}

export function getProduct(id: string): Promise<Product> {
  return request<Product>(`/api/products/${id}`);
}

export type { Product } from '@mini-shop/shared-api-types';
```

Реэкспорт `Product` в последней строке — осознанное решение (edge case 1). Потребители data-access продолжают импортировать `Product` из него: слой data-access остаётся их единственной API-дверью, boundaries из главы 06 не размываются. Но **определение** живёт только в api-types, а реэкспорт — не копия, дрейфовать нечему.

Шаг 7 — контракт-эксперимент. После `title` → `name`:

```bash
npx nx show projects --affected --base=main
# shared-api-types   ← владелец правки
# api                ← бэкенд-потребитель
# catalog-data-access
# catalog-feature    ← замыкание вверх по графу
# catalog
# shell

npx nx affected -t typecheck --base=main
# apps/api/src/main.ts:8:15 — error TS2561: Object literal may only specify known
#   properties, but 'title' does not exist in type 'Product'. Did you mean 'name'?
# libs/catalog/feature/src/lib/catalog-page.tsx:24 — error TS2339:
#   Property 'title' does not exist on type 'Product'.
```

Вот сцена целиком: **одна правка контракта — компилятор перечислил все места по обе стороны HTTP, affected собрал точный список работ**. В polyrepo этот же рефакторинг — публикация пакета типов, PR (pull request) в две репы и надежда, что никто не забыт. Чиним api и catalog-page, прогоняем `nx affected -t lint,test,typecheck,build` — зелено.

Ответы на оставшиеся edge cases:

- Задеплоить новый api при старом фронте — классический version skew. Фронт обратится к `product.title` и получит `undefined`. Это тихая деградация интерфейса, а не исключение, — потому и коварно. Отличие от first-wins главы 11: там гонка за singleton в браузере, здесь — рассинхрон артефактов по сторонам сети. Лечение общее — обратно-совместимая эволюция: добавить `name`, пометить `title` deprecated, удалить после выката всех потребителей. Плюс affected-подсказка, кого деплоить вместе.
- Zod уместен на границах, где TypeScript бессилен: вход api (тело POST-запроса — глава про валидацию пользовательского ввода), ответы внешних API, конфиги из env. Внутри нашей пары "api ↔ фронт из одной репы" сплошная рантайм-валидация каждого ответа — оверхед. Контракт и так проверен компилятором, а skew закрывается совместимостью. Включать её стоит там, где стороны деплоятся сильно независимо или источник данных не под вашим контролем.

## Проверь себя

1. Воспроизведи цепочку "переименовали поле в контракте" в монорепо и в polyrepo: какие шаги, где ловится ошибка, сколько времени проходит до обнаружения в каждом случае?
2. Почему контрактная либа обязана быть платформенно-нейтральной и как это выражается (и защищается) в терминах тегов и boundaries?
3. Что гарантирует общий `api-types`, а что — нет? Где проходит граница между работой компилятора и необходимостью рантайм-валидации?
4. Почему с esbuild-бандлером Node-приложению не нужны buildable-либы, и в каком сетапе они были нужны?
5. Правка в `shared/api-types` — опиши, что произойдёт при `nx affected -t test,build` и почему это работает "через" HTTP-границу, которой в графе нет.

<details>
<summary>Ответы</summary>

1. Монорепо: правка в api-types → tsc падает у всех потребителей локально или в PR → affected собирает их тесты → всё чинится в одном атомарном PR. Время до обнаружения — секунды. Polyrepo: правка в пакете типов → publish новой версии → каждая репа-потребитель должна сама поднять версию (когда-нибудь). До тех пор фронт и бэк собираются против разных контрактов, и первый сигнал — часто рантайм-ошибка на стенде или в проде. Время до обнаружения — дни, и оно недетерминировано.
2. Её импортируют два разных рантайма: браузерный бандл (нет fs, process) и Node (нет window и DOM — document object model, дерева документа). Любой платформенный импорт уронит сборку противоположной стороны, причём не сразу, а когда кто-то впервые дёрнет затронутый модуль. Выражается это тегами. Тег `type:util` уже запрещает зависимости вниз, а в больших репах добавляют ось `platform:*` с правилом вида `platform:web` не импортирует `platform:node`. Контракт при этом получает `platform:agnostic`.
3. Гарантирует: обе стороны *написаны* против одного описания данных, любое несовместимое изменение контракта ломает компиляцию всех потребителей немедленно. Не гарантирует: что фактические байты в HTTP-ответе соответствуют типам — типы стёрты в рантайме, а стороны могут быть задеплоены из разных коммитов. Граница: внутри одного коммита/деплоя — достаточно компилятора; через независимый деплой или внешние источники — нужна дисциплина совместимости и/или рантайм-валидация на границе.
4. esbuild бандлит приложение из исходников: workspace-либы резолвятся через алиасы tsconfig и попадают в итоговый main.js так же, как во фронтовый бандл, — отдельный артефакт либы не нужен. Buildable-либы были необходимостью в сетапах, где Node-приложение компилировалось `@nx/js:tsc` без бандлинга: tsc-сборке приложения нужны готовые d.ts/JS каждой зависимости, и каждая либа обзаводилась собственным build.
5. api-types — владелец изменённых файлов; замыкание вверх по графу (глава 05) собирает всех, кто импортирует её: api, catalog-data-access, дальше catalog-feature, catalog, shell. Для них создаются test/build-задачи (с учётом кеша). HTTP-граница тут ни при чём — работает обычный граф импортов: обе стороны сети *статически импортируют одну либу*, и именно это ребро делает бэкенд и фронтенд соседями в графе.

## Частая ошибка

Разработчик из single-app мира привык, что "типы ответа API" — это файл `types.ts` рядом с fetch-кодом. В монорепо он делает так же. Интерфейс `Product` живёт во фронтовой либе, а бэкенд "знает" контракт в виде похожего интерфейса, написанного рядом с роутом. А иногда не написанного вовсе.

Через месяц поля разъезжаются: у фронта `priceCents`, у бэка уже `price`. И все инструменты курса бессильны. **Дрейф двух копий не видит ни компилятор, ни affected, потому что связи в графе нет.**

Правило простое: описание того, что ходит по сети, живёт ровно в одном месте — в контрактной либе. Фронт и бэк её импортируют, а не пересказывают.

Вторая ошибка противоположного знака: уверовать, что раз tsc зелёный — данные корректны. Типы — иллюзия времени компиляции. Они гарантируют согласованность *кода*, но в рантайме по сети ходит нетипизированный JSON от того артефакта, который фактически задеплоен.

Пока обе стороны выезжают из одного коммита, иллюзия безопасна. При независимом деплое (а весь курс — про него) появляется зазор, в котором старый фронт разговаривает с новым api. Ответ — не паранойя со схемами на каждый вызов, а осознанность. Обратно-совместимая эволюция контракта как норма, и рантайм-валидация именно там, где стороны реально расходятся во времени или источник вам не принадлежит.
