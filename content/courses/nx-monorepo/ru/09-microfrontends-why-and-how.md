# Микрофронтенды: зачем и как это работает

## Теория

Глава концептуальная: код mini-shop не меняется. Прежде чем в главе 10 нажимать на генераторы, нужно понимать, что именно они сгенерируют и зачем — иначе Module Federation останется "магией конфигов".

### Зачем микрофронтенды: одна честная причина

У микрофронтендов одна настоящая причина существования: **независимый деплой независимыми командами**. Всё остальное из маркетинговых списков — "переиспользование", "изоляция", "разные технологии" — делится надвое. Либо это уже решено монорепо (шаринг кода, границы — главы 02 и 06), либо это антипаттерн: зоопарк фреймворков на одной странице.

Признаки, что Module Federation (MF) действительно нужен:

- Несколько команд с собственным релизным циклом упираются в общий "релизный поезд".
- Нужно катить канарейку на часть интерфейса, не трогая остальное.
- Продукт собирается из частей, у которых разные владельцы и разная скорость изменений.

Если всё это не про вас, build-time композиция из обычного монорепо проще, быстрее и надёжнее. Она у нас уже есть: shell импортирует catalog-feature.

Цена MF, о которой молчат доклады:

- **Ошибки интеграции переезжают в рантайм.** При build-time композиции несовместимость ловит компилятор; при runtime — пользователь в проде. Контракты между host и remote надо охранять отдельно: типы (глава 11), сквозные (e2e) тесты, канарейки.
- **Версии shared-зависимостей** превращаются в постоянную операционную заботу (глава 11 целиком об этом).
- **Сквозной пользовательский опыт** — роутинг, авторизация, дизайн-система, аналитика — должен работать поверх независимо деплоящихся частей. Это архитектурная работа, которой при монолитной сборке просто нет.
- **Инфраструктура**: N артефактов, N деплоев, матрица совместимости версий "какой catalog совместим с каким shell".

### Механика Module Federation: host, remote, container

Module Federation — фича бандлера, родилась в webpack 5. Она позволяет приложению **в рантайме** загружать модули из других приложений, собранных и задеплоенных отдельно.

```
       ┌──────────────────────────────┐
       │ shell (host)                 │
       │ роутер, layout, auth,        │
       │ адреса remoteEntry remote-ов │
       └──────────────────────────────┘
загружает в рантайме, в браузере пользователя
                      ▼
┌──────────────────┐    ┌───────────────────┐
│ catalog (remote) │    │ checkout (remote) │
│ exposes:         │    │ exposes:          │
│ ./CatalogPage    │    │ ./CheckoutPage    │
└──────────────────┘    └───────────────────┘
```

Словарь:

- **Remote** — приложение, которое *экспонирует* модули наружу (`exposes: { './CatalogPage': './src/...' }`). Собирается в обычные чанки плюс особый файл — **remoteEntry.js**: маленький манифест-контейнер со списком экспонируемых модулей и деклараций shared-зависимостей. Не путайте: remoteEntry — это оглавление, а не сам код; код приезжает чанками по требованию.
- **Host** — приложение, которое знает адреса remoteEntry своих remote-ов и загружает их модули в рантайме.
- **Container** — JS-объект, которым remote представляется миру. У него два метода: `init(sharedScope)` — "вот общий скоуп зависимостей, вклинься" и `get(moduleName)` — "дай фабрику модуля". Всё Module Federation API — это, по сути, эти два вызова.

Полная последовательность загрузки (это ядро главы — прочитайте диаграмму дважды):

```
┌──────────────────────────────────────────────────────┐
│ браузер грузит shell (host):                         │
│ свой бандл + список адресов remoteEntry              │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ host скачивает remoteEntry.js каталога —             │
│ маленький манифест контейнера, не весь бандл         │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ container.init(sharedScope):                         │
│ host и remote объявляют версии react, react-dom, ... │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ shared negotiation: на каждую зависимость            │
│ выбирается один совместимый экземпляр                │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ container.get("./CatalogPage") →                     │
│ догружаются чанки модуля каталога                    │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ CatalogPage рендерится в дереве host-а               │
│ тем самым, согласованным, react-ом                   │
└──────────────────────────────────────────────────────┘
```

### Shared dependencies: singleton, strictVersion, eager

Если бы каждый remote возил свой react, страница с тремя remote-ами загружала бы React четырежды. И это ещё не худшее (см. вопрос 4 в конце). Поэтому зависимости декларируются как **shared**. При `init` каждая сторона говорит "мне нужен react ^18.2, могу предоставить 18.3.1". Дальше в shared scope выбирается один экземпляр, удовлетворяющий всех.

Три флага, управляющих согласованием:

- **`singleton: true`** — экземпляр может быть только один, даже если версии формально несовместимы (тогда warning и берётся уже загруженная). Обязателен для react, react-dom, роутера, любых библиотек с глобальным состоянием или Context.
- **`strictVersion: true`** — при несовместимости версий не warning, а ошибка в рантайме. Жёстко, зато несовместимость видна сразу, а не через сломанный хук в проде.
- **`eager: true`** — зависимость кладётся в начальный бандл, а не грузится асинхронно. Нужен на стороне host для самых базовых зависимостей. Связан с классической ошибкой "Shared module is not available for eager consumption", которую мы намеренно воспроизведём в главе 11.

### Runtime- против build-time-композиции

Ключевой сдвиг в голове: до сих пор `import { CatalogPage } from '@mini-shop/catalog-feature'` разрешался **на этапе сборки**. Код каталога компилировался внутрь бандла shell, версия зафиксирована навсегда, деплой один.

С MF модуль каталога разрешается **в браузере пользователя**: shell узнаёт, какой там CatalogPage, только в момент загрузки. Отсюда суперсила: задеплоил catalog — и все пользователи получили новый каталог без пересборки shell. Отсюда же и вся цена: никто на этапе сборки не проверил, что новый catalog совместим со старым shell.

### Альтернативы, о которых надо знать

- **Build-time композиция** (наш текущий mini-shop): импорты в монорепо, один артефакт, один деплой. Выбор по умолчанию.
- **Композиция маршрутами**: `/catalog` и `/checkout` — отдельные одностраничные приложения за реверс-прокси, а переход между ними — полная перезагрузка страницы. Дёшево, надёжно, независимый деплой есть. Жертвуете бесшовностью одностраничного приложения и общим состоянием в памяти.
- **iframe**: максимальная изоляция (стили, JS, сбои), встраивание чужого/легаси; цена — коммуникация через postMessage, дубли зависимостей, мучения с роутингом, модалками и высотой. Недооценён для админок и виджетов.
- **single-spa**: оркестратор, который ведёт жизненный цикл нескольких одностраничных приложений на одной странице. Отвечает на вопрос "когда монтировать", тогда как MF — на вопрос "откуда взять код". Их иногда используют вместе.

Правило выбора состоит из трёх веток. Не нужен независимый деплой → build-time. Нужен на уровне *страниц* → композиция маршрутами. Нужен внутри одной страницы, и при этом переходы должны быть бесшовными → Module Federation.

> **Версии.** MF родился в webpack 5. Nx умеет собирать федерацию и webpack-ом, и rspack-ом — это Rust-реализация, заметно быстрее, и свежие версии Nx предлагают её по умолчанию. Для vite федерация — сторонние плагины вне основной поддержки Nx. Поэтому в главе 10 наши MF-приложения будут не на vite, как shell до сих пор, а на webpack или rspack.

> **Module Federation 2.0.** Современные версии Nx используют именно её (`@module-federation/enhanced`), с рантайм-плагинами и генерацией типов между host и remote. В старых репах стоит "родной" webpack ModuleFederationPlugin без этого.

## В рабочем монорепо

- `find . -name "module-federation.config.*" -not -path '*/node_modules/*'` — кто host, кто remote: у host в конфиге `remotes: [...]`, у remote — `exposes: {...}`.
- Откройте прод вашего продукта → вкладка Network → фильтр "remoteEntry": сколько remote-ов реально грузится, из каких доменов и сетей доставки контента, что в waterfall после каждого remoteEntry.
- `curl -s https://<прод>/catalog/remoteEntry.js | head -c 400` — remoteEntry читаем: в начале видны имя контейнера и карта модулей.
- В shared-конфиге проверьте react: есть ли `singleton: true` (его отсутствие — бомба замедленного действия, глава 11).
- Главный аудит: деплоятся ли remote-ы *реально* независимо? Если непрерывная интеграция (CI) собирает и катит всё вместе, команда платит полную цену MF, не получая единственной выгоды. Это типовая "археологическая находка" главы 14.

## Что добавляем в проект

Ничего — глава подготовительная. В главе 10 mini-shop станет федерацией. Shell превратится в host, появятся remote-ы catalog и checkout, и всё из этой главы станет строчками конфигов.

## Практическое задание

Код не пишем — проектируем и отвечаем письменно (это те решения, которые в главе 10 превратятся в конфиги).

1. **Выбор архитектуры.** Для трёх продуктов выберите: build-time / композиция маршрутами / MF / iframe — и обоснуйте одной-двумя фразами:
   - (а) стартап, 6 фронтендеров в одной команде, релиз дважды в неделю;
   - (б) банковский портал: 5 команд, у каждой свой домен (платежи, кредиты, инвестиции), релизные циклы от дня до месяца. Бесшовность одностраничного приложения обязательна;
   - (в) SaaS-дашборд (software as a service), куда клиенты встраивают собственные виджеты с произвольным кодом.
2. **Чтение схемы загрузки.** По диаграмме из теории ответьте:
   - что увидит пользователь, если сеть доставки контента (CDN) с remoteEntry каталога недоступна, и где в host-е должна жить защита;
   - что произойдёт на шаге negotiation, если shell собран с react 18.3, а catalog — с react 19 при `singleton: true` без strictVersion? А со `strictVersion: true`?
3. **Проектирование mini-shop.** Зафиксируйте письменно три вещи. Что экспонирует catalog и что checkout (модуль = страница? компонент? роут?). Полный список shared с флагами. Где живут роутинг, layout и дизайн-система (shared-ui) и почему.

**Edge cases на подумать:**

- Два remote-а используют разные мажорные версии дизайн-системы. Это проблема shared negotiation или организационная?
- Remote хочет собственный Redux store. Где граница между "своё состояние remote-а" и "общее состояние приложения"?
- Как MF уживается с рендерингом на сервере (SSR) и поисковой оптимизацией (SEO)?

## Разбор решения

**1. Выбор архитектуры.**

- (а) **Build-time** (монорепо, как наш mini-shop сейчас). Одна команда — некому деплоиться независимо; MF добавил бы всю свою цену ради решения несуществующей проблемы.
- (б) **Module Federation**. Много команд, свои релизные циклы, бесшовные переходы: композиция маршрутами с её перезагрузками не проходит по требованиям. Это точно профиль MF. Монорепо при этом остаётся — MF и монорепо не конкуренты, а слои (глава 10 покажет это буквально).
- (в) **iframe**. Чужой произвольный код на вашей странице — вопрос изоляции и безопасности, а не композиции модулей. MF исполняет remote в общем JS-контексте, что для недоверенного кода неприемлемо.

**2. Чтение схемы.**

- Недоступный remoteEntry — это отказ на шаге 2: `container` не создастся, `get()` не у кого звать. Без защиты падает весь host. Защита живёт на границе загрузки модуля. Динамический `import()` remote-модуля оборачивается в error boundary с запасным экраном: "Каталог временно недоступен". Роут каталога деградирует, не убивая приложение. Это архитектурное следствие runtime-композиции: у build-time такой ошибки не существует в принципе.
- При `singleton: true` без strictVersion в shared scope останется один react — тот, что загружен первым, то есть react host-а, 18.3. В консоль упадёт warning о несовместимости. Catalog, собранный против API react 19, будет исполняться на 18.3: может работать, а может сломаться на первом использовании API, которого в 18.3 нет. Со `strictVersion: true` будет немедленная ошибка в рантайме на шаге negotiation. Жёстче, но честнее, чем "authService is undefined" где-то в глубине.

**3. Проектирование mini-shop** (это станет конфигами главы 10):

- catalog экспонирует `./CatalogPage`, checkout — `./CheckoutPage`. **Страница или роут — правильная гранулярность экспонирования.** Экспонировать десятки мелких компонентов = превратить remote в "npm-пакет с доставкой по HTTP" и утонуть в матрице совместимости.
- shared: `react` и `react-dom` — `singleton: true` обязательно; роутер (когда появится) — тоже singleton: у приложения одна история навигации.
- Роутинг и layout — в host: это и есть его работа (композиция плюс сквозной пользовательский опыт). Дизайн-система (shared-ui) — воркспейсная либа, разделяемая между remote-ами; как именно она ведёт себя в федерации — центральный сюжет главы 11.

**Edge cases.**

- Разные мажоры дизайн-системы у двух remote-ов negotiation переживёт: это не singleton, каждый привезёт свою копию. А стили и пользовательский опыт не переживут — пользователь увидит два визуальных языка на одной странице. Проблема организационная, решается управлением версиями и дисциплиной обновлений, а не флагами webpack.
- Внутреннее состояние remote-а (фильтры каталога) — его личное дело, хоть Redux, хоть zustand. Общее состояние — корзина, пользователь — это контракт уровня приложения. Либо host предоставляет его через shared singleton-либу с событиями, либо через явный API: пропсы и колбэки в экспонируемый модуль. Правило то же, что в главе 06: общее — в shared, и это осознанный контракт, а не "remote залез в window".
- SSR + MF возможен (федерация на сервере), но сложность возрастает на порядок: рендерить надо согласованные версии на сервере и клиенте. Честный ответ: если SEO и SSR критичны, серьёзно рассмотрите композицию маршрутами по страницам или build-time, прежде чем тащить федерацию на сервер.

<summary>Ответы</summary>

1. Независимый деплой независимыми командами: возможность выкатить свою часть интерфейса, не собирая и не координируя релиз остальных. Шаринг кода решается монорепо или пакетами, без единого рантайм-риска. Если вам нужен только он, MF даёт всю цену runtime-интеграции взамен уже решённой задачи.
2. remoteEntry.js — манифест контейнера remote-а: имя, карта exposes-модулей, декларации shared. Маленький, потому что не содержит код модулей — только оглавление и загрузчик. Сам код приезжает чанками по требованию. Вызов `init(sharedScope)` встраивает remote в общий скоуп зависимостей: он объявляет свои версии и узнаёт чужие. Вызов `get(name)` возвращает фабрику экспонированного модуля, попутно догружая его чанки.
3. При `init` каждая сторона кладёт в shared scope записи "пакет → версия, которую могу предоставить + диапазон, который требую". На каждый пакет выбирается экземпляр, удовлетворяющий требованиям, — обычно старшая совместимая из предоставленных. Флаг `singleton` форсирует единственный экземпляр даже при конфликте: пишется warning и берётся уже загруженный. Флаг `strictVersion` превращает конфликт из warning в ошибку. Флаг `eager` кладёт зависимость в начальный бандл, убирая асинхронную загрузку — и создавая требование async boundary у потребителей (глава 11).
4. React хранит глобальное для экземпляра состояние, и расходится оно в трёх местах. (а) Hooks-диспетчер: компонент, отрендеренный "чужим" react-ом, вызывает хуки не на том диспетчере → "Invalid hook call". (б) Context: `createContext` из экземпляра A и `useContext` из экземпляра B — это разные объекты, поэтому провайдер "не виден". (в) Два ReactDOM спорят за события и reconciliation. Одинаковость версий не спасает. Проблема в двух копиях модуля с раздельным состоянием, поэтому react — всегда `singleton: true`.
5. Непроверенными остаются три вещи. Сигнатуры и типы экспонируемых модулей: host собирается, не видя реального кода remote-а. Совместимость версий shared. Само существование модуля по адресу. Компенсируют это набором соглашений. Генерация и проверка типов между host и remote (MF 2.0, глава 11). Контрактные и e2e-тесты связки. Канареечные деплои remote-ов. Error boundaries с fallback на каждой точке подключения remote-а.

## Частая ошибка

Разработчик из мира одиночных приложений приносит в MF-проект ментальную модель npm-пакета. Звучит она так: "catalog — это зависимость shell. Значит, её версия зафиксирована где-то в lock-файле, и пока я не подниму версию, ничего не изменится".

С Module Federation это неверно в самом главном. Remote приезжает в рантайме, и его "версия" — это **то, что сейчас лежит на CDN**, а не то, что было при сборке host. Отсюда классическое недоумение: "мы ничего не деплоили, а прод сломался". Сломался, потому что соседняя команда задеплоила свой remote.

Диагностика таких инцидентов начинается не с git log своей репы, а с вопроса "кто и что деплоил за последний час", и это фундаментальный сдвиг по сравнению с монолитом.

Вторая ошибка — тащить MF туда, где деплоит одна команда, "потому что современно" или "чтобы сборка была быстрее". Скорость сборки решают кеш и affected (главы 04–05). Независимый деплой одной команде не нужен, и остаётся чистая цена: рантайм-риски, негласные контракты, инфраструктура на N артефактов.

Микрофронтенды — организационный инструмент под организационную проблему. Если проблемы нет, лучший MF — это его отсутствие.
