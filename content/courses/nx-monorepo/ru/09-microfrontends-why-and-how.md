# Микрофронтенды: зачем и как это работает

## Теория

Глава концептуальная: код mini-shop не меняется. Прежде чем в главе 10 нажимать на генераторы, нужно понимать, что именно они сгенерируют и зачем — иначе Module Federation останется "магией конфигов".

### Зачем микрофронтенды: одна честная причина

У микрофронтендов одна настоящая причина существования: **независимый деплой независимыми командами**. Всё остальное из маркетинговых списков ("переиспользование", "изоляция", "разные технологии") либо уже решено монорепо (шаринг кода, границы — главы 02 и 06), либо является антипаттерном (зоопарк фреймворков на одной странице).

Признаки, что MF действительно нужен: несколько команд с собственным релизным циклом упираются в общий "релизный поезд"; нужно катить канарейку на часть UI, не трогая остальное; продукт собирается из частей, у которых разные владельцы и разная скорость изменений. Если всё это не про вас — build-time композиция из обычного монорепо (то, что у нас уже есть: shell импортирует catalog-feature) проще, быстрее и надёжнее.

Цена MF, о которой молчат доклады:

- **Ошибки интеграции переезжают в рантайм.** При build-time композиции несовместимость ловит компилятор; при runtime — пользователь в проде. Контракты между host и remote надо охранять отдельно (типы — глава 11, e2e, канарейки).
- **Версии shared-зависимостей** превращаются в постоянную операционную заботу (глава 11 целиком об этом).
- **Сквозной UX** — роутинг, авторизация, дизайн-система, аналитика — должен работать поверх независимо деплоящихся частей; это архитектурная работа, которой при монолитной сборке просто нет.
- **Инфраструктура**: N артефактов, N деплоев, матрица совместимости версий "какой catalog совместим с каким shell".

### Механика Module Federation: host, remote, container

Module Federation — фича бандлера (родилась в webpack 5), позволяющая приложению **в рантайме** загружать модули из других, отдельно собранных и отдельно задеплоенных приложений.

```
       ┌──────────────────────────────┐
       │ shell (host)                 │
       │ роутер, layout, auth,        │
       │ адреса remoteEntry remote-ов │
       └──────────────────────────────┘
загружает В РАНТАЙМЕ, в браузере пользователя
                      ▼
┌──────────────────┐    ┌───────────────────┐
│ catalog (remote) │    │ checkout (remote) │
│ exposes:         │    │ exposes:          │
│ ./CatalogPage    │    │ ./CheckoutPage    │
└──────────────────┘    └───────────────────┘
```

Словарь:

- **Remote** — приложение, которое *экспонирует* модули наружу (`exposes: { './CatalogPage': './src/...' }`). Собирается в обычные чанки плюс особый файл — **remoteEntry.js**: маленький манифест-контейнер со списком экспонируемых модулей и деклараций shared-зависимостей. Не путайте: remoteEntry — это оглавление, а не сам код; код приезжает чанками по требованию.
- **Host** — приложение, которое знает адреса remoteEntry своих remote-ов и загружает их модули в рантайме.
- **Container** — JS-объект, которым remote представляется миру. У него два метода: `init(sharedScope)` — "вот общий скоуп зависимостей, вклинься" и `get(moduleName)` — "дай фабрику модуля". Всё Module Federation API — это, по сути, эти два вызова.

Полная последовательность загрузки (это ядро главы — прочитайте диаграмму дважды):

```
┌──────────────────────────────────────────────────────┐
│ браузер грузит shell (host):                         │
│ свой бандл + список адресов remoteEntry              │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ host скачивает remoteEntry.js каталога —             │
│ маленький манифест контейнера, не весь бандл         │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ container.init(sharedScope):                         │
│ host и remote объявляют версии react, react-dom, ... │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ shared negotiation: на каждую зависимость            │
│ выбирается ОДИН совместимый экземпляр                │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ container.get("./CatalogPage") →                     │
│ догружаются чанки модуля каталога                    │
└──────────────────────────────────────────────────────┘
                            │
                            ▼
┌──────────────────────────────────────────────────────┐
│ CatalogPage рендерится в дереве host-а               │
│ тем самым, согласованным, react-ом                   │
└──────────────────────────────────────────────────────┘
```

### Shared dependencies: singleton, strictVersion, eager

Если бы каждый remote возил свой react, страница с тремя remote-ами загружала бы React четырежды — и это ещё не худшее (см. вопрос 4 в конце). Поэтому зависимости декларируются как **shared**: при `init` каждая сторона говорит "мне нужен react ^18.2, могу предоставить 18.3.1", и в shared scope выбирается один экземпляр, удовлетворяющий всех.

Три флага, управляющих согласованием:

- **`singleton: true`** — экземпляр может быть только один, даже если версии формально несовместимы (тогда warning и берётся уже загруженная). Обязателен для react, react-dom, роутера, любых библиотек с глобальным состоянием или Context.
- **`strictVersion: true`** — при несовместимости версий не warning, а ошибка в рантайме. Жёстко, зато несовместимость видна сразу, а не через сломанный хук в проде.
- **`eager: true`** — зависимость кладётся в начальный бандл, а не грузится асинхронно. Нужен на стороне host для самых базовых зависимостей; связан с классической ошибкой "Shared module is not available for eager consumption", которую мы намеренно воспроизведём в главе 11.

### Runtime- против build-time-композиции

Ключевой сдвиг в голове: до сих пор `import { CatalogPage } from '@mini-shop/catalog-feature'` разрешался **на этапе сборки** — код каталога компилировался внутрь бандла shell, версия зафиксирована навсегда, деплой один. С MF модуль каталога разрешается **в браузере пользователя**: shell узнаёт, какой там CatalogPage, только в момент загрузки. Отсюда и суперсила (задеплоил catalog — все пользователи получили новый каталог без пересборки shell), и вся цена (никто на этапе сборки не проверил, что новый catalog совместим со старым shell).

### Альтернативы, о которых надо знать

- **Build-time композиция** (наш текущий mini-shop): импорты в монорепо, один артефакт, один деплой. Выбор по умолчанию.
- **SPA-композиция маршрутами**: `/catalog` и `/checkout` — разные приложения за реверс-прокси; переход между ними — полная перезагрузка страницы. Дёшево, надёжно, независимый деплой есть; жертвуете бесшовным SPA-UX и общим состоянием.
- **iframe**: максимальная изоляция (стили, JS, сбои), встраивание чужого/легаси; цена — коммуникация через postMessage, дубли зависимостей, мучения с роутингом, модалками и высотой. Недооценён для админок и виджетов.
- **single-spa**: оркестратор жизненного цикла нескольких SPA на одной странице; отвечает на вопрос "когда монтировать", тогда как MF — на вопрос "откуда взять код". Их иногда используют вместе.

Правило выбора: не нужен независимый деплой → build-time; нужен на уровне *страниц* → SPA-композиция; нужен внутри одной страницы и единый SPA-UX → Module Federation.

> **Версии.** MF родился в webpack 5; Nx умеет собирать федерацию и webpack-ом, и rspack-ом (Rust-реализация, заметно быстрее — свежие версии Nx предлагают его по умолчанию). Для vite федерация — сторонние плагины вне основной поддержки Nx: поэтому в главе 10 наши MF-приложения будут не на vite, как shell до сих пор, а на webpack/rspack. Современные версии Nx используют Module Federation 2.0 (`@module-federation/enhanced`) — с рантайм-плагинами и генерацией типов между host и remote; в старых репах — "родной" webpack ModuleFederationPlugin без этого.

## В рабочем монорепо

- `find . -name "module-federation.config.*" -not -path '*/node_modules/*'` — кто host, кто remote: у host в конфиге `remotes: [...]`, у remote — `exposes: {...}`.
- Откройте прод вашего продукта → Network tab → фильтр "remoteEntry": сколько remote-ов реально грузится, откуда (домены/CDN), что в waterfall после каждого remoteEntry.
- `curl -s https://<прод>/catalog/remoteEntry.js | head -c 400` — remoteEntry читаем: в начале видны имя контейнера и карта модулей.
- В shared-конфиге проверьте react: есть ли `singleton: true` (его отсутствие — бомба замедленного действия, глава 11).
- Главный аудит: деплоятся ли remote-ы *реально* независимо? Если CI собирает и катит всё вместе — команда платит полную цену MF, не получая единственной выгоды (это типовая "археологическая находка" главы 14).

## Что добавляем в проект

Ничего — глава подготовительная. В главе 10 mini-shop станет федерацией: shell превратится в host, появятся remote-ы catalog и checkout, и всё из этой главы станет строчками конфигов.

## Разбор решения

**1. Выбор архитектуры.**

- (а) **Build-time** (монорепо, как наш mini-shop сейчас). Одна команда — некому деплоиться независимо; MF добавил бы всю свою цену ради решения несуществующей проблемы.
- (б) **Module Federation**. Много команд, свои релизные циклы, единый SPA-UX (SPA-композиция с перезагрузками не проходит по требованиям). Это точно профиль MF; монорепо при этом остаётся — MF и монорепо не конкуренты, а слои (глава 10 покажет это буквально).
- (в) **iframe**. Чужой произвольный код на вашей странице — вопрос изоляции и безопасности, а не композиции модулей: MF исполняет remote в общем JS-контексте, что для недоверенного кода неприемлемо.

**2. Чтение схемы.**

- Недоступный remoteEntry — это отказ на шаге 2: `container` не создастся, `get()` не у кого звать. Без защиты падает весь host. Защита живёт на границе загрузки модуля: динамический `import()` remote-модуля оборачивается в error boundary + fallback UI ("Каталог временно недоступен"), и роут каталога деградирует, не убивая приложение. Это архитектурное следствие runtime-композиции: у build-time такой ошибки не существует в принципе.
- `singleton: true` без strictVersion: в shared scope останется один react — тот, что загружен первым (react host-а, 18.3); в консоль упадёт warning о несовместимости, и catalog, собранный против API react 19, будет исполняться на 18.3 — может работать, а может сломаться на первом использовании API, которого в 18.3 нет. Со `strictVersion: true` — немедленная ошибка в рантайме на шаге negotiation: жёстче, но честнее, чем "authService is undefined" где-то в глубине.

**3. Проектирование mini-shop** (это станет конфигами главы 10):

- catalog экспонирует `./CatalogPage`, checkout — `./CheckoutPage`: **страница/роут — правильная гранулярность** экспонирования; экспонировать десятки мелких компонентов = превратить remote в "npm-пакет с доставкой по HTTP" и утонуть в матрице совместимости.
- shared: `react` и `react-dom` — `singleton: true` обязательно; роутер (когда появится) — тоже singleton: у приложения одна история навигации.
- Роутинг и layout — в host: это и есть его работа (композиция + сквозной UX). Дизайн-система (shared-ui) — воркспейсная либа, разделяемая между remote-ами; как именно она ведёт себя в федерации — центральный сюжет главы 11.

**Edge cases.**

- Разные мажоры дизайн-системы у двух remote-ов negotiation переживёт (не singleton — каждый привезёт свою), стили и UX — нет: пользователь увидит два визуальных языка на одной странице. Проблема организационная, решается управлением версиями и дисциплиной обновлений, а не флагами webpack.
- Внутреннее состояние remote-а (фильтры каталога) — его личное дело, хоть Redux, хоть zustand. Общее состояние (корзина, юзер) — контракт уровня приложения: либо host предоставляет его через shared singleton-либу с событиями, либо через явный API (props/callbacks в экспонируемый модуль). Правило то же, что в главе 06: общее — в shared, и это осознанный контракт, а не "remote залез в window".
- SSR + MF возможен (федерация на сервере), но сложность возрастает на порядок: рендерить надо согласованные версии на сервере и клиенте. Честный ответ: если SEO/SSR критичны, серьёзно рассмотрите SPA-композицию по страницам или build-time — прежде чем тащить федерацию на сервер.

<summary>Ответы</summary>

1. Независимый деплой независимыми командами: возможность выкатить свою часть UI, не собирая и не координируя релиз остальных. Шаринг кода решается монорепо/пакетами без единого рантайм-риска — если вам нужен только он, MF даёт всю цену runtime-интеграции взамен уже решённой задачи.
2. remoteEntry.js — манифест контейнера remote-а: имя, карта exposes-модулей, декларации shared. Маленький, потому что не содержит код модулей — только оглавление и загрузчик; сам код приезжает чанками по требованию. `init(sharedScope)` — remote встраивается в общий скоуп зависимостей (объявляет свои версии и узнаёт чужие); `get(name)` — возвращает фабрику экспонированного модуля, попутно догружая его чанки.
3. При `init` каждая сторона кладёт в shared scope записи "пакет → версия, которую могу предоставить + диапазон, который требую". На каждый пакет выбирается экземпляр, удовлетворяющий требованиям (обычно старшая совместимая из предоставленных). `singleton` форсирует единственный экземпляр даже при конфликте (warning + берётся уже загруженный); `strictVersion` превращает конфликт из warning в ошибку; `eager` кладёт зависимость в начальный бандл, убирая асинхронную загрузку (и создавая требование async boundary у потребителей — глава 11).
4. React хранит глобальное для экземпляра состояние: (а) hooks-диспетчер — компонент, отрендеренный "чужим" react-ом, вызывает хуки не на том диспетчере → "Invalid hook call"; (б) Context — `createContext` из экземпляра A и `useContext` из экземпляра B — это разные объекты, провайдер "не виден"; (в) два ReactDOM спорят за события и reconciliation. Одинаковость версий не спасает: проблема в двух копиях модуля с раздельным состоянием, поэтому react — всегда `singleton: true`.
5. Совместимость контрактов: сигнатуры и типы экспонируемых модулей (host собирается, не видя реального кода remote-а), совместимость версий shared, само существование модуля по адресу. Компенсируют: генерацией и проверкой типов между host и remote (MF 2.0, глава 11), контрактными/e2e-тестами связки, канареечными деплоями remote-ов, error boundaries + fallback на каждой точке подключения remote-а.

## Частая ошибка

Разработчик из single-app мира приносит в MF-проект ментальную модель npm-пакета: "catalog — это зависимость shell, значит, её версия зафиксирована где-то в lock-файле, и пока я не подниму версию, ничего не изменится". С Module Federation это неверно в самом главном: remote приезжает в рантайме, и его "версия" — это **то, что сейчас лежит на CDN**, а не то, что было при сборке host. Отсюда классическое недоумение: "мы ничего не деплоили, а прод сломался" — сломался, потому что соседняя команда задеплоила свой remote. Диагностика таких инцидентов начинается не с git log своей репы, а с вопроса "кто и что деплоил за последний час" — и это фундаментальный сдвиг по сравнению с монолитом.

Вторая ошибка — тащить MF туда, где деплоит одна команда, "потому что современно" или "чтобы сборка была быстрее". Скорость сборки решают кеш и affected (главы 04–05), независимый деплой одной команде не нужен — остаётся чистая цена: рантайм-риски, негласные контракты, инфраструктура на N артефактов. Микрофронтенды — организационный инструмент под организационную проблему; если проблемы нет, лучший MF — это его отсутствие.
