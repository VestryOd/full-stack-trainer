# Директивы и пайпы

## Теория

### Директива — это компонент без шаблона

Технически компонент и есть директива, у которой появился шаблон. Всё остальное — селектор, `host`, `input()`/`output()`, DI, хуки жизненного цикла — общее. Отсюда простой критерий выбора: **нужна своя разметка — компонент; нужно поведение на уже существующем элементе — директива**.

```ts
@Directive({
  // атрибутный селектор: директива цепляется к чужому элементу,
  // ничего не добавляя в разметку
  selector: '[appOverdue]',
  host: {
    '[class.is-overdue]': 'isOverdue()',
    '[attr.title]': 'isOverdue() ? "Past SLA" : null',
  },
})
export class OverdueDirective {
  readonly ticket = input.required<Ticket>({ alias: 'appOverdue' });
  protected readonly isOverdue = computed(() => /* … */);
}
```

Селектор может сужать применимость: `'button[appPrimary]'` сработает только на `button`, `'[appOverdue]:not([disabled])'` — исключит отключённые элементы. Это дешёвый способ встроить ограничение в саму директиву.

### Структурные директивы и звёздочка

```
        Во что превращается звёздочка
┌────────────────────────────────────────────┐
│ в шаблоне                                  │
│ <li *appRepeat="3">строка</li>             │
└────────────────────────────────────────────┘
                       │  компилятор
                       ▼
┌────────────────────────────────────────────┐
│ разворачивается в ng-template              │
│ <ng-template appRepeat [appRepeat]="3">    │
│   <li>строка</li>                          │
│ </ng-template>                             │
└────────────────────────────────────────────┘
                       │  DI
                       ▼
┌────────────────────────────────────────────┐
│ директива получает две зависимости         │
│ TemplateRef  — что рендерить               │
│ ViewContainerRef — куда рендерить          │
└────────────────────────────────────────────┘
                       │  рантайм
                       ▼
┌────────────────────────────────────────────┐
│ директива сама решает, сколько раз и когда │
│ vcr.createEmbeddedView(tpl, context)       │
│ vcr.clear()                                │
└────────────────────────────────────────────┘
@if/@for — те же встроенные view, но без директивы-посредника:
блоки компилируются напрямую и потому дешевле
```

Звёздочка — синтаксический сахар: компилятор оборачивает элемент в `<ng-template>` и вешает директиву на него. Директива получает `TemplateRef` (что рендерить) и `ViewContainerRef` (куда), после чего **сама решает**, создавать ли view, сколько раз и с каким контекстом. Именно так работали `*ngIf` и `*ngFor`: `*ngIf` вызывал `createEmbeddedView()`/`clear()`, `*ngFor` создавал по view на элемент и переиспользовал их по `trackBy`.

Контекст передаётся объектом; ключ `$implicit` становится значением по умолчанию для `let`:

```ts
this.vcr.createEmbeddedView(this.tpl, { $implicit: item, index: i });
// в шаблоне: *appRepeat="items; let item; let i = index"
```

Для типизации контекста существуют `ngTemplateContextGuard` (описывает тип контекста) и `ngTemplateGuard_<input>` (сужает тип по условию) — без них `strictTemplates` не сможет вывести типы внутри шаблона.

Нужны ли свои структурные директивы сегодня? Официальная позиция: для условий и списков — встроенный control flow, а структурная директива пишется, «когда нужно переиспользуемое поведение рендеринга, которого control flow не покрывает». Реальные примеры: рендер по разрешению пользователя (`*appHasRole="'admin'"`), lazy-обёртки, отображение с задержкой, повтор с особой семантикой.

### hostDirectives: композиция поведения

Наследование компонентов в Angular возможно, но быстро становится неуправляемым. Композиция решает ту же задачу лучше:

```ts
@Component({
  selector: 'app-ticket-card',
  hostDirectives: [
    HighlightOnHover,            // поведение целиком приватно
    {
      directive: OverdueDirective,
      inputs: ['appOverdue: ticket'],   // проброс входа с переименованием
      outputs: ['overdueChange'],
    },
  ],
})
export class TicketCard {}
```

Что важно знать:

- Директивы применяются **статически на этапе компиляции** — добавить их в рантайме нельзя.
- По умолчанию входы и выходы host-директивы **приватны**: снаружи их не видно, пока вы явно не перечислите их в `inputs`/`outputs` (можно с алиасом).
- Селектор host-директивы игнорируется — она применяется по факту перечисления.
- Конструкторы, хуки и биндинги host-директив выполняются **до** самого компонента, а директивы могут применять `hostDirectives` к другим директивам, образуя цепочки.
- Компонент и его host-директивы могут инжектить друг друга — это штатный способ обмена состоянием между ними.

Готовый пример такого подхода в самом фреймворке — `@angular/aria` (стабилен с v22): набор директив, закрывающих ARIA-атрибуты, клавиатурную навигацию и управление фокусом, чтобы это не переписывали в каждом проекте.

### Пайпы: чистые и нечистые

```
                        Цена вычисления в шаблоне
┌──────────────────────────────┬──────────────────────────────────┬─────┐
│ в шаблоне                    │ когда выполняется                │ кеш │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ чистый пайп, вход — примитив │ при изменении значения           │ да  │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ чистый пайп, вход — объект   │ при смене ССЫЛКИ, не мутации     │ да  │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ impure-пайп (pure: false)    │ при каждой проверке шаблона      │ нет │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ async, keyValue, slice, json │ при каждой проверке (они impure) │ нет │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ метод класса {{ f(x) }}      │ при каждой проверке шаблона      │ нет │
├──────────────────────────────┼──────────────────────────────────┼─────┤
│ computed в классе            │ при изменении зависимостей       │ да  │
└──────────────────────────────┴──────────────────────────────────┴─────┘
         встроенные date, currency, decimal, uppercase — чистые;
          async вдобавок сам зовёт markForCheck при каждом emit
```

Пайп — это класс с методом `transform` и именем, под которым он виден в шаблоне. По умолчанию пайп **чистый**: результат кешируется и пересчитывается только при изменении примитива или **ссылки** на объект. Отсюда две вещи, которые нужно принять сразу:

1. Мутация массива, переданного в чистый пайп, не приведёт к пересчёту — та же история, что с `OnPush` и сигналами (главы 02–03).
2. `pure: false` снимает кеш полностью: пайп вызывается при каждой проверке шаблона. Документация формулирует прямо — избегать, если нет крайней необходимости.

Из встроенных `pure: false` объявлены `async`, `keyValue`, `slice` и `json`; `date`, `currency`, `decimal`, `percent`, `uppercase` — чистые. `AsyncPipe` вдобавок вызывает `markForCheck()` на каждый emit — благодаря этому старый код на `| async` пережил переход на zoneless (глава 03).

Пайпы участвуют в DI: внутри `transform` можно использовать `inject()` (так работает `DatePipe` с локалью). Но обратное документация не рекомендует: не инжектить класс пайпа в сервис, чтобы позвать его `transform` — если логика нужна вне шаблона, она должна быть обычной функцией, которую пайп только оборачивает.

### Что выбрать

```
┌────────────────────────────────────┬───────────────────────┬─────────────────────────────┐
│ что нужно                          │ инструмент            │ признак выбора              │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ своя разметка и своё состояние     │ компонент             │ есть шаблон                 │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ поведение на чужом элементе        │ атрибутная директива  │ разметку не добавляем       │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ решать, рендерить ли и сколько раз │ структурная директива │ нужен TemplateRef           │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ преобразовать значение для вывода  │ пайп                  │ чистая функция от входа     │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ производное значение компонента    │ computed              │ зависит от сигналов         │
├────────────────────────────────────┼───────────────────────┼─────────────────────────────┤
│ набор поведений на компоненте      │ hostDirectives        │ композиция без наследования │
└────────────────────────────────────┴───────────────────────┴─────────────────────────────┘
```

Практическое правило: **пайп — для представления, `computed` — для данных**. Формат даты, склонение, единицы измерения — пайп: он не зависит от состояния компонента и переиспользуется где угодно. Отфильтрованный список, агрегат, флаг «просрочен» — `computed`: он привязан к состоянию и должен мемоизироваться по сигналам. Пайп, фильтрующий массив (`| filterBy`), — классический антипаттерн: чистым он не увидит мутаций, а нечистым будет отрабатывать на каждой проверке.

## Параллели с React

- **Директивы — то, чего в React нет.** В React поведение на чужом элементе оформляют либо хуком (`useHover`, `useClickOutside`), который возвращает пропсы для навешивания вручную, либо компонентом-обёрткой, добавляющей узел в DOM. Директива не добавляет узлов и подключается атрибутом — ближе к «миксину для элемента», чем к любому React-приёму.
- **`hostDirectives` против HOC и композиции хуков.** HOC оборачивает компонент новым слоем в дереве; композиция хуков требует ручного вызова внутри тела. `hostDirectives` подключает поведение к хост-элементу декларативно, без лишних узлов и без изменения тела компонента — при этом входы по умолчанию приватны, то есть API компонента не расширяется случайно.
- **Пайп против функции в JSX.** В JSX вы просто вызываете `formatDate(x)` — и это нормально, потому что тело компонента исполняется ограниченное число раз. В Angular функция в шаблоне исполняется на каждой проверке и не кешируется; чистый пайп кеширует по входу. Это не стилистика, а разница в стоимости.
- **Структурная директива против условного рендера.** `{cond && <X/>}` — обычное выражение JS: React вычисляет обе ветки как значения и решает по результату. Структурная директива получает **шаблон**, а не результат: тело не вычисляется, пока директива не создаст view. Отсюда возможность отрендерить его ноль раз, пять раз или отложенно — без пересборки самого выражения.
- **Где ломается привычка:** попытка перенести «утилиту в JSX» на пайп с фильтрацией списка. В React `{items.filter(f).map(...)}` предсказуемо; в Angular `| filterBy` заставляет выбирать между «не увидит мутаций» (pure) и «выполняется всегда» (impure). Правильный ответ — вообще не фильтровать в шаблоне: фильтрация живёт в `computed` (глава 02).

## Что увидишь в legacy-коде

- **`*ngIf` / `*ngFor` / `[ngSwitch]`** и `CommonModule` в `imports`. Это ровно те структурные директивы, механику которых описывает диаграмма выше; новый control flow делает то же самое без директив-посредников.
- **`*ngIf="user$ | async as user; else loading"`** с `<ng-template #loading>` — классическая связка «impure-пайп + структурная директива», заменяемая на `@if` с сигналом.
- **`@HostBinding('class.active')` и `@HostListener('mouseenter')`** в директивах вместо объекта `host` (глава 01). В директивах это встречается даже чаще, чем в компонентах.
- **Наследование поведения:** `export class TicketCard extends BaseHighlightComponent` — то, ради чего появились `hostDirectives`. Признак: базовый класс с `@Directive()`-декоратором без селектора, от которого наследуются компоненты.
- **Пайпы-фильтры:** `*ngFor="let t of tickets | filterByStatus: status | orderBy: 'date'"` с `pure: false`. Такой код одновременно и тормозит, и создаёт новые массивы на каждой проверке, ломая `trackBy`.
- **`constructor(private el: ElementRef, private renderer: Renderer2)`** и ручные `renderer.addClass(...)` вместо host-биндингов — так писали директивы до того, как биндинги стали декларативными.

## Что добавляем в проект

Карточка тикета получает директиву подсветки просроченных (класс и `title` на хост-элементе, без изменения разметки) и пайп форматирования SLA, который превращает часы в человекочитаемое «2h left» / «overdue by 3h». Плюс `hostDirectives` — подключаем поведение к карточке без наследования.

## Практическое задание

**Вход:** проект из главы 05 (два стора, компоненты без состояния).
**Выход:** директива, пайп и композиция поведения через `hostDirectives`.

Требования:

1. Пайп `slaRemaining`: принимает тикет (или `createdAt` + `slaHours`) и текущее время, возвращает строку вида `2h left`, `30m left`, `overdue by 3h`, `no SLA`. Пайп должен быть чистым — продумайте, как это возможно, если результат зависит от «сейчас» (подсказка: «сейчас» может быть входом).
2. Директива `appOverdue`: вешает класс и `aria`-атрибут на элемент, если SLA нарушен. Никакого `ElementRef`/`Renderer2` — только объект `host` и сигналы. Вход принимает через `input.required()` с алиасом, чтобы писалось `[appOverdue]="ticket"`.
3. Подключите директиву к карточке двумя способами: через атрибут в шаблоне списка и через `hostDirectives` в самой карточке. Сравните: где какой вариант уместнее и что происходит с входами во втором случае.
4. Структурная директива `*appHasRole="'admin'"`: рендерит содержимое, только если у текущего пользователя есть роль (роль пока берите из `APP_CONFIG` или заглушки-сервиса — авторизация будет в главе 07). Реализуйте через `TemplateRef` + `ViewContainerRef`, добавьте `ngTemplateGuard`/контекст по необходимости.
5. Измерение цены: сделайте временный impure-пайп, который пишет в консоль при каждом вызове, и посмотрите, сколько раз он отрабатывает при вводе в поиск. Затем замените на чистый и сравните.
6. Ограничение: никакой фильтрации и сортировки в пайпах.

Edge cases на подумать:

- Чистый пайп получает объект тикета. Что произойдёт, если тикет обновится через `update(id, patch)` в сторе, и почему?
- Директива навешена на элемент внутри `@if`. Когда сработает её конструктор и когда — уничтожение?
- В `hostDirectives` вход не перечислен в `inputs`. Как передать в него значение и почему так сделано по умолчанию?
- `*appHasRole` внутри `@for`: сколько инстансов директивы будет создано и что произойдёт при изменении списка?
- Почему `{{ ticket.createdAt | date: 'short' }}` дешевле, чем `{{ formatDate(ticket.createdAt) }}`, хотя обе строки выглядят одинаково?

## Разбор решения

`src/app/tickets/sla-remaining-pipe.ts`:

```ts
import { Pipe, PipeTransform } from '@angular/core';
import { Ticket } from './ticket';

@Pipe({
  name: 'slaRemaining',
  // pure по умолчанию — оставляем. Чистота возможна потому, что
  // "сейчас" передаётся аргументом: пайп остаётся функцией от входов
})
export class SlaRemainingPipe implements PipeTransform {
  transform(ticket: Ticket, now: number): string {
    if (ticket.slaHours === undefined) return 'no SLA';

    const deadline = new Date(ticket.createdAt).getTime() + ticket.slaHours * 3_600_000;
    const diffMinutes = Math.round((deadline - now) / 60_000);

    if (diffMinutes < 0) return `overdue by ${formatSpan(-diffMinutes)}`;
    return `${formatSpan(diffMinutes)} left`;
  }
}

// Логика вынесена в обычную функцию: если то же форматирование понадобится
// в сервисе или в тесте, вызывать надо её, а не инжектить класс пайпа
function formatSpan(minutes: number): string {
  if (minutes < 60) return `${minutes}m`;
  return `${Math.round(minutes / 60)}h`;
}
```

`src/app/tickets/overdue-directive.ts`:

```ts
import { Directive, computed, input } from '@angular/core';
import { Ticket } from './ticket';

@Directive({
  // атрибутный селектор: директива не добавляет ни одного узла в DOM
  selector: '[appOverdue]',
  host: {
    '[class.is-overdue]': 'isOverdue()',
    '[class.is-at-risk]': 'isAtRisk()',
    // атрибут, а не свойство: у title есть DOM-свойство, но null здесь
    // должен УБИРАТЬ атрибут, а это умеет только [attr.] (глава 01)
    '[attr.data-sla-state]': 'state()',
  },
})
export class OverdueDirective {
  // alias позволяет писать [appOverdue]="ticket" — имя входа совпадает
  // с именем селектора, как в *ngIf/*ngFor
  readonly ticket = input.required<Ticket>({ alias: 'appOverdue' });
  readonly now = input(Date.now());

  private readonly minutesLeft = computed(() => {
    const { createdAt, slaHours } = this.ticket();
    if (slaHours === undefined) return null;
    const deadline = new Date(createdAt).getTime() + slaHours * 3_600_000;
    return Math.round((deadline - this.now()) / 60_000);
  });

  protected readonly isOverdue = computed(() => (this.minutesLeft() ?? 1) < 0);
  protected readonly isAtRisk = computed(() => {
    const left = this.minutesLeft();
    return left !== null && left >= 0 && left < 60;
  });
  protected readonly state = computed(() =>
    this.minutesLeft() === null ? null : this.isOverdue() ? 'overdue' : 'ok',
  );
}
```

Подключение первым способом — атрибутом в шаблоне списка:

```html
@for (ticket of board.filtered(); track ticket.id) {
  <li [appOverdue]="ticket" [now]="now()">
    <app-ticket-card [ticket]="ticket" />
  </li>
}
```

Вторым — композицией в самой карточке:

```ts
@Component({
  selector: 'app-ticket-card',
  imports: [DatePipe, SlaRemainingPipe],
  // Поведение подключается к хост-элементу карточки. Инстанс директивы
  // создаётся раньше компонента, поэтому её биндинги применяются первыми
  hostDirectives: [
    {
      directive: OverdueDirective,
      // без этой строки вход остался бы приватным: снаружи [appOverdue]
      // писать было бы нельзя. Здесь мы прокидываем его под именем ticket,
      // то есть [ticket]="…" на карточке кормит и компонент, и директиву
      inputs: ['appOverdue: ticket'],
    },
  ],
  templateUrl: './ticket-card.html',
  styleUrl: './ticket-card.css',
})
export class TicketCard {
  readonly ticket = input.required<Ticket>();
  protected readonly now = input(Date.now());
}
```

`src/app/core/has-role-directive.ts` — структурная директива:

```ts
import { Directive, TemplateRef, ViewContainerRef, effect, inject, input } from '@angular/core';
import { CurrentUser } from './current-user';

@Directive({ selector: '[appHasRole]' })
export class HasRoleDirective {
  // TemplateRef — содержимое, обёрнутое компилятором в <ng-template>
  private readonly tpl = inject(TemplateRef<unknown>);
  // ViewContainerRef — место в DOM, куда это содержимое можно вставить
  private readonly vcr = inject(ViewContainerRef);
  private readonly user = inject(CurrentUser);

  readonly role = input.required<string>({ alias: 'appHasRole' });

  constructor() {
    // Здесь effect уместен: результат — не значение, а императивное
    // действие над view-контейнером (глава 02)
    effect(() => {
      const allowed = this.user.roles().includes(this.role());
      this.vcr.clear();
      if (allowed) this.vcr.createEmbeddedView(this.tpl);
    });
  }

  // Подсказка компилятору о типе контекста: без неё strictTemplates
  // не сможет проверить выражения внутри шаблона
  static ngTemplateContextGuard(_dir: HasRoleDirective, _ctx: unknown): _ctx is object {
    return true;
  }
}
```

Использование:

```html
<button type="button" *appHasRole="'admin'" (click)="tickets.reset()">
  Reset demo data
</button>
```

Ответы на edge cases:

- `update(id, patch)` создаёт **новый объект** тикета (`{ ...ticket, ...patch }`), поэтому ссылка меняется и чистый пайп пересчитается. Если бы стор мутировал объект на месте, пайп вернул бы закешированное значение — и это одна из причин, по которой иммутабельность в сторе не «идеология», а условие работы остальных механизмов.
- Конструктор директивы сработает в момент создания view — то есть когда `@if` впервые станет истинным. При переключении условия в `false` встроенный view уничтожается вместе с директивой (сработает `ngOnDestroy` и `DestroyRef.onDestroy`), а при обратном переключении будет создан **новый** инстанс. Состояние директивы между этими циклами не сохраняется.
- Никак не передать: неперечисленные входы host-директивы приватны и снаружи не видны. Так сделано, чтобы подключение поведения не расширяло публичный API компонента случайно: автор компонента решает, какие входы вынести наружу и под каким именем (`'appOverdue: ticket'`).
- По инстансу директивы на каждый элемент списка — каждая со своим `TemplateRef` и своим встроенным view. При изменении списка `@for` переиспользует view по `track`: для оставшихся элементов директивы сохранятся, для удалённых будут уничтожены, для добавленных — созданы.
- `date` — чистый пайп: результат кешируется по входному значению и пересчитывается только при его изменении. Метод класса кеша не имеет вовсе и вызывается при каждой проверке шаблона — а сколько будет проверок, решает change detection, а не вы (глава 03). Внешне строки похожи, но первая — это «вычислить один раз на новое значение», вторая — «вычислять всегда».

## Проверь себя

1. Объясните своими словами, что получает структурная директива вместо готового результата выражения и какие возможности это ей даёт.
2. Почему чистый пайп не увидит мутацию массива, и почему `pure: false` — плохое решение этой проблемы?
3. Чем `hostDirectives` лучше наследования компонента и почему входы host-директивы по умолчанию приватны?
4. По какому признаку вы выбираете между пайпом и `computed` для одного и того же преобразования?
5. Директива навешивает класс. Почему это делается через объект `host`, а не через `ElementRef` + `Renderer2`, и что вы теряете во втором случае?

<details>
<summary>Ответы</summary>

1. Структурная директива получает `TemplateRef` — «рецепт» разметки, ещё не превращённый в DOM, — и `ViewContainerRef`, место, куда его можно вставить. Тело шаблона не вычисляется, пока директива не позовёт `createEmbeddedView()`. Это даёт три возможности, недоступные обычному выражению: не рендерить вовсе (и не платить за создание узлов), рендерить несколько раз с разным контекстом (`$implicit`, индекс), и рендерить отложенно — по событию, разрешению или загрузке. Плюс директива управляет уничтожением: `clear()` уничтожает view вместе со всеми вложенными компонентами и их состоянием.
2. Чистый пайп пересчитывается, только когда меняется примитивное значение или **ссылка** на объект. Мутация массива оставляет ссылку прежней, значит вход «не изменился» и вернётся кеш. `pure: false` действительно решает симптом — пайп начнёт выполняться всегда, — но ценой полного отказа от кеша: он будет вызываться на каждой проверке шаблона, для каждого элемента, где он написан, а число проверок определяется change detection. Правильное решение — не мутировать: обновлять данные иммутабельно, тогда чистый пайп увидит новую ссылку.
3. Наследование связывает компоненты жёстко: одна цепочка, конфликты имён, невозможность подключить два поведения сразу, а базовый класс со временем обрастает логикой для всех наследников. `hostDirectives` — композиция: можно подключить несколько независимых поведений, каждое со своим состоянием и жизненным циклом, не меняя тела компонента и не добавляя узлов в DOM. Входы приватны по умолчанию потому, что подключение поведения не должно молча расширять публичный API компонента: автор явно решает, какие входы вынести наружу и под каким именем — иначе внутренняя деталь реализации стала бы частью контракта.
4. Критерий — от чего зависит преобразование. Если это чистая функция от значения (формат даты, единицы, склонение), она не связана с состоянием компонента, переиспользуется в любом шаблоне и естественно ложится на пайп с его кешем по входу. Если результат зависит от состояния (фильтры, выбор, агрегаты по списку), это `computed`: он мемоизируется по сигналам-зависимостям, пересчитывается ровно при их изменении и остаётся тестируемым без шаблона. Признак ошибки — пайп, которому нужно передать три-четыре аргумента состояния: это `computed`, притворяющийся пайпом.
5. Объект `host` — декларативный биндинг: Angular сам применяет и снимает класс при изменении выражения, участвует в change detection и корректно ведёт себя при конфликте биндингов. `ElementRef` + `Renderer2` — императивная запись: вы должны сами решить, когда обновлять, сами снимать класс при смене условия и сами следить за жизненным циклом, а прямой доступ к нативному элементу вдобавок ломает переносимость (SSR и не-DOM-платформы) и открывает путь к XSS при работе с содержимым. Практический итог: код длиннее, поведение при переключениях менее предсказуемо, а тестировать приходится через реальный DOM.

</details>

## Частая ошибка

Первая — пайп вместо `computed` для фильтрации и сортировки. Соблазн понятен: в React `{items.filter(f)}` пишется прямо в разметке, и хочется сделать «то же самое, но по-ангуляровски». Итог — `| filterBy: status | orderBy: 'date'`, который либо не увидит изменений (чистый пайп кеширует по ссылке), либо станет `pure: false` и начнёт выполняться на каждой проверке шаблона. Хуже того, такой пайп возвращает **новый массив** при каждом вызове, поэтому `@for` получает новую коллекцию и вынужден заново сопоставлять элементы по `track` — та самая лишняя работа, которую `track` должен предотвращать (глава 01). Правило: пайп форматирует одно значение; всё, что фильтрует, сортирует и агрегирует, живёт в `computed`.

Вторая — директива, которая лезет в DOM руками. Пришедший из React разработчик по аналогии с `ref` берёт `ElementRef` и начинает писать `nativeElement.classList.add(...)`, `nativeElement.style.color = ...`, а в тяжёлых случаях и `innerHTML`. Это работает ровно до первого изменения условия: снимать класс придётся вручную, а при переключении веток состояние DOM разъедется с состоянием данных. Плюс прямой доступ к `nativeElement` ломает рендеринг вне браузера (SSR — глава 15) и, в случае `innerHTML`, обходит встроенную санитизацию. Практически всё, что нужно от директивы, выражается декларативно: `[class.x]`, `[style.y]`, `[attr.z]` и `(event)` в объекте `host` — а редкие исключения (измерения, фокус, интеграция со сторонним виджетом) делаются в `afterRenderEffect` (глава 03).
