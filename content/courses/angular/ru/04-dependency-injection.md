# Dependency injection

## Теория

### Инжектор, токен, провайдер

DI (dependency injection, внедрение зависимостей) в Angular — не паттерн из книжки, а работающий контейнер внутри фреймворка. Три понятия:

- **Токен** — ключ, по которому запрашивают зависимость. Обычно это класс (`TicketService`), но может быть `InjectionToken<T>` для всего, что не класс.
- **Провайдер** — рецепт, как получить значение для токена.
- **Инжектор** — контейнер, который хранит провайдеры, создаёт значения по первому запросу и кеширует их.

DI стоит той сложности, которую добавляет. Он даёт три вещи:

- **Подменяемость.** В тестах вместо HTTP-сервиса подставляется мок, и мокать модули не нужно.
- **Область жизни.** Один инстанс на приложение, на маршрут или на компонент. Это решает конфигурация, а не код сервиса.
- **Конфигурируемость.** Значения из окружения раздаются через токены, а не импортируются напрямую.

### Как объявить сервис

Современный способ — декоратор `@Service()` (стабилен с v22, `@publicApi`):

```ts
@Service()
export class TicketService { /* … */ }
```

Это эргономичный шорткат для `@Injectable({ providedIn: 'root' })`: класс становится синглтоном на приложение и остаётся tree-shakable — если его никто не инжектит, сборщик выкинет его из бандла. У декоратора есть два полезных параметра:

```ts
@Service({ autoProvided: false })         // не регистрировать автоматически:
export class DraftStore {}                // провайдить вручную, где нужно

@Service({ factory: () => inject(FLAG)()  // значение создаётся фабрикой:
  ? new RealAnalytics() : new NoopAnalytics() })
export class Analytics {}
```

Декоратор `@Injectable` никуда не делся. Он нужен там, где используется **конструкторная инъекция**: `@Service` работает только с `inject()`. Ещё он умеет два скоупа, которых у `@Service` нет:

- `providedIn: 'platform'` — один инстанс на все приложения на странице.
- `providedIn: 'any'` — свой инстанс в каждом ленивом environment-инжекторе.

Оба нужны редко и всегда осознанно.

Ключевое про tree-shaking: `@Service`/`providedIn` описывает зависимость **со стороны сервиса**, поэтому неиспользуемый сервис удаляется из бандла. Перечисление в массиве `providers` — обратное направление (приложение ссылается на сервис), и такой сервис остаётся в бандле всегда.

### inject() и контекст инъекции

```ts
export class TicketList {
  private readonly tickets = inject(TicketService);
  private readonly config = inject(APP_CONFIG);
}
```

`inject()` работает **только в контексте инъекции**: инициализаторы полей класса, конструктор, фабрика провайдера или `InjectionToken`, а также внутри `runInInjectionContext(injector, fn)`. Вызов из обработчика события, из колбэка таймера или из `.then()` даст `NG0203`. Обходной путь, когда зависимость нужна позже, — сохранить `Injector` заранее:

```ts
private readonly injector = inject(Injector);

async load(): Promise<void> {
  const { Heavy } = await import('./heavy');
  runInInjectionContext(this.injector, () => new Heavy());
}
```

В v22 для того же сценария появился `injectAsync()` — ленивая инъекция с code splitting.

### Иерархия инжекторов

```
      inject(TOKEN) в TicketCard: порядок поиска
┌───────────────────────────────────────────────────┐
│ ElementInjector: сам TicketCard                   │

└───────────────────────────────────────────────────┘
                          │  не нашли
                          ▼
┌───────────────────────────────────────────────────┐
│ ElementInjector: родительские элементы            │

└───────────────────────────────────────────────────┘
                          │  не нашли
                          ▼
┌───────────────────────────────────────────────────┐
│ EnvironmentInjector: маршрут                      │
│ providers в Route (глава 07)                      │
└───────────────────────────────────────────────────┘
                          │  не нашли
                          ▼
┌───────────────────────────────────────────────────┐
│ EnvironmentInjector: root                         │
│ @Service(), providedIn: root, appConfig.providers │
└───────────────────────────────────────────────────┘
                          │  не нашли
                          ▼
┌───────────────────────────────────────────────────┐
│ EnvironmentInjector: platform                     │
│ providedIn: platform                              │
└───────────────────────────────────────────────────┘
                          │  не нашли
                          ▼
┌───────────────────────────────────────────────────┐
│ NullInjector                                      │
│ NG0201: No provider for TOKEN                     │
└───────────────────────────────────────────────────┘
первое совпадение выигрывает: провайдер на компоненте
перекрывает root и создаёт свой инстанс на каждый
инстанс этого компонента
```

Иерархий на самом деле две, и просматриваются они именно в таком порядке. Сначала **ElementInjector** — цепочка по элементам DOM (document object model, дерево объектов страницы в браузере) от запрашивающего компонента вверх. Потом **EnvironmentInjector** — маршрут, root, platform, `NullInjector`.

Внутри компонента есть два массива:

- `providers` — сервис виден в шаблоне компонента **и** в контенте, спроецированном в него через `<ng-content>`;
- `viewProviders` — только в собственном шаблоне; спроецированный контент этот провайдер не увидит (глава 11).

Модификаторы поиска задаются опциями `inject()`:

| вызов | что меняет в поиске | когда нужно |
|---|---|---|
| `inject(T)` | обычный поиск снизу вверх | по умолчанию |
| `inject(T, { optional: true })` | вернёт `null` вместо `NG0201` | необязательная зависимость |
| `inject(T, { self: true })` | только свой `ElementInjector` | требуем локальный провайдер |
| `inject(T, { skipSelf: true })` | начать с родителя | декоратор поверх родительского |
| `inject(T, { host: true })` | не выше хост-компонента | директива внутри чужого хоста |

### Рецепты провайдеров и InjectionToken

| рецепт | что подставляет | типичный случай |
|---|---|---|
| `useClass: Impl` | новый инстанс класса `Impl` | подмена реализации |
| `useValue: obj` | готовое значение как есть | конфиг, константы, мок |
| `useFactory: fn` | результат вызова `fn` | выбор реализации в рантайме |
| `useExisting: Other` | тот же инстанс, что у `Other` | узкий интерфейс к сервису |
| `multi: true` | массив всех значений токена | набор правил, интерсепторы |

Интерфейс, объект конфигурации, строка URL — не классы, поэтому токеном служить не могут. В рантайме от интерфейса ничего не остаётся. Для них есть `InjectionToken`:

```ts
export interface AppConfig {
  readonly apiUrl: string;
  readonly pageSize: number;
}

// factory делает токен tree-shakable и задаёт значение по умолчанию
export const APP_CONFIG = new InjectionToken<AppConfig>('APP_CONFIG', {
  providedIn: 'root',
  factory: () => ({ apiUrl: '/api', pageSize: 20 }),
});
```

`multi: true` превращает токен в набор: каждый провайдер добавляет элемент, а `inject()` возвращает массив. Так устроены расширяемые списки — правила валидации, обработчики, а в старом коде и интерсепторы.

### NullInjectorError как диагностика

`NG0201: No provider for X` означает буквально: поиск дошёл до `NullInjector`, ни один инжектор в цепочке не знал этот токен. Практический чеклист причин:

1. Сервис объявлен без `@Service()`/`providedIn` и не перечислен ни в одних `providers`.
2. Забыт `provide*`-вызов в `appConfig.providers` — самая частая причина для `HttpClient` (`provideHttpClient()`) и роутера.
3. Провайдер объявлен на компоненте, а зависимость запрашивают снаружи или выше по дереву.
4. Токен продублирован: два `InjectionToken` с одинаковым описанием — это два разных токена, описание не влияет на идентичность.
5. Циклический импорт: файл с токеном ещё не инициализирован, и в провайдер попадает `undefined` (симптом — «No provider for undefined»).

Рядом стоит `NG0203: inject() must be called from an injection context` — не про отсутствие провайдера, а про место вызова.

## Параллели с React

- **DI против контекста.** `useContext` работает по дереву рендера и требует обёртки `<Provider>` вокруг поддерева. Angular-инжектор привязан к дереву компонентов. И зависимость можно получить из **любого** класса, а не только из компонента: из сервиса, гарда, интерсептора. Обёртки не нужны: `@Service()` уже делает сервис доступным везде.
- **Прокидывание зависимостей.** В React объект, нужный трём уровням вниз, либо тащат пропсами, либо кладут в контекст. В Angular обе проблемы решает `inject()`, а «глубина» — не фактор: важно лишь, в каком инжекторе зарегистрирован провайдер.
- **Подмена в тестах — главное отличие.** В React зависимость обычно импортируется напрямую, и для подмены нужен `jest.mock` или ручная обёртка провайдером. В Angular подмена — штатная операция: `TestBed.configureTestingModule({ providers: [{ provide: TicketApi, useValue: fake }] })`, без участия сборщика (глава 13). Именно это делает DI не «лишним слоем», а тем, ради чего он есть.
- **Синглтоны.** Модульный синглтон в React (`export const store = createStore()`) — просто значение модуля. Подменить его в тесте трудно, а на сервере он один на все запросы. А вот `providedIn: 'root'` даёт синглтон **на инжектор**. При SSR (server-side rendering — рендеринг страницы на сервере) каждый запрос получает свой.
- **Где ломается привычка:** в React провайдер объявляют осознанно, вокруг конкретного поддерева. В Angular провайдер на компоненте выглядит безобидной строчкой `providers: [TicketService]` в декораторе. А на деле он создаёт по инстансу на каждый инстанс компонента, и общее состояние тихо распадается на N независимых копий. Это самая частая архитектурная ошибка новичков в Angular.

## Что увидишь в legacy-коде

- **`@Injectable()` без `providedIn`** плюс регистрация в `providers` NgModule; для настраиваемых библиотек — паттерн `SomeModule.forRoot(config)` / `forChild()`, который сейчас заменён функциями `provideSomething(config)`.
- **Конструкторная инъекция:** `constructor(private http: HttpClient, @Inject(APP_CONFIG) private config: AppConfig) {}` и декораторы-модификаторы `@Optional()`, `@Self()`, `@SkipSelf()`, `@Host()` вместо опций `inject()`.
- **`HTTP_INTERCEPTORS` с `multi: true` и классами-интерсепторами** — предыдущее поколение того, что сейчас делают функциональные интерсепторы (глава 08). Хороший пример «multi в дикой природе».
- **`APP_INITIALIZER`** (multi-токен для стартовой асинхронной инициализации) — в новом коде это `provideAppInitializer(...)`.
- **`InjectionToken` без фабрики** — `new InjectionToken<AppConfig>('app.config')` плюс обязательный `useValue` где-то в модуле; забыли — получите `NG0201`.
- **`ReflectiveInjector`, `Injector.create(...)`, ручные `EnvironmentInjector`** в библиотечном коде и в динамическом создании компонентов (глава 11).

## Что добавляем в проект

Три правки, и все три — про DI:

- Состояние тикетов уезжает из компонента в `TicketService`. Это задел под главу 05.
- Конфигурация приложения раздаётся через `APP_CONFIG` и функцию `provideAppConfig()`.
- Правила подсветки тикетов собираются multi-токеном: такой набор можно расширять, не трогая сервис.

## Практическое задание

**Вход:** проект из главы 03 (сигналы, счётчик из внешнего источника).
**Выход:** состояние в сервисе, конфиг и правила через DI, разобранные ошибки `NG0201` и `NG0203`.

Требования:

1. Создайте `TicketService` через `@Service()`: внутри — приватный сигнал списка, публичные `readonly`-сигналы и методы `add()`/`reset()`. `TicketList` больше не хранит массив, только читает сервис. Фильтры пока остаются в компоненте (они относятся к экрану, а не к данным) — обоснуйте, почему это осмысленная граница.
2. Заведите `APP_CONFIG: InjectionToken<AppConfig>` с фабрикой по умолчанию (`apiUrl`, `pageSize`, `slaWarningHours`) и функцию `provideAppConfig(overrides)`, возвращающую массив провайдеров. Подключите её в `app.config.ts` и прочитайте конфиг в сервисе.
3. Сделайте multi-токен `TICKET_RULES`: правило — функция `(ticket: Ticket) => string | null`. Зарегистрируйте минимум два правила. Первое срабатывает, когда под угрозой SLA (service level agreement — обещанный срок ответа по тикету). Второе — когда у тикета `urgent` нет исполнителя. Соберите правила в сервисе через `inject(TICKET_RULES)`. Компонент показывает предупреждения на карточке.
4. Компонентный провайдер: сделайте маленький `DraftStore` (черновик заметки к тикету) и объявите его в `providers` компонента карточки. Убедитесь, что у двух карточек черновики независимы. Объясните в комментарии, почему `TicketService` так объявлять нельзя.
5. Диагностика: намеренно получите `NG0201` (уберите фабрику у токена и не добавьте провайдер) и `NG0203` (вызовите `inject()` внутри обработчика клика). Прочитайте сообщения и почините — второе двумя способами: перенести вызов и через сохранённый `Injector`.
6. Ограничение: никаких `@Injectable` без нужды и никакой конструкторной инъекции — только `inject()`.

Edge cases на подумать:

- Почему `@Service()` не работает с конструкторной инъекцией и когда это заставит вас вернуться к `@Injectable`?
- Чем `providers` компонента отличается от `viewProviders`, если у компонента есть `<ng-content>`?
- Что вернёт `inject(APP_CONFIG, { optional: true })`, если провайдера нет, — и почему это лучше, чем try/catch?
- Сколько инстансов сервиса будет при `providedIn: 'root'` и сколько при `providedIn: 'any'` в приложении с ленивыми маршрутами?
- Зачем `useFactory` нужен `deps`, если внутри фабрики можно просто вызвать `inject()`?

## Разбор решения

`src/app/core/app-config.ts` — конфигурация как зависимость:

```ts
import { InjectionToken, Provider } from '@angular/core';

export interface AppConfig {
  readonly apiUrl: string;
  readonly pageSize: number;
  readonly slaWarningHours: number;
}

// Фабрика даёт две вещи сразу: значение по умолчанию (приложение
// запускается без явной настройки) и tree-shaking токена
export const APP_CONFIG = new InjectionToken<AppConfig>('APP_CONFIG', {
  providedIn: 'root',
  factory: () => ({ apiUrl: '/api', pageSize: 20, slaWarningHours: 4 }),
});

// provideXxx() вместо SomeModule.forRoot(config): обычная функция,
// возвращающая провайдеры. Так устроены все provide* в самом Angular
export function provideAppConfig(overrides: Partial<AppConfig> = {}): Provider[] {
  return [
    {
      provide: APP_CONFIG,
      useFactory: (): AppConfig => ({
        apiUrl: '/api',
        pageSize: 20,
        slaWarningHours: 4,
        ...overrides,
      }),
    },
  ];
}
```

`src/app/tickets/ticket-rules.ts` — multi-токен:

```ts
import { InjectionToken, Provider, inject } from '@angular/core';
import { APP_CONFIG } from '../core/app-config';
import { Ticket } from './ticket';

// Правило: чистая функция, возвращающая предупреждение или null
export type TicketRule = (ticket: Ticket) => string | null;

export const TICKET_RULES = new InjectionToken<readonly TicketRule[]>('TICKET_RULES');

export function provideTicketRules(): Provider[] {
  return [
    {
      provide: TICKET_RULES,
      multi: true, // каждый провайдер добавляет один элемент в массив
      // фабрика сама в контексте инъекции — здесь можно inject()
      useFactory: (): TicketRule => {
        const { slaWarningHours } = inject(APP_CONFIG);
        return (ticket) => {
          if (ticket.slaHours === undefined) return null;
          return ticket.slaHours <= slaWarningHours ? 'SLA at risk' : null;
        };
      },
    },
    {
      provide: TICKET_RULES,
      multi: true,
      useValue: ((ticket) =>
        ticket.priority === 'urgent' && ticket.assignee === null
          ? 'Urgent and unassigned'
          : null) satisfies TicketRule,
    },
  ];
}
```

`src/app/tickets/ticket-service.ts`:

```ts
import { Service, computed, inject, signal } from '@angular/core';
import { APP_CONFIG } from '../core/app-config';
import { Ticket } from './ticket';
import { TICKET_RULES } from './ticket-rules';

// @Service() = @Injectable({ providedIn: 'root' }), но короче и
// без соблазна добавить конструкторную инъекцию: он её не поддерживает
@Service()
export class TicketService {
  private readonly config = inject(APP_CONFIG);
  // multi-токен приходит массивом; порядок — порядок регистрации
  private readonly rules = inject(TICKET_RULES);

  // запись приватная, наружу — только чтение (подробно в главе 05)
  private readonly state = signal<readonly Ticket[]>(SAMPLE_TICKETS);
  readonly tickets = this.state.asReadonly();
  readonly pageSize = computed(() => this.config.pageSize);

  warningsFor(ticket: Ticket): readonly string[] {
    // сервис не знает, сколько правил и откуда они: добавить новое
    // правило можно провайдером, не трогая этот файл
    return this.rules.map((rule) => rule(ticket)).filter((w) => w !== null);
  }

  add(ticket: Ticket): void {
    this.state.update((tickets) => [ticket, ...tickets]);
  }

  reset(): void {
    this.state.set(SAMPLE_TICKETS);
  }
}
```

`src/app/app.config.ts`:

```ts
export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),

    // конфиг окружения приходит сюда, а не импортируется из environment.ts:
```

Компонентный провайдер — тот случай, когда «свой инстанс на компонент» и есть цель:

```ts
@Service({ autoProvided: false }) // не регистрируем в root: смысла нет
export class DraftStore {
  private readonly text = signal('');
  readonly draft = this.text.asReadonly();
  write(value: string): void { this.text.set(value); }
}

@Component({
  selector: 'app-ticket-card',
  // Провайдер на компоненте: у каждой карточки свой DraftStore,
  // и это ровно то, что нужно для черновика.
  // С TicketService так делать нельзя: список тикетов один на приложение,
  // а здесь получилось бы по копии состояния на карточку
  providers: [DraftStore],
  // ...
})
export class TicketCard {
  protected readonly draft = inject(DraftStore);
  private readonly tickets = inject(TicketService); // root-инстанс, общий
}
```

Разбор `NG0203` из пункта 5 — вызов не в том месте и две починки:

```ts
export class TicketList {
  private readonly injector = inject(Injector); // контекст сохраняем заранее

  // Неправильно: обработчик события — не контекст инъекции
  onClickBad(): void {
    const service = inject(TicketService); // NG0203
  }

  // Починка 1: инжектить там, где положено — в поле класса
  private readonly service = inject(TicketService);
  onClickGood(): void {
    this.service.reset();
  }

  // Починка 2: когда зависимость появляется позже (ленивый импорт),
  // выполняем код в сохранённом контексте
  async onLoadHeavy(): Promise<void> {
    const { HeavyExporter } = await import('./heavy-exporter');
    const exporter = runInInjectionContext(this.injector, () => new HeavyExporter());
    exporter.run();
  }
}
```

Ответы на edge cases:

- Декоратор `@Service()` не собирает метаданные о типах параметров конструктора, поэтому конструкторная инъекция с ним невозможна — только `inject()`. Возвращаться к `@Injectable` придётся в трёх случаях. Первый — нужен `providedIn: 'platform'` или `'any'`. Второй — класс наследуется существующим кодом с конструкторной инъекцией. Третий — сервис пишется для библиотеки, которую подключают в проектах на старом стиле.
- `providers` видны и в шаблоне компонента, и в спроецированном через `<ng-content>` контенте; `viewProviders` — только в собственном шаблоне. Разница проявляется, когда контент приходит от родителя: он «принадлежит» родителю, и если вы не хотите, чтобы чужой контент цеплялся к вашему внутреннему сервису, объявляйте его в `viewProviders`.
- Вернёт `null` вместо исключения, и это лучше try/catch. Необязательность становится частью сигнатуры зависимости, а не поведением обработчика ошибок. Типом будет `AppConfig | null`, и компилятор заставит обработать отсутствие. А блок try/catch вокруг `inject()` к тому же поймает и настоящие ошибки фабрики.
- При `providedIn: 'root'` — один инстанс на приложение, сколько бы ленивых маршрутов его ни запрашивало. При `'any'` — свой инстанс в каждом environment-инжекторе: один в root плюс по одному в каждом ленивом. Именно поэтому `'any'` почти всегда не то, что нужно: «общее» состояние распадается по ленивым границам.
- `deps` нужен, когда фабрика — обычная функция вне контекста инъекции (её вызывают, передавая зависимости позиционно). Если фабрика вызывает `inject()` внутри себя, `deps` не нужен: Angular исполняет фабрику провайдера в контексте инъекции. Современный стиль — второй: он типобезопаснее, а `deps` — массив, порядок которого компилятор не проверяет.

## Проверь себя

1. Объясните своими словами, почему `@Service()`/`providedIn: 'root'` даёт tree-shaking, а перечисление сервиса в `providers` — нет.
2. Компонент объявил `providers: [TicketService]`. Сколько инстансов сервиса окажется в приложении и что произойдёт с состоянием, которое он хранит?
3. В каком порядке Angular ищет провайдер для `inject(TOKEN)`, вызванного в дочернем компоненте, и в какой момент вы получите `NG0201`?
4. Зачем нужен `InjectionToken`, если токеном может быть класс? Почему нельзя использовать интерфейс?
5. `NG0203` — о чём эта ошибка и какие два способа её починить существуют?

<details>
<summary>Ответы</summary>

1. Направление ссылки. При `@Service()`/`providedIn` сервис сам объявляет, в каком инжекторе он живёт: приложение на него не ссылается, ссылка появляется только там, где его инжектят. Если таких мест нет, сборщик видит недостижимый класс и удаляет его. Массив `providers` — обратная ссылка: конфигурация приложения статически упоминает класс. Значит, класс достижим из точки входа и попадёт в бандл, даже если ни один компонент его не запрашивает.
2. По одному инстансу на каждый инстанс этого компонента: провайдер живёт в ElementInjector, который создаётся для элемента. Состояние, которое сервис хранит, перестаёт быть общим — каждая копия компонента получает свою. Если это черновик формы или локальный стор, поведение желаемое. А если это список тикетов или авторизация, вы получите N рассинхронизированных копий. Ошибки при этом не будет ни одной: просто данные не совпадают между экранами.
3. Сначала ElementInjector самого компонента, то есть его `providers` и `viewProviders`. Затем такие же инжекторы родительских элементов вверх по дереву. После них — environment-инжекторы: маршрутный, root, platform. Маршрутный участвует, только если компонент открыт через маршрут с `providers`. Первое совпадение выигрывает. Если ни один не знает токен, поиск доходит до `NullInjector`, который всегда бросает — это и есть `NG0201: No provider for TOKEN`.
4. Токен должен существовать в рантайме и быть уникальным объектом. Класс подходит: он есть в рантайме и уникален. Интерфейс — конструкция только системы типов: после компиляции от него ничего не остаётся, ссылаться на него в рантайме невозможно. `InjectionToken` — рантайм-объект, созданный специально как ключ, с типовым параметром для типизации возвращаемого значения. Строка тоже плохой токен: две одинаковые строки из разных мест совпадут случайно. А описание в `new InjectionToken('...')` на идентичность не влияет — два токена с одинаковым текстом остаются разными.
5. Ошибка `NG0203` означает, что `inject()` вызван вне контекста инъекции. Контекст есть при инициализации полей класса, в конструкторе и в фабриках провайдеров и токенов. Контекста нет в обработчиках событий, колбэках таймеров, `.then()` и произвольных методах. Починить можно двумя способами. Первый — перенести вызов туда, где контекст есть: обычно в поле класса, и это нормальный стиль. Второй — заранее получить `Injector` и выполнить код в `runInInjectionContext(injector, fn)`. Для ленивых импортов в v22 есть `injectAsync()`.

</details>

## Частая ошибка

Классика номер один — провайдер на уровне компонента там, где нужен root. Выглядит так. Разработчик пишет сервис состояния, видит в статье строчку `providers: [TicketService]` в декораторе компонента и копирует её. В итоге он получает по инстансу сервиса на каждый инстанс компонента.

Ошибка не даёт ни исключения, ни предупреждения: приложение просто работает. Список, добавленный на одном экране, не виден на другом, а счётчик в шапке не меняется после действия в таблице.

Диагностируется это быстро, если помнить правило: **`providers` в компоненте — это заявление «мне нужен собственный инстанс»**. Для общего состояния берите `@Service()`, то есть root. Для локального — черновика, стора конкретной формы, состояния аккордеона — компонентный провайдер. Тогда это осознанное решение, а не копипаста.

Вторая ошибка — `inject()` не в том месте. React-опыт подсказывает, что «хук можно позвать где угодно внутри компонента», и рука сама пишет `inject(TicketService)` внутри обработчика клика или в `.then()` после `await`. Результат — `NG0203: inject() must be called from an injection context`.

Особенно коварен случай с `await`: код до него ещё в контексте, а после — уже нет. Поэтому ошибка появляется «через раз» и выглядит как гонка.

Лечение простое и стилистически правильное. Все зависимости объявляйте полями класса в момент создания инстанса. А если зависимость действительно нужна позже (ленивая загрузка модуля), сохраните `Injector` заранее и используйте `runInInjectionContext`.
