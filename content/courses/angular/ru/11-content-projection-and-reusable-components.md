# Проекция контента и переиспользуемые компоненты

## Теория

### Три способа отдать разметку внутрь компонента

```
                             Три способа отдать разметку в чужой компонент
┌──────────────────────┬─────────────────────────┬────────────────────────┬───────────────────────────┐
│ способ               │ когда создаётся         │ данные внутрь          │ когда брать               │
├──────────────────────┼─────────────────────────┼────────────────────────┼───────────────────────────┤
│ ng-content           │ ВСЕГДА, даже если скрыт │ нет: контекст родителя │ статичные слоты           │
├──────────────────────┼─────────────────────────┼────────────────────────┼───────────────────────────┤
│ ng-template + outlet │ когда вставили          │ да: контекст шаблона   │ строки таблицы, ячейки    │
├──────────────────────┼─────────────────────────┼────────────────────────┼───────────────────────────┤
│ createComponent()    │ по вызову в коде        │ да: setInput()         │ модалки, тулбары, плагины │
└──────────────────────┴─────────────────────────┴────────────────────────┴───────────────────────────┘
                документация прямо запрещает оборачивать ng-content в @if/@for/@switch:
                     содержимое всё равно будет создано, а условие лишь спрячет его
```

Это первая развилка, на которой ошибаются: `ng-content` кажется универсальным решением, но у него два жёстких ограничения — контент **всегда создаётся** и не может получить данные от компонента-хозяина. Как только нужно «отрендерить строку для каждого тикета» или «создать содержимое только при открытии», это уже `ng-template` или динамическое создание.

### ng-content и слоты

```
         что пишет потребитель                   куда это попадёт в шаблоне panel
┌─────────────────────────────────────┐    ┌──────────────────────────────────────────┐
│ <app-panel>                         │    │ <header>                                 │
│   <h2 panel-title>Tickets</h2>      │    │   <ng-content select="[panel-title]" />  │
│   <button panel-action>New</button> │    │   <ng-content select="[panel-action]" /> │
│   <p>Список за сегодня</p>          │    │ </header>                                │
│ </app-panel>                        │    │ <div class="body">                       │
└─────────────────────────────────────┘    │   <ng-content>Нет данных</ng-content>    │
 ngProjectAs позволяет попасть в слот,     │ </div>                                   │
     не меняя разметку под селектор        └──────────────────────────────────────────┘
                                            ng-content без select забирает остальное;
                                                внутри тега — контент по умолчанию
```

Механика: `<ng-content>` — не элемент, а **инструкция компилятора**, куда поставить контент, переданный потребителем. Отсюда следствия:

- Селекторы `select` — обычные CSS-селекторы (`[panel-title]`, `h2`, `.actions`). `ng-content` без `select` собирает всё, что не подошло; если такого слота нет, лишний контент просто не отрендерится.
- Внутри тега можно задать **контент по умолчанию** — он покажется, если потребитель ничего не передал в этот слот.
- `ngProjectAs="[panel-title]"` позволяет попасть в слот элементу, который не соответствует селектору — например, `<ng-container>` или компоненту-обёртке. Значение статическое, биндинг невозможен.
- Проецируемый контент принадлежит **потребителю**: его выражения вычисляются в контексте родителя, его стили — родительские (глава 01), и он видит `providers` хозяина, но не `viewProviders` (глава 04).
- Документация формулирует ограничение прямо: «Angular always instantiates and creates DOM nodes for content rendered to a `<ng-content>` placeholder, even if that `<ng-content>` placeholder is hidden» и «You should not conditionally include `<ng-content>` with `@if`, `@for`, or `@switch`». То есть скрыть — можно, не создавать — нельзя.

### ng-template + ngTemplateOutlet: аналог render-props

Когда контент должен получать данные от компонента (строка таблицы знает свой тикет) или создаваться отложенно, передают **шаблон**:

```html
<!-- потребитель описывает, как рисовать ячейку, и получает данные обратно -->
<app-data-table [rows]="tickets()">
  <ng-template #cell let-ticket let-column="column">
    @switch (column) {
      @case ('title') { <a [routerLink]="['/tickets', ticket.id]">{{ ticket.title }}</a> }
      @default { {{ ticket[column] }} }
    }
  </ng-template>
</app-data-table>
```

```html
<!-- внутри таблицы: шаблон вставляется столько раз, сколько нужно -->
@for (row of rows(); track row.id) {
  <tr>
    @for (column of columns(); track column) {
      <td>
        <ng-container
          [ngTemplateOutlet]="cellTemplate()"
          [ngTemplateOutletContext]="{ $implicit: row, column }"
        />
      </td>
    }
  </tr>
}
```

Контекст передаётся объектом; `$implicit` достаётся первой `let`-переменной без имени. Сам шаблон компонент получает сигнальным запросом: `contentChild<TemplateRef<CellContext>>('cell')` (глава 02).

Для типизации контекста существует `ngTemplateContextGuard` — статический метод, объявляющий тип контекста (мы его встречали в главе 06 у структурных директив). Без него `strictTemplates` не сможет проверить `let-ticket`.

### ng-container

`<ng-container>` — группирующий элемент, который не попадает в DOM. Нужен там, где директиву или блок надо повесить, не добавляя лишний узел: в `<tbody>` нельзя вставить `<div>`, а `ng-container` можно. Он же служит носителем `[ngTemplateOutlet]`.

### Динамическое создание компонентов

Когда компонент выбирается в рантайме (модалка, панель настроек по типу виджета, плагинная архитектура), используют `ViewContainerRef`:

```ts
private readonly host = viewChild.required('modalHost', { read: ViewContainerRef });

open<T>(component: Type<T>, inputs: Record<string, unknown>): ComponentRef<T> {
  const ref = this.host().createComponent(component);
  // setInput вместо ref.instance.x = ...: setInput помечает компонент
  // как изменённый, и OnPush-компонент увидит новое значение (глава 03)
  for (const [key, value] of Object.entries(inputs)) ref.setInput(key, value);
  return ref;
}
```

Уничтожение — `ref.destroy()` или `viewContainerRef.clear()`. Ещё есть автономная функция `createComponent()` из `@angular/core`, которой нужен `EnvironmentInjector`, — для случаев, когда нет удобного `ViewContainerRef` (например, рендеринг в произвольный DOM-узел).

Обратите внимание на пару важных мелочей: компонент, созданный в `ViewContainerRef`, попадает в **логическое дерево** этого контейнера (то есть в его change detection и DI), но физически вставляется как sibling к элементу-анкору. И `setInput()` — единственный корректный способ передать входы динамическому компоненту.

## Параллели с React

- **`ng-content` ≈ `children`, но с фиксированными слотами.** В React несколько «слотов» делают пропсами (`header={<h2/>}`) или соглашением о `children`; в Angular это селекторы `select`. Разница в цене ошибки: непопавший в слот контент в Angular просто не отрендерится, без предупреждения.
- **`ng-template` + `ngTemplateOutlet` = render-props.** Прямая аналогия: `renderRow={(row) => <Cell/>}` в React и шаблон с контекстом в Angular. Разница — в реализации: React передаёт **функцию**, Angular передаёт **скомпилированный шаблон**, который вставляет `ViewContainerRef`. Отсюда типизация контекста через `ngTemplateContextGuard` вместо типа функции.
- **Ленивое создание контента.** В React `{isOpen && <Heavy/>}` не создаёт `Heavy` до открытия — и это интуитивно. В Angular тот же приём с `ng-content` **не работает**: контент создаётся всегда. Чтобы получить ленивость, нужен `ng-template` (или `@defer` — глава 12), и это несовпадение моделей ловит почти каждого.
- **Динамический компонент.** В React достаточно `const C = map[type]; return <C/>` — компонент это значение. В Angular нужен `ViewContainerRef.createComponent()` и `setInput()`, потому что компонент — не функция, а описание с метаданными, и его создание проходит через DI и change detection.
- **Где ломается привычка:** ожидание, что содержимое, переданное в компонент, «принадлежит» ему. Оно принадлежит родителю: его выражения вычисляются в родительском контексте, его стили скоупятся родителем, а сервисы он получает из `providers` хозяина, но не из `viewProviders`. Именно поэтому «мой контент не видит сервис компонента» — не баг, а различие `providers`/`viewProviders`.

## Что увидишь в legacy-коде

- **`*ngTemplateOutlet` со звёздочкой** — `<ng-container *ngTemplateOutlet="tpl; context: { $implicit: row }">`. Работает, но требует `CommonModule`; современная запись — property binding `[ngTemplateOutlet]`.
- **`@ContentChild('cell') tpl!: TemplateRef<unknown>`** с `ngAfterContentInit` вместо сигнального `contentChild()` (глава 02): значение появлялось только после хука, а на изменения подписывались через `QueryList.changes`.
- **`ComponentFactoryResolver`:** `resolveComponentFactory(Cmp)` + `vcr.createComponent(factory)` — API до Angular 13. Сейчас фабрики не нужны: `createComponent(Cmp)` принимает класс напрямую.
- **`ref.instance.title = 'x'` + `ref.changeDetectorRef.detectChanges()`** вместо `ref.setInput('title', 'x')`: ручная запись в инстанс не помечает компонент изменённым, отсюда и ручная проверка.
- **`entryComponents`** в NgModule — список компонентов, создаваемых динамически; требовался до Ivy, сейчас удалён.
- **Свои модалки на `document.body.appendChild`** и ручное управление фокусом, скроллом и `z-index` — то, для чего существует `cdk/overlay` и `cdk/a11y` с `FocusTrap`.

## Что добавляем в проект

Два переиспользуемых компонента: `DataTable` (колонки описываются потребителем через шаблоны — аналог render-props) и `Modal` (создаётся динамически, с ловушкой фокуса и закрытием по Escape). Оба должны работать с любыми данными, а не только с тикетами.

## Практическое задание

**Вход:** проект из главы 10 (список, деталь, форма).
**Выход:** таблица и модальное окно, которые можно переиспользовать вне тикетов.

Требования:

1. `DataTable<T>`: входы — массив строк и описание колонок (`{ key, header }`). Потребитель может задать шаблон ячейки, получающий строку и ключ колонки. Компонент не должен знать про `Ticket`: только дженерик.
2. Шаблоны берите сигнальным `contentChild`, типизируйте контекст (`ngTemplateContextGuard`), и предусмотрите поведение по умолчанию, если шаблон не передан.
3. Слоты: у таблицы должны быть слоты для заголовка (`[table-title]`) и для действий (`[table-actions]`), плюс контент по умолчанию для пустого состояния.
4. `Modal`: содержимое создаётся **только при открытии** — то есть через `ng-template` или `createComponent()`, не через `ng-content`. Объясните в комментарии, почему `@if` вокруг `ng-content` не подошёл бы.
5. Модалка должна: закрываться по Escape и по клику вне, возвращать фокус на элемент-триггер после закрытия, не давать фокусу уйти за пределы диалога. Реализуйте сами, а затем в комментарии укажите, какие примитивы CDK закрыли бы каждый пункт.
6. Динамическое создание: сделайте метод `open(component, inputs)`, который создаёт произвольный компонент внутри модалки через `ViewContainerRef` и передаёт входы через `setInput()`. Продемонстрируйте на форме тикета.
7. Ограничение: ни одного `any` в дженериках и никакого прямого доступа к `ref.instance` для передачи входов.

Edge cases на подумать:

- Потребитель передал в таблицу тяжёлый компонент внутри `<ng-content>`, а таблица его прячет через `@if`. Сколько раз компонент будет создан?
- Проецируемый контент пытается инжектить сервис, объявленный в `viewProviders` таблицы. Что произойдёт?
- Вы вставили один и тот же `TemplateRef` в два разных `ngTemplateOutlet`. Сколько инстансов view будет создано и разделяют ли они состояние?
- Динамический компонент создан через `createComponent()`, а потом маршрут сменился. Что произойдёт с ним, если не вызвать `destroy()`?
- В модалке нужен `Escape`, но она вложена в другую модалку. Как не закрыть обе одним нажатием?

## Разбор решения

`src/app/ui/data-table.ts`:

```ts
import {
  Component,
  TemplateRef,
  contentChild,
  input,
} from '@angular/core';
import { NgTemplateOutlet } from '@angular/common';

export interface TableColumn<T> {
  readonly key: keyof T & string;
  readonly header: string;
}

// Тип контекста шаблона ячейки: то, что потребитель получит в let-переменных
export interface CellContext<T> {
  readonly $implicit: T;
  readonly column: string;
}

@Component({
  selector: 'app-data-table',
  imports: [NgTemplateOutlet],
  templateUrl: './data-table.html',
  styleUrl: './data-table.css',
})
export class DataTable<T extends { id: number | string }> {
  readonly rows = input.required<readonly T[]>();
  readonly columns = input.required<readonly TableColumn<T>[]>();

  // Сигнальный contentChild: не требует ngAfterContentInit и обновляется сам.
  // Шаблон необязателен — если его нет, рисуем значение как текст
  readonly cellTemplate = contentChild<TemplateRef<CellContext<T>>>('cell');

  // Подсказка компилятору о типе контекста: без неё strictTemplates
  // не проверит выражения внутри let-ticket (глава 06)
  static ngTemplateContextGuard<T>(
    _dir: DataTable<T>,
    _ctx: unknown,
  ): _ctx is CellContext<T> {
    return true;
  }
}
```

`src/app/ui/modal.ts` — ленивое содержимое и динамические компоненты:

```ts
import {
  Component,
  ComponentRef,
  DestroyRef,
  ElementRef,
  Type,
  ViewContainerRef,
  computed,
  inject,
  signal,
  viewChild,
} from '@angular/core';

@Component({
  selector: 'app-modal',
  templateUrl: './modal.html',
  styleUrl: './modal.css',
  host: {
    '[class.is-open]': 'isOpen()',
    // Escape обрабатываем на хосте, а не на document: вложенная модалка
    // получит событие первой и остановит всплытие — так закроется только она
    '(keydown.escape)': 'onEscape($event)',
  },
})
export class Modal {
  private readonly host = inject(ElementRef<HTMLElement>);

  // Контейнер для динамических компонентов
  private readonly content = viewChild.required('content', { read: ViewContainerRef });

  private readonly open = signal(false);
  readonly isOpen = this.open.asReadonly();

  private lastFocused: HTMLElement | null = null;
  private currentRef: ComponentRef<unknown> | null = null;

  constructor() {
    // страховка: если модалку уничтожили открытой, чистим за собой
    inject(DestroyRef).onDestroy(() => this.currentRef?.destroy());
  }

  // Открытие с произвольным компонентом внутри
  openWith<T>(component: Type<T>, inputs: Record<string, unknown> = {}): ComponentRef<T> {
    this.lastFocused = document.activeElement as HTMLElement | null;
    this.open.set(true);

    const container = this.content();
    container.clear();
    const ref = container.createComponent(component);

    // setInput, а не ref.instance.x = …: только setInput помечает компонент
    // изменённым, иначе OnPush-компонент не увидит значение (глава 03)
    for (const [key, value] of Object.entries(inputs)) {
      ref.setInput(key, value);
    }

    this.currentRef = ref;
    return ref;
  }

  close(): void {
    this.open.set(false);
    // без destroy() компонент остался бы жить: его подписки, таймеры
    // и httpResource продолжали бы работать
    this.currentRef?.destroy();
    this.currentRef = null;
    this.content().clear();
    // фокус возвращается на элемент, с которого открыли: требование a11y
    this.lastFocused?.focus();
  }

  protected onEscape(event: Event): void {
    if (!this.open()) return;
    event.stopPropagation();   // вложенная модалка не закроет родительскую
    this.close();
  }
}
```

```html
  <div class="modal__backdrop" (click)="close()"></div>

  <div class="modal__dialog" role="dialog" aria-modal="true">
    <header class="modal__header">
      <!-- статичные слоты через ng-content: заголовок и кнопки
           не тяжёлые, создавать их заранее не жалко -->
      <ng-content select="[modal-title]" />
      <button type="button" aria-label="Close" (click)="close()">×</button>
    </header>

    <!-- Содержимое создаётся ЗДЕСЬ и только когда модалка открыта.
         Через <ng-content> так сделать нельзя: документация прямо говорит,
         что проецируемый контент создаётся всегда, даже если скрыт, —
         тяжёлая форма инициализировалась бы вместе со страницей -->
    <div class="modal__body">
      <ng-container #content />
    </div>
  </div>
}
```

Открытие формы тикета в модалке:

```ts
protected readonly modal = viewChild.required(Modal);

protected createTicket(): void {
  const ref = this.modal().openWith(TicketForm, { mode: 'create' });
  // выходы динамического компонента доступны как обычно
  ref.instance.saved.subscribe(() => this.modal().close());
}
```

Что закрыл бы CDK в этом коде: `cdk/overlay` — создание слоя, позиционирование и backdrop; `cdk/a11y` (`FocusTrap`, `cdkTrapFocus`) — удержание фокуса внутри диалога, чего в решении нет; `cdk/portal` — вставка шаблона или компонента в слой; `cdk/dialog` — всё перечисленное сразу плюс роли и возврат фокуса. Своя реализация здесь имеет смысл как учебная; в проекте, где модалок больше одной, дешевле взять `cdk/dialog`.

Ответы на edge cases:

- Один раз — и сразу, при создании таблицы. `@if` вокруг `ng-content` только скрывает уже созданные узлы: контент проецируемого содержимого инстанцируется всегда. Поэтому тяжёлый компонент внутри слота — это плата, которую вы вносите независимо от того, показан слот или нет; для ленивости нужен `ng-template`.
- Не найдёт: `viewProviders` видны только собственному шаблону компонента, а проецируемый контент принадлежит родителю. Он получит зависимость из `providers` таблицы (если она там есть) или пойдёт выше по иерархии инжекторов (глава 04). Если сервис таблицы должен быть доступен контенту — объявляйте его в `providers`, а не в `viewProviders`.
- Два независимых встроенных view. `TemplateRef` — это «рецепт», а не инстанс: каждая вставка создаёт свой набор узлов и своё состояние (свои значения `@let`, свои инстансы компонентов внутри). Общего у них только то, что приходит из контекста и из родительского компонента.
- Он продолжит существовать: `ViewContainerRef` не уничтожает созданные компоненты сам, а компонент, созданный императивно, не привязан к жизни маршрута. Его `effect`-ы, подписки и `httpResource` продолжат работать — типичная утечка. Отсюда `destroy()` в `close()` и страховка через `DestroyRef` в конструкторе.
- Обрабатывать `Escape` на **хосте модалки**, а не на `document`, и останавливать всплытие (`stopPropagation`). Тогда событие сначала получит внутренняя модалка (она глубже в дереве), закроет себя и не даст событию дойти до внешней. С `document`-слушателями пришлось бы вести стек открытых диалогов — что, собственно, и делает `cdk/overlay`.

## Проверь себя

1. Почему `@if` вокруг `<ng-content>` не даёт ленивого создания контента, и что использовать вместо этого?
2. Чем `ng-template` + `ngTemplateOutlet` отличается от `ng-content` с точки зрения передачи данных, и какой React-приём это повторяет?
3. Кому «принадлежит» проецируемый контент — родителю или компоненту-хозяину? Приведите два следствия этого факта.
4. Зачем нужен `setInput()` при динамическом создании компонента и что будет при прямой записи в `ref.instance`?
5. Что вы отдадите на CDK, а что напишете сами, если делаете свой компонент выпадающего списка? Обоснуйте границу.

<details>
<summary>Ответы</summary>

1. Потому что `<ng-content>` — не элемент, который можно создать или не создать, а инструкция компилятора о месте вставки уже существующего контента. Документация формулирует это прямо: узлы для проецируемого содержимого создаются всегда, даже если placeholder скрыт, и оборачивать `ng-content` в `@if`/`@for`/`@switch` не следует. Условие лишь скроет результат, а конструкторы компонентов, их `effect`-ы и запросы уже выполнятся. Для настоящей ленивости контент передают как `ng-template` и вставляют через `ngTemplateOutlet` (или `ViewContainerRef`) в нужный момент — либо используют `@defer` (глава 12), если задача в отложенной загрузке кода.
2. `ng-content` переносит готовую разметку без возможности что-либо в неё передать: её выражения вычисляются в контексте родителя. `ng-template` передаёт **описание** разметки, которое компонент вставляет сам и вместе с контекстом — объектом, попадающим в `let`-переменные (`$implicit` — в первую безымянную). Это прямой аналог render-props (`renderRow={(row) => …}`): потребитель описывает «как рисовать», компонент решает «сколько раз и с какими данными». Разница с React в том, что передаётся не функция, а скомпилированный шаблон, поэтому типизация контекста делается через `ngTemplateContextGuard`.
3. Родителю. Контент объявлен в его шаблоне, поэтому: (а) выражения внутри вычисляются в контексте родителя и проверяются при проверке **его** шаблона — компонент-хозяин не может «подставить» туда свои значения иначе как через `ng-template` с контекстом; (б) стили скоупятся родителем (атрибут `_ngcontent` родительского компонента), поэтому CSS хозяина на этот контент не действует; (в) в DI контент видит `providers` хозяина, но **не** `viewProviders`. Отсюда же следует, что жизненный цикл контента привязан к родителю, а `ngAfterContentInit` хозяина срабатывает уже после его создания.
4. `setInput()` не только записывает значение, но и помечает компонент как изменённый, планируя проверку — то есть делает то же, что сделал бы биндинг `[x]="…"` в шаблоне. Прямая запись `ref.instance.title = 'x'` меняет поле, но фреймворк об этом не знает: у `OnPush`-компонента (а это дефолт с v22) шаблон не будет перепроверен, и на экране останется прежнее значение. Кроме того, при записи в инстанс не работают `transform` у входов и не отрабатывает `ngOnChanges` в старом коде. Практически: `setInput()` — единственный корректный способ; ручная запись требует `markForCheck`/`detectChanges` и всё равно обходит контракт входов.
5. На CDK отдают поведение, которое легко сделать неправильно: `overlay` — создание слоя, позиционирование относительно триггера с учётом границ окна и прокрутки, backdrop; `a11y` — ловушка фокуса, `FocusMonitor`, объявления для скринридеров; `listbox`/`menu` — клавиатурная навигация, `aria-activedescendant`, типизация выбора; при желании `@angular/aria` даёт готовые директивы `combobox`/`listbox`. Сами пишут разметку, стили, анимации и предметную логику: как выглядит опция, как фильтруется список, откуда берутся данные, что считать выбранным. Граница проста: всё, что описывается словами «правильное поведение по стандарту», берут из библиотеки; всё, что описывается словами «как это выглядит и что означает в нашем продукте», пишут сами.

</details>

## Частая ошибка

Первая — попытка получить ленивое содержимое через `@if` вокруг `<ng-content>`. React-модель подсказывает, что `{isOpen && children}` не создаёт детей, пока условие ложно; в Angular контент создаётся всегда, а условие лишь прячет DOM. Симптом характерный: модалка закрыта, но форма внутри уже отправила запрос за справочниками, `effect`-ы работают, а в Network видны обращения, которых пользователь не инициировал. Иногда это ловится ещё раньше — по ошибке в консоли от компонента, который «не должен был существовать». Правильный путь: содержимое, которое должно появляться по требованию, передавать как `ng-template` и вставлять `ngTemplateOutlet`/`ViewContainerRef` в момент открытия, а для отложенной загрузки кода использовать `@defer` (глава 12).

Вторая — динамический компонент без `destroy()`. Создали через `createComponent()`, показали, закрыли модалку «скрытием» — и оставили инстанс жить. Он продолжает быть частью change detection, его подписки и `httpResource` работают, поллинг стучится в сеть, а при повторном открытии рядом появляется второй такой же. Утечка накапливается тихо: приложение просто медленно тяжелеет. Правило: у каждого `createComponent()` есть парный `destroy()` (или `clear()` контейнера), и лучше сразу подстраховаться `DestroyRef.onDestroy()` — как в разборе. Тот же принцип объясняет, почему `@if` предпочтительнее «скрытия через CSS»: удаление view уничтожает и компоненты внутри него вместе со всем их состоянием.
