# Сервисы и состояние

## Теория

### Почему состояние уезжает из компонента

Компонент живёт ровно столько, сколько его view в дереве. Уйти со страницы и вернуться — это новый инстанс с нуля. Поэтому граница проходит так: **компонент владеет состоянием экрана, сервис — состоянием данных**. Список тикетов должен пережить переход на детальную страницу и обратно; открытый аккордеон — не должен.

Второй мотив — переиспользование: тот же список нужен таблице, шапке со счётчиком и виджету «мои тикеты». Третий — тестируемость: логику в сервисе можно проверить без рендеринга (глава 13).

### Анатомия сигнального стора

```
 Сигнальный стор на сервисе: что наружу, что внутрь
┌─────────────────────────────────────────────────┐
│ компонент: только чтение и команды              │
│ store.filtered()   store.setStatus("open")      │
├─────────────────────────────────────────────────┤
│ публичное API сервиса — всё только для чтения   │
│ readonly tickets = this.state.asReadonly()      │
│ readonly filtered = computed(() => ...)         │
├─────────────────────────────────────────────────┤
│ команды: единственный способ изменить состояние │
│ add(ticket)  setStatus(s)  select(id)  reset()  │
├─────────────────────────────────────────────────┤
│ приватное состояние: только его и пишем         │
│ private state = signal<readonly Ticket[]>([])   │
└─────────────────────────────────────────────────┘
наружу не отдаётся WritableSignal: иначе любой компонент
      сможет писать в состояние в обход команд
```

Правила, которые делают из «сервиса с полями» стор:

1. **Запись приватна.** Наружу отдаются `asReadonly()`-сигналы и `computed`. Если компонент может позвать `set()`, инварианты стора нельзя гарантировать: изменение произойдёт в обход команд, и никакая сопутствующая логика (пересчёт выбора, инвалидация, логирование) не выполнится.
2. **Изменение — только через команды.** Метод описывает намерение: `assign(id, user)`, а не `setTickets(newArray)`. Тогда правила живут в одном месте, а не размазаны по компонентам.
3. **Обновления иммутабельны.** `update((tickets) => [...])`, типы `readonly Ticket[]` — чтобы компилятор ловил `push` (глава 02).
4. **Производные значения — `computed`, а не второе поле.** Дублирование состояния — источник рассинхрона: в этот момент у вас два места, где «правда».

### Кому какое состояние принадлежит

Самая полезная классификация в реальном проекте:

- **Доменные данные** — тикеты, пользователи. Живут в сервисе уровня приложения, переживают навигацию.
- **Состояние экрана** — фильтры, сортировка, выбранная строка, открытые панели. Живёт столько, сколько экран. Технически это тоже может быть сервис, но предоставленный на уровне маршрута или компонента (глава 04): тогда при уходе с экрана он уничтожается вместе с ним.
- **Серверный кеш** — то, что пришло из API, вместе с флагами загрузки и ошибками. Отдельная категория, потому что источник правды находится на сервере, а не у вас; ей посвящён `httpResource` (глава 08).
- **Состояние формы** — черновик, валидность, `dirty`. Принадлежит форме, а не стору (глава 10).

Смешивать их в одном объекте — типичная ошибка «одного большого стора»: домен и UI начинают инвалидировать друг друга, а фильтры экрана внезапно переживают уход с экрана.

### Лестница решений

```
                     Лестница решений: берём следующую ступень, когда прижало
┌──────────────────────┬───────────────────────────────────────┬─────────────────────────────────┐
│ уровень              │ когда это достаточно                  │ чем платите                     │
├──────────────────────┼───────────────────────────────────────┼─────────────────────────────────┤
│ сигналы в компоненте │ состояние живёт и умирает с экраном   │ ничем                           │
├──────────────────────┼───────────────────────────────────────┼─────────────────────────────────┤
│ сервис с сигналами   │ данные нужны нескольким экранам       │ дисциплина инкапсуляции         │
├──────────────────────┼───────────────────────────────────────┼─────────────────────────────────┤
│ NgRx SignalStore     │ много фич, нужны единые конвенции     │ зависимость + свой цикл релизов │
├──────────────────────┼───────────────────────────────────────┼─────────────────────────────────┤
│ NgRx Store (actions) │ нужны трассировка, time-travel, аудит │ бойлерплейт и обучение команды  │
└──────────────────────┴───────────────────────────────────────┴─────────────────────────────────┘
                 на 14.08.2026 стабильный NgRx — 21.1.1 с peer @angular/core ^21;
                поддержка v22 пока в 22.0.0-rc.0 под тегом next — это и есть цена
```

Честный ответ на вопрос «нужен ли NgRx»: **в большинстве приложений — нет**, и это позиция, которую можно защищать на собеседовании. Сервис с сигналами закрывает то, ради чего исторически брали Redux: единый источник правды, производные значения, предсказуемые изменения. Сигналы дают ещё и точечное обновление без селекторов и мемоизации руками.

Что действительно остаётся за сторонними решениями:

- **Единые конвенции в большой команде.** Когда сторов десятки и пишут их пятнадцать человек, «просто сервис» превращается в пятнадцать разных стилей. SignalStore задаёт форму: `signalStore(withState(...), withComputed(...), withMethods(...), withHooks(...))`, изменения — через `patchState`, работа с коллекциями — через `withEntities` из `@ngrx/signals/entities`, мост к RxJS — `rxMethod` из `@ngrx/signals/rxjs-interop`.
- **Трассировка и инструменты.** Классический NgRx Store с actions/reducers/effects даёт журнал действий, time-travel в DevTools и воспроизводимость: если бизнес требует аудита «кто и что поменял» — это его сценарий.
- **Сложная оркестрация асинхронного.** Цепочки, отмены, зависимые запросы — там, где `effects` на RxJS выразительнее ручного кода (глава 09).

И цена, о которой обычно молчат: у стороннего стора свой релизный цикл. На момент написания главы стабильный NgRx — 21.1.1 с `peer @angular/core: ^21.0.0`, а поддержка Angular 22 живёт в `22.0.0-rc.0` под тегом `next`. То есть апгрейд фреймворка упирается в готовность стора — плата, которой у встроенных средств нет.

### Как выглядит SignalStore

Для сравнения — тот же стор, написанный на `@ngrx/signals`:

```ts
export const TicketStore = signalStore(
  { providedIn: 'root' },
  withState<{ tickets: readonly Ticket[]; status: TicketStatus | null }>({
    tickets: [],
    status: null,
  }),
  withComputed(({ tickets, status }) => ({
    filtered: computed(() =>
      status() === null ? tickets() : tickets().filter((t) => t.status === status()),
    ),
  })),
  withMethods((store) => ({
    setStatus(status: TicketStatus | null): void {
      patchState(store, { status });
    },
  })),
);
```

Разница со «своим» сервисом невелика: тот же приватный стейт, те же computed, те же команды — просто зафиксированные библиотекой. Отсюда и практический вывод: начинать с сервиса, а переезжать, когда появится причина, названная выше, — переезд механический.

## Параллели с React

```
┌────────────────────────────┬───────────────────────┬───────────────────────────┐
│ задача                     │ в React               │ в Angular                 │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ состояние одного экрана    │ useState / useReducer │ signal в компоненте       │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ раздать зависимость вниз   │ Context + Provider    │ DI: сервис через inject() │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ общее состояние приложения │ Zustand / Redux       │ сервис с сигналами        │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ производное значение       │ useMemo / селектор    │ computed                  │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ серверные данные и кеш     │ TanStack Query        │ httpResource (глава 08)   │
├────────────────────────────┼───────────────────────┼───────────────────────────┤
│ строгие конвенции команды  │ Redux Toolkit         │ NgRx SignalStore / Store  │
└────────────────────────────┴───────────────────────┴───────────────────────────┘
```

- **Ближайший аналог сигнального сервиса — Zustand, а не Redux.** Там тоже стор снаружи дерева компонентов, читается селектором, меняется методами. Отличие: в Zustand подписку задаёт селектор (`useStore(s => s.tickets)`), а в Angular подписка возникает от самого факта чтения сигнала — забыть «сузить» селектор невозможно.
- **Context — это DI, а не состояние.** React-разработчики часто хранят состояние *в* контексте: `<StateProvider>` со значением из `useState`. В Angular эти две вещи разделены: DI отвечает за доставку сервиса, сигналы — за реактивность. Поэтому не нужно ни обёртки-провайдера, ни мемоизации value, ни разбиения контекстов ради производительности.
- **Иммутабельность без immer.** Redux Toolkit прячет иммутабельность за immer, чтобы можно было писать «мутирующий» код. В Angular защита другая: типы `readonly` не дают мутировать, а `Object.is` в сигнале не даст «случайно» обновиться. Помощника вроде immer нет, но и proxy-магии нет тоже.
- **Серверный кеш — отдельная категория в обоих мирах.** В React это TanStack Query, а не Redux; в Angular — `httpResource`, а не стор. Держать ответ API в общем сторе, вручную дописывая `loading`/`error`, — одинаково устаревший подход и там и там (глава 08).
- **Где ломается привычка:** в React глобальный стор — заметное архитектурное решение (поставить Provider, подключить devtools). В Angular сервис доступен отовсюду **по умолчанию**, поэтому «глобальным» состояние становится случайно: написали `@Service()`, положили туда фильтры экрана — и они переживают уход с экрана. Обратная ошибка тоже частая: положили доменные данные в компонентный провайдер и получили копию на каждый компонент (глава 04).

## Что увидишь в legacy-коде

- **`BehaviorSubject`-стор:** `private state$ = new BehaviorSubject(initial); readonly vm$ = this.state$.asObservable();` плюс `state$ | async` в шаблоне. Ровно тот же паттерн «приватная запись, публичное чтение», только на RxJS; переезд на сигналы — механический (глава 09).
- **Классический NgRx:** `createAction`/`createReducer`/`createEffect`/`createSelector`, `StoreModule.forRoot(reducers)` и `forFeature`, `EntityAdapter` из `@ngrx/entity`, `this.store.select(selectTickets)` и `this.store.dispatch(loadTickets())`.
- **Facade-сервисы поверх NgRx** — слой, который прячет `dispatch`/`select` за методами; часто вводили именно для того, чтобы компоненты не знали про стор. С сигнальным сервисом фасад и есть сам стор.
- **`@ngrx/component-store`** — предыдущее поколение локального стора (на компонент/маршрут), `setState`/`patchState`/`select`/`effect` на RxJS. Сегодняшний аналог — сервис с сигналами, предоставленный на уровне компонента.
- **Ручные подписки в компоненте:** `ngOnInit` с `subscribe`, поле `private destroy$ = new Subject()` и `takeUntil(this.destroy$)` в каждом потоке. Ошибиться легко, поэтому и появились сначала `async`-пайп, потом `takeUntilDestroyed` (глава 09), а теперь сигналы, где подписок нет вовсе.

## Что добавляем в проект

Всё состояние тикетов переезжает в `TicketStore`: данные, команды и производные значения. Фильтры и выбор выделяются в отдельный стор экрана, предоставляемый на уровне компонента, — чтобы увидеть разницу во времени жизни. Компоненты после этого не хранят ничего.

## Практическое задание

**Вход:** проект из главы 04 (`TicketService`, конфиг и правила через DI).
**Выход:** два стора с чёткими границами, компоненты без собственного состояния.

Требования:

1. `TicketStore` (уровень приложения): приватный сигнал списка, публичные `readonly`-сигналы и `computed` (общее число, число нераспределённых), команды `add`, `update(id, patch)`, `remove(id)`, `reset()`. Никаких `WritableSignal` наружу — проверьте, что компонент физически не может позвать `set()`.
2. `TicketBoardState` (уровень экрана): статус-фильтр, поисковая строка, выбранный `id`; производный `filtered`, читающий список из `TicketStore`. Предоставьте его на уровне компонента списка и объясните, что изменится при уходе с экрана и возврате.
3. Компоненты `TicketList` и `TicketFilters` не хранят состояния вообще: только чтение сигналов и вызов команд. `TicketFilters` получает значения через `input()` и сообщает об изменениях через `output()` — либо читает стор экрана напрямую; выберите вариант и обоснуйте.
4. Команда `update(id, patch)` должна: обновить тикет иммутабельно, сохранить порядок списка и не трогать выбор, если тикет остался. Продумайте, что делать, если `id` не найден.
5. Добавьте `computed`, который зависит от обоих сторов (например, «выбранный тикет целиком»), и объясните, почему это не создаёт цикла и не требует синхронизации.
6. Ограничение: ни одного `effect`. Если тянет — вы, вероятно, дублируете состояние.

Edge cases на подумать:

- `asReadonly()` защищает от `set()`. Что он **не** защищает, если состояние — массив объектов?
- Два инстанса компонента списка на одном экране (например, две вкладки) с компонентным стором экрана: сколько будет фильтров и правильно ли это?
- Стор экрана читает `TicketStore`. Что произойдёт при уничтожении компонента: не «утечёт» ли подписка на сигнал?
- Когда `computed` вырождается в бессмысленную обёртку и его стоит убрать?
- Как протестировать команду `update`, не создавая ни одного компонента?

## Разбор решения

`src/app/tickets/ticket-store.ts` — доменные данные:

```ts
import { Service, computed, signal } from '@angular/core';
import { Ticket } from './ticket';

@Service()
export class TicketStore {
  // Единственное записываемое место во всём сторе.
  // readonly Ticket[] — чтобы компилятор запретил push/sort на месте
  private readonly state = signal<readonly Ticket[]>(SAMPLE_TICKETS);

  // Наружу — только чтение. Тип Signal<T>, а не WritableSignal<T>,
  // поэтому компонент не сможет позвать set() даже случайно
  readonly tickets = this.state.asReadonly();

  readonly totalCount = computed(() => this.state().length);
  readonly unassignedCount = computed(
    () => this.state().filter((t) => t.assignee === null).length,
  );

  add(ticket: Ticket): void {
    this.state.update((tickets) => [ticket, ...tickets]);
  }

  // Команда описывает намерение и держит инвариант в одном месте:
  // порядок сохраняется, остальные тикеты остаются теми же объектами
  update(id: number, patch: Partial<Omit<Ticket, 'id'>>): void {
    this.state.update((tickets) =>
      tickets.map((ticket) => (ticket.id === id ? { ...ticket, ...patch } : ticket)),
    );
  }

  // Несуществующий id — не ошибка: map просто никого не изменит.
  // Кидать исключение здесь означало бы, что каждый вызывающий обязан
  // проверять существование заранее; в UI это лишняя связанность
  remove(id: number): void {
    this.state.update((tickets) => tickets.filter((ticket) => ticket.id !== id));
  }

  reset(): void {
    this.state.set(SAMPLE_TICKETS);
  }
}
```

`src/app/tickets/ticket-board-state.ts` — состояние экрана:

```ts
import { Service, computed, inject, linkedSignal, signal } from '@angular/core';
import { TicketStatus } from './ticket';
import { TicketStore } from './ticket-store';

// autoProvided: false — этот стор НЕ должен быть глобальным:
// он описывает состояние конкретного экрана и обязан умирать вместе с ним
@Service({ autoProvided: false })
export class TicketBoardState {
  private readonly tickets = inject(TicketStore);

  private readonly statusFilter = signal<TicketStatus | null>(null);
  private readonly searchQuery = signal('');

  readonly status = this.statusFilter.asReadonly();
  readonly search = this.searchQuery.asReadonly();

  // computed через границу сторов: читает и доменные данные, и фильтры.
  // Цикла нет, потому что зависимости однонаправленные:
  // экран знает о данных, данные о экране — нет
  readonly filtered = computed(() => {
    const status = this.statusFilter();
    const query = this.searchQuery().trim().toLowerCase();

    return this.tickets.tickets().filter((ticket) => {
      const statusMatches = status === null || ticket.status === status;
      const titleMatches = query === '' || ticket.title.toLowerCase().includes(query);
      return statusMatches && titleMatches;
    });
  });

  readonly visibleCount = computed(() => this.filtered().length);

  // выбор сбрасывается, когда тикет выпал из выборки (глава 02)
  private readonly selection = linkedSignal<readonly Ticket[], number | null>({
    source: this.filtered,
    computation: (tickets, previous) => {
      const id = previous?.value ?? null;
      return tickets.some((t) => t.id === id) ? id : null;
    },
  });

  readonly selectedId = this.selection.asReadonly();
  readonly selectedTicket = computed(
    () => this.filtered().find((t) => t.id === this.selection()) ?? null,
  );

  setStatus(status: TicketStatus | null): void {
    this.statusFilter.set(status);
  }

  setSearch(query: string): void {
    this.searchQuery.set(query);
  }

  toggleSelection(id: number): void {
    this.selection.update((current) => (current === id ? null : id));
  }
}
```

`src/app/tickets/ticket-list.ts` — компонент без состояния:

```ts
@Component({
  selector: 'app-ticket-list',
  imports: [TicketCard, TicketFilters],

export class TicketList {

  protected readonly board = inject(TicketBoardState);
```

`src/app/tickets/ticket-list.html`:

```html
<section class="ticket-list">
  <header class="ticket-list__header">

```

Обратите внимание на распределение ролей: `TicketStore` ничего не знает про фильтры и про то, что его читают с какого-то экрана; `TicketBoardState` знает про данные, но не владеет ими. Зависимость односторонняя, поэтому «синхронизировать» ничего не нужно — `filtered` пересчитается сам и при смене фильтра, и при добавлении тикета.

Ответы на edge cases:

- `asReadonly()` запрещает `set`/`update` **самого сигнала**, но не делает данные внутри неизменяемыми: `store.tickets()[0].title = 'x'` технически возможен, если объект не защищён типом. Защита — на уровне типов: `readonly` в полях интерфейса `Ticket` и `readonly Ticket[]` для массива. Компилятор поймает и мутацию поля, и `push`.
- Два инстанса компонента — два инстанса `TicketBoardState`, то есть два независимых набора фильтров. Для двух вкладок это ровно то, что нужно: каждая фильтрует по-своему. Если бы фильтры требовалось делить, стор нужно было бы поднять на уровень маршрута или приложения — и это решается конфигурацией провайдера, не переписыванием кода.
- Ничего не утечёт. Зависимость `computed` от сигнала — не подписка с ручным управлением, а ребро графа: когда `TicketBoardState` уничтожается вместе с компонентом, его `computed` становятся недостижимыми и собираются сборщиком мусора. Именно поэтому в сигнальном коде нет `takeUntilDestroyed` и `destroy$`.
- `computed`, который просто возвращает другой сигнал (`readonly x = computed(() => this.y())`), — лишний слой: он ничего не выводит и добавляет узел в граф. Если нужно просто открыть чтение — отдавайте `this.y.asReadonly()`. `computed` оправдан там, где есть вычисление: фильтрация, агрегат, комбинация нескольких источников.
- Тест на команду выглядит как обычный юнит-тест: получить инстанс из `TestBed.inject(TicketStore)`, вызвать `update(...)`, прочитать `tickets()` и сравнить. Ни компонента, ни шаблона, ни `detectChanges` — это и есть главный практический аргумент за вынос логики в сервис (глава 13).

## Проверь себя

1. Объясните своими словами, почему стор отдаёт наружу `Signal<T>`, а не `WritableSignal<T>`, и что именно ломается, если отдать записываемый сигнал.
2. По какому признаку вы решаете, живёт состояние в сервисе уровня приложения или в сторе уровня экрана? Приведите по два примера в каждую сторону.
3. Почему сигнальный сервис ближе к Zustand, чем к Redux, и в чём разница в способе подписки?
4. Назовите три ситуации, в которых NgRx (в любом виде) действительно оправдан, и одну цену, которую вы за это платите независимо от размера проекта.
5. Почему в сигнальном сторе не нужны `takeUntilDestroyed`, `destroy$` и отписки, хотя один сервис читает данные другого?

<details>
<summary>Ответы</summary>

1. Публичный `Signal<T>` даёт чтение, но не даёт `set`/`update` — записывать может только сам стор. Если отдать `WritableSignal<T>`, любой компонент сможет изменить состояние напрямую, минуя команды. Ломаются три вещи: инварианты (сопутствующая логика — пересчёт выбора, валидация, логирование — не выполнится), локализация правил (изменения расползаются по компонентам, и «почему список стал таким» приходится искать по всему проекту) и тестируемость (проверив команды стора, вы больше не можете быть уверены, что состояние меняется только ими).
2. Признак — время жизни и число владельцев. Если данные должны пережить уход с экрана и нужны нескольким местам — это сервис уровня приложения: список тикетов, текущий пользователь. Если состояние осмысленно только на этом экране и должно исчезнуть вместе с ним — это стор экрана: фильтры и сортировка таблицы, выбранная строка, открытая панель деталей. Практический тест: «если пользователь уйдёт и вернётся, он ожидает это увидеть прежним?» — да, значит уровень приложения.
3. Redux — это про поток «действие → редьюсер → новое состояние» с журналом действий; сигнальный сервис такого слоя не имеет. Zustand же — стор снаружи дерева компонентов, который читают напрямую и меняют методами, что структурно совпадает с сервисом. Разница в подписке: в Zustand компонент подписывается селектором и, указав слишком широкий селектор, получает лишние ререндеры; в Angular подписка возникает из самого факта чтения сигнала внутри шаблона или `computed`, поэтому «слишком широкой» она быть не может — вы зависите ровно от того, что прочитали.
4. Оправдан: (а) большая команда и много фич, где ценность в единых конвенциях и предсказуемой форме кода; (б) требование трассируемости — журнал действий, time-travel, воспроизведение сценария по логу, аудит; (в) сложная асинхронная оркестрация — цепочки, отмены, зависимые запросы, где RxJS-эффекты выразительнее ручного кода. Цена, не зависящая от размера проекта: внешняя зависимость со своим релизным циклом — обновление Angular становится возможным только после того, как стор выпустит совместимую версию (на момент написания стабильный NgRx требует `@angular/core ^21`, а поддержка v22 существует только в rc под тегом `next`).
5. Потому что связь между сигналами — это ребро графа зависимостей, а не подписка на поток. `computed` в сторе экрана читает сигнал доменного стора; доменный стор при этом **не хранит** ссылку на потребителя так, чтобы удерживать его в памяти после уничтожения. Когда компонент уничтожается, его стор и все его `computed` становятся недостижимыми и собираются GC. Отписываться не от чего: ничего похожего на `subscribe` не происходило. Именно поэтому целый класс утечек, привычный по RxJS-коду, в сигнальном коде отсутствует.

</details>

## Частая ошибка

Ошибка первая — «один большой стор на всё». Логика знакомая по Redux: раз состояние должно быть в одном месте, положим туда и тикеты, и фильтры, и открытые модалки, и черновик формы. В Angular это особенно легко, потому что сервис доступен отовсюду без обёрток. Последствия проявляются не сразу: фильтры экрана переживают уход с экрана (пользователь возвращается и видит вчерашние настройки), состояние формы висит в памяти после закрытия, а любое изменение UI-части заставляет пересчитываться то, что зависит от доменной. Лечится разделением по времени жизни: доменные данные — в `@Service()` уровня приложения; состояние экрана — в отдельном сторе, объявленном в `providers` компонента или маршрута, чтобы уничтожение происходило автоматически.

Ошибка вторая — копия состояния в компоненте. Выглядит невинно: компонент получает `tickets()` из стора и кладёт в свой сигнал, «чтобы локально отсортировать» или «чтобы не дёргать стор». С этого момента правды две, и они расходятся при первом же изменении: добавили тикет через команду — стор обновился, локальная копия нет. В React эта ошибка тоже встречается (`useState(props.items)`), но там она заметна быстрее, потому что пропсы меняются при каждом ререндере. Правило простое: то, что можно вывести, выводится через `computed`; локальное хранилище заводится только для того, чего в сторе нет вообще, — например, для несохранённого черновика.
