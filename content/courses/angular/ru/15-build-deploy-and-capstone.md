# Сборка, деплой и капстоун

## Теория

### Сборка и конфигурации окружений

Билдер `@angular/build:application` (esbuild/Vite) один и тот же для дев-сервера и прода — различия описываются **конфигурациями** в `angular.json`:

```json
"configurations": {
  "production": {
    "optimization": true,
    "outputHashing": "all",
    "sourceMap": false,
    "budgets": [{ "type": "initial", "maximumError": "500kB" }],
    "define": { "ngDevMode": "false" }
  },
  "staging": {
    "optimization": true,
    "sourceMap": true,
    "fileReplacements": [
      { "replace": "src/config/config.ts", "with": "src/config/config.staging.ts" }
    ]
  }
}
```

Запуск: `ng build --configuration staging`. Полезные опции: `optimization`, `outputHashing` (`none`/`media`/`bundles`/`all` — хеши для кеширования), `sourceMap`, `define` (подстановка констант в код — способ прокинуть флаг сборки), `extractLicenses`, `subresourceIntegrity`, `budgets` (глава 12).

Про конфигурацию окружений важна позиция: `fileReplacements` работает, но это подмена **файла на этапе сборки**, то есть значения зашиты в бандл и не тестируются. Современнее — отдавать конфиг через DI-токен (глава 04) и заполнять его из `define`, из ответа сервера или из `index.html`. Тогда конфиг подменяем в тестах и не требует пересборки при смене стенда.

### SSR и гидратация — обзорно

```
                   Режимы рендеринга: что выбрать для маршрута
┌────────────┬─────────────────────────────────────┬─────────────────────────────┐
│ RenderMode │ когда HTML собирается               │ для чего подходит           │
├────────────┼─────────────────────────────────────┼─────────────────────────────┤
│ Client     │ в браузере (поведение по умолчанию) │ админка, приватные экраны   │
├────────────┼─────────────────────────────────────┼─────────────────────────────┤
│ Server     │ на сервере на каждый запрос         │ персональные данные, SEO    │
├────────────┼─────────────────────────────────────┼─────────────────────────────┤
│ Prerender  │ на сборке, статический файл         │ лендинг, документация, блог │
└────────────┴─────────────────────────────────────┴─────────────────────────────┘
           outputMode: static — только пререндер, серверного файла нет;
           outputMode: server — нужен рантайм, деплой уже не на статику
```

Подключается через `ng new --ssr` или `ng add @angular/ssr`. Режим задаётся **на маршрут**, а не на приложение:

```ts
// app.routes.server.ts
export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },
  { path: 'tickets', renderMode: RenderMode.Server },
  { path: 'admin/**', renderMode: RenderMode.Client },
  {
    path: 'tickets/:id',
    renderMode: RenderMode.Prerender,
    // какие id пререндерить на сборке
    async getPrerenderParams() {
      const api = inject(TicketApi);
      const ids = await api.listIds();
      return ids.map((id) => ({ id: String(id) }));
    },
    fallback: PrerenderFallback.Server,   // остальные — рендерить на сервере
  },
];

// app.config.server.ts
export const serverConfig: ApplicationConfig = {
  providers: [provideServerRendering(withRoutes(serverRoutes))],
};
```

**Гидратация** — процесс, в котором браузерный Angular «оживляет» пришедшую с сервера разметку, не пересоздавая DOM:

```ts
provideClientHydration(
  withEventReplay(),           // события, случившиеся до гидратации, воспроизводятся
  withIncrementalHydration(),  // блоки @defer с hydrate-триггерами (глава 12)
)
```

Что даёт SSR: быстрее первый контент, работающий SEO, лучше метрики загрузки. Чем платите: нужен серверный рантайм (или пререндер), код должен уметь исполняться без DOM (никаких `window`/`document` напрямую — вместо них токены `DOCUMENT`, `REQUEST`, `RESPONSE_INIT`, `REQUEST_CONTEXT`), появляется класс ошибок «на сервере одно, в браузере другое», а состояние надо переносить между средами (для HTTP это делает transfer cache — `withHttpTransferCacheOptions`, глава 08).

Практическое правило: SSR берут, когда есть публичные страницы, которые должны индексироваться или открываться мгновенно. Для внутренней админки за логином выгода близка к нулю, а сложность вполне реальна.

### Деплой статики

Если серверный рантайм не нужен — `outputMode: 'static'`: сборка выдаёт готовые HTML-файлы, которые кладутся на любой статический хостинг (S3+CDN, Netlify, GitHub Pages, nginx). Два обязательных момента:

- **`--base-href`**, если приложение живёт не в корне домена: `ng build --base-href /support-desk/`.
- **Fallback на `index.html`** для SPA-маршрутов: без него прямой переход на `/tickets/101` вернёт 404 от сервера. На nginx это `try_files $uri $uri/ /index.html;`, на S3 — error document, у хостингов — соответствующая настройка.

Про кеширование: с `outputHashing: "all"` имена файлов содержат хеш, поэтому статику можно отдавать с длинным `max-age`, а `index.html` — с `no-cache`. Это стандартная схема, которая закрывает вопрос «пользователь видит старую версию».

### Безопасность

```
                                 Что Angular защищает сам, а что на вас
┌───────────────────────────┬──────────────────────────────────┬───────────────────────────────────────┐
│ контекст                  │ что делает Angular               │ что делаете вы                        │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ интерполяция {{ }}        │ экранирует всё как текст         │ ничего                                │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ [innerHTML]               │ санитизирует HTML                │ не звать bypassSecurityTrustHtml      │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ [href], [src]             │ санитизирует URL                 │ валидировать схему для чужих ссылок   │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ resource URL (script src) │ НЕ санитизирует: там код         │ не строить из пользовательских данных │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ nativeElement.innerHTML   │ не участвует вовсе               │ не использовать (глава 06)            │
├───────────────────────────┼──────────────────────────────────┼───────────────────────────────────────┤
│ CSP                       │ nonce через ngCspNonce/CSP_NONCE │ уникальный nonce на запрос            │
└───────────────────────────┴──────────────────────────────────┴───────────────────────────────────────┘
                   security.autoCsp в angular.json генерирует hash-based strict CSP;
                          по умолчанию выключен — пока это preview-возможность
```

Angular определяет четыре контекста безопасности — HTML, style, URL и resource URL — и санитизирует значения в HTML и URL автоматически. Resource URL (например, `<script src>`) не санитизируется в принципе: там произвольный код, и «почистить» его нельзя. Отсюда правило: значение для `[src]` скрипта или iframe никогда не строится из пользовательских данных.

`DomSanitizer` с методами `bypassSecurityTrust*` существует для случаев «я точно знаю, что это безопасно». Документация формулирует риск прямо: доверяя потенциально злонамеренному значению, вы вносите уязвимость. Практика: `bypassSecurityTrustHtml` в код-ревью требует объяснения, откуда взято значение.

CSP: три способа отдать nonce — `security.autoCsp` в `angular.json` (генерация hash-based strict CSP; по умолчанию выключено, пока фича в preview), атрибут `ngCspNonce` на корневом элементе или токен `CSP_NONCE`. Требование одно и жёсткое: nonce уникален на каждый запрос и непредсказуем. Для SSR отдельно есть `security.allowedHosts` и `trustProxyHeaders` — защита от SSRF через подмену заголовков хоста.

## Параллели с React

- **Конфигурации против `.env`.** В React-стеке окружение обычно приходит через `.env` и `process.env.NEXT_PUBLIC_*`, подставляемые сборщиком. В Angular аналог — `configurations` + `define` (или `fileReplacements` в старом стиле), но идиоматичнее раздавать конфиг через DI-токен: это единственный вариант, который подменяется в тестах.
- **`RenderMode` на маршрут ≈ Next.js per-route rendering.** Идея та же, что `dynamic`/`static` в Next.js: решение принимается для маршрута, а не для приложения. Разница в том, что в Angular SSR — опция, добавляемая к SPA, а в Next.js серверный рендеринг — основа модели.
- **Гидратация.** В React (и Next.js) гидратация — обязательный этап при SSR, и «hydration mismatch» — знакомая ошибка. В Angular гидратация включается провайдером и умеет два трюка, которых в базовом React нет: воспроизведение событий, случившихся до готовности приложения (`withEventReplay`), и порционная гидратация блоков `@defer` (`withIncrementalHydration`).
- **Санитизация из коробки.** JSX экранирует текст, но `dangerouslySetInnerHTML` — прямой путь к XSS без всякой очистки; чистить надо самому (DOMPurify). Angular санитизирует `[innerHTML]` сам, а обход требует явного `bypassSecurityTrust*` — то есть небезопасное действие видно в коде по имени метода.
- **Где ломается привычка:** обращение к `window`/`localStorage` в конструкторе. В SPA это работает всегда, в SSR — падает на сервере. React-разработчик знает симптом («ReferenceError: window is not defined»), но в Angular решение другое: не `typeof window !== 'undefined'`, а инъекция токена `DOCUMENT` или перенос кода в `afterNextRender` (глава 03), который на сервере не выполняется.

## Что увидишь в legacy-коде

- **`@angular-devkit/build-angular:browser`** и webpack-конфиги (`custom-webpack`), `angular.json` с `main`/`polyfills`/`scripts`. Webpack-билдеры помечены deprecated в v22 (глава 00).
- **`environment.ts` + `environment.prod.ts` с `fileReplacements`** как единственный механизм конфигурации и `import { environment } from '../environments/environment'` по всему коду — это то, что мешает подменить URL в тестах.
- **`@nguniversal/express-engine`** и `server.ts` с ручной настройкой Express — предшественник `@angular/ssr`. Признак: `ngExpressEngine`, `APP_BASE_HREF` руками, отсутствие `ServerRoute`.
- **`isPlatformBrowser(inject(PLATFORM_ID))`** в каждом сервисе как способ жить с SSR: работает, но чаще является следствием прямого обращения к `window` там, где хватило бы `DOCUMENT` или `afterNextRender`.
- **`DomSanitizer.bypassSecurityTrustHtml(userContent)`** без комментария о происхождении данных — самая частая уязвимость в Angular-приложениях.
- **`ng build --prod`** в скриптах (флаг удалён в Angular 12, заменён на `--configuration production`) и `ng build && cp -r dist ...` без `--base-href` в деплой-скриптах.

## Что добавляем в проект

Финальная сборка Support Desk: конфигурации `production`/`staging`, конфиг через токен вместо `environment.ts`, статический деплой с fallback на `index.html`, включённый CSP и проверка мест, где приложение доверяет данным. Пререндер лендинга — опционально, как демонстрация `RenderMode`.

Edge cases на подумать:

- `outputMode: 'static'`, но один из маршрутов помечен `RenderMode.Server`. Что произойдёт при сборке?

## Разбор решения

Конфигурации и конфиг через токен:

```json
"configurations": {
  "production": {
    "optimization": true,
    "outputHashing": "all",
    "sourceMap": false,
    "budgets": [
      { "type": "initial", "maximumWarning": "420kB", "maximumError": "500kB" },
      { "type": "anyComponentStyle", "maximumWarning": "4kB", "maximumError": "8kB" }
    ],
    "security": { "autoCsp": true },
    "define": { "API_URL": "'/api/v1'", "ENABLE_ANALYTICS": "true" }
  },
  "staging": {
    "optimization": true,
    "outputHashing": "all",
    "sourceMap": true,
    "define": { "API_URL": "'https://staging.example.com/api'", "ENABLE_ANALYTICS": "false" }
  }
}
```

```ts
// src/app/core/build-flags.d.ts — объявляем то, что подставит define
declare const API_URL: string;
declare const ENABLE_ANALYTICS: boolean;

// app.config.ts
providers: [
  // Конфиг приходит в приложение через токен, а не импортом из environment.ts:
  // так его можно подменить в тестах (глава 13) и на стенде,
  // а define лишь задаёт значения по умолчанию для сборки
  ...provideAppConfig({ apiUrl: API_URL, analyticsEnabled: ENABLE_ANALYTICS }),
]
```

Разница с `fileReplacements` принципиальная: подмена файла означает, что в бандле лежит другой модуль и проверить его в тесте нельзя; `define` — это константа, а токен — точка расширения, которую тест переопределяет провайдером.

Сборка и деплой:

```bash
# прод-сборка в подкаталог, с хешами и бюджетами
npx ng build --configuration production --base-href /support-desk/

# результат — статика: dist/support-desk/browser
```

```nginx
# nginx: главное — fallback на index.html, иначе прямой вход на /tickets/101 даст 404
location /support-desk/ {
  alias /var/www/support-desk/browser/;
  try_files $uri $uri/ /support-desk/index.html;

  # хешированные файлы: имя меняется при каждом изменении содержимого,
  # поэтому их можно кешировать навсегда
  location ~* \.(js|css|woff2|png|svg)$ {
    expires 1y;
    add_header Cache-Control "public, immutable";
  }
}

# index.html НЕ кешируется: именно он содержит ссылки на новые хеши
location = /support-desk/index.html {
  add_header Cache-Control "no-cache";
}
```

Безопасность в коде проекта:

```ts

// пришедшее с сервера. Оно проходит санитизацию Angular автоматически
@Component({
  template: `<div [innerHTML]="ticket().descriptionHtml"></div>`,
})
export class TicketDescription {
  readonly ticket = input.required<Ticket>();
  // bypassSecurityTrustHtml здесь НЕ используется: как только он появляется,
  // ответственность за XSS переходит от фреймворка к нам
}
```

```ts
// Ссылка на внешний ресурс: Angular санитизирует URL-контекст, но схему
// стоит проверить самим — javascript: он вырежет, а вот ссылку
// на фишинговый http-адрес пропустит: это не его забота
protected readonly safeLink = computed(() => {
  const url = new URL(this.ticket().sourceUrl, location.origin);
  return url.protocol === 'https:' ? url.href : null;
});
```

SSR — минимальная конфигурация и первое, что придётся починить:

```ts
// app.routes.server.ts
export const serverRoutes: ServerRoute[] = [
  { path: '', renderMode: RenderMode.Prerender },        // лендинг статикой
  { path: 'tickets', renderMode: RenderMode.Server },    // список — на сервере
  { path: 'admin/**', renderMode: RenderMode.Client },   // админка за логином
];

// app.config.server.ts
export const serverConfig: ApplicationConfig = {
  providers: [provideServerRendering(withRoutes(serverRoutes))],
};

// app.config.ts — на клиенте включаем гидратацию
providers: [
  provideClientHydration(
    withEventReplay(),          // клик, случившийся до гидратации, не потеряется
    withIncrementalHydration(), // @defer-блоки гидратируются порциями (глава 12)
  ),
]
```

```ts
// БЫЛО: падает на сервере — window там не существует
export class ThemeStore {
  private readonly theme = signal(localStorage.getItem('theme') ?? 'light');
}

// СТАЛО: доступ к браузерным API — только после рендера в браузере.
// afterNextRender не выполняется на сервере вообще (глава 03)
export class ThemeStore {
  private readonly current = signal<'light' | 'dark'>('light');
  readonly theme = this.current.asReadonly();

  constructor() {
    afterNextRender(() => {
      const stored = localStorage.getItem('theme');
      if (stored === 'dark' || stored === 'light') this.current.set(stored);
    });
  }
}
```

### Капстоун: что получилось

Support Desk за пятнадцать глав собрал полный набор механизмов Angular:

- **Компоненты и шаблоны** (главы 00–01): standalone, новый control flow, host-биндинги, изоляция стилей.
- **Реактивность** (02–03): сигналы как единственный источник состояния, `computed` вместо пересчётов, zoneless и `OnPush` как дефолты, диагностика через `provideCheckNoChangesConfig` и Profiler.
- **DI и состояние** (04–05): `@Service()`, конфиг через `InjectionToken`, multi-токен правил, домен в сторе приложения и состояние экрана в сторе маршрута.
- **UI-механика** (06, 11): директива подсветки, чистый пайп SLA, `hostDirectives`, дженерик-таблица на `ng-template`, модалка с динамическими компонентами.
- **Данные и навигация** (07–09): маршруты с `canMatch`, входы из параметров, `httpResource`, три интерсептора, живой поиск и поллинг на RxJS.
- **Формы** (10): типизированная форма, кросс-полевая валидация, async-валидатор, `ControlValueAccessor`, взгляд на Signal Forms.
- **Качество** (12–14): профилирование, `@defer`, бюджеты, тесты без `fakeAsync` и с harness'ами, структура по фичам с проверяемыми границами.
- **Прод** (15): конфигурации, статический деплой, CSP, обзор SSR.

## Проверь себя

1. Почему конфиг через `InjectionToken` предпочтительнее `environment.ts` с `fileReplacements`? Назовите два практических следствия.
2. Что произойдёт при прямом переходе на `/tickets/101` в статическом деплое без fallback на `index.html`, и почему?
3. Чем `RenderMode.Prerender` отличается от `RenderMode.Server` с точки зрения инфраструктуры и данных?
4. Что Angular санитизирует автоматически, а что нет, и почему resource URL нельзя очистить?
5. Схема кеширования «хешированные файлы навсегда, `index.html` без кеша» — почему она безопасна и что её ломает?

<details>
<summary>Ответы</summary>

1. `fileReplacements` подменяет **файл на этапе сборки**: в бандле оказывается другой модуль, значение зашито в код, и подменить его в тесте нельзя — тест либо использует тот же файл, либо мокает импорт средствами сборщика. Токен же является точкой расширения: (а) в тестах конфиг задаётся провайдером (`provideAppConfig({ apiUrl: '/api' })`), поэтому тесты не зависят от того, для какого стенда собирали код (глава 13); (б) значение можно получать в рантайме — из `index.html`, из ответа сервера, из переменной окружения через `define`, — и тогда один и тот же артефакт разворачивается на несколько стендов без пересборки. Дополнительно токен виден в графе зависимостей: понятно, кто читает конфиг, тогда как `import { environment }` расползается по файлам незаметно.
2. Сервер вернёт 404: физического файла `/tickets/101` в статике нет, а маршрут существует только внутри приложения, которое запускается из `index.html`. Пока пользователь ходит по ссылкам внутри SPA, роутер меняет URL через History API и запросов к серверу не делает — поэтому проблема проявляется только при прямом входе, перезагрузке страницы или переходе из внешней ссылки. Решение — отдавать `index.html` на любой неизвестный путь (`try_files` в nginx, error document на S3, rewrite-правило у хостинга), после чего маршрутизацию берёт на себя Angular.
3. `Prerender` (SSG) выполняется **на сборке**: результат — статические HTML-файлы, серверный рантайм не нужен, деплой на любой статический хостинг, а данные внутри — те, что были на момент сборки (для параметрических маршрутов список значений даёт `getPrerenderParams`). `Server` (SSR) выполняется **на каждый запрос**: нужен работающий Node-рантайм, можно отдавать персональные данные, заголовки и статус-коды, но каждый запрос стоит времени сервера и требует его масштабирования. Практический выбор: контент, одинаковый для всех и меняющийся редко, — `Prerender`; персональное или часто меняющееся — `Server`; закрытое логином, где SEO не нужен, — `Client`.
4. Автоматически санитизируются контексты HTML (`[innerHTML]`) и URL (`[href]`, `[src]` у изображений и ссылок): опасная разметка и схемы вроде `javascript:` вырезаются. Не санитизируется **resource URL** — то, что задаёт источник исполняемого кода (`<script src>`, `<iframe src>`), потому что содержимое по такому адресу является произвольным кодом: очистить его невозможно, любой «безопасный» URL может вернуть что угодно. Поэтому Angular требует явного `bypassSecurityTrustResourceUrl` для таких значений — то есть заставляет автора кода взять ответственность на себя. Отдельно: обход санитизации через `nativeElement.innerHTML` не проходит через механизм вообще, и никаких проверок там нет.
5. Она безопасна потому, что имя хешированного файла является функцией его содержимого: изменилось содержимое — изменилось имя, значит старый файл никогда не будет отдан вместо нового, и его можно кешировать сколь угодно долго (`immutable`). Единственная точка входа, ссылающаяся на актуальные имена, — `index.html`, и именно она не кешируется, поэтому браузер всегда получает свежий список ссылок. Ломают схему три вещи: `outputHashing` выключен или ограничен (имена стабильны, старый файл продолжает отдаваться); `index.html` попал под кеширование на CDN или в service worker; либо промежуточный прокси кеширует его по своим правилам, игнорируя заголовки. Отсюда практика: проверять заголовки ответов на реальном стенде, а не только конфиг.

## Частая ошибка

Первая — включить SSR «потому что так лучше». Решение выглядит техническим, а является продуктовым: SSR оправдан там, где есть публичные страницы, которым нужны индексация и мгновенный первый экран. Для внутреннего инструмента за логином выгода почти нулевая, а цена реальная: серверный рантайм в инфраструктуре, невозможность деплоя на статику, класс ошибок «работает в браузере, падает на сервере», необходимость думать о переносе состояния и о том, что код исполняется дважды. Симптом неверного решения узнаваем: в проекте появляются `isPlatformBrowser()` и `typeof window !== 'undefined'` в десяти местах — это плата за рендеринг, который никому не нужен. Правильный порядок: сначала ответить, какие страницы должны быть в поиске, потом включать SSR только для них через `RenderMode`.

Вторая — `bypassSecurityTrustHtml` как способ «починить» санитизацию. Выглядит так: описание тикета приходит с бэкенда с разметкой, Angular вырезает часть тегов, разработчик находит в поиске метод, который «решает проблему», и вставляет его. С этого момента фреймворк перестаёт защищать приложение, и любой пользователь, который может влиять на это поле, получает возможность выполнить свой скрипт у остальных. Документация формулирует прямо: доверяя значению, которое может быть злонамеренным, вы вносите уязвимость. Правильные варианты: чистить HTML на сервере по белому списку тегов, отдавать структурированные данные вместо разметки, либо санитизировать явно и осознанно — но никогда не «просто обойти», потому что вырезанный тег мешал вёрстке.
