# Модель Angular и первый запуск

## Теория

### Фреймворк, а не библиотека

React — это библиотека рендеринга. Всё остальное вы выбираете сами: роутер, слой данных, формы, DI, тестовый стек, сборку. Angular — фреймворк: те же задачи уже решены внутри поставки, и решены согласованно.

```
REACT: библиотека + собранный стек              ANGULAR: одна поставка
┌────────────────────────────┐        ┌───────────────────────────────────────┐
│ react + react-dom          │        │ @angular/core                         │
│                            │        │                                       │
│ роутинг   react-router     │        │ роутинг   @angular/router             │
│ данные    TanStack Query   │        │ данные    HttpClient, httpResource    │
│ формы     react-hook-form  │        │ формы     @angular/forms              │
│ DI        Context + пропсы │        │ DI        инжектор в ядре             │
│ тесты     Vitest + RTL     │        │ тесты     TestBed (+ Vitest)          │
│ сборка    Vite / Next.js   │        │ сборка    Angular CLI, @angular/build │
└────────────────────────────┘        └───────────────────────────────────────┘
каждая строка — свой выбор, свой           один мажор на всё, одна команда
  мажор и свой релизный цикл              ng update, меньше решений на входе
```

Что это даёт на практике:

- **Одно обновление на всё.** `ng update` поднимает ядро, роутер, формы, HTTP и CLI одним согласованным шагом и запускает **схематики миграции** — код-моды, которые механически переписывают ваш код под новые API. В React-стеке апгрейд — это N независимых миграций, каждая со своим гайдом.
- **Один способ делать типовые вещи.** Незнакомый Angular-проект читается быстрее: роутинг там, где ожидаешь, HTTP через `HttpClient`, зависимости через инжектор. В React два проекта на одном стеке могут быть непохожи вообще ни в чём.
- **Компилятор, а не только рантайм.** Шаблоны компилируются в код, а типы в шаблонах проверяются (`strictTemplates`). Опечатка в имени свойства в шаблоне — ошибка сборки, а не пустое место на экране.

Цена ровно та, что и ожидается: больше конвенций и больше API, которые нужно знать до того, как напишешь первую строку; меньше свободы выбрать «свой» роутер или свой слой данных; свои идиомы (декораторы, DI, шаблоны), которые нельзя объяснить через «это просто JS». Плюс объём: Angular нельзя «взять частично», как React.

### Ментальная модель: инстанс вместо функции

Это главное различие, и почти все ошибки React-разработчика в Angular растут из него.

В React компонент — функция, которая при каждом обновлении вызывается заново. Состояние живёт снаружи (в хуках), потому что тело функции — одноразовое. В Angular компонент — **класс, инстанс которого создаётся один раз** при появлении view в дереве и живёт до его удаления. Поля инстанса и есть состояние — им не нужен внешний контейнер. Тело класса и конструктор не перевызываются при обновлении: перевызывается только вычисление шаблона.

```
   REACT: функция от состояния         ANGULAR: долгоживущий инстанс
┌───────────────────────────────┐     ┌──────────────────────────────┐
│ setState(next)                │     │ count.set(next)              │
│               ↓               │     │              ↓               │
│ функция компонента вызывается │     │ сигнал помечает зависимые    │
│ заново — новые замыкания,     │     │ шаблоны грязными и планирует │
│ новые пропсы для детей        │     │ проверку                     │
│               ↓               │     │              ↓               │
│ React обходит поддерево;      │     │ change detection проходит по │
│ дети тоже рендерятся заново,  │     │ помеченным view; инстансы    │
│ если их не остановил memo     │     │ классов те же, меняется DOM  │
└───────────────────────────────┘     └──────────────────────────────┘
состояние живёт снаружи, в хуках;     инстанс класса создаётся один раз
тело функции — это и есть "рендер"    на время жизни view; тело класса
                                      не перевызывается при обновлении
```

Следствия, которые стоит принять сразу:

- **Нет «правил хуков»**, потому что нет пересборки замыканий: порядок вызовов ничего не значит, условный вызов ничего не ломает. Зато `inject()` имеет своё ограничение — контекст инъекции (глава 04).
- **Нет stale closure** как класса ошибок: `this.filter` всегда актуален, потому что это поле живого объекта, а не значение, захваченное в старом рендере.
- **Появляется отдельный механизм — change detection**: раз тело класса не перевызывается, кто-то должен решать, когда пересчитать шаблон и обновить DOM. Ответ на это — сигналы (глава 02) и change detection (глава 03).
- **Мутация не запрещена рантаймом, но опасна.** В React вы мутировали бы стейт и не увидели обновления. В Angular с `OnPush` (а это теперь дефолт) мутация объекта внутри сигнала точно так же не сообщит системе об изменении — механизм другой, симптом тот же.

### Где сейчас Angular: версии и статусы API

Angular быстро менялся последние три года, и в интернете полно материалов, описывающих предыдущее поколение API как «современное». Ориентир на момент написания курса:

- **Актуальный мажор — Angular v22** (вышел 3 июня 2026). Каденция — мажор раз в полгода, у каждого мажора окно поддержки с LTS-фазой; v21 (ноябрь 2025) в LTS.
- **Стабильно и является основным путём:** standalone-компоненты (дефолт с v19), `inject()`, новый control flow `@if`/`@for`/`@switch`/`@let`, `@defer`, функциональные guards и interceptors, вся реактивность на сигналах — `signal`, `computed`, `effect`, `linkedSignal`, сигнальные `input()`/`output()`/`model()` и сигнальные queries (стабилизированы в v20), асинхронная реактивность `resource()`/`httpResource` и Signal Forms (стабилизированы в v22), сборка на esbuild/Vite (`@angular/build`).
- **Zoneless change detection — дефолт для новых проектов с v21.** `zone.js` в новом workspace просто нет; `provideZonelessChangeDetection()` в конфиге появляется только при апгрейде старого проекта.
- **`OnPush` — дефолт для компонентов с v22.** Не через настройку схематика: компонент без поля `changeDetection` теперь работает в режиме `OnPush`. Прежнее «проверяем всегда» получило честное имя `ChangeDetectionStrategy.Eager` (алиас `Default`, добавлен в v21.2), и миграция `ng update` до v22 явно вписывает `Eager` во все существующие компоненты, чтобы поведение старого кода не изменилось.
- **Экспериментальное / developer preview** (знать о существовании, не строить на этом курс): selectorless-компоненты (импорт компонента прямо в шаблоне, без строкового селектора), декоратор `@Service`, `injectAsync()`, `@boundary` для обработки ошибок в шаблоне.
- **Deprecated:** webpack-сборка и билдеры `@angular-devkit/build-angular`. Karma/Jasmine вытеснены Vitest (`--test-runner` по умолчанию `vitest`), но встречаются в каждом втором существующем проекте.

Практический вывод: статус API в Angular нужно проверять по [angular.dev](https://angular.dev) и разделу roadmap, а не по статье из блога. Разрыв между «как пишут в статьях 2023 года» и «как пишут сейчас» здесь больше, чем в React.

### TypeScript, декораторы, strict

TypeScript в Angular не опция: шаблонный компилятор работает по типам, а DI до недавнего времени опиралась на метаданные типов конструктора. `ng new` создаёт workspace со `--strict` по умолчанию, и это включает не только строгие флаги TS, но и `strictTemplates` — проверку типов внутри шаблонов (тип входа компонента, тип выражения в биндинге, сигнатура события).

Декораторы (`@Component`, `@Injectable`, `@Directive`, `@Pipe`) — не рантайм-магия и не аннотации ради красоты. Это **метаданные для компилятора Angular**: он читает объект в декораторе на этапе сборки (AOT), компилирует `template` в инструкции рендеринга и вписывает результат в класс. Поэтому поля декоратора должны быть статически анализируемы — нельзя собрать объект метаданных в рантайме и передать его в `@Component`.

### Angular CLI и структура проекта

CLI здесь — не удобная обёртка, а часть фреймворка: сборка, дев-сервер, тесты, генерация кода и миграции живут в нём.

- `ng new <name>` — новый workspace. Полезные флаги: `--style`, `--ssr`, `--package-manager`, `--test-runner` (дефолт `vitest`), `--file-name-style-guide` (дефолт `2025` — файлы без суффиксов `.component`/`.service`), `--ai-config`, `--strict` (дефолт `true`).
- `ng generate <schematic>` (`ng g`) — генерация по схематикам: `component`, `service`, `directive`, `pipe`, `guard`, `interceptor`, `resolver`. `--dry-run` показывает, что будет создано, ничего не записывая.
- `ng serve` — дев-сервер, `ng build` — прод-сборка (глава 15), `ng test` — тесты (глава 13), `ng update` — апгрейд с миграциями.
- `angular.json` — конфигурация workspace: проекты, targets (`build`/`serve`/`test`), конфигурации окружений и **дефолты схематиков** (в существующем проекте туда часто вписаны старые конвенции имён — это то, чем `ng g` в реальном проекте отличается от `ng g` в свежем).

Скелет приложения, который выдаёт `ng new` (стиль имён 2025 — без суффиксов в именах файлов и классов):

```
support-desk/
├── angular.json          конфигурация workspace и targets
├── package.json          @angular/* одной версией
├── tsconfig.json         базовый TS-конфиг + angularCompilerOptions
├── tsconfig.app.json     конфиг сборки приложения
├── tsconfig.spec.json    конфиг тестов
├── public/               статика, копируется в бандл как есть
└── src/
    ├── main.ts           точка входа: bootstrapApplication(App, appConfig)
    ├── index.html         <app-root></app-root>
    ├── styles.css        глобальные стили
    └── app/
        ├── app.ts        корневой компонент (класс App, селектор app-root)
        ├── app.html      его шаблон
        ├── app.css       его стили
        ├── app.spec.ts   его тест
        ├── app.config.ts ApplicationConfig: провайдеры уровня приложения
        └── app.routes.ts таблица маршрутов
```

Ключевое отличие от того, что вы могли видеть раньше: **никакого `app.module.ts`**. Приложение стартует не с модуля, а с корневого компонента — `bootstrapApplication(App, appConfig)`, а провайдеры перечислены в `app.config.ts`. Модули (`NgModule`) остались только в старых проектах.

## Параллели с React

- **Импорт класса ≠ доступность в шаблоне.** В JSX `import { TicketList }` — и вы уже можете писать `<TicketList/>`, потому что это обычная ссылка на функцию в области видимости JS. Шаблон Angular не JS: чтобы `<app-ticket-list>` распознался, компонент должен быть в массиве `imports` того компонента, в чьём шаблоне он используется. TS-импорт нужен, но недостаточен — это первая ошибка, на которую натыкаются все.
- **Точка входа приложения.** `createRoot(el).render(<App/>)` монтирует дерево и на этом заканчивается. `bootstrapApplication(App, appConfig)` одновременно создаёт **root-инжектор** со всеми провайдерами приложения — то есть точка входа в Angular конфигурирует ещё и DI-контейнер, из которого потом всё приложение достаёт зависимости (глава 04).
- **Жизненный цикл.** `useEffect(() => {...}, [])` — это код внутри функции, которая вызывается заново каждый рендер, и вы вручную ограничиваете его массивом зависимостей. В Angular `ngOnInit`/`ngOnDestroy` — методы объекта, вызываемые фреймворком один раз за жизнь инстанса. Никакого «а вдруг вызовется дважды» — но и никакого автоматического пересчёта при изменении данных: за это отвечают сигналы.
- **Изоляция стилей.** В React изоляция — вопрос выбранного инструмента (CSS-модули, styled-components, Tailwind). В Angular она встроена: стили компонента по умолчанию скоупятся эмуляцией Shadow DOM (атрибуты вида `_ngcontent-*`), и это поведение, о котором нужно знать заранее — глобальный селектор из компонента «не работает» именно поэтому (глава 01).
- **Где ломается привычка:** в React вы привыкли, что «перерисовалось всё поддерево, значит новые данные точно доехали». В Angular обновление адресное: пересчитываются только те шаблоны, которым сообщили об изменении. Если сообщения не было (мутация вместо `set`, значение вне сигнала), DOM останется прежним — и «React-рефлекс» искать ошибку в данных вместо механизма оповещения уводит в сторону на часы.

## Что увидишь в legacy-коде

- **`app.module.ts` и `platformBrowserDynamic().bootstrapModule(AppModule)`** вместо `bootstrapApplication`. Провайдеры — в `providers` модуля, компоненты — в `declarations`, зависимости — в `imports` модуля, а не компонента.
- **`standalone: true` явно в декораторе.** До v19 standalone был опцией, которую надо было включать; в свежем коде этого флага нет вообще, а `standalone: false` означает «этот компонент всё ещё принадлежит какому-то NgModule».
- **Суффиксы в именах:** `ticket-list.component.ts` с классом `TicketListComponent`, `ticket.service.ts` с `TicketService`. Это конвенция style guide 2016; она не «неправильная», просто прошлая — и в существующем проекте её надо сохранять (дефолты схематиков в `angular.json` обычно уже настроены под неё после `ng update`).
- **`zone.js` в `polyfills`** в `angular.json` (или отдельный `polyfills.ts` с `import 'zone.js'`), `karma.conf.js` и `test.ts` для Karma+Jasmine, `@angular-devkit/build-angular:browser` как билдер в `angular.json` — три надёжных маркера того, что проект не проходил недавних миграций.
- **`environment.ts` / `environment.prod.ts`** с `fileReplacements` в `angular.json` — старый способ конфигурации окружений; сейчас конфиг чаще прокидывают через DI-токен (глава 04) и `--configuration` (глава 15).

## Что добавляем в проект

Создаём workspace **Support Desk** — системы тикетов поддержки, которую будем достраивать все 16 глав, — и вводим в неё первый собственный компонент: shell приложения с заголовком и заглушку списка тикетов, чтобы дальше было куда наращивать данные, роутинг и формы.

## Практическое задание

**Вход:** пустая папка и установленный Node LTS.
**Выход:** запущенное приложение Support Desk с собственным компонентом внутри корневого.

Требования:

1. Создайте workspace `support-desk`: CSS в качестве стилей, без SSR, тестовый ранер по умолчанию. Не используйте глобально установленный `ng` неизвестной версии — зафиксируйте версию CLI явно при создании.
2. Прежде чем писать код, разберитесь в сгенерированном проекте и ответьте себе на пять вопросов: где точка входа; что именно делает `bootstrapApplication`; что лежит в `app.config.ts` и зачем это отдельный файл; почему нет `app.module.ts`; чем `tsconfig.app.json` отличается от `tsconfig.spec.json`.
3. Сгенерируйте компонент списка тикетов в папке `tickets`. Сначала посмотрите план генерации, не создавая файлов, потом создайте. Обратите внимание на итоговые имена файла, класса и селектора — и на то, что поля `changeDetection` в декораторе нет: выясните по документации, какая стратегия применяется в этом случае.
4. Компонент показывает заголовок «Tickets» и число тикетов из поля класса (пока константа) через интерполяцию.
5. Замените содержимое шаблона корневого компонента на shell: заголовок приложения `Support Desk` и ниже — список тикетов. Название приложения храните в поле корневого компонента, а не в разметке.
6. Запустите дев-сервер, убедитесь, что всё рендерится, затем сделайте прод-сборку и посмотрите на размер бандла в отчёте.

Edge cases на подумать:

- Что произойдёт (и на каком этапе — сборка или рантайм), если убрать компонент из `imports` корневого, оставив TS-импорт?
- Почему в шаблоне используется `app-ticket-list`, а не имя класса? Откуда взялся префикс `app-` и где он настраивается?
- Если переименовать файл в `ticket-list.component.ts` — что сломается, а что нет?
- Чем `ng build` отличается от `ng serve` не по действию, а по конфигурации, с которой собирается код?
- В `src/app` рядом с компонентом лежит `.spec.ts`, который вы ещё не открывали. Он уже проходит? Что он проверяет?

## Разбор решения

Создание workspace:

```bash
# фиксируем версию CLI явно, без глобальной установки
npx @angular/cli@22 new support-desk --style=css --ssr=false
cd support-desk

# что вообще стоит в проекте и какой мажор
npx ng version
```

Точка входа — `src/main.ts`, её генерирует CLI:

```ts
import { bootstrapApplication } from '@angular/platform-browser';
import { appConfig } from './app/app.config';
import { App } from './app/app';

// Создаёт root-инжектор из appConfig, инстанцирует App
// и монтирует его в <app-root> из index.html.
bootstrapApplication(App, appConfig).catch((err) => console.error(err));
```

`src/app/app.config.ts` — конфигурация уровня приложения. Всё, что должно быть одним инстансом на приложение, регистрируется здесь:

```ts
import { ApplicationConfig, provideBrowserGlobalErrorListeners } from '@angular/core';
import { provideRouter } from '@angular/router';
import { routes } from './app.routes';

export const appConfig: ApplicationConfig = {
  providers: [
    provideBrowserGlobalErrorListeners(),
    provideRouter(routes),
    // сюда позже добавится provideHttpClient() с интерсепторами — глава 08
  ],
};
```

Обратите внимание: `provideZonelessChangeDetection()` здесь нет — в v21+ zoneless является режимом по умолчанию, и `zone.js` в проекте отсутствует. Если создать проект с `--no-zoneless`, схематик добавит сюда `provideZoneChangeDetection({ eventCoalescing: true })` — именно это вы увидите в старом проекте, который ещё живёт на zone.js.

Генерация компонента — сначала план, потом запись:

```bash
npx ng generate component tickets/ticket-list --dry-run
# CREATE src/app/tickets/ticket-list.ts
# CREATE src/app/tickets/ticket-list.html
# CREATE src/app/tickets/ticket-list.css
# CREATE src/app/tickets/ticket-list.spec.ts
# NOTE: The "--dry-run" option means no changes were made.

npx ng generate component tickets/ticket-list
```

`src/app/tickets/ticket-list.ts` (сгенерированный каркас, наполненный содержимым):

```ts
import { Component } from '@angular/core';

@Component({
  // селектор — то, как компонент выглядит в шаблоне; префикс app- берётся
  // из настройки prefix проекта в angular.json
  selector: 'app-ticket-list',
  imports: [],
  templateUrl: './ticket-list.html',
  styleUrl: './ticket-list.css',
  // поля changeDetection нет намеренно: с v22 отсутствие поля означает
  // OnPush — компонент проверяется только когда ему сообщили об
  // изменении. Явный Eager вернул бы старое "проверяем всегда" (глава 03)
})
export class TicketList {
  // Поле инстанса — это и есть состояние компонента. Инстанс живёт,
  // пока view в дереве, поэтому внешний контейнер для состояния не нужен.
  // На сигналы переведём в главе 02, когда данные начнут меняться.
  readonly totalCount = 3;
```

Ответы на edge cases:

- Убрать компонент из `imports` — **ошибка сборки**, а не пустой экран: `NG8001: 'app-ticket-list' is not a known element`. Шаблон компилируется, и незнакомый тег с дефисом — повод для ошибки. Это принципиальная разница с React, где незарегистрированного «тега» просто не существует как понятия.
- В шаблоне используется селектор, потому что шаблон — не JS: компилятор сопоставляет элементы разметки с селекторами компонентов и директив из области видимости. Префикс `app-` задаётся полем `prefix` проекта в `angular.json` и нужен, чтобы селекторы не конфликтовали с будущими нативными элементами и с чужими библиотеками. (Экспериментальный selectorless-режим как раз убирает этот слой, но он ещё не для продакшена.)
- Переименование файла в `ticket-list.component.ts` не сломает ничего, кроме конвенции: нужно поправить путь TS-импорта, а `templateUrl` остаётся прежним. Имена файлов для Angular не значимы — значимы декораторы и импорты. Смешивать два стиля в одном проекте не стоит: `ng g` продолжит генерировать по настройке из `angular.json`.
- `ng serve` собирает с конфигурацией `development` (sourcemaps, без оптимизации, watch), `ng build` — с `production` (минификация, tree-shaking, хеши в именах файлов, бюджеты бандла). Отсюда классическое «в дев-режиме работало»: разница именно в конфигурации, а не в командах.
- Сгенерированный `.spec.ts` проходит: он поднимает компонент через `TestBed` и проверяет, что тот создаётся. Пользы почти нет, но он показывает, как выглядит точка входа в тесты — подробно в главе 13.

## Проверь себя

1. Объясните своими словами, почему в Angular не нужны правила хуков и не возникает stale closure — и какая проблема появляется вместо них.
2. Компонент импортирован в TS-файл, но не добавлен в `imports` декоратора. Почему это ошибка **сборки**, а не тихо пустой DOM? Что это говорит об устройстве шаблонов Angular?
3. Чем `bootstrapApplication(App, appConfig)` отличается от `createRoot(el).render(<App/>)` по объёму выполняемой работы — что появляется в Angular, чего в React-варианте нет вообще?
4. Почему поля объекта в декораторе `@Component` нельзя вычислять в рантайме? Что именно делает с ними Angular и когда?
5. Zoneless — дефолт с v21, `OnPush` — дефолт для новых компонентов с v22. Что эти два дефолта говорят о том, откуда фреймворк теперь ожидает получать сигнал «данные изменились»?

<details>
<summary>Ответы</summary>

1. Правила хуков в React существуют потому, что состояние сопоставляется с вызовами по порядку внутри функции, которая вызывается заново каждый рендер; stale closure — потому что колбэк захватывает значения конкретного рендера. В Angular компонент — долгоживущий инстанс: состояние лежит в полях объекта, `this.x` всегда читает текущее значение, а тело класса выполняется один раз. Ни порядок вызовов, ни захват значений роли не играют. Вместо этого появляется новая проблема: раз ничего не перевызывается автоматически, нужен отдельный механизм оповещения об изменениях — change detection и сигналы. Ошибка «не обновляется» в Angular почти всегда про него, а не про данные.
2. Шаблон Angular компилируется, а не исполняется как JS. У каждого компонента есть своя **область видимости шаблона** — список компонентов, директив и пайпов из `imports`; компилятор сопоставляет каждый элемент разметки с селекторами из этого списка. Незнакомый тег с дефисом не может быть валидным HTML-элементом, поэтому это диагностируемая ошибка компиляции (`NG8001`), а не «пусто на экране». TS-импорт лишь делает класс доступным для значения в массиве `imports` — сам по себе он ничего не регистрирует.
3. `createRoot().render()` монтирует дерево — и всё; контекстов, провайдеров и сервисов там нет, пока вы их не отрендерите как компоненты. `bootstrapApplication` дополнительно создаёт **root-инжектор** из `appConfig`: все `provide*`-функции (роутер, HTTP, конфиг) исполняются и образуют DI-контейнер уровня приложения, из которого зависимости достаются через `inject()` в любом месте, без прокидывания через дерево. То есть точка входа в Angular конфигурирует не только рендеринг, но и всю систему зависимостей.
4. Декоратор — это метаданные для компилятора Angular (AOT), который читает их **на этапе сборки**: компилирует `template` в инструкции рендеринга, вычисляет область видимости из `imports`, генерирует фабрику компонента. К моменту запуска приложения в браузере метаданные уже «запечены» в код, поэтому их значения должны быть статически анализируемы — динамически собранный объект компилятор увидеть не может.
5. Оба дефолта означают: фреймворк больше не пытается угадать изменение, перехватывая асинхронные операции (`zone.js`) или проверяя всё дерево на каждый чих. Сигнал об изменении теперь приходит явно и адресно — из сигналов (`set`/`update`), а также из событий шаблона и `markForCheck`. Отсюда практическое следствие: состояние, которое влияет на разметку, должно жить в сигналах, иначе системе просто нечем узнать, что пора перепроверить шаблон.

</details>

## Частая ошибка

Первая ошибка почти каждого React-разработчика: сгенерировал компонент, поставил тег в шаблон, получил `NG8001: 'app-ticket-list' is not a known element` — и начинает искать проблему в пути импорта или в имени файла, потому что «класс же импортирован». В React импорт в область видимости JS **и есть** регистрация: `<TicketList/>` — это просто вызов функции по ссылке. В Angular шаблон компилируется отдельно и имеет собственную область видимости, заданную массивом `imports` в декораторе того компонента, где тег используется. Правило простое: в каждом компоненте, где вы пишете чужой тег, директиву или пайп, соответствующий класс должен быть перечислен в `imports` — локально, а не «где-то один раз в приложении» (последнее было верно для NgModules и осталось привычкой из legacy-кода).

Вторая ошибка тоньше и всплывает позже: код в конструкторе воспринимается как «тело функции-компонента» и туда кладут логику, которая должна реагировать на изменение данных, — а конструктор вызывается один раз за жизнь инстанса и больше никогда. Обратный вариант той же путаницы — вычисления в геттере или в методе, вызываемом из шаблона (`{{ getFilteredTickets() }}`): такой метод исполняется при **каждой** проверке шаблона, то есть неопределённо часто, и в React-модели «это же просто вызов внутри рендера» звучит безобидно, а в Angular становится источником тормозов. Инициализация — конструктор или `ngOnInit`; реакция на изменение данных — `computed` (глава 02).
