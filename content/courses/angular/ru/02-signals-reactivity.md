# Сигналы и реактивность

## Теория

### Сигнал как единица состояния

Сигнал — это значение, которое знает, кто его читает. Три вещи, из которых состоит API:

```ts
const count = signal(0);          // WritableSignal<number>
count();                          // чтение — и одновременно регистрация зависимости
count.set(5);                     // новое значение
count.update((n) => n + 1);       // новое значение из предыдущего
const readonlyCount = count.asReadonly(); // Signal<number> для публичного API
```

Читается сигнал вызовом — и это не косметика: **факт вызова и есть подписка**. Когда `count()` вызывается внутри `computed`, `effect` или шаблона, реактивный контекст, в котором произошло чтение, запоминается как потребитель.

Список зависимостей нигде не объявляется. Он собирается по фактическим чтениям при каждом пересчёте, поэтому зависимости могут меняться от прогона к прогону: условное чтение — условная зависимость.

Сравнение значений — `Object.is` по умолчанию. Если новое значение равно старому, потребители не оповещаются. Для не-примитивов это означает: **мутация объекта — это не изменение**. `tickets().push(t)` не оповестит никого, потому что ссылка та же.

Отсюда правило: с сигналами работают иммутабельно, как в `set([...arr, t])`. Если структуру дорого копировать, задайте свою функцию сравнения: `signal(value, { equal: myEqual })`.

### computed: ленивость и мемоизация

```ts
readonly tickets = signal<readonly Ticket[]>([]);
readonly statusFilter = signal<TicketStatus | null>(null);

readonly filtered = computed(() => {
  const status = this.statusFilter();
  const all = this.tickets();
  return status === null ? all : all.filter((t) => t.status === status);
});
```

```
  ┌─────────────────────────┐    ┌─────────────────────────────┐
  │ tickets = signal([...]) │    │ statusFilter = signal(null) │
  └─────────────────────────┘    └─────────────────────────────┘
               ▼                                ▼
┌────────────────────────────────────────────────────────────────┐
│ filtered = computed(() => ...)                                 │
│ читает оба сигнала → подписка строится сама,                   │
│ по факту чтения, а не по списку зависимостей                   │
└────────────────────────────────────────────────────────────────┘
                ▼                                  ▼
┌───────────────────────────────┐    ┌───────────────────────────┐
│ шаблон @for (t of filtered()) │    │ openCount = computed(...) │
└───────────────────────────────┘    └───────────────────────────┘
```

Механика в двух словах: изменение сигнала **помечает** зависимые узлы графа как устаревшие (push), а пересчёт происходит **при чтении** (pull). Из этого следуют свойства, которых нет у ручных пересчётов:

- **Ленивость.** Если `filtered()` никто не читает (например, блок с этим списком скрыт `@if`), функция не выполняется вообще.
- **Мемоизация.** Пока зависимости не менялись, повторные чтения возвращают закешированное значение. Поэтому `filtered()` можно спокойно читать пять раз в шаблоне.
- **Отсутствие «промежуточных» состояний.** Даже если изменить несколько сигналов подряд, каждый читатель увидит согласованный результат, а не цепочку промежуточных пересчётов.
- **`computed` только читает.** У него нет `set`; если хочется «производное, но чтобы можно было перезаписать» — это `linkedSignal`.

### linkedSignal: производное состояние, которое можно перезаписать

Классическая задача: выбранный элемент. Он зависит от списка (при смене списка выбор надо сбросить), но пользователь может его менять. `computed` не подходит — он read-only; `effect`, синхронизирующий два сигнала, — распространённая ошибка. Для этого есть `linkedSignal`:

```ts
// короткая форма: пересчитывается при изменении читаемых сигналов
readonly selectedId = linkedSignal(() => this.filtered()[0]?.id ?? null);

// расширенная форма: есть доступ к предыдущему значению
readonly selectedTicket = linkedSignal<readonly Ticket[], Ticket | null>({
  source: this.filtered,
  computation: (tickets, previous) =>
    tickets.find((t) => t.id === previous?.value?.id) ?? tickets[0] ?? null,
});

// и при этом это записываемый сигнал
this.selectedId.set(105);
```

Смысл: значение живёт как обычное состояние (принимает `set`/`update`), но при изменении источника пересчитывается заново, затирая ручной выбор. Расширенная форма позволяет «сохранить выбор, если он всё ещё есть в новом списке».

### effect: почему это не useEffect

`effect` регистрирует функцию, которая перезапускается при изменении прочитанных ею сигналов:

```ts
effect((onCleanup) => {
  const id = this.selectedId();          // зависимость
  const timer = setTimeout(() => this.markSeen(id), 3000);
  onCleanup(() => clearTimeout(timer));  // перед следующим прогоном и при уничтожении
});
```

Что важно знать про механику:

- **Зависимости не объявляются.** Нет массива, как в `useEffect`; отслеживается то, что фактически прочитано. Чтение, которое не должно создавать зависимость, оборачивается в `untracked()`.
- **Время запуска.** Эффекты, созданные в контексте компонента, выполняются как часть синхронизации Angular (в связке с change detection этого компонента), а корневые — как микротаска. Это изменилось в v19: раньше эффекты планировались независимо.
- **Уничтожение автоматическое.** Эффект живёт в контексте инъекции, в котором создан (обычно поле компонента или сервиса), и уничтожается вместе с ним. Ручной вариант: `manualCleanup: true` + `ref.destroy()`, или передать `injector` явно, если создаёте эффект не в контексте инъекции.
- **Запись сигналов внутри эффекта разрешена.** Флаг `allowSignalWrites` был удалён в v19. Разрешена — не значит рекомендована: эффект, который пишет сигнал, обычно должен был быть `computed` или `linkedSignal`.

Где `effect` действительно нужен: логирование и аналитика, синхронизация с `localStorage`, императивные API (canvas, карты, сторонние виджеты), `focus()`/скролл, интеграция с не-реактивным кодом. Где не нужен — почти всё остальное:

| задача | инструмент | почему именно он |
|---|---|---|
| значение выводится из других | `computed` | ленив, мемоизирован, только чтение |
| состояние из источника, но перезаписываемое | `linkedSignal` | сброс при смене источника, плюс `set`/`update` |
| выход во внешний мир: логи, storage, `focus()` | `effect` | ничего не возвращает, важен сам эффект |
| один сигнал повторяет другой | ни один | дублирование — ошибка модели данных |

### Сигнальные входы, выходы и запросы

| объявление | что получаем | в шаблоне родителя |
|---|---|---|
| `input<T>()` | сигнал только для чтения: `T` или `undefined` | `[x]="expr"` |
| `input.required<T>()` | `Signal<T>`; без биндинга — ошибка сборки | `[x]="expr"` |
| `input(0, { transform })` | значение проходит через `transform` | `[x]="expr"` |
| `output<T>()` | объект с `emit(value)` | `(x)="onX($event)"` |
| `model<T>(init)` | записываемый сигнал плюс выход `xChange` | `[(x)]="expr"` |
| `viewChild.required(Cmp)` | `Signal<Cmp>` из своего шаблона | — |
| `contentChildren(Cmp)` | `Signal<readonly Cmp[]>` из проекции | — |

Детали, которые стоит держать в голове:

- Вход — **сигнал только для чтения**: компонент не может писать в свой `input`. Записываемый вход — это `model()`, и он же автоматически создаёт выход `xChange`, за счёт которого работает `[(x)]`.
- `transform` должен быть чистой и статически анализируемой функцией; встроенные `booleanAttribute` и `numberAttribute` покрывают приведение из атрибутов.
- `alias` меняет только имя в шаблоне, не имя поля.
- Входы записываются компилятором статически: добавить или убрать вход в рантайме нельзя.
- Сигнальные запросы (`viewChild` и родня) возвращают сигналы, а не `QueryList`, и не требуют `ngAfterViewInit`. Результат становится доступен, когда соответствующий элемент появляется, и обновляется реактивно. По умолчанию `contentChildren` смотрит только на прямых потомков; глубже включает `descendants: true`.

### Что даёт точечное обновление

Граф зависимостей — это причина, по которой Angular обновляет DOM (document object model, дерево объектов страницы в браузере) адресно. Изменение `statusFilter` помечает грязным `filtered`, тех, кто читает `filtered`, и шаблоны, где эти чтения происходят, — и ровно эти шаблоны будут перепроверены. Ни родительский компонент, ни соседние карточки в работу не попадают.

В React аналогичной точности добиваются вручную: `useMemo`, `memo`, разделение контекстов, селекторы стора. В Angular это свойство самого механизма чтения.

## Параллели с React

- **`signal` против `useState`.** Оба хранят состояние, но `useState` возвращает снимок текущего рендера, а сигнал — живую ссылку на значение. Отсюда три следствия. Нет функциональных обновлений «чтобы не потерять актуальное состояние»: `count.update` — удобство, а не необходимость. Нет stale-значений в колбэках. И нет батчинга-как-семантики: значение доступно сразу после `set`, а DOM обновится при следующей синхронизации.
- **`computed` против `useMemo`.** `useMemo` требует ручного списка зависимостей. Он пересчитывается при каждом рендере, где эти зависимости изменились, — независимо от того, нужен ли результат. `computed` собирает зависимости сам и ленив: не читают — не считает. Ошибка в списке зависимостей как класс проблем исчезает.
- **`effect` против `useEffect` — главное расхождение.** В React `useEffect` — универсальный инструмент: и подписки, и производные данные, и синхронизация состояния, и загрузка данных. В Angular `effect` — узкий инструмент для выхода во внешний мир. Производные данные — `computed`, производное состояние — `linkedSignal`, загрузка данных — `resource`/`httpResource` (глава 08). Перенос привычки «сделаю effect, который пересчитает и запишет» даёт лишние прогоны, гонки и трудноуловимые циклы.
- **`input()` против пропсов.** Проп в React — обычное значение в замыкании рендера; сигнальный вход — сигнал, поэтому его можно читать в `computed` без «прокидывания в зависимости» и передавать дальше как источник реактивности. Обратная сторона: вход нельзя писать, а `input.required()` нельзя читать до того, как биндинг применён — в конструкторе он ещё пуст (`ngOnInit` и позже — уже нет).
- **Где ломается привычка:** в React мутация состояния «не работает» очевидным образом — компонент просто не перерисуется, и это быстро обнаруживается. В Angular мутация массива внутри сигнала выглядит успешной. Данные в памяти изменились, отладчик показывает новый элемент, а DOM прежний. Причина: `Object.is` сравнил ссылку и решил, что изменения не было. Это самая долгая по времени поиска ошибка новичка в сигналах.

## Что увидишь в legacy-коде

- **`@Input()` и `@Output()` с декораторами:** `@Input() ticket!: Ticket;`, `@Output() selected = new EventEmitter<Ticket>();`. Работают до сих пор; `EventEmitter` под капотом Subject, из-за чего в старом коде на выходы иногда подписываются как на Observable.
- **`ngOnChanges(changes: SimpleChanges)`** — реакция на изменение входов до сигналов. С сигнальными входами он не нужен: вход сам реактивен, а «на изменение входа посчитать» — это `computed`.
- **Поля класса без сигналов + `ChangeDetectorRef`:** `constructor(private cdr: ChangeDetectorRef)` и `this.cdr.markForCheck()` после асинхронного обновления. Это ручная замена того, что сигнал делает сам (глава 03).
- **`@ViewChild('input') input!: ElementRef;` + `ngAfterViewInit`** и `QueryList` с `.changes.subscribe(...)` — до сигнальных запросов результат нельзя было прочитать раньше определённого хука, а на его изменение подписывались вручную.
- **`BehaviorSubject` как состояние сервиса** и `state$ | async` в шаблоне: `private state = new BehaviorSubject(initial); readonly state$ = this.state.asObservable();`. Это предыдущее поколение того же паттерна «приватная запись, публичное чтение» (главы 05 и 09).

## Что добавляем в проект

Список тикетов переезжает на сигналы: массив становится `signal`, фильтры по статусу и поисковой строке — отдельными сигналами, отфильтрованный список и счётчики — `computed`. Карточка получает выход для выбора тикета, а панель фильтров — `model()` для двусторонней связи.

## Практическое задание

**Вход:** проект из главы 01 (статичный массив, `TicketCard` с `input.required`).
**Выход:** список с работающими фильтрами, счётчиками и выбором тикета — всё на сигналах, без единого `effect`.

Требования:

1. `TicketList`: массив тикетов — `signal`. Два сигнала фильтра: статус (`TicketStatus | null`) и строка поиска.
2. Производные значения — только `computed`. Решите заодно, считается каждый счётчик от отфильтрованного списка или от исходного, — и что должно означать «Total».
   - Отфильтрованный список: статус **и** регистронезависимый поиск по заголовку.
   - Общее число, число нераспределённых и число `urgent`-тикетов в текущей выборке.
3. Компонент `TicketFilters` (новый): вход — список доступных статусов; двусторонняя связь по выбранному статусу через `model()`; поисковая строка — тоже `model()`. Никаких `@Input`/`@Output`-декораторов.
4. `TicketCard`: добавьте выход через `output<Ticket>()` и клик по хосту, который его испускает. Имя выхода не должно совпадать с нативным DOM-событием — подумайте, почему.
5. Выбранный тикет храните в `linkedSignal`, привязанном к отфильтрованному списку. При смене фильтра выбор сбрасывается — кроме случая, когда выбранный тикет остался в выборке.
6. Добавление тикета: кнопка «Add sample ticket», которая добавляет запись в начало списка. Сделайте это так, чтобы обновление увидел и список, и счётчики (подсказка: главное — как именно вы меняете массив).
7. Запрет: ни одного `effect` в этой главе. Если кажется, что он нужен, — вы, скорее всего, дублируете состояние.

Edge cases на подумать:

- Что произойдёт, если вместо `set` использовать `this.tickets().push(newTicket)`? Почему в консоли всё «правильно», а на экране нет?
- `input.required<Ticket>()` в конструкторе — что вернёт? А в `ngOnInit`?
- Если `computed` читает сигнал внутри `if`, а условие сначала было `false`, — какие у него зависимости и что будет, когда условие станет `true`?
- Дважды подряд `statusFilter.set('open')` — сколько раз пересчитается `filtered`?
- В `linkedSignal` вы храните объект тикета. Что случится при добавлении тикета в список — сохранится ли выбор, если сравнивать по ссылке?

## Разбор решения

`src/app/tickets/ticket-filters.ts` — панель фильтров на `model()`:

```ts
import { Component, input, model } from '@angular/core';
import { TicketStatus } from './ticket';

@Component({
  selector: 'app-ticket-filters',
  templateUrl: './ticket-filters.html',
  styleUrl: './ticket-filters.css',
})
export class TicketFilters {
  // обычный вход: список статусов только читается
  readonly statuses = input.required<readonly TicketStatus[]>();

  // model() = записываемый сигнальный вход + автоматический выход statusChange.
  // Родитель пишет [(status)]="statusFilter" и получает двустороннюю связь
  readonly status = model<TicketStatus | null>(null);
  readonly search = model('');
}
```

`src/app/tickets/ticket-card.ts` — добавился выход:

```ts
import { Component, computed, input, output } from '@angular/core';
import { DatePipe } from '@angular/common';
import { Ticket } from './ticket';

@Component({
  selector: 'app-ticket-card',
  imports: [DatePipe],
  templateUrl: './ticket-card.html',
  styleUrl: './ticket-card.css',
  host: {
    class: 'ticket-card',
    '[class.ticket-card--urgent]': 'isUrgent()',
    '[class.ticket-card--selected]': 'selected()',
    '[attr.aria-label]': '"Ticket #" + ticket().id',
    '(click)': 'selectTicket.emit(ticket())',
  },
})
export class TicketCard {
  readonly ticket = input.required<Ticket>();
  // обычный булев вход: карточка не решает, выбрана ли она, — ей говорят
  readonly selected = input(false);

  // output() вместо @Output() + EventEmitter: у него нет API Subject,
  // на который в старом коде подписывались напрямую.
  // Имя не select, чтобы не пересекаться с нативным событием select
  readonly selectTicket = output<Ticket>();

  protected readonly isUrgent = computed(() => this.ticket().priority === 'urgent');
}
```

```ts
  protected readonly statusFilter = signal<TicketStatus | null>(null);
  protected readonly search = signal('');

  // Производные значения. computed ленив: если блок скрыт @if,
  // тело даже не выполнится
  protected readonly filtered = computed(() => {
    const status = this.statusFilter();
    const query = this.search().trim().toLowerCase();

    return this.tickets().filter((ticket) => {
      const statusMatches = status === null || ticket.status === status;
      const titleMatches = query === '' || ticket.title.toLowerCase().includes(query);
      return statusMatches && titleMatches;
    });
  });

  // Total — от полного списка: это свойство данных, а не выборки.
  // Остальные счётчики — от выборки: они описывают то, что видит пользователь
  protected readonly totalCount = computed(() => this.tickets().length);
  protected readonly visibleCount = computed(() => this.filtered().length);
  protected readonly unassignedCount = computed(
    () => this.filtered().filter((t) => t.assignee === null).length,
  );
  protected readonly urgentCount = computed(
    () => this.filtered().filter((t) => t.priority === 'urgent').length,
  );

  // Выбор: производное состояние, которое можно перезаписать вручную.
  // source — отфильтрованный список; computation получает новое значение
  // источника и предыдущее значение самого linkedSignal
  protected readonly selectedId = linkedSignal<readonly Ticket[], number | null>({
    source: this.filtered,
    computation: (tickets, previous) => {
      const previousId = previous?.value ?? null;
      // выбор сохраняется, если тикет остался в выборке; иначе сбрасывается
      return tickets.some((t) => t.id === previousId) ? previousId : null;
    },
  });

  protected select(ticket: Ticket): void {
    // повторный клик снимает выбор — обычное состояние, обычный set
    this.selectedId.update((id) => (id === ticket.id ? null : ticket.id));
  }

  protected addSampleTicket(): void {
    const nextId = Math.max(...this.tickets().map((t) => t.id)) + 1;

    // Новый массив, а не push: сигнал сравнивает значения через Object.is,
    // и мутация той же ссылки не оповестила бы никого
    this.tickets.update((tickets) => [
      {
        id: nextId,
        title: `Sample ticket #${nextId}`,
        status: 'new',
        priority: 'medium',
        assignee: null,
        createdAt: new Date().toISOString(),
      },
      ...tickets,
    ]);
  }
}
```

`src/app/tickets/ticket-list.html`:

```html
<section class="ticket-list">
  <header class="ticket-list__header">

    <!-- двусторонняя связь: [(status)] разворачивается в
```

Три решения в этом коде стоит отметить особо. Первое: `tickets` — приватный сигнал, наружу торчат только `computed`. Это заготовка того, что в главе 05 станет сервисом-стором.

Второе: выбранным хранится `id`, а не объект. При обновлении списка объект может быть заменён новым с теми же данными, и сравнение по ссылке потеряло бы выбор. Третье: в шаблоне нет ни одного вызова метода класса — только чтения сигналов и `computed`.

Ответы на edge cases:

- `this.tickets().push(newTicket)` изменит массив, но сигнал об этом не узнает: `set` не вызывался, а `Object.is(oldArray, oldArray)` — `true`. В консоли данные новые (вы смотрите на тот же живой объект), на экране старые. Вдобавок `readonly Ticket[]` в типе не даст вызвать `push` — тип здесь работает как страховка от этой самой ошибки.
- В конструкторе `input.required()` бросит ошибку: биндинги ещё не применены, а «обязательный вход без значения» — некорректное состояние. Читать входы можно с `ngOnInit` и позже, а лучше — вообще не читать императивно, а завернуть в `computed`, который прочитает их в момент первого использования.
- Зависимости `computed` собираются по фактическим чтениям текущего прогона. Если условие было `false` и вторая ветка не читалась, её сигналы в зависимостях отсутствуют. Когда условие станет `true` (это изменение придёт от сигнала, который *был* прочитан), `computed` пересчитается, прочитает новые сигналы — и они добавятся в граф. Никаких действий от разработчика не требуется, и это принципиальное отличие от статического массива зависимостей.
- Ноль раз. Второй `set('open')` не изменит значение (`Object.is` равны), потребители не будут помечены. А если бы значения отличались, `filtered` пересчитался бы один раз — при следующем чтении, а не при каждом `set`.
- При добавлении тикета `filtered` вернёт новый массив, где остальные объекты — те же ссылки, так что сравнение по ссылке в данном конкретном случае сработает. Но как только список начнёт приходить из HTTP (глава 08), после каждой перезагрузки это будут новые объекты с теми же `id`, и выбор терялся бы на каждом обновлении. Поэтому в решении хранится `id`.

## Проверь себя

1. Объясните своими словами, почему `computed` не нуждается в списке зависимостей и что физически происходит в момент `signal.set(...)` — до того, как кто-либо прочитал зависимое значение.
2. Почему мутация объекта внутри сигнала не приводит к обновлению DOM, и какие два способа с этим жить существуют?
3. В каких трёх ситуациях `effect` — правильный инструмент, и почему «пересчитать одно состояние из другого» в этот список не входит?
4. Чем `linkedSignal` отличается от `computed` и от пары «сигнал + effect, который его перезаписывает»?
5. `model<T>()` — что именно он создаёт и почему это работает в связке `[(x)]`? Чем он отличается от `input()` с точки зрения того, кто владеет состоянием?

<details>
<summary>Ответы</summary>

1. Зависимости не объявляются, потому что чтение сигнала — само по себе регистрация. Когда `computed` выполняет своё тело, активен реактивный контекст, и каждый вызванный внутри сигнал записывает этот контекст как своего потребителя. Список получается точным по построению (в нём ровно то, что реально прочитано) и динамическим (условное чтение — условная зависимость). При `signal.set(...)` пересчёта не происходит: сигнал сравнивает новое значение со старым через `Object.is`, и если оно отличается, помечает потребителей устаревшими (грязными) вниз по графу. Вычисление произойдёт позже — при первом чтении. Это разделение push-оповещения и pull-вычисления и даёт ленивость.
2. Сигнал сравнивает **значения**, а для объектов и массивов сравнение по умолчанию — это сравнение ссылок (`Object.is`). Мутация оставляет ссылку прежней, значит «изменения не было»: потребители не помечаются, DOM не трогается. Выходов два.

   - **Работать иммутабельно.** `set`/`update` возвращают новый объект или массив, а тип `readonly` заставляет компилятор ловить мутации.
   - **Передать свою функцию сравнения**, `signal(value, { equal })`. Оправдано, когда копирование структуры дороже сравнения, — но тогда `set` придётся вызывать вручную и осознанно.
3. `effect` уместен там, где результат — воздействие на что-то вне реактивного графа:

   - запись во внешнее хранилище, лог или аналитику;
   - императивные API — canvas, карта, сторонний виджет, `focus()`, прокрутка;
   - интеграция с не-реактивным кодом, которому нужно «сообщить» об изменении.

   «Пересчитать состояние из состояния» сюда не входит. У этого есть возвращаемое значение, и оно должно жить в графе: `computed` — если только чтение, `linkedSignal` — если нужен ещё и ручной `set`. Эффект в этой роли создаёт второй источник правды, лишние прогоны и риск циклов. А запись сигналов внутри эффектов разрешена с v19, так что рантайм вас не остановит.

4. `computed` — только чтение: перезаписать его нельзя, он всегда равен своей формуле. `linkedSignal` — записываемый сигнал, значение которого пересчитывается при изменении источника, то есть «состояние с правилом сброса». Пара «сигнал + effect» делает то же самое, но хуже. Состояние обновляется в отдельном прогоне, поэтому существует момент, когда сигнал и источник рассогласованы. Порядок эффектов не гарантирован. А расширенная форма `linkedSignal` даёт доступ к предыдущему значению, которое в связке с эффектом пришлось бы хранить руками.
5. `model<T>(init)` создаёт **записываемый** сигнальный вход и парный выход с именем `<имя>Change`. Именно поэтому работает `[(x)]="expr"` — это сахар над `[x]` + `(xChange)`, и `model` предоставляет обе половины. Разница с `input()` — в том, кто владеет состоянием. Вход `input` только читается, и единственный владелец значения родитель. А `model` — это общее владение: дочерний компонент может записать значение, и родитель об этом узнает. Практический критерий: если компонент по своей природе «редактирует» переданное значение (контрол, фильтр, аккордеон), это `model`; если только отображает — `input` плюс, при необходимости, `output` для события.

</details>

## Частая ошибка

Ошибка номер один — `effect` вместо `computed`. Выглядит она так:

```ts
// не делайте так
readonly filtered = signal<readonly Ticket[]>([]);

constructor() {
  effect(() => {
    this.filtered.set(this.tickets().filter((t) => t.status === this.statusFilter()));
  });
}
```

Код работает, поэтому и живёт в проектах. Но теперь у одних и тех же данных два источника правды — `tickets` и его отфильтрованная копия, — и они рассогласованы в течение одного прогона синхронизации.

Дальше это даёт три симптома. После первого клика фильтр правильный, а после быстрого второго отстаёт на один шаг. На экране мигает старая выборка. И как только появляется второй такой эффект, начинаются циклы обновлений.

`computed` решает ту же задачу без копии состояния: он не хранит, а выводит, и ленив в придачу. Практическое правило: если внутри `effect` есть `set`/`update` — почти наверняка это `computed` или `linkedSignal`.

Вторая частая ошибка — мутация внутри сигнала: `this.tickets().push(t)`, `this.filters().status = 'open'`, `arr().sort()`. React-разработчик в курсе, что стейт надо обновлять иммутабельно, но там нарушение видно сразу: компонент не перерисовался.

В Angular мутация «почти работает». Допустим, проверка шаблона случилась по другой причине — клик, другой сигнал, таймер. Новые данные внезапно появятся на экране, и ошибка превратится в плавающую: «иногда обновляется, иногда нет».

Защита дешёвая: типизируйте состояние как `readonly Ticket[]`/`Readonly<T>`, и компилятор запретит `push`/`sort`/присваивание поля вместо вас. Отдельно помните про `sort()` и `reverse()` — они мутируют массив на месте, поэтому в `computed` над сигналом нужен `toSorted()` или копия через spread.
