# Роутинг

## Теория

### Конфигурация маршрутов

Маршруты — обычный массив объектов, передаваемый в `provideRouter(routes)`:

```ts
export const routes: Routes = [
  { path: '', pathMatch: 'full', redirectTo: 'tickets' },
  {
    path: 'tickets',
    title: 'Tickets',                    // заголовок вкладки, ставит роутер
    loadComponent: () => import('./tickets/ticket-list').then((m) => m.TicketList),
    children: [
      { path: 'new', loadComponent: () => import('./tickets/ticket-form').then((m) => m.TicketForm) },
      { path: ':id', loadComponent: () => import('./tickets/ticket-detail').then((m) => m.TicketDetail) },
    ],
  },
  {
    path: 'admin',
    canMatch: [adminGuard],              // отсекает маршрут ДО загрузки чанка
    providers: [provideAdminTools()],    // свой EnvironmentInjector (глава 04)
    loadChildren: () => import('./admin/admin.routes').then((m) => m.ADMIN_ROUTES),
  },
  { path: '**', loadComponent: () => import('./core/not-found').then((m) => m.NotFound) },
];
```

Что стоит отметить сразу: порядок важен (маршруты проверяются сверху вниз, `'**'` всегда последний); `path: ':id'` идёт **после** `path: 'new'`, иначе `/tickets/new` совпадёт с параметром; `providers` на маршруте создаёт собственный инжектор, живущий столько же, сколько маршрут.

### Что происходит при навигации

```
Что происходит между кликом по ссылке и появлением экрана
┌───────────────────────────────────────────────────┐
│ URL: /admin/reports?range=7d                      │
└───────────────────────────────────────────────────┘
                          │  сопоставление
                          ▼
┌───────────────────────────────────────────────────┐
│ подбор маршрута сверху вниз + canMatch            │
│ false → маршрут пропускается, пробуем следующий   │
└───────────────────────────────────────────────────┘
                          │  маршрут найден
                          ▼
┌───────────────────────────────────────────────────┐
│ загрузка ленивого чанка                           │
│ loadComponent / loadChildren + providers маршрута │
└───────────────────────────────────────────────────┘
                          │  код загружен
                          ▼
┌───────────────────────────────────────────────────┐
│ canDeactivate текущего → canActivate нового       │
│ false → навигация отменяется, URL не меняется     │
└───────────────────────────────────────────────────┘
                          │  доступ есть
                          ▼
┌───────────────────────────────────────────────────┐
│ resolve: навигация ЖДЁТ данные                    │
│ ошибка → навигация падает                         │
└───────────────────────────────────────────────────┘
                          │  данные готовы
                          ▼
┌───────────────────────────────────────────────────┐
│ создание компонентов в router-outlet              │
│ входы заполняет withComponentInputBinding         │
└───────────────────────────────────────────────────┘
canMatch отсекает маршрут ДО загрузки чанка, canActivate — после:
для ленивых разделов с ролями это разница в мегабайтах
```

Навигация — не «показать компонент», а конвейер с несколькими точками отказа. Понимание порядка даёт две вещи: вы знаете, куда вставлять проверку, и понимаете, почему «страница мигнула и вернулась» (гард отработал после начала навигации).

### Гарды

```
┌──────────────────┬─────────────────────────────┬───────────────────────────┬─────────────────────┐
│ гард             │ когда выполняется           │ что значит false          │ типичный случай     │
├──────────────────┼─────────────────────────────┼───────────────────────────┼─────────────────────┤
│ canMatch         │ при подборе маршрута        │ пробуем следующий маршрут │ фича-флаг, роль     │
├──────────────────┼─────────────────────────────┼───────────────────────────┼─────────────────────┤
│ canActivate      │ после подбора, до resolve   │ навигация отменяется      │ требуется вход      │
├──────────────────┼─────────────────────────────┼───────────────────────────┼─────────────────────┤
│ canActivateChild │ для каждого дочернего       │ навигация отменяется      │ защита раздела      │
├──────────────────┼─────────────────────────────┼───────────────────────────┼─────────────────────┤
│ canDeactivate    │ при уходе с маршрута        │ остаёмся на месте         │ несохранённая форма │
├──────────────────┼─────────────────────────────┼───────────────────────────┼─────────────────────┤
│ resolve          │ после гардов, до компонента │ ошибка навигации          │ данные до рендера   │
└──────────────────┴─────────────────────────────┴───────────────────────────┴─────────────────────┘
```

Гард — обычная функция, выполняемая в контексте инъекции, поэтому внутри доступен `inject()`:

```ts
export const authGuard: CanActivateFn = (route, state) => {
  const auth = inject(AuthService);
  const router = inject(Router);

  if (auth.isLoggedIn()) return true;

  // вернуть можно boolean, UrlTree или RedirectCommand — последний
  // позволяет задать ещё и параметры навигации
  return new RedirectCommand(router.parseUrl('/login'), {
    state: { returnTo: state.url },
  });
};
```

Ключевое различие, которое спрашивают на собеседованиях: **`canMatch` работает на этапе сопоставления, `canActivate` — после**. Практических следствий два. Первое: `canMatch: false` не отменяет навигацию, а заставляет роутер продолжить перебор — по одному пути можно показать разные компоненты разным ролям. Второе: `canMatch` отсекает маршрут **до** загрузки ленивого чанка, а `canActivate` — уже после; для админ-раздела это разница между «пользователь не скачал админку» и «скачал, но не увидел».

Старый `canLoad` помечен deprecated в пользу `canMatch`; классовые гарды (`implements CanActivate`) — тоже.

### Чтение состояния маршрута

```
                                  Как прочитать состояние маршрута
┌─────────────────────────────────────┬──────────────────────────────┬─────────────────────────────┐
│ способ                              │ что даёт                     │ когда брать                 │
├─────────────────────────────────────┼──────────────────────────────┼─────────────────────────────┤
│ input() + withComponentInputBinding │ сигнал, роутер обновляет сам │ в компоненте — по умолчанию │
├─────────────────────────────────────┼──────────────────────────────┼─────────────────────────────┤
│ toSignal(route.params)              │ сигнал из Observable         │ в сервисе или гарде         │
├─────────────────────────────────────┼──────────────────────────────┼─────────────────────────────┤
│ route.snapshot.paramMap             │ значение на момент создания  │ одноразовое чтение          │
├─────────────────────────────────────┼──────────────────────────────┼─────────────────────────────┤
│ route.params.subscribe              │ поток изменений              │ старый код, глава 09        │
└─────────────────────────────────────┴──────────────────────────────┴─────────────────────────────┘
               снимок не обновляется при смене :id, если компонент переиспользован —
                     это источник бага "открыл другой тикет, а данные прежние"
```

Современный путь — `withComponentInputBinding()`: роутер сам подставляет параметры маршрута, query-параметры и `data` во **входы** компонента, по совпадению имён.

```ts
provideRouter(routes, withComponentInputBinding());

// компонент на маршруте /tickets/:id?tab=history
export class TicketDetail {
  readonly id = input.required<string>();       // из параметра маршрута
  readonly tab = input('details');              // из query-параметра
}
```

Никакого `ActivatedRoute`, никаких подписок, и входы обновляются при смене параметра — даже если компонент переиспользуется. Собственного сигнального API у `ActivatedRoute` нет: вне компонентов (в сервисе, гарде) параметры превращают в сигнал через `toSignal(route.params, { requireSync: true })`.

Отдельно про `snapshot`: он валиден на момент создания компонента. Если при навигации с `/tickets/1` на `/tickets/2` роутер переиспользует тот же инстанс — а он так и делает, когда меняется только параметр, — `snapshot` останется прежним, и `ngOnInit` повторно не вызовется. Это самая частая ловушка Angular-роутинга.

### Ленивая загрузка

`loadComponent` грузит один компонент, `loadChildren` — набор маршрутов (обычно файл `feature.routes.ts`, экспортирующий `Routes`). Оба принимают функцию с динамическим `import()`, поэтому сборщик автоматически выделяет чанк.

Предзагрузка настраивается фичей: `withPreloading(PreloadAllModules)` тянет все ленивые чанки после старта приложения, свои стратегии позволяют грузить, например, только помеченные `data: { preload: true }`.

Полезные фичи `provideRouter`: `withComponentInputBinding()`, `withViewTransitions()` (анимация через View Transitions API), `withInMemoryScrolling({ scrollPositionRestoration: 'enabled', anchorScrolling: 'enabled' })`, `withRouterConfig({ onSameUrlNavigation: 'reload' })`, `withHashLocation()`, `withNavigationErrorHandler(fn)`, `withDebugTracing()`. В v22 добавились экспериментальные `withExperimentalPlatformNavigation()` (интеграция с браузерным Navigation API) и `withExperimentalAutoCleanupInjectors` (автоматическое уничтожение неиспользуемых маршрутных инжекторов).

### Резолверы: нужны ли

`ResolveFn` задерживает навигацию, пока данные не готовы. Плюс — компонент открывается уже с данными и не мигает пустотой. Минусы: пользователь смотрит на старую страницу, не понимая, что происходит; ошибка резолвера ломает навигацию целиком; данные приходят в `data`, а не в сигналы, и обновлять их потом нечем.

Практическая позиция: резолвер уместен для того, что действительно должно быть до рендера — проверить существование сущности и увести на 404, подставить `title`, дозагрузить конфиг раздела. Данные самого экрана лучше грузить в компоненте через `httpResource` (глава 08): состояние загрузки и ошибки становится частью UI, а не навигации.

## Параллели с React

- **Роутер — часть фреймворка.** В React вы выбираете библиотеку и версию, и API между мажорами меняется заметно. В Angular роутер один, обновляется вместе с фреймворком и в `ng update` мигрируется схематиками. Меньше свободы, но и меньше решений: конфигурация маршрутов в проекте выглядит одинаково.
- **Гарды против компонентов-обёрток.** Типичный React-приём — `<RequireAuth><Dashboard/></RequireAuth>`: проверка выполняется **во время рендера**, то есть компонент уже смонтирован, а чанк уже загружен. Гард в Angular выполняется до создания компонента, а `canMatch` — вообще до загрузки кода. Практическая разница: в React защита от «случайно скачал админку» требует отдельной работы, в Angular это одна строка конфигурации.
- **Резолвер против `loader` в data-роутере React.** Идея та же — данные до рендера. Но в React Router `loader` — основной способ загрузки данных, а в Angular резолвер конкурирует с `httpResource`, который отдаёт `loading`/`error` как сигналы. Поэтому в Angular резолверы стоит применять реже, чем `loader` в React.
- **Параметры маршрута.** `useParams()` возвращает значения на каждом рендере, и React-компонент обычно перемонтируется при смене ключа. В Angular компонент переиспользуется, а входы обновляются — то есть аналог `key` не нужен, но нужно писать код, реагирующий на изменение входа (`computed`, а не разовое чтение в `ngOnInit`).
- **Где ломается привычка:** ожидание, что при смене `/tickets/1` → `/tickets/2` экран «пересоздастся». Он не пересоздаётся: тот же инстанс, тот же `snapshot`, `ngOnInit` не вызывается. Код, написанный по React-привычке «прочитать параметр при монтировании», молча показывает старые данные.

## Что увидишь в legacy-коде

- **`RouterModule.forRoot(routes)` / `forChild(routes)`** в NgModules и `loadChildren: './admin/admin.module#AdminModule'` строкой (до Angular 8). Сейчас — `provideRouter` и динамический `import()`.
- **Классовые гарды и резолверы:** `@Injectable({providedIn:'root'}) export class AuthGuard implements CanActivate` и `class TicketResolver implements Resolve<Ticket>`, перечисленные в маршруте как классы. Функциональные аналоги короче и не требуют регистрации.
- **`canLoad: [AuthGuard]`** — предшественник `canMatch`, помечен deprecated. Разница: `canLoad` только предотвращал загрузку чанка, `canMatch` ещё и позволяет продолжить перебор маршрутов.
- **`route.params.subscribe(...)` в `ngOnInit`** с ручной отпиской и `route.snapshot.paramMap.get('id')` без реакции на изменения — два поколения решений одной задачи, которые сегодня закрывает `withComponentInputBinding`.
- **`data: { roles: ['admin'] }` + один универсальный гард**, читающий `route.data`, — рабочий приём, но с функциональными гардами чаще пишут фабрику: `canActivate: [hasRole('admin')]`.
- **Кастомный `RouteReuseStrategy`** с `shouldDetach`/`shouldAttach` для «вкладок с сохранением состояния». В v22 для этого добавили официальный `destroyDetachedRouteHandle()` — раньше отсоединённые view нередко утекали.

## Что добавляем в проект

Support Desk получает настоящую навигацию: список тикетов, детальную страницу по `:id`, форму создания и ленивый админ-раздел, закрытый ролью через `canMatch`. Параметры приходят во входы компонентов, а уход с недозаполненной формы перехватывается `canDeactivate`.

## Практическое задание

**Вход:** проект из главы 06 (сторы, директива, пайп).
**Выход:** четыре маршрута, ленивый админ-раздел и две работающие защиты.

Требования:

1. Настройте `provideRouter` с `withComponentInputBinding()` и восстановлением позиции скролла. Маршруты: `/tickets` (список), `/tickets/new` (форма-заглушка), `/tickets/:id` (деталь), `/admin` (ленивый), `**` (404). Проверьте, что порядок `new` и `:id` имеет значение.
2. `TicketDetail` получает `id` **входом**, а не через `ActivatedRoute`. Тикет берётся из `TicketStore` по `id` через `computed`. Убедитесь, что при переходе с `/tickets/101` на `/tickets/102` содержимое меняется, и объясните, почему `ngOnInit` при этом не вызывается.
3. Админ-раздел: отдельный файл `admin.routes.ts` с двумя дочерними маршрутами, подключённый через `loadChildren`, и `canMatch`-гард по роли. Проверьте в DevTools (вкладка Network), что чанк админки не скачивается пользователем без роли.
4. `canDeactivate` для формы: если в форме есть несохранённые изменения, уход запрашивает подтверждение. Гард должен работать с типизированным компонентом, а не с `any`.
5. Резолвер: для `/tickets/:id` проверьте существование тикета и при отсутствии верните редирект на 404 (`RedirectCommand` или `UrlTree`). Обсудите в комментарии, почему сами данные тикета вы через резолвер **не** передаёте.
6. Ссылки: используйте `routerLink` с массивом сегментов и `routerLinkActive`; программную навигацию оставьте только там, где она действительно нужна (после сохранения формы).

Edge cases на подумать:

- Что произойдёт с `/tickets/new`, если поставить его после `/tickets/:id`?
- Компонент детали переиспользуется при смене `:id`. Что случится с состоянием, которое вы держите в его полях, и что — с `input()`?
- `canMatch` вернул `false`, а других подходящих маршрутов нет. Что увидит пользователь?
- Query-параметр `?tab=history` привязан ко входу `tab`. Что окажется во входе при `?tab=history&tab=notes`?
- Почему `providers` на маршруте админки — это не то же самое, что `providers` в корневом конфиге, и когда эти сервисы уничтожатся?

## Разбор решения

`src/app/app.routes.ts`:

```ts
import { Routes } from '@angular/router';
import { adminMatchGuard } from './admin/admin-guard';
import { ticketExistsGuard } from './tickets/ticket-exists-guard';
import { unsavedChangesGuard } from './core/unsaved-changes-guard';

export const routes: Routes = [
  { path: '', pathMatch: 'full', redirectTo: 'tickets' },
  {
    path: 'tickets',
    title: 'Tickets',
    loadComponent: () => import('./tickets/ticket-list').then((m) => m.TicketList),
  },
  {
    // ВАЖНО: статический сегмент объявляется раньше параметра,
    // иначе /tickets/new совпадёт с :id и id станет строкой "new"
    path: 'tickets/new',
    title: 'New ticket',
    loadComponent: () => import('./tickets/ticket-form').then((m) => m.TicketForm),
    canDeactivate: [unsavedChangesGuard],
  },
  {
    path: 'tickets/:id',
    loadComponent: () => import('./tickets/ticket-detail').then((m) => m.TicketDetail),
    // резолвер здесь только проверяет существование и уводит на 404;
    // сами данные компонент читает из стора (а в главе 08 — из httpResource)
    resolve: { exists: ticketExistsGuard },
  },
  {
    path: 'admin',
    // canMatch, а не canActivate: без роли маршрут не совпадёт вовсе,
    // и чанк админки не будет загружен
    canMatch: [adminMatchGuard],
    loadChildren: () => import('./admin/admin.routes').then((m) => m.ADMIN_ROUTES),
  },
  { path: '**', loadComponent: () => import('./core/not-found').then((m) => m.NotFound) },
];
```

`src/app/tickets/ticket-detail.ts`:

```ts
import { Component, computed, inject, input, numberAttribute } from '@angular/core';
import { RouterLink } from '@angular/router';
import { TicketStore } from './ticket-store';

@Component({
  selector: 'app-ticket-detail',
  imports: [RouterLink],
  templateUrl: './ticket-detail.html',
})
export class TicketDetail {
  private readonly store = inject(TicketStore);

  // Вход заполняет роутер. transform: numberAttribute — потому что из URL
  // всё приходит строкой, а стор работает с числовым id
  readonly id = input.required({ transform: numberAttribute });
  // query-параметр ?tab=… попадает в одноимённый вход
  readonly tab = input<'details' | 'history'>('details');

  // Реакция на смену :id — не хук, а зависимость: computed пересчитается
  // сам, когда роутер обновит вход, даже если компонент переиспользован
  protected readonly ticket = computed(() =>
    this.store.tickets().find((t) => t.id === this.id()) ?? null,
  );
}
```

`src/app/tickets/ticket-exists-guard.ts` — резолвер с редиректом:

```ts
import { ResolveFn, RedirectCommand, Router } from '@angular/router';
import { inject } from '@angular/core';
import { TicketStore } from './ticket-store';

export const ticketExistsGuard: ResolveFn<boolean> = (route) => {
  const store = inject(TicketStore);
  const router = inject(Router);
  const id = Number(route.paramMap.get('id'));

  if (store.tickets().some((t) => t.id === id)) return true;

  // RedirectCommand вместо простого UrlTree: можно передать ещё и
  // параметры навигации (state, replaceUrl, skipLocationChange)
  return new RedirectCommand(router.parseUrl('/not-found'), {
    state: { reason: `Ticket ${id} not found` },
  });
};
```

export const adminMatchGuard: CanMatchFn = () => {

`src/app/core/unsaved-changes-guard.ts` — типизированный `canDeactivate`:

```ts
// Контракт вместо any: гард работает с любым компонентом,
// который умеет ответить на вопрос "можно ли уходить"
export interface HasUnsavedChanges {
  readonly hasUnsavedChanges: Signal<boolean>;
}

export const unsavedChangesGuard: CanDeactivateFn<HasUnsavedChanges> = (component) => {
  if (!component.hasUnsavedChanges()) return true;
  return confirm('You have unsaved changes. Leave this page?');
};
```

Ответы на edge cases:

- `/tickets/new` совпадёт с `/tickets/:id`, и в `id` попадёт строка `"new"`. С `transform: numberAttribute` вы получите `NaN`, тикет не найдётся и экран покажет «не найдено» — то есть ошибка проявится как «форма создания не открывается». Правило: статические сегменты объявляются раньше параметрических.
- Поля компонента сохранятся: инстанс тот же, конструктор и `ngOnInit` не выполняются повторно. `input()` обновится, и всё, что от него выведено через `computed`, пересчитается. Отсюда правило: состояние экрана, зависящее от параметра, должно быть выведено из входа, а не записано в поле при инициализации.
- Роутер продолжит перебор и дойдёт до `'**'` — пользователь увидит страницу 404, а не «доступ запрещён». Если нужен явный отказ, вместо `canMatch` берут `canActivate` с редиректом на `/forbidden`: это как раз пример, когда «отменить навигацию» лучше, чем «пропустить маршрут».
- При повторяющемся ключе значение будет одно — последнее из строки запроса (`'notes'`), а не массив: `withComponentInputBinding` берёт значения из `paramMap`-подобной структуры. Если нужен массив, читайте `queryParamMap.getAll('tab')` через `ActivatedRoute`.
- `providers` на маршруте создают **отдельный environment-инжектор** для этого маршрута: сервисы создаются при входе в раздел и уничтожаются при выходе, а не живут всё время работы приложения. Это ровно тот случай, когда состояние должно жить дольше компонента, но короче приложения.

## Проверь себя

1. Объясните своими словами разницу между `canMatch` и `canActivate` и приведите случай, когда неверный выбор ухудшает не безопасность, а размер загружаемого кода.
2. Почему при переходе `/tickets/1` → `/tickets/2` не срабатывает `ngOnInit`, и как правильно реагировать на смену параметра?
3. Что делает `withComponentInputBinding()` и почему после него `ActivatedRoute` в компонентах почти не нужен?
4. Когда резолвер оправдан, а когда данные лучше грузить в самом компоненте? Назовите два минуса резолвера.
5. Что произойдёт при `canMatch: false`, если ни один другой маршрут не подошёл, и чем это отличается от `canActivate: false`?

<details>
<summary>Ответы</summary>

1. `canMatch` выполняется на этапе сопоставления URL с маршрутами: если он вернул `false`, маршрут считается неподходящим и роутер продолжает перебор — можно показать разные компоненты по одному пути разным ролям. `canActivate` выполняется уже после того, как маршрут выбран: `false` отменяет навигацию целиком. Случай про размер кода: если ленивый админ-раздел закрыть `canActivate`, роутер сначала выберет маршрут и **загрузит чанк** админки, и только потом проверит доступ — обычный пользователь скачает код, который никогда не увидит. С `canMatch` маршрут отсеивается до загрузки, и чанк не запрашивается.
2. Роутер переиспользует инстанс компонента, когда маршрут тот же и изменился только параметр: компонент не уничтожается и не создаётся заново, поэтому конструктор и `ngOnInit` не вызываются. Реагировать нужно не хуком, а зависимостью: получить параметр как `input()` (с `withComponentInputBinding`) и вывести из него всё остальное через `computed`. Тогда при смене `:id` вход обновится, зависимые вычисления пересчитаются автоматически, а `snapshot`-подход — «прочитал в `ngOnInit` и положил в поле» — покажет старые данные.
3. Он включает автоматическую привязку параметров маршрута, query-параметров и `data` к **входам** компонента по совпадению имён. Компоненту больше не нужно инжектить `ActivatedRoute`, подписываться на `params` и отписываться: вход — это сигнал, который роутер обновляет сам, и он работает даже при переиспользовании инстанса. `ActivatedRoute` остаётся нужен для нетипичных случаев: чтение `queryParamMap.getAll()`, доступ к родительским маршрутам, работа вне компонента (там параметры превращают в сигнал через `toSignal`).
4. Резолвер оправдан, когда что-то действительно обязано быть готово **до** рендера и влияет на саму навигацию: проверка существования сущности с уходом на 404, подстановка заголовка, дозагрузка конфигурации раздела. Минусы: во-первых, навигация «висит» — пользователь остаётся на старой странице без индикации, пока резолвер не завершится, и чем медленнее сеть, тем сильнее ощущение зависания; во-вторых, ошибка резолвера ломает навигацию целиком, и состояние загрузки/ошибки нельзя показать в интерфейсе экрана — оно оказывается за пределами компонента. Данные самого экрана лучше грузить в компоненте (`httpResource`, глава 08), где `loading` и `error` — часть UI.
5. Роутер продолжит перебор маршрутов и, не найдя совпадения, дойдёт до `'**'` — пользователь увидит страницу «не найдено», при этом URL останется тем, который он запросил. При `canActivate: false` навигация отменяется: URL не меняется вовсе, пользователь остаётся на текущем экране (если гард не вернул явный редирект). Отсюда практический выбор: «этого раздела для вас не существует» — `canMatch`; «раздел есть, но нужно войти» — `canActivate` с редиректом на логин.

</details>

## Частая ошибка

Первая — чтение параметра из `snapshot` в `ngOnInit`. Код выглядит безупречно и работает при первом открытии: `const id = this.route.snapshot.paramMap.get('id')`, затем загрузка данных. Проблема всплывает, когда пользователь переходит с одного тикета на другой изнутри приложения — например, по ссылке «следующий». Роутер переиспользует компонент, `ngOnInit` не вызывается, `snapshot` остаётся прежним, и на экране остаются данные предыдущего тикета при новом URL в адресной строке. Ошибка кажется мистической, потому что перезагрузка страницы «чинит» её. Правильный путь — не разовое чтение, а зависимость: `input()` с `withComponentInputBinding` плюс `computed` от него; тогда обновление приходит само.

Вторая — `canActivate` там, где нужен `canMatch`, для ленивых разделов. С точки зрения доступа обе защиты работают: пользователь без роли админку не увидит. Но с `canActivate` роутер сначала выбирает маршрут, **скачивает чанк** админ-раздела и только затем спрашивает гард — то есть код, который пользователь не имеет права выполнять, всё равно оказывается у него в браузере. Кроме лишнего трафика это ещё и неверный сигнал: содержимое админки видно любому, кто откроет вкладку Network. Замена одной строки (`canActivate` → `canMatch`) убирает и загрузку, и утечку структуры раздела. Обратная сторона: `canMatch: false` приводит на 404, а не на «доступ запрещён», поэтому там, где пользователю нужно объяснить причину, гарды комбинируют: `canMatch` по фича-флагу, `canActivate` с редиректом — по авторизации.
