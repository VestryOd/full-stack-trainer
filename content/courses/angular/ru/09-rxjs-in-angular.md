# RxJS в Angular

## Теория

### Модель Observable за пять минут

Полноценное изучение RxJS — отдельная большая тема; здесь ровно тот минимум, без которого не читается Angular-код.

**Observable** — это описание потока значений во времени. Ключевое отличие от Promise: промис — одно значение и уже начатая работа, Observable — сколько угодно значений и **отложенный старт**. Пока нет подписки, ничего не происходит (это и есть «холодность» `HttpClient` из главы 08). Подписка возвращает объект, который можно отменить, и отмена прерывает работу — так работает отмена HTTP-запросов.

Поток может завершиться (`complete`) или упасть (`error`); после любого из этих событий значений больше не будет. `Subject` — поток, в который можно вручную «толкать» значения (`next()`); `BehaviorSubject` — то же, но с текущим значением, которое новый подписчик получает сразу. Именно поэтому `BehaviorSubject` десять лет служил заменой сигналу.

Операторы — чистые функции, собираемые в конвейер через `pipe()`: `map`, `filter`, `debounceTime`, `switchMap`, `catchError`, `retry`, `startWith`, `distinctUntilChanged`. Их сила — во времени: задержки, окна, порядок, отмена, объединение нескольких источников. Именно это остаётся за RxJS в современном Angular.

Дальше в главе — только стык с Angular. Саму модель разбирает топик RxJS на этом сайте:

- marble-нотация — статья «Операторы трансформации и фильтрации»;
- горячие и холодные потоки, `shareReplay` и `refCount` — статья «Multicasting и управление подписками».

Обратное давление и полный справочник операторов — в официальной документации [rxjs.dev](https://rxjs.dev).

Версии: Angular 22 работает с RxJS 7 (`peerDependencies: rxjs ^6.5.3 || ^7.4.0`). `toPromise()` в семёрке помечен deprecated — вместо него `firstValueFrom`/`lastValueFrom`.

### Что осталось за RxJS

Правило простое: состояние и производные значения — сигналы. Всё, где важно время — задержки, окна, порядок, отмена — остаётся за RxJS.

**Где RxJS остался, а где его вытеснили сигналы**

| задача | было на RxJS | сейчас |
|---|---|---|
| состояние компонента | `BehaviorSubject` + `async` | `signal` |
| производное значение | `combineLatest` + `map` | `computed` |
| загрузка данных экрана | `switchMap` + `subscribe` | `httpResource` |
| события роутера | `router.events` | RxJS: другого API нет |
| поиск с debounce | `debounceTime` + `switchMap` | RxJS: время — его тема |
| поллинг, интервалы | `interval` + `switchMap` | RxJS или таймер + сигнал |
| valueChanges формы | `valueChanges` | RxJS в Reactive Forms |
| отписка в компоненте | `takeUntil(destroy$)` | `takeUntilDestroyed()` |

Сигналы забрали у RxJS то, для чего он был избыточен: хранение значения и вычисление производных. Осталось то, где он незаменим: **координация во времени**.

Плюс несколько API самого фреймворка, которые отдают Observable и другого интерфейса не имеют:

- `router.events`;
- `valueChanges`/`statusChanges` в Reactive Forms;
- `HttpClient` (хотя данные экрана теперь чаще берут через `httpResource`);
- выходы старых компонентов на `EventEmitter`.

### Мост между двумя моделями

```
         toSignal(obs$)                   toObservable(sig)
┌──────────────────────────────┐    ┌────────────────────────────┐
│ Observable → Signal          │    │ Signal → Observable        │
│                              │    │                            │
│ подписывается сразу и сам    │    │ значения приходят через    │
│ отписывается при уничтожении │    │ effect: не синхронно, а на │
│ контекста инъекции           │    │ следующей синхронизации    │
│                              │    │                            │
│ нужно начальное значение:    │    │ промежуточные значения     │
│ initialValue или requireSync │    │ могут не попасть в поток   │
│                              │    │                            │
│ ошибка потока → выброс при   │    │ нужен контекст инъекции    │
│ чтении сигнала               │    │ или явный injector         │
└──────────────────────────────┘    └────────────────────────────┘
  обычный путь: RxJS-конвейер       нужен редко: только чтобы отдать
     заканчивается сигналом         сигнал в готовый RxJS-конвейер
```

Всё из `@angular/core/rxjs-interop`:

```ts
// Observable → Signal. У сигнала всегда есть значение, у потока — не всегда,
// поэтому нужно либо initialValue, либо requireSync для синхронных источников
readonly params = toSignal(this.route.params, { requireSync: true });
readonly user = toSignal(this.userService.user$, { initialValue: null });

// Signal → Observable
readonly query$ = toObservable(this.query);

// Отписка, привязанная к жизни компонента или сервиса
this.router.events.pipe(takeUntilDestroyed()).subscribe(/* … */);
```

Опции `toSignal`:

- `initialValue` — значение, которое сигнал отдаёт до первого эмита;
- `requireSync` — упасть, если поток не выдал значение синхронно;
- `equal` — своя функция сравнения значений;
- `injector` — когда вызываете не в контексте инъекции;
- `manualCleanup` — подписка живёт до завершения потока, а не до уничтожения контекста. Редкий и опасный вариант.

Дополнительно в `rxjs-interop` есть:

- **`rxResource({ params, stream })`** (`@publicApi 22.0`) — `resource` из главы 08, но загрузчик возвращает Observable. Обратите внимание на имя поля: **`stream`**, а не `loader`.
- **`outputFromObservable`/`outputToObservable`** — мост между `output()` и потоками.
- **`pendingUntilEvent`** (developer preview) — помечает приложение нестабильным до эмита. Нужно для SSR (server-side rendering — отдача готового HTML с сервера) и тестов (глава 03).

### Рецепты, где RxJS выигрывает

Выбор оператора — это выбор политики по отношению к предыдущей операции. Аналога этому среди сигнальных API нет.

| оператор | что делает с предыдущим | типичный случай |
|---|---|---|
| `switchMap` | отменяет предыдущий запрос | поиск, смена фильтра |
| `concatMap` | ждёт завершения, сохраняет порядок | очередь сохранений |
| `mergeMap` | выполняет параллельно | независимые загрузки |
| `exhaustMap` | игнорирует новые, пока идёт текущий | защита от двойного клика |

Такие задачи описываются декларативно, тогда как на сигналах потребовались бы таймеры, флаги и ручная отмена:

- живой поиск — `debounceTime` + `distinctUntilChanged` + `switchMap`;
- последовательные сохранения — `concatMap`;
- поллинг — `interval` + `switchMap`;
- защита от двойной отправки формы — `exhaustMap`.

### Судьба async-пайпа

`AsyncPipe` не deprecated и работает: он подписывается, отписывается при уничтожении и вызывает `markForCheck()` на каждый emit. Именно поэтому старый код на `| async` пережил переход на zoneless (глава 03).

Но в новом коде он почти не нужен. Взамен `toSignal` даёт то же самое, только результат — сигнал: его можно читать многократно, комбинировать в `computed` и передавать во входы. Плюс уходит болезненная особенность `| async`: два `| async` в одном шаблоне — это две подписки, а значит два запроса, если поток холодный.

## Параллели с React

- **`toSignal` ≈ `useSyncExternalStore` по назначению.** Оба подключают внешний источник к системе реактивности фреймворка. Разница в требованиях: `toSignal` обязан иметь значение всегда, поэтому просит `initialValue` или `requireSync` — у сигнала не бывает состояния «значения ещё нет», в отличие от потока.
- **Отписка.** В React cleanup возвращается из `useEffect`, и забыть его сложно: он в том же коде. В Angular подписка живёт вне тела рендера, поэтому и появились три поколения решений: ручной `unsubscribe`, `takeUntil(destroy$)`, а теперь `takeUntilDestroyed()`. Сигналы этот класс ошибок убирают вовсе — отписываться не от чего.
- **Отмена запросов.** В React отмену пишут руками через `AbortController`. `switchMap` делает то же самое как побочный эффект своей семантики — «переключиться на новый источник» и означает «отменить старый».
- **Debounce.** В React обычно берут хук `useDebouncedValue` или `setTimeout` в эффекте. В RxJS это один оператор внутри конвейера. Он же гарантирует, что до сервера дойдёт только последнее значение, а промежуточные запросы будут отменены.
- **Где ломается привычка:** React-разработчик воспринимает Observable как промис и пишет `firstValueFrom` (или подписку) там, где нужен живой поток, — получая одно значение вместо потока событий. Обратная ошибка — тащить RxJS туда, где хватает сигнала: `BehaviorSubject` для состояния компонента сегодня выглядит как код 2021 года.

## Что увидишь в legacy-коде

- **`private destroy$ = new Subject<void>()`** плюс `takeUntil(this.destroy$)` в каждой подписке и `this.destroy$.next()` в `ngOnDestroy`. Сегодня это одна строка `takeUntilDestroyed()`.
- **Ручные подписки без отписки** в `ngOnInit` — источник утечек: компонент уничтожен, а подписка на `router.events` или на сервисный поток жива.
- **`BehaviorSubject`-стор** и `state$ | async` в шаблоне (глава 05), а также `combineLatest([a$, b$, c$]).pipe(map(...))` там, где сейчас три `computed`.
- **Вложенные подписки:** `a$.subscribe(a => b$.subscribe(b => ...))` — классическая ошибка, которая решается `switchMap`/`concatMap`.
- **`.toPromise()`** (deprecated в RxJS 7) и `async`/`await` поверх потоков вместо `firstValueFrom`/`lastValueFrom`.
- **`shareReplay(1)`** как способ закешировать ответ HTTP в сервисе. Работает, но без `refCount` держит подписку навсегда. Современная замена — `httpResource` или сигнальный стор.

## Что добавляем в проект

Support Desk получает три вещи, и каждая — место, где RxJS остаётся правильным инструментом:

- живой поиск с задержкой и отменой предыдущего запроса;
- поллинг счётчика новых тикетов;
- реакцию на события роутера.

Всё это заканчивается сигналами, чтобы шаблоны не знали про потоки.

## Практическое задание

**Вход:** проект из главы 08 (HTTP-слой, `httpResource`, интерсепторы).
**Выход:** три RxJS-сценария, встроенные в сигнальную архитектуру.

Требования:

1. Живой поиск: ввод в поле → задержка 300 мс → игнорирование повторов → запрос к `/api/tickets?q=` с отменой предыдущего. Реализуйте двумя способами и сравните: (а) `toObservable(signal)` + `debounceTime` + `switchMap` + `toSignal`; (б) `httpResource` с реактивным URL и отдельным «debounce-сигналом». Объясните, что теряется во втором варианте.
2. Поллинг: счётчик новых тикетов обновляется каждые 15 секунд, но **не** когда вкладка скрыта (`document.visibilityState`). Поток должен останавливаться при уничтожении сервиса. Никаких `setInterval` вручную.
3. События роутера: показывайте индикатор загрузки между `NavigationStart` и `NavigationEnd`/`NavigationCancel`/`NavigationError`. Это единственный способ — у роутера нет сигнального API для событий.
4. Отписки: ни одного `destroy$`. Везде `takeUntilDestroyed()`, а лучше — `toSignal`, который отписывается сам.
5. Сохранение формы: защитите кнопку от двойного нажатия оператором, который игнорирует новые нажатия, пока предыдущий запрос не завершился. Объясните, почему не `switchMap`.
6. Ограничение: в шаблонах нет ни одного `| async`. Всё, что попадает в разметку, — сигналы.

Edge cases на подумать:

- `toSignal` без `initialValue` и без `requireSync`: какой тип получится и что вернёт сигнал до первого значения?
- Что произойдёт, если поток внутри `toSignal` завершится ошибкой, и где эта ошибка «всплывёт»?
- Почему `toObservable` не отдаёт каждое промежуточное значение сигнала, и когда это критично?
- Два `| async` на один холодный поток в шаблоне — сколько будет HTTP-запросов и почему `toSignal` этой проблемы не имеет?
- В поллинге вы использовали `switchMap`. Что изменится, если запрос длится дольше интервала?

## Разбор решения

`src/app/tickets/ticket-search.ts` — живой поиск:

```ts
import { Service, computed, inject, signal } from '@angular/core';
import { toObservable, toSignal } from '@angular/core/rxjs-interop';
import { debounceTime, distinctUntilChanged, map, of, startWith, switchMap } from 'rxjs';
import { TicketApi } from './ticket-api';
import { Ticket } from './ticket';

@Service({ autoProvided: false })
export class TicketSearch {
  private readonly api = inject(TicketApi);

  // вход остаётся сигналом: шаблон пишет в него напрямую
  private readonly queryInput = signal('');
  readonly query = this.queryInput.asReadonly();

  // Конвейер: сигнал → поток → операторы времени → снова сигнал.
  // Именно здесь RxJS незаменим: debounce и отмена предыдущего запроса
  private readonly results$ = toObservable(this.queryInput).pipe(
    map((q) => q.trim()),
    debounceTime(300),                 // ждём паузу в наборе
    distinctUntilChanged(),            // "abc" → "abc" второй запрос не нужен
    switchMap((q) =>
      q.length < 2
        ? of([] as readonly Ticket[])  // короткий запрос — не идём в сеть
        : this.api.list({ q }),        // switchMap отменит предыдущий запрос
    ),
    startWith([] as readonly Ticket[]),
  );

  // Конвейер заканчивается сигналом: шаблон про RxJS не знает,
  // а отписка происходит при уничтожении сервиса
  readonly results = toSignal(this.results$, { requireSync: true });
  readonly hasQuery = computed(() => this.query().trim().length >= 2);

  setQuery(value: string): void {
    this.queryInput.set(value);
  }
}
```

`src/app/tickets/new-tickets-feed.ts` — поллинг с учётом видимости вкладки:

```ts
import { DestroyRef, Service, inject } from '@angular/core';
import { takeUntilDestroyed, toSignal } from '@angular/core/rxjs-interop';
import { fromEvent, interval, map, startWith, switchMap } from 'rxjs';
import { TicketApi } from './ticket-api';

@Service()
export class NewTicketsFeed {
  private readonly api = inject(TicketApi);

  // Поток видимости вкладки: пока она скрыта, поллинг не нужен —
  // это самый частый источник бессмысленного трафика
  private readonly visible$ = fromEvent(document, 'visibilitychange').pipe(
    map(() => document.visibilityState === 'visible'),
    startWith(document.visibilityState === 'visible'),
  );

  private readonly count$ = this.visible$.pipe(
    // switchMap: при уходе со вкладки внутренний interval отменяется,
    // при возврате создаётся заново
    switchMap((visible) => (visible ? interval(15_000).pipe(startWith(0)) : [])),
    switchMap(() => this.api.list({ status: 'new' })),
    map((tickets) => tickets.length),
    // подписка живёт не дольше сервиса; без этого поллинг остался бы
    // работать после уничтожения (в root-сервисе — до конца жизни приложения)
    takeUntilDestroyed(inject(DestroyRef)),
  );

  readonly count = toSignal(this.count$, { initialValue: 0 });
}
```

`src/app/core/navigation-progress.ts` — события роутера:

```ts
import { Service, inject } from '@angular/core';
import { toSignal } from '@angular/core/rxjs-interop';
import {
  NavigationCancel,
  NavigationEnd,
  NavigationError,
  NavigationStart,
  Router,
} from '@angular/router';
import { filter, map } from 'rxjs';

@Service()
export class NavigationProgress {
  private readonly router = inject(Router);

  // У роутера нет сигнального API для событий — это тот случай,
  // где RxJS обязателен, а не просто стилистический выбор
  private readonly inProgress$ = this.router.events.pipe(
    filter(
      (e) =>
        e instanceof NavigationStart ||
        e instanceof NavigationEnd ||
        e instanceof NavigationCancel ||
        e instanceof NavigationError,
    ),
    map((e) => e instanceof NavigationStart),
  );

  // на выходе — сигнал: шаблон читает его как обычное значение
  readonly isNavigating = toSignal(this.inProgress$, { initialValue: false });
}
```

Защита формы от двойной отправки:

```ts
import { inject } from '@angular/core';
import { takeUntilDestroyed } from '@angular/core/rxjs-interop';
import { Router } from '@angular/router';
import { Subject, exhaustMap } from 'rxjs';
import { TicketApi } from './ticket-api';
import { Ticket } from './ticket';

// то, что форма отправляет: тикет без полей, которые проставит сервер
type TicketDto = Omit<Ticket, 'id' | 'createdAt'>;

export class TicketForm {
  private readonly api = inject(TicketApi);
  private readonly router = inject(Router);
  private readonly submit$ = new Subject<TicketDto>();

  constructor() {
    this.submit$
      .pipe(
        // exhaustMap игнорирует новые нажатия, пока текущий запрос не завершён.
        // switchMap здесь был бы вредительством: он отменил бы уже
        // отправленный POST, а сервер мог его выполнить
        exhaustMap((dto) => this.api.create(dto)),
        takeUntilDestroyed(),
      )
      .subscribe(() => void this.router.navigate(['/tickets']));
  }

  protected save(dto: TicketDto): void {
    this.submit$.next(dto);
  }
}
```

Второй вариант живого поиска — без RxJS, через `httpResource`:

```ts
// «debounce-сигнал»: значение доезжает до URL с задержкой
private readonly debouncedQuery = signal('');

constructor() {
  effect((onCleanup) => {
    const q = this.query();                     // зависимость
    const timer = setTimeout(() => this.debouncedQuery.set(q), 300);
    onCleanup(() => clearTimeout(timer));       // отмена предыдущего таймера
  });
}

private readonly resource = httpResource<readonly Ticket[]>(
  () => `${this.config.apiUrl}/tickets?q=${encodeURIComponent(this.debouncedQuery())}`,
  { defaultValue: [] },
);
```

Работает, и отмену запроса `httpResource` берёт на себя. Но обратите внимание, чего это стоит:

- появился `effect`, который пишет сигнал, — в главе 02 мы называли это признаком ошибки;
- таймер приходится гасить вручную;
- `distinctUntilChanged` и «не искать по одной букве» надо дописывать отдельными условиями.

Это ровно та ситуация, ради которой RxJS в Angular остался. Как только в задаче появляется время, декларативный конвейер короче и честнее ручных таймеров.

Ответы на edge cases:

- Без `initialValue` и `requireSync` тип будет `Signal<T | undefined>`, и до первого значения сигнал вернёт `undefined`. Это честно отражает разрыв моделей: у потока может не быть значения, у сигнала — не может, поэтому `undefined` подставляется как заглушка. Для синхронных источников (`route.params`, `BehaviorSubject`) лучше `requireSync: true` — тогда тип без `undefined`, а при нарушении контракта вы получите ошибку сразу, а не «иногда undefined в шаблоне».
- Ошибка не «теряется»: `toSignal` запоминает её и выбрасывает **при чтении сигнала**. То есть исключение всплывёт в шаблоне или в `computed`, который его читает, — и в отладчике вы увидите стек чтения, а не стек потока. Поэтому обработку ошибок ставят внутри конвейера (`catchError`), а не полагаются на всплытие.
- `toObservable` реализован через `effect`: значения публикуются не в момент `set`, а на следующей синхронизации. Если между двумя синхронизациями сигнал изменился трижды, в поток попадёт только последнее значение. Для интерфейса это правильно. Но если вам нужны все промежуточные события — например, счётчик нажатий, — сигнал неподходящий источник. События в таком случае отправляют в `Subject` напрямую.
- Два `| async` на один холодный поток дадут **два запроса**: каждая подписка запускает работу заново. Классический обход — `shareReplay(1)` или один `| async` с `as`. У `toSignal` проблемы нет по построению: он подписывается один раз, а сигнал можно читать сколько угодно, потому что чтение сигнала — не подписка.
- Если запрос дольше интервала, `switchMap` отменит незавершённый предыдущий и начнёт новый — счётчик будет обновляться, но каждый цикл может не доходить до конца при медленной сети. Если важно, чтобы каждый запрос завершался, нужен `concatMap` (очередь) или `exhaustMap` (пропускать тики, пока идёт запрос). Для поллинга обычно правильный ответ — `exhaustMap`: он не создаёт очередь и не нагружает сервер.

## Проверь себя

1. Объясните своими словами, почему сигналы не заменили RxJS полностью, и назовите три задачи, где RxJS остаётся правильным выбором.
2. Зачем `toSignal` требует `initialValue` или `requireSync`? Что это говорит о разнице между Observable и сигналом?
3. Почему `switchMap` подходит для поиска, но опасен для сохранения формы? Какой оператор нужен во втором случае?
4. Что делает `takeUntilDestroyed()` и почему в сигнальном коде он нужен реже, чем в RxJS-коде?
5. Чем `toSignal(obs$)` лучше `obs$ | async` в шаблоне? Назовите два конкретных отличия.

<details>
<summary>Ответы</summary>

1. Сигналы описывают **значение в текущий момент**: у сигнала всегда есть значение, а история и тайминги в нём не выражаются. RxJS описывает **события во времени**, поэтому умеет то, чего у сигналов нет. Это задержки и окна (`debounceTime`, `throttleTime`), политика по отношению к предыдущей операции (`switchMap`/`concatMap`/`exhaustMap`), объединение источников с сохранением порядка, отмена. Три задачи остаются за RxJS. Первая — живой поиск с задержкой и отменой предыдущего запроса. Вторая — поллинг, зависящий от внешних условий: видимость вкладки, наличие сети. Третья — последовательность запросов, где важен порядок или нужна защита от повторной отправки. Плюс API самого фреймворка, отдающие только Observable: события роутера, `valueChanges` форм.
2. Потому что у сигнала не бывает состояния «значения ещё нет», а у потока — бывает. Между подпиской и первым emit может пройти время, а иногда значения не будет вовсе. При этом `toSignal` обязан что-то вернуть при первом чтении. Поэтому либо вы даёте `initialValue`, либо обещаете `requireSync: true` — что источник синхронный (`BehaviorSubject`, `route.params`). Тогда сигнал типизируется без `undefined`, а нарушение обещания превращается в явную ошибку. Это и есть точка, где две модели не совпадают: Observable — про события во времени, сигнал — про значение, которое есть всегда.
3. `switchMap` при новом значении **отменяет предыдущий внутренний поток**. Для поиска это ровно то, что нужно: результаты устаревшего запроса не нужны, а отмена экономит сеть. Для сохранения это опасно: отменяется уже отправленный `POST`, но сервер мог его выполнить — вы получите созданную сущность, о которой клиент не знает, либо частично применённое изменение. Для второго нажатия по кнопке правильный оператор — `exhaustMap`: он игнорирует новые события, пока текущий запрос не завершился. Если нужно выполнить все запросы и сохранить порядок — `concatMap`.
4. `takeUntilDestroyed()` — оператор, который завершает поток, когда уничтожается контекст инъекции: компонент, директива или сервис. `DestroyRef` он получает из контекста или принимает аргументом. Это замена паттерну `destroy$` + `takeUntil`. В сигнальном коде он нужен реже, потому что подписок почти нет. Зависимость `computed` от сигнала — ребро графа, а не подписка: она уничтожается вместе с недостижимым узлом. Функция `toSignal` отписывается сама, а `httpResource` сам отменяет запросы. Оператор `takeUntilDestroyed` остаётся для случаев, где вы действительно подписываетесь руками: события роутера, потоки форм, свои `Subject`.
5. Во-первых, `toSignal` подписывается **один раз**, а результат читается сколько угодно. Два `| async` на один холодный поток — это две подписки и два HTTP-запроса. Обходится это только через `shareReplay` или `as`-переменную. Во-вторых, результат `toSignal` — обычный сигнал: его можно комбинировать в `computed`, передавать во входы дочерних компонентов, читать в `effect`. А `| async` существует только внутри шаблона. Дополнительно: сигнал участвует в change detection точечно, а `AsyncPipe` устроен как impure-пайп, то есть проверяется на каждом проходе и на каждый emit зовёт `markForCheck()`.

</details>

## Частая ошибка

Первая — воспринимать Observable как промис. Из React-опыта тянется рефлекс «получить значение и продолжить». Отсюда код вида `const tickets = await firstValueFrom(this.api.list({}))` там, где нужен живой поток. Или подписка внутри подписки: `this.route.params.subscribe(p => this.api.byId(p.id).subscribe(...))`.

Второе особенно коварно. Внешний поток продолжает эмитить, внутренние подписки копятся, предыдущие запросы никто не отменяет. При быстром переключении тикетов на экран приезжает ответ не того тикета, который открыт сейчас. Лечение — оператор вместо вложенности: `switchMap` (для навигации и поиска) или `concatMap`/`exhaustMap`, если отменять нельзя.

Вторая — тащить RxJS туда, где достаточно сигнала. Симптом: `BehaviorSubject` для состояния компонента, `combineLatest` для двух флагов, `shareReplay(1)` как «кеш» и `| async` в пяти местах шаблона.

Такой код работает, но обходится дороже. Подписки нужно закрывать, а холодные потоки дублируют запросы. И `combineLatest` не выдаст значение, пока не эмитнет каждый источник — отсюда типичный баг «экран пустой, потому что один поток молчит».

Практический критерий такой. Если задача формулируется как «какое значение сейчас» — это сигнал. Если как «что произошло и в каком порядке» — RxJS. Смешивать нормально, но переход должен быть однонаправленным: конвейер RxJS заканчивается `toSignal`, а не наоборот.
