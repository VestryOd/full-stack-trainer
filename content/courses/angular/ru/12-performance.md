# Производительность

## Теория

### Сначала измерение

«Angular тормозит» — это не одна проблема. У каждого симптома своя частая причина и свой инструмент.

| симптом | частая причина | чем смотреть |
|---|---|---|
| список дёргается при обновлении | `track` по индексу или по объекту | DevTools Profiler |
| лаг на каждый ввод символа | метод или impure-пайп в шаблоне | Profiler: время проверки |
| проверок больше, чем изменений | `Eager`-компонент в горячем пути | Profiler: счётчик циклов |
| долгий первый рендер | весь код в initial-бандле | `stats.json` + esbuild analyze |
| скачет вёрстка при загрузке | нет `width`/`height` у картинок | Lighthouse: CLS (cumulative layout shift) |
| тормозит скролл длинного списка | нет виртуализации | Performance-профиль браузера |

Сначала измерение, потом оптимизация: половина «оптимизаций» на глаз усложняет код, не меняя ни одного числа.

Производительность Angular-приложения ломается в двух разных местах, и лечатся они по-разному. **Runtime** — это сколько работы делает change detection и рендеринг на каждое взаимодействие. **Загрузка** — это сколько кода и картинок нужно скачать до первого экрана. Профайлер отвечает на первое, анализ бандла — на второе.

**Angular DevTools, вкладка Profiler**: запись показывает циклы change detection, какие компоненты в них попали, сколько раз и сколько миллисекунд заняла проверка. Это единственный способ увидеть то, что в коде не видно: выражение в шаблоне, исполняющееся сотни раз, или компонент, проверяемый при каждом нажатии клавиши в другом углу экрана.

### Runtime: что уже сделано за вас

К v22 три главных runtime-оптимизации стали дефолтами (главы 03 и 02): zoneless — с v21, `OnPush` — с v22, сигналы как источник уведомлений. Поэтому современный чеклист выглядит иначе, чем три года назад: вместо «включите `OnPush`» — «не сломайте то, что включено».

Что ломает встроенные оптимизации:

- **Явный `ChangeDetectionStrategy.Eager`** в декораторе — компонент проверяется при каждом обходе. После миграции на v22 он остался в старых компонентах автоматически (глава 03), и в горячем пути это реальная стоимость.
- **Вызовы методов и геттеров в шаблоне** — исполняются при каждой проверке, кеша нет. Это самая частая причина «лага на каждый символ»: поиск обновляет сигнал, шаблон проверяется, и вместе с ним заново считаются `getTotal()`, `formatDate()` и `filterTickets()`.
- **Impure-пайпы** (`pure: false`) — то же самое (глава 06).
- **Мутация вместо `set`** — не тормозит, но приводит к «не обновляется», а следом к попыткам «починить» это лишними проверками.

### track и цена его отсутствия

`track` в `@for` — не про элегантность, а про то, переиспользует ли Angular существующие узлы DOM (document object model, дерево объектов страницы в браузере). Три варианта:

```html
@for (t of tickets(); track t.id) { … }      <!-- правильно: стабильный ключ -->
@for (t of tickets(); track $index) { … }    <!-- позиция: сломается при сортировке -->
@for (t of tickets(); track t) { … }         <!-- ссылка: сломается после перезагрузки -->
```

`track $index` привязывает узел к позиции: после сортировки на позиции 0 другой объект, и Angular перепишет содержимое **всех** узлов вместо перестановки.

Вариант `track t` (по ссылке) работает, пока массив в памяти. Но после перезагрузки из HTTP все объекты новые, и весь список пересоздаётся — вместе с компонентами внутри, их состоянием, фокусом и позицией скролла.

На практике: список из 200 карточек с `track $index` при сортировке заново выполняет 200 шаблонов и все вложенные компоненты. С `track t.id` он перемещает узлы и не выполняет ни одного лишнего шаблона.

### @defer: отложенная загрузка блоков

Триггер решает, когда блок загрузится. Ключевое слово `prefetch` принимает те же триггеры, но только скачивает код, не рендеря блок.

| триггер | что означает | типичный случай |
|---|---|---|
| `on idle` | браузер освободился (по умолчанию) | всё, что ниже первого экрана |
| `on viewport` | блок попал в область видимости | графики, комментарии |
| `on interaction` | клик или keydown по элементу | редактор, тяжёлая форма |
| `on hover` | наведение мыши или фокус | превью, тултип с данными |
| `on timer(2s)` | через заданное время | баннер, подсказка |
| `on immediate` | сразу после основного рендера | разгрузить initial-бандл |
| `when expr` | условие стало истинным | по роли, по фича-флагу |
| `prefetch on idle` | код скачать заранее, не показывать | почти всегда полезно |

`@defer` выносит содержимое блока в **отдельный чанк** и загружает его по триггеру:

```html
@defer (on viewport; prefetch on idle) {
  <app-ticket-analytics [tickets]="tickets()" />
} @placeholder (minimum 300ms) {
  <div class="skeleton skeleton--chart"></div>
} @loading (after 150ms; minimum 300ms) {
  <p>Loading analytics…</p>
} @error {
  <p>Could not load analytics</p>
}
```

Смысл параметров:

- `@placeholder (minimum 300ms)` — не мигать, если загрузка мгновенная;
- `@loading (after 150ms)` — не показывать индикатор, если всё пришло быстро;
- `minimum 300ms` — если показали, то не меньше чем на 300 мс.

Это ровно те два визуальных дефекта, которые обычно приходится лечить руками.

Главное ограничение: деферить можно только **standalone**-зависимости, и только те, на которые нет прямых ссылок вне блока.

Если тот же компонент указан в `imports` и используется в обычной разметке (или запрошен через `viewChild`), он попадёт в основной бандл. Тогда `@defer` останется лишь способом отложить рендеринг, а экономии кода не будет. Это первое, что стоит проверять, когда «поставил `@defer`, а бандл не уменьшился».

Для SSR (server-side rendering, серверный рендеринг) у `@defer` есть отдельный набор триггеров `hydrate on …` — incremental hydration. Сервер рендерит содержимое блока, а браузер оставляет его «сухим» до триггера. Гидратация происходит порциями (глава 15).

### Загрузка: ленивые маршруты и бюджеты

Ленивые маршруты (`loadComponent`/`loadChildren`, глава 07) — основной инструмент разбивки кода; `@defer` дополняет его внутри страницы. Чтобы результат не деградировал со временем, размеры фиксируют бюджетами в `angular.json`:

| тип бюджета | что измеряет | зачем следить |
|---|---|---|
| `initial` | всё, что грузится до первого рендера | главная метрика старта |
| `bundle` (+ `name`) | конкретный бандл по имени | ленивый раздел не распух |
| `anyComponentStyle` | любой один файл стилей компонента | ловит случайный импорт темы |
| `anyScript` / `allScript` | любой один / все скрипты | общий потолок JS |
| `any` / `all` | любой один / все файлы вывода | картинки, шрифты, шаблоны |

У каждого бюджета есть `maximumWarning` и `maximumError`, а также `minimum*` и `baseline` для сравнения с эталоном. Порог `maximumError` роняет сборку: бюджет становится проверкой в CI (continuous integration — непрерывная интеграция), а не рекомендацией.

Анализ бандла в новой build-системе: `ng build --stats-json` создаёт `stats.json`, который загружается в **esbuild-analyze** (`https://esbuild.github.io/analyze/`) — там видно, какой модуль сколько занимает и почему попал в бандл. Инструменты для webpack (`webpack-bundle-analyzer`) с application-билдером не работают: сборка идёт на esbuild.

### Картинки

`NgOptimizedImage` из `@angular/common` — директива, которая заставляет делать правильно. Она существует ради двух метрик загрузки. LCP (largest contentful paint) — это самый крупный элемент первого экрана. CLS показывает, насколько сильно вёрстка «прыгает» во время загрузки.

```html
<img
  ngSrc="/assets/hero.jpg"
  width="1200" height="630"
  priority                     <!-- LCP-картинка: fetchpriority=high, loading=eager -->
  alt="Support desk overview"
/>
```

Что она даёт:

- Обязательные `width`/`height` (или `fill` с позиционированным родителем) убирают сдвиг вёрстки.
- `priority` помечает LCP-изображение, остальные картинки получают `loading="lazy"` автоматически.
- Генерируются `srcset` и `preconnect`.
- В dev-режиме она предупреждает о типичных ошибках: LCP-картинка без `priority`, искажённые пропорции, неверные размеры, отсутствующий preconnect.

Для CDN (content delivery network — сеть доставки контента) есть готовые загрузчики: `provideImgixLoader`, `provideCloudflareLoader`, `provideCloudinaryLoader`, `provideImageKitLoader`, `provideNetlifyLoader` — или свой через токен `IMAGE_LOADER`.

### Виртуализация длинных списков

Если строк больше нескольких сотен, `@for` перестаёт быть решением: DOM-узлы стоят памяти и времени layout. `cdk/scrolling` (`<cdk-virtual-scroll-viewport>` + `*cdkVirtualFor`) рендерит только видимые элементы. Порог принимать решение — не количество строк, а профиль: если проверка шаблона занимает единицы миллисекунд, а тормозит именно скролл, дело в DOM, и виртуализация поможет.

## Параллели с React

- **`@defer` ≈ `React.lazy` + `Suspense`, но декларативнее.** В React вы пишете `lazy(() => import(...))` и оборачиваете в `<Suspense fallback>`; триггер загрузки — сам факт рендера. Блок `@defer` отделяет **триггер** от места: `on viewport`, `on interaction`, `prefetch on idle`. В React это делают руками через Intersection Observer и предзагрузку.
- **`track` ≈ `key`, но обязателен.** Механика идентичности одна и та же, и последствия неверного ключа одинаковы: пересоздание узлов и потеря состояния. Разница — в дисциплине: React ограничивается предупреждением в консоли, Angular не даст скомпилировать `@for` без `track`.
- **`OnPush` против `memo`.** В React мемоизация — то, что вы добавляете (`memo`, `useMemo`, `useCallback`), и её легко забыть. В Angular с v22 «мемоизация» включена по умолчанию (`OnPush` + сигналы), а работа сводится к тому, чтобы не выключать её `Eager`-компонентами и вычислениями в шаблоне.
- **Бюджеты — то, чего в React-стеке обычно нет из коробки.** Аналог собирают из `bundlesize`/`size-limit` в CI; в Angular это поле в `angular.json`, и `maximumError` роняет сборку без дополнительных инструментов.
- **Где ломается привычка:** привычка мемоизировать всё. Вызов `useMemo` в React — рефлекс, и он переносится на `computed` для тривиальных выражений. Обёртка `computed(() => this.count() + 1)` вокруг арифметики добавляет узел в граф и ничего не экономит. Сигналы уже точечные; оптимизировать нужно то, что показал профайлер, а не всё подряд.

## Что увидишь в legacy-коде

- **`ChangeDetectionStrategy.OnPush` явно в каждом компоненте** — до v22 это была осознанная оптимизация, теперь дефолт. Соседний маркер — `ChangeDetectionStrategy.Default`/`Eager`, оставленный миграцией.
- **`trackBy: trackById`** — метод класса с сигнатурой `(index, item)` рядом с `*ngFor`; в новом control flow это выражение `track item.id`.
- **`runOutsideAngular`** вокруг анимаций, скролл-обработчиков и `requestAnimationFrame` (глава 03): в zone-модели так глушили лишние проверки. В zoneless этого делать не нужно — и `NgZone` там не работает.
- **`webpack-bundle-analyzer`** в devDependencies и скрипт `analyze` с `--stats-json` для webpack. С application-билдером тот же `stats.json` читается на esbuild-analyze.
- **Ручной lazy-loading картинок:** `IntersectionObserver` в директиве, `loading="lazy"` руками, свои плейсхолдеры — до `NgOptimizedImage`.
- **`ChangeDetectorRef.detach()`/`reattach()`** как способ «выключить» тяжёлый компонент из проверок — работает, но означает, что причину не нашли.

## Что добавляем в проект

Профилируем список тикетов, находим и убираем вычисления из шаблона. Тяжёлые блоки — аналитику и историю тикета — переводим на `@defer` с осмысленными триггерами. Добавляем бюджеты в `angular.json` и приводим картинки к `NgOptimizedImage`.

## Практическое задание

**Вход:** проект из главы 11 (таблица, модалка, HTTP-слой).
**Выход:** измеренные и обоснованные улучшения, а не «оптимизации на глаз».

Требования:

1. Профилирование: сгенерируйте 500 тикетов, откройте Angular DevTools Profiler и запишите ввод трёх символов в поиск. Зафиксируйте цифры: сколько циклов change detection (CD), какие компоненты проверялись, сколько миллисекунд. Это baseline, к которому вы будете возвращаться.
2. Найдите и уберите вычисления из шаблонов (методы, геттеры, `filter`/`map` в разметке, impure-пайпы). После правки повторите замер и сравните с baseline.
3. Эксперимент с `track`: сделайте три версии `@for` (`track t.id`, `track $index`, `track t`), отсортируйте список и сравните в профайлере число выполненных шаблонов. Объясните разницу.
4. `@defer`: выделите два тяжёлых блока — панель аналитики (график) и историю изменений тикета. Аналитику грузите `on viewport; prefetch on idle`, историю — `on interaction` по кнопке. Добавьте `@placeholder` и `@loading` с параметрами, чтобы не мигало.
5. Проверьте по `stats.json`, что чанки действительно выделились: соберите с `--stats-json`, загрузите в esbuild-analyze, найдите отложенные чанки. Если код остался в основном бандле — найдите прямую ссылку, которая это вызвала.
6. Бюджеты: добавьте в `angular.json` бюджеты `initial` (warning/error с запасом ~20% от текущего размера) и `anyComponentStyle`. Убедитесь, что превышение роняет сборку: временно импортируйте что-нибудь тяжёлое и посмотрите на ошибку.
7. Картинки: переведите аватары и логотип на `NgOptimizedImage`. Поставьте `priority` там, где картинка и есть LCP. Проверьте в Lighthouse, что CLS не растёт.

Edge cases на подумать:

- Вы обернули компонент в `@defer`, но размер основного бандла не изменился. Какие две причины наиболее вероятны?
- `@defer (on viewport)` внутри блока, который сам скрыт `@if`. Когда сработает триггер?
- `@placeholder` без `minimum` при быстрой сети — что увидит пользователь?
- Список с `track t.id`, но `id` у новых (ещё не сохранённых) элементов равен `undefined`. Что произойдёт?
- Бюджет `initial` настроен на 500 kB, а приложение выросло из-за ленивого раздела. Поймает ли это бюджет?

## Разбор решения

Уборка вычислений из шаблона — самое дешёвое улучшение:

```ts
// БЫЛО: три вызова на каждую проверку шаблона, кеша нет
// <p>{{ getVisibleCount() }} of {{ getTotal() }} · {{ formatDate(ticket.createdAt) }}</p>

// СТАЛО: computed мемоизируется по сигналам, пайп кешируется по входу
protected readonly visibleCount = computed(() => this.board.tickets().length);
protected readonly totalCount = computed(() => this.store.totalCount());
// в шаблоне: {{ ticket.createdAt | date: 'short' }}
```

`@defer` на тяжёлых блоках:

```html
<!-- Аналитика ниже первого экрана, поэтому грузим при попадании в viewport,
     а код тянем заранее в простое браузера — к моменту прокрутки он уже есть -->
@defer (on viewport; prefetch on idle) {
  <app-ticket-analytics [tickets]="board.tickets()" />
} @placeholder (minimum 300ms) {
  <!-- minimum, чтобы скелетон не мигнул на быстрой сети -->
  <div class="skeleton skeleton--chart" aria-hidden="true"></div>
} @loading (after 150ms; minimum 300ms) {
  <!-- after: не показывать индикатор, если загрузка уложилась в 150 мс -->
  <p class="hint">Loading analytics…</p>
} @error {
  <p class="error">Could not load analytics</p>
}

<!-- История: нужна по требованию. Триггер — взаимодействие с кнопкой:
     код скачается при первом клике, не раньше -->
<button type="button" #historyToggle>Show history</button>

@defer (on interaction(historyToggle)) {
  <app-ticket-history [ticketId]="ticket().id" />
} @placeholder {
  <p class="hint">History is loaded on demand</p>
}
```

Важная деталь, которую легко упустить: `TicketAnalytics` и `TicketHistory` **не должны** быть указаны в `imports` компонента и не должны использоваться где-либо ещё в его шаблоне. Компилятор сам добавит их как ленивые зависимости блока; если на них есть прямая ссылка, они уедут в основной бандл, и `@defer` останется только отложенным рендерингом.

Бюджеты в `angular.json`:

```json
{
  "projects": {
    "support-desk": {
      "architect": {
        "build": {
          "configurations": {
            "production": {
              "budgets": [
                {
                  "type": "initial",
                  "maximumWarning": "420kB",
                  "maximumError": "500kB"
                },
                {
                  "type": "anyComponentStyle",
                  "maximumWarning": "4kB",
                  "maximumError": "8kB"
                },
                {
                  "type": "bundle",
                  "name": "admin",
                  "maximumWarning": "150kB",
                  "maximumError": "250kB"
                }
              ]
            }
          }
        }
      }
    }
  }
}
```

`maximumError` — это то, что делает бюджет полезным: сборка падает, и вырасти незаметно бандл больше не может. Значения ставят с небольшим запасом от текущего размера, иначе бюджет либо не срабатывает никогда, либо горит постоянно.

Анализ бандла:

```bash
# stats.json генерирует application-билдер (esbuild), а не webpack
npx ng build --stats-json

# отчёт открывается на https://esbuild.github.io/analyze/ — загрузите dist/.../stats.json
# ищем: что попало в initial-чанк, какие чанки создали @defer и ленивые маршруты
```

Картинки:

```ts
@Component({
  selector: 'app-ticket-detail',
  imports: [NgOptimizedImage],
  // …
})
```

```html
<!-- width/height обязательны: браузер резервирует место и вёрстка не скачет -->
<img ngSrc="/assets/logo.svg" width="120" height="32" alt="Support Desk" priority />

<!-- аватары не LCP: priority не нужен, loading="lazy" директива поставит сама -->
@for (ticket of board.tickets(); track ticket.id) {
  <img
    [ngSrc]="ticket.assigneeAvatar"
    width="32" height="32"
    [alt]="ticket.assignee ?? ''"
  />
}
```

Виртуализация, если профиль показал, что дело в DOM:

```html
<cdk-virtual-scroll-viewport itemSize="72" class="ticket-list__viewport">
  <!-- рендерятся только видимые строки плюс небольшой буфер -->
  <app-ticket-card
    *cdkVirtualFor="let ticket of board.tickets(); templateCacheSize: 20"
    [ticket]="ticket"
  />
</cdk-virtual-scroll-viewport>
```

Ответы на edge cases:

- Две причины, обе про прямые ссылки. Первая: компонент перечислен в `imports` этого же компонента или используется в обычной разметке вне блока — тогда он статическая зависимость и попадает в основной бандл. Вторая: на него ссылается `viewChild`/`contentChild` или он импортируется в TS-коде компонента (например, для типа с `new`) — компилятор обязан иметь его при первой загрузке. Проверяется по `stats.json`: если чанка нет, ищите ссылку.
- Не сработает, пока внешний `@if` ложен: содержимое `@defer` не существует, а значит нет и элемента, за которым наблюдает Intersection Observer. Триггер начнёт работать, когда блок появится в DOM. То есть вложенные условия «сдвигают» момент загрузки, и это стоит учитывать: prefetch в такой ситуации полезнее, чем сам триггер.
- Мигание: плейсхолдер появится и почти сразу исчезнет — визуальный «щелчок», который выглядит как баг вёрстки. Параметр `@placeholder (minimum 300ms)` гарантирует, что показанный плейсхолдер останется на экране не меньше указанного времени. Парный приём — `@loading (after 150ms)`, чтобы индикатор вообще не появлялся при быстрой загрузке.
- `undefined` как ключ у нескольких элементов даёт дубликаты ключей — Angular бросит ошибку о повторяющемся `track` (глава 01). Для несохранённых элементов нужен временный уникальный ключ: локальный отрицательный id, `crypto.randomUUID()` или составной ключ `t.id ?? t.tempId`.
- Нет: бюджет `initial` считает только то, что грузится до первого рендера, и ленивый чанк в него не входит. Именно поэтому в примере добавлен второй бюджет с `type: "bundle"` и `name: "admin"` — чтобы у ленивого раздела был свой потолок. Общий рост контролируют `allScript`/`all`.

## Проверь себя

1. Почему `track $index` в сортируемом списке — это не «просто менее точный ключ», а источник реальной работы для фреймворка?
2. Что именно делает `@defer` с кодом блока, и в каких двух случаях он не уменьшит основной бандл?
3. Зачем `@placeholder (minimum …)` и `@loading (after …)`, если можно просто показать спиннер?
4. Какие runtime-оптимизации в Angular 22 включены по умолчанию, и что в вашем коде может их отключить?
5. Чем бюджеты в `angular.json` полезнее, чем «посмотреть размер бандла глазами после сборки»?

<details>
<summary>Ответы</summary>

1. Потому что `track` определяет, какой узел DOM соответствует какому элементу данных. При `track $index` идентичностью становится позиция. После сортировки на позиции 0 оказывается другой объект, но Angular считает его «тем же» элементом. Вместо перемещения узла он перезаписывает его содержимое — и так по всей длине списка. Вместо N перестановок получается N обновлений шаблонов вместе со всеми вложенными компонентами. Плюс побочные эффекты: теряется фокус, сбрасывается позиция скролла внутри строк, ломаются анимации перехода, а состояние компонентов внутри строки (открытые меню, черновики) уезжает к другим данным.
2. `@defer` выделяет содержимое блока и его зависимости в **отдельный чанк**, который загружается только по триггеру. Он не уменьшит основной бандл в двух случаях. Первый: отложенный компонент перечислен в `imports` или используется в обычной разметке вне блока — тогда это статическая зависимость. Второй: на него есть ссылка из кода компонента, например через `viewChild`/`contentChild` или TS-импорт для типа с созданием инстанса. В обоих случаях компилятор обязан включить его в первую загрузку, а `@defer` вырождается в отложенный рендеринг. Дополнительно: деферить можно только standalone-зависимости.
3. Потому что «просто спиннер» даёт два визуальных дефекта на быстрой сети. Если загрузка занимает 40 мс, спиннер мигнёт и исчезнет — пользователь увидит щелчок и воспримет его как глюк; `@loading (after 150ms)` вообще не покажет индикатор в этом случае. Обратная ситуация: плейсхолдер показался и исчез через 20 мс — `@placeholder (minimum 300ms)` держит его достаточно долго, чтобы переход выглядел намеренным. Это управление воспринимаемой производительностью: цифры те же, ощущение разное.
4. По умолчанию включены три вещи. Zoneless change detection (с v21): проверки идут только по явным уведомлениям, а не обходом всего дерева на каждую асинхронную операцию. Режим `OnPush` для компонентов (с v22): компонент проверяется, только когда изменились входы, произошло событие или изменился прочитанный в шаблоне сигнал. И сигналы как механизм точечных уведомлений. Отключить их можно своим кодом. Явный `ChangeDetectionStrategy.Eager` заставляет проверять компонент при каждом обходе. Вызовы методов и геттеров в шаблонах и impure-пайпы вычисляются при каждой проверке, кеша нет. Мутация вместо `set` не присылает уведомления вообще. И ручные `detectChanges()` в обработчиках добавляют проверки, которых никто не просил.
5. Потому что бюджет — автоматическая проверка, а взгляд — нет. `maximumError` роняет сборку, то есть превышение ловится в CI до мержа, а не через полгода на регрессии производительности. Бюджеты также разделяют цели: `initial` следит за стартовым весом, `bundle` с именем — за конкретным ленивым разделом, `anyComponentStyle` ловит случайно импортированную тему в один компонент. И они дают числа, привязанные к конфигурации проекта, а не к памяти разработчика о том, «сколько было в прошлый раз».

</details>

## Частая ошибка

Первая — оптимизировать без измерения. Приходит из React-опыта, где мемоизация — рутина: разработчик добавляет `computed` вокруг каждого выражения, дробит компоненты «чтобы меньше перерисовывалось», расставляет `@defer` там, где загружать нечего.

В Angular 22 это почти всегда бесполезно: `OnPush` и сигналы уже дают точечные обновления, а лишние `computed` вокруг арифметики только увеличивают граф зависимостей. Хуже того, такие правки маскируют настоящую причину — обычно один метод в шаблоне горячего компонента или `Eager`-стратегия, оставшаяся после миграции.

Порядок обратный: снять профиль, найти самый дорогой цикл CD, посмотреть, чей шаблон в нём выполняется чаще всего, — и починить именно это, а затем повторить замер.

Вторая — `@defer`, который ничего не отложил. Блок написан, плейсхолдер красивый, а `initial`-чанк того же размера.

Причина в 90% случаев одна: тот же компонент упомянут в `imports` этого компонента или используется в другом месте шаблона (иногда — в скрытой ветке `@if`), поэтому остаётся статической зависимостью. Реже — ссылка через `viewChild`.

Проверяется это не рассуждением, а `stats.json` в esbuild-analyze: если отдельного чанка нет, значит компилятор не смог отделить код.

И симметричная ошибка — `@defer` на всё подряд, включая мелкие компоненты. Каждый блок это отдельный запрос и своя задержка. Дробить имеет смысл то, что действительно весит, а остальное лучше держать в основном чанке.
