# Компоненты и шаблоны

## Теория

### Компонент: что описывает декоратор

`@Component` — это описание того, как класс превращается в элемент на странице:

```ts
@Component({
  selector: 'app-ticket-card',   // как компонент вызывается из шаблона
  imports: [TicketBadge],        // область видимости этого шаблона
  templateUrl: './ticket-card.html',
  styleUrl: './ticket-card.css', // единственное число; styleUrls — старый вариант
  host: { class: 'ticket-card' }, // биндинги на хост-элемент
  // encapsulation по умолчанию Emulated, changeDetection по умолчанию OnPush
})
export class TicketCard {}
```

Селектор — не обязательно имя элемента. Компилятор сопоставляет разметку с CSS-подобным селектором, поэтому возможны варианты:

- `'app-ticket-card'` — элементный селектор, обычный случай для компонентов;
- `'[appHighlight]'` — атрибутный, обычный случай для директив (глава 06);
- `'button[appPrimary]'` — комбинация: «только на `button` с этим атрибутом»;
- `'.ticket-card'` — по классу; встречается в библиотеках, для своего кода почти не нужен.

### Шаблон компилируется, а не исполняется

Шаблон Angular — не JSX. JSX — это синтаксический сахар над вызовами функций: он превращается в JS и исполняется как обычный код. Шаблон Angular — отдельный язык, который **компилятор разбирает на этапе сборки** и превращает в две функции внутри класса компонента.

```
┌────────────────────────────────────────────────────┐
│ ticket-card.html                                   │
│ <h3>{{ ticket().title }}</h3>                      │
│ <span [class.urgent]="isUrgent()">                 │
└────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────┐
│ компилятор Angular (AOT), время сборки             │
│ разбирает шаблон, проверяет типы выражений         │
│ (strictTemplates), сопоставляет теги с селекторами │
│ из imports этого компонента                        │
└────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────┐
│ две функции, вписанные в класс компонента          │
│ create: создаёт узлы и слушатели один раз          │
│ update: перечитывает выражения биндингов           │
└────────────────────────────────────────────────────┘
                           │
                           ▼
┌────────────────────────────────────────────────────┐
│ DOM                                                │
│ узлы живут между проверками; меняются              │
│ только значения тех биндингов, что изменились      │
└────────────────────────────────────────────────────┘
```

Из этого следует три практических вещи:

1. **Ошибки в шаблоне ловятся на сборке.** Опечатка в имени свойства, неверный тип в биндинге, незарегистрированный тег (`NG8001`) — всё это диагностика компилятора, а не пустое место в браузере. В v22 компилятор дополнительно ловит на сборке невалидные `@for`, элемент, на который матчатся два компонента, и два входа под одним алиасом.
2. **Выражения ограничены подмножеством.** Не поддерживаются `new`, деструктуризация, побитовые операторы, оператор запятая. Присваивания разрешены только в обработчиках событий. Зато поддерживаются `?.`, `!`, `$any(...)`, пайпы (`| date`), spread в литералах и вызовах, а с v21.2 — стрелочные функции в обработчиках событий.
3. **Разделение «создать» и «обновить» — это и есть модель обновления Angular.** Узлы не пересоздаются: при проверке заново вычисляются только выражения биндингов. А DOM (document object model — живое дерево элементов страницы) трогается там, где значение изменилось.

Отдельно: `update` вызывается при каждой проверке шаблона. Поэтому выражение в шаблоне должно быть дешёвым — это не «один раз при рендере», как в React, а «неизвестно сколько раз».

### Синтаксис биндингов

| В шаблоне | Что делает Angular | В React |
|---|---|---|
| `{{ expr }}` | текстовый узел, обновляется при проверке | `{expr}` |
| `[prop]="expr"` | **свойство** элемента или вход компонента | `prop={expr}` |
| `[attr.x]="expr"` | атрибут через `setAttribute`/`removeAttribute` | `x={expr}` |
| `(event)="stmt"` | слушатель события, `stmt` получает `$event` | `onEvent={fn}` |
| `[(x)]="expr"` | сахар над `[x]="expr"` плюс `(xChange)="expr = $event"` | нет аналога |
| `[class.x]="cond"` | точечно добавляет или снимает один класс | `className=...` |
| `[style.w.px]="n"` | одно свойство стиля с указанием единиц | `style={{...}}` |
| `prop="text"` | статическая строка, выражение **не** вычисляется | `prop="text"` |

Ключевое различие, на котором спотыкаются: **`[x]` пишет свойство, а не атрибут**. `[value]="text"` присваивает `input.value`, а `[attr.value]="text"` вызывает `setAttribute('value', ...)`.

Для большинства HTML-свойств разница незаметна. Она становится критичной там, где свойства нет: `aria-*`, `data-*`, атрибуты SVG (scalable vector graphics), `colspan`. Там нужен `[attr.]`. Обратный случай — `disabled`: атрибут `disabled="false"` всё равно отключит кнопку, потому что важно наличие атрибута, а не значение. А `[disabled]="false"` кнопку не отключит.

Двусторонний биндинг `[(x)]="expr"` не магия и не наблюдение за объектом: это буквально пара `[x]` + `(xChange)`. Свой компонент включается в этот синтаксис, если у него есть вход `x` и выход `xChange` — или, современнее, `model()` (глава 02).

### Control flow

Встроенный control flow (`@if`, `@for`, `@switch`, `@let`) — часть языка шаблонов, ему не нужны импорты:

```html
@if (selected(); as ticket) {
  <app-ticket-card [ticket]="ticket" />
} @else if (loading()) {
  <p>Loading…</p>
} @else {
  <p>Nothing selected</p>
}

@for (ticket of tickets(); track ticket.id) {
  <app-ticket-card [ticket]="ticket" />
} @empty {
  <p>No tickets match the filter</p>
}

@switch (ticket.status) {
  @case ('new')
  @case ('open') { <span class="badge badge-active">Active</span> }
  @case ('pending') { <span class="badge">Waiting for customer</span> }
  @default { <span class="badge badge-done">Closed</span> }
}
```

Что здесь важно знать:

- **`track` обязателен** в `@for` — это не опция, а часть синтаксиса. Он говорит Angular, по какому признаку сопоставлять элементы данных с уже созданными узлами DOM. Внутри блока доступны `$index`, `$count`, `$first`, `$last`, `$even`, `$odd`; во вложенных циклах их можно переименовать через `let`.
- **`@switch` не проваливается** — `break` не нужен. Несколько подряд идущих `@case` могут указывать на один блок (как в примере выше). Запись `@default never;` в конце включает проверку исчерпывающего перебора: если в union-типе появится новый вариант, сборка упадёт.
- **`@if (expr; as alias)`** сохраняет результат выражения в переменную блока — удобно, чтобы не вызывать сигнал дважды.
- **`@let x = expr;`** объявляет локальную переменную шаблона: read-only, видна после объявления и только внутри своего блока, переопределить нельзя. Это способ не дублировать выражение, а не замена `computed` — тяжёлую логику всё равно надо уносить в класс.

### host-биндинги

Хост-элемент — это тот самый `<app-ticket-card>` в разметке родителя. Биндинги на него описываются объектом `host`:

```ts
@Component({
  selector: 'app-ticket-card',
  host: {
    class: 'ticket-card',                       // статический класс
    '[class.ticket-card--urgent]': 'isUrgent()', // условный класс
    '[attr.aria-label]': '"Ticket " + ticket().id',
    '(click)': 'open()',                        // слушатель на хосте
  },
})
```

При конфликте работают три правила. Статический биндинг компонента проигрывает биндингу потребителя. Динамический побеждает статический. А при двух динамических выигрывает host-биндинг компонента. Декораторы `@HostBinding`/`@HostListener` делают то же самое и оставлены исключительно для обратной совместимости — документация прямо рекомендует `host`.

### Стили и view encapsulation

**`ViewEncapsulation`: что происходит со стилями компонента**

| Режим | Механика | Когда брать |
|---|---|---|
| `Emulated` (по умолчанию) | атрибуты `_nghost`/`_ngcontent` плюс перезапись селекторов | почти всегда |
| `ShadowDom` | нативный shadow root: стили не входят и не выходят | жёсткая изоляция |
| `None` | стили уходят в документ как глобальные | тема, ресеты |

Селектор `:host` — это сам хост-элемент. Селектор `::ng-deep` пробивает изоляцию
вниз, но оставлен только для обратной совместимости.

В режиме Emulated компилятор дописывает к каждому селектору из `styleUrl` атрибут, уникальный для компонента, а к элементам шаблона — соответствующий атрибут. Отсюда два постоянных вопроса новичка:

- «Почему мой `.badge` из компонента не действует на дочерний компонент?» — потому что у узлов дочернего компонента другой атрибут. Стилизовать внутренности чужого компонента снаружи нельзя by design; правильный путь — вход/CSS-переменная/класс на хосте, а не `::ng-deep`.
- «Почему глобальный `styles.css` работает везде?» — глобальные стили не переписываются, изоляция односторонняя: снаружи внутрь стили проникают, изнутри наружу — нет.

`:host` в CSS компонента — это его хост-элемент (`:host(.ticket-card--urgent)` — при наличии класса). `:host-context()` существует, но опирается на механизм, который в современных браузерах считается устаревшим.

## Параллели с React

- **JSX — это JS, а шаблон — DSL (domain-specific language, предметный язык).** В JSX доступен весь язык, поэтому цена ошибки — рантайм. Шаблон Angular компилируется и типизируется (`strictTemplates`), поэтому большая часть ошибок в разметке становится ошибками сборки. Плата — ограниченное подмножество выражений: нельзя написать `items.reduce(...)` с колбэком-объявлением, нельзя `new Date()`. Логика уходит в класс, и это не стилевое предпочтение, а требование языка шаблонов.
- **`prop={expr}` против `[prop]="expr"` и `prop="text"`.** В JSX фигурные скобки — единственный способ передать не-строку, и забыть их сложно. В Angular `prop="t"` — валидная разметка, просто передающая строку `"t"`; при `strictTemplates` это чаще всего поймает компилятор по несовпадению типов, но с `string`-входом ошибка пройдёт молча.
- **`key` против `track`.** Обе вещи про идентичность элементов, но `key` в React — опциональный проп с предупреждением в консоли, а `track` в Angular — обязательная часть синтаксиса `@for`. Семантика последствий одинакова: неверный ключ или `track $index` при сортировке приводит к пересозданию/перепутыванию узлов и к потере состояния DOM (фокус, позиция скролла, значение неконтролируемого инпута).
- **Двусторонний биндинг — сахар, а не наблюдение.** В React состояние формы всегда «контролируемое»: `value` + `onChange`. `[(x)]` в Angular — тот же паттерн, просто записанный одним токеном: `[x]` + `(xChange)`. Никакого отслеживания мутаций объекта, как в старом AngularJS или в Vue, здесь нет.
- **Где ломается привычка:** в React вы спокойно пишете `{items.filter(f).map(m)}` прямо в разметке — функция компонента вызывается ограниченное число раз, и стоимость предсказуема. В Angular то же выражение попадает в `update`-функцию и исполняется при каждой проверке шаблона. Хуже того: `filter`/`map` возвращают **новый массив каждый раз**, поэтому `@for` видит новую ссылку и делает лишнюю работу по сопоставлению. Производные данные в Angular считаются в `computed` (глава 02), а не в шаблоне.

## Что увидишь в legacy-коде

- **Структурные директивы вместо блоков:** `*ngIf="cond"`, `*ngIf="cond; else other"` с `<ng-template #other>`, `*ngFor="let t of tickets; trackBy: trackById"`, `[ngSwitch]` плюс `*ngSwitchCase`. Здесь `trackBy` — метод класса с сигнатурой `(index, item)`. Работают до сих пор, но новый control flow — не альтернативный стиль, а замена: он быстрее и не требует импортов.
- **`CommonModule` в `imports`** — обязательный спутник `*ngIf`/`*ngFor`/пайпов вроде `date`, `currency`. Если видите его в standalone-компоненте, значит компонент ещё на старых директивах.
- **`[ngClass]="{active: isActive}"` и `[ngStyle]="{width: w + 'px'}"`** вместо `[class.active]`/`[style.width.px]`. Директивы никуда не делись, но точечные биндинги дешевле и типизируются лучше.
- **`@HostBinding('class.active') isActive = false;` и `@HostListener('click', ['$event'])`** вместо объекта `host` — самый частый маркер кода, писавшегося до v17.
- **`styleUrls: ['./x.component.css']`** — массив вместо единственного `styleUrl`. Рядом обычно лежат `encapsulation: ViewEncapsulation.None` «чтобы стили просто работали» и `::ng-deep`/`/deep/`/`>>>` для пробивания изоляции. А ещё шаблонные ссылки `#input` вместе с `@ViewChild('input')` вместо сигнальных queries (глава 02).

## Что добавляем в проект

Support Desk получает типизированную модель тикета, список на статичных данных с `@for`/`@empty` и компонент карточки: бейдж статуса через `@switch`, класс приоритета через host-биндинг, изолированные стили.

## Практическое задание

**Вход:** проект из главы 00 с заглушкой `TicketList`.
**Выход:** список из нескольких тикетов, каждый — отдельный компонент-карточка.

Требования:

1. Заведите модель тикета в отдельном файле: `id` (число), `title`, `status` (`'new' | 'open' | 'pending' | 'closed'`), `priority` (`'low' | 'medium' | 'high' | 'urgent'`), `assignee` (строка или `null`), `createdAt`, `slaHours` (число, опционально). Типы статуса и приоритета — объединения (union), а не `string`.
2. В `TicketList` — статичный массив из 6–8 тикетов; среди них обязательно нераспределённый (`assignee: null`), один со статусом `closed` и один с приоритетом `urgent`.
3. Компонент `TicketCard` показывает заголовок, человекочитаемую подпись статуса, приоритет, исполнителя или «Unassigned», дату создания. Подпись статуса собирается в шаблоне через `@switch`, а не мапой в классе (в этой главе цель — освоить блоки; в главе 06 то же самое станет пайпом).
4. Хост-элемент карточки: статический класс, условный класс для `urgent`, и `aria-label` с номером тикета. Всё — через объект `host`, без декораторов.
5. В `TicketList`: `@for` с корректным `track`, `@empty` с сообщением, `@if` для строки «N tickets / N unassigned», `@let` хотя бы в одном месте, где иначе пришлось бы дублировать выражение.
6. Стили карточки — в её собственном файле; бейдж не должен подтекать в другие компоненты. Общий отступ между карточками задайте так, чтобы за него отвечал список, а не карточка.
7. Ограничение: в шаблонах нет вызовов методов класса и нет `filter`/`map`.

Edge cases на подумать:

- Что произойдёт при `track ticket.id`, если в массиве окажутся два тикета с одинаковым `id`?
- Почему `aria-label` нужно писать через `[attr.aria-label]`, а `disabled` у кнопки — через `[disabled]`?
- `@empty` срабатывает на пустом массиве. А если вместо массива придёт `null` — что увидит пользователь и что скажет компилятор?
- Если в `styles.css` (глобальном) написать `.badge { color: red }`, а в `ticket-card.css` — `.badge { color: blue }`, какой цвет победит и почему?
- Вы поставили `track $index`, а потом добавили сортировку по приоритету. Что визуально сломается и почему это не заметно на неизменяемом списке?

## Разбор решения

`src/app/tickets/ticket.ts` — модель. Отдельный файл, потому что дальше её будут импортировать сервис, форма и HTTP-слой:

```ts
export type TicketStatus = 'new' | 'open' | 'pending' | 'closed';
export type TicketPriority = 'low' | 'medium' | 'high' | 'urgent';

export interface Ticket {
  readonly id: number;
  readonly title: string;
  readonly status: TicketStatus;
  readonly priority: TicketPriority;
  readonly assignee: string | null;
  readonly createdAt: string; // ISO-строка: то, что придёт из API в главе 08
  readonly slaHours?: number;
}
```

`src/app/tickets/ticket-card.ts`:

```ts
import { Component, computed, input } from '@angular/core';
import { DatePipe } from '@angular/common';
import { Ticket } from './ticket';

@Component({
  selector: 'app-ticket-card',
  // пайп date используется в этом шаблоне, поэтому импортируется здесь
  imports: [DatePipe],
  templateUrl: './ticket-card.html',
  styleUrl: './ticket-card.css',
  host: {
    // статический класс: можно было бы писать class="..." на месте
    // использования, но тогда об этом должен помнить каждый потребитель
    class: 'ticket-card',
    // условный класс — точечное включение, без [ngClass]
    '[class.ticket-card--urgent]': 'isUrgent()',
    // aria-label — атрибут, у него нет DOM-свойства, поэтому [attr.]
    '[attr.aria-label]': '"Ticket #" + ticket().id',
  },
})
export class TicketCard {
  // Сигнальный вход: значение читается как функция — ticket().
  // Механику input()/output() разбираем в главе 02, здесь достаточно того,
  // что это типизированный обязательный вход компонента
  readonly ticket = input.required<Ticket>();

  // Производное значение считается в классе, а не в шаблоне:
  // в шаблоне оно пересчитывалось бы при каждой проверке
  protected readonly isUrgent = computed(() => this.ticket().priority === 'urgent');
}
```

`src/app/tickets/ticket-card.html`:

```html
<!-- @let, чтобы не писать ticket() в каждой строке -->
@let t = ticket();

<h3 class="ticket-card__title">{{ t.title }}</h3>

<!-- @switch не проваливается: несколько @case подряд = один блок -->
@switch (t.status) {
  @case ('new')
  @case ('open') {
    <span class="badge badge--active">Active</span>
  }
  @case ('pending') {
    <span class="badge badge--waiting">Waiting for customer</span>
  }
  @default {
    <span class="badge badge--done">Closed</span>
  }
}

<dl class="ticket-card__meta">
  <dt>Priority</dt>
  <dd>{{ t.priority }}</dd>

  <dt>Assignee</dt>
  <!-- ?? вместо тернарника: null и undefined отсекаются одинаково -->
  <dd>{{ t.assignee ?? 'Unassigned' }}</dd>

  <dt>Created</dt>
  <!-- пайп date вместо метода класса: пайп кешируется по входному
       значению, метод исполнялся бы при каждой проверке (глава 06) -->
  <dd>{{ t.createdAt | date: 'mediumDate' }}</dd>
</dl>
```

`src/app/tickets/ticket-card.css`:


Обратите внимание на две вещи в этом коде. Во-первых, `DatePipe` перечислен в `imports` у `TicketCard`, где он используется в шаблоне, и отсутствует у `TicketList` — области видимости шаблонов независимы, «импортировать один раз наверху» здесь не работает. Во-вторых, `tickets` объявлен как `readonly Ticket[]`: массив в этой главе не меняется, а когда начнёт — это будет сигнал, а не мутация на месте.

Ответы на edge cases:

- Дубликат `id` при `track ticket.id` — рантайм-ошибка: Angular обнаруживает, что один ключ соответствует нескольким элементам, и падает с сообщением о дубликате в `@for`. Это лучше, чем тихо перепутанный DOM, и ровно та причина, по которой ключ должен быть уникален по-настоящему, а не «обычно уникален».
- У `aria-label` нет DOM-свойства (в отличие от `id`, `value`, `disabled`), поэтому `[ariaLabel]` просто не за что зацепить — нужен `[attr.aria-label]`. У кнопки, наоборот, есть свойство `disabled`, и биндинг свойства корректно принимает `false`; попытка сделать `[attr.disabled]="false"` оставит атрибут в разметке со строкой `"false"` и кнопка останется отключённой.
- `null` вместо массива: `@for` по `null` — ошибка типизации при `strictTemplates` (сборка не пройдёт). Если тип допускает `null`, писать надо `@for (t of tickets ?? []; track t.id)` — и тогда `@empty` отработает как для пустого массива.
- Победит `.badge` из компонента, но не из-за приоритета Angular, а по обычным правилам CSS. Компилятор дописывает к селектору атрибут, то есть селектор становится `.badge[_ngcontent-abc]` — специфичнее, чем глобальный `.badge`. Полагаться на это как на «изоляцию от глобальных стилей» нельзя: `!important` или более специфичный глобальный селектор всё равно перебьют.
- `track $index` привязывает узлы к позициям. После сортировки элемент с индексом 0 остаётся тем же узлом DOM, у которого просто меняется содержимое, — вместо переиспользования узлов Angular переписывает их все. На неизменяемом списке это незаметно: позиции и данные совпадают. Поэтому ошибка живёт в коде до первой сортировки, вставки в начало или удаления. А потом проявляется как потерянный фокус, съехавший скролл и дёргающиеся анимации.

## Проверь себя

1. Объясните своими словами, почему `[value]="text"` и `[attr.value]="text"` — разные вещи, и приведите два случая, где выбор действительно важен.
2. Что именно `track` сообщает Angular и что физически произойдёт с DOM при `track $index`, если список отсортировать?
3. `[(size)]="value"` на своём компоненте — во что это разворачивается и что должно быть у компонента, чтобы такая запись скомпилировалась?
4. Почему `{{ formatDate(t.createdAt) }}` в Angular — плохая идея, хотя `{formatDate(t.createdAt)}` в React абсолютно нормально? Что делать вместо этого?
5. Как Emulated encapsulation обеспечивает изоляцию и почему из-за неё нельзя стилизовать внутренности дочернего компонента снаружи? Что предлагается вместо `::ng-deep`?

<details>
<summary>Ответы</summary>

1. `[value]` присваивает **свойство** объекта DOM (`el.value = text`), `[attr.value]` вызывает `setAttribute`. Расходятся они там, где свойства нет или где свойство и атрибут живут отдельно. Первый случай: `aria-*`/`data-*`/атрибуты SVG/`colspan` — свойств нет, работает только `[attr.]`. Второй: `input.value` — свойство отражает текущее значение поля, а атрибут `value` — только начальное; биндинг в атрибут не обновит уже введённое значение. Третий типичный: `disabled` — атрибут действует самим фактом присутствия, поэтому `[attr.disabled]="false"` оставит кнопку заблокированной, а `[disabled]="false"` — нет.
2. `track` задаёт правило идентичности: по какому значению Angular узнаёт «это тот же элемент данных, что и раньше», чтобы переиспользовать созданный для него узел DOM и его состояние. При `track $index` идентичностью становится позиция. После сортировки на позиции 0 стоит другой объект данных, но Angular считает его «тем же элементом» и вместо перемещения узла перезаписывает его содержимое — и так по всему списку. Итог: полное обновление всех узлов вместо перестановки, потерянный фокус, сброшенный скролл, испорченные анимации, а в списках с компонентами — лишняя работа их шаблонов.
3. Разворачивается в `[size]="value"` + `(sizeChange)="value = $event"`. Значит компоненту нужны вход `size` и выход `sizeChange` с ровно таким именем (`<имя входа>Change`). Современный способ получить оба сразу — `model<T>()`, который создаёт записываемый сигнальный вход и парный выход автоматически (глава 02).
4. В React тело функции-компонента вызывается ограниченное число раз, и вызов внутри разметки стоит столько же, сколько любой другой код рендера. В Angular выражение попадает в `update`-функцию шаблона и вычисляется при **каждой** проверке этого шаблона — сколько их будет, вы не контролируете. Плюс результат нельзя закешировать: Angular не знает, от чего зависит метод. Правильные варианты: `computed` в классе (мемоизируется по сигналам-зависимостям), чистый пайп (кешируется по входному значению) или заранее подготовленные данные.
5. Компилятор добавляет каждому компоненту уникальный атрибут: узлам его шаблона — `_ngcontent-<id>`, хост-элементу — `_nghost-<id>`, и дописывает этот атрибут ко всем селекторам из `styleUrl`. Поэтому селектор из родителя не совпадёт с узлами дочернего компонента — у них атрибут другого компонента. Это и есть изоляция, и она односторонняя: глобальные стили не переписываются и проникают внутрь. Селектор `::ng-deep` оставлен для обратной совместимости и не рекомендуется. Вместо него дочерний компонент должен сам предоставлять точки настройки: вход, влияющий на его классы, CSS-переменные, которые он читает, или класс на хост-элементе, который потребитель ставит снаружи.

</details>

## Частая ошибка

Самая частая механическая ошибка — забытые квадратные скобки: `<app-ticket-card ticket="ticket" />`. В JSX без фигурных скобок вы бы передали строку и сразу это заметили. В Angular запись выглядит как валидный HTML-атрибут, потому что это он и есть. В компонент уходит строка `"ticket"`, а не объект.

Здесь спасает `strictTemplates`: вход типизирован как `Ticket`, строка не подойдёт, и сборка упадёт с расхождением типов. Но если вход имеет тип `string` — заголовок, id-как-строка, имя иконки, — ошибка проходит молча. И превращается в «почему у всех карточек одинаковый текст». Правило: всё, что не литеральная строка из разметки, передаётся через `[ ]`.

Вторая ошибка — перенос React-привычки считать данные прямо в разметке: `@for (t of tickets.filter(x => x.status !== 'closed'); track t.id)`. Здесь два независимых наказания.

Первое: выражение исполняется при каждой проверке шаблона, а не один раз. Второе, более коварное: `filter` возвращает **новый массив** при каждом вызове. Поэтому `@for` каждый раз получает другую ссылку на коллекцию и вынужден заново сопоставлять элементы по `track` — ровно та лишняя работа, которую `track` должен был предотвратить.

Фильтрация, сортировка и агрегаты живут в `computed` в классе (глава 02). Шаблон только читает готовое значение.
