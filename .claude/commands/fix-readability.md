# /fix-readability $ARGUMENTS

Правь **язык** одной зоны за сессию, не меняя технический смысл и глубину.

Целевая зона: **$ARGUMENTS**

Если аргумент не передан — останови и спроси, какую зону править. Не пытайся угадать и не берись за
весь `content/` сразу: одна зона за сессию, иначе правка вырождается в поверхностную.

---

## Шаг 1. Загрузи контракт и контекст

1. Прочитай `content/STYLE.md` целиком. Это контракт; все правки делаются по нему.
2. Найди раздел этой зоны в `audit/readability-report.md`:
   - таблица оценок A-G по зонам — чтобы знать, какие критерии здесь слабые;
   - раздел «Наблюдения аудиторов по зонам» — паттерны именно этой зоны;
   - раздел «Все конкретные места „до / после“» — уже готовые правки для этой зоны, применяй их
     в первую очередь;
   - раздел «Нерасшифрованные аббревиатуры по файлам» — проверенный вручную список по файлам.
   Если зоны в отчёте нет, работай по `STYLE.md` + флагам из шага 2, и скажи об этом пользователю.
3. Прочитай зонный JSON `audit/readability/*.json` для этой зоны, если он есть — там полные
   `worst_places` с цитатами и вариантами переписывания.

## Шаг 2. Сними метрики «до»

```bash
python3 scripts/audit/readability_flags.py <путь зоны> \
  --json-out /tmp/before.json --md-out /tmp/before.md
python3 scripts/audit/flags_digest.py <collection> [--kind topic-article|question-bank|quiz-bank|course-chapter]
```

Для quiz-банка дополнительно:

```bash
python3 scripts/audit/quiz_bias.py     # смещение ключей и длин вариантов по всем банкам
```

Сохрани числа: `unexpanded_abbrevs`, `long_sentences` и их %, `long_paragraphs`, `theory_walls`,
`caps_emphasis`, `indirect_leads`. Они понадобятся в шаге 5.

## Шаг 3. Правь файл за файлом

Порядок: сначала русская версия файла, сразу за ней английская — так видно расхождения между
локалями. Внутри файла — сверху вниз.

Что делать:

- расшифровать каждую аббревиатуру при первом употреблении **в этом файле**;
- поставить точку там, где тире соединяет два независимых утверждения;
- превратить перечисления через точку с запятой в маркированные списки;
- разбить абзацы длиннее ~6 строк;
- переписать первое предложение раздела так, чтобы оно отвечало, а не разгонялось;
- сократить блок «Частая ловушка / Common pitfall» до двух-трёх коротких предложений;
- заменить ALL-CAPS-выделение на `**жирный**`;
- убрать смешанный алфавит, непереведённый английский и изобретённые транслитерации в RU;
- заменить идиомы уровня C1 в EN на нейтральные слова, пересчитав длину предложений по своему
  порогу 25 слов;
- английскую версию **разбить заново**, а не скопировать структуру русской.

**Для банков вопросов дополнительно:** первое предложение каждого ответа = прямой ответ на
заданный вопрос простыми словами. Если ответ начинается с код-блока, вводного ярлыка
(`**Модель Pages Router:**`) или описания мира до фичи — перенеси лид-предложение наверх; оно почти
всегда уже существует ниже по тексту.

**Для quiz-банков дополнительно:** это единственное место, где правка выходит за пределы языка.
Проверь и починить: распределение `correctIndex` (сейчас перекос в 0), сопоставимость длин вариантов,
ссылки на позиции («Вариант B»), противоречия со статьями и банком вопросов той же темы, наличие
правильного варианта, верность ключа. Каждое такое изменение показывай пользователю отдельно и
объясняй — это смена содержания, а не языка.

### Запрещено

- менять поведение или смысл код-примеров;
- удалять технические детали, оговорки, крайние случаи, версии, числа;
- понижать уровень материала;
- менять структуру файлов: переименовывать, сливать, разбивать, менять порядок разделов, менять
  frontmatter и `id` записей;
- трогать файлы за пределами зоны из `$ARGUMENTS`;
- править `<!-- verified: … -->` — если контент менялся по смыслу, скажи об этом, но не меняй маркер
  сам.

### Правило сохранности фактов

После каждого файла сверь: все факты из «до» присутствуют в «после». Если предложение было длинным
потому, что несло три факта — стало три предложения, а не два факта.

## Шаг 4. Подтверждение по каждому файлу

Не переходи к следующему файлу, не показав пользователю по текущему:

1. список правок компактно — по одной строке на правку, с указанием критерия (A/B/C/D/E/F/G);
2. 2-3 самых существенных места целиком в формате до/после;
3. всё, что пришлось решать на своё усмотрение (спорный термин, неоднозначная формулировка);
4. всё, что ты заметил, но **не** стал править, потому что это выходит за рамки языка — ошибка в
   коде, неверный факт, противоречие с другой статьёй. Такие места выписывай отдельным списком, они
   пойдут в `audit/backlog.md`.

Дождись «ок» и только потом следующий файл.

## Шаг 5. Метрики «после» и разница

```bash
python3 scripts/audit/readability_flags.py <путь зоны> \
  --json-out /tmp/after.json --md-out /tmp/after.md
```

Покажи таблицу «до → после» по зоне и по худшим файлам:

| Метрика | До | После |
|---|---|---|
| нерасшифрованных аббревиатур | | |
| предложений сверх лимита (и %) | | |
| длинных абзацев | | |
| стен теории | | |
| ALL-CAPS-выделений | | |
| непрямых лидов (для банков) | | |
| флагов на 1000 слов | | |

Числа должны улучшиться по всем строкам. Если какая-то метрика выросла — объясни, почему это
осознанно (например, разбитое предложение добавило абзац), либо откати.

## Шаг 6. Итог сессии

- одна строка: что за зона, сколько файлов, какие критерии подняты;
- список найденного-но-не-исправленного (для бэклога);
- предложение следующей зоны по `audit/backlog.md`.

Коммит делай только если пользователь попросил. Сообщение: `content: readability pass on <зона>`.
